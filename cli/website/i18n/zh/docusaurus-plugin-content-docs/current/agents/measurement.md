# 评估规则

护轨机制承诺，人们将**确切了解**模型在他们自己的句子上表现如何——而不是承诺模型本身有多好。这一承诺建立在少数几项规则之上，其中大部分规则是强制执行的。本页准确陈述了这些规则，并在文末说明了如何表述具体数值。

## 评分标准 (standard/1)

每一次新的运行都以相同的方式评分 (`arena/mt_eval_harness/scoring.py`)：

- **核心指标：** 语料库级别的 **chrF++**（词序为 2 的 sacreBLEU chrF），取值范围为 0 到 100——数值越高代表越接近参考译文——附带其 **95% 自助抽样区间**及 sacreBLEU 签名。记作 `chrF++ 47.5 [45.9, 49.0]`。
- **计入哪些句段：** 核心指标、其区间以及所有对比均遵循同一规则。翻译失败的句段视为空输出——绝不丢弃，也绝不作为占位符参与评分；没有参考译文的句段在任何情况下均予以排除。
- **区间：** 核心指标专属的区间——基于这些句段的百分位自助抽样，进行 1,000 次重采样，随机种子为 12345，α 为 0.05。句段数低于 30 时，工具会发出警告，提示该区间的覆盖可能不足；少于 2 个句段时则不提供区间。
- **并列列出，绝不混合：** BLEU、spBLEU、TER，以及计算过的 COMET，各自附带其签名或模型 ID。
- **独立诊断项：** 精确匹配、等价匹配、FST 接受度、形态准确率、语义验证器、语码转换、幻觉、术语一致性、书写风格。它们绝不计入核心指标，也绝不参与排序。
- **“更好”是指 chrF++ 上的配对显著性检验**，绝不是肉眼比对两个数字。
- **无质量等级标签。** 只有人工评估才能证明质量。

**已废弃：** 加权综合评分与质量等级标签。standard/1 运行卡片包含 `composite: null` 与 `quality_tier: null`。**注意。** 绝不展示、计算或引用综合评分或等级，即便来自旧卡片也不例外。

**评分警示**是附在评分旁边的诊断信息，绝不是对评分本身的修改：`source_copy`（一半或以上的输出复制了原文）、`length_inflation` 与 `length_deflation`（输出长度超过参考译文的两倍，或不足其一半——平均而言，或在四分之一及以上的句段中）、`near_constant_output`（同一个输出在多个原文中重复出现）以及 `train_test_near_twin`（测试行在训练集中存在孪生样本——当半数或以上存在时为重大警示）。**注意。** 传递评分时必须一字不差地附带每一条警示。

## 门控评估

当一次运行包含门控链（[方法与门控](/docs/agents/methods#gate-chains)）时，**所评估的即所交付的**：

- 核心 chrF++ 对门控输出进行评分；
- 未经门控的 chrF++ 及其区间并列显示 (`overall.gates.ungated`)；
- **拒绝率**——门控拒绝的句段 ÷ 参与判定的句段——是一个独立的数值，按门控以及最终交付的内容进行统计 (`shipped_from`：方法、源文本、回退选项、无内容)；
- 门控链的**指纹**（其规范 JSON 的 sha256）随报告和任何已发布的运行一同留存。

**锁定机制。** 评估中不允许回退：在翻译或产生任何开销之前，`mt-eval run` 和 `mt-eval test` 会直接拒绝将其门控拒绝句段转入回退分支的门控链。

**注意。** 报告门控评分时，必须同时报告未门控评分及拒绝率。仅凭门控评分会掩盖被门控过滤丢弃的内容。

## 数据集及其各自用途

| 角色 | 用于 | 读取方式 |
|---|---|---|
| `train` | 学习 | 从不作为结果计分 |
| `dev`（练习） | 选择检查点；评判改进轮次（从 50 个句子起）；词典基线 | 自由读取 |
| `test` | 里程碑：对照社区预测测试模型 | 每次评分读取都需要预注册（forge）；每次读取都会记录 |
| `sealed` | 持有者之外无人可见的测试 | 一次 |

**在 nmt-forge 中**（注册中心，`.forge/eval-registry.json`；账本）：

- **锁定机制。** 对已注册数据集的每次读取都会写入哈希链账本，并附带其目的 (`score`, `dev-selection`, `audit`, `inspect`)。
- **锁定机制。** 对测试集评分需要针对其当前内容进行有效的预注册。
- **锁定机制。** 封存集仅评分一次。第二次评分会被拒绝（`sealed set '<name>' has already been spent`); a single `mt-eval` 对封存文件的读取也会消耗掉它。`--override-respend '<reason>'`（位于 `nmt-forge score` 和 `nmt-forge compare` 上）会被写入账本。`export` 拒绝再次消耗，并指明 `--no-eval`。
- **锁定机制。** 开发隔离带：训练需要注册的 `dev` 集；开发集行与测试集或封存集不得共享完全相同的原文或译文；训练集行不得为开发集行。

**在 mt-eval 中：**

- **注意。** `mt-eval run` 和 `mt-eval compare` 可以在没有任何预注册的情况下对测试集或封存文件进行评分，且绝不会因读取次数而拒绝。只有当 forge 创建过读取日志时，`mt-eval run` 才会向文件的读取日志 (`<file>.reads.jsonl`) 追加一行；`compare` 和 `test` 不记录任何内容。在社区群众的预测写下之前，绝不要使用 mt-eval 对测试集进行评分。

## 预测

```bash
nmt-forge prereg new first-model --eval-set project-test --expect "<their words>" --rationale "<their reason>"
nmt-forge prereg new round-2 --eval-set project-test --predictions predictions.json
nmt-forge prereg template --out predictions.json
```

- `--expect` 和 `--rationale`：一条用社区群众自己的话写成的关于 chrF++ 的自由文本预测。其结论由群众判定：`nmt-forge prereg verdict <id> --prediction <n> --held` (or `--missed`) `--by "<who>"`。
- `--predictions <file>`：一个 JSON 数组；每条预测指明一个 `metric` 和一个 `rationale`，以及一个带有 `baseline_score`（和可选的 `margin`）的 `direction`（`increase`、`decrease`、`no_change`）——由工具判定——或者自由文本 `expect`。
- **锁定机制。** 在对该数据集进行过任何评分读取（由 forge 或 `mt-eval run` 执行）之后写下的预测将被拒绝：*“eval set '…' was already read for scoring (N time(s): …) before this preregistration”*。`--allow-after-reads` 允许放行，且每份报告、导出和状态信息中都会对此予以说明。
- **注意。** 预测属于社区群众，是在产生任何评分之前写下的，绝不要由你来改写或缩小范围。护轨系统的问题不会暗示任何数字（*“此处不暗示任何数字，以确保猜测纯粹来自他们自身”*）；你也不要提供任何数字。

## 近似副本

`nmt-forge leak-audit` 将每个训练对与所有已注册的开发集、测试集和封存集进行比对：

| 发现项 | 规则 | 处理方式 |
|---|---|---|
| 相同文件 | sha256 | 丢弃 |
| 完全复制 | 归一化后原文相同或译文相同 | 丢弃 |
| 近似副本 | 目标词集重叠度 ≥ 0.6（Jaccard，且一方包含另一方），或 ≥ 0.9 | 丢弃 |
| 模板近亲 | 句式框架相同，内容不同 | **保留**以供学习，并进行计数，以便在包含或不包含这些测试行的情况下解读评分 |
| 仅原文匹配 | 提示句相同，内容不同 | 保留并报告 |

短句通过字符三元语法进行比对；极短的句子仅通过完全匹配进行比对。当训练集行与测试集行完全相同或在任一侧重叠 ≥ 0.6 时，该测试行即为**近似孪生样本**；当测试行有一半或更多具有孪生样本时，该评分在很大程度上反映的是记忆回溯而非翻译能力，属于重大警示。`--clean-to` 写入筛查后的文件；`--drop-test-twins` 还会丢弃与测试行孪生的训练行，以获得排除孪生样本后的评分。

护轨系统的首次开发集划分应用了相同的阈值：`nmt-forge split` 上的 `--near-dupe 0.6` 会保留单词重叠度 ≥ 0.6 的行在开发集/训练集边界的同一侧，因此首次开发集评分不会带有后续轮次筛查所排斥的近似副本记忆。`--max-group` 将近似副本组的大小限制在开发集大小的一半加一以内，以便从模板写成的文件仍能进行划分。

**注意。** 只有根据 `true_now` 或审计自身的输出时，才能表述“数据泄露审计发现……”，绝不要自行断言“测试集是干净的”。

## 词典底线

`nmt-forge floor <word lists>` 使用词典逐词翻译开发集（最长短语优先），并使用与运行的开发集评分相同的代码进行评分：chrF++ 及其 95% 区间。它在当前计算机上运行，绝不读取测试集，仅记录词典的名称、哈希值和词条数量、覆盖了多少源语言单词以及评分。只有当一次运行的开发集区间下限高于词典底线的区间上限时，该运行才算**突破底线**；`nmt-forge status` 会对未能突破底线的运行发出警告。

## 比较两个模型

**改进轮次** (`nmt-forge compare-runs <in-use> <new>`)：两个模型对**同一批开发集句子**的翻译，逐行配对；进行配对近似随机化检验（1,000 次试验），并计算差异的 95% 自助抽样区间。

| 判定 | 规则 |
|---|---|
| **过少** | 开发集句子少于 50 句，无论得分如何 —— 保持当前使用的模型，由说话人的盲测评分决定（见下文） |
| **更好** | 50 句或更多，p < 0.05 **且** 区间下限大于 0 —— 提供新模型供选用；仅在社群同意时才投入使用 |
| **更差** | 50 句或更多，p < 0.05 且区间上限小于 0 |
| **无变化** | 其他任何情况 —— 保持当前使用的模型 |

**为什么是 50。** 在虚构测试语言的 ByT5-small 输出上进行测定，每个规模测试 100 组随机练习集，采用本规则：在 23 个 dev 句子时，它在 100 次中有 9 次将两个相近的模型（在 500 个句子上相差 0.7 chrF++）判定为不同，并且在 100 次中仅有 21 次将真实的 +5.9 chrF++ 提升判定为 **better**；在 50 个句子时，这两个数值分别为 100 次中 4 次和 96 次。在 10 次中有 8 次能观察到的最小差异：23 个句子时为 8.1 个 chrF++ 点，50 个句子时为 5.8，100 个句子时为 4.0，200 个句子时为 2.8。因此，当有 200 对或更多句子时，rails 的首次划分会预留至少 50 个 dev 句子——占筛选后句对的十分之一，最多 500 个；少于 200 对时，占四分之一，即少于 50 个——并且审核表会用练习行来扩充该集合：在少于 50 个时每两行扩充一行，直至达到 200 个时每四行扩充一行。

每项判定结果还会说明其开发集能可靠检测出的最小差异（10 次中有 8 次）：区间宽度 × (1.96 + 0.84) ÷ (2 × 1.96)。当该数值超过 3 个 chrF++ 点数时，“no-change”是开发集本身的灵敏度局限，而非证明该轮次毫无作用。开发集还参与挑选了新一次运行的检查点，这会轻微偏向新模型——在转述判定结果时**请务必说明这一点**。

母语者对较新模型的盲测偏好（见下文）仅在 **too-few** 或 **no-change** 裁定后才会让 forge 提议启用该模型——绝不会在 **worse** 之后提议——且需社区首先同意（`improve-promote`，模式 `confirm`）。对某次晋升所替换的原模型的盲测偏好绝不会直接恢复该原模型：轮次报告的操作会询问社区。

**任意两次运行** (`mt-eval compare <report> <report> --significance`)：默认使用近似随机化检验（另一种方法为 `--method paired_bootstrap`），1,000 次试验 (`--n-bootstrap`)，α 为 0.05，种子为 12345，基于两份报告按 ID 共享的条目进行比对（少于 10 条会发出警告）。先检验 chrF++，随后是次要指标。每对运行均会进行检验；不存在多重假设检验校正，输出中会对此予以说明。

## 心愿单的导向依据

`nmt-forge analyze` 按句子类型细分一次运行的开发集 chrF++（该类型在开发集中至少有 5 个句子）。只有当某种类型的句子得分低于其余句子的差距的 95% 区间完全大于零时（句子级 chrF++ 的 Welch 区间），该类型才被归为**最薄弱**——并在心愿单中赋予权重。可能由随机偶然导致的较低得分会如实报告（*“……可能是偶然因素——心愿单不会据此调整导向”*），且绝不计入表格权重。

其“从未见过的词”部分要求为每个词提供两到三个表达不同含义的句子，而不是仅提供一句：在人工构造的测试语言上，训练中出现过一次的词翻译正确的概率为 27–29%，而出现过 2–4 次的词翻译正确的概率为 63–95%；在 3,200 个训练句的规模下，使用按包含最多新词筛选出的句子训练 ByT5-small，在 500 个保留句中意义正确的比例为 39.4%，而使用日常句子训练的这一比例为 53.4%，且耗费了母语者稍多一点的时间（约 57 小时对比 54 小时）。

## 母语者的评分标记

在每个 improve 轮次中，说话人会对模型给出的新句子草案标记 `Y`、`N` 或 `?`。正确率即为 `Y ÷ (Y + N)`（不计 `?`、未标记的行、练习行和再次显示的行），并附带 95% Wilson 区间。两轮之间的上升只有在满足以下条件时才算作**进展**：上一轮的区间整体高于第一轮；两轮之间换用了新模型——由社区成员选定（forge 的 `export` 和 `choose` 记录），无论是在 **better** 判定之后、根据说话人的盲测标记选定，还是凭他们自己的决定选定；仅凭 **better** 判定本身并不算数——**并且**说话人对各次晋级模型的盲测（见下文）在中间各轮汇总后，标记新模型正确的频率明显高于被替换的模型（|z| > 1.96）。
这些句子是任何模型都未见过的：这是最重要的指标，也是最先要看的依据（参见[辅导](/docs/agents/coaching)）。

**双模型盲测。** `champollion improve sheet` 会让第二个模型为草案行中以随机种子选出的一半（`nmt-forge draft-newer`）生成草案，且不做标记：如果最新训练的模型不是当前使用的模型——例如在判定为 too-few、no-change 或 worse 的轮次之后——则由该模型生成；或者在晋级后的下一次访问中，由被替换掉的模型生成。哪一行属于哪个模型记录在表格旁的 `improve/round-<k>/sheet-key.json` 中（包括 `in_use`、`other`、`relation` `newer` 或 `replaced`、各模型的训练配对数 `in_use_pairs` 和 `other_pairs`、`other_rows`，以及下文的 `repeat_rows`）。
随后 `champollion improve marks` 分别统计两个模型的数据，所有统计中均不计再次显示的行：

- 上述正确比例（即进展衡量指标）仅统计当前使用的模型的行；
- 每条标记为正确的草稿和每处修改都会成为一个训练句对，无论由哪个模型生成草稿；
- 双比例检验（合并样本，双尾 5%：|z| > 1.96）表明母语者是否更频繁地将某个模型标记为正确：`clear` 为 `newer` 或 `replaced`（另一个模型）、`in-use` 或 `neither`，记录在 `marks.json`（`blind`）中，包含两组计数（`in_use_right`、`in_use_judged`、`other_right`、`other_judged`、`in_use_share`、`other_share`）、`other`、`relation` 以及双方的训练句对计数；与较新模型的对比还会保留 `newer`、`newer_right`、`newer_judged` 和 `newer_share`。当任一模型没有被标记为 `Y` 或 `N` 的行时，`clear` 为 `null`，文本提示 *"too few rows of one model were judged to compare"*；
- 与较新模型对比时，若各模型至少有一条草稿完成评审，计数将传至 forge（`nmt-forge speaker-verdict`），后者运行相同的检验，并在其账本（`improve-speaker`）中记录 `clear`（`newer`、`in-use` 或 `neither`）。在该运行得出 **too-few** 或 **no-change** 裁定后，`clear: newer` 会促使 forge 提议启用较新模型；随后 `champollion improve marks` 打印输出 *"forge recorded it: it offers to put the newer model to use (the people say yes first)"*（[训练](/docs/agents/training#the-improve-rounds)）。

这些行是在同一张表格上随机分配的，由同一位母语者针对该家庭自己的新句子进行评判——因此明显的差异能够揭示开发集因规模过小而无法展现的信息，且母语者评判严格程度的变化对两个模型的影响是一致的。**注意。** 在读取评分标记之前，绝不要告诉母语者哪些行来自哪个模型。

**再次显示的行。** 从第 2 轮开始，表格中每有 10 个新句子，`champollion improve sheet` 就会放回一行（`REPEAT_EVERY`；向下取整，符合条件的行较少时放回的也较少）：这是说话人在之前表格中标记为 `Y` 或 `N` 的草案，连同其先前的草案一起，不做标记，放在以随机种子决定的位置——绝不会是练习行、本身就是重复项的行、已经再次显示过的行，或者本表格中的句子。表格第一行（表头上方）写道：*“下方有几行是特意从之前的表格中重新放回的。请当作新句子重新标记：标记一致的频率反映了它们的可靠程度。”* 表格中绝不会指出是哪些行；`sheet-key.json` 将它们记录为 `repeat_rows`（`row`、`from_round`、`from_row` 以及之前的标记 `mark`）。每行大约花费说话人 10 秒时间。

`improve marks` 仅对照说话人自己先前的标记来评判每一行：重复项绝不会计入本轮的比例中，绝不会再次作为训练配对，也绝不会参与盲测对比。`marks.json` 包含 `repeats`：`shown`、`judged`（本次标记为 `Y` 或 `N`；标记为 `?` 或留空则只显示、不评判）、`agreed`、`agreement`（一致数 ÷ 评判数）、`wrong_to_right`、`right_to_wrong`、`wrong_before`（曾被标记为 `N` 的已评判行）以及 `rounds_apart_wrong_before`。它会输出 *“再次显示的行：说话人对 J 行中的 A 行做出了与之前一致的标记（P%）——W 处曾错现对，R 处曾对现错。不计入本轮比例，也不再用于训练。”*

跨轮次汇总后，一旦评判数达到 10 行或更多（`MIN_REPEATS`），轮次报告便会从中解读出两项内容：

- **随机误差** `e`，来自两个方向对称变化的翻转。对同一个草案的两次标记因偶然因素出现不一致的概率为 2e(1 − e)，两个方向各占一半；设 d = 2 × min(`wrong_to_right`, `right_to_wrong`) ÷ `judged`，则 e = (1 − √(1 − 2d)) ÷ 2。误差会将所有比例拉向 50%：真实正确比例为 p 的草案被标记为正确的概率为 e + p(1 − 2e)，因此在 e = 10% 时，“真实 80% 正确”读出的大约是 74%。
- **漂移**：超出对称翻转的单向翻转。当“曾错现对”的翻转明显多于反方向时，报告会发出警告，提示标记标准可能变宽了：翻转达到 6 次或以上且符号检验满足 (`wrong_to_right` − 翻转数 ÷ 2) ÷ √(翻转数 ÷ 4) > 1.96。

其校验提示行如下：*“说话人对再次显示的 J 行中的 A 行做出了与之前一致的标记（P%）：约有 E% 的标记因随机因素发生反向变动，这会将所有标记正确的比例拉向 50%——预测中已对此做了修正。”*——对于漂移，则提示：*“且有 W 处曾标记为错误的草案现在标记为正确，而反向变动的仅有 R 处：标记标准可能变宽了，而正确率的上升并不能反映出这一点。”* 评判数不足 10 行时显示：*“再次显示的行目前已评判 N 行——说话人自身的标记误差将从 10 行起开始估算。”*

**轮次走向预测。** 轮次报告的预测仅在正确率低于 80% 且存在实际进展（见上文）时进行。学习曲线在训练数据每翻一倍时，对数几率大致呈均匀阶跃上升，因此它从晋级后的相同盲测中读取阶跃值：即 `logit(in_use_share) − logit(other_share)` 之和除以 `log2(in_use_pairs ÷ other_pairs)` 之和（比例截断在 1–99% 之间），其 95% 区间基于各比例的方差计算，评判 n 个草案时方差约为 1 ÷ (n·p·(1 − p))。它根据在用模型的训练配对数给出还需要多少配对才能达到 80% 标记正确——即预估值——以及按每个句子 70 秒计算所需的说话人小时数。该范围涵盖了阶跃区间的波动（在最多翻六倍之外不再设上限），并且在评判了 10 个再次显示的行之后，涵盖了在此说话人的标记习惯下“真实 80% 正确”可能对应的位置：e + 0.8(1 − 2e) + 0.2 × K，最高为 97%，其中 K 是每轮漂移（超出对称翻转的翻转数除以曾错行的两次标记相隔的轮次数）乘以首次与最后一次标记之间的轮次数，上限限制在 ±30% 以内。下限值是阶跃上限对应的两个目标中较小的一个，上限值是阶跃下限对应的两个目标中较大的一个；下限值为 0 时显示为“无”。正文中随后补充：*“说话人自身的标记：他们对再次显示的 J 行中的 A 行做出了与之前一致的标记（P%），因此约有 E% 的标记因随机因素发生反向变动……真实 80% 正确的草案在他们的标记下可能约有 T% 的时间被标记为正确——该范围已将此考虑在内。”*（当 K 在任意方向达到 1% 或以上时，还会附带说明曾标记为错误的草案现在标记为正确的频率高出或低出多少）；在此之前则显示：*“（尚未计入说话人自身的标记误差：评判的再次显示行数过少。）”* `report.json` 将这些数值记录为 `projection_numbers`（`more_sentences`、`range`、`speaker_hours`）。

在模拟中——带有噪声的说话人、rails 自带的开发集划分以及这些判定规则，在两组随机种子下每个场景进行 200 次试验——在每轮 400 个新句子时，预估值落在真实数量 2 倍以内的概率为 69–78%，在 800 个时为 53–56%；而真实数量落在区间内的概率分别为 89–94% 和 76–80%（不含重复项时为 91–93% 和 51–54%）。若将预估值本身根据说话人的标记进行平移，在每轮 800 个时有所改善，但在 400 个时表现更差（2 倍以内的概率分别为 64% 和 19%），因此预估值仍保留朴素的 80% 目标。我们曾尝试添加“模型可能已经可用”的提示，后被弃用：它每对一次就会错上 2 到 3 次。仅供粗略参考，特此说明。

## 数据未说明的内容

- 评分反映的是系统在该数据集上的整体表现，而非任何单句表现：不存在单句置信度。
- chrF++ 衡量的是与参考译文的重叠程度。用词不同但表意优良的译文可能得分较低；流畅但错误的译文可能得分相当高。
- FST 接受度只能说明词汇存在，不能说明句子表达的含义正确。
- 已发布的排行榜行默认由各方自行报告；验证器仅对照锁定哈希的语料库对提交的输出重新评分（误差在 1.0 chrF++ 以内），并不会重新运行方法。

## 如何汇报数值

每一个数值都必须附带**其单位、衡量内容以及测试所在的数据集**——并附带数据集的规模以及区间（若存在）。

| 应表达为 | 切勿表达为 |
|---|---|
| "在 50 个练习（dev）句子上，chrF++ 为 24.1 / 100，范围 20.6–27.6" | "24.1" · "准确率 24%" |
| "母语者标记了 24 条新草稿中的 9 条为正确——38%（21%–57%）" | "准确率 38%" |
| "无显著可测变化：在 50 个 dev 句子上仅约 5.8 点的差异才能显现" | "它略有提升" |
| "练习句子太少，尚无法判断：少于 50 个，对比无法判定——将由母语者的盲测标记决定" | 对 **too-few** 裁定表述为 "无变化" |
| "在 50 个锁定的测试句子上，单次评测，对照您所写的预测：'……'"（重读他们的原话） | 未附带测试集或预测的测试得分 |
| "盲测下，在新句子上，母语者标记较新模型 12 条中有 7 条正确，当前模型 12 条中有 5 条正确——在 24 个句子上无明显差异" | 仅凭标记即断言 "新模型更好" |
| "门控后 chrF++ 为 31.0（发布内容），未门控为 33.5，12% 被门控拒绝" | 仅提供门控后得分 |

- 区间反映的是工具的确信程度，而不是两个结果。
- 不同数据集上的两个评分不可相互对比。同一数据集上的两个评分只有在配对检验证明存在差异时才算有差异。
- 引用警示和警告时须一字不差。
- 绝不要用“好”或“坏”来评价评分；绝不要附加表示质量好坏的定性词。唯有流利的母语者才能决定什么适合投入使用。
