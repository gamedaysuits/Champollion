# 当你将数据主权写入软件时，它意味着什么

:::info[适用人群]
所有人。不要求具备法律、机器学习或原住民治理的背景知识。如果你曾想过，一旦计算机介入，一个社区究竟需要付出什么才能保持对其自身语言数据的控制权，本页面就是那个详尽的答案。
:::

大多数关于数据和同意的讨论都止步于许可：是否有人同意了。数据主权则提出了一系列更棘手的问题。谁**拥有**它？谁决定如何处理它？谁能访问它？它在物理上存放在哪里？

这些问题并非凭空出现。它们最早且最有力地由原住民提出。

---

## 1. 问题所在——以及最初提出它们的人

加拿大的第一民族（First Nations）提出了**所有权、控制权、访问权和占有权**（ownership, control, access, and possession）的数据主权原则，以此主张对自己信息的管辖权——这源于一段有据可查的历史：过去的研究往往是*针对*社区进行，而非*与*社区合作开展，且研究产生的数据从未归还给他们。

这一渊源并非微不足道的细枝末节。它们不是任何人都可以随手拿来套用的通用伦理清单；它们是特定人群在特定的法律和文化背景下对管辖权的主张，属于提出它们的社区本身。

简要概括这四个问题：

| | 它回答的问题 |
|---|---|
| **Ownership**（所有权） | 谁拥有这些信息？社区集体拥有其文化知识和数据——就像个人拥有自己的个人信息一样。 |
| **Control**（控制权） | 谁决定如何处理它？社区控制涉及他们的任何事物的每一个阶段：收集什么、如何收集、由谁收集、为了什么目的收集，以及之后如何处理。 |
| **Access**（访问权） | 谁能访问它？社区必须能够访问关于他们自身的信息，无论这些信息存放在哪里，也无论由谁持有。 |
| **Possession**（占有权） | 它在物理上存放在哪里？与所有权不同——占有权是保管的具体事实，它是使其他三项原则具有可执行性而不仅仅是承诺的机制。 |

存在着多种不同的框架，且它们之间不可互相替代：例如广泛适用于原住民数据治理的 **CARE**（集体利益、控制权威、责任、伦理）原则，以及针对毛利（Māori）数据主权的 **Te Mana Raraunga** 等。每个框架都诞生于各自独特的法律与文化环境之中。将一个框架的名称套用到另一个框架的原则之上，本身就是一种抹煞。

---

## 2. 为什么软件让这个问题变得尖锐

一项原则可以作为一种良好的意愿停留在纸面上。但软件迫使我们直面这个问题，因为计算机不凭意愿行事——它只根据被构建的代码运行。

想想评估翻译系统的常规方式。为了弄清楚一个系统是否能很好地翻译你的语言，人们需要一个**测试集（test set）**：用你的语言编写的句子，以及它们对应的含义。几乎每个评估平台都会要求你**上传**该测试集，以便对其进行评分。

带着那四个问题再读一遍。上传转移了占有权。它通常也转移了实际的控制权——一旦副本存在于别人的机器上，你说“停止”的能力就只是一种请求，而不是一种能力。访问权变成了你被授予的东西，而不是你拥有的东西。所有权只停留在纸面上，失去了实际意义。

对于一个语言数据曾被榨取的社区来说，“上传它并相信我们”并不是一个中立的请求。它与已经发生过的事情如出一辙。

---

## 3. 实际的机制是什么

本项目的立场是，如果主权是真实的，它就必须是软件的一种属性，而不是政策中的一个段落。以下是它的具体表现形式。对这些机制进行描述，是为了让你能够评估它们，并对它们提出质疑。

**注册而不交出。** 测试集的注册方式是描述*它存放在哪里*，并固定其确切内容的加密哈希值——而不是上传句子。在评估时，系统从源头获取数据，检查哈希值是否匹配，然后进行评分。不存储任何内容。如果持有者将源数据下线，该语料库就无法再被评估。控制权始终留在原处，因为占有权从未转移。

**在离开本地前加密，适用于最高安全层级。** 当某个语料库必须在完全不被读取的前提下仍可使用时，它会在**持有者自己的设备上**完成加密，且密文始终保留在持有者手中。本项目接收到的只是不包含任何实际内容的描述信息。

**没有任何单一方可以解密。** 密钥被设计为分发给一组托管人，必须达到特定人数——比如五人中的三人——协同行动才能授权任何操作。任何单个托管人无法单独行动，本项目也同样不能：该设计分配给 **Champollion 零个份额**，因此无论是否有他人配合，它都无法解密。只有当达到法定人数的托管人决定执行时，运行才会发生。

> **目前的实际现状。** 该机制已经构建完毕且可供测试，但尚未与真正的托管人一起运行。*目前尚未指定任何托管人*——托管人构成权属于相关社区，目前也没有任何群体同意持有份额。在他们同意之前，不存在活跃的托管人集合，本项目也不会公开提及候选人。因此，请将上一段理解为一个等待赋予其运转关系的有效机制，而非当下正在运行的系统。

**出结果而不暴露数据。** 密封评估返回的是分数，而不是句子。一种方法可以被证明在一个语料库上有效，而该方法的作者和本项目从未阅读过该语料库。

**传输前需同意。** 将文本发送到外部模型 API 本身就是一种披露。在权利人明确记录许可之前，受社区、定制或未声明许可证约束的语料库会**拒绝**远程评估。这种拒绝是在代码中强制执行的，任何自动化流程都不能代表社区授予许可。

**仅单向可逆。** 持有者可以通过深思熟虑的决定来放宽暴露限制。它绝不会因为默认设置、意外或为了他人的方便而放宽。

## 4. 这不是什么

**本项目未经任何原住民数据主权框架的验证、认证或批准。未进行过任何评估，没有待处理的评估，亦不暗示存在任何评估。**

现有的内容是一次**在代码中落实数据主权的尝试**——将原住民提出的原则转化为可运行的机制，而非仅仅停留在承诺层面。这一尝试属于我们。至于它是否成功，则不由我们来断言。合规判定权属于相关社区，如果一个项目自行宣称合规，那将是在以微缩的方式重蹈这些原则旨在纠正的姿态：由外部人员来决定何为对待一个社区信息的恰当方式。

这也不是对“不可能发生”的保证。软件存在缺陷。操作员会犯错。一个持有足够多关键角色的坚定的一方，是任何架构都无法消除的残余风险。我们的主张更狭窄，而且我们认为更有用：**容易的路径已被封死，而艰难的路径会留下证据。**

原则和机制之间也存在差距，我们宁愿指出它们，也不愿让你自己去发现。占有权是这些机制服务得最好的原则——代码在“不持有东西”方面确实做得很好。所有权和控制权触及的范围超出了软件本身所能达到的范畴，深入到任何密码学都无法解决的条款、治理和关系中。而且，上述每一个机制都假设社区已经具备了持有自身数据的能力和基础设施，这并不是一个中立的假设。

## 5. 请对此提出质疑

这一尝试对批评持开放态度，这种邀请绝非装饰。

如果你从事原住民数据治理、CARE、Te Mana Raraunga 或原住民语言技术领域的工作——或者如果你是本索引中所列语言对应社区的成员或代表——我们希望了解我们何处有失偏颇。具体包括：

- 机制未能满足原则要求的地方；
- 表述曲解了社区原则，或挪用了其权威的地方；
- 被描述为保护性措施但实际上无法提供保护的地方；
- 社区所需但我们尚未构建的地方；
- 用词本身不准确的地方。

可以通过[联系和下架途径](/docs/network/community/contact-objections-takedown)提出异议和更正，该途径也涵盖了请求删除关于你所代表的语言的任何内容。对此无需客气。

未经审查是这项工作的一个事实，而不是对它的辩护。邀请审查的尝试是诚实的；不邀请审查的尝试只是一种说辞。

> 本页描述的是一次向这些原则靠拢的构建尝试，而这些原则的创立者是社区本身——请查阅由其创立者直接表述的原则原文；该尝试并未获得任何负责管理这些原则的组织的背书。
