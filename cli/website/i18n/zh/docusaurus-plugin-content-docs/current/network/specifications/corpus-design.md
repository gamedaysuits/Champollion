# 评估语料库设计框架

当你在 FLORES+ 上评估一个前沿模型并获得 85 的 chrF++ 分数时，你无法区分“该模型擅长翻译”和“该模型记住了这些特定的句子对”。正是这种歧义性促成了本框架的诞生：只有当评估语料库的分数能真实反映其所宣称的含义时，它才有构建的价值，而这需要经过深思熟虑的设计——全新的句子对、可追踪的数据来源、分层的领域、分级的难度。本页面是关于 Champollion 评估数据集如何设计、构建和维护的唯一事实来源。

> **版本：** 1.0 · **状态：** 草案 · 配套内容：[语料库合作伙伴关系](/docs/network/specifications/corpus-partnership) 工作流将此方法论与研究部门一起付诸实践。

## 1. 设计原则

### 1.1 — 为什么不使用公开基准？

公开的平行语料库（FLORES+、Tatoeba、WMT 测试集、OPUS）可用于开发和调试，但**被排除在官方排行榜评估之外**。原因很直接：

**数据污染。** 前沿 LLM 是在海量的网络抓取数据上训练的。任何公开存在过的平行文本——尤其是在经过精心整理、被广泛引用的基准数据集中——都很可能存在于它们的训练数据中。这并非理论上的担忧——[研究已经表明](https://arxiv.org/abs/2311.04850) MT 基准测试中存在可测量的污染效应。（公共基准测试在这里仍然会运行——但仅限于*相对比较*通道，用于对不同方法进行相互排名，绝不作为绝对质量的衡量标准。）

对于 Champollion 而言，这一点至关重要，因为：
- 排行榜将 LLM 方法、经典 MT 服务和专用系统进行了并排比较
- 我们的价值主张是*诚实、严谨的评估*
- 我们的目标用户（语言社区）会根据这些分数做出部署决策

### 1.2 — 核心要求

每个 Champollion 评估语料库必须满足：

| 要求 | 理由 |
|------|------|
| **人工编写** | 无合成数据。所有源文本和参考翻译必须由人类编写。LLM 可能协助对齐和格式化，但绝不生成内容。 |
| **不以平行形式公开提供** | 源文本可能是公开的；参考翻译可能是公开的；但具体的*配对*不能作为可下载的平行语料库存在。 |
| **来源可追踪** | 每个条目必须有记录的来源：源文档、译者、许可证、日期。 |
| **语言学知情** | 覆盖范围必须由类型学特征指导，而不是随机抽样。 |
| **领域分层** | 条目必须跨越定义的文本领域，具有受控的表示。 |
| **难度分级** | 条目必须根据结构复杂性分配难度等级（1–5）。 |
| **版本控制** | 语料库版本是内容哈希的。分数仅在同一版本内可比较。 |
| **社区可审查** | 参考翻译必须可由语言社区成员审查。 |

### 1.3 — 语料库类型、长度和风格中立性

Champollion 是一个开放的翻译评估中心，对翻译单位是什么**保持中立**。语料库条目是任意长度的文本——一个短句子、一个长的多从句句子、一个段落或整个文档——平台以相同的方式评估所有这些。**对短文本或简单文本没有限制。** 工具不施加长度上限（它故意设置宽松的输出令牌余量以避免截断长翻译）；难度等级（§3）和领域（§2.1）是*可配置的轴*，而不是排除困难或长材料的门槛。

该中心在以下方面保持中立和可配置：

| 轴 | 范围 |
|----|------|
| **粒度** | 句子 · 长句子 · 段落 · 文档 (`sizeUnit: entries \| sentences \| segments \| documents`) |
| **长度与复杂性** | 短 → 长；简单 → 高度复杂（难度等级 1–5） |
| **风格与语域** | 正式、非正式、技术、文学、会话、行政（领域分类法，§2.1） |
| **方法** | 任何 `TranslationMethod` — LLM、神经 NMT、基于规则、混合、人工 |
| **语言与语言对** | 任何有向对；没有内置的高资源偏差 |

语料库在其卡片中声明自己的类型、粒度、语域和难度，工具尊重卡片声明的任何内容。默认的 Tatoeba 源**开发**语料库是短句子，因为 Tatoeba 就是这样——这是这些源语料库的属性，**不是**平台限制。文档级和长文本评估集是一等公民；以相同的方式注册它们（例如，对于非常长的条目，配置较小的请求批次）。

## 2. 源文本选择

### 2.1 — 领域分类法

Champollion 评估**实际部署环境**中的翻译，而不是学术练习。每个语料库条目都用**规范的 16 代码领域分类法**中的领域标记，在构建时进行验证。

分类法定义一次——在[基准规范 §2.7](/docs/network/specifications/benchmark#27-domain)中，唯一的权威来源——此处不重述以避免偏差。代码为：`conv`、`ecommerce`、`edu`、`financial`、`gov`、`legal`、`literary`、`marketing`、`medical`、`news`、`religious`、`scientific`、`subtitles`、`support`、`tech` 和 `ui`。参见 §2.7 了解每个代码的描述和典型消费者。不要引入该集合之外的领域代码。

### 2.2 — 领域分布

标准评估语料库应该力求在与目标社区最相关的领域中实现分布。确切的代码和百分比因语言对而异；下表是一个*说明性的*目标分布，使用 §2.1 中的规范代码：

| 领域 | 代码 | 目标 % | 理由 |
|------|------|--------|------|
| 软件 UI | `ui` | 25% | Champollion CLI 用户的主要部署环境 |
| 政府/行政 | `gov` | 15% | 具有法律含义的高风险翻译 |
| 教育 | `edu` | 15% | 语言复兴的核心用例 |
| 文学/叙事 | `literary` | 10% | 测试文化细微差别和文学语域 |
| 会话 | `conv` | 10% | 测试非正式语域和自然言语模式 |
| 技术 | `tech` | 10% | 测试精确性和术语一致性 |
| 医疗/健康 | `medical` | 10% | 高风险，测试领域特定词汇 |
| 新闻/新闻学 | `news` | 5% | 测试当代词汇和中立语域 |

### 2.3 — 源文本选择标准

选择新语料库的源文本时：

1. **许可证兼容性。** 源文本必须在允许在评估语料库中使用的许可证下。优先选择 CC BY、CC BY-SA 或公有领域。记录许可证。

2. **时效性。** 优先选择在过去 10 年内发布的文本。语言在演变——尤其是围绕技术、治理和医学的词汇。

3. **语域多样性。** 在每个领域内，寻求不同正式程度的文本。政府新闻稿（正式）和政府社交媒体帖子（非正式）都是 `admin` 领域但语域不同。

4. **文化相关性。** 对于土著和少数民族语言，优先选择对社区重要的文本——土地管理文件、用该语言编写的教育材料、文化保护文本——而不是碰巧存在平行版本的文本。

5. **无机器翻译源。** 如果"平行"文档是通过运行原文通过 Google Translate 然后进行后编辑创建的，它**不**可接受作为参考翻译。参考必须是独立的人工翻译。

## 3. 难度分级系统

### 3.1 — 等级定义

每个条目根据*源文本*的结构复杂性（而不是翻译难度，这因方法而异）分配一个难度等级（1–5）。

| 等级 | 标签 | 结构特征 |
|------|------|--------|
| 1 | **初级** | 简单句子。单从句。现在时。常见词汇。无习语。无嵌入结构。 |
| 2 | **中级** | 复合句。两个由连词连接的从句。过去/将来时。一些领域词汇。 |
| 3 | **高级** | 复杂句。从属从句、关系从句。混合时态。领域特定术语。被动语态。 |
| 4 | **专家** | 多个嵌入从句。法律/技术语域。条件结构。抽象概念。文化参考。 |
| 5 | **极端** | 密集散文，具有多个同时的挑战：嵌套从属、模糊的代词指代、文化习语、混合语域、罕见词汇。 |

### 3.2 — 语言学知情的难度因素

除了结构复杂性，难度还由源语言和目标语言之间的**类型学距离**调节。这些因素来自 WALS 类型学特征和语言卡片的分类数据：

| 因素 | 低难度 | 高难度 |
|------|--------|--------|
| **词序** | 相同的基本顺序（例如，SVO→SVO） | 不同的基本顺序（例如，SVO→SOV） |
| **形态类型** | 相似类型（例如，分析型→分析型） | 不同类型（例如，分析型→多综合型） |
| **语法性** | 相同系统或无性 | 源无性，目标有复杂性系统 |
| **敬语/语域** | 无语域标记 | 目标有复杂语域系统（例如，日语、韩语） |
| **文字** | 相同文字 | 不同文字（需要音译） |
| **生命性** | 无生命性区分 | 目标有生命性为基础的一致（例如，克里语） |
| **证据性** | 无证据性 | 目标在语法上标记信息来源 |

### 3.3 — 等级分布

标准语料库应该大约有：

| 等级 | 目标 % | 理由 |
|------|--------|------|
| 1 | 15% | 建立基线——即使是差的方法也应该处理这些 |
| 2 | 25% | 面包和黄油实际翻译 |
| 3 | 30% | 方法质量差异变得可见的地方 |
| 4 | 20% | 将好方法与伟大方法分开 |
| 5 | 10% | 天花板测试——很少有方法能很好地处理这些 |

## 4. 参考翻译质量

### 4.1 — 译者要求

参考翻译必须由以下人员生成：

1. **流利的目标语言使用者**（L1 或等同水平）
2. **识字**源语言和目标语言
3. **领域意识**文本的领域（医学翻译用于健康文本等）
4. **独立**——译者在翻译期间不能访问同一文本的任何 MT 输出

### 4.2 — 翻译简报

每个译者都会收到一份简报，包括：

- 要使用的**语域**（正式、会话等）
- **目标受众**（公众、专家、儿童等）
- 特定于语言社区的任何**术语约定**
- 明确的指示："翻译意思，而不是词语。自然听起来的翻译比字面翻译更有价值。"

### 4.3 — 质量保证

1. **双重翻译。** 理想情况下，每个条目有两个由不同译者进行的独立参考翻译。如果这不可行，优先考虑第 4–5 级的双重翻译。

2. **社区审查。** 参考翻译应由至少一位未生成翻译的额外使用者审查。

3. **可接受的变体。** 对于每个参考，记录已知的可接受变体（词序、正字法约定、方言形式）。这些输入 `equivalent_match_rate` 指标。

### 4.4 — 什么是坏参考

| 问题 | 为什么它使评估无效 |
|------|------------------|
| 机器翻译然后后编辑 | 后编辑保留 MT 结构；惩罚产生更自然翻译的方法 |
| 由学习者而非流利使用者翻译 | 参考可能包含惩罚正确 MT 输出的错误 |
| 过度字面 | 自然翻译对字面参考评分较低 |
| 对模糊源的单一有效解释 | 惩罚有效的替代解释 |

## 5. 污染防止

### 5.1 — 污染威胁模型

| 威胁 | 描述 | 缓解 |
|------|------|------|
| **训练数据重叠** | LLM 在平行语料库上训练 | 不公开发布平行语料库 |
| **少样本泄漏** | 方法作者使用评估条目作为少样本示例 | 指纹检查：提示中的条目被检测和标记 |
| **间接污染** | 源文本存在于 LLM 训练数据中（单语） | 可接受——预期单语源文本。*配对*必须是新颖的。 |
| **众包污染** | 社区审查者公开分享条目 | 许可证条款禁止重新分发平行语料库 |

### 5.2 — 语料库保密等级

| 等级 | 可见性 | 用途 |
|------|--------|------|
| **公开开发集** | 完全公开 | 方法开发、调试、回归测试。分数**不**发布到排行榜。 |
| **保留评估集** | 源文本可见，参考保密 | 官方排行榜评估。方法接收源文本并返回翻译；评分在服务器端进行。参考永远不会暴露给方法。 |
| **黄金标准集** | 完全保密，社区控制 | 社区验证的评估。由治理组织管理。用于"社区验证"验证等级。 |

### 5.3 — 轮换政策

评估语料库应该**定期轮换**：

1. 语料库使用 12 个月后，开始构建替代品
2. 将旧语料库转为"开发集"状态（公开）
3. 将新语料库提升为"保留评估集"
4. 这防止通过针对固定目标的迭代优化进行的逐步污染

## 6. 语料库构建工作流

### 6.1 — 分步流程

```
Step 1: Language Pair Selection
    └─ Identify target language, read language card
    └─ Review typological features (WALS), contact influences, scripts
    └─ Identify which difficulty factors apply

Step 2: Source Text Curation
    └─ Identify candidate source documents per domain
    └─ Verify licenses
    └─ Extract candidate sentences/segments
    └─ Classify by domain and preliminary difficulty tier

Step 3: Segment Selection
    └─ Sample segments to match domain distribution (§2.2)
    └─ Sample segments to match difficulty distribution (§3.3)
    └─ Ensure linguistic phenomenon coverage (§6.2)
    └─ Target minimum corpus size (§6.3)

Step 4: Reference Translation
    └─ Assign segments to qualified translators
    └─ Provide translation brief
    └─ Collect translations
    └─ Dual-translate Tier 4–5 entries

Step 5: Quality Assurance
    └─ Community review of references
    └─ Document acceptable variants
    └─ Flag and resolve disagreements

Step 6: Metadata & Packaging
    └─ Assign final difficulty tiers
    └─ Add provenance metadata per entry
    └─ Content-hash the corpus for versioning
    └─ Package as corpus JSON per harness spec

Step 7: Registration
    └─ Register in Supabase datasets table
    └─ Add to ATTRIBUTION.md if new sources used
    └─ Document in arena website
```

### 6.2 — 语言学现象覆盖

每个语料库应该包括测试特定语言学现象的条目，这些现象与语言对相关。这些来自语言卡片的 `linguisticChallenges` 和 `contactInfluences` 字段：

**通用现象（所有语言对）：**
- 代词解析（模糊的先行词）
- 否定（单、双、范围）
- 量词（全部、一些、无、大多数）
- 时间表达（相对日期、持续时间）
- 命名实体（人、地、组织）
- 数字和测量
- 列表和枚举

**语言对特定现象（来自语言卡片）：**
- 对于多综合型目标：复杂动词形态、并入
- 对于有性别目标：性别一致、中立/包容性参考
- 对于 SOV 目标：从句末动词、后置词
- 对于声调语言：声调依赖的意义区分
- 对于敬语语言：语域标记、社会背景
- 对于接触语言：代码转换边界、借词整合

### 6.3 — 最小语料库大小

统计可靠性需要最小条目计数。这些基于配对引导置信区间要求（来自 `significance.py`）：

| 目的 | 最小条目 | 推荐 |
|------|---------|------|
| 开发集 | 50 | 100–200 |
| 保留评估集 | 100 | 200–500 |
| 黄金标准集 | 200 | 500+ |
| 每个领域最小 | 10 | 25+ |
| 每个等级最小 | 10 | 20+ |

**为什么评估最少 100 个？** 少于约 100 个条目时，配对引导显著性测试（1,000 次重新采样）无法可靠地检测小于约 5 chrF++ 点的差异。有 200+ 个条目时，我们可以在 p<0.05 时检测约 2 点的差异。

## 8. 反作弊措施

### 8.1 — 语料库完整性

| 措施 | 实现 |
|------|------|
| **内容哈希** | 语料库版本 = 排序条目 ID + 参考的 SHA-256。任何修改都会产生新版本。 |
| **条目指纹** | 每个条目都有一个内容派生的 ID。如果有人针对修改的语料库提交结果，指纹将不匹配。 |
| **保留执行** | 对于官方评估，方法仅接收源文本。参考永远不会暴露。评分在服务器端进行。 |
| **轮换计划** | 语料库每年轮换以防止针对固定目标的长期优化。 |

### 8.2 — 提交完整性

| 措施 | 实现 |
|------|------|
| **确定性指纹** | 运行配置（模型、温度、提示、语料库版本）被哈希。相同的配置产生相同的指纹。 |
| **樱桃采摘检测** | 提交者必须披露所有运行，而不仅仅是最好的。具有相同指纹的多个提交被标记。 |
| **污染检查** | 如果评估条目在方法的提示或教练数据中逐字出现，提交将被取消资格。 |

## 9. 现有语料库

### 9.1 — EDTeKLA 开发集 v1

| 属性 | 值 |

## 10. 语言卡片集成

语料库框架与语言卡片系统集成：

1. **领域选择**由卡片的 `linguisticChallenges` 知情——如果语言有独特的挑战（多综合、声调、生命性），语料库必须包括测试它们的条目。

2. **难度校准**使用卡片的 `classification`——源和目标语族之间的类型学距离影响什么构成"困难"。

3. **语域覆盖**使用卡片的 `registers`——如果语言有定义的语域（正式菲律宾语、他加禄语专业、他加禄语非正式），语料库应该在每个语域级别包括条目。

4. **接触影响测试**使用卡片的 `contactInfluences`——对于有重借词层的语言（菲律宾语：西班牙语 + 英语 + 阿拉伯语），包括测试方法是否正确处理借词与过度翻译它们的条目。

5. **文字处理**使用卡片的 `scripts[]`——对于多文字语言（塞尔维亚语：西里尔字母 + 拉丁字母），包括测试正确文字选择的条目。
