# 奖项规范

奖金是“评估优先”契约中的激励部分。社区或研究小组策划一个小型、封闭的评估集——几百个语料对，每一个都经过检查（[语料库合作](/docs/network/specifications/corpus-partnership) 就是该工作流）。赞助商针对该评估集上的目标分数设立奖金。从那一刻起，该语言就成为一项长期挑战：世界上任何方法构建者都可以以此为目标，排行榜会公开衡量每一次尝试，而标准由社区自己的标准答案来决定，而不是由谁的声音最大来决定。本文档详细说明了此类奖金的运作方式——阈值条件、申领流程、依赖类别和规则——以便在奖金开放时，标准是明确的且与具体方法无关的。

奖金由**赞助商出资并由赞助商保管**：资金存放在赞助组织或赞助商指定的社区信托基金中——**Champollion 从不持有、托管或路由奖金资金。** 任何社区或组织都可以通过 [举办主权竞赛](/docs/network/sovereignty/run-a-sovereign-contest) 中的自助路径举办比赛，持有自己的语料库和资金。

> **状态：提议阶段 —— 目前没有开放的奖金，此处也没有任何可申领的内容。**
> 决定奖金*开放*的关卡在于衡量方面：社区认可的黄金标准语料库、物理隔离的评估沙盒（已出规范，尚未构建）以及母语者审查关卡。本网站上的任何分数都尚未跨过奖金门槛。请参阅 [诚实的局限性](/docs/network/honest-limitations)。指标参考：[评分规范](/docs/network/specifications/scoring)；协议：[基准测试规范](/docs/network/specifications/benchmark)。

## 想帮助将一种语言引入网络吗？

你不需要等待奖项。你今天可以做的最高杠杆的事情：

- **赞助机器翻译成就奖项。** 资助一个有针对性的标准——例如，一个可靠的英语→平原克里语方法。Champollion 协调测量；资金留在**你**这里（你的组织或你指定的社区信托），并按社区条款颁发（参见 [数据主权](/docs/network/sovereignty/data-sovereignty) 和 [经济模型](/docs/network/sovereignty/economic-model)）。端到端自助路径记录在 [运行主权竞赛](/docs/network/sovereignty/run-a-sovereign-contest) 中；引入新的语言对始于 [语料库合作](/docs/network/specifications/corpus-partnership)。
- **协调计算捐赠。** 汇集 API 额度/代币，以便公共队列可以映射更多对，并显示翻译在哪里是——以及不是——可靠的。
- **直接支持我们构建的开源倡议。** Champollion 是连接其他人开放工作的管道；支持*他们*就是支持这个地图（我们宁愿指向上游而不是为他们的工作邀功）：
  - [Tatoeba](https://tatoeba.org) ——社区贡献的平行句子
  - [濒危语言目录 (ELCat)](https://www.endangeredlanguages.com) ——濒危数据
  - [Glottolog](https://glottolog.org) · [WALS](https://wals.info) · [Grambank](https://grambank.clld.org) · [PHOIBLE](https://phoible.org) ——语言目录和类型学
  - [GiellaLT](https://giellalt.uit.no) / ALTLab ——形态学转导器 (FST)
  - [Masakhane](https://www.masakhane.io) ——非洲语言机器翻译社区
  - [OPUS](https://opus.nlpl.eu) ——开放平行语料库

> 要赞助奖项、组织计算捐赠或讨论合作，请通过 [GitHub](https://github.com/gamedaysuits) 联系项目。社区关键保管人正在确认中；在任何国家或组织同意之前，不会将其命名为合作伙伴。

## 1. 哲学

> **一句话的交易：破解一种语言，赢得奖项，将其交还。** Champollion 有意是一个机器学习基准测试操作——竞争是如何解决困难对的。我们邀请机器学习研究人员和任何有能力的构建者为特定困难的语言对构建最佳方法，赢得奖项，**并**将生成的方法交给拥有该语言的主权组织（§1.3）。竞争能量是真实的，它指向使命——让每种语言都被翻译，按其人民设定的条款——而不是为了自身而爬排行榜。

### 1.1 奖项奖励突破，而非参与

奖项资金仅在方法明确达到定义的能力阈值时才发放。没有参与奖、亚军奖或安慰奖。如果没有人通过标准，没有人获得报酬。这是设计使然——这意味着赞助商只为真正有效的结果付费。

### 1.2 社区验证是不可协商的

自动化指标是代理（SCORING_SPEC §1.1）。一个方法可以在 chrF++ 和 FST 接受度上得分很高，同时产生没有说话人会接受的输出。**每个奖项申领都需要社区验证**——双语使用者必须确认输出是可用的。这是人工验证门槛（BENCHMARK_SPEC §7）。

### 1.3 所有权转移是交易的一部分

申领奖项的方法受所有权转移条款约束（BENCHMARK_SPEC §8.3）。开发者保留署名和出版权。治理组织获得使用、修改、分发和货币化该语言方法的权利。这不是惩罚——这是重点。奖项资金资助创建属于语言社区的技术。

### 1.4 反作弊

奖项阈值针对**黄金标准评估**定义（秘密测试集，由治理组织在沙箱中运行）。开发者永远看不到测试数据。这在架构上被强制执行——不是依赖荣誉的政策。参见 BENCHMARK_SPEC §8.2。

### 1.5 语料库许可：非商业语料库不在奖项通道中

在方法开发过程中使用的一些语料库带有非商业许可证——例如，EdTeKLA 克里语（Cree）教科书语料库采用 **EdTeKLA 修改版的 CC BY-NC-SA**（限定主权范围、非商业性；基础教科书为 CC BY-NC-ND 4.0）。这些语料库**仅限研究/开发通道**使用：

1. **奖项黄金标准语料库不得嵌入 NC 许可语料库内容。** 黄金标准测试段是社区委托的原创（参见语料库合作战略）——为奖项人工编写，从一开始就清除了评估和商业部署的权利。
2. **申领奖项的方法不得嵌入 NC 许可语料库内容**（例如，作为教练数据、嵌入示例或查找表）。转移的方法必须可由治理组织在其选择的任何条款下部署——包括商业上，如果社区这样决定（BENCHMARK_SPEC §8.3）；其中的 NC 许可内容会破坏这种自由。
3. **开发者可以自由使用 NC 许可语料库进行开发和自我评估**——这就是开发通道的用途。限制适用于提交的内容和部署的内容，而不是开发者如何学习。

### 1.6 依赖类别限制奖项资格

所有奖项评估都在沙箱中进行（§1.4），奖项获胜方法转移给治理组织（§1.3）。两个事实都施加了相同的约束：**方法依赖的一切都必须是开发者有权放入沙箱并转移给社区的东西。** 每个提交都声明一个依赖类别——在 [方法接口规范](/docs/network/specifications/methods#method-validity-and-dependency-classes) 中定义——资格遵循该类别：

| 依赖类别 | 奖项资格？ | 条件 |
|---------|---------|------|
| **S** ——自包含 | ✅ 是 | 除了 §2 中的阈值条件外，无其他条件 |
| **O** ——开放外部（例如，在提交时镜像的 AGPL FST） | ✅ 是 | 工件固定并供应到提交中；许可允许社区转移；copyleft 条款保留（社区获得许可授予所有人的相同权利） |
| **A1** ——可替代的 LLM 推理 | ⚠️ 条件性 | 模型声明、固定和可替代（必须针对社区托管的开放权重模型运行）；评估通过沙箱 LLM 网关路由（🔲 计划中——A1 方法在网关可用之前无法产生黄金标准分数）；转移传达完整配方（提示、教练、代码），而不是模型 |
| **A2** ——不可替代的外部数据/服务 API | ❌ 尚未 | 不符合条件，直到权利持有人授予沙箱包含和转移权限。在开放排行榜上允许，带有可见的"外部依赖"标志 |
| **X** ——无权利的捆绑内容 | ❌ 永不 | 在每个通道中都不可接受 |

方法的类别是其声明依赖中最严格的类别。任何类别的未声明依赖都是取消资格的（§5）。

### 2.1 创始人奖——EN→平原克里语 (nêhiyawêwin)

| 字段 | 值 |
|------|-----|
| **奖项池** | **$10,000 加元**（建议） |
| **语言对** | 英语→平原克里语 (EN→CRK) |
| **预期赞助商** | Champollion 项目创始人——一个预期的承诺，**目前没有资金在任何地方持有。** 承诺时，资金将由赞助商或指定的社区信托持有——永远不会由 Champollion 持有。 |
| **状态** | **建议中——未开放。** 不接受提交。 |
| **开放** | 仅当黄金标准语料库、评估沙箱和说话人审查门槛都存在（目前都不存在），且赞助商的资金按 §4.2 可验证地持有时。 |
| **过期** | 开放后无过期。 |

#### 阈值条件

方法通过同时满足**所有**以下条件来申领创始人奖：

| # | 条件 | 指标 | 阈值 | 理由 |
|---|------|------|------|------|
| 1 | **综合分数** | `composite` (SCORING_SPEC §4) | **≥ 0.80** | 在可部署 (0.70) 和流畅 (0.85) 之间。要求所有指标维度的高质量——不仅仅是形态学有效性。 |
| 2 | **FST 接受度** | `fst_acceptance_rate` (SCORING_SPEC §2.2) | **≥ 0.99 (99%+)** | 实际上所有输出词都必须是 GiellaLT FST 识别的形态学有效形式。1% 的容差考虑了 FST 可能合理不覆盖的边界情况（专有名词、新词、借词）。这是多综合语机器翻译的定义质量门槛——如果 FST 拒绝超过 1% 的词，该方法正在产生语言中不存在的形式。这个奖项的全部要点是购买一个不会破坏事物的系统。 |
| 3 | **chrF++** | `chrf_plus_plus` (SCORING_SPEC §2.1) | **≥ 55.0** | 字符 n-gram 重叠必须在 0–100 标度上超过 55。确保与参考翻译的表面相似性，而不仅仅是形态学有效性。 |
| 4 | **社区验证** | 人工审查 (BENCHMARK_SPEC §7) | **≥ 70% "可接受"或"优秀"** | 输出的分层样本（≥30 个条目，跨越难度等级 2–5）由 ≥2 名双语 CRK 使用者审查。至少 70% 的审查条目必须从两名审查者那里获得"可接受"或"优秀"评级。 |
| 5 | **黄金标准评估** | 沙箱执行 (BENCHMARK_SPEC §8.2) | **必需** | 所有自动化指标必须针对 `gold_standard` 语料库段计算，由治理组织在沙箱环境中运行。开发集分数不计数。 |
| 6 | **可重现性** | 指纹匹配 (BENCHMARK_SPEC §3.8) | **±2%** | 治理组织必须能够重新运行该方法并实现在提交的运行卡的 ±2% 内的分数。 |

> **为什么 99+% FST？** 多综合语机器翻译的中心问题是幻觉——LLM 产生看起来像目标语言但形态学无效的字符串。一个产生 95% 有效输出的方法仍然有 5% 的虚构词——任何生产使用都无法接受的噪音。99%+ 阈值要求接近零的幻觉，同时允许罕见的边界情况（FST 不知道的专有名词、合法的新词）。如果一个方法无法达到 99%+ FST 接受度，它就没有解决问题。
>
> **为什么 0.80 综合？** 这位于可部署 (0.70) 和流畅 (0.85) 之间。一个在 0.80 综合且 99%+ FST 接受度的方法产生的输出中，几乎每个词都是真实的克里语词*并且*整体翻译质量在表面、结构和语义维度上都很高。社区验证门槛（条件 #4）确保这不仅仅是指标游戏——说话人必须确认输出确实可用。

#### 这个阈值在实践中意味着什么

在综合 ≥ 0.80、FST ≥ 0.99 和 chrF++ ≥ 55 时，双语使用者通常会看到：

- **几乎每个**输出词都是真实的克里语词（FST 验证 99%+——接近零的虚构形式）
- 主要语法类别（人称、数、时态）在大多数条目中是正确的
- 词序通常是自然的
- 意义得到可靠保留
- 剩余错误是真实语言错误（错误的屈折、不正确的显著性、动物性不匹配）——不是虚构词
- 流畅的使用者可以使用输出作为高质量草稿，并比从头翻译快得多地纠正它

这是一个**不会破坏语言**的系统。它可能不完美，但它产生的每个词都是真实的词。这是对多综合语尊重的机器翻译的最低标准。

## 3. 奖项申领流程

### 3.1 提交

1. 开发者向治理组织提交他们完整的、可运行的方法：
   - 所有源代码
   - 所有依赖（教练数据、字典、FST 配置、提示）
   - 安装和执行说明
   - 描述方法方法的 README
   - 显示近似分数的开发集运行卡（用于预筛选）

2. 开发者签署参与条款，包括：
   - 所有权转移条款 (BENCHMARK_SPEC §8.3)
   - 未在评估数据上训练的声明
   - 可重现性承诺

### 3.2 评估

1. 治理组织在沙箱工具中安装并针对 `gold_standard` 语料库运行该方法
2. 计算自动化指标（综合、FST、chrF++ 等）
3. 如果自动化阈值满足（条件 1–3），治理组织继续进行社区审查
4. 如果自动化阈值**未**满足，开发者收到分数和反馈。不触发社区审查。

### 3.3 社区审查

1. 输出的分层样本（≥30 个条目，覆盖难度等级 2–5）呈现给双语使用者
2. 至少 2 名独立审查者对每个条目进行评级
3. 评级标度：**拒绝** / **要点** / **可接受** / **优秀**
4. 如果 ≥70% 的条目从两名审查者那里获得"可接受"或"优秀"，社区验证通过

### 3.4 支付

1. 所有 6 个条件都满足
2. 治理组织确认结果
3. 奖项在确认后 30 天内支付
4. 方法所有权按 BENCHMARK_SPEC §8.3 转移
5. 结果在排行榜上发布，带有"社区验证"验证等级

### 3.5 多次提交

- 同一开发者/团队可以多次提交
- 每个提交独立评估
- 如果方法改进并重新提交，仅最新运行卡计数
- 奖项颁发给**首个**通过所有阈值的方法——不分割

### 3.6 团队提交

- 团队和长者-青年对符合条件
- 团队内的奖项分配是团队的责任
- 所有团队成员必须签署参与条款
- 排行榜上的署名列出所有团队成员

## 4. 未来奖项池 {#4-future-prize-pools}

创始人奖是种子。额外的奖项池由赞助商资助。每个新奖项池都记录为 §2 的新小节，带有其自己的：

- 奖项金额和货币
- 语言对
- 赞助商署名
- 阈值条件（可能与创始人奖不同）
- 过期日期（如果有）
- 任何特殊条件

### 4.1 赞助商奖项模板

赞助商以任何金额资助奖项池。建议的等级：

| 等级 | 金额 | 建议阈值 |
|------|------|---------|
| **种子** | $5,000–$15,000 | 可部署 (综合 ≥ 0.70) + 社区验证 |
| **突破** | $25,000–$50,000 | 流畅 (综合 ≥ 0.85) + 社区验证 |
| **大奖** | $100,000+ | 流畅 + 多寄存器覆盖 + 部署集成 |

赞助商也可以资助：
- **改进赏金**——对当前最佳 chrF++ 的每 5 点改进的固定支付
- **寄存器奖**——特定寄存器的单独奖项（正式、仪式、教育）
- **速度奖**——最佳成本调整分数 (SCORING_SPEC §6.3)

### 4.2 奖项资金的持有位置

奖项资金是**赞助商持有**：它们由赞助组织或赞助商指定的社区信托持有——**永远不会由 Champollion 持有**，它协调测量且不接触任何资金。一个可信的奖项在开放前发布：**谁持有资金**，在什么安排下（组织账户、信托或赞助商选择的第三方托管），以及奖项阈值——以便通过标准可从发布的分数加上社区的说话人验证判决进行验证，支付违约将作为一个可见的。目前没有奖项资金在任何地方持有。如果奖项过期未申领，资金留在它一直所在的地方——与赞助商——由赞助商自行决定重定向或撤回。自助机制，包括赞助商违约风险及其缓解措施，记录在 [运行主权竞赛](/docs/network/sovereignty/run-a-sovereign-contest) 和 [条款模板](/docs/network/sovereignty/terms-templates) 中。

## 5. 取消资格

提交在以下情况下被取消资格：

1. **在评估数据上训练。** 方法暴露于 `gold_standard` 或 `held_out` 语料库条目。（在架构上由沙箱执行防止——但如果发现污染证据，结果被作废。）
2. **不可重现。** 治理组织无法在 ±2% 内重现分数。
3. **未声明或不符合条件的依赖。** 该方法需要运行时访问其依赖清单未声明的外部服务，或其有效依赖类别是 A2 或 X (§1.6)。声明的 A1 LLM 推理通过评估网关路由是允许的；任何其他运行时网络依赖——以及任何类别的任何未声明依赖——都是取消资格的。
4. **未签署参与条款。** 所有团队成员必须同意所有权转移。
5. **检测到作弊。** 输出针对指标而不是翻译质量进行优化（由社区审查和/或 BENCHMARK_SPEC §9.3 中的反作弊检查捕获）。
