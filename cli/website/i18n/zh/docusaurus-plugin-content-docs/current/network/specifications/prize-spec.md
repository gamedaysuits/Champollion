# 奖项规范

奖项是“评估优先”（eval-first）契约中代表激励的一半。社区或研究团队策划一个规模较小且密封的评估集——包含数百个句对，每一对都经过核验（[语料库合作流程](/docs/network/specifications/corpus-partnership)即为此项工作）。赞助方根据该数据集的目标分数设立奖金。从那一刻起，该语言就成为了一个公开的长期挑战：全世界的任何方法构建者都可以以此为目标发起冲击，排行榜公开衡量每一次尝试，而衡量标准则由社区自己的标准答案决定，而非谁的声音最大。本文档规范了此类奖项的运作方式——门槛条件、申领流程、依赖类别和规则——以便在奖项开放时，门槛明确且不偏向任何特定方法。

奖金由**赞助方出资并持有**：资金存放在赞助机构，或存放在赞助方指定的社区信托机构中——**Champollion 绝不持有、托管或转移奖金资金。** 任何社区或组织都可以按照[举办主权竞赛](/docs/network/sovereignty/run-a-sovereign-contest)中的自主服务路径自行举办竞赛，持有自己的语料库和资金。

> **状态：草案（PROPOSED）——目前尚无开放的奖项，此处内容暂不可申领。**
> 限制奖项*开放*的前提是衡量体系：获得社区许可的黄金标准语料库以及母语者审核关卡。
> 目前两者均未就绪。物理隔离（air-gapped）的评估沙箱已经发布——参见
> [基准规范 §8.6](/docs/network/specifications/benchmark#86-dependency-classes-and-the-sandbox-network-policy)。
> 本网站上的任何分数均未达到奖项门槛。参见
> [局限性说明](/docs/network/honest-limitations)。指标参考：
> [评分规范](/docs/network/specifications/scoring)；协议参考：
> [基准规范](/docs/network/specifications/benchmark)。

> **承诺层现已上线。** 截至 2026-09-07，一旦存在参赛提交即冻结已声明的奖项条款不可编辑，以及暂扣（`hidden_until_close`）结果等规则，已在网络托管端点的数据库层强制执行。联邦节点通过应用随测试套件提供的数据库迁移脚本即可获得相同的规则；对于较旧的端点，测试套件会回退到基准集并明确声明，而非假装支持。§3.2 中仅允许聚合数据出站的规则一直随处强制执行。

## 想帮助将一种语言引入网络吗？

你不需要等待奖项。你今天可以做的最高杠杆的事情：

- **赞助机器翻译成就奖项。** 资助一个有针对性的标准——例如，一个可靠的英语→平原克里语方法。Champollion 协调测量；资金留在**你**这里（你的组织或你指定的社区信托），并按社区条款颁发（参见 [数据主权](/docs/network/sovereignty/data-sovereignty) 和 [经济模型](/docs/network/sovereignty/economic-model)）。端到端自助路径记录在 [运行主权竞赛](/docs/network/sovereignty/run-a-sovereign-contest) 中；引入新的语言对始于 [语料库合作](/docs/network/specifications/corpus-partnership)。
- **协调计算捐赠。** 汇集 API 额度/代币，以便公共队列可以映射更多对，并显示翻译在哪里是——以及不是——可靠的。
- **直接支持我们构建的开源倡议。** Champollion 是连接其他人开放工作的管道；支持*他们*就是支持这个地图（我们宁愿指向上游而不是为他们的工作邀功）：
  - [Tatoeba](https://tatoeba.org) ——社区贡献的平行句子
  - [濒危语言目录 (ELCat)](https://www.endangeredlanguages.com) ——濒危数据
  - [Glottolog](https://glottolog.org) · [WALS](https://wals.info) · [Grambank](https://grambank.clld.org) · [PHOIBLE](https://phoible.org) ——语言目录和类型学
  - [GiellaLT](https://giellalt.uit.no) / ALTLab ——形态学转导器 (FST)
  - [Masakhane](https://www.masakhane.io) ——非洲语言机器翻译社区
  - [OPUS](https://opus.nlpl.eu) ——开放平行语料库

> 如需赞助奖项、组织算力捐赠或探讨合作事宜，请通过 [GitHub](https://github.com/gamedaysuits) 与项目方取得联系。目前尚未任命任何社区密钥保管人，且在获得明确同意之前，不会将任何族群或组织列为合作伙伴。

## 1. 哲学

> **一句话总结：攻克一种语言，在主办方声明的条款下赢得奖项。**
> Champollion 专门从事机器学习基准测试——竞争正是解决棘手语言对的途径。我们邀请机器学习研究人员和任何有能力的开发者为特定的高难度语言对构建最佳方法并赢取奖金。方法获奖后的归属与处置是**主办方**公布的选择，既不是我们的决定，也不是既定默认值：想要接管获奖方法的社区会在其条款中明确声明，而只希望评估后即删除的社区则会声明后者（§1.3）。这种竞争能量是真实的，并且直接指向使命本身——在人们自己设定的条款下，实现每种语言的翻译——而不是为了排行榜排名本身而内卷。

### 1.1 奖项奖励突破，而非参与

奖项资金仅在方法明确达到定义的能力阈值时才发放。没有参与奖、亚军奖或安慰奖。如果没有人通过标准，没有人获得报酬。这是设计使然——这意味着赞助商只为真正有效的结果付费。

### 1.2 社区验证是不可协商的

自动化指标是代理（SCORING_SPEC §1.1）。一个方法可以在 chrF++ 和 FST 接受度上得分很高，同时产生没有说话人会接受的输出。**每个奖项申领都需要社区验证**——双语使用者必须确认输出是可用的。这是人工验证门槛（BENCHMARK_SPEC §7）。

### 1.3 获奖方法的处置方式由条款声明，而非预先假定 {#1-3-declared-terms}

有一件事是固定的，因为这正是主权竞赛的*本质*：参赛作品会被移交给主办方自己的物理隔离节点，该节点在主办方的机器上针对密封数据集运行该作品。而*此后*对它的处置取决于主办方的声明选择，按竞赛分别设定并随之公布——这是**三选一**的决定：

| 条款 | 对参赛者意味着什么 |
|---|---|
| `pass_to_holders` — *移交给持有方* | 该方法移交给主权基准持有方。无论谁获胜，他们都会对其评分并保留它。 |
| `retain_ip` — *保留知识产权* | 你保留自己方法的所有权。主办方对其评分，最多保留一份密封副本用于审计。 |
| `release_open` — *开源发布* | 你保留所有权，但必须在开源许可证下发布该方法。完成该发布是获得奖金的前提条件。 |

由条款衍生的所有其他事项——是否保留构建物、权利是否转移、主办方可将其用于何处、何时须完成发布——均**派生**自主办方选择的选项（§2.1，条件 7），而不是由主办方逐一勾选的独立设置。主办方选择条款，细节随之确定。

有两点后果值得明确说明：

- **未声明奖项条款的竞赛没有奖项。** 这是默认状态。这并不意味着它是次等的竞赛，参赛作品的任何权益也不会发生变动。
- **不存在隐式假定。** 声明的条款会被哈希化，以通俗语言展示给参赛者，并由该哈希值接受；接受凭据随参赛作品一起传输并由其内容哈希覆盖，主办方节点会拒绝接受了其他任何条款的参赛提交。随后，一旦竞赛迎来第一个参赛作品，条款就会立即冻结，因此没有人会被迫遵守他们未能读到的条款。

当主办方选择 `pass_to_holders` 时，开发者仍保留署名权和发表权，这一安排的核心在于奖金资助了语言社区真正能够使用的技术。这是社区主办方选择该条款的一个充分理由。这是一种选择，而不是硬性规则。

### 1.4 反作弊

奖项阈值针对**黄金标准评估**定义（秘密测试集，由治理组织在沙箱中运行）。开发者永远看不到测试数据。这在架构上被强制执行——不是依赖荣誉的政策。参见 BENCHMARK_SPEC §8.2。

### 1.5 语料库许可：非商业语料库不在奖项通道中

在方法开发期间使用的某些语料库带有非商业许可证——例如，EdTeKLA 克里语教科书语料库采用 **EdTeKLA 修改版 CC BY-NC-SA**（限定主权范围，非商业；源教科书为 CC BY-NC-ND 4.0）。这些语料库**仅限研究/开发赛道**：

1. **奖项黄金标准语料库不得嵌入 NC 许可语料库内容。** 黄金标准测试段是社区委托的原创（参见语料库合作战略）——为奖项人工编写，从一开始就清除了评估和商业部署的权利。
2. **申领奖项的方法不得嵌入 NC 许可语料库内容**（例如，作为教练数据、嵌入示例或查找表）。转移的方法必须可由治理组织在其选择的任何条款下部署——包括商业上，如果社区这样决定（BENCHMARK_SPEC §8.3）；其中的 NC 许可内容会破坏这种自由。
3. **开发者可以自由使用 NC 许可语料库进行开发和自我评估**——这就是开发通道的用途。限制适用于提交的内容和部署的内容，而不是开发者如何学习。

### 1.6 依赖类别限制奖项资格

所有奖项评估都在沙箱中进行（§1.4），奖项获胜方法转移给治理组织（§1.3）。两个事实都施加了相同的约束：**方法依赖的一切都必须是开发者有权放入沙箱并转移给社区的东西。** 每个提交都声明一个依赖类别——在 [方法接口规范](/docs/network/specifications/methods#method-validity-and-dependency-classes) 中定义——资格遵循该类别：

| 依赖类别 | 奖项资格？ | 条件 |
|---------|---------|------|
| **S** ——自包含 | ✅ 是 | 除了 §2 中的阈值条件外，无其他条件 |
| **O** ——开放外部（例如，在提交时镜像的 AGPL FST） | ✅ 是 | 工件固定并供应到提交中；许可允许社区转移；copyleft 条款保留（社区获得许可授予所有人的相同权利） |
| **A1** ——可替代的 LLM 推理 | ⚠️ 条件性 | 模型声明、固定和可替代（必须针对社区托管的开放权重模型运行）；评估通过沙箱 LLM 网关路由（🔲 计划中——A1 方法在网关可用之前无法产生黄金标准分数）；转移传达完整配方（提示、教练、代码），而不是模型 |
| **A2** ——不可替代的外部数据/服务 API | ❌ 尚未 | 不符合条件，直到权利持有人授予沙箱包含和转移权限。在开放排行榜上允许，带有可见的"外部依赖"标志 |
| **X** ——无权利的捆绑内容 | ❌ 永不 | 在每个通道中都不可接受 |

方法的类别是其声明依赖中最严格的类别。任何类别的未声明依赖都是取消资格的（§5）。

#### 阈值条件

方法通过同时满足**所有**以下条件来申领创始人奖：

| # | 条件 | 指标 | 阈值 | 原理阐述 |
|---|-----------|--------|-----------|-----------|
| 1 | ~~综合得分~~ — **已废止** | — | — | 该条件（综合得分 ≥ 0.80）已于 2026-10-04 随综合评分机制一同废止（[评分规范 §4](/docs/network/specifications/scoring#4-composite-score)）。评分条件仅保留 chrF++（条件 3）；保留序号是为了让其他条件保持原有编号。 |
| 2 | **FST 接受度**（诊断关卡，非最终得分） | `fst_acceptance_rate`（SCORING_SPEC §2.2） | **≥ 0.99 (99%+)** | 实际上所有输出词汇都必须是由 GiellaLT FST 认可的形态学有效形式。1% 的容差涵盖了 FST 可能无法正当覆盖的边缘情况（专有名词、新词、借词）。这是多式综合语机器翻译的决定性质量关卡——如果 FST 拒绝了超过 1% 的词汇，说明该方法正在生成该语言中不存在的形式。该奖项的核心目的就是为了获取一个不胡言乱语的系统。 |
| 3 | **chrF++**（最终得分） | `chrf_plus_plus`（SCORING_SPEC §2.1），附带 sacreBLEU 签名和 95% 置信区间 | **≥ 55.0** | 密封集上的语料库级 chrF++ 必须在 0–100 的刻度上达到 55——这是标准的核心指标（[评分规范](/docs/network/specifications/scoring#how-runs-are-scored)）。它将每个输出与其参考译文进行比较，因此系统无法通过输出未能翻译输入的有效词汇来达到此标准。 |
| 4 | **社区验证** | 人工审核（BENCHMARK_SPEC §7） | **≥ 70% “可接受”或“优秀”** | 分层抽样的一组输出（跨越难度等级 2–5 的 ≥30 个条目）由 ≥2 名 CRK 双语母语者进行审核。至少 70% 的审核条目必须获得“可接受”或“优秀”评级。 |
| 5 | **黄金标准评估** | 沙箱执行（BENCHMARK_SPEC §8.2） | **必须满足** | 所有自动化指标必须针对 `gold_standard` 语料库分段进行计算，由治理机构在沙箱环境中运行。开发集得分无效。 |
| 6 | **可复现性** | 指纹匹配（BENCHMARK_SPEC §3.8） | **±2%** | 治理机构必须能够重新运行该方法，并取得与所提交运行卡误差在 ±2% 以内的得分。 |
| 7 | **满足竞赛声明的奖项条款** | 该条款所要求的核验（见下文） | **必须满足** | 奖项仅存在于主权竞赛中，在此类竞赛中，你的参赛提交将由主办方的物理隔离节点在密封集上执行。执行*之后*如何处置，是竞赛开放提交前公布的三种声明选项之一——并非每场竞赛强加的单一条件。 |

#### 条件 7 详解：条款为三选一

每场主权竞赛在执行时的工作机制完全相同：你将你的方法（权重或代码）交付给主办方的物理隔离节点，该节点在密封集上对其进行评分。这就是“主办方对其完成了测算”的含义，不可调整。

此*后*发生的事情由主办方按竞赛自主声明选择，共有三个选项之一。主办方在开放提交之前公布该选项；一旦竞赛迎来第一个提交，该选项就会被**冻结**，因此你看到的条款就是你需要遵守的条款。

| 条款 | 对参赛者意味着什么 |
|---|---|
| `pass_to_holders` — *移交给持有方* | 该方法移交给主权基准持有方。无论谁获胜，他们都会对其评分并保留它。 |
| `retain_ip` — *保留知识产权* | 你保留自己方法的所有权。主办方对其评分，最多保留一份密封副本用于审计。 |
| `release_open` — *开源发布* | 你保留所有权，但必须在开源许可证下发布该方法。完成该发布是获得奖金的前提条件。 |

**各个选项的详细含义。** 这四个维度——以及随要求发布附带的许可证——均*派生*自所选选项：主办方绝不能手动编写 `rights` 或 `host_use`，任何竞赛都不能随意拼凑：

| 字段 | `pass_to_holders` | `retain_ip` | `release_open` |
|---|---|---|---|
| `retention` — 构建物在评分后是否保留？ | `retain` | `retain_sealed_audit` | `retain` |
| `rights` — 所有权是否转移？ | `assignment_to_host` | `participant_retains_all` | `participant_retains_all` |
| `host_use` — 主办方可将其用于何处？ | `any` | `evaluation_only` | `any`（根据你发布的开源许可证） |
| `release` — **你**是否必须发布，何时发布？ | `not_required` | `not_required` | `required_before_prize` |
| `release_license` — 你在何种许可证下发布 | — | — | `any_osi`，或指定的 SPDX 标识符 |

其中两个选项允许主办方缩减一个字段的范围，仅此而已：

- 在 `retain_ip` 下，主办方可以将 `retention` 设置为 `delete_after_scoring`——你的方法在完成评分后即被销毁；
- 在 `release_open` 下，主办方可以将发布节点调整为 `required_before_scores`（在你自己的分数公布前发布）或 `required_after_prize`（在支付奖金后发布），并可以指定具体的许可证，而不是接受任何 OSI 批准的许可证。

这三种选项都可以附带一个 `community_terms_url`——即指向主办方自定义书面条款的 `https://` 链接。在竞赛本身中，所选选项被记录为其 `disposition`，以上所有内容均从这单一值中读取。

任何其他内容在创建竞赛时都会被拒绝：选项不提供其未包含的字段，而在应当自动派生之处若手动填写字段，系统会按名称拒绝该字段，而不会盲目采信。

**奖金支付前核验的内容。** 所需的核验均从条款中派生；没有任何主办方能对其进行单独配置：

- **交付** — 始终必须。主办方持有其完成评分的精确构建物（节点记录的方法摘要）。这是经过测量的。
- **发布** — 在 `release_open` 下，当发布到期时间位于公布分数之前或颁奖之前时。主办方记录发布 URL 和已发布构建物的 SHA-256；该记录会经过核验，但绝不会请求该 URL，因此冻结的结果绝不依赖第三方的在线状态。如果要求在颁发奖金*之后*发布，则该义务在奖金支付后才到期，因此不属于支付前核验项。
- **转让** — 在 `pass_to_holders` 下，即所有权转移的情况。转让属于在此平台之外签署的法律文书；主办方记录该文书及其日期，平台仅核验记录是否存在。
  **平台绝不核验法律效力。**

**未声明奖项条款的竞赛没有奖项。** 没有默认条款，也不会代表任何人假定条款。参加确实声明了条款的竞赛意味着在提交时通过其哈希值明确接受它——该接受凭证被打包到你的提交包中，是主办方节点核验内容的一部分。

> **为什么要求 99+% 的 FST 接受度？** 多式综合语机器翻译的核心问题是幻觉——LLM 会生成*看起来*像目标语言但在形态学上无效的字符串。输出有效率为 95% 的方法仍包含 5% 的捏造词汇——对于任何生产用途来说，这都是不可接受的噪声。99%+ 的门槛要求近乎零幻觉，同时允许极少见的边缘情况（FST 不认识的专有名词、合规的新词）。如果一种方法无法达到 99%+ 的 FST 接受度，它就没有解决该问题。
>
> **为什么需要 chrF++ 和 FST 结合，为什么单靠两者之一都不够？** FST 接受度只能说明每个词确实存在；一个对每个输入都重复同一句合规句子的系统可以通过这项测试。chrF++ 将每个输出与参考译文进行比对，因此能发现这种情况。两个自动化数值都无法单独证明质量：社区验证关卡（条件 #4）才是确认母语者认为输出切实可用的关键。

#### 这个阈值在实践中意味着什么

这些条件共同确立了：

- **几乎每一个**输出词都是真实的克里语词汇（FST 验证率达 99%+——捏造形式接近于零）
- 输出与密封集上的参考译文接近（chrF++ ≥ 55）
- 双语母语者按照社区自己的协议，将分层样本中至少 70% 的条目评为可接受或更佳——这是唯一能反映质量的条件
- 剩余的错误属于真实语言错误（错误的曲折变化、不正确的旁指、有生性不匹配）——而不是捏造的词汇

这是一个**不会破坏语言**的系统。它可能不完美，但它产生的每个词都是真实的词。这是对多综合语尊重的机器翻译的最低标准。

## 3. 奖项申领流程

### 3.1 准入，然后提交

1. **公开取得资格。** 开发者使用自己的系统对竞赛公布的开发集进行评分，并保留回执（`mt-eval contest qualify`）。根据设计，该回执属于自报数据——它是一种声明，主办方将在第 4 步对其进行核验。

2. **交付参赛提交。** 参加竞赛的方式是向主办方的节点提供其可运行的内容，包含以下两种赛道之一：
   - **模型** — safetensors 权重、声明式分词器和配置文件，完全不包含任何代码（`mt-eval contest submit-model`）；或
   - **方法** — Dockerfile 和入口点，包含所有依赖项（vendored），以便在无网络的情况下构建和运行（`mt-eval contest submit-method`）。

   上传已发布测试集的翻译结果，以及链接开发者自行发布的分数，**已于 2026-09-06 作为竞赛提交途径废止**，相应命令已被删除。自报分数仍然属于公开排行榜，那是一个按语料库和语言对方向索引的公开看板——并非竞赛，也不属于奖项赛道。

3. **在提交本身中声明：** 赛道（`constrained` — 仅在主办方允许的数据上训练 — 或 `unconstrained`）、参数量、权重的许可证及是否公开、约束声明所涉及的训练数据、此提交是团队的主要提交还是对比提交，以及（在竞赛有要求时）系统描述。开发者还须传入用于方法提交条款的 `--agree`，以及在竞赛声明了奖项条款时传入用于该条款的 `--accept-terms <hash>`。

### 3.2 评估

1. 主办方节点对提交包运行**静态检查**，拒绝任何需要网络访问的内容，并拒绝接受了非本竞赛声明之奖项条款的提交。
2. 节点在自己本地的公开开发集副本上，使用相同的赛道执行器和相同的评分器，**自行重新执行资格验证**。开发者的回执只是一种声明；此处才是实际测算。若未达到指标，在此阶段就会被拒绝——在此之前无需任何保管人批准，密封集也不会打开——并附带声明值、测算值和门槛要求。
3. **保管人授权**密封运行（M-of-N 多签，依据竞赛的授权模型）。授权是一次性、有时间限制的，并与精确的（提交包哈希、语料库、语料库版本、节点）指纹绑定。
4. 参赛作品在主办方自己机器上的网络隔离沙箱内，针对 `gold_standard` 密封语料库运行，并计算自动化指标（chrF++ 及其置信区间和签名、其他标准指标以及诸如 FST 接受度等诊断指标）。声明的密封保留集和任何第三方测试套件都在**同一**授权运行中执行。
5. **仅允许聚合分数出站**——在数据库层强制执行，而非仅凭约定。如果竞赛承诺了 `hidden_until_close`，则运行卡会被暂扣，直到结算公布。
6. 如果满足自动化阈值（条件 2–3），主办方将进入社区审核阶段。如果不满足，开发者将收到其得分，不会触发社区审核。

### 3.3 社区审查

1. 输出的分层样本（≥30 个条目，覆盖难度等级 2–5）呈现给双语使用者
2. 至少 2 名独立审查者对每个条目进行评级
3. 评级标度：**拒绝** / **要点** / **可接受** / **优秀**
4. 如果 ≥70% 的条目从两名审查者那里获得"可接受"或"优秀"，社区验证通过

### 3.4 支付

顺序是固定的：**验证声明的关卡步骤 → 竞赛结算关闭 → 支付奖金。** 涉及哪些具体步骤取决于*本场*竞赛声明的条款（§2.1，条件 7）——但无论如何，它们都会在结算之前完成验证，且绝不会从仍在变动的排名中发放任何款项。

组织者可以使用 `close --force` 跳过未满足的关卡。届时结算仍会完成，冻结的排名将精确记录该参赛作品计算得出的获奖资格——即不具备资格，并标明未通过的步骤。强制结算只是关闭竞赛，绝不等同于通过关卡。

1. 满足所有 7 项条件
2. **核验竞赛声明的奖项条款所要求的每个关卡步骤**——必须包含所评分构建物的交付，以及在这些条款有要求时记录的已发布记录和/或已转让记录
3. 竞赛**结算关闭**，其排名冻结
4. 治理机构根据冻结的排名确认结果
5. 奖金在确认后 30 天内支付
6. 声明条款中有关所有权的任何规定均按这些条款的说明生效——对于 `rights` 为 `participant_retains_all` 的竞赛，完全不发生任何权益转移
7. 结果在排行榜上发布，带有“社区已验证”（Community Validated）验证等级

### 3.5 多次提交

- 同一开发者/团队可以多次提交
- 每个提交独立评估
- 如果方法改进并重新提交，仅最新运行卡计数
- 奖项颁发给**首个**通过所有阈值的方法——不分割

### 3.6 团队提交

- 团队和长者-青年对符合条件
- 团队内的奖项分配是团队的责任
- 所有团队成员必须签署参与条款
- 排行榜上的署名列出所有团队成员

## 4. 未来奖项池 {#4-future-prize-pools}

创始人奖是种子。额外的奖项池由赞助商资助。每个新奖项池都记录为 §2 的新小节，带有其自己的：

- 奖项金额和货币
- 语言对
- 赞助商署名
- 阈值条件（可能与创始人奖不同）
- 过期日期（如果有）
- 任何特殊条件

### 4.1 赞助商奖项模板

赞助商以任何金额资助奖项池。建议的等级：

| 级别 | 金额 | 建议门槛 |
|------|--------|---------------------|
| **种子奖** | $5,000–$15,000 | 密封集上的 chrF++ 门槛，在竞赛开放前公布 + 社区验证 |
| **突破奖** | $25,000–$50,000 | 更高的 chrF++ 门槛 + 社区验证 |
| **大奖** | $100,000+ | 突破奖条件 + 多语体覆盖 + 部署集成 |

门槛始终基于 chrF++（附带其签名，以确保可复现）；可添加诸如 FST 接受度等诊断关卡作为把关条件。综合得分或质量等级不可作为奖项门槛。

赞助方还可以资助：
- **进步赏金** — 相比当前最优成绩，chrF++ 每提高 5 分获得固定金额奖励
- **语体奖** — 针对特定语体（正式、典礼、教学）的独立奖项
- **成本奖** — 在达到 chrF++ 门槛的方法中，单次条目成本最低者获奖（成本显示在分数旁，绝不与分数合并）

### 4.2 奖项资金的持有位置

奖项资金是**赞助商持有**：它们由赞助组织或赞助商指定的社区信托持有——**永远不会由 Champollion 持有**，它协调测量且不接触任何资金。一个可信的奖项在开放前发布：**谁持有资金**，在什么安排下（组织账户、信托或赞助商选择的第三方托管），以及奖项阈值——以便通过标准可从发布的分数加上社区的说话人验证判决进行验证，支付违约将作为一个可见的。目前没有奖项资金在任何地方持有。如果奖项过期未申领，资金留在它一直所在的地方——与赞助商——由赞助商自行决定重定向或撤回。自助机制，包括赞助商违约风险及其缓解措施，记录在 [运行主权竞赛](/docs/network/sovereignty/run-a-sovereign-contest) 和 [条款模板](/docs/network/sovereignty/terms-templates) 中。

## 5. 取消资格

提交在以下情况下被取消资格：

1. **在评估数据上进行训练。** 方法曾接触过 `gold_standard` 或 `held_out` 语料库条目。（架构上通过沙箱执行予以杜绝——但如果发现污染证据，结果作废。）
2. **不可复现。** 治理机构无法在 ±2% 误差范围内复现得分。
3. **未声明或不合规的依赖项。** 该方法在运行时需要访问其依赖清单声明之外的外部服务，或者其实际依赖类别属于 A2 或 X（§1.6）。允许通过评估网关路由声明的 Class A1 LLM 推理；任何其他运行时网络依赖项——以及任何未声明的任何类别依赖项——均将取消资格。
4. **未签署参与条款。** 所有团队成员必须同意方法提交条款，并且在竞赛声明了奖项条款（§1.3）时，必须通过哈希值同意这些条款。
5. **检测到刷分作弊行为。** 输出针对指标而非翻译质量进行了刻意优化（由社区审核和/或按照 BENCHMARK_SPEC §9.3 的防作弊检查捕获）。

## 7. 代码–规范同步

### 7.1 规范源

本文档 (`cli/website/docs/network/specifications/prize-spec.md`) 是以下内容的规范源：
- 奖项池定义 (§2)
- 阈值条件 (§2.x)
- 申领流程 (§3)
- 取消资格规则 (§5)

### 7.2 实现要求

当奖金池激活时：
1. 排行榜 UI 必须显示处于活跃状态的奖项及其门槛条件
2. 达到自动化门槛（条件 2–3）的运行卡必须被标记以供社区审核
3. 不使用质量等级：每个新运行卡上的 `quality_tier` 字段均为空（null）（scoring standard/1）
4. 奖项**条款**层已经就绪（`contest_prize_terms` — 包含声明、哈希、接受凭证以及支付关卡），评分机制本身保持不变。新增奖金池所需补充的仅是 §2 中的门槛策略以及上述第 1–2 项中的排行榜前端展示

*奖金结构必须与同一竞赛声明的奖项条款相兼容（§1.3）。这些条款涵盖各个维度的自主选择——从“测算完毕后删除，所有权利保留在参赛者手中”到“你交付成果，无论谁获胜我们都会测算并保留”——它们在任何人参赛之前便已公布、哈希化并被接受。希望获奖方法成为社区财产的社区主办方可以明确声明这一点，届时奖金将资助创造出属于该语言社区的技术。本文档绝不会代表任何主办方擅自假定这一点。*
