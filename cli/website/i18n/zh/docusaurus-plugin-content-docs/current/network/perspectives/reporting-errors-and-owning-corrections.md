# 报告错误和纠正所有权

> **立场。** 对于一个发布关于多种语言的事实与评估结果的平台而言，出错是不可避免的。但*并非*不可避免的是：当错误被报告时，谁的话会被采信，以及谁拥有该修正的所有权。我们的回答是：流利母语者的报告优先级高于我们的自动化系统；每一次修正都带有溯源信息，标明是谁修改了什么以及为什么修改；社区可以撤回或否决对其语言数据的使用——这不是一种出于客气的施舍，而是架构中硬性执行的特性。

大多数数据平台将错误报告视为支持工单：用户投诉，维护者决定，记录无声地改变。对于土著语言数据，这种模式是颠倒的。报告错误的人通常比平台更有权威性——使用者告诉我们一个词是错误的不是"用户"，他们是纠正代理的基本事实。下面的设计遵循认真对待这一点。

---

## 两种错误，一个原则

该平台发布两种可能出错的主张：

1. **语言事实** — 驱动评估的语言卡片：分类数据、正字法、语言学特征、适用的指标。卡片中可能包含错误的说话人口估算、错误的方言关系，或错误的书写系统状态。
2. **翻译判断** — 语料库中被语言使用者认为错误或不自然的参考翻译；排除了有效词汇或接受了无效词汇的自动评估指标；语言使用者无法接受但获得高自动评分的输出。

涵盖两者的原则，已在[评分规范](/docs/network/specifications/scoring)和[基准规范 §7](/docs/network/specifications/benchmark#7-human-validation)中生效：**自动化输出是代理；使用者是基本事实。** [使用者验证协议 §6](/docs/network/specifications/speaker-validation#6-what-speakers-get)中的已发布承诺直言不讳：如果使用者说 linter 在某些方面是错误的，我们会修复 linter。

## 报告如何流转

以下是报告采取的路径，带有诚实的状态标记——其中一些现在运行，一些已指定但尚未构建。

**报告不良翻译或指标判断（目前已上线，通过直接渠道）。** 如果母语者发现错误的参考翻译、被错误拒绝的词汇或不可接受的“对等表达”，可以通过项目的公开仓库 Issue 跟踪器或直接联系项目团队进行报告。这一机制的结构化版本——带有*拒绝 / 大意相符 / 可接受 / 优秀*选项以及自由文本备注的评分界面——即社区评审界面，已在[基准规范 §7.3](/docs/network/specifications/benchmark#7-human-validation)中详细说明，但尚未正式上线。在该功能上线前，报告将通过人对人方式处理，而验证任务本身（付费的结构化母语者评审——参见[与母语者合作](/docs/working-with-speakers)）则是主要的修正流水线。

**报告语言卡片上的错误事实（现在运行，相同渠道）。** 卡片纠正遵循相同路径：报告、审查、版本化更改。因为卡片驱动评估行为——哪些指标加载、推荐哪些模型——卡片修复可以改变分数，所以纠正作为记录的数据更改应用，从不无声编辑。

**接下来会发生什么——谁决定：**

- **语言层面的裁决权属于该语言的母语者。** 某种形式是否有效、两种表述是否等价、某种语域是否恰当——平台负责实现答案，而非提供答案。在母语者存在分歧的地方（方言、正字法惯例），答案会被记录为变体，而不是由我们来裁决——语料库和 linter 模式支持将方言变体标记为可接受的替代方案，而不是强行裁定出单一胜者。
- **关于社区数据的决策权属于其管理组织。** 对于设有管理组织的语言，评估语料库的变更、将修正纳入封装测试集以及部署层面的后果，均须经由它们审批——这就是语言数据的社区控制权——参见[您的语言，您的规则](/docs/your-words-your-rules)——它被实现为具体流程，而非宣传口号。
- **机械性错误直接修复即可。** 错别字、失效链接、解析错误的字段——报告、修正、记录即可。并非所有事情都需要委员会介入。

## 纠正附带来源信息

无法追踪的纠正只是一个更新的观点。三个来源规则适用于每个事实和每个修复：

1. **每一条事实都标明来源。** 语言卡片和语料库条目都会记录每个数值的来源——是公开发布的数据集、社区贡献，还是母语者的评审。
2. **派生值标记归属于我们，而非上游。** 当平台计算某项内容时——如聚合值、重新编码或综合指标——它会被记录为平台*源自*上游源的派生数据，绝不会冠以上游的名义。上游数据集绝不应为它未曾发布的数值承担责任或获得荣誉。
3. **修正会成为记录的一部分。** 母语者的修正会被记录为一条署名的新断言（实名或匿名，由母语者自行决定——条款与验证工作相同），并取代旧值；变更历史保持可审计。语料库版本带有哈希清单（[注册语料库](/docs/network/sovereignty/registering-corpora)），因此修正后的语料库是一个明确可见的新版本，并且每张运行卡片都会准确记录它是针对哪个版本进行评分的——旧评分保持可解释性，新评分则体现了修复。

## 否决权，具体来说

"社区控制"很容易声称。以下是它在已发布架构中的具体体现：

- **母语者可以撤回其贡献。** 母语者可以随时撤回其评分，撤回后这些评分将从所有分析中移除（[母语者验证 §5](/docs/network/specifications/speaker-validation#5-data-governance)）。母语者对其认为存在问题的结果发布也拥有否决权。
- **社区可以彻底终止评估。** 封装测试集经过加密，Champollion 不持有任何密钥分片，因此平台自身永远无法重构它们。目前，封装测试集的密钥由组织者持有——社区密钥保管人：尚未指定。一旦社区指定的保管人持有了测试集密钥的分片，他们就可以通过拒绝参与密钥重构来终止评估（[注册语料库](/docs/network/sovereignty/registering-corpora)）。对于“如果我们想终止怎么办？”这个问题，有着明确的规范回答：封装数据绝不会被暴露，评估随即终止。
- **任何评分都不能凌驾于社区决定之上。** 排行榜上的排名不会赋予任何人针对某个社区的语言部署某种方法的许可（[所有权转让](/docs/network/sovereignty/ownership-transfer)）——而如果某个社区决定完全不为其语言部署机器翻译，这是在行使系统原本设计的功能，而非破坏系统（参见[翻译不等于语言复兴](/docs/network/perspectives/translation-is-not-revitalization)）。

## 我们尚未构建的内容

秉承本栏目其他内容一贯的原则：社群审查界面目前仍在规划中，尚未上线。目前尚未针对任何语言建立治理组织——包括 Plains Cree 在内的任何基准测试均未指定社群保管人（community custodian），并且在征得同意之前，我们不会公开列出任何保管人姓名。在这些机制建立起来之前，修正将通过直接且可追溯的渠道进行，已发布的规范——而非本页面——始终是该流程具有约束力的说明。如果本页面与规范存在分歧，以规范为准，并且我们也会将此类分歧视为值得报告的 Bug。

## 这对你意味着什么

:::info[如果您是社区成员]
如果本平台上关于您的语言有任何内容出现错误——无论是事实、翻译还是标签——您的报告都是来自第一手事实的证言，而不是等待分类排查的普通投诉。您可以自行决定修正是实名署名还是匿名；您的贡献之后可以撤回；您的社区也可以彻底叫停对其数据的使用。请从[您的语言，您的规则](/docs/your-words-your-rules)开始，或者直接在公开仓库上提交 Issue。
:::

:::info[如果你是研究人员]
这里的更正是带有来源信息的数据，而非无声的编辑：语料库版本经过哈希处理，运行卡会固定它们所针对的确切版本，衍生值会被标记为衍生。如果你基于 Network 分数或语料库进行构建，请引用版本——并将由说话者驱动的大规模更正波视为关于指标有效性的一项发现，因为这正是它的本质。
:::

:::info[如果你是开发者]
你的方法的分数可以在代码未变的情况下合理地改变——一个被错误拒绝的词被加入允许列表，一个参考翻译被更正，一个变体类被修复。为此进行设计：在运行卡中固定语料库版本（[Run Card spec](/docs/network/specifications/run-card)），监控数据集变更日志，并将说话者更正视为你能免费获得的最可靠的错误信号。
:::
