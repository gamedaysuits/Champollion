# 技术限制

> **初来乍到？**[尚无法实现的功能](/docs/what-it-cant-do-yet)用通俗易懂的语言说明了同样的内容。本页面则是面向开发者、研究人员和智能体的精确版本。

这些是我们**绝不**夸大的声明界限。如果本网站其他任何地方暗示的内容超出了此处所写的范围，请将其视为错误并[通知我们](/docs/network/perspectives/reporting-errors-and-owning-corrections)。

评估基础设施只有通过对其边界诚实才能赢得信任。以下是我们的边界，表述得足够清楚以便验证。

## 1. 深度形态学验证依赖于 FST *以及* 可排名的测试集

基于 FST 的形态学验证——即检查每个输出词在目标语言中是否均为构词规范的词——对某个语言对需要具备两点：评测框架所固定的 FST，以及该语言对可排名的评测集。`GiellaLTFSTMetric` 本身是**通用**的：它可以对任何拥有固定 GiellaLT FST 的语言进行评分（平原克里语、萨米诸语言、芬兰语、书面挪威语、伊努克提图特语等）。这些语言中有数种拥有开放评测集（Tatoeba、WMT、WMT24++）——[数据集页面](/docs/network/leaderboard/datasets)列出了完整目录，`mt-eval corpora --source eng --target <code>` 列出了某个语言对可以运行的内容，而 `mt-eval corpora --with-fst` 仅列出目标语言拥有固定 FST 的语言对，并指明其是否已安装在你的机器上。平原克里语（这项 FST 工作的发源语言）是个例外：它的两个评测集（EdTeKLA）被编目为隔离标签，数据库会拒绝任何针对它们提交的分数。

这里还有另外两项限制。当固定的 FST 仅是拼写检查**接受器（acceptor）**（北萨米语、阿姆哈拉语、巴斯克语）时，它只能表明某个词是否存在，而无法判断其屈折变化是否正确，因此不会计算 `morphological_accuracy`——而且接受器会接受某些英文和首字母大写的单词，因此 FST 接受率可能会给未翻译的输出计分（此时运行卡片会显示源文复制警告；参见[评分警告](/docs/network/specifications/scoring#2-8-score-caveats)）。FST 接受率仅作为诊断指标：它绝不会计入 chrF++ 核心指标，也不会用于运行排名。
如果对每个输入都重复输出同一个有效句子，它也会计分；此时运行卡片会显示接近恒定输出警告。
此外，所有没有 FST 的语言对都使用表面指标（chrF++、BLEU）和行为检查来进行评分。这些虽然是有用的信号，但并**不能**保证形态学有效性。对于没有同时具备 FST 和可排名评测集的任何语言，我们均不声称具备形态学验证。

## 2. 信任层级：目前每一行均为自行上报 {#2-trust-tiers-are-self-reported-at-launch}

大多数评分都是由贡献者自行运行测试套件并发布结果计算得出的。**验证**——即根据提交自身的输出，对照 SHA 固定的规范语料库重新评分——虽然已经构建完成，但它是一个由维护者手动运行的命令：提交时不会自动运行任何验证，也没有任何调度机制，因此目前每一行在提交时以及之后都处于自行基准测试状态（参见[提交规则](/docs/network/leaderboard/rules#verification-tiers)）。请注意每一行上的信任徽章：**“自行上报”就是字面上的意思**，并且这是默认状态。

## 3. 社区使用者验证尚未进行

拟设奖项要求**双语使用者的认可度 ≥ 70%**（目前尚未开放任何奖项）。该准入门槛已经明确规范，运行所需的工具也在构建中——但**尚未进行过任何社区使用者评审**，且**本网站上的任何评分均未通过使用者门槛**。chrF++ 以及其他所有自动化指标都只是机器信号，而非社区判定，这也是为什么此处的任何评分都不带质量标签的原因。

## 4. 评测沙箱与密钥仪式已存在；尚未有保管人使用过它们

我们从源头获取语料库并进行 SHA 固定，保留拆分集则处于封存状态。当社区持有秘密测试集时，可以在测试集完全不离开他们掌控的情况下对某种方法进行评分——而该评估现在有**两条通道**。针对标准神经模型，首选通道是**声明式**的：参与者仅提交数据——safetensors 权重 + 声明式分词器 + 配置文件——组织者则在自己受信任的推理引擎中运行它（`trust_remote_code=False`，离线；对架构较为宽容，因为安全性源自无代码格式，而非架构名称）。完全不运行任何参与者代码，因此无需沙箱隔离；安全检查属于可判定的格式验证（这是 safetensors 而不是 pickle 吗？没有 `trust_remote_code` 吗？），而不是试图证明任意代码的安全性。对于确实包含代码的方法（流水线、LLM 辅导的混合方法），备用方案是网络隔离的**沙箱**（静态检查、`--network=none` 容器、仅限分数的出站传输、可选的真正物理隔离文件传输）。由于沙箱没有网络，方法在其中运行时必须将其调用的所有模型都包含在打包套件内：LLM 辅导的混合方法必须将其 LLM 以开放权重形式打包提供，因为无法访问托管的 LLM API。沙箱容纳不受信任的代码而不是拒绝运行它，因此客观而言它是安全性较弱的通道——其主要承重保障是 `--network=none`（启发式静态扫描无法审查二进制模型），更深度的加固（seccomp、microVM）则暂缓实现。有关具体上线与未上线的内容，请参阅[举办自主竞赛](/docs/network/sovereignty/run-a-sovereign-contest)。离线节点的**密钥仪式已构建完成**——测试集密钥采用 M-of-N 分片，仅在达到法定人数授权的运行期间在内存中重新组装——但它从未与真正的保管人一起使用过，且在此第一版中，分片仍是纯文本文件。**尚未**构建的内容包括：门限签名（评分由单个节点密钥签名）和硬件认证（评分清单仅在软件层面签名）。尚未指定任何社区密钥保管人，因此在保管人和社区同意落实之前，黄金标准的**奖项**评估仍保持关闭状态。

## 5. 目前密钥由组织者持有；尚未指定社区保管人 {#5-key-custody-is-designed-no-custodians-are-appointed-yet}

**目前，封存测试集的密钥由其组织者持有**——即由封存该测试集的人在其自己的机器上持有。**Champollion 不持有任何密钥分片。**面向多个持有者的保管*机制*已构建完成：离线节点的 M-of-N 密钥仪式可在多位保管人之间拆分测试集密钥。但该机制尚未与真正的保管人一同运行过。保管人由社区自行挑选，目前尚未指定任何保管人：**社区密钥保管人——尚无指定。**保管并不等同于知情同意：基于关系的社区知情同意流程是一条独立的、更漫长且更重要的轨道。

## 6. 我们在基准上衡量方法；我们不对单条翻译打分 {#system-vs-output}

有两种不同的事物都被称为“值得信赖的机器翻译”。我们做的是其中之一。

**系统级别——我们所做的事。** 给定一个语言对、一个测试集和一种方法：该方法在什么指标下、在哪个领域中、在哪个数据污染通道中、在哪个信任等级上得分如何？这是关于*基准上的方法*的断言，加上关于由谁设定标准的断言。评分规则是公开的，语料库是固定的，对于主权基准，拥有测试集的社区决定了何为合格。排行榜、地图、运行卡片以及 `mt-eval` 全都属于此类，而且仅此而已。

**输出级别——我们不做的事。** 给定一个源句及其一条翻译：*该*翻译正确的概率有多大？在机器翻译和自然语言处理中，这属于质量评估与不确定性量化，它本身就是一个独立的研究领域。我们**不发布任何翻译的单句置信度**，本站上的任何内容都不是某个给定输出是否正确的校准概率。高分的榜单行并不代表对该方法生成的下一句话提供担保。

反向的推导是一个更容易犯的错误，它对我们也同样适用。当本站的某个页面显示某个语言对没有任何方法得分足以支持上线部署时——正如[人工翻译服务](/human-services)中所指出的——这是针对被测测试集上被测方法的声明。这是不为该语言对交付机器翻译输出的充分理由。但它并不是对任何特定句子的裁决。

**质量评估是一个预留的插槽，而不是隐瞒的缺陷。** 评测框架已经计算了一个无参考的神经评分 AfriCOMET-QE（`qe_score`），作为没有黄金参考的运行的充分度信号。它在独立的神经通道中作为**语料库级别**的数值报告，由验证器重新推导，且绝不会计入 chrF++ 核心指标（[评分规范](/docs/network/specifications/scoring#how-runs-are-scored)）。指标均以插件形式存在（[插件规范](/docs/reference/plugin-spec)），因此句级 QE 指标是此评测框架可以接纳的。在某个指标像基于参考的指标那样完成接入、发布并按语言进行元评估（[指标可靠性](/docs/network/specifications/metric-reliability)）之前，我们不对单个输出做任何评判。
