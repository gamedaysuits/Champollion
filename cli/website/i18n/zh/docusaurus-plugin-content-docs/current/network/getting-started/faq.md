# 常见问题

> **执行摘要。** 关于 Champollion 网络的常见问题解答 — 评分如何运作、哪些内容会被取消资格、如何处理没有 FST 的语言、模型和参数建议，以及提交流程。

---

## 评分与指标

### 测试框架计算哪些指标？

该测试框架计算五个指标。其中三个与语言无关，适用于任何语言对；另外两个目前依赖于 CRK 特定的插件，随着我们扩展到更多语言，这些指标将被泛化。当前可运行的参考语料库是开放许可的公共数据集——Global Voices、Tatoeba、TICO-19、IN22、SMOL 等（参见 [数据集](/docs/network/leaderboard/datasets)）——排行榜对所有已注册的语言对开放提交。Plains Cree 只是两个特定语言（基于 FST）指标首次实现的地方。

| 指标 | 范围 | 测量内容 | 状态 |
|--------|-------|-----------------|--------|
| **chrF++** | 0–100 | 预测翻译和参考翻译之间的字符 n-gram 重叠。对形态丰富的语言最佳的表面指标。使用 sacrebleu 的原生评分。 | ✅ 所有语言 |
| **精确匹配** | 0.0–1.0 | 规范化后预测与参考完全匹配的条目比例。 | ✅ 所有语言 |
| **FST 接受度** | 0.0–1.0 | 有限状态转换器（形态分析器）接受的输出词的比例。仅在提供 FST 二进制文件时计算。 | ✅ 所有具有 FST 的语言 |
| **等价匹配** | 0.0–1.0 | 与参考或可接受变体匹配的条目分数 — 考虑词序、正字法约定和方言差异。 | ⚡ CRK（泛化中） |
| **语义评分** | 0.0–1.0 | 意义保留评分 — 翻译在多大程度上捕捉了预期含义，无论表面形式如何？ | ⚡ CRK（泛化中） |

计划增加更多指标：**形态准确性**、**代码混用检测**、**术语遵循**和**幻觉检测**。参见 [评分规范 §2](/docs/network/specifications/scoring#2-metric-inventory) 了解完整的指标清单（六个类别）。

### 综合评分如何计算？

综合评分是可用指标的加权平均值，归一化为 0.0–1.0 范围。权重在两个配置文件中定义：

- **配置文件 A**（具有 FST 的语言）：9 个指标，结构指标（FST + 形态准确性）占综合权重的 40%
- **配置文件 B**（没有 FST 的语言）：8 个指标，语义和 chrF++ 承载相等的最高权重

当指标不可用时，其权重按比例重新分配到其余指标中。这意味着早期基准（仅具有 chrF++ 和精确匹配）仍然产生有效的综合评分 — 有效权重只是反映可用的内容。

**完整的权重表、规范化规则和排除理由在 [评分规范 §4](/docs/network/specifications/scoring#4-composite-score) 中。** 测试框架代码在 `mt_eval_harness/scoring.py` 中镜像这些表。chrF++ 通过在加权前除以 100 来规范化；代码混用和幻觉率被反转（越低越好）。

### 什么是质量等级？

质量等级是映射到综合评分范围的启发式标签。它们帮助传达评分在实践中的*含义*：

| 等级 | 综合范围 | 解释 |
|------|----------------|----------------|
| **基线** | 0.00 – 0.30 | 低于有用质量。方法需要显著改进。 |
| **新兴** | 0.30 – 0.50 | 显示前景。某些翻译正确但不一致。 |
| **功能性** | 0.50 – 0.70 | 可用于参考，需要人工审查。不适合未审查的部署。 |
| **可部署** | 0.70 – 0.85 | 准备好用于生产，需要定期审查。触发所有权转移资格。 |
| **流畅** | 0.85 – 1.00 | 接近母语质量。适合无监督部署。 |

### 质量等级和验证等级之间有什么区别？

**质量等级**描述*自动评分的含义*（基线 → 流畅）。**验证等级**描述*谁验证了结果*：

| 验证级别 | 含义 |
|-------------------|---------------|
| **Self-benchmarked** | 提交者自行运行了测试框架。分数看似合理但未经证实。 |
| **Champollion Verified** | 维护者使用提交的方法配置重现了该结果。 |
| **Community Validated** | 根据社区自身协议获得资格的目标语言双语使用者，审查了输出的分层样本（≥30 个条目，≥2 名审查者），且 ≥70% 达到了社区的标准。仅通过社区自身的测试授予；通过抽查降级是对等的，且同样公开。 |

一个方法可以是"可部署"质量但仅"自我基准测试"验证 — 意味着评分看起来很好但没有人独立确认过。

## 提交与取消资格

### 什么会导致我的提交被取消资格？

如果出现以下情况，您的提交将被拒绝或标记：

1. **您的方法接触到了评估数据。** 如果您从评估数据集中训练、微调、少样本提示或以其他方式使用了任何条目，您的评分会被人为夸大。这包括在提示中使用参考翻译。
2. **您的运行卡未通过完整性检查。** 指纹必须与配置匹配。篡改的运行卡会被拒绝。
3. **您的方法未实现 TranslationMethod 协议。** 测试框架期望 `translate(entries, config) → results`。绕过测试框架的自定义集成不被接受。

### 我可以多次提交吗？

可以。排行榜跟踪所有提交。您可以迭代 — 运行数十个实验，仅提交最佳的。每个提交记录一个唯一的指纹，因此不存在关于哪个运行产生哪个评分的歧义。

### 我如何获得评分验证？

1. **Self-benchmarked（自动）：** 每次提交都从这里开始。
2. **Champollion Verified（自动）：** 服务器使用测试框架指标，对照固定 SHA 值的参考语料库对您提交的输出重新评分。当您的分数被重现时，该运行将晋升为 Champollion Verified —— 这是排行榜进行排名的唯一级别。如果无法重现，或者存储的参考资料被更改，该运行将被取消资格。
3. **Community Validated：** 根据社区自身协议获得资格的目标语言双语使用者，审查您方法输出的分层样本 —— 至少 30 个条目，至少 2 名审查者 —— 且至少 70% 必须达到社区的标准。该级别仅由社区自行决定通过其自身运行的测试来授予，并且可以以相同的方式撤销：未通过抽查将同样公开地对该方法进行降级。这无法自动化 —— 它需要社区的参与。

### 为什么不重新运行每个人的方法来进行验证？

因为我们负担不起，也没有必要。服务器免费对*所有人*提交的输出重新评分（这能捕获手动输入或篡改的分数）。实际重新运行模型需要消耗真实的计算资源，因此我们通过**基于声誉加权的审计**选择**样本**来进行：如果一次运行具有高风险（例如它首次打通了通往整个语系的桥梁）或存在异常（例如比之前的最佳结果好得令人难以置信），则始终会重新运行；而对于已证明可靠的贡献者，则很少进行抽查。声誉只能通过通过这些审计（或由独立贡献者证实您的结果）来获得 —— 绝不是通过提交数量 —— 因此，新注册的“一次性”身份得不到任何好处。一旦发现造假，贡献者的声誉将归零，其整个已验证的历史记录将被重新审计，并像撤稿一样被公开记录。我们**不**声称您的运行“通过了测试框架” —— 对于无法由服务器验证的自托管计算而言 —— 因此，有效性取决于*可重现性 + 声誉质押 + 交叉证实*，而不是单方面的证明。有关完整模型，请参阅 [MT 评估规则](/docs/network/leaderboard/rules#how-verification-scales-reputation-weighted-auditing)。

### 提交 API 是否已上线？

还没有。`https://champollion.dev/api/leaderboard/submit` 端点是一个愿景。当前的提交路径是 `mt-eval publish`——它将测试框架输出目录（`eval/logs/harness/`）中的运行卡直接上传到排行榜，作为*自基准测试（未验证）*。

## 模型与参数

### 我应该使用什么模型？

没有单一的最佳模型 — 这取决于语言对、您的预算和您的方法。一般指导：

| 语言类型 | 推荐起点 | 原因 |
|---------------|---------------------------|-----|
| **高资源**（法语、西班牙语、日语） | `google/gemini-2.5-flash` 或 `gpt-4o-mini` | 快速、便宜、强大的基线 |
| **低资源但有一定 LLM 覆盖**（克丘亚语、约鲁巴语） | `google/gemini-2.5-pro` 或 `anthropic/claude-sonnet-4` | 更大的模型具有更好的潜在知识 |
| **多综合型 / 极低资源**（平原克里语、因纽克提图特语） | `google/gemini-2.5-pro` 带教练数据 | 教练数据比模型选择更重要。OMT-1600 包括一些多综合型语言（例如，R1 等级的 CRK），但使用标准 BPE 分词 — 在网络中将其作为基线进行基准测试。 |

评估框架使用 OpenRouter，因此可以对 OpenRouter 上可用的任何模型进行基准测试。有关可用列表，请参见 [openrouter.ai/models](https://openrouter.ai/models)。

### 我应该使用什么温度？

对于翻译，通常越低越好：

| 温度 | 效果 | 推荐用于 |
|-------------|--------|-----------------|
| **0.0 – 0.2** | 高度确定性、一致的输出 | 生产方法、最终基准 |
| **0.3 – 0.5** | 某些变化、偶尔更有创意 | 探索、早期迭代 |
| **0.6+** | 高度变化、不可预测 | 不推荐用于 MT 基准测试 |

温度记录在运行卡中，因此不同的温度产生不同的指纹 — 它们被视为不同的实验。

### 教练数据有帮助吗？

是的，对低资源语言特别有帮助。教练数据（语法规则、字典条目、风格说明）被注入到 LLM 系统提示中。对于平原克里语，教练方法对多综合型语言的表现一致优于原始 LLM 方法，因为通用 LLM 对多综合型的接触有限，没有形态意识。即使是专门为 CRK 训练的 OMT-1600，也使用无法在结构上表示多综合型形态的标准 BPE 分词。教练数据提供了模型缺少的语言学背景。

对于高资源语言（法语、西班牙语），教练的影响较小，因为模型已经具有强大的基线知识。

参见 [教练数据](https://champollion.dev/docs/concepts/coaching-data) 了解完整规范。

## FST 与形态验证

### 如果我的语言没有 FST 怎么办？

许多语言没有有限状态转换器。这没关系 — 测试框架在没有 FST 的情况下也能工作。综合评分使用配置文件 B 权重（参见 [评分规范 §4.3](/docs/network/specifications/scoring#43-weight-tables)），这将权重转移到语义和表面指标。FST 接受度在运行卡中标记为 `null`。

现有 FST 的主要注册表：

| 注册表 | 覆盖范围 | URL |
|----------|----------|-----|
| **GiellaLT** | 100 多种语言 —— 萨米语、克里语、伊努克提图特语以及许多其他乌拉尔语系和少数民族语言 | [giellalt.uit.no](https://giellalt.uit.no/) |
| **ALTLab** | 平原克里语、楚蒂纳语、奥达瓦语 | [altlab.ualberta.ca](https://altlab.ualberta.ca/) |
| **Apertium** | 约 60 种语言对，主要为欧洲语言 | [apertium.org](https://apertium.org/) |
| **UniMorph** | 150 多种语言的形态学范式 | [unimorph.github.io](https://unimorph.github.io/) |

### 我可以构建 FST 吗？

可以，但这并非易事。FST 编码了语言的形态规则 — 所有有效的词形。构建一个需要对语言有深入的语言学知识。如果您可以访问形态语法（例如，来自语言学系），可以使用 [HFST](https://hfst.github.io/) 或 [Foma](https://fomafst.github.io/) 等工具将其编译为 FST。

### FST 门控在实践中如何工作？

FST 门控管道的工作方式如下：

1. LLM 生成翻译
2. 输出中的每个词都针对 FST 进行检查
3. FST 拒绝的词被标记为形态无效
4. 方法可以使用反馈重试（"词 X 无效，请重试"）
5. 重试后，剩余的无效词被记录

FST 接受度衡量有多少词通过验证。参见 [FST 门控管道教程](/docs/network/tutorials/fst-gated-pipeline) 了解完整的工作示例。

## 数据与数据集

### 我可以为新语言贡献数据集吗？

可以。来自 [基准规范 §11](/docs/network/specifications/benchmark#11-extending-to-new-languages) 的最低要求：

- **50 个金标准条目**（源 + 验证的参考翻译）
- **30 个开发条目**（对于小语料库可与金标准重叠）
- **社区同意**（对于土著语言，需要来自治理机构的明确授权）
- **出处文档**（数据来自何处、适用什么许可证）

新数据集自动打开新的排行榜轨道。参见 [为语言社区](/docs/network/community/for-language-communities) 了解贡献者指南。

### 我的数据集应该是什么格式？

具有规范字段名称的 JSON：

```json
{
  "name": "my-language-dev-v1",
  "language_pair": "en-xxx",
  "segment": "development",
  "version": "1.0",
  "entries": [
    {
      "id": 1,
      "source": "Hello",
      "reference": "[translation in target language]",
      "difficulty": 1,
      "domain": "general"
    }
  ]
}
```

参见 [数据集](/docs/network/leaderboard/datasets) 了解完整的模式和难度等级定义。

## 主权与所有权

### 谁拥有为土著语言构建的方法？

对于土著语言，达到可部署等级（综合评分 ≥ 0.70）且通过社区验证的方法触发 [所有权转移](/docs/network/sovereignty/ownership-transfer) 流程。代码所有权从研究者转移到语言社区的治理组织。

研究者保留：
- 出版权（关于该方法的学术论文）
- 排行榜上的署名
- 将相同*技术*应用于其他语言的权利

治理组织获得：
- 方法代码和教练数据的完全所有权
- 对部署的控制（何时、何地、如何）— 以及部署获得的一切。Champollion 是非商业性的，不收取任何份额

### 我可以在没有任何主权问题的情况下为非土著语言使用 champollion 吗？

可以。对于标准语言（法语、日语、西班牙语等），没有主权考虑。正常使用 champollion — 翻译、同步、发布随意。主权框架特别适用于土著和社区治理语言，其中数据治理原则——语言数据由社区拥有和控制、CARE、Te Mana Raraunga——需要特殊考虑。
