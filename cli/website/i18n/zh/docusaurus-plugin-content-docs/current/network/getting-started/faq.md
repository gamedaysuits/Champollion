# 常见问题

> **执行摘要。** 关于 Champollion 网络的常见问题解答 — 评分如何运作、哪些内容会被取消资格、如何处理没有 FST 的语言、模型和参数建议，以及提交流程。

---

## 评分与指标

### 测试框架计算哪些指标？

核心指标，也是唯一用于对运行结果进行排名的数值，是附带 95% 置信区间的 **corpus chrF++**。在其旁边，评估框架（harness）还会报告其他标准指标——**BLEU、spBLEU 和 TER**，以及安装后的 **COMET**——每项指标独立显示，绝不混合。其余各项皆为**诊断指标**（diagnostic）：单独报告以解释得分，绝不计入评分。下表涵盖 chrF++ 和主要诊断指标；其中三项与语言无关，另外两项目前依赖特定于普莱恩斯克里语（CRK）的插件，随着我们扩展到更多语言，它们将被通用化。目前可运行的参考语料库均为开源许可的公开数据集——Global Voices、Tatoeba、TICO-19、IN22、SMOL 等（参见[数据集](/docs/network/leaderboard/datasets)）——且排行榜面向所有已注册的语言对开放提交。普莱恩斯克里语只是这两项特定于语言的（基于 FST 的）指标最初实现的地方。

| 指标 | 标度 | 评估内容 | 状态 |
|---|---|---|---|
| **chrF++**（核心指标） | 0–100 | 预测翻译与参考翻译之间的字符 n-gram 重叠度，使用 sacreBLEU 在整个语料库上计算（记录其签名）。形态丰富型语言的标准表层指标。 | ✅ 所有语言 |
| **精确匹配**（诊断指标） | 0.0–1.0 | 归一化后，预测与参考完全匹配的词条比例。 | ✅ 所有语言 |
| **FST 接受度**（诊断指标） | 0.0–1.0 | 被有限状态转换器（形态分析器）接受的输出词比例。仅在提供 FST 二进制文件时计算。 | ✅ 所有具有 FST 的语言 |
| **等价匹配**（诊断指标） | 0.0–1.0 | 与参考或可接受的变体匹配的词条比例——考虑了词序、正字法规范和方言差异。 | ⚡ CRK（通用化中） |
| **语义得分**（诊断指标） | 0.0–1.0 | 语义保留得分——无论表层形式如何，翻译在多大程度上捕捉到了预期含义？ | ⚡ CRK（通用化中） |

更多诊断指标——**形态准确度**、**语码转换**、**术语符合度**、**幻觉**和**写作风格**——以及各指标的实现状态，请参见[评分规范 §2](/docs/network/specifications/scoring#2-metric-inventory)（完整指标清单）。

### 运行结果如何评分？

每次新运行都根据评分标准 `standard/1` 进行评分，遵循该领域报告机器翻译（MT）评估的方式（WMT、FLORES-200、AmericasNLP）：

- **核心指标：** corpus chrF++，附带其 95% bootstrap 置信区间和 sacreBLEU 签名——例如 `chrF++ 47.5 [45.9, 49.0]`。
- **并行指标：** BLEU、spBLEU、TER 以及 COMET（计算时）。绝不混合。
- **诊断指标：** 精确匹配、FST 接受度、形态准确度、语码转换、幻觉、术语、写作风格。单独报告；它们绝不用于对运行进行排名。
- 当评估框架检测到会导致数值产生误导的模式时，**评分警示**会直接显示在核心指标旁边。

一次运行是否**优于**另一次运行，取决于对 chrF++ 的配对显著性检验（`mt-eval compare --significance`），而不是简单对比两个数字。完整规则请参见：[运行评分方式](/docs/network/specifications/scoring#how-runs-are-scored)和[显著性规范](/docs/network/specifications/significance)。

### 综合得分和质量层级发生了什么变化？

两者在新的运行中均已**弃用**。综合得分（composite）过去是 chrF++、精确匹配、FST 接受度和其他信号的加权混合，而层级（Baseline → Fluent）是根据它得出的标签。它的若干输入项从未将输出与源文或参考译文进行对比，因此系统即使不进行翻译也能获得大部分分数：一个未经训练的英语→北萨米语模型对每个输入都重复同一句有效句子，得到了 0.6244 分——被标记为“可用（functional）”——而其 chrF++ 仅为 5.5。新的运行卡片会发布 `composite: null` 和 `quality_tier: null`。

在该标准出台之前发布的卡片保留其存储的综合得分并保持可验证；凡是展示该得分的地方均标记为 **legacy composite (retired)**。请参见[为什么弃用综合得分](/docs/network/specifications/scoring#why-the-composite-was-retired)。

自动评分不是质量评判。只有该语言母语使用者的人工评估才能对质量进行认证。

### 验证层级是什么？

**验证层级**描述的是*谁验证了结果*，而不是结果有多好：

| 验证层级 | 含义 |
|---|---|
| **自行评测** | 提交者自行运行了评测套件。分数合理但未经核实。 |
| **Champollion 已验证** | 项目方根据 sha 固定（sha-pinned）的参考语料库对提交的输出重新评分，且分数得以复现。重新评分工具是维护者手动运行的命令，因此目前没有任何记录会在提交时直接获得晋级。 |
| **社区已验证** | 符合目标语言社区自身规范资质的双语使用者对输出的分层抽样样本进行了审核（≥30 条条目，≥2 位审核者），且 ≥70% 达到了社区的标准。该状态仅能通过社区自身的测试授予；抽检降级机制与之对称，并且同样公开。 |

一次运行可能获得很高的 chrF++，但依然只是“自行基准测试”（Self-benchmarked）——这意味着尚无人独立确认该得分，也没有该语言使用者对输出进行过评判。

## 提交与取消资格

### 什么会导致我的提交被取消资格？

如果出现以下情况，您的提交将被拒绝或标记：

1. **您的方法接触到了评估数据。** 如果您从评估数据集中训练、微调、少样本提示或以其他方式使用了任何条目，您的评分会被人为夸大。这包括在提示中使用参考翻译。
2. **您的运行卡未通过完整性检查。** 指纹必须与配置匹配。篡改的运行卡会被拒绝。
3. **您的方法未实现 TranslationMethod 协议。** 测试框架期望 `translate(entries, config) → results`。绕过测试框架的自定义集成不被接受。

### 我可以多次提交吗？

可以。排行榜跟踪所有提交。您可以迭代 — 运行数十个实验，仅提交最佳的。每个提交记录一个唯一的指纹，因此不存在关于哪个运行产生哪个评分的歧义。

### 我如何获得评分验证？

1. **自行基准测试（Self-benchmarked）：** 每次提交都从这里开始，目前排行榜上的每一行仍处于该层级。
2. **Champollion 验证（Champollion Verified）：** 项目方使用评估框架指标，针对 SHA 固定的参考语料库对您提交的输出进行重新评分。当您的得分成功复现时，该运行将被提升为 Champollion Verified——这是竞赛排名默认使用的层级，也是唯一有资格获得奖金的层级；公开排行榜也会列出自测行，并标明其状态。如果无法复现，或存储的参考语料库被篡改，该运行将被取消资格。重新评分是由维护者手动执行的批处理操作：提交时不会自动运行，也没有任何自动化调度。
3. **社区验证（Community Validated）：** 目标语言的双语使用者（根据社区自身协议取得资质）审查您方法输出的分层抽样——至少 30 个条目，至少 2 位审校者——并且必须有至少 70% 符合社区标准。该层级仅通过社区自行决定开展的测试赋予，并可以通过相同方式撤销：抽样审查未通过将同样公开地对该方法进行降级。这无法实现自动化——它需要社区的实际参与。

### 为什么不对每个人的方法都重新运行以进行验证？

因为我们既承担不起，也没有必要这么做。对*所有人*提交的输出重新评分是零成本的（这可以发现打字输入或编辑过的伪造得分）。真正重新运行模型需要消耗实际算力，因此只会针对通过**声誉加权审计**选出的**样本**进行——抽样策略已经构建并完成测试，但由其驱动的重新运行器尚未就绪，因此目前尚未触发任何抽样重新运行，被选中的运行记录为 *L2-pending*。在该策略下，如果某次运行关系重大（例如为整个语系架起了第一座桥梁）或存在异常（比之前的最佳成绩出现了好得令人难以置信的跃升），则必然会被选中；而对于已证明信誉的贡献者，抽查频率很低。声誉只能通过通过这些审计（或由独立贡献者证实您的结果）来积累——绝不能靠刷提交量——因此临时注册的一次性身份无法获利。一旦发现一次捏造造假，贡献者的声誉就会归零，其所有已验证的历史记录都将重新审计，并像学术撤稿一样被公开记录。我们**不会**声称您的运行“由评估框架官方产出”——因为对于自托管算力而言，这是无法在服务器端验证的——因此有效性建立在*可复现性 + 声誉质押 + 交叉佐证*之上，而非依赖官方证明。完整模型请参见[机器翻译评估规则](/docs/network/leaderboard/rules#how-verification-scales-reputation-weighted-auditing)。

### 提交 API 是否已上线？

还没有。`https://champollion.dev/api/leaderboard/submit` 端点是一个愿景。当前的提交路径是 `mt-eval publish`——它将测试框架输出目录（`eval/logs/harness/`）中的运行卡直接上传到排行榜，作为*自基准测试（未验证）*。

## 模型与参数

### 我应该使用什么模型？

没有单一的最佳模型 — 这取决于语言对、您的预算和您的方法。一般指导：

| 语言类型 | 推荐起点 | 原因 |
|---|---|---|
| **高资源语言**（法语、西班牙语、日语） | 快速、低成本的“flash”级别模型 | 快速、便宜、基线表现强劲 |
| **具有一定 LLM 覆盖度的低资源语言**（克丘亚语、约鲁巴语） | 更大的“pro”级别模型 | 更大的模型具有更好的潜在知识 |
| **多式综合语 / 极低资源语言**（平原克里语、伊努克提图特语） | 配合辅导（coaching）的更大模型 | 辅导数据比模型选择更重要。OMT-1600 包含部分多式综合语（例如处于 R1 层级的 CRK），但采用标准 BPE 分词——可以在 Network 中将其作为基线进行评测。 |

请使用模型的完整 slug 指定模型（例如 OpenRouter 上的 `provider/model`）；短别名和浮动 ID（`…-latest`）会被拒绝。CLI 和评测套件使用的默认值位于 `shared/model-defaults.json` 中。评测套件默认使用 OpenRouter，因此上面提供的任何模型均可进行基准测试（[openrouter.ai/models](https://openrouter.ai/models)）；直接使用模型提供商的 API 密钥或本地机器上的模型也同样支持。

### 我应该使用什么温度？

CLI 和评测套件的默认值均为 **0**（确定性）——统一数值，确保所测即所用。对于翻译任务，该值通常越低越好：

| 温度 | 效果 | 推荐用于 |
|-------------|--------|-----------------|
| **0.0 – 0.2** | 高度确定性、一致的输出 | 生产方法、最终基准 |
| **0.3 – 0.5** | 某些变化、偶尔更有创意 | 探索、早期迭代 |
| **0.6+** | 高度变化、不可预测 | 不推荐用于 MT 基准测试 |

温度记录在运行卡中，因此不同的温度产生不同的指纹 — 它们被视为不同的实验。

### 教练数据有帮助吗？

是的，对低资源语言特别有帮助。教练数据（语法规则、字典条目、风格说明）被注入到 LLM 系统提示中。对于平原克里语，教练方法对多综合型语言的表现一致优于原始 LLM 方法，因为通用 LLM 对多综合型的接触有限，没有形态意识。即使是专门为 CRK 训练的 OMT-1600，也使用无法在结构上表示多综合型形态的标准 BPE 分词。教练数据提供了模型缺少的语言学背景。

对于高资源语言（法语、西班牙语），教练的影响较小，因为模型已经具有强大的基线知识。

参见 [教练数据](https://champollion.dev/docs/concepts/coaching-data) 了解完整规范。

## FST 与形态验证

### 如果我的语言没有 FST 怎么办？

许多语言并没有有限状态转换器（FST）。这没关系——评估框架在没有 FST 的情况下也能工作。无论如何核心指标都是 chrF++，因此使用或不使用 FST 的运行在评分机制上是一样的；FST 接受度是一项诊断指标，未使用 FST 时，它在运行卡片中会被标记为 `null`。

现有 FST 的主要注册表：

| 注册表 | 覆盖范围 | URL |
|---|---|---|
| **GiellaLT** | 100+ 种语言——萨米语支诸语言、克里语、因纽特语以及许多其他乌拉尔语言和少数民族语言 | [giellalt.uit.no](https://giellalt.uit.no/) |
| **ALTLab** | 普莱恩斯克里语、图齐纳语、奥达瓦语 | [altlab.ualberta.ca](https://altlab.ualberta.ca/) |
| **Apertium** | 约 60 个语言对，主要为欧洲语言 | [apertium.org](https://apertium.org/) |
| **UniMorph** | 150+ 种语言的形态词形变化表 | [unimorph.github.io](https://unimorph.github.io/) |

### 我可以构建 FST 吗？

可以，但这并非易事。FST 编码了语言的形态规则 — 所有有效的词形。构建一个需要对语言有深入的语言学知识。如果您可以访问形态语法（例如，来自语言学系），可以使用 [HFST](https://hfst.github.io/) 或 [Foma](https://fomafst.github.io/) 等工具将其编译为 FST。

### FST 门控在实践中如何工作？

FST 门控管道的工作方式如下：

1. LLM 生成翻译
2. 输出中的每个词都针对 FST 进行检查
3. FST 拒绝的词被标记为形态无效
4. 方法可以使用反馈重试（"词 X 无效，请重试"）
5. 重试后，剩余的无效词被记录

FST 接受率用于衡量有多少词汇通过了验证。完整实例请参见 [FST 门控流水线教程](/docs/agents/methods)。

## 数据与数据集

### 我可以为新语言贡献数据集吗？

可以。来自 [基准规范 §11](/docs/network/specifications/benchmark#11-extending-to-new-languages) 的最低要求：

- **50 个金标准条目**（源 + 验证的参考翻译）
- **30 个开发条目**（对于小语料库可与金标准重叠）
- **社区同意**（对于土著语言，需要来自治理机构的明确授权）
- **出处文档**（数据来自何处、适用什么许可证）

新数据集会自动开启新的排行榜赛道。有关贡献者指南，请参见[你的语言，你的规则](/docs/your-words-your-rules)。

### 我的数据集应该是什么格式？

具有规范字段名称的 JSON：

```json
{
  "name": "my-language-dev-v1",
  "language_pair": "en-xxx",
  "segment": "development",
  "version": "1.0",
  "entries": [
    {
      "id": 1,
      "source": "Hello",
      "reference": "[translation in target language]",
      "difficulty": 1,
      "domain": "general"
    }
  ]
}
```

参见 [数据集](/docs/network/leaderboard/datasets) 了解完整的模式和难度等级定义。

## 主权与所有权

### 谁拥有为土著语言构建的方法？

归你所有，除非你另有约定。在公开排行榜上占有一席之地不会转移任何权利。仅当你参加密封竞赛时，权利才会根据主办方在任何人参赛前声明的奖金条款发生转移——条款为以下三种之一（[奖金规范 §1.3](/docs/network/specifications/prizes#1-3-declared-terms)）：

- `pass_to_holders` —— 方法转让给拥有主权的基准持有者（[社区转让模板](/docs/network/sovereignty/ownership-transfer)对此有详细说明）；
- `retain_ip` —— 你保留所有权；主办方最多保留一份密封副本用于审计；
- `release_open` —— 你保留所有权，但必须以开放许可证发布该方法。

在 `pass_to_holders` 之下，研究人员保留：
- 发表权（关于该方法的学术论文）
- 排行榜上的署名权
- 将相同*技术*应用于其他语言的权利

而持有者获得：
- 方法代码和辅导数据的全部所有权
- 部署的控制权（何时、何地、如何部署）——以及部署所产生的一切收益。Champollion 不参与分成

### 我可以在没有任何主权问题的情况下为非土著语言使用 champollion 吗？

是的。对于常规标准语言（法语、日语、西班牙语等），不存在主权方面的考量。正常使用 Champollion 即可——随心翻译、同步和发布。数据主权框架专门适用于原住民语言和由社区治理的语言，在这些语言中，数据治理原则——语言数据的社区所有权与控制权、CARE 原则、Te Mana Raraunga 原则——需要特殊考量。
