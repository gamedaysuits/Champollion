# اختبار الدلالة الإحصائية

> **الحالة**: ✅ أُطلِقت. اختبار الدلالة المقترن (العشوائية التقريبية افتراضيًا؛ وتوليد العينات التكرارية المقترن (paired bootstrap) عند الطلب) وفترات ثقة bootstrap مطبقة في `mt_eval_harness/significance.py` و`mt_eval_harness/confidence.py`، ومُصدَّرة من الحزمة، ومُتاحة عبر واجهة سطر الأوامر (CLI)، ومُغطاة بمجموعات اختبارات الدلالة / الثقة / التسجيل.
> **قاعدة الكود**: `arena` — مربوطة بـ `tester.py` (فترات الثقة لكل تشغيل) و`compare.py` (الدلالة بين التشغيلات).
> **الغرض**: تمكين الباحثين من تحديد ما إذا كان الفرق بين عمليتي تقييم ذا دلالة إحصائية أم مجرد تشويش عشوائي.

توثق هذه الصفحة **السلوك المُطلق** — فهي وصفية وليست قائمة مهام.

---

## لماذا يُعد هذا مهمًا

عند مقارنة تشغيلين (مثال توضيحي: النظام A بدرجة chrF++‎ تبلغ 42.96 مقابل النظام B بدرجة chrF++‎ تبلغ 41.80 على 92 مدخلة)، فإن الفارق النقطي الخام بحد ذاته لا يُعبر عما إذا كان حقيقيًا أم مجرد تشويش. فمع وجود نحو 92 مدخلة اختبار فقط، يمكن للتباين العشوائي أن يُحدث بسهولة تقلبات بمقدار نقطة إلى نقطتين. يطلب الخبراء اختبارات الدلالة — ولذا يقوم إطار الاختبار بحسابها.

**وفقًا لمعيار التسجيل (`standard/1`)، فإن الاختبار المقترن على chrF++ هو ما يحسم ما إذا كان أحد التشغيلين أفضل من الآخر.** يُعد chrF++‎ المقياس الأساسي المُعلن مسبقًا ([مواصفات التسجيل](/docs/network/specifications/scoring#how-runs-are-scored)). تُختبر مقاييس BLEU وspBLEU وTER وCOMET (عندما يحمل كلا التشغيلين درجات COMET لكل مقطع من النموذج نفسه) وتُعرض كمقاييس معيارية ثانوية، بينما تُعرض درجات التطابق التام ومعدلات الإضافات كمقاييس تشخيصية؛ ولا يحسم أيٌّ منها النتيجة. يتبع هذا دراسة Kocmi et al. (2021, "To Ship or Not to Ship")، التي وجدت عبر آلاف الأحكام البشرية أن الفارق في المقياس مقترنًا بدلالته الإحصائية هو ما يتنبأ بالتفضيل البشري.

## الخوارزمية: العشوائية التقريبية المقترنة (الافتراضية)

يستخدم `mt-eval compare --significance` اختبار **العشوائية التقريبية المقترنة (AR)** لـ Riezler & Maxwell (2005). وهو أيضًا الخيار الافتراضي في SacreBLEU لمقارنة الأنظمة.

### آلية العمل

بافتراض وجود نظامين A وB جرى تقييمهما على نفس عدد مدخلات الاختبار N:

1. حساب الفارق المرصود على مستوى المدونة: `Δ = metric(A) - metric(B)`.
2. التكرار `n_trials` مرة (الافتراضي 1000):
   a. لكل مدخلة، يُبدّل مخرجا A وB باحتمال ½.
   b. يُعاد حساب مقياس المدونة على المجموعتين بعد التبديل العشوائي.
   c. يُسجل ما إذا كان `|Δ_shuffled| ≥ |Δ|`.
3. تكون القيمة الاحتمالية (p-value) هي مستوى الدلالة المتحقق ثنائي الطرف:
   `p = (#{|Δ_shuffled| ≥ |Δ|} + 1) / (n_trials + 1)`. يحسب الرقم +1 التعيين المرصود كسحب صحيح واحد، وبالتالي لا تكون قيمة p صفرًا تمامًا على الإطلاق.
4. إذا كانت p < α (الافتراضي 0.05)، يُبلّغ عن الفارق بأنه ذو دلالة إحصائية.

فترة الثقة لـ Δ هي فترة مئينية لـ bootstrap (حيث يُعطي AR قيمة احتمالية p-value وليس فترة ثقة). وتُحسب على دفق عشوائي منفصل حتى لا تؤثر على سحوبات AR.

### الخصائص الرئيسية

- **اختبار فرضية حقيقي:** يتم سحب عمليات التبديل العشوائي في ظل فرضية العدم التي تفترض أنه لا يوجد فرق في أي من النظامين أنتج مدخلة معينة.
- **مقترن:** تتم مقارنة كلا النظامين مدخلة بمدخلة، مما يحافظ على الارتباط على مستوى المدخلات.
- **لا معلمي:** لا يفترض أي توزيع محدد للدرجات.

### توليد العينات التكرارية المقترن (Paired Bootstrap) (متاح، وليس افتراضيًا)

يُنفّذ `paired_bootstrap()` خوارزمية paired bootstrap لـ Koehn (2004): حيث يعيد أخذ عينات من المدخلات مع الإحلال ويحسب عدد المرات التي تتغير فيها إشارة Δ. وهو مُقدَّم لأغراض المقارنة مع الأوراق البحثية الأقدم، لكنه يعتبر وسيلة حدسية لقوة الإشارة وليس مستوى دلالة إحصائية قياسيًا بالمعنى الأكاديمي. يتمركز توزيعه حول Δ المرصودة، وليس حول فرضية العدم، لذا قد يبالغ في تقدير الدلالة مقارنةً بـ AR. يمكن اختياره من سطر الأوامر عبر
`mt-eval compare <reports…> --significance --method paired_bootstrap`، أو باستخدام
`method="paired_bootstrap"` في `run_significance_tests`.

## حزمة sacrebleu تبعية إجبارية

تُعد sacrebleu تبعية إجبارية. فإطار تقييم الترجمة الآلية الذي لا يستطيع حساب chrF++ أو BLEU لا يُعد إطار تقييم للترجمة الآلية حقًا، ولذا:

1. يتم التصريح عن `sacrebleu>=2.3` تحت `[project.dependencies]` في `pyproject.toml` (وليس `[project.optional-dependencies]`).
2. يتم استيرادها مباشرة في `tester.py` — `from sacrebleu.metrics import CHRF, BLEU, TER` — دون استخدام `try/except` كحاجز وقائي.
3. يتم استيرادها مباشرة في `significance.py`.

لا توجد أي مسارات شرطية لـ `HAS_SACREBLEU` في أي مكان: فالتشغيل بدون sacrebleu ليس تكوينًا مدعومًا.

### 2. الوحدة: `mt_eval_harness/significance.py`

تنفيذ اختبار الدلالة (العشوائية التقريبية افتراضيًا، وpaired bootstrap عند الطلب). واجهتها العامة:

```python
"""
Statistical significance testing via paired bootstrap resampling.

Standard method used by WMT shared tasks, SacreBLEU, and MT-Lens.
Compares two runs on the same corpus to determine if the performance
difference is statistically significant.
"""

from __future__ import annotations

import random
from dataclasses import dataclass
from sacrebleu.metrics import CHRF, BLEU


@dataclass
class SignificanceResult:
    """Result of a paired bootstrap significance test."""
    metric_name: str           # e.g., "corpus_chrf", "exact_match_rate"
    system_a_score: float      # Score for system A
    system_b_score: float      # Score for system B
    delta: float               # A - B
    p_value: float             # Two-sided p-value
    n_bootstrap: int           # Number of bootstrap iterations
    confidence_level: float    # 1 - alpha
    significant: bool          # p_value < alpha
    winner: str | None         # "A", "B", or None if not significant
    ci_lower: float            # Lower bound of 95% CI on the delta
    ci_upper: float            # Upper bound of 95% CI on the delta


def paired_bootstrap(
    entries_a: list[dict],
    entries_b: list[dict],
    metric_fn: callable,
    n_bootstrap: int = 1000,
    alpha: float = 0.05,
    seed: int = 12345,
    metric_name: str = "metric",
) -> SignificanceResult:
    """Run paired bootstrap resampling significance test.

    Args:
        entries_a: Per-entry results from system A (from TestReport["entries"])
        entries_b: Per-entry results from system B (must be same length, same IDs)
        metric_fn: Function(list[dict]) -> float that computes the corpus-level
                   metric from a list of entry dicts. Must handle the entry format
                   from TestReport.
        n_bootstrap: Number of bootstrap iterations (1000 is standard)
        alpha: Significance level (0.05 = 95% confidence)
        seed: RNG seed for reproducibility (12345 matches SacreBLEU default)
        metric_name: Human-readable name for the metric being tested

    Returns:
        SignificanceResult with all fields populated.

    Raises:
        ValueError: If entries_a and entries_b have different lengths or IDs.
    """
```

### 3. دوال المقاييس المدمجة

```python
def exact_match_rate(entries: list[dict]) -> float:
    """Compute exact match rate from a list of entry dicts."""
    non_error = [e for e in entries if not e.get("error")]
    if not non_error:
        return 0.0
    exact = sum(1 for e in non_error if e.get("exact_match"))
    return exact / len(non_error)


def corpus_chrf(entries: list[dict]) -> float:
    """Compute corpus-level chrF++ from a list of entry dicts."""
    chrf = CHRF(word_order=2)
    refs = [e["expected"] for e in entries if e.get("expected", "").strip()]
    hyps = [e["predicted"] if e.get("predicted", "").strip() else "EMPTY"
            for e in entries if e.get("expected", "").strip()]
    if not refs:
        return 0.0
    return chrf.corpus_score(hyps, [refs]).score


def corpus_bleu(entries: list[dict]) -> float:
    """Compute corpus-level BLEU from a list of entry dicts."""
    bleu = BLEU()
    refs = [e["expected"] for e in entries if e.get("expected", "").strip()]
    hyps = [e["predicted"] if e.get("predicted", "").strip() else "EMPTY"
            for e in entries if e.get("expected", "").strip()]
    if not refs:
        return 0.0
    return bleu.corpus_score(hyps, [refs]).score
```

### 4. التكامل مع `compare.py`

يقوم `compare.py` بإجراء مقارنة جنبًا إلى جنب لتقارير TestReports متعددة ويجري اختبارات الدلالة الإحصائية بينها. يتولى `run_significance_tests()` قيادة الاختبارات عبر تقريرين بينما يتولى `format_significance_table()` عرضها. يحمل كل نتيجة `role` الخاصة به: `primary` (chrF++ — الاختبار الفاصل الذي يحسم النتيجة)، أو `secondary` (المقاييس المعيارية الأخرى)، أو `diagnostic`. ويختبر بالترتيب التالي:

| المقياس | الدور | يُحسب لكل إعادة معاينة من |
|---|---|---|
| `corpus_chrf` | أساسي | إحصاءات sacreBLEU لكل مقطع |
| `corpus_bleu` | ثانوي | إحصاءات sacreBLEU لكل مقطع |
| `corpus_spbleu` | ثانوي | إحصاءات sacreBLEU لكل مقطع، باستخدام مُجزئ SentencePiece الخاص بـ FLORES-200 (مقياس spBLEU هو BLEU مع ذلك المُجزئ، وهو الرقم الذي تعرضه جداول FLORES/NLLB). عندما لا يكون المُجزئ متاحًا (عدم وجود `sentencepiece`، أو دون اتصال بالإنترنت مع عدم تنزيل النموذج بعد)، يُدرج على أنه لم يُختبر، ولا يُحذف أبدًا بصمت |
| `corpus_ter` | ثانوي | إحصاءات sacreBLEU لكل مقطع. يُعد TER معدل تحرير، لذا فإن **الأقل هو الأفضل**: تشير قيمة Δ السالبة إلى تفوق A |
| `comet_score` | ثانوي | درجات COMET لكل مقطع والتي يتضمنها كلا التقريرين بالفعل (يمثل متوسطها درجة النظام لـ COMET؛ ولا يُعاد تشغيل النموذج أبدًا). يُدرج على أنه لم يُختبر، مع ذكر السبب، عندما يتم تسجيل تشغيل واحد فقط بواسطة COMET أو عند استخدام نموذجي COMET مختلفين |
| `exact_match_rate` | تشخيصي | علامة التطابق التام لكل مدخلة |
| معدلات المكونات الإضافية في كلا التقريرين، مثل `giellalt_fst_validity.avg_fst_validity`، `.corpus_validity_rate`، `.morphological_accuracy`، `code_switching.avg_code_switching_rate`، `hallucination.avg_hallucination_rate` | تشخيصي | نتائج المكون الإضافي الخاصة بكل مدخلة، مجمعة بالطريقة ذاتها التي جُمعت بها النتيجة الإجمالية |

**الدرجة المركبة القديمة المستبعدة لا تخضع للاختبار.** استُبعدت الدرجة المركبة الموزونة وصفّ `segment_composite` الذي كان يُختبر هنا سابقًا بموجب معيار التسجيل ([مواصفات التسجيل §4](/docs/network/specifications/scoring#4-composite-score)). ولا يزال ملف JSON للمقارنة الذي كُتب قبل اعتماد المعيار يعرض صفوف `segment_composite` (أو `composite_score`)، مصنفة كدرجة مركبة قديمة لا تحسم شيئًا. وعندما يكون التقرير المقارَن قديمًا، يشير `compare` إلى أن درجته المركبة مستبعدة ولا يقارنها.

```python
# In compare_reports(), after computing deltas:
if len(reports) == 2:
    sig_results = run_significance_tests(reports[0], reports[1])
    comparison["significance"] = [asdict(r) for r in sig_results]
```

عند مقارنة أكثر من تقريرين، تُجرى اختبارات الدلالة الثنائية لجميع الأزواج: ويكون `significance` حينها قائمة من كائنات `{"pair": [run_a_id, run_b_id], "letters": ["A", "C"], "tests": [...]}`، كائن لكل زوج، وتكون كل قائمة `tests` مُنسقة مثل حالة التقريرين. يُمثل `letters` حرْفَي التشغيلين في جدول التشغيلات، وتكون Δ هي الأول ناقص الثاني.

إلى جانب `significance`، يحمل كائن JSON للمقارنة `significance_settings`: وهي `method`، و`n_resamples`، و`alpha`، و`seed`، والتشغيل الذي يمثله كل حرف (`runs`)، وماهية `ci_lower`/`ci_upper`، و`multiple_testing_correction: "none"`، وعدد المقاييس التي تم اختبارها لكل زوج وعبر كم زوجًا، والملاحظة المبسطة حول القيم الاحتمالية غير المصححة (أدناه)، وأي ملاحظات أثارتها الاختبارات (المدخلات المستبعدة من المقارنة الثنائية، المقاييس التي لم تُختبر).

### 5. التكامل مع سطر الأوامر (CLI)

يتيح `mt-eval compare` الخيار `--significance`، مع `--method` لاختيار الاختبار المقترن (`approximate_randomization`، وهو الافتراضي، أو `paired_bootstrap`) و`--n-bootstrap` لتعيين عدد التكرارات:

```bash
# Compare two runs with significance testing
mt-eval compare report_a.json report_b.json --significance

# The Koehn (2004) paired bootstrap instead of approximate randomization
mt-eval compare report_a.json report_b.json --significance --method paired_bootstrap

# Custom resampling count
mt-eval compare report_a.json report_b.json --significance --n-bootstrap 5000
```

يأخذ `compare` ملفات `*_report.json` التي يكتبها `mt-eval run` (أو سجلات التشغيل، حيث يستخدم التقرير المجاور لها). ويطبع جدول التشغيل مع صف واحد لكل مقياس وعمود واحد لكل تشغيل، ثم جدول الدلالة الإحصائية، ويكتب ملف JSON للمقارنة في موقع محايد ما لم يحدد `-o` ملفًا آخر: `comparison-<hash>.json` بجوار التقارير عندما تشترك في مجلد واحد، وإلا ففي `comparisons/` داخل أقرب مجلد مشترك لها (التقارير الموجودة في المجلد الخاص بكل تشغيل، مثل مجلدات `mcp-run-<id>/` الخاصة بـ `run_benchmark`، لا يُكتب ملف المقارنة داخل أحدها أبدًا). يمثل `<hash>` أول عشرة أحرف ست عشرية من تشفير sha256 لمعرّفات التشغيلات المقارنة بالترتيب المعطى، بحيث لا تؤدي مقارنة أخرى في المجلد نفسه إلى الكتابة فوق هذه المقارنة أبدًا؛ وإعادة مقارنة نفس التشغيلات تعيد كتابة ملفها الخاص. يؤدي تحديد اسم ملف باستخدام `-o` إلى استبدال أي محتوى موجود هناك، ويوضح الخرج ذلك. ويقوم بطباعة المسار الذي كتب فيه. تقتبس مقارنة التشغيلات على مدونة محلية فقط أو مختومة أو تتطلب موافقة جُمَلَ تلك المدونات، لذا فإنها تحمل علامة تلك المدونة في ملف ملحق `<file>.champollion.json` أينما كُتبت.

يُظهر عمود **Avg latency (s/entry)** في جدول التشغيل `—` للتشغيل الذي لم يسجل أي وقت، مع ملاحظة أسفل الجدول توضح السبب: سواء كان ذلك لأن كل المدخلات جاءت من الذاكرة المؤقتة، أو أن المخرجات تم إنتاجها خارج إطار الاختبار، أو أن الطريقة لم تبلغ عن أي وقت. وتُعرض القيمة التي تقل عن 0.01 ثانية بأربع منازل عشرية (حيث يفك نموذج صغير التشفير على وحدة المعالجة المركزية في بضع أجزاء من الألف من الثانية للجملة)، ولا تُقرب أبدًا إلى 0.00.

### 6. تنسيق المخرجات

يُصيّر `format_significance_table()` طريقة العرض في وحدة التحكم؛ وتُضاف نفس البيانات إلى ملف JSON للمقارنة.

تُعطى التقارير حروفًا بالترتيب الوارد: التقرير الأول هو التشغيل **A**، والثاني **B**، ثم **C**، و**D**، وهكذا، وهي نفس الأحرف المستخدمة في جدول التشغيل أعلاه. يُسمي كل جدول للمقارنة الثنائية تشغيلَيه بهذين الحرفين ومعرفات التشغيل الخاصة بهما، على سبيل المثال `--- A (baseline) vs C (nllb-ft) ---`، وتستخدم أعمدته وΔ نفس الأحرف (`Δ (A−C)`). وتكون Δ دائمًا **الأول − الثاني**. يُطبع شرح الجدول وكل ملاحظة تحته **مرة واحدة**، مهما كان عدد الأزواج. يطبع كل صف أيضًا **فترة الثقة 95% لـ Δ**: وهي فترة bootstrap المئينية في `ci_lower`/`ci_upper` في ملف JSON، والتي تشير إلى الحجم المحتمل للفرق، وليس إشارته فقط. يتم وسم كل مقياس باتجاهه من سجل المقاييس (↑ الأعلى أفضل، ↓ الأقل أفضل)، ويذكر عمود **Better** التشغيل ذا النتيجة الأفضل مع مراعاة الاتجاه، مع وضع `(n.s.)` عندما لا يكون الفارق ذا دلالة إحصائية. وبالتالي، فإن المعدل الذي تكون فيه القيمة الأقل أفضل مثل TER أو التبديل اللغوي أو الهلوسة إذا ارتفع، فإنه يطبع Δ موجبة مع تحديد **B** كالتشغيل الأفضل، والنموذج المدرب الذي تم تمريره ثانيًا ويتفوق على خط الأساس بمقدار 63.5 chrF++ يطبع Δ بقيمة ‎-63.52 مع تحديد **B** كأفضل. والمقياس الذي لا يُصرّح السجل باتجاهه يُعرض مع `?`. تُطبع الدرجات وΔ وفترة الثقة بمنزلتين عشريتين، وبعدد أكبر (يصل إلى ست منازل) في الصفوف التي قد يؤدي التقريب فيها إلى إخفاء فرق حقيقي: فنتيجة spBLEU بقيمة 0.0684 مقابل 0.0673 تطبع Δ بقيمة ‎+0.0011 [+0.0001, +0.0021]، ولا تُطبع أبدًا ‎+0.00 [+0.00, +0.00] بجانب **Yes**، ويوضح الجدول أن تلك الصفوف تحمل منازل عشرية إضافية. يحتفظ ملف JSON بأربع منازل عشرية، وبأربعة أرقام معنوية لأي قيمة غير صفرية أصغر من ذلك، بحيث لا يُخزن الفرق الحقيقي كـ 0 أبدًا. تُعطي المخرجات المتطابقة Δ بقيمة 0 تمامًا وp = 1، وبالتالي فهي ليست ذات دلالة إحصائية أبدًا. وإذا انخفضت p عن α بينما فترة bootstrap لـ Δ هي [0, 0] تمامًا (لأن المقاطع المختلفة قليلة جدًا بحيث لا يمكن تقدير الفرق)، يُظهر عمود **Sig?** القيمة `?†` ويُظهر عمود **Better** القيمة `—†`، مع ملاحظة: لا يُعتبر أي تشغيل أفضل فيها. وبالنسبة لمعدل الإضافة الذي تكون فيه القيمة الأقل أفضل، فإن حقل `winner` في ملف JSON يراعي الاتجاه أيضًا (المعدل الأقل يفوز)، كما كان الحال دائمًا مع `corpus_ter`؛ أما معدل الإضافة الذي ليس له اتجاه تفضيل (محايد، مثل `morph_coverage`، أو غير مصرّح به) فيكون `winner: null`. ويحمل كل نتيجة أيضًا `direction` الخاص به.

### 7. التكامل مع لوحة التحكم (تحسين اختياري)

عند توفر بيانات الدلالة الإحصائية في ملف JSON للمقارنة، يمكن للوحة التحكم إبرازها — كصف في جدول المقارنة مع مؤشرات الدلالة (`*` لـ p < 0.05، و`**` لـ p < 0.01). هذه طبقة عرض تكميلية فوق العمليات الحسابية المعتمدة، وليست جزءًا من الميزة الأساسية.

---

## الحالات الحدية والتحقق

1. **عدم تطابق المدخلات**: يجب أن يمتلك تقريرا TestReport نفس معرّفات المدخلات. وإذا لم يكن الأمر كذلك (على سبيل المثال، عمل أحدهما على مجموعة فرعية)، يتم اختبار الدلالة فقط على التقاطع المشترك بينهما، مع إصدار تحذير بشأن المدخلات المستبعدة.

2. **قلة عدد المدخلات**: إذا كان N < 10، يتم التحذير من أن اختبارات الدلالة الإحصائية غير موثوقة مع هذا العدد القليل جدًا من المدخلات. ومع ذلك يتم تشغيلها مع طباعة التحذير.

3. **تطابق الدرجات**: إذا أنتج كلا النظامين نتائج متطابقة لكل مدخلة، يجب أن تكون قيمة p_value مساوية لـ 1.0 (لا يوجد فرق على الإطلاق).

4. **مقاييس الإضافات**: يُختبر معدل الإضافة الذي يظهر في كلا التقريرين فقط بالاعتماد على القيم الخاصة بكل مقطع والموجودة فعليًا في التقرير. يعني ذلك تجميع الإضافة الخاص بها عبر نتائجها لكل مدخلة (مقياس FST)، أو متوسط القيمة لكل مدخلة التي يجمعها تجميع `avg_<name>` (المقاييس السلوكية). ومعدل الإضافة الذي لا يتضمن قيمًا لكل مقطع يُدرج كغير مُختبَر، ولا يُعرض أبدًا كـ 0.00 مقابل 0.00. ولا تُختبر الأعداد مثل `total_words_checked`.

5. **قابلية إعادة الإنتاج**: يجب تسجيل بذرة توليد الأرقام العشوائية في المخرجات لتكون النتائج قابلة لإعادة الإنتاج بدقة. القيمة الافتراضية هي 12345 (مطابقةً لاتفاقية SacreBLEU).

---

## ما لا يجب بناؤه

- **عدم إعادة استدلال COMET في الاختبار**: يُختبر COMET باختبار مقترن بالاعتماد على درجات كل مقطع المتوفرة بالفعل في كلا التقريرين؛ ولا يُعاد تشغيل النموذج أبدًا لكل إعادة سحب. والتشغيلان اللذان سُجِّلت نتائجهما بنماذج COMET مختلفة لا يتم اختبارهما ضد بعضهما البعض.
- **عدم استخدام التحليل البايزي**: الالتزام بـ bootstrap التكراري. فهذا ما يتوقعه مجتمع الترجمة الآلية ويفهمه.
- **عدم تطبيق تصحيح الاختبارات المتعددة**: عند اختبار مقاييس متعددة، لا تُطبق تصحيحات Bonferroni أو ما شابهها. فالعرف المتبع في تقييم الترجمة الآلية هو الإبلاغ عن القيم الاحتمالية الخام لكل مقياس وترك التفسير للقارئ. يذكر `mt-eval compare` **ذلك صراحة** في مخرجاته وفي `comparison.json` (`significance_settings.multiple_testing_correction: "none"` مع ملاحظة بكلمات واضحة): مع اختبار عدة مقاييس، قد تظهر نتيجة واحدة عند p < 0.05 بالصدفة البحتة، وقد تكون قيمة Δ الصغيرة ذات دلالة إحصائية دون أن تكون ذات أهمية عملية، لذا احرص على قراءة فترة الثقة CI لـ Δ وموثوقية المقياس للغة المعنية قبل اتخاذ أي إجراء بناءً على صفة "ذو دلالة" فردية.

## مجموعات الترتيب {#ranking-clusters}

> **الحالة**: ✅ أُطلِقت، للمسابقات. ترتيب المسابقة عبارة عن مجموعة من **العناقيد** (clusters)، وليس ترتيبًا صارمًا — فاختبار الدلالة يحدد أي المدخلات المتجاورة يمكن التمييز بينها فعليًا. يصف هذا القسم الميزات المُطلقة، بما في ذلك الحالات التي تكون فيها الأدلة أضعف من الاختبار المقترن.

### التسلسل المتجاور، ترقيم المسابقات

تُقسَّم المدخلات حسب **المسار** أولاً — فلا يُرتب نظام `constrained` مقابل نظام `unconstrained` أبدًا، ويحمل كل مسار ترتيبه الخاص ومجموعات التعادل ونطاقات الرتب، وبالتالي فإن "المرتبة 1" تعني دائمًا المرتبة 1 *ضمن المسار نفسه*.

ضمن المسار، تُرتَّب المدخلات وفقًا للمقياس الأساسي للمسابقة (chrF++ ما لم تسجل المسابقة مقياسًا مختلفًا)، ثم حسب المقاييس السطحية المتبقية، وأخيرًا حسب أسبقية التقديم. ويُختبر كل زوج **متجاور** في ذلك الترتيب. ويشترك الزوج الذي يعجز الاختبار عن التفريق بينه في نفس الرتبة، والرتب المشتركة **تتسلسل**: فإذا تعادل A مع B وتعادل B مع C، فإن الثلاثة يقعون في مجموعة تعادل واحدة حتى وإن لم يُقارن A وC بشكل مباشر أبدًا.

تستخدم الرتب نظام ترقيم المسابقات — فالتعادل الثلاثي في الصدارة يكون `1, 1, 1` وتكون المدخلة التالية `4`؛ والتعادل الثنائي على المركز الثاني يكون `1, 2, 2, 4`.

**الحد المنطقي للتسلسل**: غياب الدلالة الإحصائية ليس صفة متعدية. إذ يمكن لسلسلة طويلة أن تربط بين مدخلتين *كان* الاختبار المباشر ليفصل بينهما. ولهذا السبب يتم الإبلاغ عن المجموعة كـ **نطاق** وليس كنقطة محددة.

### نطاقات الرتب

تحمل كل مدخلة `rank_min` و`rank_max` — وهما أفضل وأسوأ موضع يتوافق مع الأدلة، على النمط الذي تستخدمه WMT لنطاقات رتبها. فالمدخلة المنفردة في مجموعتها يكون لها `rank_min == rank_max`. والمدخلة داخل مجموعة من أربعة تمتد عبر المراكز من 2 إلى 5 تحمل `rank_min: 2, rank_max: 5`، و**لا توجد أي مدخلة داخل تلك المجموعة "تتقدم على" أخرى**. واقتطاع رتبة برقم أحادي من المجموعة يعد قراءة خاطئة للنتيجة.

### سلم الأدلة

لا يمكن اختبار كل زوج بالطريقة نفسها، لذا يسجل كل زوج الدرجة التي صدر منها الحكم فعليًا. وتُعد هذه التسمية جزءًا من النتيجة ولا تُسقط أبدًا:

| الدرجة | الدليل | متى تتوفر | القوة |
|---|---|---|---|
| 1 | **اختبار مقترن لكل مقطع** — عشوائية تقريبية بشكل افتراضي، وإعادة تمهيد مقترنة عند الطلب (الخوارزمية الموضحة أعلاه) | فقط عندما يحمل **كلا** المدخلين مجموعة درجات كاملة ومحاذاة لكل مقطع | الاختبار الحقيقي |
| 2 | **تداخل فترات ثقة bootstrap بنسبة 95%** على حدود الفترات المنشورة | عندما يحتوي المقياس الأساسي على حدود فترات ثقة في كلا المدخلين (يتوفر ذلك في chrF++؛ بينما لا يحتوي BLEU وCOMET على أعمدة فترات) | بديل متحفظ — الفترات المتداخلة **لا** تثبت التكافؤ، كما أن عدم التداخل هو معيار أكثر صرامة من الاختبار المقترن |
| 3 | **تطابق النقاط** عند التقريب المعروض للمقياس | دائمًا | أضعف الدرجات: يشير فقط إلى أن الرقمين المطبوعين متطابقان |

### المسابقات المختومة: تعمل الدرجة 1 على العقدة

تحتاج الدرجة 1 إلى درجات كل مقطع من كلا النظامين. وفي المسابقات المختومة، تحتفظ عقدة التقييم الخاصة بالمنظم بالمراجع و**لا تُصدّر أبدًا مخرجات كل مقطع**. وهذا هو الهدف الأساسي من المسار المختوم، وهو إعداد لا يمكن التهاون فيه. ولذا فإن الاختبار المقترن ينتقل إلى البيانات بدلاً من العكس.

يُشغّل `mt-eval node verdicts` الاختبار المقترن الخاص بالمسابقة على العقدة، عبر المراجع المختومة وكل زوج من المدخلات التي تم تقييمها، ويكتب **الأحكام فقط**: لكل زوج، الطريقة، والقيمة الاحتمالية (p-value)، وفارق الدرجات، وفترة ثقته، وعدد المقاطع. ولا يحتوي الملف على أي مقطع أو مرجع أو ترجمة. وتوقعه العقدة بمفتاح توقيع الدرجات الخاص بها. ثم يُغلق المنظم العملية باستخدام `mt-eval contest close --node-verdicts <file> --verify-key <node public key>`. ويستخدم الترتيب الأحكام فقط إذا تم التحقق من التوقيع وكانت قد حُسبت لهذه المسابقة، ومجموعتها المختومة، ومقياسها، وسياستها الثابتة للتعادل، وإصدار إطار الاختبار المعتمد. وإلا، يُرفض الإغلاق.

عند عدم توفير أي أحكام، تعتمد حالات التعادل في المسابقة المختومة على تداخل فترات الثقة حيثما يحتوي المقياس على فترات، وعلى التساوي النقطي حيثما لا تتوفر فترات. وتكون مجموعاتها حينئذٍ أوسع مما ستكون عليه في الاختبار المقترن. ويوضح الترتيب نفسه الحالة المطبقة: يذكر `ranking_method.evidence_used` الدرجات المستخدمة فعليًا، ويذكر `ranking_method.node_verdicts` العقدة التي استُخدمت أحكامها، إن وُجدت.

### ما لا يرتبه الترتيب

- **المدخلات التباينية** يُبلّغ عنها في قسمها الخاص ولا تفوز أبدًا.
- **وقت التشغيل، والعتاد، والتكلفة** تُرفق ببطاقة التشغيل ويُبلّغ عنها، ولا تدخل في الترتيب أبدًا. لا يوجد مسار للكفاءة.
- **التقييم البشري** غير موجود في هذه التصنيفات على الإطلاق. يمكن تسجيل *اختيار* للتقييم البشري — أي الأنظمة التي ستغطيها ميزانية ثابتة، مع أخذ مجموعات التعادل بأكملها حتى لا تُقسم أي مجموعة إلى نصفين — في مسابقة مغلقة، ولكن لا توجد تقييمات؛ راجع [قواعد تقييم الترجمة الآلية](/docs/network/leaderboard/rules#verification-tiers).

## تغطية الاختبارات

مجموعات اختبارات الدلالة الإحصائية / الثقة / التسجيل ناجحة بالكامل. وهي تغطي:

1. **الحتمية باستخدام البذرة**: نفس المدخلات + نفس البذرة → نفس القيمة الاحتمالية، في كل مرة
2. **اختبار الإجابة المعروفة**: مجموعتا نتائج متطابقتان → p_value = 1.0
3. **اختبار الدلالة المعروفة**: مجموعتا نتائج تكون إحداهما أفضل بوضوح (على سبيل المثال، جميعها تطابق تام مقابل جميعها إخفاق) → p_value ≈ 0.0
4. **عدم تطابق المعرّفات**: إطلاق `ValueError`، أو التحذير والحساب على التقاطع المشترك
5. **المدخلات الفارغة**: معالجة سلسة (p_value = 1.0 أو إطلاق خطأ)

## فترات الثقة (ميزة مصاحبة)

> **Status**: ✅ IMPLEMENTED in `confidence.py`

تجيب فترات الثقة (CIs) عن سؤال مختلف عن اختبار الدلالة الإحصائية:

- **اختبار الدلالة الإحصائية** (`significance.py`): "هل الفرق بين النظام A والنظام B حقيقي؟"
- **فترات الثقة** (`confidence.py`): "ما مدى عدم اليقين في درجة هذا النظام بمفرده؟"

### التنفيذ: `confidence.py`

يستخدم نفس طريقة إعادة أخذ العينات المئينية لـ bootstrap المستخدمة في اختبار الدلالة الإحصائية:

| المعامل | القيمة | التبرير |
|---|---|---|
| `n_bootstrap` | 1000 | القيمة الافتراضية في SacreBLEU، وفقًا لاتفاقية WMT 2024 |
| `seed` | 12345 | البذرة الافتراضية في SacreBLEU لقابلية التكرار |
| `alpha` | 0.05 | مستوى الثقة القياسي 95% |
| الطريقة | طريقة المئين لإعادة التمهيد (Percentile bootstrap) | Koehn (2004)، Efron (1979) |

### المقاييس التي تحصل على فترات ثقة

المقاييس الحتمية على مستوى المدونة المحسوبة بواسطة إطار الاختبار:
- `corpus_chrf` (درجة chrF++)
- `corpus_bleu` (درجة BLEU)
- `exact_match_rate` (0.0–1.0)
- `fst_acceptance_rate` (عند توفر بيانات FST)


تُعد فترة ثقة chrF++ جزءًا من النتيجة الرئيسية المنشورة (`chrF++ 47.5 [45.9, 49.0]`). وتُحسب فترات الثقة **أيضًا** لـ `comet_score`، باستخدام bootstrap من درجاته المخزنة مؤقتًا لكل مدخلة (دون إعادة الاستدلال العصبي بشكل متكرر). لا تُحسب فترة ثقة للمقياس المركب في التشغيلات الجديدة؛ ويُعاد اشتقاق فترة ثقة المقياس المركب المخزنة للبطاقة القديمة فقط عند التحقق من تلك البطاقة.

### خيارات سطر الأوامر (CLI)

```bash
# Default: CIs are computed automatically
mt-eval test run_log.json

# Skip CI computation (faster, for quick iteration)
mt-eval test run_log.json --no-ci

# More bootstrap iterations (more precise, slower)
mt-eval test run_log.json --n-bootstrap-ci 2000
```

### تحذير العينة الصغيرة

عندما يكون N < 30 مدخلة، تصدر الوحدة تحذيرًا بأن فترات الثقة قد تكون ذات تغطية ضعيفة. إذ لا يمكن لـ bootstrap إنشاء معلومات غير موجودة في العينة الأصلية — ومع وجود عدد قليل جدًا من المدخلات، ستكون الفترات واسعة، مما يعكس بدقة حالة عدم اليقين العالية.

### COMET (مقياس قياسي عند حسابه، إلى جانب chrF++)

COMET هو **مقياس عصبي يُعرض بجانب النتيجة الرئيسية لـ chrF++** متى ما تم حسابه، مصحوبًا بمعرف النموذج الخاص به. ولا يُدمج أبدًا مع chrF++، ولا يُعتبر النتيجة الرئيسية لأنه يتطلب نموذجًا كبيرًا وغير مُعاير لمعظم اللغات منخفضة الموارد (انظر [مواصفات التسجيل §2.3](/docs/network/specifications/scoring#2-metric-inventory)). تُحسب فترات ثقة Bootstrap عبر درجاته المخزنة مؤقتًا لكل مدخلة:
- النموذج: `Unbabel/wmt22-comet-da` (نموذج قائم على المراجع لـ WMT 2022)؛ ويُختار AfriCOMET تلقائيًا للغات الإفريقية المدعومة
- يُحسب عند تثبيت `unbabel-comet`
- تُخزن الدرجات لكل مدخلة في مدخلات TestReport؛ وتحمل قيمة المدونة تنبيهًا بشأن المعايرة للغات منخفضة الموارد
- يُعاد اشتقاقه بواسطة أداة التحقق — حيث يجب أن تتطابق قيمة COMET المُبلّغ عنها عند إعادة الإنتاج
- تبعية اختيارية: `python3 -m pip install 'mt-eval-harness[comet]'` (أو `mt-eval setup --comet`)

### أعمدة Supabase

يحتوي جدول `run_cards` على الأعمدة المقابلة القابلة للقيم الخالية (انظر [scoring.md §9.1](/docs/network/specifications/scoring)):
- `chrf_plus_plus`، و`chrf_ci_lower`، و`chrf_ci_upper` (`real`) — النتيجة الرئيسية وفترة الثقة 95% الخاصة بها
- `comet_score` (`real`) — تُعرض بجانب النتيجة الرئيسية، ولا تُدمج معها أبدًا
- `corpus_bleu` (`real`)

تُخزن المجموعة الكاملة لفترات الثقة داخل كائن JSON لـ `scores` الخاص ببطاقة التشغيل تحت `confidence_intervals` (وفقًا لمخطط بطاقة التشغيل في scoring.md §9)؛ وتكون حدود chrF++ وحدها ملغاة التطبيع أيضًا كأعمدة.
