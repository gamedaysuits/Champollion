# بيئة التقييم (Eval Harness) الإصدار 2.0

> **ملخص تنفيذي.** تغطي هذه الصفحة تثبيت بيئة تقييم الترجمة الآلية وإعدادها واستخدامها — وهي الأداة التي تقيس أداء طرق الترجمة مقارنةً بمجموعات النصوص المعيارية وتنشئ بطاقات تشغيل (run cards) مُقيّمة بالدرجات. للاطلاع على التعريفات المعتمدة للمقاييس والمخططات وبروتوكول التقييم، راجع [مواصفات المعيار المرجعي](/docs/network/specifications/benchmark).

تُجري بيئة التقييم تجارب الترجمة وتنشئ بطاقات التشغيل. وهي تتولى بناء المطالبات، واستدعاءات واجهة برمجة التطبيقات (API)، وحساب الدرجات، وتسلسل النتائج — وما عليك سوى توفير مجموعة البيانات والنموذج.

## التثبيت

**المتطلبات:** Python 3.11+

```bash
python3 -m pip install mt-eval-harness
```

يؤدي هذا إلى تثبيت الأمر `mt-eval`.

## الاستخدام

```bash
mt-eval run --corpus path/to/dataset.json
```

يقوم هذا بتمرير كل إدخال في مجموعة النصوص عبر النموذج المكوّن (أو ملحق الطريقة)، ويحسب درجات المخرجات، ويكتب ملف بطاقة التشغيل بتنسيق JSON في دليل المخرجات.

## خيارات واجهة سطر الأوامر (CLI Flags)

### `mt-eval run`

| الخيار | مطلوب | الافتراضي | الوصف |
|------|----------|---------|-------------|
| `--corpus` | ✅ | — | مسار ملف المدونة (`.json`، `.jsonl`، `.tsv`) |
| `--source-file` / `--reference-file` | — | — | ملفات نصوص متوازية (تنسيق FLORES+، WMT) |
| `-m, --model` | — | `google/gemini-3.1-pro-preview` | المُعرّف الدقيق للنموذج: معرّف OpenRouter الكامل، أو الاسم الدقيق للمزوّد المباشر نفسه. لا أسماء مستعارة ولا معرّفات عائمة (`~vendor/…`، `…-latest`): يُرفض الاسم القصير مثل `gemini-pro`، ويحدّد الرفضُ المُعرّف الواجب كتابته. يُفصل بينها بفواصل لعمليات التشغيل متعددة النماذج. مع `--method local-model` يكون هو النموذج المراد تشغيله — معرّف Hugging Face أو دليل النموذج — وهو مطلوب: فذلك المحرك لا يحتوي على نموذج افتراضي. مع ملحق الطريقة، يُمرَّر إلى الملحق كـ `config.method_model`. يترجم أي محرك ترجمة آلية آخر بنموذجه الخاص وتفيد عملية التشغيل بأن `-m` غير مُستخدم |

| `--tools` | — | `false` | تفعيل وضع استدعاء الأدوات |
| `--tools-list` | — | — | أسماء الأدوات مفصولة بفواصل |
| `--max-tool-rounds` | — | `8` | الحد الأقصى لجولات استدعاء الأدوات لكل مدخل |
| `--style-profile` | — | — | مسار ملف JSON لملف تعريف الأسلوب. يفعّل مقاييس اتساق أسلوب الكتابة (تشخيصية — ليست جزءًا من النتيجة الرئيسية أبدًا؛ انظر [§ مقاييس أسلوب الكتابة ومستوى الخطاب](#writing-style-and-register-metrics-informational)) |

| `--target-lang-code` | — | — | رمز لغة BCP-47 |
| `--target-script` | — | — | نظام الكتابة (ISO 15924) الذي يجب كتابة الترجمات به (`Latn`، `Cans`، …)، وهو نظام تدرجه بطاقة لغة الهدف. تطلبه صياغة منظومة التقييم (مُلحقًا بنص ملف التدريب أيضًا)، لذا فهو جزء من sha256 الخاص بالصياغة التوجيهية. بالنسبة للغة تُكتب بأكثر من نظام كتابة واحد، مثل كري السهول، استخدم نظام الكتابة المكتوبة به مراجعك. وبدونه، تُحصي منظومة التقييم أحرف المراجع حسب نظام الكتابة (بشكل إجمالي: لا تُعرض أي جملة، لذا ينطبق هذا على المدونة المحلية فقط أيضًا) وتطلب نظام الكتابة الذي يشكل 90% أو أكثر منها، موضحة ذلك في رأس التشغيل ("references are 100% Latn → prompting for Latn") وتسجله في سجل التشغيل (`config.target_script_source`)؛ والمراجع المختلطة لا تحصل على نظام كتابة وتتلقى تحذيرًا بالنسب، ويسجل المرجع المكتوب بنظام الكتابة الآخر حينئذٍ نتيجة تقارب الصفر. يُرفض لمحرك الترجمة الآلية أو ملحق الطريقة، إذ لا يتلقيان أي صياغة توجيهية |

تمت إحالة `--champollion-config` و`--prompt champollion` إلى التقاعد في الإصدار 0.2.0 ويتم رفضهما مع بيان السبب. والأمر نفسه ينطبق على `--champollion-cards-dir`؛ اضبط `MT_EVAL_CARDS_DIR` لتوجيه بيئة التقييم إلى دليل بطاقات آخر. فقد كانت تعيد بناء مطالبة واجهة سطر الأوامر بلغة Python، وتباينت تلك النسخة عن واجهة سطر الأوامر. استخدم ملحق طريقة (`--method`) لتقييم طريقة CLI، واستخدم `mt-eval export-config` لإعادة النتيجة إلى مشروع CLI.

### المقاييس العصبية الاختيارية

يتم حساب COMET متى كان `unbabel-comet` مثبتًا (`mt-eval setup --comet`: حوالي 300 ميغابايت للتثبيت، ونحو 2.3 غيغابايت للنموذج عند أول استخدام). وهناك مقياسان إضافيان يتم تعطيلهما ما لم يطلبهما التشغيل، لأن كل منهما يحمّل نموذجًا كبيرًا. ومثل COMET، يتم تشغيلهما محليًا على هذا الجهاز (دون تكلفة API، ودون إرسال أي نصوص إلى أي مكان)، ويُعرضان بجانب نتيجة chrF++ الرئيسية ولا يُدمجان معها أبدًا، وتذكر بطاقة التشغيل "not run" مع توضيح الخيار الذي يجب تمريره عندما لا يتم طلبهما.

| المقياس | الخيار | ما يتطلبه | تكلفته |
|--------|------|---------------|---------------|
| MetricX-24 (`metricx_score`، القيمة الأقل أفضل، 0–25) | `--metricx` (نقطة الفحص: `--metricx-model`) | `python3 -m pip install 'mt-eval-harness[metricx]'` (PyTorch، Transformers، SentencePiece) وكود نموذج Google، وهو غير متوفر على PyPI: `python3 -m pip install git+https://github.com/google-research/metricx` | تقوم نقطة الفحص الافتراضية `google/metricx-24-hybrid-large-v2p6` ومجزئ النصوص mT5-XL بتنزيل عدة غيغابايت من Hugging Face عند الاستخدام الأول؛ ويكون حساب الدرجات بطيئًا على وحدة المعالجة المركزية. وفي حال غياب المرجع، يحسب الدرجات في وضعه الخالي من المراجع (QE) |
| مقارِن نمط FUSE (`fuse_score`) | `--fuse` | `python3 -m pip install 'mt-eval-harness[fuse]'` (sentence-transformers، jellyfish) | ينزّل LaBSE حوالي 1.8 غيغابايت عند الاستخدام الأول. وبدون LaBSE لا يتم حساب النتيجة، ويوضح التقرير ذلك. وهو غير مدرب (متوسط غير مرجح لأجزائه)، ويتم تمييز النتيجة بعلامة `fuse_untrained` |

عبر MCP (الملف التعريفي الكامل، `--profile full`)، يأخذ `run_benchmark` كلاً من `metricx` (مع `metricx_model`) و`fuse`، ويتطلب `comet: true` مقياس COMET؛ وتوضح خطته ما إذا كان كل منها مثبّتًا، وتُرفض أي عملية تشغيل مؤكدة تطلب مقياسًا لا تستطيع منظومة التقييم احتسابه.

ما يقيسه كل مقياس ومدى إمكانية الوثوق به للغة معينة مفصل في [حساب الدرجات](/docs/network/specifications/scoring) و[موثوقية المقاييس](/docs/network/specifications/metric-reliability).

### ذاكرة التخزين المؤقت للترجمة

تحتفظ كل عملية تشغيل بمخرجات النموذج لكل جملة مصدر في ذاكرة تخزين مؤقت (`--cache-dir`، افتراضيًا `eval/cache/harness` داخل الدليل الذي يبدأ فيه التشغيل)، بحيث تعيد عملية إعادة التشغيل بنفس الإعداد استخدامها مجانًا دون تكلفة إضافية. يغطي مفتاح التخزين المؤقت النموذج، والمطالبة كما أُرسلت (تجزئة sha256 الخاصة بها)، والإعدادات التي تغير المخرجات، وإصدار بيئة التقييم، بحيث لا يُقدَّم مخرج قديم أبدًا عند تغيير أي منها. وتحتفظ ذاكرة التخزين المؤقت بنسخ من جمل مجموعة النصوص:

- يطبع رأس التشغيل والتشغيل التجريبي مكان وجودها وعدد الإدخالات التي تحتوي عليها؛
- يحتوي المجلد على `.gitignore`، لذا يتجاهله git؛
- لا تُكتب أبدًا داخل مجلد `mt-eval contest prepare` مصنف على أنه قابل للنشر (ملف `public/` الخاص به): يرفض `mt-eval run` استخدام مثل هذا `--cache-dir` أو `--output-dir` ويحدد مجلد `runs/` للمسابقة بدلاً من ذلك ([إدارة مسابقة سيادية](/docs/network/sovereignty/run-a-sovereign-contest))؛
- تحصل مجموعة النصوص المحلية فقط أو المغلقة أو التي تتطلب موافقة على مجلد `protected/<namespace>/` خاص بها، يُفهرس بإعدادات التشغيل وتجزئة sha256 لمجموعة النصوص وشروطها، ويحمل كل ملف هناك علامة مجموعة النصوص في ملف جانبي `<file>.champollion.json` ([تسجيل مجموعات النصوص](/docs/network/sovereignty/registering-corpora))؛
- احذف المجلد لإزالة النسخ، أو مرر `--no-cache` لعدم الاحتفاظ بأي منها.

يذكر `run_benchmark` الخاص بخادم MCP (الملف التعريفي الكامل) ذاكرة التخزين المؤقت في خطته ونتيجته. بالنسبة لملف بحوزتك، فإنه يضع ذاكرة التخزين المؤقت بجانب نتائج التشغيل (`<corpus folder>/results/cache/`)، وبالنسبة لمعرّف مدونة مسجّل، يضعها في مجلدها الخاص (`~/.champollion-mcp/cache/harness/`). وتستمر الاستفادة من ذاكرة التخزين المؤقت الموجودة بالفعل في `eval/cache/harness` ضمن دليل عمل الخادم من عمليات تشغيل سابقة، وبذلك لا يتم الدفع مقابل مخرجاتها مرتين. ولا تعتمد مدخلاتها على مكان وجود المجلد، لذا يمكن نقله.

### كافة الأوامر الفرعية

جميع الأوامر الفرعية العشرين ذات المستوى الأعلى. كل خيار من خيارات كل أمر منها موجود في
[مرجع أوامر `mt-eval`](/docs/reference/mt-eval) المُنشأ تلقائيًا؛ ويوضح هذا القسم
الغرض من كلٍّ منها.

**التشغيل وحساب الدرجات**

| الأمر الفرعي | ما يفعله |
|---|---|
| `mt-eval run` | تنفيذ عملية تشغيل ترجمة (الخيارات أعلاه) |
| `mt-eval test <log>` | تحليل سجل تشغيل مكتمل. يكتب `-o <path>` التقرير في مكان آخر غير `<log>_report.json`، ويسجل سجل التشغيل هذا المسار بحيث يعثر عليه `card` و`compare`. يحسب `--glossary <file>` درجات المصطلحات مقارنةً بذلك المسرد؛ ويسجل التقرير اسمه وتجزئة sha256، وتوضح البطاقة و`compare` ومعاينة النشر المسرد الذي تم قياس الالتزام بمصطلحاته (كأداة تشخيصية) |
| `mt-eval compare <reports…>` | مقارنة تشغيلين أو أكثر (`*_report.json`، أو سجلات التشغيل). صف واحد لكل مقياس (chrF++، BLEU، spBLEU، TER، …)، وعمود واحد لكل تشغيل بالأحرف A، B، C…، مع تمييز المقاييس التي تكون فيها القيمة الأقل أفضل؛ يضيف `--significance` اختبارات مقترنة لكل زوج، ويُسمى كل جدول بأحرف عمليات التشغيل، مع فترة ثقة 95% لـ Δ، ويوضح أن قيم p تكون لكل مقياس وغير مصححة؛ يستبدل `--method paired_bootstrap` التوزيع العشوائي التقريبي الافتراضي بأسلوب Koehn bootstrap ([الدلالة الإحصائية](/docs/network/specifications/significance)). يكتب `comparison-<hash>.json` (تجزئة معرّفات عمليات التشغيل المقارنة، حتى لا تقوم مقارنة أخرى بالكتابة فوقه) بجانب التقارير عندما تتشارك في مجلد واحد، وإلا ففي `comparisons/` داخل أقرب مجلد مشترك بينها (ولا يُكتب أبدًا في مجلد خاص بتشغيل واحد)، ما لم يحدد `-o` ملفًا. اختبار chrF++ وحده يحدد أي عملية تشغيل هي الأفضل؛ وتُعرض الصفوف الأخرى دون استخدامها في اتخاذ القرار. ويُشار إلى النتيجة المركبة في التقرير القديم على أنها متقاعدة ولا تدخل في المقارنة |
| `mt-eval dashboard <logs…>` | إنشاء لوحة تحكم تفاعلية بتنسيق HTML |
| `mt-eval card <run log>` | تنسيق وطباعة بطاقة تشغيل مقروءة بشريًا. تأتي الدرجات من تقرير التشغيل: بجانب السجل، حيث سجله `mt-eval test -o`، أو `--report <path>`. ويُظهر التشغيل الذي لم يُعثر له على تقرير عبارة NOT SCORED والمكان الذي تم البحث فيه، ولا يُظهر أصفارًا أبدًا. يمكن أيضًا تمرير ملف تقرير؛ حيث يُقرأ مع سجل التشغيل الذي يسجله |

**تشغيل طريقة ما** (لا يتم احتساب أي نقاط)

| الأمر الفرعي | وظيفته |
|---|---|
| `mt-eval translate` | ترجمة مدخلات المصدر فقط باستخدام طريقة ما — مسار عمل التشغيل دون احتساب درجات. يكتب `.jsonl` أو `.tsv` مع شروط المدخلات كملف جانبي set/1؛ والطريقة التي يكون ناتجها محليًا فقط لا تكتب إلا داخل المشروع ما لم يحدد `--holders-agreed-by` مَن وافق مِن حَمَلَة البيانات |
| `mt-eval serve` | تقديم خدمة لطريقة تعمل على هذا الجهاز (`lexicon`، أو `local-model`، أو ملحق من فئة التبعية S أو O) خلف عقد `/translate` الخاص بـ champollion، من ملف deployment/1 أو من خيارات، مع ملف gate-chain/1 اختياري يضبط كل إجابة. يرتبط بالعنوان 127.0.0.1 افتراضيًا؛ وتتطلب استضافة أخرى `$MT_EVAL_SERVE_TOKEN` |

**اختيار الطريقة المناسبة**

| الأمر الفرعي | ما يفعله |
|---|---|
| `mt-eval recommend <src> <tgt>` | إرشادات اختيار الطريقة لزوج لغوي — التوافر بالإضافة إلى **الأدلة الموثقة**، وليس مجرد تصنيف مجرد. يمكن أيضًا تحديد الزوج كـ `--source <src> --target <tgt>`، وهو التنسيق الذي يقبله `corpora` |
| `mt-eval corpora --source X --target Y` | سرد مجموعات نصوص التقييم المتاحة لزوج لغوي. يعمل أي من الخيارين منفردًا: يسرد `--target Y` كل مجموعة نصوص إلى Y، ويسرد `--source X` كل مجموعة نصوص من X |
| `mt-eval corpora --with-fst` | مجموعات النصوص فقط التي تحتوي لغتها الهدف على FST مثبّت بواسطة بيئة التقييم، حتى يمكن تقييم قبول FST. تُسرد كل لغة هدف مع بيان ما إذا كان FST الخاص بها مثبتًا على هذا الجهاز وكيفية تثبيته (`mt-eval setup --lang <code>`، أو تثبيت يدوي لبعض التنسيقات). ادمجه مع `--source`/`--target`، أو استخدمه بمفرده لكل زوج. لا يتم تنزيل أي شيء |
| `mt-eval list models\|prompts\|datasets` | سرد الموارد المتاحة |

**المساهمة**

| الأمر الفرعي | وظيفته |
|---|---|
| `mt-eval publish <report>` | إرسال TestReport إلى لوحة الصدارة |
| `mt-eval queue` | تشغيل أعلى قائمة انتظار الحوسبة المجتمعية باستخدام مفتاحك الخاص — انظر [المساهمة بالحوسبة](/docs/network/getting-started/contributing-compute) |
| `mt-eval export` | حزم TestReport كملحق طريقة champollion (ملف `method.json` من نوع method/1) |
| `mt-eval generate-plugin` | اسم بديل لـ `export` |
| `mt-eval export-config` | إنشاء مقتطف `champollion.config.json` من TestReport |

**المسابقات، وتنظيم مسابقتك الخاصة**

| الأمر الفرعي | وظيفته |
|---|---|
| `mt-eval contest` | تشغيل **مسابقة سيادية** أو المشاركة فيها — من جانب المنظِّم: `prepare`، `register`، `create`، `rank`، `close`، `export`؛ ومن جانب المشارك: `qualify` (التقييم الذاتي لمجموعة التطوير العامة للحصول على إيصال القبول؛ المؤهل هو chrF++ بمقياس 0–100)، و`validate` (التدرب على فحوصات العقدة دون اتصال بالإنترنت)، و`submit-model` / `submit-method` (تسليم نموذج أو طريقة)، و`status`، و`list`. تتم المشاركة في المسابقة بتقديم شيء يمكن لعقدة المنظِّم تشغيله؛ وقد تم إيقاف رفع الترجمات وربط بطاقة التقرير الذاتي كمسارات مشاركة في 2026-09-06 |
| `mt-eval shared-task` | مظلة إصدار المهام المشتركة متعددة الأزواج: يجمع صفٌ واحد مسابقات الأزواج البالغ عددها N لإصدار مهمة مشتركة متعددة الأزواج ويحمل الإعدادات الافتراضية لسياستها. **للتجميع والإعدادات الافتراضية فقط — تظل كل بوابة لكل مسابقة على حدة** |
| `mt-eval node` | **عقدة تقييم المنظِّم.** استطلاع المدخلات، وتطبيق البوابة بناءً على المؤهل العام، والترخيص وفقًا لسياسة المسابقة، واحتساب النقاط مقابل **مراجع سرية يحتفظ بها المنظِّم**، ونشر النتائج فقط. هذا هو الأمر الكامن وراء [تشغيل مسابقة سيادية](/docs/network/sovereignty/run-a-sovereign-contest) و[عقدة التقييم السيادي](/docs/network/sovereignty/sovereign-eval-node) — فالمدونة لا تغادر جهاز المنظِّم أبدًا |

يحتوي `mt-eval node` على ثمانية عشر أمرًا فرعيًا خاصًا به، بما في ذلك مسار الفجوة الهوائية
(`import-bundle`، `export-scores`، `relay`، `egress-check`، `manifest`) ومراسم
حضانة M-of-N ‏(`ceremony`، `seal`، `keygen`، `sign-manifest`،
`verify-manifest`، `ledger`). شغّل `mt-eval node --help`؛ وتم شرح آليات
السيادة في الصفحتين المربوطتين أعلاه.

**الإعداد**

| الأمر الفرعي | ما يفعله |
|---|---|
| `mt-eval setup` | تثبيت التبعيات الاختيارية (مقياس COMET العصبي، بيئة تشغيل FST) |
| `mt-eval logout` | إزالة بيانات اعتماد المصادقة المخزنة |

### أمثلة

```bash
# Run with defaults (google/gemini-3.1-pro-preview, naive prompt)
mt-eval run --corpus eval-amh-fra-globalvoices-test-v1

# Coached experiment with coaching file
mt-eval run \
  --corpus eval-amh-fra-globalvoices-test-v1 \
  --model google/gemini-3.1-pro-preview \
  --coaching-file prompts/crk-coaching-v8.txt \
  --temperature 0.0

# Run a custom method plugin
mt-eval run \
  --corpus eval-amh-fra-globalvoices-test-v1 \
  --method ./methods/fst-gated-pipeline
```

لا تعيد منظومة التقييم أبدًا محاولة ترجمة يرفضها FST ولا تصفيها: إذ يُعد
قبول FST مقياسًا يُحتسب عندما تحتوي حزمة تقييم اللغة على FST. أما الطريقة
التي تتطلب إعادة المحاولات الموجهة بواسطة FST، فتجريها داخل الملحق الخاص بها،
كما يوضح البرنامج التعليمي `fst-gated-pipeline`. (لم يتم ربط `--fst-retries` و`--hooks`
بأي شيء على سطر الأوامر أبدًا؛ وكلاهما يُرفض لهذا السبب).

## مخطط بطاقة التشغيل (Run Card Schema)

تنتج كل تجربة **بطاقة تشغيل** — وهي وثيقة JSON قائمة بذاتها. البنية ذات المستوى الأعلى:

```json
{
  "run_id": "uuid-v4",
  "harness_version": "2.0",
  "model_slug": "google/gemini-3.1-pro-preview",
  "model_id": "gemini-3.1-pro-001",
  "condition": "naive",
  "timestamp": "2026-06-01T03:22:41Z",
  "elapsed_seconds": 142.7,
  "dataset": { ... },
  "config": { ... },
  "method_card": { ... },
  "system_prompt_sha256": "abc123...",
  "system_prompt_used": "You are a translator...",
  "fingerprint": { ... },
  "scores": { ... },
  "totals": { ... },
  "environment": { ... },
  "results": [ ... ],
  "run_card_hash": "sha256-of-entire-card"
}
```

راجع [مواصفات بطاقة التشغيل](/docs/network/specifications/run-card) للاطلاع على المخطط الكامل مع توثيق كل حقل.

:::info[المخطط المعتمد]
تُعد [مواصفات المعيار المرجعي](/docs/network/specifications/benchmark) المصدر الموثوق الوحيد لمخطط بطاقة التشغيل. للاطلاع على تعريفات المقاييس وكيفية حساب درجات التشغيل، راجع [مواصفات حساب الدرجات](/docs/network/specifications/scoring). توثق هذه الصفحة كيفية استخدام بيئة التقييم، بينما تحدد المواصفات دلالات المخرجات.
:::

### الكتل الرئيسية

**`dataset`** — يحدد مجموعة البيانات المستخدمة، بما في ذلك تجزئة المحتوى الخاصة بها لربط النتائج بإصدار محدد:

```json
// Example using textbook_dev.json — the 436-entry textbook dev split
{
  "id": "edtekla-dev-v1",
  "version": "1.0",
  "language_pair": "EN→CRK",
  "sha256": "...",
  "entry_count": 436
}
```

**`scores`** — المقاييس الإجمالية للتشغيل:

```json
// Counts reflect the dataset used (here: textbook_dev.json, 436 entries)
{
  "total": 436,
  "exact_matches": 12,
  "exact_match_rate": 0.0968,
  "fst_accepted": 87,
  "fst_acceptance_rate": 0.7016,
  "chrf_plus_plus": 42.31,
  "errors": 0,
  "avg_latency_seconds": 1.15,
  "median_latency_seconds": 1.02,
  "p95_latency_seconds": 2.34,
  "by_difficulty": { ... },
  "by_provenance": { ... }
}
```

**`totals`** — استخدام الرموز وتتبع التكلفة:

```json
{
  "prompt_tokens": 48200,
  "completion_tokens": 3100,
  "reasoning_tokens": 0,
  "cached_tokens": 12000,
  "total_cost_usd": 0.42,
  "cost_per_entry_usd": 0.0034,
  "reasoning_ratio": 0.0
}
```

## مقاييس أسلوب الكتابة ومستوى الخطاب (معلوماتية) {#writing-style-and-register-metrics-informational}

تستطيع بيئة التقييم فحص ما إذا كانت الترجمات تتطابق مع **مستوى الخطاب** و**أسلوب الكتابة** المستهدفين، عبر ملحق المقياس `WritingStyleConsistency` (`mt_eval_harness/plugins/writing_style.py`). فقد تكون الترجمة صحيحة لغويًا ولكنها في مستوى خطاب خاطئ — مثل الصياغة غير الرسمية في وثيقة قانونية، أو العبارات الرسمية النمطية في نصوص تسويقية — ولن تلاحظ المقاييس النصية العادية ذلك. أما هذه المقاييس فترصده.

**ما يتم قياسه (لكل إدخال):**

| المقياس | المقياس الرقمي | المعنى |
|--------|-------|---------|
| `style_register_match` | منطقي | هل يتطابق الناتج مع مستوى الخطاب المتوقع؟ يأتي الهدف من حقل `register` لإدخال مجموعة النصوص (انظر [مواصفات المعيار المرجعي §2.6](/docs/network/specifications/benchmark)) أو من ملف تعريف الأسلوب |
| `style_sentence_length_ratio` | عدد عشري | متوسط طول الجملة المتوقع مقارنةً بالمرجع (1.0 = تطابق تام؛ والتباعد = انحراف في الأسلوب) |
| `style_formality_score` | 0.0–1.0 | وجود علامات الخطاب الرسمي/غير الرسمي (ضمائر المخاطبة T–V، الاختصارات، …) باستخدام موارد العلامات الخاصة بكل لغة |

**الإجمالي:** `style_consistency_rate` — نسبة الإدخالات التي لم يُكتشف فيها أي عدم تطابق في مستوى الخطاب.

يمكنك تفعيل هدف مخصص باستخدام `--style-profile path/to/profile.json` (مثل ملف تعريف نبرة العلامة التجارية)؛ وبدونه، يعتمد الملحق تلقائيًا على البيانات الوصفية `register` لكل إدخال في مجموعة النصوص حيثما وجدت.

:::caution[تحديد دقيق للنطاق]
هذه المقاييس هي **أدوات تشخيصية** — وليست جزءًا من النتيجة الرئيسية أبدًا، كما أن رصد مستوى الرسمية يعتمد على علامات محددة (أسلوب إرشادي)، وليس حكمًا متعلمًا بالذكاء الاصطناعي. عاملها كأداة للكشف عن الانحراف في الالتزام بمستوى الخطاب، وليس كحكم نهائي على جودة الأسلوب.
:::

## البصمة مقابل تجزئة بطاقة التشغيل {#fingerprint-vs-run-card-hash}

تنتج بيئة التقييم قيمتي تجزئة متمايزتين، وتخدم كل منهما غرضًا مختلفًا:

### البصمة

تجيب **البصمة** عن السؤال: *"هل يمكن إعادة إنتاج هذا التشغيل؟"*

فهي تُجري تجزئة لمجموعة المدخلات التي تحدد تكوين التجربة — وليس المخرجات:

- تجزئة SHA-256 لمجموعة البيانات
- معرّف النموذج
- تسمية الحالة
- تجزئة SHA-256 لمطالبة النظام
- درجة الحرارة
- حجم الدفعة
- الأدوات المفعلة
- إصدار بيئة التقييم

ثمانية مكونات في المجمل: فحجم الدفعة واستدعاء الأدوات يغيران المخرجات
تغييرًا جوهريًا، لذا فهما جزء من هوية التجربة — وتشغيلان بحجمي
دفعة مختلفين **لا** يشتركان في نفس البصمة. راجع
[مواصفات المعيار المرجعي §3.8](/docs/network/specifications/benchmark#38-fingerprint).

أي تشغيلين ببصمتين متطابقتين قد استخدما نفس الإعداد. ويجب أن تكون نتائجهما قابلة للمقارنة (مع مراعاة عدم الحتمية في استجابات واجهة برمجة التطبيقات).

### تجزئة بطاقة التشغيل

تجيب **تجزئة بطاقة التشغيل** عن السؤال: *"هل تم التلاعب بملف النتائج المحدد هذا؟"*

وهي تجزئة SHA-256 لكامل ملف JSON لبطاقة التشغيل (باستثناء حقل `run_card_hash` نفسه). وإذا تغير أي حقل — درجة، أو طابع زمني، أو مخرج واحد — تنكسر التجزئة وتفقد صلاحيتها.

:::info[متى تستخدم كل منهما]
استخدم **البصمة** لتجميع عمليات التشغيل القابلة للمقارنة (نفس التجربة، بتنفيذات مختلفة). واستخدم **تجزئة بطاقة التشغيل** للتحقق من سلامة ملف نتائج بعينه وعدم التلاعب به.
:::

## النشر في لوحة الصدارة

بعد إكمال التشغيل، استخدم `mt-eval publish` على `<run-id>_report.json` الخاص بالتشغيل. وتتطلب الكتابة إلى لوحة الصدارة الحية تمرير `--prod` صريح (أو `MT_EVAL_ALLOW_PROD=1`)؛ وينفذ `mt-eval run --publish --prod` كلتا الخطوتين معًا في آن واحد:

```bash
mt-eval publish eval/logs/harness/<run-id>_report.json --dry-run   # preview
mt-eval publish eval/logs/harness/<run-id>_report.json --prod      # write to the live board
```

إذا لم يتم توفير `--method-card` أثناء التشغيل، يطلق `mt-eval publish` معالجًا تفاعليًا (`method_card_wizard.py`) يرشدك خطوة بخطوة لوصف طريقتك (الاسم، الفئة، الأدوات المستخدمة، وما إلى ذلك). ويتم تضمين مخرجات المعالج في بطاقة التشغيل قبل الإرسال.

### الفحص اليدوي

تُحفظ بطاقات التشغيل كملفات JSON في دليل المخرجات (`eval/logs/harness/` افتراضيًا) — افحصها هناك قبل النشر. ويُعد `mt-eval publish` مسار الإرسال الوحيد؛ إذ لا يوجد استقبال لبطاقات التشغيل عبر طلبات السحب.

:::note[واجهة برمجة تطبيقات الإرسال والرفع عبر الويب لم يُطلقا بعد]
نقطة نهاية `POST https://champollion.dev/api/leaderboard/submit` وواجهة مستخدم الرفع إلى لوحة الصدارة قيد التخطيط ولكن **لم يتم تنفيذهما بعد**. وحتى إطلاقهما، فإن مسار الإرسال الفعال الوحيد هو `mt-eval publish`.
:::

:::warning[التحقق من صحة بيانات لوحة الصدارة]
تتحقق لوحة الصدارة من صحة بطاقات التشغيل المرسلة مقارنةً بسجل مجموعات البيانات. ويتم رفض الإرسالات التي تشير إلى مجموعات بيانات غير معروفة، أو التي تحتوي على `run_card_hash` غير صالح.
:::

:::danger[لا تدرّب على بيانات التقييم]
إذا كانت طريقتك قد اطلعت على مجموعة بيانات التقييم أثناء التطوير — كبيانات تدريب، أو أمثلة قليلة التعلم، أو مدخلات قاموس، أو مواد لهندسة المطالبات — فسيتم **استبعاد مشاركتك وإلغاء تأهيلها**. راجع [تقييم الترجمة الآلية](/docs/network/leaderboard/rules) للتعرف على ما يميز الطرق المقبولة عن المرفوضة.
:::
