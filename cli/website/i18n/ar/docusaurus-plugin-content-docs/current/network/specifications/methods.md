# واجهة الأسلوب المشتركة

> **ملخص تنفيذي.** تحدد هذه الصفحة بروتوكول `TranslationMethod` الذي يجب أن تطبقه جميع أساليب Network، وفئات الأساليب الست (`raw-llm`، `coached-llm`، `pipeline`، `custom-plugin`، `api`، `human`)، ومحور **النموذج الفكري** (paradigm) المتعامد (`rule-based`، `statistical`، `neural-nmt`، `llm`، `hybrid`، …) الذي يجعل *طريقة ترجمة الأسلوب* قابلة للمقارنة عبر الأنظمة، وتنسيق الملحق الإضافي للأسلوب (method plugin)، و**فئات التبعية** (S/O/A1/A2/X) التي تحدد ما إذا كان بإمكان الأسلوب العمل في بيئة الاختبار المعزولة (sandbox) والتأهل للجوائز. هذه ثلاثة محاور مستقلة. يمكن تقييم أي نهج يطبق هذا البروتوكول عبر مقاييس الأداء؛ وما يعتمد عليه يحدد أين يمكنه المنافسة.

تتشارك بيئة التقييم (eval harness) وchampollion مفهوماً مشتركاً لـ **أسلوب الترجمة** (translation method). الأسلوب هو أي إجراء يأخذ نص المصدر وينتج نصاً مترجماً — سواء كان استدعاءً مباشراً لنموذج لغوي كبير (LLM)، أو خط معالجة متعدد المراحل (multi-stage pipeline)، أو واجهة برمجة تطبيقات (API) لطرف ثالث، أو مترجماً بشرياً.

## البنية المعمارية

```
Method Plugin (v2 Spec)
├── method.json           ← Manifest (name, class, entry_point, dependencies, metadata)
├── method_card.json      ← Leaderboard description (what, not how)
├── pipeline.py           ← Python module implementing TranslationMethod
└── (optional helpers)    ← Additional Python modules
```

يتم التحميل عبر `--method path/to/dir`. لا تكتشف بيئة التقييم أي شيء تلقائياً.

## نظامان، واجهة واحدة

| | بيئة التقييم (Eval Harness) | champollion |
|---|---|---|
| **اللغة** | Python | Node.js |
| **نقطة الدخول** | `translate.py` | `translate.js` |
| **الواجهة** | بروتوكول `TranslationMethod` | إعداد `methodPlugin` |
| **الغرض** | تقييم دفعي مع احتساب الدرجات | توطين مباشر في بيئات التطوير/التكامل المستمر (dev/CI) |
| **المخرجات** | بطاقة تشغيل تتضمن المقاييس | ملفات اللغات المترجمة |

يوفر الأسلوب الذي يدعم كلا النظامين نقطتي دخول — نقطة لكل بيئة تشغيل لغة. وتُعد **بطاقة الأسلوب** (method card) هي الجسر الرابط: فهي تصف الأسلوب بتنسيق يفهمه كلا النظامين.

## بطاقة الأسلوب {#method-card}

تصف بطاقة الأسلوب *ماهية* أسلوب الترجمة دون الكشف عن تفاصيل مملوكة مثل موجه النظام الكامل (system prompt). وهي تجيب عما يلي:

- ما هي فئة هذا الأسلوب؟ (LLM خام، LLM موجّه، خط معالجة، API، إلخ)
- ما هو **النموذج الفكري** الذي يستخدمه؟ (قائم على القواعد، إحصائي، عصبي-NMT، LLM، هجين)
- ما هي الأدوات التي يستخدمها؟ (محلل FST، قاموس، إلخ)
- هل التنفيذ مفتوح المصدر؟
- ما هي أزواج اللغات التي يدعمها؟

راجع [مواصفات بطاقة الأسلوب](/docs/network/specifications/methods#method-card) للاطلاع على مخطط JSON الكامل.

### مثال

```json
{
  "method_id": "fst-gated-v8",
  "name": "FST-Gated Coached Translation v8",
  "class": "pipeline",
  "paradigm": "hybrid",
  "description": "LLM translation with morphological validation. Failed words are retried with FST feedback.",
  "author": "Curtis Forbes",
  "tools_used": ["HFST morphological analyzer", "Wolvengrey dictionary"],
  "open_source": false,
  "dependency_class": "A2",
  "supported_pairs": ["eng>crk"]
}
```

يلخص الحقل `dependency_class` ما يحتاجه الأسلوب للتشغيل والنقل — راجع [صلاحية الأسلوب وفئات التبعية](#method-validity-and-dependency-classes) أدناه. ويضع الحقل `paradigm` الأسلوب على **محور النموذج الفكري** (هنا `hybrid`: نموذج لغوي كبير مقترن ببوابة FST قائمة على القواعد) — راجع [النماذج الفكرية](#paradigms) أدناه.

### فئات الأساليب

| الفئة | الوصف |
|-------|-------------|
| `raw-llm` | استدعاء مباشر لـ LLM مع تعليمات دنيا |
| `coached-llm` | نموذج LLM مع موجه منظم وأمثلة وقيود |
| `pipeline` | خط معالجة متعدد المراحل بمكونات حتمية |
| `custom-plugin` | عملية خارجية تطبق بروتوكول `TranslationMethod` |
| `api` | واجهة برمجة تطبيقات ترجمة لطرف ثالث (Google Translate، وDeepL، وغيرها) |
| `human` | ترجمة بشرية (لتحديد خطوط الأساس) |

### النماذج الفكرية {#paradigms}

يُعد **النموذج الفكري** (paradigm) محوراَ ثالثاً ومستقلاً: *كيف يترجم الأسلوب على المستوى الخوارزمي*. وهو متعامد مع كل من فئة الأسلوب وفئة التبعية. ففئة الأسلوب وحدها متمحورة حول نماذج LLM — فنظام [Apertium](https://www.apertium.org/) القائم على القواعد وGoogle Translate يقعان كلاهما ضمن `pipeline`/`api`، ومن ثم لا يمكن تمييز "القائم على القواعد مقابل العصبي" بدونه. يجعل محور النموذج الفكري تلك المقارنة مفهوماً أساسياً قابلاً للتصفية في لوحة المتصدرين.

| النموذج الفكري | الوصف | أمثلة |
|----------|-------------|----------|
| `rule-based` | محولات الحالة المحدودة (FST)، وقواعد لغوية مكتوبة يدوياً، ونقل صرفي | Apertium، وتوليد GiellaLT FST |
| `statistical` | ترجمة آلية قائمة على العبارات / إحصائية (SMT) يتم تعلمها من مدونات متوازية | Moses الكلاسيكي |
| `neural-nmt` | نموذج ترجمة آلية عصبية مخصص من نوع المشفر-مفكك التشفير (encoder–decoder) | Google Translate، وDeepL، وMicrosoft Translator، وOPUS-MT، وLibreTranslate، وTilde MT، وTranslated (Lara) |
| `llm` | نموذج لغوي كبير للأغراض العامة يتم توجيهه للترجمة | استدعاء GPT / Claude / Gemini خام أو موجّه |
| `hybrid` | يجمع بين نموذجين فكريين أو أكثر في أسلوب واحد | نموذج LLM مقترن ببوابة FST قائمة على القواعد (crk-translate)؛ ترجمة آلية عصبية (NMT) + تحرير لاحق قائم على القواعد |
| `human` | ترجمة بشرية (خط أساس على مستوى النموذج الفكري) | خط أساس مترجم المجتمع المحلي |
| `unknown` | غير محدد — لم تعلن البطاقة عن أي نموذج فكري | القيمة الافتراضية للتوافق مع الإصدارات السابقة للبطاقات السابقة لظهور النموذج الفكري |

المحاور مستقلة عن بعضها. إليك بعض الأمثلة العملية:

| الأسلوب | `class` | `paradigm` | `dependency_class` |
|--------|---------|-----------|--------------------|
| Google Translate | `api` | `neural-nmt` | A2 |
| Tilde MT / Translated (Lara) | `api` | `neural-nmt` | A2 |
| LibreTranslate (self-hosted, OSS) | `api` | `neural-nmt` | O |
| Apertium | `pipeline` | `rule-based` | O |
| crk-translate (FST-gated, LLM-coached) | `pipeline` | `hybrid` | A2 |
| Raw GPT call | `raw-llm` | `llm` | A1 |

يُعد النموذج الفكري **اختيارياً** في بطاقة الأسلوب؛ ويتم تسجيل النموذج الفكري الغائب كـ `unknown` (ولا يؤدي غيابه إلى حظر النشر أبداً — فالمحور إضافي). والتعداد المذكور أعلاه هو المفردات القياسية والمدعومة التي تفرضها بيئة التقييم (`config.VALID_PARADIGMS`). ونظراً لأن الفرض يتم على جانب التطبيق وليس عبر قيد في قاعدة البيانات، يمكن إضافة نماذج فكرية جديدة لاحقاً دون الحاجة إلى ترحيل بيانات (migration)؛ وتقتصر التكلفة فقط على إعادة تسمية قيمة أو إزالتها بعد أن تبدأ الأساليب بالاعتماد عليها.

## صلاحية الأسلوب وفئات التبعية {#method-validity-and-dependency-classes}

تعتمد إمكانية تشغيل الأسلوب، وإمكانية نقله، على أقل تبعياته توفراً. وتعتمد آليتان في Network على معرفة ما يحتاجه الأسلوب بالضبط:

1. **التقييم داخل بيئة معزولة** ([مواصفات التقييم المعياري §8.2](/docs/network/specifications/benchmark)) — تصدر الدرجات الرسمية للمعيار الذهبي من بيئة معزولة تكون سياسة الشبكة فيها **الحظر الافتراضي** (default-deny). ولا يمكن لأسلوب يتطلب خدمة خارجية دون إفصاح صريح أن ينتج درجات رسمية.
2. **نقل الجوائز** ([مواصفات الجوائز](/docs/network/specifications/prizes)) — تنتقل الأساليب الفائزة بالجوائز إلى منظمة حوكمة مجتمع اللغة المعني. ولا يمكن قانوناً نقل أسلوب يحزم محتوى لم يكن للمُرسِل الحق في تضمينه. يجب أن يمتلك المُرسِل (أو يُمنح) حقوق كل شيء مشمول في الحزمة.

ولجعل كلا الفحصين آليين بدلاً من كونهما مخصصين، يعلن كل أسلوب عن **فئة تبعية**، مشتقة من **بيان التبعيات** (dependency manifest) في `method.json`.

> **ملاحظة حول التسمية — ثلاثة محاور مستقلة.** تصف *فئة الأسلوب* (الفقرة أعلاه: `raw-llm`، `pipeline`، …) *هيكل* الأسلوب — أي عقد الواجهة الذي يقدمه. ويصف *النموذج الفكري* ([§النماذج الفكرية](#paradigms): `rule-based`، `neural-nmt`، `llm`، …) *كيفية ترجمته خوارزمياً*. وتصف *فئة التبعية* (هذا القسم) *ما يحتاجه للتشغيل والنقل*. هذه المحاور الثلاثة متعامدة: فيمكن لأسلوب `pipeline` أن يكون `rule-based` أو `hybrid`، ويمكن أن ينتمي إلى أي فئة تبعية. (تم فصل الفئة عن النموذج الفكري عمداً لأن الفئة وحدها متمحورة حول LLM — ولا يمكنها التمييز بين نظام قائم على القواعد ونظام عصبي عندما يقدم كلاهما كـ `pipeline` أو `api`.)

### فئات التبعية الخمس

| الفئة | الاسم | التعريف | قابل للتشغيل في البيئة المعزولة؟ | مؤهل للجوائز؟ |
|-------|------|-----------|-------------------|-----------------|
| **S** | قائم بذاته (Self-contained) | يتم تضمين جميع التعليمات البرمجية والبيانات والنماذج والأوزان داخل دليل الأسلوب، بموجب تراخيص تسمح بإعادة التوزيع والنقل إلى المجتمع. | ✅ نعم، كما هو | ✅ نعم |
| **O** | خارجي مفتوح (Open external) | يعتمد على مكونات برمجية مستضافة خارجياً بموجب تراخيص مفتوحة تسمح بإعادة التوزيع (بما في ذلك تراخيص الحقوق المتروكة مثل AGPL) — على سبيل المثال، FST يتم تنزيله وقت التثبيت. | ✅ نعم — يتم تثبيت المكونات البرمجية و**نسخها احتياطياً ضمن ملف الإرسال** | ✅ نعم، مع شروط توافق التراخيص: يتم الحفاظ على بنود الحقوق المتروكة (copyleft) أثناء النقل، ويحصل المجتمع على نفس الحقوق التي يمنحها الترخيص للجميع |
| **A1** | معتمد على API، قابل للاستبدال | يتطلب استنتاج LLM أثناء التشغيل، حيث يكون النموذج **إعداداً قابلاً للاستبدال** — يمكن إدخال أي نموذج يتمتع بقدرات كافية مكانه. تكمن قيمة الأسلوب في موجهاته، وبيانات تدريبه الإرشادي، وشفرته البرمجية، وليس في نموذج أي مزود بعينه. | ⚠️ فقط عبر **بوابة LLM** التي تحددها مواصفات البيئة المعزولة (🔲 مخطط له — انظر أدناه) | ⚠️ مشروط — انظر أدناه |
| **A2** | معتمد على API، غير قابل للاستبدال | يتطلب استدعاءات أثناء التشغيل لواجهة برمجة تطبيقات خارجية للبيانات أو الخدمات لا يمكن نسخها أو استبدالها — عادةً لأن المحتوى المقدم مملوك أو غير مرخص (مثل واجهة برمجة تطبيقات لقاموس لا يملك ترخيصاً عاماً). | ❌ لا — لا يمكن أن تتواجد التبعية في البيئة المعزولة دون إذن صاحب الحقوق | ❌ ليس حتى يمنح صاحب الحقوق أذونات التضمين في البيئة المعزولة **ونقل الحقوق**. يُسمح به على لوحة المتصدرين المفتوحة (قطاع التطوير) مع علامة واضحة تشير إلى وجود **"تبعية خارجية"** |
| **X** | مغلق | يحزم محتوى ليس للمُرسِل الحق في إعادة توزيعه — مجموعات بيانات غير مرخصة، ومحتوى مملوك تم استخراجه، ومكونات غير متوافقة مع التراخيص. | ❌ | ❌ غير مقبول في أي مسار. يُعد حزم المحتوى دون حقوق انتهاكاً للترخيص بغض النظر عن مكان تشغيل الأسلوب |

**الفئة الفعلية.** فئة تبعية الأسلوب هي الفئة *الأكثر تقييداً* من بين جميع تبعياته المعلنة، بالترتيب S < O < A1 < A2 < X. فقاموس واحد غير مرخص يجعل خط المعالجة الذي كان ليكون قائماً بذاته من الفئة A2 (إذا تم الوصول إليه أثناء التشغيل) أو من الفئة X (إذا تم حزمه دون حقوق).

### التمييز بين A1 وA2: القابلية للاستبدال

تعتمد معظم الأساليب على استدعاء نماذج LLM. ولا تتجاهل Network هذا الواقع — ولكنها تميز بين نوعين مختلفين تماماً من التبعية لـ API:

- **A1 (قابل للاستبدال):** توفر واجهة برمجة التطبيقات (API) استنتاجاً قياسياً لـ LLM. معرّف النموذج هو مجرد إعداد: يجب أن يعمل الأسلوب بصورة متكاملة وشاملة (end-to-end) مع أي نقطة نهاية استنتاج متوافقة، بما في ذلك النماذج مفتوحة الأوزان التي يستضيفها المجتمع. قد تختلف جودة المخرجات عبر النماذج — وتلك مخاطرة يتحملها المطور، وتكون الدرجات الرسمية مرتبطة بالنموذج المثبت المستخدم في التقييم. أما الأسلوب الذي يعتمد على **حالة من جانب المزود** (مثل ضبط دقيق مستضاف فقط لدى المزود، أو مخازن ملفات المزود، أو مساعدين خاصين بمزود محدد) فهو *غير* قابل للاستبدال: لا يمكن استبدال هذه الحالة، وبالتالي تكون التبعية من الفئة A2 ما لم يتم تضمين الأوزان أو البيانات الأساسية في ملف الإرسال.
- **A2 (غير قابل للاستبدال):** تقدم واجهة برمجة التطبيقات شيئاً فريداً — عادةً ما يكون بيانات مملوكة أو غير مرخصة. ولا توجد نقطة نهاية بديلة يمكنها توفير ذلك، كما لا يمكن نسخ المحتوى احتياطياً في البيئة المعزولة دون إذن صاحب الحقوق. ويعمل هذا الأسلوب على لوحة المتصدرين المفتوحة (مع وضع علامة تنبيهية)، ولكنه لا يمكنه تحقيق درجات رسمية في البيئة المعزولة أو التأهل للجوائز حتى تتوفر الأذونات اللازمة.

**ما ينقله نقل جائزة A1 فعلياً.** لا يتسلم المجتمع النموذج نفسه — فلا أحد يستطيع نقل أوزان نماذج Anthropic أو Google أو OpenAI. يغطي النقل الوصفة الكاملة *المحيطة* بالنموذج: جميع الموجهات، وبيانات التدريب الإرشادي (coaching data)، ورمز خط المعالجة، ومنطق إعادة المحاولة، والإعدادات، ومتطلبات النموذج الموثقة. ولأن النموذج قابل للاستبدال بطبيعته التصميمية، يستطيع المجتمع توجيه الأسلوب المنقول إلى أي مزود يختاره — أو إلى نموذج مفتوح الأوزان على أجهزتهم الخاصة — دون الحاجة لتدخل المطور. فالوصفة مملوكة؛ بينما المحرك مستأجر وقابل للاستبدال.

### بيان التبعيات (`method.json`)

يعلن كل أسلوب عن تبعياته في بيان `method.json`. يسجل كل مدخل ماهية المكون البرمجي (artifact)، ومصدره، والترخيص الذي يغطيه، وكيفية وصول الأسلوب إليه:

```json
{
  "name": "FST-Gated Coached Translation v8",
  "method_id": "fst-gated-v8",
  "class": "pipeline",
  "paradigm": "hybrid",
  "entry_point": "pipeline:PipelineMethod",
  "supported_pairs": ["eng>crk"],
  "dependency_class": "A2",
  "dependencies": [
    {
      "id": "giellalt-lang-crk-fst",
      "kind": "software",
      "license": "AGPL-3.0-or-later",
      "access": "mirrored",
      "source": "https://github.com/giellalt/lang-crk",
      "pin": "sha256:3f1a…",
      "redistributable": true,
      "transferable": true
    },
    {
      "id": "llm-inference",
      "kind": "model",
      "license": "proprietary",
      "access": "gateway",
      "source": "openrouter:google/gemini-2.5-flash",
      "substitutable": true,
      "redistributable": false,
      "transferable": false,
      "notes": "Any compatible chat-completions endpoint works; the model slug is configuration."
    },
    {
      "id": "crk-dictionary-api",
      "kind": "service",
      "license": "none",
      "access": "external-api",
      "source": "https://itwewina.altlab.app/",
      "redistributable": false,
      "transferable": false,
      "notes": "Dictionary content has no public license; runtime lookups only. Class A2 until the rights holders grant permission."
    }
  ]
}
```

| الحقل | مطلوب | الوصف |
|-------|----------|-------------|
| `id` | ✅ | معرّف ثابت للتبعية |
| `kind` | ✅ | `data`، أو `model`، أو `software`، أو `service` |
| `license` | ✅ | معرّف SPDX، أو `proprietary`، أو `none`. ويعني `none` عدم وجود ترخيص عام — وتُعامل على أنها جميع الحقوق محفوظة |
| `access` | ✅ | `bundled` (مضمن داخل دليل الأسلوب)، أو `mirrored` (يتم جلبه عند التثبيت، وتثبيته، ودمجه في ملف الإرسال)، أو `gateway` (استنتاج LLM أثناء التشغيل عبر بوابة التقييم)، أو `external-api` (أي استدعاء شبكي آخر أثناء التشغيل) |
| `source` | ✅ | رابط URL قياسي أو معرّف `provider:slug` |
| `pin` | لـ `mirrored` | الإصدار، أو التثبيت (commit)، أو تجزئة المحتوى التي تثبت المكون البرمجي الدقيق |
| `substitutable` | لـ `gateway`/`external-api` | ما إذا كان بإمكان أي نقطة نهاية متوافقة تقديم هذه التبعية |
| `redistributable` | ✅ | ما إذا كان الترخيص يسمح بإعادة توزيع المكون البرمجي |
| `transferable` | ✅ | ما إذا كان المكون البرمجي (أو حقوقه) يمكن نقله إلى المجتمع بموجب شروط نقل الجوائز |
| `notes` | ❌ | سياق حر |

**اشتقاق الفئة.** تسهم كل تبعية بفئة؛ وتكون `dependency_class` للأسلوب هي الفئة الأكثر تقييداً:

| ملف تعريف التبعية | المساهمة في الفئة |
|--------------------|-------------|
| `bundled` + ترخيص يسمح بإعادة التوزيع والنقل | S |
| `mirrored` + ترخيص مفتوح يسمح بإعادة التوزيع (بما في ذلك الحقوق المتروكة) | O |
| `gateway` + `substitutable: true` (استنتاج LLM) | A1 |
| `external-api`، أو `gateway` مع `substitutable: false` | A2 |
| `bundled` + `license: none` أو ترخيص غير متوافق مع إعادة التوزيع | X |

يجب أن تتطابق `dependency_class` المعلنة مع الفئة التي تشتقها بيئة التقييم من البيان. ويُعد عدم التطابق خطأً في التحقق من الصحة.

يعلن الأسلوب الذي **لا يحتوي على** تبعيات خارجية عن `"dependency_class": "S"` و`"dependencies": []`. تُعد المصفوفة الفارغة تصريحاً مؤكداً، ويتم تدقيقها كأي تصريح آخر.

### كيفية التحقق من الصلاحية

ثلاث طبقات، من الأقل تكلفة إلى الأكثر موثوقية:

1. **تدقيق البيان.** تشتق بيئة التقييم الفئة الفعلية من البيان وترفض حالات عدم التطابق. يتحقق المراجعون من كل تبعية معلنة مقابل ترخيصها ومصدرها المحددين — وتفشل التبعية المعلنة كـ `redistributable: true` في المراجعة إذا كان ترخيص المصدر ينص على خلاف ذلك.
2. **التحليل الساكن.** يتم فحص الكود البرمجي المقدم بحثاً عن استدعاءات الشبكة، وعمليات التنزيل الديناميكية، والوصول إلى نظام الملفات التي لم تُذكر في البيان. ويُعد العثور على تبعية *غير معلنة* أثناء المراجعة سبباً للرفض بغض النظر عن الفئة التي كانت ستنتمي إليها — يجب أن يكون البيان مكتملاً وليس دقيقاً فحسب.
3. **سياسة شبكة البيئة المعزولة.** تتطلب مواصفات البيئة المعزولة **حظر حركة البيانات الصادرة افتراضياً** (default-deny egress): لا تحصل حاويات الأساليب على أي وصول للشبكة ما لم يتم إدراج المسار صراحة في القائمة المسموح بها. والمسار الصادر الوحيد الذي تحدده المواصفات هو **بوابة LLM** (LLM gateway) — وهي وكيل استنتاج (inference proxy) تديره البنية التحتية للتقييم، ويقتصر على قائمة مسموح بها صريحة من النماذج المثبتة، مع تسجيل كل طلب واستجابة للتدقيق بعد التشغيل. وأي شيء غير مدرج في القائمة المسموح بها يفشل عند طبقة الشبكة، وليس عند طبقة السياسات. راجع [مواصفات التقييم المعياري §8.6](/docs/network/specifications/benchmark) للاطلاع على سياسة الشبكة وتصميم البوابة.

> **بيئتان معزولتان مختلفتان — إحداهما مخطط لها والأخرى نشطة.** اقرأ هذا بعناية، لأن كلمة "بيئة معزولة" (sandbox) تشمل أمرين متميزين:
>
> - 🔲 **مخطط لها: البيئة المعزولة للمنصة وبوابتها الخاصة بـ LLM.** البيئة التي تديرها البنية التحتية للتقييم والموضحة في هذا القسم — وهي البيئة التي ستتيح بوابتها الخاصة بـ LLM لأساليب الفئة A1 إنتاج درجات رسمية للمعيار الذهبي — محددة في المواصفات ولكن لم يتم بناؤها بعد. وإلى أن يتم ذلك، تكون أساليب الفئة A1 مؤهلة للجوائز *من حيث المبدأ* ولكنها لا تستطيع بعد إنتاج درجات رسمية للمعيار الذهبي.
> - ✅ **نشطة: مسار تنفيذ الأساليب في عقدة المنظم.** تقوم عقدة التسجيل الخاصة بمنظم المسابقة بالفعل بتنفيذ حزم الأساليب المقترحة داخل حاوية معزولة عن الشبكة (`mt-eval node run-method`): يتم بناؤها وتشغيلها باستخدام `--network=none`، مع جذر للقراءة فقط، وتبعيات مدمجة — مما يقصرها على الأساليب التي لا تحتاج إلى شبكة أثناء التشغيل (الفئة S/O بطبيعتها التصميمية). ويمكن تشغيلها على جهاز معزول تماماً عن الهواء (airgap) مع نقل حزم النتائج الموقعة فقط عبر وسائط قابلة للإزالة. راجع [إدارة مسابقة سيادية](/docs/network/sovereignty/run-a-sovereign-contest) للاطلاع على المسار الشامل من البداية إلى النهاية.
>
> يصف هذا القسم ما تتطلبه مواصفات المنصة، وليس ما يعمل حالياً على المنصة.

### العرض على لوحة المتصدرين

- تعرض لوحة المتصدرين فئة تبعية كل أسلوب بجانب شارة فئة الأسلوب الخاصة به.
- تحمل أساليب الفئة A2 على لوحة المتصدرين المفتوحة شارة واضحة تشير إلى وجود **"تبعية خارجية"** (external dependency): إذ تعتمد درجاتها على خدمة لطرف ثالث قد تتغير أو تختفي، وهي غير مؤهلة للجوائز حالياً.
- لا يتم إدراج أساليب الفئة X.

## بيئة التقييم: بروتوكول TranslationMethod {#eval-harness-translationmethod-protocol}

تستخدم بيئة التقييم نظام الكتابة الهيكلية في Python (`Protocol`) للملحقات البرمجية. وتعمل أي فئة تحتوي على الأعضاء المناسبين — دون الحاجة إلى وراثة. يتكون البروتوكول من ثلاثة أعضاء؛ ويلزم فقط `translate` للملحق البرمجي الذي يتم تحميله باستخدام `--method path/to/dir`:

1. **`async translate(entries, config)`** (`-> list[dict]`) — **مطلوب.** الترجمة نفسها: دفعة من المدخلات كمدخل، وقاموس نتائج (result dict) واحد لكل مدخل كمخرج.
2. **`name`** (`str`) — اختياري. اسم الأسلوب بصيغة قابلة للقراءة البشرية، يُستخدم في السجلات. بدونه تستخدم بيئة التقييم `name` الخاص بـ `method.json`.
3. **`method_card()`** (`-> dict | None`) — اختياري. بيانات وصفية للأسلوب لأغراض التتبع والأصل، مضمنة في سجل التشغيل وبطاقة التشغيل المنشورة. وبدونها تبني بيئة التقييم البطاقة من `method.json`: وهي `method_id`، و`name`، و`class`، و`paradigm`، و`description`، و`author`، و`version`، و`tools_used`، و`open_source`، و`prompt_published`، و`supported_pairs`، و`dependency_class` حيثما أُعلن عنها، مع تعيين `method_id` افتراضياً إلى اسم دليل الملحق البرمجي، و`class` إلى `custom-plugin` و`paradigm` إلى `unknown`. تطبع عملية التشغيل الأعضاء التي أخذتها من `method.json`. حدد `method_card()` (أو أرجع `None` منه) لتجاوز ذلك.

عندما تقوم بيئة التقييم بتحميل ملحق برمجي عبر `--method path/to/dir`، فإنها تتحقق من كل هذا عند التحميل وتبلغ عن كل مشكلة في رسالة خطأ واحدة: فقدان `translate`، أو `name` ليس سلسلة نصية غير فارغة، أو `method_card` غير قابل للاستدعاء أو لا يرجع قاموساً (dict) أو `None`، أو بطاقة مبنية من `method.json` ليست بطاقة صالحة (على سبيل المثال `method_id` ليس بصيغة kebab-case)، أو بطاقة `class` أو `paradigm` خارج المفردات القياسية.

يتم نشر تشغيل الملحق البرمجي مع فئة أسلوبه كـ `condition` خاصة به (على سبيل المثال `custom-plugin` أو `pipeline`)، وليس شروط موجه LLM `naive`/`coached`، والتي لا تنطبق أبداً على أسلوب يترجم بمفرده.

**النموذج الذي يُعطى للملحق البرمجي.** يتلقى `translate()` قيمة `RunConfig` الخاصة بالتشغيل. وبالنسبة لتشغيل الملحق البرمجي، فإن `config.model` هي `method_id` الخاصة بالملحق، وهي الهوية التي يُنشر التشغيل بموجبها. النموذج الذي تمرره إلى الملحق البرمجي عبر `-m/--model` هو `config.method_model` (سلسلة نصية فارغة في حال عدم تقديم أي نموذج)، بأي تسمية يستخدمها الملحق، تماماً كما قُدمت: لا تتحقق بيئة التقييم من النموذج مقابل سجل النماذج، ولا تستدعيه أبداً، ولا تعيد كتابته مطلقاً. وتسجل بطاقة التشغيل ذلك (`method_plugin.model_given`، و`method_config.model`) إلى جانب `version` و`dependency_class` و`dependencies` المعلنة للملحق وتجزئة (hash) لملفاته، ويُعد النموذج والتبعيات جزءاً من [بصمة](/docs/network/specifications/benchmark#38-fingerprint) التشغيل، ولذلك فإن تشغيل الملحق نفسه على نموذجين مختلفين يُعد تجربتين منفصلتين.

```python
class MyMethod:
    name = "My Pipeline v1"  # optional — defaults to method.json's "name"

    def method_card(self) -> dict | None:
        # optional — defaults to a card built from method.json
        return {
            "method_id": "my-pipeline-v1",
            "name": self.name,
            "class": "pipeline",
        }

    async def translate(self, entries: list[dict], config: RunConfig) -> list[dict]:
        # The model given with -m/--model ("" when none was given).
        model = config.method_model
        results = []
        for entry in entries:
            translation = await self.do_translation(entry["source"], model)
            results.append({
                "id": entry["id"],
                "predicted": translation,
                "latency_s": 0.5,
                "usage": {"prompt_tokens": 0, "completion_tokens": 0},
                "error": None,
                "tool_calls": [],
                "tool_call_count": 0,
                "metadata": {},
            })
        return results
```

يحتاج دليل الملحق البرمجي إلى بيان `method.json` يحتوي على الأقل على `name` و`entry_point` (`"module_name:ClassName"` — حيث يتم تحميل الوحدة النمطية من دليل الملحق وإنشاء مثيل للفئة). وإذا أعلنت بطاقة الأسلوب المُرجعة عن `class` أو `paradigm`، فيجب أن تستخدم المفردات القياسية المذكورة أعلاه — فالبطاقة التي لا تلتزم بالتصنيف المحدد تفشل في التحقق من الصحة وقت التحميل بدلاً من أن تسقط بصمت من عوامل تصفية لوحة المتصدرين.

للاطلاع على مثال عملي كامل — بناء ملحق وتشغيله وإرساله من البداية إلى النهاية — راجع [إرسال أسلوب](/docs/network/getting-started/submit-a-method) و[دليل خط المعالجة المقترن ببوابة FST](/docs/network/tutorials/fst-gated-pipeline).

## champollion: إعداد methodPlugin

في champollion، يتم تسجيل الأساليب لكل زوج لغوي في `champollion.config.json`:

```json
{
  "version": 3,
  "pairs": {
    "en:fr": {
      "methodPlugin": "french-formal-v1"
    }
  }
}
```

راجع [مواصفات الملحق البرمجي](https://champollion.dev/docs/reference/plugin-spec) للاطلاع على الواجهة من جانب champollion.

## التكامل مع لوحة المتصدرين

عند إرفاق بطاقة أسلوب بعملية تشغيل (عبر `--method-card`)، يتم تضمينها في بطاقة التشغيل وعرضها على لوحة المتصدرين:

```bash
# Run with method card attached
mt-eval run \
  --method path/to/my-method \
  --corpus eval-amh-fra-globalvoices-test-v1 \
  --method-card method_card.json

# Publish to the leaderboard
mt-eval publish eval/logs/harness/your-run-card.json
```

إذا لم يتم توفير `--method-card`، فإن `mt-eval publish` يطلق معالجاً تفاعلياً يرشدك خلال خطوات وصف أسلوبك.

تعرض لوحة المتصدرين ما يلي:
- **شارة الفئة** — مؤشر مرئي (مثل "pipeline"، و"coached-llm")
- **النموذج الفكري** — النموذج الفكري الخوارزمي (مثل "rule-based"، و"neural-nmt"، و"llm"، و"hybrid")، وهو عمود قابل للتصفية (راجع [النماذج الفكرية](#paradigms))
- **فئة التبعية** — S/O/A1/A2 (راجع [صلاحية الأسلوب وفئات التبعية](#method-validity-and-dependency-classes))؛ وتحمل أساليب A2 علامة "تبعية خارجية" (external dependency)
- **اسم الأسلوب** — مأخوذ من بطاقة الأسلوب
- **الأدوات المستخدمة** — مسرودة من بطاقة الأسلوب
- **مؤشر المصدر المفتوح**

عندما لا تكون هناك بطاقة أسلوب مرفقة، تعرض لوحة المتصدرين الإعدادات الأصلية الخاصة ببيئة التقييم (النموذج، إصدار الموجه، درجة الحرارة، الأدوات المُمكّنة).

يطبع `mt-eval publish --dry-run` هذه الحقول كما ستحملها البطاقة — الأسلوب وفئته، والنموذج الفكري، وفئة التبعية، والأدوات، وعلامة المصدر المفتوح، وتجزئة الكود الخاصة بتشغيل الملحق وإصداره والنموذج الذي تم تمريره إليه — قبل إرسال أي شيء. وتُحدد تكلفة تشغيل الملحق وفقاً لشروط فئة التبعية التي يعلن عنها `method.json` الخاص به. فالملحق من الفئة S أو O لا يستدعي أي واجهة برمجة تطبيقات (API): فعندما لا تذكر قائمة `dependencies` الخاصة به أي وصول عبر `gateway` أو `external-api` (بما في ذلك `[]` الخاص بملحق S)، فإن الخطة وملخص التشغيل وبطاقة التشغيل و`compare` ومعاينة النشر تشير جميعها إلى **تكلفة API تبلغ 0 دولار (يعمل على هذا الجهاز)**، ويسجل التقرير `cost_unknown: false` و`api_cost_usd: 0`. ويعتمد ذلك على الإقرار الصادر؛ إذ تشغل بيئة التقييم الملحق في عمليتها الخاصة ولكنها لا تراقب استخدامه للشبكة، لذا فإن المدونة المحلية فقط لا تزال بحاجة إلى إقرار المستخدم قبل أن يتمكن الملحق من قراءتها. أما الملحق من الفئة A1 أو A2، أو الملحق الذي لا يعلن عن أي فئة، فيجري مكالماته الخاصة ويدفع تكلفتها، وهي تكلفة لا تستطيع بيئة التقييم تسعيرها: فتكون تكلفته **غير معروفة**، وليست 0 دولار أبداً.

:::danger[لا تدرب على بيانات التقييم]
الأساليب التي تضمنت عملية تطويرها التعرض لمجموعة بيانات التقييم — كبيانات تدريب، أو أمثلة للتعلم من أمثلة قليلة (few-shot examples)، أو مدخلات قواميس، أو مواد لضبط الموجهات (prompt tuning) — سيتم **استبعادها** من لوحة المتصدرين. راجع [تقييم الترجمة الآلية](/docs/network/leaderboard/rules) لمعرفة ما يميز الأسلوب الجيد عن الأسلوب السيئ.
:::
