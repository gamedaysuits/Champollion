# การแปลเนื้อหา (Markdown)

Champollion แปลไฟล์ Markdown และ MDX ทั้งฟิลด์ front matter และเนื้อหาหลัก บล็อกโค้ด ชอร์ตโค้ด และองค์ประกอบเชิงโครงสร้างอื่นๆ จะได้รับการปกป้องจากการแปล

ไฟล์เหล่านี้จะอยู่ใน**ไดเรกทอรีเนื้อหา** (`contentDir`) ซึ่งสามารถเป็นโฟลเดอร์ Markdown ใดๆ ก็ได้ เช่น `content/` ของเว็บไซต์ Hugo หรือโฟลเดอร์จดหมายข่าวภายในแอป Next.js ส่วนเว็บไซต์ Docusaurus (ไซต์ที่มี `docusaurus.config.js`) จะแตกต่างออกไป โดย `docs/` และ `blog/` จะได้รับการแปลไปยังโฟลเดอร์ `i18n/<locale>/` โดยไม่ต้องมี `contentDir` ดูที่ [การผสานการทำงานกับเฟรมเวิร์ก](/docs/guides/framework-integration)

## การตั้งค่า

กำหนดค่า `contentDir` ในไฟล์การกำหนดค่าของคุณ หรือส่ง `--content-dir` ผ่านบรรทัดคำสั่ง:

```json title="champollion.config.json"
{
  "version": 3,
  "inputLocale": "en",
  "localesDir": "./messages",
  "contentDir": "./newsletters"
}
```

```bash
npx champollion sync                              # translates string files and content files
npx champollion sync --content-dir ./newsletters  # same, folder given on the command line
```

เมื่อเริ่มต้นการทำงาน คำสั่ง sync จะระบุชื่อโฟลเดอร์และแจ้งว่าไฟล์แปลจะถูกบันทึกไว้ที่ใด:

```
[INFO] Content directory: newsletters — a folder of Markdown/MDX files (no Hugo site found); each translation is written beside its source as <name>.<locale>.md
```

สำหรับเว็บไซต์ Hugo ระบบจะระบุหลักฐานที่ตรวจพบด้วย เช่น `Detected framework: Hugo (hugo.toml)` โดยระบบจะถือว่าพบ Hugo เมื่อมีไฟล์ `hugo.toml`/`.yaml`/`.yml`/`.json`, โฟลเดอร์ `config/_default/` ของ Hugo, `config.toml` หรือ `config.yaml` ที่มีการตั้งค่าเฉพาะของ Hugo เช่น `baseURL`, โฟลเดอร์ `archetypes/` หรือโฟลเดอร์ `layouts/` สำหรับเทมเพลตของ Hugo ไม่ว่าจะเป็น Hugo หรือไม่ ไฟล์ต่างๆ จะได้รับการแปลและตั้งชื่อในรูปแบบเดียวกัน

## ตำแหน่งจัดเก็บไฟล์แปล

การแปลแต่ละรายการจะถูกบันทึกไว้**ข้างๆ ไฟล์ต้นฉบับ** โดยจะเพิ่มรหัสภาษาเป้าหมายไว้ก่อนนามสกุลไฟล์ ซึ่งเป็นแบบแผนการแปลตามชื่อไฟล์ (translation-by-filename) ของ Hugo:

```
newsletters/2026-10.md      → newsletters/2026-10.crk.md
newsletters/2026-10.md      → newsletters/2026-10.fr.md
posts/launch.mdx            → posts/launch.crk.mdx       (.mdx stays .mdx)
posts/launch.en.md          → posts/launch.crk.md        (the source-language suffix is dropped)
```

ระบบจะค้นหาในโฟลเดอร์ย่อยด้วย และไฟล์แปลแต่ละไฟล์จะยังคงอยู่ในโฟลเดอร์ของไฟล์ต้นฉบับ แอปของคุณจะเลือกไฟล์สำหรับแต่ละภาษาตามชื่อดังกล่าว เช่น หน้าของ Next.js จะอ่าน `newsletters/2026-10.crk.md` สำหรับภาษา Plains Cree

**ไฟล์ใดบ้างที่นับเป็นต้นฉบับ** ทุกไฟล์ `.md` และ `.mdx` ในโฟลเดอร์ถือเป็นต้นฉบับ เว้นแต่ชื่อไฟล์จะลงท้ายด้วย `.<code>.md` (หรือ `.mdx`) และ `<code>` มีรูปแบบเหมือนรหัสภาษา รหัสภาษาในที่นี้คือตัวอักษรพิมพ์เล็ก 2 หรือ 3 ตัว ซึ่งอาจตามด้วยสคริปต์ เช่น `-Hant` และ/หรือภูมิภาค เช่น `-BR` หรือ `-419` ไฟล์เหล่านั้นจะถือว่าเป็นไฟล์แปลและถูกข้ามไป ส่วนไฟล์ที่มีคำลงท้ายเป็นภาษาต้นทาง (`launch.en.md`) ยังคงนับเป็นไฟล์ต้นฉบับ ข้อควรระวัง: ไฟล์ต้นฉบับที่ตั้งชื่อเช่น `guide.faq.md` จะลงท้ายด้วยตัวอักษร 2 ถึง 3 ตัวเช่นกัน จึงถูกมองว่าเป็นการแปลเป็นภาษา "faq" และจะไม่ได้รับการแปล ให้เปลี่ยนชื่อไฟล์ใหม่ เช่น เป็น `guide-faq.md`

## สิ่งที่จะถูกแปล

### Front Matter

รองรับทั้ง YAML (`---`) และ TOML (`+++`) delimiters โดยค่าเริ่มต้น ฟิลด์เหล่านี้จะถูกแปล:

- `title`
- `description`
- `summary`
- `subtitle`
- `caption`
- `linkTitle`
- `sidebar_label`

ฟิลด์อื่นๆ ทั้งหมด (`date`, `draft`, `tags`, `weight`, `slug` ฯลฯ) จะถูกคัดลอกจากต้นฉบับตามที่เป็นอยู่ คุณสามารถเปลี่ยนรายการนี้ได้ด้วย `translatableFields` ในไฟล์การกำหนดค่าของคุณ

### เนื้อหาในส่วน Body

ตามค่าเริ่มต้น เนื้อหาหลักจะถูกแบ่งออกเป็นย่อหน้าและบล็อกระดับบนสุดอื่นๆ และจะแปลทีละบล็อก องค์ประกอบเชิงโครงสร้างจะได้รับการป้องกันด้วยตัวแทนชั่วคราวก่อนการแปลและคืนค่ากลับคืนหลังแปลเสร็จ หากใช้ `contentSegmentation: "page"` เนื้อหาจะได้รับการแปลรวมเป็นชิ้นเดียว

## การป้องกัน Block

องค์ประกอบเหล่านี้จะผ่านกระบวนการแปลโดยไม่ถูกแก้ไข:

| องค์ประกอบ | ตัวอย่าง | การป้องกัน |
|---------|---------|-----------|
| Code blocks | ``````` ```js ... ``` ``````` | ป้องกันทั้ง block |
| Inline code | `` `variable` `` | ถูกป้องกัน |
| Hugo shortcodes | `{{< figure >}}`, `{{% note %}}` | ป้องกันทั้ง block |
| Raw HTML | `<div>`, `<table>` | ถูกป้องกัน |
| Links (URLs) | `[text](https://...)` | URL ถูกเก็บไว้, ข้อความถูกแปล |
| Interpolation | `{{ .Count }}` | ถูกป้องกัน |

## เมื่อไฟล์ได้รับการแปลใหม่อีกครั้ง

Sync จะบันทึกลายนิ้วมือ (SHA-256) ของแต่ละไฟล์ต้นฉบับไว้ใน `.champollion-content.lock` ให้ commit ไฟล์ดังกล่าวร่วมกับไฟล์แปลของคุณ

- **ต้นฉบับไม่เปลี่ยนแปลง:** จะไม่มีการแตะต้องไฟล์แปล
- **ต้นฉบับมีการเปลี่ยนแปลง:** ไฟล์จะได้รับการอัปเดต โดยย่อหน้าที่ภาษาอังกฤษไม่เปลี่ยนแปลงจะถูกดึงมาจาก [Translation Memory](/docs/concepts/translation-memory) โดยไม่มีค่าใช้จ่าย ดังนั้นคุณจึงจ่ายเฉพาะส่วนย่อหน้าที่เปลี่ยนแปลงเท่านั้น
- **ไฟล์แปลที่ไม่มีรายการใน lock** (ไฟล์ที่คุณเขียนขึ้นมาเอง) จะคงไว้ตามเดิมและบันทึกว่าเป็นของคุณ ข้อยกเว้นคือไฟล์ที่ยังคงมีมาร์กเกอร์ `[EN] ` ซึ่งเขียนโดย CLI เวอร์ชันเก่ากว่า 0.5.0 จะได้รับการแปลใหม่อีกครั้ง
- **บล็อกที่ quality gate ปฏิเสธ รวมถึงเมื่อส่งคำขอซ้ำพร้อมเหตุผลแล้ว** จะยังคงเก็บข้อความต้นฉบับไว้ โดยไม่มีมาร์กเกอร์บนหน้า รายการ lock ของหน้านั้นจะระบุว่า `pending:<hash>` และการปฏิเสธจะถูกบันทึกไว้ใน `.champollion-content.lock` การ sync ในภายหลังจะไม่ส่งบล็อกนั้นไปยังโมเดลเดิมอีก จึงไม่เกิดค่าใช้จ่ายซ้ำ `status` และ `verify` จะแสดงรายชื่อหน้านั้น คุณสามารถส่งคำขอแปลใหม่อีกครั้งด้วย `--redo files:<page>`, เพิ่มวิธี `fallback` หรือเขียนย่อหน้านั้นด้วยตัวเอง (ระบบจะเก็บรักษาไว้) ฟิลด์ front-matter ที่ถูกปฏิเสธจะเก็บข้อความต้นฉบับไว้ในลักษณะเดียวกัน และส่วนที่เหลือของหน้าจะได้รับการเขียนตามปกติ ดูที่ [บล็อก Markdown และฟิลด์ front-matter ที่ถูกปฏิเสธ](/docs/concepts/quality-gate#refused-markdown-blocks-and-front-matter-fields)

หากต้องการแปลไฟล์ใหม่อีกครั้งโดยเจตนา ให้ระบุชื่อไฟล์ โดยเส้นทางพาธจะเป็นแบบเดียวกับที่ sync แสดงผล ซึ่งสัมพันธ์กับไดเรกทอรีเนื้อหา:

```bash
npx champollion sync --redo files:2026-10.md          # rebuild from the cache (free for unchanged text)
npx champollion sync --redo files:2026-10.md --fresh  # translate it again from scratch (paid again)
```

## การตรวจทานและแก้ไขคำแปล {#reviewing-and-editing-translations}

ผู้ตรวจทานสามารถแก้ไข Markdown ที่แปลแล้วได้โดยตรงในไฟล์แปล และ Champollion จะเก็บรักษาการแก้ไขเหล่านั้นไว้เมื่อต้นฉบับมีการเปลี่ยนแปลงในภายหลัง

1. รัน `champollion sync` แล้ว commit ไฟล์แปลร่วมกับ `.champollion-content.lock`
2. ผู้ตรวจทานเปิดไฟล์แปล เช่น `newsletters/2026-10.crk.md` แล้วทำการแก้ไข โดยสามารถแก้ไขย่อหน้าใดก็ได้ หรือฟิลด์ front-matter ที่แปลแล้ว เช่น `title` หรือ `description`
3. ผู้ตรวจทาน commit ไฟล์ โดยไม่จำเป็นต้องใช้คำสั่งใดๆ เพื่อ "ยอมรับ" การแก้ไข

สิ่งที่จะเกิดขึ้นกับการแก้ไขในการรัน `champollion sync` ครั้งถัดไป:

| สถานการณ์ | สิ่งที่ sync ทำ |
|---|---|
| ต้นฉบับไม่เปลี่ยนแปลง | ไม่ทำอะไร ไฟล์แปลจะคงอยู่ตามที่ผู้ตรวจทานแก้ไขไว้ทุกประการ |
| ต้นฉบับเปลี่ยนแปลงในย่อหน้า**อื่น** | ย่อหน้าและฟิลด์ของผู้ตรวจทานจะ**ถูกเก็บรักษาไว้คำต่อคำ** และย่อหน้าที่เปลี่ยนแปลงจะได้รับการแปล การรันจะแจ้งเตือนเช่น `kept the edits made by hand to 1 paragraph(s) of 2026-10.crk.md` ข้อความของผู้ตรวจทานจะยังคงเป็นของผู้ตรวจทานในทุกการ sync ถัดไป |
| ย่อหน้าต้นฉบับที่ผู้ตรวจทานแก้ไข**มีการเปลี่ยนแปลงด้วย** | ย่อหน้านั้นจะได้รับการแปลใหม่อีกครั้ง เนื่องจากเวอร์ชันของผู้ตรวจทานแปลภาษาอังกฤษที่ไม่มีอยู่อีกต่อไปแล้ว การรันจะแสดงคำเตือนพร้อมข้อความเดิมของผู้ตรวจทาน เพื่อให้สามารถนำกลับมาปรับใช้ใหม่ได้หากยังเหมาะสม |
| ผู้ตรวจทานมีการเพิ่ม ลบ หรือรวมย่อหน้า หรือคู่นั้นใช้ `contentSegmentation: "page"` | การแก้ไขไม่สามารถจับคู่แบบย่อหน้าต่อย่อหน้าได้ เมื่อต้นฉบับเปลี่ยนแปลง ไฟล์จะ**ถูกปล่อยไว้ตามเดิมทุกประการ** และการ sync ทุกครั้งจะแจ้งเตือนและระบุชื่อไฟล์นี้จนกว่าจะได้รับการแก้ไข คุณสามารถอัปเดตด้วยตนเอง (การ sync ถัดไปจะถือว่าไฟล์ที่แก้ไขแล้วเป็นเวอร์ชันล่าสุด) หรือแทนที่ด้วยการแปลด้วยเครื่องโดยใช้ `--redo files:<path>` |

การแก้ไขบล็อกโค้ด ช่องว่างระหว่างย่อหน้า และฟิลด์ front-matter ที่ไม่ได้แปล (`date`, `tags` เป็นต้น) จะไม่ถูกเก็บรักษาไว้เมื่อมีการเขียนไฟล์ใหม่ ส่วนเหล่านี้จะมาจากต้นฉบับเสมอ

**การแทนที่การแก้ไขโดยเจตนา** การแก้ไขจะถูกแทนที่ก็ต่อเมื่อคุณระบุชื่อไฟล์เท่านั้น โดย `--redo files:2026-10.md` จะนำการแปลด้วยเครื่องที่แคชไว้กลับมา ส่วน `--redo files:2026-10.md --fresh` (หรือ `--retranslate 2026-10.md`) จะแปลใหม่อีกครั้งตั้งแต่ต้น การรันที่ประมวลผลเนื้อหาทั้งหมดใหม่โดยไม่ระบุชื่อไฟล์ (`--redo content`, `--force-content`) จะยังคงเก็บรักษาการแก้ไขไว้

**ระบบรับรู้การแก้ไขได้อย่างไร** ทุกครั้งที่ sync เขียนไฟล์แปล ระบบจะบันทึกลายนิ้วมือสั้นๆ ของทุกย่อหน้าที่เขียนลงใน `.champollion-content.lock` ด้วย ย่อหน้าบนดิสก์ที่ไม่ตรงกันอีกต่อไปแสดงว่าได้รับการแก้ไขโดยมนุษย์ หากไฟล์ lock สูญหาย จะไม่สามารถรับรู้การแก้ไขได้ ดังนั้นโปรดเก็บไฟล์นี้ไว้ในระบบควบคุมเวอร์ชัน ไฟล์แปลที่เขียนโดย Champollion เวอร์ชันเก่าจะถูกบันทึกในการ sync ครั้งถัดไป หากการแก้ไขของคุณแตกต่างจากสิ่งที่อยู่ใน Translation Memory ระบบจะรับรู้ว่าสิ่งนั้นเป็นการแก้ไขของคุณ

ข้อความของผู้ตรวจทานจะไม่ถูกบันทึกไว้ใน Translation Memory ในฐานะผลลัพธ์จากเครื่องจักรอย่างเด็ดขาด

:::note[XLIFF รองรับเฉพาะไฟล์ข้อความแบบสตริงเท่านั้น]
`champollion xliff export` จะส่ง**ไฟล์สตริง**ของแอปคุณ (คีย์และค่า) ไปยังเครื่องมือ CAT ของนักแปล ดูที่ [การทำงานร่วมกับนักแปลมืออาชีพ](/docs/guides/professional-translators) ในปัจจุบันยังไม่มีการส่งออก XLIFF สำหรับเนื้อหา Markdown ดังนั้น Markdown ที่แปลแล้วจึงต้องตรวจทานในไฟล์โดยตรงตามที่อธิบายไว้ข้างต้น
:::

## วิธีการที่ใช้ได้เฉพาะกับ Markdown

:::warning[Google Translate และ Markdown]
Google Translate **ไม่รู้จัก**บล็อกโค้ด, ชอร์ตโค้ด หรือตัวแปรแทรก (interpolation variables) ซึ่งจะทำให้เนื้อหา Markdown ที่มีโครงสร้างเสียหาย ให้ใช้วิธีการแบบ LLM (`llm` หรือ `llm-coached`) สำหรับการแปลเนื้อหา เนื่องจากวิธีการเหล่านี้จะปกป้ององค์ประกอบเชิงโครงสร้างไว้อย่างชัดเจน
:::

เมื่อการแปลเนื้อหาถอยกลับจาก Google Translate ไปใช้วิธี LLM champollion จะบันทึกคำเตือนพร้อมอธิบายสาเหตุ
