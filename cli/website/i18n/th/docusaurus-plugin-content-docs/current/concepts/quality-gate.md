# Quality Gate

ทุกการแปลจะผ่านการตรวจสอบแบบ deterministic ก่อนที่จะถูกเขียนลงดิสก์ Quality gate จะตรวจจับความผิดพลาดที่พบบ่อยในการแปลด้วยเครื่อง — ไม่มี silent fallback ไม่มีข้อมูลที่ไม่ถูกต้องถูกเขียนลงไฟล์ locale ของคุณ

## การตรวจสอบ

| การตรวจสอบ | สิ่งที่ตรวจจับได้ | ป้ายกำกับ Gate |
|---|---|---|
| **ค่าว่าง/เว้นวรรคล้วน** | โมเดลส่งคืนสตริงว่างหรือช่องว่าง | `[GATE] empty` |
| **การสะท้อนข้อความต้นฉบับ (Source echo)** | โมเดลส่งคืนข้อความภาษาอังกฤษต้นฉบับ — ไม่ว่าจะส่งคืนมาตรงๆ หรือแปลงรูปเล็กน้อย (การเติมเครื่องหมายกำกับเสียง, ตัวพิมพ์เล็ก-ใหญ่, ตัวอักษรแบบเต็มความกว้าง (fullwidth)), ไม่ว่าจะเป็นทั้งข้อความหรือในรูปพหูพจน์รูปแบบใดรูปแบบหนึ่ง | `[GATE] source-echo` |
| **โครงสร้าง ICU / ตัวแทนข้อความ (placeholder)** | ตัวแปร คำสำคัญของพหูพจน์ หรือตัวเลือกถูกแปลไป, หรือ `#` หรือ `%s` สูญหาย | `[GATE] icu` |
| **มาร์กอัป** | มีการเปิด ปิด หรือซ้อนแท็กแตกต่างไปจากต้นฉบับ | `[GATE] markup` |
| **การตัดประโยคข้างตัวแทนข้อความ** | การแปลใส่เครื่องหมายจบประโยคไว้หน้าหรือหลังตัวแทนข้อความ ทั้งที่ต้นฉบับไม่มี: `Take this medicine at {time}.` → `… sina. {time}.` | `sentence break beside a placeholder` |
| **ลูปอาการประสาทหลอน (Hallucination loop)** | รูปแบบไตรแกรม (trigram) ที่ซ้ำซ้อนกัน (เช่น `"Qo' Qo' Qo'"`) | `[GATE] hallucination` |
| **ความยาวขยายตัวเกินจริง (Length inflation)** | ผลลัพธ์ยาวกว่าต้นฉบับอย่างมีนัยสำคัญ | `[GATE] length` |
| **การลบเนื้อหา (Content deletion)** | ผลลัพธ์คือข้อความต้นฉบับที่ถูกลบตัวอักษรทิ้ง | `[GATE] content` |
| **ความถูกต้องของระบบการเขียน (Script compliance)** | ระบบการเขียน (script) ไม่ถูกต้องสำหรับโลแคลเป้าหมาย | `[GATE] script` |
| **ผลลัพธ์เหมือนกันจากต้นฉบับที่ต่างกัน** | ข้อความเดียวถูกส่งคืนให้กับสตริงต้นฉบับที่แตกต่างกันหลายรายการ (ประโยคที่ถูกท่องจำมา) | `[GATE] shared-output` |
| **หมวดหมู่พหูพจน์ของ ICU** | ขาดรูปพหูพจน์ที่จำเป็นสำหรับโลแคลนั้น | `[GATE] icu-plural` |

คีย์ที่ประกาศไว้ใน [`noTranslate`](/docs/getting-started/configuration#no-translate) จะไม่ผ่านเข้ามายัง gate เลย — เพราะคีย์เหล่านี้จะถูกคัดลอกมาจากต้นฉบับแบบคำต่อคำ จึงไม่มีสิ่งใดต้องตรวจสอบความถูกต้อง

**หน้า Markdown จะได้รับการตรวจสอบแบบเดียวกัน โดยตรวจทีละบล็อก** ในโฟลเดอร์เนื้อหา (`contentDir`, เอกสาร Docusaurus) แต่ละหัวข้อ, ย่อหน้า, รายการในลิสต์ และเซลล์ในตารางจะถูกตรวจสอบแยกกัน รวมถึงแต่ละฟิลด์ของ front-matter ด้วย การตรวจสอบจะเป็นรายการเดียวกับด้านบน: ค่าว่าง, การสะท้อนต้นฉบับ, ลูปอาการประสาทหลอน, ความยาวขยายตัวเกินจริง, การลบเนื้อหา, ระบบการเขียน และผลลัพธ์เหมือนกันสำหรับต้นฉบับที่ต่างกัน หัวข้อสั้นๆ เช่น `## Feast` ที่ถูกส่งคืนกลับมาเป็นประโยคยาวจะถูกปฏิเสธ เช่นเดียวกับแอปคีย์ที่มีข้อความเดียวกัน

บล็อกที่ถูกปฏิเสธจะ**ถูกขอให้แปลใหม่อีกหนึ่งครั้งพร้อมระบุเหตุผล** โมเดลจะได้รับแจ้งว่ามีสิ่งใดผิดพลาด และข้อความที่ถูกต้องอยู่แล้วสามารถส่งกลับมาเหมือนเดิมได้ การปฏิเสธบางกรณีไม่สามารถตัดสินได้ด้วยกฎตายตัว: หัวข้อที่เป็นชื่อเฉพาะ (`### BLEURT (Sellam et al., 2020)`), รายการในเอกสารอ้างอิง, ตารางรหัสโค้ด หรือคำอธิบายศัพท์ อาจถูกต้องตรงตามที่เขียนอยู่แล้ว หรืออาจเป็นส่วนที่แปลตกหล่น หากบล็อกนั้นถูกส่งกลับมาเหมือนเดิม หรือคงเป็นอักษรละตินในภาษาที่ไม่ใช่อักษรละติน และโมเดลยังคงให้คำตอบเดิมอีกครั้ง คำตอบนั้นจะได้รับการยอมรับว่าเป็นความตั้งใจ ส่วนการปฏิเสธในกรณีอื่นๆ ทั้งหมดจะต้องผ่านเกณฑ์ของ gate อย่างสมบูรณ์ในการตอบครั้งที่สอง สำหรับปลายทางที่ระบุว่าไม่รับคำสั่งเพิ่มเติม (`"acceptsInstructions": false`) จะไม่ถูกถามซ้ำ โดยคำตอบแรกจะถูกตัดสินเสมือนเป็นคำตอบครั้งที่สองทันที

สิ่งที่ยังคงถูกปฏิเสธจะถูกส่งต่อไปยังเมธอด `fallback` ของคู่นั้น หากไม่มีเมธอดดังกล่าว **บล็อกนั้นจะคงข้อความต้นฉบับไว้ โดยไม่มีการเพิ่มมาร์กเกอร์ใดๆ ลงในหน้า**, จะไม่ถูกแคช และรายการล็อกของหน้านั้นจะระบุเป็น `pending:<hash>` คำสั่ง `status` และ `verify` จะแสดงรายชื่อหน้าเหล่านี้ และ sync จะระบุชื่อแต่ละบล็อก การปฏิเสธนี้จะถูกบันทึกจำไว้: การรัน sync แบบปกติครั้งถัดไปจะไม่ส่งบล็อกดังกล่าวไปยังโมเดลเดิมอีก (ดูที่ [บล็อก Markdown และฟิลด์ front-matter ที่ถูกปฏิเสธ](#refused-markdown-blocks-and-front-matter-fields)) โค้ด ลิงก์ และมาร์กอัปในบล็อกจะได้รับการป้องกันแยกต่างหาก และคอมเมนต์ HTML จะไม่ถูกส่งไปแปลเลย ข้อความบางประเภทจะได้รับการคงไว้ตามที่เขียนโดยไม่มีการสอบถามซ้ำ:
- ชื่อสั้นๆ (`## GitHub`) โดยวัดความยาวโดยไม่นับรวมโค้ดอินไลน์ เครื่องหมายคำพูด วงเล็บ และ `{#anchor}`
- รายการในเอกสารอ้างอิง หรือรายการอ้างอิงทั้งหมดในบล็อกเดียว
- ตัวอักษรแบบเต็มความกว้าง (fullwidth) ที่ปรากฏอยู่ในต้นฉบับเอง

ตารางจะถูกวัดขนาดจากเซลล์ภายใน ไม่ใช่จากเครื่องหมายไพป์และแถวแบ่งคอลัมน์ `verify` จะตรวจสอบบล็อกที่อยู่บนดิสก์แล้วด้วยวิธีเดียวกัน ยกเว้นบล็อกที่มีเนื้อหาตรงกับสิ่งที่ sync ยอมรับและแคชไว้สำหรับต้นฉบับนั้นอย่างแม่นยำ บล็อกที่ไม่ผ่านจะถือเป็นคำเตือน ซึ่งจะทำให้ `verify --strict` ไม่ผ่าน และจะแสดงพร้อมคำสั่งซ่อมแซม `champollion sync --pair en:fr --redo files:<page>` โดย sync จะพิมพ์คำสั่งเดียวกันนี้สำหรับไฟล์เดียวกันออกมา

### ว่างเปล่า/เว้นวรรค

ปฏิเสธการแปลที่เป็น string ว่าง มีแต่ whitespace หรือ `null` ตรวจจับโมเดลที่ไม่คืนค่าใดๆ สำหรับ key ที่แปลยาก

### Source Echo

ตรวจจับเมื่อโมเดลส่งคืนข้อความต้นฉบับภาษาอังกฤษแทนที่จะแปล ซึ่งมักเกิดขึ้นบ่อยกับสตริงสั้นๆ และพรอมต์ที่ระบุรายละเอียดไม่เพียงพอ มีกฎสองข้อที่นำมาใช้ โดยแต่ละข้อจะวัดสิ่งต่างกัน:

1. **การคัดลอกมาเหมือนเดิมทุกประการ** (ตรงกับต้นฉบับแบบไบต์ต่อไบต์) จะถูกปฏิเสธ — ยกเว้นค่าที่**สั้นและส่วนใหญ่เป็นอักขระ ASCII**: มีความยาวไม่เกิน 30 อักขระ และเป็น plain ASCII มากกว่า 80% คำเช่น `"Blog"`, `"GitHub"`, `"npm"` สามารถคงเป็นภาษาอังกฤษได้ตามความเหมาะสม ดังนั้นในภาษาเป้าหมายที่ใช้อักษรละติน การคัดลอกเช่นนี้จะได้รับการยอมรับ (`verify` จะระบุไว้ว่าเป็นการสะท้อนต้นฉบับ); ส่วนในภาษาเป้าหมายที่ไม่ใช่อักษรละติน โมเดลจะถูกถามหนึ่งครั้งว่าเป็นชื่อเฉพาะหรือไม่ และหากยืนยันคำตอบเดิมสองครั้งก็จะยอมรับว่าเป็นชื่อเฉพาะ **ข้อยกเว้นนี้พิจารณาจากความยาว และครอบคลุมเฉพาะการคัดลอกที่เหมือนเดิมทุกประการเท่านั้น**
2. **การคัดลอกแบบแปลงรูป** — คือต้นฉบับที่เปลี่ยนเฉพาะตัวพิมพ์เล็ก-ใหญ่, เครื่องหมายกำกับเสียง, การเว้นวรรค, อักขระที่มองไม่เห็น หรือรูปแบบการใช้งานร่วมกัน (compatibility forms เช่น ตัวอักษรเต็มความกว้าง หรือ ligatures) — จะถูกปฏิเสธเมื่อต้นฉบับมีคำที่มีตัวอักษรตั้งแต่**สามคำขึ้นไป** (ตัวแทนข้อความ เช่น `{count}` หรือ `%s` และแท็กมาร์กอัปจะไม่นับ) **ไม่ว่าข้อความนั้นจะสั้นแค่ไหนก็ตาม** เช่น `"Book an appointment"` (19 อักขระ, 3 คำ) → `"Bóok án appóintment"` จะถูกปฏิเสธ; ส่วน `"cafe"` → `"café"` (1 คำ) จะได้รับการยอมรับ เพราะการแปลจริงอาจแตกต่างจากภาษาอังกฤษเพียงแค่เครื่องหมายกำกับเสียงเท่านั้น สำหรับชื่อเฉพาะที่ยาวกว่าซึ่งควรได้รับเครื่องหมายกำกับเสียงเพิ่มขึ้น (`"Universite de Montreal"`) จะได้รับการยอมรับเมื่อคุณประกาศการสะกดแบบมีเครื่องหมายกำกับเสียงเป็นคำที่ได้รับการปกป้อง (protected term)

กฎทั้งสองข้อนี้มีผลบังคับใช้**กับรูปพหูพจน์แต่ละรูปแบบ**ด้วยเช่นกัน ไม่ว่าจะเป็นพหูพจน์ `msgstr[n]` ของ gettext, กิ่ง `{n, plural, …}` ของ ICU หรือคีย์ `_one`/`_other` ของ i18next จะอยู่ภายใต้กฎเดียวกันกับค่าเอกพจน์: รูปพหูพจน์ภาษารัสเซียที่มีรูปแบบ `few` ส่งกลับมาเป็นภาษาอังกฤษที่เติมเครื่องหมายกำกับเสียงจะถูกปฏิเสธเช่นเดียวกับรูปเอกพจน์

ค่าที่ยาวกว่าซึ่งถูกต้องอยู่แล้วโดยไม่ต้องเปลี่ยนแปลง — เช่น URL, พาธของที่เก็บโค้ด (repository), ตัวระบุผลิตภัณฑ์ — ไม่ใช่ปัญหาของ gate และไม่สามารถแก้ไขได้ด้วยการปรับแต่ง gate: เพราะคำตอบที่ถูกต้อง *คือ* การสะท้อนต้นฉบับ ดังนั้นผลลัพธ์ที่เป็นไปได้ทั้งหมดจากโมเดลจึงผิด ให้ประกาศคีย์เหล่านั้นด้วย [`noTranslate`](/docs/getting-started/configuration#no-translate) แล้วคีย์เหล่านั้นจะข้ามกระบวนการทั้งหมดไปโดยสิ้นเชิง โดยปกติแล้วคีย์ที่มีค่าเป็น URL จะได้รับการจัดการด้วยวิธีนี้โดยดีฟอลต์

### Hallucination Loop

วิเคราะห์รูปแบบ trigram (3 ตัวอักษร) ในผลลัพธ์ หากมี trigram ใดซ้ำกันเกินจำนวน threshold เมื่อเทียบกับความยาวของผลลัพธ์ การแปลนั้นจะถูกปฏิเสธ ตรวจจับผลลัพธ์ที่ผิดปกติ เช่น `"Qo' Qo' Qo' Qo' Qo'"`

### Length Inflation

ปฏิเสธคำแปลที่มีความยาวผลลัพธ์เกิน `maxLengthRatio × source length` (ค่าดีฟอลต์: 4 เท่า) — ต้องมากกว่าอย่างชัดเจน: คำแปลที่ยาวเท่ากับ 4 เท่าพอดีจะผ่านเกณฑ์ การตรวจสอบนี้ช่วยดักจับอาการประสาทหลอนของโมเดลที่สร้างข้อความยาวเป็นพรืดสำหรับอินพุตสั้นๆ

กำหนดค่าได้ผ่าน `maxLengthRatio` ในไฟล์ config ของคุณ

### การลบเนื้อหา (Content Deletion)

เป็นด้านตรงข้ามของความยาวขยายตัวเกินจริง โมเดลที่ไม่มีคลังคำศัพท์สำหรับสตริงหนึ่งๆ อาจลบตัวอักษรทุกตัวที่ไม่สามารถแปลออก แล้วเหลือทิ้งไว้เพียงเครื่องหมายวรรคตอนและการเว้นวรรคของต้นฉบับ:

```
"low-resource nmt · tokenizers · nêhiyawêwin"  →  "   ·   · êhiêi"
"the simple-builder approach"                  →  "  "
```

ไม่มีการตรวจสอบอื่นใดดักจับสิ่งนี้ได้ มันไม่ใช่ค่าว่าง ไม่ใช่การสะท้อนต้นฉบับ ไม่ซ้ำซ้อน และที่ระดับ 33% ของ*ความยาว*ต้นฉบับ มันสามารถผ่าน `minLengthRatio` ได้อย่างสบายๆ

การตรวจสอบนี้จะเปรียบเทียบ**อักขระเนื้อหา** — ตัวอักษรและตัวเลข โดยไม่สนใจเครื่องหมายวรรคตอน ช่องว่าง และการจัดรูปแบบที่มองไม่เห็น — ระหว่างต้นฉบับกับผลลัพธ์ แต่ความหนาแน่นเพียงอย่างเดียวไม่สามารถนำมาใช้เป็นกฎได้ เพราะระบบการเขียนที่มีความหนาแน่นสูงตามธรรมชาติก็อยู่ในเกณฑ์ระดับเดียวกัน:

| ต้นฉบับ | ผลลัพธ์ | เนื้อหาที่คงอยู่ | ผลการตัดสิน |
|---|---|---|---|
| `low-resource nmt · tokenizers · nêhiyawêwin` | `   ·   · êhiêi` | 14% | **ปฏิเสธ** |
| `Getting started` | `入门` | 14% | ยอมรับ |
| `Frequently asked questions` | `常见问题` | 17% | ยอมรับ |

เกณฑ์ใดก็ตามที่ดักจับกรณีแรกได้จะปฏิเสธภาษาจีน ญี่ปุ่น และเกาหลีอย่างสิ้นเชิง สิ่งที่แยกแยะกรณีเหล่านี้ได้ไม่ใช่สัดส่วนเนื้อหาที่รอดมา แต่เป็น*ที่มาของมัน*: ผลลัพธ์ที่กลวงเปล่าจะเป็น**ลำดับย่อย (subsequence)** ของต้นฉบับตัวเอง — ซึ่งสร้างขึ้นมาได้โดยการลบอักขระออกจากต้นฉบับ — ในขณะที่การแปลจริงๆ แทบจะไม่มีอะไรซ้ำกับต้นฉบับเลย การจะตั้งค่าสถานะ (flag) ได้จำเป็นต้องมีสัญญาณ**ทั้งสองอย่าง**ร่วมกัน ดังนั้นการตรวจสอบนี้จึงเป็นเงื่อนไขที่จำเป็นแต่ไม่เพียงพอในตัวมันเอง เช่นเดียวกับตัวตรวจจับการซ้ำซ้อน

สามารถกำหนดค่าได้ผ่าน `minContentRetention` (ค่าดีฟอลต์ `0.35`) โดยกำหนดต่อคู่ภาษาหรือต่อภาษาก็ได้ การเพิ่มค่านี้จะทำให้การตรวจสอบเข้มงวดขึ้น แต่จะทำงานก็ต่อเมื่อเกิดร่วมกับสัญญาณลำดับย่อยเสมอ

:::note[นี่คือสัญญาณเตือนเรื่องคลังคำศัพท์ ไม่ใช่ปุ่มปรับคุณภาพ]
เมื่อสิ่งนี้ถูกทริกเกอร์ซ้ำๆ สำหรับภาษาเป้าหมายใดภาษาหนึ่ง แสดงว่าโมเดลไม่มีคลังคำสำหรับข้อความนั้น — ซึ่งมักเป็นสตริงสั้นๆ ที่เต็มไปด้วยศัพท์เฉพาะในภาษาที่มีคลังคำจำกัด การผ่อนปรนเกณฑ์ลงจะทำให้ข้อความเสียหายอย่างเงียบๆ กลับมาอีกครั้ง แต่ไม่ได้ช่วยให้ได้คำแปลออกมา ควรแก้ไขที่พรอมต์, ข้อมูลตัวอย่าง (coaching data) หรือคู่โมเดลแทน
:::

### Script Compliance

สำหรับโลแคลที่แผ่นข้อมูลภาษา (language card) ระบุว่าเป็นระบบการเขียนที่ไม่ใช่อักษรละติน (อาหรับ, CJK, ซีริลลิก, …) จะมีการตรวจสอบว่าผลลัพธ์ไม่ได้ประกอบด้วยอักษรละตินล้วน ตัวอักษรจะถูกจำแนกตาม**ระบบการเขียนของ Unicode (Unicode script)** ไม่ใช่ตามไบต์: อักษรละตินที่มีเครื่องหมายกำกับเสียง (`"Bóók"`) และอักษรละตินแบบเต็มความกว้าง (`"Ｂｏｏｋ"`) ถือเป็นอักษรละติน ดังนั้นทั้งคู่จึงไม่ผ่านเกณฑ์การเป็นภาษารัสเซีย อักษรละตินแบบเต็มความกว้างจะถูกปฏิเสธในภาษาเป้าหมายใดๆ นอกเหนือจากการจัดพิมพ์แบบ CJK (ซึ่ง `"ＯＫ"` ถือเป็นการใช้งานปกติในภาษาญี่ปุ่น) — เพราะนั่นคือภาษาอังกฤษที่แปลงรูปมา ข้อยกเว้นตามปกติยังคงมีผล: ชื่อสั้นๆ ที่คงไว้ตามที่เขียน (คำถามเรื่องชื่อหรือเลเบลตามที่กล่าวไว้ข้างต้น), คำที่ได้รับการปกป้องตามที่ประกาศไว้ และคีย์ `noTranslate` (รวมถึง URL) จะไม่มีทางไม่ผ่านเกณฑ์นี้

คำชี้แจงสองประการเกี่ยวกับสิ่งที่ไม่ใช่การตรวจสอบนี้:

- การตรวจสอบนี้**ไม่ได้ทำงานตามฟิลด์การกำหนดค่า `script:`** ฟิลด์นั้นมีไว้สำหรับเลือกอักขรวิธีของผลลัพธ์สำหรับการ[แปลงระบบการเขียน](/docs/getting-started/configuration#script-conversion); ความคาดหวังของ gate นั้นมาจากแผ่นข้อมูลภาษา
- การตรวจสอบจะตรวจความถูกต้องของ**ระบบการเขียนขณะประมวลผลที่โมเดลส่งออกมา**เสมอ *ก่อน* ที่จะมีการแปลงระบบการเขียนใดๆ โลแคลที่มีตัวแปลงระบบการเขียน (crk, sr, tlh, …) ซึ่งสร้างผลลัพธ์เป็นอักษรละตินขณะประมวลผลได้อย่างถูกต้อง จึงได้รับการยกเว้นจากการตรวจสอบนี้; ส่วนการแปลง — หากเลือกเปิดใช้ในการกำหนดค่า — จะเกิดขึ้นหลังจากผ่าน gate แล้ว

### มาร์กอัป

แท็กคือโค้ด สำหรับแต่ละชื่อแท็ก คำแปลจะต้องเปิด ปิด และเป็น self-close ในจำนวนที่เท่ากับต้นฉบับ รวมถึงต้องซ้อนแท็กในลักษณะเดียวกัน (`<b>` ที่อยู่ภายใน `<a>` จะต้องอยู่ภายใน `<a>`); ลำดับของแท็กในระดับเดียวกันอาจเปลี่ยนไปตามลำดับคำได้ ตัวอย่างเช่น `"Please <strong>book</strong> now"` → `"Veuillez <strong>réserver maintenant"` จะถูกปฏิเสธ — แท็กปิดที่สูญหายจะทำให้หน้าเว็บเสียหาย ในข้อความพหูพจน์ แต่ละรูปแบบจะถูกนำไปเปรียบเทียบกับรูปแบบต้นฉบับที่มันแปลออกมา คำสั่ง `verify` จะรันการตรวจสอบแบบเดียวกันนี้กับไฟล์ต่างๆ

### การตัดประโยคข้างตัวแทนข้อความ

ตัวแทนข้อความ (placeholder) จะถูกแทนที่ค่าในขณะรันไทม์ ดังนั้นเครื่องหมายจบประโยคที่คำแปลใส่ไว้ติดกับตัวแทนข้อความจะเปลี่ยนสิ่งที่ผู้อ่านเห็น: `"Take this medicine at {time}."` → `"… sina. {time}."` จะแสดงเวลาแยกออกมาเป็นอีกประโยคหนึ่ง Gate จะปฏิเสธคำแปลที่ใส่เครื่องหมายจบประโยค (`.`, `!`, `?` หรือเครื่องหมายของระบบการเขียนอื่น: `。`, `？`, `।`, `؟`, `።`, `᙮`, …) ไว้ติดอยู่ด้าน**หน้า**ตัวแทนข้อความ หรือติดอยู่ด้าน**หลัง**ตัวแทนข้อความที่มีข้อความอื่นตามมา เมื่อต้นฉบับไม่มีเครื่องหมายตรงนั้นและคำแปลมีเครื่องหมายจบประโยคมากกว่าต้นฉบับ ตัวแทนข้อความที่ย้ายไปอยู่ท้ายประโยคเพียงอย่างเดียว (`"Shipped by {carrier} on {date}."` → `"Expédié le {date} par {carrier}."`) จะผ่านเกณฑ์ เช่นเดียวกับจุดไข่ปลา ทศนิยม หรือชื่อไฟล์ (`{host}.com`) และคำย่ออักษรตัวเดียว (`"M. {name}"`) ส่วนคำย่อที่ยาวกว่าซึ่งอยู่หน้าตัวแทนข้อความ (`"ca. {count}"`) จะไม่สามารถแยกแยะออกจากเครื่องหมายจบประโยคได้ จึงจะถูกปฏิเสธด้วยเช่นกัน และจะถูกส่งต่อให้วิธีสำรอง (fallback) ของคู่โมเดล หรือรอคำตอบที่ปรับเปลี่ยนถ้อยคำใหม่ คำสั่ง `verify` จะแฟล็กค่าลักษณะเดียวกันนี้บนดิสก์ พร้อมกับคำสั่ง `--redo` เพื่อขอให้แปลใหม่ สำหรับข้อความพหูพจน์และ select ของ ICU จะปล่อยให้เป็นการตรวจสอบของ ICU จัดการ

### ผลลัพธ์เหมือนกันจากต้นฉบับที่ต่างกัน

โมเดลที่ท่องจำประโยคจากชุดข้อมูลฝึกฝนอาจส่งคืนประโยคนั้นสำหรับสตริงที่ไม่รู้จัก: ได้ประโยคเดียวกันสำหรับชื่อแอป, "Contact the school", ชื่อจดหมายข่าว และหัวข้อของจดหมายข่าว โดยที่แต่ละรายการผ่านการตรวจสอบทั้งหมดข้างต้นมาได้ด้วยตัวเอง เมื่อคำแปลเดียวกันตอบกลับสตริงต้นฉบับที่**แตกต่างกันตั้งแต่สามรายการขึ้นไป**ภายในการรันของโลแคลหนึ่งๆ — และคำแปลนั้นมีตั้งแต่สี่คำขึ้นไป หรือต้นฉบับแต่ละรายการมีตั้งแต่สองคำขึ้นไปโดยแทบไม่มีอะไรร่วมกัน — คีย์เหล่านั้นจะถูกปฏิเสธ (เพื่อให้ระบบลองใหม่ จากนั้นส่งต่อให้วิธีสำรองจัดการ) สตริงต้นฉบับที่ต่างกันเพียง **สอง** รายการก็เพียงพอแล้วหากมีหลักฐานที่ชัดเจน: ทั้งคู่มีตั้งแต่สองคำขึ้นไป มีคำที่เหมือนกันน้อยกว่าครึ่งหนึ่ง และคำแปลที่ใช้ร่วมกันมีความยาวตั้งแต่สี่คำขึ้นไป (`"Thank you for coming!"` และ `"Please bring the forms."` ตอบกลับด้วยประโยคเดียวกัน) ประโยคที่ถูกดักจับด้วยวิธีนี้จะถูกจดจำไว้สำหรับโลแคลนั้น: การ sync ในภายหลังที่ได้รับประโยคนี้กลับมาอีก แม้จะสำหรับสตริงเดียวก็ตาม จะปฏิเสธมัน และรายการในแคชที่เคยให้บริการข้อความนี้ไปแล้วจะถูกลบออก เพื่อให้การทำซ้ำ (redo) สอบถามไปยังโมเดลใหม่อีกครั้งแทนที่จะเขียนจากแคช คำพ้องรูป/ความหมายที่ถูกยุบรวมเป็นคำแปลสั้นๆ คำเดียว (`"OK"`/`"Okay"`/`"Sure"` → `"D'accord"`, `"Close"`/`"Dismiss"` → `"Fermer"`) จะผ่านเกณฑ์ เช่นเดียวกับข้อความต้นฉบับข้อความเดียวที่ใช้ในหลายคีย์ บล็อก Markdown และฟิลด์ front-matter ของไฟล์เนื้อหาในการรันนั้นจะถูกนับด้วย รวมถึงแต่ละกิ่งของข้อความพหูพจน์หรือ select ของ ICU (กิ่งต่างๆ ของพหูพจน์เดียวกันจะนับเป็นต้นฉบับเดียว — ภาษาที่ไม่มีการเปลี่ยนรูปตามจำนวนจะเขียนข้อความเดียวกันในแต่ละกิ่ง) ผลลัพธ์จะถูกนำมาเปรียบเทียบกันโดยไม่นำตัวพิมพ์เล็ก-ใหญ่ เครื่องหมายวรรคตอน และมาร์กเกอร์ของบล็อก Markdown มาคิด ดังนั้น `"S?"`, `"S."` และหัวข้อ `# S` จึงถือเป็นผลลัพธ์เดียวกัน การนับจะรวมถึงสิ่งที่โลแคลมีอยู่แล้วบนดิสก์และสิ่งที่แคชจะนำมาเสิร์ฟ (ประโยคที่ถูกแคชทีละข้อความโดยเครื่องมืออื่นจะถูกปฏิเสธที่ระดับแคช ไม่ถูกนำมาเขียน) ดังนั้นคีย์ที่เพิ่มเข้ามาทีละครั้งในการ sync แต่ละรอบก็จะถูกดักจับได้ด้วยเช่นกัน `verify` จะล้มเหลวเมื่อพบแพตเทิร์นเดียวกันบนดิสก์ และเครื่องมือ MCP `translate` จะปฏิเสธสิ่งนี้ภายในคอลนั้นทันที

### คำถามที่เครื่องหมายสูญหาย

เมื่อต้นฉบับลงท้ายด้วย `?` หรือ `!` แต่คำแปลไม่ได้ลงท้ายด้วยเครื่องหมายนั้น หรือเครื่องหมายที่เทียบเท่าในระบบการเขียนของภาษานั้น (`？`, `؟`, อักษรกรีก `;`, `¿…?`, `！`, …) คำสั่ง `sync` และ `verify` จะแจ้งเตือน: เพราะ `"Where does it hurt?"` ที่เขียนในรูปประโยคบอกเล่าจะถูกอ่านเป็นประโยคบอกเล่า กรณีนี้เป็นเพียงคำเตือน ไม่ใช่การปฏิเสธ เนื่องจากบางภาษาใช้วิธีระบุคำถามด้วยคำหรืออนุภาค (particle) แทนการใช้เครื่องหมาย คำเตือนจะระบุชื่อคีย์และคำสั่ง `--redo keys:<key> --fresh` เพื่อขอให้แปลใหม่ (`--fresh` เนื่องจากคำตอบถูกเก็บอยู่ในแคชแล้ว)

## สิ่งที่เกิดขึ้นเมื่อล้มเหลว

1. คำแปลที่ไม่ผ่านจะถูกบันทึกไปยัง stderr พร้อมพรีฟิกซ์ `[GATE]`, ชื่อคีย์, เหตุผล และตัวอย่างข้อความบางส่วนของค่านั้น
2. คีย์ดังกล่าวจะ**ไม่**ถูกเขียนลงในไฟล์โลแคล
3. ลำดับขั้นการลองใหม่ (retry cascade) จะเริ่มทำงาน (ดูด้านล่าง)
4. หากยังคงไม่ผ่าน การปฏิเสธจะถูก**จดจำไว้** (ดูที่ [คีย์ที่ถูกปฏิเสธจะถูกระงับไว้](#refused-keys-are-held-back))

```
[GATE] hero.title: source-echo — "Welcome to our platform"
[GATE] nav.about: hallucination — "À À À À À À À À"
```

## การลองใหม่พร้อมฟีดแบ็กและลำดับขั้นการลองใหม่

คีย์ที่ถูก gate ปฏิเสธจะได้รับสิทธิ์**ลองใหม่พร้อมฟีดแบ็กหนึ่งครั้ง**: เหตุผลของการปฏิเสธจะถูกแทรกลงในพรอมต์เป็นบริบทเฉพาะของคีย์นั้น (การลองใหม่สุ่มสี่สุ่มห้าด้วยอุณหภูมิ (temperature) ต่ำจะได้ผลลัพธ์ที่ตรงกันแบบไบต์ต่อไบต์) หากการลองใหม่ผ่าน คีย์นั้นจะถูกเขียนลงไฟล์และสถานะการ sync จะเป็น**สีเขียว (ผ่าน)** — การที่ gate ปฏิเสธแล้วระบบสามารถแก้ไขตัวเองได้จะไม่ถือเป็นความล้มเหลว และนี่คือพฤติกรรมที่ตั้งใจไว้ คีย์ที่ยังคงไม่ผ่านหลังจากการลองใหม่จะถูกข้ามและรายงานผล (การ sync จะจบการทำงานด้วยรหัส `2`)

การลองใหม่จะดำเนินการผ่านเมธอดการแปลของคู่นั้นๆ ไม่ว่าจะเป็นอะไรก็ตาม — LLM, Google Translate, DeepL หรือผู้ให้บริการโดยตรง จะมีเฉพาะเมธอด LLM เท่านั้นที่อ่านฟีดแบ็ก; บรรทัดการรันจะระบุไว้ชัดเจน (`retrying with feedback` หรือ `asking once more (deepl takes no instructions…)`) สำหรับปลายทาง `api` จะได้รับฟีดแบ็กก็ต่อเมื่อมีการประกาศ `"acceptsInstructions": true` ไว้ (บนคู่ภาษาหรือใน manifest ของปลั๊กอิน); ส่วนปลายทางที่ประกาศ `false` — ซึ่งเป็นโมเดล NMT ที่ผ่านการเทรนมา เช่น `nmt-forge serve` ซึ่งจะให้คำตอบเดิมเสมอ — จะไม่ถูกถามซ้ำเลย: คำตอบของมันจะถูกตัดสินเสมือนเป็นคำตอบครั้งที่สอง และสิ่งที่มันปฏิเสธจะถูกส่งต่อไปยังวิธีสำรองของคู่นั้น การลองใหม่ยังใช้กับข้อมูลที่ตรงกันใน Translation Memory ด้วย: ค่าที่แคชไว้ซึ่ง gate ปฏิเสธจะถูกดีดออกและแปลใหม่ภายในการรันรอบเดียวกัน เพื่อให้แคชที่มีข้อมูลเสียรักษาตัวเองได้

### คีย์ที่ถูกปฏิเสธจะถูกระงับไว้

การปฏิเสธจะถูกจดจำไว้ใน `.champollion.lock` แยกตามคีย์ สำหรับ**ข้อความต้นฉบับปัจจุบัน**ของคีย์นั้น รวมถึง**เมธอดและโมเดล**ที่สร้างคำตอบที่ถูกปฏิเสธ สตริง UI ของ Docusaurus (`i18n/<locale>/code.json` และไฟล์ JSON ของปลั๊กอิน) จะใช้กฎเดียวกัน โดยแยกตามไฟล์และ id การรัน `sync` แบบปกติครั้งถัดไปจะไม่ส่งคีย์นั้นไปยังโมเดลเดิมอีก — เพราะจะเสียค่าใช้จ่ายกับคำตอบเดิม — พร้อมทั้งระบุว่ามีกี่คีย์ที่ถูกระงับไว้และต้องดำเนินการอย่างไรต่อไป:

- ร้องขอใหม่อีกครั้ง: `champollion sync --redo keys:<key>` (หรือ `--redo all` หรือ `--fresh`) — การระบุชื่อคีย์ถือเป็นการสั่งลองใหม่โดยชัดแจ้ง
- เติมค่าด้วยวิธีอื่น: เพิ่มเมธอด `"fallback"` ให้กับคู่ภาษา (ระบบจะสอบถามวิธีนี้สำหรับคีย์ที่เมธอดหลักของคู่ปฏิเสธ), ระบุชื่อคีย์ใน `noTranslate` หากต้องการคงข้อความไว้ตามที่เขียน หรือเขียนคำแปลลงในไฟล์ด้วยตนเอง

คีย์ที่ถูกระงับจะถือว่ายังไม่ได้รับการแปล ดังนั้นการ sync จะจบการทำงานด้วยรหัส `2` จนกว่าคีย์นั้นจะได้รับการเติมค่า การเปลี่ยนข้อความต้นฉบับ โมเดล หรือเมธอดจะปลดการระงับ (เนื่องจากการปฏิเสธนั้นผูกอยู่กับข้อความเดิมจากโมเดลเดิม) ระบบยังคงอ่านแคชสำหรับคีย์นั้น — การระงับมีไว้เพื่อหยุดการเรียก API ที่มีค่าใช้จ่าย ไม่ใช่การเรียกฟรี มีข้อยกเว้นเพียงกรณีเดียวคือคีย์ที่กระบวนการ redo ทำไม่สำเร็จ ตามรายละเอียดด้านล่าง

### บล็อก Markdown และฟิลด์ front-matter ที่ถูกปฏิเสธ

กฎเดียวกันนี้ใช้กับไฟล์เนื้อหา (`contentDir`, เอกสาร Docusaurus) บล็อกหรือฟิลด์ front-matter ที่ gate ปฏิเสธจะถูกจดจำไว้ใน `.champollion-content.lock` แยกตามหน้า บล็อก และโลแคล สำหรับ**ข้อความต้นฉบับปัจจุบัน**ของบล็อกนั้น รวมถึง**เมธอดและโมเดล**ที่สร้างคำตอบที่ถูกปฏิเสธ บล็อกจะถูกระบุด้วยข้อความต้นฉบับ ดังนั้นการแก้ไขย่อหน้าจะปลดการระงับ การรัน `sync` แบบปกติครั้งถัดไปจะไม่ส่งบล็อกนั้นไปยังโมเดลเดิมอีก และจะรายงานว่ามีกี่บล็อกและกี่ฟิลด์ที่ถูกระงับไว้ในหน้าใดบ้าง:

- บล็อกที่ถูกระงับจะคงข้อความต้นฉบับไว้บนหน้า โดยไม่มีมาร์กเกอร์ใดๆ จนกว่าจะได้รับการเติมค่า; ส่วนที่เหลือของหน้าจะถูกเขียนตามปกติ
- ฟิลด์ front-matter ที่ถูกระงับจะคงข้อความต้นฉบับไว้ในลักษณะเดียวกัน และส่วนที่เหลือของหน้าจะถูกเขียนตามปกติ
- หน้าที่แปลทั้งหน้า (`contentSegmentation: "page"`) จะถูกปฏิเสธทั้งหน้าเมื่อคำตอบสร้างความเสียหายให้กับบล็อกที่ได้รับการปกป้องหรือทำให้เนื้อหาในหน้ากลวงเปล่า หน้านั้นจะถูกจดจำด้วยข้อความของเนื้อหา (body) และถูกระงับไว้ทั้งหน้า: จะไม่มีการเขียนไฟล์ และไม่มีสิ่งใดถูกส่งไปแปล จนกว่าจะได้รับการเติมค่า การแก้ไขเนื้อหา หรือการเปลี่ยนไปใช้การแบ่งส่วนแบบบล็อก จะปลดการระงับ

การปฏิเสธที่เกิดจาก gate เวอร์ชันก่อนหน้าจะถูกปลดโดยอัตโนมัติ เมื่อมีการผ่อนปรนกฎการตรวจสอบ สิ่งที่เคยถูกปฏิเสธจะถูกส่งไปแปลใหม่อีกครั้งในการ sync รอบถัดไป โดยไม่ต้องสั่ง redo

ลำดับความสำคัญจะเป็นไปตามลำดับของคีย์:

1. หน้าที่ระบุชื่อไว้อย่างชัดเจนสำหรับการ redo จะถูกส่งไปแปลเสมอ: `champollion sync --redo files:<page>`, `--redo content` (ทุกหน้า), `--retranslate` หรือสิ่งใดก็ตามภายใต้ `--fresh`
2. หากไม่ใช่กรณีข้างต้น บล็อกหรือฟิลด์ที่ถูกปฏิเสธจะถูกระงับไว้ หากคู่ภาษามีเมธอด `fallback` ที่ยังไม่เคยปฏิเสธบล็อกนั้น ระบบจะส่งไปถามวิธีสำรองแทนและจะไม่ส่งไปยังเมธอดหลักของคู่นั้น
3. การเปลี่ยนโมเดลหรือเมธอดจะปลดการระงับ เช่นเดียวกับการแก้ไขข้อความต้นฉบับของบล็อก

ระบบจะยังคงอ่านแคชก่อนเสมอ ดังนั้นการระงับจึงหยุดเฉพาะการเรียกใช้ที่มีค่าใช้จ่าย ไม่ใช่การเรียกฟรี บล็อกที่ได้รับการเติมค่าด้วยวิธีอื่นจะลบบันทึกการระงับทิ้ง: ไม่ว่าจะผ่านวิธีสำรอง, ผ่านแคช หรือผ่านย่อหน้าที่คุณเขียนลงในคำแปลด้วยตนเอง (โฟลเดอร์เนื้อหาจะเก็บย่อหน้าที่เขียนด้วยมือไว้) บล็อกหรือฟิลด์ที่ถูกระงับจะถือว่ายังไม่ได้แปล ดังนั้นการ sync จะจบการทำงานด้วยรหัส `2` จนกว่าจะได้รับการเติมค่า สิ่งนี้มีผลเช่นเดียวกันกับบล็อกที่ gate ปฏิเสธในระหว่างการรันรอบนี้ การรันแบบ dry run จะแสดงรายการสิ่งที่การรันจริงจะระงับไว้

### กระบวนการ redo ที่ทำไม่สำเร็จ

เมื่อ `--redo all`, `--redo keys:` หรือการสลับโมเดล (`--redo all --fresh-on-model-change`) ทำให้คีย์ในไฟล์ key-value ยังคงไม่ได้รับการแปล คีย์เหล่านั้นจะถูกบันทึกสถานะเป็น **pending (รอดำเนินการ)** ใน `.champollion.lock` และการรัน `sync` แบบปกติครั้งถัดไปจะขอให้โมเดลแปลใหม่อีกหนึ่งครั้ง — โดยขอจากโมเดล ไม่ใช่จากแคช (เนื่องจากจุดประสงค์ของการ redo คือต้องการข้อความจากโมเดลใหม่) คำสั่ง `champollion status` จะแสดงรายการคีย์เหล่านี้ หากการลองใหม่นั้นยังคงถูกปฏิเสธ คีย์จะยังคงมีสถานะ pending (คำสั่ง status จะแสดงสถานะนี้) และจะถูกระงับไว้เหมือนกับคีย์ที่ถูกปฏิเสธทั่วไป ตามลำดับความสำคัญ: คีย์ที่ระบุผ่าน `--redo`/`--fresh` จะถูกส่งไปแปลเสมอ; คีย์ที่ pending จะได้รับการลองใหม่หนึ่งครั้ง; คีย์ที่ถูกปฏิเสธจะถูกระงับไว้ สตริง UI ของ Docusaurus จะไม่มีการลองใหม่สำหรับสถานะ pending: หากถูกปฏิเสธระหว่างการ redo มันจะถูกระงับไว้ในการ sync แบบปกติครั้งถัดไป เช่นเดียวกับบล็อกเนื้อหา

นอกจากนี้ เมื่อเกิดข้อผิดพลาดขึ้นกับทั้งแบตช์ (ข้อผิดพลาดการพาร์ส JSON) Champollion จะลองใหม่โดยค่อยๆ ปรับขนาดแบตช์ให้เล็กลง:

```
Full batch (80 keys) → parse error
  └→ Half batch (40 keys) → 2 failures
      └→ Individual keys (1 each) → isolates the 2 problem keys
```

งบประมาณการลองใหม่ถูกจำกัดด้วย `maxRetries` (ค่าเริ่มต้น: 3 กำหนดค่าได้ต่อภาษา) เพื่อป้องกันการใช้ token มากเกินไปกับ key ที่ล้มเหลวซ้ำๆ

หลังจากใช้ความพยายามในการลองใหม่จนหมดแล้ว คีย์ที่มีปัญหาจะถูกบันทึกประวัติและข้ามไป คีย์ที่ไม่ได้รับคำตอบที่นำมาใช้ได้ (หายไปจากการตอบกลับ) จะถูกนำมาถามใหม่อีกครั้งในการรัน `sync` รอบถัดไป; ส่วนคีย์ที่ gate ปฏิเสธจะถูกระงับไว้ตามที่อธิบายไว้ข้างต้น

## Prompt Caching

system message (register กฎไวยากรณ์ หมายเหตุสไตล์) จะถูกแยกออกจาก user message (key ที่ต้องการแปล) การแยกนี้มีเหตุผล:

- system message **เหมือนกันทุก batch** สำหรับ locale ที่กำหนด
- Provider อย่าง Anthropic และ Google จะ cache system message ที่ซ้ำกัน
- ผลลัพธ์: batch แรกจ่าย token cost เต็มจำนวน batch ถัดไปจ่ายเฉพาะ user message

สิ่งนี้สามารถลดต้นทุน token ได้อย่างมีนัยสำคัญสำหรับโปรเจกต์ที่มี batch จำนวนมาก

## ICU MessageFormat Validation

คำสั่ง `integrity` จะตรวจสอบรูปแบบ ICU MessageFormat plural กับกฎ CLDR plural หากไฟล์ต้นฉบับของคุณใช้ ICU syntax เช่น:

```json
"items": "{count, plural, one {# item} other {# items}}"
```

Champollion จะตรวจสอบว่าเวอร์ชันที่แปลแล้วมีหมวดหมู่ plural ที่จำเป็นทั้งหมดสำหรับ locale เป้าหมาย ตัวอย่างเช่น ภาษาอาหรับต้องการหกหมวดหมู่ (`zero`, `one`, `two`, `few`, `many`, `other`) — ไม่ใช่แค่ `one` และ `other`

### รูปพหูพจน์ที่คำแปลไม่ได้ระบุมา

พรอมต์จะระบุชื่อหมวดหมู่ CLDR ของภาษาเป้าหมาย เมื่อข้อความพหูพจน์ถูกส่งกลับมาโดยขาดรูปแบบที่ภาษานั้นใช้สำหรับการนับจำนวนทั่วไป (จำนวนนับใดๆ ตั้งแต่ 0 ถึง 1000 — ภาษารัสเซียใช้ `few` สำหรับ 2, 3, 4 และ `many` สำหรับ 0, 5, 6) gate จะขอให้โมเดลแปลใหม่อีกหนึ่งครั้ง พร้อมระบุรูปแบบที่ขาดหายไปและช่วงจำนวนนับที่ครอบคลุม คำตอบรอบที่สองที่ยังคงขาดรูปแบบเหล่านี้จะได้รับการยอมรับ จะไม่มีการถามเป็นครั้งที่สาม และเครื่องมือจะไม่เติมข้อความให้โดยพลการ — จากนั้น sync จะ:

- แจ้งเตือน โดยระบุชื่อแต่ละคีย์และรูปแบบที่ขาดหายไป รวมถึงคำสั่งสำหรับขอให้แปลใหม่ (`sync --redo keys:… --fresh` ซึ่งการใช้ `--model` ที่มีความสามารถสูงขึ้นจะช่วยได้)
- ในแคตตาล็อก gettext ซึ่ง `msgfmt` จำเป็นต้องมีครบทุก `msgstr[n]` ระบบจะเขียนรูปแบบที่ขาดหายไปเป็นสำเนาของ `other` และทำเครื่องหมายรายการนั้นด้วยคอมเมนต์สำหรับผู้แปล `# champollion:` (Poedit และ Weblate จะแสดงคอมเมนต์นี้; `verify` จะอ่านค่านี้นำไปใช้ รวมถึงใน CI ที่ไม่มีแคชด้วย)
- ในไฟล์ ICU (next-intl, ARB) จะเขียนข้อความตามที่ส่งกลับมา โดยแอปพลิเคชันจะแสดงรูปแบบ `other` สำหรับจำนวนนับเหล่านั้น

ข้อความลักษณะนี้จะไม่ถือว่าได้รับการแปลเสร็จสมบูรณ์ การ sync ในภายหลังที่ใช้เมธอดหรือโมเดลอื่น — ที่ยังไม่เคยตอบข้อความนี้ เช่น โมเดลแบบโฮสต์บน CI หลังจากการทดสอบด้วยโมเดลโลคัล — จะขอรับการแปลใหม่อีกครั้งจากโมเดล ไม่ใช่จากแคช (ซึ่งเก็บคำตอบที่ไม่สมบูรณ์เอาไว้); โดยการประเมินค่าใช้จ่าย (estimate) จะคำนวณราคาส่วนนี้ด้วย คำสั่ง `sync --redo gaps` จะสั่งแปลข้อความลักษณะนี้ทุกข้อความ ไม่ว่าจะเกิดจากโมเดลใดก็ตาม หากคำตอบใหม่ยังคงขาดรูปแบบดังกล่าว ข้อความจะคงเดิม (โดยทำเครื่องหมายไว้ในแคตตาล็อก) และ `.champollion.lock` จะบันทึกว่าการตั้งค่าใดบ้างที่ให้คำตอบไม่ครบถ้วน เพื่อไม่ให้มีการถามซ้ำสำหรับการตั้งค่าเดิมกับข้อความเดิมอีก ([คู่มือ CI](/docs/guides/ci-cd#plural-gaps))

`verify` จะรายงานทั้งสองกรณีพร้อมคำสั่งซ่อมแซม สำหรับรูปแบบที่ใช้เฉพาะกับจำนวนที่มากกว่า 1000 หรือทศนิยมเท่านั้น (เช่น ภาษาฝรั่งเศสและสเปน `many` ที่ใช้สำหรับ 1 000 000) จะแสดงเป็นเพียงข้อความแจ้งเพื่อทราบ (info) ไม่ใช่คำเตือน เอนจินการแปลด้วยเครื่อง (DeepL, Google, …) ไม่สามารถรับคำสั่งได้ว่าต้องเขียนรูปแบบใดบ้าง ดังนั้นคำตอบจากเอนจินเหล่านี้จึงไม่มีการลองใหม่ — มีเพียงการรายงานผลเท่านั้น สำหรับไฟล์ i18next แต่ละรูปแบบที่ต้นฉบับไม่มี (เช่น ภาษาฝรั่งเศส `count_many` จากภาษาอังกฤษ) จะแยกเป็นคีย์ของตัวเอง โดยแปลจากข้อความ `_other`: สำหรับ LLM จะถูกขอให้แปลรูปแบบนั้น และ sync จะระบุไว้อย่างชัดเจน; ส่วนเอนจินการแปลด้วยเครื่อง ระบบจะแจ้งว่าค่านั้นเก็บรูปแบบ `other` ไว้

รัน `champollion integrity` เพื่อตรวจสอบความครบถ้วนของ plural ในทุก locale

## Terminology Enforcement

สำหรับคู่ที่มีการ coach พร้อม dictionary champollion จะรันการตรวจสอบ terminology หลังการแปล หลังจาก quality gate ผ่านแล้ว จะตรวจสอบว่า LLM ใช้คำศัพท์ที่กำหนดใน dictionary จริงหรือไม่

```
[TERM] en→fr: 2 term violation(s)
  • hero.title: "dashboard" → expected "tableau de bord" but got "panneau de contrôle"
```

การละเมิด terminology เป็น **คำเตือน ไม่ใช่ข้อผิดพลาดที่บล็อกการทำงาน** การแปลยังคงถูกเขียนลงดิสก์ ซึ่งเป็นเจตนา — LLM อาจมีเหตุผลที่ถูกต้องในการเลือกทางเลือกอื่น (บริบท ไวยากรณ์) และการบล็อกเมื่อคำศัพท์ไม่ตรงกันจะก่อให้เกิดผลเสียมากกว่าผลดี

หากต้องการแก้ไขการละเมิด ให้อัปเดต coaching dictionary หรือแก้ไขไฟล์ locale ด้วยตนเอง
