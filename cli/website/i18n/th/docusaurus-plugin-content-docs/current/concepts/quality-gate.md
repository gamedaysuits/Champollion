# Quality Gate

ทุกการแปลจะผ่านการตรวจสอบแบบ deterministic ก่อนที่จะถูกเขียนลงดิสก์ Quality gate จะตรวจจับความผิดพลาดที่พบบ่อยในการแปลด้วยเครื่อง — ไม่มี silent fallback ไม่มีข้อมูลที่ไม่ถูกต้องถูกเขียนลงไฟล์ locale ของคุณ

## การตรวจสอบ

| การตรวจสอบ | สิ่งที่ตรวจพบ | ป้ายกำกับ Gate |
|-------|----------------|-----------|
| **ว่างเปล่า/ช่องว่าง** | โมเดลส่งคืนสตริงว่างหรือช่องว่าง | `[GATE] empty` |
| **สะท้อนต้นฉบับ** | โมเดลส่งคืนอินพุตภาษาอังกฤษต้นฉบับ | `[GATE] source-echo` |
| **ลูปการหลอนข้อมูล** | รูปแบบไตรแกรมที่ซ้ำกัน (เช่น `"Qo' Qo' Qo'"`) | `[GATE] hallucination` |
| **ความยาวเพิ่มขึ้นผิดปกติ** | เอาต์พุตยาวกว่าต้นฉบับอย่างมีนัยสำคัญ | `[GATE] length` |
| **เนื้อหาถูกลบ** | เอาต์พุตคือต้นฉบับที่ถูกลบตัวอักษรออก | `[GATE] content` |
| **ความถูกต้องของระบบตัวเขียน** | ระบบตัวเขียนไม่ถูกต้องสำหรับ locale ปลายทาง | `[GATE] script` |
| **หมวดหมู่พหูพจน์ ICU** | ขาดรูปแบบพหูพจน์ที่จำเป็นสำหรับ locale | `[GATE] icu-plural` |

คีย์ที่ประกาศเป็น [`noTranslate`](/docs/getting-started/configuration#no-translate) จะไม่ถูกส่งไปยัง Gate — คีย์เหล่านี้จะถูกคัดลอกมาจากต้นฉบับทุกประการ ดังนั้นจึงไม่มีอะไรต้องตรวจสอบความถูกต้อง

### ว่างเปล่า/เว้นวรรค

ปฏิเสธการแปลที่เป็น string ว่าง มีแต่ whitespace หรือ `null` ตรวจจับโมเดลที่ไม่คืนค่าใดๆ สำหรับ key ที่แปลยาก

### Source Echo

ตรวจจับเมื่อโมเดลคืนค่าเป็นข้อความภาษาอังกฤษต้นฉบับแทนที่จะแปล พบบ่อยกับ string สั้นๆ และ prompt ที่ระบุรายละเอียดไม่เพียงพอ

สตริงสั้นๆ ที่ส่วนใหญ่เป็น ASCII (≤ 30 ตัวอักษร) จะได้รับการยกเว้น — `"Blog"`, `"GitHub"`, `"npm"` สามารถคงเป็นภาษาอังกฤษได้ในทุกที่อย่างถูกต้อง และการปฏิเสธสตริงเหล่านี้จะทำให้เกิดลูปไม่รู้จบ

ค่าที่ยาวกว่าซึ่งถูกต้องแม้ไม่มีการเปลี่ยนแปลง — เช่น URL, พาธของ repository, รหัสระบุผลิตภัณฑ์ — ไม่ใช่ปัญหาของ Gate และไม่สามารถแก้ไขได้ด้วยการปรับแต่ง Gate: คำตอบที่ถูกต้อง *คือ* การสะท้อนต้นฉบับ ดังนั้นทุกเอาต์พุตที่เป็นไปได้ของโมเดลจึงผิดทั้งหมด ให้ประกาศคีย์เหล่านั้นด้วย [`noTranslate`](/docs/getting-started/configuration#no-translate) แล้วคีย์เหล่านี้จะข้ามไปป์ไลน์ไปทั้งหมดโดยสมบูรณ์ คีย์ที่มีค่าเป็น URL จะถูกจัดการด้วยวิธีนี้โดยค่าเริ่มต้น

### Hallucination Loop

วิเคราะห์รูปแบบ trigram (3 ตัวอักษร) ในผลลัพธ์ หากมี trigram ใดซ้ำกันเกินจำนวน threshold เมื่อเทียบกับความยาวของผลลัพธ์ การแปลนั้นจะถูกปฏิเสธ ตรวจจับผลลัพธ์ที่ผิดปกติ เช่น `"Qo' Qo' Qo' Qo' Qo'"`

### Length Inflation

ปฏิเสธการแปลที่ความยาวของผลลัพธ์เกิน `maxLengthRatio × source length` (ค่าเริ่มต้น: 4×) ตรวจจับ hallucination ของโมเดลที่สร้างข้อความจำนวนมากสำหรับ input สั้นๆ

กำหนดค่าได้ผ่าน `maxLengthRatio` ในไฟล์ config ของคุณ

### เนื้อหาถูกลบ

ตรงข้ามกับความยาวเพิ่มขึ้นผิดปกติ โมเดลที่ไม่มีคำศัพท์สำหรับสตริงอาจลบทุกตัวอักษรที่ไม่สามารถแปลได้ และเหลือทิ้งไว้เพียงเครื่องหมายวรรคตอนและช่องว่างของต้นฉบับ:

```
"low-resource nmt · tokenizers · nêhiyawêwin"  →  "   ·   · êhiêi"
"the simple-builder approach"                  →  "  "
```

ไม่มีการตรวจสอบอื่นใดที่ตรวจพบสิ่งนี้ได้ มันไม่ได้ว่างเปล่า ไม่ได้สะท้อนต้นฉบับ ไม่ได้ซ้ำซาก และด้วย *ความยาว* 33% ของต้นฉบับ มันจึงผ่าน `minLengthRatio` ได้อย่างสบายๆ

การตรวจสอบนี้จะเปรียบเทียบ **ตัวอักษรของเนื้อหา** — ตัวอักษรและตัวเลข โดยละเว้นเครื่องหมายวรรคตอน ช่องว่าง และการจัดรูปแบบที่มองไม่เห็น — ระหว่างต้นฉบับและเอาต์พุต แต่ความหนาแน่นเพียงอย่างเดียวไม่สามารถใช้เป็นกฎได้ เนื่องจากระบบตัวเขียนที่มีความหนาแน่นอย่างถูกต้องก็อยู่ในจุดเดียวกันพอดี:

| ต้นฉบับ | เอาต์พุต | เนื้อหาที่คงอยู่ | คำตัดสิน |
|--------|--------|------------------|---------|
| `low-resource nmt · tokenizers · nêhiyawêwin` | `   ·   · êhiêi` | 14% | **ถูกปฏิเสธ** |
| `Getting started` | `入门` | 14% | ยอมรับ |
| `Frequently asked questions` | `常见问题` | 17% | ยอมรับ |

เกณฑ์ใดๆ ที่ตรวจจับกรณีแรกได้ จะปฏิเสธภาษาจีน ญี่ปุ่น และเกาหลีโดยทันที สิ่งที่แยกความแตกต่างระหว่างกรณีเหล่านี้ไม่ใช่ปริมาณที่เหลือรอด แต่เป็น *ที่มาของมัน*: เอาต์พุตที่กลวงโบ๋นั้นเป็น **ลำดับย่อย (subsequence)** ของต้นฉบับของมันเอง — ซึ่งสร้างขึ้นได้โดยการลบตัวอักษรออกจากต้นฉบับ — ในขณะที่คำแปลที่แท้จริงแทบจะไม่มีส่วนใดเหมือนกับต้นฉบับเลย การตั้งค่าสถานะ (flag) จำเป็นต้องใช้ **ทั้งสอง** สัญญาณ ดังนั้นการตรวจสอบนี้จึงเป็นเงื่อนไขที่จำเป็นแต่ไม่เพียงพอ (necessary-but-not-sufficient) ในทำนองเดียวกับตัวตรวจจับการซ้ำซาก

สามารถกำหนดค่าได้ผ่าน `minContentRetention` (ค่าเริ่มต้น `0.35`) ต่อคู่ภาษาหรือต่อภาษา การเพิ่มค่านี้จะทำให้การตรวจสอบทำงานไวขึ้น; โดยมันจะทำงานควบคู่ไปกับสัญญาณลำดับย่อยเท่านั้น

:::note[นี่คือสัญญาณของคำศัพท์ ไม่ใช่ตัวปรับคุณภาพ]
เมื่อสิ่งนี้ทำงานซ้ำๆ สำหรับภาษาปลายทางภาษาใดภาษาหนึ่ง แสดงว่าโมเดลไม่มีคำศัพท์สำหรับข้อความนั้น — ซึ่งมักจะเป็นสตริงสั้นๆ ที่เต็มไปด้วยศัพท์เฉพาะในภาษาที่มีคลังคำศัพท์แบบปิด การผ่อนปรนเกณฑ์จะทำให้เกิดการเสียหายแบบเงียบๆ (silent corruption) กลับมา; มันไม่ได้ช่วยสร้างคำแปลแต่อย่างใด คุณควรแก้ไขพรอมต์ ข้อมูลการสอน (coaching data) หรือคู่ภาษา
:::

### Script Compliance

สำหรับ locale ที่การ์ดภาษา (language card) ระบุว่าเป็นระบบตัวเขียนที่ไม่ใช่ละติน (อาหรับ, CJK, ซีริลลิก, …) จะมีการตรวจสอบว่าเอาต์พุตมีตัวอักษรที่ไม่ใช่ ASCII อยู่จริง — เอาต์พุตที่มีเฉพาะอักษรละตินสำหรับ locale เหล่านั้นจะถูกปฏิเสธเนื่องจากระบบตัวเขียนไม่ถูกต้อง

คำชี้แจงสองประการเกี่ยวกับสิ่งที่การตรวจสอบนี้ *ไม่ได้* เป็น:

- มัน **ไม่ได้ถูกควบคุมโดยฟิลด์การกำหนดค่า `script:`** ฟิลด์นั้นจะเลือกอักขรวิธีของเอาต์พุตสำหรับ [การแปลงระบบตัวเขียน](/docs/getting-started/configuration#script-conversion); ความคาดหวังของ Gate นั้นมาจากการ์ดภาษา
- มันจะตรวจสอบความถูกต้องของ **ระบบตัวเขียนขณะทำงาน (working script) ที่โมเดลส่งออกมา** เสมอ *ก่อน* ที่จะมีการแปลงระบบตัวเขียนใดๆ Locale ที่มีตัวแปลงระบบตัวเขียน (crk, sr, tlh, …) จะสร้างเอาต์พุตระบบตัวเขียนขณะทำงานเป็นอักษรละตินอย่างถูกต้อง ดังนั้นจึงได้รับการยกเว้นจากการตรวจสอบนี้; การแปลง — หากการกำหนดค่าเลือกที่จะทำ — จะเกิดขึ้นหลังจากผ่าน Gate แล้ว

## สิ่งที่เกิดขึ้นเมื่อล้มเหลว

1. การแปลที่ล้มเหลวจะถูก log ไปยัง stderr พร้อมคำนำหน้า `[GATE]` ชื่อ key เหตุผล และตัวอย่างของค่านั้น
2. Key นั้น **จะไม่** ถูกเขียนลงไฟล์ locale
3. retry cascade จะเริ่มทำงาน (ดูด้านล่าง)

```
[GATE] hero.title: source-echo — "Welcome to our platform"
[GATE] nav.about: hallucination — "À À À À À À À À"
```

## การลองใหม่พร้อมฟีดแบ็ก (Feedback Retry) และการลองใหม่แบบลดหลั่น (Retry Cascade)

คีย์ที่ถูกปฏิเสธโดย Gate จะได้รับ **การลองใหม่พร้อมฟีดแบ็กหนึ่งครั้ง**: เหตุผลที่ถูกปฏิเสธจะถูกแทรกเข้าไปในพรอมต์เป็นบริบทเฉพาะคีย์ (การลองใหม่แบบสุ่มสี่สุ่มห้าที่อุณหภูมิต่ำจะส่งคืนเอาต์พุตที่เหมือนกันทุกไบต์) หากการลองใหม่ผ่าน คีย์นั้นจะถูกเขียนและสถานะการซิงค์จะเป็น **สีเขียว** — การปฏิเสธของ Gate ที่สามารถรักษาตัวเองได้ (self-heals) ไม่ถือเป็นความล้มเหลว และนี่คือความหมายที่ตั้งใจไว้ มีเพียงคีย์ที่ยังคงล้มเหลวหลังจากการลองใหม่เท่านั้นที่จะถูกข้ามไป ถูกรายงาน (การซิงค์ออกด้วยค่าที่ไม่ใช่ศูนย์) และถูกพยายามใหม่อีกครั้งในการซิงค์ครั้งถัดไป

การลองใหม่จะทำงานผ่านวิธีการแปลของคู่ภาษานั้นๆ ไม่ว่าจะเป็นอะไรก็ตาม — LLM, Google Translate, DeepL หรือผู้ให้บริการโดยตรง นอกจากนี้ยังนำไปใช้กับข้อมูลที่ตรงกันในหน่วยความจำการแปล (Translation Memory) ด้วย: ค่าในแคชที่ Gate ปฏิเสธจะถูกขับออกและแปลใหม่ในการทำงานรอบเดียวกัน ดังนั้นแคชที่เป็นพิษ (poisoned cache) จึงสามารถรักษาตัวเองได้

ในอีกกรณีหนึ่ง เมื่อแบตช์ทั้งหมดล้มเหลว (ข้อผิดพลาดในการแยกวิเคราะห์ JSON) champollion จะลองใหม่ด้วยขนาดแบตช์ที่เล็กลงเรื่อยๆ:

```
Full batch (80 keys) → parse error
  └→ Half batch (40 keys) → 2 failures
      └→ Individual keys (1 each) → isolates the 2 problem keys
```

งบประมาณการลองใหม่ถูกจำกัดด้วย `maxRetries` (ค่าเริ่มต้น: 3 กำหนดค่าได้ต่อภาษา) เพื่อป้องกันการใช้ token มากเกินไปกับ key ที่ล้มเหลวซ้ำๆ

หลังจากใช้การลองใหม่หมดแล้ว key ที่มีปัญหาจะถูก log และข้ามไป โดยจะถูกลองใหม่ในการรัน `sync` ครั้งถัดไป

## Prompt Caching

system message (register กฎไวยากรณ์ หมายเหตุสไตล์) จะถูกแยกออกจาก user message (key ที่ต้องการแปล) การแยกนี้มีเหตุผล:

- system message **เหมือนกันทุก batch** สำหรับ locale ที่กำหนด
- Provider อย่าง Anthropic และ Google จะ cache system message ที่ซ้ำกัน
- ผลลัพธ์: batch แรกจ่าย token cost เต็มจำนวน batch ถัดไปจ่ายเฉพาะ user message

สิ่งนี้สามารถลดต้นทุน token ได้อย่างมีนัยสำคัญสำหรับโปรเจกต์ที่มี batch จำนวนมาก

## ICU MessageFormat Validation

คำสั่ง `integrity` จะตรวจสอบรูปแบบ ICU MessageFormat plural กับกฎ CLDR plural หากไฟล์ต้นฉบับของคุณใช้ ICU syntax เช่น:

```json
"items": "{count, plural, one {# item} other {# items}}"
```

Champollion จะตรวจสอบว่าเวอร์ชันที่แปลแล้วมีหมวดหมู่ plural ที่จำเป็นทั้งหมดสำหรับ locale เป้าหมาย ตัวอย่างเช่น ภาษาอาหรับต้องการหกหมวดหมู่ (`zero`, `one`, `two`, `few`, `many`, `other`) — ไม่ใช่แค่ `one` และ `other`

รัน `champollion integrity` เพื่อตรวจสอบความครบถ้วนของ plural ในทุก locale

## Terminology Enforcement

สำหรับคู่ที่มีการ coach พร้อม dictionary champollion จะรันการตรวจสอบ terminology หลังการแปล หลังจาก quality gate ผ่านแล้ว จะตรวจสอบว่า LLM ใช้คำศัพท์ที่กำหนดใน dictionary จริงหรือไม่

```
[TERM] en→fr: 2 term violation(s)
  • hero.title: "dashboard" → expected "tableau de bord" but got "panneau de contrôle"
```

การละเมิด terminology เป็น **คำเตือน ไม่ใช่ข้อผิดพลาดที่บล็อกการทำงาน** การแปลยังคงถูกเขียนลงดิสก์ ซึ่งเป็นเจตนา — LLM อาจมีเหตุผลที่ถูกต้องในการเลือกทางเลือกอื่น (บริบท ไวยากรณ์) และการบล็อกเมื่อคำศัพท์ไม่ตรงกันจะก่อให้เกิดผลเสียมากกว่าผลดี

หากต้องการแก้ไขการละเมิด ให้อัปเดต coaching dictionary หรือแก้ไขไฟล์ locale ด้วยตนเอง
