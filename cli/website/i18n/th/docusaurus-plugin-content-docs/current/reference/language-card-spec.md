# ข้อกำหนดการ์ดภาษา

> **แหล่งข้อมูลความจริงจุดเดียว** เอกสารนี้กำหนดโครงสร้างมาตรฐาน (canonical shape) ของ
> การ์ดภาษาทุกใบ การ์ดจะระบุเฉพาะสิ่งที่แหล่งข้อมูลที่อ้างอิงระบุไว้เท่านั้น: ฟิลด์ที่ไม่มี
> แหล่งข้อมูลใดระบุจะถูก **ละไว้ ไม่ใช่ค่า null** — ฟิลด์ที่ขาดหายไปหมายถึง
> "ไม่มีแหล่งข้อมูลใดกล่าวถึง" ไม่เคยหมายถึง "ไม่มีอะไรให้รับรู้" สกีมาที่เครื่องสามารถ
> ตรวจสอบได้จะจัดส่งมาในรูปแบบ `shared/schemas/language-card.schema.json` ในแพ็กเกจ npm
> และ [ตัวอย่างมาตรฐานด้านล่าง](#canonical-template) ได้รับการสร้างขึ้นจาก
> คลังข้อมูลจริงในทุกครั้งที่มีการบิลด์ไซต์ ดังนั้นหน้านี้จึงไม่มีทางคลาดเคลื่อน
> ไปจากการ์ดที่อธิบายไว้อย่างแน่นอน

## การสร้าง Atlas ใหม่รอบ 2026-08 — สิ่งที่เปลี่ยนแปลงในสกีมานี้

ตอนนี้คลังข้อมูลการ์ด (card corpus) คือ **ผลลัพธ์จากการบิลด์ (build output)**: การ์ดทุกใบถูกโปรเจกต์ (project) มาจากที่จัดเก็บ
สแนปช็อตต้นน้ำที่ตรึงเวอร์ชันไว้ และถูกสร้างขึ้นใหม่เสมอ — ไม่มีการแก้ไขโดยตรง — เมื่อ
ข้อเท็จจริงมีการเปลี่ยนแปลง สิ่งที่เปลี่ยนไปในรูปแบบโครงสร้างจากการสร้างใหม่ครั้งนี้มี 4 ประการ:

1. **ฟิลด์ที่มีข้อโต้แย้งจะมี Attribution Envelope กำกับไว้** ในจุดที่แหล่งข้อมูลที่อ้างอิง
   มีความเห็นไม่ตรงกันอย่างแท้จริง ฟิลด์จะไม่เป็นค่าเดี่ยว (flat value) แต่จะเป็น
   `{"agreement": "...", "consensus": <value?>, "values": [{"value": ...,
   "source": "..."}]}`. This applies to `name`, `classification.family`,
   `speakerEstimates`, `endangerment` และฟิลด์ใดก็ตามที่มีแหล่งข้อมูลใหม่ทำให้เกิดข้อโต้แย้ง
   ผู้ใช้งานควรอ่านการ์ดผ่านอะแดปเตอร์ที่เผยแพร่ไว้
   (`normalizeCard()` ในแพ็กเกจ npm) แทนที่จะสันนิษฐานว่าเป็นค่าเดี่ยว —
   `display()` จะแปลง envelope ให้เป็นค่าที่มีความเห็นพ้อง และตั้งใจ
   ไม่คืนค่าใดๆ เมื่อมีข้อโต้แย้งอย่างแท้จริง แทนที่จะเลือกข้างใดข้างหนึ่ง

2. **ฟิลด์ที่เปลี่ยนชื่อ** `endonym` แทนที่ `nativeName` · `codeAliases`
   แทนที่ `aliases` · `scripts[]` (ระบบการเขียนทั้งหมดที่มีหลักฐานรับรอง) แทนที่ฟิลด์เดี่ยว
   `script` โดยระบบการเขียนหลักจะอนุมานมาจากแท็ก BCP 47 สูงสุดของการ์ด · `endangerment` (การประเมินของทุกแหล่งข้อมูล
   ตามสเกลของแหล่งข้อมูลนั้นๆ) แทนที่ออบเจกต์ `vitality` เดี่ยว · `isoLanguageType` และ
   `isoScope` ขณะนี้ใช้คำของ ISO 639-3 โดยตรง ("Living", "Macrolanguage")
   แทนที่จะใช้อักษรย่อ ฟิลด์ใหม่: `modality` ("spoken"/"signed" อนุมาน
   มาจากสายวิวัฒนาการของ Glottolog), `glottologBucket` (หมวดหมู่ที่ไม่เกี่ยวกับสายสัมพันธ์ทางพันธุกรรมของ Glottolog ซึ่งแยกออกจากช่องตระกูลภาษา), `locale`/`localeScoped`

3. **ฟิลด์ที่ไม่มีการระบุข้อเท็จจริงจะถูกละไว้ ไม่ใช่ค่า null** ฟิลด์ที่ไม่มีแหล่งข้อมูลใดกล่าวอ้าง
   จะไม่มีอยู่ในการ์ด กฎข้อเดิมก่อนหน้านี้ ("การ์ดทุกใบต้องมีทุกฟิลด์ระดับบนสุด
   แม้ว่าจะเป็นค่า null ก็ตาม") ถูกยกเลิกแล้ว: ค่าว่างบนอินเทอร์เฟซสาธารณะจะดูเหมือน
   เป็นการอ้างว่าไม่มีสิ่งใดให้รับรู้ ซึ่งไม่เหมือนกับการที่ยังไม่ได้สำรวจ

4. **การมีอยู่ของการ์ดโลแคล (Locale card)** นอกเหนือจากการ์ดภาษาแล้ว การโปรเจกต์โลแคล
   (`fra-CA`, `cmn-Hant`) จะเก็บข้อเท็จจริงของภาษาที่ถูกแปลงให้เจาะจงสำหรับ
   ดินแดนหรือระบบการเขียนนั้นๆ โดยระบุตัวตนด้วยบล็อก `locale: {language, region, script}`
   ทั้งนี้ โลแคลไม่ใช่ภาษา: โปรดคัดแยกโลแคลออกจากการนับจำนวนภาษา
   โดยอิงจากบล็อกดังกล่าว

## หลักการออกแบบ

1. **อ้างอิงแหล่งที่มาของทุกสิ่ง** ข้อกล่าวอ้างข้อเท็จจริงทุกรายการต้องย้อนรอยไปยังแหล่งข้อมูล
   ปฐมภูมิที่มีการระบุชื่อและเวอร์ชันอย่างชัดเจน ข้อกล่าวอ้างที่ไม่มีแหล่งที่มาคือข้อกล่าวอ้างที่ไม่สามารถตรวจสอบได้
   แมป `_fieldSources` (และคำอธิบาย `source` รายฟิลด์ในออบเจกต์ย่อย)
   จะช่วยระบุที่มาอย่างชัดเจน

2. **รักษาความเห็นต่างไว้** เมื่อหน่วยงานอ้างอิงมีความเห็นไม่ตรงกัน (แหล่งข้อมูลหนึ่งระบุว่า
   มีผู้พูด 50,000 คน อีกแห่งระบุว่า 20,000 คน) การ์ดจะจัดเก็บ *ทั้งสองค่า*
   พร้อมการระบุแหล่งที่มา — ตามรูปแบบโครงสร้าง envelope ข้างต้น เราจะไม่หาค่าเฉลี่ย ไม่ตัดสินชี้ขาด หรือ
   เลือกข้างใดข้างหนึ่ง เพื่อให้ผู้ใช้สามารถพิจารณารายละเอียดเชิงลึกได้ด้วยตนเอง

3. **การไม่ปรากฏหมายถึงไม่มีการระบุข้อเท็จจริง** ฟิลด์ที่ขาดหายไปหมายถึงไม่มีแหล่งข้อมูลใดระบุ
   ค่าไว้ เมื่อคุณสมบัติหนึ่งๆ ไม่สามารถใช้ได้กับภาษานั้นจริงๆ (เช่น เพศทางไวยากรณ์
   สำหรับภาษาที่ไม่มีระบบนี้) ค่าที่อ้างอิงจะระบุไว้อย่างชัดเจนแทนที่จะปล่อยว่างไว้

4. **สร้างใหม่เสมอ ไม่มีการปะแก้ (patch)** การ์ดจะถูกโปรเจกต์จากแหล่งข้อมูลที่ตรึงเวอร์ชันไว้
   ด้วยกระบวนการบิลด์แบบดีเทอร์มินิสติก (deterministic build) ข้อผิดพลาดของข้อเท็จจริงจะได้รับการแก้ไขที่ตัวจัดการแหล่งข้อมูล (source handler)
   แล้วจึงบิลด์คลังข้อมูลใหม่ — ไม่มีการแก้ไขไฟล์โดยตรง ณ จุดเดิม และไม่มีเลเยอร์เสริมข้อมูลแบบผสานรวมอย่างเดียว

## โมเดลการสืบทอด

> **แทบจะกลายเป็นประวัติศาสตร์ไปแล้วนับตั้งแต่การสร้าง Atlas ใหม่** ไม่มีการ์ดภาษาใดบนดิสก์
> ที่มี `extends` อยู่อีกต่อไป — การ์ดทุกใบถูกสร้างขึ้นอย่างสมบูรณ์ (materialized) จากการบิลด์
> เนื่องจากการสืบทอดข้อความอธิบายนั้นไม่สามารถอ้างอิงแหล่งที่มาได้ (ข้อกล่าวอ้างระดับตระกูลภาษากลับไปใช้ที่อยู่ระดับภาษา)
> ตัวกลไกนี้ยังคงหลงเหลืออยู่ในจุดเดียว: บันเดิลออฟไลน์ของแพ็กเกจ npm
> จะส่งมอบการ์ดโลแคลในรูปแบบผลต่าง (delta) ขนาดกะทัดรัดของ `extends` เทียบกับภาษาหลัก
> ซึ่งจะถูกแปลงผ่านการผสานรวมแบบเดียวกับที่อธิบายไว้ที่นี่

เมื่อการ์ดกำหนด `"extends": "family-dravidian"` รันไทม์จะรวมการ์ดหลัก
เข้ากับการ์ดลูกโดยใช้ `_deepMerge()` (ใน `lib/registers.js`) ซึ่งช่วยให้
การ์ด genus กำหนด register ที่ใช้ร่วมกัน ระบบความเป็นทางการ และแนวทางเรื่องเพศ
ที่ส่งต่อไปยังภาษาสมาชิกทั้งหมด โดยไม่ต้องทำซ้ำข้อมูลในการ์ดแต่ละใบหลายร้อยใบ

### ความหมายของการรวม

| ค่าของการ์ดลูก | พฤติกรรม | เหตุผล |
|-------------|----------|-----|
| `null` | สืบทอดจากการ์ดหลัก | `null` หมายถึง "ฉันไม่ได้กำหนดค่านี้" — ค่าของการ์ดหลักจะถูกนำมาใช้ |
| ไม่ใช่ null | แทนที่การ์ดหลัก | ข้อมูลของการ์ดลูกเฉพาะเจาะจงกว่า — มีความสำคัญสูงกว่า |
| ออบเจกต์ซ้อน | รวมแบบเรียกซ้ำ | ฟิลด์ของการ์ดลูกแทนที่ ฟิลด์ของการ์ดหลักถูกเก็บไว้ |
| อาร์เรย์ | แทนที่ทั้งหมด | อาร์เรย์ไม่รวมทีละรายการ — อาร์เรย์ของการ์ดลูกชนะ |

### ฟิลด์อัตลักษณ์ (ไม่สืบทอดเด็ดขาด)

ฟิลด์บางฟิลด์เป็นของการ์ดนั้นเองและต้องไม่สืบทอดจากการ์ดหลักเด็ดขาด:

```
code, extends, _migration, aliases, iso639_1, iso639_3
```

แม้ว่าการ์ดหลักจะกำหนด `aliases: ["macro-code"]` การ์ดลูกจะไม่
สืบทอด alias เหล่านั้น ฟิลด์เหล่านี้เป็นค่าของการ์ดลูกเสมอ (รวมถึง
`null` หากไม่ได้กำหนดไว้)

**เหตุผล:** หากไม่มีกฎนี้ ภาษา Cree ทุกภาษาจะสืบทอด `aliases: ["cre"]`
จากการ์ดหลัก macrolanguage ทำให้ทุกสำเนียงกลายเป็น alias ของ macro

### ตัวอย่าง: วิธีที่การ์ด Cree ถูก Resolve

```
┌───────────────────────┐
│  family-algic.json    │  formality: null, registers: null
│  (no registers)       │
└──────────┬────────────┘
           │ extends
┌──────────┴────────────┐
│  genus-cree.json      │  formality: { system: "obviative-animate", ... }
│  (sourced registers)  │  registers: { formal: {...}, informal: {...} }
└──────────┬────────────┘
           │ extends
┌──────────┴────────────┐
│  crk.json             │  code: "crk", extends: "genus-cree"
│  (Plains Cree)        │  formality: null → inherits from genus-cree
│                       │  registers: null → inherits from genus-cree
│                       │  script: "Cans"  → own value, no inheritance
│                       │  code: "crk"     → identity field, never inherited
└───────────────────────┘
```

ในรันไทม์ `getLanguageCard("crk")` จะคืนค่าออบเจกต์ที่รวมแล้วพร้อม register ของ genus-cree
+ คุณสมบัติของ family-algic (ถ้ามี) + อัตลักษณ์และ metadata ของ crk เอง

### เทมเพลตการ์ด Genus

การ์ด Genus อยู่ใน `shared/language-cards/genera/` และกำหนดคุณสมบัติที่ใช้ร่วมกัน
สำหรับกลุ่มภาษา โดยใช้ schema เดียวกับการ์ดปกติแต่มีข้อตกลงที่แตกต่างกัน:

```jsonc
{
  // Identity — genus cards use a prefixed code, NOT an ISO 639-3 code
  "code": "genus-cree",           // "genus-", "family-", or "macrolanguage-" prefix
  "name": "Cree Languages",      // Human-readable group name
  "extends": "family-algic",     // Genus cards can extend family cards (chaining)

  // Formality — shared across the group, sourced from typological databases
  "formality": {
    "system": "obviative-animate",
    "description": "Cree languages use an obviative/proximate system...",
    "default": "formal",
    "source": "WALS 37A, 38A + Wolfart 1973"
  },

  // Registers — shared presets, if the group shares a formality system
  "registers": {
    "formal": {
      "label": "Formal (Proximate)",
      "description": "...",
      "prompt": "...",
      "isDefault": true
    },
    "informal": {
      "label": "Informal",
      "description": "...",
      "prompt": "..."
    }
  },

  // Gender — shared grammatical gender behavior
  "gender": {
    "grammatical": false,       // Cree doesn't have grammatical gender
    "inclusiveGuidance": null   //   so no inclusive guidance needed
  },

  // Everything else is null — individual cards provide their own
  // classification, geography, resources, etc.
  "classification": null,
  "methodSupport": null,
  // ...
}
```

**กฎสำคัญ:** การ์ด Genus ต้องมีเฉพาะข้อมูลที่ใช้ร่วมกันจริงๆ ทั่วทั้งกลุ่ม
และอ้างอิงจากแหล่งข้อมูลที่น่าเชื่อถือเท่านั้น หากระบบความเป็นทางการแตกต่างกันระหว่างสมาชิก
ควรระบุในการ์ดแต่ละใบ ไม่ใช่ใน genus

## ตัวอย่างมาตรฐาน \{#canonical-template}

> **สร้างขึ้นโดยอัตโนมัติ ไม่ได้เขียนขึ้นเอง** ทุกสิ่งในส่วนนี้ถูกดึงมาจาก
> คลังข้อมูลจริง ณ เวลาบิลด์: การ์ด `crk` (Plains Cree) ฉบับสมบูรณ์
> แบบไบต์ต่อไบต์ พร้อมด้วยส่วนตัดตอนของโลแคล `fra-CA` เมื่อคลังข้อมูลถูกบิลด์ใหม่
> การบิลด์ไซต์ครั้งถัดไปจะดึงข้อมูลมาสร้างหน้านี้ใหม่ จะไม่มีเทมเพลตที่ต้องดูแลด้วยมือหลงเหลือ
> ให้ล้าสมัยอีกต่อไป — เทมเพลตก่อนหน้านี้คลาดเคลื่อนตามหลังการ์ดไปหนึ่งเจเนอเรชันของสกีมา
> และถูกยกเลิกไปเมื่อ 2026-08-16

ตัวอย่างนี้แสดง **โครงสร้างบนดิสก์** — สิ่งที่คุณจะได้เห็นเมื่อเปิดไฟล์ขึ้นมา
ผู้ใช้งานยังควรอ่านการ์ดผ่านอะแดปเตอร์ที่เผยแพร่ไว้
(`normalizeCard()` ในแพ็กเกจ npm): ซึ่งจะช่วยแปลง envelope เชื่อมโยงชื่อเก่า
ก่อนการเปลี่ยนผ่าน และแปลงค่าที่ใช้สำหรับการแสดงผลเท่านั้น (ระบบการเขียนหลัก ระดับความมีชีวิตของภาษา)
ซึ่งการ์ดดิบตั้งใจไม่บรรจุไว้

ข้อสังเกตขณะอ่าน:

1. **Attribution envelopes** `name`, `classification.family`,
   `endangerment`, `speakerEstimates`, `endonym`, `bcp47FullTag` และ
   `politenessDistinction` แต่ละรายการจะมี `{agreement, consensus?, values:
   [{value, source}]}`, every value attributed to its source. `endangerment`
   มี `"agreement": "incommensurable"`: เนื่องจากแหล่งข้อมูลประเมินบนสเกลที่แตกต่างกัน
   ดังนั้นแต่ละค่าจึงระบุ `scale` ของตน แทนที่จะถูกแปลงไปเป็นสเกลของค่าที่ชนะ

2. **การละไว้หมายถึงไม่มีการระบุข้อเท็จจริง** การ์ดนี้ไม่มี `iso639_1` (Plains Cree ไม่มี
   รหัส ISO 639-1) และไม่มี `phonologicalInventory` (ไม่มีแหล่งข้อมูลที่นำเข้าใดระบุไว้) —
   ฟิลด์เหล่านี้จึงไม่มีอยู่เฉยๆ ไม่เคยเป็น `null` หรือ `[]`

3. **ที่มาของข้อมูล (Provenance) เป็นเลเยอร์ชั้นหนึ่ง** `_fieldSources` จะแมปทุกฟิลด์ไปยัง
   แหล่งข้อมูลที่ระบุค่านั้น พร้อมระบุ `champollion-derived-v1` เพื่อทำเครื่องหมาย
   ค่าที่ Champollion คำนวณขึ้นมา ส่วน `_card` จะประทับประเภท รหัส การแก้ไขของการ์ด
   และฟิลด์ที่ช่องทางการแก้ไข (correction lane) สามารถปรับปรุงได้; `_atlas` จะประทับการเผยแพร่ของคลังข้อมูล

4. **ไม่มีผลลัพธ์จากการรัน (Run results)** ไม่มีสิ่งใดบนการ์ดที่เป็นคะแนนวัดผลลัพธ์
   ของวิธีการแปล — chrF อัตราการยอมรับของ FST และผลลัพธ์ประเภทเดียวกันเป็นผลจากการรันที่ระบุคีย์ด้วย
   (method, dataset, metric) และจะอยู่บนลีดเดอร์บอร์ด การ์ดจะระบุเพียงแค่ว่า
   ทรัพยากรเหล่านั้น *มีอยู่จริง* หรือไม่เท่านั้น (`resources`, `lexicalResources`,
   `methodSupport`)

### การ์ดโลแคลคือการโปรเจกต์ ไม่ใช่ภาษา \{#locale-card-example}

ข้างๆ การ์ดภาษาจะมีการ์ดโลแคล (`fra-CA`, `cmn-Hant`): ข้อเท็จจริงของภาษาที่
**ถูกแปลงให้เจาะจงสำหรับดินแดนหรือระบบการเขียน** โดยระบุตัวตนด้วยบล็อก

## ข้อมูลอ้างอิงฟิลด์ (Field Reference) \{#field-reference}

ข้อตกลงร่วมกันสองประการที่ใช้กับทุกตารางด้านล่าง:

- **"envelope"** หมายถึง Attribution Envelope — `{agreement, consensus?,
  values: [{value, source, note?, scale?}]}` — ซึ่งบรรจุข้อกล่าวอ้างของ *ทุก* แหล่งข้อมูล
  ฟิลด์ที่ระบุเป็น `envelope` อาจปรากฏเป็นค่าเดี่ยว (flat value) บนการ์ดที่มี
  แหล่งข้อมูลกล่าวถึงเพียงแห่งเดียว (ตัวอย่างเช่น ภาษาเฉพาะใน Glottolog จะมีค่าเดี่ยว
  `name`) ผู้ใช้งานจะต้องจัดการได้ทั้งสองรูปแบบ ซึ่งเป็นสิ่งที่อะแดปเตอร์ที่เผยแพร่ไว้จัดการให้อยู่แล้ว
- ไม่มีฟิลด์ใดที่จำเป็นต้องมีนอกเหนือจาก `code` และ `name` ส่วนฟิลด์อื่นๆ ทั้งหมดจะ
  **ถูกละไว้เมื่อไม่มีแหล่งข้อมูลใดระบุ** แหล่งข้อมูลที่ระบุในแต่ละฟิลด์จะถูกบันทึกไว้
  แยกตามการ์ดใน `_fieldSources` ดังนั้นตารางจึงอธิบายถึง *ประเภท* ของแหล่งข้อมูล
  แทนที่จะตรึงเวอร์ชันซึ่งอาจล้าสมัยได้ในอนาคต

### § 1. ฟิลด์อัตลักษณ์

| ฟิลด์ | รูปแบบ | หมายเหตุ |
|-------|-------|-------|
| `code` | `string` | **จำเป็นต้องมี** รหัสของการ์ดและชื่อไฟล์ ใช้ ISO 639-3 สำหรับการ์ดภาษา (`crk`); ภาษาเฉพาะใน Glottolog จะใช้ glottocode; การ์ดโลแคลจะใช้รหัสโลแคล (`fra-CA`) |
| `name` | envelope | **จำเป็นต้องมี** ชื่ออ้างอิงภาษาอังกฤษ (ISO 639-3 registry, LinguaMeta, Glottolog) |
| `endonym` | envelope | มาแทนที่ `nativeName` ชื่อที่ผู้พูดใช้เรียกภาษาของตนในภาษานั้นๆ (LinguaMeta, Wikidata) จะไม่มีอยู่เมื่อไม่มีแหล่งข้อมูลใดระบุไว้ — เราจะไม่คิดค้นหรือทับศัพท์ชื่อภาษาท้องถิ่นขึ้นมาเองโดยเด็ดขาด |
| `alternateNames` | `string[]` | ชื่อภาษาอังกฤษอื่นๆ ที่มีหลักฐานรับรอง |
| `iso639_1` | `string` | มีอยู่เฉพาะเมื่อมีรหัสสองตัวอักษร ISO 639-1 เท่านั้น (`fra` → `"fr"`) |
| `isoScope` | `string` | คำเฉพาะของ ISO 639-3 เอง — `"Individual"`, `"Macrolanguage"`, `"Special"` (แทนที่อักษรย่อ `"I"`/`"M"`/`"S"`) |
| `isoLanguageType` | `string` | มาแทนที่ `isoType` คำเฉพาะของ ISO 639-3 เอง — `"Living"`, `"Extinct"`, `"Ancient"`, `"Historical"`, `"Constructed"` |
| `macrolanguage` | `string` | ภาษามาโคร (Macrolanguage) ที่ภาษานี้สังกัดอยู่ (`crk` → `"cre"`) การแมปภาษามาโครของ ISO 639-3 |
| `macrolanguageMembers` | `string[]` | บนการ์ดศูนย์กลางของภาษามาโคร: รหัสของภาษาสมาชิกแต่ละภาษา (`nor` → `["nno", "nob"]`) |
| `canonicalisedMembers` | envelope | บนการ์ดภาษามาโคร: สมาชิกที่รีจิสทรี BCP 47 ยุบรวมแท็กเข้ากับแท็กของภาษามาโครนี้ (ตารางนามแฝงของ CLDR + SIL langtags โดยแต่ละรายการมีการระบุแหล่งที่มา) |
| `supersededCodes` | `string[]` | รหัส ISO 639-3 ที่ยกเลิกแล้วซึ่งปัจจุบัน SIL กำหนดให้ชี้มาที่ภาษานี้ — บันทึกไว้บนภาษาที่เป็นตัวสืบทอดเพื่อให้คลังข้อมูลที่เผยแพร่ภายใต้รหัสเดิมยังคงแปลงค่าได้ |
| `codeAliases` | `string[]` | มาแทนที่ `aliases` ตัวระบุระดับรหัสที่แปลงค่ามายังการ์ดนี้ |
| `bcp47` | `string` | แท็ก BCP 47 ของภาษาตามที่ระบุไว้ (LinguaMeta) |
| `bcp47Tag` | envelope | ค่าที่ได้จากการคำนวณของ Champollion: แท็ก RFC 5646 (รหัส ISO 639 ที่สั้นที่สุดจะชนะ) |
| `bcp47FullTag` | envelope | รูปแบบภาษา–ระบบการเขียน–ภูมิภาคแบบสูงสุด (maximal language–script–region form) (CLDR likelySubtags + SIL langtags) อะแดปเตอร์จะอนุมาน **ระบบการเขียนหลัก** จากแท็กนี้ |
| `modality` | `string` | `"spoken"` หรือ `"signed"` อนุมานมาจากสายวิวัฒนาการของ Glottolog การเขียนเป็นคุณลักษณะของระบบการสะกดคำ ไม่ใช่รูปแบบการสื่อสาร (modality) — ภาษาที่ไม่มีการเขียนก็ยังคงเป็นภาษาพูดหรือภาษามือโดยสมบูรณ์ |
| `locale` | `object` | **เฉพาะการ์ดโลแคลเท่านั้น** `{language, region, script, publishedTag, source, note}` — ตัวระบุตัวตนของโลแคล โปรดคัดแยกการ์ดโลแคลออกจากการนับจำนวนภาษาโดยอิงตามบล็อกนี้ ห้ามใช้รูปแบบของรหัสเป็นเกณฑ์เด็ดขาด |
| `localeScoped` | `object` | เฉพาะการ์ดโลแคลเท่านั้น: ค่าที่ถูกแปลงให้เจาะจงสำหรับดินแดน/ระบบการเขียนของโลแคล (เช่น `scriptName`, `cldrOfficialStatus`) |

### § 2. ฟิลด์การจำแนกประเภท

| ฟิลด์ | รูปแบบ | หมายเหตุ |
|-------|-------|-------|
| `glottocode` | `string` | ตัวระบุของ Glottolog สำหรับ languoid นี้ (`crk` → `"plai1258"`) ภาษาที่มีเฉพาะใน Glottolog — ภาษาที่ Glottolog บันทึกไว้แต่ไม่มีใน ISO 639-3 — จะใช้ glottocode เป็น `code` ของการ์ด |
| `classification` | `object` | คอนเทนเนอร์สำหรับฟิลด์ตำแหน่งทางอนุกรมวิธานด้านล่าง แต่ละฟิลด์มีแหล่งที่มาแยกจากกันและอาจละเว้นได้โดยอิสระ — ภาษาโดดเดี่ยว (isolate) หรือภาษาที่จัดอยู่ในหมวดหมู่ทั่วไปของ Glottolog จะมีข้อมูลเพียงบางส่วนของออบเจกต์นี้อย่างถูกต้องตามหลักวิชา |
| `classification.family` | envelope | ตระกูลภาษาระดับบนสุดที่หน่วยงานจัดหมวดหมู่แต่ละแห่งระบุ Glottolog และ WALS เป็นระบบอนุกรมวิธานที่แยกจากกันและอาจไม่เห็นพ้องกันเสมอไป ดังนั้นจึงเก็บข้อมูลจากทั้งสองแห่งพร้อมระบุแหล่งที่มา กฎการตรวจสอบ (Lint rule) R5 จะตรวจสอบค่าของ Glottolog ภายใน envelope เทียบกับผังของ Glottolog เอง: WALS อาจเห็นต่างจาก Glottolog ได้ แต่ Glottolog จะต้องไม่ถูกอ้างอิงผิดพลาด ภาษาโดดเดี่ยวจะไม่มีข้อมูลตระกูลภาษาเลย |
| `classification.familyGlottocode` | `string` | Glottocode ของตระกูลภาษาระดับบนสุดดังกล่าว (`crk` → `"algi1248"`) |
| `classification.genus` | `string` | โหนดการจัดหมวดหมู่ระดับกลางของ WALS (`crk` → `"Algonquian"`) ซึ่งเป็นแนวคิดของ WALS **ไม่ใช่** ของ Glottolog — เนื่องจาก Glottolog เผยแพร่ผังแบบความลึกไม่จำกัดโดยไม่มีระดับ genus — ดังนั้นฟิลด์นี้จึงมีอยู่เฉพาะภาษาที่ WALS ให้รหัสไว้เท่านั้น |
| `classification.ancestry` | `string[]` | เส้นทางการสืบเชื้อสายตาม Glottolog ในรูปแบบของ glottocode บรรพบุรุษ โดยเริ่มจากรากก่อน (`["algi1248", …, "plai1264"]`) ลำดับดังกล่าว **คือ** ตัวข้อกล่าวอ้าง: นี่คือเส้นทาง ไม่ใช่เซตที่เรียงตามตัวอักษร |
| `classification.glottologBucket` | `string` | หมวดหมู่ที่ไม่เกี่ยวกับสายสัมพันธ์ทางพันธุกรรมของ Glottolog — `"Artificial Language"`, `"Pidgin"`, `"Mixed Language"`, `"Speech Register"`, `"Unclassifiable"`, `"Unattested"` ถูกแยกออกจากช่องตระกูลภาษาเนื่องจากหมวดหมู่เหล่านี้จัดกลุ่มตามประเภท ไม่ใช่สายการสืบเชื้อสาย: การ์ดที่มีหมวดหมู่นี้จะไม่มีตระกูลภาษา และนั่นคือผลลัพธ์ที่ตรงไปตรงมาตามจริง |
| `isIsolate` | `boolean` | ระบุว่า Glottolog จัดภาษาเป็นภาษาโดดเดี่ยว (isolate) หรือไม่ |

การ์ดก่อนการเปลี่ยนผ่านเคยมีฟิลด์ `genusGlottocode` ด้วย ซึ่งถูกยกเลิกไป
พร้อมกับข้อผิดพลาดเชิงหมวดหมู่ที่สร้างมันขึ้นมา: genus เป็นแนวคิดของ WALS และ
การนำตัวระบุของ Glottolog มาสวมทับถือเป็นการอ้างถึงโหนดในผังที่ Glottolog ไม่มีอยู่จริง
ลำดับชั้นของ Glottolog จะถูกเก็บไว้ใน `ancestry` แทน

### § 3. ฟิลด์ภูมิศาสตร์

| ฟิลด์ | รูปแบบ | หมายเหตุ |
|-------|-------|-------|
| `macroarea` | `string` | พื้นที่มหภาค (Macroarea) ของ Glottolog — `"Africa"`, `"Australia"`, `"Eurasia"`, `"North America"`, `"Papunesia"` หรือ `"South America"` |
| `coordinates` | `object` | `{lat, lng}` — จุดพิกัดตัวแทนของ Glottolog เป็นจุดพิกัด ไม่ใช่เขตแดน: ใช้เพื่อวางตำแหน่งภาษาบนแผนที่ และไม่ได้อ้างถึงขอบเขตหรือพรมแดนใดๆ |
| `countries` | `string[]` | รหัส ISO 3166-1 alpha-2 ของประเทศที่ Glottolog เชื่อมโยงกับภาษานั้น (`["CA", "US"]`) |
| `cldrOfficialStatus` | `string` | สถานะทางการที่ดินแดนบางแห่งมอบให้กับภาษานั้น ตามที่ CLDR บันทึกไว้ (ส่งผ่านทาง LinguaMeta) — `"Official"`, `"Regional official"` สำหรับการ์ดโลแคล สถานะที่แปลงเฉพาะสำหรับดินแดนของ *โลแคลนั้นๆ* จะอยู่ใน `localeScoped.cldrOfficialStatus` |

อาร์เรย์ `regions` ก่อนการเปลี่ยนผ่าน (การแจกแจงจำนวนผู้พูดรายประเทศพร้อมรหัสเขตการปกครอง) และ `arealContext` (การเป็นสมาชิกกลุ่มความสัมพันธ์ทางภาษา หรือ Sprachbund) ถูกยกเลิกแล้ว: เนื่องจากไม่มีแหล่งข้อมูลนำเข้าใดระบุข้อมูลเหล่านี้ และการคัดสรรโดยไม่มีแหล่งอ้างอิงจะไม่ถูกคงไว้ในการสร้างใหม่
ข้อกล่าวอ้างเรื่องจำนวนผู้พูดในระดับภูมิภาคอาจกลับมาได้ในวันที่แหล่งข้อมูลที่อ้างอิงได้ถูกนำเข้าสู่ไปป์ไลน์ จนกว่าจะถึงตอนนั้น การไม่มีข้อมูลอยู่จึงเป็นสถานะที่ซื่อตรงที่สุด

### § 4. ฟิลด์ระบบการเขียน

| ฟิลด์ | รูปแบบ | หมายเหตุ |
|-------|-------|-------|
| `scripts` | `string[]` | มาแทนที่ฟิลด์เดี่ยว `script` รหัส ISO 15924 **ทั้งหมด** ที่มีหลักฐานรับรอง (`crk` → `["Cans", "Latn"]`) แบบไม่เรียงลำดับ — ห้ามอ่าน `scripts[0]` ว่าเป็นระบบการเขียน "หลัก" โดยเด็ดขาด ระบบการเขียนหลักจะถูกอนุมานโดยอะแดปเตอร์จากแท็กสูงสุดของ `bcp47FullTag` |
| `scriptNames` | `string[]` | ชื่อที่ใช้แสดงผลสำหรับ `scripts[]` ซึ่งคำนวณโดย Champollion (`"Unified Canadian Aboriginal Syllabics"`) |
| `textDirection` | `string` | มาแทนที่ `dir` คำเฉพาะของแหล่งข้อมูลเอง — `"left-to-right"` / `"right-to-left"` (เดิมคือ `"ltr"`/`"rtl"`) |
| `suppressScript` | `string` | CLDR Suppress-Script: ระบบการเขียนที่เป็นมาตรฐานสำหรับภาษานั้นจนแท็ก BCP 47 ละเว้นไว้ (`fra` → `"Latn"`) |
| `script` | `string` | **เฉพาะการ์ดโลแคลเท่านั้น**: ระบบการเขียนที่แปลงเฉพาะสำหรับโลแคล (`fra-CA` → `"Latn"`, `cmn-Hant` → `"Hant"`) การ์ดภาษาจะไม่มีฟิลด์ระบบการเขียนแบบค่าเดี่ยว |

ภาษาที่ไม่มีหลักฐานการเขียนจะ **ไม่มีฟิลด์ `scripts`** เลย —
การไม่ปรากฏฟิลด์นี้หมายถึงไม่มีแหล่งข้อมูลใดระบุระบบการเขียนไว้ ไม่ใช่การอ้างว่าภาษานั้น
"ไม่มีภาษาเขียน" (ภาษามือคือกลุ่มที่ใหญ่ที่สุดในลักษณะนี้: เนื่องจากไม่มีระบบสัญกรณ์ใด
ที่ได้รับการยอมรับเป็นมาตรฐานชุมชนสำหรับการรู้หนังสือในชีวิตประจำวัน)

### § 5. ฟิลด์ข้อมูลประชากรและความมีชีวิตชีวา

| ฟิลด์ | รูปแบบ | หมายเหตุ |
|-------|-------|-------|
| `speakerEstimates` | envelope | การประมาณการของทุกแหล่งข้อมูลพร้อมระบุแหล่งที่มา ค่าอาจเป็นจำนวนนับที่แน่นอนหรือข้อความช่วงตัวเลขของแหล่งข้อมูลเอง (`"10000-99999"`) โดยมีข้อจำกัด/คำเตือนของแหล่งข้อมูลระบุไว้ตามจริงใน `note` ค่า `"agreement": "conflicting"` พบได้ทั่วไป — การแสดงความขัดแย้งของข้อมูล *คือ* เป้าหมายของเรา ไม่มีการนำมาเฉลี่ยหรือเลือกฝ่ายใดฝ่ายหนึ่ง |
| `endangerment` | envelope | มาแทนที่ออบเจกต์ `vitality` เดี่ยว การประเมินของทุกแหล่งข้อมูล **ตามสเกลของแหล่งข้อมูลนั้นเอง** — แต่ละค่าจะมีฟิลด์ `scale` และค่า `"agreement": "incommensurable"` ถือเป็นเรื่องปกติ เนื่องจากชุดคำศัพท์ของ ELCat, Glottolog AES และ LinguaMeta ไม่ได้เทียบเคียงกันได้แบบหนึ่งต่อหนึ่ง อะแดปเตอร์จะอนุมาน *ระดับความมีชีวิต (vitality tier)* สำหรับการแสดงผลหนึ่งค่าจากแหล่งข้อมูลที่ระบุเพียงแห่งเดียวตามลำดับความสำคัญของหน่วยงานที่ประกาศไว้ ระดับดังกล่าวมีไว้สำหรับการแสดงผลเท่านั้น — ชุดข้อมูลที่ระบุแหล่งที่มาทั้งหมดจะยังคงอยู่บนการ์ด |

จำนวนผู้พูดที่ *แสดงผล* ที่ใดก็ตามใน Champollion จะต้องตรงกับรายการใดรายการหนึ่งใน
`speakerEstimates` ที่อ้างอิง หรือมีการระบุที่มาของข้อมูล `champollion-derived` อย่างชัดเจน —
ซึ่งบังคับใช้โดยกฎความถูกต้องสมบูรณ์ของการ์ด (card-integrity rules)

### § 5.5 ฟิลด์เอกสารและการปรากฏตัวในโลกดิจิทัล

| ฟิลด์ | รูปแบบ | หมายเหตุ |
|-------|-------|-------|
| `documentation` | `object` | มาแทนที่ `documentationDepth` บันทึกของ Glottolog ว่าภาษานี้มีการบันทึกเอกสารไว้อย่างละเอียดเพียงใด ตามนิยามของ Glottolog เอง |
| `documentation.medLevel` | `string` | ระดับ Most Extensive Description ของ Glottolog ตามข้อความจริง — `"long grammar"`, `"grammar"`, `"grammar sketch"`, `"phonology"`, `"wordlist"` |
| `documentation.medSourceId` | `string` | คีย์บรรณานุกรมของคำอธิบายที่ละเอียดที่สุดดังกล่าวในแค็ตตาล็อกอ้างอิงของ Glottolog |
| `documentation.firstDocumented` | `number` | คอลัมน์ปีแรกของการบันทึกเอกสารของ Glottolog เอง ตามข้อความจริง — ย้ายมาที่นี่จากฟิลด์ระดับบนสุดก่อนการเปลี่ยนผ่าน มีอยู่ในการ์ดภาษาเพียงไม่กี่ร้อยภาษาเท่านั้น และความเบาบางของข้อมูลนี้ก็เป็นสิ่งที่มีค่าควรแก่การรับรู้ในตัวมันเอง |
| `documentation.lastDocumented` | `number` | คอลัมน์ปีสุดท้ายของการบันทึกเอกสารของ Glottolog ตามข้อความจริง — มีอยู่ในภาษาประมาณหนึ่งพันภาษา |
| `wikipediaEdition` | `object` | มาแทนที่ `digitalPresence` `{site, url, name}` — มี Wikipedia เวอร์ชันเปิดในภาษานี้ (`afr` → `af.wikipedia.org`) ระบุเฉพาะการมีอยู่เท่านั้น โดยตั้งใจ **ไม่รวมจำนวนบทความ**: เนื่องจากหลายเวอร์ชันสร้างขึ้นโดยบอตเป็นส่วนใหญ่ และเวอร์ชันที่มีบทความจำนวนมหาศาลก็ไม่ได้แปลว่า "มีเอกสารบันทึกไว้ดีกว่า" เวอร์ชันขนาดเล็กในมิติที่นักแปลสามารถนำไปใช้ประโยชน์ได้ |
| `dialectCount` | `number` | คอลัมน์ `child_dialect_count` ของ Glottolog เอง ตามข้อความจริง — เฉพาะภาษาถิ่นย่อยชั้นแรกโดยตรงเท่านั้น ไม่รวมทั้งผังย่อย นี่คือข้อกล่าวอ้างของ Glottolog ไม่ใช่การคำนวณของเรา: กฎเดิมเคยประทับตราไว้เป็น `champollion-derived` และทำให้การ์ดหลายพันใบอ้างสิทธิ์การนับของ Glottolog ว่าเป็นของตนเอง |

ส่วนที่เหลือของบล็อก `digitalPresence` ก่อนการเปลี่ยนผ่าน (ชั่วโมงของ Common Voice,
จำนวนประโยคของ Tatoeba) ถูกระงับไว้จนกว่าแหล่งข้อมูลเหล่านั้นจะเข้าสู่ไปป์ไลน์ —
คลังข้อมูล Tatoeba เองนั้นปรากฏอยู่ในตำแหน่งที่ถูกต้องแล้ว ในฐานะคลังข้อมูลคู่ขนาน
ภายใต้ `resources.corpora` (§ 9)

### § 6. ฟิลด์ความเป็นทางการ Register และเพศ

คลังข้อมูลที่ถูกโปรเจกต์จะมีฟิลด์ที่นี่เพียงฟิลด์เดียว — นั่นคือข้อเท็จจริงที่อ้างอิง:

| ฟิลด์ | รูปแบบ | หมายเหตุ |
|-------|-------|-------|
| `politenessDistinction` | envelope | ระบุว่าภาษานี้มีการใช้ไวยากรณ์แสดงความสุภาพในรูปบุรุษที่ 2 หรือไม่ อ้างอิงระหว่าง Grambank GB415 (ระบบทวิภาค: มี/ไม่มี) และ WALS 45A (สี่ระดับ: ไม่มีความแตกต่าง / ระบบทวิภาค / หลายระดับ / หลีกเลี่ยงการใช้สรรพนาม) ข้อมูลเหล่านี้ใช้สเกลที่ต่างกัน ดังนั้นแต่ละค่าจึงระบุ `scale` ของตน และ envelope จะรายงานว่าข้อมูลเหล่านี้ **เทียบเคียงกันไม่ได้ (incommensurable)** แทนที่จะรายงานว่าเป็นข้อขัดแย้ง |

**ระบบระดับภาษา (register system) คือการกำหนดค่า ไม่ใช่ข้อเท็จจริงของการ์ด** คลังข้อมูล
ก่อนการเปลี่ยนผ่านเคยจัดเก็บข้อความ `formality` และพรอมต์ `registers` ไว้บนการ์ดเกือบ
หนึ่งพันแปดร้อยใบในแต่ละรายการ — ซึ่งเกือบทั้งหมดสร้างขึ้นจากแหล่งข้อมูลสองแห่งข้างต้น
แล้วนำมาใช้งานประหนึ่งว่าเป็นการกำหนดค่าที่ดูแลด้วยมือ ตัว Atlas จะเก็บข้อเท็จจริงไว้;
ส่วนอินเทอร์เฟซการกำหนดค่า — `formality`, `registers`,
`gender`, `codeSwitching` — ยังคงเป็นส่วนหนึ่งของ **สกีมาที่ดูแลโดยผู้เชี่ยวชาญของแพ็กเกจ npm**
(`language-card.schema.json`) โดยอยู่ที่การ์ดศูนย์กลางระดับ genus/family ที่ดูแลไว้
และส่งต่อไปยัง CLI ผ่านการผสานรวม `extends` ของระบบระดับภาษา
ตามที่อธิบายไว้ใน [โมเดลการสืบทอด](#inheritance-model) ฟิลด์เหล่านี้ไม่ใช่ฟิลด์ที่ถูกโปรเจกต์ของ Atlas: ไม่มีการ์ดใดในคลังข้อมูลที่โปรเจกต์แล้วบรรจุฟิลด์เหล่านี้ไว้ และกระบวนการบิลด์ของ Atlas จะไม่มีวันเขียนฟิลด์เหล่านี้ขึ้นมา คำแนะนำใน
[การเขียนพรีเซ็ตระดับภาษาที่ดี](#writing-good-register-presets) จะใช้กับ
ช่องทางที่ดูแลด้วยมือดังกล่าว

### § 7. ฟิลด์โปรไฟล์ทางภาษาศาสตร์

| ฟิลด์ | รูปแบบ | หมายเหตุ |
|-------|-------|-------|
| `typologicalProfile` | `object` | หนึ่งคีย์ต่อหนึ่งคุณลักษณะทางวิทยาภาษาระบบลักษณ์ (typological feature) ที่นำเข้า แต่ละค่าคือรหัสของแหล่งข้อมูลเอง แต่ละคีย์จะมีอยู่เฉพาะเมื่อแหล่งข้อมูลนั้นให้รหัสกับภาษานี้ บูลีนมาจากคุณลักษณะของ Grambank ส่วนสตริงหมวดหมู่มาจากบทต่างๆ ของ WALS; รีจิสทรีการตัดสินใจจะระบุพารามิเตอร์ต้นน้ำที่แน่ชัดสำหรับทุกคีย์ |
| `phonologicalInventory` | `object` | `{consonants, vowels, tones, totalPhonemes, hasTone}` — จำนวนที่ Champollion คำนวณจากคลังข้อมูล PHOIBLE ที่อ้างอิง (PHOIBLE เผยแพร่หนึ่งแถวต่อหนึ่งหน่วยเสียงย่อยและไม่มีการระบุผลรวมจำนวน) ดังนั้นทุกค่าจึงมีที่มาเป็น `champollion-derived` **PHOIBLE เป็นหน่วยงานอ้างอิงเรื่องวรรณยุกต์เพียงแห่งเดียว** (lint R1): Grambank ไม่มีคุณลักษณะเรื่องวรรณยุกต์ และไม่มีฟิลด์อื่นใดในการ์ดที่สามารถอ้างถึงระบบวรรณยุกต์ได้ |
| `numeralSystem` | `object` | `{base}` — ฐานของระบบตัวเลข ตามข้อความจริงจาก *Numeral Systems of the World's Languages* ของ Chan (`"decimal"`, `"quinary-vigesimal"`, `"body tally"`; มีเกือบร้อยค่าที่แตกต่างกัน) จะไม่มีอยู่เมื่อคอลัมน์ฐานของ Chan ว่างเปล่า — ซึ่งคิดเป็นประมาณครึ่งหนึ่งของภาษาที่สำรวจ — เนื่องจากตัวสร้างข้อมูลก่อนหน้านี้ใส่ค่าว่างด้วย `"decimal"` และสร้างค่าสมมติขึ้นมาเองสำหรับภาษาสองพันภาษา |
| `pluralCategories` | `string[]` | หมวดหมู่พหูพจน์ของจำนวนนับที่ CLDR ระบุไว้สำหรับภาษานี้ — ภาษาอาหรับแยกแยะ `["zero", "one", "two", "few", "many", "other"]` ภาษาฝรั่งเศสมีสามหมวดหมู่ ภาษาจีนมีหนึ่งหมวดหมู่ อ่านจากคีย์ของชุดกฎของ CLDR โดยตรง จึงเป็นข้อกล่าวอ้างของ CLDR ไม่ใช่การอนุมานของเรา มาแทนที่ `rules.plurals.categories` ก่อนการเปลี่ยนผ่าน; ไปป์ไลน์ i18n จำเป็นต้องใช้ข้อมูลนี้เพื่อทราบว่าข้อความต้องเตรียมรูปพหูพจน์ไว้กี่รูปแบบ |

คีย์ `typologicalProfile` ที่ถูกโปรเจกต์อยู่ในปัจจุบัน พร้อมพารามิเตอร์ต้นน้ำ:

- **บทของ WALS** (สตริงหมวดหมู่ ป้ายกำกับค่าของ WALS เอง): `fusion`
  (20A), `verbSynthesis` (22A), `affixPreference` (26A), `reduplication`
  (27A), `genderCount` (30A), `caseCount` (49A), `wordOrder` (81A),
  `subjectVerbOrder` (82A), `verbalAlignment` (100A), `negationOrder` (143A)
- **คุณลักษณะของ Grambank** (บูลีน): `hasGenderInPronouns` (GB030),
  `hasSexBasedGender` (GB051), `hasNumeralClassifiers` (GB057), `hasCoreCase`
  (GB070), `hasObliqueCase` (GB072), `marksPastTense` (GB083),
  `marksPresentTense` (GB082)

บล็อก `linguisticChallenges` และ `contactInfluences` ก่อนการเปลี่ยนผ่านจะไม่ถูก
โปรเจกต์ — ข้อความเชิงวิจัยที่ไม่มีแหล่งข้อมูลนำเข้าจะยังคงอยู่ในสกีมาที่ดูแลโดยผู้เชี่ยวชาญของแพ็กเกจ npm
เช่นเดียวกับอินเทอร์เฟซระดับภาษาใน § 6 (ตาราง
[ประเภทของอิทธิพลจากการสัมผัสภาษา](#contact-influence-types) ด้านล่างจัดทำขึ้นสำหรับช่องทางนั้น)
ส่วนบล็อก `rules` ถูกยกเลิกแล้ว: ข้อมูลที่สามารถอ้างอิงได้จะยังคงอยู่
ในรูปของ `pluralCategories` ที่นี่ และฟิลด์ระบบการเขียนใน § 4

### § 8. ฟิลด์สารานุกรม

ถูกยกเลิกออกจากการ์ดแล้ว บล็อก `encyclopedic` ก่อนการเปลี่ยนผ่าน (บทความประวัติศาสตร์
และภาษาถิ่น ลิงก์สถาบัน), `culturalAphorism` และ `varieties` เดิมเป็น
ข้อความที่เขียนขึ้นด้วยมือในระดับการ์ด ซึ่งการสร้างใหม่ได้ลบออกตามการออกแบบ
ข้อเท็จจริงเกี่ยวกับการเป็นสมาชิกที่ `varieties` เคยอ้างถึง บัดนี้กลายเป็นฟิลด์ระบุตัวตนที่มีการอ้างอิง
(§ 1 `macrolanguageMembers` และ `canonicalisedMembers`) และความครอบคลุมของเครื่องมือสำหรับแต่ละภาษาย่อย
จะถูกระบุไว้บนการ์ดของภาษานั้นๆ เอง (`methodSupport`,
`resources`) สุภาษิตตัวแทนอาจกลับมาได้ผ่านช่องทางการมีส่วนร่วมของชุมชน
โดยมีความยินยอมและการอ้างอิงที่ชัดเจน; แต่จะไม่กลับมาในรูปแบบฟิลด์บนการ์ดที่ไร้แหล่งอ้างอิง

### § 9. ฟิลด์ทรัพยากรดิจิทัล

ทุกสิ่งในส่วนนี้เป็นการระบุถึง **การมีอยู่จริงและความสามารถ ไม่ใช่การระบุคุณภาพ**:
นั่นคือมีการเผยแพร่ทรัพยากรนั้นและใครเป็นผู้เผยแพร่ — ไม่เคยระบุว่าทรัพยากรนั้นดี สมบูรณ์
หรือใช้งานได้ดีเพียงใด และไม่เคยมีคะแนนวัดผล คะแนนที่วัดผลลัพธ์ของวิธีการใดๆ
เป็นผลจากการรันที่ระบุคีย์ด้วย (method, dataset, metric) ซึ่งจะอยู่บนกระดานผู้นำ (leaderboard)
และห้ามมีอยู่บนการ์ดโดยเด็ดขาด (lint R3)

| ฟิลด์ | รูปแบบ | หมายเหตุ |
|-------|-------|-------|
| `resources` | `object` | คอนเทนเนอร์: แต่ละฟิลด์ย่อยด้านล่างเป็นรายการที่มีแหล่งที่มาอิสระต่อกัน และจะถูกละไว้เมื่อไม่มีแหล่งข้อมูลใดระบุ |
| `resources.fsts` | `object[]` | ตัววิเคราะห์สัณฐานวิทยาแบบสถานะจำกัด (finite-state morphological analysers) ที่เผยแพร่: `{name, url, publisher, license, licenceEstablished, archived}` สัญญาอนุญาตจะระบุแยกตามแต่ละรายการแทนที่จะถือว่าเหมือนกันทั้งหมดในแค็ตตาล็อก — ขอบเขตของสัญญาอนุญาตจำเป็นต้องใช้ข้อกำหนดจริง สำหรับภาษาประเภทควบรวมคำ (polysynthetic language) นั้น FST มักจะเป็นการตรวจสอบโครงสร้างเพียงอย่างเดียวที่มีอยู่จริง |
| `resources.corpora` | `object[]` | คลังข้อมูลคู่ขนานที่มีหลักฐานรับรองภาษานี้: `{corpus, corpusId, pairCount, topPartners, alignmentPairsTotal, …}` ระบุเป็น **คู่ภาษา** เสมอ เนื่องจากคลังข้อมูลคู่ขนานจะรับรองภาษาผ่านคู่ภาษาเท่านั้น — การกล่าวว่า "ครอบคลุมภาษาสวาฮิลี" โดยไม่ระบุว่าคู่กับภาษาใดเป็นการตอบคำถามที่ไม่มีใครถาม ระบุเฉพาะการมีอยู่และขนาด ไม่เคยระบุคุณภาพ |
| `resources.monolingualCorpora` | `object[]` | คลังข้อมูลภาษาเดียว — แยกต่างหากจาก `corpora` เพื่อไม่ให้คำว่า "มีคลังข้อมูล" สื่อถึงสองสิ่งที่เปรียบเทียบกันไม่ได้ |
| `resources.speech` | `object[]` | ทรัพยากรเสียงพูดที่เผยแพร่ ระบุเฉพาะการมีอยู่เท่านั้น |
| `resources.keyboards` | `object[]` | ผังแป้นพิมพ์ที่เผยแพร่ เรียบง่ายแต่สำคัญมาก: สำหรับระบบการสะกดคำที่ต้องใช้อักขระที่ไม่มีบนแป้นพิมพ์มาตรฐาน ผังแป้นพิมพ์คือตัวชี้วัดว่าภาษานั้นจะสามารถพิมพ์ได้หรือไม่ |
| `resources.typology` | `object[]` | ชุดข้อมูลเชิงวิทยาภาษาระบบลักษณ์ที่ *ให้รหัส* ภาษานี้ พร้อมขอบเขต: `{dataset, featuresCoded, datasetFeatureTotal}` ระบุเฉพาะการมีอยู่และขอบเขต ไม่เคยระบุเนื้อหา — สิ่งที่คุณลักษณะระบุไว้จะไม่อยู่บนการ์ดจนกว่าจะมีผู้เขียนแมปพารามิเตอร์ที่ยอมรับค่านั้น (ค่าที่ยอมรับแล้วจะแสดงใน § 7 `typologicalProfile`) จำนวนคุณลักษณะมาจากการคำนวณของเรา ดังนั้นจึงระบุที่มาเป็น `champollion-derived` |
| `lexicalResources` | `object` | คอนเทนเนอร์สำหรับข้อเท็จจริงเกี่ยวกับการมีอยู่ของคำศัพท์ |
| `lexicalResources.datasets` | `object[]` | รายการคำศัพท์ที่เผยแพร่พร้อมความครอบคลุม: `{dataset, forms, concepts, release}` |
| `lexicalResources.dictionaries` | `object[]` | พจนานุกรมที่เผยแพร่ — ระบุการมีอยู่ ไม่ใช่คุณภาพ และมีการ **ระบุทิศทาง** ตามที่ผู้เผยแพร่กำหนด: พจนานุกรมที่แปลไปทางหนึ่งถือเป็นคนละทรัพยากรกับพจนานุกรมที่แปลในทิศทางตรงกันข้าม ข้อมูลแต่ละรายการไม่มีโครงสร้างรูปแบบเดียวกัน (ชุดข้อมูล CLDF จะทราบจำนวนรายการ; ส่วนที่เก็บข้อมูลจะทราบคู่ภาษาและทิศทาง); แต่ละรายการจะระบุแหล่งข้อมูลของตน และสัญญาอนุญาตรวมถึงสถานะการจัดเก็บถาวรจะแนบไปกับแต่ละรายการ |
| `lexicalResources.colexificationConcepts` / `colexifyingForms` | `number` | จำนวนที่ Champollion คำนวณจาก CLICS³: แนวคิดที่มีหลักฐานรับรองสำหรับภาษานี้ และรูปคำที่แมปกับแนวคิดที่แตกต่างกันตั้งแต่สองแนวคิดขึ้นไป `champollion-derived` |
| `methodSupport` | `object` | วิธีการแปลใดบ้างที่ครอบคลุมภาษานี้ — ระบุความสามารถ ไม่ใช่คะแนน รูปแบบ: `{total, byTier, named, truncated}` ภาษาอังกฤษมีวิธีการแปลเชื่อมโยงอยู่หลายพันรายการในขณะที่ภาษาทั่วไปมีประมาณสองสามสิบรายการ ดังนั้นการ์ดจะเก็บ *รูปแบบ* ของหลักฐานไว้ — `total` บวกกับจำนวน `byTier` ต่อระดับความเชื่อมั่น (`fetched`, `partially-confirmed`, `model-card-declared`) — และจะระบุเฉพาะรายการที่แข็งแกร่งที่สุด (แต่ละ `{value, variant, source, confidence}`) ตามขีดจำกัดที่กำหนดไว้ ส่วน **บริการ** ในรีจิสทรีจะได้รับการระบุชื่อเต็มเสมอโดยไม่จำกัดจำนวน ดังนั้นการไม่มีบริการใน `named` จึงเป็นคำตอบที่แท้จริง; การที่รายการของ Model Card ไม่มีอยู่หมายถึง "ไม่ได้อยู่ในกลุ่มที่แข็งแกร่งที่สุด" เท่านั้น และความเชื่อมโยงทุกรายการยังคงสามารถสอบถามได้ในที่จัดเก็บข้อมูล Atlas |
| `metricModelSupport` | envelope | โมเดลเมตริกการประเมินที่เผยแพร่การรองรับภาษานี้ พร้อมตัวระบุโมเดลที่ชุดทดสอบสามารถโหลดได้ (`masakhane/africomet-mtl`) ใช้สำหรับขับเคลื่อนพฤติกรรมการทำงานจริง — การเลือกโมเดล COMET — และยังคงเป็นเรื่องของความสามารถ ไม่ใช่คะแนน |

**ยุบรวมเข้ากับฟิลด์ด้านบน:** ฟิลด์ `keyboardSupport` ก่อนการเปลี่ยนผ่าน (→
`resources.keyboards`), `corpusAvailability` (→ `resources.corpora` /
`resources.monolingualCorpora`) และ `databaseCoverage` (→
`resources.typology` บวกกับ `lexicalResources` — รายการฐานข้อมูลในปัจจุบันคือ
ข้อเท็จจริงความครอบคลุมที่อ้างอิงได้พร้อมระบุขอบเขต ไม่ใช่ค่าบูลีน)

**ยกเลิกออกจากการ์ด:** `omt1600`, `evalDatasets`, `pipelineReadiness` และ
`metricPlugins` — ไม่มีรายการใดที่ได้รับการรับรองโดยแหล่งข้อมูลนำเข้า และระดับความพร้อม
(readiness tier) เป็นการตัดสินเชิงดุลยพินิจ ไม่ใช่การอ้างอิง

**ดูแลด้วยมือ ไม่ได้มาจากการโปรเจกต์:** อินเทอร์เฟซการประกาศมาตรฐานการประเมิน
(`evalStandard`, `evalMetrics`, `evalPack`) จะคงอยู่ในสกีมาที่ดูแลโดยผู้เชี่ยวชาญของแพ็กเกจ npm
ซึ่งจะบอกชุดเครื่องมือประเมิน (evaluation harness) ว่าแพ็กเกจผู้ตัดสินภายนอกใด
จะทำหน้าที่ให้คะแนนภาษา (เป็นผู้ตัดสิน ไม่ใช่ผู้เข้าแข่งขัน — แกนกลางของชุดเครื่องมือจะไม่มี
โค้ดให้คะแนนเฉพาะภาษาใดๆ); ชุดเครื่องมือจะอ่านค่าเหล่านี้จากการ์ดเมื่อมีระบุไว้
แต่ปัจจุบันไม่มีการ์ดใดในคลังข้อมูลที่ถูกโปรเจกต์บรรจุค่าเหล่านี้ไว้ และกระบวนการบิลด์ของ Atlas
จะไม่เขียนฟิลด์เหล่านี้ เช่นเดียวกับบล็อก `install` ที่ตัวติดตั้ง FST ของชุดเครื่องมือ
อ่านจากรายการ `resources.fsts[]` (`get_fst_install_info()` ใน `language_cards.py`): รายการที่ถูกโปรเจกต์
จะบรรจุเฉพาะข้อเท็จจริงเกี่ยวกับการมีอยู่เท่านั้น

### § 10. ฟิลด์แหล่งที่มา

| ฟิลด์ | รูปแบบ | หมายเหตุ |
|-------|-------|-------|
| `_fieldSources` | `object` | มีอยู่ในการ์ดทุกใบ ทำการแมปทุกพาธฟิลด์บนการ์ด (`"classification.family"`, `"coordinates.lat"`) ไปยังรหัสแหล่งข้อมูลที่จัดเรียงแล้วซึ่งระบุฟิลด์นั้น (`["glottolog-v5.3", "wals-v2020.5"]`) ค่าที่ Champollion คำนวณจะมี `champollion-derived-v1` รหัสแหล่งข้อมูลมีการระบุเวอร์ชัน — `grambank-v1.0.3`, `iso639-3-20260715` — เพื่อให้ข้อกล่าวอ้างทุกรายการสามารถย้อนรอยไปยังรุ่นที่เผยแพร่ได้อย่างแม่นยำ |
| `coverage` | `object` | มีอยู่ในการ์ดทุกใบ และ **คำนวณโดยตัวโปรเจกต์ ไม่ได้ระบุโดยแหล่งข้อมูลใดๆ**: `{sourceCount, componentsPresent, componentsTotal, notAttested}` — จำนวนแหล่งข้อมูลที่แตกต่างกันที่กล่าวถึงภาษานี้ จำนวนองค์ประกอบของการ์ดที่มีค่าเมื่อเทียบกับจำนวนทั้งหมดที่มีให้กรอก และจำนวนค่าที่แหล่งข้อมูลบันทึกไว้อย่างชัดเจนว่า *ไม่มีอยู่* (สำรวจแล้วและระบุว่าไม่มี — ซึ่งเป็นข้อเท็จจริงคนละอย่างกับการไม่เคยสำรวจเลย) สิ่งนี้ช่วยให้การ์ดที่มีข้อมูลน้อยสามารถบอกได้ว่า **เหตุใด** จึงมีข้อมูลน้อย แทนที่จะดูเหมือนถูกละเลย |
| `_card` | `object` | เมทาดาทาของการ์ดเอง: `{type, id, revision, correctableFields}` โดย `type` คือ `"language"` หรือ `"locale"` (การ์ดวิธีการแปลและคลังข้อมูลใช้ตัวโปรเจกต์เดียวกัน); `revision` เป็นแฮชของเนื้อหา ดังนั้นการเปลี่ยนแปลงเนื้อหาใดๆ บนการ์ดจะทำให้ค่านี้เปลี่ยนไปด้วย; `correctableFields` จะแสดงรายการพาธฟิลด์ที่มีค่า — ซึ่งเป็นฟิลด์ที่ช่องทางการแก้ไขสามารถปรับปรุงได้ |
| `_atlas` | `object` | `{version}` — ตราประทับรุ่นการเผยแพร่ของคลังข้อมูล (`"unreleased"` ในช่วงระหว่างการเผยแพร่แต่ละรุ่น) ตั้งใจให้เป็นรหัสรุ่นการเผยแพร่ **ไม่ใช่** ประทับเวลาการบิลด์: เนื่องจากการประทับเวลาจะทำให้การบิลด์สองครั้งจากการตรึงเวอร์ชันที่เหมือนกันแสดงผลต่างกันตามปฏิทิน ซึ่งจะทำลายคุณสมบัติที่ช่วยให้ทุกคนสามารถตรวจสอบ Atlas ได้ — อินพุตที่ตรึงเวอร์ชันเหมือนเดิม ย่อมได้ผลลัพธ์เป็นไบต์เดิมเสมอ |

บล็อกที่มาของข้อมูลก่อนการเปลี่ยนผ่านถูกยกเลิกทั้งหมด: `dataSources`
(ถูกแทนที่ด้วยแมป `_fieldSources` รายฟิลด์), `supportTier` (การตัดสินที่คำนวณขึ้น
ถูกแทนที่ด้วยการนับที่เป็นกลางของ `coverage`), `_generated` (คลังข้อมูลทั้งหมด
ถูกสร้างขึ้นโดยอัตโนมัติ; ตราประทับคือ `_card.revision` บวกกับ
`_atlas.version`), `humanReviewed` และ `notes` (การดูแลข้อมูลที่เป็นของ
ช่องทางที่มีบันทึกของตนเอง) และฟิลด์ระดับบนสุด
`firstDocumented`/`lastDocumented` (ย้ายเข้าไปอยู่ใน `documentation` ใน § 5.5
ซึ่งเป็นจุดที่แหล่งข้อมูลระบุไว้จริง)

## นโยบายรหัสภาษา

Champollion ใช้ **ISO 639-3** เป็นตัวระบุมาตรฐาน รหัสมาตรฐานอื่นๆ
ถูกลงทะเบียนเป็น alias และ resolve ไปยังรหัส ISO 639-3 ในรันไทม์

| ลำดับความสำคัญ | มาตรฐาน | ตัวอย่าง | ฟิลด์ | การใช้งาน |
|----------|----------|---------|-------|-----|
| 1 (มาตรฐาน) | ISO 639-3 | `crk` | `code` | ชื่อไฟล์การ์ด, คีย์การกำหนดค่า, พารามิเตอร์ API |
| 2 (นามแฝง) | ISO 639-1 | `iu` | `codeAliases[]` | ยอมรับใน CLI, แปลงค่าเป็น ISO 639-3 |
| 3 (นามแฝง) | BCP 47 | `fil` | `codeAliases[]` | ยอมรับใน CLI, แปลงค่าเป็น ISO 639-3 |
| อ้างอิง | Glottocode | `plai1258` | `glottocode` | ใช้สำหรับการจัดหมวดหมู่เท่านั้น ไม่ใช้ตอนรันไทม์ |

**ลำดับการแปลงค่า (Resolution order):** เมื่อผู้ใช้ระบุรหัส:
1. ตรงกับ `card.code` โดยตรง → พบข้อมูล
2. ตรงกับ `card.codeAliases[]` → พบข้อมูล, ส่งคืนการ์ดมาตรฐาน
3. ตรงกับ `card.iso639_1` → พบข้อมูล (ทางเลือกสำรอง)
4. ไม่พบข้อมูล → แจ้งข้อผิดพลาด

### ประวัติการย้าย: ISO 639-1 → ISO 639-3

ก่อน v8 ชื่อไฟล์การ์ดใช้รหัส ISO 639-1 เมื่อมีให้ใช้ (`fr.json`,
`de.json`, `ja.json`) ในการย้ายไปใช้ 639-3 การ์ดทั้งหมดถูกเปลี่ยนชื่อเป็น
รหัส ISO 639-3 ที่เทียบเท่า:

| ก่อน | หลัง | เหตุผล |
|--------|-------|-----|
| `fr.json` | `fra.json` | 639-3 เป็นมาตรฐาน |
| `de.json` | `deu.json` | 639-3 เป็นมาตรฐาน |
| `zh.json` | `cmn.json` | Macrolanguage → individual ค่าเริ่มต้น |
| `ar.json` | `arb.json` | Macrolanguage → Modern Standard Arabic |
| `ms.json` | `zsm.json` | Macrolanguage → Standard Malay |

**เกิดอะไรขึ้นกับรหัสเดิม?**
- รหัส 639-1 เดิมอยู่ใน `card.iso639_1`
- รหัส 639-1 เดิมอยู่ใน `card.codeAliases[]` (`fra` → `["fr"]`)
- `resolveCode("fr")` จะส่งคืน `"fra"` ในช่วงรันไทม์ — รองรับความเข้ากันได้ย้อนหลัง
- ผู้ใช้ยังคงสามารถระบุ `"fr"` ในการกำหนดค่าได้ — ซึ่งจะแปลงค่าให้อย่างโปร่งใส

**สิ่งที่เปลี่ยนแปลงในเชิงสถาปัตยกรรม:**
- `_deepMerge()` ตอนนี้ข้ามค่า `null` (สืบทอดจากการ์ดหลัก)
- `_deepMerge()` ตอนนี้มีชุดฟิลด์อัตลักษณ์ (code, extends, aliases ไม่สืบทอด)
- `formality.default` ตอนนี้ได้จาก register `isDefault: true` flags
- การ์ด 205 ใบที่ได้จาก Grambank ได้รับการแก้ไข `formality.default` เชิงโครงสร้าง
- การ์ด genus/family/macrolanguage 38 ใบให้เป้าหมายการสืบทอด

## กรณีพิเศษ

### ภาษามือ (Sign Languages)
ภาษามือ (เช่น ASE — American Sign Language) เป็นภาษาที่ชอบธรรม
และมีรหัส ISO 639-3 ภาษามือมีข้อมูลภูมิศาสตร์และจำนวนผู้พูด แต่:
- `modality` จะเป็น `"signed"` — ข้อกล่าวอ้างที่ชัดเจนของการ์ดว่าภาษานั้น
  *คือ* อะไร; ส่วนการไม่มีระบบการเขียนถือเป็นข้อเท็จจริงที่แยกจากกัน
- `scripts` มักจะไม่มีอยู่ (ไม่มีระบบสัญกรณ์ใดที่ได้รับการยอมรับ
  เป็นมาตรฐานชุมชน) แม้ว่า `"Sgnw"` (SignWriting) จะปรากฏเมื่อมีแหล่งข้อมูลระบุไว้
- `textDirection` จะไม่มีอยู่
- `linguisticChallenges` ควรกล่าวถึงไวยากรณ์เชิงพื้นที่ (spatial grammar), ตัวจำแนก (classifiers) ฯลฯ

### ภาษาโบราณและภาษาในประวัติศาสตร์ (Ancient & Historical Languages)
ภาษาอย่างภาษาละติน (`lat`, isoLanguageType `"Historical"`) และภาษาสันสกฤต
(`san`) ยังคงถูกใช้ในบริบทเฉพาะ (ทางศาสนา, ทางวิชาการ) แต่ไม่มี
ผู้พูดเป็นภาษาแม่:
- `isoLanguageType` จะแสดงคำระบุสถานะของ ISO เอง (`"Ancient"`,
  `"Historical"`, `"Extinct"`) — การ์ดจะไม่ลดทอนหรือเขียนทับค่านี้โดยเด็ดขาด
- `endangerment` และ `speakerEstimates` จะรายงานสิ่งใดก็ตามที่แหล่งข้อมูลที่อ้างอิง
  ประเมินไว้จริง พร้อมข้อจำกัดตามจริง (จำนวนผู้พูดในชุมชนภาษาที่สองยังคงระบุป้ายกำกับตามที่แหล่งข้อมูลระบุไว้)
- `firstDocumented` / `lastDocumented` ระบุตำแหน่งของภาษาตามช่วงเวลา

### ภาษาประดิษฐ์ (Constructed Languages)
ภาษาเอสเปรันโต (`epo`, isoLanguageType `"Constructed"`), ภาษาโลจบาน ฯลฯ:
- `classification` อาจไม่มีอยู่ — Glottolog จัดภาษาประดิษฐ์ไว้ภายใต้
  หมวดหมู่ที่ไม่เกี่ยวกับสายสัมพันธ์ทางพันธุกรรม และหมวดหมู่นี้จะไม่แสดงเป็นตระกูลภาษาเด็ดขาด
- `contactInfluences` สะท้อนถึงข้อมูลของภาษาต้นทาง (เช่น ภาษาเอสเปรันโตดึงมาจากกลุ่มภาษาโรมานซ์, เจอร์แมนิก, สลาวิก)
- `endangerment` มีลักษณะพิเศษ — มีชุมชนผู้พูดที่เติบโตขึ้นแต่ไม่มีมาตุภูมิของภาษาแม่

### ภาษามาโคร (Macrolanguages)
ภาษาอาหรับ (`ara`), ภาษาจีน (`zho`), ภาษาครี (`cre`), ภาษาเกชัว (`que`) เป็นภาษามาโคร
ที่ครอบคลุมภาษาเดี่ยวหลายภาษา:
- `isoScope: "Macrolanguage"` — ศูนย์กลางสำหรับการนำทาง ไม่เคยใช้เป็นเป้าหมายของการวัดประสิทธิภาพ (benchmark target)
- `macrolanguageMembers` แสดงรายการรหัสของสมาชิกแต่ละภาษา;
  `canonicalisedMembers` บันทึกว่าสมาชิกลำดับใดที่รีจิสทรี BCP 47 ยุบรวม
  เข้ากับแท็กของภาษามาโครนี้ (โดยระบุแหล่งที่มาของแต่ละรีจิสทรี)
- `methodSupport` สะท้อนถึงสิ่งที่ *การ์ดภาษามาโคร* รองรับ (มักเป็นภาษามาตรฐาน)
- สมาชิกแต่ละภาษาจะมีการ์ดของตนเอง ซึ่งจะมี `macrolanguage` ชี้กลับมายังศูนย์กลาง

### ภาษาที่ไม่มีระบบการสะกดคำมาตรฐาน (Languages Without Standardized Orthography)
หลายภาษา (โดยเฉพาะภาษาที่ถ่ายทอดทางมุขปาฐะ) ไม่มีระบบการเขียน
ที่เป็นมาตรฐาน หรือมีระบบการสะกดคำที่ใช้แข่งขันกันหลายระบบ:
- `scripts`, `scriptNames` และ `textDirection` จะไม่มีอยู่ — ไม่มีแหล่งข้อมูลใด
  ระบุระบบการเขียนไว้ ซึ่งไม่ใช่ข้อกล่าวอ้างเดียวกันกับคำว่า "ไม่มีภาษาเขียน"
- `notes` ควรอธิบายสถานการณ์ของระบบการสะกดคำ
- `linguisticChallenges` ควรระบุว่าสถานการณ์นี้ส่งผลต่อ MT อย่างไร (เช่น ไม่มีชุดข้อมูลฝึกสอน)

### Diglossia
ภาษาอย่างภาษาอาหรับ (MSA กับสำเนียง) หรือ Guaraní (Jopará กับ Guaraní บริสุทธิ์):
- `codeSwitching` บันทึกสถานการณ์สำเนียงผสม
- `registers` สามารถเสนอ preset สำหรับระดับต่างๆ
- `varieties` สามารถแสดงรายการคู่ diglossic

## ประเภทอิทธิพลจากการสัมผัสภาษา

| ประเภท | ความหมาย | ตัวอย่าง |
|------|---------|---------|
| `superstrate` | ภาษาที่มีอำนาจเหนือกว่าถูกกำหนดให้กับชุมชน | French → English (หลัง ค.ศ. 1066) |
| `substrate` | ภาษาพื้นเมืองที่มีอิทธิพลต่อภาษาที่ถูกกำหนด | Celtic → English |
| `adstrate` | ภาษาเพื่อนบ้านที่มีอิทธิพลซึ่งกันและกัน | Norse → English |
| `learned_borrowing` | การยืมผ่านการศึกษา/วิชาการ | Latin → English |
| `lexical_borrowing` | การยืมคำศัพท์โดยตรงผ่านการสัมผัส | Spanish → Filipino |
| `relexification` | การแทนที่คำศัพท์ทั้งหมด | Portuguese → Papiamentu |

## ระดับความลึกของอิทธิพลจากการสัมผัสภาษา

| ระดับ | ความหมาย |
|-------|---------|
| `light` | คำยืมเพียงไม่กี่คำ ผลกระทบต่อโครงสร้างน้อยมาก |
| `moderate` | คำศัพท์จำนวนมากในโดเมนเฉพาะ |
| `heavy` | คำศัพท์แพร่หลายและลักษณะโครงสร้างบางส่วน |
| `structural` | ไวยากรณ์ ไวยากรณ์ประโยค และสัทวิทยาได้รับผลกระทบ |
| `defining` | อัตลักษณ์หลักถูกหล่อหลอมโดยการสัมผัส (creoles, ภาษาผสม) |

## การเขียน Register Preset ที่ดี

**prompt ของ preset ที่ดี:**
- ระบุลักษณะความเป็นทางการอย่างชัดเจน (เช่น "해요체", "vous-form", "siz-form")
- อธิบายสรรพนามหรือรูปแบบกริยาเฉพาะที่ต้องใช้
- ให้บริบทว่า register นี้เหมาะสมเมื่อใด
- กล่าวถึงข้อพิจารณาเรื่อง script หากเกี่ยวข้อง

**อย่า** ใส่แนวทางเรื่องเพศแบบครอบคลุมใน prompt ของ preset แนวทางเรื่องเพศ
ควรอยู่ใน `card.gender.inclusiveGuidance` — จะถูกแทรกแยกต่างหาก

```
❌ Bad:  "Standard Thai. Professional register."
✔ Good: "Professional Thai. Use คุณ (khun) for second person, เรา (rao)
         for first person when needed. Clear, concise phrasing
         appropriate for digital interfaces."
```

### ข้อตกลงการตั้งชื่อ Preset

คีย์ preset ควรสื่อความหมายและใช้ตัวพิมพ์เล็กคั่นด้วยขีดกลาง:
- ภาษา T-V: `formal-vous`, `informal-tu`, `formal-Sie`, `casual-du`
- ระดับการพูด: `polite-haeyo`, `formal-hapsyo`, `casual-hae`
- กลาง: `professional`, `neutral-professional`
- การสลับรหัส: `taglish-professional`, `pure-filipino`

## กระบวนการอัปเดตข้อเท็จจริงบนการ์ด

การ์ดคือ **ผลลัพธ์จากการบิลด์ (build output)** — ซึ่งเป็นการโปรเจกต์แบบดีเทอร์มินิสติกจากสแนปช็อต
ต้นน้ำที่ตรึงเวอร์ชันไว้ จะไม่มีขั้นตอนการเสริมข้อมูลรายใบอีกต่อไป: ช่องทางการรันสคริปต์
`enrich-*` ด้วยมือถูกยกเลิกแล้ว และการแก้ไขที่ทำลงบนไฟล์การ์ดโดยตรง
จะถูกลบออกเมื่อมีการบิลด์ครั้งถัดไป หากต้องการเปลี่ยนแปลงข้อเท็จจริง:

1. **ลงทะเบียนการตัดสินใจ** แต่ละฟิลด์คือหนึ่งแถวในรีจิสทรีการตัดสินใจ
   ของการบิลด์: พารามิเตอร์ต้นน้ำใดที่ป้อนข้อมูลเข้ามา โปรเจกต์อย่างไร และความหมายของค่าที่ขาดหายไปคืออะไร
2. **แก้ไขที่เลเยอร์การนำเข้าข้อมูล (ingest layer)** ค่าที่ไม่ถูกต้องคือข้อบกพร่องในตัวจัดการแหล่งข้อมูล
   (หรือการตรึงเวอร์ชันต้นน้ำที่ล้าสมัย) ไม่ใช่สิ่งที่จะไปตามปะแก้บนการ์ด
3. **บิลด์ใหม่และสลับไปใช้ (cut over)** กระบวนการบิลด์จะโปรเจกต์การ์ดทุกใบใหม่จากสแนปช็อต
   ที่ตรึงเวอร์ชันไว้; จุดตรวจสอบ (gates) จะปฏิเสธการบิลด์ที่ไม่สมบูรณ์ ปฏิเสธค่า null/ค่าว่าง และการ์ดที่ไม่ผ่านกฎความถูกต้องสมบูรณ์

### การจัดการความขัดแย้ง

เมื่อแหล่งข้อมูลมีความเห็นไม่ตรงกัน:
1. **จัดเก็บข้อมูลทั้งหมด** พร้อมระบุแหล่งที่มา — นั่นคือวัตถุประสงค์ของ
   Attribution Envelope
2. **ห้ามหาค่าเฉลี่ย** หรือเลือกข้างใดข้างหนึ่ง — `consensus` จะปรากฏเฉพาะเมื่อ
   แหล่งข้อมูลมีความเห็นตรงกันจริงๆ เท่านั้น
3. **เก็บข้อจำกัด/คำเตือนของแต่ละแหล่งข้อมูลไว้** ตามข้อความจริงในฟิลด์ `note` ของค่านั้น
4. ค่าเดี่ยวสำหรับการแสดงผลหรือการคำนวณจะ **ถูกอนุมานโดยอะแดปเตอร์**
   จากลำดับความสำคัญของหน่วยงานที่ประกาศไว้ — การ์ดเองจะเก็บข้อมูลที่หลากหลายครบถ้วนไว้ทั้งหมด

เมื่อส่งคำขอการเปลี่ยนแปลงที่เกี่ยวข้องกับการ์ด (โปรดจำไว้ว่า: แก้ไขที่การบิลด์
ไม่ใช่ที่การ์ด):

- [ ] `classification` มาจาก Glottolog (ไม่ได้สร้างขึ้นเองด้วยมือ)
- [ ] ที่มาของข้อมูลของทุกฟิลด์ที่ถูกแก้ไขจะปรากฏใน `_fieldSources` โดย
      ค่าที่ Champollion คำนวณจะมีที่มาเป็น `champollion-derived`
- [ ] ไม่มีคะแนนวัดผลลัพธ์ของวิธีการแปลปรากฏอยู่ที่ใดบนการ์ด
- [ ] Linter และด่านตรวจสอบความถูกต้องสมบูรณ์ของการ์ดผ่านโดยไม่มีข้อผิดพลาด
