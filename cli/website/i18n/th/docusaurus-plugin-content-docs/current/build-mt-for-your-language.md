# สร้างโมเดลการแปลด้วยเครื่อง (MT) สำหรับภาษาของคุณ

หน้านี้จะพาคุณเปลี่ยนจากคำถามที่ว่า *"เราต้องการระบบแปลภาษาสำหรับภาษาของเรา — จะเริ่มต้นอย่างไรดี?"* ไปสู่เวิร์กโฟลว์การแปลที่คุณได้**ประเมินผลกับประโยคของคุณเอง**และนำไปใช้งานจริง เอกสารนี้เขียนขึ้นสำหรับทั้งมนุษย์และ AI agent: ทุกขั้นตอนจะระบุคำสั่งที่ต้องรัน และระบุ [เครื่องมือ MCP](/docs/network/getting-started/mcp-server) ที่ agent สามารถเรียกใช้แทนได้หากมี

ตัวอย่างกรณีการใช้งานสองกรณี:

- **โรงเรียนแห่งหนึ่ง**ต้องการแปลจากภาษาอังกฤษ → Plains Cree สำหรับจดหมายข่าวและแอปขนาดเล็ก คุณครูได้ตรวจสอบความถูกต้องของประโยคสองสามร้อยประโยคแล้ว และต้องการเก็บข้อมูลเหล่านั้นไว้เป็นส่วนตัว
- **โรงพยาบาลแห่งหนึ่ง**ต้องการแปลจากภาษาอังกฤษ → ภาษาที่ดัชนียังแทบไม่มีข้อมูล เพื่อใช้ทำสมุดรวมวลีข้างเตียงผู้ป่วย ประโยคทดสอบมีข้อความทางการแพทย์และต้องไม่ถูกส่งไปยังบริการ AI ภายนอกโดยเด็ดขาด

สิ่งที่คุณจะได้ในตอนท้ายคือ: ชุดข้อมูลทดสอบส่วนตัว, คะแนนการประเมินของวิธีการต่าง ๆ บนชุดข้อมูลนั้น, วิธีการแปลที่ดีกว่าเดิม (โมเดลที่มีการเทรนไกด์/coached หรือโมเดลที่คุณเทรนเอง) และการนำวิธีการนั้นไปใช้งานผ่าน CLI — โดยที่ตัวเลขทุกตัวสามารถตรวจสอบย้อนกลับไปยังที่มาได้อย่างชัดเจน

:::info[สิ่งที่กระบวนการนี้ไม่ได้ทำ]
ไม่มีสิ่งใดในนี้ที่ทำให้คำแปลถูกต้องโดยอัตโนมัติ คะแนนจะบอกเพียงว่าตัวเลือกใด*ผิดพลาดน้อยกว่าเมื่อเทียบกับประโยคของคุณ*; ผู้ที่พูดภาษานั้นได้อย่างคล่องแคล่วเท่านั้นที่จะเป็นผู้ตัดสินว่าคำแปลใดเหมาะสมต่อการใช้งาน โปรดอ่าน [ข้อจำกัดอย่างตรงไปตรงมา](/docs/network/honest-limitations) ก่อนที่คุณจะปักใจเชื่อตัวเลขใด ๆ
:::

:::warning[สำหรับ Agent: ก่อนที่คุณจะเปิดดูไฟล์ใด ๆ ของผู้ใช้]
หากชุดข้อมูลทดสอบอาจเป็นข้อมูลส่วนตัว (ผ่านการตรวจสอบโดยครู, ผ่านการตรวจสอบโดยพยาบาล หรือสิ่งใดก็ตามที่ชุมชนยังไม่ได้เผยแพร่สู่สาธารณะ) ห้ามอ่านไฟล์นั้นเป็นอันขาด — ไม่ว่าจะด้วย `cat`, `head` หรือการพรีวิว แม้กระทั่งเพื่อดูรูปแบบไฟล์ก็ตาม สิ่งที่คุณอ่านจะถูกส่งไปยังผู้ให้บริการโมเดลของคุณ ขอให้ถามผู้ใช้ก่อน และกำหนดให้เป็นไฟล์เฉพาะภายในเครื่อง (local-only) เสียก่อน ([ขั้นตอนที่ 2](#2-gather-your-data--and-protect-your-test-set))
:::

## 0. ติดตั้ง

```bash
npm install -g champollion        # translate + deploy        (Node 20.11+)
python3 -m pip install mt-eval-harness       # measure                   (Python 3.11+)
python3 -m pip install 'nmt-forge[hf]'       # train a model (optional; a CPU is enough to start)
```

สำหรับ agent ให้เพิ่มเซิร์ฟเวอร์ MCP ลงในการกำหนดค่า:

```json
{
  "mcpServers": {
    "champollion": { "command": "npx", "args": ["-y", "champollion-mcp-server"] }
  }
}
```

## 1. สำรวจดูว่ามีข้อมูลอะไรอยู่แล้วบ้าง

มีข้อมูลอะไรที่ทราบเกี่ยวกับภาษานี้แล้วบ้าง — พจนานุกรม, ไวยากรณ์, คลังข้อมูล (corpora), เครื่องมือวิเคราะห์ทางสัณฐานวิทยา (FSTs), โมเดล, ผลลัพธ์ที่เผยแพร่แล้ว, บริการต่าง ๆ — และข้อเท็จจริงแต่ละอย่างมาจากแหล่งใด

```bash
champollion network card crk                 # the cited language card
champollion network recommend eng crk        # methods you can run, with the evidence for each
mt-eval corpora --source eng --target crk   # registered test sets for the pair
nmt-forge discover crk               # what a training project can use
```

**Agent:** `search_languages { "query": "Atya" }` จะค้นหารหัสภาษาได้แม้จะสะกดผิดก็ตาม (ค้นหาชื่อที่ใกล้เคียงที่สุดตาม edit distance) ผลลัพธ์แต่ละรายการจะแสดงสถานที่ที่มีผู้พูดภาษานั้นเฉพาะเมื่อการ์ดข้อมูลภาษาระบุแหล่งที่มาไว้เท่านั้น และจะแสดงแหล่งที่มานั้นด้วย เพื่อให้ผู้ใช้สามารถเลือกระหว่างภาษาที่มีชื่อคล้ายกันได้ หากสถานที่ใดไม่มีแหล่งที่มาอ้างอิง ระบบจะไม่แสดงโดยเด็ดขาด: บรรทัดนั้นจะระบุเช่นนั้นและใส่ลิงก์ไปยังเรคคอร์ด Glottolog ของภาษานั้นแทน ซึ่งสามารถเปรียบเทียบตัวเลือกต่าง ๆ จากแหล่งข้อมูลต้นทางได้ สำหรับการติดตั้งผ่าน npm ภาษาที่อยู่นอกเหนือชุดหลักที่รวมมาด้วยจะถูกดึงมาจากตารางการ์ดข้อมูลที่เผยแพร่ของ champollion.dev ซึ่งขณะนี้ยังไม่มีแหล่งที่มารายฟิลด์ (จะมาพร้อมกับการอัปโหลดตารางในรอบถัดไป) บรรทัดของภาษานั้นจึงมีลิงก์ Glottolog แทนที่จะเป็นสถานที่ตั้ง เมื่อไม่มีข้อมูลใดที่แสดงช่วยจำแนกตัวเลือกได้ ให้ผู้พูดภาษานั้นเป็นผู้ตัดสิน (ดูด้านล่าง) จากนั้น `language_overview { "code": "<code>" }` จะแสดงผลหนึ่งหน้า: มีข้อมูลอะไรอยู่บ้าง, มีเกณฑ์มาตรฐาน (benchmarks) และผลลัพธ์ใดบ้าง และขั้นตอนถัดไปตามลำดับหมายเลข เครื่องมือใดก็ตามที่รับค่าภาษาเดียวจะยอมรับค่าเป็น `language` ได้เช่นกัน

ให้อ่านการ์ดข้อมูลตามที่ระบุไว้: **การไม่มีข้อมูลหมายถึงยังไม่ทราบ ไม่ได้แปลว่าเป็นศูนย์** การ์ดที่ไม่แสดงพจนานุกรมหมายถึงดัชนียังไม่ได้บันทึกไว้ — ไม่ได้แปลว่าไม่มีอยู่จริง ในจุดที่แหล่งข้อมูลมีความเห็นไม่ตรงกัน (จำนวนผู้พูดมักจะไม่ตรงกัน) การ์ดจะแสดงข้อมูลจากทุกแหล่ง

หากภาษาของคุณไม่มีการ์ดข้อมูลเลย คุณก็ยังสามารถทำตามขั้นตอนด้านล่างทั้งหมดได้ เพียงแต่เครื่องมือต่าง ๆ จะมีข้อมูลเกี่ยวกับภาษาน้อยลง (`nmt-forge init <code> --no-card --name <name>` จะเริ่มโปรเจกต์การเทรนให้ต่อไปอยู่ดี)

### เมื่อยังไม่ยืนยันความหลากหลายทางภาษา (variety) ที่แน่ชัด

ชื่อหนึ่งชื่ออาจตรงกับหลายภาษาได้ ตัวอย่างเช่น "Ayta" ตรงกับภาษา Ayta ถึงหกภาษาในประเทศฟิลิปปินส์ ซึ่งแต่ละภาษามีรหัสของตนเอง **ให้ถามผู้พูดภาษานั้นก่อนเป็นอันดับแรก** ชุมชนย่อมรู้ว่าตนเองพูดภาษาถิ่นย่อยใด และการเลือกรหัสแทนพวกเขาถือเป็นการสรุปอ้างสิทธิ์เกี่ยวกับตัวพวกเขา

หากคุณจำเป็นต้องเริ่มต้นก่อนที่พวกเขาจะตอบกลับมา ให้ใช้รหัสสำหรับการใช้งานส่วนตัว (private-use code): ISO 639 ได้สงวนรหัส `qaa` ถึง `qtz` ไว้สำหรับกรณีนี้โดยเฉพาะ พร้อมทั้งตั้งชื่อที่ใช้แสดง เพื่อให้พรอมต์และรายงานต่าง ๆ ระบุชื่อภาษานั้นได้:

```bash
champollion init --yes --langs qaa --name qaa="Ayta (variety not yet confirmed)"
```

ซึ่งจะเขียนลงใน `champollion.config.json`:

```json
"languages": { "qaa": { "name": "Ayta (variety not yet confirmed)" } }
```

`init` จะแจ้งว่ารหัสดังกล่าวเป็นรหัสสำหรับการใช้งานส่วนตัวและไม่มีการ์ดข้อมูลภาษา (จะไม่ถามให้คุณตรวจการสะกด)

`init`, `sync`, `verify` และ `network register-corpus` ล้วนรองรับรหัสสำหรับการใช้งานส่วนตัว ข้อจำกัดที่คุณต้องยอมรับ จนกว่าจะมีรหัสจริงมาแทนที่ ได้แก่:

- **ไม่มีข้อมูลจากการ์ดภาษา** ไม่มีค่าพรีเซ็ตของระดับภาษา (register presets), กฎการสร้างพหูพจน์ หรือระบบการเขียนจากการ์ดภาษา คำสั่ง sync จะใช้การตั้งค่าทั่วไป ดังนั้นควรตรวจสอบผลลัพธ์แรก ๆ ร่วมกับผู้พูดภาษานั้น
- **ไม่มี FST** ไม่มีการผูกเครื่องมือวิเคราะห์ทางสัณฐานวิทยาเข้ากับรหัสสำหรับการใช้งานส่วนตัว จึงไม่มีการตรวจสอบความถูกต้องแบบคำต่อคำ
- **ไม่มีผลลัพธ์ก่อนหน้า** การทดสอบมาตรฐานที่เผยแพร่และคิวงานจะใช้รหัสจริงเป็นหลัก ดังนั้น `recommend` และ `corpora` จึงไม่มีข้อมูลใด ๆ ให้แสดง

เมื่อชุมชนยืนยันความหลากหลายทางภาษาที่แน่นอนแล้ว ให้เปลี่ยนไปใช้รหัสของภาษานั้น:

1. ใน `champollion.config.json` ให้แทนที่ `qaa` ด้วยรหัสจริง (และนำ `name` ออกหากชื่อในการ์ดตรงกันอยู่แล้ว)
2. เปลี่ยนชื่อไฟล์ภาษา (locale files) (`messages/qaa.json` → `messages/ayt.json`) คำแปลเดิมจะยังคงใช้ได้: คำสั่ง `champollion sync` ครั้งถัดไปจะเก็บคำแปลเดิมไว้และแปลเฉพาะส่วนที่เพิ่มเข้ามาใหม่เท่านั้น
3. ลงทะเบียนชุดข้อมูลทดสอบใหม่อีกครั้งภายใต้คู่ภาษาจริง:
   `champollion network register-corpus --pair "eng>ayt" --data <file> --role test …`
   คำสั่งจะพิมพ์ `--id` ที่ต้องส่ง เนื่องจากไฟล์ที่ลงทะเบียนแล้วจะยังคงใช้ id เดิมเว้นแต่คุณจะเลือก id ใหม่ (`--pair` สามารถรับ `eng-ayt` หรือ `"eng>ayt"` ได้ทั้งในที่นี้และใน `nmt-forge init`; ให้ใส่เครื่องหมายคำพูดครอบรูปแบบ `>` ด้วย เนื่องจากเชลล์จะตีความ `>` โดด ๆ ว่าเป็นการ "เขียนลงไฟล์")

## 2. รวบรวมข้อมูล — และปกป้องชุดข้อมูลทดสอบของคุณ

**แยกชุดข้อมูลทดสอบออกมาก่อนเป็นอันดับแรก** แยกประโยคที่คุณจะใช้เป็นเกณฑ์ตัดสินทุกสิ่ง (ประโยคที่ครูตรวจแล้ว, ประโยคที่พยาบาลตรวจแล้ว) ออกมาก่อนที่คุณจะเทรนหรือปรับจูน (tune) สิ่งใด และอย่าเทรนโมเดลด้วยประโยคเหล่านี้โดยเด็ดขาด

ชุดข้อมูลทดสอบจะเป็นไฟล์ TSV: บรรทัดละหนึ่งคู่ประโยค ประกอบด้วยต้นฉบับ ตามด้วยเครื่องหมาย TAB แล้วตามด้วยคำแปลอ้างอิง บรรทัดที่ขึ้นต้นด้วย `# ` จะถือเป็นคอมเมนต์

```text
# teacher-checked, 2026 term 1
The library opens at nine.	<the teacher's translation>
```

จากนั้นตัดสินใจว่าจะอนุญาตให้ส่งข้อมูลออกไปได้ไกลแค่ไหน:

| ความต้องการของคุณ… | สิ่งที่ต้องทำ |
|---|---|
| ห้ามข้อมูลออกจากเครื่องนี้ — ห้ามบริการ AI ภายนอกเห็นประโยคเหล่านี้โดยเด็ดขาด | วางไฟล์มาร์กเกอร์ไว้ข้าง ๆ (ดูด้านล่าง) มีเพียงโมเดลในเครื่องของคุณเองเท่านั้นที่จะได้รับการทดสอบเทียบกับชุดข้อมูลนี้ |
| ให้ผู้อื่นเห็นว่ามีชุดข้อมูลทดสอบนี้อยู่ได้ แต่ห้ามเห็นเนื้อหาภายในโดยเด็ดขาด | `champollion network register-corpus --tier private --role test …` จะลงทะเบียนเฉพาะ metadata เท่านั้น |
| จัดการแข่งขันประเมินผลบนชุดข้อมูลนี้ โดยรันบนเครื่องที่คุณควบคุม ซึ่งอาจเป็นแบบออฟไลน์โดยสมบูรณ์ (air-gapped) | `--tier sealed` พร้อมด้วย [sovereign node](/docs/network/sovereignty/sovereign-eval-node) |
| เป็นข้อมูลสาธารณะและใช้สัญญาอนุญาตแบบเปิด | `--tier public` จะชี้ไปยังตำแหน่งที่ไฟล์อยู่; เราจะไม่ทำหน้าที่โฮสต์ไฟล์ดังกล่าวอยู่ดี |

มาร์กเกอร์สำหรับ "ห้ามข้อมูลออกจากเครื่องนี้โดยเด็ดขาด":

```bash
echo '{"transmission": "local-only"}' > data/nurse_checked_test.tsv.champollion.json
```

เมื่อมีไฟล์นี้อยู่ `mt-eval run` จะปฏิเสธผู้ให้บริการระยะไกล (remote provider) ทุกรายสำหรับไฟล์ดังกล่าว และจะรันเทียบกับโมเดลบน loopback เท่านั้น ดูรายละเอียดได้ที่:
[การลงทะเบียนคลังข้อมูล](/docs/network/sovereignty/registering-corpora)

**รหัสสัญญาอนุญาต (licence id) ใดที่ควรใช้** การลงทะเบียนจะถามหา `--license`: ข้อกำหนดที่เจ้าของข้อมูลอนุญาตจริง ๆ ห้ามใส่ค่าชั่วคราว ให้ถามเจ้าของข้อมูลก่อน แล้วเลือกรหัสที่ระบุข้อกำหนดนั้น: เช่น รหัส SPDX หากพวกเขาเผยแพร่ข้อความภายใต้รหัสนั้นอยู่แล้ว;
`community-eval-grant-nc` สำหรับ "ใช้ประเมินคะแนนระบบเท่านั้น ห้ามนำไปเทรน ห้ามแชร์ ห้ามประเมินคะแนนแบบมีค่าใช้จ่าย"; `community-eval-grant` สำหรับเงื่อนไขเดิมแต่อนุญาตให้ประเมินคะแนนแบบมีค่าใช้จ่ายได้; `proprietary` สำหรับสงวนลิขสิทธิ์ทั้งหมด; หรือ
`LicenseRef-<name>` สำหรับข้อกำหนดเฉพาะของพวกเขาเอง สี่ตัวเลือกหลังนี้เป็นรหัส `LicenseRef-…` ซึ่งเป็นการอนุญาตเฉพาะราย: การประเมินผลจากระยะไกลเทียบกับข้อมูลเหล่านี้จะถูกปฏิเสธจนกว่าผู้ดูแลข้อมูล (steward) จะบันทึกการอนุญาต จนกว่าผู้ดูแลจะยืนยัน ให้บันทึกตัวเลือกของคุณเป็นแบบชั่วคราว (provisional) ข้อมูลแบบ local-only จะอยู่เฉพาะในเครื่องเสมอไม่ว่าจะใช้สัญญาอนุญาตใด: ตัวมาร์กเกอร์เป็นตัวกำหนดว่าประโยคจะถูกส่งไปที่ใด ไม่ใช่ตัวสัญญาอนุญาต
[รหัสสัญญาอนุญาตใดที่เหมาะสำหรับชุดข้อมูลทดสอบส่วนตัว](/docs/network/sovereignty/registering-corpora#which-licence-id-for-a-private-test-set)

**สำหรับ Agent: ห้ามอ่านไฟล์ทดสอบที่เป็น local-only** ห้ามใช้ `cat`, `head` หรือเปิดไฟล์เพื่อดู สิ่งที่คุณอ่านจะถูกส่งไปยังผู้ให้บริการโมเดลของคุณ ซึ่งเป็นปลายทางที่มาร์กเกอร์ระบุว่าประโยคเหล่านี้จะต้องไม่ถูกส่งไป และคุณไม่จำเป็นต้องเปิดดู: เครื่องมือต่าง ๆ จะตัดประโยคเหล่านี้ออกจากสิ่งที่พิมพ์ออกมาอยู่แล้ว (`mt-eval compare` จะแสดง id ของรายการและคะแนนแทน) และ `--show-text` มีไว้สำหรับมนุษย์ที่ใช้งานเทอร์มินัลเท่านั้น

**Agent:** `language_overview { "code": "<code>" }` จะแสดงตัวเลือกการปกป้องข้อมูลสำหรับภาษานั้น;
`run_benchmark` จะปฏิบัติตามมาร์กเกอร์และส่งกลับข้อความปฏิเสธ (พร้อมเหตุผล) แทนที่จะส่งประโยคที่ได้รับการปกป้องออกไป

### หากคุณอาจเทรนโมเดลในภายหลัง: ให้ลงทะเบียน, คัดกรอง, คาดการณ์ — ก่อนที่จะมีการวัดคะแนนใด ๆ

ให้ทำสามสิ่งนี้ตอนนี้ตามลำดับ ก่อนที่ขั้นตอนที่ 3 จะทำการวัดผลใด ๆ บนชุดข้อมูลทดสอบ Forge จะนับทุกครั้งที่มีการเปิดดูชุดข้อมูลทดสอบ และการทดสอบเกณฑ์มาตรฐาน (ขั้นตอนที่ 3) ถือเป็นการอ่านเพื่อคิดคะแนน: การลงทะเบียนล่วงหน้า (preregistration) ที่เขียนขึ้นหลังจากนั้นจะถูกปฏิเสธ ลำดับขั้นตอนมีความสำคัญอย่างยิ่ง; การทำในภายหลังจะให้ผลลัพธ์ที่ไม่เหมือนกัน

1. **ลงทะเบียนชุดข้อมูลทดสอบกับ NMT Forge** บันทึกการอ่านข้อมูลจะเริ่มต้นที่นี่ เพื่อให้การอ่านในภายหลังทุกครั้งถูกนับ (การอ่านเพื่อคิดคะแนนก่อนการลงทะเบียนจะแสดงในรายการ แต่จะไม่ถูกนับ)
2. **คัดกรองคลังข้อมูลสำหรับเทรนเทียบกับชุดข้อมูลทดสอบ** (`leak-audit`) คำสั่งนี้จะอ่านชุดข้อมูลทดสอบเพื่อตรวจสอบ (audit) เท่านั้น ไม่ใช่เพื่อคิดคะแนน จึงไม่นับรวมกับการคาดการณ์ของคุณ ให้อ่านผลการตัดสิน: หากแถวในชุดข้อมูลทดสอบส่วนใหญ่มีข้อความที่เกือบซ้ำกัน (near-twin) ในคลังข้อมูลของคุณ โมเดลที่เทรนด้วยข้อมูลทั้งหมดจะกลายเป็นการวัดผลการจำจำลองวลีที่ใช้เทรน ไม่ใช่การแปล จากนั้นคุณมักจะต้องเทรนสองโมเดล: โมเดลหนึ่งเทรนด้วยข้อมูลทั้งหมด และอีกโมเดลหนึ่งแบบไม่มีข้อความซ้ำ (`--drop-test-twins` จะเขียนคลังข้อมูลและการกำหนดค่าของโมเดลนี้, `config-notwins.json`)
3. **เขียนสิ่งที่คุณคาดหวังลงไป โดยทำหนึ่ง preregistration ต่อหนึ่งโมเดลที่คุณวางแผนจะเทรน** และตั้งชื่อตามโมเดลนั้น การคาดการณ์เหล่านี้คือสิ่งที่จะใช้ตัดสินคะแนนทดสอบในภายหลัง: ขั้นตอนการส่งออก (export) จะตัดสินแต่ละโมเดลเทียบกับโมเดลที่คุณระบุด้วย `--prereg <id>` (หากมีสองโมเดลบนชุดข้อมูลทดสอบเดียว ระบบจะปฏิเสธที่จะคาดเดาเอง) คุณสามารถตรึงการคาดการณ์ไว้กับการกำหนดค่าของโมเดลนั้นได้ด้วย `--config-hash <hash>` ซึ่งเป็นแฮชเต็มรูปแบบที่ `nmt-forge preflight run --config config-notwins.json` พิมพ์ออกมา การแก้ไขการกำหนดค่านั้นในภายหลัง (เช่น ปรับเวลา time budget) จะทำให้แฮชเปลี่ยนและยกเลิกการตรึง ดังนั้นการตั้งชื่อ prereg ตอน export จึงเป็นวิธีที่ง่ายกว่า

```bash
nmt-forge init crk --dir school-crk
cd school-crk
nmt-forge registry add project-test ../data/test.tsv --role test
nmt-forge leak-audit ../data/corpus.tsv --clean-to corpus.clean.jsonl
nmt-forge prereg template --out predictions.json      # edit it: what you expect, and why
nmt-forge prereg new all-data --eval-set project-test --predictions predictions.json
cd ..                                                 # step 3 runs from here
```

หากผลการตัดสินออกมาเป็น SEVERE ให้เพิ่มโมเดลแบบไม่มีข้อความซ้ำ (twin-free) และการคาดการณ์ของโมเดลนั้นลงไป (ใน `school-crk/`):

```bash
nmt-forge leak-audit ../data/corpus.tsv --clean-to corpus.notwins.jsonl --drop-test-twins
nmt-forge prereg new notwins --eval-set project-test --predictions predictions-notwins.json  # your edited copy
```

คลังข้อมูลแบบ twin-free จะถูกบันทึกแยกเป็นไฟล์ของตัวเอง `corpus.clean.jsonl` จะยังคงเป็นคลังข้อมูลที่มีข้อมูลทั้งหมด: leak-audit จะปฏิเสธการเขียนทับไฟล์ที่มีการกำหนดค่า, การรัน หรือการแบ่งส่วนข้อมูล (split) กำลังอ่านอยู่ หรือไฟล์ที่ audit อื่นเขียนขึ้น (`--overwrite` ใช้สำหรับตั้งใจแทนที่ไฟล์เดิม) คำตอบใน `--json` จะแสดงหมายเลขแถวแรก ๆ ของแต่ละรายการ; ส่วนไฟล์ `.audit.json` ที่อยู่ข้าง ๆ คลังข้อมูลที่ล้างแล้วจะเก็บข้อมูลทั้งหมดไว้

`--allow-after-reads` มีไว้สำหรับการคาดการณ์ที่ถูกเขียนขึ้นล่วงหน้าก่อนการอ่านข้อมูลจริง ๆ เท่านั้น (เช่น เขียนไว้บนกระดาษ) ข้อมูลนี้จะถูกบันทึกไว้ และรายงานทุกฉบับ
export and DEPLOY.md then says the predictions came after the scores.

**Agent:** `forge_init { "code": "<code>", "dir": "<dir>" }` จากนั้น
`forge_register_eval { "name": "project-test", "path": "../data/test.tsv", "role": "test", "project_dir": "<dir>" }`,
`forge_leak_audit { "corpus": "../data/corpus.tsv", "clean_to": "corpus.clean.jsonl", "project_dir": "<dir>" }`
(พาธจะถูกอ่านจาก `project_dir` เนื่องจากคำสั่งด้านบนถูกรันจากภายในโปรเจกต์; พาธแบบสัมบูรณ์ (absolute path) สามารถใช้ได้จากทุกที่),
จากนั้นเรียก `forge_prereg_template` → `forge_prereg { id, eval_set, predictions }`
ร่วมกับผู้ใช้ หนึ่งรายการต่อหนึ่งโมเดล แต่ละรายการตั้งชื่อตามโมเดลของตน (จากนั้น `forge_export` จะรับ id นั้นเป็น `prereg`; หรือใช้ `config_hash` บน `forge_prereg` เพื่อตรึงเข้ากับการกำหนดค่าแทน) `forge_status` จะระบุขั้นตอนนี้ทันทีที่ชุดข้อมูลทดสอบได้รับการลงทะเบียน ขั้นตอนที่ 4 จะทำการเทรนในโปรเจกต์เดียวกัน
`language_overview` ก็จะแสดงรายการขั้นตอนเหล่านี้ตามลำดับเช่นกัน

## 3. วัดผลตัวเลือกต่าง ๆ

รันการทดสอบแต่ละตัวเลือกเทียบกับชุดข้อมูลทดสอบของ**คุณ** (ซึ่งต้องได้รับการลงทะเบียน, คัดกรอง และ preregister กับ forge ไว้ก่อน หากคุณอาจเทรนโมเดลในภายหลัง —
[ขั้นตอนที่ 2](#2-gather-your-data--and-protect-your-test-set)) ระบบทดสอบจะให้คะแนนทุกตัวเลือกด้วยวิธีการเดียวกัน ตามแนวทางมาตรฐานการรายงานผลการประเมิน MT ในวงการวิชาการ: ค่าหลักคือระดับคลังข้อมูล chrF++ พร้อมช่วงความเชื่อมั่น (confidence interval) 95% เคียงคู่กับ BLEU, spBLEU และ TER (ไม่นำมารวมกันเป็นตัวเลขเดียว) การจับคู่ตรงกันทุกประการ (Exact match) และการตรวจสอบพฤติกรรม (ผลลัพธ์ผิดระบบการเขียน, สัญญาณอาการประสาทหลอน/hallucination) จะถูกรายงานเป็นการวินิจฉัย พร้อมด้วยต้นทุนค่าใช้จ่ายและความเร็วควบคู่กันไป ในกรณีที่ระบบทดสอบมีการตรึงเครื่องมือวิเคราะห์ทางสัณฐานวิทยาสำหรับภาษานั้นไว้ ก็จะเพิ่มการยอมรับของ FST (FST acceptance) และความถูกต้องทางสัณฐานวิทยาเข้ามาเป็นข้อมูลวินิจฉัยด้วย;
`mt-eval setup --status` จะแสดงรายชื่อภาษาเหล่านั้น และ `mt-eval setup --comet`
จะเพิ่ม COMET ในกรณีที่สามารถใช้ได้

```bash
# a hosted model (needs OPENROUTER_API_KEY); --max-cost stops before spending more
mt-eval run --corpus data/test.tsv --source-lang English --target-lang "Plains Cree" \
  --target-lang-code crk --provider openrouter --model google/gemini-3.8-flash \
  --max-cost 1 -n gemini-3.8-flash -o results

# a model on your own machine (Ollama, llama.cpp, vLLM — anything OpenAI-compatible)
mt-eval run --corpus data/test.tsv --source-lang English --target-lang "Plains Cree" \
  --target-lang-code crk --provider local --base-url http://127.0.0.1:11434/v1 \
  --model llama3.1 -n local-llama -o results

mt-eval compare results/*_report.json --significance
```

`compare` จะระบุว่าความแตกต่างนั้นมีนัยสำคัญจริงหรือเป็นเพียงความคลาดเคลื่อนทางสถิติ (paired approximate randomization) ความแตกต่างที่อยู่ภายในช่วงความเชื่อมั่นจะไม่ถือเป็นการจัดอันดับ คำสั่งนี้จะเขียนไฟล์ `comparison-<hash>.json` ซึ่งตั้งชื่อตามรอบการรันที่นำมาเปรียบเทียบกัน ไว้ข้าง ๆ รายงานหากอยู่ในโฟลเดอร์เดียวกัน หรือเขียนลงในโฟลเดอร์ `comparisons/` ที่อยู่เหนือขึ้นไปหากอยู่คนละโฟลเดอร์ โดยจะไม่เขียนลงในโฟลเดอร์ของรอบการรันใดรอบหนึ่งโดยเฉพาะ และการเปรียบเทียบครั้งอื่นจะไม่เขียนทับไฟล์นี้

**แพ็กเกจการประเมินผล (Evaluation packs)** บางภาษาจะมีการประกาศเครื่องมือเพิ่มเติมที่เมทริกซ์จำเป็นต้องใช้ (สำหรับ Plains Cree คือเครื่องมือวิเคราะห์ทางสัณฐานวิทยา) เมื่อรัน `mt-eval run` ครั้งแรก ระบบจะระบุสิ่งที่ขาดหายไป การที่ไม่มีเครื่องมือวิเคราะห์จะไม่ทำให้การรันหยุดชะงัก: FST acceptance จะถูกระบุว่าไม่ได้คำนวณ (not computed), คำสั่ง `mt-eval setup --lang crk` จะติดตั้งเครื่องมือดังกล่าว (ทำเพียงครั้งเดียวต่อเครื่อง) และจากนั้น `mt-eval test <run log>` จะเพิ่มคะแนนดังกล่าวให้โดยไม่ต้องทำการแปลใหม่อีกรอบ

**Agent:** `run_benchmark { "corpus": "data/test.tsv", "provider": "local",
"base_url": "http://127.0.0.1:11434/v1", "model": "llama3.1",
"target_language": "crk" }` plans first and runs only with `confirm: true`;
`get_run_status { "job_id": "<id>" }` จะส่งคืนคะแนนกลับมา ระบบจะไม่เผยแพร่สิ่งใดเว้นแต่คุณจะส่งค่า `publish: true` รหัสภาษาอย่าง `target_language` จะถูกแปลงเป็นชื่อจากในการ์ดภาษา ("Plains Cree") ก่อนที่จะส่งไปยังพรอมต์ และแผนจะแสดงพรอมต์ที่โมเดลจะได้รับ ไฟล์ช่วยเทรน (coaching file) จะเข้ามาแทนที่พรอมต์นั้น ซึ่งแผนงานจะระบุไว้เช่นกัน เมื่อการ์ดระบุระบบการเขียนไว้สองแบบและคุณไม่ได้ส่ง `script` แผนงานจะอ่านว่าชุดอ้างอิงใช้ระบบการเขียนแบบใด (นับตัวอักษรบนเครื่องของคุณ ไม่มีการแสดงประโยค) และจะร้องขอระบบการเขียนนั้น รายงานจะถูกบันทึกไว้ข้าง ๆ ไฟล์ทดสอบ ใน `data/results/mcp-run-<id>/` พร้อมแคชการแปลของระบบทดสอบใน `data/results/cache/` `get_run_status` จะพิมพ์คำสั่ง `mt-eval compare` สำหรับไฟล์เหล่านั้น และสำหรับการรันบน corpus id ที่ลงทะเบียนไว้ ระบบจะแสดงรายการรายงานตามพาธ แผนงาน `local-model` จะระบุไว้ล่วงหน้าว่าการยืนยันจะต้องดาวน์โหลดข้อมูลขนาดเท่าใดและดาวน์โหลดไปที่ใด

**เมทริกซ์ใดที่ควรเชื่อถือ** ขึ้นอยู่กับตัวภาษา:
`get_metric_reliability { "language": "<code>" }` (MCP) จะรายงานว่ามีเมทริกซ์อัตโนมัติใดที่เคยผ่านการตรวจสอบเทียบกับการตัดสินของมนุษย์สำหรับภาษานั้นหรือไม่ สำหรับภาษาที่มีทรัพยากรน้อยส่วนใหญ่จะยังไม่เคยมี ดังนั้น chrF++ จึงเป็นมาตรฐานที่นิยมใช้ — ให้อ่านค่านี้เพื่อเปรียบเทียบระหว่างวิธีการต่าง ๆ บนชุดข้อมูลทดสอบเดียวกัน ไม่ใช่การให้เกรดวัดผลสัมบูรณ์

## 4. สร้างสิ่งที่ดีกว่าเดิม

มีสองแนวทาง ให้วัดผลทั้งสองแนวทางด้วยวิธีเดียวกับขั้นตอนที่ 3

**เทรนไกด์โมเดลทั่วไป (Coach a general model)** ใส่คำอธิบายอภิธานศัพท์และคำแนะนำให้แก่โมเดล จากนั้นรันขั้นตอนที่ 3 ซ้ำอีกครั้งพร้อมกับคำแนะนำ:

```bash
mt-eval run --corpus data/test.tsv --source-lang English --target-lang "Plains Cree" \
  --target-lang-code crk --provider openrouter --model google/gemini-3.8-flash \
  --coaching-file coaching.json -n gemini-coached -o results
```

`--coaching-file` รองรับรูปแบบ Markdown, ข้อความธรรมดา (plain text) หรือ JSON; ข้อความทั้งหมดในไฟล์จะทำหน้าที่เป็นคำสั่งสำหรับโมเดล โดยจะถูกส่งไปตามที่เขียนไว้

หากต้องการคิดคะแนนคำศัพท์เฉพาะ (แต่ละคำศัพท์ที่ระบุไว้ถูกแปลออกมาตรงตามคำแปลที่กำหนดหรือไม่) ให้ส่งรายการคำศัพท์ชุดเดียวกันให้ทุกการรันที่คุณนำมาเปรียบเทียบผ่าน `--glossary terms.json` (`{"blood pressure": "…"}` หรือรายการรูปแบบคำที่ยอมรับได้ต่อหนึ่งคำศัพท์) อภิธานศัพท์นี้จะใช้สำหรับการคิดคะแนนเท่านั้น; จะไม่มีการส่งไปยังโมเดล ดังนั้นการรันแบบปกติและการรันแบบ coached จะถูกคิดคะแนนบนชุดคำศัพท์เดียวกัน หากไม่มี `--glossary` ระบบจะใช้ `dictionary` ของไฟล์ coaching แบบ JSON (รูปแบบ [coached prompting](/docs/network/tutorials/coached-llm-prompting): `grammar_rules`, `dictionary`, `style_notes`) แทน ในกรณีนั้น การรันจะถูกคิดคะแนนเทียบกับการ coaching ของตัวมันเอง และผลลัพธ์จะระบุไว้ชัดเจน ส่วนไฟล์ coaching แบบ Markdown จะช่วยไกด์โมเดลในลักษณะเดียวกันแต่ไม่มีอภิธานศัพท์มาให้

ดูเพิ่มเติมที่ [coached prompting](/docs/network/tutorials/coached-llm-prompting) และ
[dictionary-augmented prompting](/docs/network/tutorials/dictionary-augmented-llm)

**เทรนโมเดลของคุณเอง** ด้วย NMT Forge ซึ่งจะช่วยป้องกันข้อผิดพลาดที่มักทำให้ผลลัพธ์จากข้อมูลชุดเล็กดูดีเกินจริง (ข้อมูลทดสอบรั่วไหล, การแบ่งข้อมูลที่ไม่ดี, การเลือกเช็กพอยต์บนชุดทดสอบ, การตีความความคลาดเคลื่อนว่าเป็นความก้าวหน้า):

```bash
cd school-crk     # after step 2: registered, screened, preregistered
nmt-forge split corpus.clean.jsonl --test 0 --dev 100 --seed 42 --out data/split --register project
nmt-forge preflight run --config config.json          # every check run makes, with fixes
nmt-forge run config.json
nmt-forge export .forge/runs/<run>/run-manifest.json --prereg all-data --out export/
```

`preflight run` จะทำการตรวจสอบแบบเดียวกับที่ `run` ทำก่อนการเทรน — ชุด dev, การตรวจสอบการรั่วไหลของทุกไฟล์เทรน, ความยาวการถอดรหัส — ดังนั้นการรันที่ผ่านคำสั่งนี้จะไม่ถูกปฏิเสธเมื่อเริ่มต้น `config.json` จะอ่านการแบ่งส่วนข้อมูลจาก `data/split/`; หากการแบ่งส่วนข้อมูลถูกเขียนไว้ที่อื่น ระบบจะบอกว่าต้องแก้ไขบรรทัดใด

คู่ประโยคสำหรับเทรนจะอยู่ในไฟล์ TSV เช่นเดียวกับชุดทดสอบ (หรือ JSONL พร้อม `source` และ `target`); คำสั่ง `leak-audit` (ขั้นตอนที่ 2) ได้ตัดข้อมูลใดก็ตามที่จะทำให้ชุดทดสอบรั่วไหลไปสู่การเทรนออกไปแล้วพร้อมระบุเหตุผล หากต้องการเทรนสองโมเดล? หลังจากการแบ่งส่วนข้อมูลแล้ว ให้รัน leak-audit แบบ twin-free จากขั้นตอนที่ 2 อีกครั้ง (เมื่อลงทะเบียนชุด dev แล้ว แถวของชุด dev ก็จะถูกตัดออกจากไฟล์ twin-free ด้วยเช่นกัน) จากนั้นใช้ `nmt-forge run config-notwins.json` และ
export it to its own folder with `--prereg notwins`. `nmt-forge status` names
คำสั่งถัดไปได้ทุกเมื่อ โมเดลเริ่มต้นสามารถเทรนบน CPU ได้ภายในไม่กี่นาที; สำหรับคู่ประโยค 1–2 พันคู่ คาดหวังคะแนน chrF++ ได้ประมาณ 5–30 — โมเดลจะเรียนรู้วลีและรูปแบบของข้อมูลของคุณ ไม่ใช่ภาษาในภาพรวมทั้งหมด `export` จะคิดคะแนนชุดทดสอบหนึ่งครั้งและเขียนรายงาน mt-eval เพื่อให้สามารถเปรียบเทียบโมเดลที่เทรนแล้วกับทุกตัวเลือกจากขั้นตอนที่ 3 ได้ ดูคู่มือฉบับเต็มได้ที่: [เทรนโมเดลแรกของคุณ](/docs/network/getting-started/train-your-first-model)

**Agent:** ให้เรียกใช้ `forge_status { "project_dir": "<dir>" }` เป็นอันดับแรกและหลังจากทุกขั้นตอน; หลังจากทำ `forge_init`, `forge_register_eval`, `forge_leak_audit`
และ `forge_prereg` ในขั้นตอนที่ 2 แล้ว: ให้เรียก `forge_split { corpus, test, seed, out }`,
`forge_preflight { "target": "run" }` จากนั้น — หลังจากรัน `nmt-forge run` ในเทอร์มินัลแล้ว — ให้เรียก `forge_export { run_manifest, out, prereg }` เรียก
`get_training_guardrails` หนึ่งครั้งก่อน `forge_split`: เครื่องมือนี้จะแสดงกฎแต่ละข้อที่ forge บังคับใช้และข้อผิดพลาดที่กฎนั้นช่วยป้องกัน พารามิเตอร์ `register` ของ `forge_split` รับค่าเป็น prefix หรือ `true` (`project`) และ `out` มีค่าเริ่มต้นเป็น `data/split` เครื่องมือ forge ทุกตัวหลังจาก `forge_init` จะรับค่า `project_dir` ที่ส่งคืนกลับมา `get_training_guardrails` (ใส่ `topic` หรือไม่ก็ได้) จะอธิบายกฎแต่ละข้อ รายละเอียดอาร์กิวเมนต์ทั้งหมดของทุกเครื่องมือดูได้ที่: [MCP Server](/docs/network/getting-started/mcp-server#arguments)

## 5. พิสูจน์ผลลัพธ์ — แบบส่วนตัว หรือแบบสาธารณะ

คะแนนของคุณเป็นของคุณ จะไม่มีการเผยแพร่สิ่งใดสู่สาธารณะเว้นแต่คุณจะเลือกเปิดเผยเอง

```bash
mt-eval publish results/<run-id>_report.json --dry-run   # shows exactly what would leave, and what is withheld
mt-eval publish results/<run-id>_report.json --scores-only --prod
```

ชุดข้อมูลทดสอบที่เป็นส่วนตัวหรือเป็นแบบ local-only จะไม่ถูกอัปโหลดประโยคขึ้นไปโดยเด็ดขาด; `--dry-run` จะระบุแจ้งทีละบรรทัด หากต้องการให้ผู้อื่นเข้ามาแข่งขันประเมินผลบนชุดทดสอบของคุณโดยที่พวกเขาไม่มีทางเห็นเนื้อหา ให้จัดการแข่งขันขึ้นบนเครื่องที่คุณเป็นผู้ควบคุม: ผู้เข้าแข่งขันจะส่งมอบวิธีการแปลของตน วิธีการนั้นจะรันบนโหนดของคุณ และมีเพียงคะแนนเท่านั้นที่จะถูกส่งออกมา การแข่งขันใหม่จะซ่อนคะแนนทั้งหมดไว้จนกว่าการแข่งขันจะปิดลง เพื่อไม่ให้ใครสามารถนำชุดทดสอบของคุณไปใช้ปรับจูนโมเดลได้
ดูที่ [จัดการแข่งขันแบบ Sovereign](/docs/network/sovereignty/run-a-sovereign-contest)
หากต้องการส่งโมเดลที่คุณเทรนเข้าร่วมการแข่งขันของผู้อื่น ให้อ่าน `DEPLOY.md` §6 ในไฟล์ export ซึ่งจะระบุชื่อไฟล์ที่ประกอบกันเป็นผลงานที่ส่งและคำสั่ง `mt-eval contest submit-model` ที่แน่นอน

**Agent:** `list_contests { "language": "<code>" }`, `get_contest { id }`;
`get_results { "target_language": "<code>" }` และ `get_run_card { id }` สำหรับกระดานคะแนนสาธารณะ

## 6. รวมสิ่งที่ดีที่สุดเข้าด้วยกัน

**ตัดสินใจเลือกจากผลการวัดผลของคุณเองก่อน** ทุกสิ่งที่คุณวัดผลบนชุดข้อมูลทดสอบของคุณจะออกมาเป็นรายงาน mt-eval: ไม่ว่าจะเป็น baseline และรอบการรันแบบ coached จากขั้นตอนที่ 3 และ 4 รวมถึงไฟล์ export ของแต่ละโมเดลที่ผ่านการเทรน (`evaluation/runlog_report.json` ใน
export folder). A terminal run with `-o results` writes to
`results/*_report.json`; รอบการรันที่เริ่มผ่าน MCP `run_benchmark` จะเขียนไฟล์ไว้ข้าง ๆ ไฟล์ทดสอบ ใน `data/results/mcp-run-<id>/`) เปรียบเทียบทั้งหมดพร้อมกันได้ในครั้งเดียว — โดยใช้ glob แรกสำหรับการรันในเทอร์มินัล และ glob ที่สองสำหรับการรันผ่าน agent (เลือกใช้แบบที่ตรงกับรอบการรันของคุณ; zsh จะหยุดทำงานหาก glob ไม่ตรงกับไฟล์ใดเลย):

```bash
mt-eval compare results/*_report.json school-crk/export*/evaluation/runlog_report.json --significance
mt-eval compare data/results/mcp-run-*/*_report.json school-crk/export*/evaluation/runlog_report.json --significance
```

ความแตกต่างที่อยู่ภายในช่วงความเชื่อมั่นจะไม่ถือเป็นการจัดอันดับ และโมเดลที่ผ่านการเทรนซึ่งมีแถวในชุดทดสอบเกือบซ้ำ (near-twins) กับข้อมูลที่ใช้เทรนจะถือว่าได้คะแนนจากการจำ: ให้อ้างอิงตัวเลข twin-free ควบคู่ไปด้วยเสมอ (DEPLOY.md และ `nmt-forge report` จะระบุว่าเป็นตัวเลขใด) พร้อมด้วย**ข้อควรระวังของคะแนน (score caveat)** ที่ mt-eval ระบุไว้กับตัวเลขนั้น ข้อควรระวังประเภท *near-constant output* (การให้ผลลัพธ์เป็นประโยคเดิมซ้ำ ๆ ให้กับประโยคทดสอบที่แตกต่างกันจำนวนมาก) หมายความว่าผลลัพธ์ไม่ได้แปรผันตามข้อความต้นฉบับ ไม่ว่าคะแนนจะได้เท่าใดก็ตาม; forge จะพิมพ์เตือนไว้ข้างคะแนนใน `export`, `DEPLOY.md`, `status`, `report`, `compare` และ `lint` หากมีโมเดลที่ export หลายโมเดล `nmt-forge status` จะแสดงรายการแต่ละโมเดลพร้อมคะแนน, คะแนนแบบ twin-free และข้อควรระวัง และจะขอให้คุณเลือกว่าจะนำโมเดลใดไปใช้งานจริง ให้บันทึกตัวเลือกด้วย `nmt-forge choose <export>/model` (หรือ `nmt-forge serve <export>/model --choose`) การรัน serve โมเดลเพื่อทดลองใช้จะถูกบันทึกว่าเป็นเพียงการทดลองเสิร์ฟ ไม่ใช่โมเดลที่คุณเลือกใช้งาน ดังนั้น `status` จะยังคงถามซ้ำจนกว่าคุณจะเลือก

**Agent:** `forge_status { "project_dir": "<dir>" }` — ในสถานะ
`choose-export` ให้แสดง `result.advice.exports` แก่ผู้ใช้ พร้อมทั้งคะแนนของแต่ละ export และ `score_caveats` ของแต่ละโมเดล แล้วถามผู้ใช้ว่าจะนำโมเดลใดไปใช้งานจริง; คำตอบของผู้ใช้จะถูกบันทึกด้วยคำสั่ง `nmt-forge choose` ในเทอร์มินัล การเสิร์ฟแบบชั่วคราวจะไม่ถือเป็นการตอบคำถามนี้ `forge_compare { eval_set, hyps_a, hyps_b }` จะทำการทดสอบ A/B ระหว่างสองโมเดลของ forge พร้อมแสดงข้อควรระวัง near-twin และข้อควรระวังคะแนน mt-eval ของแต่ละโมเดลเคียงข้างโมเดลที่ชนะ; โดยไฟล์ hypotheses ของแต่ละโมเดลคือพาธ `hypotheses` ที่ `forge_export` ส่งคืนมา (`<export>/evaluation/battery-hyps.jsonl`)

จากนั้นให้มองออกไปให้กว้างกว่ารอบการรันของคุณเอง วิธีการที่แตกต่างกันอาจให้ผลลัพธ์ที่ดีที่สุดสำหรับคู่ภาษาและประเภทข้อความที่ต่างกัน หน้า [เครือข่าย (Network)](/docs/network/) จะแสดงรายการวิธีการและบริการที่มีอยู่ รวมถึงหลักฐานอ้างอิงของแต่ละรายการ — ซึ่งเป็นสิ่งที่เคยได้รับการเผยแพร่มาแล้ว ไม่ใช่สิ่งที่คุณวัดผลเอง:

```bash
champollion network recommend eng crk               # runnable methods + cited evidence for the pair
champollion network leaderboard --pair "eng>crk"     # published results for the pair
```

วิธีการที่เผยแพร่อยู่บนกระดานผู้นำ (leaderboard) พร้อมการกำหนดค่า สามารถนำมาติดตั้งได้ตรงตามการกำหนดค่าเดิมที่มีการวัดคะแนนไว้ทุกประการ: คำสั่ง `champollion network leaderboard --install <method> --apply` จะเพิ่มค่านั้นลงในโปรเจกต์ของคุณสำหรับคู่ภาษานั้น โดย CLI จะกำหนดค่าวิธีการแปล**แยกตามแต่ละคู่ภาษา** ดังนั้นภาษา Cree สำหรับจดหมายข่าวจึงสามารถใช้โมเดลที่คุณเทรนเองได้ ในขณะที่ภาษาฝรั่งเศสสามารถใช้โมเดลแบบโฮสต์ได้ การต่อเชื่อมวิธีการแปลหลายตัวเข้าด้วยกัน (เช่น ใช้โมเดลก่อนแล้วตามด้วยตัวตรวจสอบ) สามารถอ่านเพิ่มเติมได้ที่ [chained models](/docs/network/tutorials/chained-models)

## 7. นำไปใช้งานจริง

นำวิธีการที่คุณได้ทำการวัดผลจริงไปใช้งาน — อย่าใช้วิธีอื่นที่ไม่ได้วัดผล

```bash
nmt-forge serve export/model                     # your trained model on http://127.0.0.1:8378
LOCAL_API_BASE=http://127.0.0.1:8378/v1 champollion sync --method local
```

ในขณะที่โมเดลกำลังทำงาน `nmt-forge status` จะระบุว่า `serving` (ระบบจะคอยตรวจสอบว่าเซิร์ฟเวอร์ยังตอบสนองอยู่หรือไม่); หลังจากเซิร์ฟเวอร์หยุดทำงาน ระบบจะแจ้งคำสั่ง `serve` อีกครั้ง บนพอร์ตเดิม

หรือหากเป็นโมเดลแบบโฮสต์ที่มีการ coached ให้กำหนดค่านั้นให้กับคู่ภาษาใน `champollion.config.json` ไม่ว่าจะเลือกวิธีใด:

```bash
champollion init --langs crk     # detects your app's locale files
champollion sync                 # translates only what changed
champollion verify               # placeholders, scripts, key parity
```

**สิ่งที่โมเดลของคุณเองยังทำไม่ได้ในตอนนี้** โมเดลขนาดเล็กที่เทรนด้วยประโยคเพียงไม่กี่พันประโยคจะเรียนรู้เฉพาะวลีเหล่านั้น บ่อยครั้งที่โมเดลจะทำความเสียหายให้กับตัวแทนข้อความ (`{name}`), รูปแบบพหูพจน์ และมาร์กอัป หรือเปลี่ยนป้ายข้อความสั้น ๆ เช่น "Home" ให้กลายเป็นทั้งประโยค ระบบคัดกรองคุณภาพ (quality gate) จะปฏิเสธผลลัพธ์เหล่านั้น; จะไม่มีข้อความที่เสียหายถูกเขียนลงไป ให้กำหนด **fallback** ให้กับคู่ภาษานั้น แล้วสตริงข้อความเหล่านั้นจะถูกส่งต่อไปยังวิธีการแปลสำรองลำดับที่สองในการซิงค์รอบเดียวกัน:

```json
"pairs": {
  "en:crk": {
    "method": "api",
    "endpoint": "http://127.0.0.1:8378/translate",
    "fallback": { "method": "llm-coached", "model": "google/gemini-3.8-flash" }
  }
}
```

หากไม่มีข้อความใดที่สามารถส่งออกจากเครื่องของคุณได้ ให้กำหนด fallback เป็นโมเดลที่คุณรันบนเครื่องนั้นด้วยเช่นกัน: `"fallback": { "method": "local", "model": "<your local model>" }` จะส่งคำขอไปยังเซิร์ฟเวอร์ที่รองรับ OpenAI บนเครื่องนี้ (Ollama, llama.cpp, vLLM) โดยไม่มีค่าใช้จ่าย API ($0) โดยทั่วไปแล้วโมเดลแบบโฮสต์มักจะให้ความเห็นที่สองที่แม่นยำกว่า; ให้ใช้โมเดลประเภทนี้เมื่อข้อความนั้นได้รับอนุญาตให้ส่งไปยังผู้ให้บริการได้

โมเดลของคุณจะแปลทุกประโยคเท่าที่สามารถทำได้ วิธีการ fallback จะได้รับเฉพาะประโยคที่ถูกปฏิเสธจาก gate รวมถึงบล็อก Markdown ที่ถูกตัดทิ้งหรือเสียหาย และผลลัพธ์ของ fallback ก็จะต้องผ่าน gate เดียวกันนี้ด้วย `sync` จะพิมพ์บรรทัด `[FALLBACK]` สำหรับแต่ละคู่ภาษาพร้อมแสดงจำนวนนับ และ `champollion verify` จะแสดงรายการข้อความที่ไม่สามารถแปลได้จากทั้งสองวิธี ดูเพิ่มเติมที่ [วิธีการ Fallback](/docs/getting-started/configuration#fallback)

สำหรับการแปลเฉพาะกิจแบบครั้งเดียว คุณสามารถเลือกแปลเฉพาะสตริงเหล่านั้นด้วยวิธีอื่นได้:

```bash
champollion sync --method llm-coached --redo keys:nav.home,greeting
```

…หรือแปลด้วยตนเอง หรือส่งให้ผู้ตรวจทานผ่าน `champollion xliff export` และอย่ายืมนำสตริงของแอปพลิเคชันมาใส่ไว้ในชุดข้อมูลทดสอบของคุณ: โมเดลที่ทำคะแนนได้ดีกับประโยคของคุณครู อาจแปลประโยคอย่าง "Where does it hurt?" (เจ็บตรงไหน?) ผิดพลาดได้

**ระบบการเขียน** หากภาษานั้นมีระบบการเขียนมากกว่าหนึ่งแบบ (เช่น Plains Cree: อักษรโรมันมาตรฐาน (SRO) และอักษรพยางค์ (syllabics)) CLI จะขอให้คุณเลือกก่อนทำการแปล ให้ตั้งค่า `"script"` สำหรับภาษานั้นในการกำหนดค่า; ข้อความจะแสดงรายการตัวเลือกที่มีให้เลือก

หน่วยความจำการแปล (translation memory) จะช่วยให้คุณไม่ต้องจ่ายเงินซ้ำสองให้กับประโยคที่ไม่มีการเปลี่ยนแปลง และการสลับโมเดลจะไม่ทำให้ต้องแปลใหม่ทั้งหมด เชื่อมต่อกระบวนการนี้เข้ากับ CI ได้โดยดูที่ [คู่มือ CI/CD](/docs/guides/ci-cd) โดยที่ `export/model/DEPLOY.md` (จากขั้นตอนที่ 4) จะระบุการกำหนดค่าที่แน่นอนสำหรับโมเดลที่เทรนแล้ว รวมถึงวิธีการ `api` และวิธีเปิดให้บริการบนเครือข่ายอย่างปลอดภัย

**Agent:** `translate { texts, source_language, target_language }` จะส่งสตริงผ่านไปป์ไลน์เดียวกัน เพิ่ม `method: "local"` และ `base_url` หรือ
`method: "api"` และ `endpoint` สำหรับโมเดลที่คุณโฮสต์เอง และใส่ `script` สำหรับภาษาที่มีระบบการเขียนมากกว่าหนึ่งแบบ

## การตัดสินใจในแต่ละขั้นตอน

| การตัดสินใจ | เลือก… | เมื่อ |
|---|---|---|
| ตำแหน่งจัดเก็บชุดทดสอบ | local-only | ข้อมูลมีความละเอียดอ่อน หรือคุณยังไม่ได้ขออนุญาตจากผู้ที่เขียนข้อความเหล่านั้น |
| | private / sealed | คุณต้องการให้ผู้อื่นรู้ว่ามีชุดข้อมูลนี้อยู่ หรือต้องการให้แข่งขันประเมินผลได้ โดยไม่เห็นเนื้อหา |
| Coached หรือเทรนเอง | Coached โมเดลแบบโฮสต์ | คุณมีอภิธานศัพท์และมีข้อความคู่ขนานน้อย รวมถึงยอมรับการใช้บริการภายนอกได้ |
| | เทรนด้วย forge | คุณมีคู่ประโยคตั้งแต่สองสามพันคู่ขึ้นไป หรือข้อมูลต้องอยู่บนเครื่องของคุณเท่านั้น |
| การเผยแพร่ | เผยแพร่เฉพาะคะแนน | เป็นค่าเริ่มต้นสำหรับข้อมูลใดก็ตามที่คุณไม่ได้เขียนขึ้นเอง |
| | ไม่เผยแพร่สิ่งใด | อนุญาตให้ทำได้เสมอ — การวัดผลเป็นการภายในก็มีประโยชน์อย่างยิ่ง |

## ค่าใช้จ่าย

- เครื่องมือเหล่านี้ใช้งานได้ฟรีสำหรับการใช้งานที่ไม่ใช่เชิงพาณิชย์: ครอบคลุมถึงโรงเรียน, โรงพยาบาลหรือคลินิกรัฐ, องค์กรการกุศล หรือโครงการวิจัย (CLI, nmt-forge และเซิร์ฟเวอร์ MCP ใช้สัญญาอนุญาต PolyForm Noncommercial 1.0.0; ส่วนระบบทดสอบประเมินผลเป็นโอเพนซอร์ส สัญญาอนุญาต AGPL-3.0-or-later) [ใครที่สามารถใช้งานได้บ้าง](/docs/getting-started/who-may-use-this)
- โมเดลแบบโฮสต์จะมีค่าใช้จ่ายตามที่ผู้ให้บริการเรียกเก็บ; `--max-cost` จะหยุดการรันก่อนที่ค่าใช้จ่ายจะเกินกว่าที่คุณกำหนดไว้ และรายงานจะแสดงค่าใช้จ่ายต่อประโยค ส่วนโมเดลในเครื่องจะไม่มีค่าใช้จ่ายใด ๆ นอกจากเวลาการทำงานของเครื่องคุณ
- การเทรนโมเดลเริ่มต้นของ forge ใช้เพียง CPU และใช้เวลาไม่กี่นาที; พรีเซ็ตขนาดใหญ่ขึ้นจะต้องใช้ GPU
