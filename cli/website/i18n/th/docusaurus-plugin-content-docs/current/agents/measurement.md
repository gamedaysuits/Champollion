# กฎเกณฑ์การวัดผล

แนวทางคุ้มครอง (rails) สัญญาว่าชุมชนจะ**รู้**ว่าโมเดลทำงานได้ดีเพียงใดกับประโยคของตนเอง — ไม่ได้สัญญาว่ามันจะออกมาดี คำสัญญานั้นตั้งอยู่บนกฎเกณฑ์ไม่กี่ข้อ ซึ่งส่วนใหญ่มีการบังคับใช้อย่างเคร่งครัด หน้านี้ระบุกฎเกณฑ์เหล่านั้นไว้อย่างชัดเจน และปิดท้ายด้วยวิธีระบุตัวเลขอย่างถูกต้อง

## มาตรฐานการให้คะแนน (standard/1)

การรันใหม่ทุกครั้งจะได้รับการให้คะแนนในรูปแบบเดียวกัน (`arena/mt_eval_harness/scoring.py`):

- **คะแนนหลัก (headline):** **chrF++** ระดับคลังข้อมูล (sacreBLEU chrF ที่กำหนด word order เป็น 2) ตั้งแต่ 0 ถึง 100 — ยิ่งสูงยิ่งใกล้เคียงกับคำแปลอ้างอิง — พร้อมกับ **ช่วงความเชื่อมั่นแบบบูตสแตรป 95%** และซิกเนเจอร์ของ sacreBLEU เขียนระบุเป็น `chrF++ 47.5 [45.9, 49.0]`
- **เซกเมนต์ใดบ้างที่นับ:** ใช้กฎเดียวกันสำหรับคะแนนหลัก ช่วงความเชื่อมั่น และทุกการเปรียบเทียบ เซกเมนต์ที่แปลไม่สำเร็จจะนับเป็นผลลัพธ์ว่างเปล่า — ไม่มีการตัดทิ้ง และไม่คิดคะแนนแบบข้อความแทนที่ (placeholder) ส่วนเซกเมนต์ที่ไม่มีคำแปลอ้างอิงจะถูกละเว้นในทุกจุด
- **ช่วงความเชื่อมั่น:** มาจากตัวคะแนนหลักเอง — ใช้วิธี percentile bootstrap จากเซกเมนต์เหล่านั้น สุ่มซ้ำ 1,000 ครั้ง (seed 12345, α 0.05) หากต่ำกว่า 30 เซกเมนต์ เครื่องมือจะเตือนว่าช่วงความเชื่อมั่นอาจมีความครอบคลุมต่ำ และหากน้อยกว่า 2 เซกเมนต์จะไม่มีช่วงความเชื่อมั่น
- **แสดงเคียงข้างกัน ไม่นำมาปะปน:** BLEU, spBLEU, TER และ COMET (เมื่อมีการคำนวณ) โดยแต่ละตัวจะแสดงพร้อมซิกเนเจอร์หรือ model id ของตนเอง
- **การวินิจฉัย แยกไว้ต่างหาก:** exact match, equivalent match, FST acceptance, morphological accuracy, semantic validator, code-switching, hallucination, terminology adherence, writing style สิ่งเหล่านี้จะไม่รวมอยู่ในคะแนนหลักและไม่ใช้จัดอันดับ
- **คำว่า "ดีกว่า" ต้องมาจากการทดสอบนัยสำคัญแบบจับคู่ (paired significance test)** บน chrF++ เสมอ ไม่ใช่การกะดูเปรียบเทียบตัวเลขด้วยสายตา
- **ไม่มีป้ายกำกับคุณภาพ** มีเพียงการประเมินโดยมนุษย์เท่านั้นที่รับรองคุณภาพได้

**ยกเลิกการใช้งานแล้ว:** คะแนนรวมถ่วงน้ำหนัก (weighted composite score) และป้ายกำกับระดับคุณภาพ (quality-tier labels) run card แบบ standard/1 จะระบุ `composite: null` และ `quality_tier: null` **ข้อสังเกต** ห้ามนำเสนอ คำนวณ หรืออ้างอิงคะแนนรวมหรือระดับคุณภาพ ไม่ว่าจะจากการ์ดเก่าก็ตาม

**ข้อควรระวังของคะแนน (score caveats)** คือการวินิจฉัยที่เขียนกำกับไว้ข้างคะแนน ไม่ใช่การแก้ไขคะแนน: `source_copy` (ผลลัพธ์ครึ่งหนึ่งหรือมากกว่าคัดลอกข้อความต้นทางมา), `length_inflation` และ `length_deflation` (ผลลัพธ์ยาวเกินสองเท่า หรือสั้นกว่าครึ่งหนึ่งของความยาวอ้างอิง — โดยเฉลี่ย หรือในหนึ่งในสี่ของเซกเมนต์ขึ้นไป), `near_constant_output` (ผลลัพธ์เดียวซ้ำกันในหลายต้นทาง) และ `train_test_near_twin` (แถวชุดทดสอบที่มีแถวแฝดในชุดฝึกฝน — เป็นเรื่องสำคัญเมื่อมีตั้งแต่ครึ่งหนึ่งขึ้นไป) **ข้อสังเกต** โปรดส่งต่อทุกข้อควรระวังไปพร้อมกับคะแนนแบบคำต่อคำ

## การวัดผลแบบมีเกต (gated measurement)

เมื่อการรันมีห่วงโซ่เกต (gate chain) ([วิธีการและเกต](/docs/agents/methods#gate-chains)) **สิ่งที่วัดคือสิ่งที่จะนำไปใช้งานจริง**:

- คะแนนหลัก chrF++ จะวัดผลลัพธ์ที่ผ่านเกตแล้ว
- คะแนน chrF++ แบบไม่ผ่านเกต พร้อมช่วงความเชื่อมั่น จะแสดงอยู่เคียงข้างกัน (`overall.gates.ungated`)
- **อัตราการปฏิเสธ (refusal rate)** — จำนวนเซกเมนต์ที่เกตปฏิเสธ ÷ จำนวนเซกเมนต์ที่ตัดสิน — เป็นตัวเลขเฉพาะของตัวเอง พร้อมจำนวนนับแยกตามเกตและตามสิ่งที่นำไปใช้จริง (`shipped_from`: วิธีการ, ต้นทาง, วิธีสำรอง, ไม่มีอะไรเลย)
- **ลายนิ้วมือ (fingerprint)** ของห่วงโซ่ (sha256 ของ JSON แบบบัญญัติ) จะแนบไปกับรายงานและการรันที่เผยแพร่ทุกครั้ง

**การล็อก** ห้ามใช้วิธีสำรองในการวัดผล: `mt-eval run` และ `mt-eval test` จะปฏิเสธห่วงโซ่ที่เกตส่งเซกเมนต์ที่ถูกปฏิเสธไปยังวิธีสำรอง ก่อนที่จะมีการแปลหรือใช้ทรัพยากรใดๆ

**ข้อสังเกต** รายงานคะแนนที่ผ่านเกตควบคู่ไปกับคะแนนที่ไม่ผ่านเกตและอัตราการปฏิเสธเสมอ การรายงานคะแนนที่ผ่านเกตเพียงอย่างเดียวจะบดบังสิ่งที่เกตคัดทิ้งไป

## ชุดข้อมูลและหน้าที่ของแต่ละชุด

| บทบาท | ใช้สำหรับ | การอ่าน |
|---|---|---|
| `train` | การเรียนรู้ | ไม่เคยนำมาคิดคะแนนเป็นผลลัพธ์ |
| `dev` (การฝึกซ้อม) | การเลือกเช็กพอยต์; การตัดสินรอบการปรับปรุง (ตั้งแต่ 50 ประโยคขึ้นไป); ค่าพื้นฐานของพจนานุกรม | ได้อย่างอิสระ |
| `test` | เหตุการณ์สำคัญ: การทดสอบโมเดล เทียบกับการคาดการณ์ของผู้คน | การอ่านเพื่อคิดคะแนนทุกครั้งต้องมีการลงทะเบียนล่วงหน้า (forge); การอ่านทุกครั้งจะถูกบันทึกไว้ |
| `sealed` | การทดสอบที่ไม่มีใครภายนอกกลุ่มผู้ถือกรรมสิทธิ์มองเห็น | ครั้งเดียว |

**ใน nmt-forge** (รีจิสทรี, `.forge/eval-registry.json`, สมุดบัญชี):

- **การล็อก** การอ่านชุดข้อมูลที่ลงทะเบียนไว้ทุกครั้งจะถูกบันทึกลงในสมุดบัญชีแบบ hash-chained พร้อมระบุวัตถุประสงค์ (`score`, `dev-selection`, `audit`, `inspect`)
- **การล็อก** การคิดคะแนนชุดทดสอบต้องมีการลงทะเบียนล่วงหน้า (preregistration) ที่ถูกต้องสำหรับเนื้อหาปัจจุบันของชุดนั้น
- **การล็อก** ชุดข้อมูลที่ปิดผนึก (sealed set) จะคิดคะแนนได้เพียงครั้งเดียว การคิดคะแนนครั้งที่สองจะถูกปฏิเสธ (`sealed set '<name>' has already been spent`); a single `mt-eval` ที่อ่านไฟล์ที่ปิดผนึกก็จะถือว่าใช้สิทธิ์ไปแล้วเช่นกัน `--override-respend '<reason>'` (บน `nmt-forge score` และ `nmt-forge compare`) จะถูกบันทึกลงในสมุดบัญชี `export` จะปฏิเสธการใช้ซ้ำและระบุชื่อ `--no-eval`
- **การล็อก** รั้วกั้น dev (dev fence): การฝึกฝนต้องใช้ชุดข้อมูล `dev` ที่ลงทะเบียนไว้ แถวใน dev ต้องไม่มีต้นทางหรือปลายทางที่ตรงกันทุกประการกับชุดทดสอบหรือชุดที่ปิดผนึก และต้องไม่มีแถวฝึกฝนใดเป็นแถว dev

**ใน mt-eval:**

- **ข้อสังเกต** `mt-eval run` และ `mt-eval compare` คิดคะแนนไฟล์ทดสอบหรือไฟล์ที่ปิดผนึกโดยไม่ต้องมีการลงทะเบียนล่วงหน้า และไม่ปฏิเสธจากจำนวนครั้งที่อ่าน `mt-eval run` จะเพียงแค่เพิ่มบรรทัดลงในบันทึกการอ่านของไฟล์ (`<file>.reads.jsonl`) เมื่อ forge ได้สร้างบันทึกไว้เท่านั้น ส่วน `compare` และ `test` จะไม่บันทึกอะไรเลย ห้ามคิดคะแนนชุดทดสอบด้วย mt-eval ก่อนที่จะมีการเขียนการคาดการณ์ของชุมชน

## การคาดการณ์ (Predictions)

```bash
nmt-forge prereg new first-model --eval-set project-test --expect "<their words>" --rationale "<their reason>"
nmt-forge prereg new round-2 --eval-set project-test --predictions predictions.json
nmt-forge prereg template --out predictions.json
```

- `--expect` และ `--rationale`: การคาดการณ์แบบข้อความอิสระหนึ่งข้อความเกี่ยวกับ chrF++ ด้วยถ้อยคำของชุมชนเอง คำตัดสินเป็นของชุมชน: `nmt-forge prereg verdict <id> --prediction <n> --held` (or `--missed`) `--by "<who>"`
- `--predictions <file>`: อาร์เรย์ JSON โดยการคาดการณ์แต่ละข้อจะระบุ `metric` และ `rationale` และระบุอย่างใดอย่างหนึ่งระหว่าง `direction` (`increase`, `decrease`, `no_change`) พร้อม `baseline_score` (และระบุ `margin` เพิ่มเติมได้) — ซึ่งตัดสินโดยเครื่องมือ — หรือเป็นข้อความอิสระ `expect`
- **การล็อก** การคาดการณ์ที่เขียนขึ้นหลังจากการอ่านเพื่อคิดคะแนนของชุดข้อมูลดังกล่าว (โดย forge หรือโดย `mt-eval run`) จะถูกปฏิเสธ: *"eval set '…' was already read for scoring (N time(s): …) before this preregistration"* โดย `--allow-after-reads` จะยอมให้ผ่านได้ และทุกรายงาน การส่งออก และสถานะจะระบุไว้อย่างชัดเจน
- **ข้อสังเกต** การคาดการณ์เป็นของชุมชน ซึ่งเขียนขึ้นก่อนที่จะมีคะแนนใดๆ คุณต้องไม่ปรับเปลี่ยนถ้อยคำหรือตีกรอบให้แคบลง คำถามของแนวทางคุ้มครองไม่ได้ชี้แนะตัวเลขใดๆ (*"No number is suggested here, so the guess stays theirs"*) คุณจึงไม่ควรเสนอแนะตัวเลขใดๆ เช่นกัน

## ข้อมูลเกือบซ้ำ (Near-copies)

`nmt-forge leak-audit` เปรียบเทียบคู่ข้อมูลฝึกฝนทุกคู่กับชุด dev, ชุดทดสอบ และชุดที่ปิดผนึกทุกชุดที่ลงทะเบียนไว้:

| สิ่งที่พบ | กฎ | สิ่งที่เกิดขึ้น |
|---|---|---|
| ไฟล์เดียวกัน | sha256 | ตัดทิ้ง |
| สำเนาตรงกันทุกประการ | ต้นทางเหมือนกันหรือปลายทางเหมือนกันหลังปรับให้เป็นมาตรฐาน (normalization) | ตัดทิ้ง |
| สำเนาใกล้เคียงกัน | ชุดคำปลายทางทับซ้อนกัน ≥ 0.6 (Jaccard) เมื่อฝั่งหนึ่งครอบคลุมอีกฝั่ง หรือ ≥ 0.9 | ตัดทิ้ง |
| แม่แบบร่วม (Template sibling) | โครงสร้างประโยคเดียวกัน แต่คำตอบต่างกัน | **เก็บไว้** เพื่อเรียนรู้ และนับจำนวนไว้ เพื่อให้สามารถดูคะแนนทั้งแบบรวมและไม่รวมแถวทดสอบเหล่านั้นได้ |
| ตรงกันเฉพาะต้นทาง | ข้อความกระตุ้นเดียวกัน แต่คำตอบต่างกัน | เก็บไว้ และรายงานผล |

ประโยคสั้นจะเปรียบเทียบด้วยไตรแกรมของตัวอักษร (character trigrams) ส่วนประโยคที่สั้นมากจะเปรียบเทียบแบบตรงกันทุกประการเท่านั้น แถวทดสอบจะถือว่าเป็น **คู่แฝดใกล้เคียง (near-twin)** เมื่อแถวฝึกฝนเหมือนกันทุกประการหรือทับซ้อนกัน ≥ 0.6 ในด้านใดด้านหนึ่ง เมื่อแถวทดสอบตั้งแต่ครึ่งหนึ่งขึ้นไปมีคู่แฝด คะแนนที่ได้จะเกิดจากการจำได้เป็นหลัก ไม่ใช่การแปล และถือเป็นข้อควรระวังสำคัญ `--clean-to` จะเขียนไฟล์ที่ผ่านการคัดกรองแล้ว ส่วน `--drop-test-twins` จะตัดแถวฝึกฝนที่เป็นคู่แฝดกับแถวทดสอบออกด้วย เพื่อให้ได้คะแนนที่ปลอดคู่แฝด

การแบ่งชุด dev ครั้งแรกของแนวทางคุ้มครองใช้เกณฑ์เดียวกัน: `--near-dupe 0.6` บน `nmt-forge split` จะเก็บแถวที่คำทับซ้อนกัน ≥ 0.6 ไว้ในฝั่งใดฝั่งหนึ่งของเส้นแบ่ง dev/ฝึกฝน เพื่อไม่ให้คะแนน dev แรกมีความจำของข้อมูลเกือบซ้ำที่การคัดกรองในรอบถัดไปจะปฏิเสธ `--max-group` จะจำกัดขนาดกลุ่มข้อมูลเกือบซ้ำไว้ไม่เกินครึ่งหนึ่งของขนาด dev บวกหนึ่ง เพื่อให้ไฟล์ที่เขียนขึ้นจากแม่แบบยังคงสามารถแบ่งได้

**ข้อสังเกต** ให้พูดว่า "การตรวจสอบการรั่วไหลพบว่า…" เฉพาะเมื่ออ้างอิงจาก `true_now` หรือผลลัพธ์ของการตรวจสอบเท่านั้น อย่าสรุปเอาเองว่า "ชุดทดสอบสะอาดเรียบร้อย"

## เกณฑ์ขั้นต่ำของพจนานุกรม (The dictionary floor)

`nmt-forge floor <word lists>` จะแปลชุด dev แบบคำต่อคำด้วยพจนานุกรม (วลียาวที่สุดก่อน) และให้คะแนนด้วยโค้ดเดียวกันกับคะแนน dev ของการรัน: chrF++ พร้อมช่วงความเชื่อมั่น 95% กระบวนการนี้ทำงานบนคอมพิวเตอร์เครื่องนี้ ไม่เคยอ่านชุดทดสอบ และบันทึกเฉพาะชื่อ แฮช และจำนวนรายการของพจนานุกรม จำนวนคำต้นทางที่ครอบคลุม และคะแนนที่ได้ การรันจะ**ชนะเกณฑ์ขั้นต่ำ**ก็ต่อเมื่อขอบล่างของช่วงความเชื่อมั่น dev ของตนอยู่สูงกว่าขอบบนของช่วงความเชื่อมั่นของเกณฑ์ขั้นต่ำเท่านั้น โดย `nmt-forge status` จะแจ้งเตือนเกี่ยวกับการรันที่ไม่ผ่านเกณฑ์นี้

## การเปรียบเทียบสองโมเดล

**รอบการปรับปรุง** (`nmt-forge compare-runs <in-use> <new>`): คำแปลของทั้งสองโมเดลจาก**ประโยค dev เดียวกัน** โดยจับคู่แบบแถวต่อแถว มีการทดสอบ approximate-randomization แบบจับคู่ (1,000 ครั้ง) และช่วงความเชื่อมั่นแบบบูตสแตรป 95% ของผลต่าง

| คำตัดสิน | กฎ |
|---|---|
| **น้อยเกินไป** | ประโยค dev น้อยกว่า 50 ประโยค ไม่ว่าคะแนนจะเป็นอย่างไร — โมเดลที่ใช้งานอยู่จะคงเดิม และการตรวจให้คะแนนแบบไม่ทราบที่มาของผู้พูดจะเป็นผู้ตัดสิน (ด้านล่าง) |
| **ดีขึ้น** | 50 ประโยคขึ้นไป, p < 0.05 **และ**ปลายล่างของช่วงอยู่เหนือ 0 — โมเดลใหม่จะได้รับการเสนอให้ใช้งาน และจะนำมาใช้งานก็ต่อเมื่อคนในชุมชนตอบตกลงเท่านั้น |
| **แย่ลง** | 50 ประโยคขึ้นไป, p < 0.05 และปลายบนของช่วงอยู่ต่ำกว่า 0 |
| **ไม่เปลี่ยนแปลง** | กรณีอื่นทั้งหมด — โมเดลที่ใช้งานอยู่จะคงเดิม |

**เหตุผลที่ต้องเป็น 50** จากการวัดผลลัพธ์ของ ByT5-small บนภาษาทดสอบที่สร้างขึ้นมา ชุดฝึกซ้อมแบบสุ่มขนาดละ 100 ชุด โดยใช้กฎนี้: ที่ประโยค dev 23 ประโยค ระบบตัดสินว่าโมเดลสองตัวที่ใกล้เคียงกันมาก (ต่างกัน 0.7 chrF++ บน 500 ประโยค) มีความแตกต่างกัน 9 ครั้งจาก 100 ครั้ง และตัดสินว่าการเพิ่มขึ้นจริง +5.9 chrF++ นั้น **better** เพียง 21 ครั้งจาก 100 ครั้ง; ส่วนที่ 50 ประโยค ตัวเลขคือ 4 ครั้ง และ 96 ครั้งจาก 100 ครั้ง ความแตกต่างที่น้อยที่สุดที่พบได้ 8 ใน 10 ครั้งคือ 8.1 คะแนน chrF++ ที่ 23 ประโยค, 5.8 ที่ 50 ประโยค, 4.0 ที่ 100 ประโยค และ 2.8 ที่ 200 ประโยค ดังนั้น การแบ่งชุดข้อมูลครั้งแรกของ rails จึงกันประโยค dev ไว้อย่างน้อย 50 ประโยค เมื่อมีคู่ประโยค 200 คู่ขึ้นไป — คิดเป็นหนึ่งในสิบของคู่ที่ผ่านการคัดกรอง สูงสุดไม่เกิน 500 คู่; หากมีน้อยกว่า 200 คู่ จะกันไว้หนึ่งในสี่ ซึ่งน้อยกว่า 50 คู่ — และแผ่นงานตรวจทานจะเพิ่มขนาดของชุดข้อมูลด้วยแถวฝึกซ้อม: หนึ่งในสองแถวในขณะที่ยังน้อยกว่า 50 แถว และหนึ่งในสี่แถวจนกว่าจะถึง 200 แถว

แต่ละคำตัดสินยังระบุถึงผลต่างที่น้อยที่สุดที่ชุด dev สามารถแสดงได้อย่างน่าเชื่อถือ (8 ใน 10 ครั้ง): ความกว้างของช่วงความเชื่อมั่น × (1.96 + 0.84) ÷ (2 × 1.96) หากค่าดังกล่าวเกิน 3 คะแนน chrF++ คำตัดสิน "no-change" จะเป็นข้อจำกัดของชุด dev เอง ไม่ใช่ข้อพิสูจน์ว่ารอบนั้นไม่ได้ส่งผลอะไร นอกจากนี้ ชุด dev ยังถูกใช้เลือกเช็กพอยต์ของการรันใหม่ ซึ่งทำให้โมเดลใหม่ได้เปรียบเล็กน้อย — **โปรดแจ้งเรื่องนี้** เมื่อคุณส่งต่อคำตัดสิน

การที่ผู้พูดเลือกโมเดลที่ใหม่กว่าแบบบลายด์ (ดูด้านล่าง) ทำให้ forge เสนอโมเดลดังกล่าวเพื่อนำไปใช้งานเฉพาะหลังจากคำตัดสิน **too-few** หรือ **no-change** เท่านั้น — ไม่เคยเสนอหลังคำตัดสิน **worse** — และต้องให้ผู้คนเห็นชอบก่อนเสมอ (`improve-promote`, โหมด `confirm`) ส่วนการเลือกแบบบลายด์ที่เลือกโมเดลเดิมซึ่งการเลื่อนขั้นเคยแทนที่ไปแล้ว จะไม่นำโมเดลนั้นกลับมาใช้โดยอัตโนมัติ: การดำเนินการในรายงานประจำรอบจะถามความเห็นจากผู้คนก่อน

**การรันสองครั้งใดๆ** (`mt-eval compare <report> <report> --significance`): ใช้ approximate randomization เป็นค่าเริ่มต้น (`--method paired_bootstrap` สำหรับตัวอื่น), 1,000 ครั้ง (`--n-bootstrap`), α 0.05, seed 12345 บนรายการที่รายงานแชร์ร่วมกันตาม id (มีคำเตือนหากต่ำกว่า 10) โดยจะประเมิน chrF++ ก่อน แล้วตามด้วยเมตริกเสริม ทุกคู่ของการรันจะได้รับการทดสอบ จะไม่มีการปรับแก้สำหรับการทดสอบหลายสมมติฐาน (multiple-testing correction) และผลลัพธ์จะระบุไว้อย่างชัดเจน

## สิ่งที่รายการประสงค์ใช้เป็นแนวทางนำทาง

`nmt-forge analyze` จำแนก chrF++ ของชุด dev ในการรันตามประเภทของประโยค (โดยต้องมีประโยค dev ในประเภทนั้นอย่างน้อย 5 ประโยค) ประเภทหนึ่งๆ จะถือว่า**อ่อนแอที่สุด** — และเพิ่มน้ำหนักให้กับรายการประสงค์ — ก็ต่อเมื่อช่วงความเชื่อมั่น 95% ของระยะห่างที่คะแนนของประโยคประเภทนั้นต่ำกว่าส่วนที่เหลืออยู่เหนือศูนย์ทั้งหมด (ช่วงความเชื่อมั่นของ Welch บน chrF++ ระดับประโยค) คะแนนที่ต่ำกว่าซึ่งอาจเกิดจากความบังเอิญจะถูกรายงานตามนั้น (*"… could be chance — the wishlist does not steer by it"*) และจะไม่นำมาถ่วงน้ำหนักในตาราง

ส่วน "คำที่ไม่เคยพบมาก่อน" จะขอประโยคสองหรือสามประโยคสำหรับแต่ละคำ โดยแต่ละประโยคควรสื่อความหมายต่างกัน ไม่ใช่เพียงประโยคเดียว: ในภาษาทดสอบที่ประดิษฐ์ขึ้น คำที่พบเพียงครั้งเดียวในการฝึกฝนแปลถูกต้อง 27–29% ของเวลาทั้งหมด และคำที่พบ 2–4 ครั้งแปลถูกต้อง 63–95% และที่ประโยคฝึกฝน 3,200 ประโยค ByT5-small ที่ฝึกฝนด้วยประโยคที่คัดเลือกมาจากคำใหม่มากที่สุด แปลประโยคที่กันไว้ 500 ประโยคได้ความหมายถูกต้อง 39.4% เทียบกับ 53.4% สำหรับประโยคทั่วไปในชีวิตประจำวัน โดยใช้เวลาของผู้พูดมากกว่าเล็กน้อย (ประมาณ 57 ชั่วโมงเทียบกับ 54 ชั่วโมง)

## การให้คะแนนของผู้พูด

ในแต่ละรอบ improve ผู้พูดจะทำเครื่องหมายร่างคำแปลประโยคใหม่ของโมเดลว่า
`Y`, `N` หรือ `?` สัดส่วนที่ถูกต้องคือ `Y ÷ (Y + N)` (โดยไม่รวม `?`, แถวที่ไม่ได้ทำเครื่องหมาย, แถวฝึกซ้อม
และแถวที่นำมาแสดงซ้ำ) พร้อมช่วงความเชื่อมั่น Wilson 95% การเพิ่มขึ้นระหว่างรอบจะถือเป็น
**ความก้าวหน้า** ก็ต่อเมื่อช่วงความเชื่อมั่นของรอบล่าสุดอยู่เหนือรอบแรกทั้งหมด,
มีการนำโมเดลของรอบใดรอบหนึ่งมาใช้งานในระหว่างนั้น — ซึ่งผู้คนเป็นผู้เลือก
(บันทึก `export` และ `choose` ของ forge) ไม่ว่าจะเป็นหลังคำตัดสินว่า **better**,
ตามการทำเครื่องหมายแบบ blind ของผู้พูด หรือโดยการตัดสินใจของพวกเขาเอง โดยคำตัดสินว่า **better**
เพียงอย่างเดียวจะไม่นับ — **และ** การตรวจแบบ blind ของผู้พูดในการเลื่อนขั้นแต่ละครั้ง
(ด้านล่าง) เมื่อรวมผลข้ามรอบในระหว่างนั้นแล้ว ได้ทำเครื่องหมายว่าโมเดลใหม่ถูกต้อง
บ่อยกว่าโมเดลเดิมที่ถูกแทนที่อย่างชัดเจน (|z| > 1.96)
สิ่งเหล่านี้คือประโยคที่ไม่มีโมเดลใดเคยเห็นมาก่อน: ตัวชี้วัดที่สำคัญที่สุด และเป็นตัวชี้วัด
ที่ควรยึดเป็นหลัก ([coaching](/docs/agents/coaching))

**สองโมเดลแบบ blind** `champollion improve sheet` จะให้โมเดลที่สองร่างคำแปล
ครึ่งหนึ่งของแถวที่ร่างขึ้นโดยการสุ่มแบบกำหนด seed (`nmt-forge draft-newer`) โดยไม่ระบุเครื่องหมาย:
นั่นคือโมเดลที่ฝึกฝนล่าสุดเมื่อโมเดลนั้นไม่ใช่ตัวที่กำลังใช้งานอยู่ — เช่น หลังจากรอบ
ที่ผลคำตัดสินคือ too-few, no-change หรือ worse — หรือในการเข้าตรวจหลังจาก
การเลื่อนขั้น จะเป็นโมเดลที่โมเดลปัจจุบันเข้าไปแทนที่ ข้อมูลว่าแถวใดเป็นของโมเดลใดจะถูกเก็บไว้
ข้างชีตใน `improve/round-<k>/sheet-key.json` (`in_use`, `other`,
`relation` `newer` หรือ `replaced`, คู่ประโยคฝึกฝนของแต่ละโมเดล `in_use_pairs`
และ `other_pairs`, `other_rows`, และ `repeat_rows` ด้านล่าง)
จากนั้น `champollion improve marks` จะนับแยกผลของทั้งสองโมเดลออกจากกัน โดยไม่รวมแถวที่นำมา
แสดงซ้ำในกระบวนการทั้งหมด:

- สัดส่วนที่ถูกต้องข้างต้น — ซึ่งเป็นมาตรวัดความก้าวหน้า — จะนับเฉพาะแถวของโมเดลที่ใช้งานอยู่เท่านั้น;
- ทุกร่างที่ถูกทำเครื่องหมายว่าถูกต้อง และการแก้ไขทุกจุดจะกลายเป็นคู่ข้อมูลฝึกฝน ไม่ว่าโมเดลใดจะเป็นผู้ร่างก็ตาม;
- การทดสอบสัดส่วนสองกลุ่ม (แบบรวมกลุ่ม, ทดสอบสองด้านที่ระดับ 5%: |z| > 1.96) จะระบุว่าผู้พูดทำเครื่องหมายว่าโมเดลใดถูกต้องบ่อยกว่า หากมีข้อแตกต่าง: `clear` คือ `newer` หรือ `replaced` (โมเดลอีกตัวหนึ่ง), `in-use` หรือ `neither` ซึ่งบันทึกไว้ใน `marks.json` (`blind`) พร้อมจำนวนนับของทั้งสองโมเดล (`in_use_right`, `in_use_judged`, `other_right`, `other_judged`, `in_use_share`, `other_share`), `other`, `relation` และจำนวนคู่ประโยคสำหรับเทรนของทั้งสอง; การเปรียบเทียบกับโมเดลที่ใหม่กว่าจะเก็บค่า `newer`, `newer_right`, `newer_judged` และ `newer_share` ไว้ด้วย เมื่อโมเดลใดโมเดลหนึ่งไม่มีแถวที่ถูกทำเครื่องหมายเป็น `Y` หรือ `N` เลย ค่า `clear` จะเป็น `null` และข้อความจะระบุว่า *"มีแถวของโมเดลใดโมเดลหนึ่งได้รับการตัดสินน้อยเกินไปจนไม่สามารถเปรียบเทียบได้"*;\
- เมื่อเทียบกับโมเดลที่ใหม่กว่า โดยมีการตัดสินร่างประโยคของแต่ละโมเดลอย่างน้อยหนึ่งร่าง จำนวนนับจะถูกส่งไปยัง forge (`nmt-forge speaker-verdict`) ซึ่งจะทำการทดสอบเดียวกันและบันทึก `clear` (`newer`, `in-use` หรือ `neither`) ลงในสมุดบัญชี (`improve-speaker`) หลังคำตัดสิน **too-few** หรือ **no-change** ในรอบการทำงานนั้น `clear: newer` จะทำให้ forge เสนอโมเดลที่ใหม่กว่าเพื่อนำไปใช้งาน; จากนั้น `champollion improve marks` จะพิมพ์ว่า *"forge บันทึกไว้แล้ว: มีการเสนอให้นำโมเดลที่ใหม่กว่าไปใช้งาน (ผู้คนเห็นชอบก่อน)"* ([การเทรน](/docs/agents/training#the-improve-rounds))

แถวข้อความถูกจัดสรรแบบสุ่มในตารางเดียวกัน ตัดสินโดยผู้พูดคนเดียวกัน บนประโยคใหม่ของครอบครัวเอง — ดังนั้นความแตกต่างที่ชัดเจนจึงบ่งบอกสิ่งสำคัญที่ชุด dev อาจมีขนาดเล็กเกินกว่าจะแสดงได้ และการเปลี่ยนแปลงในระดับความผ่อนปรนในการให้คะแนนของผู้พูดย่อมส่งผลต่อทั้งสองโมเดลเท่าๆ กัน **ข้อสังเกต** ห้ามบอกผู้พูดเด็ดขาดว่าแถวใดมาจากโมเดลใดก่อนที่จะตรวจอ่านคะแนนเสร็จสิ้น

**แถวที่นำมาแสดงซ้ำ** ตั้งแต่รอบที่ 2 เป็นต้นไป `champollion improve sheet` จะใส่แถวกลับเข้ามาหนึ่งแถว
ต่อทุกๆ 10 ประโยคใหม่ในชีต (`REPEAT_EVERY` ปัดเศษลง
และน้อยกว่านั้นเมื่อมีแถวที่เข้าเกณฑ์น้อยกว่า): ร่างคำแปลที่ผู้พูดเคยทำเครื่องหมาย `Y` หรือ `N` ไว้ใน
ชีตก่อนหน้า พร้อมร่างคำแปลเดิมของประโยคนั้น โดยไม่ระบุเครื่องหมาย ในตำแหน่งสุ่มแบบกำหนด seed —
โดยต้องไม่ใช่แถวฝึกซ้อม ไม่ใช่แถวที่เป็นการแสดงซ้ำอยู่แล้ว ไม่ใช่แถวที่เคยนำมาแสดงซ้ำแล้ว
หรือไม่ใช่ประโยคที่มีอยู่แล้วในชีตนี้ บรรทัดแรกของชีตเหนือส่วนหัวระบุไว้ว่า:
*"มีบางแถวด้านล่างที่ตั้งใจนำกลับมาจากชีตก่อนหน้า
โปรดทำเครื่องหมายใหม่เสมือนว่าเป็นประโยคใหม่: ความถี่ที่เครื่องหมายตรงกันจะบอกว่าผลการประเมินน่าเชื่อถือเพียงใด"*
ชีตจะไม่บอกว่าคือแถวใด `sheet-key.json` จะเก็บแถวเหล่านั้นไว้เป็น
`repeat_rows` (`row`, `from_round`, `from_row` และ `mark` ซึ่งเป็นเครื่องหมาย
ที่ทำไว้ก่อนหน้า) แถวเหล่านี้ใช้เวลาของผู้พูดประมาณ 10 วินาทีต่อแถว

`improve marks` จะตัดสินแต่ละแถวเทียบกับเครื่องหมายเดิมของผู้พูดเองเท่านั้น: แถวที่แสดงซ้ำ
จะไม่ถูกนับรวมในสัดส่วนของรอบนั้น ไม่นำมาเป็นคู่ประโยคฝึกฝนอีก
และไม่อยู่ในการเปรียบเทียบแบบ blind `marks.json` จะเพิ่ม `repeats`: `shown`,
`judged` (ที่ทำเครื่องหมาย `Y` หรือ `N` ในครั้งนี้; `?` หรือที่เว้นว่างไว้จะแสดงขึ้นมาแต่ไม่นำมาตัดสิน),
`agreed`, `agreement` (ตรงกัน ÷ ตัดสินแล้ว), `wrong_to_right`,
`right_to_wrong`, `wrong_before` (แถวที่ตัดสินแล้วซึ่งเคยทำเครื่องหมาย `N`) และ
`rounds_apart_wrong_before` โดยจะพิมพ์ว่า *"Rows shown again: the speaker
marked A of J the way they did before (P%) — W once wrong now right, R once
right now wrong. Not counted in this round's share, and not trained on
again."*

เมื่อรวมผลข้ามรอบแล้ว ทันทีที่มีการตัดสินครบ 10 แถวขึ้นไป (`MIN_REPEATS`) รายงาน
ประจำรอบจะอ่านค่าสองสิ่งจากแถวเหล่านั้น:

- **ความคลาดเคลื่อนแบบสุ่ม** `e` จากการเปลี่ยนเครื่องหมายสลับไปมาทั้งสองทางเท่าๆ กัน เครื่องหมายสองครั้งของ
  ร่างหนึ่งร่างจะไม่ตรงกันโดยบังเอิญคิดเป็น 2e(1 − e) ของจำนวนครั้งทั้งหมด โดยแบ่งเป็นฝั่งละกึ่งหนึ่ง เมื่อ
  d = 2 × min(`wrong_to_right`, `right_to_wrong`) ÷ `judged`,
  e = (1 − √(1 − 2d)) ÷ 2 ความคลาดเคลื่อนจะดึงทุกสัดส่วนเข้าหา 50%: ร่างคำแปลที่ถูกต้อง
  อย่างแท้จริงเป็นสัดส่วน p จะถูกทำเครื่องหมายว่าถูกต้องเป็น e + p(1 − 2e) ของจำนวนครั้งทั้งหมด ดังนั้น
  ที่ e = 10% "ถูกต้องอย่างแท้จริง 80%" จะอ่านค่าได้ประมาณ 74%
- **การเลื่อนไหล**: การเปลี่ยนเครื่องหมายไปในทิศทางหนึ่งมากกว่าการเปลี่ยนแบบสมดุล รายงานจะเตือนว่า
  การทำเครื่องหมายอาจใจดีขึ้นเมื่อการเปลี่ยนจากเคยผิดกลายเป็นถูกมีจำนวนมากกว่า
  ทิศทางตรงกันข้ามอย่างชัดเจน: เมื่อมีการเปลี่ยนเครื่องหมายตั้งแต่ 6 ครั้งขึ้นไป และการทดสอบเครื่องหมาย
  (`wrong_to_right` − flips ÷ 2) ÷ √(flips ÷ 4) > 1.96

บรรทัดตรวจสอบระบุว่า: *"The speaker marked A of J rows shown again the way they did
before (P%): about E% of marks go the other way at random, which pulls every
share marked right toward 50% — the projection allows for it."* — และในส่วนของการเลื่อนไหล ระบุว่า *"And W drafts once marked wrong are now marked right, against R the
other way: the marking may be growing kinder, which a rise in the share would
not show."* หากตัดสินไม่ถึง 10 แถว จะระบุว่า: *"N rows shown again judged so far — the
speaker's own marking error is estimated from 10."*

**ทิศทางที่รอบต่างๆ ชี้ไป** การคาดการณ์ของรายงานประจำรอบจะคำนวณจาก
ความก้าวหน้าที่แท้จริง (ข้างต้น) เท่านั้น ในขณะที่สัดส่วนที่ถูกต้องยังต่ำกว่า 80% เส้นทางการเรียนรู้
จะเพิ่มขึ้นเป็นขั้นที่ค่อนข้างสม่ำเสมอในรูป log-odds ต่อการเพิ่มข้อมูลฝึกฝนขึ้นเป็นเท่าตัว ดังนั้น
รายงานจึงอ่านค่าขั้นดังกล่าวจากการตรวจแบบ blind เดียวกันนี้หลังจากการเลื่อนขั้น: ผลรวมของ
`logit(in_use_share) − logit(other_share)` หารด้วยผลรวมของ
`log2(in_use_pairs ÷ other_pairs)` (จำกัดสัดส่วนไว้ที่ 1–99%) พร้อมช่วงค่า 95%
จากความแปรปรวนของแต่ละสัดส่วน ประมาณ 1 ÷ (n·p·(1 − p)) สำหรับร่างคำแปล n รายการ
ที่ได้รับการตัดสิน จากคู่ประโยคฝึกฝนของโมเดลที่กำลังใช้งาน รายงานจะบอกว่าต้องใช้อีกกี่คู่ประโยคจึงจะถึง
80% ที่ทำเครื่องหมายว่าถูกต้อง — ซึ่งก็คือค่าประมาณการ — และชั่วโมงทำงานของผู้พูดที่อัตรา 70 วินาทีต่อ
ประโยค ช่วงค่าดังกล่าวครอบคลุมช่วงของขั้นการเรียนรู้ (ไม่มีขอบเขตบนเกินกว่าการเพิ่มขึ้นเป็นสองเท่าอีกหกครั้ง)
และเมื่อตัดสินแถวที่นำมาแสดงซ้ำครบ 10 แถวแล้ว จะบอกว่าจุดที่ "ถูกต้องอย่างแท้จริง 80%" อาจอยู่ตรงไหน
ในผลการทำเครื่องหมายของผู้พูดคนนี้: e + 0.8(1 − 2e) + 0.2 × K สูงสุดไม่เกิน 97%
โดย K คือการเลื่อนไหลต่อรอบ (การเปลี่ยนเครื่องหมายที่เกินกว่าส่วนที่สมดุล หารด้วยจำนวนรอบที่ห่างกัน
ระหว่างการทำเครื่องหมายสองครั้งของแถวที่เคยผิด) คูณด้วยจำนวนรอบระหว่างเครื่องหมายแรกกับเครื่องหมายสุดท้าย
โดยจำกัดค่าไว้ไม่เกิน ±30% ค่าต่ำสุดคือค่าที่น้อยกว่าของทั้งสองเป้าหมาย ณ ขอบเขตบนของขั้นการเรียนรู้
ค่าสูงสุดคือค่าที่มากกว่า ณ ขอบเขตล่างของขั้นการเรียนรู้ หากค่าต่ำสุดเป็น 0 จะแสดงเป็น
"none" จากนั้นข้อความจะระบุเพิ่มเติมว่า *"The speaker's own marking: they marked A of J
rows shown again the way they did before (P%), so about E% of marks go the
other way at random … drafts truly right on 80% may be marked right about T%
of the time on their marks — the range takes that in."* (พร้อมทั้งระบุว่า เมื่อ K มีค่าตั้งแต่
1% ขึ้นไปไม่ว่าในทิศทางใด ร่างคำแปลที่เคยทำเครื่องหมายว่าผิดถูกเปลี่ยนเป็นถูกบ่อยขึ้นหรือน้อยลงเพียงใด); ก่อนหน้านั้น จะระบุว่า *"(The speaker's own marking error is not yet
allowed for: too few rows shown again have been judged.)"* `report.json`
จะส่งต่อตัวเลขเป็น `projection_numbers` (`more_sentences`, `range`,
`speaker_hours`)

ในการจำลอง — โดยจำลองผู้พูดที่ไม่สม่ำเสมอ, ชุดข้อมูล dev split ของ rails เอง และกฎการตัดสินเหล่านี้ โดยทำการทดลอง 200 ครั้งต่อสถานการณ์จำลองบน seed สองชุด — ค่าประมาณการอยู่ในช่วงไม่เกิน 2 เท่าของจำนวนที่แท้จริง 69–78% ของการทดลองเมื่อใช้ประโยคใหม่ 400 ประโยคต่อรอบ และ 53–56% เมื่อใช้ 800 ประโยค และจำนวนที่แท้จริงตกอยู่ภายในช่วงค่าดังกล่าว 89–94% และ 76–80% ของการทดลอง (หากไม่มีการแสดงซ้ำ จะอยู่ที่ 91–93% และ 51–54%)
การปรับค่าประมาณการให้เข้ากับผลการทำเครื่องหมายของผู้พูดช่วยให้ผลดีขึ้นที่ 800 ประโยคต่อรอบ แต่กลับแย่ลงที่ 400 ประโยค (อยู่ในช่วงไม่เกิน 2 เท่า: 64% และ 19%) ค่าประมาณการจึงยังคงไว้ที่ 80% ตามเดิม เคยมีการทดลองใส่หมายเหตุว่าโมเดล "may already be working" แต่ถูกยกเลิกไป: เนื่องจากให้ผลผิด 2–3 ครั้งต่อทุกๆ ครั้งที่ถูก เป็นเพียงการคาดเดาคร่าวๆ และระบุไว้อย่างตรงไปตรงมาเช่นนั้น

## สิ่งที่ตัวเลขไม่ได้บ่งบอก

- คะแนนเป็นของระบบบนชุดข้อมูลนั้น ไม่ใช่ของประโยคใดประโยคหนึ่ง: ไม่มีความเชื่อมั่นระดับประโยค
- chrF++ วัดการทับซ้อนกับคำแปลอ้างอิง คำแปลที่ดีที่ใช้ถ้อยคำต่างออกไปอาจได้คะแนนต่ำ ส่วนคำแปลที่สละสลวยแต่ผิดความหมายอาจได้คะแนนค่อนข้างสูง
- การยอมรับของ FST (FST acceptance) บอกเพียงว่ามีคำเหล่านั้นอยู่จริง ไม่ได้บอกว่าประโยคนั้นสื่อความหมายถูกต้อง
- แถวบนตารางผู้นำ (leaderboard) ที่เผยแพร่จะเป็นการรายงานตนเองเป็นค่าเริ่มต้น ตัวตรวจสอบจะคิดคะแนนผลลัพธ์ที่ส่งมาใหม่อีกครั้งเทียบกับคลังข้อมูลที่ตรึงด้วยแฮช (hash-pinned corpus) (ภายใน 1.0 chrF++) และไม่ได้รันวิธีการซ้ำใหม่
