# วิธีการและเกต

**วิธีการ (method)** คือสิ่งใดก็ตามที่ทำหน้าที่แปล: โมเดลที่ผ่านการฝึกฝน, LLM ที่ใช้พรอมต์, การค้นหาจากพจนานุกรม, เอนจินแบบอิงกฎ, บริการภายนอก, หรือมนุษย์ ส่วน **เกต (gate)** คือการตรวจสอบระหว่างผลลัพธ์ของวิธีการกับสิ่งที่จะถูกส่งมอบจริง วิธีการเริ่มต้นของ rails คือโมเดลที่ฝึกฝนด้วย nmt-forge ([การฝึกฝน](/docs/agents/training)); หน้านี้จะอธิบายถึงรูปแบบที่ทั้งสองส่วนถูกเขียนขึ้น รวมถึงสูตรการทำงานอื่นๆ

สูตรการทำงานทั้งหมดด้านล่างนี้เป็นไปตาม [กฎการส่งผ่านข้อมูล](/docs/agents/data-rules):
**วิธีการที่เรียกใช้ผู้ให้บริการโมเดลจะส่งข้อความไปยังผู้ให้บริการนั้น** และไฟล์ที่ระบุว่าใช้ได้เฉพาะในเครื่อง (local-only), ปิดผนึก (sealed) หรือต้องได้รับความยินยอม (consent-required) จะปฏิเสธการส่งข้อความดังกล่าว

## method/1

`$schema` `https://champollion.dev/schemas/method/1.json` จำเป็นต้องมี: `id`
(คำตัวพิมพ์เล็กคั่นด้วยยัติภังค์), `name`, `kind` — พร้อมด้วยการตั้งค่าหนึ่งค่าที่ประเภทนั้นต้องการ ซึ่งได้รับการตรวจสอบโดยตัวอ่านด้วยข้อความเดียวกันในรันไทม์ทั้งสอง

| `kind` | การตั้งค่าที่จำเป็น | ทำงานใน | ส่งข้อความไปยัง |
|---|---|---|---|
| `llm` | `model` (id ที่ตรงกันทุกประการ ห้ามใช้นามแฝง); ตัวเลือกเพิ่มเติม `provider` | CLI; harness ผ่านทาง `-m` และ `--provider` | ผู้ให้บริการ |
| `llm-coached` | `model`; ข้อมูลการโค้ชจะอยู่ใน `coaching` (`file`, `prompt` หรือ `dir`) | CLI; harness ผ่านทาง `-m` และ `--coaching-file` | ผู้ให้บริการ: ทั้งประโยคและข้อมูลการโค้ช |
| `mt-api` | `engine` (จาก `shared/method-registry.json`) | CLI; harness | บริการของเอนจิน |
| `local-model` | `model` (id ของ Hugging Face หรือโฟลเดอร์ในเครื่อง) | Harness, ภายในโพรเซส | ไม่ส่งไปที่ใดเลย |
| `nmt-checkpoint` | `model_dir` | ผ่านบริการของตัวมันเอง (`nmt-forge serve`) | เซิร์ฟเวอร์ของคอมพิวเตอร์เครื่องนี้ |
| `lexicon` | `dictionary` | Harness, ภายในโพรเซส | ไม่ส่งไปที่ใดเลย |
| `python` | `entry_point` (`module:Class`) | Harness (`mt-eval run --method <folder>`) | ปลายทางใดก็ตามที่ปลั๊กอินส่งไป (`dependency_class`) |
| `service` | `service.endpoint` | CLI (วิธีการ `api`) | เอนด์พอยต์นั้น |
| `human` | — | มนุษย์; ให้คะแนนผลลัพธ์ด้วย `mt-eval test` | — |

ตัวเลือกเพิ่มเติม: `version`, `description`, `author`, `pairs` (`{source?, target}`),
`decode` (`temperature` 0–2, `batch_size`, `max_tokens`), `card` (สิ่งที่ลีดเดอร์บอร์ดแสดง), `dependency_class` (`S` เบ็ดเสร็จในตัวเอง, `O` ภายนอกแบบเปิด,
`A1`/`A2` ขึ้นอยู่กับ API, `X` แบบปิด), `evidence` (การรันที่วัดผลแล้ว: `dataset`,
`metric`, `score`, `ci`, `n` — ตัวเลขเท่านั้น), `runtimes` (`cli`, `engine`)

**ที่มาของ method.json:** `methods/<id>/method.json` ในโปรเจกต์;
`nmt-forge export` (ประเภท `nmt-checkpoint`); `mt-eval export --report <report>
--name <name> --type <type> --locales <code>`; `champollion serve
--emit-manifest` (kind `service` รูปแบบโครงสร้างเดิม (แมนิเฟสต์ปลั๊กอินของ CLI ที่มี `type`, แมนิเฟสต์ปลั๊กอินของ harness ที่มี `entry_point`) ยังคงอ่านได้ โดยถือเป็น method/0 พร้อมคำเตือน เอกสารที่มี `$schema` จะถูกอ่านเป็น method/1 และต้องผ่านการตรวจสอบความถูกต้อง

**รันไทม์ใดรับประเภทใด** CLI จะปฏิเสธ `python`, `lexicon`,
`local-model` และ `human` (*"ทำงานในเอนจินประเมินผล (mt-eval run --method)
ไม่ใช่ใน champollion CLI — หรือให้บริการผ่านเซิร์ฟเวอร์แล้วใช้งานผ่านเอนด์พอยต์"*)
ส่วน `--method <folder>` ของ harness จะโหลดเฉพาะ `python` เท่านั้น สำหรับประเภทอื่นๆ จะระบุแฟล็กที่ใช้รันแทน

**การถอดรหัส (Decoding)** ค่า temperature เริ่มต้นคือ **0** (`shared/model-defaults.json`):
ค่าเดียวสำหรับทั้งการแปลของแอปและการประเมินผลของ harness เพื่อให้สิ่งที่วัดผลตรงกับสิ่งที่จะส่งมอบจริง — `mt-eval run --temperature` มีค่าเริ่มต้นเป็นค่านี้
คู่ภาษา การกำหนดค่า หรือการรันแต่ละครั้งสามารถกำหนดค่าของตนเองได้
Model id จะต้องเป็น slug ที่ตรงกันทุกประการ ห้ามใช้นามแฝง

## ห่วงโซ่เกต (Gate chains)

`$schema` `https://champollion.dev/schemas/gate-chain/1.json` ไฟล์เดี่ยวใน
`gates/` จำเป็นต้องมี: `id`, `gates` (หนึ่งรายการขึ้นไป) ตัวเลือกเพิ่มเติม: `description`,
`fallback`

เกตแต่ละตัว: `id`, `kind` (`metric-threshold` ซึ่งเป็นประเภทเดียวที่มี), `metric` (ชื่อของปลั๊กอินเมตริก), `field` (คีย์ในผลลัพธ์รายเซกเมนต์ของปลั๊กอินนั้น — ตัวเลข หรือ true/false ที่อ่านเป็น 1/0), `min` และ/หรือ `max`, `on_refuse`

**กฎเกณฑ์** (`arena/mt_eval_harness/gates.py`):

- เกตจะทำงานตามลำดับ; เกตตัว**แรก**ที่ปฏิเสธเซกเมนต์จะเป็นตัวกำหนดสิ่งที่จะถูกส่งมอบ:

  | `on_refuse` | สิ่งที่ส่งมอบ | นับเป็น |
  |---|---|---|
  | `drop` | ไม่มีอะไรเลย | ถูกปฏิเสธ (refused) |
  | `keep-source` | ข้อความต้นฉบับ | ถูกปฏิเสธ (refused) |
  | `flag` | ผลลัพธ์ พร้อมทำเครื่องหมาย | ถูกตั้งค่าสถานะ (flagged) ไม่ได้ถูกปฏิเสธ |
  | `fallback` | คำแปลจากตัวสำรอง (fallback) หากเกตชุดเดิมยอมรับ; หากถูกปฏิเสธซ้ำ จะไม่ส่งมอบอะไรเลย | ถูกปฏิเสธ (refused) |

- **ข้อกำหนดตายตัว (Lock)** เซกเมนต์ที่ปลั๊กอินไม่สามารถให้คะแนนได้จะถูกปฏิเสธ (`no_value` หรือ `plugin_error:<type>`) — จะไม่มีการส่งมอบเสมือนว่าผ่านเกณฑ์อย่างเด็ดขาด
- **ข้อกำหนดตายตัว (Lock)** เกตที่ไม่ได้โหลดปลั๊กอิน หรือไม่สามารถให้คะแนนที่นี่ได้ จะหยุดการรันก่อนที่จะมีการแปลใดๆ: *"เกตที่ไม่สามารถตัดสินได้จะไม่ถือว่าผ่านเกณฑ์เด็ดขาด"*
- **ข้อกำหนดตายตัว (Lock)** ตัวสำรอง (fallback) ต้องทำงานภายในโพรเซสนี้ (`lexicon`, `local-model` หรือปลั๊กอินที่ประกาศ `dependency_class` `S` หรือ `O`) เพื่อไม่ให้เซกเมนต์ที่ถูกปฏิเสธหลุดออกไปที่อื่น
- **ข้อกำหนดตายตัว (Lock)** `mt-eval run` และ `mt-eval test` จะปฏิเสธห่วงโซ่ที่มีเกต `fallback`: *"ตัวสำรองมีไว้สำหรับการให้บริการและการแปล ไม่ใช่สำหรับการวัดผล เพราะคะแนนจะกลายเป็นของวิธีการนี้ส่วนหนึ่งและของตัวสำรองส่วนหนึ่งภายใต้ชื่อเดียวกัน"* ให้วัดผลตัวสำรองในฐานะวิธีการแยกต่างหาก
- **จุดที่เกตมีผลใช้งาน:** `mt-eval run --gates`, `mt-eval test <run log>
  --gates` (re-scored without translating again), `mt-eval translate --gates`,
  `mt-eval serve --gates` และ `gates` ของการปรับใช้ (deployment)
- ในการวัดผล คะแนนหลักจะวัดสิ่งที่ถูกส่งมอบจริง ส่วนคะแนน chrF++ ที่ไม่ผ่านเกตและอัตราการปฏิเสธจะแสดงควบคู่กันไป และลายนิ้วมือของห่วงโซ่ (sha256 ของ JSON แบบบัญญัติ) จะแนบไปกับรายงาน ([การวัดผล](/docs/agents/measurement#gated-measurement)) ในกรณี `keep-source` คะแนนหลักจะคิดจากข้อความต้นฉบับในจุดที่ถูกส่งมอบ
- **ข้อกำหนดตายตัว (Lock)** ทุกเกตต้องมี `min` และ/หรือ `max` รหัสเกตต้องไม่ซ้ำกัน และเกต `fallback` ต้องมี `fallback` ของห่วงโซ่ — `champollion validate` และ harness จะให้ผลการตัดสินเดียวกัน ทั้งนี้ระบบยังไม่ได้สร้างกลไกการลองแปลเซกเมนต์ที่ถูกปฏิเสธซ้ำโดยใช้เหตุผลของเกต

## ตัวอย่างการใช้งาน: เกตตรวจสอบความถูกต้องด้วย FST

ตัววิเคราะห์สถานะจำกัด (finite-state analyzer หรือ FST) จะระบุว่าคำนั้นสร้างขึ้นมาถูกต้องตามหลักภาษาหรือไม่ ปลั๊กอินเมตริก `giellalt_fst_validity` ของ harness จะรายงาน `fst_total_words`, `fst_valid_words`, `fst_invalid_words` และ `fst_validity_rate` (0–1) ในแต่ละเซกเมนต์ โดยคำจะถูกตัดด้วยช่องว่างและตัดเครื่องหมายวรรคตอนที่ขอบออก สำหรับคำที่ขึ้นต้นด้วยตัวพิมพ์ใหญ่จะลองใหม่อีกครั้งในรูปตัวพิมพ์เล็ก

```json
{
  "$schema": "https://champollion.dev/schemas/gate-chain/1.json",
  "id": "fst-every-word",
  "description": "Ship a sentence only when the analyzer accepts every word.",
  "gates": [
    { "id": "fst-all-words", "kind": "metric-threshold",
      "metric": "giellalt_fst_validity", "field": "fst_validity_rate",
      "min": 1.0, "on_refuse": "flag" }
  ]
}
```

```bash
mt-eval setup --status               # the languages with a pinned analyzer
mt-eval setup --fst                  # the analyzer runtime
mt-eval setup --lang <code>          # the language's analyzer, once per machine
mt-eval run --corpus <dev file> --target-lang-code <code> --method local-model -m <model folder> \
  --gates gates/fst-every-word.json
```

- ตัววิเคราะห์นี้**ไม่ได้รวมมาในชุด**: harness ส่งมอบเฉพาะการตรึงค่า (pins: ชื่อไฟล์และ sha256 ต่อภาษา) และ `setup --lang` จะดึงตัววิเคราะห์จากต้นน้ำมายัง `~/.mt-eval/fsts/<code>/` ภายใต้ข้อกำหนดของต้นน้ำ โดยรันเป็นเครื่องมือแยกต่างหากและไม่เชื่อมโยงเข้าไปใน CLI `champollion`
- ตัววิเคราะห์ที่สูญหายจะไม่ถูกนับเป็นศูนย์เด็ดขาด: หากเป็นเมตริกจะถูกทำเครื่องหมายว่าไม่ได้คำนวณ; หากเป็นเกตจะหยุดการรันทันที
- ผลลัพธ์ที่ว่างเปล่าจะได้คะแนน 0 และถูกปฏิเสธหากต่ำกว่า `min`
- หากต้องการให้บริการร่วมด้วย ให้ใช้ `on_refuse: "fallback"` และ `fallback` เช่น `{"method": "lexicon", "model": "data/lexicon/words.tsv"}` — สำหรับ `translate` และ `serve` เท่านั้น
- **หมายเหตุ** การยอมรับของ FST บอกเพียงว่าคำนั้นมีอยู่จริง ไม่ได้บอกว่าประโยคนั้นมีความหมายถูกต้อง นี่คือเครื่องมือวินิจฉัย จึงไม่ถูกนำไปคิดในคะแนนหลัก chrF++ เด็ดขาด

## สูตรการทำงาน (The recipes)

### Coached LLM (`llm-coached`)

โมเดลทั่วไปที่ได้รับพรอมต์ด้วยคำแนะนำจากชุมชนเจ้าของภาษา: บันทึกไวยากรณ์ รูปแบบการเขียน คำศัพท์

```bash
mt-eval run --corpus <dev file> -m <exact model id> --coaching-file coaching.md --glossary terms.json
champollion sync --method llm-coached --coaching-file coaching.md
```

- **ใน harness** ข้อความในไฟล์การโค้ช*คือ* system prompt ทั้งหมด ดังนั้นจึงต้องระบุสิ่งที่จะแปลและสั่งให้ส่งออกเฉพาะคำแปลเท่านั้น `--glossary` เป็นอินพุตสำหรับการให้คะแนน (ความสอดคล้องกับคำศัพท์) ซึ่งจะไม่ถูกส่งออกไปเด็ดขาด
- **ข้อกำหนดตายตัว (Lock)** การรัน harness มีการโค้ชได้เพียงแบบเดียว: `--coaching-file`, `--coaching` (ข้อความแบบอินไลน์) หรือ `--custom-prompt` แบบเดิม — ให้ระบุเพียงอย่างใดอย่างหนึ่ง หากระบุมาสองอย่างจะถูกปฏิเสธ: *"--coaching-file and --coaching each give the run its coaching — give one (put inline text in the file, or drop the file)"*
- **ใน CLI** `llm-coached` จะส่งพรอมต์ของตัวเองโดยมีข้อมูลการโค้ชเป็นบล็อก "Coaching guidance" พร้อมด้วย `.champollion/coaching/<locale>.json` (`grammar_rules`, `style_notes`, `dictionary`)
- **หมายเหตุ** ทั้งสองนี้เป็นพรอมต์คนละตัวกัน: คะแนน coached ที่วัดได้ใน harness ไม่ได้มาจากพรอมต์เดียวกับที่ CLI ส่งมอบจริง โปรดระบุให้ชัดเจนเมื่อคุณนำคะแนนหนึ่งไปอ้างอิงเป็นหลักฐานของอีกอันหนึ่ง
- **สิ่งที่ส่งออกไป:** ทุกประโยคต้นฉบับและข้อมูลการโค้ชแบบเต็มไปยังผู้ให้บริการ ไฟล์การโค้ชที่มี sidecar แบบ local-only จะทำงานบนเอนด์พอยต์แบบ loopback เท่านั้น (`champollion data mark coaching.md --local-only` ใช้ทำเครื่องหมายกรณีนี้)

### Few-shot

ตัวอย่างคำแปลที่ดีภายในข้อมูลการโค้ช นี่คือ coached LLM: ใช้คำสั่งเดียวกัน การส่งข้อมูลแบบเดียวกัน — ตัวอย่างจะเดินทางใน system prompt ไปยังผู้ให้บริการ

- **หมายเหตุ** อย่าดึงตัวอย่างจากชุดทดสอบ (test set) เด็ดขาด และอย่าใช้ไฟล์ local-only กับผู้ให้บริการระยะไกลเด็ดขาด ระบบไม่มีการตรวจสอบตัวอย่าง few-shot เทียบกับข้อมูลอ้างอิงการทดสอบโดยอัตโนมัติ

### LLM เสริมด้วยพจนานุกรม (Dictionary-augmented LLM)

- **CLI:** `dictionary` ใน `.champollion/coaching/<locale>.json` จะถูกส่งไปยังทุกวิธีการ LLM ในรูปแบบ "REQUIRED TERMINOLOGY" สำหรับคำศัพท์ที่พบในแต่ละชุดข้อมูล (จับคู่อนุสตริงแบบไม่คำนึงถึงตัวพิมพ์เล็ก-ใหญ่) DeepL จะได้รับในฐานะประมวลอภิธานศัพท์ (glossary) ข้อผิดพลาดจะมีการเตือนหลังการแปล แต่จะไม่มีการลองใหม่
- **Harness:** พจนานุกรมจะส่งไปถึงโมเดลในรูปของข้อความในไฟล์การโค้ชเท่านั้น
- **พจนานุกรมเพียงอย่างเดียว:** `mt-eval run --method lexicon -m data/lexicon/words.tsv
  --corpus <dev file>` — แปลวลีที่ยาวที่สุดก่อน คำที่ไม่รู้จักจะคงไว้ ทำงานภายในโพรเซส `nmt-forge floor` คือรูปแบบนี้บนชุด dev
  ([การวัดผล](/docs/agents/measurement#the-dictionary-floor))
- **สิ่งที่ส่งออกไป:** รายการพจนานุกรมที่ตรงกัน พร้อมกับประโยค ไปยังผู้ให้บริการ พจนานุกรมแบบ local-only จะต้องไม่ถูกส่งไปยังผู้ให้บริการระยะไกลเด็ดขาด

### ระบบไฮบริดแบบอิงกฎ (Rule-based hybrid)

ไม่มีเอนจินแบบอิงกฎติดตั้งมาในตัว สิ่งที่มีอยู่คือ: `lexicon` (ดีเทอร์มินิสติก ภายในโพรเซส); `mt-eval run --method apertium` (เอนจินแบบอิงกฎ — จะส่งข้อความไปยัง `apertium.org` เว้นแต่ว่า `APERTIUM_API_URL` จะชี้ไปยังเซิร์ฟเวอร์ของคุณเอง); และปลั๊กอิน `python` สำหรับกฎของคุณเอง ซึ่งอาจใช้ร่วมกับ LLM ได้ คลาสปลั๊กอินจำเป็นต้องมี `async def translate(self, entries, config)`; รันด้วย `mt-eval run
--method <folder>` ตรวจสอบความถูกต้องของผลลัพธ์ด้วยห่วงโซ่เกต

- **สิ่งที่ส่งออกไป:** อะไรก็ตามที่ปลั๊กอินเรียกใช้ ปลั๊กอินคือวิธีการภายนอก: บนคลังข้อมูลที่ต้องได้รับความยินยอมหรือถูกปิดผนึก (รวมถึง local-only) harness จะปฏิเสธ เว้นแต่ว่ามีการระบุ `--attest-local-transport` — ซึ่งคุณควรส่งพารามิเตอร์นี้หลังจากตรวจสอบยืนยันแล้วว่าทุกสิ่งที่ปลั๊กอินเรียกใช้อยู่บนเครื่องนี้จริง

### วิธีการแบบลูกโซ่ (Chained methods)

มีห่วงโซ่ที่ติดตั้งมาในตัวสองรูปแบบ:

1. **ตัวสำรองของห่วงโซ่เกต:** วิธีการ → เกต → ตัวสำรองภายในโพรเซส → เกตชุดเดิม สำหรับ `translate` และ `serve` เท่านั้น
2. **ตัวสำรองของคู่ภาษาใน CLI** (`"fallback": {"method": …}` บนคู่ภาษาของแอป):
   วิธีการหลัก → เกตคุณภาพของ CLI → การลองใหม่พร้อมข้อคิดเห็นจากเกต (วิธีการ LLM หรือเอนด์พอยต์ `api` ที่ประกาศ `acceptsInstructions`) → ตัวสำรองหนึ่งครั้ง ผ่านเกตชุดเดิม

กระบวนการใดๆ ที่ยาวกว่านี้ (สร้าง, แก้ไข, ตรวจสอบความถูกต้องข้ามโมเดล) จะถือเป็นปลั๊กอิน `python` หรือ `service`

- **สิ่งที่ส่งออกไป:** แต่ละข้อต่อในห่วงโซ่จะส่งข้อมูลตามประเภทของมัน ความเป็นส่วนตัวของทั้งห่วงโซ่จะเท่ากับข้อต่อที่มีความเป็นส่วนตัวน้อยที่สุด

### การแปลบางส่วน (มนุษย์และเครื่องจักร)

โมเดลเป็นผู้ร่าง; ผู้พูดภาษานั้นจะเป็นผู้ตรวจสอบและแก้ไข ใน rails ขั้นตอนนี้คือรอบการปรับปรุง: `champollion improve sheet` ทำหน้าที่ร่าง, ผู้พูดภาษาจะทำเครื่องหมาย `Y`/`N`/`?`, `champollion improve marks` จะเปลี่ยนข้อความที่แก้ไขและร่างที่ยืนยันแล้วให้เป็นคู่ฝึกฝน และเปลี่ยนแถวฝึกหัดเป็นประโยค dev ([การโค้ช](/docs/agents/coaching))
หากต้องการให้คะแนนคำแปลของมนุษย์ในฐานะวิธีการหนึ่ง (`kind` `human`) ให้รัน `mt-eval test` บนผลลัพธ์ของพวกเขา เกตที่มี `on_refuse: "flag"` จะทำเครื่องหมายผลลัพธ์เพื่อส่งให้ตรวจทาน

- **หมายเหตุ** ประโยคที่ใช้ในการโค้ชหรือฝึกฝนวิธีการใดๆ จะต้องไม่ใช่ประโยคที่ใช้วัดผลวิธีการนั้นโดยเด็ดขาด
- **สิ่งที่ส่งออกไป:** ไม่มีสิ่งอื่นใดนอกเหนือกฎของโมเดลที่ใช้ร่าง แผ่นงานจะยังคงอยู่ในโฟลเดอร์โปรเจกต์

### โมเดลไฟน์จูน (Fine-tuned model)

- **บน rails:** `nmt-forge` (`nmt-checkpoint`; ค่าที่ตั้งไว้ล่วงหน้า `cpu-tiny`,
  `byt5-small`, `byt5-small-lowmem`, `cpu-finetune`, `nllb-600m`) ที่ส่งออกแล้ว
  ให้บริการและเชื่อมต่อแล้ว —
  [การฝึกฝน](/docs/agents/training), [การให้บริการ](/docs/agents/serving)
- **โมเดลแบบเปิดที่คุณมีอยู่แล้ว:** `mt-eval run --method local-model -m
  <Hugging Face id or folder>` — ภายในโพรเซส ไม่มีสิ่งใดหลุดออกนอกเครื่อง
- **LLM ที่คุณเปิดให้บริการเอง** (Ollama, vLLM หรือสิ่งใดก็ตามที่เข้ากันได้กับ OpenAI):
  `mt-eval run --provider local --base-url http://127.0.0.1:11434/v1 -m
  <model name>` จะถือว่าเป็น local ก็ต่อเมื่อเอนด์พอยต์เป็นที่อยู่แบบ loopback เท่านั้น
- **สิ่งที่ส่งออกไป:** ไม่มีสิ่งใดส่งออกนอกเครื่อง หากเอนด์พอยต์เป็น local อย่างแท้จริง
