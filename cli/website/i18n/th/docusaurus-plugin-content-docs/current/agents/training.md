# การฝึกโมเดลด้วย nmt-forge

`nmt-forge` ฝึกโมเดลจากคู่ประโยคของชุมชนภายใต้แนวป้องกัน: ระบบจะ
ปฏิเสธสิ่งที่จะทำให้ผลลัพธ์เสียหาย และการปฏิเสธทุกครั้งจะระบุว่าเกิดอะไรขึ้น เพราะเหตุใด และวิธีแก้ไข
ระบบไม่ได้คำนวณมาตรวัดของตนเองขึ้นมาใหม่ — ทุกคะแนนมาจาก
เครื่องมือประเมินผล (`mt-eval`) ซึ่งเป็นโค้ดชุดเดียวกับที่ให้คะแนนสิ่งอื่นทั้งหมด

เมื่ออยู่บน rails คุณแทบไม่ต้องพิมพ์คำสั่งเหล่านี้ด้วยตนเอง: `champollion next` จะระบุคำสั่งให้
และตั้งแต่ขั้นตอน `forge` เป็นต้นไป ระบบจะส่งต่อคำแนะนำจากระบบแนะนำของ forge เอง
(`nmt-forge status`) หน้านี้จะอธิบายการทำงานของขั้นตอนเหล่านั้น

## โมเดล

`nmt-forge init --model <preset>` จะเขียนค่าพรีเซ็ตลงใน `config.json` เป็น
ตัวเลขที่ชัดเจน (ถูกแฮชเป็นเอกลักษณ์ของการรันแต่ละครั้ง: forge เวอร์ชันใหม่กว่า
จะไม่เปลี่ยนการรันเดิมของโปรเจกต์) `nmt-forge use-model <preset>`
ใช้สำหรับสลับโปรเจกต์

| ค่าพรีเซ็ต | คืออะไร | สิ่งที่ต้องใช้ | สิ่งที่ forge แนะนำให้คาดหวัง |
|---|---|---|---|
| `cpu-tiny` | ทรานส์ฟอร์เมอร์ขนาดเล็กที่ฝึกขึ้นใหม่จากคู่ประโยค พร้อมคลังคำศัพท์ขนาด 4,000 ชิ้นคำที่เรียนรู้จากแถวข้อมูลฝึกสอน | CPU เท่านั้น · ไม่ต้องดาวน์โหลด | "กับคู่ประโยคประมาณ 1–2 พันคู่: chrF++ ราว 5–30 (คะแนนระดับสูงเฉพาะข้อมูลที่เป็นเทมเพลตชัดเจน) — จำเป็นวลีและรูปแบบเทมเพลตของข้อมูลคุณ ไม่ใช่การแปลแบบทั่วไป" |
| `byt5-small` | ByT5-small ของ Google (พารามิเตอร์ 300 ล้านตัว อ่านระดับไบต์ — ไม่ต้องปรับคลังคำศัพท์) แบบไฟน์จูน | ดาวน์โหลด ~1.2 GB · แนะนำ Apple silicon หรือ CUDA GPU | "จากการทดสอบของ forge เอง โมเดลนี้เรียนรู้จากคู่ประโยคชุดเดียวกันได้มากกว่า cpu-tiny อย่างมาก — แต่ยังคงต้องวัดผลเทียบกับโมเดลที่คุณใช้อยู่บน dev set" |
| `byt5-small-lowmem` | โมเดลเดียวกัน อัตราการเรียนรู้และขีดจำกัดความยาวเท่ากัน ตั้งค่าสำหรับคอมพิวเตอร์ที่มีหน่วยความจำ 8–15 GB: Adafactor, gradient checkpointing และแบทช์ละ 4 คู่สะสม 4 ครั้ง (รวม 16 คู่ต่อสเต็ปเช่นกัน) — ใช้หน่วยความจำต่อสเต็ปน้อยลง แต่ใช้เวลามากขึ้น ยังไม่ได้วัดผลบนคอมพิวเตอร์ขนาด 8 GB | เหมือนกับ `byt5-small` | เหมือนกับ `byt5-small` |
| `cpu-finetune` | โมเดล Marian/opus-mt ที่เทรนล่วงหน้าขนาดเล็ก ไฟน์จูนบน CPU คุณต้องระบุโมเดลตั้งต้นเอง (`--base`) ระบบจะไม่คาดเดาให้ | CPU เท่านั้น · ดาวน์โหลด ~300 MB | "ขึ้นอยู่กับว่าภาษาเป้าหมายของโมเดลตั้งต้นมีความเกี่ยวข้องกันเพียงใด — ให้วัดผลเทียบกับ cpu-tiny บน dev set ของคุณ" |
| `nllb-600m` | NLLB-200 distilled 600M ร่วมกับ LoRA | CUDA GPU (8 GB ขึ้นไป) · ดาวน์โหลด ~2.5 GB | "มีประสิทธิภาพสูงสุดในสามตัวเลือกเมื่อ NLLB ครอบคลุมภาษาที่เกี่ยวข้องกัน แต่ยังคงต้องวัดผล — อย่าด่วนสรุปเอง" |

ทุกพรีเซ็ตจะฝึกด้วย training extra ของ forge (`nmt-forge[hf]`) โดยใช้ seed 42
ไม่มีพรีเซ็ตใดกำหนดงบประมาณเวลา: ตัวเลขดังกล่าวขึ้นอยู่กับการตัดสินใจของชุมชน

- **หากไม่มี `--model`**, `init` จะเขียน `cpu-tiny`
- **`--model auto`** (ค่าที่ rails ส่งมา) จะอ่านหน่วยความจำของ GPU ที่ forge
  สามารถใช้ฝึกได้ — บน Mac ที่ใช้ Apple silicon จะเป็นหน่วยความจำของเครื่อง (ที่แชร์กับ
  GPU); หากมี `nvidia-smi` บน `PATH` จะใช้ของการ์ด NVIDIA ที่ใหญ่ที่สุด:
  16 GB ขึ้นไป (หรือหน่วยความจำที่อ่านไม่ได้) → `byt5-small`; 8–15 GB →
  `byt5-small-lowmem`; ต่ำกว่า 8 GB → `cpu-tiny` หากไม่มี GPU ทั้งสองแบบ จะเป็น `cpu-tiny`
  เหตุผลพร้อมหน่วยความจำที่พบจะถูกพิมพ์ออกมา (`chosen: …`) และส่งคืน
  เป็น `model_choice` ใน `--json` ขั้นตอนนี้ไม่ได้ทดสอบว่า GPU ทำงานได้จริงหรือไม่
  `NMT_FORGE_AUTO_PRESET` จะแทนที่ค่านี้ (โดยต้องระบุชื่อพรีเซ็ต)
- **โมเดลที่ทรงพลังกว่าที่รอบการปรับปรุงเสนอ** จะส่งให้เฉพาะโปรเจกต์ที่โมเดล
  ที่ใช้อยู่คือ `cpu-tiny`: โดยจะเป็น `byt5-small-lowmem` หาก `--model auto` จะเลือกตัวนี้
  มิฉะนั้นจะเป็น `byt5-small` — รวมถึงบนคอมพิวเตอร์ที่ `auto` จะเลือก
  `cpu-tiny` ด้วยเช่นกัน; ข้อเสนอของ `why` จะระบุสิ่งที่จำเป็นต้องใช้

**หมายเหตุ** อย่ามองว่าสิ่งที่คาดหวังจากพรีเซ็ตเป็นคำสัญญา ให้วัดผลบน
dev set เสมอ

## ลูปที่มีแนวป้องกัน

แต่ละคำสั่งจะรับ `--json`; ส่วน `--workspace <dir>` (ค่าเริ่มต้น `.forge`) จะอยู่
ก่อนคำสั่งย่อย Forge จะปฏิเสธแฟล็กที่เป็นตัวย่อ

| ขั้นตอน | คำสั่ง | การทำงาน | สิ่งที่ปฏิเสธ |
|---|---|---|---|
| เวิร์กช็อป | `nmt-forge init <code> --dir . --pair <src>-<tgt> --model auto` | เขียน `.forge/`, `config.json`, `NEXT_STEPS.md` | `--pair` ที่อ่านไม่ได้; `cpu-finetune` ที่ไม่มี `--base` |
| ชุดทดสอบ | `nmt-forge registry add project-test <file> --role test` | ตรึง sha256 ของไฟล์; เริ่มต้นบันทึกการอ่าน | แถวสังเคราะห์ในชุดทดสอบหรือชุดปิดผนึก; ชื่อที่ลงทะเบียนไว้แล้วแต่เนื้อหาต่างกัน (เว้นแต่ `--allow-rotate`) |
| คัดกรอง | `nmt-forge leak-audit <corpus> --clean-to <clean.jsonl>` | คัดกรองทุกคู่เทียบกับชุดพัฒนา ชุดทดสอบ และชุดปิดผนึกทุกชุดที่ลงทะเบียนไว้; เขียนสำเนาที่สะอาด | การเขียนทับไฟล์ที่ใช้งานอยู่ (เว้นแต่ `--overwrite`); ผลลัพธ์ที่ไม่เหลือข้อมูลสำหรับการฝึกฝน |
| ทำนาย | `nmt-forge prereg new <id> --eval-set <set> --expect "…" --rationale "…"` | เขียนคำทำนายของชุมชนก่อนการให้คะแนนใดๆ | id ที่มีอยู่แล้ว; การเขียนหลังจากการอ่านชุดข้อมูลเพื่อคิดคะแนนใดๆ ไม่ว่าจะโดย forge หรือ `mt-eval` (เว้นแต่ `--allow-after-reads` ซึ่งจะถูกบันทึกลงใน ledger) |
| ชุดพัฒนา | `nmt-forge split <clean.jsonl> --test 0 --dev <n> --seed 42 --near-dupe 0.6 --max-group <m> --out data/split --register project` | การแบ่งส่วนชุดพัฒนาแบบกลุ่มไม่ทับซ้อนกัน (group-disjoint) ลงทะเบียนเป็น `project-dev` โดยที่ `<n>` ของ rails กำหนดไว้ที่: หนึ่งในสิบของคู่ประโยคที่ผ่านการคัดกรอง อย่างน้อย 50 คู่ และไม่เกิน 500 คู่ — หนึ่งในสี่ของจำนวนดังกล่าวหากมีคู่ประโยคต่ำกว่า 200 คู่ ([shell](/docs/agents/shell#build-and-test-a-model)) ส่วน `--near-dupe 0.6` จะเก็บคู่ที่เกือบซ้ำกัน (คำซ้อนทับกัน ≥ 0.6) ไว้ฝั่งเดียวกัน ซึ่งเป็นเกณฑ์เดียวกับที่การคัดกรองในรอบถัดๆ ไปทุกรอบนำมาใช้; rails จะตั้งค่า `--max-group` เป็นครึ่งหนึ่งของขนาดชุดพัฒนายกกำลังบวกหนึ่ง เพื่อให้ไฟล์ที่เขียนขึ้นจากเทมเพลตยังคงสามารถแบ่งส่วนได้ | ฝั่งใดฝั่งหนึ่งเกิน 1.5 เท่าของที่ร้องขอ หรือข้อมูลการฝึกฝนเหลือไม่ถึงครึ่งหนึ่งของแถวทั้งหมด |
| ค่าพื้นฐาน | `nmt-forge floor <word lists>` | แปลชุดพัฒนาแบบคำต่อคำจากพจนานุกรมและให้คะแนนในลักษณะเดียวกับคะแนน dev ของรอบการรัน | ไม่มีชุดพัฒนาที่ลงทะเบียนไว้ |
| ตรวจสอบ | `nmt-forge preflight run --config config.json` | รันทุกเกตที่รอบการรันจะต้องผ่าน พร้อมเสนอวิธีแก้ไข; จบการทำงานด้วยรหัส 2 หากมีเกตใดไม่ผ่าน | — |
| ฝึกฝน | `nmt-forge run config.json --detach` | ฝึกฝน เลือกเช็กพอยต์ที่ดีที่สุดบนชุดพัฒนา ลบเช็กพอยต์อื่นๆ ของรอบการรันนั้นออก ([พื้นที่ดิสก์](#disk-space)) เขียน `.forge/runs/<run name>-<8 hex>/` พร้อมกับ `run-manifest.json`, `run-report.md`, `dev-outputs.jsonl` | รอบการรันที่มีอยู่แล้ว (การกำหนดค่า ไฟล์ฝึกฝน และชุดพัฒนาเดียวกัน); ดิสก์ที่มีพื้นที่ไม่พอ (`disk-room` ก่อนที่จะมีการเขียนข้อมูลใดๆ; `--skip-disk-check` จะแทนที่การตรวจสอบนี้); รอบการรันที่กำลังดำเนินอยู่; แถวฝึกฝนที่รั่วไหลเข้าไปในชุดทดสอบหรือชุดปิดผนึก; แถวชุดพัฒนาที่ปนอยู่ในข้อมูลฝึกฝน; ข้อมูลที่ทำเครื่องหมายว่าห้ามฝึกฝน (do-not-train) หรือถูกกักกัน (quarantined); `terms.training: not-allowed`; ข้อมูลสังเคราะห์ที่เกินขีดจำกัด; ขีดจำกัดการถอดรหัสที่สั้นเกินไปสำหรับข้อมูลอ้างอิง; คีย์การกำหนดค่าที่ไม่รู้จัก |
| คะแนนทดสอบ | `nmt-forge export <run-manifest.json> --prereg <id> --out export/` | ให้คะแนนชุดทดสอบหนึ่งครั้งเทียบกับคำทำนาย; รวมชุดโมเดลเป็นแพ็กเกจ พร้อมวาง `input-words.json` ไว้ข้างโฟลเดอร์ของโมเดล — ซึ่งเป็นคำศัพท์ที่โมเดลเคยใช้ฝึกฝน เพื่อให้เซิร์ฟเวอร์สามารถระบุคำที่ไม่เคยเห็นได้ ([การให้บริการ](/docs/agents/serving#what-an-export-holds)) | ไม่มีการลงทะเบียนล่วงหน้า หรือลงทะเบียนไว้หลายรายการโดยไม่มี `--prereg`; ชุดปิดผนึกที่ถูกใช้ไปแล้ว; `--out` ที่ไม่ว่างเปล่าโดยไม่มี `--force` |
| เลือก | `nmt-forge choose <export>/model` | บันทึกการเลือกโมเดลของชุมชน | โฟลเดอร์ที่ไม่ได้มาจากการส่งออกที่บันทึกไว้พร้อมโมเดล |
| ให้บริการ | `nmt-forge serve <export>/model --detach` | ให้บริการโมเดลบนคอมพิวเตอร์เครื่องนี้ ([การให้บริการ](/docs/agents/serving#nmt-forge-serve)) | นอก loopback โดยไม่มีโทเค็น หรือโมเดลสำหรับใช้เฉพาะในเครื่องโดยไม่มี `--holders-agreed-by` |

ทุกสิ่งที่มีความสำคัญจะถูกเขียนลงในบัญชีแยกประเภทแบบลูกโซ่แฮช (hash-chained ledger)
(`.forge/ledger.jsonl`): การลงทะเบียน, การอ่านข้อมูลพร้อมวัตถุประสงค์, การคาดการณ์,
คะแนน, การใช้ sealed set, การเขียนทับ (override), ผลการตรวจสอบความถูกต้อง, คะแนนขั้นต่ำ (floor), การส่งออก,
การเลือกโมเดล, การให้บริการ ตลอดจนการเริ่มต้นและการสิ้นสุดของงาน โดย run manifest คือบันทึกของการรันแต่ละครั้ง

**เกณฑ์ก่อนการรัน (Preflight gates):** config (พิมพ์แฮชของการกำหนดค่าทั้งหมด), workspace match, no
run in progress, dev fence, training data, backend installed, selection
plugins, test near-twins และ dev near-twins (คำเตือน), leak audit, training
mix, generation headroom, schedule sanity

**การถอดรหัส (Decoding)** การถอดรหัส dev ขั้นสุดท้าย, การอ่านชุดทดสอบ (`export`), โมเดลที่ใช้งานอยู่
เมื่อแปลชุด dev อีกครั้ง และโมเดลที่เปิดให้บริการ จะใช้ beam search ด้วย
`decode.num_beams` (ขนาด 4 เว้นแต่ `config.json` จะระบุเป็นอย่างอื่น); การเลือก
เช็กพอยต์ซึ่งต้องจัดอันดับหลายเช็กพอยต์จะถอดรหัสแบบ greedy การส่งออก
จะบันทึก `beams_applied` ไว้ และ `nmt-forge serve` จะถอดรหัสตามวิธีที่โมเดลได้รับการ
วัดผล: การส่งออกรุ่นเก่าที่ไม่มีค่านี้จะให้บริการแบบ greedy

**ขีดจำกัดความยาว** โมเดลจะเรียนรู้จากประโยคต้นทางไม่เกิน `model.max_src` โทเคน
และจากคำแปลไม่เกิน `model.max_tgt` โทเคน, อ่านได้ไม่เกิน
`model.max_src` เมื่อทำการแปล และเขียนได้ไม่เกิน
`decode.max_new_tokens` (`byt5-small`: ชนิดละ 320 ไบต์ — ประมาณ 320 ตัวอักษรสำหรับ
อักษรละติน, ประมาณ 100 ตัวสำหรับอักษรสัญลักษณ์แทนพยางค์ (syllabics); `cpu-tiny`: ขาเข้า 256 ชิ้นคำ, ขาออก 384 ชิ้นคำ)
จะไม่มีการตัดทอนข้อความอย่างเงียบๆ: การฝึกจะนับจำนวนคู่ประโยคที่เกินขีดจำกัดใดขีดจำกัดหนึ่งก่อนที่จะตัดออก
และการถอดรหัส dev ขั้นสุดท้ายจะนับประโยคที่ถูกตัดทอนก่อนเข้าสู่โมเดลและ
คำแปลที่หยุดเมื่อถึงขีดจำกัด ทั้งสองข้อมูลจะถูกบันทึกไว้ใน run manifest
(`length_limits`) และ `status` จะแจ้งเตือนพร้อมวิธีแก้ไข: ให้แบ่งประโยคยาว หรือ
เพิ่มค่า `model.max_src` และ `model.max_tgt` (รวมถึง `decode.max_new_tokens`) ใน
`config.json` — ซึ่งจะทำให้การฝึกใช้เวลานานขึ้น

**หมายเหตุ** `nmt-forge run` เองไม่ได้บังคับว่าต้องมีการคาดการณ์ แต่ทาง rails จะถามหา
ข้อมูลนี้ก่อน อย่าเพิ่งเริ่มฝึกก่อนที่ขั้นตอนการคาดการณ์ (predict) จะเสร็จสิ้น

**หมายเหตุ** `export` คือขั้นตอนที่อ่านชุดทดสอบ การเรียกใช้คำสั่งนี้ถือเป็น
หมุดหมายสำคัญ โดยจะต้องบันทึกการคาดการณ์ของชุมชนไว้เรียบร้อยแล้ว — ไม่ใช่การตรวจสอบ
ตามปกติทั่วไป

## งานเบื้องหลัง

`run --detach` และ `serve --detach` จะเริ่มงานที่มีการควบคุมดูแล (supervised job) แล้วส่งคืนสถานะทันที

```bash
nmt-forge jobs                          # every job: state, stage, step, time left, last sign of life
nmt-forge jobs stop <name> --wait 120   # stop it, and wait up to 120 s (at most 180) for it to exit
```

- สถานะต่างๆ ได้แก่: `running`, `finished`, `refused`, `crashed`, `stalled`,
  `deadline`, `interrupted`, `lost` โดย `lost` คืองานที่ supervisor สิ้นสุดลง
  โดยไม่มีการบันทึกข้อมูล — รวมถึงหลังจากการรีบูตเครื่อง เมื่อหมายเลขโปรเซสนั้น
  กลายเป็นของโปรเซสอื่นไปแล้ว
- **ฝึกทีละงานเท่านั้นบนคอมพิวเตอร์เครื่องนี้** งานฝึกโมเดลจะเข้าคิว
  ระดับเครื่องตามลำดับก่อนหลัง (`~/.nmt-forge/machine/train-queue`)
  ครอบคลุมทุกโปรเจกต์ งานที่รอคิวจะอยู่ในสถานะ `running` โดยมี `queued_behind`
  (งานที่กำลังรอ) ใน `nmt-forge jobs --json`; `status` จะเป็น `training`
  และระบุว่ากำลังรอต่อจากงานใด จากนั้นจะเริ่มทำงานเองโดยอัตโนมัติ การสั่งหยุดขณะที่
  รอคิวจะทำให้งานสิ้นสุดลงโดยยังไม่ได้เริ่ม (`interrupted`); การรอเกิน 24 ชั่วโมงจะทำให้งานสิ้นสุดลง
  (`deadline`)
- **ขอบเขตการทำงาน (Bounds)** (งานฝึกโมเดล): ไม่มีการตอบสนองเป็นเวลา 15 นาทีตอนเริ่มต้น
  (`--startup-minutes`); ไม่มีความคืบหน้าเป็นเวลา 10 นาทีหรือ 30 เท่าของเวลาสเต็ปมัธยฐาน
  (ขึ้นอยู่กับว่าค่าใดนานกว่า) (`--stall-minutes`); กำหนดเวลาสิ้นสุดที่ `--deadline-hours`,
  มิฉะนั้นจะใช้งบประมาณเวลาของการกำหนดค่า × 1.25, มิฉะนั้นคือ 24 ชั่วโมง งานที่เกินขอบเขตจะถูก
  สั่งหยุดและบันทึกประวัติไว้
- **การสั่งหยุด**: การรันจะหยุดลงในสเต็ปถัดไป โดย supervisor จะยกระดับเป็นการ
  terminate หลังจาก 60 วินาที และ kill ในอีก 10 วินาทีถัดมา
- **เกณฑ์เวลาจริง (Wall-clock gate)** (แบ็กเอนด์ Hugging Face): หลังช่วง warm-up ทาง forge จะจับเวลา
  ของแต่ละสเต็ป ประเมินเวลาของการรัน และปฏิเสธการรันที่ใช้เวลาเกินงบประมาณ
  (`wall-clock budget exceeded: …`) หากไม่ได้กำหนดงบประมาณไว้ ขีดจำกัดสูงสุดคือเพดาน 24 ชั่วโมง
- ในระหว่างที่งานฝึกกำลังทำงาน `status` จะเป็น `training` และขั้นตอนของ rails จะเป็น
  `wait` งานที่ล้มเหลวจะแสดงเป็นคำเตือนในทุกการตรวจสถานะหลังจากนั้น
- **การทำงานต่อ (Resuming)** เมื่อจบงานฝึกครั้งล่าสุดด้วยสถานะ `lost`, `crashed`, `stalled`
  หรือ `deadline` หลังจากบันทึกเช็กพอยต์แล้ว `status` จะระบุ `nmt-forge preflight
  run --config config.json && nmt-forge run config.json --resume --detach`:
  ซึ่งเป็นการรันใหม่ที่เริ่มต้นจากเช็กพอยต์ล่าสุดของการรันที่ถูกขัดจังหวะ (ค่าน้ำหนัก, optimizer ใหม่, จำนวน epoch ที่เหลืออยู่) และ manifest ของการรันนี้จะระบุ
  จุดที่ทำงานต่อ (`resumed_from`) ตัวเลือกนี้จะไม่แสดงให้ใช้หลังจากการสั่งหยุดด้วยตนเอง
- งานแบบ detach รองรับเฉพาะระบบ POSIX เท่านั้น (macOS, Linux)

## พื้นที่ดิสก์

การฝึกฝนจะเขียนเช็กพอยต์: พร้อมกันสูงสุดไม่เกิน `model.save_total_limit` จุด
(4 จุด เว้นแต่ `config.json` จะระบุไว้เป็นอย่างอื่น) แต่ละจุดมีขนาดประมาณ 1.4 GB สำหรับ ByT5-small
ก่อนที่จะมีกฎเหล่านี้ แต่ละรอบการปรับปรุงของโครงการ ByT5-small จะเก็บข้อมูลไว้ประมาณ
5.6 GB โดยไม่มีอะไรคอยลบโมเดลของรอบก่อนหน้า และดิสก์ที่เต็มก็ทำให้
การรันหยุดชะงักระหว่างที่กำลังบันทึกข้อมูล หน่วย GB ของ Forge คือ 1024³ ไบต์

- **รอบการเทรนที่เสร็จสิ้นจะเก็บเฉพาะเช็กพอยต์ที่ได้รับเลือกไว้เท่านั้น** โฟลเดอร์
  `checkpoint-*` อื่นๆ ทั้งหมดของรอบจะถูกลบออกทันทีที่เลือกเช็กพอยต์แล้ว:
  ไม่มีสิ่งใดอ่านโฟลเดอร์เหล่านั้นอีก (`export` จะคัดลอกเช็กพอยต์ที่เลือก; รอบถัดไป
  จะเริ่มจากโมเดลที่กำลังใช้งานอยู่) manifest จะบันทึก `checkpoints_pruned`
  (`removed`, `bytes`, `kept`) ส่วน `"keep_checkpoints": "all"` ในบล็อก `model`
  ของ `config.json` จะเก็บโฟลเดอร์ทั้งหมดไว้ ค่าอื่นๆ จะถูกปฏิเสธเมื่ออ่านคอนฟิก
  ก่อนที่จะเริ่มการเทรนใดๆ (`ConfigError`; ในที่นี้สำหรับค่า `x`):
  `config.model.keep_checkpoints is "selected" (the default: only the checkpoint the run picks stays) or "all", not 'x'`
- **การล็อก (Lock)** การรันที่ดิสก์มีพื้นที่ไม่พอจะถูกปฏิเสธก่อนที่จะมีการเขียนสิ่งใด
  (ตัวป้องกัน `disk-room`); การรันแบบ detached จะถูกปฏิเสธทันทีก่อนที่งาน
  จะเริ่มขึ้น การประเมิน: ขนาดของหนึ่งเช็กพอยต์ — เช็กพอยต์ที่เก็บไว้ของ
  การรันก่อนหน้าของโมเดลฐานเดียวกันในพื้นที่ทำงานนี้ มิฉะนั้นจะเป็นไฟล์ค่าน้ำหนักของ
  ตัวโมเดลฐานเอง (โฟลเดอร์ในเครื่อง หรือแคชของ Hugging Face) — คูณด้วย
  `model.save_total_limit` บวกอีก 1 GB จนเสร็จสิ้น; ไม่ต่ำกว่า 2 GB เสมอ
  ข้อความปฏิเสธจะระบุ
  `[disk-room] this computer has <free> free; training this model needs about <need> (<n> checkpoints of about <size> each while it trains, and room to finish)`
  — หรือเมื่อไม่ทราบขนาด *"(ต้องมีพื้นที่ว่างอย่างน้อยเท่านี้ไม่ว่าจะเป็นโมเดลใดก็ตาม)"* — จากนั้นตามด้วย
  `why: a disk that fills mid-training loses the run as it saves, and slows the whole computer`
  และ `fix` ที่ระบุว่า `nmt-forge tidy` สามารถเพิ่มพื้นที่ว่างอะไรได้บ้างที่นี่ (เมื่อสามารถ
  เพิ่มพื้นที่ว่างได้), การย้ายไฟล์อื่นๆ ออกจากดิสก์ และ `--skip-disk-check`
- `nmt-forge run … --skip-disk-check` (ไม่ว่าจะระบุ `--detach` หรือไม่) จะเริ่มทำงาน
  ต่อไปอยู่ดี `disk_room` ของ manifest จะบันทึกการตรวจสอบนี้ — `free_bytes`,
  `checkpoint_bytes` (`null` เมื่อไม่ทราบขนาด), `checkpoints_at_once`,
  `need_bytes` — หรือ `{"skipped": "--skip-disk-check"}` **หมายเหตุ** การประเมิน
  อาจคลาดเคลื่อนได้; การจะข้ามการตรวจสอบหรือไม่นั้นขึ้นอยู่กับการตัดสินใจของคุณ
- **`nmt-forge tidy`** จะแสดงรายการค่าน้ำหนักโมเดลของรอบก่อนหน้าที่ไม่มีสิ่งใด
  ใช้งาน — แต่ละการรันพร้อมขนาด พื้นที่รวม และพื้นที่ว่าง — และไม่ลบ
  สิ่งใดออก `nmt-forge tidy --yes` จะลบรายการเหล่านั้น โดยจะไม่ลบโมเดลที่กำลัง
  ใช้งานอยู่ การรันล่าสุด หรือโมเดลที่ถูกโมเดลที่กำลังใช้งานอยู่แทนที่ (ใบตรวจ
  แบบบอดใช้ร่างร่วมด้วย); บรรทัด `Kept:` ของผลลัพธ์จะระบุแต่ละรายการพร้อมเหตุผล การรันที่ถูกจัดเก็บกวาดล้างแล้วจะยังคงเก็บบันทึกไว้ — manifest, คำแปลชุด dev, รายงาน —
  และ manifest จะได้รับ `model_removed` (`at`, `by`, `bytes`, `why`);
  บัญชีบันทึก (ledger) จะได้รับรายการ `tidy` (`runs`, `bytes`) การรันที่ถูกจัดเก็บกวาดล้างไปแล้วเมื่อถูกสั่งให้
  แปล (`compare-runs` ที่แปลชุด dev ซ้ำด้วยการรันนั้น) จะถูกปฏิเสธ:
  `run <name>'s model was removed by nmt-forge tidy on <time> to free disk space — its record stays, its weights do not`
  **หมายเหตุ** `--yes` จะลบไฟล์: ให้แสดงรายการให้คุณเห็น และสั่งรันเมื่อคุณตอบตกลงเท่านั้น
- **`status` จะแจ้งเตือน** — บรรทัดหนึ่งใน `warnings` ซึ่งส่งต่อผ่าน rails — เมื่อดิสก์
  ที่เก็บพื้นที่ทำงานมีพื้นที่ว่างเหลือน้อยกว่า 10 GB หรือการจัดเก็บกวาดล้างสามารถเพิ่มพื้นที่ว่างได้ตั้งแต่ 5 GB
  ขึ้นไป: *"คอมพิวเตอร์เครื่องนี้มีพื้นที่ว่าง X GB; โมเดลจาก N รอบก่อนหน้าที่ไม่มีสิ่งใดใช้งานกินพื้นที่ Y GB — `nmt-forge tidy` แสดงรายการโมเดลเหล่านั้น,
  `nmt-forge tidy --yes` ลบเพื่อเพิ่มพื้นที่ว่าง (โมเดลที่กำลังใช้งานอยู่ โมเดลล่าสุด และ
  โมเดลที่ถูกแทนที่จะได้รับการเก็บไว้)"* (ข้อความหลังเครื่องหมายอัฒภาคจะมีขึ้นก็ต่อเมื่อ
  tidy สามารถเพิ่มพื้นที่ว่างได้)

## รอบการปรับปรุง

เมื่อนำโมเดลไปใช้งานแล้ว แต่ละรอบจะฝึกการรันใหม่ด้วยข้อมูลที่มากขึ้นโดยใช้
dev set ชุดเดิม

**วิธีฝึกในแต่ละรอบ** `champollion improve prepare` จะรันคำสั่ง `nmt-forge
round-plan --config config.json`, which rewrites `config.json` ด้วยวิธีใดวิธีหนึ่ง
จากสองวิธี และเขียนแผนลงในบัญชีแยกประเภท (`round-plan`):

- **ฝึกต่อจากโมเดลที่ใช้งานอยู่** (`init_from` โฟลเดอร์โมเดลนั้น): วนฝึก 4 รอบ
  (epoch) บนประโยคทั้งหมดที่มีอยู่จนถึงปัจจุบัน — ข้อมูลเก่าจะช่วยป้องกันไม่ให้โมเดล
  ลืม — โดยใช้อัตราการเรียนรู้ครึ่งหนึ่ง ใช้เวลาน้อยกว่าการฝึกตั้งแต่เริ่มต้นมาก
  การตั้งค่าแบบเต็มจะอยู่ใน `config.json` ภายใต้ `model_full`
- **ฝึกตั้งแต่เริ่มต้น** โดยนำการตั้งค่าแบบเต็มกลับมาใช้ เมื่อยังไม่มีโมเดลที่นำไป
  ใช้งาน; เมื่อมีการเปลี่ยนโมเดล (`use-model` ซึ่งจะละทิ้ง
  `model_full` ด้วย); สำหรับ `cpu-tiny` ซึ่งคลังคำศัพท์มาจากประโยค
  ที่ใช้ฝึกสอน (ใช้เวลาฝึกเพียงไม่กี่นาที); สำหรับโมเดล adapter (LoRA); และทุกๆ
  รอบที่ 4 เพื่อป้องกันไม่ให้การฝึกต่อสั้นๆ หลายครั้งทำให้โมเดลเบี่ยงเบนไป (drift)

`prepare` จะพิมพ์แผนและเหตุผลออกมา และบันทึก `training` (`mode`,
`epochs`) ลงใน `improve/round-<k>/prepared.json` ไม่ว่าจะเลือกทางใด โมเดลรอบใหม่จะถูก
ตัดสินเทียบกับโมเดลที่ใช้งานอยู่บนประโยคชุดพัฒนาชุดเดียวกัน จากนั้น (ข้อ 1, 3 และ
4 คือสถานะที่ที่ปรึกษาของ forge ระบุ; ข้อ 2 บันทึกโดย rails):

1. **`improve-compare`** (`auto`): `nmt-forge compare-runs <in-use
   run-manifest.json> <new run-manifest.json>` — โมเดลทั้งสองจับคู่เปรียบเทียบ
   ประโยคต่อประโยคบนชุด dev หากมีประโยค dev น้อยกว่า 50 ประโยค
   คำตัดสินคือ **too-few** ไม่ว่าคะแนนจะเป็นเท่าใดก็ตาม: *"ประโยค dev น้อยเกินไปที่จะ
   บอกได้: หากต่ำกว่า 50 ประโยค จะไม่สามารถแยกความแตกต่างออกจากความบังเอิญได้อย่างน่าเชื่อถือ ไม่ว่า
   ความแตกต่างนั้นจะมีขนาดเท่าใดก็ตาม"* ตั้งแต่ 50 ประโยคขึ้นไป: จะตัดสินว่า **better** ก็ต่อเมื่อการทดสอบแบบจับคู่ได้ค่า p < 0.05
   **และ** ช่วงความเชื่อมั่น 95% ของผลต่างอยู่เหนือศูนย์; ตัดสินว่า **worse** เมื่อ
   p < 0.05 และค่าอยู่ต่ำกว่าศูนย์; นอกเหนือจากนั้นคือ **no-change** ทุกคำตัดสินจะระบุ
   ความแตกต่างที่น้อยที่สุดที่ชุด dev สามารถแสดงได้อย่างน่าเชื่อถือ จะไม่มีการอ่าน
   ชุดทดสอบโดยเด็ดขาด จะถูกปฏิเสธ (`improve-loop`) สำหรับการรันที่ใช้ชุด dev ต่างกัน, การรัน
   ที่ไม่มีการบันทึกคำแปลชุด dev หรือชุด dev มีการเปลี่ยนแปลงไปหลังจากการรันใหม่
2. **คำตัดสินของผู้พูดภาษา** ในกรณีที่ชุด dev ไม่สามารถตัดสินได้ โมเดลของรอบที่
   ยังไม่ถูกนำไปใช้งานจะทำหน้าที่ร่างครึ่งหนึ่งของแถวที่ร่างในใบตรวจรอบถัดไป
   แบบบอด (`draft-newer` ด้านล่าง) และ `champollion improve marks`
   จะบันทึกจำนวนการประเมินของผู้พูดภาษาร่วมกับ forge:
   `nmt-forge speaker-verdict --newer <run> --in-use <run> --newer-right <n> --newer-judged <n> --in-use-right <n> --in-use-judged <n> --json`
   โดย forge จะดำเนินการกับผลนี้หลังจากมีคำตัดสินแบบ **too-few** หรือ **no-change** เท่านั้น การทดสอบ
   ความต่างของสองสัดส่วนแบบรวม (pooled two-proportion test) แบบสองหางที่ระดับ 5% (|z| > 1.96) จะให้ผล `clear`:
   `newer`, `in-use` หรือ `neither`; รายการ `improve-speaker` ในบัญชีบันทึก (ledger) จะเก็บ
   ชื่อการรันทั้งสอง จำนวนนับทั้งสี่ `z` และ `clear` — เฉพาะจำนวนนับเท่านั้น ระบบจะ
   ปฏิเสธจำนวนนับที่ต่ำกว่า 0 ค่าที่ถูกต้องมากกว่าจำนวนที่ตัดสิน และโมเดลที่ไม่มี
   ฉบับร่างที่ได้รับการตัดสิน ข้อความระบุว่า: *"การตรวจแบบบอดในการพบปะครั้งเดียวกัน ผู้พูดภาษา
   ตัดสินว่าโมเดลใหม่ถูกต้อง A จาก B ประโยคใหม่ (P%) และโมเดล
   ที่ใช้งานอยู่ถูกต้อง C จาก D (Q%)"* ตามด้วย *"โมเดลใหม่ดีกว่าอย่างเห็นได้ชัดใน
   ประโยคเหล่านี้ — forge เสนอให้นำไปใช้งาน"*, *"โมเดลที่ใช้งานอยู่ดีกว่าอย่างเห็นได้ชัดในประโยคเหล่านี้ — ยังคงใช้โมเดลเดิมต่อไป"* หรือ *"ไม่มีความแตกต่างชัดเจน
   ในประโยคเหล่านี้ — ยังคงใช้โมเดลเดิมต่อไป"*
3. **`improve-promote`** (`confirm`) เมื่อผลตัดสินเป็น **better** — หรือเมื่อเป็น **too-few** หรือ
   **no-change** ในกรณีที่ `speaker-verdict` ล่าสุดของการรันนั้นระบุว่า
   `clear: newer` (ไม่มีทางเสนอเมื่อผลเป็น **worse**) นี่เป็นเพียงข้อเสนอ: คำตัดสินเพียงอย่างเดียวจะไม่นำโมเดล
   ไปใช้งาน เมื่อชุมชนตอบตกลง ระบบจะเอ็กซ์พอร์ตการรันใหม่โดยไม่อ่าน
   ชุดทดสอบ (`--no-eval`) บันทึกว่าได้รับการเลือก (`choose`) หยุดเซิร์ฟเวอร์ที่กำลัง
   ทำงานอยู่ และให้บริการโมเดลใหม่ที่พอร์ตเดิม มีเพียง
   `export` และ `choose` เท่านั้นที่นับว่าเป็นการนำโมเดลไปใช้งาน: จนกว่าจะถึงจุดนั้น รายงานประจำรอบ
   จะระบุว่า *"ดีขึ้นอย่างวัดผลได้: ยังไม่ได้นำไปใช้งาน — ชุมชนยังไม่ได้เลือกโมเดลนี้"*
   และการติดตามความคืบหน้า การคาดการณ์ และการตรวจสอบ overfit จะไม่นับรวมโมเดลนี้ สำหรับคะแนนประเมิน
   ของผู้พูดภาษา `why` จะเพิ่มจำนวนนับของพวกเขาและระบุว่า *"มีความแตกต่างชัดเจน: โมเดลใหม่ดีกว่าในประโยคที่ครอบครัว
   จำเป็นต้องใช้"* ในใบตรวจถัดไป ครึ่งหนึ่งของแถวที่ร่างจะมาจากโมเดลที่ถูกแทนที่
   เพื่อให้ผู้พูดภาษาตรวจสอบการเลื่อนขั้นนี้แบบบอด (ดูด้านล่าง)
4. มิฉะนั้น โมเดลที่ใช้งานอยู่จะยังคงอยู่และรอบถัดไปจะเริ่มต้นขึ้น — เว้นแต่
   คำตัดสินของสองรอบล่าสุดนับตั้งแต่การเปลี่ยนโมเดลครั้งล่าสุดจะเป็น
   **no-change** หรือ **worse** ทั้งคู่ โดยกำลังใช้งาน `cpu-tiny` อยู่ การเปลี่ยนโมเดล
   ครั้งล่าสุดคือรายการ `model-change` ล่าสุด (การสลับพรีเซ็ตหรือ `not-now`) หรือ
   รายการ `choose` ในบัญชีบันทึก — ไม่ว่าจะเป็นโมเดลใดก็ตามที่ชุมชนนำไปใช้งาน รวมถึง
   การเลื่อนขั้นตามคะแนนประเมินของผู้พูดภาษาด้วย รอบที่ได้ผลตัดสิน **too-few** จะไม่นับว่าเป็น
   รอบที่ได้รับการตัดสิน: หากรอบใดรอบหนึ่งในสองรอบล่าสุดเป็น too-few จะไม่มีการยื่นข้อเสนอ
   จากนั้นจะเป็น **`improve-stronger-model`** (`ask_user`):
   `nmt-forge use-model <preset> --config config.json --answer yes` (หรือ
   `not-now`), พรีเซ็ต `byt5-small` หรือ `byt5-small-lowmem`
   ([models](#models)) ช่องสำหรับคำตอบคือ `try_it` โดย `yes` จะเขียนทับ
   โมเดลของคอนฟิกใหม่ (โดยยังคงงบเวลาของชุมชนไว้) และขั้นตอนถัดไปจะทำการเทรน
   โมเดลนั้น; `not-now` จะไม่เปลี่ยนแปลงสิ่งใด ทั้งสองกรณีจะถูกบันทึกลงในบัญชีบันทึก
   (`model-change`) และข้อเสนอจะกลับมาอีกครั้งหลังจากผ่านรอบในลักษณะนี้ไปอีกสองรอบเท่านั้น
   สำหรับ MCP คำว่า "not now" ในที่นี้คือคำตอบ `try_it: "not-now"`;
   `declined: true` จะถูกปฏิเสธในขั้นตอนนี้
   ([MCP](/docs/agents/mcp#not-now)) `why` ของข้อเสนอนี้จะไม่บอกว่าประโยคที่เพิ่มขึ้น
   ไม่ได้ช่วยอะไร: เมื่อชุด dev เล็กเกินกว่าจะมองเห็นการพัฒนาของรอบการเทรน จะระบุว่า *"อาจมีการพัฒนา
   เล็กๆ น้อยๆ ซ่อนอยู่"*; มิฉะนั้น จะระบุว่ารอบการเทรน *"ไม่พบการเปลี่ยนแปลงที่ประโยค dev
   สามารถมองเห็นได้ (ประมาณ X คะแนน chrF++ ขึ้นไป): แต่ละรอบอาจเพิ่มคะแนนได้น้อยกว่านั้น
   หรือไม่เพิ่มขึ้นเลย"* — ใกล้จุดสูงสุดของเส้นโค้งการเรียนรู้ รอบการเทรนจะเพิ่มคะแนน chrF++
   ได้ประมาณครึ่งจุด ซึ่งต่ำกว่าระดับที่ประโยค dev จำนวน 200 ประโยคจะมองเห็นได้
   **หมายเหตุ** `--answer` มีค่าเริ่มต้นเป็น `yes`: โปรดส่งคำตอบของชุมชนอย่างชัดเจนเสมอ

Rails จะเป็นตัวขับเคลื่อนส่วนที่เหลือของรอบการทำงาน (`champollion improve …`): `nmt-forge
wishlist` จะเขียนแผ่นรายการสิ่งที่น่าจะช่วยได้มากที่สุด (โดยค่าเริ่มต้นคือ 40 หัวข้อกระตุ้น อย่าง
น้อยหนึ่งในสี่จะเปิดกว้างไว้; คำศัพท์ที่โมเดลไม่เคยเห็นมาก่อนจะขอประโยคสองหรือ
สามประโยคสำหรับแต่ละคำ โดยแต่ละประโยคต้องสื่อความหมายต่างกัน — คำที่พบเพียงครั้งเดียว
ในการฝึกฝนมักแทบจะไม่ถูกเรียนรู้
([การวัดผล](/docs/agents/measurement#what-the-wishlist-steers-on))) `nmt-forge analyze` จะแจกแจงคะแนน chrF++ ของชุดพัฒนาตามประเภท
ของประโยค และ `nmt-forge grow-dev` จะเพิ่มประโยคฝึกซ้อมของผู้พูดภาษาเข้าสู่
ชุดพัฒนาภายใต้ชื่อเดียวกัน — โดยต้องไม่เป็นแถวที่มีอยู่ในชุดพัฒนาอยู่แล้ว และต้องไม่เป็น
แถวที่มีข้อความต้นทางอยู่ในชุดทดสอบหรือชุดปิดผนึก ประเภทของประโยคจะชี้นำ
wishlist ก็ต่อเมื่อประโยคนั้นได้คะแนนต่ำกว่าประเภทอื่นอย่างเห็นได้ชัดเท่านั้น
([การวัดผล](/docs/agents/measurement#what-the-wishlist-steers-on))
`nmt-forge draft-newer` (รันโดย `champollion improve sheet`) จะสุ่มแถวครึ่งหนึ่ง
ของแผ่นตรวจสอบถัดไปให้ร่างด้วยโมเดลอีกตัวหนึ่ง โดยไม่ระบุเครื่องหมาย เพื่อให้
ผู้พูดภาษาตัดสินโมเดลทั้งสองแบบไม่เปิดเผยชื่อ
([การวัดผล](/docs/agents/measurement#the-speakers-marks)): นั่นคือโมเดลล่าสุด
ที่ฝึกฝนเสร็จเมื่อไม่ได้เป็นโมเดลที่ใช้งานอยู่ (รอบดังกล่าวไม่ได้ถูกนำไปใช้งาน) หรือหลังจาก
มีการเลื่อนขั้น จะเป็นโมเดลที่โมเดลปัจจุบันเข้ามาแทนที่ ทั้งนี้ `--json`
จะระบุว่าใช้โมเดลใด (`relation`: `newer` หรือ `replaced`, `null` เมื่อไม่มีโมเดลอื่น
และทุกแถวมาจากโมเดลที่ใช้งานอยู่) พร้อมด้วย `other`, `in_use`, คู่ประโยค
การฝึกฝนที่อยู่เบื้องหลังแต่ละโมเดล (`other_pairs`, `in_use_pairs`) และ `n`;
ส่วนรายการ `draft-newer` ใน ledger จะบันทึกข้อมูลเดียวกันนี้ไว้ วิธีการส่งต่องานในแต่ละรอบ:
[การให้คำแนะนำ](/docs/agents/coaching)

## ข้อมูลสังเคราะห์และการแปลย้อนกลับ

- `nmt-forge synth <pack> --out <file>` จะเรียกใช้ตัวสร้างข้อมูล (generator) ของ language pack
  Forge ไม่ได้จัดส่งแพ็กภาษามาให้ในตัว แต่ละแถวจะได้รับการตรวจสอบและประทับตรา `synthetic: true`
- ไฟล์สังเคราะห์จะนำไปฝึกเป็นเลนที่มีแท็กกำกับใน `config.json`
  (`data.synthetic`, `{"path", "tag": "<synth>"}`) หากข้อมูลชนิดใดชนิดหนึ่งเกิน 15% การรัน
  จะถูกปฏิเสธ เว้นแต่ใน config จะระบุ `mix.synthetic_sample`;
  `nmt-forge sample --cap 0.15 --key kind` จะสุ่มตัวอย่างตามขีดจำกัดที่กำหนดไว้
- **การแปลย้อนกลับ (Back-translation) ไม่มีคำสั่งเฉพาะ** แต่เป็นฟังก์ชันไลบรารี
  (`nmt_forge.training.backtranslation.backtranslate`): คุณจัดเตรียมโมเดล
  ย้อนกลับมาเอง; ระบบจะคัดกรองข้อความภาษาเดียวเทียบกับชุดข้อมูลที่ลงทะเบียนไว้ทั้งหมด
  ก่อน แล้วแท็กผลลัพธ์เป็น `<bt>`; จากนั้นผลลัพธ์จะนำไปฝึกเป็นเลนข้อมูล
  สังเคราะห์ โดยไม่มีตัวกรองคุณภาพทำงานกับข้อมูลนี้ และจะปฏิเสธ `config.data.monolingual`
- **หมายเหตุ** ข้อความภาษาเดียวถือเป็นข้อมูลของชุมชนเช่นเดียวกับข้อมูลอื่น: ข้อกำหนดใน sidecar
  จะมีผลบังคับใช้ และโมเดลย้อนกลับที่เป็น LLM แบบโฮสต์จะส่งข้อมูลนี้ไปยังผู้ให้บริการ
  ([กฎเกี่ยวกับข้อมูล](/docs/agents/data-rules))

|---|---|---|
| `cpu-tiny` ทำคะแนน chrF++ บนชุดพัฒนาได้ระหว่าง 5 ถึง 30 | โมเดลถูกออกแบบมาให้อ่อนแอ: เป็น phrasebook สำหรับวลีที่เหมือนกับข้อมูลฝึกฝนของมัน | เพิ่มคู่ประโยคจริงให้มากขึ้น; บน Apple silicon หรือ GPU ให้ใช้ `byt5-small` (`nmt-forge use-model byt5-small`; `byt5-small-lowmem` ในกรณีที่ GPU มี VRAM 8–15 GB) |
| "ทำงานได้ดีบนเทมเพลต แต่แย่บนข้อความจริง" | กฎ R7 (transfer plateau): dev loss แตะจุดต่ำสุดก่อนเช็กพอยต์สุดท้าย และเพิ่มขึ้น 5% หรือมากกว่า กฎนี้จะทำงานเมื่อมีการเพิ่มขึ้นดังกล่าว ไม่ว่า dev chrF++ จะเป็นอย่างไร — ให้อ่านควบคู่กับคะแนนบนชุดพัฒนา | เพิ่มคู่ประโยคจริงให้มากขึ้น แสดงโดย `nmt-forge lint <run-manifest.json>` ไม่ใช่จากการส่งออกโมเดล |
| คะแนนดูดีเกินไป | มีข้อมูลชุดทดสอบที่ซ้ำหรือเกือบซ้ำอยู่ในข้อมูลฝึกฝน; หรือแถวส่วนใหญ่ในชุดทดสอบมีคู่แฝดอยู่ในข้อมูลฝึกฝน (R4-recall-not-translation อยู่ที่ครึ่งหนึ่งหรือมากกว่า) | ใช้ `leak-audit --drop-test-twins` เพื่อสร้างไฟล์ที่ปลอดจากคู่แฝด; รายงานคะแนนทั้งแบบที่มีและไม่มีคู่แฝด |
| ความแตกต่างระหว่างสองโมเดลน้อยมาก | ช่วงความเชื่อมั่นกว้างเกินไป (R5-low-power, ช่วงความเชื่อมั่นกว้างกว่า 8 จุด) | `nmt-forge compare` (การทดสอบแบบจับคู่); สำหรับรอบการทำงาน ให้ใช้ `compare-runs` ขยายขนาดชุดพัฒนา |
| รอบการทำงานระบุว่า "มีประโยคในชุดพัฒนาน้อยเกินไปที่จะบอกได้" (`too-few`) | ชุดพัฒนามีประโยคน้อยกว่า 50 ประโยค: ไม่มีการเปรียบเทียบใดตัดสินได้ในจุดนี้ | ไม่ต้องแก้ไขสิ่งใด: แผ่นงานถัดไปจะผสมผลงานร่างของทั้งสองโมเดลแบบไม่เปิดเผยชื่อ และคะแนนของผู้พูดภาษาจะเป็นผู้ตัดสิน; หนึ่งในสองแถวของแผ่นงานจะเป็นแถวฝึกซ้อมจนกว่าชุดพัฒนาจะมีครบ 50 ประโยค |
| รอบการทำงานระบุว่า "ไม่มีความเปลี่ยนแปลงที่วัดผลได้" | ชุดพัฒนาเล็กเกินกว่าจะมองเห็นการพัฒนาของแต่ละรอบ | ขยายขนาดชุดพัฒนาจากประโยคฝึกซ้อมของผู้พูดภาษา (`grow-dev` ขับเคลื่อนโดย `champollion improve prepare`) |
| การฝึกฝนถูกปฏิเสธ: `[disk-room] this computer has … free` | ดิสก์มีพื้นที่ไม่พอสำหรับเก็บเช็กพอยต์ของรอบการรัน | `nmt-forge tidy` จะแสดงรายการพื้นที่ที่โมเดลของรอบก่อนหน้าสามารถคืนได้; รัน `nmt-forge tidy --yes` เมื่อบุคคลนั้นยินยอม; หรือเพิ่มพื้นที่ว่างจากที่อื่น ใช้ `--skip-disk-check` เฉพาะเมื่อบุคคลนั้นตัดสินใจว่าการประเมินขนาดผิดพลาด |
| รอบการรันไม่สามารถเอาชนะเกณฑ์พื้นฐานของพจนานุกรมได้ | การฝึกฝนไม่ได้เรียนรู้สิ่งใดเพิ่มเติมจากที่รายการคำศัพท์มีให้อยู่แล้ว | เพิ่มคู่ประโยคให้มากขึ้น; ตรวจสอบความครอบคลุมของเกณฑ์พื้นฐาน; ชี้แจงข้อเท็จจริงนี้แก่ชุมชน |
| ชุดพัฒนาอิ่มตัวแล้ว | ขอบเขตล่างของช่วงความเชื่อมั่นอยู่ที่ 99% ของเพดานคะแนน | ใช้ชุดพัฒนาที่ยากขึ้น; คะแนนไม่สามารถเพิ่มขึ้นไปกว่านี้ได้แล้ว |
| ถูกปฏิเสธก่อนเริ่มการฝึกฝน | ดูแถว "ฝึกฝน" ด้านบน; `preflight run` จะระบุชื่อแต่ละเกตที่ไม่ผ่านพร้อมวิธีแก้ไข | ปฏิบัติตามวิธีแก้ไข หากขาด training extra: `uv tool install --reinstall --python 3.12 'nmt-forge[hf]'` (หรือ `pip` ลงใน Python ของ forge เอง) |
| หยุดทำงานเนื่องจากหมดเวลาจริง (wall clock) | การรันที่คาดการณ์ไว้เกินงบประมาณที่ตั้งไว้ (24 ชั่วโมงหากไม่ได้กำหนดไว้) | ใช้โมเดลที่เล็กลงหรือลดจำนวนรอบ epoch หรือใช้งบประมาณเวลาที่ชุมชนกำหนด (`model.time_budget_hours`) |
| งานเบื้องหลังล้มเหลว | `nmt-forge jobs` แสดง `crashed`, `stalled`, `deadline`, `lost` หรือ `refused` | อ่าน `stderr.log` ใน `.forge/jobs/<name>/` และแก้ไขข้อผิดพลาด; จากนั้นฝึกฝนใหม่อีกครั้ง หรือทำงานต่อจากเช็กพอยต์ล่าสุดเมื่อ `status` ระบุชื่อ `--resume` |
| การฝึกฝนหยุดรอและไม่ยอมเริ่ม | มีการฝึกฝนอื่นกำลังทำงานอยู่บนคอมพิวเตอร์เครื่องนี้; งานนี้จึงถูกจัดเข้าคิวต่อท้าย (`queued_behind`) | รอสักครู่: งานจะเริ่มต้นขึ้นเองโดยอัตโนมัติ ห้ามสั่งเริ่มงานอื่นซ้ำ |
| ประโยคยาวถูกตัดทอน | ขีดจำกัดความยาว: `status` แจ้งเตือนพร้อมจำนวนนับ (คู่ประโยคที่ถูกตัดในการฝึกฝน, ประโยคในชุดพัฒนาที่ถูกตัดตั้งแต่แรกนำเข้า, คำแปลที่หยุดลงเมื่อถึงขีดจำกัด) | แบ่งประโยคยาวออกเป็นท่อนๆ; หรือเพิ่ม `model.max_src`, `model.max_tgt` และ `decode.max_new_tokens` (การฝึกฝนที่ยาวนานขึ้น) |
| คำแปลออกมาเป็นชิ้นส่วนที่ไม่รู้จัก (`cpu-tiny`) | คลังคำศัพท์ถูกเรียนรู้จากแถวข้อมูลการฝึกฝนเท่านั้น | เพิ่มคู่ประโยคที่ใช้คำเหล่านั้นให้มากขึ้น; หรือใช้ `byt5-small` ซึ่งอ่านข้อมูลในระดับไบต์ |

## การจำแนกประเภทความล้มเหลว

Forge สร้างขึ้นจากบัญชีรายการข้อผิดพลาดที่โปรเจกต์ฝึกโมเดลมักหลอกตัวเอง โดย
สรุปแล้ว — "บังคับใช้" (enforced) หมายถึงเครื่องมือจะปฏิเสธการทำงาน:

| กลุ่มปัญหา | ความล้มเหลว | การจัดการในโค้ด |
|---|---|---|
| ข้อมูลรั่วไหล (Leakage) | มีคำตอบอยู่ในชุดฝึกสอน; ข้อความที่เกือบซ้ำกัน; ประโยคถอดความที่คร่อมอยู่ระหว่างการแบ่งชุดข้อมูล; เทมเพลตที่เชื่อมโยงกัน | บังคับใช้ (leak audit, split guard) ทั้งนี้ข้อความเทมเพลตที่เป็นชุดเดียวกันจะถูกเก็บไว้และนับจำนวน |
| การปนเปื้อนของ dev/test | การเลือกเช็กพอยต์บนชุดทดสอบ; การใช้ sealed set ซ้ำสองครั้ง; การคิดคะแนนทดสอบโดยไม่มีการคาดการณ์; การคาดการณ์หลังจากเปิดอ่านข้อมูลแล้ว | บังคับใช้ (dev fence, eval ledger, preregistration) |
| Tokenizer และระบบการสะกดคำ | Tokenizer ไม่สามารถเขียนตัวอักษรของภาษานั้นได้; การสะกดคำหลายรูปแบบปะปนกัน | ไม่มีการตรวจสอบสำหรับ tokenizer; ส่วนการสะกดคำที่ปะปนกันจะตรวจแบบ lint เฉพาะเมื่อมีการระบุไว้ใน config |
| ข้อมูลสังเคราะห์ | การควบคุมสัดส่วนข้อมูลสังเคราะห์; early stopping ที่ตัดการรันที่มีข้อมูลสังเคราะห์มากเกินไป; โมเดลล่มสลาย (collapse); การแปลย้อนกลับที่ป้อนข้อผิดพลาดซ้ำเติมตัวเอง | บังคับใช้เกณฑ์ขั้นต่ำของ early-stopping; ส่วนที่เหลือจะตรวจแบบ lint หรือติดแท็กกำกับ |
| ความครอบคลุม (Coverage) | คำศัพท์ขาดหายไปสำหรับระดับภาษา (register) นั้นๆ | ตรวจแบบ lint เมื่อมีปลั๊กอินรายงานความครอบคลุม |
| การวัดผล | ผลต่าง (delta) แคบกว่าช่วงความเชื่อมั่นของมัน; ตัวเลขลอยๆ เพียงค่าเดียวที่ไม่โปร่งใส; การคำนวณมาตรวัดภายนอกเครื่องมือประเมินผล | บังคับใช้: ทุกคะแนนต้องมีช่วงความเชื่อมั่นกำกับและต้องคำนวณมาจากเครื่องมือประเมินผล |
| การถอดรหัส | ผลลัพธ์ถูกตัดทอน; การเลือกเช็กพอยต์จากค่า loss แทนที่จะเป็นผลลัพธ์ที่สร้างจริง | บังคับใช้: decode headroom, generation-metric selection; มีการนับจำนวนการตัดความยาวและแจ้งเตือน |
| กระบวนการทำงาน | คีย์การกำหนดค่าที่ไม่รู้จัก; ข้อมูลที่ระบุว่า do-not-train; การรันที่ทำงานเตลิดจนควบคุมไม่ได้ (runaway runs) | บังคับใช้ |

ช่องว่างที่ทราบและยังไม่มีโค้ดจัดการ: ความครอบคลุมของ tokenizer, คุณภาพของการแปลย้อนกลับ,
การตัดทอนตามระดับภาษา, อัตราส่วนระหว่างข้อมูลจริง (gold) กับข้อมูลสังเคราะห์, ความแปรปรวนระหว่างค่า seed ต่างๆ

## ผลลัพธ์สำหรับโปรแกรม

`--json` จะส่งออกเอกสาร JSON เพียงฉบับเดียวไปยัง stdout การปฏิเสธจะเป็น
`{"error": {"type", "guard", "message", "why", "fix", "how_to_get", "text"}}`
และออกด้วย exit 2 (`details` จะถูกเพิ่มเข้ามาสำหรับการปฏิเสธเรื่อง split และ dev-fence) ส่วน exit 1 คือข้อผิดพลาด
ที่ไม่คาดคิด `nmt-forge run` จะสิ้นสุดด้วย `RUN EXIT <code>` (0, 1, 2 หรือ
130); `run --detach` จะส่งคืน 0 พร้อมกับเอกสารของงาน `nmt-forge status
--json` is `{"snapshot", "advice": {"state", "next_command", "why", "ready",
"blockers", "warnings", "answers"}}`
