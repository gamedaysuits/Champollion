# จากการวัดประสิทธิภาพสู่การใช้งานจริง: เส้นทางการแก้ไขหลังการแปลด้วยเครื่อง

> **สรุปสั้น ๆ** คะแนนในตารางจัดอันดับไม่ใช่ผลิตภัณฑ์ เส้นทางจาก "วิธีนี้ได้คะแนน 0.78" ไปสู่ "สำนักงานชุมชนเผยแพร่เอกสารในภาษานั้นทุกสัปดาห์" ผ่านกระบวนการเดียวเท่านั้น: เครื่องสร้างร่างแปล ผู้พูดภาษาที่คล่องแคล่วตรวจแก้ไข และเผยแพร่เฉพาะข้อความที่ผ่านการแก้ไขแล้วเท่านั้น เกณฑ์คุณภาพทุกข้อในข้อกำหนดของเราถูกปรับเทียบให้เหมาะกับกระบวนการนี้ — ไม่ใช่สำหรับผลลัพธ์จากเครื่องที่ไม่ผ่านการตรวจสอบ ซึ่งเราไม่แนะนำสำหรับภาษาใด ๆ บนแพลตฟอร์มนี้

บางครั้งมีคนถามว่าวิธีการแปลจะ "ดีพอที่จะใช้ได้เลย" เมื่อใด สำหรับภาษาที่ Network นี้ให้บริการ คำถามนั้นมีกับดักซ่อนอยู่ คำตอบที่ตรงไปตรงมาคือ เกณฑ์ที่ควรมุ่งไปไม่ใช่ "ดีพอที่จะเผยแพร่โดยไม่ต้องตรวจสอบ" — แต่คือ **"ดีพอที่การตรวจแก้ร่างแปลนั้นเร็วกว่าการแปลใหม่ตั้งแต่ต้น"** เกณฑ์นั้นต่ำกว่ามาก วัดได้ และเมื่อผ่านเกณฑ์นี้ได้ก็จะเปลี่ยนแปลงสิ่งที่สำนักงานแปลของชุมชนสามารถผลิตได้ในหนึ่งสัปดาห์

## กระบวนการทำงานตั้งแต่ต้นจนจบ

```
 English source document
        │
        ▼
 Machine draft  ←  a benchmarked, community-owned method
        │
        ▼
 Fluent-speaker post-edit  ←  the human gate; nothing skips it
        │
        ▼
 Published text  ←  carries human approval, not a machine score
        │
        ▼
 (Optional, community-controlled) corrections become
 data that improves the next version of the method
```

สามสิ่งที่ควรสังเกต:

1. **เครื่องไม่เคยเผยแพร่เอง** หน่วยผลลัพธ์คือร่างแปล การตรวจแก้ไขของผู้พูดภาษาไม่ใช่การประกันคุณภาพที่ต่อท้ายในตอนสุดท้าย — มันคือตัวกระบวนการทำงานเอง
2. **เวลาของผู้พูดภาษาคือทรัพยากรที่ต้องเพิ่มประสิทธิภาพ** วิธีหนึ่งดีกว่าอีกวิธีหนึ่งก็ต่อเมื่อทำให้ผู้พูดภาษาต้องแก้ไขน้อยลง งานวิจัยเกี่ยวกับการแก้ไขหลังการแปลด้วยเครื่องสำหรับภาษาที่มีทรัพยากรเพียงพอพบอย่างสม่ำเสมอว่าเร็วกว่าการแปลใหม่ตั้งแต่ต้นเมื่อคุณภาพ MT อยู่ในระดับปานกลาง (Plitt & Masselot 2010; Green, Heer & Manning 2013 ทั้งคู่อ้างอิงพร้อมลิงก์ใน [Translation Is Not Revitalization](/docs/network/perspectives/translation-is-not-revitalization)) ว่าสิ่งนี้จะเป็นจริงสำหรับภาษาแบบ polysynthetic หรือไม่นั้น คือสิ่งที่การวัดประสิทธิภาพมีไว้เพื่อค้นหา — เราถือว่ามันเป็นสมมติฐานที่ต้องตรวจสอบเป็นรายภาษา ไม่ใช่สิ่งที่สันนิษฐานไว้ล่วงหน้า
3. **วงจรป้อนกลับเป็นของชุมชน** เอกสารที่ผ่านการแก้ไขทุกฉบับเป็นข้อมูลสำหรับการฝึกและการสอนที่มีศักยภาพ — และเป็นของชุมชน เพื่อนำกลับมาใช้ (หรือไม่ก็ได้) ตามเงื่อนไขของตนเองภายใต้กฎ[อธิปไตยข้อมูล](/docs/network/sovereignty/data-sovereignty) กลไกป้อนกลับเป็นเป้าหมายการออกแบบของแพลตฟอร์ม แต่ยังไม่ได้สร้างขึ้น ดู [Reporting Errors and Owning Corrections](/docs/network/perspectives/reporting-errors-and-owning-corrections) สำหรับวิธีที่การแก้ไขและที่มาของข้อมูลมีแผนจะทำงาน

## ความหมายของระดับคุณภาพสำหรับการใช้งานจริง

ตารางจัดอันดับให้คะแนนวิธีการต่าง ๆ บนพื้นฐานของเมตริกอัตโนมัติแบบผสม ([ข้อกำหนดการให้คะแนน](/docs/network/specifications/scoring)) และคะแนนจะจับคู่กับระดับที่มีชื่อเรียก นี่คือการแปลความหมายที่ตรงไปตรงมาของระดับเหล่านั้นในแง่การใช้งานประจำวัน:

| ระดับ (แบบผสม) | ความหมายสำหรับเส้นทางการแก้ไขหลังการแปล |
|---|---|
| **Baseline** (0.00–0.30) | ใช้งานไม่ได้เลย ผลลัพธ์ส่วนใหญ่ไม่ใช่ภาษาเป้าหมาย มีประโยชน์เฉพาะในฐานะจุดเริ่มต้นของการวิจัย |
| **Emerging** (0.30–0.50) | ยังไม่ใช่เครื่องมือสร้างร่างแปล มีส่วนที่ถูกต้องปรากฏขึ้น แต่ผู้พูดภาษาจะเสียเวลาแก้ไขมากกว่าการเขียนใหม่ตั้งแต่ต้น |
| **Functional** (0.50–0.70) | ระดับแรกที่การแก้ไขหลังการแปล *อาจ* เร็วกว่าการแปลใหม่ตั้งแต่ต้นสำหรับข้อความง่าย ๆ — คุ้มค่าที่จะทดลองกับผู้พูดภาษา แต่ยังไม่ควรพึ่งพา ยังคงมีข้อผิดพลาดทางสัณฐานวิทยาบ่อยครั้ง |
| **Deployable** (0.70–0.85) | ระดับเป้าหมายสำหรับกระบวนการข้างต้น: ร่างแปลที่สัณฐานวิทยาส่วนใหญ่ถูกต้องและผู้พูดภาษาที่คล่องแคล่วสามารถแก้ไขได้เร็วกว่าการแปลใหม่อย่างมีนัยสำคัญ **"Deployable" หมายถึงพร้อมใช้งาน *ในกระบวนการแก้ไขหลังการแปล* — ไม่ใช่ "เผยแพร่โดยไม่ต้องตรวจสอบ" เด็ดขาด** |
| **Fluent** (0.85–1.00) | ใกล้เคียงกับการแปลโดยมนุษย์ที่มีความสามารถ ข้อผิดพลาดน้อยและเล็กน้อย การตรวจสอบยังคงอยู่ — เพียงแต่เร็วขึ้น |

กฎความซื่อสัตย์เชิงโครงสร้างสองข้ออยู่เหนือตารางนี้ ตรงมาจาก [ข้อกำหนดการวัดประสิทธิภาพ §5 และ §7](/docs/network/specifications/benchmark#5-quality-tiers):

- **ระดับอัตโนมัติเป็นป้ายกำกับชั่วคราว ไม่ใช่คำตัดสิน** มันคือการเสนอชื่อเพื่อการตรวจสอบโดยมนุษย์ เกณฑ์จะถูกปรับเทียบใหม่เมื่อข้อมูลการตรวจสอบจากผู้พูดภาษาสะสมมากขึ้น และอาจได้ผลต่างกันสำหรับภาษาที่แตกต่างกัน
- **ไม่มีวิธีใดอ้างระดับ Deployable หรือสูงกว่าได้โดยไม่ผ่านการตรวจสอบจากชุมชน** ตัวอย่างแบบแบ่งชั้นของผลลัพธ์จะถูกส่งให้ผู้พูดภาษาสองภาษา ซึ่งให้คะแนนการแปลแต่ละรายการว่า *ปฏิเสธ / เข้าใจความหมาย / ยอมรับได้ / ดีเยี่ยม* องค์กรกำกับดูแล — ไม่ใช่ตารางจัดอันดับ — เป็นผู้ตัดสินว่าวิธีนั้นผ่านหรือไม่

เพื่อการเปรียบเทียบ เกณฑ์ [Founder's Prize](/docs/network/specifications/prizes) (แบบผสม ≥ 0.80, คำที่ถูกต้องทางสัณฐานวิทยา ≥99%, ผู้พูดภาษาให้คะแนนยอมรับได้หรือดีกว่า ≥70%) อธิบายวิธีที่ข้อผิดพลาดที่เหลืออยู่เป็น *ข้อผิดพลาดในภาษาจริง* — การผันคำผิด ไม่ใช่คำที่ประดิษฐ์ขึ้น นั่นคือสิ่งที่ "ร่างแปลที่คุ้มค่าเวลาของผู้พูดภาษา" หน้าตาเป็นอย่างไรในรูปตัวเลข

## จากวิธีที่ชนะสู่สำนักงานที่ทำงานได้จริง

สมมติว่าวิธีหนึ่งผ่านเกณฑ์เหล่านั้น ขั้นตอนที่เหลือเป็นเรื่องขององค์กร และถูกกำหนดไว้แล้วแทนที่จะปล่อยให้เป็นการด้นสด:

1. **ความเป็นเจ้าของถ่ายโอน** โค้ดของวิธีนั้นกลายเป็นทรัพย์สินขององค์กรกำกับดูแลของชุมชน — นักพัฒนาคงไว้ซึ่งสิทธิ์การระบุแหล่งที่มาและสิทธิ์การเผยแพร่ ([Ownership Transfer](/docs/network/sovereignty/ownership-transfer))
2. **วิธีนั้นกลายเป็นบริการ — บริการของชุมชน** มันถูกบรรจุเป็น plugin ที่องค์กรกำกับดูแลสามารถรันบนโครงสร้างพื้นฐานของตนเอง ควบคุมการเข้าถึงและการใช้งานที่อนุญาต ([Deploy to Production](/docs/network/getting-started/deploy-to-production)) หากชุมชนเลือกที่จะนำเสนอในเชิงพาณิชย์ นั่นคือธุรกิจของชุมชนในทุกความหมาย — Champollion ไม่รับส่วนแบ่ง ([How the Work Is Funded](/docs/network/sovereignty/economic-model))
3. **นักแปลนำไปใช้ในงานประจำวัน** สำนักงานแปลชี้กระบวนการเอกสารที่มีอยู่ไปยัง API ของวิธีนั้น: ข้อความต้นฉบับเข้า ร่างแปลออก แก้ไข เผยแพร่ ข้อความที่เผยแพร่มีชื่อและอำนาจของนักแปล — เครื่องเป็นเพียงเครื่องมือบนโต๊ะทำงานของพวกเขา เหมือนพจนานุกรม

## สถานะปัจจุบัน

พูดตรง ๆ: เส้นทางทั้งหมดถูกกำหนดไว้ตั้งแต่ต้นจนจบ และสร้างขึ้นบางส่วนแล้ว ระบบประเมิน เมตริก run card และตารางจัดอันดับสาธารณะมีอยู่แล้ว คลังข้อมูลการพัฒนา Plains Cree และรางวัลที่ยังดำเนินอยู่มีอยู่แล้ว แพลตฟอร์มการ deploy มีอยู่แล้ว อินเทอร์เฟซการตรวจสอบของชุมชน แซนด์บ็อกซ์การประเมิน และวงจรป้อนกลับข้อความที่แก้ไขแล้วถูกกำหนดไว้แต่ยังไม่พร้อมใช้งาน — ข้อกำหนดระบุว่าเป็นแผนงาน และเราก็ระบุเช่นกัน ยังไม่มีวิธีใดที่ผ่านเส้นทางทั้งหมดจากการวัดประสิทธิภาพสู่การใช้งานจริงในชุมชน การเดินทางนั้นคือนิยามความสำเร็จของโครงการ ซึ่งเป็นเหตุผลที่เราจะไม่อ้างสิ่งนั้นก่อนเวลา

## สิ่งนี้หมายความว่าอะไรสำหรับคุณ

:::info[หากคุณเป็นสมาชิกชุมชน]
ป้าย "Deployable" บนลีดเดอร์บอร์ดไม่ได้หมายความว่าเครื่องจักรจะเผยแพร่เนื้อหาในภาษาของคุณโดยไม่มีการดูแล — แต่หมายความว่าตัวสร้างแบบร่างอาจพร้อมที่จะ *ออดิชัน* ให้กับนักแปลของคุณ ตามเงื่อนไขของคุณ โดยมีผู้พูดภาษาของคุณเป็นผู้ตัดสิน (และได้รับค่าตอบแทน — ดู [วิธีที่ผู้พูดได้รับค่าตอบแทน](/docs/network/perspectives/how-speakers-get-paid)) หากชุมชนของคุณมีสำนักงานแปล คำถามที่ควรนำมาหารือกับเราคือ: "โครงการนำร่องจะมีหน้าตาอย่างไร และใครจะเป็นผู้ตรวจสอบผลลัพธ์?"
:::

:::info[หากคุณเป็นนักวิจัย]
กรอบแนวคิดการแก้ไขหลังการแปลเปลี่ยนสิ่งที่ควรวัด: เวลาที่ใช้จนได้ข้อความที่ยอมรับได้โดยมีผู้พูดเข้ามามีส่วนร่วม ไม่ใช่แค่คะแนนรวม เมตริกของ Network เป็นตัวแทนสำหรับสิ่งนั้น ([ข้อกำหนดการให้คะแนน §1](/docs/network/specifications/scoring)) และการศึกษาการแก้ไขหลังการแปลเฉพาะภาษาสำหรับภาษาที่มีโครงสร้างทางสัณฐานวิทยาซับซ้อนยังคงเป็นช่องว่างการวิจัยที่เปิดอยู่ ซึ่งโครงสร้างพื้นฐานนี้ได้รับการออกแบบมาเพื่อรองรับ
:::

:::info[หากคุณเป็นผู้พัฒนา]
ปรับให้เหมาะสมสำหรับผู้แก้ไข ไม่ใช่เมตริก วิธีการที่สร้างคำจริงพร้อมการผันรูปที่ผิดพลาดเป็นครั้งคราวสามารถแก้ไขได้ในไม่กี่วินาทีโดยผู้พูด แต่วิธีการที่สร้างรูปแบบที่ดูน่าเชื่อถือแต่ผิดพลาดจะทำให้กระบวนการทำงานทั้งหมดเสียหาย — นั่นคือเหตุผลที่ความถูกต้องทางสัณฐานวิทยาถูกกำหนดเป็นเงื่อนไขที่เข้มงวดมากที่นี่ เริ่มต้นที่ [ส่งวิธีการ](/docs/network/getting-started/submit-a-method) และอ่าน [Method Interface](/docs/network/specifications/methods) เพื่อทำความเข้าใจสิ่งที่คุณจะต้องส่งมอบหากคุณชนะ
:::
