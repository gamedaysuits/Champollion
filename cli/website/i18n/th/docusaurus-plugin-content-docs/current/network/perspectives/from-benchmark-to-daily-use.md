# จากการวัดประสิทธิภาพสู่การใช้งานจริง: เส้นทางการแก้ไขหลังการแปลด้วยเครื่อง

> **โดยสรุป** คะแนนบนลีดเดอร์บอร์ดไม่ใช่ตัวผลิตภัณฑ์ เส้นทางจาก "วิธีนี้ได้คะแนน chrF++ 47.5" ไปสู่ "สำนักงานบริหารชนเผ่า (band office) เผยแพร่เอกสารในภาษานั้นได้ทุกสัปดาห์" ต้องผ่านเวิร์กโฟลว์เพียงรูปแบบเดียวเท่านั้น นั่นคือ เครื่องสร้างฉบับร่าง ผู้พูดภาษาได้อย่างคล่องแคล่วตรวจสอบแก้ไข และมีเพียงข้อความที่ผ่านการตรวจแก้แล้วเท่านั้นที่จะได้รับการเผยแพร่ เกณฑ์วัดคุณภาพทุกข้อในข้อกำหนดของเราได้รับการปรับเทียบให้สอดคล้องกับเวิร์กโฟลว์ดังกล่าว ไม่ใช่สำหรับการเผยแพร่ผลลัพธ์ของเครื่องโดยไม่มีมนุษย์ควบคุม ซึ่งเป็นสิ่งที่เราไม่รับรองสำหรับภาษาใดๆ บนแพลตฟอร์มนี้

บางครั้งมีคนถามว่าวิธีการแปลจะ "ดีพอที่จะใช้ได้เลย" เมื่อใด สำหรับภาษาที่ Network นี้ให้บริการ คำถามนั้นมีกับดักซ่อนอยู่ คำตอบที่ตรงไปตรงมาคือ เกณฑ์ที่ควรมุ่งไปไม่ใช่ "ดีพอที่จะเผยแพร่โดยไม่ต้องตรวจสอบ" — แต่คือ **"ดีพอที่การตรวจแก้ร่างแปลนั้นเร็วกว่าการแปลใหม่ตั้งแต่ต้น"** เกณฑ์นั้นต่ำกว่ามาก วัดได้ และเมื่อผ่านเกณฑ์นี้ได้ก็จะเปลี่ยนแปลงสิ่งที่สำนักงานแปลของชุมชนสามารถผลิตได้ในหนึ่งสัปดาห์

## กระบวนการทำงานตั้งแต่ต้นจนจบ

```
 English source document
        │
        ▼
 Machine draft  ←  a benchmarked, community-owned method
        │
        ▼
 Fluent-speaker post-edit  ←  the human gate; nothing skips it
        │
        ▼
 Published text  ←  carries human approval, not a machine score
        │
        ▼
 (Optional, community-controlled) corrections become
 data that improves the next version of the method
```

สามสิ่งที่ควรสังเกต:

1. **เครื่องไม่เคยเผยแพร่เอง** หน่วยผลลัพธ์คือร่างแปล การตรวจแก้ไขของผู้พูดภาษาไม่ใช่การประกันคุณภาพที่ต่อท้ายในตอนสุดท้าย — มันคือตัวกระบวนการทำงานเอง
2. **เวลาของผู้พูดภาษาคือทรัพยากรที่ต้องเพิ่มประสิทธิภาพ** วิธีหนึ่งดีกว่าอีกวิธีหนึ่งก็ต่อเมื่อทำให้ผู้พูดภาษาต้องแก้ไขน้อยลง งานวิจัยเกี่ยวกับการแก้ไขหลังการแปลด้วยเครื่องสำหรับภาษาที่มีทรัพยากรเพียงพอพบอย่างสม่ำเสมอว่าเร็วกว่าการแปลใหม่ตั้งแต่ต้นเมื่อคุณภาพ MT อยู่ในระดับปานกลาง (Plitt & Masselot 2010; Green, Heer & Manning 2013 ทั้งคู่อ้างอิงพร้อมลิงก์ใน [Translation Is Not Revitalization](/docs/network/perspectives/translation-is-not-revitalization)) ว่าสิ่งนี้จะเป็นจริงสำหรับภาษาแบบ polysynthetic หรือไม่นั้น คือสิ่งที่การวัดประสิทธิภาพมีไว้เพื่อค้นหา — เราถือว่ามันเป็นสมมติฐานที่ต้องตรวจสอบเป็นรายภาษา ไม่ใช่สิ่งที่สันนิษฐานไว้ล่วงหน้า
3. **วงจรป้อนกลับเป็นของชุมชน** เอกสารที่ผ่านการแก้ไขทุกฉบับเป็นข้อมูลสำหรับการฝึกและการสอนที่มีศักยภาพ — และเป็นของชุมชน เพื่อนำกลับมาใช้ (หรือไม่ก็ได้) ตามเงื่อนไขของตนเองภายใต้กฎ[อธิปไตยข้อมูล](/docs/network/sovereignty/data-sovereignty) กลไกป้อนกลับเป็นเป้าหมายการออกแบบของแพลตฟอร์ม แต่ยังไม่ได้สร้างขึ้น ดู [Reporting Errors and Owning Corrections](/docs/network/perspectives/reporting-errors-and-owning-corrections) สำหรับวิธีที่การแก้ไขและที่มาของข้อมูลมีแผนจะทำงาน

## สิ่งที่คะแนนบนลีดเดอร์บอร์ดบอกได้และบอกไม่ได้

ลีดเดอร์บอร์ดจะจัดอันดับวิธีต่างๆ ตามแนวทางของแวดวง MT: โดยใช้ **chrF++** (0–100) ระดับคลังข้อมูล (corpus-level) พร้อมช่วงความเชื่อมั่น 95% และ sacreBLEU signature โดยแสดงผลร่วมกับ BLEU, spBLEU, TER และ COMET รวมถึงรายงานผลการวินิจฉัย เช่น การยอมรับของ FST แยกต่างหาก ([ข้อกำหนดการให้คะแนน](/docs/network/specifications/scoring#how-runs-are-scored)) การที่วิธีหนึ่งจะดีกว่าอีกวิธีหนึ่งในชุดประเมินเดียวกันหรือไม่นั้น ตัดสินโดยการทดสอบนัยสำคัญแบบจับคู่ (paired significance test) ไม่ใช่การกวาดตามองตัวเลขสองตัว ([การทดสอบนัยสำคัญ](/docs/network/specifications/significance))

สิ่งที่ข้อมูลนี้บอกชุมชนได้คือ: วิธีใดให้ผลลัพธ์ที่ใกล้เคียงกับคำแปลอ้างอิงที่เชื่อถือได้มากกว่า และความแตกต่างระหว่างสองวิธีนั้นมีจริงหรือไม่ ส่วนสิ่งที่ข้อมูลนี้บอกคุณไม่ได้คือ: ฉบับร่างนั้นคุ้มค่ากับเวลาของผู้พูดภาษาหรือไม่ ค่า chrF++ ที่เท่ากันมีความหมายแตกต่างกันไปในแต่ละภาษาและแต่ละชุดประเมิน ดังนั้นจึงไม่มีคะแนนอัตโนมัติใดในที่นี้ที่ใช้เป็นป้ายกำกับระดับคุณภาพได้ ในอดีต Network เคยแมปค่าคะแนนรวมถ่วงน้ำหนัก (weighted composite) เข้ากับระดับขั้นที่ตั้งชื่อไว้ ("functional", "deployable", …) แต่ป้ายกำกับเหล่านั้นถูกยกเลิกไปแล้ว ส่วนหนึ่งเป็นเพราะระบบที่สร้างประโยคที่ถูกต้องประโยคเดิมซ้ำๆ สำหรับทุกอินพุตกลับถูกติดป้ายกำกับว่า "functional" ([เหตุผลที่ยกเลิกคะแนนรวม](/docs/network/specifications/scoring#why-the-composite-was-retired))

จากนี้คือกฎแห่งความโปร่งใสทางโครงสร้างสองข้อ จาก [ข้อกำหนดเกณฑ์มาตรฐาน §7](/docs/network/specifications/benchmark#7-human-validation):

- **คะแนนคือการเสนอชื่อเพื่อรับการตรวจสอบโดยมนุษย์ ไม่ใช่คำตัดสินขั้นสุดท้าย** ค่า chrF++ ที่สูงทำให้วิธีนั้นคุ้มค่าต่อการนำไปทดลองนำร่องร่วมกับผู้พูดภาษา แต่มิได้หมายความว่าพร้อมใช้งานแล้ว
- **การตรวจสอบจากชุมชนเท่านั้นที่จะบอกได้ว่าวิธีดังกล่าวพร้อมสำหรับเวิร์กโฟลว์การตรวจแก้หลังการแปล (post-editing) หรือไม่** ตัวอย่างแบบแบ่งชั้น (stratified sample) ของผลลัพธ์จะถูกส่งไปยังผู้พูดสองภาษา ซึ่งจะให้คะแนนคำแปลแต่ละรายการเป็น *ปฏิเสธ (reject) / พอเข้าใจใจความ (gist) / ยอมรับได้ (acceptable) / ยอดเยี่ยม (excellent)* โดยองค์กรกำกับดูแล — ไม่ใช่ลีดเดอร์บอร์ด — จะเป็นผู้ตัดสินว่าวิธีนั้นจะได้ผ่านไปยังขั้นถัดไปหรือไม่

สำหรับการเปรียบเทียบ เงื่อนไขของ [Founder's Prize](/docs/network/specifications/prizes) (เกณฑ์ขั้นต่ำของ chrF++, มีคำที่ถูกต้องตามหลักสัณฐานวิทยา ≥99% เป็นเกณฑ์คัดกรอง, ≥70% ได้รับการประเมินจากผู้พูดภาษาว่ายอมรับได้หรือดีกว่า) อธิบายถึงวิธีที่ข้อผิดพลาดที่ยังหลงเหลืออยู่นั้นเป็น *ข้อผิดพลาดในภาษาจริง* เช่น การผันคำผิด ไม่ใช่การสร้างคำขึ้นมาเองอย่างไร้ความหมาย นั่นคือหน้าตาของ "ฉบับร่างที่คุ้มค่ากับเวลาของผู้พูดภาษา" ในรูปแบบของตัวเลข และคำตัดสินของผู้พูดภาษาคือเงื่อนไขชี้ขาด

## จากวิธีที่ชนะสู่สำนักงานที่ทำงานได้จริง

สมมติว่าวิธีหนึ่งผ่านเกณฑ์เหล่านั้น ขั้นตอนที่เหลือเป็นเรื่องขององค์กร และถูกกำหนดไว้แล้วแทนที่จะปล่อยให้เป็นการด้นสด:

1. **ความเป็นเจ้าของถ่ายโอน** โค้ดของวิธีนั้นกลายเป็นทรัพย์สินขององค์กรกำกับดูแลของชุมชน — นักพัฒนาคงไว้ซึ่งสิทธิ์การระบุแหล่งที่มาและสิทธิ์การเผยแพร่ ([Ownership Transfer](/docs/network/sovereignty/ownership-transfer))
2. **วิธีนั้นกลายเป็นบริการ — บริการของชุมชน** มันถูกบรรจุเป็น plugin ที่องค์กรกำกับดูแลสามารถรันบนโครงสร้างพื้นฐานของตนเอง ควบคุมการเข้าถึงและการใช้งานที่อนุญาต ([Deploy to Production](/docs/network/getting-started/deploy-to-production)) หากชุมชนเลือกที่จะนำเสนอในเชิงพาณิชย์ นั่นคือธุรกิจของชุมชนในทุกความหมาย — Champollion ไม่รับส่วนแบ่ง ([How the Work Is Funded](/docs/network/sovereignty/economic-model))
3. **นักแปลนำไปใช้ในงานประจำวัน** สำนักงานแปลชี้กระบวนการเอกสารที่มีอยู่ไปยัง API ของวิธีนั้น: ข้อความต้นฉบับเข้า ร่างแปลออก แก้ไข เผยแพร่ ข้อความที่เผยแพร่มีชื่อและอำนาจของนักแปล — เครื่องเป็นเพียงเครื่องมือบนโต๊ะทำงานของพวกเขา เหมือนพจนานุกรม

## สถานะปัจจุบัน

กล่าวอย่างตรงไปตรงมา: เส้นทางฉบับสมบูรณ์ได้รับการระบุข้อกำหนดไว้ตั้งแต่ต้นจนจบ และถูกสร้างขึ้นแล้วบางส่วน ชุดเครื่องมือประเมินผล (evaluation harness), เมตริก, run cards และลีดเดอร์บอร์ดสาธารณะมีพร้อมใช้งานแล้ว; แซนด์บ็อกซ์สำหรับประเมินผลถูกสร้างขึ้นแล้วแต่เพิ่งได้รับการซักซ้อมด้วยวิธีจำลองขนาดเล็ก (toy method) เท่านั้น; คลังข้อมูลสำหรับพัฒนาภาษา Plains Cree มีอยู่แล้วในส่วนต้นน้ำ (upstream); มีการเสนอรางวัล แต่ยังไม่มีการเปิดรับสมัคร; แพลตฟอร์มการนำไปใช้งานจริง (deployment platform) มีพร้อมแล้ว ส่วนอินเทอร์เฟซสำหรับการตรวจสอบโดยชุมชนและวงจรป้อนกลับของข้อความที่แก้ไขแล้วได้รับการระบุข้อกำหนดไว้แต่ยังไม่เปิดดำเนินการ — ข้อกำหนดระบุว่าเป็นสิ่งที่วางแผนไว้ และเราก็ระบุเช่นนั้นเช่นกัน ยังไม่มีวิธีใดผ่านเส้นทางทั้งหมดตั้งแต่เกณฑ์มาตรฐานไปจนถึงการใช้งานจริงในชุมชนทุกๆ วัน เส้นทางดังกล่าวคือนิยามความสำเร็จของโครงการนี้ และนั่นคือเหตุผลที่เราจะไม่รีบอ้างความสำเร็จก่อนเวลาอันควร

## สิ่งนี้หมายความว่าอะไรสำหรับคุณ

:::info[หากคุณเป็นสมาชิกของชุมชน]
คะแนนลีดเดอร์บอร์ดที่สูงไม่เคยหมายความว่าเครื่องจะเผยแพร่เอกสารในภาษาของคุณโดยปราศจากการควบคุมดูแล — แต่มันหมายความว่าตัวสร้างฉบับร่างอาจพร้อมที่จะรับการ *ทดสอบคัดเลือก (audition)* สำหรับนักแปลของคุณ ภายใต้เงื่อนไขของคุณ โดยมีผู้พูดภาษาของคุณเป็นผู้ตัดสิน (และได้รับค่าตอบแทน — ดูที่ [ผู้พูดภาษาได้รับค่าตอบแทนอย่างไร](/docs/network/perspectives/how-speakers-get-paid)) หากชุมชนของคุณมีสำนักงานแปล คำถามสำคัญที่คุณสามารถสอบถามเราได้คือ: "โครงการนำร่องจะมีรูปแบบอย่างไร และใครจะเป็นผู้ตรวจสอบผลลัพธ์?"
:::

:::info[หากคุณเป็นนักวิจัย]
กรอบการทำงานแบบตรวจแก้หลังการแปล (post-editing) เปลี่ยนสิ่งที่มีคุณค่าต่อการวัดผล: นั่นคือเวลาที่ใช้จนได้ข้อความที่ยอมรับได้ (time-to-acceptable-text) โดยมีผู้พูดภาษาอยู่ในกระบวนการ ไม่ใช่เพียงแค่ chrF++ เมตริกของ Network เป็นเพียงตัวแทนสำหรับสิ่งนั้น ([ข้อกำหนดการให้คะแนน §1](/docs/network/specifications/scoring)) และการศึกษาการตรวจแก้หลังการแปลในแต่ละภาษาสำหรับภาษาที่มีความซับซ้อนทางสัณฐานวิทยาถือเป็นช่องว่างทางการวิจัยที่โครงสร้างพื้นฐานนี้ได้รับการออกแบบมาเพื่อรองรับ
:::

:::info[หากคุณเป็นผู้พัฒนา]
ปรับให้เหมาะสมสำหรับผู้แก้ไข ไม่ใช่เมตริก วิธีการที่สร้างคำจริงพร้อมการผันรูปที่ผิดพลาดเป็นครั้งคราวสามารถแก้ไขได้ในไม่กี่วินาทีโดยผู้พูด แต่วิธีการที่สร้างรูปแบบที่ดูน่าเชื่อถือแต่ผิดพลาดจะทำให้กระบวนการทำงานทั้งหมดเสียหาย — นั่นคือเหตุผลที่ความถูกต้องทางสัณฐานวิทยาถูกกำหนดเป็นเงื่อนไขที่เข้มงวดมากที่นี่ เริ่มต้นที่ [ส่งวิธีการ](/docs/network/getting-started/submit-a-method) และอ่าน [Method Interface](/docs/network/specifications/methods) เพื่อทำความเข้าใจสิ่งที่คุณจะต้องส่งมอบหากคุณชนะ
:::
