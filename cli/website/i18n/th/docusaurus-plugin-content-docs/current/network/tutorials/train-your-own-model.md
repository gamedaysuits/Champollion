# คุณต้องการฝึกโมเดลของตัวเองใช่ไหม

นี่คือคำแนะนำทีละขั้นตอนฉบับสมบูรณ์ในการเทรนโมเดลแปลภาษาด้วยเครื่อง (machine translation) สำหรับ
ภาษาที่มีทรัพยากรน้อย (low-resource language) — ตั้งแต่ "ฉันพูดภาษานี้ได้แต่แทบไม่มีชุดข้อมูลเลย"
ไปจนถึงโมเดลที่คุณสามารถรายงานผลได้อย่างตรงไปตรงมา, นำไปให้บริการแก่แอปของคุณเองผ่าน
champollion CLI และส่งเข้าร่วม [Network](/docs/network/) การเทรนเป็นเพียง
ขั้นตอนหนึ่งของการเดินทางที่ยาวไกลกว่านั้น (ค้นหาสิ่งที่มีอยู่, ประเมินทางเลือกต่างๆ, สร้าง
สิ่งที่ดีกว่า, พิสูจน์ผลลัพธ์, นำไปใช้งานจริง); [สร้าง MT สำหรับ
ภาษาของคุณ](/docs/build-mt-for-your-language) คือภาพรวมของกระบวนการทั้งหมดนี้
เนื้อหานี้เขียนขึ้นสำหรับผู้เริ่มต้น และตั้งอยู่บนวิธีปฏิบัติงานยุคใหม่:
**คุณสั่งการ coding agent** (Claude Code, OpenAI Codex, Cursor, OpenCode,
Google Antigravity หรือเครื่องมือที่คล้ายกัน) และ agent จะเป็นผู้เรียกใช้เครื่องมือต่างๆ

แต่ละขั้นตอนด้านล่างมีรูปแบบเดียวกัน:

- 🗣️ **บอก agent ของคุณ** — สิ่งที่ต้องขอ เป็นภาษาธรรมดา
- 🛠️ **สิ่งที่เครื่องมือทำ** — สิ่งที่ [nmt-forge](/docs/network/getting-started/training-honestly) รันแทนคุณ และ **guardrail** ที่ดักจับข้อผิดพลาดคลาสสิกก่อนที่มันจะสร้างความเสียหาย
- 👀 **วิธีอ่านผลลัพธ์** — ลักษณะของ "ผลดี" และสิ่งที่ควรระวัง

:::info[ก่อนอื่น ทำความเข้าใจคำศัพท์]
หากคำอย่าง *dev set*, *decoding*, *chrF++*, *leakage* หรือ *round-trip verification* ยังไม่คุ้นเคย ให้อ่าน
[**MT Training in Plain Language**](/docs/network/context/mt-training-concepts)
ก่อน — หน้านั้นนิยามทุกคำที่ใช้ที่นี่พร้อมตัวอย่างประกอบ หน้านี้จะอ้างอิงคำเหล่านั้นทั้งหมด
:::

:::note[ความสุจริตคือคุณสมบัติ ไม่ใช่อุปสรรค]
เครื่องมือนี้มีความเห็นที่ชัดเจนโดยตั้งใจ guardrail ของมันทำให้ข้อผิดพลาดจริงที่วัดได้จากโปรเจกต์จริงกลายเป็นกระบวนการอัตโนมัติ — เพื่อให้เส้นทางที่สุจริตเป็นค่าเริ่มต้น และทางลัดที่ไม่สุจริต **จะถูกปฏิเสธพร้อมข้อความที่ระบุวิธีแก้ไข** เมื่อคุณเห็นการปฏิเสธในคู่มือนี้ นั่นคือเครื่องมือกำลังทำหน้าที่ของมัน และคุณต้องการให้มันทำเช่นนั้น
:::

## สิ่งที่คุณต้องมีก่อนเริ่มต้น

- **Coding agent** ที่มีสิทธิ์เข้าถึงเทอร์มินัลและระบบไฟล์ ซึ่งทำหน้าที่เป็นผู้ขับเคลื่อนหลัก
- **ประโยคแปลจริงบางส่วน** สำหรับคู่ภาษาของคุณ — แม้จะมีเพียงไม่กี่
  ร้อยคู่ที่มนุษย์แปลขึ้นมาก็เป็นจุดเริ่มต้นที่ใช้ได้จริง หนังสือเรียนสองภาษา, คลังข้อมูล
  ของชุมชน, บันทึกสาธารณะที่มีการแปล, สื่อการเรียนรู้ เน้นคุณภาพมากกว่า
  ปริมาณ
- **มีก็ดีแต่ไม่บังคับ:** ข้อความภาษาเดี่ยวในภาษาเป้าหมายของคุณ,
  พจนานุกรมสองภาษา, หนังสือไวยากรณ์อ้างอิงที่ตีพิมพ์แล้ว และโปรแกรมวิเคราะห์
  ทางสัณฐานวิทยา (FST) คุณ**ไม่**จำเป็นต้องมีสิ่งเหล่านี้ครบทั้งหมดเพื่อเริ่มต้น — เครื่องมือจะแจ้ง
  ให้คุณทราบอย่างแน่ชัดว่ามีอะไรอยู่บ้างและสิ่งใดจะปลดล็อกความสามารถใดได้
- **พลังประมวลผล (Compute):** คอมพิวเตอร์แล็ปท็อป กลไกควบคุม (guardrails), การแบ่งข้อมูล (splitting), การสังเคราะห์ (synthesis), การตรวจสอบการรั่วไหล (auditing) และ
  การให้คะแนน ทั้งหมดทำงานบน CPU ได้ รวมถึงการเทรนโมเดลเริ่มต้น (ทรานส์ฟอร์เมอร์ขนาดเล็ก
  ที่เทรนขึ้นใหม่ตั้งแต่ต้น) ด้วยเช่นกัน GPU จะจำเป็นก็ต่อเมื่อคุณเลือกพรีเซ็ต
  ขนาดใหญ่ที่สุด (`nllb-600m`) — ดู [ขั้นตอนที่ 5](#step-5--train)

> 🗣️ **บอก agent ของคุณว่า:** *"ติดตั้ง nmt-forge พร้อมแพ็กเกจเสริมสำหรับการเทรน
> (`python3 -m pip install 'nmt-forge[hf]'`) และตรวจสอบว่าคำสั่ง `nmt-forge` ทำงานได้
> เรากำลังจะเทรนโมเดลแปลภาษาอังกฤษ → \<your language\>
> อย่างตรงไปตรงมา"*

```bash
python3 -m pip install 'nmt-forge[hf]'     # Python 3.11+; brings mt-eval-harness, the scorer
```

แพ็กเกจเสริม `[hf]` คือสแตกสำหรับการเทรน (torch, transformers, accelerate,
tokenizers, sentencepiece, peft); ใช้ wheel แบบ CPU-only ได้ ไม่มีปัญหา ไม่จำเป็น
ต้องใช้อะไรอื่นอีก — ไม่ต้องโคลนที่เก็บโค้ดของ Champollion คำสั่งทุกคำสั่งรับพารามิเตอร์ `--json`
(เอกสาร JSON หนึ่งชุดบน stdout; หากปฏิเสธการทำงานจะส่งคืนเป็น `{"error": {…, "why",
"fix"}}` with exit code 2), and `nmt-forge status` จะระบุคำสั่งถัดไปให้
ในทุกจุดของขั้นตอน

Agent ของคุณสามารถเรียกใช้เครื่องมือ `get_training_guardrails` ของ Champollion MCP server (ไม่ต้องระบุอาร์กิวเมนต์; มีตัวเลือกเสริม `topic`)
เพื่อโหลดกฎเกณฑ์ฉบับเต็ม — กลไกควบคุมทั้งสิบข้อและข้อผิดพลาดที่แต่ละข้อช่วยป้องกัน —
เข้าสู่ context ของตัวมันเองก่อนที่จะเขียนคำสั่งใดๆ หากคุณเป็นผู้ควบคุม agent
ให้สั่งให้ agent ทำขั้นตอนนี้เป็นอันดับแรก

## ขั้นตอนที่ 1 — เลือกภาษาและดูว่ามีอะไรอยู่จริงๆ

ทุกโปรเจกต์เริ่มต้นด้วยการถาม index ว่าภาษานั้น *มี* อะไรอย่างสุจริต

> 🗣️ **บอก agent ของคุณ:** *"รัน `nmt-forge discover` สำหรับรหัส ISO 639-3 ของภาษาเป้าหมายของฉัน และสรุปว่ามีข้อมูลอะไรอยู่และขาดอะไรไป"*

```bash
nmt-forge discover nav        # Navajo, as an example
```

🛠️ **หน้าที่ของเครื่องมือนี้** เครื่องมือจะอ่าน **การ์ด (card)** ประจำภาษาของ Champollion — ซึ่งเป็น
แหล่งความจริงจุดเดียวสำหรับข้อมูลทั้งหมดที่ทราบเกี่ยวกับภาษานั้น — แล้วรายงาน
ระบบการเขียน, โปรแกรมวิเคราะห์ทางสัณฐานวิทยา, พจนานุกรม, คลังข้อมูลภาษา และชุดข้อมูลประเมินผลที่มีการบันทึกไว้
จากนั้นจะจัดวางภาษานั้นลงบน **บันไดสินทรัพย์ (asset ladder)** (การ์ดนำมาจาก
ไดเรกทอรีที่คุณระบุด้วย `--cards-dir`, สำเนาในเครื่องหรือ
`node_modules/champollion` หรือดัชนีการ์ดสาธารณะ — มีการแคชไว้ จึงทำงาน
แบบออฟไลน์ได้หลังจากดึงข้อมูลครั้งแรก หากออฟไลน์และไม่มีแคช ให้ส่งออกการ์ดด้วย
`champollion network card <code> --json` ไปยังไดเรกทอรีแล้วส่ง `--cards-dir` เข้าไป)

```
THE ASSET LADDER — what this language can do TODAY:
  ✓ rung 1: parallel text → train with every guard (no pack needed)
  ? rung 2: monolingual text → the tagged backtranslation lane
  ? rung 3: dictionary (+ grammar) → a cited template pack is worth building
  ? rung 4: morphological analyzer → round-trip-VERIFIED synthesis
  ? rung 5: LYSS referee → the language's own metric in selection
```

👀 **วิธีอ่านผลลัพธ์** เครื่องหมาย `✓` คือสิ่งที่คุณทำได้ทันที; เครื่องหมาย `?`
คือขั้นบันไดที่ยังรอสินทรัพย์อยู่ ข้อสำคัญคือ **การไม่มีระบุอยู่บนการ์ดหมายถึง
*ยังไม่ทราบข้อมูล* ไม่ได้หมายความว่า "ภาษานี้ไม่มีอะไรเลย"** การ์ดที่มีข้อมูลน้อยถือเป็นคำเชิญชวน
ให้คุณช่วยเพิ่มสิ่งที่คุณรู้ ไม่ใช่ทางตัน — และแม้แต่การ์ดที่ว่างเปล่าก็ยังให้
ลูปการเทรนที่มีระบบป้องกันแบบเต็มรูปแบบบนขั้นที่ 1 ได้ การ์ดที่มีข้อมูลสมบูรณ์ (เช่น ภาษา Plains Cree) จะเชื่อมต่อ
ขั้นบนๆ ให้โดยอัตโนมัติ: ชุดประเมินผลจะถูกตั้งค่าสถานะ **ห้ามใช้เทรนโดยเด็ดขาด (NEVER TRAIN ON THIS)** มาให้ทันที
และระบบตัดสิน (referee) เฉพาะของภาษานั้นจะพร้อมเชื่อมต่อใช้งาน ขั้นที่ 5 จะถูกทำเครื่องหมายถูกเฉพาะเมื่อ
แพ็กเกจของระบบตัดสินนั้นได้รับการติดตั้งในเครื่องนี้แล้วเท่านั้น มิฉะนั้นจะแสดงเป็น ✗ *UNAVAILABLE*
พร้อมคำสั่งติดตั้ง — และระบบตัดสินจะไม่ถูกโหลดมาใช้กับชุดทดสอบเฉพาะในเครื่องหรือ
ชุดทดสอบแบบปิดผนึก (sealed test set) โดยเด็ดขาด เนื่องจากระบบอาจส่งคำศัพท์ไปค้นหาบนบริการภายนอกได้

จากนั้น scaffold โปรเจกต์:

> 🗣️ **บอก agent ของคุณ:** *"Scaffold โปรเจกต์ด้วย `nmt-forge init` สำหรับคู่ภาษานี้ และอ่าน `NEXT_STEPS.md` ที่มันสร้างขึ้นให้ฉันฟัง"*

```bash
nmt-forge init nav --dir my-nav-mt --pair eng-nav
cd my-nav-mt                     # run every later command from here
```

🛠️ คำสั่งนี้จะสร้างพื้นที่ทำงาน (ไดเรกทอรี `.forge/` ที่กลไกควบคุมทุกตัว
จะเข้ามาตรวจสอบ), **starter config** และเอกสารสรุปงาน `NEXT_STEPS.md` ที่เขียนขึ้นสำหรับ *คุณ
และ agent ของคุณ* — ลำดับคำสั่ง, บันไดสินทรัพย์สำหรับภาษาของคุณ และ
สิ่งที่ไม่สามารถต่อรองได้ นี่คือแผนที่นำทางสำหรับทุกขั้นตอนด้านล่างนี้ เส้นทางไฟล์ใน config เป็นแบบ
relative ดังนั้นโปรดรัน forge จากภายในไดเรกทอรีของโปรเจกต์

`init` ยังทำหน้าที่เลือก **โมเดล** ที่คุณจะใช้เทรน (`--model` ซึ่งเขียนออกมาเป็น
ตัวเลขที่ระบุชัดเจนใน `config.json`): ค่าเริ่มต้นคือ `cpu-tiny`, `cpu-finetune --base
<hf-id>`, or `nllb-600m` [ขั้นตอนที่ 5](#step-5--train) จะอธิบายทางเลือกเหล่านี้ หาก
ภาษาของคุณยังไม่มีการ์ด คำสั่ง `nmt-forge init <code> --no-card --name "<name>"`
ก็ยังคงสร้างโครงสร้างโปรเจกต์ให้ได้ — โดยข้อเท็จจริงทุกอย่างบนการ์ดจะถูกบันทึกเป็น "ไม่ทราบข้อมูล" ไม่มีการกุข้อมูลขึ้นมาเอง

## ขั้นตอนที่ 2 — ชี้ไปที่ analyzer และพจนานุกรม (ถ้ามี)

ขั้นตอนนี้เกี่ยวกับ **ขั้นที่ 3–4** ของ ladder หากภาษาของคุณไม่มี analyzer ให้ข้ามไปที่ [ขั้นตอนที่ 4](#step-4--split-your-real-data-safely) — คุณจะฝึกบนข้อมูลจริง (และ backtranslated) เพียงอย่างเดียว ซึ่งเป็นเส้นทางที่ถูกต้องสมบูรณ์

หาก analyzer และพจนานุกรม *มีอยู่จริง* สิ่งเหล่านี้จะปลดล็อกความสามารถในการ *ผลิต* ข้อมูลฝึกที่ผ่านการตรวจสอบแล้ว — ซึ่งเป็นตัวช่วยที่ทรงพลังที่สุดสำหรับภาษาที่มีข้อความคู่ขนานน้อย

> 🗣️ **บอก agent ของคุณ:** *"Card ระบุว่ามี morphological analyzer และพจนานุกรมสำหรับภาษานี้ ดึงข้อมูลตามคำแนะนำการติดตั้งบน card ชี้ language pack ไปที่สิ่งเหล่านั้นผ่าน environment variable ที่ระบุไว้ และยืนยันว่า analyzer round-trip คำที่รู้จักสองสามคำได้"*

🛠️ **สิ่งที่เครื่องมือทำ — และขอบเขตที่มันจะไม่ข้าม** Analyzer (FST) และพจนานุกรมเป็น **เครื่องมือแยกต่างหากที่ผู้ใช้ดึงมาเองภายใต้ใบอนุญาตของตัวเอง** suite **ไม่เคยรวมหรือแจกจ่ายซ้ำ** — มันชี้ให้คุณรู้ว่าสิ่งเหล่านั้นมาจากไหนและใบอนุญาตของมันคืออะไร และคุณดึงมาเอง นี่ไม่ใช่ระบบราชการ: ทรัพยากรภาษาจำนวนมากมีข้อจำกัดด้านสิทธิ์และอำนาจอธิปไตยที่แท้จริง และเครื่องมือเคารพสิ่งเหล่านั้นโดยการออกแบบ

เนื้อเยื่อเชื่อมต่อคือ **language pack**: plugin ขนาดเล็กที่ปรับ analyzer, พจนานุกรม, กฎการสะกด และ template ประโยคที่อ้างอิงไวยากรณ์ *ของคุณ* ให้เข้ากับ engine suite **ไม่ได้** จัดส่ง pack ใดๆ เอง — pack อยู่กับภาษาของมัน (เช่น Plains Cree pack อยู่ในโปรเจกต์ของตัวเองและเสียบเข้าผ่าน module path)

👀 **วิธีอ่านผลลัพธ์** คุณต้องการให้ analyzer **round-trip** ได้: สะกดรูปแบบหนึ่ง ป้อนการสะกดนั้นกลับเข้าไป และได้ grammatical tag เดิม หากทำไม่ได้ **canonicalizer** ของ pack — ฟังก์ชันเดียวที่ normalize การสะกดทุกที่ที่ component สองตัวพบกัน — อาจต้องการกฎเพิ่มเติม การทำสิ่งนี้ให้ถูกต้องมีความสำคัญ: อักขระเดียวที่ไม่ได้รับการแก้ไข (`ý` กับ `y`) เคยลบกริยาออกไป 1,375 คำจาก generation pipeline อย่างเงียบๆ เป็นเวลาหลายสัปดาห์ **funnel audit** ของเครื่องมือนับจำนวนที่รอดในแต่ละขั้นตอนอย่างแม่นยำ เพื่อให้การหายไปอย่างเงียบๆ แบบนั้นไม่สามารถซ่อนตัวได้

## ขั้นตอนที่ 3 — สังเคราะห์ข้อมูลฝึกจากกฎไวยากรณ์

ด้วย analyzer + พจนานุกรม + pack ของ template ที่อ้างอิงไวยากรณ์ คุณสามารถผลิตคู่ประโยคที่ผ่านการตรวจสอบแล้วได้หลายแสนคู่

> 🗣️ **บอก agent ของคุณ:** *"สร้างข้อมูลฝึก synthetic ด้วย `nmt-forge synth` โดยใช้ language pack ของเรา จากนั้นแสดง coverage report ให้ฉันดู"*

```bash
nmt-forge synth my_pack.module:get_pack --out data/synth.jsonl
```

🛠️ **สิ่งที่เครื่องมือทำ — emit law** ทุก row ที่ไปถึง output ต้องผ่านกฎที่ไม่มี pack ใดสามารถยกเว้นได้:

- **Round-trip verified** — ทุกคำที่สร้างขึ้นต้องผ่าน *generate → analyze → same analysis* มิฉะนั้น row นั้นจะถูกทิ้ง ไม่มีรูปแบบที่ไม่ผ่านการตรวจสอบถูก emit ออกมาเลย
- **Grammar-cited** — ทุก template ต้องอ้างอิงไวยากรณ์ที่ตีพิมพ์แล้วที่มันถอดความมา Template ที่ไม่มีการอ้างอิงไม่มีอยู่จริง code ปฏิเสธที่จะโหลดมัน
- **Coverage-checked** — template ถูกตรวจสอบกับ checklist ของปรากฏการณ์ทางไวยากรณ์ที่จำเป็น (imperative, คำถาม, การครอบครอง, inverse form…) หากปรากฏการณ์ที่ *จำเป็น* มีตัวอย่างเป็นศูนย์ การ build จะล้มเหลว นี่คือการป้องกัน trap "ประโยคล้านประโยคแต่รูปแบบเดิมๆ" — ปริมาณที่ซ่อนช่องว่างเชิงโครงสร้าง
- **Provenance-stamped** — ทุก row synthetic ถูกทำเครื่องหมาย `synthetic: true` เครื่องหมายนั้นมีความสำคัญ: registry จะ **ปฏิเสธ** การลงทะเบียน row synthetic เป็น test set ข้อมูล test ต้องเป็นข้อมูลจริงเท่านั้น

👀 **วิธีอ่านผลลัพธ์** ดูที่ coverage report สำหรับ **รายการที่จำเป็นที่มี coverage เป็นศูนย์** (ปรากฏการณ์ทางไวยากรณ์ที่ template ของคุณไม่เคยสร้างขึ้น) และที่ **kind distribution** — หาก template สองรูปแบบครอบงำ per-kind cap ของ sampler (ค่าเริ่มต้น 15%) จะปรับสมดุลใหม่เพื่อไม่ให้รูปแบบเดียวกลายเป็นครึ่งหนึ่งของประสบการณ์ของโมเดล

:::tip[ไม่มีโปรแกรมวิเคราะห์? ให้ใช้การแปลย้อนกลับ (Backtranslation) แทน]
หากคุณไม่สามารถสังเคราะห์ข้อมูลจากกฎไวยากรณ์ได้แต่มีข้อความภาษาเป้าหมายแบบ**ภาษาเดี่ยว (monolingual)**
อยู่ ให้บอก agent ของคุณให้ใช้แนวทาง **backtranslation**: กระบวนการนี้จะแปลข้อความภาษาเดี่ยวของคุณ
*กลับมาเป็น* ภาษาอังกฤษด้วยโมเดลย้อนกลับที่คุณระบุ แล้วนำผลลัพธ์แต่ละรายการมาจับคู่กับ
ประโยคภาษาเป้าหมายที่เป็นของ**จริง** ฝั่งภาษาเป้าหมายจึงยังคงเป็นภาษาแท้ตามธรรมชาติ
กระบวนการนี้เป็นการเรียกใช้ผ่านไลบรารีของ Python (`nmt_forge.training.backtranslation.backtranslate`)
ไม่ใช่คำสั่งย่อยของ CLI: agent ของคุณจะเขียนสคริปต์สั้นๆ ครอบไว้แล้วเพิ่ม
ไฟล์เอาต์พุตที่มีแท็กกำกับเข้าไปในเลน `data.synthetic` ของ config การเรียกใช้ฟังก์ชันนี้
**จะตรวจสอบการรั่วไหลของข้อความภาษาเดี่ยวก่อนเป็นอันดับแรก** — เพราะข้อความนั้นอาจแอบ*เป็น*
ข้อมูลประเมินผลของคุณอยู่ก็เป็นได้ ดูเพิ่มเติมได้ที่
[คู่มือปฏิบัติการ Back-Translation](/docs/network/tutorials/back-translation)
:::

## ขั้นตอนที่ 4 — แบ่งข้อมูลจริงอย่างปลอดภัย

คราวนี้ ให้นำคู่ประโยคของ**จริง**ของคุณมา แล้วคัดแยกประโยคที่คุณจะใช้เป็นเกณฑ์
ตัดสินทุกสิ่งทุกอย่างออกมา นี่คือจุดที่ข้อผิดพลาดร้ายแรงที่สุดซึ่งทำลายผลลัพธ์ของ
MT ภาษาที่มีทรัพยากรน้อยมักซ่อนอยู่ และเป็นจุดที่กลไกควบคุมแสดงคุณค่าได้อย่างแท้จริง

ไฟล์ของคุณสามารถเป็นรูปแบบ `.tsv` (ข้อความต้นทาง, แท็บ, ตามด้วยข้อความแปล, บรรทัดละ
หนึ่งคู่; บรรทัดที่ขึ้นต้นด้วย `# ` ถือเป็นคอมเมนต์) หรือ `.jsonl` (`{"source": …,
"target": …}` ต่อบรรทัด)

**หากคุณมีชุดทดสอบอยู่แล้ว** — ผ่านการตรวจโดยครู, ผ่านการตรวจโดยพยาบาล, หรือเป็นข้อมูลส่วนตัว —
ให้เก็บแยกเป็นไฟล์ต่างหาก, ลงทะเบียนไว้, ตรวจกรองคลังข้อมูลเทียบกับชุดทดสอบนั้น แล้วแบ่ง
เฉพาะชุดข้อมูล train และ dev เท่านั้น:

> 🗣️ **บอก agent ของคุณว่า:** *"ลงทะเบียนชุดทดสอบของเรา, ตรวจสอบการรั่วไหลของคลังข้อมูล
> เทียบกับชุดทดสอบนั้น, จากนั้นแบ่งคลังข้อมูลที่คัดกรองแล้วออกเป็น train และ dev ด้วย
> `nmt-forge split` แบบ group-disjoint โดยกำหนด seed คงที่"*

```bash
nmt-forge registry add project-test ~/teacher-test.tsv --role test
nmt-forge leak-audit ~/corpus.tsv --clean-to corpus.clean.jsonl
nmt-forge split corpus.clean.jsonl --test 0 --dev 100 --seed 42 \
    --out data/split --register project
```

**หากคุณยังไม่มี** ให้แบ่งชุดทดสอบออกจากคลังข้อมูลในขั้นตอนเดียวกันนี้:

```bash
nmt-forge split corpus.tsv --test 150 --dev 100 --seed 42 \
    --out data/split --register project
```

🛠️ **หน้าที่ของเครื่องมือ — กลไกป้องกันการแบ่งข้อมูล (split-guard)** เครื่องมือจะทำ **การแบ่งข้อมูล
แบบ group-disjoint**: คู่ประโยคใดก็ตามที่ใช้ข้อความต้นทาง *หรือ* ข้อความเป้าหมายร่วมกัน จะถูกรวมไว้ในกลุ่มเดียวกัน
และทุกกลุ่มจะถูกจัดให้อยู่ฝั่งใดฝั่งหนึ่งอย่างสมบูรณ์ จากนั้นจะ **ตรวจสอบว่าต้องไม่มีส่วนที่ซ้อนทับกันเลย (zero overlap)**
และปฏิเสธที่จะดำเนินการต่อหากพบการซ้อนทับแม้แต่จุดเดียว:

```
split corpus.clean.jsonl: 1580 rows in 1544 share-groups (largest 4)
  train 1480 · dev 100 · test 0  → data/split/
  verified: 0 shared canonical source/target keys across sides
  registered project-dev (role=dev)
```

สิ่งนี้ช่วยกำจัดการรั่วไหลแบบ **"Feed him" / "Feed her"**: แบบฝึกหัดในหนังสือเรียนจับคู่ข้อความฝึกภาษาอังกฤษทั้งสองประโยค
เข้ากับคำภาษาเป้าหมายคำเดียว (`asam`); การแบ่งข้อมูลแบบสุ่มธรรมดาจะนำประโยคหนึ่งไปไว้ใน train
และอีกประโยคที่เป็นคู่แฝดไปไว้ใน test ทำให้โมเดล "สอบผ่าน" ได้เพราะอาศัยความจำ ในโปรเจกต์จริงโปรเจกต์หนึ่ง มีข้อมูลทดสอบรั่วไหล
ด้วยวิธีนี้ถึง 17 จาก 54 แถว และได้คะแนน 83 เทียบกับ 44 สำหรับแถวที่สะอาด — ทำให้ข้อค้นพบ
ทั้งหมดที่อ้างอิงจากตัวเลขนั้นกลายเป็นโมฆะ `--register project` จะบันทึกชุด
dev (และชุด test เมื่อถูกแบ่งออกมา) เป็น `project-dev` / `project-test` — ซึ่งเป็น
ชื่อที่ starter config ชี้ไว้อยู่แล้ว — เพื่อให้คำสั่งในภายหลังทั้งหมดทราบว่าไฟล์เหล่านี้
เป็น *ชุดประเมินผลที่ห้ามนำไปเทรนโดยเด็ดขาด* เมื่อมีการลงทะเบียนชุดทดสอบไว้แล้ว
`split` จะคัดกรองไฟล์ train และ dev ที่สร้างขึ้นใหม่เทียบกับชุดทดสอบนั้นทันที ณ จุดนั้นด้วย

🛠️ **และการตรวจสอบการรั่วไหล (leak-audit)** `leak-audit` จะคัดกรองแถวข้อมูลเทียบกับชุดประเมินผล
ที่ลงทะเบียนไว้ทั้งหมด และระบุพร้อมแสดงตัวอย่างจากคลังข้อมูลของคุณเองว่าแถวใดที่จะถูก **ตัดทิ้ง** —
แถวที่ข้อความต้นทางเหมือนกับพรอมต์ทดสอบทุกประการ (แม้คำแปลจะต่างกัน), แถวที่ข้อความเป้าหมายเหมือนกับ
คำตอบทดสอบทุกประการ และแถวที่ข้อความเป้าหมายใกล้เคียงกับคำตอบทดสอบมาก (มีคำตอบนั้นรวมอยู่, เป็น
ส่วนหนึ่งของคำตอบ หรือเหมือนกันอย่างน้อย 90% เมื่อปรับลดรูปเครื่องหมายกำกับเสียงแล้ว) — และแถวใดที่
**ตั้งใจเก็บไว้**: *ประโยคแม่แบบพี่น้อง (template siblings)* ที่ใช้โครงสร้างประโยคเดียวกันแต่เปลี่ยน
คำศัพท์ (*"I see the dog"* / *"I see the cat"*) รวมถึงพรอมต์ที่ใกล้เคียงกันมากแต่มีคำตอบต่างกัน
แถวทดสอบที่มีประโยคแม่แบบพี่น้องอยู่ในชุดฝึกจะถูกทำรายการไว้ และ — เนื่องจาก starter config กำหนดค่า `eval.near_dupe_corpus`
ชี้ไปยังไฟล์ฝึกของคุณ — รายงานขั้นสุดท้ายจะให้คะแนนแถวทดสอบที่ *ไม่มี* ประโยคพี่น้อง
แยกต่างหาก เป็นคะแนน "(strict)" เพื่อให้เห็นความได้เปรียบที่ประโยคพี่น้องช่วยเพิ่มเข้ามาอย่างชัดเจน
เมื่อแถวทดสอบส่วนใหญ่มีประโยคพี่น้องและชุดทดสอบถูกกำหนดไว้ตายตัวแล้ว
`--clean-to <file> --drop-test-twins` จะช่วยลบประโยคคู่แฝดเหล่านั้นออกจากชุดฝึกด้วย (โดยจะ
รายงานชุดย่อยแบบ strict ทั้งก่อนและหลังการลบ และจะปฏิเสธการทำงานหากผลลัพธ์ทำให้ชุดฝึกว่างเปล่า)
โปรดระบุไฟล์แยกต่างหากให้คำสั่งนี้ (`corpus.notwins.jsonl`): ไฟล์นี้จะเป็นคลังข้อมูลของโมเดล
ฉบับปลอดคู่แฝด ซึ่งจะอยู่ควบคู่ไปกับไฟล์ข้อมูลทั้งหมด และ leak-audit จะปฏิเสธที่จะเขียน
ทับไฟล์ที่ config, การรัน หรือการแบ่งข้อมูลกำลังอ่านอยู่
ผลลัพธ์ที่ได้จะเป็นแบบ deterministic และจะไม่มีการพิมพ์ข้อความของตัวไฟล์
ทดสอบออกมาโดยเด็ดขาด

👀 **วิธีอ่านผลลัพธ์** คุณต้องการเห็นบรรทัด **verified: 0 shared** หากแทนที่คุณได้รับ `SplitLeakageError` อย่าลบ row ด้วยมือ — นั่นแค่สับเปลี่ยนปัญหา รัน group-disjoint split ใหม่ นั่นคือวิธีแก้ไข และข้อความ error ก็บอกเช่นนั้น

add-harness`) เครื่องมือจะประทับตราและถือว่ามันเป็นสิ่งต้องห้ามสำหรับการฝึก — **ทุก** registry benchmark ถูกทำเครื่องหมาย *do-not-train* Fine-tune บนสิ่งที่คุณมีสิทธิ์ใช้ได้อย่างถูกต้อง แต่อย่าฝึกบน test set เด็ดขาด นี่คือ
[กฎข้อเดียว](/docs/network/leaderboard/rules) ของ Network ทั้งหมด
:::

## ขั้นตอนที่ 5 — ฝึกโมเดล

ไฟล์ config เพียงไฟล์เดียวจะอธิบายการรันทั้งหมด; คำสั่งเพียงคำสั่งเดียวจะสั่งประมวลผล
อย่างทำซ้ำได้ (reproducibly) โดย `nmt-forge init` ได้สร้างไฟล์นี้เตรียมไว้ให้แล้ว

> 🗣️ **บอก agent ของคุณว่า:** *"อ่าน `config.json`, เพิ่มเลนข้อมูลสังเคราะห์เข้าไปถ้าเรา
> มีการสร้างไว้, รัน `nmt-forge preflight run --config config.json`, แก้ไขสิ่งต่างๆ ตามที่
> แจ้งเตือน, จากนั้นรัน `nmt-forge run config.json` และคอยสังเกต
> การวินิจฉัยตารางเวลา (schedule diagnostics)"*

ตัวอย่างบางส่วนจาก starter config ที่ใช้โมเดลเริ่มต้น `cpu-tiny` และมี
การเพิ่มเลนข้อมูลสังเคราะห์เข้าไป:

```jsonc
{
  "run_name": "nav-baseline",
  "workspace": ".forge",
  "data": {
    "gold": ["data/split/train.jsonl"],
    "synthetic": [{"path": "data/synth.jsonl", "tag": "<synth>"}],
    "dev": "project-dev"              // registry name, role=dev — the fence
  },
  "mix": {"gold_upweight": 20, "kind_cap": 0.15, "seed": 42},
  "regime": "auto",
  "model": {"backend": "hf-scratch", "device": "cpu", "d_model": 256,
            "layers": 3, "epochs": 60, ...},   // no time_budget_hours: init writes none
  "selection": {"metric": "generation:chrf++", "top_k": 3},
  "decode": {"max_new_tokens": 384, "headroom_factor": 1.5},
  "eval": {"battery": "project-test", "metrics": ["chrf++"],
           "near_dupe_corpus": "data/split/train.jsonl"}
}
```

**ควรเลือกโมเดลใด?** เลือกได้ตอนที่คุณรัน `init` (`--model`); ตัวเลขทุกค่าจะถูก
เขียนลงใน `config.json`:

| พรีเซ็ต | รายละเอียด | สิ่งที่ต้องใช้ | ความคาดหวังตามจริง |
|---|---|---|---|
| `cpu-tiny` (ค่าเริ่มต้น) | ทรานส์ฟอร์เมอร์ขนาดเล็ก (~6M พารามิเตอร์) ที่เทรนขึ้นใหม่ตั้งแต่ต้น; คลังคำศัพท์จะเรียนรู้จากแถวในชุด **train** เท่านั้น | CPU ของแล็ปท็อป, ไม่ต้องดาวน์โหลด | ต่ำ: สำหรับคู่ประโยค 1–2 พันคู่ ค่า chrF++ จะอยู่ที่ประมาณ 5–30 (ตัวเลขระดับบนจะได้เฉพาะกับข้อมูลที่มีรูปแบบซ้ำๆ ชัดเจนเท่านั้น) — แปลได้เฉพาะวลีและรูปแบบประโยคที่มีในข้อมูลของคุณ ไม่ใช่การแปลทั่วไป |
| `cpu-finetune --base <hf-id>` | ไฟน์จูนโมเดล Marian/opus-mt ขนาดเล็กที่ผ่านการพรีเทรนมาแล้วตามที่คุณระบุ — ให้เลือกโมเดลสำหรับคู่ภาษาที่ *มีความเกี่ยวข้องกัน* | CPU, พื้นที่ดาวน์โหลด ~300 MB | มักจะดีกว่า `cpu-tiny` เมื่อมีคู่ภาษาที่เกี่ยวข้องกันอยู่ — ให้วัดผลจริงบน dev อย่าเพิ่งด่วนสรุป |
| `nllb-600m` | NLLB-200 distilled 600M พร้อม LoRA | GPU, พื้นที่ดาวน์โหลด ~2.5 GB | จุดเริ่มต้นที่แข็งแกร่งที่สุด; หากรันบน CPU ระบบตรวจสอบเวลาจริง (wall-clock check) จะปฏิเสธการทำงานภายในไม่กี่นาที |

จุดประสงค์ของ `cpu-tiny` ไม่ได้อยู่ที่คะแนนของมัน แต่มันทำให้ลูปการทำงาน**ทั้งหมด**เกิดขึ้นได้จริง —
ทั้งแนวป้องกัน, การตรวจสอบการรั่วไหล, การทดสอบที่ลงทะเบียนไว้ล่วงหน้า, โมเดลที่ CLI สามารถเรียกใช้ได้ — เพื่อให้
โมเดลที่ดีกว่าในภายหลังสามารถนำมาใส่ในโปรเจกต์เดิมและวัดผลด้วยวิธีเดียวกันได้ทันที

`preflight` จะแสดงรายการเงื่อนไขตรวจสอบ (gate) ทั้งหมดที่การรันจะต้องผ่าน พร้อมสัญลักษณ์ ✓ หรือ ✗ และวิธีแก้ไขสำหรับแต่ละ ✗
— รวมถึงการตรวจสอบว่าได้ติดตั้งแพ็กเกจเสริมสำหรับการเทรนไว้แล้วหรือไม่
(`✗ backend-installed: … fix: python3 -m pip install 'nmt-forge[hf]'`)

```bash
nmt-forge preflight run --config config.json
nmt-forge run config.json
```

🛠️ **สิ่งที่เครื่องมือทำ — guardrail สี่ตัวพร้อมกัน**

- **การตรวจสอบการรั่วไหลก่อนเทรน (Leak-audit before training)** *ทุก* เลน — ข้อมูลมาตรฐาน (gold), ข้อมูลสังเคราะห์ และข้อความ
  ที่แปลย้อนกลับทั้งหมด — จะถูกคัดกรองเทียบกับชุดทดสอบและชุดปิดผนึกที่ลงทะเบียนไว้ *ทั้งหมด*
  การรั่วไหลของคำตอบ (พรอมต์หรือคำตอบที่เหมือนกันทุกประการ, คำตอบที่ใกล้เคียงกันมาก) และการตรงกันทั้งไฟล์
  ถือเป็นข้อผิดพลาดร้ายแรง; ประโยคแม่แบบพี่น้องจะถูกเก็บไว้และรายงานให้ทราบ
  (`--drop-test-twins` จะช่วยลบประโยคเหล่านี้ออกสำหรับชุดทดสอบที่กำหนดไว้ตายตัว)
  จะไม่มีการเทรนใดๆ จนกว่าชุดข้อมูลผสมจะสะอาดบริสุทธิ์
- **แนวป้องกันชุด Dev (Dev-fence)** การเทรน **จะปฏิเสธที่จะเริ่มทำงานหากไม่มีการลงทะเบียนชุด dev ไว้** และ
  จะเลือก checkpoint โดยอิงจากชุด dev นั้นเท่านั้น — จะไม่ใช้ชุดทดสอบโดยเด็ดขาด
  (ระบบจะตรวจสอบเนื้อหาของแถวข้อมูลในชุด dev เทียบกับชุดทดสอบด้วยซ้ำ เพื่อป้องกัน
  ลูกเล่นแบบ `cp test.jsonl dev.jsonl`) การเลือก checkpoint สามารถใช้ **dev loss** หรือ
  **เมตริกการสร้างข้อความ (generation metric)** บนชุด dev — โดยถอดรหัสชุด dev แล้วให้คะแนนเอาต์พุตจริง
  ซึ่งเป็นสัญญาณที่สะท้อนความเป็นจริงได้มากกว่า (starter config จะใช้ค่า chrF++ จากเอาต์พุต dev ที่ถอดรหัสแล้ว)
- **การตรวจสอบความสมเหตุสมผลของตารางเวลา (Schedule-sanity)** หากชุดข้อมูลผสมของคุณเน้นข้อมูลสังเคราะห์เป็นหลัก เครื่องมือจะ *คำนวณ*
  ขีดจำกัดขั้นต่ำในการหยุดเทรนจากขนาดของชุดข้อมูลผสม และประคองการเทรนให้ผ่านพ้นช่วง **ที่ราบสูง (plateau)** — ซึ่งเป็น
  ช่วงที่โมเดลเรียนรู้ข้อมูลสังเคราะห์ที่ง่ายเสร็จสิ้นแล้ว แต่ยังไม่ได้ส่งผ่านความรู้นั้นไปสู่คุณภาพที่แท้จริง
  สิ่งนี้ช่วยป้องกัน "การด่วนจบที่ครึ่งเอพอก (half-epoch death)" ซึ่งการทำ early stopping แบบไร้เดียงสาจะตัดจบการทำงานไปตั้งแต่ยังไม่ถึงหนึ่งในยี่สิบของแผนงาน
  ความถี่ในการประเมินผลชุด dev ก็คำนวณมาจากขนาดของการรันเช่นกัน
  ทำให้การรันขนาดเล็กก็ยังได้รับการประเมินผลอย่างเหมาะสม ทุกการแทรกแซงจะพิมพ์แนวโน้มของ dev-loss
  พร้อมเหตุผลประกอบด้วยภาษาธรรมดาที่เข้าใจง่าย
- **การคำนวณความถี่การสัมผัสข้อมูล + แท็กกำกับข้อมูลสังเคราะห์ (Exposure math + tagged synthetic)** ข้อมูล gold จะถูกเพิ่มน้ำหนัก (ทำซ้ำ)
  เพื่อไม่ให้ข้อมูลจริงที่มีอยู่น้อยนิดถูกกลืนหายไป; ไฟล์กำกับ (manifest) จะบันทึก **ความถี่การสัมผัสข้อมูลจริงต่อหนึ่งประโยคที่ไม่ซ้ำกัน (effective exposure per unique sentence)**
  เอาไว้ เพื่อให้การทดสอบ A/B ยังคงยุติธรรม แหล่งข้อมูลสังเคราะห์จะติดแท็กกำกับไว้; ข้อมูล gold จะไม่ติดแท็กเพื่อเป็นตัวยึดเหนี่ยวรูปแบบของผลลัพธ์

การเทรนเป็นขั้นตอนเดียวที่ต้องใช้เวลาพอสมควร Agent ของคุณควรรันขั้นตอนนี้ใน
เบื้องหลังโดยส่งเอาต์พุตไปยังไฟล์ล็อก และคอยเฝ้าดูบรรทัดข้อมูลที่สำคัญ
(`refused`, `Error`, `wall-clock`, `RUN EXIT`) แทนที่จะคอยส่งคำสั่งตรวจสอบซ้ำๆ (polling) หน้าแดชบอร์ดสด
ที่แสดงกราฟ loss พร้อมปุ่มหยุดจะเปิดขึ้นมาให้ **คุณ** ดู (ที่
`http://127.0.0.1:8377` เมื่อพอร์ตนั้นว่างอยู่) ในช่วงนาทีแรกๆ forge จะวัดความเร็วในการเทรน
และพิมพ์การประมาณการเวลาจริง (wall-clock) ออกมา เริ่มจากการประมาณการเบื้องต้น แล้วตามด้วย
การประมาณการในสภาวะคงที่ (steady-state) `init` ไม่ได้กำหนดงบประมาณเวลาไว้ให้ เพราะงบประมาณเป็นตัวเลขของคุณ
ไม่ใช่ตัวเลขที่เครื่องมือจะกุขึ้นมาเอง ให้อ่านการประมาณการเวลา พิจารณาว่าคุณยอมรับเวลาได้นานเท่าใด
แล้วเพิ่ม `"time_budget_hours": <hours>` เข้าไปใน `config.json` ใต้ส่วน `model` นับจาก
นั้นเป็นต้นไป forge จะปฏิเสธการรันที่ไม่สามารถเสร็จสิ้นภายในเวลานั้น เพื่อให้การรันที่ตั้งค่าขนาดไม่เหมาะสมล้มเหลวโดยเร็ว
จนกว่าคุณจะกำหนดไว้ จะมีเพียงเพดานความปลอดภัยของ forge เท่านั้นที่มีผลบังคับใช้: ระบบจะหยุด
การรันที่อาจกินเวลานานหลายวัน และทุกการประมาณการจะพิมพ์ระบุไว้ว่า "no budget set; … ceiling" ไม่ใช่งบประมาณที่ใครตั้งขึ้นมา

👀 **วิธีอ่านผลลัพธ์** การรันจะพิมพ์ **รายงาน dev พร้อมช่วงความเชื่อมั่น (confidence intervals)** — โดยจะ
ไม่มีเอาต์พุตที่มีแค่คะแนนลอยๆ — ตามด้วยคำสั่งถัดไป (ตัวเลข
ด้านล่างนี้เป็นเพียงตัวอย่างประกอบ):

```
dev report (95% CIs — there is no bare-score rendering):
n=100 · set=project-dev
  chrf++       21.40  [18.95, 23.90] 95% CI

NEXT: nmt-forge export .forge/runs/nav-baseline-…/run-manifest.json --out export/
```

หากคุณเห็นข้อความ `schedule-sanity` ที่อธิบายว่ามัน *รักษา* การฝึกไว้เกินจุดหยุดก่อนกำหนด นั่นคือ plateau guard กำลังทำงาน — ดีมาก run ยังเขียน **manifest** ด้วย: config hash, data file hash, seed และ derived schedule เพื่อให้ run ทั้งหมด reproducible ได้

## ขั้นตอนที่ 6 — ประเมินผลอย่างสุจริต

คุณมีโมเดลแล้ว ก่อนที่จะให้คะแนนบน test set คุณต้องเขียนสิ่งที่คาดหวัง — *ก่อน*

> 🗣️ **บอก agent ของคุณว่า:** *"เขียน preregistration สำหรับการประเมินคะแนนชุดทดสอบ —
> ระบุเมตริกที่เราคาดการณ์ ทิศทาง และส่วนต่าง พร้อมเหตุผลหนึ่งบรรทัด — จากนั้น
> สั่งส่งออกผลการรัน ซึ่งจะทำการประเมินคะแนนชุดทดสอบหนึ่งครั้ง"*

```bash
# 1. Predict BEFORE you peek — the one format is a JSON array; edit the template
nmt-forge prereg template --out predictions.json
nmt-forge prereg new run1 --eval-set project-test --predictions predictions.json

# 2. Score the test set once against that prediction, and package the model
nmt-forge export .forge/runs/<run>/run-manifest.json --prereg run1 --out export/
```

`--prereg` จะระบุชื่อ preregistration ที่ใช้ตัดสินโมเดลนี้ หากมีไฟล์เดียวสำหรับ
ชุดทดสอบ การส่งออกจะค้นหาไฟล์นั้นให้เองโดยอัตโนมัติ; แต่หากมีโมเดลที่สองพร้อมกับ
preregistration ของตัวเองบนชุดทดสอบเดียวกัน ระบบส่งออกจะไม่เดาให้ ดังนั้นโปรดระบุชื่อของแต่ละไฟล์ให้ชัดเจน

(การทำ preregistration สามารถทำเมื่อใดก็ได้ก่อนการประเมินคะแนนทดสอบครั้งแรก — `nmt-forge
status` จะร้องขอขั้นตอนนี้ก่อนเริ่มการเทรน)

🛠️ **สิ่งที่เครื่องมือทำ — anti-storytelling guards**

- **Preregistration** การประเมินคะแนนชุด **ทดสอบ (test)** ที่ลงทะเบียนไว้ จำเป็นต้องมี
  preregistration ที่เขียนขึ้น *ก่อน* การเปิดดูข้อมูลครั้งแรก ไฟล์การคาดการณ์คืออาร์เรย์
  JSON: การคาดการณ์แต่ละรายการจะระบุเมตริกและเหตุผล รวมถึงระบุทิศทาง
  เปรียบเทียบกับเกณฑ์มาตรฐาน (ตรวจสอบโดยอัตโนมัติด้วย `nmt-forge prereg check`) หรือ
  ความคาดหวังแบบข้อความอิสระที่มนุษย์เป็นผู้ตรวจสอบ แม่แบบที่ยังไม่ได้แก้ไข, Markdown และ
  ข้อความธรรมดาจะถูกปฏิเสธพร้อมแจ้งรูปแบบที่ถูกต้องและวิธีแก้ไข หากไม่มี preregistration
  การประเมินคะแนนจะ **ปฏิเสธการทำงาน** ทันที:

  ```
  [preregister] no preregistration for eval set 'project-test' at its current content hash
    why: results looked at without written-down expectations become
         post-hoc stories; ...
    fix: write one FIRST: ... — then score
  ```

  นี่คือกลไกป้องกันการนำสิ่งที่รู้ผลแล้วมาแต่งเป็นคำทำนายล่วงหน้า (postdictions — เช่น "ก็เห็นอยู่แล้วว่ามันต้องแปลเรื่องเล่ามุขปาฐะได้ดีขึ้น")
  การจดบันทึกการคาดเดาที่ *ล้มเหลว* คือสิ่งที่ทำให้การคาดเดาที่ประสบความสำเร็จมีความน่าเชื่อถือ
- **ต้องมีช่วงความเชื่อมั่น (Confidence intervals) เสมอ** ทุกคะแนนจะแสดงพร้อมค่า 95% bootstrap
  CI เสมอ; จะไม่มีเอาต์พุตที่ไร้ CI คะแนนที่เพิ่มขึ้นใน `+0.5` แต่ช่วงความเชื่อมั่นทับซ้อนกัน จะไม่ถือว่า
  ชนะเกณฑ์เดิม
- **สมุดบัญชีการประเมินผล (eval-ledger)** การอ่านชุดข้อมูลประเมินผลทุกครั้งจะถูกบันทึกลงล็อก (เขียนต่อท้ายได้อย่างเดียว
  ตรวจสอบร่องรอยการแก้ไขได้) สอบถาม `nmt-forge ledger show --set project-test` ได้ว่าชุดข้อมูลนั้นถูก "ใช้งานช้ำ"
  ไปเพียงใดแล้ว ชุดข้อมูลแบบ **ปิดผนึก (Sealed)** จะประเมินได้เพียงครั้งเดียว — ตรวจให้คะแนนหนึ่งครั้งแล้วปิดผนึกทันที (หากเรียก
  `export` ซ้ำจะถูกปฏิเสธ; ส่วน `--no-eval` จะแพ็กเกจให้โดยไม่คำนวณคะแนนใหม่)

`export` จะถอดรหัสชุดทดสอบโดยใช้ checkpoint ที่คัดเลือกมาจาก dev, ทำการประเมินคะแนน และ
ต่อท้ายด้วยส่วน **การวินิจฉัยและคำแนะนำ (Diagnosis & Recommendations)** ด้วยภาษาที่เข้าใจง่าย นอกจากนี้ยัง
เขียนผลลัพธ์ออกมาเป็น **mt-eval report** (`export/evaluation/`) เพื่อให้ `mt-eval
compare` นำโมเดลของคุณไปวางเปรียบเทียบกับวิธีอื่นๆ ที่วัดผลด้วยชุดเครื่องมือเดียวกัน
บนชุดทดสอบเดียวกันได้ และจะแพ็กเกจตัวโมเดลเอง (ขั้นตอนที่ 8) ไว้ใน `export/model/`
ซึ่งไม่มีประโยคทดสอบบรรจุอยู่ `export/evaluation/` จะมีประโยคทดสอบ
ของคุณอยู่: ห้ามคัดลอกไฟล์นี้ไปพร้อมกับโมเดลโดยเด็ดขาด และโปรดเก็บรักษาไว้ร่วมกับชุดทดสอบ `nmt-forge evaluate <run-manifest>` คือส่วนที่ให้คะแนนอย่างเดียว
สำหรับกรณีที่คุณไม่ต้องการแพ็กเกจโมเดล

👀 **วิธีอ่านผลลัพธ์** อ่านตัวเลข **พร้อมกับช่วงความเชื่อมั่นและแยกตาม
ระดับภาษา (register)**, ดูคะแนน "(strict)" หากข้อมูลฝึกของคุณใช้แม่แบบประโยค
ร่วมกับชุดทดสอบ และตรวจสอบว่า **ควรเชื่อถือเมตริกใด** ก่อนที่คุณจะ
ด่วนฉลอง หากต้องการให้คะแนนไฟล์เอาต์พุตของระบบอื่นบนชุดข้อมูลที่ลงทะเบียนชุดเดียวกัน
โดยใช้เมตริกเพิ่มเติม:

```bash
nmt-forge score --eval-set project-test --hyps decoded.txt \
    --metric chrf++ --metric comet --target-lang nav
```

`nmt-forge discover` แสดง **ความน่าเชื่อถือที่วัดได้** ของแต่ละ metric สำหรับ language family ของคุณ (จาก WMT meta-evaluation) สำหรับบาง family metric อย่าง BLEU แทบไม่สะท้อนการตัดสินของมนุษย์ในขณะที่ COMET ทำได้ สำหรับ low-resource family จำนวนมาก คำตอบที่สุจริตคือ *ไม่ได้วัด* — ในกรณีนั้น การตัดสินของเจ้าของภาษา ไม่ใช่ตัวเลขอัตโนมัติใดๆ คือ signal ที่แท้จริง ดูที่ [Metric Reliability](/docs/network/specifications/metric-reliability)

:::tip[referee ของภาษาคุณเอง]
หากภาษาของคุณมีมาตรฐาน eval แบบ LYSS (linter ที่รู้ว่า เช่น การสะกดสองแบบต่างกันเพียงแค่ตามข้อตกลง long-vowel ที่มีเอกสาร) ให้เสียบมันด้วย `--plugin` และมันจะให้คะแนนควบคู่กับ chrF++ — และยังสามารถ *เลือก* checkpoint ได้ด้วย เพื่อให้โมเดลที่ชนะคือโมเดลที่ referee ของภาษานั้นเองชอบ ทุกตัวเลขจาก plugin ก็มี confidence interval เช่นกัน
:::

## ขั้นตอนที่ 7 — ปรับปรุงซ้ำ

ตอนนี้คุณปรับปรุง — และทุกการปรับปรุงถูกวัดด้วยวิธีที่สุจริตเหมือนกัน

> 🗣️ **บอก agent ของคุณว่า:** *"ปรับเปลี่ยนสิ่งหนึ่ง — เพิ่มประเภทของแม่แบบ / เพิ่มข้อมูล
> ที่แปลย้อนกลับ / เปลี่ยนพรีเซ็ตโมเดลเป็นแบบอื่น — เทรนใหม่ และทำ A/B ทดสอบเทียบกับ
> การรันก่อนหน้านี้บนชุด dev พร้อมทดสอบนัยสำคัญทางสถิติ"*

การรันแต่ละครั้งจะพิมพ์คะแนน dev พร้อมช่วงความเชื่อมั่นออกมาอยู่แล้ว สำหรับการทดสอบ
แบบจับคู่ (paired test) ให้ถอดรหัสชุด dev จากการรันแต่ละครั้ง — `nmt-forge evaluate <run-manifest>
--config dev-eval.json --out-hyps run1-dev.jsonl`, where `dev-eval.json` คือ
สำเนา config ของคุณที่เปลี่ยน `eval.battery` เป็น `project-dev` — จากนั้น:

```bash
nmt-forge compare --eval-set project-dev \
    --hyps-a run1-dev.jsonl --hyps-b run2-dev.jsonl --metric chrf++
```

🛠️ **สิ่งที่เครื่องมือทำ** `compare` รัน **paired significance test** ไม่ใช่แค่การลบ เพื่อให้ "B ชนะ A" เป็นการอ้างที่สถิติรองรับ — ไม่ใช่ noise ปรับปรุงซ้ำบน **dev** set (นั่นคือไว้สำหรับสิ่งนั้น); เก็บ **test** set ไว้สำหรับการตรวจสอบที่ไม่บ่อยและ preregistered; เก็บ set ที่ **sealed** ไว้สำหรับตอนสุดท้าย

👀 **วิธีอ่านผลลัพธ์** การปรับปรุงจริงต้องผ่าน confidence interval *และ* significance test หากไม่ผ่าน คุณก็ยังได้เรียนรู้บางอย่าง — ว่า lever นั้นอ่อนแอกว่าที่หวัง ซึ่งเป็นสิ่งที่ควรรู้ guardrail ด้าน plateau/coverage/leak หมายความว่าตัวเลขที่คุณเปรียบเทียบน่าเชื่อถือ ดังนั้นคุณสามารถเชื่อ iteration loop ของตัวเองได้จริงๆ

lever ถัดไปที่พบบ่อย เรียงตามลำดับผลตอบแทนสำหรับภาษาที่ขาดแคลนข้อมูล:

1. **เพิ่มคู่ประโยคจริง** — สำหรับข้อมูลระดับไม่กี่พันประโยค คู่ประโยคจริงที่เพิ่มเข้ามา
   แต่ละคู่มีผลมากกว่าการตั้งค่าใดๆ ทั้งสิ้น
2. **เพิ่มความครอบคลุม (coverage)** ในการสังเคราะห์ข้อมูล — เพิ่มปรากฏการณ์ทางไวยากรณ์ที่ขาดหายไปตามที่
   รายงานความครอบคลุมได้แจ้งเตือนไว้
3. **การแปลย้อนกลับ (Backtranslation)** — แปลงข้อความภาษาเดี่ยวในภาษาเป้าหมายให้กลายเป็นคู่ประโยคสำหรับฝึกฝนเพิ่มเติม
4. **จุดเริ่มต้นที่แข็งแกร่งขึ้น** — `cpu-finetune` ร่วมกับโมเดลตั้งต้นสำหรับคู่ภาษา
   ที่เกี่ยวข้องกัน หรือ `nllb-600m` บน GPU — โดยวัดผลเทียบกับ `cpu-tiny` บน
   ชุด dev เดียวกัน
5. **หลักสูตรการเรียนรู้ (Curriculum)** — พรีเทรนด้วยข้อมูลสังเคราะห์ก่อน แล้วจึงค่อยไฟน์จูนด้วยคู่ประโยคจริง

## ขั้นตอนที่ 8 — นำไปใช้งานจริง และส่งต่อไปยัง Network

โมเดลที่ผ่านการเทรนมาอย่างตรงไปตรงมาคือสิ่งที่คุณสามารถนำไปใช้งานได้ตั้งแต่วันนี้ และเป็นสิ่งที่
[Champollion Network](/docs/network/) ถูกสร้างขึ้นมาเพื่อรองรับอย่างแท้จริง

**นำไปใช้งานด้วยตัวเอง** คำสั่ง `export` ได้ทำการแพ็กเกจโมเดลไว้ให้เรียบร้อยแล้ว: ไดเรกทอรีโมเดลที่สมบูรณ์ในตัวเอง,
`forge-model.json` (ข้อมูลโมเดลและวิธีการวัดผล),
ไฟล์กำกับปลั๊กอินของ champollion (`method.json`) และ `DEPLOY.md` ที่ระบุ
คำสั่งไว้อย่างแม่นยำ

> 🗣️ **บอก agent ของคุณว่า:** *"เปิดให้บริการโมเดลที่ส่งออก และนำไปใช้แปล
> ข้อความในแอปของเราด้วย champollion CLI"*

```bash
nmt-forge serve export/model                               # http://127.0.0.1:8378
LOCAL_API_BASE=http://127.0.0.1:8378/v1 champollion sync --method local
```

`serve` รองรับข้อกำหนด **api method** ของ champollion (`POST /translate`) และ
รูปแบบที่ **เข้ากันได้กับ OpenAI** (`/v1/chat/completions`) — ซึ่งรูปแบบหลังคือสิ่งที่
`--method local` ใช้งาน; ส่วน `DEPLOY.md` จะมีสนิปเป็ต `champollion.config.json` สำหรับ
รูปแบบแรก เครื่องมือจะรอรับการเชื่อมต่อที่ `127.0.0.1` เท่านั้น; การเปิดให้เข้าถึงผ่านเครือข่ายภายนอกจะต้องใช้
โทเค็น (`--token` หรือ `NMT_FORGE_SERVE_TOKEN`) โมเดล NMT จะแปลเฉพาะตัวข้อความและ
เพิกเฉยต่อคำสั่งสั่งการ ดังนั้นพรอมต์กำหนดน้ำเสียง, ไฟล์โค้ชชิ่ง และคลังคำศัพท์ที่ CLI
ส่งไปยังวิธีแบบ LLM จะไม่มีผลใดๆ ต่อโมเดลนี้ — และผลลัพธ์ของโมเดลจำเป็นต้องได้รับการตรวจสอบจาก
ผู้ที่พูดภาษานั้นได้อย่างคล่องแคล่วก่อนที่จะนำไปเผยแพร่สู่ผู้อ่าน

**ส่งต่อไปยัง Network**

> 🗣️ **บอก agent ของคุณ:** *"Package โมเดลนี้เป็น method และส่งไปยัง leaderboard สำหรับคู่ภาษาของเรา"*

- **[Submit a Method](/docs/network/getting-started/submit-a-method)** เปลี่ยนโมเดลของคุณให้เป็น Network entry ที่ให้คะแนนบน public reference corpora และระบุว่าเป็นของคุณ
- เนื่องจากการประเมินของคุณสะอาด — group-disjoint, dev-fenced, leak-audited, CI'd, preregistered — การส่งของคุณจะผ่านการตรวจสอบที่ทำให้ low-resource MT claim ส่วนใหญ่ล้มเหลว สถาปัตยกรรม anti-gaming (test set ลับที่ชุมชนเป็นเจ้าของ, การตรวจสอบ reproducibility, การตรวจสอบโดยเจ้าของภาษา) ไม่ใช่อุปสรรคสำหรับโมเดลที่สร้างด้วยวิธีนี้ แต่เป็นตราประทับความน่าเชื่อถือ
- หาก **รางวัล** เปิดอยู่สำหรับภาษาของคุณ method ที่ยืนหยัดและดีกว่า baseline ที่สร้างอย่างสุจริตคือสิ่งที่ sponsored pool ให้รางวัล และเมื่อ method ใช้ได้ผลสำหรับภาษาพื้นเมือง **ความเป็นเจ้าของสามารถโอนไปยังชุมชนได้** — คุณสร้างที่นี่และพวกเขา deploy มัน ตามเงื่อนไขของพวกเขา ดูที่ [Prize Specification](/docs/network/specifications/prizes) และ [Ownership Transfer](/docs/network/sovereignty/ownership-transfer)

## ภาพรวมทั้งหมด ในหนึ่งประโยค

1. **สำรวจ** สิ่งที่ภาษานั้นมีอยู่ (`discover`, `init`) — การไม่มีระบุไว้หมายถึงยังไม่ทราบข้อมูล ไม่ใช่มีค่าเป็นศูนย์
2. **ระบุตำแหน่ง** ของโปรแกรมวิเคราะห์ + พจนานุกรม หากมีอยู่ (ขั้นที่ 3–4) โดยปฏิบัติตามสัญญาอนุญาตอย่างถูกต้อง
3. **สังเคราะห์** ข้อมูลสำหรับฝึกที่ผ่านการตรวจสอบ, มีการอ้างอิง และตรวจความครอบคลุมแล้ว (`synth`) — หรือ **แปลย้อนกลับ** ข้อความภาษาเดี่ยว
4. **แบ่ง** ข้อมูลจริงแบบ group-disjoint, ตรวจกรองเทียบกับชุดทดสอบของคุณ และลงทะเบียนชุดประเมินผล (`registry add`, `leak-audit`, `split`)
5. **เทรน** ผ่าน config เดียว — ทำงานบน CPU เป็นค่าเริ่มต้น — มีแนวป้องกันชุด dev, ตรวจสอบการรั่วไหล, รู้จักรับมือช่วงที่ราบสูง (`preflight`, `run`)
6. **ประเมินผล** โดยเขียนคำคาดการณ์ไว้ล่วงหน้าเสมอ, มี CI ทุกครั้ง, ใช้เมตริกที่ถูกต้อง (`prereg`, `export`)
7. **วนซ้ำพัฒนา** ด้วยการทดสอบ A/B ที่มีการทดสอบนัยสำคัญทางสถิติ (`compare`)
8. **นำไปใช้งาน** ผ่าน CLI (`serve`) และ **ส่งผลงาน** เข้าร่วม Network — ที่ซึ่งการทำงานอย่างซื่อตรงและตรงไปตรงมาคือหัวใจสำคัญที่สุด

คุณไม่จำเป็นต้องจำสิบวิธีที่ผลลัพธ์ low-resource MT ผิดพลาด เครื่องมือทำให้เส้นทางที่สุจริตเป็นค่าเริ่มต้นและปฏิเสธทางลัดพร้อมคำอธิบาย นั่นคือแนวคิดทั้งหมด: **guardrail ดักจับข้อผิดพลาดของมือใหม่ เพื่อให้คุณสามารถมุ่งเน้นที่ภาษา**
