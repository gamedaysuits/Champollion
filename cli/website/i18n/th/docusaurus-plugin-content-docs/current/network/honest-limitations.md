# ข้อจำกัดที่ยอมรับตามความเป็นจริง

> นี่คือสิ่งที่เรา**จะไม่**อ้างเกินความเป็นจริง หากมีเนื้อหาใดในเว็บไซต์นี้ที่บ่งชี้มากกว่าที่เขียนไว้ที่นี่ ให้ถือว่าเป็นข้อผิดพลาดและ
> [แจ้งให้เราทราบ](/docs/network/perspectives/reporting-errors-and-owning-corrections)

โครงสร้างพื้นฐานสำหรับการประเมินจะได้รับความไว้วางใจก็ต่อเมื่อมีความซื่อสัตย์เกี่ยวกับขอบเขตของตนเอง
ต่อไปนี้คือข้อจำกัดของเรา ระบุไว้อย่างชัดเจนพอที่จะตรวจสอบได้

## 1. การตรวจสอบสัณฐานวิทยาเชิงลึกในปัจจุบันครอบคลุมเพียงหนึ่งคู่ภาษา

การตรวจสอบสัณฐานวิทยาด้วย FST — ซึ่งตรวจสอบว่าทุกคำในผลลัพธ์เป็นคำที่ถูกต้องตามรูปแบบของภาษาเป้าหมาย — ในทางปฏิบัติถูกกำหนดไว้สำหรับ **English → Plains Cree เท่านั้น** ตัว `GiellaLTFSTMetric` เองนั้น**เป็นแบบทั่วไป**: สามารถให้คะแนนภาษาใดก็ได้ที่มีตัววิเคราะห์ `.hfstol` ที่เผยแพร่โดย GiellaLT (Plains Cree, ภาษากลุ่ม Sámi, Finnish, Norwegian Bokmål, Inuktitut และอื่น ๆ) ดังนั้นความสามารถนี้จึงครอบคลุมในวงกว้าง แต่**ปัจจุบันมีคลังข้อมูลสำหรับการประเมินเฉพาะ Plains Cree เท่านั้น** ดังนั้น crk จึงเป็นคู่ภาษาเดียวที่ได้รับการให้คะแนนด้วย FST ในทางปฏิบัติ ทุกคู่ภาษาอื่นในตารางอันดับจะถูกให้คะแนนด้วยเมตริกพื้นผิว (chrF++, BLEU) และการตรวจสอบเชิงพฤติกรรม สัญญาณเหล่านั้นมีประโยชน์ แต่**ไม่ได้รับประกัน**ความถูกต้องทางสัณฐานวิทยา เราจะไม่อ้างการตรวจสอบสัณฐานวิทยาสำหรับภาษาใดหากไม่มีทั้ง FST และคลังข้อมูลสำหรับการประเมิน

## 2. ระดับความน่าเชื่อถือเป็นการรายงานด้วยตนเองเมื่อเปิดตัว

คะแนนส่วนใหญ่คำนวณโดยผู้มีส่วนร่วมที่รันชุดทดสอบด้วยตนเองและเผยแพร่ผลลัพธ์ **การยืนยัน**ฝั่งเซิร์ฟเวอร์ — การให้คะแนนซ้ำกับคลังข้อมูลมาตรฐานที่ SHA-pinned — มีอยู่และกำลังขยายตัว แต่ "verified" ยังไม่เป็นสากล อ่านป้ายระดับความน่าเชื่อถือในแต่ละแถว: **"self-reported" หมายความตามนั้นตรง ๆ** และเป็นค่าเริ่มต้น

## 3. การตรวจสอบโดยผู้พูดในชุมชนยังไม่เกิดขึ้น

รางวัลของเรากำหนดให้ต้องมี**การยอมรับ ≥ 70% จากผู้พูดสองภาษา** เกณฑ์นี้ถูกระบุไว้แล้ว และเครื่องมือสำหรับดำเนินการอยู่ระหว่างการพัฒนา — แต่**ยังไม่มีการตรวจสอบโดยผู้พูดในชุมชน** และ**ไม่มีคะแนนใดในเว็บไซต์นี้ผ่านเกณฑ์ผู้พูด** ตัวเลข Composite และ chrF++ เป็นสัญญาณจากเครื่อง ไม่ใช่คำตัดสินจากชุมชน

## 4. แซนด์บ็อกซ์สำหรับการประเมินมีอยู่แล้ว แต่พิธีการดูแลรักษายังไม่มี

เราดึงข้อมูลคลังข้อความ (corpora) จากแหล่งที่มาและทำการตรึงด้วย SHA (SHA-pin) และชุดข้อมูลที่แยกไว้ทดสอบ (held-out splits) จะถูกปิดผนึกไว้ เมื่อชุมชนถือครองชุดทดสอบที่เป็นความลับ วิธีการต่างๆ สามารถถูกประเมินคะแนนกับชุดทดสอบนั้นได้โดยที่ชุดข้อมูลไม่ต้องหลุดออกจากมือของพวกเขาเลย — และการประเมินผลดังกล่าวในตอนนี้มี **สองเส้นทาง** เส้นทางที่แนะนำสำหรับโมเดลนิวรัลมาตรฐานคือแบบ **declarative**: ผู้เข้าร่วมจะส่งเพียงแค่ข้อมูลเท่านั้น — น้ำหนัก (weights) แบบ safetensors + tokenizer แบบ declarative + config — และผู้จัดงานจะรันข้อมูลเหล่านี้ใน inference engine ที่เชื่อถือได้ของตนเอง (`trust_remote_code=False`, ออฟไลน์; ยืดหยุ่นเรื่องสถาปัตยกรรมเนื่องจากความปลอดภัยนั้นอยู่ในรูปแบบที่ปราศจากโค้ด ไม่ใช่ชื่อของสถาปัตยกรรม) จะไม่มีการรันโค้ดของผู้เข้าร่วมเลย ดังนั้นจึงไม่มีอะไรที่ต้องทำ sandbox; การตรวจสอบความปลอดภัยจะเป็นการตรวจสอบความถูกต้องของรูปแบบที่สามารถตัดสินได้ (นี่คือ safetensors และไม่ใช่ pickle ใช่หรือไม่? ไม่มี `trust_remote_code` ใช่หรือไม่?) ไม่ใช่ความพยายามที่จะพิสูจน์ว่าโค้ดใดๆ นั้นปลอดภัย สำหรับวิธีการที่เป็นโค้ดจริงๆ (pipelines, LLM-coached hybrids) ทางเลือกสำรองคือ **sandbox** ที่ถูกแยกออกจากเครือข่าย (การตรวจสอบแบบ static, คอนเทนเนอร์ `--network=none`, การส่งออกข้อมูลเฉพาะคะแนนเท่านั้น, และตัวเลือกการส่งผ่านไฟล์แบบ true-airgap) sandbox จะกักเก็บโค้ดที่ไม่น่าเชื่อถือไว้แทนที่จะปฏิเสธการรัน ดังนั้นมันจึงเป็นเส้นทางที่อ่อนแอกว่าอย่างตรงไปตรงมา — การรับประกันหลักของมันคือ `--network=none` (การสแกนแบบ static เชิงฮิวริสติกไม่สามารถตรวจสอบโมเดลไบนารีได้) และการเพิ่มความปลอดภัยในระดับที่ลึกกว่า (seccomp, microVMs) จะถูกเลื่อนออกไปก่อน ดู [run a sovereign contest](/docs/network/sovereignty/run-a-sovereign-contest) เพื่อดูรายละเอียดที่แน่ชัดว่าสิ่งใดเปิดใช้งานจริงแล้วและสิ่งใดยังไม่เปิดใช้งาน สิ่งที่ **ไม่ได้** ถูกสร้างขึ้นในทั้งสองเส้นทางคือ: ฝั่งการดูแลคีย์โดยชุมชน (community-key-custodied) — threshold signing, key ceremonies, และ node attestation การอนุญาต (authorization) ในปัจจุบันเป็นกระบวนการที่มีการบันทึกไว้ (ผู้ดูแลคนเดียว, คีย์เดียว, ติดป้ายกำกับอย่างตรงไปตรงมา) ดังนั้นการประเมิน **รางวัล** ระดับมาตรฐานทองคำจึงยังคงปิดอยู่จนกว่าระบบการดูแลคีย์และความยินยอมของชุมชนจะพร้อมสมบูรณ์

## 5. การดูแลรักษาคีย์ได้รับการตัดสินใจแล้ว แต่ผู้ดูแลรักษาจากชุมชนอยู่ระหว่างการยืนยัน

*กลไก*การดูแลรักษาคีย์ได้รับการตัดสินใจแล้ว: เป็นรูปแบบ threshold/multisig ที่ **Champollion ไม่ถือครองส่วนแบ่งคีย์ใด ๆ** ผู้ดูแลรักษาเองได้รับการเลือกโดยชุมชน และการสนทนาเหล่านั้นยังดำเนินอยู่ — ดังนั้นเราจึงระบุว่า **"ผู้ดูแลรักษาคีย์จากชุมชน (อยู่ระหว่างการยืนยัน)"** การดูแลรักษาคีย์ไม่ใช่ความยินยอม: กระบวนการความยินยอมเชิงสัมพันธ์ตามหลักอธิปไตยทางข้อมูลเป็นเส้นทางของตัวเอง ช้ากว่า และสำคัญกว่า

---

ข้อจำกัดเหล่านี้จะเปลี่ยนแปลงไปตามความคืบหน้าของงาน เมื่อข้อจำกัดใดเปลี่ยนแปลง หน้านี้จะเปลี่ยนตาม — และการเปลี่ยนแปลงควรปรากฏในประวัติของหน้า ไม่ใช่ถูกลบออกอย่างเงียบ ๆ
