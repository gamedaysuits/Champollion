# โหนดประเมินผลแบบอธิปไตย (Sovereign Eval Node) — ฮาร์ดแวร์และการปฏิบัติการแบบ Air-Gap

โหนดประเมินผลแบบอธิปไตยคือเครื่องที่**คุณ**ควบคุม ซึ่งเก็บชุดทดสอบที่เป็นความลับและใช้ประเมินวิธีการแปลต่างๆ วิธีการแปลจะถูกส่งไปยังข้อมูล แต่ข้อมูลจะไม่ถูกส่งออกไปไหนเลย คะแนน — และเฉพาะคะแนนเท่านั้น — ที่จะออกมา

หน้านี้คือข้อกำหนดในเชิงปฏิบัติ: ฮาร์ดแวร์ที่ควรซื้อ (หรือนำกลับมาใช้ใหม่) วิธีการตั้งค่า และวินัยในการปฏิบัติงานที่ทำให้ "ชุดทดสอบไม่เคยออกจากเครื่อง" เป็นข้อเท็จจริงที่คุณสามารถยืนยันได้ แทนที่จะเป็นเพียงคำสัญญาที่คุณต้องเชื่อใจ

:::info[สิ่งที่พร้อมใช้งานแล้วในปัจจุบันเทียบกับสิ่งที่อยู่ระหว่างดำเนินการ]
ซอฟต์แวร์โหนดผู้จัดงาน**พร้อมใช้งานแล้ววันนี้**ใน `mt-eval` — ดูที่
[คู่มือการแข่งขันแบบอธิปไตย](/docs/network/sovereignty/run-a-sovereign-contest):
การเตรียมและปิดผนึกการแข่งขัน, ประตูกรองรอบคัดเลือกสาธารณะที่**ถูกรันซ้ำโดย
ตัวโหนดเองในทุกผลงานที่ส่งเข้ามาก่อนที่ผู้ดูแล (custodian) จะได้รับคำขอให้อนุมัติสิ่งใดก็ตาม**,
การให้คะแนนแบบจำกัดสิทธิ์ด้วยเกณฑ์คะแนนขั้นต่ำ (threshold-gated), และตัวรันเมธอดที่แยกขาดจากเครือข่าย
พร้อมการสแกนการอิมพอร์ต สิ่งที่โหนดรับคือ**โมเดลหรือเมธอด** — ซึ่งเป็น
อาร์ทิแฟกต์ที่ตัวโหนดสามารถรันได้ การอัปโหลดคำแปลของชุดทดสอบแบบไม่เปิดเผยเฉลยที่ต้นฉบับเป็นสาธารณะ (source-public blind set)
ถูกยกเลิกไม่ให้เป็นช่องทางส่งผลงานเข้าประกวดตั้งแต่วันที่ 2026-09-06 และคำสั่งดังกล่าวถูกลบออกไปแล้ว โดย
รอบที่เป็น source-public จะคงอยู่เฉพาะเพื่อเป็นเครื่องมือวินิจฉัยทางเลือกสำหรับผู้จัดงานเท่านั้น และ
คะแนนที่รายงานด้วยตนเองจัดอยู่ในลีดเดอร์บอร์ดแบบเปิด ซึ่งเป็นบอร์ดสาธารณะที่จัดทำดัชนี
ตามคลังข้อมูลและทิศทางคู่ภาษา ไม่ใช่การแข่งขัน
**พิธีสร้างคีย์แบบกำหนดเกณฑ์ขั้นต่ำ (threshold key ceremony) และเวิร์กโฟลว์การปิดผนึกข้อมูลขณะจัดเก็บ (sealed-at-rest) ของ §4 ก็พร้อมใช้งานแล้วในปัจจุบันเช่นกัน**: `mt-eval node ceremony init|share|verify|restore`, `mt-eval node
seal`, ส่วนแบ่งคีย์ตามองค์ประชุม (quorum shares) ที่ต้องแสดง ณ เวลาที่รัน
(`node run-method --offline --share …`), บัญชีแยกประเภทการอนุญาตภายในเครื่องที่เชื่อมโยงด้วยแฮช (`node ledger verify|head`), รายการกำกับคะแนนที่มีลายเซ็นกำกับ
(`node sign-manifest` / `node verify-manifest`), และเครื่องมือแอร์แก็ป (air-gap) ของ §2–§3 (`node bundle`, `node manifest`, `node egress-check`) ชุดบันเดิลคะแนนจะได้รับการลงลายเซ็น**บนโหนดด้วย Python** — บันเดิลแบบออฟไลน์ไม่จำเป็นต้องใช้ Node.js runtime — และรูปแบบลายเซ็นแบบแยกส่วน (detached-signature) เดียวกันนี้สามารถตรวจสอบได้ด้วย
การอิมพลีเมนต์ทั้งสองแบบ ทางฝั่งผู้จัดงาน **การจัดเตรียมคำขอ (request staging) ก็พร้อมใช้งานแล้วเช่นกัน**:
`mt-eval node stage-request` จะเขียนคำขอแลกเปลี่ยนในแบบเดียวกับที่รีเลย์ออนไลน์จะทำขึ้นมาจากไฟล์บันเดิลโดยไม่ต้องใช้ฐานข้อมูลเลยแม้แต่น้อย (สำหรับการซักซ้อม หรือการปรับใช้ที่ไม่เคยเชื่อมต่อเครือข่าย), ซึ่งผ่านการตรวจสอบล่วงหน้าในแบบเดียวกับที่ขั้นตอนการอิมพอร์ตจะตรวจสอบและผูกไว้กับ ID ของโหนด; คะแนนที่ได้กลับมาสามารถ
ตรวจสอบความถูกต้องผ่านรายการกำกับได้แต่จะไม่ถูกเผยแพร่ผ่านรีเลย์ เนื่องจากไม่มีระเบียนการอนุญาต
ใดๆ ที่จะใช้อ้างอิงในการเผยแพร่ได้ ตัวแทนแบบ
คู่คีย์เดี่ยว (single-keypair stand-in) จะยังคงมีไว้สำหรับการแข่งขันที่ผู้จัดงาน
ถือครองข้อมูลอ้างอิงไว้เองโดยสมบูรณ์เท่านั้น — ทุกส่วนแสดงผลจะระบุไว้อย่างชัดเจนว่ากำลังใช้เลนใดอยู่ หากจะกล่าวให้ชัดเจน สิ่งที่ v1 ยัง**ไม่**รวมอยู่ด้วย: ไม่มีการอ้างสิทธิ์การรับรองความถูกต้องของฮาร์ดแวร์จากระยะไกล (TEE) (§5) และการ*ลงลายเซ็น*แบบกำหนดเกณฑ์ขั้นต่ำฝั่งแพลตฟอร์ม
(การอนุมัติผ่านโทรศัพท์ของผู้ดูแลเทียบกับโครงสร้างพื้นฐานที่โฮสต์ไว้) ถือเป็น
งานในอนาคต — บนโหนดอธิปไตย การดูแลสิทธิ์จะกระทำผ่านการ
แสดงส่วนแบ่ง M จาก N ส่วนต่อหน้าเครื่องจริงๆ (§4) และเพื่อให้ชัดเจนในแง่ของ
การเข้ารหัสลับ: นี่คือการแบ่งปันความลับของ Shamir แบบ M-of-N โดยคีย์จะ
**ถูกประกอบขึ้นใหม่ในหน่วยความจำที่ถูกล็อกไว้ของโหนดระหว่างการรันที่ได้รับอนุญาต**
(จากนั้นจะถูกล้างค่าเป็นศูนย์) — นี่*ไม่ใช่*การคำนวณแบบหลายฝ่าย (multi-party computation) และคีย์จะคงอยู่
ในสภาพที่ประกอบแล้วบนเครื่องออฟไลน์ของคุณเพียงชั่วครู่เท่านั้น ประการสุดท้าย จนกว่า
ประตูกรองความยินยอมจากชุมชนจะเปิดออก เลนนี้จะทำงานกับ
**ข้อมูลสังเคราะห์เท่านั้น**; คลังข้อมูลจริงจะต้องรอจนกว่าจะได้รับความยินยอมนั้น
:::

## 1. ฮาร์ดแวร์อ้างอิง

ตัวดำเนินการ (executor) จะรันวิธีการแบบเบ็ดเสร็จในตัว: การถอดรหัส NMT ในเครื่อง, การตรวจสอบ FST/สัณฐานวิทยา, และการคำนวณเมตริก จะไม่มีการเรียกใช้คลาวด์ภายใน Air-gap (วิธีการแบบ LLM-API คือคลาสที่โหนดแบบ Air-gap จะปฏิเสธอย่างแน่นอน — ดูคลาสของวิธีการได้ที่ [benchmark spec's](/docs/network/specifications/benchmark))

| ระดับ | สเปก | ความเหมาะสม | ราคาคร่าวๆ (ปี 2026) |
|---|---|---|---|
| **ขั้นต่ำ** (ใช้งานได้) | 4-core x86_64 หรือ Apple/ARM, RAM 16 GB, SSD 500 GB | การประเมินเมตริก + FST, การถอดรหัสด้วย CPU สำหรับโมเดล NMT ขนาดเล็ก (ช้าแต่ถูกต้อง) | US$0 (แล็ปท็อปสำรอง) – $400 (มือสอง) |
| **แนะนำ** | 8-core, RAM 32 GB, NVMe 1 TB, NVIDIA GPU ≥ 12 GB VRAM (เช่น ระดับ RTX 4070) | การถอดรหัส NMT ที่ราบรื่นสำหรับชุดทดสอบเต็มรูปแบบ; การประเมินวิธีการแบบขนาน | ~US$900–1,600 (เวิร์กสเตชันขนาดเล็ก) |
| **ระดับสถาบัน** | 16-core, RAM 64–128 GB, NVMe 2 TB, VRAM 24 GB+ | การแข่งขันที่มีหลายวิธีการ, ชุดทดสอบขนาดใหญ่, พื้นที่จัดเก็บไซเฟอร์เท็กซ์ที่เก็บถาวร | ~US$2,500–4,000 |

ข้อกำหนดที่จำเป็นอย่างยิ่งในทุกระดับ:

- **ไม่มีวิทยุสื่อสาร หรือวิทยุสื่อสารที่คุณสามารถพิสูจน์ได้ว่าปิดอยู่** ดีที่สุด: เดสก์ท็อปที่ไม่มีการ์ด Wi-Fi/Bluetooth ยอมรับได้: แล็ปท็อปที่ถอดการ์ดไร้สายออกทางกายภาพหรือปิดใช้งานในเฟิร์มแวร์ "โหมดเครื่องบิน" ไม่ใช่ Air-gap
- **NIC แบบมีสายที่คุณสามารถปล่อยทิ้งไว้โดยไม่เสียบสายได้** การไม่มีสายเคเบิลคือการควบคุมเครือข่ายที่สามารถตรวจสอบได้ดีที่สุด
- **ไดรฟ์ USB เฉพาะสองตัว** (ติดป้าย IN และ OUT — ดู §3) และในทางอุดมคติ ควรเป็นเครื่องที่คุณปิดการใช้งานพอร์ตอื่นๆ ในเฟิร์มแวร์
- **การเข้ารหัสทั้งดิสก์ (Full-disk encryption)** (LUKS บน Linux) เพื่อให้โหนดที่ถูกขโมยไปกลายเป็นแค่ก้อนอิฐ และควรมี UPS หากไฟฟ้าของคุณไม่เสถียร — การประเมินที่ถูกขัดจังหวะกลางคันสามารถกู้คืนได้ แต่จะเสี่ยงไปทำไม

## 2. การตั้งค่าซอฟต์แวร์ (ทำครั้งเดียว, ~หนึ่งชั่วโมง)

1. ติดตั้ง Linux LTS เวอร์ชันปัจจุบัน (Ubuntu/Debian) จากตัวติดตั้ง USB **โดย
   ถอดสายเครือข่ายออก**; เปิดใช้งานการเข้ารหัสทั้งดิสก์ (full-disk encryption) ขณะติดตั้ง
2. บนเครื่องออนไลน์อีกเครื่องหนึ่งที่ติดตั้ง harness ไว้แล้ว
   (`python3 -m pip install mt-eval-harness` เวอร์ชัน 0.2.0 หรือใหม่กว่า) ให้บิลด์บันเดิลแบบออฟไลน์
   `mt-eval node bundle --out <dir>` จะทำสี่สิ่งต่อไปนี้:
   - สร้าง wheel สำหรับ harness ที่ติดตั้งไว้และดีเพนเดนซีของมัน (หรือระบุ wheel ที่เจาะจง
     ด้วย `--wheel <file>`);
   - ดึงไลบรารีการเข้ารหัสลับตามรายการที่ล็อกแฮชไว้ซึ่งจัดส่งมา
     พร้อมกับ harness;
   - คัดลอกอาร์ทิแฟกต์ `--include` ใดๆ;
   - เขียนรายการกำกับ sha256 ครอบคลุมทุกไฟล์

   ใส่ **language cards** สำหรับทุกภาษาที่โหนดจะให้คะแนน
   (`--include <cards-dir>`): โหนดจะระบุคู่ภาษาของการรันจาก
   ดัชนีการ์ดในเครื่องและจะไม่ดึงข้อมูลจากภายนอกเลย ทั้งสองแพ็กเกจที่ติดตั้งไม่ได้ส่งมอบ
   ไดเรกทอรีการ์ดสำหรับแต่ละภาษามาด้วย ดังนั้นให้เขียนไฟล์ขึ้นที่นี่ด้วย `champollion`
   CLI, หนึ่ง `<code>.json` ต่อหนึ่งภาษา (`champollion network card eng --json >
   node-cards/eng.json` จากนั้นทำแบบเดียวกันสำหรับอีกภาษาของคุณ) และส่งพารามิเตอร์
   `--include node-cards` บนโหนด ไฟล์นี้จะอยู่ที่
   `<dir>/artifacts/node-cards`; ให้ชี้ `cards_dir` ไปที่นั่น ทุกสิ่งที่โหนดต้องการจะถูกส่งข้าม
   ผ่านไดรฟ์ IN เพียงครั้งเดียว บิลด์บน Python เวอร์ชันเดียวกับที่โหนดรัน
   (3.11 หรือ 3.12); รายการที่ล็อกไว้จะปฏิเสธเวอร์ชันอื่นๆ ทั้งหมด
3. ถ่ายโอนบันเดิลผ่านไดรฟ์ IN; ตรวจสอบ sha256 ของอาร์ทิแฟกต์ทุกตัว
   เทียบกับรายการกำกับ**บนโหนด**ก่อนทำการติดตั้ง
   (`mt-eval node bundle --verify <dir>`) จากนั้นติดตั้งจาก
   wheel ที่รวมมาในบันเดิลเท่านั้น:
   `python3 -m pip install --no-index --find-links <dir>/wheels 'mt-eval-harness[node]'`
   ส่วนเสริม `[node]` คือไลบรารี `cryptography` ที่คำสั่ง `mt-eval node
   keygen` and the custody ceremony need; a plain `mt-eval-harness` ขาดไป
   หากติดตั้งแบบมาตรฐาน
4. สร้างคู่คีย์สำหรับลงลายเซ็นของโหนด (`mt-eval node keygen`) และบันทึก
   ฝั่งพับลิกคีย์เอาไว้ — คุณจะต้องเผยแพร่คีย์นี้เพื่อให้ทุกคนสามารถตรวจสอบรายการกำกับ
   คะแนนของคุณได้ (§5)
   โหนดจำเป็นต้องมี **Docker** (หรือ Podman) เช่นกัน ซึ่งจะรันแต่ละเมธอดที่ส่งเข้ามา
   ภายในคอนเทนเนอร์โดยไม่มีเครือข่าย; หากไม่มีทั้งคู่ใน `PATH`,
   `mt-eval node run-method` จะปฏิเสธการทำงานในบรรทัดเดียวโดยระบุชื่อทั้งสองตัว และ
   คำขอดังกล่าวจะยังคงอยู่ในสถานะที่สามารถนำมารันได้ นอกจากนี้ยังจำเป็นต้องมีคอนฟิกของโหนดที่
   `~/.mt-eval/node.json` ไฟล์นั้นจะระบุชื่อโหนด, ไดเรกทอรีการ์ดของโหนด
   (`cards_dir` หรือ `MT_EVAL_CARDS_DIR`) และการแข่งขันที่โหนดให้บริการ
   `mt-eval node init` จะเขียนคอนฟิกเริ่มต้นพร้อมคีย์ทั้งหมดที่โหนดให้คะแนน
   อ่าน รวมถึงประตูกรองรอบคัดเลือกสาธารณะ (`qualifier` + `dev_corpus`
   ซึ่งโหนดจะรันซ้ำกับทุกเมธอดก่อนที่จะเปิดชุดข้อมูลที่ปิดผนึกไว้)
   และสล็อตสำหรับชุดทดสอบที่สงวนไว้และปิดผนึกอยู่ (`holdout_set_id` + `holdout_corpus`;
   ลบรายการเหล่านี้ออกสำหรับการแข่งขันที่ไม่มีชุด holdout)
   `mt-eval node init --from-contest <out>` จะเติมค่าต่างๆ ของการแข่งขันจาก
   รายการกำกับที่ `contest prepare` เขียนไว้ (การจับคู่ระบุไว้ใน
   [คู่มือการแข่งขันแบบอธิปไตย](/docs/network/sovereignty/run-a-sovereign-contest#organizer-prerequisites))
   บล็อก `sandbox` ในนั้นคือนโยบายทรัพยากรของโหนด (RAM 4 GB, พื้นที่ชั่วคราว scratch 4 GB,
   30 นาทีต่อการรัน, ไม่มี GPU) และ `contest submit-method` จะประกาศ
   ค่าเหล่านี้ตรงตามนั้นโดยค่าเริ่มต้น ดังนั้นโปรดเผยแพร่ขีดจำกัดของคุณพร้อมกับการแข่งขันหากคุณ
   ปรับเปลี่ยนค่าเหล่านั้น
   คอนฟิกของโหนดที่ประกาศประตูกรองดังกล่าวไว้เพียงครึ่งเดียวจะถูกปฏิเสธเมื่อเริ่มต้นระบบ
   `mt-eval node ledger verify` จะตรวจสอบไฟล์ที่กรอกข้อมูลแล้ว: คำสั่งนี้จะปฏิเสธตั้งแต่
   ค่า `<...>` แรกที่หลงเหลืออยู่ หรือไฟล์ที่ประกาศไว้แต่ไม่มีอยู่บนโหนด,
   พิมพ์สิ่งที่ตรวจสอบออกมา จากนั้นจึงรีเพลย์ห่วงโซ่แฮชของบัญชีแยกประเภทภายในเครื่อง ส่วน
   เครื่องที่เชื่อมต่อเครือข่ายซึ่งทำหน้าที่รีเลย์คำขอไปยังโหนดจำเป็นต้องมี
   **service-role key** ของฐานข้อมูล (`MT_EVAL_SUPABASE_SERVICE_KEY`) คีย์นี้
   ไม่จำเป็นต้องมีบนตัวโหนดที่เป็นแอร์แก็ปเลย
5. จากนั้นเป็นต้นไป เครื่องจะไม่เชื่อมต่อกับเครือข่ายใดๆ อีก — และสามารถสั่งให้รันแบบปิดผนึก
   เพื่อพิสูจน์เรื่องนี้ก่อนได้: `mt-eval node egress-check` (ซึ่งบังคับใช้
   โดยอัตโนมัติด้วย `assert_airgap` ในคอนฟิกของโหนดเช่นกัน) จะปฏิเสธการทำงานเมื่อ
   เราต์, โพรบ หรือ DNS บ่งชี้ว่ามีทางออกสู่ภายนอก การอัปเดตระบบปฏิบัติการจะต้องกระทำอย่างรอบคอบ
   เป็นชุดบันเดิล และผ่านการตรวจสอบแฮชเสมอ — ไม่ใช่การทำงานผ่านเซอร์วิสเบื้องหลัง

## 3. วินัยในการถ่ายโอน (ทุกการแข่งขัน, ทั้งสองทิศทาง)

Air-gap คือ*ขั้นตอนการปฏิบัติ* ไม่ใช่ผลิตภัณฑ์ ขั้นตอนการปฏิบัติมีดังนี้:

- **ไดรฟ์ IN** บรรจุ: บันเดิลเมธอดหรือโมเดลที่ส่งเข้ามา และรายการกำกับ
  ของบันเดิลเหล่านั้น ก่อนที่สิ่งใดจะเริ่มรัน โหนดจะตรวจสอบแฮชของแต่ละแพ็กเกจ
  เทียบกับรายการกำกับ และการสแกนการอิมพอร์ตจะทำงาน (ระบบจะปฏิเสธเมธอด
  ที่อิมพอร์ตไลบรารีเครือข่าย — ความสามารถนี้พร้อมใช้งานแล้วในปัจจุบัน)
- **ไดรฟ์ OUT** บรรจุ: รายการกำกับคะแนนที่ลงลายเซ็นแล้ว — คะแนนรวม,
  แฮชของเมธอด/คอนฟิกที่คะแนนนั้นสังกัด, ส่วนหัวของบันทึกการตรวจสอบ (audit log) — และ*ไม่มี
  สิ่งอื่นใดนอกเหนือจากนี้* ผลลัพธ์ระดับเซกเมนต์จะยังคงอยู่บนโหนดภายใต้
  การควบคุมของผู้จัดงาน; การเผยแพร่ผลลัพธ์ดังกล่าวเป็นการตัดสินใจร่วมกันของชุมชนที่ต้องทำแยกต่างหากและเป็นไปอย่างรอบคอบ
- ทิศทางเดียวต่อหนึ่งไดรฟ์เสมอ ไดรฟ์ที่สัมผัสกับโหนดแล้วจะต้องไม่
  เมานต์โดยอัตโนมัติบนเครื่องออนไลน์เด็ดขาด — ให้เมานต์แบบ `noexec,nodev` และคัดลอก
  รายการกำกับออกมาด้วยตนเอง
- `mt-eval node manifest write <drive> --direction in|out` จะแฮชทุกไฟล์
  บนไดรฟ์ก่อนการข้ามฝั่ง; `mt-eval node manifest verify`
  ฝั่งผู้รับจะปฏิเสธสิ่งใดก็ตามที่มีการเพิ่ม แก้ไข หรือสูญหาย
- บันทึกการข้ามฝั่งทุกครั้ง (วันที่, ไดรฟ์, แฮชของรายการกำกับ) ลงในบันทึกกระดาษหรือ
  บันทึกบนตัวโหนด ความน่าเบื่อคือหัวใจสำคัญ: บันทึกนี้คือสิ่งที่จะช่วยให้คุณตอบคำถามที่ว่า "เคยมี
  สิ่งอื่นใดหลุดออกไปหรือไม่?" ได้อย่างมีหลักฐานยืนยัน

## 4. การดูแลคีย์ (M-of-N, ถือครองโดยชุมชน)

ชุดทดสอบที่ปิดผนึกไว้จะได้รับการเข้ารหัสขณะจัดเก็บ; การถอดรหัสต้องใช้องค์ประชุมของ
ส่วนแบ่งคีย์ที่ถือครองโดยผู้ดูแลที่**ชุมชนเป็นผู้เลือก** — เช่น สภาผู้อาวุโส,
องค์กรกำกับดูแลภาษา, หน่วยงานด้านการศึกษา การออกแบบนี้ทำให้
แพลตฟอร์มมีส่วนแบ่งคีย์เป็นศูนย์ ดังนั้น Champollion จึงไม่สามารถถอดรหัสชุดข้อมูลที่ปิดผนึกไว้ได้ และ
ผู้ดูแลคนใดคนหนึ่งเพียงลำพังก็ไม่สามารถทำได้เช่นกัน พิธีกรรมด้านล่างนี้ยัง
ไม่เคยดำเนินการร่วมกับผู้ดูแลจริง

พิธีการ (การนั่งทำออฟไลน์หนึ่งครั้ง; เครื่องมือที่ให้มาจะทำให้อัตโนมัติ):
`mt-eval node ceremony init` จะสร้างคีย์ของชุดข้อมูลบนโหนด, แบ่งมันออกเป็น N ส่วน (ใช้ M ส่วนใดๆ เพื่อสร้างใหม่; หากน้อยกว่านี้จะไม่เปิดเผยสิ่งใดเลย — การแบ่งปันนี้เป็นไปตามทฤษฎีข้อมูล), และล้างคีย์เป็นศูนย์ในลมหายใจเดียวกัน; `ceremony share` จะปล่อยส่วนแบ่งของผู้ดูแลแต่ละคนออกมาเป็นไฟล์สำหรับโทเค็นพร้อมกับข้อมูลสำรองบนกระดาษที่พิมพ์ได้; `ceremony verify` จะพิสูจน์ว่าสำเนาที่แจกจ่ายไปสามารถสร้างใหม่ได้ — โดยไม่มีการบันทึกสิ่งใดลงดิสก์; `ceremony share
--wipe-originals` then destroys the node's own copies. `mt-eval node
seal` จะเข้ารหัสคลังข้อมูลด้วยพับลิกคีย์ของพิธีการ: โหนดจะจัดเก็บไซเฟอร์เท็กซ์และการ์ดเมตาดาต้าที่ไม่มีเนื้อหา และไม่มีสิ่งอื่นใดอีก จากนั้นเป็นต้นไป การรันการประเมินหมายความว่าผู้ดูแลจะต้องนำเสนอส่วนแบ่ง M จาก N ส่วนทางกายภาพ (`node run-method --offline --share …`): คีย์จะถูกสร้างขึ้นใหม่**ในหน่วยความจำที่ถูกล็อกของตัวดำเนินการเท่านั้น**, ใช้สำหรับการรันที่ผูกกับการอนุญาตนั้นเพียงครั้งเดียว, และถูกล้างเป็นศูนย์ — มันจะไม่สัมผัสดิสก์อีกเลย ทุกคำขอ, การโหวต, การอนุญาต, และการใช้งานจะถูกต่อท้ายบัญชีแยกประเภทในเครื่องแบบแฮชเชน (`node ledger verify`), และความพยายามที่ไม่มีองค์ประชุมจะถูกปฏิเสธ*และ*ถูกบันทึกไว้

ประโยคที่ตรงไปตรงมาหนึ่งประโยคเกี่ยวกับกลไกนี้: นี่คือการแบ่งปันความลับแบบ Shamir โดยมีการสร้างใหม่ในหน่วยความจำของเครื่องออฟไลน์ที่ชุมชนถือครอง — ไม่ใช่การคำนวณแบบหลายฝ่าย (multi-party computation) ในระหว่างการรันที่ได้รับอนุญาต คีย์จะถูกประกอบขึ้นและมีอยู่ชั่วครู่บนฮาร์ดแวร์ที่ชุมชนควบคุมทางกายภาพ; คุณสมบัติที่มันปกป้องคือ *ไม่มีคีย์ค้างอยู่บนดิสก์*, *ไม่มีการรันหากไม่มีองค์ประชุม*, และ *ทุกการใช้งานจะถูกเชื่อมโยงเข้ากับบัญชีแยกประเภทที่ตรวจสอบได้* การเซ็นชื่อแบบแบ่งส่วนฝั่งแพลตฟอร์ม ซึ่งคีย์จะไม่ถูกประกอบขึ้นที่ใดเลย ยังคงเป็นงานในอนาคตและถูกระบุไว้เช่นนั้นในทุกที่ที่มีการกล่าวถึง

การหมุนเวียนและการเปลี่ยนตัวผู้ดูแลจะต้องรันพิธีการใหม่; การสูญเสียส่วนแบ่งมากกว่า N−M ส่วนหมายความว่าชุดข้อมูลจะต้องถูกปิดผนึกใหม่จากสำเนาต้นฉบับของชุมชน — ชุมชนจะเก็บรักษาต้นฉบับที่เป็นเพลนเท็กซ์ของตนเองไว้เสมอ เพราะ[การครอบครอง](/docs/network/sovereignty/data-sovereignty)ไม่เคยเป็นสิ่งที่เราถือสิทธิ์

## 5. ความหมายของ "การรับรอง (attested)" ในที่นี้ — และสิ่งที่ไม่ใช่

ทุกการประเมินจะสร้าง **รายการคะแนนที่มีการเซ็นชื่อ (signed score manifest)**: ลายเซ็นของโหนดบนคะแนน, แฮชของแพ็กเกจวิธีการ, เช็คซัมของคลังข้อมูล, และส่วนหัวของบันทึกการตรวจสอบแบบต่อท้ายเท่านั้น (append-only audit log) ใครก็ตามที่ถือพับลิกคีย์ที่เผยแพร่ของโหนดสามารถตรวจสอบได้ — `mt-eval node verify-manifest <manifest>
--pubkey <published .pub.json>` — ว่า*โหนดนี้*สร้าง*คะแนนเหล่านี้*สำหรับ*อินพุตที่แน่นอนเหล่านี้* และบันทึกแบบแฮชเชนจะทำให้สามารถตรวจจับการแอบแก้ไขประวัติได้

นั่นคือ**การรับรองซอฟต์แวร์ (software attestation)** — มันพิสูจน์ความสมบูรณ์ของบันทึก และเป็นสิ่งที่ v1 นำเสนอ มัน**ไม่ได้**พิสูจน์ว่าซิลิคอนใดเป็นตัวดำเนินการรัน: การรับรองฮาร์ดแวร์ระยะไกล (TEEs) เป็นงานในอนาคตและจงใจที่จะไม่กล่าวอ้างถึง คำแถลงด้านความปลอดภัยที่ตรงไปตรงมาสำหรับ v1 คือ: วินัยของผู้จัดงาน (§3) บวกกับรายการที่มีการเซ็นชื่อ บวกกับการดูแลเครื่องทางกายภาพของชุมชนคือจุดยึดเหนี่ยวความไว้วางใจ (trust anchor) — ซึ่งเป็นจุดที่การออกแบบที่คำนึงถึงอธิปไตยเป็นอันดับแรกต้องการให้ความไว้วางใจตั้งอยู่พอดี

## 6. วงจรการปฏิบัติงาน

1. ประกาศการแข่งขัน; เผยแพร่พับลิกคีย์ของโหนด + เกณฑ์คะแนนขั้นต่ำของชุด dev
2. รับผลงานที่ส่งเข้ามาทางออนไลน์ (เครื่องคอมพิวเตอร์ทั่วไป), รวบรวมรายการกำกับ IN
   (`mt-eval node manifest write <drive> --direction in`)
3. นำไดรฟ์ IN ไปที่โหนด; ตรวจสอบแฮช (`node manifest verify`);
   import-scan (`node import-bundle`); queue methods. An entrant's offline
   ข้อเสนอจะมาถึงในสถานะ *pending* โหนดจะตรวจสอบข้อเสนอนั้นก่อน (`node run-method
   <id> --offline` จะรันรอบคัดเลือกของผู้ส่งผลงานซ้ำบนชุด dev สาธารณะ
   และตรวจสอบ container runtime สำหรับผลงานประเภทโค้ด โดยไม่เปิดข้อมูลที่ปิดผนึกใดๆ และ
   บันทึกผลการผ่านลงในบัญชีแยกประเภทภายในเครื่อง) จากนั้นผู้ดูแลจะบันทึกการตัดสินใจ
   ลงบนโหนด (`node approve <id> --offline --actor <custodian>` ซึ่งจะถูกปฏิเสธ
   จนกว่าการตรวจสอบนั้นจะผ่าน หรือ `node deny … --offline --reason …`: การลงคะแนน
   + การอนุญาตในบัญชีแยกประเภทภายในเครื่อง และระเบียนที่ลงลายเซ็นด้วยคีย์ของโหนด;
   `node list --offline` จะแสดงรายการที่กำลังรออยู่) การรันแบบปิดผนึก (`node run-method
   --offline` อีกครั้ง) จะปฏิเสธข้อเสนอที่ยังค้างอยู่จนกว่าการอนุมัตินั้นจะได้รับการ
   บันทึกและตรวจสอบผ่านแล้ว
4. ผู้ดูแลอนุญาตการรันโดยการแสดงส่วนแบ่งคีย์ครบตามองค์ประชุม (§4 —
   `node run-method <id> --offline --share … --share …`); ชุดข้อมูลที่ปิดผนึกไว้จะ
   ถอดรหัสเข้าไปยังตัวรันเมธอดเท่านั้น หากไม่มีองค์ประชุม จะไม่มีการรัน — และ
   ความพยายามดังกล่าวจะถูกบันทึกลงในบัญชีแยกประเภท
5. ดำเนินการรัน; คำนวณคะแนน; ผลลัพธ์ระดับเซกเมนต์จะถูกเก็บรักษาไว้ฝั่งโหนด
6. ขั้นตอนการเคลียร์ระบบ: ล้างข้อความธรรมดา (plaintext) ที่ใช้ทำงานทิ้งทั้งหมด; ผนวกบันทึกการตรวจสอบ; ลงลายเซ็นในรายการกำกับ
7. นำไดรฟ์ OUT กลับไป; เผยแพร่คะแนน + รายการกำกับ; ทุกคนสามารถตรวจสอบความถูกต้องได้
   (`node verify-manifest`)
8. บันทึกการข้ามฝั่ง; ไดรฟ์ยังคงถูกแยกใช้เฉพาะทาง; โหนดยังคงถูกตัดการเชื่อมต่อโดยสมบูรณ์
