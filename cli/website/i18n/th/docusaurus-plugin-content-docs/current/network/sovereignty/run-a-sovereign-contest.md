# จัดการแข่งขันแบบ Sovereign

> **สรุปสำหรับผู้บริหาร** ชุมชนหรือองค์กรสามารถจัดการแข่งขันประเมินผล — รวมถึงรางวัลที่มีผู้สนับสนุน — โดยใช้ชุดข้อมูลทดสอบที่สงวนไว้ซึ่ง **ไม่เคยออกจากโครงสร้างพื้นฐานของตนเอง** คุณสร้างชุดข้อมูล เข้ารหัส โฮสต์ และถือกุญแจเอง Network บันทึกเพียงการ์ดข้อมูลเมตาที่ไม่มีเนื้อหา และ digest ของ ciphertext เท่านั้น วิธีการต้องผ่านการคัดเลือกจากชุดข้อมูลสาธารณะก่อน ทุกการรันกับชุดข้อมูลที่ปิดผนึกต้องได้รับอนุญาตจากผู้ดูแลของคุณ และมีเพียง **คะแนน** เท่านั้นที่ถูกเผยแพร่ออกมา เงินรางวัลอยู่ใน **ความดูแลของผู้สนับสนุน** — โดยองค์กรของคุณหรือกองทุนที่คุณกำหนด — และ **Champollion ไม่แตะต้องเงินหรือข้อมูลเลย** หน้านี้คือคู่มือการดำเนินการแบบครบวงจรที่คุณจัดการเองได้

:::warning[สิ่งที่พร้อมใช้งานในปัจจุบัน vs. ที่อยู่ระหว่างพัฒนา]
ควรทำความเข้าใจให้ชัดเจนก่อนเริ่มต้น — นี่คือโครงการวิจัยที่กำลังพัฒนาและไม่มีวัตถุประสงค์เชิงพาณิชย์
เราต้องการให้คุณตรวจสอบเราแทนที่จะเชื่อใจเราโดยไม่มีข้อสงสัย:

- ✅ **ใช้งานได้แล้ว:** การลงทะเบียนคลังข้อมูล (การ์ดเมทาดาตา, การตรึงแฮช, exposure
  lanes), รีจิสทรีชุดข้อมูลที่ปิดผนึก (ไดเจสต์ + กลุ่มผู้ดูแล + ตัวคัดกรอง, ไม่รวม
  เนื้อหา), กลไกการแข่งขันพร้อมเลนที่ปิดผนึก, เลเยอร์ข้อมูลคำขอ/การอนุญาต/การตรวจสอบสิทธิ์
  (รอดำเนินการ → การตัดสินใจแบบ M-of-N → สิทธิ์ที่ใช้ได้ครั้งเดียวแบบจำกัดเวลา,
  บันทึกการตรวจสอบที่ต่อท้ายได้เท่านั้นและเชื่อมโยงด้วยแฮช) และการปล่อยเฉพาะคะแนน
  ที่บังคับใช้ในระดับฐานข้อมูล
- ✅ **ใช้งานได้แล้ว: โหนดให้คะแนนของผู้จัดการแข่งขัน** คำสั่งเดียวจะแบ่งคลังข้อมูลของคุณ
  ออกเป็นชุดข้อมูล dev สาธารณะ (ตัวคัดกรองที่ผู้เข้าร่วมแข่งขันจะให้คะแนนตนเอง) และชุดข้อมูล
  ลับที่ปิดผนึกไว้ซึ่งโหนดของคุณจะใช้ประมวลผลผลงานที่ส่งเข้าประกวด และปิดผนึกข้อมูลลับครึ่งหนึ่ง
  ไว้ขณะจัดเก็บ (at rest) บนเครื่องของคุณเอง (`mt-eval contest prepare`) การลงทะเบียนชุดข้อมูล
  ที่ปิดผนึก ตัวคัดกรอง และการแข่งขันสามารถ**ทำได้ด้วยตนเองจากการลงชื่อเข้าใช้ของคุณ** —
  `contest prepare --self-serve` หรือ `mt-eval contest register --manifest`
  สำหรับการแข่งขันที่คุณเตรียมไว้ก่อนหน้า — โดยทุกแถวจะถูกผูกกับตัวตนที่ระดับ
  ฐานข้อมูล ไม่มีภัณฑารักษ์เข้ามาเกี่ยวข้องและไม่มีคีย์ที่มีสิทธิ์พิเศษ (ดูข้อจำกัดตามจริง
  ในขั้นตอนที่ 4)
- ✅ **ใช้งานได้แล้ว: ผลงานที่ส่งเข้าประกวดคือวิธีการ ไม่ใช่คำแปล** การเข้าร่วมการแข่งขัน
  ทำได้โดยการส่งสิ่งใดก็ตามที่โหนดของคุณสามารถ RUN (รัน) ได้ ผู้เข้าร่วมจะให้คะแนนชุดข้อมูล
  dev สาธารณะด้วยตนเอง (`mt-eval contest qualify`) เพื่อรับใบเสร็จ จากนั้นจึงส่งโมเดล
  หรือวิธีการ โหนดของคุณจะทำการประมวลผลคะแนนของใบเสร็จนั้นซ้ำอีกครั้งบนสำเนาชุดข้อมูล dev
  ของตนเอง ก่อนที่จะขอให้ผู้ดูแลคนใดอนุมัติสิ่งใด และจะปฏิเสธหากผลลัพธ์ไม่ตรงกัน โหนดจะเลือกเลน
  จากการส่งผลงาน:
  - **เลน A — โมเดลเชิงประกาศ (แนะนำ)** โมเดลนิวรัลมาตรฐานคือ
    DATA (ข้อมูล): `mt-eval contest submit-model` จะส่งค่าน้ำหนัก safetensors + โทเคไนเซอร์
    เชิงประกาศ + การกำหนดค่า — **ไม่มีโค้ด, ไม่มี Dockerfile** โหนดของคุณ
    จะตรวจสอบความถูกต้องว่าไม่มีโค้ด (เป็น safetensors ไม่ใช่ pickle, ไม่มี
    `trust_remote_code`/`auto_map`, เป็นไฟล์ข้อมูลล้วน) และรันค่าน้ำหนักใน
    เอ็นจินที่เชื่อถือได้ของตัวเอง (`transformers`, `trust_remote_code=False`, ออฟไลน์)
    สถาปัตยกรรมจะเปิดกว้างตามค่าเริ่มต้น (อะไรก็ตามที่เอ็นจินของคุณโหลดได้ในตัว) โฮสต์ที่
    รอบคอบสามารถปักหมุดรายการที่อนุญาต (allowlist) ไว้ได้ ไม่มีสิ่งที่ไม่น่าเชื่อถือถูกประมวลผล
    จึงไม่ต้องทำแซนด์บ็อกซ์ เผยแพร่เป็น `declarative-model` อัตลักษณ์ของวิธีการ
    **ปราศจากโค้ดโดยโครงสร้าง**
  - **เลน B — บันเดิลที่รันได้ (แซนด์บ็อกซ์สำรอง)** สำหรับวิธีการที่เป็นโค้ดจริงๆ:
    `mt-eval contest submit-method` จะส่ง Dockerfile + จุดเข้าใช้งาน (entrypoint) หลังจาก
    ผู้ดูแลของคุณอนุมัติแล้ว โหนดของคุณจะรันมันภายในคอนเทนเนอร์ที่แยกการเชื่อมต่อเครือข่าย
    (`--network=none` — สแตกเครือข่ายจะไม่มีอยู่ภายใน รูทแบบอ่านอย่างเดียว, ตัดความสามารถพิเศษทิ้ง,
    สภาพแวดล้อมที่ผ่านการชำระล้าง) โดยมีการตรวจสอบสถิติก่อนโดยอัตโนมัติ และข้อความอ้างอิง
    จะไม่เข้าไปในคอนเทนเนอร์เลย เผยแพร่เป็น `method-execution` พร้อมอัตลักษณ์
    **ที่ผ่านการตรวจสอบการรัน**
  ไม่ว่าจะเลนใด: แฮชของบันเดิลจะถูกตรึงไว้ในคำขออนุญาต (สิ่งที่รันจะพิสูจน์ได้ว่าเป็น
  สิ่งที่เสนอมาอย่างแท้จริง) และคะแนนจะเผยแพร่ผ่านช่องทางเฉพาะค่ารวมเท่านั้น เพื่อการแยกความปลอดภัย
  ระดับสูงสุด เครื่องให้คะแนนสามารถเป็นแอร์แก็ป (airgap) ที่แท้จริงได้: คำขอที่ได้รับอนุญาตและบันเดิลเฉพาะคะแนน
  ที่ลงนามด้วย Ed25519 จะส่งผ่านสื่อบันทึกข้อมูลที่ถอดเสียบได้ (`mt-eval node relay` / `import-bundle` / `export-scores`) —
  ข้อความลับจะไม่ไปถึงเครื่องที่เชื่อมต่อเครือข่ายเลย สิ่งที่เลนเหล่านี้ยังไม่ได้รวมไว้:
  การรับรองฮาร์ดแวร์ของโหนด (อัตลักษณ์เป็นการรายงานตนเอง), กลไกการระงับข้อพิพาทอย่างเป็นทางการ,
  และ — สำหรับเลน B โดยเฉพาะ — การเสริมความแกร่งของคอนเทนเนอร์ที่ลึกกว่าการตัดสแตกเครือข่ายออก
  (โปรไฟล์ seccomp, microVM; นี่คือเหตุผลที่ควรเลือกเลน A) ดูที่
  [ข้อจำกัดตามจริง](/docs/network/honest-limitations)
- ✅ **เลเยอร์คำมั่นสัญญาใช้งานได้แล้ว (2026-09-07):** การประกาศผลงาน
  (หลัก/แบบคอนทราสต์, แทร็ก), ระยะการส่งผลงาน, ผลลัพธ์ที่ระงับไว้
  (`hidden_until_close`) และการตรึงที่ทำให้คำมั่นสัญญาที่คุณประกาศไว้ไม่สามารถแก้ไขได้
  เมื่อมีผลงานส่งเข้ามาแล้ว จะถูกบังคับใช้ในฐานข้อมูลบนเอนด์พอยต์ที่โฮสต์บนเครือข่าย โฮสต์แบบรวมศูนย์
  (federated) จะได้กฎเดียวกันโดยใช้การไมเกรชันที่มาพร้อมกับ harness เมื่อเทียบกับเอนด์พอยต์ที่เก่ากว่า
  harness จะถอยกลับไปใช้ชุดพื้นฐานและแจ้งให้ทราบ (`declarations_available: false`)
  แทนที่จะแสร้งทำเป็นใช้ได้ จุดที่ขั้นตอนด้านล่างระบุว่า*ฐานข้อมูลจะตรึง /
  ระงับไว้* นั่นหมายความตามนั้นจริง
- 🔲 **อยู่ระหว่างการพัฒนา: การลงนามแบบกำหนดเกณฑ์ (threshold signing)** สำหรับชุดข้อมูลที่ปิดผนึกด้วย
  `champollion seal-corpus` การอนุมัติของผู้ดูแลแบบ M-of-N จะถูก*บันทึก*ใน
  ตารางการอนุญาตและการตรวจสอบสิทธิ์ และคีย์การปิดผนึกจะเป็นตัวแทนคู่คีย์เดี่ยวที่มีป้ายกำกับ
  (`champollion seal-corpus keygen`) ชุดข้อมูลที่ปิดผนึกบนโหนดออฟไลน์
  (`mt-eval node seal`) จะใช้**พิธีการคีย์** (`mt-eval node ceremony`)
  ที่สร้างขึ้นของโหนด: คีย์ชุดข้อมูลจะถูกแบ่งแบบ M-of-N และประกอบกลับคืนมาในหน่วยความจำเท่านั้น
  ระหว่างการรันที่ได้รับอนุญาตจากองค์ประชุม พิธีการดังกล่าวไม่เคยถูกใช้กับผู้ดูแลจริง
  และส่วนแบ่ง (shares) ของมันเป็นไฟล์ธรรมดาใน v1 ทั้งสองแนวทางยังไม่มีการลงนามแบบกำหนดเกณฑ์
  (threshold signing): ลายเซ็นของบันเดิลคะแนนแบบแอร์แก็ปจะเป็นคีย์โหนดเดี่ยว (`seal-corpus sign-keygen`)
- ❌ **ไม่มีอยู่จริง โดยเจตนา:** การที่ Champollion จะโฮสต์คลังข้อมูลของคุณ, ถือครองคีย์ของคุณ,
  หรือถือครองกองทุนเงินรางวัล บันเดิลของผู้เข้าร่วมแข่งขัน (โมเดลหรือโค้ดของพวกเขาเอง)
  จะส่งผ่านสตอเรจของเราไปยังโหนดของคุณ แต่เนื้อหาคลังข้อมูลของคุณจะไม่ผ่านเข้ามาเลย
- ❌ **ลบทิ้งแทนที่จะปล่อยทิ้งไว้เป็นกับดัก:** `contest submit-hypotheses` (ยกเลิกเมื่อ 2026-09-06) ซึ่งเคยอัปโหลด
  คำแปลของชุด blind set ที่เปิดเผยต้นฉบับต่อสาธารณะ; `contest submit` (ยกเลิกเมื่อ 2026-09-06) ซึ่งเคยเชื่อมโยงคะแนนที่คุณ
  เผยแพร่ด้วยตนเอง ทั้งสองวิธีนี้
  ไม่ถือเป็นเส้นทางการส่งผลงานเข้าแข่งขันอีกต่อไปแล้ว รอบ blind set ที่เปิดเผยต้นฉบับต่อสาธารณะยังคงมีอยู่
  เพียงเพื่อเป็นเครื่องมือวินิจฉัยทางเลือกสำหรับผู้จัดเท่านั้น และคะแนนที่รายงานด้วยตนเองยังคงอยู่
  บนกระดานผู้นำสาธารณะ — ซึ่งเป็นกระดานสาธารณะที่จัดทำดัชนีตามคลังข้อมูลและทิศทางคู่ภาษา
  ไม่ใช่การแข่งขัน

หากขั้นตอนใดด้านล่างขึ้นอยู่กับสิ่งที่อยู่ในรายการ 🔲 ขั้นตอนนั้นจะระบุไว้ชัดเจน
:::

## รูปแบบของข้อตกลง

| ใคร | ถือครอง | ไม่ถือครอง |
|-----|-------|-------------|
| **คุณ (ชุมชน/องค์กร)** | ชุดข้อมูล, กุญแจเข้ารหัส (ผ่าน custodians ของคุณ), เงินรางวัล, การตัดสินรางวัล | — |
| **Champollion / Network** | การ์ดข้อมูลเมตา, ciphertext digest, บันทึก authorization + audit, คะแนนที่เผยแพร่ | เนื้อหาชุดข้อมูลของคุณ, กุญแจของคุณ, เงินของคุณ |
| **นักพัฒนาวิธีการ** | วิธีการของตน | ข้อมูลทดสอบของคุณ — พวกเขาเห็นคะแนน ไม่เห็นประโยค |

ทุกอย่างด้านล่างคือการขยายความเชิงกลไกของตารางนั้น

## ข้อกำหนดเบื้องต้นสำหรับผู้จัดการแข่งขัน

ก่อนขั้นตอนที่ 1 ควรทราบว่าการรัน node จริงนั้นต้องการอะไรบ้าง:

- **Harness พร้อมส่วนเสริม node:**
  `python3 -m pip install 'mt-eval-harness[node]'` (เวอร์ชัน 0.2.0 หรือใหม่กว่า; ใช้
  `python3 -m pip` ซึ่งทำงานได้ในทุกสภาพแวดล้อมที่ harness ทำงาน —
  คำสั่ง `pip` เดี่ยวๆ อาจไม่ได้อยู่บน `PATH` ในทุก virtual environment) ส่วนเสริม `[node]`
  จะเพิ่มไลบรารี `cryptography` ที่ `mt-eval node keygen`, พิธีการของผู้ดูแล
  และการลงนามกำกับคะแนนใช้งาน การติดตั้งแบบทั่วไป
  `python3 -m pip install mt-eval-harness` จะไม่มีไลบรารีนี้ และคำสั่งเหล่านั้นจะหยุดทำงานและแจ้งให้
  ติดตั้งตัวนี้
- **docker หรือ podman** — จำเป็นสำหรับเลนการรันวิธีการ โหนดจะตรวจหา
  docker โดยอัตโนมัติ แล้วตามด้วย podman (`sandbox.runtime` ใน `node.json` จะเป็น `null`
  ตามค่าเริ่มต้น; สามารถระบุตัวใดตัวหนึ่งที่นั่นเพื่อเจาะจงใช้งาน) หากไม่มีตัวใดอยู่บน `PATH`
  คำสั่ง `mt-eval node run-method` จะปฏิเสธการทำงานพร้อมข้อความบรรทัดเดียวที่ระบุชื่อทั้งสองตัว ก่อนที่จะรัน
  สิ่งใดๆ และคำขอจะถูกคงไว้ตามเดิมเพื่อให้คุณสามารถรันได้เมื่อติดตั้งรันไทม์แล้ว
  จะ**ไม่มีการถอยกลับไปใช้วิธีอื่น (no fallback)** การแยกคอนเทนเนอร์ด้วย
  `--network=none` เป็นหัวใจสำคัญของการรับประกันความปลอดภัย ดังนั้นจะไม่มีสิ่งใดทำงานได้หากไม่มีรันไทม์คอนเทนเนอร์
- **Node.js 20.11+ และ npm CLI ของ `champollion`** — harness ไม่ได้
  ใช้วิธีนำรหัสการปิดผนึกไปเขียนขึ้นมาใหม่ `champollion seal-corpus` (คำสั่ง: `keygen`,
  `seal`, `open`, `sign-keygen`, `sign`, `verify`) เป็นการนำรหัสไปใช้งานเพียงหนึ่งเดียว
  (X25519-ECDH → HKDF-SHA256 → AES-256-GCM) และโหนดของผู้จัดการแข่งขัน
  จะเรียกใช้คำสั่งเชลล์ไปยังตัวนี้
- **การกำหนดค่าโหนดที่ `~/.mt-eval/node.json`** ทุกคำสั่งของ `mt-eval node`
  จะปฏิเสธการเริ่มทำงานหากไม่มีไฟล์นี้ `mt-eval node init` จะเขียนการกำหนดค่าเริ่มต้น
  ไว้ที่นั่น (`--print` จะแสดงให้ดูแทน) ไฟล์นี้จะเก็บ `node_id` ที่คุณรายงานตนเอง
  (ซึ่งถูกผูกไว้ในลายนิ้วมือของทุกคำขอ) และแมป `contests` ที่ชี้ไปยัง
  ชุดข้อมูล dev ของคุณ, ชุดข้อมูลที่ปิดผนึกของคุณ (`secret_set_id` + `secret_artifact`),
  ชุดข้อมูล holdout ที่ปิดผนึกของคุณหากคุณได้เตรียมไว้ (`holdout_set_id` + `holdout_corpus`; ลบ
  คีย์ทั้งสองออกหากไม่ได้จัดเตรียมไว้) และเกณฑ์คัดกรองสาธารณะ (`qualifier` +
  `dev_corpus` ซึ่งเป็นเกณฑ์บนสเกลตัวคัดกรอง 0–100) เมื่อคุณรันคำสั่ง
  `contest prepare` แล้ว (ขั้นตอนที่ 1) คำสั่ง `mt-eval node init --from-contest ./mytask`
  จะเขียนการกำหนดค่าเริ่มต้นโดยเติมค่าต่างๆ ของการแข่งขันไว้ล่วงหน้าจาก
  `./mytask/local/manifest.json` และระบุรายการสิ่งที่เหลือให้คุณทำ การแมป
  ที่นำมาใช้ (กรอกด้วยตนเองหากคุณต้องการ):

  | `local/manifest.json` | `node.json` (ภายใต้ `contests.<contest-id>`) |
  |---|---|
  | `contest.language_pair` | `language_pair` |
  | `secret.sealed_set_id` | `secret_set_id` |
  | `secret.corpus_sealed_artifact` | `secret_artifact` |
  | `holdout.sealed_set_id` / `holdout.corpus_sealed_artifact` | `holdout_set_id` / `holdout_corpus` (จะถูกลบออกทั้งคู่เมื่อไม่มีชุด holdout) |
  | `qualifier.corpus_file` | `dev_corpus` |
  | `qualifier.qualifier_id`, `corpus_card_id`, `threshold`, `metric`, `year` | `qualifier.*` (ชื่อเดียวกัน) |
  | `test_suites[].suite_id` / `sha256`, `test_suite_local_copies` | `test_suites[].suite_id` / `corpus_sha256` / `corpus_path`: สำเนาที่ `contest prepare` อ่าน (`--test-suite <id>=<path>` หรือชุดที่ตรวจพบ) เมื่ออยู่บนเครื่องนี้พร้อมไบต์ที่ตรึงไว้ มิฉะนั้นคุณจะต้องตั้งค่า `corpus_path` |
  | `secret.sealed_block.keyScheme` | `custody`: `single-key` สำหรับชุดข้อมูลที่ปิดผนึกด้วยคู่คีย์เดี่ยว (จากนั้นตั้งค่า `secret_privkey`), `threshold-quorum` สำหรับพิธีการ |
  | `registration.prize_terms` (บันทึกโดย `contest prepare` และ `contest register`) | `prize_terms_sha256`: SHA-256 ของข้อกำหนด แฮชที่ผู้เข้าร่วมส่งไปยัง `--accept-terms` (เว้นว่างไว้เมื่อการแข่งขันไม่ได้ประกาศรางวัล) |

  รหัสการแข่งขันคือ `--slug` ที่คุณระบุให้กับ `contest prepare` (`mytask` ใน
  ตัวอย่างด้านล่าง) คำสั่ง prepare จะบันทึกไว้ใน manifest การลงทะเบียนจะสร้าง
  การแข่งขันภายใต้รหัสนี้ และเป็นรหัสที่ผู้เข้าร่วมส่งไปยัง `contest qualify`
  และ `submit-method` ดังนั้นโปรดประกาศรหัสนี้พร้อมกับการเปิดตัว dev ส่วน `--contest-id`
  จะเขียนทับค่านั้น (manifest ที่เขียนขึ้นก่อนที่จะมีการบันทึกรหัสจะยังคงใช้รหัส
  ที่การลงทะเบียนรับมาจากชื่อของมัน `"My Task 2026"` → `my-task-2026`
  เนื่องจากเป็นค่าที่การแข่งขัน ใบเสร็จ และการกำหนดค่าโหนดใช้งานอยู่แล้ว) ไม่มี
  manifest ใดที่รู้ `node_id`, `cards_dir`, `signing_key` หรือไฟล์คีย์ส่วนตัวของคุณ
  ดังนั้นค่าเหล่านี้จะยังคงเป็น `<...>` เพื่อให้คุณกรอกเอง
  จากนั้น `mt-eval node ledger verify` จะตรวจสอบและแจ้งสิ่งที่ได้ตรวจสอบไป: มันจะ
  โหลดการกำหนดค่า (การดูแล, เกณฑ์คัดกรองทั้งหมด, คู่ข้อมูล holdout,
  ดัชนีการ์ดในเครื่อง), ปฏิเสธค่าแรกที่ยังคงเป็นตัวแทน `<...>`
  หรือไฟล์ที่ประกาศไว้ซึ่งไม่ได้อยู่บนเครื่องนี้, พิมพ์ชุดข้อมูลและไฟล์ของการแข่งขันแต่ละรายการ
  และจากนั้นจึงเล่นซ้ำ hash chain ของบัญชีการอนุญาต (ไม่มีรายการใดๆ บนโหนดใหม่)
- **ดัชนีการ์ดภาษาในเครื่องที่โหนดพกพาไปด้วย** การให้คะแนนจะระบุชื่อคู่ภาษา
  ของการรัน และโหนดจะไม่ค้นหาภาษาผ่านเครือข่ายเลย
  กำหนดให้ `cards_dir` ใน `node.json` ชี้ไปยังไดเรกทอรีที่เก็บการ์ดสำหรับทุก
  ภาษาที่โหนดของคุณให้คะแนน (หรือตั้งค่า `MT_EVAL_CARDS_DIR`) โหนดที่ไม่มีดัชนี
  ในเครื่องจะปฏิเสธการทำงานตั้งแต่เริ่มต้น แทนที่จะพยายามดึงข้อมูลมา แพ็กเกจที่ติดตั้ง
  ทั้งสองแพ็กเกจไม่ได้จัดส่งไดเรกทอรีการ์ดภาษาแยกตามภาษามาให้ ดังนั้นให้เขียนขึ้นมาบนเครื่องที่เชื่อมต่อ
  เครือข่ายด้วย CLI `champollion` หนึ่งไฟล์ `<code>.json` ต่อหนึ่งภาษา
  ของคู่ภาษาของคุณ:

  ```bash
  mkdir -p node-cards
  champollion network card eng --json > node-cards/eng.json
  champollion network card crk --json > node-cards/crk.json
  ```

  จากนั้นตั้งค่า `"cards_dir"` ให้เป็นพาธสัมบูรณ์ของไดเรกทอรีนั้น สำหรับโหนด
  แบบแอร์แก็ป ให้นำติดตัวไปด้วยในบันเดิลออฟไลน์
  (`mt-eval node bundle --out <dir> --include node-cards`) ซึ่งจะไปอยู่ที่
  `<dir>/artifacts/node-cards` และให้ `cards_dir` ชี้ไปที่นั่นบนโหนด
- **การลงชื่อเข้าใช้** ไม่มีขั้นตอนการสร้างบัญชีแยกต่างหาก: คำสั่งแรก
  ที่ต้องการระบุตัวตน (เช่น `mt-eval contest prepare --self-serve` หรือ
  `mt-eval publish`) จะเปิดการลงชื่อเข้าใช้ OAuth ผ่านเบราว์เซอร์ด้วย **GitHub หรือ Google**
  (Supabase Auth) อีเมลของบัญชีนั้นคืออัตลักษณ์ที่ทุกแถวในรีจิสทรีจะถูก
  ผูกไว้ด้วย — โปรดใช้อีเมลที่องค์กรของคุณเป็นผู้ควบคุม
- **การจำกัดอัตราการส่งผลงาน (intake throttle)** การส่งผลงานของผู้เข้าร่วมจะถูกจำกัดอัตราต่อ
  ผู้ส่งผลงานไว้ที่ **5 ครั้งต่อ 24 ชั่วโมงตามค่าเริ่มต้น** (เพื่อป้องกันการลองส่งตรวจเช็ก; กำหนดค่าแยกตามการแข่งขัน
  ได้ด้วย `--intake-daily-limit` ในขณะที่รัน prepare หรือใช้เป็นค่าเริ่มต้น
  ของภารกิจร่วม) วางแผนกำหนดการแข่งขันของคุณโดยคำนึงถึงเงื่อนไขนี้ด้วย

**ข้อควรระวังตามจริงหนึ่งประการเกี่ยวกับการลงทะเบียนด้วยตนเอง** บน **เอนด์พอยต์ที่โฮสต์บนเครือข่าย
ตามค่าเริ่มต้น** การลงทะเบียนด้วยตนเอง (`contest prepare
--self-serve` / `contest register`) ปัจจุบันจะถูกระงับไว้ที่ตัวป้องกันเอนด์พอยต์การผลิต
(production-endpoint guard): CLI จะปฏิเสธการทำงานพร้อมข้อความที่ชัดเจนแทนที่จะเขียนลงใน
โปรเจกต์ระดับโปรดักชัน ซึ่งอยู่ระหว่างการตัดสินใจเชิงนโยบายเกี่ยวกับการเปิดช่องทางดังกล่าว โฮสต์แบบรวมศูนย์
(federated hosts - โปรเจกต์ Supabase ของคุณเอง) จะไม่ได้รับผลกระทบ หากคุณพบตัวป้องกันนี้
บนโฮสต์เริ่มต้น นั่นคือสถานะปัจจุบันของระบบ ไม่ใช่ความผิดพลาดในการกำหนดค่า
ของคุณแต่อย่างใด — [เปิด issue](https://github.com/gamedaysuits/Champollion/issues)
แล้วเราจะช่วยดำเนินการลงทะเบียนให้เสร็จสิ้น

## Step 1 — สร้างชุดข้อมูลทดสอบที่สงวนไว้

ออกแบบชุดข้อมูลที่คุณจะใช้วัดผล และสงวนไว้ตั้งแต่วันแรก: ไม่มีสิ่งใดในนั้นที่ควรเคยถูกเผยแพร่, โพสต์ หรือแชร์กับผู้ให้บริการโมเดลมาก่อน

- ปฏิบัติตาม [Corpus Design Framework](/docs/network/specifications/corpus-design) สำหรับโครงสร้าง entry, ระดับความยาก และการครอบคลุม register และ [Corpus Creation cookbook](/docs/network/tutorials/corpus-creation) สำหรับเครื่องมือ
- ให้ผู้พูดที่คล่องแคล่วตรวจสอบ entries ก่อนปิดผนึก — [Speaker Validation Protocol](/docs/network/specifications/speaker-validation) อธิบายโครงสร้างการตรวจสอบที่คุณสามารถนำมาใช้ซ้ำสำหรับ QA ของชุดข้อมูล ไม่ใช่แค่การตรวจสอบวิธีการ
- กำหนดป้ายกำกับ **version** ของชุดข้อมูลตอนนี้ (เช่น `v1`) authorization grants ถูกผูกกับ version เฉพาะ ดังนั้น versioning เป็นส่วนหนึ่งของโมเดลความปลอดภัย ไม่ใช่แค่การจัดระเบียบ

### วิธีการแบ่งส่วนคลังข้อมูล

คำสั่งเดียวจะนำคลังข้อมูลหลักของคุณมาสร้างทุกระดับชั้น แบบกำหนดผลลัพธ์ได้อย่างแน่นอน (deterministically)
จากค่า seed ที่คุณเลือกและบันทึกไว้:

```bash
mt-eval contest prepare --corpus master.json --slug mytask --name "My Task 2026" \
    --pair 'eng>crk' --seed 20260906 --qualifier-threshold 35 \
    --dev-size 400 --secret-size 500 --sealed-holdout-size 250 \
    --test-suite <a public corpus card id> \
    --license <the licence the rights-holder grants> \
    --custodian-group <opaque id> --threshold-pubkey ./contest.pub.json \
    --out ./mytask
```

`--qualifier-threshold` คือคะแนนที่วิธีการจะต้องไปให้ถึงบนชุดข้อมูล dev สาธารณะ
ก่อนที่โหนดของคุณจะยอมรันบนชุดข้อมูลที่ปิดผนึกและชุดข้อมูล holdout ที่ปิดผนึก ค่านี้อยู่บน
**สเกลตัวคัดกรอง 0–100**: คะแนนคัดกรองคือ **chrF++ ระดับคลังข้อมูล**
(sacreBLEU chrF, `word_order=2`) ของผลลัพธ์ dev เทียบกับข้อความอ้างอิง
ของ dev ที่เผยแพร่ — ซึ่งเป็นเมทริกหลักของมาตรฐานการให้คะแนน และเป็นตัวเลขเดียวกับที่
การ์ด `mt-eval run` แสดงเป็นพาดหัวสำหรับผลลัพธ์เดียวกัน จะไม่มีสิ่งอื่นใดนำมาคำนวณผสม
ค่าความตรงกันทุกประการ (exact match) จะแสดงอยู่ข้างๆ เพื่อการวินิจฉัยเท่านั้นและไม่นำมาใช้เป็นเกณฑ์ตัดสิน โหนด
ของคุณจะคำนวณตัวเลขเดียวกันเมื่อรันวิธีการซ้ำ ดังนั้นใบเสร็จของผู้เข้าร่วม
และค่าที่วัดได้ของโหนดคุณจึงสามารถเปรียบเทียบกันได้

กำหนดเกณฑ์จากคะแนน chrF++ ที่คุณเคยวัดได้บนชุดข้อมูล dev นี้ (รัน
`contest qualify` บนผลลัพธ์ dev ของเบสไลน์) ไม่ใช่จากคะแนนบนชุดประเมินผล
อื่นๆ: ระดับของ chrF++ จะแตกต่างกันอย่างมากระหว่างภาษาและคลังข้อมูล

[มาตรฐานการให้คะแนน](/docs/network/specifications/scoring#how-runs-are-scored)
ที่ใช้ค่าคอมโพสิตเดิมที่ยกเลิกไปแล้วเป็นเมทริกจะยังคงทำงานได้: เกณฑ์ของมันจะถูกอ่าน
บนสเกล chrF++ และ qualify จะแจ้งให้ทราบทุกครั้ง ดังนั้นโปรดยืนยันตัวเลขหรือ
สลับไปใช้ตัวคัดกรองใหม่

จำเป็นต้องระบุ `--license` เพื่อระบุสัญญาอนุญาตของชุดข้อมูล dev ที่เผยแพร่
และ mt-eval จะไม่เลือกสัญญาอนุญาตให้คุณเอง ไฟล์ที่เผยแพร่จะระบุสัญญาอนุญาตนี้ไว้เป็น
`dataset.license` ซึ่งเป็นสิ่งที่ `mt-eval run`, `contest qualify` และ
`publish` ใช้อ่าน ดังนั้นการรันของผู้เข้าร่วมจึงถูกควบคุมด้วยสัญญาอนุญาตของคุณ ให้ใช้สิทธิ์ที่ได้รับ
จากผู้ถือสิทธิ์เองเป็นรหัส SPDX หากใช้ `CC-BY-4.0` ผู้เข้าร่วมจะสามารถประเมินผลด้วยบริการโมเดลใดก็ได้
หากใช้สัญญาอนุญาตที่ไม่ใช่เชิงพาณิชย์ เช่น `CC-BY-NC-4.0` โมเดลระยะไกลจะรันได้เฉพาะ
ผ่านช่องทางที่ไม่มีการนำข้อมูลไปเทรนเท่านั้น หากใช้ข้อกำหนดของคุณเอง (`LicenseRef-<name>`) การประเมินผล
ระยะไกลจะถูกปฏิเสธจนกว่าจะมีการบันทึกการอนุญาตจากผู้ถือสิทธิ์ เพื่อให้ผู้เข้าร่วม
ใช้โมเดลในเครื่อง

ไฟล์ที่เผยแพร่ยังระบุข้อกำหนดอื่นๆ ของชุดข้อมูลหลัก ซึ่งอ่านได้จากการ์ด
ของชุดข้อมูลหลักเอง (การ์ดคลังข้อมูลที่ `champollion network register-corpus`
เขียนไว้ ผ่านทางไซด์คาร์ `<file>.champollion.json` ของมัน) และซองจดหมายของมันเอง:
`dataset.do_not_train` และเมื่อชุดหลักถูกระบุว่าเป็นแบบในเครื่องเท่านั้น (local-only)
`dataset.transmission: "local-only"` (ผู้เข้าร่วมจะสามารถรันชุดข้อมูล dev ได้เฉพาะ
ด้วยโมเดลบนเครื่องของตนเองเท่านั้น) โดยมี `dataset.terms_from` ระบุที่มา
ของแต่ละรายการ เมื่อการ์ดของชุดข้อมูลหลักไม่ได้ระบุข้อกำหนดการเทรน ให้ส่งพารามิเตอร์
`--do-not-train true` หรือ `false` แฟล็กนี้สามารถทำให้ข้อกำหนดของชุดหลักเข้มงวดขึ้นได้
แต่จะผ่อนปรนไม่ได้ (การใช้ `--do-not-train false` บนชุดหลัก `doNotTrain: true` จะถูก
ปฏิเสธ) คำสั่ง prepare จะพิมพ์ข้อกำหนดเหล่านี้ และเตือนเมื่อการ์ดของชุดหลักระบุว่า
ห้ามแจกจ่ายซ้ำ: การเผยแพร่ `public/` ถือเป็นการแจกจ่ายซ้ำ ดังนั้นอย่า
เผยแพร่จนกว่าผู้ถือสิทธิ์จะยินยอม

| ส่วนย่อย (Split) | ใครมองเห็นได้บ้าง | มีไว้เพื่ออะไร |
|---|---|---|
| **ชุดข้อมูล dev สาธารณะ** (`--dev-size`) | ทุกคน — ต้นฉบับ *และ* ข้อความอ้างอิงได้รับการเผยแพร่ | **ตัวคัดกรอง**: ผู้เข้าร่วมจะให้คะแนนตนเองบนชุดนี้ก่อนจึงจะสามารถส่งผลงานได้ (ขั้นตอนที่ 8) |
| **ชุดข้อมูลที่ปิดผนึก** (`--secret-size`) | ไม่มีใครเห็นนอกจากโหนดของคุณ — ต้นฉบับ *และ* ข้อความอ้างอิงยังคงถูกเข้ารหัส | สิ่งที่ใช้ให้คะแนนผลงานจริง |
| **ชุดข้อมูล holdout ที่ปิดผนึก** (`--sealed-holdout-size`, ทางเลือก) | ไม่มีใครเห็นนอกจากโหนดของคุณ | ส่วนย่อยที่ปิดผนึกชุดที่ **สอง** ซึ่งให้คะแนนในการรันเดียวกัน โดยจะระงับคะแนนไว้จนกว่าคุณจะปิดการแข่งขัน |
| *ชุดข้อมูล blind* (`--blind-size`, ค่าเริ่มต้น 0) | เผยแพร่ต้นฉบับ ระงับข้อความอ้างอิง | รอบการวินิจฉัยทางเลือกของคุณเอง นี่**ไม่ใช่**ช่องทางการส่งผลงาน: การเข้าร่วมการแข่งขันทำได้โดยการส่งมอบวิธีการ ไม่ใช่การอัปโหลดคำแปล |

ส่วนย่อยต่างๆ จะแยกออกจากกันโดยสิ้นเชิง (disjoint) และสร้างซ้ำได้เสมอ: คลังข้อมูลเดิม, seed เดิม, ส่วนย่อยเดิม
ตลอดไป สูตรการสร้างจะคงอยู่ใน manifest ภายในเครื่องของผู้จัดซึ่งจะไม่หลุดออกไปจาก
เครื่องของคุณ

**ประโยคที่ซ้ำกันจะอยู่ฝั่งเดียวกันเสมอ** การแบ่งส่วนจะเป็นแบบกลุ่มไม่ทับซ้อนกัน
(`group-disjoint/1` ซึ่งบันทึกไว้ในบล็อก `split` ของ manifest): แถวที่มี
ต้นฉบับหรือข้อความอ้างอิงร่วมกัน ไม่ว่าจะเหมือนกันทุกประการหรือเหมือนกันหลังจากปรับรูปแบบตัวพิมพ์ เครื่องหมายวรรคตอน
และการเว้นวรรคแล้ว จะรวมเป็นกลุ่มเดียวกัน และทั้งกลุ่มจะอยู่ในส่วนย่อยเดียวกันทั้งหมด ดังนั้นจึงไม่มี
แถวที่ปิดผนึกแถวใดซ้ำกับแถวของชุดข้อมูล dev ที่เผยแพร่ กลุ่มต่างๆ จะถูกสับเปลี่ยนด้วย
seed ของคุณและจัดวางตามลำดับเป็น dev, blind, secret, holdout; คลังข้อมูลหลักที่ไม่มี
ประโยคซ้ำกันเลยจะได้ผลการแบ่งส่วนเหมือนกับการสับเปลี่ยนแบบทีละแถวพอดี หากทั้งกลุ่ม
ไม่สามารถเติมเต็มขนาดที่คุณระบุได้ prepare จะปฏิเสธ พร้อมแจ้งจำนวนแถวที่ซ้ำกันและ
วิธีแก้ไข: นำแถวที่ซ้ำออก (เก็บไว้กลุ่มละหนึ่งแถว) หรือขอขนาดรวมที่น้อยกว่าขนาดของชุดหลัก
เพื่อให้สามารถตัดบางกลุ่มออกได้

**`public/` สามารถเผยแพร่ได้; บันทึกการรันจะไปอยู่ที่ `runs/`** prepare จะเขียนไฟล์เครื่องหมาย
`.champollion-releasable.json` ลงใน `public/` บันทึกการรัน รายงาน และแคช
การแปลจะไม่ถูกเขียนลงในนั้นเด็ดขาด: `mt-eval run` จะปฏิเสธ
`--output-dir` หรือ `--cache-dir` ที่อยู่ข้างใน และจะระบุชื่อ `runs/` ที่อยู่ข้างๆ
(`<out>/runs/`) แทน และ `run_benchmark` ของเซิร์ฟเวอร์ MCP จะวางการรัน
บนชุดข้อมูล dev ที่เผยแพร่ (เบสไลน์ที่คุณรันเพื่อตั้งค่าเกณฑ์) ลงใน `runs/`
โดยอัตโนมัติและแจ้งให้ทราบ การแข่งขันที่เตรียมไว้ก่อนที่จะมีไฟล์เครื่องหมาย
จะได้รับการตรวจสอบจากโครงสร้างเลย์เอาต์ (`public/` ข้างๆ `local/manifest.json`)

**เหตุใดจึงต้องมีชุด holdout** ชุดข้อมูลที่ปิดผนึกเพียงชุดเดียวอาจยังถูกปรับจูน (tune) เข้าหาได้
ตลอดการแข่งขันที่ยาวนาน — ทุกการส่งผลงานเปรียบเสมือนการส่งหัววัด (probe) และการวัดที่มากพอย่อมทำให้ข้อมูลรั่วไหลได้เล็กน้อย ส่วนย่อย
ชุดที่สองที่ได้รับการให้คะแนนในการรันที่ได้รับอนุญาตเดียวกัน แต่ไม่มีใครเห็นตัวเลข
จนกว่าจะปิดการแข่งขัน จะช่วยให้คุณอ่านผลได้อย่างเที่ยงธรรมในตอนท้าย: หากอันดับของระบบมีการเปลี่ยนแปลง
ระหว่างสองชุดนี้ คุณจะได้เรียนรู้ว่าคะแนนนั้นมาจากการปรับจูนมากน้อยเพียงใดและมาจากการแปล
จริงเท่าใด ชุดข้อมูลทั้งสองได้รับการครอบคลุมโดยการอนุญาต**เพียงครั้งเดียว** ดังนั้นผู้ดูแล
ของคุณจึงไม่ต้องทำพิธีการเพิ่มเติม

**ชุดทดสอบของบุคคลที่สาม** `--test-suite` จะระบุชื่อคลังข้อมูลสำหรับการวินิจฉัยที่เป็นสาธารณะ —
ซึ่งเป็นของบุคคลอื่น มีการตรึงแฮช และดาวน์โหลดได้แบบสาธารณะ — ซึ่งทุกผลงานจะถูกนำไป
รันด้วยเช่นกัน ตัวเลขเหล่านั้นจะ**รายงานไว้แต่จะไม่นำมาจัดอันดับ**: มีไว้เพื่อให้
ผู้อ่านสามารถดูได้ว่าคะแนนของชุดข้อมูลที่ปิดผนึกที่ดีนั้น ยังคงทำได้ดีบนชุดข้อมูล
ที่การแข่งขันของคุณไม่ได้เป็นผู้ออกแบบหรือไม่ Champollion จะปฏิเสธชุดทดสอบที่ถูกกักกัน (quarantined),
ไม่มีการตรึงแฮช, ไม่ใช่สำหรับคู่ภาษาของคุณ หรือเป็นหนึ่งในส่วนย่อยของคุณเอง

**แถวที่ปิดผนึกที่กลายเป็นสาธารณะไปแล้วจะไม่ถือว่าปิดผนึก** `contest prepare`
จะเปรียบเทียบชุดข้อมูลที่ปิดผนึกและชุด holdout ที่ปิดผนึกของคุณกับทุกอย่างที่เป็นสาธารณะ: ชุดข้อมูล dev
ที่เผยแพร่ (การแบ่งส่วนแบบกลุ่มไม่ทับซ้อนกันข้างต้นจะทำให้ค่านี้เป็นศูนย์), การเผยแพร่ต้นฉบับของ
ชุด blind หากมี และชุดทดสอบที่ประกาศไว้ทั้งหมด มันจะตรวจสอบความตรงกัน
ทั้งแบบตรงทุกประการและหลังจากปรับรูปแบบตัวพิมพ์ เครื่องหมายวรรคตอน และการเว้นวรรคแล้ว (การเปรียบเทียบ
แบบเดียวกับที่ใช้จัดกลุ่มการแบ่งส่วน) จากนั้นจะพิมพ์ความทับซ้อนแต่ละรายการพร้อมระบุจำนวน (เช่น
"30 จาก 30 แถวยังปรากฏในชุดทดสอบ …") และบันทึกจำนวนลงใน
`local/manifest.json` สำหรับชุดทดสอบของบุคคลที่สาม ระบบจะเตือนแทนที่จะ
ปฏิเสธ: ชุดทดสอบนั้นเป็นข้อความสาธารณะของผู้อื่น และคุณสามารถตัดสินใจได้ว่าจะ
นำแถวเหล่านั้นออกจากชุดหลักหรือละทิ้งชุดทดสอบนั้น แล้วทำการเตรียมใหม่อีกครั้ง ในการตรวจสอบชุดทดสอบ คำสั่ง prepare จำเป็นต้องมี
ประโยคของชุดนั้น มันจะใช้สำเนาที่มีอยู่แล้วบนเครื่องของคุณ และจะไม่ดาวน์โหลด
ระหว่างการเตรียมอย่างเด็ดขาด ระบุสำเนาของคุณด้วย `--test-suite <id>=<path>` ซึ่ง
sha256 ของมันจะต้องตรงกับหมุดในรีจิสทรี หากไม่พบสำเนา คำเตือนจะระบุว่า
ชุดทดสอบ**ไม่ได้รับการตรวจสอบ** ไม่ใช่ระบุว่ามันสะอาด manifest จะบันทึก
พาธของสำเนาแต่ละชุดที่ prepare อ่าน เพื่อให้ `node init --from-contest` สามารถชี้
โหนดของคุณไปยังไฟล์นั้นได้

ชุด holdout และชุดทดสอบที่คุณประกาศไว้จะกลายเป็นคำมั่นสัญญา: เมื่อผลงานชิ้นแรกมาถึง
การแข่งขันจะตรึงค่าเหล่านั้นไว้ ทำให้คุณไม่สามารถเพิ่มหรือลบชุดทดสอบระหว่างการแข่งขันได้

## Step 2 — เข้ารหัสและโฮสต์บนโครงสร้างพื้นฐานของคุณเอง

เข้ารหัสชุดข้อมูลขณะพักเก็บ (ด้วย AEAD scheme สมัยใหม่ใดก็ได้ — เช่น `age`/x25519 หรือ AES-256-GCM) และโฮสต์ **ciphertext** ในที่ที่คุณควบคุม Champollion ไม่เคยรับ plaintext *หรือ* ciphertext

เผยแพร่เพียงสิ่งเดียว: **SHA-256 digest ของ ciphertext blob**

```bash
shasum -a 256 sealed-corpus-v1.age
# → 3b5f0c…e91a  sealed-corpus-v1.age
```

digest เป็นสาธารณะ แต่ข้อมูลไม่ใช่ ทุกคนสามารถตรวจสอบในภายหลังได้ว่า blob ที่ใช้ประเมินผลนั้นเหมือนกันทุก byte กับ blob ที่คุณปิดผนึก — ความสมบูรณ์โดยไม่ต้องครอบครอง นี่คือวินัย hash-instead-of-copy เดียวกับ [การลงทะเบียนชุดข้อมูลทั่วไป](/docs/network/sovereignty/registering-corpora#1-registration-is-metadata-not-content)

## Step 3 — ลงทะเบียนการ์ดข้อมูลเมตา

ลงทะเบียนชุดข้อมูลผ่าน [registration lane](/docs/network/sovereignty/registering-corpora) มาตรฐานแบบ fail-private: การ์ดที่มี `language_pair`, `license`, `attribution` และ `do_not_train` — **ไม่มีประโยค** เลือก exposure lane แบบ **private** การลงทะเบียน sealed set ในขั้นตอนถัดไปคือสิ่งที่ทำให้มีสิทธิ์เข้าร่วมการแข่งขัน

sealed set คือ registry entry ที่ไม่มีเนื้อหา ซึ่งบันทึกสิ่งสามอย่างไว้ในบันทึกสาธารณะ:

| Field | สิ่งที่คุณผูกพัน |
|-------|------------------------|
| `ciphertext_digest` | bytes ที่แน่นอนซึ่งนับเป็น "ชุดข้อมูล" |
| `custodian_group_id` | opaque id สำหรับกลุ่มที่ควบคุมการเข้าถึง (ไม่ใช่ชื่อองค์กร/ชาติสาธารณะก่อนได้รับความยินยอม) |
| `current_qualifier_id` | รอบสาธารณะที่วิธีการต้องผ่านก่อนที่จะสามารถเสนอ sealed run ได้ |

การลงทะเบียนเป็น **self-serve จาก sign-in ของคุณเอง** — ไม่มีผู้ดูแลเข้ามาเกี่ยวข้องและไม่มีกุญแจพิเศษ:

```bash
# Register a contest you prepared with `mt-eval contest prepare --no-register`
mt-eval contest register --manifest local/manifest.json

# Or do it in one shot at prepare time
mt-eval contest prepare … --self-serve
```

manifest จะคงอยู่บนเครื่องของคุณ — การลงทะเบียนจะส่งเฉพาะ
รหัส ไดเจสต์ และเกณฑ์ที่ปราศจากเนื้อหาเท่านั้น คุณสามารถอ่านสิ่งที่มันส่งไปได้อย่างแม่นยำก่อนที่
จะมีการส่งข้อมูลใดๆ: `contest prepare --no-register` จะพิมพ์แผนการลงทะเบียน
ทุกแถวที่ `contest register` จะเขียน ตามลำดับ — รหัสของชุดข้อมูลที่ปิดผนึกแต่ละชุดและ
SHA-256 ของข้อความไซเฟอร์เท็กซ์ (พร้อมจำนวนแถวที่ยังคงปิดผนึกอยู่บนเครื่องของคุณ),
กลุ่มผู้ดูแล, รหัสและเกณฑ์ของตัวคัดกรอง, แถวการแข่งขันพร้อมคำมั่นสัญญาที่บันทึกไว้,
คอลัมน์นโยบาย และชุด holdout, ชุดทดสอบ และข้อกำหนดรางวัลใดๆ ที่รวมเข้ากับ
เมทาดาตาของการแข่งขัน แผนนี้สร้างขึ้นโดยโค้ดเดียวกับที่ส่งแถวข้อมูล
จึงไม่มีทางที่จะอธิบายสิ่งที่แตกต่างไปจากสิ่งที่ถูกส่งได้
ทุกแถวในรีจิสทรีจะถูก**ผูกกับอัตลักษณ์**: ฐานข้อมูลจะ
บันทึกบัญชีที่ลงชื่อเข้าใช้ซึ่งเป็นผู้ลงทะเบียน และตรึงการผูกมัดนั้นไว้ไม่ให้แก้ไข
ในภายหลัง และตัวคัดกรองจะควบคุมได้เฉพาะชุดข้อมูลที่ปิดผนึกซึ่งลงทะเบียนโดยอัตลักษณ์**เดียวกัน**
เท่านั้น ชุดข้อมูลที่ปิดผนึกจะเริ่มต้นด้วยสถานะกักกัน (ไม่สามารถนำไปสนับสนุน
การแข่งขันทั่วไปหรือจัดอันดับบนกระดานผู้นำสาธารณะได้) ตัวคัดกรองจะเริ่มต้นในสถานะปลอดภัย
และการลงทะเบียนจะถูกจำกัดอัตรา — ทั้งหมดนี้บังคับใช้โดยทริกเกอร์ของฐานข้อมูล
ที่อยู่ใต้ไคลเอนต์ทุกตัว รวมถึงของเราด้วย ตัวรีจิสทรีเองสามารถอ่านได้แบบสาธารณะ
คุณจึงสามารถตรวจสอบได้ว่าผลงานของคุณระบุตรงตามที่คุณปิดผนึกไว้ทุกประการ —
และไม่มีสิ่งอื่นใดเกินมา

**ข้อจำกัดตามจริง** ช่องทางการทำด้วยตนเองนั้นเปิดสำหรับการลงทะเบียนเท่านั้น (เพิ่มข้อมูลได้อย่างเดียวในระดับฐานข้อมูล)
**การสลับตัวคัดกรองและการปลดระวางชุดข้อมูลที่ปิดผนึกยังคงต้องผ่านภัณฑารักษ์** —
เปิด issue หรือติดต่อโครงการผ่านทาง
[GitHub](https://github.com/gamedaysuits/Champollion/issues) และการรันโหนดให้คะแนนของผู้จัดการแข่งขัน
ในขั้นตอนถัดไป (การเลื่อนวงจรชีวิต, การให้สิทธิ์การอนุญาต, การดำเนินการตรวจสอบ)
จะเป็นเลนแยกต่างหากที่ใช้ข้อมูลรับรองบริการบนโหนดของคุณเอง —
การทำด้วยตนเองจะสิ้นสุดลงที่บันทึกสาธารณะ

## Step 5 — เลือก custodians และกฎ M-of-N

เลือกบุคคลหรือสถาบันที่ต้องอนุมัติร่วมกันสำหรับทุกการประเมินกับชุดข้อมูลของคุณ และกำหนด threshold (เช่น **3 จาก 5**) Custodians ควรรับผิดชอบต่อชุมชนของคุณ ไม่ใช่ต่อ Champollion — ดู [Data Stewardship](/docs/network/sovereignty/data-sovereignty) และ [Ownership & Terms](/docs/network/sovereignty/ownership-transfer) สำหรับวิธีการกำหนดเงื่อนไขต่อชุมชน

**กล่องความจริงใจ:** การ*ลงนาม*แบบกำหนดเกณฑ์ (สิทธิ์ที่ไม่สามารถสร้างขึ้นได้
หากไม่มีลายเซ็นครบ M ลายเซ็นอย่างแท้จริง) กำลัง**อยู่ระหว่างการพัฒนา** พิธีการคีย์ของโหนดออฟไลน์
(`mt-eval node ceremony`, Shamir M-of-N) ได้รับการสร้างขึ้นแล้วแต่ยังไม่ได้นำไปใช้จริง
กับผู้ดูแลจริงๆ ในกรณีอื่นๆ กฎ M-of-N จะถูกบังคับใช้ในฐานะกระบวนการที่ถูกบันทึกไว้: คำขอเข้าถึง
ทุกรายการจะเข้าสู่คิว**รอดำเนินการ (pending)**, การตัดสินใจของผู้ดูแลจะถูกบันทึกไว้, สิทธิ์จะถูกสร้างขึ้น
เฉพาะสำหรับคำขอที่ได้รับอนุญาตเท่านั้น, สิทธิ์แต่ละรายการจะ**ใช้ได้ครั้งเดียว, มีการจำกัดเวลา, และ
ผูกไว้กับลายนิ้วมือเฉพาะของ (วิธีการ, เวอร์ชันคลังข้อมูล, โหนดประเมินผล)**
และทุกเหตุการณ์ — รวมถึงความพยายามที่ถูกบล็อก — จะบันทึกลงใน**บันทึกการตรวจสอบที่ต่อท้ายได้เท่านั้น
เชื่อมโยงด้วยแฮช และอ่านได้แบบสาธารณะ** ฐานข้อมูลจะปฏิเสธการเปลี่ยนสถานะที่ไม่ถูกต้อง
ภายใต้ไคลเอนต์และคีย์ทั้งหมด สิ่งที่ยังไม่สามารถปฏิเสธได้ในปัจจุบันคือการประนีประนอมความปลอดภัยของผู้ดูแลแพลตฟอร์มเอง —
ซึ่งเป็นสิ่งที่การลงนามแบบกำหนดเกณฑ์จะเข้ามาอุดช่องโหว่นี้ และจนกว่าฟีเจอร์นี้จะเปิดตัว คุณควรปฏิบัติต่อคำว่า
"Champollion ไม่ได้ถือครองส่วนแบ่งคีย์ใดๆ" ในฐานะเป้าหมายการออกแบบที่กำลังสร้างขึ้น
ไม่ใช่คุณสมบัติที่คุณสามารถตรวจสอบได้ในปัจจุบัน

## ขั้นตอนที่ 6 — กำหนดรางวัล และประกาศข้อกำหนดของรางวัล

รางวัลเป็นสิ่งที่ไม่บังคับ **การแข่งขันที่ไม่มีการประกาศข้อกำหนดรางวัล ก็คือไม่มีรางวัล** —
นั่นเป็นค่าเริ่มต้น และไม่ได้ถือว่าเป็นการแข่งขันที่ด้อยกว่าแต่อย่างใด

หากคุณต้องการมอบรางวัล ให้ตัดสินใจและเผยแพร่พร้อมกับการแข่งขัน:

- **จำนวนเงินและสกุลเงิน**
- **ผู้สนับสนุน** — ใครเป็นผู้ออกเงินรางวัล
- **เงินรางวัลเก็บไว้ที่ใด** — บัญชีองค์กรของคุณ หรือกองทุนเพื่อชุมชน
  ที่คุณแต่งตั้ง **Champollion จะไม่ถือครอง, ดูแลในบัญชีเอสโครว์, หรือส่งต่อเงินรางวัลเด็ดขาด**
  การเปิดเผยอัตลักษณ์ของผู้ถือครองเงินรางวัลล่วงหน้าคือสิ่งที่ทำให้รางวัลมีความน่าเชื่อถือ;
  ดู[บันทึกความเสี่ยงการผิดนัดชำระของผู้สนับสนุน](/docs/network/sovereignty/terms-templates#trojan-horse-risks)
  ในเทมเพลตข้อกำหนด
- **เงื่อนไขเกณฑ์คะแนน** — แถบระดับคะแนนที่วิธีการจะต้องผ่าน ซึ่งเขียนขึ้น
  ตาม[ข้อกำหนดรางวัล](/docs/network/specifications/prizes): เกณฑ์คะแนน
  chrF++, เกณฑ์การวินิจฉัยใดๆ ที่คุณต้องการ (เช่น การยอมรับ FST ขั้นต่ำ —
  เกณฑ์ที่ผลงานต้องผ่าน ไม่ใช่ตัวคะแนน), ข้อกำหนดการตรวจสอบโดยผู้พูดภาษา,
  ความสามารถในการทำซ้ำได้ กำหนดเงื่อนไขการให้รางวัล
  ให้สามารถตรวจสอบได้จากคะแนนที่เผยแพร่ เพื่อไม่ให้ใครต้องเชื่อคำพูดของคุณ
  (หรือของเรา) ในการตัดสินว่าผ่านเกณฑ์หรือไม่
- **ข้อกำหนดรางวัล** — จะเกิดอะไรขึ้นกับตัวผลงานที่ส่งเข้ามา

### ข้อกำหนดรางวัลขึ้นอยู่กับคุณเป็นผู้เลือก

การรันได้รับการกำหนดไว้อย่างตายตัว: ในการแข่งขันแบบมีอำนาจอธิปไตย ผู้เข้าร่วมจะส่งมอบโมเดลหรือ
วิธีการให้กับคุณ และโหนดของคุณจะเป็นผู้รัน สิ่งที่จะเกิดขึ้นกับมัน*หลังจากนั้น*ขึ้นอยู่กับการตัดสินใจของคุณ
และมีให้เลือกหนึ่งในสามข้อต่อไปนี้:

| ข้อกำหนด | สิ่งที่คุณกำลังบอกกับผู้เข้าร่วม |
|---|---|
| `pass_to_holders` — *ส่งมอบให้ผู้ถือครอง* | วิธีการจะตกเป็นของคุณ ซึ่งเป็นผู้ถือครองเบนช์มาร์กที่มีอำนาจอธิปไตย คุณจะให้คะแนนและเก็บมันไว้ ไม่ว่าใครจะเป็นผู้ชนะก็ตาม |
| `retain_ip` — *คงสิทธิ์ในทรัพย์สินทางปัญญา* | ผู้เข้าร่วมยังคงเป็นเจ้าของ คุณจะให้คะแนนผลงานและเก็บสำเนาที่ปิดผนึกไว้สำหรับการตรวจสอบสิทธิ์เท่านั้น |
| `release_open` — *เผยแพร่แบบเปิด* | ผู้เข้าร่วมยังคงเป็นเจ้าของ แต่ต้องเผยแพร่วิธีการภายใต้สัญญาอนุญาตแบบเปิด การเผยแพร่นั้นคือเงื่อนไขการรับรางวัล |

รายละเอียดจะแปรผันตามข้อกำหนด จึงไม่มีตารางที่ต้องกรอก: สิ่งที่คุณ
จะเก็บไว้ (`retention`), มีการโอนย้ายสิทธิ์ใดๆ หรือไม่ (`rights`), คุณสามารถนำไปใช้เพื่ออะไรได้บ้าง
(`host_use`) และผู้เข้าร่วมจะต้องเผยแพร่หรือไม่ (`release`) ทั้งหมดจะถูก
**อนุมาน**มาจากตัวเลือกที่คุณเลือก ตัวเลือกสองรายการจะอนุญาตให้คุณจำกัดขอบเขต
ได้หนึ่งฟิลด์:

- ภายใต้ `retain_ip` ตัวเลือก `--prize-retention delete_after_scoring` จะทำลายอาร์ติแฟกต์ทันทีหลังจากให้คะแนนแล้ว (ค่าเริ่มต้นจะเก็บสำเนาที่ปิดผนึกไว้เพื่อการตรวจสอบ)
- ภายใต้ `release_open` ตัวเลือก `--prize-release-timing` จะเปลี่ยนการเผยแพร่เป็น `required_before_scores` หรือ `required_after_prize` (ค่าเริ่มต้นคือ `required_before_prize`) และ `--prize-release-license` จะระบุชื่อสัญญาอนุญาตแทนที่จะยอมรับสัญญาอนุญาตที่ผ่านการอนุมัติจาก OSI ใดๆ (`any_osi`)

ตารางอนุมานฉบับเต็ม และวิธีที่แต่ละตัวเลือกได้รับการตรวจสอบก่อนการจ่ายเงินรางวัล ดูได้ที่
[ข้อกำหนดรางวัล §2.1, เงื่อนไขที่ 7](/docs/network/specifications/prizes#condition-7-in-detail-the-term-is-one-choice-of-three)

```bash
# The term…
mt-eval contest prepare … --prize-disposition retain_ip

# …with the one narrowing that option offers
mt-eval contest prepare … --prize-disposition retain_ip \
  --prize-retention delete_after_scoring

# …or the same declaration from a JSON file
mt-eval contest prepare … --prize-terms my-terms.json
```

ไม่ว่าคุณจะเลือกข้อใด ข้อกำหนดจะถูกพิมพ์ออกมาให้คุณเห็นเป็นภาษาธรรมดาพร้อมกับ
**SHA-256** ก่อนที่จะมีการเขียนสิ่งใดลงไป แฮชดังกล่าวคือโทเค็นการยอมรับ:
ผู้เข้าร่วมจะส่งพารามิเตอร์ `--accept-terms <hash>` การยอมรับจะถูกบรรจุลงใน
บันเดิลของพวกเขาและถูกครอบคลุมด้วยแฮชเนื้อหา และโหนดของคุณจะปฏิเสธบันเดิล
ที่ยอมรับข้อกำหนดอื่น ข้อกำหนดจะถูกตรึงทันทีที่การแข่งขันของคุณมีผลงาน
ส่งเข้ามาเป็นชิ้นแรก เพื่อไม่ให้มีใครต้องผูกพันกับข้อกำหนดที่พวกเขาไม่เคยอ่าน

เรื่องเงินจะถูกแยกออกไป*ไม่รวม*อยู่ในข้อกำหนดโดยเจตนา: จำนวนเงิน, สกุลเงิน และ
ผู้สนับสนุนเป็นข้อมูลการแข่งขัน และข้อกำหนดเกี่ยวกับความเป็นเจ้าของในวิธีการ
เป็นข้อความคนละประเภทกับข้อความเกี่ยวกับจำนวนเงินที่จ่าย

## Step 7 — สร้างการแข่งขัน

การแข่งขันบน sealed sets ใช้ **sealed lane** อย่างชัดเจน การมีสิทธิ์เข้าร่วมเป็นแบบ fail-closed: การแข่งขันจะถูกปฏิเสธหากการลงทะเบียน sealed set ของคุณไม่มีอยู่หรือไม่ active — และการสร้างการแข่งขันไม่ได้ให้สิทธิ์ **ใคร** เข้าถึงชุดข้อมูลเลย

```bash
mt-eval contest create \
  --name "EN→CRK Community Challenge 2026" \
  --corpus sealed-eng-crk-v1 \
  --language-pair "en>crk" \
  --visibility public \
  --use-context non-commercial \
  --prize-disposition retain_ip \
  --results-visibility hidden_until_close \
  --anonymize-until-close \
  --description "Community-custodied held-out set; scores-only; prize held by <your org/trust>."
```

แฟล็กสองตัวจากทั้งหมดจะได้รับการกำหนดตายตัวหรือถูกตรึงโดยฐานข้อมูล ไม่ว่าคุณจะทำสิ่งใด
หลังจากนั้น และอีกสามตัวจะเป็น**คำมั่นสัญญา**:

- `--use-context` เป็นส่วนหนึ่งของอัตลักษณ์การแข่งขัน: มันจะถูกกำหนดตายตัวทันที
  ที่ลงทะเบียนการแข่งขันและไม่สามารถเปลี่ยนแปลงได้อีก (ให้สร้างการแข่งขันใหม่แทน)
  ค่าเริ่มต้นคือ `non-commercial`
- `--primary-metric` (ค่าเริ่มต้น `chrf_plus_plus`) ซึ่งเป็นเมทริกที่ใช้จัดอันดับ
  จะถูกตรึงเมื่อการแข่งขันมีผลงานส่งเข้าประกวดชิ้นแรก การแข่งขันใหม่ที่ระบุค่า
  `composite` เดิมที่ยกเลิกไปแล้วจะถูกปฏิเสธพร้อมเหตุผล ส่วนการแข่งขันที่ลงทะเบียนก่อน
  [มาตรฐานการให้คะแนน](/docs/network/specifications/scoring#how-runs-are-scored)
  จะยังคงทำงานได้ตามเดิม
- `--visibility` (ค่าเริ่มต้น `public`), `--description` และสถานะการเปิดรับผลงาน
  จะไม่ถูกตรึง

คำมั่นสัญญาทั้งสามประการจะถูกตรึงทันทีที่การแข่งขันของคุณมีผลงานชิ้นแรก:

- `--prize-disposition` / `--prize-terms` — ข้อกำหนดจากขั้นตอนที่ 6 หากละเว้นทั้งคู่
  การแข่งขันนั้นจะไม่มีรางวัล
- `--results-visibility hidden_until_close` — ทุกคะแนนที่โหนดของคุณวัดได้
  จะถูก**ระงับไว้**จนกว่าคุณจะปิดการแข่งขัน เพื่อไม่ให้ใครปรับจูนเข้าหา
  ชุดข้อมูลที่ปิดผนึกจากผลลัพธ์ของตนเอง นี่คือค่าเริ่มต้น ตัวอย่างระบุไว้
  เพื่อให้เห็นคำมั่นสัญญานี้อย่างชัดเจนในบันทึกของคุณเอง ให้ส่งพารามิเตอร์
  `--results-visibility immediate` หากคุณต้องการกระดานคะแนนแบบสดแทน โดยแต่ละ
  การ์ดจะเผยแพร่ทันทีที่โหนดของคุณดำเนินการเสร็จสิ้น
- `--anonymize-until-close` — ผู้เข้าร่วมจะปรากฏภายใต้นามแฝงที่คงที่ในการ
  จัดอันดับของคุณในขณะที่การแข่งขันยังเปิดอยู่ (นี่คือมุมมองการจัดอันดับของคุณ มันไม่ได้
  ปกปิดตัวตนของการ์ดเมื่อเผยแพร่ไปยังกระดานสาธารณะแล้ว)

แฟล็กทั้งสามตัวนี้สามารถใช้งานได้ใน `contest prepare` และ `contest register`
ซึ่งเป็นที่ที่ผู้จัดส่วนใหญ่จะตั้งค่าไว้ เนื่องจากช่องทางเหล่านั้นจะสร้าง
การแข่งขันให้คุณ เมื่อใช้ `contest prepare --no-register` แฟล็กการลงทะเบียน
ที่คุณส่งไป (`--results-visibility`, `--anonymize-until-close`,
`--primary-metric`, แฟล็กรางวัล, `--visibility`, `--use-context`,
`--closed-intake`) จะถูกบันทึกไว้ใน `local/manifest.json` และ
`contest register --manifest` จะนำไปปรับใช้ เว้นแต่คุณจะส่งแฟล็กของมันเองเข้าไป
และจะแจ้งให้ทราบเมื่อมีค่าใดเข้าไปแทนที่ค่าที่บันทึกไว้ คำสั่ง prepare จะพิมพ์
ข้อกำหนดแต่ละข้อเหล่านี้พร้อมค่าของมัน ไม่ว่าคุณจะเป็นผู้กำหนดหรือเป็นค่าเริ่มต้น
และแจ้งเวลาที่จะไม่สามารถเปลี่ยนแปลงได้อีก ก่อนที่จะมีการลงทะเบียนสิ่งใด
พารามิเตอร์ `--help` จะระบุค่าเริ่มต้นของแต่ละตัว

*(ค่า `--corpus` คือ `sealed_set_id` ที่คุณลงทะเบียนไว้ sealed lane ถูกเลือก **โดยอัตโนมัติ** จากการลงทะเบียน sealed set — ไม่ต้องใช้ flag เพิ่มเติม sealed set ไม่สามารถสนับสนุนการแข่งขันทั่วไปได้ และ quarantined dataset ทั่วไปไม่สามารถสนับสนุนการแข่งขันใดๆ ได้ ทั้งสองกฎบังคับใช้ในฐานข้อมูลใต้ทุก client หากคุณลงทะเบียนใน Step 4 ด้วย `contest register` หรือ `prepare --self-serve` row ของการแข่งขัน **มีอยู่แล้ว** — ข้ามขั้นตอนนี้ไป `contest create` ด้วยตนเองใช้เฉพาะสำหรับการประกอบการแข่งขันจาก sealed set ที่ลงทะเบียนไว้แล้ว)*

## Step 8 — วิธีการต้องผ่านการคัดเลือกจากสาธารณะก่อน

นักพัฒนาจะสร้างและให้คะแนนวิธีการของตนเองบน**ชุดข้อมูล dev สาธารณะ**
ที่คุณเผยแพร่ในขั้นตอนที่ 1 โดย `current_qualifier_id` ของชุดข้อมูลที่ปิดผนึกจะระบุรอบดังกล่าว และ
วิธีการจะต้องผ่านเกณฑ์ของรอบนี้ก่อน จึงจะสามารถขอรับการรันบนชุดที่ปิดผนึกได้ ซึ่งจะ
ช่วยลดแรงกดดันในการลองส่งตรวจเช็กคลังข้อมูลของคุณ: ไม่มีใครมีสิทธิ์เข้าถึงชุดข้อมูลที่ปิดผนึก
จนกว่าพวกเขาจะแสดงให้เห็นถึงประสิทธิภาพที่แท้จริงในพื้นที่เปิดเสียก่อน

ผู้เข้าร่วมสามารถรันด้วยตนเองแบบออฟไลน์ได้ด้วยคำสั่งเดียว:

```bash
mt-eval contest qualify <contest-id> --dev my-dev-output.txt \
    --dev-corpus <the dev corpus you released> \
    --system "acme-nmt" --method-class pipeline \
    --offline-qualifier-id <qualifier id> --offline-threshold <threshold>
```

รหัสตัวคัดกรองและเกณฑ์คะแนนคือข้อมูลสองอย่างที่การให้คะแนนต้องการจาก
คุณ ดังนั้นโปรดประกาศทั้งสองอย่างพร้อมกับการเปิดตัว dev สำหรับการแข่งขันที่สร้างขึ้นด้วย `contest
prepare` รหัสตัวคัดกรองคือรหัสของคลังข้อมูล dev เอง
(`dataset.corpus_id` ของมัน) และ prepare จะเขียนเกณฑ์คะแนนลงในคำอธิบายของคลังข้อมูล dev
หากไม่มีแฟล็ก `--offline-…` ทั้งสองตัว qualify จะอ่านค่าจาก
ฐานข้อมูลการแข่งขันแทน ซึ่งจะทำงานได้ก็ต่อเมื่อการแข่งขันได้รับการลงทะเบียนบน
เอนด์พอยต์ที่ผู้เข้าร่วมชี้ไปแล้วเท่านั้น เมื่อไม่พบข้อมูลที่นั่น หรือไม่สามารถเข้าถึงฐานข้อมูลได้
คำสั่ง qualify จะหยุดทำงานและพิมพ์คำสั่งออฟไลน์ด้านบนออกมา โดยกรอก
อาร์กิวเมนต์ของผู้เข้าร่วมลงไปให้เสร็จสรรพ

`--dev` รับไฟล์คำแปลชุด dev ของผู้เข้าร่วมแบบบรรทัดละหนึ่งประโยค
ตามลำดับของคลังข้อมูล, ในรูปแบบ JSON ที่ใช้ entry id เป็นคีย์, หรือเป็นบันทึกการรันที่ `mt-eval run
--corpus <the dev corpus>` wrote (or its `_report.json`) บันทึกการรันจะถูกอ่านตาม
entry id และตรวจสอบว่าเป็นการรันบนคลังข้อมูล dev เดียวกันนั้น บันทึกที่มี
รายการที่เกิดข้อผิดพลาดจะถูกปฏิเสธ เนื่องจากทุกรายการจะต้องได้รับการให้คะแนน จากนั้นสรุปผลจะระบุว่า
ผลลัพธ์นั้นสร้างขึ้นโดย harness ในการรันนั้นและให้คะแนนใหม่จากไฟล์ดังกล่าว
(พร้อมต้นทุนของการรันนั้น) โดยจะไม่ระบุว่าสร้างขึ้นนอก harness; มีเพียง
ไฟล์สมมติฐานธรรมดาเท่านั้นที่จะถูกอธิบายในลักษณะนั้น

**การผ่านเกณฑ์ยังไม่ใช่การส่งผลงาน** หลังการตัดสิน qualify จะบอกสิ่งที่
สามารถบอกได้ล่วงหน้าเกี่ยวกับการส่งผลงาน สำหรับการรันปลั๊กอินวิธีการที่มีโฟลเดอร์
อยู่บนเครื่อง มันจะรันการสแกนสถิติแบบเดียวกับที่ `submit-method` และโหนดของคุณ
รัน (ไลบรารีเครือข่าย, เครื่องมือเครือข่ายของเชลล์, พาธระบบไฟล์ที่ต้องห้าม) และ
แสดงสิ่งใดก็ตามที่จะถูกปฏิเสธ เช่น ปลั๊กอินที่อิมพอร์ต `urllib`
เพื่อเรียกใช้เซิร์ฟเวอร์โมเดล สำหรับการรันพาธ LLM ของ harness เอง (โมเดล
ที่เข้าถึงผ่านผู้ให้บริการ) มันจะแจ้งว่าไม่มีวิธีการที่จะส่งได้ในสภาพที่เป็นอยู่:
โหนดจะรันผลงานโดยไม่มีการเชื่อมต่อเครือข่าย ดังนั้นโมเดลจึงต้องเดินทางอยู่ภายในบันเดิล
(ดู *รวมทุกโมเดลที่วิธีการของคุณเรียกใช้ไว้ในบันเดิล* ด้านล่าง) มิฉะนั้นบรรทัดที่แจ้งว่าผ่าน
จะระบุการตรวจสอบที่ยังรออยู่ข้างหน้าในเวลาส่งผลงาน สิ่งเหล่านี้ไม่ได้เปลี่ยนแปลง
คำตัดสินหรือใบเสร็จ

มันจะพิมพ์คะแนนตัวคัดกรอง (สิ่งที่ใช้ตัดสิน) และเกณฑ์คะแนนควบคู่กัน
ทั้งสองอยู่บนสเกลตัวคัดกรอง chrF++ 0–100 จากนั้นจะบอกว่าคะแนนนั้นคืออะไร: chrF++
ระดับคลังข้อมูลพร้อมลายเซ็น sacreBLEU, เมทริกมาตรฐานอื่นๆ ที่อยู่ข้างเคียง
(ไม่นำมาผสมกัน), exact match เป็นการวินิจฉัยที่ไม่นำมาเป็นเกณฑ์ตัดสิน และข้อควรระวัง
ของคะแนนใดๆ qualify จะไม่เผยแพร่สิ่งใด ระบบที่ผลลัพธ์ dev
ส่วนใหญ่เป็นการคัดลอกข้อความต้นฉบับจะถูกปฏิเสธไม่ว่าจะได้คะแนนเท่าใดก็ตาม:
เมื่อผลลัพธ์ครึ่งหนึ่งหรือมากกว่านั้นเหมือนกับต้นฉบับ (ไม่สนใจตัวพิมพ์เล็กพิมพ์ใหญ่ เครื่องหมายกำกับเสียง และวรรคตอน
และละเว้นบรรทัดที่ข้อความอ้างอิงเป็นตัวต้นฉบับเอง เช่น ชื่อเฉพาะ) ผู้เข้าร่วมไม่ได้กำลังแปล
กฎเดียวกันนี้จะปฏิเสธอีกครั้งเมื่อโหนดของคุณรันซ้ำ การดำเนินการนี้จะเขียน **ใบเสร็จตัวคัดกรอง**
ลงบนเครื่องของพวกเขา ซึ่ง `submit-model` และ `submit-method` จะปฏิเสธที่จะสร้าง
การส่งผลงานหากไม่มีใบเสร็จนี้ ใบเสร็จจะถูกเก็บแยกตามการแข่งขันและตามระบบ (`--system`)
ดังนั้นผู้เข้าร่วมที่ผ่านการคัดกรองสองระบบจะเก็บไว้ได้ทั้งสองใบเสร็จ การคัดกรอง
ระบบเดิมซ้ำจะเก็บใบเสร็จก่อนหน้าไว้ควบคู่กัน `submit-method` และ
`submit-model` จะใช้ใบเสร็จสำหรับ `--system` (ค่าเริ่มต้น: ใบเสร็จสำหรับ `--name`,
มิฉะนั้นจะเป็นใบเสร็จเพียงใบเดียวของการแข่งขัน) และจะปฏิเสธพร้อมแสดงรายการ หากเกิดความคลุมเครือ
ใบเสร็จถูกสร้างขึ้นโดย
เป็นการรายงานตนเอง — จึงไม่ใช่สิ่งที่ใช้ตัดสินขั้นสุดท้าย ก่อนที่จะมีการ
อนุมัติสิทธิ์ใดๆ **โหนดของคุณจะรันวิธีการที่ส่งเข้ามาซ้ำอีกครั้งบนชุดข้อมูล dev เดียวกัน** และ
เปรียบเทียบการวัดของตนเองกับการกล่าวอ้าง ใบเสร็จที่ระบุคะแนนของวิธีการเกินจริง
จะถูกปฏิเสธที่จุดนี้ โดยมีข้อมูลคะแนนที่อ้างเทียบกับคะแนนที่วัดได้แสดงในการปฏิเสธ

**ใบเสร็จจะระบุการรันที่เป็นที่มา** เมื่อ `--dev` เป็นบันทึกการรัน (หรือ
`_report.json` ของมัน) ใบเสร็จจะบันทึกการรันและโมเดลที่ใช้รัน: สำหรับ
`mt-eval run --method local-model -m <model>` จะระบุ Hugging Face id และ
revision หรือไดเรกทอรีโมเดลพร้อม SHA-256 ของไฟล์ต่างๆ บันทึกการรันของ
`local-model` ที่ไม่ระบุชื่อโมเดลจะถูกปฏิเสธ — บิลด์ 0.2.0 รุ่นก่อนหน้า
ไม่ได้ส่ง `-m` ไปยังเอ็นจินนั้น ซึ่งทำให้มันไปรันโมเดลสำรองภาษาอังกฤษ→สเปน
แทน จากนั้น `submit-model` จะตรวจสอบว่าค่าน้ำหนักที่บรรจุอยู่ในบันเดิลนั้น
เป็นหนึ่งในไฟล์ที่ใบเสร็จระบุชื่อไว้ และจะปฏิเสธพร้อมระบุแฮชทั้งสองตัว หาก
ไม่ตรงกัน ใบเสร็จที่ได้คะแนนมาจากไฟล์สมมติฐานธรรมดาจะไม่ระบุชื่อโมเดล
การรันซ้ำของโหนดจะเป็นตัวตรวจสอบสำหรับกรณีนี้

**ส่วนต่างระหว่างใบเสร็จและโหนดจะถูกแจ้งเตือน** ตัวเลขทั้งสองคำนวณด้วย
วิธีเดียวกัน — ตัวให้คะแนนเดียวกัน, ชุดข้อมูล dev เดียวกัน และสำหรับโมเดลจะใช้
กฎความยาวการถอดรหัสแบบเดียวกัน — ดังนั้นค่าน้ำหนักเดียวกันจะให้ผลลัพธ์ต่างกันไม่เกินเศษเสี้ยว
ของคะแนน เมื่อตัวเลขของโหนดและของใบเสร็จต่างกันมากกว่า **2.0
คะแนน** บนสเกลตัวคัดกรอง 0–100 โหนดจะแจ้งให้ทราบหลังจากการ
รันซ้ำ; โหนดแบบแอร์แก็ปจะบันทึกส่วนต่างนี้พร้อมการตรวจสอบไว้ในบัญชีแยกประเภทในเครื่อง
และพิมพ์ออกมาให้ผู้ดูแลเห็นอีกครั้งที่คำสั่ง `node approve
--offline` นี่เป็นเพียงการแจ้งเตือน ไม่ใช่การปฏิเสธ:
ตัวเลขของโหนดเองคือสิ่งที่เป็นเกณฑ์ตัดสิน (เกณฑ์ 2.0 เป็นค่าที่ตั้งไว้อย่าง
รัดกุมโดยเจตนาเพื่อให้แจ้งเตือนได้ง่าย ซึ่งเป็นค่านโยบายที่ผู้จัดการแข่งขัน
อาจต้องการทบทวนใหม่ได้)

### ผู้เข้าร่วมสามารถซักซ้อมทุกอย่างได้ก่อนที่จะส่งผลงานจริง

ไม่ควรมีใครต้องมารู้ว่าบันเดิลของตนมีรูปแบบไม่ถูกต้องจากการถูกปฏิเสธในอีกหลายวัน
ถัดมา `mt-eval contest validate` จะรันบนเครื่องของผู้เข้าร่วมโดยไม่มี
การเชื่อมต่อเครือข่าย แบบเดียวกับที่โหนดของคุณรันในขั้นแรกทุกประการ:

```bash
# the static checks your node runs on a bundle
mt-eval contest validate ./my-bundle.tar.gz

# …and the qualifier: does my dev output line up, and does it clear the bar?
mt-eval contest validate ./my-bundle.tar.gz --contest <contest-id> \
    --dev my-dev-output.txt --dev-corpus <released dev corpus>
```

คำสั่งจะพิมพ์ตารางผลการตรวจสอบและส่งรหัสออก (exit code) ที่ไม่ใช่ศูนย์หากมีสิ่งใดที่จะถูกปฏิเสธ
(`--json` สำหรับเครื่องมืออัตโนมัติ) แนะนำให้ผู้เข้าร่วมใช้คำสั่งนี้ในประกาศเชิญชวนเข้าร่วม:
พวกเขาใช้คำสั่งเพียงคำสั่งเดียวแต่ช่วยลดภาระการปฏิเสธผลงานของคุณได้มาก

`validate` จะไม่เขียนสิ่งใด มันจะให้คะแนนผลลัพธ์ของ dev ซ้ำโดยไม่เขียน
ใบเสร็จ จากนั้นจึงตรวจสอบใบเสร็จ:

- **บันเดิลที่แพ็กแล้ว** (ไฟล์ `.tar.gz` ที่คำสั่ง submit เขียนขึ้น) จะบรรจุ
  ใบเสร็จที่แพ็กมาด้วย และสำเนานั้นคือชุดที่โหนดของคุณอ่าน ดังนั้น
  validate จะตรวจสอบการซักซ้อมเทียบกับสำเนานั้น นอกจากนี้ยังค้นหาใบเสร็จ
  บนเครื่องของผู้เข้าร่วมที่เป็นที่มาของสำเนาดังกล่าวและระบุชื่อระบบของมัน ไม่ว่า
  วิธีการของบันเดิลจะตั้งชื่อว่าอะไรก็ตาม ระบบจะเตือนเมื่อ `--system` ระบุชื่อ
  ใบเสร็จคนละใบ และเมื่อผู้เข้าร่วมได้ทำการคัดกรองระบบนั้นซ้ำอีกครั้งนับตั้งแต่
  การแพ็กบันเดิล (บันเดิลจะยังคงบรรจุใบเสร็จอันเก่าอยู่) หากไม่มี
  แฟล็ก `--offline-…` รหัสตัวคัดกรองและเกณฑ์คะแนนจะนำมาจาก
  สำเนานั้นด้วย ซึ่งหมายความว่าเป็นค่าที่ผู้เข้าร่วมระบุให้กับ `contest qualify`
  ผลการตรวจสอบจะแจ้งให้ทราบ
- **ไดเรกทอรีต้นทาง** ที่แพ็กไว้สำหรับการตรวจสอบด้วย `--manifest`: validate
  จะใช้ใบเสร็จที่ `submit-method` และ `submit-model` จะฝังลงไป ซึ่งค้นพบ
  ด้วยวิธีเดียวกับที่คำสั่งเหล่านั้นใช้: `--system` มิฉะนั้นจะเป็นใบเสร็จที่ตั้งชื่อตาม
  วิธีการของบันเดิล หรือมิฉะนั้นจะเป็นใบเสร็จเพียงใบเดียวของการแข่งขัน

ระบบจะเตือนเมื่อใบเสร็จนั้นครอบคลุมผลลัพธ์ dev ที่แตกต่างกัน, เป็นไฟล์ dev อื่น หรือ
ตัวคัดกรองอื่น นอกจากนี้ยังเตือนเมื่อไม่มีใบเสร็จ ใบเสร็จจะมาจาก
`contest qualify` เท่านั้น

นี่เป็นการซักซ้อม และระบบจะแจ้งเช่นนั้น โหนดของคุณจะยังคงสร้างอิมเมจโดยไม่มี
การเชื่อมต่อเครือข่าย รันคอนเทนเนอร์ และรันตัวคัดกรองซ้ำด้วยตนเอง การที่ validate ผ่านเรียบร้อย
หมายความว่ายังไม่มีสิ่งใดที่*ตรวจพบอยู่แล้ว*ว่าผิดพลาด — ไม่ได้รับประกันว่าการรันจริงจะได้คะแนน

:::note[สำหรับผู้เข้าร่วม: การแข่งขันของคุณอยู่บนเอนด์พอยต์ใด?]
การแข่งขันแบบ**โฮสต์บนเครือข่าย** ไม่จำเป็นต้องตั้งค่าเอนด์พอยต์ใดๆ — เอนด์พอยต์เริ่มต้นที่
harness ติดตั้งมาด้วยจะมีกลไกการแข่งขันอยู่แล้ว (เกณฑ์คัดกรอง, การเสนอ
วิธีการ, การอนุญาต) และ `mt-eval contest submit-model` /
`submit-method` จะสื่อสารกับมันโดยตรง คุณต้องใช้ harness **เวอร์ชัน 0.2.0 หรือใหม่กว่า**
(`mt-eval --version`); รุ่นก่อนหน้านี้จะไม่มี `qualify`, `validate`, `rank` และ
`close` การแข่งขันแบบโฮสต์บนเครือข่ายจะเปิดก็ต่อเมื่อผู้จัดการแข่งขันได้รับการลงทะเบียน
ผ่านช่องทางที่อธิบายไว้ในข้อควรระวังข้างต้น ดังนั้นการแข่งขันส่วนใหญ่ในปัจจุบันจึงเป็นแบบ
**รวมศูนย์ (federated)**

การแข่งขันแบบ **federated** — ผู้จัดงานรันกลไกบน Supabase project ของตนเอง ดังนั้นการส่งจึงไม่ผ่านของเรา — เผยแพร่ endpoint พร้อมกับเอกสารการแข่งขัน ส่งออกก่อนส่งผลงาน:

```bash
export MT_EVAL_SUPABASE_URL=https://<contest-host>.supabase.co
export MT_EVAL_SUPABASE_ANON_KEY=<contest-anon-key>
```

หาก harness ชี้ไปยัง endpoint ที่ไม่มีกลไกการแข่งขัน (เช่น federated host ที่ขาด migration) คำสั่งจะหยุดพร้อมข้อความ *"the contest lane isn't available on this Supabase endpoint yet"* และบอกคุณว่ากำลังคุยกับ endpoint ใด (ผู้จัดงานแบบ federated: เผยแพร่สองค่านี้ควบคู่กับการเผยแพร่ corpus ของคุณ, `--node-id` และ `--corpus-version`)
:::

## Step 9 — Sealed runs: ขอ, อนุมัติ, รัน, ส่งออกคะแนน

สำหรับแต่ละผลงาน:

1. จะมีการยื่น **คำขอ (request)** เทียบกับชุดข้อมูลที่ปิดผนึกของคุณ — มันจะเข้าสู่ `pending` และ
   พกลายนิ้วมือที่ไม่สามารถเปลี่ยนแปลงได้ของ (แฮชบันเดิล, รหัสคลังข้อมูล, เวอร์ชัน
   คลังข้อมูล, `scores-only`, ผลการวัดของโหนดประเมินผล)
2. โหนดของคุณจะรัน **การตรวจสอบสถิติของตนเอง** บนบันเดิล สำหรับผลงานที่เป็นโค้ด
   (เลน B) จากนั้นจะตรวจสอบว่าสามารถรันได้หรือไม่: มีรันไทม์คอนเทนเนอร์
   อยู่หรือไม่ และ RAM, พื้นที่ดิสก์ชั่วคราว (scratch disk) และเวลาการรันที่บันเดิลประกาศไว้นั้น สอดคล้องกับ
   ขีดจำกัด `sandbox` ของคุณหรือไม่ หากไม่ผ่านตรงนี้ จะไม่ถือเป็นคำตัดสินต่อวิธีการ การ
   ปฏิเสธจะระบุทุกค่าที่ไม่ตรงกัน ("ขอ RAM 8 GB แต่โหนดนี้อนุญาต 4 GB
   (sandbox.max_ram_gb)") จะไม่มีสิ่งใดถูกรันหรือถูกปฏิเสธทิ้ง และคำขอจะคงอยู่
   เช่นเดิม คุณสามารถเพิ่มขีดจำกัดใน `node.json` และรันคำสั่ง
   `mt-eval node run-method <id>` ซ้ำได้โดยไม่ต้องส่งผลงานใหม่ หรือผู้เข้าร่วมสามารถ
   แพ็กเกจใหม่ด้วยแฟล็กตามที่การปฏิเสธระบุ (เช่น `--ram-gb 4`);
   ข้อกำหนดเหล่านี้อยู่ภายในแฮชของบันเดิล ดังนั้นจึงถือเป็นคำขอใหม่
   จากนั้นโหนดจะ **รันการอ้างสิทธิ์ตัวคัดกรองของผู้เข้าร่วมซ้ำ** บนสำเนา
   ของชุดข้อมูล dev สาธารณะของตนเอง ใบเสร็จของพวกเขาคือคำกล่าวอ้าง; นี่คือ
   การวัดจริง หากไม่ผ่านเกณฑ์จะ
   ถูกปฏิเสธที่นี่ — ก่อนที่จะขอให้ผู้ดูแลคนใดอนุมัติสิ่งใด และก่อนที่
   ชุดข้อมูลที่ปิดผนึกจะถูกเปิด — และการปฏิเสธจะระบุสิ่งที่อ้าง สิ่งที่วัดได้
   และเกณฑ์ที่กำหนดไว้ บันเดิลที่ยอมรับข้อกำหนดรางวัลอื่นนอกเหนือ
   จากที่การแข่งขันของคุณประกาศไว้ จะถูกปฏิเสธที่จุดนี้เช่นกัน
3. **ผู้ดูแลของคุณตัดสินใจ** (M-of-N) การอนุมัติจะสร้าง **สิทธิ์ (grant)**: ใช้ได้ครั้งเดียว,
   มีวันหมดอายุ, ใช้ได้เฉพาะกับลายนิ้วมือที่ตรงกันทุกประการนั้นเท่านั้น
4. การประเมินผลจะรันในแซนด์บ็อกซ์ที่ตัดการเชื่อมต่อเครือข่ายบนโหนด **ของคุณ**
   (`mt-eval node run-method`): คอนเทนเนอร์ที่ไม่มีสแตกเครือข่าย ข้อความอ้างอิง
   จะถูกเก็บไว้นอกคอนเทนเนอร์ — หรือเพื่อการแยกส่วนความปลอดภัยขั้นสูงสุด สามารถรันบนเครื่องแอร์แก็ปที่แท้จริง
   โดยมีบันเดิลเฉพาะคะแนนที่ลงนามแล้วส่งผ่านสื่อบันทึกข้อมูลที่ถอดเสียบได้ (ดูสถานะในกล่องข้อความ
   ด้านบนสำหรับสิ่งที่ครอบคลุมและไม่ครอบคลุม) โหนดที่มืด (dark node - ออฟไลน์) จะไม่อัปโหลดสิ่งใด: คุณ
   จะนำบันเดิลคะแนนที่ลงนามแล้วของมันออกมาและเผยแพร่การ์ดการรันจากเครื่องที่เชื่อมต่อเครือข่าย
   (`mt-eval node relay`) ชุด holdout ที่ปิดผนึกของคุณและชุดทดสอบของบุคคลที่สามที่ประกาศไว้จะรันอยู่ภายใน
   การรันที่ได้รับอนุญาต **เดียวกัน** ดังนั้นจึงไม่ทำให้ผู้ดูแลของคุณต้องทำพิธีการเพิ่มเติม
5. **มีเฉพาะคะแนนเท่านั้นที่ออกจากระบบ** กฎการปล่อยข้อมูลแบบ `scores-only` ถูกปักหมุดไว้ที่
   ระดับฐานข้อมูล; ข้อความรายรายการจากคลังข้อมูลของคุณจะไม่ถูกเผยแพร่อย่างเด็ดขาด
6. หากการแข่งขันของคุณให้คำมั่นสัญญา `hidden_until_close` คะแนนจะยังไม่ถูกเผยแพร่
   ในทันที: แต่จะถูก **ระงับไว้** ในฐานะผลลัพธ์ที่เลื่อนเวลาออกไปซึ่งมีเพียงคุณเท่านั้นที่เห็นได้ และ
   คำสั่ง `contest close` จะเผยแพร่การ์ดที่ถูกระงับไว้ทั้งหมดก่อนที่จะตรึง
   การจัดอันดับ ผลลัพธ์ที่ระงับไว้จะไม่สูญหายไปไหน
7. ทุกขั้นตอน — คำขอ, การลงคะแนน, สิทธิ์, การใช้งาน และความพยายามใดๆ ที่ถูกบล็อก — จะถูก
   ต่อท้ายลงในบันทึกการตรวจสอบสาธารณะที่เชื่อมโยงด้วยแฮช ซึ่งคุณ (และใครก็ตาม) สามารถตรวจสอบย้อนหลังได้

## การส่งวิธีการ (สำหรับผู้เข้าร่วม) — สองเลน

ผลงาน NMT ส่วนใหญ่ไม่ได้มีความแปลกใหม่พิสดาร: เป็นทรานส์ฟอร์เมอร์มาตรฐานที่ปรับแต่งมาแล้วและ
ค่าน้ำหนักของมัน สำหรับกรณีเหล่านี้ จะมี **เลนที่ปราศจากโค้ดซึ่งเป็นเลนแนะนำ** — และมีแซนด์บ็อกซ์
เป็นทางเลือกสำรองสำหรับวิธีการที่เป็นโค้ดจริงๆ

### เลน A — โมเดลเชิงประกาศ (แนะนำสำหรับ NMT มาตรฐาน)

หากวิธีการของคุณเป็นโมเดลนิวรัลมาตรฐาน คุณจะส่งมันในรูปแบบ **ข้อมูล (data)** — ซึ่งประกอบด้วย
ค่าน้ำหนัก, โทเคไนเซอร์ และการกำหนดค่า — และผู้จัดการแข่งขันจะรันมันในเอ็นจินการอนุมาน
ที่เชื่อถือได้ของพวกเขาเอง **ไม่มี Dockerfile, ไม่มีโค้ด, ไม่มีแซนด์บ็อกซ์** เนื่องจากไม่มีสิ่งใดที่คุณ
ส่งเข้ามาถูกประมวลผล การตรวจสอบความปลอดภัยของผู้จัดจึงเป็นการตรวจสอบรูปแบบที่ตัดสินได้ชัดเจน
แทนที่จะต้องพยายามพิสูจน์ว่าโค้ดใดๆ ปลอดภัยหรือไม่ — ซึ่งเป็นการรับประกันที่รัดกุมกว่าอย่างแท้จริง
สำหรับคุณและสำหรับคลังข้อมูล

```bash
mt-eval contest submit-model <contest-id> \
  --model-dir ./my-model \          # config.json + model.safetensors + tokenizer.* at the ROOT
  --name "My NMT" --version 2.0 \
  --architecture MarianMTModel \    # must be on the organizer's trusted whitelist
  --method-class pipeline --paradigm neural-nmt \
  --track constrained --training-data-file ./training-data.txt \
  --parameter-count 92487 \
  --weights-license Apache-2.0 --weights-public \
  --developer "Your Name" --node-id <organizer-advertised-node-id> --agree
```

**โมเดลที่เทรนด้วย NMT Forge** `nmt-forge export` จะเขียน
โฟลเดอร์ที่พร้อมปรับใช้ `export/model/` นอกจากค่าน้ำหนัก การกำหนดค่า และโทเคไนเซอร์แล้ว
มันยังเก็บ `forge-model.json` (คะแนนของโมเดลนั้นบนชุดทดสอบส่วนตัวของคุณ
และพาธในเครื่อง), `DEPLOY.md` และ `champollion-plugin/` ซึ่งไม่มีส่วนใด
เป็นส่วนหนึ่งของผลงาน `submit-model` จะแพ็กเฉพาะไฟล์ที่ transformers ใช้อ่าน
(ค่าน้ำหนัก, `config.json`, `generation_config.json`, ไฟล์โทเคไนเซอร์) และ
พิมพ์ทุกสิ่งที่ตัดออกไป ดังนั้นไฟล์ทั้งสามนั้นจึงถูกคัดแยกออกไปเองโดยอัตโนมัติ
ส่วนที่ 6 ของ `DEPLOY.md` นั้นจะแสดงรายการไฟล์ที่ประกอบเป็นผลงาน,
สถาปัตยกรรมจาก `config.json` และจำนวนพารามิเตอร์ที่อ่านได้จาก
ส่วนหัวของไฟล์ค่าน้ำหนัก พร้อมคำสั่งที่ถูกต้อง หากต้องการส่งเฉพาะไฟล์ที่คุณ
ได้ตรวจสอบแล้ว ให้คัดลอกไฟล์เหล่านั้นลงในโฟลเดอร์ของมันเองและส่งเป็น
`--model-dir`:

```bash
mkdir -p lane-a
cp export/model/config.json export/model/generation_config.json \
   export/model/model.safetensors export/model/tokenizer.json \
   export/model/tokenizer_config.json lane-a/      # the files DEPLOY.md §6 lists
mt-eval contest submit-model <contest-id> --model-dir lane-a \
  --architecture MarianMTModel --paradigm neural-nmt …
```

**จำนวนพารามิเตอร์ใดที่ต้องใช้** เลน A จะตรวจสอบ `--parameter-count` เทียบกับ
ไฟล์ค่าน้ำหนัก โดยจะบวกขนาดของเทนเซอร์ในส่วนหัว `safetensors` และ
ปฏิเสธคำกล่าวอ้างที่คลาดเคลื่อนเกิน 1% นั่นคือสิ่งที่ไฟล์เก็บไว้จริง และอาจ
แตกต่างจากการนับใน torch ค่าน้ำหนักที่ผูกไว้ (tied) หรือใช้ร่วมกันจะถูกบันทึกเพียงครั้งเดียว ตาราง
ที่โมเดลสร้างขึ้นใหม่เมื่อโหลด เช่น ตำแหน่งแบบไซนูซอยด์ (sinusoidal positions) อาจไม่ถูก
บันทึกไว้เลย ข้อความปฏิเสธจะพิมพ์จำนวนที่นับได้จากไฟล์; ให้ประกาศด้วยตัวเลขนั้น

กฎเกณฑ์ที่บันเดิลของคุณต้องผ่าน (ตรวจสอบในเครื่องก่อนอัปโหลด และตรวจสอบซ้ำ
โดยโหนดของผู้จัดการแข่งขัน):

- **ค่าน้ำหนักต้องเป็น `safetensors` ไม่ใช่ pickle เด็ดขาด** PyTorch `.bin`/`.pt`/`.ckpt`
  เป็น pickle — ซึ่งเป็นโค้ดใดๆ ที่จะรันเมื่อโหลด — และจะถูกปฏิเสธ ให้เอ็กซ์พอร์ตเป็น
  `model.safetensors` (`safetensors` / `transformers` ทำสิ่งนี้ได้ในตัว)
- **สถาปัตยกรรมที่เอ็นจินของผู้จัดสามารถโหลดได้ในตัว** `architectures` ของ `config.json`
  สามารถเป็นสถาปัตยกรรมใดก็ได้ที่ `transformers` ของโฮสต์รองรับ
  (Marian, NLLB/M2M100, mBART, T5, Pegasus และอื่นๆ อีกมากมาย) — โฮสต์จะ
  **เปิดกว้างตามค่าเริ่มต้น** เนื่องจากเมื่อใช้ `trust_remote_code=False` ความปลอดภัย
  จะมาจากรูปแบบที่ไร้โค้ด ไม่ใช่จากชื่อสถาปัตยกรรม (สถาปัตยกรรมที่ไม่รองรับ
  ก็เพียงแค่โหลดไม่ผ่าน และไม่มีสิ่งใดถูกรัน) โฮสต์ที่รอบคอบอาจ
  เผยแพร่รายการที่อนุญาต ห้ามมี `auto_map`, ห้ามมี `trust_remote_code` — สิ่งเหล่านี้จะแอบแฝง
  โค้ดที่กำหนดเองกลับเข้ามา และจะถูกปฏิเสธเสมอ
- **โทเคไนเซอร์เชิงประกาศ** (`tokenizer.json` หรือ `sentencepiece` `.model` +
  vocab) และ **เฉพาะไฟล์ข้อมูลเท่านั้น** — ห้ามมี `.py`/สคริปต์/ไบนารีในบันเดิล

**สิ่งที่ `submit-model` ทำการแพ็ก** ไฟล์ข้อมูลที่อยู่ที่รูทของ `--model-dir`
(`.safetensors`, `.json`, `.model`, `.txt`, `.spm`, `.vocab`, `.merges`):
ค่าน้ำหนัก, การกำหนดค่า, โทเคไนเซอร์ และการกำหนดค่าการสร้างข้อความ สิ่งอื่นทั้งหมด — เช่น
`README.md` หรือ `DEPLOY.md`, โฟลเดอร์ย่อย, เช็กพอยต์แบบ pickle ที่อยู่ข้างๆ
safetensors — จะถูกละเว้นไว้ และคำสั่งจะแสดงรายการสิ่งที่ละเว้นไว้ ดังนั้น
โฟลเดอร์ `model/` ที่ `nmt-forge export` เขียนขึ้นสามารถส่งได้ตามที่เป็นอยู่: `DEPLOY.md`
และ `champollion-plugin/` ของมันจะถูกทิ้งไว้ข้างหลัง `contest validate` จะแพ็กในลักษณะเดียวกัน
และรายงานไฟล์ที่ละเว้นไว้เป็นผลการตรวจสอบระดับ INFO การตรวจสอบของโหนดคุณยังคง
เหมือนเดิม: บันเดิลที่มีไฟล์ที่ไม่ใช่ข้อมูลจะยังคงถูกปฏิเสธที่นั่น

**ผลลัพธ์สามารถยาวได้เท่าใด** โหนดของคุณจะถอดรหัสด้วยความยาวที่ระบุไว้อย่างชัดเจน
เสมอ: `max_new_tokens` หรือ `max_length` ที่โมเดลประกาศไว้
(`generation_config.json` ของมัน) มิฉะนั้นจะสร้างโทเค็นใหม่ได้สูงสุด `max(64, 4 × source tokens)`
โทเค็นต่อประโยค โดยจำกัดไม่เกินตำแหน่งของตัวถอดรหัส คำสั่ง `mt-eval run --method
local-model` จะถอดรหัสตามกฎเดียวกัน ดังนั้นใบเสร็จของผู้เข้าร่วมและการ
รันซ้ำของโหนดคุณจึงสอดคล้องกัน `submit-model` จะพิมพ์ความยาวที่จะนำมาใช้
และเขียนลงใน manifest (`model.decodeLength`); โหนดจะบันทึก
ความยาวที่นำไปใช้ในข้อเท็จจริงการรันของการรันนั้น (`execution.generation`)
หากไม่มีการระบุความยาวที่ชัดเจน ไลบรารี transformers จะหยุดทำงานที่ประมาณ 20
โทเค็น และทุกผลงานจะถูกให้คะแนนจากผลลัพธ์ที่ขาดหายไป

ผู้จัดการแข่งขันจะรันมันด้วย `trust_remote_code=False` แบบออฟไลน์ และมีเพียงคะแนนเท่านั้น
ที่ส่งออกไป — เผยแพร่เป็น `declarative-model` อัตลักษณ์ของวิธีการ **ปราศจากโค้ดโดย
โครงสร้าง** (หากค่าน้ำหนักมีขนาดหลาย GB: ให้ใช้ `--bundle-out` สำหรับเลน sneakernet
เช่นเดียวกับด้านล่าง)

### เลน B — บันเดิลที่รันได้ (แซนด์บ็อกซ์ สำหรับวิธีการที่เป็นโค้ด)

หากวิธีการของคุณเป็นโค้ดจริงๆ — เช่น ไปป์ไลน์, วิธีการไฮบริดที่ใช้ LLM ช่วยกำกับ, ตัวถอดรหัส
ที่กำหนดเอง — จะไม่สามารถรันแบบประกาศได้ จึงต้องผ่านแซนด์บ็อกซ์ที่แยกขาดจาก
เครือข่ายแทน นี่เป็นเลนที่โดยสัจจริงแล้วมีความปลอดภัยต่ำกว่า (เนื่องจากมีโค้ดที่ไม่น่าเชื่อถืออยู่ภายใน
แทนที่จะปฏิเสธไม่รันโค้ดเลย) ดังนั้นโปรดใช้เลน A ทุกครั้งที่วิธีการของคุณเป็น
โมเดลมาตรฐาน

**รวมทุกโมเดลที่วิธีการของคุณเรียกใช้ไว้ในบันเดิล** โหนดจะรันผลงานของคุณโดยไม่มี
เครือข่ายเลย ดังนั้นวิธีการที่เรียกใช้ API โมเดลที่โฮสต์ไว้ (เช่น ไฮบริดที่ใช้ LLM ช่วยกำกับ
โดยสอบถามไปยัง cloud LLM หรือบริการ MT) จะไม่ได้รับคำตอบและไม่ได้คะแนน
เลย ไฮบริดที่ใช้ LLM ช่วยกำกับจะผ่านการคัดกรองได้ก็ต่อเมื่อมี LLM อยู่ภายในบันเดิลเท่านั้น:
เป็นค่าน้ำหนักแบบเปิดภายใต้ `/method` รันภายในโพรเซสหรือผ่านเซิร์ฟเวอร์ในเครื่องที่
จุดเข้าใช้งานของคุณเริ่มต้นขึ้น ข้อกำหนดเดียวกันนี้ใช้กับพจนานุกรม, FST หรือข้อมูลอื่นใด
ที่วิธีการของคุณอ่านในขณะรัน ([ข้อกำหนดวิธีการ](/docs/network/specifications/methods#method-validity-and-dependency-classes)
เรียกวิธีการที่ต้องการ LLM ที่โฮสต์ไว้ภายนอกว่าเป็นคลาสการพึ่งพา A1; เกตเวย์ที่จะ
ช่วยให้สามารถรันในแซนด์บ็อกซ์ได้นั้นยังไม่ได้ถูกสร้างขึ้น)

**สัญญาของบันเดิลที่รันได้คือ stdin/stdout** ภายในคอนเทนเนอร์ โหนดของ
ผู้จัดจะรันคำสั่งตามนี้อย่างแม่นยำ:

```
cat /eval/source.txt | <your entrypoint> > /output/translations.txt
```

ประโยคต้นฉบับจะเข้ามาทีละบรรทัดทาง stdin; คุณเขียนคำแปลทีละหนึ่งบรรทัด
ออกทาง stdout คอนเทนเนอร์จะไม่มีสแตกเครือข่าย (`--network=none`), รูทแบบ
อ่านอย่างเดียว และมี `/tmp` ที่เขียนได้

**ไฟล์ของคุณไปอยู่ที่ใด** ทุกสิ่งในโฟลเดอร์ที่คุณส่งเป็น `--method-dir`
จะถูกแพ็กไว้ภายใต้ `method/` ในบันเดิล และเมานต์เป็น **แบบอ่านอย่างเดียวที่ `/method`**
ในขณะรัน รวมถึงค่าน้ำหนักด้วย จึงไม่จำเป็นต้องคัดลอกสิ่งใดลงในอิมเมจ
ให้จัดวางโครงสร้างตามนี้:

```text
my-method/              ← --method-dir ./my-method
  translate.py          ← --entrypoint translate.py   (runs as /method/translate.py)
  weights/              ← read at /method/weights
  wheels/               ← vendored dependencies (see the Dockerfile below)
Dockerfile              ← --dockerfile ./Dockerfile
training-data.txt       ← --training-data-file ./training-data.txt
```

`--entrypoint` คือพาธของสคริปต์ภายใน `--method-dir` พาธในบันเดิลของมันคือ
`method/translate.py` ซึ่งได้รับการยอมรับเช่นกัน หากชื่อไฟล์อาจหมายถึงไฟล์ที่ต่างกันสอง
ไฟล์ คำสั่งจะปฏิเสธและระบุชื่อทั้งสองไฟล์; หากไฟล์หายไป คำสั่งจะระบุ
ทุกพาธที่ได้ค้นหา

**ตัวอย่าง Hugging Face transformers wrapper ขั้นต่ำ:**

```python title="my-method/translate.py"
#!/usr/bin/env python3
import sys
from transformers import AutoModelForSeq2SeqLM, AutoTokenizer

tok = AutoTokenizer.from_pretrained("/method/weights")
model = AutoModelForSeq2SeqLM.from_pretrained("/method/weights")

for line in sys.stdin:
    inputs = tok(line.strip(), return_tensors="pt", truncation=True)
    out = model.generate(**inputs, max_new_tokens=256)
    print(tok.decode(out[0], skip_special_tokens=True), flush=True)
```

**Dockerfile ต้องสร้างได้โดยไม่ใช้เครือข่าย** ผู้จัดการแข่งขันจะ build image ของคุณด้วย `--network=none` — การทดสอบ build แบบ air-gap *คือ* ขั้นตอน build นั่นเอง — ดังนั้น dependency ทุกอย่างต้อง **vendor ไว้ใน bundle** (`pip install` ที่เชื่อมต่อ PyPI จะทำให้ build ล้มเหลว และการสแกน static แบบ pre-flight จะตรวจพบการเรียกใช้เครือข่ายก่อนที่จะมีการส่งข้อมูลใดๆ) ให้ ship wheels ไว้ใน method dir และติดตั้งจาก wheels เหล่านั้น:

```dockerfile title="Dockerfile"
FROM python:3.11-slim
# The build context is the bundle root: Dockerfile + method/
COPY method/wheels/ /wheels/
RUN python3 -m pip install --no-index --find-links=/wheels torch transformers sentencepiece
# Weights are NOT copied — /method is mounted read-only at run time.
```

**สิ่งที่ทุกการส่งผลงานต้องมี** สิ่งเหล่านี้จำเป็นต้องระบุ และคำสั่ง
จะหยุดทำงานก่อนขั้นตอนทางเครือข่ายใดๆ หากมีสิ่งใดขาดหายไป:

- `--method-dir`, `--dockerfile`, `--entrypoint`, `--name`, `--version`,
  `--method-class`, `--developer`, `--node-id` และ `--agree`;
- **ใบเสร็จ `mt-eval contest qualify` ที่ผ่านเกณฑ์** สำหรับการแข่งขันนี้และ
  ระบบนี้ (ขั้นตอนที่ 8; `--system` จะระบุชื่อเมื่อคุณผ่านการคัดกรองมากกว่าหนึ่งระบบ);
- คำประกาศสองรายการ ซึ่งจะถูกบันทึกเป็นคำกล่าวอ้างของคุณ: `--track constrained` หรือ
  `--track unconstrained` (ไม่มีค่าเริ่มต้น) และ `--parameter-count`;
- สำหรับวิธีการที่มีค่าน้ำหนักที่ผ่านการเทรน (`--parameter-count` มากกว่า 0): ต้องระบุ
  `--weights-license <SPDX id or LicenseRef-…>` และอย่างใดอย่างหนึ่งระหว่าง `--weights-public`
  หรือ `--weights-private` ด้วย;
- สำหรับวิธีการที่**ไม่มีค่าน้ำหนักที่ผ่านการเทรน** (ใช้กฎเกณฑ์, พจนานุกรม, FST):
  ให้ระบุ `--parameter-count 0` และไม่ต้องมีแฟล็กค่าน้ำหนัก การส่งผลงานจะบันทึก
  สัญญาอนุญาตและความเปิดกว้างของค่าน้ำหนักเป็น "ไม่เกี่ยวข้อง" (not applicable) แทนที่จะเป็นสัญญาอนุญาตที่คุณ
  ต้องแต่งขึ้นมาเอง;
- สำหรับวิธีการที่**ใช้การพรอมต์ LLM** (ไม่ได้เทรนอะไรเลย เพียงแค่เขียน
  พรอมต์): จำนวนพารามิเตอร์คือพารามิเตอร์ของทุกโมเดลที่บันเดิลรัน รวมถึง
  LLM ด้วย แม้ว่าคุณจะไม่ได้เป็นผู้เทรนก็ตาม ให้นำมาจาก model card ของ LLM
  หรือส่วนหัวของค่าน้ำหนัก และส่งสัญญาอนุญาตของ LLM เป็น
  `--weights-license` พร้อมกับ `--weights-public` เมื่อสามารถดาวน์โหลดค่าน้ำหนักได้อย่างเปิดเผย
  การใช้ `--parameter-count 0` จะถือเป็นการระบุระบบที่ผิดพลาด: 0 หมายความว่า
  วิธีการนั้นไม่ได้รันโมเดลใดๆ เลย วิธีการที่เรียกใช้ LLM ที่โฮสต์ไว้ภายนอกจะไม่สามารถเข้าร่วม
  การแข่งขันที่ปิดผนึกได้เลย: โหนดไม่มีการเชื่อมต่อเครือข่าย และเกตเวย์ที่จะ
  รองรับการเรียกดังกล่าวก็ยังไม่ได้ถูกสร้างขึ้น (ดู *รวมทุกโมเดลที่วิธีการของคุณเรียกใช้
  ไว้ในบันเดิล* ด้านล่าง) `contest qualify` ได้ระบุไว้แล้วเมื่อผลลัพธ์
  ที่นำมาให้คะแนนได้มาจากผู้ให้บริการภายนอก;
- เมื่อใช้ `--track constrained`: ต้องระบุ `--training-data-file` ซึ่งเป็นรายการข้อความธรรมดาของ
  ข้อมูลที่คุณใช้เทรน (วิธีการที่ไม่ได้เทรนด้วยข้อมูลใดเลยให้ระบุไว้ในไฟล์);
- หากการแข่งขันประกาศข้อกำหนดรางวัล: ต้องระบุ `--accept-terms <hash>` (รัน
  หนึ่งครั้งโดยไม่มีแฟล็กนี้ แล้วข้อกำหนดจะถูกพิมพ์ออกมาพร้อมแฮชเพื่อให้นำมาส่งกลับ); หาก
  การแข่งขันต้องการคำอธิบาย: ต้องระบุ `--description-file`

**ทรัพยากรที่วิธีการของคุณประกาศ** บันเดิลจะระบุ RAM, พื้นที่ดิสก์
ชั่วคราว และเวลาจริง (wall-clock time) ที่ต้องการ และโหนดของผู้จัดจะปฏิเสธบันเดิล
ที่ร้องขอเกินขีดจำกัด `sandbox` ของตน ค่าเริ่มต้นจะเป็นขีดจำกัดใน
เทมเพลตโหนดที่ `mt-eval node init` เขียนขึ้น: `--ram-gb 4`, `--disk-gb 4`,
`--max-runtime-minutes 30`, ไม่มี GPU ดังนั้น บันเดิลที่แพ็กเกจด้วยค่าเริ่มต้น
จะสามารถรันบนโหนดที่กำหนดค่าด้วยค่าเริ่มต้นของเทมเพลตได้ หากวิธีการของคุณ
ต้องการทรัพยากรมากกว่านั้น ให้ระบุด้วยแฟล็กเหล่านั้น (และ `--gpu`) และตรวจสอบว่า
โหนดของผู้จัดการแข่งขันอนุญาตหรือไม่ ผู้จัดที่เปลี่ยนขีดจำกัดควรประกาศ
ให้ทราบพร้อมกับการแข่งขัน หากโหนดปฏิเสธ ข้อความปฏิเสธจะระบุค่าแต่ละค่า
และสิ่งที่โหนดอนุญาต

ส่งด้วยคำสั่ง:

```bash
mt-eval contest submit-method <contest-id> \
  --method-dir ./my-method --dockerfile ./Dockerfile \
  --name "My NMT" --version 1.0 \
  --entrypoint translate.py \
  --method-class pipeline --paradigm neural-nmt \
  --developer "Your Name" --node-id <organizer-advertised-node-id> \
  --track constrained --parameter-count 78000000 \
  --weights-license Apache-2.0 --weights-public \
  --training-data-file ./training-data.txt \
  --primary \
  --agree
```

โหนดของผู้จัดจะรันวิธีการของคุณซ้ำบนสำเนาชุดข้อมูล dev สาธารณะของตนเอง
ก่อนที่จะขอให้ผู้ดูแลคนใดอนุมัติการรัน คำสั่ง `--agree` จะเป็นการยอมรับ
ข้อกำหนดการส่งวิธีการ

**ค่าน้ำหนักขนาดหลาย GB หรือไม่มีการเชื่อมต่อ: ใช้เลน sneakernet** ช่องทางการรับผลงาน
ที่โฮสต์ไว้จะอัปโหลด tarball ของคุณเป็น **POST เดียว** ไปยังสตอเรจของ
โฮสต์การแข่งขัน จึงถูกจำกัดด้วยขีดจำกัดการอัปโหลดของสตอเรจของโฮสต์นั้น — ซึ่งใช้ได้ดีสำหรับโค้ด
และโมเดลขนาดเล็ก แต่ไม่ใช่สำหรับเช็กพอยต์ขนาดหลาย GB ตัวสัญญาของบันเดิลเอง
อนุญาตให้อาร์ติแฟกต์มีขนาดใหญ่กว่านั้นมาก (tarball สูงสุด 100 GB, อิมเมจที่สร้างเสร็จแล้วสูงสุด
150 GB) คำสั่ง `--offline` จะแพ็กเกจบันเดิลและเขียนไดเรกทอรีแลกเปลี่ยน
โดยไม่มีการใช้เครือข่ายเลย เมื่อไม่มีการเชื่อมต่อเครือข่าย ก็จะไม่มีแถวการแข่งขันให้อ่าน
ดังนั้นจึงต้องใช้ค่าต่างๆ ที่ผู้จัดประกาศไว้ด้วย: `--bundle-out`,
`--secret-set`, `--pair`, `--developer-email`, `--offline-qualifier-id` และ
`--offline-threshold` (เกณฑ์คะแนนบนสเกลตัวคัดกรอง 0–100) ตัวอย่างวิธีการแบบใช้กฎเกณฑ์
ที่ไม่มีค่าน้ำหนัก ซึ่งแพ็กเกจแบบออฟไลน์:

```bash
mt-eval contest submit-method <contest-id> \
  --method-dir ./my-method --dockerfile ./Dockerfile \
  --name "My Rules" --version 1.0 \
  --entrypoint translate.py \
  --method-class pipeline --paradigm rule-based \
  --developer "Your Name" --developer-email you@example.org \
  --node-id <organizer-advertised-node-id> \
  --track constrained --parameter-count 0 \
  --training-data-file ./training-data.txt \
  --agree \
  --offline --bundle-out ./exchange \
  --secret-set <sealed-set-id> --pair 'eng>crk' \
  --offline-qualifier-id <published-qualifier-id> --offline-threshold 35
```

ไดเรกทอรี exchange จะส่งถึงผู้จัดการแข่งขันผ่านสื่อแบบถอดได้ (หรือช่องทางใดก็ได้ที่ทั้งสองฝ่ายไว้วางใจ) โดยผู้จัดการแข่งขันจะนำเข้าด้วย `mt-eval node import-bundle` SHA-256 ของ bundle จะถูกตรึงไว้ใน authorization request ไม่ว่าจะใช้วิธีใด ดังนั้นสิ่งที่รันจึงพิสูจน์ได้ว่าตรงกับสิ่งที่คุณเสนอ

**สำหรับผู้จัด: ข้อเสนอแบบออฟไลน์จะต้องรอผู้ดูแลเช่นเดียวกับแบบออนไลน์ — และโหนดจะตรวจสอบก่อน ตามลำดับในขั้นตอนที่ 9**
ข้อเสนอจะเข้ามาในฐานะคำขอที่ *รอดำเนินการ (pending)* และโหนดแบบแอร์แก็ปจะบันทึกทั้งการตรวจสอบของตนเอง
และการตัดสินใจของผู้ดูแลไว้เอง โดยไม่ต้องพึ่งพาฐานข้อมูลและไม่ต้องใช้เซอร์วิสคีย์:

```bash
mt-eval node import-bundle ./exchange               # stages it: PENDING custodian approval
mt-eval node run-method <request-id> --offline      # the node's checks: re-runs the entrant's qualifier, checks the container runtime
mt-eval node list --offline                         # what is staged, checked, approved or waiting, and the next command
mt-eval node approve <request-id> --offline --actor <custodian>
#   or: mt-eval node deny <request-id> --offline --actor <custodian> --reason "…"
mt-eval node run-method <request-id> --offline      # the sealed run: refuses until the approval is recorded
mt-eval node export-scores ./exchange               # signed scores, or the signed refusal
```

คำสั่ง `node run-method --offline` ครั้งแรกบนข้อเสนอที่รอดำเนินการจะไม่เปิดสิ่งใด
ที่ปิดผนึกไว้ มันจะรันตัวคัดกรองของผู้เข้าร่วมซ้ำบนชุดข้อมูล dev สาธารณะ (`qualifier`
+ `dev_corpus` ที่ `node.json` ของคุณประกาศไว้; คำสั่ง `node init
--from-contest` จะเติมข้อมูลทั้งสองให้) และสำหรับผลงานที่เป็นโค้ด จะตรวจสอบว่ามี
รันไทม์คอนเทนเนอร์อยู่หรือไม่ และ RAM, พื้นที่ดิสก์ชั่วคราว และเวลาการรันที่บันเดิลประกาศไว้นั้น สอดคล้องกับ
ขีดจำกัด `sandbox` ของคุณหรือไม่ ผลการผ่านจะถูกเขียนลงในบัญชีแยกประเภทในเครื่อง
ที่เชื่อมโยงด้วยแฮชของโหนด หากไม่ผ่านเกณฑ์ตัวคัดกรองจะถูกปฏิเสธที่นี่ บันทึกไว้เป็น
การปฏิเสธของโหนด และส่งกลับไปในรูปแบบการปฏิเสธที่ลงนามแล้ว: โดยไม่มีการสอบถามผู้ดูแล
โหนดที่ไม่สามารถรันผลงานได้ (ไม่มีรันไทม์, ขีดจำกัดต่ำเกินไป) จะปฏิเสธโดยถือเป็น
ปัญหาของโหนดและไม่บันทึกสิ่งใด และคำขอจะคงอยู่เช่นเดิม

คำสั่ง `node approve --offline` จะปฏิเสธการทำงานจนกว่าจะมีการบันทึกผลการตรวจสอบที่ผ่าน
ลงในบัญชีแยกประเภทสำหรับลายนิ้วมือและบันเดิลที่ตรงกันทุกประการของคำขอนี้ และข้อผิดพลาดจะระบุ
คำสั่งที่ต้องรันก่อน จากนั้นจะเขียนผลการลงคะแนนและการอนุญาตลงใน
บัญชีแยกประเภทเดียวกัน (ชุดเดียวกับที่พิธีการส่วนแบ่งของผู้ดูแลใช้งาน) และบันทึกการตัดสินใจ
ที่ลงนามด้วย `signing_key` ของโหนด โดยระบุการตรวจสอบที่ได้รับการยอมรับ คำสั่ง
`node run-method --offline` ครั้งที่สองจะตรวจสอบทั้งสามส่วนก่อนที่สิ่งใดก็ตามที่ปิดผนึก
จะถูกรัน (บัญชีแยกประเภทได้รับการยืนยัน, แสดงว่าคำขอนี้ได้รับอนุญาตภายใต้
ลายนิ้วมือที่อิมพอร์ตเข้ามา และบันทึกที่ลงนามแล้วได้รับการยืนยันและระบุชื่อ
คำขอนี้) ดังนั้นข้อเสนอที่รอดำเนินการจะไม่ถูกรันตามคำสั่งของผู้ควบคุมแต่เพียงผู้เดียวอย่างเด็ดขาด จากนั้น
จะรันการตรวจสอบรันไทม์และตัวคัดกรองซ้ำก่อนที่ชุดข้อมูลที่ปิดผนึกจะเปิดออก
การปฏิเสธจะถูกบันทึกในลักษณะเดียวกันและส่งกลับไปยังผู้เข้าร่วมในฐานะการปฏิเสธที่ลงนามแล้ว
ผู้ดูแลสามารถปฏิเสธได้ทุกเมื่อ ไม่ว่าจะตรวจสอบแล้วหรือไม่ก็ตาม
คำขอที่ส่งเข้ามาโดยได้รับอนุญาตอยู่แล้ว — เช่น การเอ็กซ์พอร์ตแบบรีเลย์ (ได้รับอนุญาตแล้วใน
ฐานข้อมูลการแข่งขัน) หรือ `node stage-request` (ผู้จัดการแข่งขันในสเตจจิงเป็นผู้อนุญาต) —
ไม่จำเป็นต้องมีการตัดสินใจรอบที่สอง

**ผู้จัดการแข่งขัน: โหลด base image ล่วงหน้าบนเครื่อง airgap** เนื่องจาก image build รันด้วย `--network=none` base image ของ `FROM` ใน Dockerfile จะต้องมีอยู่ใน local image store ของเครื่องแล้ว บนเครื่องที่เชื่อมต่ออินเทอร์เน็ต `docker pull python:3.11-slim && docker save -o base.tar python:3.11-slim`;
นำ `base.tar` ไปพร้อมกับ bundle; บนเครื่อง airgap ให้รัน
`docker load -i base.tar` ก่อนรัน `mt-eval node run-method` ตกลงเรื่อง base image กับผู้เข้าร่วมในเอกสารการแข่งขันที่คุณเผยแพร่

## ขั้นตอนที่ 10 — จัดอันดับ, ปิดการแข่งขัน, เอ็กซ์พอร์ต

ผลลัพธ์เฉพาะคะแนนจะเผยแพร่ไปยัง [กระดานผู้นำ](/docs/network/leaderboard/rules)
เช่นเดียวกับการรันอื่นๆ โดยทำเครื่องหมายว่าเป็นการประเมินผลชุดข้อมูลที่ปิดผนึก การจัดอันดับ
ของการแข่งขันเองนั้นขึ้นอยู่กับคุณในการสร้าง ตรึง และเผยแพร่:

```bash
mt-eval contest open-intake <contest-id>     # entry intake on — submit-model / submit-method admitted (owner only)
mt-eval contest close-intake <contest-id>    # intake off — work already received still scores
mt-eval contest rank <contest-id> --json     # provisional ranking, any time
mt-eval contest close <contest-id>           # one-way: freezes the ranking, shuts intake
mt-eval contest export <contest-id> --format csv --out results.csv
```

สิ่งที่ `rank` ดำเนินการ เพื่อให้คุณสามารถระบุไว้ในกฎของคุณได้: ผลงานจะได้รับการจัดอันดับตาม
**เมทริกหลักที่บันทึกไว้** ของการแข่งขัน (`--primary-metric` ในตอนสร้าง; chrF++
ตามค่าเริ่มต้น) จากนั้นตามด้วย chrF++ → BLEU → COMET → เวลาส่งผลงานที่เช้าที่สุด
จะเป็นการจัดอันดับ**เฉพาะที่ผ่านการตรวจสอบแล้วตามค่าเริ่มต้น** — ซึ่งได้แก่การ์ดการรันที่โหนดเผยแพร่ — และจะนับ
จำนวนการ์ดที่รายงานตนเองที่ซ่อนไว้ คู่ที่อยู่ติดกันแต่ละคู่จะมีการตัดสินผลคะแนนที่เท่ากัน (tie verdict)
พร้อมป้ายกำกับ: การทดสอบนัยสำคัญแบบจับคู่รายเซ็กเมนต์ในกรณีที่มีแถวรายเซ็กเมนต์อยู่
มิฉะนั้นจะเป็น **ช่วงความเชื่อมั่น 95% ทับซ้อนกัน** หรือมิฉะนั้นคือคะแนนเท่ากันทุกประการ
**การแข่งขันที่ปิดผนึกจะไม่เผยแพร่แถวรายเซ็กเมนต์อย่างเด็ดขาด** (ปล่อยเฉพาะค่ารวม
โดยเจตนา) ดังนั้นการทดสอบแบบจับคู่จะรันบนโหนดของคุณแทน ก่อนที่จะปิด ให้รัน
`mt-eval node verdicts --contest <id> --out verdicts.json` บนโหนด; มันจะ
เขียนเฉพาะคำตัดสินที่ลงนามแล้ว (ต่อคู่: p-value, ผลต่างคะแนน, ช่วงความเชื่อมั่น,
จำนวนเซ็กเมนต์ — ไม่มีข้อความ) จากนั้นปิดด้วยคำสั่ง `--node-verdicts verdicts.json
--verify-key <the node's .pub.json>` หากไม่มีคำตัดสิน ผลการเสมอกันจะมาจากการทับซ้อน
ของ CI ไม่ว่าจะวิธีใด ผลลัพธ์จะระบุหลักฐานที่นำมาใช้ และระบบที่เสมอกัน
จะครองอันดับร่วมกัน (`1, 1, 3`)

คำสั่ง `close` เป็นแบบทางเดียว มันจะจัดอันดับตามเมทริกที่บันทึกไว้, ปฏิเสธการทำงานในขณะที่
ผลงานยังอยู่ระหว่างการให้คะแนน (เว้นแต่คุณจะบังคับ), แสดงตารางให้คุณเห็น,
ถามยืนยัน และจากนั้นจะตรึงการจัดอันดับลงในบันทึกการแข่งขัน คำสั่ง `export`
จะส่งคืนผลลัพธ์ที่ถูกตรึงไว้นั้นตามข้อความเดิมทุกประการ ในรูปแบบ JSON หรือ CSV เพื่อใช้สำหรับหน้าข้อค้นพบ (Findings)
หรือหน้าผลลัพธ์ของคุณ การ์ดที่ให้คะแนนบนชุดข้อมูลอื่น (ชุดข้อมูล T2 ที่เป็นความลับโดยสมบูรณ์, การ์ดชุด dev
ที่หลงเข้ามา) จะแสดงแยกไว้ต่างหากและไม่มีการนำไปปะปนกับการจัดอันดับหลักอย่างเด็ดขาด

### การตัดสินใจเกี่ยวกับช่วงเวลาที่ผลลัพธ์จะปรากฏ

คำมั่นสัญญาสองประการที่คุณให้ไว้เมื่อตอนสร้าง และไม่สามารถแอบเปลี่ยนแปลงได้ในภายหลัง —
ฐานข้อมูลจะตรึงทั้งสองค่าไว้ทันทีที่การแข่งขันของคุณมีผลงานส่งเข้ามา:

```bash
mt-eval contest create … \
  --results-visibility hidden_until_close \   # no score is visible while the contest runs
  --anonymize-until-close                     # pseudonyms in YOUR ranking artifacts
```

**`--results-visibility hidden_until_close` คือตัวที่ซ่อนคะแนนอย่างแท้จริง**
ภายใต้ตัวเลือกนี้ ทุกการ์ดที่โหนดของคุณให้คะแนนจะถูกระงับไว้แทนที่จะเผยแพร่:
วิธีการยังคงรันอยู่, สิทธิ์การอนุญาตยังคงถูกใช้ไป และการ์ดยังคงถูกประกอบ
ตรวจสอบ และจัดเก็บไว้ตามข้อความเดิมทุกประการ — เพียงแค่มันไม่ได้อยู่บนกระดาน
คำสั่ง `contest close` จะเผยแพร่ทุกการ์ดที่ถูกระงับไว้ **ก่อน** แล้วจึงสร้างและ
ตรึงการจัดอันดับ ดังนั้นจึงไม่มีสิ่งใดสูญหาย และผลลัพธ์ที่ถูกตรึงจะจัดอันดับทุกสิ่ง
ที่คุณมีอยู่ สิ่งนี้จะเกิดขึ้นในการสั่งปิดแบบบังคับ (forced close) เช่นกัน: การบังคับใช้กับงานจัดอันดับ
ที่ยังดำเนินการค้างอยู่เท่านั้น ไม่ใช่การระงับคะแนนที่การแข่งขันของคุณต้องเปิดเผย สแนปช็อต
ที่ถูกตรึงจะแสดงรายการผลลัพธ์ที่การปิดนั้นเผยแพร่อย่างชัดเจน

การระงับเป็น **สถานะที่ถูกบันทึกไว้ ไม่ใช่การรันที่สูญหาย**: การ์ดที่ถูกระงับไม่สามารถ
แก้ไขได้ และตัวชี้ที่บอกตำแหน่งที่มันถูกเผยแพร่จะถูกเขียนเพียงครั้งเดียวและไม่มีการ
ชี้ตำแหน่งใหม่ — ทั้งสองอย่างนี้ถูกบังคับใช้ในฐานข้อมูล ภายใต้ไคลเอนต์ทุกตัว ในขณะที่
การแข่งขันยังเปิดอยู่ คำสั่ง `rank` จะบอกให้คุณทราบว่ามีผลลัพธ์ถูกระงับไว้กี่รายการ เพื่อไม่ให้
การจัดอันดับชั่วคราวถูกอ่านว่าเสร็จสมบูรณ์แล้วในเวลาที่ยังไม่เสร็จสิ้น

**`--anonymize-until-close` มีบทบาทน้อยกว่า และควรทำความเข้าใจให้ชัดเจนว่ามันทำสิ่งใด**
มันจะแทนที่ชื่อผู้เข้าร่วมด้วยนามแฝงแบบกำหนดผลลัพธ์ได้ในอาร์ติแฟกต์การจัดอันดับ *ของคุณ* —
ได้แก่ ตาราง `rank`, JSON ของมัน, CSV — ในขณะที่การแข่งขัน
ยังเปิดอยู่ และคำสั่ง `close` จะเปิดเผยชื่อเหล่านั้นออกมา มัน **ไม่ได้** ปกปิดตัวตนบนกระดานผู้นำ
สาธารณะ: การ์ดที่เผยแพร่แล้วจะแสดงชื่อผู้จัดทำตามที่ผลงานนั้นประกาศไว้
หากคุณต้องการให้ผู้เข้าร่วมไม่สามารถมองเห็นผลลัพธ์ของกันและกันได้ก่อนที่จะ
สิ้นสุดการแข่งขัน ให้ใช้ `--results-visibility hidden_until_close`; แฟล็กนี้ไม่ได้มีไว้ใช้
ทดแทนสิ่งนั้น

หากวิธีการผ่านเงื่อนไขเกณฑ์คะแนนที่คุณเผยแพร่ไว้ในขั้นตอนที่ 6 —
รวมถึง [การตรวจสอบโดยผู้พูดภาษา](/docs/network/specifications/speaker-validation)
ซึ่งเป็นเกณฑ์ตัดสินของชุมชนของคุณ ไม่ใช่เกณฑ์อัตโนมัติ — **คุณ** (หรือกองทุนของคุณ)
จะเป็นผู้มอบรางวัล ตามข้อกำหนดที่คุณเผยแพร่ไว้เอง บทบาทของ Champollion จะสิ้นสุดลง
ที่การวัดผลเท่านั้น

## สิ่งที่คุณเก็บไว้ตลอดไป

- **ชุดข้อมูล** มันไม่เคยออกจากโครงสร้างพื้นฐานของคุณ นำ ciphertext ออกไปออฟไลน์และ sealed set ก็หยุดรันได้ทันที
- **กุญแจ** การเข้าถึงสิ้นสุดเมื่อ custodians ของคุณหยุดอนุมัติ
- **เงิน** มันไม่เคยอยู่ที่อื่น
- **บันทึก** head digest ของ audit log สามารถเผยแพร่ได้ ดังนั้นประวัติว่าใครรันอะไรกับชุดข้อมูลของคุณไม่สามารถถูกเขียนทับอย่างเงียบๆ — โดยใครก็ตาม รวมถึงเราด้วย

สำหรับภาษาเงื่อนไขที่คุณสามารถนำไปปรับใช้ — ความเป็นเจ้าของ, การอนุญาตใช้งานเฉพาะคะแนน และการสำรวจวิธีที่การแข่งขันอาจถูกโจมตีอย่างละเอียด — ดู [Terms Templates](/docs/network/sovereignty/terms-templates)
