# MT Training in Plain Language

การฝึกโมเดลแปลภาษาด้วยเครื่อง (MT) มีศัพท์เฉพาะของตัวเอง และส่วนใหญ่ไม่เคยถูกอธิบายให้ผู้เริ่มต้นเข้าใจ — มักถูกสันนิษฐานว่ารู้อยู่แล้ว หน้านี้ไม่สันนิษฐานสิ่งใดทั้งสิ้น ทุกคำศัพท์ด้านล่างถูกนิยามด้วยภาษาที่เข้าใจง่าย และยึดโยงกับตัวอย่างที่จับต้องได้ เพื่อให้เมื่อคุณอ่าน[คู่มือการฝึก](/docs/network/tutorials/train-your-own-model) หรือดู coding agent รันคำสั่ง คุณจะรู้ว่าคำเหล่านั้นหมายความว่าอะไร และที่สำคัญกว่านั้น **คำไหนซ่อนความผิดพลาดที่ค่อยๆ ทำลายผลลัพธ์โดยที่ไม่มีใครสังเกตเห็น**

:::info[หน้านี้เหมาะสำหรับใคร]
คุณไม่จำเป็นต้องเขียน Python วิธีที่คาดหวังในการทำงานนี้ในปัจจุบันคือการ**สั่งการ coding agent** — Claude Code, OpenAI Codex, Cursor, OpenCode, Google Antigravity หรือเครื่องมือที่คล้ายกัน — ที่รันเครื่องมือต่างๆ แทนคุณ หน้าที่ของคุณคือเข้าใจแนวคิดให้ดีพอที่จะให้คำสั่งที่ดีและอ่านผลลัพธ์อย่างตรงไปตรงมา นั่นคือสิ่งที่หน้านี้มีไว้เพื่อ เมื่อเรากล่าวถึงเครื่องมือ เราหมายถึง [**nmt-forge**](/docs/network/getting-started/training-honestly) ซึ่งเป็น training suite ที่แนวคิดเหล่านี้ถูกสร้างขึ้นมาด้วย แต่คำศัพท์ต่างๆ นั้นเป็นของทั้งวงการ ไม่ใช่ของเราเพียงฝ่ายเดียว
:::

ตัวอย่างที่ดำเนินไปตลอดหน้านี้จะเชื่อมทุกส่วนเข้าด้วยกัน สมมติว่าคุณต้องการสร้างโมเดลที่แปล **ภาษาอังกฤษ → ภาษาที่มีทรัพยากรน้อย** — เรียกมันว่า *ภาษาเป้าหมาย* ของคุณ — ซึ่งแทบไม่มีข้อความที่แปลแล้วอยู่เลย ทุกสิ่งด้านล่างนี้คือส่วนหนึ่งของโปรเจกต์นั้น

## 1. สองกอง: ข้อมูลฝึกและข้อมูลประเมินผล

**ข้อมูลคู่ขนาน (Parallel data)** คือข้อความที่จับคู่กับคำแปล — ความหมายเดียวกันในสองภาษา เรียงต่อกันทีละประโยค

> `The children are playing.` → `awâsisak mêtawêwak.`

โมเดลเรียนรู้โดยการศึกษาคู่ประโยคเหล่านี้หลายพันคู่ แต่คุณต้องแยกคู่ประโยคออกเป็น**สองกองที่ไม่เคยสัมผัสกัน**:

- **ข้อมูลฝึก (Training data)** — คู่ประโยคที่โมเดล*ได้รับอนุญาตให้ศึกษา* โมเดลอ่านซ้ำแล้วซ้ำเล่าและปรับตัวเองเพื่อสร้างผลลัพธ์ที่ตรงกัน
- **ข้อมูลประเมินผล (Evaluation data)** (หรือ **eval data**) — คู่ประโยคที่โมเดล*ไม่เคยได้รับอนุญาตให้เห็นระหว่างการฝึก* คุณซ่อนคำแปลไว้ ขอให้โมเดลแปลด้านต้นฉบับโดยไม่มีข้อมูลช่วย แล้วเปรียบเทียบคำตอบกับความจริงที่ซ่อนไว้ นี่คือการวัดผลที่ซื่อสัตย์เพียงอย่างเดียวว่าโมเดลเรียนรู้ที่จะ*แปล*จริงๆ ไม่ใช่แค่*จำ*

:::tip[สรุปทุกอย่างในหน้านี้ในหนึ่งประโยค]
การทดสอบจะมีความหมายก็ต่อเมื่อโมเดลไม่เคยเห็นคำตอบมาก่อน ความผิดพลาดเกือบทุกอย่างด้านล่างนี้คือวิธีที่แตกต่างกันที่คำตอบรั่วไหลจากกองประเมินผลเข้าสู่กองฝึกโดยที่ไม่มีใครสังเกตเห็น
:::

### ข้อมูลคู่ขนานจริงกับข้อมูลสังเคราะห์

- **ข้อมูลคู่ขนานจริง (หรือ *gold*)** สร้างโดยมนุษย์: ตำราเรียนสองภาษา บันทึกของรัฐบาลที่แปลโดยคน เรื่องราวที่ชุมชนเก็บรักษาไว้ ข้อมูลนี้เชื่อถือได้แต่สำหรับภาษาส่วนใหญ่มีน้อยมากอย่างเจ็บปวด — มักมีเพียงไม่กี่ร้อยคู่ประโยค
- **ข้อมูลคู่ขนานสังเคราะห์ (Synthetic parallel data)** ถูก*สร้างขึ้น*โดยโปรแกรมแทนที่จะเขียนโดยคน เมื่อคุณมีคู่ประโยคจริงเพียง 400 คู่ คุณไม่สามารถฝึกโมเดลที่ใช้งานได้ — ดังนั้นคุณจึงสร้างคู่ประโยคเพิ่มเติมหลายแสนคู่จากกฎเกณฑ์ (อ่านเพิ่มเติมเกี่ยวกับวิธีการใน [§7](#7-manufacturing-data-when-you-dont-have-enough))

ความสัมพันธ์นี้มีความสำคัญอย่างมาก:

> **ตัวอย่างที่ใช้งานได้จริง** โปรเจกต์หนึ่งมีคู่ประโยค English→Cree จริง 435 คู่ และสร้างคู่ประโยคสังเคราะห์ประมาณ 1,000,000 คู่ โมเดลฝึกบนกองสังเคราะห์ขนาดใหญ่ *บวกกับ* คู่ประโยคจริงไม่กี่ร้อยคู่ ข้อมูลสังเคราะห์ช่วยให้ครอบคลุมภาษาได้กว้างขึ้น ส่วนข้อมูลจริงยึดโมเดลไว้กับวิธีที่ภาษาถูกใช้จริงๆ ทั้งหมดของงานฝีมือนี้คือ (a) ทำให้กองสังเคราะห์ครอบคลุมภาษาให้มากที่สุดเท่าที่จะเป็นไปได้ และ (b) วัดผลเฉพาะบนข้อความจริงที่โมเดลไม่เคยสัมผัส

:::danger[ห้ามทดสอบบนข้อมูลสังเคราะห์เด็ดขาด]
ชุดข้อมูลประเมินผลต้องเป็น**ข้อมูลจริงเท่านั้น** หากคุณทดสอบบนประโยคที่สร้างขึ้น คุณกำลังวัดว่าโมเดลตรงกับ*ตัวสร้างข้อมูล*ของคุณ — ไม่ใช่ว่ามันสามารถแปลได้จริงหรือไม่ training suite ที่ดีจะปฏิเสธการลงทะเบียนแถวสังเคราะห์เป็นชุดทดสอบตั้งแต่ต้น
:::

## 2. การแบ่งข้อมูล: train, dev และ test

คุณเริ่มต้นด้วยกองคู่ประโยคจริงหนึ่งกองและ**แบ่ง**มันออกเป็นสามบทบาท

| ชุดข้อมูล | เรียกอีกชื่อว่า | ใช้สำหรับ | โมเดลเห็นในระหว่างการฝึกหรือไม่ |
|---|---|---|---|
| **train** | training set | คู่ประโยคที่โมเดลศึกษา | ใช่ |
| **dev** | validation set, held-in | ตัดสินใจว่า*จะหยุดเมื่อไหร่*และ*เวอร์ชันไหนดีที่สุด* | ไม่ (เพียง*ให้คะแนน*เท่านั้น ไม่ได้ศึกษา) |
| **test** | held-out, evaluation set | เกรดสุดท้ายที่ซื่อสัตย์ | **ไม่เคย** |

ตารางนั้นซ่อนแนวคิดสองอย่างไว้:

- **Held-out** หมายความว่า "แยกออกและเก็บห่างจากการฝึก" ชุดทดสอบถูก held out โดยตั้งใจ
- **Dev set** คือลูกกลางที่ฉลาด โมเดลไม่เคย*ศึกษา*มัน แต่คุณ*แอบดู*ว่าโมเดลทำได้ดีแค่ไหนบนมันระหว่างการฝึกเพื่อตัดสินใจ — เหมือนข้อสอบฝึกหัดที่บอกว่าควรเรียนต่อหรือไม่ โดยไม่ใช่ข้อสอบจริง การใช้ dev set แบบนี้ถูกต้องตามกติกา แต่การใช้ชุด*test*แบบนี้คือการโกง (ดู [§4](#4-contamination-and-leakage-the-mistake-that-eats-results))

### Sealed sets และ re-splits

- **Sealed set** คือชุดทดสอบที่อาจให้คะแนน**เพียงครั้งเดียวเท่านั้น** ทันทีที่คุณดูคะแนนบนมัน มันถือว่า "ใช้ไปแล้ว" — เพราะเมื่อคุณรู้ตัวเลขนั้น การตัดสินใจทุกอย่างในภายหลังของคุณจะถูกกำหนดโดยมันอย่างละเอียดอ่อน Sealed sets คือวิธีที่การแข่งขันและชุมชนรักษาเกรดสุดท้ายให้เป็นสุดท้ายจริงๆ
- **Re-split** คือเมื่อคุณสร้างการแบ่ง train/dev/test ใหม่ตั้งแต่ต้น — มักเป็นเพราะคุณค้นพบว่าการแบ่งเดิมถูกปนเปื้อน คุณไม่สามารถแก้ไขการแบ่งที่รั่วไหลได้ด้วยการลบแถวบางแถว คุณต้องจัดกลุ่มทุกอย่างใหม่และแบ่งใหม่ ([§4](#4-contamination-and-leakage-the-mistake-that-eats-results) อธิบายว่าทำไม)

## 3. สิ่งที่ "การฝึก" ทำจริงๆ: loss และสองหน้าของมัน

การฝึกคือวงวน โมเดลทำการทำนาย เห็นว่าผิดพลาดแค่ไหน และปรับตัวเลขภายในให้ผิดพลาดน้อยลงเล็กน้อยในครั้งต่อไป — ซ้ำแล้วซ้ำเล่าหลายล้านครั้ง

**Loss** คือตัวเลขเดียวที่วัด "ความผิดพลาด" ยิ่งต่ำยิ่งดี แต่มี loss *สองประเภท* และการสับสนระหว่างกันเป็นกับดักคลาสสิก:

- **Training loss** — ความผิดพลาดของโมเดลบนคู่ประโยคที่กำลังศึกษาอยู่ ค่านี้มักลดลงเรื่อยๆ เพราะโมเดลสามารถ ในที่สุด เพียงแค่*จำ*คู่ประโยคฝึกได้
- **Dev loss** (validation loss) — ความผิดพลาดของโมเดลบน dev set ที่ถูกเก็บไว้ซึ่งมัน*ไม่ได้*ศึกษา นี่คือสัญญาณที่ซื่อสัตย์ เมื่อ dev loss หยุดดีขึ้นในขณะที่ training loss ยังคงลดลง โมเดลได้หยุด*เรียนรู้ภาษา*และเริ่ม*จำชุดฝึก*แล้ว

> **ตัวอย่างที่ใช้งานได้จริง** หลังจากผ่านไปสักพัก คุณเห็น training loss อยู่ที่ 0.8 และกำลังลดลง แต่ dev loss ติดอยู่ที่ 1.9 และค่อยๆ *เพิ่มขึ้น* ช่องว่างนั้นคือสัญญาณเตือน: โมเดลเก่งขึ้นในการท่องจำคู่ประโยคฝึก แต่ไม่ดีขึ้น — แย่ลงด้วยซ้ำ — ในการแปลสิ่งใหม่

### Loss คือตัวแทน Decoding คือสิ่งที่แท้จริง

นี่คือความละเอียดอ่อนที่ทำให้เกือบทุกคนสะดุด Loss วัดว่าโมเดลให้ความน่าจะเป็นสูงกับคำถัดไปที่ถูกต้องหรือไม่ *เมื่อคำตอบที่ถูกต้องอยู่ตรงหน้ามันแล้ว* นั่น**ไม่ใช่**สิ่งเดียวกับที่โมเดลสร้างคำแปลที่ดีด้วยตัวเองจริงๆ

- **Decoding** (หรือ *generation* หรือ *inference*) คือโมเดล**แปลจริงๆ**: ให้เฉพาะประโยคต้นฉบับ มันสร้างประโยคเป้าหมายทีละคำ โดยไม่มีอะไรพิงพักได้
- **Loss** คือ*ตัวแทน*ราคาถูกที่คำนวณระหว่างการฝึก มันสัมพันธ์กับคุณภาพ แต่ไม่สมบูรณ์แบบ

> **ตัวอย่างที่ใช้งานได้จริง** checkpoint สองอันมี dev loss ที่เกือบเหมือนกัน แต่เมื่อคุณ*decode*ประโยค dev และให้คะแนนคำแปลจริงๆ อันหนึ่งชัดเจนว่าลื่นไหลกว่า Loss ไม่สามารถเห็นความแตกต่างนั้น แต่ decoding ทำได้ นี่คือเหตุผลที่การเลือก checkpoint อย่างจริงจังต้อง decode ชุด dev และให้คะแนนผลลัพธ์จริง แทนที่จะเชื่อ loss เพียงอย่างเดียว

:::note["dev loss ติดตามคุณภาพได้หรือไม่" เป็นคำถามเปิด ไม่ใช่ความเชื่อที่สืบทอดกันมา]
คุณจะได้ยินคำกล่าวอ้างที่มั่นใจว่า "eval loss โกหก" ให้ถือว่านั่นเป็นสิ่งที่**ยังไม่ได้รับการพิสูจน์** ไม่ใช่ความจริงที่ยืนยันแล้ว — ความเชื่อที่สืบทอดกันมาส่วนใหญ่มาจากการทดลองที่ถูกปนเปื้อน จุดยืนที่ซื่อสัตย์: dev loss เป็นสัญญาณที่มีประโยชน์และราคาถูก ส่วน**เมตริกการสร้างข้อความ**บน dev (decode แล้วให้คะแนน) เป็นสัญญาณที่ตรงกว่า ให้เลือกสัญญาณที่ตรงกว่าสำหรับการตัดสินใจสุดท้าย และอย่าพูดซ้ำว่า "loss โกหก" ราวกับเป็นข้อเท็จจริง
:::

## 4. การปนเปื้อนและการรั่วไหล: ความผิดพลาดที่กัดกินผลลัพธ์

**การปนเปื้อน (Contamination)** (หรือ **การรั่วไหล/leakage**) หมายความว่าคำตอบของ eval ได้แอบเข้าไปอยู่ในกองฝึกแล้ว โมเดลจึง "ทำข้อสอบได้ดีเยี่ยม" ด้วยความจำ คะแนนของคุณดูดีมาก และผลลัพธ์นั้นไร้ค่า นี่คือวิธีที่พบบ่อยที่สุดที่ผลลัพธ์ MT สำหรับภาษาที่มีทรัพยากรน้อยกลายเป็นของปลอม — และเป็นสิ่งสำคัญที่สุดที่หน้านี้กำลังเตือนคุณ

รูปแบบคลาสสิกที่แอบซ่อนคือ **shared-target minimal pair**:

> **ตัวอย่างที่ใช้งานได้จริง — "Feed him" / "Feed her"** ตำราเรียนภาษาหนึ่งแมปแบบฝึกหัดภาษาอังกฤษที่แตกต่างกันหลายแบบไปยัง**คำเดียว**ในภาษาเป้าหมาย *"Feed him"* และ *"Feed her"* ทั้งคู่แปลเป็นรูปแบบเดียวกัน `asam` การแบ่งแบบสุ่มแบบไม่ระมัดระวังจะส่ง *"Feed him"* → `asam` ไปยัง**ชุดฝึก**และ *"Feed her"* → `asam` ไปยัง**ชุดทดสอบ** คำตอบเป้าหมาย `asam` จึงอยู่ในทั้งสองกอง โมเดลจำ `asam` จากการฝึกและ "ตอบถูก" ในการทดสอบ — แต่มันไม่ได้เรียนรู้อะไรเลย ในโปรเจกต์จริงหนึ่งโปรเจกต์ 17 จาก 54 แถว "ทดสอบ" รั่วไหลแบบนี้ และแถวเหล่านั้นได้คะแนน **83** บนเมตริกคุณภาพเทียบกับ **44** สำหรับแถวที่สะอาด ทุกผลการค้นพบที่สร้างบนตัวเลขนั้นต้องถูกทิ้งทั้งหมด

การรั่วไหลมีหลายรูปแบบ และ**การตรวจสอบการรั่วไหล (leak audit)** ที่เหมาะสมต้องตรวจสอบทุกรูปแบบ:

- **การซ้อนทับแบบตรงทั้งหมด (Exact overlap)** — ต้นฉบับ*หรือ*เป้าหมายเดียวกันปรากฏในทั้งสองฝั่ง (ตัวอย่างข้างต้น)
- **การซ้อนทับแบบใกล้เคียง (Near-duplicate overlap)** — ไม่เหมือนกันทุกตัวอักษร แต่มีเวอร์ชัน*ที่เขียนใหม่*ของประโยคทดสอบอยู่ในชุดฝึก เอกสารในโดเมนเดียวกันมักมีการถอดความที่คล้ายกัน การจับคู่แบบตรงทั้งหมดจะพลาดสิ่งเหล่านี้ ดังนั้น audit จึงวัดความคล้ายคลึงของการซ้อนทับของคำด้วย
- **การซ้อนทับทั้งไฟล์ (Whole-file overlap)** — มีคนฝึกบนสำเนาของไฟล์ทดสอบโดยไม่ตั้งใจ (สิ่งนี้เกิดขึ้นจริง: การเก็บรวบรวม "ข้อมูลฝึก" หนึ่งครั้งกลายเป็นตำราทอง 489 จาก 489 บรรทัดตรงกัน)

### การแบ่งแบบ group-disjoint — วิธีแก้ไข

คุณไม่สามารถแก้ไขการรั่วไหลได้ด้วยการลบแถวที่มีปัญหาทีละแถว รูปแบบจะปรากฏขึ้นมาใหม่ วิธีแก้คือ**การแบ่งแบบ group-disjoint**: ก่อนแบ่ง ให้มัดทุกคู่ที่มีต้นฉบับ*หรือ*เป้าหมายร่วมกันเป็น**กลุ่ม** จากนั้นส่งแต่ละ*กลุ่มทั้งหมด*ไปยังฝั่งเดียวเท่านั้น ตอนนี้ `asam` และทุกอย่างที่แชร์มันอยู่ใน train *หรือ* test ทั้งหมด — ไม่มีทั้งสองฝั่ง หลังจากแบ่งแล้ว คุณ**ตรวจสอบว่าไม่มีการซ้อนทับ**และปฏิเสธที่จะดำเนินการต่อหากยังมีอยู่

:::tip[นี่คือสิ่งที่ "split-guard" ทำให้คุณ]
เมื่อ agent ของคุณรัน splitter มันจะทำการแบ่งแบบ group-disjoint โดยค่าเริ่มต้นและตรวจสอบว่าไม่มีการซ้อนทับโดยอัตโนมัติ คุณไม่ต้องจำกับดัก "Feed him / Feed her" — เครื่องมือทำให้การทำผิดพลาดนั้นเป็นเรื่องยาก และหากคุณพยายามหลีกเลี่ยงมัน มันจะปฏิเสธพร้อมข้อความที่ระบุวิธีแก้ไข
:::

## 5. Overfitting, early stopping และ plateau

**Overfitting** คือสิ่งที่เกิดขึ้นเมื่อโมเดลศึกษาต่อเกินจุดที่เรียนรู้และเริ่ม*จำ* training loss ของมันดูดีมาก แต่คุณภาพการแปลจริงแย่ลง ช่องว่าง loss ใน [§3](#3-what-training-actually-does-loss-and-its-two-faces) คือวิธีที่คุณสังเกตเห็นมัน

**Early stopping** คือการป้องกัน: ดูสัญญาณ dev และเมื่อมันหยุดดีขึ้นตามจำนวนการตรวจสอบที่กำหนด (ค่า **patience** ของมัน) ให้หยุดการฝึกและเก็บเวอร์ชันที่ดีที่สุดก่อนหน้า — **checkpoint** ที่ดีที่สุด (snapshot ที่บันทึกไว้ของโมเดลระหว่างการฝึก) Early stopping ป้องกันทั้งการสิ้นเปลืองทรัพยากรการคำนวณและ overfitting ในคราวเดียว

แต่ early stopping มีโหมดความล้มเหลวที่มีชื่อเสียงเมื่อคุณฝึกส่วนใหญ่บนข้อมูลสังเคราะห์ — **synthetic→real transfer plateau**:

> **ตัวอย่างที่ใช้งานได้จริง — การตายครึ่ง epoch** โมเดลฝึกบนส่วนผสมที่เป็นข้อมูลสังเคราะห์ 97.5% และถูกตัดสินบน dev set *จริง* 42 ประโยค ในช่วงแรก โมเดลเก่งขึ้นอย่างรวดเร็วกับกองสังเคราะห์ขนาดใหญ่ ดังนั้น dev loss บนประโยคจริงลดลงเร็ว ถึงจุดต่ำสุดประมาณ step 8,000 — แล้วค่อยๆ *เพิ่มขึ้น* Early stopping แบบไม่ระมัดระวังเห็น "dev loss เพิ่มขึ้น 6 ครั้งติดต่อกัน" และประกาศชัยชนะที่ epoch 0.52 ซึ่งเป็นหนึ่งในยี่สิบของการฝึกที่วางแผนไว้ แต่โมเดลยังไม่เสร็จ มันเพิ่งเสร็จสิ้นการเรียนรู้สังเคราะห์ที่*ง่าย*และยังไม่ได้เริ่ม**การถ่ายโอน**ที่ช้าไปสู่คุณภาพภาษาจริง มันถูกหยุดที่ plateau ก่อนที่จะได้รับผลตอบแทน

บทเรียน: ด้วยส่วนผสมที่มีข้อมูลสังเคราะห์หนัก การดิ่งลงแล้วขึ้นของ dev loss ในช่วง*แรก*เป็นสิ่งที่**คาดหวังได้** ไม่ใช่การลู่เข้า กฎการหยุดต้องฉลาดพอที่จะรักษาการฝึกผ่าน plateau — ค่าพื้นที่ได้มาจากขนาดของส่วนผสมของคุณ ไม่ใช่ตัวเลขมหัศจรรย์ที่คุณควรรู้อยู่แล้ว

:::note[การตั้งค่าที่ซื่อสัตย์ทำให้บั๊กจริงๆ ปรากฏขึ้น]
บั๊ก plateau นั้นมองไม่เห็นมาหลายเดือน — เพราะการรันก่อนหน้านี้ (อย่างไม่ถูกต้อง) ใช้ชุด*test*เป็น dev set ซึ่งซ่อนมันไว้ การรัน*ที่สะอาด*ครั้งแรกต่างหากที่เปิดเผยมัน นี่คือธีมที่เกิดซ้ำ: การทำอย่างซื่อสัตย์ไม่เพียงแต่ทำให้คุณซื่อสัตย์ มันทำให้ปัญหาจริงๆ มองเห็นได้
:::

## 6. การวัดคุณภาพ: เมตริก, batteries และ registers

เมื่อโมเดล*decode*ประโยคทดสอบ คุณให้คะแนนคำตอบเทียบกับคำแปลอ้างอิงอย่างไร?

### เมตริกแบบให้คะแนนบางส่วน: chrF++ และ BLEU

คำแปลแทบไม่เคยตรงกับคำอ้างอิงทุกคำ แต่ก็ยังสามารถดีมากได้ ดังนั้น MT จึงใช้เมตริก**แบบให้คะแนนบางส่วน**ที่ให้รางวัลกับ*การซ้อนทับ*แทนที่จะต้องการการจับคู่แบบตรงทั้งหมด:

- **chrF++** ให้คะแนนการซ้อนทับของ**ลำดับตัวอักษร** (บวกกับลำดับคำบางส่วน) ระหว่างผลลัพธ์ของโมเดลและคำอ้างอิง เนื่องจากทำงานในระดับตัวอักษร จึงให้คะแนนบางส่วนสำหรับการได้คำ*เกือบ*ถูกต้อง — รากศัพท์ที่ถูกต้องแต่ลงท้ายผิดยังได้คะแนนบ้าง ทำให้เหมาะสมกับภาษาที่มีสัณฐานวิทยาซับซ้อน ซึ่งรากหนึ่งรากมีหลายรูปแบบ ยิ่งสูงยิ่งดี มักรายงานในระดับ 0–100
- **BLEU** คือมาตรฐานเก่า ให้คะแนนการซ้อนทับของ**ชิ้นส่วนคำทั้งคำ** (n-grams) ยังคงรายงานกันอย่างแพร่หลาย แต่เข้มงวดกับภาษาที่คำมีรูปแบบผันหลายแบบ เพราะการพลาดเล็กน้อยที่ลงท้ายนับเป็นการพลาดทั้งหมด

> **ตัวอย่างที่ใช้งานได้จริง** คำอ้างอิง: `awâsisak mêtawêwak` ผลลัพธ์ของโมเดล: `awâsisak mêtawêw` (รากถูกต้อง พยางค์สุดท้ายผิด) BLEU มองว่าคำที่สองผิดทั้งหมด chrF++ เห็นว่าตัวอักษรส่วนใหญ่ตรงกันและให้คะแนนบางส่วน ผลลัพธ์เดียวกัน คะแนนต่างกันมาก — นั่นคือเหตุผลที่เมตริกที่คุณเลือกเปลี่ยนเรื่องราว

:::tip[เมตริกไหนที่ควรเชื่อเป็นคำถามที่ต้องวัด]
ไม่ใช่ทุกเมตริกที่ติดตามการตัดสินของมนุษย์ได้เท่ากันสำหรับทุกภาษา สำหรับบางตระกูลภาษา BLEU แทบไม่สัมพันธ์กับสิ่งที่มนุษย์คิด สำหรับบางภาษาเมตริก neural ที่ซับซ้อนกลับเป็นตัวที่ไม่น่าเชื่อถือ ก่อนที่คุณจะปรับให้เหมาะสมกับ*เมตริกใดๆ* ให้ตรวจสอบหลักฐาน[ความน่าเชื่อถือของเมตริก](/docs/network/specifications/metric-reliability)สำหรับตระกูลภาษาของคุณ — และหากคำตอบที่ซื่อสัตย์คือ "ยังไม่ได้วัด" ให้พูดเช่นนั้นแทนที่จะเชื่อตัวเลข
:::

### เมตริก neural: COMET, MetricX

นอกเหนือจากการซ้อนทับของตัวอักษร/คำ **เมตริก neural** (COMET, COMET-QE, MetricX) ใช้โมเดลที่ฝึกแล้วเพื่อ*ตัดสิน*คำแปลได้ใกล้เคียงกับมนุษย์มากขึ้น อาจน่าเชื่อถือกว่ามาก — แต่เฉพาะสำหรับภาษาที่ถูกฝึกให้ตัดสิน ซึ่งไม่รวมภาษาที่มีทรัพยากรน้อยส่วนใหญ่ นอกจากนี้ยังทำงานแบบขึ้นกับทิศทาง: **MetricX** คือ**ยิ่งต่ำยิ่งดี** ตรงข้ามกับ chrF++ — รายละเอียดที่ควรรู้ก่อนเปรียบเทียบตัวเลข

### Error bars: อย่าเชื่อตัวเลขเดียว

คะแนนเดียวที่ไม่มีความไม่แน่นอนคือกับดัก บนชุดทดสอบขนาดเล็ก ความแตกต่างมักเป็นแค่สัญญาณรบกวน

> **ตัวอย่างที่ใช้งานได้จริง** "โมเดลดีขึ้นจาก 16.7 เป็น 18.1 บนชุดเรื่องเล่าปากเปล่า" ฟังดูเหมือนความก้าวหน้า — จนกว่าคุณจะสังเกตว่าชุดนั้นมี 37 ประโยค ด้วยข้อมูลน้อยขนาดนั้น การแกว่งของ ±3 คะแนนเป็นเรื่องของโชคล้วนๆ รายงานที่ซื่อสัตย์คือ `17.4 [15.1, 19.8] 95% CI`: ตัวเลข บวกกับ**ช่วงความเชื่อมั่น (CI)** — ช่วงที่ค่าจริงน่าจะอยู่ในนั้น หากช่วงของโมเดลสองตัวซ้อนทับกันมาก คุณไม่สามารถอ้างได้ว่าตัวหนึ่งดีกว่า

เครื่องมือที่ดีปฏิเสธที่จะพิมพ์คะแนนโดยไม่มี CI และใช้[การทดสอบนัยสำคัญ](/docs/network/specifications/significance)ก่อนประกาศว่า A ชนะ B

### Batteries และ registers

ภาษาจริงไม่ใช่สิ่งเดียวที่แบนราบ **Register** (หรือ **domain**) คือ*ประเภท*ของภาษา: การสนทนาทั่วไป แบบฝึกหัดในตำราเรียน บทความข่าว เรื่องเล่าปากเปล่า ร้อยแก้วทางการของรัฐบาล โมเดลอาจเก่งในประเภทหนึ่งและอ่อนในอีกประเภทหนึ่ง

**Battery** คือชุดประเมินผลที่แบ่งออกเป็นหลาย register โดยตั้งใจ ให้คะแนน**แยกกัน** เพื่อไม่ให้ค่าเฉลี่ยเดียวซ่อนจุดอ่อน

> **ตัวอย่างที่ใช้งานได้จริง** โมเดลได้คะแนน 46 โดยรวม — น่าพอใจ แต่การแยกย่อย battery แสดงให้เห็น 58 สำหรับแบบฝึกหัดในตำราเรียนและ 22 สำหรับเรื่องเล่าปากเปล่า ค่าเฉลี่ยกำลังซ่อนความล้มเหลวเกือบสมบูรณ์ในการพูดตามธรรมชาติ มีเพียง battery แบบแยก register เท่านั้นที่เปิดเผยมัน

## 7. การสร้างข้อมูลเมื่อคุณมีไม่พอ

เมื่อคู่ประโยคจริงมีน้อย คุณต้องสร้างคู่ประโยคสังเคราะห์ สองเทคนิคที่ครองตลาด และทั้งคู่อยู่หรือตายด้วยคำเดียว: **การตรวจสอบ**

### FSTs และ morphological analyzers

**Morphological analyzer** คือเครื่องมือที่รู้ไวยากรณ์คำของภาษา: วิธีที่รากศัพท์รวมกับคำนำหน้าและคำต่อท้ายเพื่อสร้างคำที่ถูกต้อง หลายตัวถูกสร้างเป็น **FSTs** — *finite-state transducers* เทคโนโลยีที่แม่นยำและอิงกฎเกณฑ์ (ไม่ใช่ neural network) ที่สามารถทำงานได้สองทิศทาง:

- **analyze**: ให้คำหนึ่งคำ แยกมันออกเป็นราก + แท็กไวยากรณ์ (`nipâw` → "นอนหลับ, บุรุษที่สาม เอกพจน์")
- **generate**: ให้ราก + แท็ก สะกดรูปแบบคำที่ถูกต้อง (`sleep + 3sg` → `nipâw`)

สำหรับภาษา polysynthetic — ที่คำเดียวสามารถบรรจุสิ่งที่ภาษาอังกฤษต้องการทั้งประโยค — FST มีค่ามาก: มันสามารถสะกด*รูปแบบที่ถูกต้องใดๆ*ของ*รากที่รู้จักใดๆ* ซึ่งเป็นวัตถุดิบที่ต้องการสำหรับการสร้างข้อมูลฝึก

### การตรวจสอบแบบ round-trip — กฎที่ทำให้ข้อมูลสังเคราะห์น่าเชื่อถือ

การสร้างข้อมูลเป็นเรื่องอันตราย: ตัวสร้างสามารถส่งออกสิ่งไร้สาระโดยไม่มีเสียง วินัยที่ป้องกันมันคือ**กฎ round-trip**: ทุกคำที่สร้างขึ้นต้องผ่าน *generate → analyze → การวิเคราะห์เดิมที่คุณเริ่มต้น* หากคุณขอให้ FST สะกดรูปแบบหนึ่งแล้วป้อนการสะกดนั้นกลับไปและไม่ได้รับแท็กของคุณคืน คำนั้นจะถูกทิ้ง ไม่มีสิ่งใดที่ล้มเหลวการ round-trip ได้รับอนุญาตให้เข้าสู่ข้อมูลฝึกเลย

> **ตัวอย่างที่ใช้งานได้จริง — การรั่วไหลหนึ่งตัวอักษร** พจนานุกรมสะกดเสียงหนึ่งด้วยตัวอักษร `ý` ส่วน analyzer คาดหวัง `y` ธรรมดา เพราะไม่มีใครประสานการสะกดสองแบบที่จุดเชื่อมต่อ *กริยา 1,375 คำ*จึงถูกตัดสินว่า "ไม่รู้จัก" อย่างเงียบๆ และถูกตัดออกจากการสร้าง — เป็นเวลาหลายสัปดาห์โดยไม่มีใครรู้ วิธีแก้คือ**canonicalizer**: ฟังก์ชันเดียวที่ทำให้การสะกดเป็นมาตรฐานเดียว*ทุกที่*ที่สองส่วนประกอบพบกัน บวกกับ**funnel audit**ที่นับจำนวนรายการที่ผ่านแต่ละขั้นตอนของ pipeline เพื่อไม่ให้การหายไปอย่างเงียบๆ ของ 1,375 รายการซ่อนตัวได้อีก

### ความครอบคลุม ไม่ใช่แค่ปริมาณ

ประโยคสังเคราะห์หนึ่งล้านประโยคฟังดูครอบคลุม แต่ไม่ใช่ หากมันเป็นหนึ่งล้านรูปแบบของรูปทรงเดิมไม่กี่แบบ

> **ตัวอย่างที่ใช้งานได้จริง** corpus สังเคราะห์ 1,000,000 คู่กลายเป็นว่าไม่มี**ประโยคคำสั่ง** ("Vote!") **ไม่มีคำถาม wh** ("who/where/when") **ไม่มีการแสดงความเป็นเจ้าของ** ("my dog") และ**ไม่มีรูปแบบ inverse** ("she sees *me*" — ไวยากรณ์หลักในหลายภาษา) analyzer สามารถสร้างทั้งหมดนั้นได้ แต่ template ไม่เคยขอ ปริมาณซ่อนช่องว่างเชิงโครงสร้าง

การป้องกันคือ**รายการตรวจสอบความครอบคลุม**ที่คัดลอกมาจากไวยากรณ์ที่ตีพิมพ์: ปรากฏการณ์ทางไวยากรณ์ที่จำเป็น แต่ละอย่างมีการอ้างอิง เพื่อให้การสร้างล้มเหลวหากปรากฏการณ์ที่จำเป็นมีตัวอย่างเป็นศูนย์ และ**ขีดจำกัดต่อประเภท**หยุดไม่ให้รูปทรง template ใดครองตลาด — ใน corpus หนึ่ง รูปทรงสองแบบคิดเป็น 54% ของข้อมูล ดังนั้นครึ่งหนึ่งของ "ประสบการณ์" ของโมเดลคือรูปแบบประโยคสองแบบ

### Backtranslation

**Backtranslation** คืออีกเทคนิคสังเคราะห์ขนาดใหญ่ และมันฉลาดมาก หากคุณมีข้อความธรรมดา*ที่ยังไม่ได้แปล*ในภาษาเป้าหมายของคุณ (corpus **monolingual** — หาได้ง่ายกว่าข้อความคู่ขนานมาก) คุณสามารถ:

1. นำโมเดล*ย้อนกลับ* (เป้าหมาย → ภาษาอังกฤษ)
2. แปลข้อความเป้าหมาย monolingual ของคุณ*เป็น*ภาษาอังกฤษด้วยเครื่อง
3. จับคู่แต่ละประโยคภาษาอังกฤษที่แปลด้วยเครื่องกับประโยคเป้าหมาย**จริง**ที่คุณเริ่มต้น และ
4. ฝึกโมเดลไปข้างหน้า (ภาษาอังกฤษ → เป้าหมาย) บนคู่ประโยคเหล่านั้น

ด้านเป้าหมายเป็นภาษาจริง มีเพียงด้านภาษาอังกฤษเท่านั้นที่เป็นสังเคราะห์ — โดยทั่วไปถือเป็นการแลกเปลี่ยนที่ดี

> **ตัวอย่างที่ใช้งานได้จริง** คุณมีประโยคจริง 50,000 ประโยคในภาษาเป้าหมายของคุณ แต่มีคู่ประโยคคู่ขนานเพียง 400 คู่ Backtranslate 50,000 ประโยคเป็นภาษาอังกฤษคร่าวๆ และคุณได้เปลี่ยนข้อความ monolingual เป็นคู่ประโยคฝึก 50,000 คู่ที่ด้าน*เป้าหมาย*เป็นของแท้

:::danger[ตรวจสอบการรั่วไหลในข้อความ monolingual ของคุณด้วย]
Backtranslation รู้สึกปลอดภัยเพราะ "มันแค่ข้อความ monolingual" — แต่ข้อความนั้นอาจ*เป็น*ข้อมูล eval ของคุณในรูปแบบปลอมตัว ในโปรเจกต์หนึ่ง leak audit พบว่าการเก็บรวบรวม monolingual ตรงกับชุดทดสอบทองพอดี ตรวจสอบ**ทุก**input กับ**ทุก**ชุด eval ทั้งข้อมูลสังเคราะห์และ monolingual รวมถึง — ไม่ใช่แค่ corpus คู่ขนานที่ชัดเจนของคุณ
:::

### การติดแท็กข้อมูลสังเคราะห์

อีกหนึ่งแนวปฏิบัติสุดท้าย: **ติดแท็ก**แหล่งข้อมูลสังเคราะห์ด้วยเครื่องหมาย (เช่น `<synth>` หรือ `<bt>`) และปล่อยให้ข้อมูลจริง (gold) ไม่มีแท็ก วิธีนี้ช่วยให้โมเดลแยกแยะ "วัสดุฝึกหัด" จาก "ของจริง" เพื่อให้ข้อมูลแท้ยึดรูปแบบผลลัพธ์ของมัน ในเวลาแปลคุณไม่ต้องเพิ่มแท็ก และโมเดลจะพึ่งพาสิ่งที่เรียนรู้จาก gold (ดู[คู่มือ Back-Translation](/docs/network/tutorials/back-translation)สำหรับเทคนิคนี้อย่างละเอียด)

## 8. วิธีที่ชิ้นส่วนต่างๆ เชื่อมต่อกัน

อ่านจากบนลงล่าง นี่คือ workflow หนึ่ง:

1. รวบรวม**ข้อมูลคู่ขนานจริง** ([§1](#1-the-two-piles-training-data-and-evaluation-data)) — มักมีน้อยเกินไป
2. **แบ่ง**แบบ group-disjoint เป็น train / dev / test ([§2](#2-splitting-train-dev-and-test), [§4](#4-contamination-and-leakage-the-mistake-that-eats-results))
3. **สร้าง**ข้อมูลสังเคราะห์เพื่อเติมช่องว่าง — ผ่านการตรวจสอบ round-trip ตรวจสอบความครอบคลุม ตรวจสอบการรั่วไหล ([§7](#7-manufacturing-data-when-you-dont-have-enough))
4. **ฝึก**บนส่วนผสม โดยดู**dev loss / dev generation**เพื่อหลีกเลี่ยง**overfitting**และผ่าน**plateau** ([§3](#3-what-training-actually-does-loss-and-its-two-faces), [§5](#5-overfitting-early-stopping-and-the-plateau))
5. **Decode** **test battery**ที่ถูก held-out และให้คะแนนด้วย**เมตริกแบบให้คะแนนบางส่วน + ช่วงความเชื่อมั่น**แยกตาม**register** ([§6](#6-measuring-quality-metrics-batteries-registers))
6. ทำทั้งหมดโดยไม่ให้คำตอบ eval สัมผัสกับการฝึกเลย ([§4](#4-contamination-and-leakage-the-mistake-that-eats-results)) — กฎที่อีกห้าข้อรับใช้

กฎทุกข้อที่นี่สอดคล้องกับความผิดพลาดจริงที่วัดได้ซึ่งโปรเจกต์จริงทำและบันทึกไว้ คุณไม่ต้องจำทั้งหมด: training suite ทำให้แต่ละข้อเป็นกลไกอัตโนมัติ เพื่อให้เส้นทางที่ซื่อสัตย์เป็นค่าเริ่มต้นและเส้นทางที่ไม่ซื่อสัตย์ปฏิเสธพร้อมคำอธิบาย นั่นคือหัวข้อของหน้าถัดไป

## การสั่งการ agent ของคุณด้วยคำศัพท์เหล่านี้

เนื่องจากคุณจะทำงานผ่าน coding agent ผลตอบแทนในทางปฏิบัติของหน้านี้คือตอนนี้คุณสามารถให้ — และตรวจสอบ — คำสั่งแบบนี้ได้:

- *"แบ่ง corpus แบบ group-disjoint และตรวจสอบว่าไม่มีการซ้อนทับก่อนการฝึก"*
- *"แกะ dev set จากฝั่งฝึก อย่าเลือก checkpoint บนชุดทดสอบ"*
- *"ตรวจสอบการรั่วไหลของทุก input กับทุกชุด eval รวมถึงข้อมูลสังเคราะห์และ monolingual"*
- *"รายงาน chrF++ พร้อมช่วงความเชื่อมั่น 95% แยกตาม register"*
- *"ตรวจสอบความน่าเชื่อถือของเมตริกสำหรับตระกูลภาษานี้ก่อนที่เราจะปรับให้เหมาะสมกับคะแนนใดๆ"*

หาก agent ของคุณมี Champollion MCP server พร้อมใช้งาน มันสามารถเรียก `get_training_guardrails` เพื่อดึงกฎเหล่านี้ — และความผิดพลาดที่แต่ละข้อกำจัด — เข้าสู่ context โดยตรงก่อนที่มันจะเขียนคำสั่งแม้แต่คำสั่งเดียว

**ถัดไป:** นำไปใช้งานจริงใน [**So You Want to Train Your Own Model**](/docs/network/tutorials/train-your-own-model) คู่มือแบบทีละขั้นตอน — หรืออ่าน [**Train a Model Honestly**](/docs/network/getting-started/training-honestly) เพื่อดูว่า suite เปลี่ยนแนวคิดทุกอย่างที่นี่ให้เป็น guardrail อัตโนมัติได้อย่างไร

หากคำศัพท์อย่าง *tokenizer* ยังคงไม่ชัดเจน บทความปูพื้นฐานจากศูนย์คือ [Tokenizers](/docs/learn/tokenizers) — อ่านเพียงครั้งเดียวแล้วทุกอย่างข้างต้นจะเข้าใจได้ง่ายขึ้น
