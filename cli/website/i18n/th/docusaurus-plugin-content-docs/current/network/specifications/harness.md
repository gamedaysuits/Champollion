# Eval Harness v2.0

> **สรุปสำหรับผู้บริหาร** หน้านี้ครอบคลุมการติดตั้ง การกำหนดค่า และการใช้งาน MT evaluation harness — เครื่องมือที่ใช้เปรียบเทียบประสิทธิภาพวิธีการแปลกับ corpus มาตรฐานและสร้าง run card ที่มีคะแนน สำหรับนิยามอย่างเป็นทางการของ metric, schema และโปรโตคอลการประเมิน โปรดดูที่ [Benchmark Specification](/docs/network/specifications/benchmark)

harness รันการทดลองแปลและสร้าง run card โดยจัดการการสร้าง prompt, การเรียก API, การให้คะแนน และการบันทึกผลลัพธ์ — คุณเพียงแค่จัดเตรียม dataset และ model

## การติดตั้ง

**ข้อกำหนด:** Python 3.11+

```bash
python3 -m pip install mt-eval-harness
```

การดำเนินการนี้จะติดตั้งคำสั่ง `mt-eval`

## การใช้งาน

```bash
mt-eval run --corpus path/to/dataset.json
```

การดำเนินการนี้จะรันทุก entry ใน corpus ผ่าน model ที่กำหนดค่าไว้ (หรือ method plugin), ให้คะแนน output และเขียนไฟล์ run card JSON ไปยัง output directory

| `--target-script` | — | — | อักษรตามมาตรฐาน ISO 15924 ที่คำแปลต้องเขียนด้วย (`Latn`, `Cans`, …) ซึ่งต้องเป็นอักษรที่ language card ของภาษาปลายทางระบุไว้ พรอมต์ของ harness จะขอให้ใช้อักษรนี้ (และจะต่อท้ายข้อความของไฟล์แนะนำด้วยเช่นกัน) ดังนั้นจึงถือเป็นส่วนหนึ่งของ sha256 ของพรอมต์ สำหรับภาษาที่เขียนด้วยระบบอักษรมากกว่าหนึ่งระบบ เช่น Plains Cree ให้ใช้ระบบอักษรเดียวกับที่ข้อความอ้างอิงของคุณเขียน หากไม่ระบุ harness จะนับตัวอักษรของข้อความอ้างอิงตามระบบอักษร (ผลรวมทั้งหมด: ไม่มีการแสดงประโยคใด ๆ ข้อกำหนดนี้จึงใช้กับคลังข้อมูลแบบใช้งานเฉพาะที่ได้ด้วยเช่นกัน) และขอให้ใช้อักษรที่มีสัดส่วนตั้งแต่ 90% ขึ้นไป โดยระบุไว้ในส่วนหัวของการรัน ("references are 100% Latn → prompting for Latn") และบันทึกไว้ในบันทึกการรัน (`config.target_script_source`) ข้อความอ้างอิงที่มีหลายอักษรปะปนกันจะไม่ได้รับระบบอักษรใด ๆ และจะมีคำเตือนพร้อมสัดส่วน และข้อความอ้างอิงในอีกอักษรหนึ่งก็จะได้คะแนนใกล้ศูนย์ จะถูกปฏิเสธสำหรับเอนจิน MT หรือปลั๊กอินระเบียบวิธี ซึ่งไม่ได้รับพรอมต์ |

`--champollion-config` และ `--prompt champollion` ถูกยกเลิกการใช้งานแล้วใน 0.2.0 และจะถูกปฏิเสธพร้อมระบุเหตุผล เช่นเดียวกับ `--champollion-cards-dir`; ให้ตั้งค่า `MT_EVAL_CARDS_DIR` เพื่อชี้ harness ไปยังไดเรกทอรี cards อื่น เนื่องจากคำสั่งเหล่านี้สร้างพร้อมต์ของ CLI ขึ้นใหม่ใน Python และสำเนาดังกล่าวเริ่มคลาดเคลื่อนไปจาก CLI ให้ใช้ปลั๊กอินระเบียบวิธี (`--method`) ในการประเมินวิธีของ CLI และใช้ `mt-eval export-config` เพื่อนำผลลัพธ์กลับไปยังโปรเจกต์ CLI

### เมตริกนิวรัลแบบเลือกใช้

COMET จะถูกคำนวณเมื่อใดก็ตามที่ติดตั้ง `unbabel-comet` (`mt-eval setup --comet`: ขนาดประมาณ 300 MB สำหรับการติดตั้ง และประมาณ 2.3 GB สำหรับโมเดลเมื่อใช้งานครั้งแรก) เมตริกอีกสองตัวจะปิดไว้ เว้นแต่การรันจะร้องขอ เนื่องจากแต่ละตัวต้องโหลดโมเดลขนาดใหญ่ เมตริกเหล่านี้ทำงานบนเครื่องนี้เช่นเดียวกับ COMET (ไม่มีค่าใช้จ่าย API, ไม่มีการส่งข้อความไปที่ใด) รายงานควบคู่กับคะแนนหลัก chrF++ และไม่นำมารวมกัน และ run card จะระบุว่า "not run" พร้อมแจ้งแฟล็กที่ต้องส่งค่าเมื่อไม่ได้ร้องขอ

| เมตริก | แฟล็ก | สิ่งที่ต้องใช้ | ทรัพยากรที่ใช้ |
|--------|------|---------------|---------------|
| MetricX-24 (`metricx_score`, ยิ่งน้อยยิ่งดี, 0–25) | `--metricx` (เช็กพอยต์: `--metricx-model`) | `python3 -m pip install 'mt-eval-harness[metricx]'` (PyTorch, Transformers, SentencePiece) และโค้ดโมเดลของ Google ซึ่งไม่ได้อยู่บน PyPI: `python3 -m pip install git+https://github.com/google-research/metricx` | เช็กพอยต์ `google/metricx-24-hybrid-large-v2p6` เริ่มต้นและตัวตัดคำ mT5-XL จะดาวน์โหลดข้อมูลหลาย GB จาก Hugging Face เมื่อใช้งานครั้งแรก; การให้คะแนนจะช้าเมื่อใช้ CPU หากไม่มีข้อความอ้างอิงจะให้คะแนนในโหมดไม่ต้องมีข้อความอ้างอิง (QE) |
| ตัวเปรียบเทียบรูปแบบ FUSE (`fuse_score`) | `--fuse` | `python3 -m pip install 'mt-eval-harness[fuse]'` (sentence-transformers, jellyfish) | LaBSE จะดาวน์โหลดข้อมูลประมาณ 1.8 GB เมื่อใช้งานครั้งแรก หากไม่มี LaBSE จะไม่คำนวณคะแนน และรายงานจะระบุไว้เช่นนั้น เมตริกนี้ไม่ได้ผ่านการเทรน (เป็นค่าเฉลี่ยแบบไม่ถ่วงน้ำหนักของส่วนประกอบต่าง ๆ) และผลลัพธ์จะถูกตั้งค่าสถานะ `fuse_untrained` |

บน MCP (โปรไฟล์ตัวเต็ม `--profile full`) ตัว `run_benchmark` รองรับ `metricx` (ร่วมกับ `metricx_model`) และ `fuse` ส่วน `comet: true` จำเป็นต้องใช้ COMET โดยแผนการทำงานจะระบุว่าแต่ละตัวได้รับการติดตั้งไว้หรือไม่ และการรันที่ได้รับการยืนยันแล้วซึ่งร้องขอสิ่งที่ harness ไม่สามารถคำนวณได้จะถูกปฏิเสธ

รายละเอียดว่าแต่ละเมตริกวัดอะไรและเชื่อถือได้มากเพียงใดสำหรับภาษาหนึ่ง ๆ สามารถดูได้ที่ [การให้คะแนน](/docs/network/specifications/scoring) และ [ความน่าเชื่อถือของเมตริก](/docs/network/specifications/metric-reliability)

### แคชการแปล

ทุกการรันจะเก็บผลลัพธ์ของโมเดลสำหรับประโยคต้นทางแต่ละประโยคไว้ในแคช (`--cache-dir` โดยค่าเริ่มต้นคือ `eval/cache/harness` ภายใต้ไดเรกทอรีที่เริ่มการรัน) ทำให้การรันซ้ำด้วยการตั้งค่าเดิมสามารถนำผลลัพธ์มาใช้ใหม่ได้โดยไม่มีค่าใช้จ่าย คีย์ของแคชครอบคลุมถึงโมเดล, พร้อมต์ตามที่ส่งไป (sha256 ของพร้อมต์), การตั้งค่าที่ส่งผลต่อเอาต์พุต และเวอร์ชันของ harness ดังนั้นการเปลี่ยนแปลงใด ๆ ข้างต้นจะไม่มีทางได้ผลลัพธ์เก่าอย่างแน่นอน แคชนี้จะเก็บสำเนาประโยคของคลังข้อมูล:

- ส่วนหัวของการรันและการทำ dry run จะพิมพ์บอกตำแหน่งและจำนวนรายการที่แคชเก็บไว้
- โฟลเดอร์จะมี `.gitignore` เพื่อให้ git ละเว้นโฟลเดอร์นี้
- จะไม่มีการเขียนลงในโฟลเดอร์ `mt-eval contest prepare` ที่ระบุว่าสามารถเผยแพร่ได้ (ใน `public/`): `mt-eval run` จะปฏิเสธ `--cache-dir` หรือ `--output-dir` ดังกล่าว และจะระบุโฟลเดอร์ `runs/` ของการแข่งขันแทน ([จัดและรันการแข่งขันแบบอธิปไตย](/docs/network/sovereignty/run-a-sovereign-contest))
- คลังข้อมูลที่ใช้เฉพาะในเครื่อง ปิดผนึก หรือต้องได้รับความยินยอม จะได้โฟลเดอร์ `protected/<namespace>/` ของตัวเอง โดยใช้คีย์จากการตั้งค่าของการรัน, sha256 ของคลังข้อมูล และข้อกำหนดของคลังข้อมูล และทุกไฟล์ในนั้นจะกำกับตราของคลังข้อมูลไว้ในไฟล์เสริม (sidecar) `<file>.champollion.json` ([การลงทะเบียนคลังข้อมูล](/docs/network/sovereignty/registering-corpora))
- ลบโฟลเดอร์เพื่อลบสำเนา หรือส่งแฟล็ก `--no-cache` หากไม่ต้องการเก็บไว้เลย

`run_benchmark` ของเซิร์ฟเวอร์ MCP (โปรไฟล์ตัวเต็ม) จะระบุชื่อแคชในแผนและผลลัพธ์ สำหรับไฟล์ที่คุณถือไว้ แคชจะถูกวางไว้ข้าง ๆ ผลลัพธ์ของการรัน (`<corpus folder>/results/cache/`) และสำหรับ id ของคลังข้อมูลที่ลงทะเบียนไว้ จะวางไว้ในโฟลเดอร์ของมันเอง (`~/.champollion-mcp/cache/harness/`) แคชที่มีอยู่แล้วใน `eval/cache/harness` ภายใต้ไดเรกทอรีการทำงานของเซิร์ฟเวอร์จากการรันครั้งก่อนหน้าจะยังคงถูกนำมาใช้ต่อไป จึงไม่ต้องจ่ายเงินซ้ำซ้อนสำหรับผลลัพธ์เดิม ข้อมูลในแคชไม่ขึ้นอยู่กับตำแหน่งของโฟลเดอร์ ดังนั้นจึงสามารถย้ายได้

### คำสั่งย่อยทั้งหมด

คำสั่งย่อยระดับบนสุดทั้งหมด 20 คำสั่ง แฟล็กทุกตัวของแต่ละคำสั่งอยู่ใน
[การอ้างอิงคำสั่ง `mt-eval`](/docs/reference/mt-eval) ที่สร้างขึ้น ส่วนนี้
จะอธิบายว่าแต่ละคำสั่งมีไว้สำหรับทำอะไร

**รันและให้คะแนน**

| คำสั่งย่อย | หน้าที่ |
|---|---|
| `mt-eval run` | ดำเนินการรันการแปล (ตามแฟล็กข้างต้น) |
| `mt-eval test <log>` | วิเคราะห์บันทึกการรันที่เสร็จสมบูรณ์ `-o <path>` จะเขียนรายงานไปยังตำแหน่งอื่นที่ไม่ใช่ `<log>_report.json` และบันทึกการรันจะบันทึกเส้นทางนั้นไว้เพื่อให้ `card` และ `compare` ค้นพบได้ `--glossary <file>` จะให้คะแนนคำศัพท์เทียบกับกลอสซารีดังกล่าว รายงานจะบันทึกชื่อและ sha256 ของกลอสซารี ส่วน card, `compare` และตัวอย่างก่อนเผยแพร่จะระบุว่าความสอดคล้องของคำศัพท์ (การวินิจฉัย) ได้รับการให้คะแนนเทียบกับกลอสซารีใด |
| `mt-eval compare <reports…>` | เปรียบเทียบการรันตั้งแต่สองรายการขึ้นไป (`*_report.json` หรือบันทึกการรัน) หนึ่งแถวต่อหนึ่งเมตริก (chrF++, BLEU, spBLEU, TER, …), หนึ่งคอลัมน์ต่อหนึ่งการรันกำกับด้วยตัวอักษร A, B, C…, เมตริกที่ค่ายิ่งน้อยยิ่งดีจะถูกทำเครื่องหมายไว้; `--significance` จะเพิ่มการทดสอบแบบจับคู่สำหรับทุกคู่ แต่ละตารางตั้งชื่อตามตัวอักษรของการรัน พร้อมช่วงความเชื่อมั่น 95% ของ Δ และระบุว่าค่า p-value เป็นรายเมตริกและยังไม่ได้รับการปรับแก้; `--method paired_bootstrap` จะสลับจากการสุ่มแบบประมาณ (approximate randomization) ที่เป็นค่าเริ่มต้นไปใช้ Koehn bootstrap ([นัยสำคัญทางสถิติ](/docs/network/specifications/significance)) โดยจะเขียนไฟล์ `comparison-<hash>.json` (แฮชของ id ของการรันที่เปรียบเทียบ เพื่อไม่ให้การเปรียบเทียบอื่นเขียนทับ) ไว้ข้าง ๆ รายงานเมื่อใช้โฟลเดอร์ร่วมกัน หรือเขียนใน `comparisons/` ในโฟลเดอร์ร่วมที่ใกล้ที่สุด (ไม่เขียนลงในโฟลเดอร์ของการรันใดการรันหนึ่งโดยเฉพาะ) เว้นแต่ `-o` จะระบุชื่อไฟล์ไว้ การทดสอบ chrF++ เพียงอย่างเดียวจะเป็นตัวตัดสินว่าการรันใดดีกว่า แถวอื่น ๆ จะแสดงไว้แต่ไม่ได้ใช้ในการตัดสิน คะแนนรวม (composite) ของรายงานรุ่นเก่าจะถูกระบุว่ายกเลิกการใช้งานแล้วและจะไม่นำมาเปรียบเทียบ |
| `mt-eval dashboard <logs…>` | สร้างแดชบอร์ด HTML แบบอินเทอร์แอ็กทีฟ |
| `mt-eval card <run log>` | พิมพ์ run card ให้อ่านง่ายในรูปแบบที่มนุษย์อ่านเข้าใจได้ คะแนนจะนำมาจากรายงานของการรัน: ซึ่งอยู่ข้าง ๆ บันทึก log ที่ `mt-eval test -o` บันทึกไว้ หรือ `--report <path>` การรันที่ไม่พบรายงานจะแสดงข้อความ NOT SCORED และตำแหน่งที่ค้นหา โดยจะไม่แสดงเป็นเลขศูนย์ สามารถส่งไฟล์รายงานเข้ามาได้เช่นกัน ซึ่งจะอ่านควบคู่กับบันทึกการรันที่ระบุไว้ |

**นำระเบียบวิธีไปใช้งาน** (ไม่มีการให้คะแนน)

| คำสั่งย่อย | หน้าที่การทำงาน |
|---|---|
| `mt-eval translate` | แปลอินพุตที่มีเฉพาะต้นทางด้วยระเบียบวิธีหนึ่ง — ไปป์ไลน์การรันที่ไม่มีการให้คะแนน บันทึก `.jsonl` หรือ `.tsv` พร้อมข้อกำหนดของอินพุตเป็น sidecar แบบ set/1 สำหรับระเบียบวิธีที่มีเอาต์พุตแบบใช้งานเฉพาะที่จะบันทึกไว้เฉพาะภายในโปรเจกต์เท่านั้น เว้นแต่ `--holders-agreed-by` จะระบุว่าผู้ถือครองข้อมูลรายใดให้ความยินยอมแล้ว |
| `mt-eval serve` | ให้บริการระเบียบวิธีที่รันบนเครื่องนี้ (`lexicon`, `local-model` หรือปลั๊กอินในคลาสของความต้องพึ่งพา S หรือ O) ภายใต้ข้อตกลง `/translate` ของ champollion โดยใช้ไฟล์ deployment/1 หรือแฟล็ก พร้อมไฟล์ gate-chain/1 ทางเลือกที่จะคอยตรวจสอบคัดกรองทุกคำตอบ ค่าเริ่มต้นจะผูกกับ 127.0.0.1 หากต้องการใช้โฮสต์อื่นจำเป็นต้องระบุ `$MT_EVAL_SERVE_TOKEN` |

**ค้นหาระเบียบวิธีที่เหมาะสม**

| คำสั่งย่อย | หน้าที่ |
|---|---|
| `mt-eval recommend <src> <tgt>` | คำแนะนำระเบียบวิธีสำหรับคู่ภาษา — ความพร้อมใช้งานพร้อมกับ**หลักฐานอ้างอิง** ไม่ใช่แค่การจัดอันดับเปล่า ๆ สามารถระบุคู่ภาษาเป็น `--source <src> --target <tgt>` ซึ่งเป็นรูปแบบที่ `corpora` ใช้ได้เช่นกัน |
| `mt-eval corpora --source X --target Y` | แสดงรายการคลังข้อมูลสำหรับการประเมินที่มีอยู่สำหรับคู่ภาษา แฟล็กใดแฟล็กหนึ่งสามารถทำงานแยกเดี่ยวได้: `--target Y` แสดงคลังข้อมูลทั้งหมดที่แปลไปยัง Y ส่วน `--source X` แสดงคลังข้อมูลทั้งหมดที่แปลออกจาก X |
| `mt-eval corpora --with-fst` | แสดงเฉพาะคลังข้อมูลที่ภาษาปลายทางมี FST ที่ harness ตรึงเวอร์ชันไว้ เพื่อให้สามารถคิดคะแนน FST acceptance ได้ แต่ละภาษาปลายทางจะแสดงข้อมูลว่ามี FST ติดตั้งอยู่บนเครื่องนี้หรือไม่ และจะติดตั้งอย่างไร (`mt-eval setup --lang <code>` หรือการติดตั้งด้วยตนเองสำหรับบางรูปแบบ) ใช้งานร่วมกับ `--source`/`--target` หรือใช้เดี่ยว ๆ สำหรับทุกคู่ภาษาได้ โดยจะไม่มีการดาวน์โหลดสิ่งใด |
| `mt-eval list models\|prompts\|datasets` | แสดงรายการทรัพยากรที่มีอยู่ |

| คำสั่งย่อย | หน้าที่การทำงาน |
|---|---|
| `mt-eval contest` | จัดหรือเข้าร่วม **sovereign contest** — ส่วนของผู้จัด: `prepare`, `register`, `create`, `rank`, `close`, `export`; ส่วนของผู้เข้าร่วม: `qualify` (ให้คะแนนชุดพัฒนาสาธารณะด้วยตนเองเพื่อรับใบเสร็จการเข้ารับการคัดเลือก เกณฑ์คัดเลือกคือ chrF++ ในช่วง 0–100), `validate` (ซักซ้อมการตรวจสอบของโหนดแบบออฟไลน์), `submit-model` / `submit-method` (ส่งมอบโมเดลหรือระเบียบวิธี), `status`, `list` การเข้าร่วมการแข่งขันทำได้โดยการส่งมอบสิ่งที่โหนดของผู้จัดสามารถสั่ง RUN ได้ โดยการอัปโหลดคำแปลและการใส่ลิงก์ไปยังการ์ดที่รายงานผลด้วยตนเองได้ถูกยกเลิกเป็นช่องทางการเข้าร่วมตั้งแต่วันที่ 2026-09-06 |
| `mt-eval shared-task` | ร่มรวมฉบับงานร่วมแบบหลายคู่ภาษา: แถวหนึ่งจะจัดกลุ่มการแข่งขัน N การแข่งขันต่อคู่ภาษาของฉบับงานร่วมแบบหลายคู่ภาษา และนำค่านโยบายเริ่มต้นมาใช้ **มีไว้สำหรับการจัดกลุ่มและค่าเริ่มต้นเท่านั้น — เกตทุกตัวยังคงแยกตามแต่ละการแข่งขัน** |
| `mt-eval node` | **โหนดการให้คะแนนของผู้จัด** ตรวจดึงข้อมูลขาเข้า ตรวจสอบคัดกรองตามเกณฑ์คุณสมบัติสาธารณะ ตรวจสอบสิทธิ์ตามนโยบายของการแข่งขัน ให้คะแนนเทียบกับ**ข้อความอ้างอิงลับที่ผู้จัดถือไว้** และเผยแพร่เฉพาะคะแนนเท่านั้น นี่คือคำสั่งเบื้องหลัง [จัด Sovereign Contest](/docs/network/sovereignty/run-a-sovereign-contest) และ [Sovereign Eval Node](/docs/network/sovereignty/sovereign-eval-node) — คลังข้อมูลจะไม่ถูกส่งออกจากเครื่องของผู้จัดโดยเด็ดขาด |

`mt-eval node` มีคำสั่งย่อยในตัวอีก 18 คำสั่ง รวมถึงช่องทาง airgap
(`import-bundle`, `export-scores`, `relay`, `egress-check`, `manifest`) และพิธี
มอบสิทธิ์ดูแลแบบ M-of-N (`ceremony`, `seal`, `keygen`, `sign-manifest`,
`verify-manifest`, `ledger`) รัน `mt-eval node --help`; โดยกลไก
ความเป็นอธิปไตยจะอธิบายไว้ในทั้งสองหน้าที่เชื่อมโยงไว้ด้านบน

**การติดตั้งและตั้งค่า**

| คำสั่งย่อย | หน้าที่ |
|---|---|
| `mt-eval setup` | ติดตั้งการพึ่งพาเสริม (เมตริกนิวรัล COMET, รันไทม์ FST) |
| `mt-eval logout` | ลบข้อมูลรับรองการยืนยันตัวตนที่จัดเก็บไว้ |

### ตัวอย่าง

```bash
# Run with defaults (google/gemini-3.1-pro-preview, naive prompt)
mt-eval run --corpus eval-amh-fra-globalvoices-test-v1

# Coached experiment with coaching file
mt-eval run \
  --corpus eval-amh-fra-globalvoices-test-v1 \
  --model google/gemini-3.1-pro-preview \
  --coaching-file prompts/crk-coaching-v8.txt \
  --temperature 0.0

# Run a custom method plugin
mt-eval run \
  --corpus eval-amh-fra-globalvoices-test-v1 \
  --method ./methods/fst-gated-pipeline
```

harness จะไม่ลองแปลซ้ำหรือกรองคำแปลที่ FST ปฏิเสธโดยเด็ดขาด: การยอมรับ
ของ FST เป็นเมตริกวัดผล ซึ่งจะคำนวณคะแนนเมื่อ eval pack ของภาษานั้นมี FST
ระเบียบวิธีที่ต้องการการลองแปลซ้ำโดยใช้ FST นำทาง ให้ดำเนินการภายในปลั๊กอินของตัวเอง ดังที่
บทแนะนำ `fst-gated-pipeline` แสดงไว้ (`--fst-retries` และ `--hooks` ไม่เคย
ถูกเชื่อมโยงกับสิ่งใดบนบรรทัดคำสั่ง และทั้งสองจะถูกปฏิเสธด้วยเหตุผลดังกล่าว)

## Run Card Schema

ทุกการทดลองจะสร้าง **run card** — เอกสาร JSON ที่มีข้อมูลครบในตัวเอง โครงสร้างระดับบนสุด:

```json
{
  "run_id": "uuid-v4",
  "harness_version": "2.0",
  "model_slug": "google/gemini-3.1-pro-preview",
  "model_id": "gemini-3.1-pro-001",
  "condition": "naive",
  "timestamp": "2026-06-01T03:22:41Z",
  "elapsed_seconds": 142.7,
  "dataset": { ... },
  "config": { ... },
  "method_card": { ... },
  "system_prompt_sha256": "abc123...",
  "system_prompt_used": "You are a translator...",
  "fingerprint": { ... },
  "scores": { ... },
  "totals": { ... },
  "environment": { ... },
  "results": [ ... ],
  "run_card_hash": "sha256-of-entire-card"
}
```

ดูที่ [Run Card Specification](/docs/network/specifications/run-card) สำหรับ schema แบบเต็มพร้อมเอกสารประกอบทุก field

:::info[สคีมาที่มีผลผูกพันอย่างเป็นทางการ]
[ข้อกำหนดมาตรฐานการวัดประสิทธิภาพ (Benchmark Specification)](/docs/network/specifications/benchmark) คือแหล่งข้อมูลความจริงแหล่งเดียว (SSOT) สำหรับสคีมาของ run card สำหรับคำนิยามของเมตริกและวิธีการให้คะแนนการรัน โปรดดูที่ [ข้อกำหนดการให้คะแนน](/docs/network/specifications/scoring) หน้านี้ให้ข้อมูลวิธีใช้งาน harness ส่วนเอกสารข้อกำหนดจะนิยามความหมายของผลลัพธ์ต่าง ๆ
:::

### บล็อกสำคัญ

**`dataset`** — ระบุว่าใช้ dataset ใด รวมถึง content hash เพื่อผูกผลลัพธ์กับเวอร์ชันที่เฉพาะเจาะจง:

```json
// Example using textbook_dev.json — the 436-entry textbook dev split
{
  "id": "edtekla-dev-v1",
  "version": "1.0",
  "language_pair": "EN→CRK",
  "sha256": "...",
  "entry_count": 436
}
```

**`scores`** — metric รวมสำหรับการรัน:

```json
// Counts reflect the dataset used (here: textbook_dev.json, 436 entries)
{
  "total": 436,
  "exact_matches": 12,
  "exact_match_rate": 0.0968,
  "fst_accepted": 87,
  "fst_acceptance_rate": 0.7016,
  "chrf_plus_plus": 42.31,
  "errors": 0,
  "avg_latency_seconds": 1.15,
  "median_latency_seconds": 1.02,
  "p95_latency_seconds": 2.34,
  "by_difficulty": { ... },
  "by_provenance": { ... }
}
```

**`totals`** — การติดตามการใช้ token และค่าใช้จ่าย:

```json
{
  "prompt_tokens": 48200,
  "completion_tokens": 3100,
  "reasoning_tokens": 0,
  "cached_tokens": 12000,
  "total_cost_usd": 0.42,
  "cost_per_entry_usd": 0.0034,
  "reasoning_ratio": 0.0
}
```

## เมตริกรูปแบบการเขียนและระดับภาษา (เพื่อให้ข้อมูล) {#writing-style-and-register-metrics-informational}

harness สามารถประเมินว่าการแปลตรงกับ **register** และ **รูปแบบการเขียน** เป้าหมายหรือไม่ ผ่าน metric plugin `WritingStyleConsistency` (`mt_eval_harness/plugins/writing_style.py`) การแปลอาจถูกต้องทางภาษาศาสตร์แต่ใช้ register ผิด — ภาษาไม่เป็นทางการในเอกสารทางกฎหมาย หรือภาษาทางการในเนื้อหาการตลาด — และ string metric จะไม่สังเกตเห็น แต่ metric เหล่านี้จะตรวจพบ

**สิ่งที่วัด (ต่อ entry):**

| Metric | Scale | ความหมาย |
|--------|-------|---------|
| `style_register_match` | boolean | output ตรงกับ register ที่คาดหวังหรือไม่? เป้าหมายมาจาก field `register` ของ corpus entry (ดู [Benchmark Spec §2.6](/docs/network/specifications/benchmark)) หรือจาก style profile |
| `style_sentence_length_ratio` | float | ความยาวประโยคเฉลี่ยที่คาดการณ์เทียบกับ reference (1.0 = ตรงกัน; ค่าที่เบี่ยงเบน = style drift) |
| `style_formality_score` | 0.0–1.0 | การมีอยู่ของ marker ทางการ/ไม่เป็นทางการ (สรรพนาม T–V, คำย่อ, …) โดยใช้ทรัพยากร marker ตามภาษา |

**ค่ารวม:** `style_consistency_rate` — สัดส่วนของ entry ที่ไม่พบความไม่ตรงกันของ register

เปิดใช้งานเป้าหมายที่กำหนดเองด้วย `--style-profile path/to/profile.json` (เช่น brand-voice profile) หากไม่มี plugin จะใช้ metadata `register` ของแต่ละ corpus entry แทนเมื่อมีข้อมูล

:::caution[ขอบเขตตามความเป็นจริง]
เมตริกเหล่านี้เป็น**การวินิจฉัย** — ไม่เคยนำมารวมเป็นส่วนหนึ่งของคะแนนหลัก และการตรวจหาระดับความเป็นทางการนั้นใช้ตัวบ่งชี้เป็นหลัก (ฮิวริสติก) ไม่ใช่การตัดสินที่มาจากการเรียนรู้ของโมเดล โปรดปฏิบัติต่อเมตริกเหล่านี้ในฐานะเครื่องตรวจจับความคลาดเคลื่อน (drift detector) สำหรับการรักษาระดับภาษา ไม่ใช่คำตัดสินคุณภาพของรูปแบบการเขียน
:::

## Fingerprint vs Run Card Hash {#fingerprint-vs-run-card-hash}

harness สร้าง hash ที่แตกต่างกันสองแบบ โดยแต่ละแบบมีวัตถุประสงค์ต่างกัน:

### Fingerprint

**fingerprint** ตอบคำถามว่า: *"การรันนี้สามารถทำซ้ำได้หรือไม่?"*

มันสร้าง hash จากการรวมกันของ input ที่กำหนดการกำหนดค่าการทดลอง — ไม่ใช่ output:

- SHA-256 ของชุดข้อมูล
- สลักโมเดล (Model slug)
- ป้ายกำกับเงื่อนไข
- SHA-256 ของ System prompt
- อุณหภูมิ (Temperature)
- ขนาดแบทช์ (Batch size)
- เครื่องมือที่เปิดใช้งาน
- เวอร์ชันของ Harness

รวมทั้งหมดแปดองค์ประกอบ: ขนาดแบทช์และการเรียกใช้เครื่องมือส่งผลต่อเอาต์พุต
อย่างมีนัยสำคัญ จึงถือเป็นส่วนหนึ่งของอัตลักษณ์การทดลอง — การรันสองครั้งที่มี
ขนาดแบทช์ต่างกันจะ**ไม่**ใช้ลายนิ้วมือ (fingerprint) ร่วมกัน ดูที่
[ข้อกำหนด Benchmark §3.8](/docs/network/specifications/benchmark#38-fingerprint)

การรันสองครั้งที่มี fingerprint เหมือนกันใช้การตั้งค่าเดียวกัน ผลลัพธ์ควรเปรียบเทียบได้ (ยกเว้นความไม่แน่นอนของ API)

### Run Card Hash

**run card hash** ตอบคำถามว่า: *"ไฟล์ผลลัพธ์เฉพาะนี้ถูกแก้ไขหรือไม่?"*

มันคือ SHA-256 ของ run card JSON ทั้งหมด (ยกเว้น field `run_card_hash` เอง) หากมี field ใดเปลี่ยนแปลง — คะแนน, timestamp, output เดียว — hash จะเสีย

:::info[เลือกใช้อะไรในสถานการณ์ใด]
ใช้ **fingerprint** เพื่อจัดกลุ่ม run ที่เปรียบเทียบกันได้ (experiment เดียวกัน ต่าง execution) ใช้ **run card hash** เพื่อตรวจสอบความสมบูรณ์ของไฟล์ผลลัพธ์เฉพาะรายการ
:::

## การเผยแพร่ไปยัง Leaderboard

หลังจากเสร็จสิ้นการรัน ให้ใช้ `mt-eval publish` กับ `<run-id>_report.json` ของการรันนั้น การเขียนลงในลีดเดอร์บอร์ดจริงจำเป็นต้องระบุ `--prod` (หรือ `MT_EVAL_ALLOW_PROD=1`) อย่างชัดเจน; โดยที่ `mt-eval run --publish --prod` จะทำทั้งสองขั้นตอนพร้อมกันในคราวเดียว:

```bash
mt-eval publish eval/logs/harness/<run-id>_report.json --dry-run   # preview
mt-eval publish eval/logs/harness/<run-id>_report.json --prod      # write to the live board
```

หากไม่ได้ระบุ `--method-card` ระหว่างการรัน `mt-eval publish` จะเปิด interactive wizard (`method_card_wizard.py`) ที่จะแนะนำคุณในการอธิบาย method (ชื่อ, class, tool ที่ใช้ ฯลฯ) output ของ wizard จะถูกฝังใน run card ก่อนการส่ง

### การตรวจสอบด้วยตนเอง

Run card จะถูกบันทึกเป็นไฟล์ JSON ในไดเรกทอรีผลลัพธ์ (`eval/logs/harness/` โดยค่าเริ่มต้น) — ตรวจสอบที่นั่นก่อนเผยแพร่ `mt-eval publish` คือเส้นทางการส่ง ไม่มีการรับ run card ผ่าน PR

:::note[Submission API และการอัปโหลดผ่านเว็บยังไม่พร้อมใช้งาน]
endpoint `POST https://champollion.dev/api/leaderboard/submit` และ UI สำหรับอัปโหลดไปยัง Leaderboard อยู่ในแผนงานแต่**ยังไม่ได้พัฒนา** จนกว่าจะพร้อมใช้งาน เส้นทางการส่งที่ใช้งานได้เพียงทางเดียวคือ `mt-eval publish`
:::

:::warning[การตรวจสอบของ Leaderboard]
Leaderboard จะตรวจสอบ run card ที่ส่งมากับ dataset registry การส่งที่อ้างอิง dataset ที่ไม่รู้จัก หรือมี `run_card_hash` ที่เสียหาย จะถูกปฏิเสธ
:::

:::danger[ห้ามนำข้อมูลประเมินผลไปใช้ฝึกโมเดล]
หากวิธีการของคุณได้เห็นชุดข้อมูลประเมินผลระหว่างการพัฒนา ไม่ว่าจะเป็นข้อมูลฝึก, ตัวอย่าง few-shot, รายการในพจนานุกรม หรือเนื้อหาสำหรับ prompt engineering — การส่งของคุณจะถูก**ตัดสิทธิ์** ดูที่ [MT Evaluation](/docs/network/leaderboard/rules) สำหรับเกณฑ์ที่ทำให้วิธีการดีหรือไม่ดี
:::
