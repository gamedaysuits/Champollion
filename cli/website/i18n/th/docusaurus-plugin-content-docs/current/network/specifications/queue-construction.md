# ข้อกำหนดการสร้างคิว

**เวอร์ชันสูตร: `ecv-v3` (ค่าลูกโซ่ที่คาดหวังพร้อมความน่าเชื่อถือของสะพาน)**
เอกสารนี้คือนิยามเชิงบรรทัดฐานของวิธีการเรียงลำดับ
[champollion.dev/queue.json](https://champollion.dev/queue.json)
การนำไปใช้งาน
(`arena/scripts/generate_sweep_queue.py` ใน public harness repo)
สะท้อนหน้านี้ทีละส่วน โดยข้อมูลเมตาของคิวจะสะท้อนค่าพารามิเตอร์ที่ใช้จริงในขณะสร้าง และ **ทุกรายการมีรายละเอียดสูตรครบถ้วน** เพื่อให้สามารถคำนวณอันดับใดก็ได้ด้วยมือจาก JSON ที่เผยแพร่เพียงอย่างเดียว หากหน้านี้และคิวขัดแย้งกัน ถือเป็น bug — กรุณารายงาน

**คิวในปัจจุบัน สรุปในหนึ่งย่อหน้า** คิวสาธารณะ (public queue) จะรวบรวมทั้งรายการของ LLM (เงื่อนไขการพรอมต์แบบ naive และ coached) และรายการของเอนจิน MT-service ไว้บนบอร์ดเดียวกัน โดยจัดอันดับตาม survey ordering (`map`, §2.2): การค้นพบครั้งแรก (first light) ข้ามคู่ภาษา, ภาษา, และตระกูลภาษาต่อดอลลาร์ พร้อมกับการบูสต์การอ่านครั้งแรก (first-reading boost) สำหรับภาษาที่ไม่เคยถูกวัดผลมาก่อน (§2.2), ระดับงบประมาณ (budget tiers) ที่เผยแพร่ในพรีวิว (§2.1.1), และการจัดอันดับฉบับสมบูรณ์ที่ให้บริการจากฐานข้อมูล (ไฟล์สแตติกจะเก็บเฉพาะส่วนบนสุดเมื่อการจัดอันดับทั้งหมดมีขนาดเกินขีดจำกัด และจะมีการระบุไว้) ส่วนต่างๆ ด้านล่างนี้คือคำจำกัดความเชิงบรรทัดฐาน (normative definition) ซึ่งเก็บรักษาไว้พร้อมประวัติการตัดสินใจที่ระบุวันที่ — เมทาดาตาบนคิวที่ให้บริการใดๆ จะระบุพารามิเตอร์ที่แน่นอนซึ่งใช้ในการจัดอันดับคิวนั้น

> **v3 (2026-06-13).** ทุก edge ขณะนี้คือ *สะพาน* ที่มีสองตัวเลข —
> คุณภาพและความน่าเชื่อถือ — และ chain matrix ทำงานบนผลคูณของทั้งสอง
> (§1.5) รายการคำศัพท์เดี่ยว 62 คำที่รันครั้งเดียวไม่สามารถนับเป็น path ได้อีกต่อไป
> การทำซ้ำ คอร์ปัสขนาดใหญ่ขึ้น คอร์ปัสที่สมบูรณ์ขึ้น และช่วงความเชื่อมั่นที่แคบลง
> ล้วนมีมูลค่าที่ตีราคาได้ คิว v2 (เฉพาะคุณภาพ) ยังคงตีความได้ผ่านข้อมูลเมตาของตัวเอง

## 1. วัตถุประสงค์: mesh ที่ถ่วงน้ำหนักด้วยคุณภาพ

ภารกิจคือ *ทุกภาษาสู่ทุกภาษาผ่าน chain คู่ภาษาที่วัดค่าได้รายคู่* การแปลระหว่างสองภาษาที่ไม่มี benchmark ตรงจะให้บริการโดย **การเชื่อมต่อแบบลูกโซ่** ของคู่ที่มี benchmark (X→pivot→Y) ดังนั้นสิ่งที่ benchmark มีค่าไม่ใช่จำนวนคอร์ปัส แต่คือ **ความสามารถในการเชื่อมต่อแบบลูกโซ่ของกราฟ**

**นิยาม.** ให้ *กราฟ benchmark* มีหนึ่ง node ต่อหนึ่งภาษา และสำหรับทุกคู่ภาษาที่มีการรันที่เผยแพร่แล้วและไม่ถูกตัดสิทธิ์อย่างน้อยหนึ่งครั้ง จะมี **ความแข็งแกร่งของ edge**

```
s(e) = (best published corpus-level chrF++ on that pair) / 100   ∈ [0, 1]
```

chrF++ ระดับคอร์ปัสคือตัวเลขที่เผยแพร่เป็นมาตรฐาน (ดู
[ข้อกำหนดการให้คะแนน](/docs/network/specifications/scoring)) โดย *best* เพราะ
chain จะเลือกเส้นทางผ่านระบบที่ดีที่สุดที่พิสูจน์แล้วต่อ hop
คู่ที่ไม่มีการรันที่เผยแพร่จะมี s(e) = 0

**ความแข็งแกร่งของ chain ที่ประมาณการ** ของ path P ระหว่างสองภาษาคือ

```
strength(P) = λ^(|P|−1) · Π_{e ∈ P} s(e)
```

— คุณภาพของ edge ประกอบกันแบบคูณ และแต่ละ *junction* (pivot กลาง) มีต้นทุนเป็นปัจจัยความเที่ยงตรงเพิ่มเติม **λ < 1**
ทั้งสองตัวเลือกมีพื้นฐานจากวรรณกรรมการแปลผ่าน pivot:
การแปลผ่าน pivot สูญเสียคุณภาพอย่างสม่ำเสมอเมื่อเทียบกับการแปลตรง
เกินกว่าที่การประกอบแบบไร้เดียงสาจะแนะนำ (Utiyama & Isahara
2007; Wu & Wang 2007) ขนาดของการสูญเสียขึ้นอยู่กับ pivot ที่เลือก (Paul et al. 2009)
และการสร้างคู่ *ตรง* ที่ไม่ยึดภาษาอังกฤษเป็นศูนย์กลางให้ผลดีกว่าการใช้ภาษาอังกฤษเป็น pivot อย่างวัดได้ในระดับขนาดใหญ่ — ประมาณ ~10 BLEU ในการตั้งค่า many-to-many ของ M2M-100 (Fan et al. 2021) λ คือตัวเตือนถาวรในสูตรว่า chain ที่ประมาณการไม่ใช่การวัด: มีเพียงการรันตรงเท่านั้นที่ลบส่วนลดออกได้

**best-chain matrix** และ **mesh objective** คือ

```
Q(u,v) = max over paths P from u to v of strength(P)      (1 if u = v, 0 if disconnected)

Φ = mean over ordered language pairs (u ≠ v) of Q(u,v)    ∈ [0, 1]
```

Q คำนวณอย่างแม่นยำในฐานะปัญหา shortest-path ภายใต้การแปลง log มาตรฐาน (น้ำหนัก edge −ln(λ·s(e)) ≥ 0, Dijkstra, จากนั้น
Q = exp(−d)/λ) Φ คือการสร้าง *global efficiency* ของ [Latora & Marchiori
(2001)](https://arxiv.org/abs/cond-mat/0101396) โดยแทนที่ kernel 1/distance ด้วย chain fidelity แบบคูณ — kernel ที่เป็นธรรมชาติเมื่อ edge มีการรักษาคุณภาพต่อ hop แทนที่จะเป็นความยาวหน่วย (คิว v1 จัดอันดับโดย unweighted global efficiency gain — กรณีพิเศษของตระกูลนี้ที่คุณรู้เพียงว่า edge มีอยู่หรือไม่)

### 1.5 ความน่าเชื่อถือ: สะพานคือ (q, r)

คะแนนที่โดดเด่นบนคอร์ปัสขนาดเล็ก บาง และไม่เคยทำซ้ำไม่ใช่สะพาน
v3 จึงแบ่ง edge ที่วัดแล้วทุกอันออกเป็น:

```
quality      q(e)   = best published corpus-level chrF++ / 100
reliability  r(e)   = f_size · f_rich · f_conf · f_repl        ∈ [0, 1]
effective    s_eff(e) = q(e) · r(e)        ← what chains compose over
```

| ปัจจัย | นิยาม | เครดิตเต็มที่ | จุดยึด |
|---|---|---|---|
| `f_size` | min(1, n/100), n = จำนวน entry ที่ประเมินของการรันที่ดีที่สุด | 100 entries | ระดับนัยสำคัญของ [corpus-design](/docs/network/specifications/corpus-design); Koehn (2004) ตรวจสอบ bootstrap testing บนชุด ~300 ประโยค — แม้แต่ 300 ก็ถือว่า "เล็ก" ดังนั้นขนาดจึงลดความน่าเชื่อถือแทนที่จะเป็นเพียงเกณฑ์การแสดงผล |
| `f_rich` | min(1, L̄/5), L̄ = ความยาวต้นฉบับ *effective* เฉลี่ย | 5 effective words | AmericasNLP (Mager et al. 2021) นำ chrF มาใช้เพราะหน่วยระดับคำแตกสลายบนสัณฐานวิทยาที่ซับซ้อน; Mager et al. (2022) บันทึก whitespace token ว่าเป็นหน่วยที่ผิด |
| `f_conf` | min(1, 5/h), h = ครึ่งความกว้าง chrF 95% CI ของการรันที่ดีที่สุด (proxy `50/√n` เมื่อไม่ได้เผยแพร่) | CI ≤ ±5 chrF | ระดับ noise ที่ต่ำกว่านั้น delta ไม่สามารถแยกแยะได้บนคอร์ปัสขนาดเล็ก; Kocmi et al. (2021) แสดงให้เห็นว่า delta ภายใน CI มักขัดแย้งกับความชอบของมนุษย์ |
| `f_repl` | min(1, runs/2) | 2 การรันที่เผยแพร่ | Marie, Fujita & Rubino (2021) ประเมิน meta 769 บทความ: การเปรียบเทียบครั้งเดียวที่ไม่ได้ทำซ้ำคือความล้มเหลวด้านความน่าเชื่อถือที่บันทึกไว้ในสาขา |

**ความยาว effective** วัดในหน่วยเนื้อหา ไม่ใช่คำที่คั่นด้วยช่องว่าง: `L̄ = mean source chars / c(L)` โดยที่ *character economy*
`c(L)` คือค่ามัธยฐานของอักขระในฝั่งภาษา L ต่อคำภาษาอังกฤษในฝั่งที่จัดแนวแล้ว วัดจากคอร์ปัสคู่ขนานของโปรเจกต์นี้เอง
(มากกว่า 7,400 entries ที่จัดแนวแล้วเมื่อ v3 เปิดตัว: cmn 1.6, jpn 2.3, kor 2.6;
eng baseline 5.0; deu 6.0; crk 4.7 — คำ polysynthetic ตีราคาตามเนื้อหาที่บรรจุ) ไม่มีตารางค้นหา typology; การประมาณการจะแม่นยำขึ้นเมื่อคอร์ปัสเติบโต; ภาษาที่ไม่มีข้อมูลคู่กับ eng ใช้ economy เริ่มต้น บันทึกต่อคอร์ปัสในรีจิสทรี (บล็อก `richness`)

**ระดับสะพาน** (คำศัพท์การแสดงผล): **established** — n ≥ 100,
L̄ ≥ 5, h ≤ 5, runs ≥ 2; **provisional** — วัดแล้วแต่ไม่ผ่านเกณฑ์ใดเกณฑ์หนึ่ง;
**registered** — ไม่มีการรันที่เผยแพร่ การอ้างสิทธิ์ chain ("คุณสามารถไปจาก X
ถึง Y ได้") แข็งแกร่งเพียงเท่ากับระดับของ hop ที่อ่อนแอที่สุด และการแสดงผล mesh แสดงความน่าเชื่อถือเป็นความทึบแสงของ edge

**การตรวจสอบตัวอย่าง** (จาก verification script ที่ check-in ไว้ รันก่อน v3 เปิดตัว): *รายการคำศัพท์เดี่ยว 62 คำ, รันหนึ่งครั้ง* → r ≈ **0.04**
(ไม่ใช่ path); *200 ประโยค, ±3 CI, 3 การรัน* → r = **1.00**; คอร์ปัสภาษาญี่ปุ่น 101 entry ที่จำนวนคำแบบไร้เดียงสาเป็น 1.0 (artifact ของ script)
ฟื้นฟูเป็น 6.5 effective words และ `f_rich` เต็ม
Bounds และ per-factor monotonicity ผ่านการทดสอบ property

**มูลค่าของการรันหนึ่งครั้งภายใต้ v3.** การรันสามารถปรับปรุงสะพานได้สองวิธี และ
ΔΦ ใช้ค่าที่ดีกว่าระหว่าง: **(a)** กลายเป็นการรันที่ดีที่สุดของ edge —
`ŝ_eff = คุณภาพที่คาดการณ์ × r(n ของคอร์ปัส, richness, CI proxy,
runs+1)`; หรือ **(b)** เพียงแค่ทำซ้ำ — best ปัจจุบันยังคงอยู่,
`f_repl` เพิ่มขึ้น การทำซ้ำบน edge ที่รันครั้งเดียวจึงเป็นมูลค่าจริงที่ตีราคาได้ และคอร์ปัสที่ใหญ่กว่าหรือสมบูรณ์กว่าบนคู่ที่วัดแล้วมีอันดับสูงกว่าการรันซ้ำบนคอร์ปัสขนาดเล็ก รายการแสดง `edge_quality`,
`edge_reliability`, `edge_tier`, `effective_strength`,
`post_run_reliability` และ `predicted_effective` ควบคู่กับฟิลด์การคาดการณ์ v2

**สิ่งที่ Φ ไม่ใช่.** Φ คือสกุลเงินการจัดลำดับความสำคัญภายในของคิว
ไม่ใช่การอ้างสิทธิ์ความสามารถ input ของมันคือคะแนน development-set พร้อมข้อแม้ทั้งหมดของ [Corpus Design
Framework](/docs/network/specifications/corpus-design): การปนเปื้อนของข้อมูลฝึกที่เป็นไปได้ทำให้แต่ละคะแนนเป็นขอบบน ค่า chrF++ ไม่สามารถเปรียบเทียบได้อย่างเคร่งครัดข้ามภาษา และคอร์ปัสขนาดเล็กมีช่วงความเชื่อมั่นกว้าง สูตรต้องการเพียงให้ Φ *จัดลำดับการรันตามประโยชน์*; มันไม่เคยถูกเผยแพร่เป็นการรับประกันคุณภาพ

## 2. ปัญหาการตัดสินใจ

รายการที่เปิดอยู่ของคิวคือทุกๆ การรวมกันของ (corpus, model, condition) ที่มีสิทธิ์ (development split, สิทธิ์การใช้งานที่แจกจ่ายซ้ำได้, ไม่ถูกกักกัน, มีสิทธิ์ในการส่งผ่าน, และ **สามารถแก้ไขเบนช์มาร์กได้ (benchmark-resolvable)** — ดู language-identity gate ใน §2.2) และยังไม่อยู่บนลีดเดอร์บอร์ด การรันซ้ำที่เหมือนกันของการรวมกันที่ครอบคลุมแล้วจะถูกยกเว้น — ลายนิ้วมือของ run-card จะลบข้อมูลที่ซ้ำซ้อน (dedupe) เมื่อเผยแพร่ — แต่โมเดลหรือเงื่อนไขใหม่บนคู่ภาษาที่เคยวัดผลแล้วจะยังคงเป็นรายการที่เปิดอยู่

compute ที่มีส่วนร่วมคืองบประมาณ การเลือกว่าจะรันรายการเปิดใดต่อไปเพื่อให้ mesh ปรับปรุงเร็วที่สุดคือการ maximization แบบ budgeted coverage และแนวทางมาตรฐานคือการเลือกแบบ greedy โดย **มูลค่าส่วนเพิ่มต่อหน่วยต้นทุน**: สำหรับ objective แบบ monotone submodular กฎ greedy มีการรับประกัน (1 − 1/e) แบบคลาสสิก (Nemhauser,
Wolsey & Fisher 1978) และรูปแบบ benefit/cost-ratio คือ algorithm มาตรฐานภายใต้งบประมาณ (Khuller, Moss & Naor 1999) เราใช้กฎ ratio เป็นหลักการจัดอันดับ (หมายเหตุความซื่อสัตย์: objective ของเราให้ผลตอบแทนลดลงแบบ coverage-like ในแกนกลางที่กำหนดได้ แต่ชั้นการคาดการณ์แบบ stochastic หมายความว่าเราอ้างการรับประกัน greedy เป็น *แรงจูงใจ* ไม่ใช่ทฤษฎีบทเกี่ยวกับระบบนี้โดยเฉพาะ)

```
ECV(item) = ΔΦ(item) / max(est_cost_usd, COST_FLOOR)
```

รายการจัดอันดับโดย ECV จากมากไปน้อย การเสมอกันแบ่งโดย: naive ก่อน coached, ถูกกว่าก่อน, จากนั้น item id

### 2.1 การแก้ไขการจัดอันดับ — 2026-07-12

การปรับแต่งสี่รายการที่ซ้อนทับบนกฎ greedy ECV โดยแต่ละรายการจะสะท้อนอยู่ใน
metadata ของ queue (`priority_parameters.contamination_ecv_factors`,
`priority_parameters.frontier_interleave`, `metadata.preview_policy`):

1. **ตัวคูณการปนเปื้อน** ECV ของแต่ละรายการจะถูกคูณด้วย
   ค่าตัวประกอบจากระดับการปนเปื้อนของ corpus นั้น: **LOW 1.0 / MEDIUM
   0.4 / HIGH 0.1** โดยระดับที่ไม่ทราบหรือขาดหายไปจะถูกถือว่าเป็น
   MEDIUM (ห้ามสันนิษฐานว่าสะอาด) เหตุผล: กราฟ clean chain อนุญาตเฉพาะ edge ที่มีการปนเปื้อนระดับ LOW เท่านั้น ดังนั้น run ที่ไม่ใช่ LOW จึงไม่สามารถเข้าสู่กราฟนั้นได้ และต้องไม่มีอันดับสูงกว่างาน clean-mesh ที่มีต้นทุนเท่ากัน รายการที่ไม่ใช่ LOW ยังคงอยู่ใน queue — การเปรียบเทียบภายใน relative-lane มีคุณค่าจริง — เพียงแต่จัดอันดับไว้หลังงานที่สะอาด
2. **การสลับ Frontier** หลังจากการเรียงลำดับแบบ greedy ทุกๆ ช่องลำดับความสำคัญที่ 5
   จะบรรจุรายการที่มีอันดับสูงสุดที่ยังไม่ได้จัดวางจากชุด frontier-model (ซึ่งดูแลเป็นข้อมูลใน generator และสะท้อนอยู่ใน metadata) เพื่อให้หลักฐานจาก frontier เข้าถึง prediction priors ได้เร็ว แทนที่จะรอจนกว่า tier ราคาถูกจะอิ่มตัว เป็นการจัดเรียงใหม่ล้วนๆ: ไม่มีรายการใดถูกตัดออกหรือซ้ำกัน รายการ frontier ที่ได้รับช่องตามธรรมชาติจะคงช่องนั้นไว้ และลำดับความสำคัญจะนับจากลำดับที่ถักทอแล้ว — การจัดอันดับที่เผยแพร่คือความจริง
3. **ขีดจำกัด source-hub ใน Preview** การแสดงตัวอย่างสาธารณะ top-25 จะแสดง
   รายการที่ใช้ภาษาต้นทางเดียวกันได้สูงสุด **6** รายการ เพื่อป้องกันไม่ให้ hub ที่มีทรัพยากรมากผูกขาดหน้าต่างแสดงผล รายการที่เกินขีดจำกัดยังคงลำดับความสำคัญจริงใน queue เต็ม โดย preview จะดึงรายการถัดไปที่มีสิทธิ์ตามลำดับการจัดอันดับ
4. **การยกเว้นภาษาประดิษฐ์ใน Preview** รายการที่มีภาษาต้นทางหรือภาษาปลายทางเป็นภาษาประดิษฐ์จะถูกข้ามโดย preview การพิจารณาขึ้นอยู่กับ card-family (กลุ่ม Artificial Language ของ Glottolog อ่านจาก language cards — ไม่ใช่ชุดภาษาที่กำหนดตายตัว) และรายการโค้ดที่ได้มาจะเผยแพร่ใน
   `metadata.preview_policy` เพื่อให้การรีเฟรชฝั่ง server ใช้การคัดเลือกเดียวกัน

(3) และ (4) เป็น **นโยบายการนำเสนอเท่านั้น**: `queue.json` ฉบับเต็ม
การจัดอันดับ และลำดับความสำคัญของมันไม่ได้รับผลกระทบใดๆ

### 2.1.1 ระดับงบประมาณ (Budget tiers) — "เงิน $X ซื้ออะไรได้บ้าง?" (2026-08-24)

`queue-preview.json` จะมีอาร์เรย์ `budget_tiers` ที่สรุปข้อมูลสำหรับงบประมาณ **$1 / $10 / $100 / $1000** ซึ่งเป็น greedy affordable prefix ของการจัดอันดับที่เผยแพร่: ไล่ดูรายการตามลำดับความสำคัญ, เลือกแต่ละรายการที่ต้นทุนประเมินยังคงอยู่ในงบประมาณ, ข้ามรายการที่เกินงบ, และเติมเต็มต่อไปด้วยรายการที่ถูกกว่าในลำดับถัดไป แต่ละระดับจะรายงานว่าสามารถซื้อได้กี่รายการ, ต้นทุนประเมินรวมเป็นเท่าใด, ครอบคลุมคู่ภาษาและโมเดลที่แตกต่างกันกี่รายการ, และงบประมาณนั้นเข้าถึงการจัดอันดับได้ลึกเพียงใด (`max_priority`)

เนื่องจากผลการจัดอันดับเป็นแบบมูลค่าส่วนเพิ่มต่อต้นทุน (marginal-value-per-cost) อยู่แล้ว (§2) greedy affordable prefix **จึงเป็น** การจัดสรรที่โมเดลนี้แนะนำสำหรับยอดใช้จ่ายนั้น — ผู้ร่วมสมทบทุนรายเล็กและรายใหญ่ต่างก็ได้รับคำตอบที่เป็นรูปธรรมและเหมาะสมที่สุดจากการจัดอันดับที่เผยแพร่ชุดเดียวกัน แทนที่จะเป็นรายการเดียวที่ไม่ได้กำหนดขนาดให้เหมาะกับใครเลย ระดับต่างๆ เป็นเพียงบทสรุปเท่านั้น: การจัดสรรที่แท้จริงก็คือการจัดอันดับ ซึ่งไล่เรียงตามลำดับเทียบกับงบประมาณของคุณเอง การรีเฟรชฝั่งเซิร์ฟเวอร์จะคำนวณระดับต่างๆ ใหม่จากรายการที่เหลืออยู่ด้วยการไล่เรียงแบบเดียวกัน (ตัวสร้างและฟังก์ชันรีเฟรชถูกนำมาใช้งานแบบคู่ขนานกัน และผ่านการทดสอบทั้งสองฝั่ง)

### 2.2 เลนและโหมดการจัดอันดับ (Lanes and ranking modes) — 2026-07-19

คิวที่ให้บริการจะประกาศในเมทาดาตาของตัวเองว่าคิวนั้นอยู่ใน **เลน (lane)** ใด และใช้ **โหมดการจัดอันดับ (ranking mode)** ใดในการเรียงลำดับ เมทาดาตาคือแหล่งข้อมูลอ้างอิงหลัก ส่วนนี้จะเป็นการกำหนดคำศัพท์ที่ใช้

**เลน (Lanes)** (`metadata.lane`, `metadata.lane_policy`) ตั้งแต่วันที่ 2026-08-27 คิวสาธารณะจะใช้เลนแบบ **both** (ทั้งคู่): รายการ LLM (โมเดล × เงื่อนไขการพรอมต์) **และ** รายการ MT-service (เงื่อนไข `engine` — DeepL, Google Translate, Microsoft Translator, LibreTranslate, Tilde; แต่ละรายการจะเข้าคิวเฉพาะคู่ภาษาที่อยู่ในรายการความครอบคลุมที่เผยแพร่ของตนเองเท่านั้น) เลน **llm** ของวันที่ 2026-07-19 — เฉพาะรายการ LLM เท่านั้น โดยจำกัดเฉพาะคู่ภาษาที่อย่างน้อยหนึ่งฝั่งอยู่นอกเหนือความครอบคลุมที่เผยแพร่ของบริการ MT ทุกแห่ง — ได้สงวนการทำเบนช์มาร์กบริการไว้สำหรับแคมเปญที่ดำเนินการโดยผู้จัดซึ่งไม่เคยเกิดขึ้นจริง ทำให้แคตตาล็อกส่วนใหญ่ถูกพักไว้; การวัดผลบริการต่างๆ *คือ* แกนหลักของแผนที่ความครอบคลุม ดังนั้นงานทั้งสองประเภทจึงมาอยู่บนบอร์ดเดียวกันแล้วในตอนนี้ ยูเนียนของความครอบคลุม (ใช้นามแฝงเป็นภาษามหาภาค (macrolanguage) ผ่านการ์ดภาษา) ยังคงถูกสะท้อนออกมาเป็น `service_coverage_methods` และ `service_covered_languages` และคิวในเลน llm ยังคงรายงานคู่ภาษาที่ถูกยกเว้นเป็น `pairs_dropped_fully_covered`

**ขีดจำกัดขนาด Blob (Blob size cap)** (2026-08-27) `queue.json` ที่ให้บริการคือไฟล์สแตติกที่มีเพดานการโฮสต์แบบตายตัว ดังนั้นเมื่อการจัดอันดับทั้งหมดมีขนาดใหญ่เกินไป ไฟล์จะเก็บเฉพาะ **ส่วนบนสุด (top slice)** ของการจัดอันดับและระบุไว้ใน `metadata.blob_truncated {kept, total}` — จะไม่มีการจำกัดแบบเงียบๆ เด็ดขาด คิวฐานข้อมูล (`queue_top()` / `queue_pairs()`) จะให้บริการการจัดอันดับที่ **สมบูรณ์** เสมอและเป็นรายการงานที่เชื่อถือได้; การรวมคู่ภาษาและระดับงบประมาณของพรีวิวจะอธิบายถึงอาร์ติแฟกต์ที่จัดส่งมาพร้อมกัน

**เกตระบุตัวตนภาษา (Language-identity gate)** (2026-07-19) รายการในคิวจะกำหนดเป้าหมายเฉพาะ **รหัส ISO 639-3 เดี่ยวที่ใช้งานอยู่ (active individual ISO 639-3 codes)** เท่านั้น — คะแนนที่เทียบกับภาษามหาภาค ("Arabic") หรือรหัสกลุ่มตระกูลภาษา ("Berber languages") จะเป็นการกล่าวอ้างที่ไม่สามารถพิสูจน์ได้เกี่ยวกับความหลากหลายของภาษาที่ไม่เคยถูกประเมิน (เหตุผลเดียวกับที่ FLORES-200/NLLB ใช้โดยการเข้ารหัสข้อมูลเป็น `arb`/`quy`/`zsm`) ป้ายกำกับคลังข้อมูลต้นน้ำจะถูก *แก้ไข (resolved)* โดยจะไม่ทำตามหรือละทิ้งโดยเด็ดขาด: แท็กสคริปต์จะถูกตัดออกโดยอัตโนมัติ (คลังข้อมูล `eng→cmn-Hans` จะเข้าคิวสำหรับ `eng→cmn` โดยสคริปต์จะถูกเก็บไว้เป็นเมทาดาตาสำหรับแสดงผลของรายการ `source_script`/ `target_script`); รหัสที่ถูกยกเลิกอย่างสมบูรณ์จะตามรหัสสืบทอด ISO อย่างเป็นทางการ; และคลังข้อมูลที่มีป้ายกำกับแบบมหาภาคจะเข้าคิวภายใต้ **การแก้ไขความหลากหลาย (variety resolution)** ที่มีการบันทึกและอ้างอิงในรายการรีจิสทรีเท่านั้น (เช่น FLORES+ บันทึกภาษา Quechua เป็น `quy`) คลังข้อมูลที่ไม่สามารถแก้ไขได้ในทั้งสองเส้นทางจะถูกยกเว้นพร้อมเหตุผลที่เครื่องอ่านได้ซึ่งเผยแพร่ใน `metadata.doctrine_exclusions` (ยอดรวม, จำนวนตามเหตุผล, เหตุผลต่อคลังข้อมูล) และนับรวมในบัญชีแยกประเภท desert (`service_landscape.invisible_reasons.corpus_excluded_by_doctrine`) — เป็นการยกเว้นที่มองเห็นได้ ไม่มีการตัดทิ้งแบบเงียบๆ ผลลัพธ์ในอดีตบนคลังข้อมูลที่มีป้ายกำกับแบบครอบคลุม (umbrella-labeled) จะเก็บโหนด mesh ที่ตั้งชื่อตามจริงของตนเองไว้ (โหนด `scope`: `macrolanguage` / `collective` / `retired`) โดยจะไม่ถูกรวมเข้ากับความหลากหลายของสมาชิก อินพุตการแก้ไขทั้งหมดจะถูกเผยแพร่: แสตมป์ `language_resolution` ต่อรายการของรีจิสทรีจะเก็บรหัสที่แก้ไขแล้ว, ขอบเขต, และการอ้างอิงที่ปักหมุดไว้

**โหมดการจัดอันดับ (Ranking modes)** (`metadata.rank_mode`, อธิบายไว้ใน `metadata.priority_model`) การเรียงลำดับสองแบบสำหรับรายการเดียวกัน:

- **ecv** — กฎ greedy expected-chain-value ของ §2–§3: การปรับปรุง mesh ต่อดอลลาร์ที่ประเมินไว้ เป็นการเรียงลำดับแบบ exploitation; เหมาะสมเมื่อบอร์ดมีความหนาแน่นพอสำหรับการทำนายและ ΔΦ สามารถส่งสัญญาณได้
- **map** (map-value v2) — การเรียงลำดับแบบ survey: `MapValue = novelty × uncertainty × promise × connectivity × corpus-quality × contamination ÷ cost` ซึ่งประกอบขึ้นด้วย exact greedy trace *Novelty* คือเครดิต first-light ตามตำแหน่งที่จะลดลงเมื่อรายการที่จัดวางแล้วครอบครองคู่ภาษาที่มีทิศทางเดียวกัน (1/(1+n)), ภาษาเป้าหมาย, ตระกูลภาษาเป้าหมาย, เซลล์ method × target-family, และเซลล์ target × domain (แต่ละอัน 1/√(1+n); ตระกูลภาษาจากการ์ดภาษา, โดเมนจากอนุกรมวิธานของรีจิสทรีคลังข้อมูล — ความครอบคลุมในช่วงแรกของเป้าหมายควรกระจายไปตามรีจิสเตอร์ ไม่ใช่ทำซ้ำโดเมนแรกที่วัดผล) *Uncertainty* คือความลึกของการถอยกลับ (back-off depth) ของการทำนายใน §3.1 (คู่ภาษา 0.25 · ภาษาเป้าหมาย 0.55 · ภาษาต้นทาง 0.75 · โกลบอล 1.0) × 1/(1+การรันที่เผยแพร่บนเอดจ์) *Promise* คือความแข็งแกร่งที่ทำนายไว้ใน §3.1 โดยมีค่าต่ำสุดที่ 0.25 — สิ่งที่ไม่รู้จักแต่มีแนวโน้มว่าจะใช้งานได้จะนำหน้า และการทำแผนที่ในพื้นที่ที่อาจเป็น desert ก็ยังมีมูลค่า *Connectivity* จะจัดอันดับคู่ภาษาที่ **เชื่อมโยงเครือข่ายที่วัดผลแล้วไปยังภาษาที่ยังเข้าไม่ถึง**: จุดสิ้นสุดจะถือว่า *established* เมื่ออยู่บนเอดจ์ของ mesh ที่วัดผลแล้ว (`mesh.json`, สถานะ `measured`) หรืออยู่ภายในรายการความครอบคลุมที่เผยแพร่ของบริการ MT ใดๆ (ใช้นามแฝงเป็นภาษามหาภาค ซึ่งเป็นการใช้นามแฝงเดียวกับ lane gate ด้านบน); **bridges** (มีจุดสิ้นสุดที่ established เพียงจุดเดียว) และ **islands** (ไม่มีเลย) จะได้คะแนน 1.0 ทั้งคู่ — ตั้งแต่วันที่ 2026-08-27 first light ของ desert ที่ถูกตัดขาดจะถูกนับเต็มจำนวน (islands ได้คะแนน 0.5 ภายใต้การกำหนดขนาดแบบ grow-out-of-the-network ของวันที่ 2026-07-19 ซึ่งลดระดับส่วนหางที่ลึกที่สุดในเชิงโครงสร้าง) — ในขณะที่การเพิ่มความหนาแน่น **interior** (established ทั้งคู่) จะได้คะแนน 0.5: การเสริมความแข็งแกร่งระหว่างจุดที่รู้จักเป็นหน้าที่ของโหมด ecv **first-reading boost** (×2.0) จะคูณเพิ่มมูลค่า survey ของรายการใดๆ ที่ภาษาต้นทางหรือเป้าหมายมีจำนวนการวัดผลที่เผยแพร่เป็นศูนย์ในทุกที่ — หลักการที่เก้า ระบุไว้อย่างชัดเจนว่า: **การอ่านครั้งแรกของภาษามีความสำคัญเหนือกว่าการปรับแต่ง (refinement)** ปัจจัยด้านความไม่แน่นอนเพียงอย่างเดียวไม่สามารถแสดงสิ่งนี้ได้ (มันให้คะแนนคู่ภาษาที่ไม่เคยวัดผลระหว่างสองภาษาที่วัดผลมาอย่างดีเท่ากับภาษาที่ไม่เคยถูกวัดผลเลย); การบูสต์ทำให้ first light ของ long tail เป็นวัตถุประสงค์ที่ระบุไว้ชัดเจน แทนที่จะเป็นเหตุบังเอิญที่เกิดขึ้น ปัจจัยทั้งสองนี้ทำงานบน `metadata.map_value_parameters` และนำไปใช้ในลักษณะเดียวกันภายในคอมโพเนนต์ survey ของ edv (§2.3)

  อีกครึ่งหนึ่งของหลักการที่เก้าอยู่ นอกเหนือ การจัดอันดับ: ไม่มีการเรียงลำดับรายการที่มีอยู่ใดๆ ที่สามารถเข้าถึงภาษาที่ไม่มีคลังข้อมูลเลยได้ (ปัจจุบันมีภาษาที่มีรหัสเดี่ยวและยังมีผู้ใช้งานอยู่ประมาณ 7,500 ภาษา) **รายการคลังข้อมูลที่ต้องการ (corpus wish-list)** (`/corpus-wishlist.json`, สร้างขึ้นใหม่ควบคู่กับคิว) จะเผยแพร่พรมแดนการได้มาซึ่งข้อมูลนั้น: ทุกภาษาที่มีรหัสเดี่ยว, ยังมีผู้ใช้งาน, และไม่มีคลังข้อมูล จะถูกจัดอันดับตามจำนวนผู้พูดที่มีการอ้างอิงดีที่สุด — จำนวนผู้พูดเป็นตัวแทนความเป็นไปได้สำหรับชุมชนที่สามารถสร้างคลังข้อมูลได้จริง — ทุกจำนวนจะถูกระบุแหล่งที่มาและไม่มีการตัดสินชี้ขาด
  *Corpus-quality* คือศักยภาพความน่าเชื่อถือที่แท้จริงของคลังข้อมูล `f_size × f_rich` จาก §1.5 — การสำรวจควรลงเอยที่คลังข้อมูลที่สามารถรับน้ำหนักได้ ดังนั้นรายการคำศัพท์คำเดียว 62 รายการจะไม่เป็นหัวข้อหลักอีกต่อไปเพียงเพราะมันมีราคาถูก; การวัดความสมบูรณ์ (richness) ที่หายไปจะยังคงเป็นกลาง (การไม่มีการวัดผลไม่ใช่หลักฐานของความขาดแคลน) วินัยด้านต้นทุนและการปนเปื้อนจะเหมือนกับ ecv การแทรกสลับพรมแดน (frontier interleave) และการตัดสินชี้ขาด (tie-breaks) (§2.1) จะนำมาใช้โดยไม่มีการเปลี่ยนแปลง เหมาะสมสำหรับเฟสการสำรวจ: มันช่วยเพิ่มสิ่งที่ *แผนที่เรียนรู้* ต่อดอลลาร์ให้ได้สูงสุด — การวัดผลครั้งแรกข้ามคู่ภาษา, ภาษา, ตระกูลภาษา, เซลล์วิธีการ, และโดเมน โดยเติบโตออกจากเครือข่ายที่วัดผลแล้วแทนที่จะกระจัดกระจาย — โดยแลกมาด้วยการเติบโตของความแข็งแกร่งของ mesh ที่ช้าลงอย่างจงใจ

> **map-value v2 (2026-07-19).** ส่วนเพิ่มเติมที่กำกับโดยผู้ก่อตั้งสองรายการสำหรับการเรียงลำดับแบบ survey: คู่ภาษาที่ *เชื่อมโยงเข้าสู่เครือข่ายที่วัดผลแล้ว* ตอนนี้จะอยู่ในอันดับที่สูงกว่าโพรบที่ถูกตัดขาดและการเพิ่มความหนาแน่นภายใน, และคุณภาพของคลังข้อมูล (ขนาดขั้นต่ำ × ความสมบูรณ์ที่มีประสิทธิภาพ, §1.5) บวกกับการกระจายโดเมนต่อเป้าหมายจะถ่วงน้ำหนักการจัดอันดับ — การประมวลผลของผู้ร่วมสมทบทุนควรเชื่อมโยงเส้นทางที่ established แล้วเข้ากับเส้นทางใหม่ บนคลังข้อมูลที่ดีพอที่จะรับน้ำหนักได้ สิทธิ์การใช้งานยังคงเป็น **เกต ไม่ใช่น้ำหนัก (gate, not a weight)**: กฎของสิทธิ์การใช้งานและช่องทางการส่งผ่านจะเป็นตัวตัดสินว่าสิ่งใดสามารถเข้าคิวได้บ้าง (§2, และ `transmission_note` ของคิว); ในบรรดาคลังข้อมูลที่มีสิทธิ์ การจัดอันดับจะไม่สนใจสิทธิ์การใช้งาน (license-blind) ดังนั้นชุดการวิจัยที่ถูกจำกัดแต่ถูกปักหมุดไว้ — ซึ่งมักจะเป็นคลังข้อมูลเดียวของคู่ภาษา — จะไม่ถูกปล่อยให้อดอยากอย่างเป็นระบบ คิว v1 (novelty × uncertainty × promise เท่านั้น) ยังคงสามารถตีความได้ผ่านเมทาดาตาของตัวเอง

ค่าปัจจัยที่แน่นอนที่ใช้ตอนสร้างจะจัดส่งมาใน `metadata.map_value_parameters`; อินพุตด้านการเชื่อมต่อและคุณภาพสามารถหามาใหม่ได้จาก `mesh.json` ที่เผยแพร่ (เอดจ์ที่วัดผลแล้ว), ยูเนียนความครอบคลุมของบริการที่สะท้อนในเมทาดาตา, และ `registry.json` (จำนวนรายการ + ความสมบูรณ์) นอกจากนี้ ทุกรายการยังคงรักษาฟิลด์การวินิจฉัย ecv-v3 แบบเต็มไว้โดยไม่คำนึงถึงโหมด ดังนั้นการเรียงลำดับแบบใดแบบหนึ่งก็สามารถหามาใหม่ได้จากอาร์ติแฟกต์เดียวกัน

### 2.3 โหมดการจัดอันดับ `edv` — expected decision value (2026-08-27)

*สถานะ: นำไปใช้งานแล้ว, ค่าเริ่มต้นถูกปิดไว้เพื่อรอการเปรียบเทียบที่วัดผลใน §2.3.6 ค่าเริ่มต้นที่เผยแพร่ยังคงเป็น `map` จนกว่าจะถึงตอนนั้น*

คิวจะซื้อผลิตภัณฑ์สองอย่างเท่านั้น: **แผนที่ความสามารถ (capability map)** (วิธีการใดเก่งเรื่องอะไร พร้อมความไม่แน่นอนตามจริง) และ **routing mesh** (คู่ภาษาที่วัดผลแล้วซึ่งเชื่อมโยงเป็นเส้นทาง) `edv` จะกำหนดราคาแต่ละรายการที่เป็นตัวเลือกตามความสามารถในการพัฒนาทั้งสองอย่าง ในฐานะพอร์ตโฟลิโอแบบถ่วงน้ำหนัก:

```
EDV(item) = [ w_judge·Ĵ + w_mesh·M̂ + w_survey·Ŝ ] × contamination ÷ max(cost, COST_FLOOR)
```

โดยมีค่าเริ่มต้น `w_judge = 0.35, w_mesh = 0.25, w_survey = 0.40` (ผู้ก่อตั้งสามารถปรับเปลี่ยนได้; ทุกการสร้างจะสะท้อนน้ำหนักที่ใช้จริงใน `metadata.edv_parameters`) ปัจจัยการปนเปื้อน (การแก้ไข §2.1 ข้อ 1) จะถูกนำมาใช้เพียงครั้งเดียว ในฐานะตัวคูณภายนอก สิทธิ์การใช้งานและการส่งผ่านยังคงเป็น **เกต ไม่ใช่น้ำหนัก** — สิทธิ์จะถูกตัดสินก่อนที่จะมีการคำนวณมูลค่าใดๆ และการจัดอันดับจะไม่สนใจสิทธิ์การใช้งานในบรรดาคลังข้อมูลที่มีสิทธิ์

#### 2.3.1 Ĵ — method-judgment value

กำหนดราคาว่าการรันนั้นช่วยพัฒนา **การยุติการเปรียบเทียบวิธีการบนคลังข้อมูลเดียวกัน** ได้มากเพียงใด — ซึ่งเป็นการกล่าวอ้างข้ามวิธีการเพียงอย่างเดียวที่งานวิจัยการวัดผลของโปรเจกต์นี้อนุญาต (การศึกษา difficulty-transfer ของ W2 ปฏิเสธการเชื่อมโยงความสามารถข้ามภาษา; ผลลัพธ์เชิงบวกที่ได้รับอนุญาต — การปรับ method × corpus แบบบวกภายในภาษา — คือสิ่งที่คอมโพเนนต์นี้ใช้พอดี คะแนนจะถูกใช้สำหรับการเรียงลำดับและการแยกเท่านั้น จะไม่ถูกแปลงเป็นความน่าจะเป็นของการยอมรับ ตามโครงการนำร่องการสอบเทียบ)

สำหรับตัวเลือก (คลังข้อมูล C, วิธีการ M, เงื่อนไข): **พาร์ทเนอร์เปรียบเทียบ (contrast partners)** คือวิธีการ M′ ที่มีการรันที่เผยแพร่แล้วบน (C, เงื่อนไขเดียวกัน) สำหรับแต่ละพาร์ทเนอร์ โดยที่ `sep` คือการแยกคะแนนในหน่วย chrF เหนือ pooled CI half-widths (CI ที่บันทึกไว้; พร็อกซี `50/√n` เมื่อไม่ได้เผยแพร่), และ `sep_pred` คือการคำนวณแบบเดียวกันเทียบกับคะแนนที่ทำนายไว้ใน §3.1:

| สถานะการเปรียบเทียบของ {M, M′} บนคู่ภาษา | เครดิต |
|---|---|
| **unmet** — ยังไม่มีคลังข้อมูลร่วมกัน | `JUDGE_FIRST = 1.0` |
| **contested** — มีคลังข้อมูลร่วมกัน, ทั้งหมด `sep < Z_DEC` | `JUDGE_CONTESTED = 0.8 × clip(sep_pred / Z_DEC, 0, 1)` |
| **decided** — บางส่วน `sep ≥ Z_DEC`, คลังข้อมูล n_dec ตัดสินมัน | `JUDGE_DECIDED = 0.25 / (1 + n_dec)` |

แต่ละรายการคูณด้วย `w_top = 1/√(rank(M)·rank(M′))` — การตัดสินอันดับหนึ่งเทียบกับอันดับสองมีค่ามากกว่าอันดับเจ็ดเทียบกับอันดับแปด การจัดอันดับวิธีการต่อคู่ภาษาจะใช้ additive method × corpus fit ที่ได้รับอนุญาต (alternating least squares เหนือเซลล์ที่สังเกตได้) เมื่อคู่ภาษามีการวัดผล ≥2 วิธีการ × ≥2 คลังข้อมูล มิฉะนั้นจะใช้คะแนนที่ดีที่สุดต่อวิธีการ; การฟิตติ้งนี้ **เป็นแบบต่อคู่ภาษาอย่างเคร่งครัด ไม่มีการรวมข้ามภาษาเด็ดขาด** `Z_DEC = 1.96`

การเปรียบเทียบ coached-vs-naive บน (C, M) เดียวกันจะเพิ่ม `JUDGE_COND = 0.5 / (1 + n_cond)` การเปรียบเทียบของรายการจะถูกรวมเข้าด้วยกันโดยมีผลตอบแทนที่ลดลง (diminishing returns) (`JUDGE_GAMMA = 0.7` ต่อการเปรียบเทียบเพิ่มเติม, เรียงลำดับจากมากไปน้อย), บวกกับ **seed term** `JUDGE_SEED = 0.25 × min(1, m_C/3) × corpus-quality` (m_C = วิธีการอื่นๆ ในรายการที่มีรายการคิวบน C) ดังนั้นบอร์ดที่ว่างเปล่าจึงยังคงต้องการคลังข้อมูลที่สามารถตัดสินการเปรียบเทียบในอนาคตได้ — เป็นมูลค่าของสถานที่ (venue value) ไม่ใช่คะแนนที่ยืมมา ในระหว่างการประกอบ คอมโพเนนต์ judge จะลดลง `1/(1 + items already placed on the same pair and condition lane)`

#### 2.3.2 M̂ และ Ŝ

`M̂` คือ expected mesh gain (ΔΦ) ของ §3 ซึ่งไม่มีการเปลี่ยนแปลง โดยเมทริกซ์เชนจะถูกแช่แข็งไว้ ณ เวลาที่สร้าง `Ŝ` คือแกนหลักของ map-value v2 ของ §2.2 — `uncertainty × promise × connectivity × corpus-quality` พร้อมกับการลดลงของ novelty ตามตำแหน่ง — ไม่มีการเปลี่ยนแปลง *ระดับ* คะแนนที่ทำนายไว้ (promise) จะอยู่ใน Ŝ เท่านั้น; Ĵ จะใช้เฉพาะ *การแยก* คะแนนเท่านั้น — คอมโพเนนต์ทั้งสองไม่สามารถนับความคาดหวังเดียวกันซ้ำซ้อนได้

#### 2.3.3 การทำให้เป็นบรรทัดฐาน (Normalization)

คอมโพเนนต์ทั้งสามอยู่ในสเกลที่ไม่สามารถเปรียบเทียบกันได้ ดังนั้นแต่ละคอมโพเนนต์แบบสแตติกจะถูกหารด้วยเปอร์เซ็นไทล์ที่ 95 เหนือชุดตัวเลือก (จำกัดที่ `EDV_NORM_CAP = 4.0`); ตัวทำให้เป็นบรรทัดฐาน (normalizers) ทั้งสามจะจัดส่งมาใน `metadata.edv_parameters.normalizers` ทำให้ทุกค่า EDV ที่เผยแพร่สามารถหามาใหม่ได้จากอาร์ติแฟกต์ของมันเอง

#### 2.3.4 การประกอบ (Assembly)

การเรียงลำดับเป็น lazy-greedy trace แบบเดียวกับโหมด map ทุกประการ: ตัวคูณที่ขึ้นอยู่กับลำดับทุกตัว (survey novelty, judge placement decay) จะเป็นแบบ monotone non-increasing เมื่อมีการจัดวางรายการ ดังนั้นรายการฮีปที่เก่า (stale heap entry) จะทำได้เพียงประเมินสูงเกินไปเท่านั้น — lazy-greedy invariant ยังคงอยู่ และ trace จะเท่ากับ brute-force greedy การแทรกสลับพรมแดน, นโยบายพรีวิว, และระดับงบประมาณจะนำมาใช้โดยไม่มีการเปลี่ยนแปลง

#### 2.3.5 ความสามารถในการอธิบาย (Explainability)

ทุกรายการจะเก็บรักษาข้อมูลไว้ในการวินิจฉัย: รายการเปรียบเทียบที่ได้รับเครดิต (พาร์ทเนอร์, สถานะ, การแยกที่ทำนายไว้, น้ำหนักอันดับ), seed และ decay terms, ฟิลด์ §2.2 และ §3 ทั้งหมด, น้ำหนักและตัวทำให้เป็นบรรทัดฐาน — ค่า EDV ที่เผยแพร่สามารถคำนวณใหม่ได้อย่างแม่นยำจากแถวข้อมูล คำถามที่ว่า "รายการนี้ได้อันดับนี้มาได้อย่างไร?" สามารถตอบได้โดยไม่ต้องใช้สถานะภายนอกใดๆ

#### 2.3.6 เกณฑ์การนำไปใช้ (Adoption criterion)

`edv` จะกลายเป็นค่าเริ่มต้นที่เผยแพร่ก็ต่อเมื่อผ่านการเปรียบเทียบที่วัดผลกับ `map` และ `ecv` บนบอร์ดเดียวกัน: อยู่ภายใน 10% ของ map ในทุกเมตริกการสำรวจ (เปอร์เซ็นไทล์ความลึกของ first-light, คู่ภาษา/ภาษา/ตระกูลภาษาที่แตกต่างกันที่ความลึก, อัตราคู่ภาษาใหม่ส่วนเพิ่ม), ดีกว่าอย่างเคร่งครัดในทั้งสองเมตริกการตัดสิน (การเปรียบเทียบที่มีการแข่งขันถูกแก้ไขต่อการจำลอง $1k; การกู้คืนการจัดอันดับวิธีการที่ยอดใช้จ่ายคงที่), และการเติบโตของ mesh ต่อดอลลาร์ต้องไม่แย่กว่า map รายงานการเปรียบเทียบจะถูกเผยแพร่ควบคู่ไปกับการสลับค่า

## 3. มูลค่าของการรันหนึ่งครั้ง

### 3.1 การคาดการณ์คะแนนก่อนรัน

คะแนนที่คาดหวังของ (pair, model, condition) ที่ยังไม่ได้รันคือผลรวมที่เรียบง่ายและตรวจสอบได้อย่างสมบูรณ์โดยเจตนา — การคาดการณ์ main-effects สองทางบวก optimism แบบมีโครงสร้าง โดยทุก term เผยแพร่บนรายการ:

```
ŝ = clip( pair_prior + model_offset + condition_offset + exploration_bonus,  0, S_CAP )
```

- **`pair_prior`** — hierarchical back-off เหนือความแข็งแกร่งที่เผยแพร่:
  ค่าเฉลี่ยบนคู่นี้ → ค่าเฉลี่ยบนภาษาเป้าหมายนี้ → ค่าเฉลี่ยบนภาษาต้นฉบับนี้ → ค่าเฉลี่ยทั่วโลก → `S0_FALLBACK` ระดับที่ใช้เผยแพร่เป็น `prior_basis`
- **`model_offset`** — model นี้ทำได้ดีแค่ไหนเมื่อเทียบกับ model *อื่น* บนคู่เดียวกัน เฉลี่ยบนทุกคู่ที่มีการเปรียบเทียบ ศูนย์สำหรับ model ที่ไม่เคยเห็น
- **`condition_offset`** — delta coached-minus-naive ที่สังเกตได้บนคู่เดียวกัน (ถอยกลับไปที่ภาษาเป้าหมายเดียวกัน) และ **ศูนย์ในกรณีอื่น**: ผลกำไรจากการ coaching เป็นจริงเมื่อวัดแล้วแต่ไม่ถือว่าถ่ายโอนข้ามภาษา ดังนั้นบนคู่ที่ไม่มีหลักฐาน แบบแผน baseline-first จะใช้
- **`exploration_bonus`** — optimism ในสภาวะที่ไม่แน่นอน พร้อม UCB1 schedule (Auer, Cesa-Bianchi & Fischer 2002):
  `κ·sqrt(2·ln(1+N)/(1+n))` โดยที่ N คือจำนวนรวมของการรันที่ให้คะแนนที่เผยแพร่ และ n คือจำนวนบน (pair, model) นี้ เซลล์ที่ไม่เคยลองจะได้รับ bonus ที่ใหญ่ที่สุด; เซลล์ที่วัดดีแล้วจะลดลงสู่ศูนย์
  เราใช้ schedule — รูปร่างที่ทำให้ arm ที่สำรวจน้อยกลับมาในอัตราที่เหมาะสม — ไม่ใช่ทฤษฎีบท regret ซึ่งสมมติ bandit แบบ stationary ที่ระบบนี้ไม่ใช่

### 3.2 mesh gain ในรูปแบบปิด

การรันสามารถปรับปรุง mesh ได้โดยการยก edge ของคู่ขึ้นสู่
`s' = max(s(e), ŝ)` เท่านั้น สำหรับการเปลี่ยนแปลง edge เดียว best chain ใหม่ระหว่างสองภาษาใดก็ตามจะเพิกเฉยต่อ edge ใหม่หรือใช้มันครั้งเดียวพอดี ดังนั้น matrix ที่อัปเกรดแล้ว — และด้วยเหตุนี้ ΔΦ — จึงมีรูปแบบบรรทัดเดียวที่แม่นยำ (ไม่ต้องแก้กราฟทั้งหมดใหม่):

```
Q'(u,v) = max( Q(u,v),  E(u,a)·s'·E(b,v),  E(u,b)·s'·E(a,v) )

E(x,y) = λ·Q(x,y) for x ≠ y;  E(x,x) = 1        (edge e = {a, b})

ΔΦ = mean over ordered pairs of (Q'(u,v) − Q(u,v))
```

E คือ "best chain ไปยัง endpoint ของ edge ใหม่ โดยจ่าย junction เพื่อต่อเข้ากับมัน"; สองเทอมคือสองทิศทางของการข้าม edge นี้ สิ่งนี้ทดสอบใน harness suite เทียบกับการคำนวณ Φ แบบ brute-force

การคาดการณ์ที่ไม่สามารถเอาชนะความแข็งแกร่งของ edge ปัจจุบันได้จะให้ ΔΦ = 0: สูตรใช้เงินของผู้บริจาคเพื่อยืนยันสิ่งที่ไม่รู้ ไม่ใช่วัดซ้ำสิ่งที่พิสูจน์แล้ว (exploration bonus ป้องกันไม่ให้เซลล์ที่อ่อนแอหรือ sample น้อยถูกอดอาหารตลอดไป)

### 3.3 สิ่งที่นับเป็นหลักฐานเทียบกับสิ่งที่สามารถ queue ได้

สองเกณฑ์ที่แตกต่างกัน โดยเจตนาไม่สมมาตร:

- **หลักฐาน** มาจากการรันที่เผยแพร่และไม่ถูกตัดสิทธิ์ *ทุกครั้ง* —
  รวมถึงการรันบนคอร์ปัสที่ไม่สามารถ queue ได้สาธารณะ (เช่น ชุดที่มีใบอนุญาตไม่เชิงพาณิชย์) การวัดคู่ที่เผยแพร่คือความรู้ ไม่ว่าคุณจะรันซ้ำได้หรือไม่
- **Actions** (รายการคิว) มาจากคอร์ปัสที่รันได้อย่างเปิดเผยเท่านั้น:
  development split, ใบอนุญาตตระกูล CC-BY, ดึงข้อมูลได้โดยทุกคน

ภาษาที่เข้าถึงได้เฉพาะผ่านคอร์ปัสที่ queue ไม่ได้ยังคงอยู่ในกราฟ: การปรับปรุง edge *รอบๆ* พวกมันเปลี่ยนค่า chain ของพวกมัน และสูตรคำนึงถึงสิ่งนี้

## 6. ข้อจำกัดที่ทราบ (และสิ่งที่จะแก้ไขได้)

1. **chrF++ ไม่สามารถเปรียบเทียบได้ข้ามภาษา.** สัณฐานวิทยาเลื่อนระดับ; edge 0.5 เข้าสู่ภาษา Basque ไม่ใช่ความสำเร็จเดียวกับเข้าสู่ภาษาดัตช์ การบรรเทา: ลำดับความสำคัญถูกครอบงำโดย *โครงสร้าง* (การเปลี่ยนผ่าน s = 0 → s > 0) ที่ผลกระทบของระดับเป็นลำดับที่สอง การแก้ไข: การ normalize คะแนนต่อภาษา หรือ metric ที่มีการปรับเทียบข้ามภาษาที่ดีกว่าเมื่อมีให้สำหรับภาษาเหล่านี้
2. **chain model แบบ product-λ คือ prior ไม่ใช่การวัด.** มีการสนับสนุนในทิศทางจากวรรณกรรม pivot แต่ไม่ได้ปรับเทียบสำหรับการแปล LLM การแก้ไข (วางแผนไว้): mesh ขณะนี้มีสามเหลี่ยมที่วัดแล้ว (เช่น deu→fra ตรงควบคู่กับ deu→eng→fra) ดังนั้นผลลัพธ์ที่เชื่อมต่อสามารถให้คะแนนได้โดยตรงและ λ fit กับข้อมูลแทนที่จะเลือก
3. **การปนเปื้อนและสถานะ dev-set.** ความแข็งแกร่งของ edge รับข้อแม้ทุกอย่างของ development set สาธารณะ — ถือว่า Φ เป็นสัญญาณการวางแผนขอบบน ไม่ใช่การอ้างสิทธิ์ความสามารถ
   ([Corpus Design](/docs/network/specifications/corpus-design))
4. **ความตาบอดด้าน domain.** Edge ที่วัดบนข้อความสนทนาถือเป็นตัวเลขเดียว; chain ที่ข้าม domain จะเสื่อมลงมากกว่าที่ λ คาดการณ์
5. **ทิศทาง.** Edge ขณะนี้ไม่มีทิศทาง (หลักฐาน X→Y จุด X↔Y) เมื่อการประกอบ chain กลายเป็นไวต่อทิศทางในทางปฏิบัติ ความแข็งแกร่งจะแยกตามทิศทาง — สูตรไม่เปลี่ยน กราฟเพียงแค่เพิ่มเป็นสองเท่า
