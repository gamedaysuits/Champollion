# การทดสอบนัยสำคัญทางสถิติ

> **สถานะ**: ✅ เผยแพร่แล้ว (Shipped) การทดสอบนัยสำคัญแบบจับคู่ (paired significance testing: สุ่มแบบประมาณการเป็นค่าเริ่มต้น และ paired bootstrap เมื่อร้องขอ) และช่วงความเชื่อมั่นแบบบูตสแตรป (bootstrap confidence intervals) ได้รับการนำไปใช้งานใน `mt_eval_harness/significance.py` และ `mt_eval_harness/confidence.py` ถูกส่งออกจากแพ็กเกจ เปิดให้ใช้งานผ่าน CLI และครอบคลุมโดยชุดการทดสอบ significance / confidence / scoring
> **โค้ดเบส**: `arena` — เชื่อมโยงเข้ากับ `tester.py` (ช่วงความเชื่อมั่นต่อรอบการรัน) และ `compare.py` (นัยสำคัญระหว่างรอบการรัน)
> **วัตถุประสงค์**: ช่วยให้นักวิจัยสามารถระบุได้ว่าความแตกต่างระหว่างการประเมินผลสองรอบมีนัยสำคัญทางสถิติหรือเป็นเพียงแค่สัญญาณรบกวน (noise)

หน้านี้บันทึก **พฤติกรรมที่เปิดตัวแล้ว** — เป็นเอกสารเชิงพรรณนา ไม่ใช่รายการสิ่งที่ต้องทำ

## เหตุใดสิ่งนี้จึงสำคัญ

เมื่อเปรียบเทียบการรันสองครั้ง (ตัวอย่างเพื่อประกอบความเข้าใจ: ระบบ A ได้ chrF++ 42.96 เทียบกับระบบ B ได้ chrF++ 41.80 บน 92 รายการ) ความแตกต่างของคะแนนดิบเพียงอย่างเดียวไม่สามารถบอกได้ว่าผลลัพธ์นั้นเป็นจริงหรือเป็นเพียงสัญญาณรบกวน เมื่อมีรายการทดสอบเพียง ~92 รายการ ความแปรปรวนแบบสุ่มสามารถสร้างความแกว่งได้ง่าย 1–2 คะแนน ผู้เชี่ยวชาญต้องการการทดสอบนัยสำคัญ — ดังนั้น harness จึงคำนวณให้

**ภายใต้มาตรฐานการให้คะแนน (`standard/1`) การทดสอบแบบจับคู่บน chrF++ คือสิ่งชี้ขาดว่าการรันหนึ่งดีกว่าอีกการรันหนึ่งหรือไม่** chrF++ เป็นเมตริกหลักที่ประกาศไว้ล่วงหน้า ([ข้อกำหนดการให้คะแนน](/docs/network/specifications/scoring#how-runs-are-scored)) ส่วน BLEU, spBLEU, TER และ COMET (เมื่อการรันทั้งสองมีคะแนน COMET รายเซกเมนต์จากโมเดลเดียวกัน) จะได้รับการทดสอบและแสดงเป็นเมตริกมาตรฐานรอง และใช้อัตราการจับคู่ตรงทั้งหมด (exact match) กับอัตราจากปลั๊กอินเป็นการวินิจฉัย โดยไม่มีตัวใดในกลุ่มนี้มีผลชี้ขาด แนวทางนี้เป็นไปตาม Kocmi และคณะ (2021, "To Ship or Not to Ship") ซึ่งพบจากการตัดสินของมนุษย์หลายพันครั้งว่าความแตกต่างของเมตริกร่วมกับค่านัยสำคัญของมันคือสิ่งทำนายความชอบของมนุษย์

## อัลกอริทึม: Paired Approximate Randomization (ค่าเริ่มต้น)

`mt-eval compare --significance` ใช้การทดสอบ **paired approximate randomization (AR)** ของ Riezler & Maxwell (2005) ซึ่งเป็นค่าเริ่มต้นของ SacreBLEU ในการเปรียบเทียบระบบเช่นกัน

### วิธีการทำงาน

กำหนดให้ระบบสองระบบ A และ B ถูกประเมินบนรายการทดสอบ N รายการเดียวกัน:

1. คำนวณความแตกต่างระดับคลังข้อมูลที่สังเกตได้: `Δ = metric(A) - metric(B)`
2. ทำซ้ำ `n_trials` ครั้ง (ค่าเริ่มต้นคือ 1000):
   a. สำหรับแต่ละรายการ ให้สลับผลลัพธ์ของ A และ B ด้วยความน่าจะเป็น ½
   b. คำนวณเมตริกระดับคลังข้อมูลใหม่บนกองข้อมูลสองกองที่สลับแล้ว
   c. บันทึกว่า `|Δ_shuffled| ≥ |Δ|` หรือไม่
3. ค่า p-value คือระดับนัยสำคัญที่ได้แบบสองด้าน:
   `p = (#{|Δ_shuffled| ≥ |Δ|} + 1) / (n_trials + 1)` โดยที่ +1 จะนับการกำหนดค่าที่สังเกตได้จริงเป็นการสุ่มที่ถูกต้องหนึ่งครั้ง ดังนั้นค่า p จะไม่มีทางเป็น 0 พอดี
4. หาก p < α (ค่าเริ่มต้นคือ 0.05) ความแตกต่างจะถูกรายงานว่ามีนัยสำคัญ

ช่วงความเชื่อมั่นของ Δ คือ bootstrap percentile interval (เนื่องจาก AR ให้ค่า p-value ไม่ใช่ช่วง) ซึ่งคำนวณบนสตรีมสุ่มแยกต่างหากเพื่อไม่ให้รบกวนการสุ่มของ AR

### คุณสมบัติสำคัญ

- **การทดสอบสมมติฐานที่แท้จริง:** การสลับข้อมูลถูกสุ่มขึ้นภายใต้สมมติฐานว่างที่ว่าระบบใดเป็นผู้สร้างรายการนั้น ๆ ก็ไม่สร้างความแตกต่าง
- **แบบจับคู่ (Paired):** ทั้งสองระบบได้รับการเปรียบเทียบกันแบบรายการต่อรายการ ซึ่งรักษาความสัมพันธ์ระดับรายการไว้
- **นอนพารามิเตอร์ (Non-parametric):** ไม่มีการตั้งสมมติฐานใด ๆ เกี่ยวกับการแจกแจงของคะแนน

### The paired bootstrap (มีให้ใช้งาน ไม่ใช่ค่าเริ่มต้น)

`paired_bootstrap()` ใช้งาน paired bootstrap ของ Koehn (2004) โดยจะสุ่มซ้ำรายการแบบใส่คืนและนับจำนวนครั้งที่เครื่องหมายของ Δ พลิกกลับ วิธีนี้มีไว้เพื่อให้สามารถเปรียบเทียบกับงานวิจัยเก่า ๆ ได้ แต่มันเป็นเพียงฮิวริสติกความคงทนของเครื่องหมาย ไม่ใช่ระดับนัยสำคัญตามตำรา การแจกแจงของมันมีศูนย์กลางอยู่ที่ค่า Δ ที่สังเกตได้ ไม่ได้อยู่ที่สมมติฐานว่าง จึงอาจรายงานนัยสำคัญเกินจริงเมื่อเทียบกับ AR เลือกใช้งานผ่านบรรทัดคำสั่งด้วย `mt-eval compare <reports…> --significance --method paired_bootstrap` หรือกำหนด `method="paired_bootstrap"` ใน `run_significance_tests`

## sacrebleu เป็น Hard Dependency

sacrebleu เป็น hard dependency การประเมิน MT ที่ไม่สามารถคำนวณ chrF++ หรือ BLEU ไม่ถือเป็น MT eval harness ดังนั้น:

1. `sacrebleu>=2.3` ถูกประกาศภายใต้ `[project.dependencies]` ใน `pyproject.toml` (ไม่ใช่ `[project.optional-dependencies]`)
2. นำเข้าโดยตรงใน `tester.py` — `from sacrebleu.metrics import CHRF, BLEU, TER` — โดยไม่มีการป้องกัน `try/except`
3. นำเข้าโดยตรงใน `significance.py`

ไม่มีเส้นทางแบบมีเงื่อนไข `HAS_SACREBLEU` ที่ใดเลย: การรันโดยไม่มี sacrebleu ไม่ใช่การกำหนดค่าที่รองรับ

### 2. โมดูล: `mt_eval_harness/significance.py`

การนำการทดสอบนัยสำคัญไปใช้งาน (approximate randomization เป็นค่าเริ่มต้น, paired bootstrap เมื่อร้องขอ) อินเทอร์เฟซสาธารณะ:

```python
"""
Statistical significance testing via paired bootstrap resampling.

Standard method used by WMT shared tasks, SacreBLEU, and MT-Lens.
Compares two runs on the same corpus to determine if the performance
difference is statistically significant.
"""

from __future__ import annotations

import random
from dataclasses import dataclass
from sacrebleu.metrics import CHRF, BLEU


@dataclass
class SignificanceResult:
    """Result of a paired bootstrap significance test."""
    metric_name: str           # e.g., "corpus_chrf", "exact_match_rate"
    system_a_score: float      # Score for system A
    system_b_score: float      # Score for system B
    delta: float               # A - B
    p_value: float             # Two-sided p-value
    n_bootstrap: int           # Number of bootstrap iterations
    confidence_level: float    # 1 - alpha
    significant: bool          # p_value < alpha
    winner: str | None         # "A", "B", or None if not significant
    ci_lower: float            # Lower bound of 95% CI on the delta
    ci_upper: float            # Upper bound of 95% CI on the delta


def paired_bootstrap(
    entries_a: list[dict],
    entries_b: list[dict],
    metric_fn: callable,
    n_bootstrap: int = 1000,
    alpha: float = 0.05,
    seed: int = 12345,
    metric_name: str = "metric",
) -> SignificanceResult:
    """Run paired bootstrap resampling significance test.

    Args:
        entries_a: Per-entry results from system A (from TestReport["entries"])
        entries_b: Per-entry results from system B (must be same length, same IDs)
        metric_fn: Function(list[dict]) -> float that computes the corpus-level
                   metric from a list of entry dicts. Must handle the entry format
                   from TestReport.
        n_bootstrap: Number of bootstrap iterations (1000 is standard)
        alpha: Significance level (0.05 = 95% confidence)
        seed: RNG seed for reproducibility (12345 matches SacreBLEU default)
        metric_name: Human-readable name for the metric being tested

    Returns:
        SignificanceResult with all fields populated.

    Raises:
        ValueError: If entries_a and entries_b have different lengths or IDs.
```

### 3. ฟังก์ชันเมตริกในตัว

```python
def exact_match_rate(entries: list[dict]) -> float:
    """Compute exact match rate from a list of entry dicts."""
    non_error = [e for e in entries if not e.get("error")]
    if not non_error:
        return 0.0
    exact = sum(1 for e in non_error if e.get("exact_match"))
    return exact / len(non_error)


def corpus_chrf(entries: list[dict]) -> float:
    """Compute corpus-level chrF++ from a list of entry dicts."""
    chrf = CHRF(word_order=2)
    refs = [e["expected"] for e in entries if e.get("expected", "").strip()]
    hyps = [e["predicted"] if e.get("predicted", "").strip() else "EMPTY"
            for e in entries if e.get("expected", "").strip()]
    if not refs:
        return 0.0
    return chrf.corpus_score(hyps, [refs]).score


def corpus_bleu(entries: list[dict]) -> float:
    """Compute corpus-level BLEU from a list of entry dicts."""
    bleu = BLEU()
    refs = [e["expected"] for e in entries if e.get("expected", "").strip()]
    hyps = [e["predicted"] if e.get("predicted", "").strip() else "EMPTY"
            for e in entries if e.get("expected", "").strip()]
    if not refs:
        return 0.0
    return bleu.corpus_score(hyps, [refs]).score
```

### 4. การผสานรวมเข้ากับ `compare.py`

`compare.py` ทำการเปรียบเทียบแบบเคียงข้างกันของ TestReport หลายฉบับและรันการทดสอบนัยสำคัญระหว่างรายงานเหล่านั้น `run_significance_tests()` ขับเคลื่อนการทดสอบระหว่างสองรายงาน และ `format_significance_table()` ทำการเรนเดอร์ ทุกผลลัพธ์จะระบุ `role` ของตน: `primary` (chrF++ — การทดสอบหนึ่งเดียวที่มีผลชี้ขาด), `secondary` (เมตริกมาตรฐานอื่น ๆ) หรือ `diagnostic` โดยจะทดสอบตามลำดับดังนี้:

| เมตริก | บทบาท | คำนวณต่อการสุ่มซ้ำจาก |
|---|---|---|
| `corpus_chrf` | หลัก | สถิติของ sacreBLEU ต่อเซกเมนต์ |
| `corpus_bleu` | รอง | สถิติของ sacreBLEU ต่อเซกเมนต์ |
| `corpus_spbleu` | รอง | สถิติของ sacreBLEU ต่อเซกเมนต์ บนโทเคไนเซอร์ SentencePiece ของ FLORES-200 (spBLEU คือ BLEU ที่ใช้โทเคไนเซอร์ดังกล่าว ซึ่งเป็นตัวเลขที่ตาราง FLORES/NLLB รายงาน) เมื่อไม่มีโทเคไนเซอร์ให้ใช้งาน (ไม่มี `sentencepiece` หรืออยู่ในโหมดออฟไลน์โดยที่ยังไม่ได้ดาวน์โหลดโมเดล) จะถูกระบุว่าไม่ได้ทดสอบ โดยจะไม่ถูกตัดทิ้งอย่างเงียบ ๆ |
| `corpus_ter` | รอง | สถิติของ sacreBLEU ต่อเซกเมนต์ TER เป็นอัตราการแก้ไข ดังนั้น **ยิ่งต่ำยิ่งดี**: ค่า Δ ที่เป็นลบจะส่งผลดีต่อ A |
| `comet_score` | รอง | คะแนน COMET รายเซกเมนต์ที่รายงานทั้งสองมีอยู่แล้ว (ค่าเฉลี่ยคือคะแนนระดับระบบของ COMET โดยไม่มีการรันโมเดลซ้ำ) จะระบุว่าไม่ได้ทดสอบพร้อมเหตุผล เมื่อมีการรันเพียงรอบเดียวที่คิดคะแนนด้วย COMET หรือทั้งสองรอบใช้โมเดล COMET ต่างกัน |
| `exact_match_rate` | การวินิจฉัย | แฟล็ก exact-match ของแต่ละรายการ |
| อัตราจากปลั๊กอินในทั้งสองรายงาน เช่น `giellalt_fst_validity.avg_fst_validity`, `.corpus_validity_rate`, `.morphological_accuracy`, `code_switching.avg_code_switching_rate`, `hallucination.avg_hallucination_rate` | การวินิจฉัย | ผลลัพธ์รายรายการของตัวปลั๊กอินเอง โดยรวมยอดในแบบเดียวกับตัวเลขสรุปหลัก |

**คะแนนรวมที่เลิกใช้แล้วจะไม่ถูกทดสอบ** คะแนนรวมแบบถ่วงน้ำหนักและแถว `segment_composite` ที่เคยได้รับการทดสอบที่นี่ถูกยกเลิกแล้วตามมาตรฐานการให้คะแนน ([ข้อกำหนดการให้คะแนน §4](/docs/network/specifications/scoring#4-composite-score)) ไฟล์ JSON การเปรียบเทียบที่เขียนขึ้นก่อนมาตรฐานนี้จะยังคงแสดงแถว `segment_composite` (หรือ `composite_score`) โดยระบุว่าเป็นคะแนนรวมแบบเก่าที่ไม่มีผลชี้ขาดใด ๆ เมื่อรายงานที่นำมาเปรียบเทียบเป็นรายงานรุ่นเก่า `compare` จะแจ้งว่าคะแนนรวมของรายงานนั้นเลิกใช้แล้วและจะไม่ทำการเปรียบเทียบ

```python
# In compare_reports(), after computing deltas:
if len(reports) == 2:
    sig_results = run_significance_tests(reports[0], reports[1])
    comparison["significance"] = [asdict(r) for r in sig_results]
```

เมื่อมีการเปรียบเทียบรายงานมากกว่า 2 ฉบับ การทดสอบนัยสำคัญแบบจับคู่จะรันสำหรับทุกคู่: `significance` จะกลายเป็นรายการของออบเจกต์ `{"pair": [run_a_id, run_b_id], "letters": ["A", "C"], "tests": [...]}` หนึ่งรายการต่อหนึ่งคู่ โดยแต่ละรายการ `tests` จะมีรูปแบบเหมือนกับกรณีของสองรายงาน `letters` คือตัวอักษรของการรันทั้งสองในตารางการรัน และ Δ คือตัวแรกหักลบด้วยตัวที่สอง

นอกจาก `significance` แล้ว JSON การเปรียบเทียบยังมี `significance_settings`: `method`, `n_resamples`, `alpha`, `seed`, ตัวอักษรแต่ละตัวหมายถึงการรันใด (`runs`), `ci_lower`/`ci_upper` คืออะไร, `multiple_testing_correction: "none"`, จำนวนเมตริกที่ทดสอบต่อคู่และมีกี่คู่, ข้อความอธิบายแบบเข้าใจง่ายเกี่ยวกับค่า p-value ที่ไม่ได้ปรับแก้ (ด้านล่าง) และหมายเหตุใด ๆ ที่การทดสอบสร้างขึ้น (รายการที่ถูกตัดออกจากการจับคู่, เมตริกที่ไม่ได้ทดสอบ)

### 5. การผสานรวม CLI

`mt-eval compare` มีแฟล็ก `--significance` ให้ใช้งาน พร้อมด้วย `--method` สำหรับเลือกการทดสอบแบบจับคู่ (`approximate_randomization` ซึ่งเป็นค่าเริ่มต้น หรือ `paired_bootstrap`) และ `--n-bootstrap` สำหรับกำหนดจำนวนรอบการวนซ้ำ:

```bash
# Compare two runs with significance testing
mt-eval compare report_a.json report_b.json --significance

# The Koehn (2004) paired bootstrap instead of approximate randomization
mt-eval compare report_a.json report_b.json --significance --method paired_bootstrap

# Custom resampling count
mt-eval compare report_a.json report_b.json --significance --n-bootstrap 5000
```

`compare` รับไฟล์ `*_report.json` ที่ `mt-eval run` เขียนขึ้น (หรือไฟล์บันทึกการรัน ซึ่งจะใช้รายงานที่อยู่ในระดับเดียวกัน) โดยจะพิมพ์ตารางการรันที่มีหนึ่งแถวต่อหนึ่งเมตริกและหนึ่งคอลัมน์ต่อหนึ่งการรัน จากนั้นพิมพ์ตารางนัยสำคัญ และเขียนไฟล์ JSON การเปรียบเทียบไปยังตำแหน่งที่เป็นกลาง เว้นแต่ว่า `-o` จะระบุชื่อไฟล์อื่น: `comparison-<hash>.json` ข้าง ๆ รายงานเมื่อไฟล์เหล่านั้นอยู่ในโฟลเดอร์เดียวกัน มิฉะนั้นจะเขียนลงใน `comparisons/` ในโฟลเดอร์ร่วมที่ใกล้ที่สุด (รายงานที่อยู่ในโฟลเดอร์เฉพาะของการรันแต่ละตัว เช่น โฟลเดอร์ `mcp-run-<id>/` ของ `run_benchmark` จะไม่มีวันถูกเขียนไฟล์เปรียบเทียบลงในโฟลเดอร์ใดโฟลเดอร์หนึ่งของพวกมัน) ค่า `<hash>` คืออักขระฐานสิบหก 10 ตัวแรกของ sha256 จาก id ของการรันที่เปรียบเทียบตามลำดับที่กำหนด ดังนั้นการเปรียบเทียบอื่นในโฟลเดอร์เดียวกันจะไม่มีวันเขียนทับไฟล์นี้ การเปรียบเทียบการรันชุดเดิมซ้ำอีกครั้งจะเขียนทับไฟล์ของมันเอง การระบุชื่อไฟล์ด้วย `-o` จะแทนที่สิ่งที่มีอยู่เดิม และเอาต์พุตจะระบุเช่นนั้น คำสั่งจะพิมพ์เส้นทางของไฟล์ที่เขียนขึ้น การเปรียบเทียบการรันบนคลังข้อมูลที่เป็นแบบใช้เฉพาะในเครื่อง, แบบปิดผนึก หรือแบบต้องได้รับความยินยอม จะมีการอ้างอิงประโยคของคลังข้อมูลเหล่านั้น ดังนั้นจึงจะมีเครื่องหมายของคลังข้อมูลนั้นอยู่ในไฟล์เสริม `<file>.champollion.json` ไม่ว่าจะถูกเขียนไว้ที่ใด

คอลัมน์ **Avg latency (s/entry)** ของตารางการรันจะแสดง `—` สำหรับการรันที่ไม่มีการบันทึกเวลา พร้อมหมายเหตุใต้ตารางระบุเหตุผล: รายการทั้งหมดมาจากแคช, ผลลัพธ์ถูกสร้างขึ้นนอก harness หรือเมธอดไม่ได้รายงานเวลา ค่าที่ต่ำกว่า 0.01 วินาทีจะแสดงทศนิยมสี่ตำแหน่ง (โมเดลขนาดเล็กบน CPU ถอดรหัสประโยคละไม่กี่มิลลิวินาที) และจะไม่ถูกปัดเศษเป็น 0.00

### 6. รูปแบบผลลัพธ์

`format_significance_table()` แสดงผลมุมมอง console โดยข้อมูลเดียวกันจะถูกเพิ่มลงใน JSON ของการเปรียบเทียบ

รายงานจะถูกกำหนดตัวอักษรตามลำดับที่ระบุ: รายงานแรกคือการรัน **A** รายงานที่สองคือ **B** จากนั้นเป็น **C**, **D** และต่อ ๆ ไป ซึ่งเป็นตัวอักษรเดียวกับตารางการรันด้านบน ตารางเปรียบเทียบทีละคู่ทุกตารางจะระบุชื่อการรันทั้งสองด้วยตัวอักษรเหล่านี้พร้อม run id เช่น `--- A (baseline) vs C (nllb-ft) ---` และคอลัมน์รวมถึง Δ จะใช้ตัวอักษรเดียวกัน (`Δ (A−C)`) โดย Δ จะเป็น **ตัวแรก − ตัวที่สอง** เสมอ คำอธิบายของตารางและหมายเหตุทุกข้อด้านล่างจะถูกพิมพ์เพียง **ครั้งเดียว** ไม่ว่าจะมีกี่คู่ก็ตาม แต่ละแถวยังพิมพ์ค่า 95% **CI on Δ**: ซึ่งก็คือ bootstrap percentile interval ใน `ci_lower`/`ci_upper` ของ JSON ซึ่งบ่งบอกว่าขนาดของความแตกต่างน่าจะอยู่ที่เท่าใด ไม่ใช่แค่เครื่องหมายบวกหรือลบ เมตริกแต่ละตัวจะกำกับด้วยทิศทางจากทะเบียนเมตริก (↑ ยิ่งสูงยิ่งดี, ↓ ยิ่งต่ำยิ่งดี) และคอลัมน์ **Better** จะระบุชื่อการรันที่มีคะแนนดีกว่าโดยคำนึงถึงทิศทาง พร้อมแสดง `(n.s.)` เมื่อความแตกต่างไม่มีนัยสำคัญ ดังนั้น อัตราประเภทที่ยิ่งต่ำยิ่งดี เช่น TER, การสลับภาษา หรือการสร้างข้อมูลเท็จ ที่เพิ่มขึ้น จะแสดงผล Δ เป็นบวกโดยมี **B** เป็นการรันที่ดีกว่า และโมเดลที่ผ่านการฝึกฝนซึ่งส่งเข้ามาเป็นอันดับสองและเอาชนะเบสไลน์ได้ 63.5 chrF++ จะพิมพ์ Δ −63.52 พร้อมระบุว่า **B** ดีกว่า เมตริกที่ไม่มีการประกาศทิศทางในทะเบียนจะแสดงผลด้วย `?` คะแนน, Δ และช่วงความเชื่อมั่นจะพิมพ์ทศนิยมสองตำแหน่ง และพิมพ์เพิ่มขึ้น (สูงสุดหกตำแหน่ง) ในแถวที่การปัดทศนิยมอาจบดบังความแตกต่างที่แท้จริง: spBLEU ที่ได้ 0.0684 เทียบกับ 0.0673 จะพิมพ์ Δ +0.0011 [+0.0001, +0.0021] และไม่มีทางเป็น +0.00 [+0.00, +0.00] ข้าง ๆ **Yes** พร้อมทั้งตารางจะระบุว่าแถวเหล่านั้นแสดงทศนิยมมากกว่าปกติ ไฟล์ JSON จะเก็บทศนิยมสี่ตำแหน่ง และเลขนัยสำคัญสี่ตำแหน่งสำหรับค่าที่ไม่เป็นศูนย์ซึ่งมีค่าน้อยกว่านั้น เพื่อไม่ให้ความแตกต่างที่แท้จริงถูกบันทึกเป็น 0 ผลลัพธ์ที่เหมือนกันทุกประการจะให้ Δ เป็น 0 พอดี และ p = 1 จึงไม่มีทางมีนัยสำคัญ หากค่า p ต่ำกว่า α ในขณะที่ช่วงบูตสแตรปของ Δ เป็น [0, 0] พอดี (มีเซกเมนต์ที่แตกต่างกันน้อยเกินไปที่จะประมาณความแตกต่างได้) **Sig?** จะแสดง `?†` และ **Better** จะแสดง `—†` พร้อมหมายเหตุว่า: ไม่มีการรันใดถูกระบุว่าดีกว่าในเมตริกนี้ สำหรับอัตราจากปลั๊กอินประเภทที่ยิ่งต่ำยิ่งดี ค่า `winner` ใน JSON จะคำนึงถึงทิศทางเช่นกัน (อัตราที่ต่ำกว่าเป็นฝ่ายชนะ) เหมือนเช่นที่เคยเป็นมาสำหรับ `corpus_ter`; อัตราจากปลั๊กอินที่ไม่มีทิศทางที่ดีกว่า (เป็นกลาง เช่น `morph_coverage` หรือไม่ได้ประกาศไว้) จะมีค่าเป็น `winner: null` นอกจากนี้ ทุกผลลัพธ์ยังระบุ `direction` ของตนอีกด้วย

**เอาต์พุตคอนโซล** (ตัวเลขเพื่อเป็นตัวอย่าง):
```
  Significance Tests (paired approximate randomization, n=1000, α=0.05):
  Each table names its two runs by their letters in the run table above.
  Δ = first run − second run.  ↑ higher is better, ↓ lower is better.
  Better = the run with the better score, by the metric's direction; (n.s.) = not significant.
  95% CI on Δ = bootstrap percentile interval: how large the difference plausibly is.

  --- A (baseline) vs B (coached) ---

  Metric                                          A        B  Δ (A−B)      95% CI on Δ  p-value  Sig?  Better
  ---------------------------------------- -------- -------- -------- ---------------- -------- -----  --------
  ↑ corpus_chrf                               42.96    41.80    +1.16   [-0.85, +3.12]    0.142    No  A (n.s.)
  ↑ corpus_bleu                                6.80     3.81    +2.99   [+0.61, +5.40]    0.018 Yes *  A
  ↑ corpus_spbleu                              9.10     6.42    +2.68   [+0.35, +5.02]    0.027 Yes *  A
  ↓ corpus_ter                                61.20    64.90    -3.70   [-7.05, -0.41]    0.030 Yes *  A
  ↑ exact_match_rate                           0.20     0.19    +0.01   [-0.03, +0.05]    0.381    No  A (n.s.)
  ↓ code_switching.avg_code_switching_rate     0.60     0.08    +0.52   [+0.45, +0.59]    0.001 Yes *  B

  p-values are per metric and uncorrected — no multiple-testing correction is
  applied (deliberately: the MT convention is to report each metric's own
  p-value). 6 metrics were tested, so one "significant" result at p<0.05 can
  turn up by chance alone. And a small Δ can be significant yet not
  meaningful: check the CI on Δ (how large the difference plausibly is) and
  how reliable the metric is for this language before acting on it.
```

ในตัวอย่างนี้ผลการตัดสินคือ **ไม่มีความแตกต่างอย่างมีนัยสำคัญ**: chrF++ ซึ่งเป็นเมตริกหลัก ไม่สามารถแยกความแตกต่างระหว่าง A และ B ได้ (p = 0.142) ดังนั้นจึงไม่มีการรันใดถูกระบุว่าดีกว่า — แม้ว่า BLEU, spBLEU และ TER จะบ่งชี้ว่า A ดีกว่า และการสลับภาษาจะบ่งชี้ว่า B ดีกว่า แถวเหล่านั้นจะถูกแสดงไว้ และผู้อ่านอาจต้องการตรวจสอบเพิ่มเติม แต่แถวเหล่านั้นไม่มีผลชี้ขาด ตารางจะแสดงรายการ chrF++ เป็นอันดับแรก ตามด้วยเมตริกมาตรฐานอื่น ๆ แล้วจึงเป็นเมตริกสำหรับการวินิจฉัย

หากมีการรันมากกว่าสองรายการ ตาราง `--- X (run) vs Y (run) ---` แต่ละตารางจะแสดงต่อกันภายใต้ส่วนหัวเดียว และหมายเหตุจะนับการทดสอบทั้งหมดที่ได้ทำไป (`6 metrics were tested per pair (36 tests over 6 pairs)`)

### 7. การผสานรวม Dashboard (การปรับปรุงเสริม)

เมื่อมีข้อมูลนัยสำคัญอยู่ใน JSON ของการเปรียบเทียบ dashboard สามารถแสดงผลได้ — แถวตารางการเปรียบเทียบพร้อมตัวบ่งชี้นัยสำคัญ (`*` สำหรับ p < 0.05, `**` สำหรับ p < 0.01) นี่คือ presentation layer ที่อยู่บนการคำนวณที่เปิดตัวแล้ว ไม่ใช่ส่วนหนึ่งของฟีเจอร์หลัก

## กรณีขอบและการตรวจสอบ

1. **รายการไม่ตรงกัน**: TestReports ทั้งสองต้องมี entry ID เดียวกัน หากไม่ตรงกัน (เช่น รายการหนึ่งรันบนชุดย่อย) ให้ทดสอบนัยสำคัญเฉพาะบนส่วนที่ตัดกัน และแจ้งเตือนเกี่ยวกับรายการที่ถูกยกเว้น

2. **รายการน้อยเกินไป**: หาก N < 10 ให้แจ้งเตือนว่าการทดสอบนัยสำคัญไม่น่าเชื่อถือเมื่อมีรายการน้อยมาก ยังคงรันการทดสอบ แต่พิมพ์คำเตือน

3. **คะแนนเหมือนกัน**: หากทั้งสองระบบให้ผลลัพธ์ต่อรายการที่เหมือนกัน p_value ควรเป็น 1.0 (ไม่มีความแตกต่างเลย)

4. **เมตริกของปลั๊กอิน**: อัตราจากปลั๊กอินที่ปรากฏในทั้งสองรายงานจะได้รับการทดสอบจากค่ารายเซกเมนต์ที่รายงานมีอยู่จริงเท่านั้น ซึ่งหมายถึงการรวมยอดของตัวปลั๊กอินเองจากผลลัพธ์รายรายการ (เมตริก FST) หรือค่าเฉลี่ยของค่ารายรายการที่การรวมยอดแบบ `avg_<name>` คำนวณ (เมตริกเชิงพฤติกรรม) อัตราจากปลั๊กอินที่ไม่มีค่ารายเซกเมนต์จะถูกระบุว่าไม่ได้ทดสอบ และไม่มีทางแสดงเป็น 0.00 เทียบกับ 0.00 จำนวนนับอย่างเช่น `total_words_checked` จะไม่ถูกนำมาทดสอบ

5. **การทำซ้ำได้**: ต้องบันทึก seed ของ RNG ในผลลัพธ์เพื่อให้ผลลัพธ์สามารถทำซ้ำได้อย่างแม่นยำ ค่าเริ่มต้นคือ 12345 (ตามแบบแผนของ SacreBLEU)

## สิ่งที่ไม่ควรสร้าง

- **ไม่มีการอนุมาน COMET ซ้ำในการทดสอบ**: COMET จะได้รับการทดสอบแบบจับคู่จากคะแนนรายเซกเมนต์ที่รายงานทั้งสองมีอยู่แล้ว โมเดลจะไม่มีวันถูกรันซ้ำในแต่ละรอบการสุ่มซ้ำ การรันสองรอบที่คิดคะแนนด้วยโมเดล COMET ต่างกันจะไม่ถูกนำมาทดสอบเปรียบเทียบกัน
- **ไม่มีการวิเคราะห์แบบเบย์เซียน**: ยึดตามวิธีบูตสแตรปแบบฟรีเควนทิสต์ ซึ่งเป็นสิ่งที่ชุมชน MT คาดหวังและเข้าใจ
- **ไม่มีการปรับแก้สำหรับการทดสอบหลายสมมติฐาน**: เมื่อทดสอบหลายเมตริก อย่าใช้การปรับแก้แบบ Bonferroni หรือวิธีที่คล้ายกัน ธรรมเนียมปฏิบัติในการประเมินผล MT คือการรายงานค่า p-value ดิบต่อแต่ละเมตริกและให้ผู้อ่านตีความเอง `mt-eval compare` **ระบุเช่นนี้** ในเอาต์พุตและใน `comparison.json` (`significance_settings.multiple_testing_correction: "none"` พร้อมหมายเหตุภาษาเข้าใจง่าย): เมื่อทดสอบหลายเมตริก ผลลัพธ์ที่ได้ p < 0.05 เพียงหนึ่งตัวอาจเกิดขึ้นจากความบังเอิญได้ และค่า Δ ที่น้อยมากก็อาจมีนัยสำคัญได้โดยที่ไม่ได้มีความสำคัญเชิงปฏิบัติจริง ดังนั้นควรอ่านค่า CI ของ Δ และความน่าเชื่อถือของเมตริกสำหรับภาษานั้น ๆ ก่อนที่จะตัดสินใจโดยอิงจากคำว่า "มีนัยสำคัญ" เพียงจุดเดียว

## คลัสเตอร์การจัดอันดับ {#ranking-clusters}

> **สถานะ**: ✅ เผยแพร่แล้ว สำหรับการแข่งขัน การจัดอันดับการแข่งขันเป็นชุดของ**คลัสเตอร์** ไม่ใช่อันดับแบบเคร่งครัด — การทดสอบนัยสำคัญคือสิ่งชี้ขาดว่ารายการที่อยู่ติดกันสามารถแยกความแตกต่างได้จริงหรือไม่ ส่วนนี้จะอธิบายสิ่งที่ส่งมอบ รวมถึงกรณีที่หลักฐานมีน้ำหนักน้อยกว่าการทดสอบแบบจับคู่

### การต่อลูกโซ่รายการที่ติดกัน, การกำหนดหมายเลขอันดับแบบการแข่งขัน

รายการต่าง ๆ จะถูกแบ่งตาม **แทร็ก** ก่อนเป็นอันดับแรก — ระบบแบบ `constrained` จะไม่มีวันถูกนำมาจัดอันดับเทียบกับระบบแบบ `unconstrained` และแต่ละแทร็กจะมีลำดับ กลุ่มคะแนนเสมอกัน และช่วงอันดับของตนเอง ดังนั้น "อันดับ 1" จึงหมายถึงอันดับ 1 *ภายในแทร็กนั้นเสมอ*

ภายในแทร็ก รายการต่าง ๆ จะเรียงลำดับตามเมตริกหลักของการแข่งขัน (chrF++ เว้นแต่การแข่งขันจะบันทึกเมตริกอื่นไว้) จากนั้นเรียงตามเมตริกเชิงสถิติพื้นผิวที่เหลือ และสุดท้ายเรียงตามเวลาที่ส่งก่อนหลัง ทุกคู่ที่**อยู่ติดกัน**ในลำดับดังกล่าวจะได้รับการทดสอบ คู่ที่การทดสอบไม่สามารถแยกความแตกต่างได้จะครองอันดับร่วมกัน และอันดับร่วมนี้จะ**เชื่อมโยงเป็นลูกโซ่**: หาก A เสมอกับ B และ B เสมอกับ C ทั้งสามรายการจะจัดอยู่ในกลุ่มเสมอกลุ่มเดียวกัน แม้ว่า A และ C จะไม่เคยถูกเปรียบเทียบกันโดยตรงก็ตาม

อันดับจะใช้การกำหนดหมายเลขอันดับแบบการแข่งขัน — เสมอกันสามอันดับที่หัวตารางจะเป็น `1, 1, 1` และรายการถัดไปคือ `4`; หากเสมอกันสองอันดับสำหรับที่สองจะเป็น `1, 2, 2, 4`

**ข้อจำกัดตามจริงของการเชื่อมโยงลูกโซ่**: ความไม่มีนัยสำคัญไม่มีคุณสมบัติการถ่ายทอด โซ่ที่ยาวอาจเชื่อมรายการสองรายการที่การทดสอบโดยตรง*สามารถ*แยกออกจากกันได้ ด้วยเหตุนี้ คลัสเตอร์จึงถูกรายงานเป็น**ช่วง** ไม่ใช่ค่าเดี่ยว

### ช่วงอันดับ

ทุกรายการจะมี `rank_min` และ `rank_max` — ซึ่งเป็นตำแหน่งที่ดีที่สุดและแย่ที่สุดที่สอดคล้องกับหลักฐาน ในรูปแบบเดียวกับที่ WMT ใช้สำหรับช่วงอันดับ รายการที่อยู่เดี่ยว ๆ ในคลัสเตอร์จะมี `rank_min == rank_max` รายการที่อยู่ภายในคลัสเตอร์ที่มี 4 รายการครอบคลุมอันดับที่ 2–5 จะมี `rank_min: 2, rank_max: 5` และ**ไม่มีรายการใดภายในคลัสเตอร์นั้นที่ "นำหน้า" รายการอื่น** การนำตัวเลขอันดับเดี่ยว ๆ ออกมาจากคลัสเตอร์ถือเป็นการตีความผลลัพธ์ที่ผิด

### ขั้นบันไดหลักฐาน

ไม่ใช่ว่าทุกคู่จะสามารถทดสอบด้วยวิธีเดียวกันได้ ดังนั้นแต่ละคู่จึงบันทึกขั้นที่ผลการตัดสินนั้นได้มาจริง ๆ ป้ายกำกับนี้เป็นส่วนหนึ่งของผลลัพธ์และจะไม่ถูกตัดทิ้ง:

| ขั้น | หลักฐาน | กรณีที่มีให้ใช้งาน | น้ำหนักความน่าเชื่อถือ |
|---|---|---|---|
| 1 | **การทดสอบแบบจับคู่รายเซกเมนต์** — approximate randomization เป็นค่าเริ่มต้น, paired bootstrap เมื่อร้องขอ (อัลกอริทึมตามที่อธิบายไว้ข้างต้น) | เฉพาะเมื่อรายการทั้งสองมีชุดคะแนนรายเซกเมนต์ที่สมบูรณ์และตรงแนวกัน | การทดสอบที่แท้จริง |
| 2 | **การซ้อนทับของ 95% bootstrap-CI** บนขอบเขตของช่วงที่เผยแพร่ | เมื่อเมตริกหลักมีขอบเขตช่วงความเชื่อมั่นในทั้งสองรายการ (chrF++ มี; ส่วน BLEU และ COMET ไม่มีคอลัมน์ช่วงความเชื่อมั่น) | ตัวแทนแบบอนุรักษนิยม — ช่วงที่ซ้อนทับกัน**ไม่ได้**พิสูจน์ความเทียบเท่ากัน และการไม่ซ้อนทับกันถือเป็นเกณฑ์ที่เข้มงวดกว่าการทดสอบแบบจับคู่ |
| 3 | **ความเท่ากันของค่าจุด** ตามการปัดเศษการแสดงผลของเมตริก | เสมอ | ขั้นที่อ่อนที่สุด: บ่งบอกเพียงแค่ว่าตัวเลขที่พิมพ์ออกมาสองตัวนั้นเหมือนกัน |

### การแข่งขันแบบปิดผนึก: ขั้นที่ 1 จะรันบนโหนด

ขั้นที่ 1 จำเป็นต้องใช้คะแนนรายเซกเมนต์จากทั้งสองระบบ ในการแข่งขันแบบปิดผนึก โหนดประเมินผลของผู้จัดจะถือชุดข้อมูลอ้างอิงไว้และ**ไม่มีทางส่งออกเอาต์พุตรายเซกเมนต์** นี่คือหัวใจสำคัญของเลนแบบปิดผนึกและไม่ใช่การตั้งค่าที่จะผ่อนปรนได้ ดังนั้นการทดสอบแบบจับคู่จึงส่งไปรันที่ตัวข้อมูลแทน

`mt-eval node verdicts` จะรันการทดสอบแบบจับคู่ของการแข่งขันบนโหนด โดยกระทำกับชุดอ้างอิงที่ปิดผนึกและทุกคู่ของรายการที่คิดคะแนน และเขียน**เฉพาะผลการตัดสินเท่านั้น**: สำหรับแต่ละคู่ จะระบุเมธอด, ค่า p-value, ผลต่างของคะแนน, ช่วงความเชื่อมั่น และจำนวนเซกเมนต์ โดยไม่มีเซกเมนต์ ข้อมูลอ้างอิง หรือคำแปลอยู่ในไฟล์ โหนดจะลงนามไฟล์ด้วยคีย์ score-sign จากนั้นผู้จัดจะปิดการแข่งขันด้วย `mt-eval contest close --node-verdicts <file> --verify-key <node public key>` การจัดอันดับจะใช้ผลการตัดสินก็ต่อเมื่อลายเซ็นได้รับการตรวจสอบความถูกต้อง และผลการตัดสินนั้นถูกคำนวณสำหรับการแข่งขันนี้, ชุดข้อมูลที่ปิดผนึกนี้, เมตริกนี้, นโยบายผลเสมอที่กำหนดไว้ตายตัว และเวอร์ชันของ harness ตามที่สัญญาไว้ มิฉะนั้นการปิดการแข่งขันจะถูกปฏิเสธ

เมื่อไม่มีการส่งผลการตัดสิน ผลเสมอของการแข่งขันแบบปิดผนึกจะขึ้นอยู่กับการซ้อนทับของช่วงความเชื่อมั่นในกรณีที่เมตริกมีช่วงความเชื่อมั่น และขึ้นอยู่กับความเท่ากันของค่าจุดในกรณีที่ไม่มี คลัสเตอร์ที่ได้จึงจะกว้างกว่าคลัสเตอร์ที่ได้จากการทดสอบแบบจับคู่ ตัวการจัดอันดับเองจะระบุว่ากรณีใดมีผลบังคับใช้: `ranking_method.evidence_used` จะระบุขั้นที่นำมาใช้จริง และ `ranking_method.node_verdicts` จะระบุชื่อโหนดที่นำผลการตัดสินมาใช้ (หากมี)

### สิ่งที่การจัดอันดับไม่ได้จัดอันดับ

- **รายการเชิงเปรียบเทียบความแตกต่าง** จะถูกรายงานในส่วนของตนเองและไม่มีวันชนะ
- **เวลาทำงาน, ฮาร์ดแวร์ และค่าใช้จ่าย** จะระบุอยู่ในการ์ดการรันและได้รับการรายงานเท่านั้น ไม่มีการนำมาจัดอันดับ ไม่มีการแข่งขันในแทร็กประสิทธิภาพ
- **การตัดสินโดยมนุษย์** ไม่ได้รวมอยู่ในการจัดอันดับเหล่านี้เลย โดย*การคัดเลือก*สำหรับการประเมินโดยมนุษย์ — ซึ่งพิจารณาว่าระบบใดบ้างที่งบประมาณจำกัดจะครอบคลุมถึง โดยเลือกทั้งกลุ่มคะแนนเสมอเพื่อไม่ให้คลัสเตอร์ถูกแบ่งครึ่ง — สามารถบันทึกไว้สำหรับการแข่งขันที่ปิดแล้วได้ แต่ไม่มีคะแนนการประเมิน ดูที่ [กฎการประเมิน MT](/docs/network/leaderboard/rules#verification-tiers)

## ความครอบคลุมของการทดสอบ

ชุดทดสอบ significance / confidence / scoring ผ่านทั้งหมด ครอบคลุม:

1. **Deterministic ด้วย seed**: input เดียวกัน + seed เดียวกัน → p-value เดียวกัน ทุกครั้ง
2. **การทดสอบด้วยคำตอบที่ทราบ**: ชุดผลลัพธ์สองชุดที่เหมือนกัน → p_value = 1.0
3. **การทดสอบที่มีนัยสำคัญที่ทราบ**: ชุดผลลัพธ์สองชุดที่หนึ่งดีกว่าอย่างชัดเจน (เช่น ตรงทั้งหมด vs ไม่ตรงทั้งหมด) → p_value ≈ 0.0
4. **ID ไม่ตรงกัน**: ยก `ValueError` หรือแจ้งเตือนและคำนวณบนส่วนที่ตัดกัน
5. **Input ว่างเปล่า**: จัดการได้อย่างเหมาะสม (p_value = 1.0 หรือยกข้อผิดพลาด)

## Confidence Intervals (ฟีเจอร์เสริม)

> **สถานะ**: ✅ พัฒนาแล้วใน `confidence.py`

Confidence intervals (CIs) ตอบคำถามที่แตกต่างจากการทดสอบนัยสำคัญ:

- **การทดสอบนัยสำคัญ** (`significance.py`): "ความแตกต่างระหว่างระบบ A และระบบ B เป็นจริงหรือไม่?"
- **Confidence intervals** (`confidence.py`): "คะแนนของระบบนี้มีความไม่แน่นอนมากเพียงใดในตัวมันเอง?"

### การพัฒนา: `confidence.py`

ใช้วิธี percentile bootstrap resampling เดียวกับการทดสอบนัยสำคัญ:

| พารามิเตอร์ | ค่า | เหตุผล |
|---|---|---|
| `n_bootstrap` | 1000 | ค่าเริ่มต้นของ SacreBLEU, แบบแผน WMT 2024 |
| `seed` | 12345 | seed เริ่มต้นของ SacreBLEU สำหรับการทำซ้ำได้ |
| `alpha` | 0.05 | ระดับความเชื่อมั่นมาตรฐาน 95% |
| Method | Percentile bootstrap | Koehn (2004), Efron (1979) |

### สิ่งที่ได้รับ CIs

เมตริกระดับคลังข้อมูลแบบกำหนดได้แน่นอนที่คำนวณโดย harness:
- `corpus_chrf` (คะแนน chrF++)
- `corpus_bleu` (คะแนน BLEU)
- `exact_match_rate` (0.0–1.0)
- `fst_acceptance_rate` (เมื่อมีข้อมูล FST)


ช่วงของ chrF++ เป็นส่วนหนึ่งของตัวเลขสรุปหลักที่เผยแพร่ (`chrF++ 47.5 [45.9, 49.0]`) และ**ยัง**มีการคำนวณค่า CI สำหรับ `comet_score` ซึ่งบูตสแตรปมาจากคะแนนรายรายการที่แคชไว้ (ไม่มีการอนุมานของโครงข่ายประสาทเทียมซ้ำซ้อน) ไม่มีการคำนวณ CI ของคะแนนรวมสำหรับการรันใหม่ ส่วน CI ของคะแนนรวมที่บันทึกไว้ในการ์ดรุ่นเก่าจะถูกคำนวณใหม่ก็ต่อเมื่อการ์ดนั้นได้รับการตรวจสอบความถูกต้องเท่านั้น

### แฟล็ก CLI

```bash
# Default: CIs are computed automatically
mt-eval test run_log.json

# Skip CI computation (faster, for quick iteration)
mt-eval test run_log.json --no-ci

# More bootstrap iterations (more precise, slower)
mt-eval test run_log.json --n-bootstrap-ci 2000
```

### คำเตือนสำหรับตัวอย่างขนาดเล็ก

เมื่อมีรายการ N < 30 รายการ โมดูลจะส่งคำเตือนว่า CIs อาจมีความครอบคลุมที่ไม่ดี Bootstrap ไม่สามารถสร้างข้อมูลที่ไม่มีอยู่ในตัวอย่าง — เมื่อมีรายการน้อยมาก ช่วงจะกว้าง ซึ่งสะท้อนความไม่แน่นอนสูงได้อย่างถูกต้อง

### COMET (เมตริกมาตรฐานเมื่อมีการคำนวณ แสดงควบคู่กับ chrF++)

COMET เป็น**เมตริกโครงข่ายประสาทเทียมที่แสดงควบคู่กับตัวเลขสรุปหลัก chrF++** ทุกครั้งที่มีการคำนวณ พร้อม id โมเดลของมัน โดยไม่มีการนำไปผสมรวมกับ chrF++ และไม่ได้ใช้เป็นตัวเลขสรุปหลักเนื่องจากต้องใช้โมเดลขนาดใหญ่และยังไม่มีการเทียบปรับมาตรฐานสำหรับภาษาที่มีทรัพยากรน้อยส่วนใหญ่ (ดู [ข้อกำหนดการให้คะแนน §2.3](/docs/network/specifications/scoring#2-metric-inventory)) โดยจะคำนวณ Bootstrap CI จากคะแนนรายรายการที่แคชไว้:
- โมเดล: `Unbabel/wmt22-comet-da` (โมเดลอิงข้อมูลอ้างอิง WMT 2022); เลือก AfriCOMET โดยอัตโนมัติสำหรับภาษาแอฟริกันที่รองรับ
- คำนวณเมื่อมีการติดตั้ง `unbabel-comet`
- คะแนนรายรายการจะถูกจัดเก็บในรายการของ TestReport; ค่าระดับคลังข้อมูลจะมีคำเตือนเกี่ยวกับการเทียบปรับมาตรฐานสำหรับภาษาทรัพยากรน้อย
- คำนวณใหม่โดยเครื่องมือตรวจสอบ — ค่า COMET ที่รายงานจะต้องสามารถสร้างซ้ำได้
- ส่วนประกอบเพิ่มเติมที่เลือกได้: `python3 -m pip install 'mt-eval-harness[comet]'` (หรือ `mt-eval setup --comet`)

### คอลัมน์ Supabase

ตาราง `run_cards` มีคอลัมน์ที่สามารถเป็นค่าว่างได้ที่สอดคล้องกัน (ดู [scoring.md §9.1](/docs/network/specifications/scoring)):
- `chrf_plus_plus`, `chrf_ci_lower`, `chrf_ci_upper` (`real`) — ตัวเลขสรุปหลักและช่วง 95% ของมัน
- `comet_score` (`real`) — แสดงควบคู่กับตัวเลขสรุปหลัก ไม่มีการนำไปผสมรวม
- `corpus_bleu` (`real`)

ชุดช่วงความเชื่อมั่นทั้งหมดจะถูกจัดเก็บไว้ใน JSON `scores` ของการ์ดการรันภายใต้ `confidence_intervals` (ตามสกีมาของการ์ดการรันใน scoring.md §9); โดยมีเพียงขอบเขตของ chrF++ เท่านั้นที่ถูกดีนอร์มัลไลซ์ออกมาเป็นคอลัมน์เพิ่มเติม
