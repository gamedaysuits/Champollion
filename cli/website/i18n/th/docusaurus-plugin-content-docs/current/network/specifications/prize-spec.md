# ข้อกำหนดรางวัล

รางวัลคือส่วนที่เป็นแรงจูงใจของข้อตกลงแบบประเมินผลก่อน (eval-first bargain) ชุมชนหรือ
กลุ่มวิจัยจะคัดสรรชุดข้อมูลประเมินผลขนาดเล็กที่ถูกปิดผนึกไว้ — ซึ่งมีจำนวนไม่กี่ร้อยคู่
โดยทุกคู่ผ่านการตรวจสอบแล้ว ([Corpus Partnership](/docs/network/specifications/corpus-partnership)
คือเวิร์กโฟลว์สำหรับกระบวนการนี้) ผู้สนับสนุนจะตั้งรางวัลโดยอิงจากคะแนนเป้าหมายของชุดข้อมูล
นั้น นับจากวินาทีนั้น ภาษานั้นจะกลายเป็นความท้าทายที่เปิดรับอยู่เสมอ: ผู้สร้างวิธีการ
คนใดในโลกก็สามารถตั้งเป้าหมายเพื่อพิชิตได้ กระดานผู้นำจะวัดผลทุกความพยายาม
แบบสาธารณะ และมาตรฐานจะถูกกำหนดโดยชุดคำตอบของชุมชนเอง แทนที่จะ
เป็นของผู้ที่ส่งเสียงดังที่สุด เอกสารนี้ระบุถึงวิธีการทำงานของรางวัลดังกล่าว
— เงื่อนไขเกณฑ์ขั้นต่ำ กระบวนการขอรับรางวัล คลาสการพึ่งพา และกฎเกณฑ์ —
เพื่อให้มาตรฐานมีความชัดเจนและไม่ยึดติดกับวิธีการใดๆ เมื่อมีการเปิดรับรางวัล

รางวัลจะถูก **สนับสนุนเงินทุนและถือครองโดยผู้สนับสนุน**: เงินรางวัลจะอยู่กับ
องค์กรผู้สนับสนุน หรืออยู่กับกองทุนของชุมชนที่ผู้สนับสนุนกำหนด —
**Champollion จะไม่ถือครอง เป็นคนกลาง (escrow) หรือจัดการเส้นทางการโอนเงินรางวัลใดๆ ทั้งสิ้น** ชุมชน
หรือองค์กรใดๆ สามารถจัดการแข่งขันได้ด้วยตนเองผ่านเส้นทางแบบบริการตนเองใน
[Run a Sovereign Contest](/docs/network/sovereignty/run-a-sovereign-contest)
โดยถือครองคลังข้อมูลและเงินรางวัลของตนเอง

> **สถานะ: PROPOSED (เสนอ) — ยังไม่มีการเปิดรับรางวัลใดๆ และยังไม่มีสิ่งใดในที่นี้ที่สามารถขอรับได้**
> สิ่งที่เป็นตัวกำหนดการ *เปิดรับ* รางวัลคือด้านการวัดผล:
> คลังข้อมูลมาตรฐานทองคำที่ได้รับความยินยอมจากชุมชน, แซนด์บ็อกซ์การประเมินผลแบบ air-gapped
> (มีการระบุสเปกไว้แล้ว แต่ยังไม่ได้สร้าง) และด่านการตรวจสอบโดยผู้พูด ยังไม่มีคะแนนใด
> บนเว็บไซต์นี้ที่ผ่านเกณฑ์รางวัล ดูเพิ่มเติมที่
> [Honest Limitations](/docs/network/honest-limitations) ข้อมูลอ้างอิงเกี่ยวกับตัวชี้วัด:
> [Scoring Spec](/docs/network/specifications/scoring); โปรโตคอล:
> [Benchmark Spec](/docs/network/specifications/benchmark)

## ต้องการช่วยนำภาษาเข้าสู่เครือข่ายหรือไม่?

คุณไม่จำเป็นต้องรอรางวัล สิ่งที่คุณสามารถทำได้วันนี้เพื่อสร้างผลกระทบสูงสุด:

- **สนับสนุนรางวัลความสำเร็จด้าน MT** ระดมทุนสำหรับเกณฑ์เฉพาะ — ตัวอย่างเช่น วิธีการแปล English → Plains Cree ที่เชื่อถือได้ Champollion ประสานงานการวัดผล; เงินอยู่กับ**คุณ** (องค์กรของคุณ หรือกองทุนชุมชนที่คุณกำหนด) และมอบรางวัลตามเงื่อนไขของชุมชน (ดู
  [อธิปไตยข้อมูล](/docs/network/sovereignty/data-sovereignty)
  และ [รูปแบบเศรษฐกิจ](/docs/network/sovereignty/economic-model)) เส้นทางบริการตนเองแบบครบวงจรมีเอกสารอยู่ใน
  [จัดการแข่งขันแบบอธิปไตย](/docs/network/sovereignty/run-a-sovereign-contest); การนำคู่ภาษาใหม่เข้ามาเริ่มต้นด้วย
  [ความร่วมมือด้านคลังข้อมูล](/docs/network/specifications/corpus-partnership)
- **ประสานงานการบริจาคทรัพยากรคำนวณ** รวม API credits / tokens เพื่อให้คิวสาธารณะสามารถแมปคู่ภาษาได้มากขึ้น และแสดงให้เห็นว่าการแปลนั้นเชื่อถือได้หรือยังไม่ได้ในส่วนใด
- **สนับสนุนโครงการโอเพนซอร์สที่เราพึ่งพา — *โดยตรง*** Champollion เป็นระบบประสานที่เชื่อมงานโอเพนซอร์สของผู้อื่นเข้าด้วยกัน การสนับสนุน*พวกเขา*คือการสนับสนุนแผนที่นี้ (เราอยากชี้ให้คุณไปหาต้นทางมากกว่าจะรับเครดิตจากงานของพวกเขา):
  - [Tatoeba](https://tatoeba.org) — ประโยคคู่ขนานที่ชุมชนร่วมกันสร้าง
  - [Endangered Languages Catalog (ELCat)](https://www.endangeredlanguages.com) — ข้อมูลระดับความเสี่ยงของภาษา
  - [Glottolog](https://glottolog.org) · [WALS](https://wals.info) · [Grambank](https://grambank.clld.org) · [PHOIBLE](https://phoible.org) — แคตาล็อกภาษาและวิทยาการประเภทภาษา
  - [GiellaLT](https://giellalt.uit.no) / ALTLab — transducer ทางสัณฐานวิทยา (FSTs)
  - [Masakhane](https://www.masakhane.io) — ชุมชน MT สำหรับภาษาแอฟริกัน
  - [OPUS](https://opus.nlpl.eu) — คลังข้อมูลคู่ขนานแบบเปิด

> หากต้องการสนับสนุนรางวัล จัดการบริจาคทรัพยากรคำนวณ หรือหารือเรื่องความร่วมมือ
> ติดต่อโครงการผ่าน [GitHub](https://github.com/gamedaysuits) ผู้ดูแลกุญแจชุมชนอยู่ระหว่างการยืนยัน; ยังไม่มีชาติหรือองค์กรใดถูกระบุชื่อเป็นพันธมิตรก่อนที่จะให้ความยินยอม

## 1. ปรัชญา

> **ข้อตกลงในหนึ่งบรรทัด: แก้ปัญหาภาษา, ชนะ, คืนให้ชุมชน** Champollion เป็นการดำเนินงานด้าน ML-benchmarking โดยเจตนา — การแข่งขันคือวิธีที่ทำให้คู่ภาษายากๆ ได้รับการแก้ไข เราเชิญนักวิจัย ML และผู้สร้างที่มีความสามารถทุกคนให้สร้างวิธีการที่ดีที่สุดสำหรับคู่ภาษายากเฉพาะ, ชนะรางวัล, **และ**ส่งมอบวิธีการที่ได้ให้กับองค์กรอธิปไตยที่เป็นเจ้าของภาษานั้น (§1.3) พลังงานการแข่งขันนั้นเป็นของจริง และมุ่งไปที่พันธกิจ — การแปลทุกภาษาภายใต้เงื่อนไขที่ผู้คนของภาษานั้นกำหนด — ไม่ใช่การไต่อันดับบนลีดเดอร์บอร์ดเพื่อประโยชน์ของตัวเอง

### 1.1 รางวัลตอบแทนความก้าวหน้า ไม่ใช่การมีส่วนร่วม

เงินรางวัลจะถูกปล่อยออกมาเฉพาะเมื่อวิธีการหนึ่งบรรลุเกณฑ์ความสามารถที่กำหนดไว้อย่างชัดเจน ไม่มีรางวัลสำหรับการมีส่วนร่วม, รางวัลรองชนะเลิศ, หรือการจ่ายเงินปลอบใจ หากไม่มีใครผ่านเกณฑ์ ก็ไม่มีใครได้รับเงิน นี่คือการออกแบบโดยเจตนา — หมายความว่าผู้สนับสนุนจ่ายเงินเฉพาะสำหรับผลลัพธ์ที่ใช้งานได้จริงเท่านั้น

### 1.2 การตรวจสอบโดยชุมชนเป็นสิ่งที่ต้องมี

ตัวชี้วัดอัตโนมัติเป็นเพียงตัวแทน (SCORING_SPEC §1.1) วิธีการหนึ่งอาจได้คะแนนดีใน chrF++ และการยอมรับของ FST ในขณะที่ผลิตผลลัพธ์ที่ผู้พูดภาษาไม่ยอมรับ **ทุกการเรียกร้องรางวัลต้องผ่านการตรวจสอบโดยชุมชน** — ผู้พูดสองภาษาต้องยืนยันว่าผลลัพธ์นั้นใช้งานได้ นี่คือด่านตรวจสอบโดยมนุษย์ (BENCHMARK_SPEC §7)

### 1.3 การโอนกรรมสิทธิ์เป็นส่วนหนึ่งของข้อตกลง

วิธีการที่เรียกร้องรางวัลอยู่ภายใต้ข้อกำหนดการโอนกรรมสิทธิ์ (BENCHMARK_SPEC §8.3) นักพัฒนาคงไว้ซึ่งสิทธิ์การระบุที่มาและสิทธิ์การเผยแพร่ องค์กรกำกับดูแลได้รับสิทธิ์ในการใช้, แก้ไข, เผยแพร่, และสร้างรายได้จากวิธีการสำหรับภาษาของตน นี่ไม่ใช่บทลงโทษ — นี่คือจุดประสงค์ เงินรางวัลสนับสนุนการสร้างเทคโนโลยีที่เป็นของชุมชนภาษา

### 1.4 การป้องกันการโกง

เกณฑ์รางวัลถูกกำหนดเทียบกับ**การประเมินมาตรฐานทองคำ** (ชุดทดสอบลับ, ดำเนินการโดยองค์กรกำกับดูแลในแซนด์บ็อกซ์) นักพัฒนาไม่เคยเห็นข้อมูลทดสอบ นี่ถูกบังคับใช้ทางสถาปัตยกรรม — ไม่ใช่นโยบายที่อาศัยความซื่อสัตย์ ดู BENCHMARK_SPEC §8.2

### 1.5 การอนุญาตสิทธิ์คลังข้อมูล: คลังข้อมูลที่ไม่ใช่เชิงพาณิชย์ไม่อยู่ในเส้นทางรางวัล

คลังข้อมูลบางส่วนที่ใช้ในระหว่างการพัฒนาวิธีการนั้นมีสัญญาอนุญาตแบบไม่ใช้เพื่อการค้า — ตัวอย่างเช่น คลังข้อมูล EdTeKLA Cree Language Textbook ใช้สัญญาอนุญาต **CC BY-NC-SA ที่ปรับปรุงโดย EdTeKLA** (กำหนดขอบเขตตามอธิปไตย, ไม่ใช้เพื่อการค้า; หนังสือเรียนต้นฉบับคือ CC BY-NC-ND 4.0) คลังข้อมูลเหล่านี้มีไว้สำหรับ **เส้นทางการวิจัย/การพัฒนาเท่านั้น (research/development-lane only)**:

1. **คลังข้อมูลมาตรฐานทองคำสำหรับรางวัลต้องไม่ฝังเนื้อหาคลังข้อมูลที่มีใบอนุญาต NC** ส่วนทดสอบมาตรฐานทองคำเป็นต้นฉบับที่ชุมชนว่าจ้างสร้าง (ดู Corpus Partnership Strategy) — เขียนโดยมนุษย์สำหรับรางวัล โดยมีสิทธิ์ที่ได้รับการอนุมัติสำหรับการประเมินและการใช้งานเชิงพาณิชย์ตั้งแต่ต้น
2. **วิธีการที่เรียกร้องรางวัลต้องไม่ฝังเนื้อหาคลังข้อมูลที่มีใบอนุญาต NC** (เช่น เป็นข้อมูลการฝึก, ตัวอย่างที่ฝังไว้, หรือตารางค้นหา) วิธีการที่โอนให้ต้องสามารถนำไปใช้งานโดยองค์กรกำกับดูแลได้ภายใต้เงื่อนไขใดก็ได้ที่ตนเลือก — รวมถึงเชิงพาณิชย์ หากชุมชนตัดสินใจเช่นนั้น (BENCHMARK_SPEC §8.3); เนื้อหาที่มีใบอนุญาต NC ภายในจะทำลายเสรีภาพนั้น
3. **นักพัฒนาสามารถใช้คลังข้อมูลที่มีใบอนุญาต NC ได้อย่างอิสระเพื่อพัฒนาและประเมินตนเอง** — นั่นคือจุดประสงค์ของเส้นทางพัฒนา ข้อจำกัดใช้กับสิ่งที่ส่งและสิ่งที่นำไปใช้งาน ไม่ใช่กับวิธีที่นักพัฒนาเรียนรู้

### 1.6 ประเภทการพึ่งพากำหนดสิทธิ์การรับรางวัล

การประเมินรางวัลทั้งหมดเกิดขึ้นในแซนด์บ็อกซ์ (§1.4) และวิธีการที่ชนะรางวัลจะโอนให้กับองค์กรกำกับดูแล (§1.3) ทั้งสองข้อเท้าความจริงเดียวกัน: **ทุกสิ่งที่วิธีการพึ่งพาต้องเป็นสิ่งที่นักพัฒนามีสิทธิ์นำเข้าแซนด์บ็อกซ์และส่งมอบให้ชุมชน** ทุกการส่งผลงานต้องประกาศประเภทการพึ่งพา — กำหนดไว้ใน [ข้อกำหนด Method Interface](/docs/network/specifications/methods#method-validity-and-dependency-classes) — และสิทธิ์การรับรางวัลขึ้นอยู่กับประเภท:

| ประเภทการพึ่งพา | มีสิทธิ์รับรางวัล? | เงื่อนไข |
|------------------|----------------|------------|
| **S** — พึ่งพาตนเอง | ✅ ใช่ | ไม่มีเงื่อนไขนอกจากเงื่อนไขเกณฑ์ใน §2 |
| **O** — เปิดภายนอก (เช่น AGPL FST ที่ mirror ณ เวลาส่งผลงาน) | ✅ ใช่ | Artifacts ถูก pin และ vendor เข้าในการส่งผลงาน; ใบอนุญาตอนุญาตให้โอนให้ชุมชน; เงื่อนไข copyleft ได้รับการรักษาไว้ (ชุมชนได้รับสิทธิ์เดียวกับที่ใบอนุญาตมอบให้ทุกคน) |
| **A1** — การอนุมาน LLM ที่แทนที่ได้ | ⚠️ มีเงื่อนไข | โมเดลถูกประกาศ, pin, และแทนที่ได้ (ต้องรันกับโมเดลน้ำหนักเปิดที่ชุมชนโฮสต์); การประเมินถูกส่งผ่าน sandbox LLM gateway (🔲 วางแผนไว้ — วิธีการ A1 ไม่สามารถสร้างคะแนนมาตรฐานทองคำได้จนกว่า gateway จะพร้อมใช้งาน); การโอนส่งมอบสูตรครบถ้วน (prompts, coaching, code) ไม่ใช่โมเดล |
| **A2** — API ข้อมูล/บริการภายนอกที่แทนที่ไม่ได้ | ❌ ยังไม่ได้ | ไม่มีสิทธิ์จนกว่าผู้ถือสิทธิ์จะให้สิทธิ์การรวมในแซนด์บ็อกซ์และการโอน อนุญาตบนลีดเดอร์บอร์ดเปิดพร้อมป้าย "external dependency" ที่มองเห็นได้ |
| **X** — เนื้อหาที่รวมไว้โดยไม่มีสิทธิ์ | ❌ ไม่มีวันได้ | ไม่รับในทุกเส้นทาง |

ประเภทของวิธีการคือประเภทที่จำกัดที่สุดในบรรดาการพึ่งพาที่ประกาศ การพึ่งพาที่ไม่ได้ประกาศในประเภทใดก็ตามถือเป็นเหตุตัดสิทธิ์ (§5)

#### เงื่อนไขเกณฑ์

วิธีการเรียกร้อง Founder's Prize โดยต้องตรงตาม**ทุก**เงื่อนไขต่อไปนี้พร้อมกัน:

| # | เงื่อนไข | ตัวชี้วัด | เกณฑ์ | เหตุผล |
|---|-----------|--------|-----------|-----------|
| 1 | **คะแนนรวม** | `composite` (SCORING_SPEC §4) | **≥ 0.80** | อยู่ระหว่าง Deployable (0.70) และ Fluent (0.85) ต้องการคุณภาพสูงในทุกมิติตัวชี้วัด — ไม่ใช่แค่ความถูกต้องทางสัณฐานวิทยา |
| 2 | **การยอมรับของ FST** | `fst_acceptance_rate` (SCORING_SPEC §2.2) | **≥ 0.99 (99%+)** | คำในผลลัพธ์ทั้งหมดต้องเป็นรูปแบบที่ถูกต้องทางสัณฐานวิทยาที่ GiellaLT FST รู้จัก ความคลาดเคลื่อน 1% รองรับกรณีขอบ (คำนามเฉพาะ, คำใหม่, คำยืม) ที่ FST อาจไม่ครอบคลุมอย่างถูกต้อง นี่คือด่านคุณภาพที่กำหนดสำหรับ MT แบบ polysynthetic — หาก FST ปฏิเสธคำมากกว่า 1% แสดงว่าวิธีการกำลังสร้างรูปแบบที่ไม่มีอยู่ในภาษา จุดประสงค์ทั้งหมดของรางวัลนี้คือการซื้อระบบที่ไม่บิดเบือนภาษา |
| 3 | **chrF++** | `chrf_plus_plus` (SCORING_SPEC §2.1) | **≥ 55.0** | ความทับซ้อนของ character n-gram ต้องเกิน 55 บนสเกล 0–100 เพื่อให้มั่นใจว่ามีความคล้ายคลึงระดับพื้นผิวกับการแปลอ้างอิง ไม่ใช่แค่ความถูกต้องทางสัณฐานวิทยา |
| 4 | **การตรวจสอบโดยชุมชน** | การตรวจสอบโดยมนุษย์ (BENCHMARK_SPEC §7) | **≥ 70% "ยอมรับได้" หรือ "ดีเยี่ยม"** | ตัวอย่างผลลัพธ์แบบแบ่งชั้น (≥30 รายการครอบคลุมระดับความยาก 2–5) ถูกตรวจสอบโดยผู้พูดภาษา CRK สองภาษา ≥2 คน อย่างน้อย 70% ของรายการที่ตรวจสอบต้องได้รับการให้คะแนน "ยอมรับได้" หรือ "ดีเยี่ยม" |
| 5 | **การประเมินมาตรฐานทองคำ** | การรันในแซนด์บ็อกซ์ (BENCHMARK_SPEC §8.2) | **จำเป็น** | ตัวชี้วัดอัตโนมัติทั้งหมดต้องคำนวณเทียบกับส่วน `gold_standard` ของคลังข้อมูล โดยดำเนินการโดยองค์กรกำกับดูแลในสภาพแวดล้อมแซนด์บ็อกซ์ คะแนนจากชุดพัฒนาไม่นับ |
| 6 | **การทำซ้ำได้** | การจับคู่ลายนิ้วมือ (BENCHMARK_SPEC §3.8) | **±2%** | องค์กรกำกับดูแลต้องสามารถรันวิธีการซ้ำและได้คะแนนภายใน ±2% ของ run card ที่ส่งมา |

> **ทำไมต้อง 99%+ FST?** ปัญหาหลักในการแปลด้วยเครื่องสำหรับภาษา polysynthetic คือการสร้างข้อมูลเท็จ — LLMs สร้างสตริงที่*ดูเหมือน*ภาษาเป้าหมายแต่ไม่ถูกต้องทางสัณฐานวิทยา วิธีการที่สร้างผลลัพธ์ถูกต้อง 95% ยังคงมีคำที่สร้างขึ้นเท็จ 5% — เสียงรบกวนที่ยอมรับไม่ได้สำหรับการใช้งานจริง เกณฑ์ 99%+ ต้องการการสร้างข้อมูลเท็จใกล้ศูนย์ในขณะที่อนุญาตสำหรับกรณีขอบที่หายาก (คำนามเฉพาะที่ FST ไม่รู้จัก, คำใหม่ที่ถูกต้อง) หากวิธีการไม่สามารถบรรลุการยอมรับ FST 99%+ แสดงว่ายังไม่ได้แก้ปัญหา
>
> **ทำไมต้อง 0.80 composite?** ค่านี้อยู่ระหว่าง Deployable (0.70) และ Fluent (0.85) วิธีการที่ได้ 0.80 พร้อม FST 99%+ สร้างผลลัพธ์ที่แทบทุกคำเป็นคำ Cree จริง *และ* คุณภาพการแปลโดยรวมสูงในทุกมิติ ด่านตรวจสอบโดยชุมชน (เงื่อนไข #4) ทำให้มั่นใจว่านี่ไม่ใช่แค่การเล่นกับตัวชี้วัด — ผู้พูดภาษาต้องยืนยันว่าผลลัพธ์ใช้งานได้จริง

#### ความหมายของเกณฑ์นี้ในทางปฏิบัติ

ที่ composite ≥ 0.80 พร้อม FST ≥ 0.99 และ chrF++ ≥ 55 ผู้พูดสองภาษาจะเห็นโดยทั่วไป:

- **แทบทุก**คำในผลลัพธ์เป็นคำ Cree จริง (FST ตรวจสอบ 99%+ — รูปแบบที่สร้างขึ้นเท็จใกล้ศูนย์)
- หมวดหมู่ไวยากรณ์หลัก (บุคคล, จำนวน, กาล) ถูกต้องในรายการส่วนใหญ่
- ลำดับคำเป็นธรรมชาติโดยทั่วไป
- ความหมายได้รับการรักษาไว้อย่างน่าเชื่อถือ
- ข้อผิดพลาดที่เหลืออยู่เป็นข้อผิดพลาดในภาษาจริง (การผันคำผิด, การใช้ obviation ผิด, ความไม่ตรงกันของ animacy) — ไม่ใช่คำที่สร้างขึ้น
- ผู้พูดที่คล่องแคล่วสามารถใช้ผลลัพธ์เป็นร่างคุณภาพสูงและแก้ไขได้เร็วกว่าการแปลจากศูนย์อย่างมีนัยสำคัญ

นี่คือระบบที่**ไม่บิดเบือนภาษา** อาจไม่สมบูรณ์แบบ แต่ทุกคำที่สร้างขึ้นเป็นคำจริง นั่นคือเกณฑ์ขั้นต่ำสำหรับการแปลด้วยเครื่องที่เคารพภาษา polysynthetic

## 3. กระบวนการเรียกร้องรางวัล

### 3.1 การส่งผลงาน

1. นักพัฒนาส่งวิธีการที่สมบูรณ์และรันได้ให้กับองค์กรกำกับดูแล:
   - ซอร์สโค้ดทั้งหมด
   - การพึ่งพาทั้งหมด (ข้อมูลการฝึก, พจนานุกรม, การตั้งค่า FST, prompts)
   - คำแนะนำการติดตั้งและการรัน
   - README ที่อธิบายแนวทางของวิธีการ
   - run card จากชุดพัฒนาที่แสดงคะแนนโดยประมาณ (สำหรับการคัดกรองเบื้องต้น)

2. นักพัฒนาลงนามในเงื่อนไขการมีส่วนร่วม รวมถึง:
   - ข้อกำหนดการโอนกรรมสิทธิ์ (BENCHMARK_SPEC §8.3)
   - การประกาศว่าไม่ได้ฝึกบนข้อมูลประเมินผล
   - ความมุ่งมั่นด้านการทำซ้ำได้

### 3.2 การประเมินผล

1. องค์กรกำกับดูแลติดตั้งและรันวิธีการในชุดทดสอบแบบแซนด์บ็อกซ์เทียบกับคลังข้อมูล `gold_standard`
2. คำนวณตัวชี้วัดอัตโนมัติ (composite, FST, chrF++ ฯลฯ)
3. หากตรงตามเกณฑ์อัตโนมัติ (เงื่อนไข 1–3) องค์กรกำกับดูแลดำเนินการตรวจสอบโดยชุมชน
4. หากไม่ตรงตามเกณฑ์อัตโนมัติ นักพัฒนาจะได้รับคะแนนและข้อเสนอแนะ ไม่มีการตรวจสอบโดยชุมชน

### 3.3 การตรวจสอบโดยชุมชน

1. ตัวอย่างผลลัพธ์แบบแบ่งชั้น (≥30 รายการ ครอบคลุมระดับความยาก 2–5) ถูกนำเสนอต่อผู้พูดสองภาษา
2. ผู้ตรวจสอบอิสระอย่างน้อย 2 คนให้คะแนนแต่ละรายการ
3. สเกลการให้คะแนน: **ปฏิเสธ** / **เข้าใจใจความ** / **ยอมรับได้** / **ดีเยี่ยม**
4. หาก ≥70% ของรายการได้รับ "ยอมรับได้" หรือ "ดีเยี่ยม" จากผู้ตรวจสอบทั้งสองคน การตรวจสอบโดยชุมชนผ่าน

### 3.4 การจ่ายเงิน

1. ตรงตามเงื่อนไขทั้ง 6 ข้อ
2. องค์กรกำกับดูแลยืนยันผลลัพธ์
3. รางวัลจ่ายภายใน 30 วันหลังการยืนยัน
4. กรรมสิทธิ์วิธีการโอนตาม BENCHMARK_SPEC §8.3
5. ผลลัพธ์ถูกเผยแพร่บนลีดเดอร์บอร์ดพร้อมระดับการตรวจสอบ "Community Validated"

### 3.5 การส่งผลงานหลายครั้ง

- นักพัฒนา/ทีมเดียวกันสามารถส่งผลงานได้หลายครั้ง
- แต่ละการส่งผลงานได้รับการประเมินอย่างอิสระ
- หากวิธีการได้รับการปรับปรุงและส่งใหม่ จะนับเฉพาะ run card ล่าสุด
- รางวัลมอบให้กับวิธีการ**แรก**ที่ผ่านเกณฑ์ทั้งหมด — ไม่มีการแบ่ง

### 3.6 การส่งผลงานเป็นทีม

- ทีมและคู่ผู้อาวุโส-เยาวชนมีสิทธิ์เข้าร่วม
- การแบ่งเงินรางวัลภายในทีมเป็นความรับผิดชอบของทีม
- สมาชิกทีมทุกคนต้องลงนามในเงื่อนไขการมีส่วนร่วม
- การระบุที่มาบนลีดเดอร์บอร์ดแสดงรายชื่อสมาชิกทีมทั้งหมด

## 4. กองทุนรางวัลในอนาคต {#4-future-prize-pools}

Founder's Prize คือจุดเริ่มต้น กองทุนรางวัลเพิ่มเติมได้รับการสนับสนุนจากผู้สนับสนุน กองทุนรางวัลใหม่แต่ละกองทุนถูกบันทึกเป็นหัวข้อย่อยใหม่ของ §2 พร้อมด้วย:

- จำนวนเงินรางวัลและสกุลเงิน
- คู่ภาษา
- การระบุที่มาของผู้สนับสนุน
- เงื่อนไขเกณฑ์ (ซึ่งอาจแตกต่างจาก Founder's Prize)
- วันหมดอายุ (ถ้ามี)
- เงื่อนไขพิเศษใดๆ

### 4.1 เทมเพลตรางวัลผู้สนับสนุน

ผู้สนับสนุนสามารถระดมทุนกองทุนรางวัลในจำนวนใดก็ได้ ระดับที่แนะนำ:

| ระดับ | จำนวนเงิน | เกณฑ์ที่แนะนำ |
|------|--------|---------------------|
| **Seed** | $5,000–$15,000 | Deployable (composite ≥ 0.70) + การตรวจสอบโดยชุมชน |
| **Breakthrough** | $25,000–$50,000 | Fluent (composite ≥ 0.85) + การตรวจสอบโดยชุมชน |
| **Grand Prize** | $100,000+ | Fluent + ครอบคลุมหลาย register + การรวมการใช้งาน |

ผู้สนับสนุนยังสามารถระดมทุนสำหรับ:
- **รางวัลการปรับปรุง** — การจ่ายเงินคงที่สำหรับการปรับปรุง chrF++ ทุก 5 คะแนนเหนือค่าที่ดีที่สุดในปัจจุบัน
- **รางวัล register** — รางวัลแยกสำหรับ register เฉพาะ (ทางการ, พิธีกรรม, การศึกษา)
- **รางวัลความเร็ว** — คะแนนที่ปรับตามต้นทุนดีที่สุด (SCORING_SPEC §6.3)

### 4.2 ที่เก็บเงินรางวัล

เงินรางวัล**ถือครองโดยผู้สนับสนุน**: อยู่กับองค์กรผู้สนับสนุน หรือกับกองทุนชุมชนที่ผู้สนับสนุนกำหนด — **ไม่ใช่กับ Champollion** ซึ่งประสานงานการวัดผลและไม่แตะต้องเงิน รางวัลที่น่าเชื่อถือต้องเผยแพร่ก่อนเปิดรับ: **ใครถือครองเงิน** ภายใต้การจัดการแบบใด (บัญชีองค์กร, กองทุน, หรือ escrow ของบุคคลที่สามตามที่ผู้สนับสนุนเลือก) และเกณฑ์การมอบรางวัล — เพื่อให้การผ่านเกณฑ์ตรวจสอบได้จากคะแนนที่เผยแพร่บวกกับคำตัดสินการตรวจสอบโดยผู้พูดภาษาของชุมชน และการผิดนัดชำระจะมองเห็นได้สาธารณะ ยังไม่มีเงินรางวัลถูกถือครองที่ใดในปัจจุบัน หากรางวัลหมดอายุโดยไม่มีผู้เรียกร้อง เงินยังคงอยู่ที่เดิม — กับผู้สนับสนุน — เพื่อนำไปใช้ใหม่หรือถอนออกตามดุลยพินิจของผู้สนับสนุน กลไกบริการตนเอง รวมถึงความเสี่ยงการผิดนัดของผู้สนับสนุนและมาตรการบรรเทา มีเอกสารอยู่ใน [จัดการแข่งขันแบบอธิปไตย](/docs/network/sovereignty/run-a-sovereign-contest) และ [เทมเพลตข้อกำหนด](/docs/network/sovereignty/terms-templates)

## 5. การตัดสิทธิ์

การส่งผลงานถูกตัดสิทธิ์หาก:

1. **ฝึกบนข้อมูลประเมินผล** วิธีการถูกเปิดเผยต่อรายการคลังข้อมูล `gold_standard` หรือ `held_out` (ป้องกันทางสถาปัตยกรรมโดยการรันในแซนด์บ็อกซ์ — แต่หากพบหลักฐานการปนเปื้อน ผลลัพธ์จะถูกยกเลิก)
2. **ทำซ้ำไม่ได้** องค์กรกำกับดูแลไม่สามารถทำซ้ำคะแนนภายใน ±2%
3. **การพึ่งพาที่ไม่ได้ประกาศหรือไม่มีสิทธิ์** วิธีการต้องการการเข้าถึงบริการภายนอกในขณะรันนอกเหนือจากที่ manifest การพึ่งพาประกาศ หรือประเภทการพึ่งพาที่แท้จริงคือ A2 หรือ X (§1.6) การอนุมาน LLM ประเภท A1 ที่ประกาศแล้วซึ่งส่งผ่าน evaluation gateway ได้รับอนุญาต; การพึ่งพาเครือข่ายในขณะรันอื่นใด — และการพึ่งพาที่ไม่ได้ประกาศในประเภทใดก็ตาม — ถือเป็นเหตุตัดสิทธิ์
4. **ไม่ได้ลงนามในเงื่อนไขการมีส่วนร่วม** สมาชิกทีมทุกคนต้องยินยอมในการโอนกรรมสิทธิ์
5. **ตรวจพบการโกง** ผลลัพธ์ถูกปรับให้เหมาะสมสำหรับตัวชี้วัดมากกว่าคุณภาพการแปล (ตรวจพบโดยการตรวจสอบชุมชนและ/หรือการตรวจสอบการโกงตาม BENCHMARK_SPEC §9.3)

## 7. การซิงโครไนซ์โค้ด–ข้อกำหนด

### 7.1 แหล่งข้อมูลหลัก

เอกสารนี้ (`cli/website/docs/network/specifications/prize-spec.md`) เป็นแหล่งข้อมูลหลักสำหรับ:
- คำจำกัดความกองทุนรางวัล (§2)
- เงื่อนไขเกณฑ์ (§2.x)
- กระบวนการเรียกร้อง (§3)
- กฎการตัดสิทธิ์ (§5)

### 7.2 ข้อกำหนดการนำไปใช้งาน

เมื่อกองทุนรางวัลถูกเปิดใช้งาน:
1. UI ลีดเดอร์บอร์ดต้องแสดงรางวัลที่เปิดรับและเงื่อนไขเกณฑ์
2. run card ที่ตรงตามเกณฑ์อัตโนมัติ (เงื่อนไข 1–3) ต้องถูกตั้งค่าสถานะสำหรับการตรวจสอบชุมชน
3. ฟิลด์ `quality_tier` ใน schema ของ run card บันทึกระดับแล้ว ("deployable", "fluent")
4. ไม่จำเป็นต้องเปลี่ยนแปลงโค้ดใหม่ใน harness — ข้อกำหนดรางวัลเป็นชั้นนโยบายที่อยู่บนการให้คะแนนที่มีอยู่

---

*โครงสร้างรางวัลต้องเข้ากันได้กับเงื่อนไขการโอนกรรมสิทธิ์ ผู้ชนะสามารถเรียกร้องรางวัลได้ แต่วิธีการจะกลายเป็นทรัพย์สินขององค์กรกำกับดูแลหากบรรลุระดับ Deployable นี่คือการออกแบบโดยเจตนา — เงินรางวัลสนับสนุนการสร้างเทคโนโลยีที่เป็นของชุมชนภาษา*
