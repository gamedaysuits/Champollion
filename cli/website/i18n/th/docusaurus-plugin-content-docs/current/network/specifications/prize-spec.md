# ข้อกำหนดรางวัล

รางวัลคือส่วนของสิ่งจูงใจในข้อตกลงแบบ eval-first (ประเมินก่อนเสมอ) ชุมชนหรือกลุ่มวิจัยจะรวบรวมและดูแลชุดประเมินขนาดเล็กที่ถูกปิดผนึกไว้ — ไม่กี่ร้อยคู่ประโยค ซึ่งทุกคู่ผ่านการตรวจสอบแล้ว ([การเป็นพันธมิตรด้านคลังข้อมูล](/docs/network/specifications/corpus-partnership) คือเวิร์กโฟลว์ดังกล่าว) ผู้สนับสนุนจะตั้งรางวัลสำหรับคะแนนเป้าหมายในชุดประเมินนั้น นับจากช่วงเวลานั้น ภาษานี้จะกลายเป็นความท้าทายแบบเปิด: ผู้พัฒนาวิธีการใดๆ ในโลกสามารถมุ่งเป้ามาที่ความท้าทายนี้ได้ ตารางผู้นำจะวัดผลความพยายามทุกครั้งในที่สาธารณะ และเกณฑ์มาตรฐานจะถูกกำหนดโดยเฉลยคำตอบของชุมชนเอง แทนที่จะเป็นใครก็ตามที่ส่งเสียงดังที่สุด เอกสารนี้ระบุวิธีที่รางวัลดังกล่าวทำงาน — เงื่อนไขเกณฑ์คะแนน กระบวนการขอรับรางวัล คลาสของดีเพนเดนซี และกฎเกณฑ์ — เพื่อให้เกณฑ์มีความชัดเจนและไม่ขึ้นอยู่กับวิธีการใดวิธีการหนึ่งเมื่อมีการเปิดรับ

เงินรางวัลได้รับการ**สนับสนุนจากผู้สนับสนุนและถือครองโดยผู้สนับสนุน**: เงินจะอยู่ที่องค์กรผู้สนับสนุน หรืออยู่กับกองทุนทรัสต์ของชุมชนที่ผู้สนับสนุนกำหนด — **Champollion ไม่เคยถือครอง อายัด หรือโอนส่งเงินรางวัล** ชุมชนหรือองค์กรใดๆ สามารถจัดการแข่งขันได้เองตามแนวทางบริการตนเองใน [จัดการแข่งขันแบบอธิปไตย](/docs/network/sovereignty/run-a-sovereign-contest) โดยถือครองทั้งคลังข้อมูลและเงินของตนเอง

> **สถานะ: ข้อเสนอ (PROPOSED) — ยังไม่มีการเปิดรับรางวัล และยังไม่มีสิ่งใดที่นี่สามารถขอรับรางวัลได้**
> สิ่งที่เป็นประตูกั้นการ*เปิด*รางวัลคือฝั่งการวัดผล: คลังข้อมูลมาตรฐานระดับทองคำที่ได้รับความยินยอมจากชุมชน และประตูกั้นการตรวจสอบโดยผู้พูดภาษา
> ซึ่งทั้งสองอย่างยังไม่มีในขณะนี้ แต่แซนด์บ็อกซ์การประเมินแบบแยกส่วนจากเครือข่าย (air-gapped) มีให้ใช้งานแล้ว — ดูที่ [ข้อกำหนดเกณฑ์มาตรฐาน §8.6](/docs/network/specifications/benchmark#86-dependency-classes-and-the-sandbox-network-policy)
> ยังไม่มีคะแนนใดบนไซต์นี้ผ่านเกณฑ์รางวัล ดูที่ [ข้อจำกัดตามจริง](/docs/network/honest-limitations) ข้อมูลอ้างอิงเมตริก: [ข้อกำหนดการให้คะแนน](/docs/network/specifications/scoring); โปรโตคอล: [ข้อกำหนดเกณฑ์มาตรฐาน](/docs/network/specifications/benchmark)

> **เลเยอร์สัญญา (Promise layer) ใช้งานได้แล้ว** การระงับการแก้ไข (freeze) ซึ่งทำให้ข้อกำหนดรางวัลที่ประกาศไว้ไม่สามารถแก้ไขได้เมื่อมีผลงานส่งเข้ามาแล้ว และผลลัพธ์ที่ระงับไว้ (`hidden_until_close`) มีการบังคับใช้ในฐานข้อมูลบนเอนด์พอยต์ที่โฮสต์บนเครือข่ายตั้งแต่วันที่ 2026-09-07 โฮสต์แบบรวมศูนย์ (federated host) จะได้รับกฎเดียวกันโดยการปรับใช้การไมเกรชันที่มาพร้อมกับ harness เมื่อเทียบกับเอนด์พอยต์รุ่นเก่า harness จะถอยกลับไปใช้ชุดข้อมูลพื้นฐานและแจ้งให้ทราบอย่างตรงไปตรงมาแทนที่จะแสร้งทำเป็นใช้ได้ กฎการส่งออกเฉพาะข้อมูลสรุป (aggregates-only egress) ใน §3.2 ได้รับการบังคับใช้ทุกที่เสมอมา

## ต้องการช่วยนำภาษาเข้าสู่เครือข่ายหรือไม่?

คุณไม่จำเป็นต้องรอรางวัล สิ่งที่คุณสามารถทำได้วันนี้เพื่อสร้างผลกระทบสูงสุด:

- **สนับสนุนรางวัลความสำเร็จด้าน MT** ระดมทุนสำหรับเกณฑ์เฉพาะ — ตัวอย่างเช่น วิธีการแปล English → Plains Cree ที่เชื่อถือได้ Champollion ประสานงานการวัดผล; เงินอยู่กับ**คุณ** (องค์กรของคุณ หรือกองทุนชุมชนที่คุณกำหนด) และมอบรางวัลตามเงื่อนไขของชุมชน (ดู
  [อธิปไตยข้อมูล](/docs/network/sovereignty/data-sovereignty)
  และ [รูปแบบเศรษฐกิจ](/docs/network/sovereignty/economic-model)) เส้นทางบริการตนเองแบบครบวงจรมีเอกสารอยู่ใน
  [จัดการแข่งขันแบบอธิปไตย](/docs/network/sovereignty/run-a-sovereign-contest); การนำคู่ภาษาใหม่เข้ามาเริ่มต้นด้วย
  [ความร่วมมือด้านคลังข้อมูล](/docs/network/specifications/corpus-partnership)
- **ประสานงานการบริจาคทรัพยากรคำนวณ** รวม API credits / tokens เพื่อให้คิวสาธารณะสามารถแมปคู่ภาษาได้มากขึ้น และแสดงให้เห็นว่าการแปลนั้นเชื่อถือได้หรือยังไม่ได้ในส่วนใด
- **สนับสนุนโครงการโอเพนซอร์สที่เราพึ่งพา — *โดยตรง*** Champollion เป็นระบบประสานที่เชื่อมงานโอเพนซอร์สของผู้อื่นเข้าด้วยกัน การสนับสนุน*พวกเขา*คือการสนับสนุนแผนที่นี้ (เราอยากชี้ให้คุณไปหาต้นทางมากกว่าจะรับเครดิตจากงานของพวกเขา):
  - [Tatoeba](https://tatoeba.org) — ประโยคคู่ขนานที่ชุมชนร่วมกันสร้าง
  - [Endangered Languages Catalog (ELCat)](https://www.endangeredlanguages.com) — ข้อมูลระดับความเสี่ยงของภาษา
  - [Glottolog](https://glottolog.org) · [WALS](https://wals.info) · [Grambank](https://grambank.clld.org) · [PHOIBLE](https://phoible.org) — แคตาล็อกภาษาและวิทยาการประเภทภาษา
  - [GiellaLT](https://giellalt.uit.no) / ALTLab — transducer ทางสัณฐานวิทยา (FSTs)
  - [Masakhane](https://www.masakhane.io) — ชุมชน MT สำหรับภาษาแอฟริกัน
  - [OPUS](https://opus.nlpl.eu) — คลังข้อมูลคู่ขนานแบบเปิด

> หากต้องการสนับสนุนรางวัล จัดเตรียมการบริจาคทรัพยากรประมวลผล หรือหารือเกี่ยวกับความร่วมมือ โปรดติดต่อโครงการผ่าน [GitHub](https://github.com/gamedaysuits) ยังไม่มีการแต่งตั้งผู้ดูแลคีย์ของชุมชน และจะไม่มีการระบุชื่อชนชาติหรือองค์กรใดๆ ในฐานะพันธมิตรก่อนที่จะได้รับความยินยอม

## 1. ปรัชญา

> **ข้อตกลงในบรรทัดเดียว: พิชิตภาษา ชนะรางวัล ภายใต้ข้อกำหนดที่โฮสต์ประกาศไว้**
> Champollion ดำเนินการเปรียบเทียบมาตรฐาน ML โดยเจตนา — การแข่งขันคือวิธีที่คู่ภาษาที่ยากจะได้รับการแก้ไข เราขอเชิญชวนนักวิจัย ML และผู้พัฒนาที่มีความสามารถทุกคนสร้างวิธีการที่ดีที่สุดสำหรับคู่ภาษาที่ยากโดยเฉพาะและคว้าเงินรางวัล สิ่งที่จะเกิดขึ้นกับวิธีการดังกล่าวหลังจากนั้นคือทางเลือกที่เผยแพร่โดย**โฮสต์** ไม่ใช่ของเราและไม่ใช่ค่าเริ่มต้น: ชุมชนที่ต้องการให้ส่งมอบวิธีการที่ชนะรางวัลจะระบุไว้ในข้อกำหนด และชุมชนที่ต้องการเพียงแค่วัดผลแล้วลบทิ้งก็จะระบุเช่นนั้นแทน (§1.3) พลังแห่งการแข่งขันนั้นมีอยู่จริง และมันมุ่งตรงไปที่พันธกิจ — การแปลทุกภาษา ภายใต้เงื่อนไขที่คนของภาษานั้นกำหนด — ไม่ใช่การไต่อันดับตารางผู้นำเพื่อผลประโยชน์ส่วนตัว

### 1.1 รางวัลตอบแทนความก้าวหน้า ไม่ใช่การมีส่วนร่วม

เงินรางวัลจะถูกปล่อยออกมาเฉพาะเมื่อวิธีการหนึ่งบรรลุเกณฑ์ความสามารถที่กำหนดไว้อย่างชัดเจน ไม่มีรางวัลสำหรับการมีส่วนร่วม, รางวัลรองชนะเลิศ, หรือการจ่ายเงินปลอบใจ หากไม่มีใครผ่านเกณฑ์ ก็ไม่มีใครได้รับเงิน นี่คือการออกแบบโดยเจตนา — หมายความว่าผู้สนับสนุนจ่ายเงินเฉพาะสำหรับผลลัพธ์ที่ใช้งานได้จริงเท่านั้น

### 1.2 การตรวจสอบโดยชุมชนเป็นสิ่งที่ต้องมี

ตัวชี้วัดอัตโนมัติเป็นเพียงตัวแทน (SCORING_SPEC §1.1) วิธีการหนึ่งอาจได้คะแนนดีใน chrF++ และการยอมรับของ FST ในขณะที่ผลิตผลลัพธ์ที่ผู้พูดภาษาไม่ยอมรับ **ทุกการเรียกร้องรางวัลต้องผ่านการตรวจสอบโดยชุมชน** — ผู้พูดสองภาษาต้องยืนยันว่าผลลัพธ์นั้นใช้งานได้ นี่คือด่านตรวจสอบโดยมนุษย์ (BENCHMARK_SPEC §7)

### 1.3 สิ่งที่จะเกิดขึ้นกับวิธีการที่ชนะได้รับการประกาศไว้ ไม่ได้ทึกทักเอาเอง {#1-3-declared-terms}

มีสิ่งหนึ่งที่ตายตัว เนื่องจากเป็นสิ่งสะท้อนว่าการแข่งขันแบบอธิปไตย*คืออะไร*: ผลงานที่ส่งเข้าประกวดจะถูกส่งมอบให้กับโหนดแบบ air-gapped ของโฮสต์เอง ซึ่งจะรันผลงานกับชุดข้อมูลที่ถูกปิดผนึกไว้บนเครื่องของโฮสต์ สิ่งที่จะเกิดขึ้นกับผลงาน*หลังจากนั้น*คือทางเลือกที่ประกาศโดยโฮสต์ กำหนดขึ้นต่อการแข่งขันแต่ละครั้งและเผยแพร่ควบคู่กัน — และเป็น**หนึ่งทางเลือกจากสามทางเลือก**:

| ข้อกำหนด | ความหมายสำหรับคุณ |
|---|---|
| `pass_to_holders` — *ส่งมอบให้ผู้ถือครอง* | วิธีการจะถูกส่งมอบให้แก่ผู้ถือครองเกณฑ์มาตรฐานอธิปไตย พวกเขาจะให้คะแนนและเก็บรักษาไว้ ไม่ว่าใครจะชนะก็ตาม |
| `retain_ip` — *คงสิทธิ์ในทรัพย์สินทางปัญญา* | คุณยังคงเป็นเจ้าของวิธีการของคุณ โฮสต์จะให้คะแนนและเก็บรักษาสำเนาที่ปิดผนึกไว้สำหรับการตรวจสอบเท่านั้น |
| `release_open` — *เผยแพร่เป็นโอเพนซอร์ส* | คุณยังคงเป็นเจ้าของแต่ต้องเผยแพร่วิธีการภายใต้สัญญาอนุญาตแบบเปิด การเผยแพร่ดังกล่าวเป็นเงื่อนไขในการรับรางวัล |

สิ่งอื่นๆ ทั้งหมดที่ตามมาจากข้อกำหนด — ไม่ว่าจะเป็นการเก็บรักษาอาร์ทิแฟกต์ไว้หรือไม่ การโอนสิทธิ์ใดๆ หรือไม่ โฮสต์สามารถนำไปใช้ทำอะไรได้บ้าง กำหนดการเผยแพร่เมื่อใด — ล้วน**ได้มาโดยอนุมาน**จากตัวเลือกที่โฮสต์เลือก (§2.1 เงื่อนไขที่ 7) ไม่ใช่ช่องที่แยกต่างหากให้โฮสต์ทำเครื่องหมายเลือก โฮสต์เลือกข้อกำหนด รายละเอียดต่างๆ ก็จะเป็นไปตามนั้น

ผลลัพธ์สองประการที่ควรระบุให้ชัดเจน:

- **การแข่งขันที่ไม่มีการประกาศข้อกำหนดรางวัลจะไม่มีรางวัล** นั่นคือค่าเริ่มต้น ไม่ใช่การแข่งขันที่ด้อยกว่า และไม่มีสิ่งใดเกี่ยวกับผลงานที่ถูกถ่ายโอน
- **ไม่มีการบอกเป็นนัยใดๆ** ข้อกำหนดที่ประกาศไว้จะถูกแฮช แสดงแก่ผู้ส่งผลงานด้วยภาษาที่เข้าใจง่าย และได้รับการยอมรับตามแฮชนั้น การยอมรับนี้จะถูกส่งไปพร้อมกับผลงานและครอบคลุมโดยแฮชเนื้อหาของผลงาน และโหนดของโฮสต์จะปฏิเสธผลงานที่ยอมรับสิ่งอื่นใด จากนั้นข้อกำหนดจะถูกระงับการแก้ไขทันทีที่มีการส่งผลงานชิ้นแรกเข้ามา เพื่อไม่ให้มีใครต้องผูกพันกับข้อกำหนดที่พวกเขาไม่สามารถอ่านได้

ในกรณีที่โฮสต์เลือก `pass_to_holders` นักพัฒนายังคงรักษาสิทธิ์ในการระบุแหล่งที่มาและสิทธิ์ในการเผยแพร่ และจุดประสงค์ของการจัดการนี้คือเงินรางวัลจะสนับสนุนเทคโนโลยีที่ชุมชนภาษาสามารถนำไปใช้ได้จริง นั่นคือเหตุผลที่ดีสำหรับโฮสต์ของชุมชนในการเลือกข้อกำหนดดังกล่าว มันคือทางเลือก ไม่ใช่กฎเกณฑ์บังคับ

### 1.4 การป้องกันการโกง

เกณฑ์รางวัลถูกกำหนดเทียบกับ**การประเมินมาตรฐานทองคำ** (ชุดทดสอบลับ, ดำเนินการโดยองค์กรกำกับดูแลในแซนด์บ็อกซ์) นักพัฒนาไม่เคยเห็นข้อมูลทดสอบ นี่ถูกบังคับใช้ทางสถาปัตยกรรม — ไม่ใช่นโยบายที่อาศัยความซื่อสัตย์ ดู BENCHMARK_SPEC §8.2

### 1.5 การอนุญาตสิทธิ์คลังข้อมูล: คลังข้อมูลที่ไม่ใช่เชิงพาณิชย์ไม่อยู่ในเส้นทางรางวัล

คลังข้อมูลบางชุดที่ใช้ในระหว่างการพัฒนาวิธีการมีสัญญาอนุญาตแบบไม่ใช้เพื่อการค้า — ตัวอย่างเช่น คลังข้อมูลตำราเรียนภาษาครีของ EdTeKLA ใช้สัญญาอนุญาต **CC BY-NC-SA ฉบับปรับปรุงของ EdTeKLA** (ขอบเขตด้านอธิปไตย ไม่ใช้เพื่อการค้า โดยตำราเรียนต้นฉบับคือ CC BY-NC-ND 4.0) คลังข้อมูลเหล่านี้มีไว้สำหรับ**ช่องทางการวิจัย/พัฒนาเท่านั้น**:

1. **คลังข้อมูลมาตรฐานทองคำสำหรับรางวัลต้องไม่ฝังเนื้อหาคลังข้อมูลที่มีใบอนุญาต NC** ส่วนทดสอบมาตรฐานทองคำเป็นต้นฉบับที่ชุมชนว่าจ้างสร้าง (ดู Corpus Partnership Strategy) — เขียนโดยมนุษย์สำหรับรางวัล โดยมีสิทธิ์ที่ได้รับการอนุมัติสำหรับการประเมินและการใช้งานเชิงพาณิชย์ตั้งแต่ต้น
2. **วิธีการที่เรียกร้องรางวัลต้องไม่ฝังเนื้อหาคลังข้อมูลที่มีใบอนุญาต NC** (เช่น เป็นข้อมูลการฝึก, ตัวอย่างที่ฝังไว้, หรือตารางค้นหา) วิธีการที่โอนให้ต้องสามารถนำไปใช้งานโดยองค์กรกำกับดูแลได้ภายใต้เงื่อนไขใดก็ได้ที่ตนเลือก — รวมถึงเชิงพาณิชย์ หากชุมชนตัดสินใจเช่นนั้น (BENCHMARK_SPEC §8.3); เนื้อหาที่มีใบอนุญาต NC ภายในจะทำลายเสรีภาพนั้น
3. **นักพัฒนาสามารถใช้คลังข้อมูลที่มีใบอนุญาต NC ได้อย่างอิสระเพื่อพัฒนาและประเมินตนเอง** — นั่นคือจุดประสงค์ของเส้นทางพัฒนา ข้อจำกัดใช้กับสิ่งที่ส่งและสิ่งที่นำไปใช้งาน ไม่ใช่กับวิธีที่นักพัฒนาเรียนรู้

### 1.6 ประเภทการพึ่งพากำหนดสิทธิ์การรับรางวัล

การประเมินรางวัลทั้งหมดเกิดขึ้นในแซนด์บ็อกซ์ (§1.4) และวิธีการที่ชนะรางวัลจะโอนให้กับองค์กรกำกับดูแล (§1.3) ทั้งสองข้อเท้าความจริงเดียวกัน: **ทุกสิ่งที่วิธีการพึ่งพาต้องเป็นสิ่งที่นักพัฒนามีสิทธิ์นำเข้าแซนด์บ็อกซ์และส่งมอบให้ชุมชน** ทุกการส่งผลงานต้องประกาศประเภทการพึ่งพา — กำหนดไว้ใน [ข้อกำหนด Method Interface](/docs/network/specifications/methods#method-validity-and-dependency-classes) — และสิทธิ์การรับรางวัลขึ้นอยู่กับประเภท:

| ประเภทการพึ่งพา | มีสิทธิ์รับรางวัล? | เงื่อนไข |
|------------------|----------------|------------|
| **S** — พึ่งพาตนเอง | ✅ ใช่ | ไม่มีเงื่อนไขนอกจากเงื่อนไขเกณฑ์ใน §2 |
| **O** — เปิดภายนอก (เช่น AGPL FST ที่ mirror ณ เวลาส่งผลงาน) | ✅ ใช่ | Artifacts ถูก pin และ vendor เข้าในการส่งผลงาน; ใบอนุญาตอนุญาตให้โอนให้ชุมชน; เงื่อนไข copyleft ได้รับการรักษาไว้ (ชุมชนได้รับสิทธิ์เดียวกับที่ใบอนุญาตมอบให้ทุกคน) |
| **A1** — การอนุมาน LLM ที่แทนที่ได้ | ⚠️ มีเงื่อนไข | โมเดลถูกประกาศ, pin, และแทนที่ได้ (ต้องรันกับโมเดลน้ำหนักเปิดที่ชุมชนโฮสต์); การประเมินถูกส่งผ่าน sandbox LLM gateway (🔲 วางแผนไว้ — วิธีการ A1 ไม่สามารถสร้างคะแนนมาตรฐานทองคำได้จนกว่า gateway จะพร้อมใช้งาน); การโอนส่งมอบสูตรครบถ้วน (prompts, coaching, code) ไม่ใช่โมเดล |
| **A2** — API ข้อมูล/บริการภายนอกที่แทนที่ไม่ได้ | ❌ ยังไม่ได้ | ไม่มีสิทธิ์จนกว่าผู้ถือสิทธิ์จะให้สิทธิ์การรวมในแซนด์บ็อกซ์และการโอน อนุญาตบนลีดเดอร์บอร์ดเปิดพร้อมป้าย "external dependency" ที่มองเห็นได้ |
| **X** — เนื้อหาที่รวมไว้โดยไม่มีสิทธิ์ | ❌ ไม่มีวันได้ | ไม่รับในทุกเส้นทาง |

ประเภทของวิธีการคือประเภทที่จำกัดที่สุดในบรรดาการพึ่งพาที่ประกาศ การพึ่งพาที่ไม่ได้ประกาศในประเภทใดก็ตามถือเป็นเหตุตัดสิทธิ์ (§5)

#### รายละเอียดเงื่อนไขที่ 7: ข้อกำหนดคือหนึ่งทางเลือกจากสามทางเลือก

การแข่งขันแบบอธิปไตยทุกรายการทำงานในลักษณะเดียวกันในเวลาประมวลผล: คุณส่งมอบวิธีการของคุณ (ค่าน้ำหนักหรือโค้ด) ให้กับโหนดแบบ air-gapped ของโฮสต์ และโหนดจะให้คะแนนวิธีการนั้นบนชุดข้อมูลที่ปิดผนึก นั่นคือความหมายของคำว่า "โฮสต์เป็นผู้วัดผล" และไม่สามารถปรับเปลี่ยนได้

สิ่งที่จะเกิดขึ้น*หลังจาก*นั้นคือทางเลือกของโฮสต์ ซึ่งประกาศแยกตามการแข่งขัน และเป็นหนึ่งในสามตัวเลือก โฮสต์จะเผยแพร่ก่อนเปิดรับผลงาน โดยจะถูก**ระงับการแก้ไข**ทันทีที่มีการส่งผลงานชิ้นแรกเข้ามา ดังนั้นข้อกำหนดที่คุณอ่านจึงเป็นข้อกำหนดที่คุณต้องปฏิบัติตาม

| ข้อกำหนด | ความหมายสำหรับคุณ |
|---|---|
| `pass_to_holders` — *ส่งมอบให้ผู้ถือครอง* | วิธีการจะถูกส่งมอบให้แก่ผู้ถือครองเกณฑ์มาตรฐานอธิปไตย พวกเขาจะให้คะแนนและเก็บรักษาไว้ ไม่ว่าใครจะชนะก็ตาม |
| `retain_ip` — *คงสิทธิ์ในทรัพย์สินทางปัญญา* | คุณยังคงเป็นเจ้าของวิธีการของคุณ โฮสต์จะให้คะแนนและเก็บรักษาสำเนาที่ปิดผนึกไว้สำหรับการตรวจสอบเท่านั้น |
| `release_open` — *เผยแพร่เป็นโอเพนซอร์ส* | คุณยังคงเป็นเจ้าของแต่ต้องเผยแพร่วิธีการภายใต้สัญญาอนุญาตแบบเปิด การเผยแพร่ดังกล่าวเป็นเงื่อนไขในการรับรางวัล |

**รายละเอียดความหมายของแต่ละตัวเลือก** มิติทั้งสี่นี้ — รวมถึงสัญญาอนุญาตที่มาพร้อมกับการเผยแพร่ที่จำเป็น — ล้วน*ได้มาโดยอนุมาน*จากตัวเลือก: โฮสต์จะไม่เขียน `rights` หรือ `host_use` ด้วยตนเอง และไม่มีการแข่งขันใดที่สามารถผสมผสานตัวเลือกเหล่านี้ได้:

| ฟิลด์ | `pass_to_holders` | `retain_ip` | `release_open` |
|---|---|---|---|
| `retention` — อาร์ทิแฟกต์จะยังคงอยู่หลังจากการให้คะแนนหรือไม่? | `retain` | `retain_sealed_audit` | `retain` |
| `rights` — ความเป็นเจ้าของมีการเปลี่ยนมือหรือไม่? | `assignment_to_host` | `participant_retains_all` | `participant_retains_all` |
| `host_use` — โฮสต์สามารถนำไปใช้เพื่ออะไรได้บ้าง? | `any` | `evaluation_only` | `any` (ภายใต้สัญญาอนุญาตแบบเปิดที่คุณเผยแพร่) |
| `release` — **คุณ**ต้องเผยแพร่หรือไม่ และเมื่อใด? | `not_required` | `not_required` | `required_before_prize` |
| `release_license` — ภายใต้สัญญาอนุญาตใดที่คุณเผยแพร่ | — | — | `any_osi` หรือตัวระบุ SPDX ที่ระบุชื่อ |

สองในตัวเลือกเหล่านี้อนุญาตให้โฮสต์จำกัดขอบเขตของหนึ่งฟิลด์ได้ และนั่นคือทั้งหมดที่มี:

- ภายใต้ `retain_ip` โฮสต์อาจตั้งค่า `retention` เป็น `delete_after_scoring` — วิธีการของคุณจะถูกทำลายเมื่อได้รับการให้คะแนนแล้ว
- ภายใต้ `release_open` โฮสต์อาจเลื่อนการเผยแพร่ไปเป็น `required_before_scores` (คุณเผยแพร่ก่อนที่คะแนนของคุณจะได้รับการเผยแพร่) หรือ `required_after_prize` (คุณเผยแพร่หลังจากการจ่ายเงินรางวัล) และอาจระบุชื่อสัญญาอนุญาตแทนที่จะยอมรับสัญญาอนุญาตใดๆ ที่ได้รับการรับรองจาก OSI

`community_terms_url` — ลิงก์ `https://` ไปยังข้อกำหนดเป็นลายลักษณ์อักษรของโฮสต์เอง — อาจแนบมากับตัวเลือกใดก็ได้ในสามตัวเลือกนี้ ในตัวการแข่งขันเอง ตัวเลือกที่เลือกจะถูกบันทึกเป็น `disposition` และนั่นคือค่าเดียวที่ทุกอย่างข้างต้นใช้อ่านข้อมูล

สิ่งอื่นใดจะถูกปฏิเสธเมื่อสร้างการแข่งขัน: ตัวเลือกจะไม่เสนอฟิลด์ที่ไม่ได้จัดเตรียมไว้ และฟิลด์ที่เขียนขึ้นเองในส่วนที่ควรได้มาโดยอนุมานจะถูกปฏิเสธโดยระบุชื่อแทนที่จะยอมรับไปโดยปริยาย

**สิ่งที่ได้รับการตรวจสอบก่อนจ่ายเงินรางวัล** การตรวจสอบยืนยันที่จำเป็นจะเป็นไปตามข้อกำหนด ไม่มีโฮสต์คนใดกำหนดค่าแยกต่างหาก:

- **การส่งมอบ (Handover)** — เสมอ โฮสต์จะถือครองอาร์ทิแฟกต์ที่แท้จริงที่ตนได้ให้คะแนน (ไดเจสต์ของวิธีการที่บันทึกโดยโหนด) รายการนี้ได้รับการวัดผล
- **การเผยแพร่ (Release)** — ภายใต้ `release_open` เมื่อถึงกำหนดการเผยแพร่ก่อนการเปิดเผยคะแนนหรือก่อนการมอบรางวัล โฮสต์จะบันทึก URL การเผยแพร่และ SHA-256 ของอาร์ทิแฟกต์ที่เผยแพร่ บันทึกจะได้รับการตรวจสอบและจะไม่มีการดึงข้อมูลจาก URL ดังนั้นผลลัพธ์ที่ถูกระงับการแก้ไขจะไม่ขึ้นอยู่กับสถานะการออนไลน์ (uptime) ของผู้อื่น การเผยแพร่ที่จำเป็นต้องทำ*หลัง*ได้รับรางวัลถือเป็นภาระผูกพันที่มีผลหลังจากจ่ายเงินรางวัล จึงไม่ใช่หนึ่งในการตรวจสอบเพื่อจ่ายเงิน
- **การโอนสิทธิ์ (Assignment)** — ภายใต้ `pass_to_holders` ซึ่งความเป็นเจ้าของจะถูกเปลี่ยนมือ การโอนสิทธิ์เป็นเอกสารสัญญาที่ลงนามนอกแพลตฟอร์มนี้ โฮสต์จะบันทึกเอกสารดังกล่าวและวันที่ และแพลตฟอร์มจะตรวจสอบยืนยันว่ามีบันทึกอยู่จริง **แพลตฟอร์มจะไม่ตรวจสอบความถูกต้องทางกฎหมาย**

**การแข่งขันที่ไม่มีการประกาศข้อกำหนดรางวัลจะไม่มีรางวัล** ไม่มีการใช้ข้อกำหนดเริ่มต้นและไม่มีการทึกทักเอาเองในนามของผู้ใด การเข้าร่วมการแข่งขันที่มีการประกาศข้อกำหนดหมายถึงการยอมรับข้อกำหนดอย่างชัดเจน โดยใช้แฮชของข้อกำหนด ณ เวลาที่ส่งผลงาน — การยอมรับนี้จะถูกรวมไว้ในบันเดิลของคุณและเป็นส่วนหนึ่งของสิ่งที่โหนดของโฮสต์ตรวจสอบ

> **เหตุใดจึงต้องเป็น FST 99+%?** ปัญหาหลักในการแปลด้วยเครื่องสำหรับภาษาคำติดต่อแบบหลายหน่วยคำคืออาการหลอน (hallucination) — LLM มักสร้างข้อความที่*ดูเหมือน*ภาษาเป้าหมายแต่ไม่ถูกต้องตามหลักสัณฐานวิทยา วิธีการที่สร้างผลลัพธ์ที่ถูกต้อง 95% ยังคงมีคำที่แต่งขึ้นเองถึง 5% — ซึ่งเป็นสัญญาณรบกวนที่ไม่อาจยอมรับได้สำหรับการใช้งานจริง เกณฑ์ 99%+ กำหนดให้อาการหลอนต้องเข้าใกล้ศูนย์ในขณะที่ยังเปิดรับกรณีพิเศษที่พบได้ยาก (คำนามเฉพาะที่ FST ไม่รู้จัก หรือคำสร้างใหม่ที่ถูกต้อง) หากวิธีการใดไม่สามารถบรรลุการยอมรับโดย FST 99%+ ได้ แสดงว่าวิธีการนั้นยังไม่ได้แก้ปัญหานี้
>
> **เหตุใดจึงต้องใช้ chrF++ และ FST ควบคู่กัน และทำไมอย่างใดอย่างหนึ่งจึงไม่เพียงพอ** การยอมรับโดย FST บอกเพียงว่าแต่ละคำมีอยู่จริงในภาษาเท่านั้น ระบบที่ตอบซ้ำประโยคที่ถูกต้องเพียงประโยคเดียวสำหรับทุกอินพุตจะผ่านเกณฑ์นี้ได้อย่างสมบูรณ์ แต่ chrF++ จะเปรียบเทียบแต่ละผลลัพธ์กับชุดอ้างอิง จึงตรวจจับกรณีนี้ได้ ตัวเลขอัตโนมัติทั้งสองนี้ไม่สามารถรับรองคุณภาพได้: ประตูกั้นการตรวจสอบยืนยันโดยชุมชน (เงื่อนไขที่ 4) คือสิ่งที่จะยืนยันว่าผู้พูดภาษานั้นพบว่าผลลัพธ์สามารถนำไปใช้งานได้จริง

#### ความหมายของเกณฑ์นี้ในทางปฏิบัติ

สิ่งที่เงื่อนไขต่างๆ กำหนดร่วมกัน:

- คำผลลัพธ์**แทบทุกคำ**เป็นคำภาษาครีที่มีอยู่จริง (FST ตรวจสอบยืนยันได้ 99%+ — รูปคำที่แต่งขึ้นเองแทบเป็นศูนย์)
- ผลลัพธ์มีความใกล้เคียงกับชุดอ้างอิงบนชุดข้อมูลที่ปิดผนึก (chrF++ ≥ 55)
- ผู้พูดสองภาษา ภายใต้โปรโตคอลของชุมชนเอง ประเมินให้ตัวอย่างแบบแบ่งชั้นอย่างน้อย 70% อยู่ในเกณฑ์ยอมรับได้หรือดีกว่า — ซึ่งเป็นเงื่อนไขเดียวที่สะท้อนถึงคุณภาพอย่างแท้จริง
- ข้อผิดพลาดที่หลงเหลืออยู่เป็นข้อผิดพลาดทางภาษาจริง (การผันรูปผิด การระบุสถานะ obviation ไม่ถูกต้อง ความไม่สอดคล้องของภาวะมีชีวิต/ไม่มีชีวิต (animacy)) — ไม่ใช่คำที่แต่งขึ้นเอง

นี่คือระบบที่**ไม่บิดเบือนภาษา** อาจไม่สมบูรณ์แบบ แต่ทุกคำที่สร้างขึ้นเป็นคำจริง นั่นคือเกณฑ์ขั้นต่ำสำหรับการแปลด้วยเครื่องที่เคารพภาษา polysynthetic

## 3. กระบวนการเรียกร้องรางวัล

### 3.1 การผ่านเกณฑ์เบื้องต้น แล้วจึงส่งผลงาน

1. **ผ่านเกณฑ์เบื้องต้นในที่สาธารณะ** นักพัฒนาให้คะแนนชุดพัฒนา (dev set) ที่เผยแพร่ของการแข่งขันด้วยระบบของตนเองและเก็บใบรับรองผลไว้ (`mt-eval contest qualify`) โดยโครงสร้างแล้วใบรับรองผลนี้เป็นการรายงานด้วยตนเอง — มันคือการอ้างสิทธิ์ และโฮสต์จะตรวจสอบในขั้นตอนที่ 4

2. **ส่งมอบผลงาน** การเข้าร่วมการแข่งขันทำได้โดยการมอบสิ่งที่โหนดของโฮสต์สามารถรันได้ ในช่องทางใดช่องทางหนึ่งจากสองช่องทางนี้:
   - **โมเดล** — ค่าน้ำหนัก safetensors, ตัวตัดคำ (tokenizer) แบบ declarative และการกำหนดค่า (config) โดยไม่มีโค้ดเลย (`mt-eval contest submit-model`) หรือ
   - **วิธีการ** — Dockerfile และ entrypoint ที่รวมดีเพนเดนซีไว้ภายใน (vendored) เพื่อให้สามารถบิลด์และรันได้โดยไม่ต้องใช้เครือข่าย (`mt-eval contest submit-method`)

   การอัปโหลดคำแปลของชุดทดสอบที่เผยแพร่ และการลิงก์คะแนนที่นักพัฒนาเผยแพร่ด้วยตนเองนั้น **ถูกยกเลิกในฐานะเส้นทางการส่งผลงานเข้าแข่งขันเมื่อ 2026-09-06** และคำสั่งดังกล่าวถูกลบออกไป คะแนนที่รายงานด้วยตนเองยังคงอยู่บนตารางผู้นำแบบเปิด ซึ่งเป็นกระดานสาธารณะที่จัดทำดัชนีตามคลังข้อมูลและทิศทางคู่ภาษา — ไม่ใช่การแข่งขัน และไม่ใช่ช่องทางชิงรางวัล

3. **ประกาศบนตัวผลงานเอง:** แทร็ก (`constrained` — เทรนเฉพาะข้อมูลที่โฮสต์อนุญาตเท่านั้น — หรือ `unconstrained`) จำนวนพารามิเตอร์ สัญญาอนุญาตของค่าน้ำหนักและระบุว่าเปิดเป็นสาธารณะหรือไม่ ข้อมูลการเทรนที่การอ้างสิทธิ์แบบ constrained กล่าวถึง ระบุว่านี่เป็นผลงานหลักของทีมหรือผลงานเพื่อการเปรียบเทียบ (contrastive entry) และ — เมื่อการแข่งขันกำหนด — คำอธิบายระบบ นักพัฒนายังต้องส่ง `--agree` สำหรับข้อกำหนดการส่งวิธีการ และเมื่อการแข่งขันมีการประกาศข้อกำหนดรางวัล จะต้องส่ง `--accept-terms <hash>` สำหรับข้อกำหนดเหล่านั้นด้วย

### 3.2 การประเมินผล

1. โหนดของโฮสต์จะทำการ**ตรวจสอบแบบสแตติก**บนบันเดิล โดยปฏิเสธสิ่งใดก็ตามที่ต้องใช้เครือข่าย และปฏิเสธผลงานที่ยอมรับข้อกำหนดรางวัลอื่นนอกเหนือจากที่การแข่งขันนี้ประกาศไว้
2. โหนดจะ**รันตัวคัดเลือกซ้ำด้วยตนเอง**บนสำเนาชุดพัฒนาสาธารณะของโฮสต์เอง โดยใช้ตัวรันช่องทางเดียวกันและตัวให้คะแนนเดียวกัน ใบรับรองผลของนักพัฒนาคือการอ้างสิทธิ์ ส่วนนี่คือการวัดผลจริง หากไม่ผ่านเกณฑ์จะถูกปฏิเสธที่นี่ — ก่อนที่จะมีการขอให้ผู้ดูแลคนใดอนุมัติสิ่งใด และก่อนที่ชุดข้อมูลที่ปิดผนึกจะถูกเปิด — พร้อมระบุสิ่งที่อ้างสิทธิ์ สิ่งที่วัดได้ และเกณฑ์ที่กำหนดไว้
3. **ผู้ดูแลให้อนุมัติ**การรันชุดข้อมูลที่ปิดผนึก (M-of-N ตามโมเดลการอนุญาตของการแข่งขัน) สิทธิ์ที่ได้รับจะเป็นแบบใช้ครั้งเดียว มีการจำกัดเวลา และผูกกับลายนิ้วมือ (bundle hash, corpus, corpus version, node) ที่แน่นอน
4. ผลงานจะรันกับคลังข้อมูลที่ปิดผนึก `gold_standard` ภายในแซนด์บ็อกซ์ที่แยกส่วนจากเครือข่ายบนเครื่องของโฮสต์เอง และระบบจะคำนวณเมตริกอัตโนมัติ (chrF++ พร้อม CI และซิกเนเจอร์ เมตริกมาตรฐานอื่นๆ และการวินิจฉัย เช่น การยอมรับโดย FST) ชุดข้อมูลสงวนที่ปิดผนึกไว้ที่ประกาศไว้และชุดทดสอบของบุคคลที่สามจะทำงานภายในการรันที่ได้รับอนุญาตครั้ง**เดียวกัน**
5. **ส่งออกเฉพาะคะแนนรวมเท่านั้น** — มีการบังคับใช้ในระดับฐานข้อมูล ไม่ใช่แค่ตามธรรมเนียมปฏิบัติ หากการแข่งขันสัญญาว่าจะใช้ `hidden_until_close` ระบบจะระงับการแสดง card ไว้จนกว่าจะมีการปิดการแข่งขันและเผยแพร่
6. หากผ่านเกณฑ์อัตโนมัติ (เงื่อนไขที่ 2–3) โฮสต์จะดำเนินการตรวจทานโดยชุมชนต่อไป หากไม่ผ่าน นักพัฒนาจะได้รับคะแนนของตนและไม่มีการเริ่มการตรวจทานโดยชุมชน

### 3.3 การตรวจสอบโดยชุมชน

1. ตัวอย่างผลลัพธ์แบบแบ่งชั้น (≥30 รายการ ครอบคลุมระดับความยาก 2–5) ถูกนำเสนอต่อผู้พูดสองภาษา
2. ผู้ตรวจสอบอิสระอย่างน้อย 2 คนให้คะแนนแต่ละรายการ
3. สเกลการให้คะแนน: **ปฏิเสธ** / **เข้าใจใจความ** / **ยอมรับได้** / **ดีเยี่ยม**
4. หาก ≥70% ของรายการได้รับ "ยอมรับได้" หรือ "ดีเยี่ยม" จากผู้ตรวจสอบทั้งสองคน การตรวจสอบโดยชุมชนผ่าน

### 3.4 การจ่ายเงิน

ลำดับขั้นตอนได้รับการกำหนดไว้อย่างตายตัว: **ตรวจสอบยืนยันขั้นตอนประตูกั้นที่ประกาศไว้ → ปิดการแข่งขัน → จ่ายเงินรางวัล** ขั้นตอนเหล่านั้นจะเป็นขั้นตอนใดขึ้นอยู่กับข้อกำหนดที่การแข่งขัน*นี้*ประกาศไว้ (§2.1 เงื่อนไขที่ 7) — แต่ไม่ว่าจะเป็นขั้นตอนใด จะต้องได้รับการตรวจสอบยืนยันก่อนปิดการแข่งขัน และจะไม่มีการจ่ายเงินใดๆ จากอันดับที่ยังคงมีการเปลี่ยนแปลง

ผู้จัดสามารถใช้ `close --force` เพื่อข้ามประตูกั้นที่ไม่ผ่านเกณฑ์ได้ จากนั้นการปิดการแข่งขันจะดำเนินการต่อไป และอันดับที่ถูกระงับการแก้ไขจะบันทึกสิทธิ์ในการรับรางวัลของผลงานนั้นตามที่คำนวณได้อย่างแม่นยำ — คือไม่มีสิทธิ์ พร้อมระบุชื่อขั้นตอนที่ไม่ผ่าน การบังคับปิดการแข่งขันคือการปิดการแข่งขัน แต่ไม่ใช่การผ่านประตูกั้น

1. ผ่านเงื่อนไขทั้ง 7 ข้อครบถ้วน
2. **ทุกขั้นตอนของประตูกั้นที่ข้อกำหนดรางวัลที่ประกาศไว้ของการแข่งขันต้องการได้รับการตรวจสอบยืนยันแล้ว** — ต้องมีการส่งมอบอาร์ทิแฟกต์ที่ได้รับการให้คะแนนเสมอ รวมทั้งการบันทึกการเผยแพร่และ/หรือการบันทึกการโอนสิทธิ์เมื่อข้อกำหนดเหล่านั้นระบุไว้
3. การแข่งขันได้รับการ**ปิด** และอันดับถูกระงับการแก้ไข
4. องค์กรกำกับดูแลยืนยันผลลัพธ์เทียบกับอันดับที่ถูกระงับการแก้ไข
5. จ่ายเงินรางวัลภายใน 30 วันนับจากการยืนยัน
6. สิ่งใดก็ตามที่ข้อกำหนดที่ประกาศไว้ระบุเกี่ยวกับความเป็นเจ้าของจะมีผลบังคับใช้ตามที่ข้อกำหนดนั้นระบุ — สำหรับการแข่งขันที่ `rights` เป็น `participant_retains_all` จะไม่มีการถ่ายโอนใดๆ ทั้งสิ้น
7. ผลลัพธ์ได้รับการเผยแพร่บนตารางผู้นำด้วยระดับการตรวจสอบยืนยัน "Community Validated" (ผ่านการตรวจสอบโดยชุมชน)

### 3.5 การส่งผลงานหลายครั้ง

- นักพัฒนา/ทีมเดียวกันสามารถส่งผลงานได้หลายครั้ง
- แต่ละการส่งผลงานได้รับการประเมินอย่างอิสระ
- หากวิธีการได้รับการปรับปรุงและส่งใหม่ จะนับเฉพาะ run card ล่าสุด
- รางวัลมอบให้กับวิธีการ**แรก**ที่ผ่านเกณฑ์ทั้งหมด — ไม่มีการแบ่ง

### 3.6 การส่งผลงานเป็นทีม

- ทีมและคู่ผู้อาวุโส-เยาวชนมีสิทธิ์เข้าร่วม
- การแบ่งเงินรางวัลภายในทีมเป็นความรับผิดชอบของทีม
- สมาชิกทีมทุกคนต้องลงนามในเงื่อนไขการมีส่วนร่วม
- การระบุที่มาบนลีดเดอร์บอร์ดแสดงรายชื่อสมาชิกทีมทั้งหมด

## 4. กองทุนรางวัลในอนาคต {#4-future-prize-pools}

Founder's Prize คือจุดเริ่มต้น กองทุนรางวัลเพิ่มเติมได้รับการสนับสนุนจากผู้สนับสนุน กองทุนรางวัลใหม่แต่ละกองทุนถูกบันทึกเป็นหัวข้อย่อยใหม่ของ §2 พร้อมด้วย:

- จำนวนเงินรางวัลและสกุลเงิน
- คู่ภาษา
- การระบุที่มาของผู้สนับสนุน
- เงื่อนไขเกณฑ์ (ซึ่งอาจแตกต่างจาก Founder's Prize)
- วันหมดอายุ (ถ้ามี)
- เงื่อนไขพิเศษใดๆ

### 4.1 เทมเพลตรางวัลผู้สนับสนุน

ผู้สนับสนุนสามารถระดมทุนกองทุนรางวัลในจำนวนใดก็ได้ ระดับที่แนะนำ:

| ระดับ | จำนวนเงิน | เกณฑ์คะแนนที่แนะนำ |
|------|--------|---------------------|
| **Seed** | $5,000–$15,000 | เกณฑ์ chrF++ บนชุดข้อมูลที่ปิดผนึก ซึ่งเผยแพร่ก่อนเปิดการแข่งขัน + การตรวจสอบยืนยันโดยชุมชน |
| **Breakthrough** | $25,000–$50,000 | เกณฑ์ chrF++ ที่สูงขึ้น + การตรวจสอบยืนยันโดยชุมชน |
| **Grand Prize** | $100,000+ | เงื่อนไขของ Breakthrough + ครอบคลุมระดับภาษาที่หลากหลาย (multi-register) + การบูรณาการเพื่อการนำไปใช้งานจริง (deployment integration) |

เกณฑ์มาตรฐานจะเป็น chrF++ เสมอ (พร้อมซิกเนเจอร์ เพื่อให้สามารถทำซ้ำได้) อาจมีการเพิ่มประตูกั้นเพื่อการวินิจฉัย เช่น การยอมรับโดย FST ในฐานะประตูกั้น คะแนนรวมหรือระดับคุณภาพไม่สามารถนำมาใช้เป็นเกณฑ์ตัดสินรางวัลได้

ผู้สนับสนุนอาจให้ทุนสำหรับ:
- **รางวัลการพัฒนา (Improvement bounties)** — การจ่ายเงินคงที่สำหรับการพัฒนาคะแนน chrF++ เพิ่มขึ้นทุกๆ 5 จุดเมื่อเทียบกับสถิติที่ดีที่สุดในปัจจุบัน
- **รางวัลตามระดับภาษา (Register prizes)** — รางวัลแยกต่างหากสำหรับระดับภาษาเฉพาะ (ทางการ พิธีการ การศึกษา)
- **รางวัลด้านต้นทุน (Cost prizes)** — ต้นทุนต่อผลงานต่ำที่สุดในบรรดาวิธีการที่ผ่านเกณฑ์ chrF++ (รายงานต้นทุนควบคู่ไปกับคะแนน ไม่นำมารวมเข้าด้วยกัน)

### 4.2 ที่เก็บเงินรางวัล

เงินรางวัล**ถือครองโดยผู้สนับสนุน**: อยู่กับองค์กรผู้สนับสนุน หรือกับกองทุนชุมชนที่ผู้สนับสนุนกำหนด — **ไม่ใช่กับ Champollion** ซึ่งประสานงานการวัดผลและไม่แตะต้องเงิน รางวัลที่น่าเชื่อถือต้องเผยแพร่ก่อนเปิดรับ: **ใครถือครองเงิน** ภายใต้การจัดการแบบใด (บัญชีองค์กร, กองทุน, หรือ escrow ของบุคคลที่สามตามที่ผู้สนับสนุนเลือก) และเกณฑ์การมอบรางวัล — เพื่อให้การผ่านเกณฑ์ตรวจสอบได้จากคะแนนที่เผยแพร่บวกกับคำตัดสินการตรวจสอบโดยผู้พูดภาษาของชุมชน และการผิดนัดชำระจะมองเห็นได้สาธารณะ ยังไม่มีเงินรางวัลถูกถือครองที่ใดในปัจจุบัน หากรางวัลหมดอายุโดยไม่มีผู้เรียกร้อง เงินยังคงอยู่ที่เดิม — กับผู้สนับสนุน — เพื่อนำไปใช้ใหม่หรือถอนออกตามดุลยพินิจของผู้สนับสนุน กลไกบริการตนเอง รวมถึงความเสี่ยงการผิดนัดของผู้สนับสนุนและมาตรการบรรเทา มีเอกสารอยู่ใน [จัดการแข่งขันแบบอธิปไตย](/docs/network/sovereignty/run-a-sovereign-contest) และ [เทมเพลตข้อกำหนด](/docs/network/sovereignty/terms-templates)

## 5. การตัดสิทธิ์

การส่งผลงานถูกตัดสิทธิ์หาก:

1. **การเทรนบนข้อมูลการประเมินผล** วิธีการได้รับการเปิดเผยต่อข้อมูลคลังข้อมูล `gold_standard` หรือ `held_out` (ซึ่งในทางสถาปัตยกรรมจะถูกป้องกันไว้โดยการทำงานในแซนด์บ็อกซ์ — แต่หากพบหลักฐานการปนเปื้อน ผลลัพธ์จะถือเป็นโมฆะ)
2. **ไม่สามารถทำซ้ำได้** องค์กรกำกับดูแลไม่สามารถทำซ้ำคะแนนให้อยู่ภายในช่วง ±2% ได้
3. **มีดีเพนเดนซีที่ไม่ได้ประกาศหรือไม่ผ่านเกณฑ์** วิธีการต้องการการเข้าถึงบริการภายนอกในขณะรันไทม์เกินกว่าที่ประกาศไว้ใน dependency manifest หรือคลาสดีเพนเดนซีที่มีผลบังคับใช้คือ A2 หรือ X (§1.6) อนุญาตให้ใช้การอนุมาน LLM คลาส A1 ที่ประกาศไว้ซึ่งส่งผ่าน evaluation gateway ได้ ส่วนการพึ่งพาเครือข่ายภายนอกขณะรันไทม์อื่นๆ — และดีเพนเดนซีใดๆ ที่ไม่ได้ประกาศไว้ไม่ว่าจะอยู่ในคลาสใด — จะถือว่าขาดคุณสมบัติ
4. **ไม่ได้ลงนามในข้อกำหนดการเข้าร่วม** สมาชิกทุกคนในทีมต้องยอมรับข้อกำหนดการส่งวิธีการ และ — เมื่อการแข่งขันมีการประกาศข้อกำหนดรางวัล (§1.3) — ต้องยอมรับข้อกำหนดเหล่านั้นด้วยแฮช
5. **ตรวจพบการเล่นตุกติกกับระบบ (Gaming detected)** ผลลัพธ์ได้รับการปรับแต่งเพื่อหวังผลทางเมตริกมากกว่าคุณภาพการแปลจริง (ตรวจพบโดยการตรวจทานโดยชุมชน และ/หรือการตรวจสอบการเล่นตุกติกตาม BENCHMARK_SPEC §9.3)

## 7. การซิงโครไนซ์โค้ด–ข้อกำหนด

### 7.1 แหล่งข้อมูลหลัก

เอกสารนี้ (`cli/website/docs/network/specifications/prize-spec.md`) เป็นแหล่งข้อมูลหลักสำหรับ:
- คำจำกัดความกองทุนรางวัล (§2)
- เงื่อนไขเกณฑ์ (§2.x)
- กระบวนการเรียกร้อง (§3)
- กฎการตัดสิทธิ์ (§5)

### 7.2 ข้อกำหนดการนำไปใช้งาน

เมื่อกองทุนรางวัลได้รับการเปิดใช้งาน:
1. UI ของตารางผู้นำต้องแสดงรางวัลที่กำลังเปิดอยู่และเงื่อนไขเกณฑ์คะแนนของรางวัลเหล่านั้น
2. Run cards ที่ผ่านเกณฑ์อัตโนมัติ (เงื่อนไขที่ 2–3) จะต้องถูกตั้งค่าสถานะเพื่อรอการตรวจทานโดยชุมชน
3. ไม่มีการใช้ระดับคุณภาพ: ฟิลด์ `quality_tier` จะเป็นค่า null ในทุก run card ใหม่ (scoring standard/1)
4. เลเยอร์**ข้อกำหนด**รางวัลมีให้ใช้งานแล้ว (`contest_prize_terms` — การประกาศ แฮช การยอมรับ และประตูกั้นการจ่ายเงินรางวัล) และตัวการให้คะแนนเองไม่มีการเปลี่ยนแปลง สิ่งที่กองทุนรางวัลใหม่เพิ่มเข้ามาคือนโยบายเกณฑ์คะแนนใน §2 และการแสดงผลบนตารางผู้นำในข้อ 1–2 ข้างต้น

---

*โครงสร้างรางวัลต้องเข้ากันได้กับข้อกำหนดรางวัลที่การแข่งขันเดียวกันประกาศไว้ (§1.3) ข้อกำหนดเหล่านั้นเป็นทางเลือกของโฮสต์ในทุกมิติ — ตั้งแต่ "ให้คะแนน ลบทิ้ง สิทธิ์ทั้งหมดยังคงอยู่กับผู้ส่งผลงาน" ไปจนถึง "คุณส่งมอบ เราให้คะแนนและเก็บรักษาไว้ไม่ว่าผลจะเป็นอย่างไร" — และได้รับการเผยแพร่ แฮช และยอมรับก่อนที่ใครจะเข้าร่วม โฮสต์ของชุมชนที่ต้องการให้วิธีการที่ชนะตกเป็นทรัพย์สินของชุมชนสามารถประกาศเช่นนั้นได้โดยตรง และรางวัลจะทำหน้าที่สนับสนุนเงินทุนในการสร้างเทคโนโลยีที่เป็นของชุมชนภาษานั้น ไม่มีสิ่งใดในที่นี้ที่ทึกทักเอาเองในนามของโฮสต์ใดๆ*
