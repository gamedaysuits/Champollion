# กลยุทธ์การเป็นพันธมิตรด้านคลังข้อมูล: การจัดตั้งคลังข้อมูลประเมินผลผ่านภาควิชาภาษาศาสตร์ในสถาบันการศึกษา

การสร้างคลังข้อมูล *training* สำหรับภาษาที่มีทรัพยากรน้อยต้องใช้คู่ประโยคหลายแสนคู่ — ซึ่งมากเกินกว่าจะตรวจสอบได้ทั้งหมด ทำให้คุณภาพมีความแตกต่างกันในแบบที่ไม่มีใครเห็นจนกว่าโมเดลที่ฝึกสอนด้วยข้อมูลเหล่านั้นจะทำงานล้มเหลว คลังข้อมูล *evaluation* ใช้คู่ประโยคเพียงไม่กี่ร้อยคู่ โดยทุกคู่จะได้รับการตรวจสอบจากผู้ที่รู้ภาษานั้น และคลังข้อมูลนี้จะไม่มีวันล้าสมัย: โมเดลหรือวิธีการใหม่ๆ ที่เกิดขึ้นจะถูกนำมาวัดผลกับคลังข้อมูลนี้ เอกสารนี้คือเวิร์กโฟลว์สำหรับการสร้างสิ่งหลังซึ่งมีต้นทุนถูกกว่าอย่างมาก — ซึ่งเป็นผลลัพธ์เดียวที่ความเชี่ยวชาญของแผนกสามารถเข้าถึงได้ในทุกๆ ประโยค — และสำหรับสิ่งที่จะเกิดขึ้นหลังจากนั้น: เมื่อมีมาตรฐานการประเมินแล้ว [รางวัลที่ประกาศไว้](/docs/network/specifications/prizes) จะเปลี่ยนภาษาของคุณให้กลายเป็นเป้าหมายที่ผู้สร้างวิธีการใดๆ ในโลกสามารถมุ่งเป้ามาได้ และกระดานผู้นำสาธารณะจะวัดผลทุกความพยายาม

> **วัตถุประสงค์** เวิร์กโฟลว์ฉบับสมบูรณ์สำหรับการสร้างคลังข้อมูลประเมินผลการแปลด้วยเครื่องผ่านการเป็นพันธมิตรกับแผนกภาษาศาสตร์: สิ่งที่แผนกต้องส่งมอบ, ลักษณะที่คลังข้อมูลต้องเป็น, วิธีการปิดผนึกด้วยการเข้ารหัส, วิธีการทำงานของการประเมินผลแบบ sandbox, และสิ่งที่แผนกจะได้รับเป็นการตอบแทน นี่คือเอกสารที่คุณสามารถนำไปใช้ในการประชุมกับผู้ที่อาจมาเป็นพันธมิตรทางวิชาการ
>
> **กลุ่มเป้าหมาย** หัวหน้าแผนก, นักวิจัยหลัก (PI), ผู้ประสานงานการวิจัย, และผู้อำนวยการโครงการภาษาพื้นเมืองในมหาวิทยาลัยที่มีการจัดทำเอกสารทางภาษาหรือมีโปรแกรม NLP ที่ดำเนินการอยู่
>
> **เอกสารประกอบ:**
> - [Corpus Design Framework](/docs/network/specifications/corpus-design) — ระเบียบวิธีเบื้องหลังคลังข้อมูลการประเมินผลที่ถูกต้องและเชื่อถือได้
> - [Prize Specification](/docs/network/specifications/prizes) — ส่วนของแรงจูงใจ: การประกาศรางวัลสำหรับชุดข้อมูลที่ปิดผนึกของคุณ
> - [Registering Corpora](/docs/network/sovereignty/registering-corpora) — วิธีที่คลังข้อมูลเข้าร่วม Network โดยที่ข้อมูลยังคงอยู่ในการควบคุมของคุณ
> - [Speaker Validation Protocol](/docs/network/specifications/speaker-validation) — การขอให้ผู้พูดสองภาษาช่วย *ให้คะแนน* คำแปลที่มีอยู่ (การประเมินคุณภาพ, การตรวจสอบด้วย linter, การทบทวนด้วย FST)
> - [Benchmark Specification](/docs/network/specifications/benchmark) — ข้อกำหนดทางเทคนิคฉบับเต็มสำหรับคลังข้อมูล, run cards, และโปรโตคอลการประเมินผล
> - [Data Sovereignty](/docs/network/sovereignty/data-sovereignty) — หลักการอธิปไตยทางข้อมูล, CARE, และเหตุผลที่การโอนกรรมสิทธิ์มีความสำคัญ

## 1. สิ่งที่การเป็นพันธมิตรนี้ผลิตขึ้น

**คลังข้อมูลที่ปิดผนึกแล้ว**: ชุดคู่ข้อความคู่ขนานที่คัดสรรแล้ว (ภาษาต้นทาง → ภาษาปลายทาง) ซึ่งกลายเป็นมาตรฐานความจริงสำหรับการวัดคุณภาพการแปลด้วยเครื่อง วิธีการต่าง ๆ จะถูกทดสอบกับคลังข้อมูลนี้ในแซนด์บ็อกซ์ — นักพัฒนาจะไม่เห็นข้อมูลทดสอบเลย

การเป็นพันธมิตรนี้ผลิตสิ่งส่งมอบสามรายการ:

| สิ่งส่งมอบ | คืออะไร | ใครควบคุม |
|----------|-----------|-----------------|
| **คลังข้อมูลพัฒนา** | คู่ข้อความคู่ขนานสาธารณะ 100–200+ คู่สำหรับการพัฒนาวิธีการ | เผยแพร่แบบเปิด (CC BY-NC-SA 4.0 หรือเทียบเท่า) |
| **ชุดทดสอบมาตรฐานทอง** | คู่ข้อความคู่ขนานลับ 50–150 คู่สำหรับการประเมินผลอย่างเป็นทางการ | องค์กรกำกับดูแลชุมชน (ปิดผนึกด้วยการเข้ารหัสลับ) |
| **ชุดทดสอบวินิจฉัย** | คู่ข้อความเปรียบเทียบเฉพาะเจาะจง 10–50 คู่ที่ทดสอบปรากฏการณ์ทางภาษาศาสตร์เฉพาะ | เผยแพร่แบบเปิด |

รวมกันแล้วจะได้คู่ประโยค 160–400 คู่ — ซึ่งเป็นคลังข้อมูลที่กลุ่มวิจัยหนึ่งกลุ่มสามารถคัดสรรให้ได้มาตรฐานระดับมืออาชีพได้จริง เมื่อเทียบกับจำนวนหลายแสนคู่ที่คลังข้อมูล training ต้องการ คลังข้อมูล development ช่วยให้ทุกคนสามารถสร้างวิธีการแปลได้ ชุดข้อมูล gold-standard ช่วยให้มั่นใจได้ว่าวิธีการเหล่านั้นจะได้รับการทดสอบอย่างตรงไปตรงมา ชุดข้อมูล diagnostic จะช่วยตรวจจับรูปแบบความล้มเหลวที่เฉพาะเจาะจง (เช่น "ระบบนี้สามารถจัดการกับ obviation ได้หรือไม่?")

## 2. สิ่งที่ภาควิชาต้องดำเนินการ

### ระยะที่ 1: การออกแบบคลังข้อมูล (2–4 สัปดาห์ เวลานักวิจัย)

**ผู้นำ:** นักวิจัยหลักหรือนักวิจัยหลังปริญญาเอกที่มีความเชี่ยวชาญในภาษาเป้าหมาย

1. **เลือกโดเมนของวัสดุต้นทาง** เลือก 4–6 โดเมนในโลกจริงที่ชุมชนภาษาต้องการการแปลจริง ๆ อนุกรมวิธานของเรารองรับ 16 โดเมน (ดู Benchmark Spec §2.7):

   | ลำดับความสำคัญ | โดเมน | เหตุผล |
   |----------|--------|-----|
   | 🔴 สูง | `edu` — การศึกษา | ตำราเรียน หลักสูตร — ความต้องการของชุมชนโดยตรง |
   | 🔴 สูง | `gov` — ราชการ | เอกสารสภาชนเผ่า นโยบาย — ความต้องการในชีวิตประจำวัน |
   | 🔴 สูง | `medical` — สุขภาพ | แบบฟอร์มรับผู้ป่วยคลินิก ข้อมูลสุขภาพ — สำคัญต่อความปลอดภัย |
   | 🟡 ปานกลาง | `conv` — การสนทนา | การพูดในชีวิตประจำวัน — สร้างพื้นฐานความคล่องแคล่ว |
   | 🟡 ปานกลาง | `legal` — กฎหมาย | เอกสารสิทธิ์ สนธิสัญญา — ความสำคัญต่อชุมชน |
   | 🟢 ต่ำกว่า | `literary` — วรรณกรรม/วัฒนธรรม | เรื่องราว ประวัติศาสตร์บอกเล่า — การอนุรักษ์วัฒนธรรม |

2. **ร่างเอกสารออกแบบคลังข้อมูล** โดยระบุ:
   - ขนาดเป้าหมายต่อส่วน (development, gold_standard, diagnostic)
   - การกระจายระดับความยาก (ดู §3.3 ด้านล่าง)
   - การครอบคลุมรีจิสเตอร์และโดเมน
   - เกณฑ์การเลือกประโยคต้นทาง (ไม่มีข้อความสังเคราะห์ ไม่ใช้พระคัมภีร์เพียงอย่างเดียว)
   - แผนการสรรหาผู้พูด

3. **ส่งการออกแบบให้เราตรวจสอบ** เราจะตรวจสอบกับสคีมาคลังข้อมูล (Benchmark Spec §2) และส่งคืนข้อเสนอแนะภายใน 1 สัปดาห์

### ระยะที่ 2: การสร้างประโยคต้นทาง (4–8 สัปดาห์ เวลาผู้พูด)

**ผู้นำ:** ผู้ประสานงานวิจัยที่ทำงานร่วมกับผู้พูดสองภาษา

1. **สร้างหรือเลือกประโยคต้นทาง** ครอบคลุมโดเมนและระดับความยากที่วางแผนไว้ แหล่งที่มาอาจเป็น:
   - วัสดุสองภาษาที่ตีพิมพ์แล้ว (ตำราเรียน เอกสารราชการ)
   - ประโยคที่สร้างขึ้นใหม่เพื่อครอบคลุมปรากฏการณ์ทางภาษาศาสตร์เฉพาะ
   - ดัดแปลงจากเอกสารในโลกจริง (วาระการประชุมสภาชนเผ่า แบบฟอร์มคลินิก วัสดุการศึกษา)

2. **ประโยคต้นทางแต่ละประโยคต้องมี:**
   - แท็กโดเมน (จากอนุกรมวิธาน 16 รหัส)
   - แท็กรีจิสเตอร์ (การสนทนา ทางการ เทคนิค พิธีกรรม การศึกษา)
   - แท็กบริบท (การทักทาย การประกาศ คำถาม คำสั่ง การเล่าเรื่อง ป้ายกำกับ ข้อผิดพลาด)
   - ระดับความยากโดยประมาณ (1–5 ดู §3.3)
   - แท็กที่มา (ตำราเรียน elicited corpus gold_standard)

3. **แปลประโยคต้นทางแต่ละประโยค** เป็นภาษาเป้าหมาย โดยผู้พูดสองภาษาเป็นผู้ดำเนินการ การมีการแปลอ้างอิงหลายรายการต่อรายการมีคุณค่าแต่ไม่จำเป็น

4. **เพิ่มการวิเคราะห์ทางสัณฐานวิทยาสำหรับการแปลอ้างอิงแต่ละรายการ (ไม่บังคับ):**
   - การอธิบายแบบ interlinear (การแยกส่วนทีละหน่วยคำ)
   - สตริงแท็ก FST (หากมี FST สำหรับภาษานั้น)
   - หมายเหตุของผู้แปลเกี่ยวกับรูปแบบภาษาถิ่น ความกำกวม หรือบริบททางวัฒนธรรม

### ระยะที่ 3: การประกันคุณภาพ (2–4 สัปดาห์)

**ผู้นำ:** นักภาษาศาสตร์ที่มีความเชี่ยวชาญในภาษาเป้าหมาย

1. **การตรวจสอบข้ามกัน** การแปลแต่ละรายการควรได้รับการตรวจสอบโดยผู้พูดสองภาษาอย่างน้อยหนึ่งคนที่ไม่ได้เป็นผู้แปลต้นฉบับ ผู้ตรวจสอบตรวจสอบ:
   - การแปลถูกต้องหรือไม่?
   - ฟังดูเป็นธรรมชาติหรือไม่?
   - การให้คะแนนความยากถูกต้องหรือไม่?
   - มีรูปแบบที่ยอมรับได้ที่ควรบันทึกไว้หรือไม่?

2. **รันผ่านตัวตรวจสอบสคีมาของเรา** เราจัดเตรียมสคริปต์ที่ตรวจสอบคลังข้อมูลกับสคีมารายการ (Benchmark Spec §2.2) โดยตรวจสอบ:
   - ฟิลด์ที่จำเป็นมีครบหรือไม่
   - รหัสโดเมนถูกต้องหรือไม่
   - ระดับความยากเป็นจำนวนเต็ม 1–5 หรือไม่
   - ไม่มี ID ซ้ำกัน
   - การเข้ารหัสอักขระ (การทำให้เป็นมาตรฐาน UTF-8 NFC)

3. **หาก FST มีอยู่สำหรับภาษานั้น** ให้รันการแปลอ้างอิงผ่าน FST ทุกคำในการอ้างอิงควรถูกต้องตาม FST คำที่ไม่ถูกต้อง (คำยืม คำใหม่ ชื่อเฉพาะ) ควรบันทึกไว้ใน allowlist

### ระยะที่ 4: การแบ่งส่วนและการปิดผนึก (1 สัปดาห์ วิศวกรรมของเรา)

**ผู้นำ:** ทีม Champollion โดยมีภาควิชาตรวจสอบ

1. **การแบ่งแบบ stratified** เราแบ่งคลังข้อมูลออกเป็นส่วนต่าง ๆ โดยใช้การสุ่มตัวอย่างแบบกำหนดได้ (seed ที่บันทึกไว้ สามารถทำซ้ำได้):

   | ส่วน | ขนาดเป้าหมาย | การเข้าถึง |
   |---------|------------|--------|
   | `development` | 60% ของรายการ (ขั้นต่ำ 100) | สาธารณะ |
   | `gold_standard` | 30% ของรายการ (ขั้นต่ำ 50) | ลับ ปิดผนึก |
   | `held_out` | 10% ของรายการ (ขั้นต่ำ 10) | ลับ ปิดผนึก ไม่ใช้จนกว่าจะเปิดใช้งาน |

   การแบ่งจะรักษาการกระจายระดับความยาก (การสุ่มตัวอย่างแบบ stratified) เพื่อให้แต่ละส่วนมีการแทนค่าตามสัดส่วนในทุกระดับ

2. **การปิดผนึกด้วยการเข้ารหัสลับ** ของส่วน gold_standard และ held_out:

   ```
   1. SHA-256 hash of each entry (source + reference + metadata)
   2. SHA-256 hash of the complete segment file
   3. Segment file encrypted with AES-256-GCM
   4. Encryption key split using Shamir Secret Sharing (2-of-3 threshold)
   5. Key shares distributed to:
        - Share 1: Community governance organization
        - Share 2: Academic department partner
        - Share 3: Champollion project (escrow)
   6. Hash manifest published to a public commit (proves the corpus existed
      at a specific time without revealing its contents)
   ```

3. **ส่วน development** จะถูก commit ไปยัง repository สาธารณะและเผยแพร่พร้อมการอนุญาตสิทธิ์ครบถ้วน

4. **ส่วน diagnostic** ก็เป็นสาธารณะเช่นกัน — ทดสอบปรากฏการณ์ทางภาษาศาสตร์เฉพาะ (ดู §3.4)

### ระยะที่ 5: การรวมระบบและการเปิดตัว (1–2 สัปดาห์ วิศวกรรมของเรา)

1. **การกำหนดค่า harness** เราเพิ่มภาษาเข้าสู่ evaluation harness:
   - สร้างหรือตรวจสอบ language card
   - ลงทะเบียนคลังข้อมูลใน dataset registry
   - กำหนดค่าเมตริก LYSS (LYSS-fst หาก FST มีอยู่ LYSS-eq หากมีกฎ linter)
   - เลือก scoring profile เริ่มต้น (Profile A หาก FST มีอยู่ Profile B ในกรณีอื่น)

2. **เกณฑ์มาตรฐานพื้นฐาน** เรารัน 12 โมเดลกับส่วน development เพื่อเติมข้อมูลเริ่มต้นใน leaderboard

3. **การประกาศสาธารณะ** ภาษาปรากฏบน Network leaderboard พร้อมเกณฑ์มาตรฐาน development segment แบบสด โดยระบุภาควิชาเป็นพันธมิตรคลังข้อมูล

## 3. รูปแบบที่คลังข้อมูลต้องมี

### 3.1 รูปแบบ

ไฟล์คลังข้อมูลทุกไฟล์เป็นเอกสาร JSON ตามสคีมาใน Benchmark Spec §2.1–§2.2:

```json
{
  "dataset": {
    "id": "crk-ualberta-v1",
    "version": "1.0",
    "language_pair": "EN→CRK",
    "source_language": "en",
    "target_language": "crk",
    "created": "2026-09-15",
    "license": "CC-BY-NC-SA-4.0",
    "provenance": ["textbook", "elicited", "gold_standard"]
  },
  "entries": [
    {
      "id": 1,
      "source": "I see the dog",
      "reference": "niwâpamâw atim",
      "segment": "development",
      "difficulty": 2,
      "provenance": "textbook",
      "register": "conversational",
      "context": "declaration",
      "domain": "edu",
      "morphological_analysis": "ni-wâpam-âw atim | 1sg-see.TA-3sg.DIR dog.AN",
      "notes": "Animate noun (atim); direct form because speaker is proximate"
    }
  ]
}
```

### 3.2 ข้อกำหนดขนาดขั้นต่ำ

| ส่วน | รายการขั้นต่ำ | แนะนำ |
|---------|----------------|-------------|
| `development` | 100 | 200–300 |
| `gold_standard` | 50 | 100–150 |
| `diagnostic` | 10 | 30–50 |
| `held_out` | 10 | 20–30 |
| **รวม** | **170** | **350–530** |

### 3.3 การกระจายระดับความยาก

คลังข้อมูลต้องมีรายการครอบคลุมทุกห้าระดับความยาก โดยเน้นที่ระดับ 2–4:

| ระดับ | คำอธิบาย | การกระจายเป้าหมาย |
|------|-------------|-------------------|
| 1 — คำศัพท์พื้นฐาน | คำเดี่ยว การทักทายทั่วไป ตัวเลข | 10–15% |
| 2 — ประโยคง่าย | SVO กาลปัจจุบัน | 25–30% |
| 3 — ความซับซ้อนปานกลาง | กาลอดีต/อนาคต การแสดงความเป็นเจ้าของ animacy | 30–35% |
| 4 — สัณฐานวิทยาซับซ้อน | Obviation passive conjunct order relative clauses | 15–20% |
| 5 — ขั้นสูง | หลายอนุประโยค รีจิสเตอร์ทางการ พิธีกรรม สำนวน | 5–10% |

### 3.4 ชุดทดสอบวินิจฉัย

ส่วน diagnostic ทดสอบปรากฏการณ์ทางภาษาศาสตร์เฉพาะโดยใช้ **คู่เปรียบเทียบ**: การแปลที่ถูกต้องหนึ่งรายการและการแปลที่ผิดพลาดซึ่งแตกต่างกันน้อยที่สุดหนึ่งรายการ หากเมตริกของระบบให้คะแนนรายการที่ถูกต้องสูงกว่า การทดสอบจะผ่าน

สำหรับภาษาโพลีซินเทติก ชุดทดสอบวินิจฉัยควรมุ่งเป้าที่:

| ปรากฏการณ์ | ตัวอย่าง (Cree) | สิ่งที่ทดสอบ |
|-----------|----------------|--------------|
| **การสอดคล้องของ animacy** | atim (AN) vs. maskisin (IN) — รูปแบบกริยาต่างกัน | ระบบรู้หรือไม่ว่าคำนามใดมีชีวิต? |
| **Obviation** | บุรุษที่สามแบบ proximate vs. obviative | ระบบติดตามลำดับชั้นบุรุษที่สามหรือไม่? |
| **Inverse marking** | รูปแบบกริยา direct vs. inverse | ระบบจัดการกับ patient-outranks-agent ได้หรือไม่? |
| **Conjunct/Independent** | ลำดับกริยาในประโยคหลัก vs. ประโยคย่อย | ระบบใช้ paradigm กริยาที่ถูกต้องหรือไม่? |
| **Inclusive/Exclusive** | "เรา (รวมคุณ)" vs. "เรา (ไม่รวมคุณ)" | ระบบแยกแยะรูปแบบพหูพจน์บุรุษที่หนึ่งได้หรือไม่? |

สำหรับตระกูลภาษาอื่น ให้ระบุปรากฏการณ์วินิจฉัย 3–5 รายการที่แยกแยะการแปลที่มีความสามารถออกจากการแปลที่ไม่มีความสามารถ ความเชี่ยวชาญทางภาษาศาสตร์ของภาควิชามีความสำคัญอย่างยิ่งในที่นี้ — เหล่านี้คือการทดสอบที่เฉพาะผู้เชี่ยวชาญเท่านั้นที่จะรู้ว่าต้องเขียน

### 3.5 สิ่งที่เราไม่ต้องการ

| รูปแบบที่ไม่พึงประสงค์ | เหตุผล |
|-------------|-----|
| **ข้อความจากพระคัมภีร์เพียงอย่างเดียว** | รีจิสเตอร์โบราณ คำศัพท์พิธีกรรม โครงสร้างสูตรสำเร็จ OMT-1600 ประเมิน 1,560 ภาษาด้วยวิธีนี้ — เราหลีกเลี่ยงโดยเจตนา |
| **คู่ประเมินผลสังเคราะห์** | การอ้างอิงที่สร้างโดย LLM ทำลายวัตถุประสงค์ของการประเมินผล การอ้างอิงต้องเขียนโดยมนุษย์ |
| **คลังข้อมูลรีจิสเตอร์เดียว** | ทางการทั้งหมด หรือการสนทนาทั้งหมด การแปลในโลกจริงครอบคลุมหลายรีจิสเตอร์ |
| **ระดับความยาก 1 เท่านั้น** | คำเดี่ยวและการทักทายไม่ทดสอบการแปล — ทดสอบแค่การค้นหาคำศัพท์ |
| **การอ้างอิงที่แปลด้วยเครื่อง** | การใช้ผลลัพธ์ Google Translate เป็น "การอ้างอิง" เป็นวงกลม |
| **ประโยคที่ไม่มีแท็กบริบท** | เราต้องการทราบฟังก์ชันการสื่อสารสำหรับการวิเคราะห์วินิจฉัย |

## 4. การปิดผนึกด้วยการเข้ารหัสลับและการทดสอบในแซนด์บ็อกซ์ {#4-cryptographic-sealing-and-sandbox-testing}

### 4.1 เหตุใดจึงต้องปิดผนึกชุดทดสอบ?

เกณฑ์มาตรฐาน ML แบบดั้งเดิมเผยแพร่ชุดทดสอบแบบเปิด เมื่อเผยแพร่แล้ว LLM ชั้นนำจะฝึกกับข้อมูลเหล่านั้นในที่สุด (โดยตั้งใจหรือผ่านการ scrape เว็บ) ทำให้คะแนนไม่น่าเชื่อถือ สำหรับข้อมูลภาษาของชนพื้นเมือง มีข้อกังวลเพิ่มเติม: ข้อมูลทางภาษาศาสตร์ที่เผยแพร่อาจถูกนำไปใช้โดยไม่ได้รับความยินยอมจากชุมชน

การปิดผนึกช่วยให้มั่นใจว่า:
- **ความสมบูรณ์ของชุดทดสอบ:** วิธีการต่าง ๆ ไม่สามารถ overfit กับข้อมูลที่ไม่เคยเห็น
- **อธิปไตยของข้อมูล:** ชุมชนควบคุมว่าใครประเมินกับข้อมูลของตน
- **ความสดใหม่ตลอดกาล:** ชุดทดสอบไม่เคยถูกปนเปื้อน

### 4.2 วิธีการทำงานของการทดสอบในแซนด์บ็อกซ์

```
Developer workflow:
  1. Developer builds a translation method using the PUBLIC development corpus
  2. Developer tests locally against the development segment (unlimited, self-serve)
  3. When ready, developer submits their complete method (code + config + coaching data)
  4. Governance org installs the method in the evaluation sandbox
  5. Sandbox runs the method against the SEALED gold-standard test set
  6. Only scores are returned to the developer
  7. Developer never sees the source sentences or reference translations

The sandbox:
  - Runs on governance-controlled infrastructure
  - Has selective network access (LLM APIs only, no exfiltration)
  - Produces a tamper-proof run card (SHA-256 hash of all inputs and outputs)
  - Logs all execution for audit purposes
  - Can be inspected by the governance org at any time
```

### 4.3 การจัดการคีย์

คีย์เข้ารหัสสำหรับชุดทดสอบที่ปิดผนึกถูกแบ่งโดยใช้ Shamir Secret Sharing ด้วยเกณฑ์ 2-of-3:

| ผู้ถือ share | บทบาท | อำนาจการเพิกถอน |
|-------------|------|-----------------|
| **องค์กรกำกับดูแลชุมชน** | ผู้ดูแลหลัก | สามารถเพิกถอนการเข้าถึงการประเมินได้ฝ่ายเดียว |
| **พันธมิตรภาควิชาวิชาการ** | ผู้ดูแลร่วม | สามารถมีส่วนร่วมในการสร้างคีย์ใหม่ |
| **โครงการ Champollion** | Escrow | ไม่สามารถเข้าถึงข้อมูลได้คนเดียว รับประกันความต่อเนื่องหากฝ่ายอื่นไม่พร้อมใช้งาน |

2 ใน 3 share ใด ๆ สามารถสร้างคีย์ใหม่ได้ ซึ่งหมายความว่า:
- ชุมชน + ภาควิชาสามารถเข้าถึงข้อมูลได้โดยไม่ต้องมี Champollion
- ชุมชน + Champollion สามารถเข้าถึงข้อมูลได้โดยไม่ต้องมีภาควิชา
- Champollion คนเดียวไม่สามารถเข้าถึงข้อมูลได้เลย

### 4.4 Hash Manifests

เมื่อคลังข้อมูลถูกปิดผนึก **hash manifest** จะถูกเผยแพร่ไปยัง Git commit สาธารณะ:

```json
{
  "corpus_id": "crk-ualberta-v1",
  "seal_date": "2026-09-15T00:00:00Z",
  "segments": {
    "development": {
      "entry_count": 200,
      "sha256": "a3f7c...",
      "access": "public"
    },
    "gold_standard": {
      "entry_count": 100,
      "sha256": "b8d2e...",
      "access": "sealed",
      "key_scheme": "shamir-2-of-3"
    },
    "held_out": {
      "entry_count": 20,
      "sha256": "c9e4f...",
      "access": "sealed",
      "key_scheme": "shamir-2-of-3"
    },
    "diagnostic": {
      "entry_count": 30,
      "sha256": "d1a3b...",
      "access": "public"
    }
  },
  "total_entries": 350,
  "manifest_sha256": "e2b5c..."
}
```

สิ่งนี้พิสูจน์ว่า:
- คลังข้อมูลมีอยู่ ณ วันที่เฉพาะเจาะจง
- มีขนาดและโครงสร้างที่ทราบแน่ชัด
- การแก้ไขใด ๆ ต่อส่วนที่ปิดผนึกจะทำลาย hash chain
- ชุมชนสามารถตรวจสอบได้ว่าข้อมูลของตนไม่ถูกดัดแปลง

## 5. สิ่งที่ภาควิชาได้รับ

### 5.1 โครงสร้างพื้นฐานการวิจัย

| สินทรัพย์ | คำอธิบาย |
|-------|------------|
| **Evaluation harness** | กรอบการประเมินผลที่ใช้งานได้และทดสอบแล้วสำหรับภาษาของตน — ประหยัดเวลาการสร้างเครื่องมือหลายเดือน |
| **เมตริก LYSS** | เมตริกการประเมินผลเฉพาะภาษา (LYSS-fst, LYSS-eq, LYSS-sem) ที่กำหนดค่าสำหรับภาษาของตน — หาก FST และทรัพยากรพจนานุกรมมีอยู่ |
| **Leaderboard** | leaderboard สาธารณะแบบสดที่แสดงสถานะของศิลปะสำหรับคู่ภาษาของตน |
| **เกณฑ์มาตรฐานพื้นฐาน** | การรัน 12 โมเดลที่ให้เกณฑ์มาตรฐานเริ่มต้นที่สามารถตีพิมพ์ได้ทันที |
| **ชุดทดสอบวินิจฉัย** | การทดสอบเฉพาะเจาะจงสำหรับปรากฏการณ์ทางภาษาศาสตร์ — นำมาใช้ซ้ำสำหรับการประเมินผลอื่น ๆ ได้ |

### 5.2 สิ่งตีพิมพ์

การสร้างคลังข้อมูลและผลการประเมินผลรองรับสิ่งตีพิมพ์หลายรายการ:

| บทความ | สถานที่ตีพิมพ์ | บทบาทของภาควิชา |
|-------|-------|-----------------|
| วิธีการสร้างคลังข้อมูล | LREC, ComputEL | ผู้เขียนหลักหรือผู้เขียนร่วม |
| ผลการประเมินผลพื้นฐาน | ACL, EMNLP | ผู้เขียนร่วม |
| การตรวจสอบเมตริก LYSS | WMT Metrics Shared Task | ผู้เขียนร่วม |
| การออกแบบชุดทดสอบวินิจฉัย | SIGMORPHON, NAACL | ผู้เขียนหลักหรือผู้เขียนร่วม |
| ทรัพยากร NLP เฉพาะภาษา | สถานที่ตีพิมพ์เฉพาะภาษา | ผู้เขียนหลัก |

### 5.3 การวางตำแหน่งสำหรับทุน

การเป็นพันธมิตรนี้ให้ผลลัพธ์ที่เป็นรูปธรรมสำหรับข้อเสนอทุน:

- "โครงสร้างพื้นฐานการประเมินผลแบบโอเพนซอร์สสำหรับ MT ของ [ภาษา]" — ผลส่งมอบที่พิสูจน์ได้
- "อธิปไตยข้อมูลด้วยการเข้ารหัสลับสำหรับข้อมูลทางภาษาศาสตร์ของชนพื้นเมือง" — นำกรอบอธิปไตยทางข้อมูลของชนพื้นเมืองที่ได้รับการยอมรับ (CARE, Kaitiakitanga, TK Labels) มาใช้กับการประเมินผล MT; สามารถตีพิมพ์ได้
- "เกณฑ์มาตรฐานที่กำกับดูแลโดยชุมชนพร้อม leaderboard แบบสด" — เมตริกผลกระทบต่อเนื่อง
- "การประเมินผลอิสระของ OMT-1600 / Google Translate สำหรับ [ภาษา]" — ทันเวลา มีการมองเห็นสูง

### 5.4 ผลกระทบต่อชุมชน

- ชุมชนภาษาได้รับ **ความสามารถในการประเมินผลอิสระ** — สามารถประเมินได้ว่าระบบ MT ใด ๆ (Google, Meta หรือแบบกำหนดเอง) ทำงานได้จริงสำหรับภาษาของตนหรือไม่
- ชุมชน **ควบคุมข้อมูลทดสอบ** ผ่านการดูแลคีย์เข้ารหัสลับ
- วิธีการใด ๆ ที่พิสูจน์ผ่านเกณฑ์มาตรฐาน **โอนความเป็นเจ้าของไปยังชุมชน** (ดู Benchmark Spec §8.3) ซึ่งเก็บทุกอย่างที่ deployment เคยได้รับ — Champollion ไม่แสวงหากำไรและไม่รับส่วนแบ่งใด ๆ

### 5.5 ต้นทุนสำหรับภาควิชา

| ส่วนประกอบ | ต้นทุนโดยประมาณ | ใครจ่าย |
|-----------|---------------|----------|
| เวลา PI/นักวิจัยหลังปริญญาเอก (การออกแบบ การดูแล) | ~40 ชั่วโมง | ภาควิชา (หรือได้รับทุน) |
| ค่าตอบแทนผู้พูด (การแปล) | $2,500–6,000 | ได้รับทุนหรือ Champollion เป็นผู้จ่าย |
| ค่าตอบแทนผู้พูด (การตรวจสอบ) | $500–1,500 | ได้รับทุนหรือ Champollion เป็นผู้จ่าย |
| เวลาผู้ประสานงานวิจัย | ~20 ชั่วโมง | ภาควิชา |
| **วิศวกรรม โครงสร้างพื้นฐาน harness** | **$0** | **โครงการ Champollion** |

เราจัดเตรียมวิศวกรรมทั้งหมด การกำหนดค่า harness การตั้งค่าเมตริก LYSS การรวม leaderboard และโครงสร้างพื้นฐานต่อเนื่องโดยไม่มีค่าใช้จ่ายสำหรับภาควิชา การมีส่วนร่วมของภาควิชาคือความเชี่ยวชาญทางภาษาศาสตร์และการเข้าถึงผู้พูด

## 6. ไทม์ไลน์

| ระยะ | ระยะเวลา | เหตุการณ์สำคัญ |
|-------|----------|--------------|

| **รวม** | **10–19 สัปดาห์** | **leaderboard แบบสดพร้อมการประเมินผลที่ปิดผนึก** |

## 7. วิธีเริ่มต้น {#7-how-to-get-started}

1. **ติดต่อเรา** — [อีเมล/ช่องทางติดต่อโครงการ] เราจะนัดหมายการโทร 30 นาทีเพื่อหารือเกี่ยวกับภาษา ทรัพยากรที่มีอยู่ และรายละเอียดการเป็นพันธมิตร

2. **เราจัดเตรียม:**
   - เอกสารนี้
   - สคีมาคลังข้อมูลและเครื่องมือตรวจสอบ
   - ตัวอย่างจากคลังข้อมูล Cree (CRK) ที่มีอยู่ของเรา
   - เทมเพลตออกแบบคลังข้อมูลร่าง

3. **สิ่งที่คุณต้องจัดเตรียม:**
   - นักวิจัยหลัก (PI) หรือนักวิจัยหลังปริญญาเอก (postdoc) เพื่อเป็นผู้นำในงานด้านภาษาศาสตร์
   - การเข้าถึงผู้พูดสองภาษา (หรือแผนการในการสรรหา)
   - ข้อมูลเกี่ยวกับทรัพยากรที่มีอยู่ (FST, พจนานุกรม, คลังข้อมูลที่มีอยู่)
   - การอนุมัติจากสถาบันสำหรับการกำกับดูแลข้อมูล (สอดคล้องกับหลักการอธิปไตยทางข้อมูลของ First Nations หรือกรอบการทำงานของชุมชนเอง)

4. **เราออกแบบคลังข้อมูลร่วมกัน** — การเลือกโดเมน การกระจายระดับความยาก การทดสอบวินิจฉัย ไทม์ไลน์ และงบประมาณ

5. **เริ่มงาน** เราตรวจสอบทุกสัปดาห์ ภาควิชามีอิสระเต็มที่ในการตัดสินใจทางภาษาศาสตร์ เราดูแลวิศวกรรมทั้งหมด

## 8. คำถามที่พบบ่อย

### "เรามีคลังข้อมูลคู่ขนานอยู่แล้ว สามารถใช้ได้หรือไม่?"

ได้ — หากคลังข้อมูลมีที่มาที่ชัดเจน เขียนโดยมนุษย์ และใบอนุญาตอนุญาตให้ใช้ในการประเมินผล เราจะช่วยจัดรูปแบบให้ตรงกับสคีมาของเรา เพิ่มข้อมูลเมตาที่ขาดหายไป และรวมเข้าระบบ คลังข้อมูลที่มีอยู่สามารถเร่งไทม์ไลน์ได้อย่างมาก (ข้ามระยะที่ 2 หรือลดเหลือเพียงการเติมช่องว่าง)

### "เราไม่มี FST สำหรับภาษาของเรา"

ไม่เป็นไร LYSS-fst (ความถูกต้องทางสัณฐานวิทยา) ต้องการ FST แต่ harness ทำงานได้โดยไม่มีโดยใช้น้ำหนัก Profile B (chrF++, BLEU, COMET, เมตริกพฤติกรรม) หาก GiellaLT FST มีอยู่สำหรับภาษาที่เกี่ยวข้อง เราอาจสามารถปรับใช้ได้ หากไม่มี คลังข้อมูลยังคงเปิดใช้งานการประเมินผลที่มีคุณค่า — เพียงแต่ไม่มีประตูความถูกต้องทางสัณฐานวิทยา

### "ผู้พูดของเราใช้อักษรที่ไม่ใช่ Latin"

รองรับอย่างสมบูรณ์ สคีมาคลังข้อมูลรองรับอักษร Unicode ใด ๆ เราออกแบบสำหรับ SRO (Standard Roman Orthography) และ syllabics สำหรับ Cree แต่โครงสร้างพื้นฐานเดียวกันทำงานได้กับ Devanagari อักษรอาหรับ CJK Ethiopic หรือระบบการเขียนอื่น ๆ

### "เกี่ยวกับความหลากหลายของภาษาถิ่นล่ะ?"

ติดแท็กไว้ สคีมารายการคลังข้อมูลมีฟิลด์ `notes` สำหรับข้อมูลภาษาถิ่น หากมีการแทนค่าหลายภาษาถิ่น ให้บันทึกไว้ equivalence classes ของ linter (LYSS-eq) สามารถกำหนดค่าให้ยอมรับรูปแบบภาษาถิ่นเป็นเทียบเท่าได้ ชุดทดสอบวินิจฉัยสามารถรวมการเปรียบเทียบเฉพาะภาษาถิ่นได้

### "ใครเป็นเจ้าของคลังข้อมูล?"

ชุมชนภาษา ผ่านองค์กรกำกับดูแล ภาควิชาได้รับการระบุเป็นพันธมิตรวิจัย Champollion ถือ share คีย์ escrow เพื่อความต่อเนื่องในการดำเนินงานแต่ไม่สามารถเข้าถึงข้อมูลที่ปิดผนึกได้คนเดียว ส่วน development เผยแพร่ภายใต้ใบอนุญาต Creative Commons ที่ชุมชนกำหนด

### "ถ้าเราต้องการหยุดล่ะ?"

ชุมชนสามารถเพิกถอนการเข้าถึงการประเมินผลได้ตลอดเวลาโดยปฏิเสธการสร้างคีย์เข้ารหัสใหม่ ข้อมูลที่ปิดผนึกจะไม่ถูกเปิดเผยเลย ส่วน development ที่เผยแพร่แล้วยังคงเป็นสาธารณะภายใต้ใบอนุญาตของตน ผลลัพธ์การวิจัยของภาควิชา (สิ่งตีพิมพ์ การนำเสนอ) เป็นของภาควิชาที่จะเก็บไว้ไม่ว่าจะเกิดอะไรขึ้น

### "ถ้าองค์กรกำกับดูแลยังไม่มีอยู่ล่ะ?"

เราสามารถเริ่มต้นด้วยระยะที่ 1–3 (การออกแบบคลังข้อมูล การสร้าง การประกันคุณภาพ) โดยไม่มีองค์กรกำกับดูแล การปิดผนึก (ระยะที่ 4) ต้องการการระบุผู้ดูแลคีย์ ในระหว่างนี้ ภาควิชาสามารถทำหน้าที่เป็นผู้ดูแลร่วมควบคู่กับโครงการ Champollion โดยมีความเข้าใจว่าการดูแลจะโอนไปยังองค์กรกำกับดูแลชุมชนเมื่อมีการจัดตั้งขึ้น

## ภาคผนวก: การติดแท็กเทียบกับการสร้างคลังข้อมูล

เอกสารนี้ครอบคลุม **การสร้างคลังข้อมูล** — การสร้างคู่ข้อความคู่ขนานที่เป็นมาตรฐานความจริงสำหรับการประเมินผล การติดแท็ก (การอธิบายทางสัณฐานวิทยา การอธิบายแบบ interlinear สตริงแท็ก FST) เป็นกิจกรรมแยกต่างหากที่เพิ่มคุณค่าให้คลังข้อมูลแต่ไม่จำเป็นสำหรับการประเมินผลพื้นฐาน

| กิจกรรม | จำเป็นหรือไม่? | สิ่งที่เปิดใช้งาน |
|----------|-----------|-----------------|
| **การสร้างคลังข้อมูล** (เอกสารนี้) | ✅ จำเป็น | การประเมินผลพื้นฐาน: chrF++, exact match, COMET, เมตริกพฤติกรรม |
| **การตรวจสอบความครอบคลุม FST** | 🟡 ไม่บังคับ | เมตริกความถูกต้องทางสัณฐานวิทยา LYSS-fst **และ** `morphological_accuracy` ที่ได้จาก FST (lemma-matched — ไม่ต้องการการอธิบาย; Scoring Spec §2.2) |
| **การอธิบายทางสัณฐานวิทยา** | 🟡 ไม่บังคับ | จะเปิดใช้งานการอัปเกรด *gold-validated* ในอนาคตของ `morphological_accuracy`; เวอร์ชันที่ได้จาก FST (ข้างต้น) ไม่ต้องการสิ่งใด |
| **กฎ equivalence ของ linter** | 🟡 ไม่บังคับ | เมตริก equivalent match ของ LYSS-eq |
| **กฎ semantic validator** | 🟡 ไม่บังคับ | เมตริกการตรวจสอบความหมาย LYSS-sem |
| **การให้คะแนนคุณภาพโดยผู้พูด** | กิจกรรมแยกต่างหาก | การตรวจสอบเมตริก (ดู [โปรโตคอลการตรวจสอบโดยผู้พูด](/docs/network/specifications/speaker-validation)) |

การติดแท็กและการตรวจสอบโดยผู้พูดครอบคลุมโดยเอกสารแยกต่างหากและสามารถดำเนินการควบคู่กับหรือหลังจากการสร้างคลังข้อมูล
