# การวินิจฉัยการรัน Training

โมเดลของคุณเทรนเสร็จแล้ว แต่ตัวเลขไม่ได้เป็นไปตามที่คุณหวังไว้ หน้านี้เริ่มต้นจาก
**สิ่งที่คุณกำลังพบเห็น** และพาคุณไปดูสาเหตุที่เป็นไปได้พร้อมเครื่องมือของ forge ที่
ช่วยแก้ไข สิ่งเหล่านี้ส่วนใหญ่ทำงานแบบอัตโนมัติ — `nmt-forge export` (และส่วนที่เน้นเฉพาะคะแนนอย่าง
`nmt-forge evaluate`) จะเพิ่มส่วน **Diagnosis & Recommendations**
ที่ระบุสิ่งที่ตรวจพบและแนวทางปรับปรุง คู่มือนี้คือฉบับอธิบายด้วยภาษาที่เข้าใจง่าย
รวมถึงสิ่งเล็กๆ น้อยๆ สองสามข้อที่ forge ทำได้เพียงแค่ *แจ้งเตือน* เท่านั้น (ทำเครื่องหมาย ⚠ **สิ่งที่ต้องระวัง**)

บอก agent ของคุณว่า: *"รัน `nmt-forge lint <battery-manifest.json> --json` และจัดการกับ
ข้อค้นพบที่มีความรุนแรงสูงสุด"* หลังจากการส่งออก รายการชุดทดสอบคือ
`export/evaluation/battery-hyps-battery.json` จากนั้นจับคู่รายงานที่ได้กับ
หัวข้อด้านล่างนี้

## "คะแนนของโมเดลเริ่มต้นอยู่ในระดับต่ำ"

คุณเทรนด้วยพรีเซ็ตเริ่มต้น `cpu-tiny` และคะแนนทดสอบอยู่ระหว่าง
5 ถึง 30 chrF++

**สิ่งที่เกิดขึ้น:** นี่คือลักษณะการทำงานปกติของพรีเซ็ตนี้ โดยเป็นทรานส์ฟอร์เมอร์ขนาดเล็ก
ที่เทรนขึ้นมาใหม่ตั้งแต่ต้นจากคู่ข้อมูลของคุณเพียงอย่างเดียว ดังนั้นเมื่อมีข้อมูลเพียง 1–2 พันคู่ โมเดลจะเรียนรู้
เฉพาะวลีและรูปแบบประโยคจากข้อมูลของคุณเท่านั้น ไม่ใช่ภาษาโดยรวม — คะแนนระดับ
บนสุดของช่วงนี้จะปรากฏก็ต่อเมื่อข้อมูลเป็นเทมเพลตซ้ำๆ อย่างมากเท่านั้น หน้าที่ของมันคือ
การทำให้กระบวนการทั้งหมดเกิดขึ้นได้จริง (dev set ที่มีการล้อมรั้วป้องกัน, ข้อมูลที่ผ่านการตรวจสอบ, test set ที่ลงทะเบียนล่วงหน้า, โมเดล
ที่ CLI สามารถเรียกใช้ได้) ไม่ใช่เพื่อเป็นโมเดลสำหรับนำไปใช้งานจริง

**วิธีแก้ไข:** ปรับเปลี่ยนทีละอย่างแล้ววัดผลบน dev set โดยเรียงลำดับตามผลลัพธ์ที่คุ้มค่าที่สุด
โดยประมาณ:

1. **เพิ่มคู่ข้อมูลจริง** ในขนาดระดับนี้ ปริมาณข้อมูลชนะการตั้งค่าทั้งหมด
2. **เริ่มต้นจากโมเดล pretrained** `nmt-forge init <code> --model cpu-finetune --base
   <hf-id>` จะทำการไฟน์จูนโมเดล Marian/opus-mt ขนาดเล็กที่ผ่านการพรีเทรนมาแล้วบน CPU — ให้เลือก
   โมเดลสำหรับคู่ภาษาที่ *เกี่ยวข้องกัน* และเปรียบเทียบกับ `cpu-tiny` บน dev
   แทนที่จะด่วนสรุปว่ามันจะดีกว่าเสมอไป `--model nllb-600m` เป็นจุดเริ่มต้นที่ทรงพลังที่สุด
   และจำเป็นต้องใช้ GPU
3. **สร้างข้อมูลเพิ่มจากสิ่งที่คุณมี** — การแปลย้อนกลับ (backtranslation) ของข้อความภาษาเดียว หรือ
   การสังเคราะห์ข้อมูลที่ผ่านการตรวจสอบความถูกต้องหากภาษาของคุณมีตัววิเคราะห์ (ดู
   [หากคุณต้องการเทรนโมเดลของคุณเอง](/docs/network/tutorials/train-your-own-model))

⚠ **สิ่งที่ต้องระวัง:** คะแนนที่สูงจาก `cpu-tiny` ควรตรวจสอบให้รอบคอบก่อนที่จะ
ฉลอง — ดูที่ ["คะแนนดูดีเกินไป"](#the-score-looks-too-good)

## "ดีมากกับตัวอย่างในตำราเรียน แต่แย่มากกับประโยคจริง"

**กับดักที่พบบ่อยที่สุดสำหรับทรัพยากรน้อย** ข้อมูล synthetic/template ของคุณได้คะแนนสวยงาม
แต่ข้อความจริงพังทลาย

**สิ่งที่เกิดขึ้น:** เกิด **transfer plateau** ระหว่างการเทรน loss บน dev set จริงของคุณ
ลดลงต่ำสุดเร็วแล้วค่อย ๆ เพิ่มขึ้น ในขณะที่ training loss ยังคงลดลงต่อเนื่อง —
โมเดลกำลังเชี่ยวชาญ *ปริมาณ* ข้อมูล synthetic ไม่ใช่เรียนรู้การแปล
การเพิ่มข้อมูล synthetic จะ **ไม่** ช่วย

**สิ่งที่ forge พบ:** `R7-transfer-plateau` (จาก schedule story ของ run manifest)
**Lever: REAL-DATA**

**วิธีแก้:** เพิ่มข้อความจริง Backtranslate ข้อมูล monolingual ภาษาเป้าหมาย
(`nmt_forge.training.backtranslation`) หรือหาประโยคคู่ขนานจริง
ปริมาณข้อมูล synthetic ไม่ใช่ตัวแปรที่ต้องปรับ — ความหลากหลายของข้อมูล *จริง* ต่างหาก

⚠ **ระวังสิ่งนี้:** หาก mix ของคุณมีข้อมูล synthetic ~99% เทียบกับ dev set จริงขนาดเล็ก
คุณมีความเสี่ยงที่จะเกิดปัญหานี้ *ก่อน* ที่จะเห็นในคะแนน ยังไม่มี pre-flight lint
สำหรับ ratio ที่ผิดปกติ — ตรวจสอบจำนวน gold/synthetic ใน mix manifest ของคุณ

## "Register หนึ่งแย่กว่าตัวอื่นมาก"

ดูตาราง per-register มี register เดียว (เช่น ราชการหรือกฎหมาย) ที่ต่ำกว่าตัวอื่นมาก

**สาเหตุมีสองแบบ — การวินิจฉัยแยกแยะโดยดูที่ *coverage*
และว่า output *ไม่สมบูรณ์* หรือไม่:**

- **โมเดลขาดคำศัพท์** (`R1-vocabulary-gap`: coverage ต่ำ **และ** อัตรา incomplete สูง)
  **Lever: VOCABULARY** ขยาย lexicon (พจนานุกรม / การเก็บรวบรวม attestation)
  แล้วรัน `nmt-forge` funnel accounting เพื่อยืนยันว่า entry ใหม่ไปถึง corpus จริง —
  ความไม่ตรงกันของ orthography เพียงหนึ่งตัวอักษรเคยลบคำหลายพันคำไปโดยไม่มีใครรู้
- **โมเดลมีคำศัพท์แต่ขาดรูปประโยค** (`R2-structure-gap`:
  coverage ผ่าน แต่ยังไม่สมบูรณ์) **Lever: STRUCTURE** รัน coverage map
  เทียบกับ grammar checklist ของคุณและเพิ่ม construction ที่ขาดหายไป
  (imperatives, wh-questions, possession, inverse — อะไรก็ตามที่ template ของคุณไม่เคยครอบคลุม)

## "Output ผสมการสะกดหลายแบบในประโยคเดียว"

โมเดลเขียนเสียงเดียวกันสองแบบ บางครั้งในประโยคเดียวกัน

**สิ่งที่เกิดขึ้น:** ข้อมูลเป้าหมายในการเทรนสอนให้โมเดลคิดว่า convention สามารถใช้แทนกันได้ —
corpus มีเนื้อหาเดียวกันในหลาย orthography

**สิ่งที่ forge พบ:** `R3-mixed-convention` **Lever: ORTHOGRAPHY**

**วิธีแก้:** `convention-lint` corpus ทำให้เป็น **หนึ่ง** convention มาตรฐาน
ที่ data boundary แล้วเทรนใหม่ เก็บ mixed-convention rate ไว้ใน battery
เพื่อให้เห็นว่ามันลดลง

## "Model B ชนะ model A — แต่ต่างกันนิดเดียว"

คุณเปรียบเทียบสองโมเดลและตัวหนึ่งนำอยู่เพียงเศษเสี้ยวของคะแนน

**สิ่งที่เกิดขึ้น:** ความแตกต่างอาจเล็กกว่า noise ด้วยประโยค 80 ประโยค
ช่องว่าง chrF++ 0.4 คือการโยนเหรียญ

**สิ่งที่ forge พบ:** `R5-low-power` (confidence interval กว้างกว่า delta)
**Lever: MEASUREMENT**

**วิธีแก้:** อย่าดำเนินการกับ delta ที่เล็กกว่า CI ขยาย eval set สำหรับ register นั้น
หรือใช้ `nmt-forge compare` ซึ่งรายงาน *paired* significance test
แทนที่จะเป็นสอง interval ที่ทับซ้อนกัน forge ไม่แสดงคะแนนเปล่า ๆ —
interval มีอยู่เสมอเพื่อให้คุณเห็นสิ่งนี้

⚠ **ระวังสิ่งนี้:** ผลลัพธ์จาก **seed เดียว** ไม่มี variance-across-seeds band
ผลกำไรที่ไม่รอดจากการ re-seeding ไม่ใช่ผลจริง
หากการตัดสินใจมีความสำคัญ ให้รันซ้ำด้วย 2–3 seed

## "คะแนนดูดีเกินไป"

สูงอย่างน่าสงสัย โดยเฉพาะในช่วงต้นหรือกับข้อมูลน้อย จงเชื่อความสงสัยนั้น

**ตรวจสอบตามลำดับ:**

1. **การรั่วไหลของข้อมูล (Leakage)** `nmt-forge leak-audit <corpus>` — มีประโยคทดสอบหลุดเข้าไปในชุดข้อมูลฝึกฝนหรือไม่? คำสั่งนี้จะตัดแถวที่มี prompt ตรงกับ prompt ในชุดทดสอบ (แม้ว่าคำแปลจะต่างกันก็ตาม), แถวที่มีคำตอบตรงกับคำตอบในชุดทดสอบ, รวมถึงแถวที่มีข้อความอยู่ภายใน เป็นเศษส่วนหนึ่ง หรือเหมือนกับคำตอบในชุดทดสอบตั้งแต่ ≥90% ขึ้นไป `nmt-forge run` จะปฏิเสธแถวข้อมูลฝึกฝนที่รั่วไหลไปยังชุดทดสอบหรือ sealed set ที่ลงทะเบียนไว้ ดังนั้นสิ่งนี้จึงสำคัญที่สุดสำหรับข้อมูลหรือไปป์ไลน์ที่อยู่นอก forge — หรือชุดทดสอบที่คุณไม่เคยลงทะเบียน
2. **การเลือก Checkpoint** Checkpoint ถูกเลือกโดยอิงจาก **fenced dev set** ไม่ใช่ชุดทดสอบใช่หรือไม่? forge ปฏิเสธที่จะฝึกฝนโดยไม่มี dev set เพื่อป้องกันปัญหานี้โดยเฉพาะ แต่ไปป์ไลน์ที่สร้างขึ้นเองจะไม่ป้องกันสิ่งนี้
3. **คะแนนที่สูงเกินจริงจากประโยคที่เกือบเหมือนกัน (Optimism from near-twins)** `R4-optimism-bound`: หากคะแนนชุดทดสอบแบบ "full" สูงกว่าคะแนนแบบ "strict" อยู่หลายคะแนน ส่วนต่างนั้นคือ drill-sibling optimism (คะแนนที่สูงเกินจริงจากคู่ประโยคตามเทมเพลต) `leak-audit` *คงไว้* ซึ่งเทมเพลตที่คล้ายกันโดยเจตนา (*"I see the dog"* ในการฝึกฝน, *"I see the cat"* ในชุดทดสอบ) และแสดงรายการแถวทดสอบที่มีคู่ดังกล่าว โดยเมื่อตั้งค่า `eval.near_dupe_corpus` ชี้ไปยังไฟล์การฝึกฝนของคุณ (การกำหนดค่าเริ่มต้นทำสิ่งนี้อยู่แล้ว) รายงานจะให้คะแนนแถวทดสอบที่ *ไม่มี* คู่ที่คล้ายกันแยกต่างหาก โดยระบุว่า "(strict)" **ให้อ้างอิงตัวเลข strict** สำหรับการอ้างสิทธิ์ด้านความสามารถในการประยุกต์ใช้ทั่วไป (generalization) ใดๆ หาก *ทุก* แถวทดสอบมีคู่ที่คล้ายกัน (`R4-recall-not-translation`: ซับเซ็ต strict จะว่างเปล่า ดังนั้นคะแนนจึงวัดเพียงการระลึกจำวลีที่ฝึกฝนมา) และชุดทดสอบไม่สามารถเปลี่ยนแปลงได้ ให้เขียนคอร์ปัสที่ปลอดประโยคคู่เหมือน (twin-free) แยกเป็นไฟล์ของตัวเองด้วยคำสั่ง `nmt-forge leak-audit <train> --clean-to <train>.notwins.jsonl --drop-test-twins` แล้วฝึกฝนโมเดลที่ปลอดประโยคคู่เหมือนตัวที่สองด้วยไฟล์นี้ (leak-audit จะไม่เขียนทับไฟล์ที่โมเดลแรกใช้ฝึกฝน) — หรือหาประโยคทดสอบที่เขียนขึ้นอย่างอิสระโดยไม่อิงจากเทมเพลตการฝึกฝน
4. **ผลลัพธ์ไม่สอดคล้องกับอินพุต** `R9-harness-score-caveat`: รายงาน mt-eval ระบุว่าคะแนนดังกล่าวมีเงื่อนไขกำกับ — โดยส่วนใหญ่มักเป็น **ผลลัพธ์ที่แทบจะคงที่ (near-constant output)**: ประโยคทดสอบที่แตกต่างกันจำนวนมากได้รับผลลัพธ์เดียวกันเพียงไม่กี่แบบ (ในการทดสอบเดินระบบครั้งหนึ่งของเรา โมเดลคู่มือวลีสำหรับโรงพยาบาลจำลองตอบประโยคที่แตกต่างกัน 150 ประโยคด้วยผลลัพธ์เพียง 9 แบบ แต่ยังคงได้คะแนน chrF++ ถึง 48 เนื่องจากวลีที่พบบ่อยมีอักขระร่วมกับข้อความอ้างอิงหลายรายการ) โมเดลแบบ twin-free มักเป็นสาเหตุหลัก: เมื่อนำเทมเพลตการฝึกฝนออกไป โมเดลขนาดเล็กอาจถอยกลับไปใช้ประโยคที่พบบ่อยที่สุด forge ส่งต่อข้อควรระวังนี้ตามถ้อยคำของ harness — ในสรุปการส่งออก, `DEPLOY.md`, `status`, `report`, `compare` และ `lint` — และไม่เคยเรียกคะแนนดังกล่าวว่าเป็น "ตัวเลขที่ควรนำไปอ้างอิง" โดยปราศจากข้อควรระวังนี้ ให้อ่านผลลัพธ์บางส่วน (`<export>/evaluation/battery-hyps.jsonl` บนเครื่องที่มีชุดทดสอบ) ก่อนที่คุณจะรายงานคะแนนดังกล่าวเป็นคุณภาพการแปล การเพิ่มคู่ประโยคฝึกฝนจริงที่มีความหลากหลายคือทางออกสำคัญ

## "Training หยุดเกือบทันที"

การรันจบลงหลังจากไม่กี่ร้อย step โมเดลแทบไม่ได้เห็นข้อมูลของตัวเอง

**สิ่งที่เกิดขึ้น:** early stopping เข้าใจผิดว่า dev wobble ที่หนักไปด้วย synthetic
ตามปกติคือการ convergence

**พฤติกรรมของ forge:** สิ่งนี้ได้รับการ *ป้องกัน* ไว้เป็นค่าเริ่มต้น — `nmt-forge run` จะคำนวณ
**เกณฑ์ขั้นต่ำ (floor)** สำหรับการหยุดเทรนจากชุดข้อมูลที่คุณผสม และระงับการหยุดก่อนกำหนดที่ต่ำกว่าเกณฑ์นั้น พร้อมบันทึก
เหตุผลไว้ในบรรทัด `[schedule-sanity]` ความถี่ในการประเมิน dev set จะถูก
คำนวณจากขนาดของการรันด้วยเช่นกัน ดังนั้นการรันขนาดเล็กจึงไม่ถูกปล่อยทิ้งไว้โดยไม่ประเมิน หาก
คุณพบการหยุดทำงานที่ไม่คาดคิด โปรดอ่านบรรทัดเหล่านั้น โดย run manifest จะบันทึก
ไว้อย่างชัดเจนว่าเกิดอะไรขึ้นและเพราะเหตุใด (การรันที่ดำเนินไปจนถึงขั้นตอนสุดท้ายตามแผน
จะได้รับรายงานว่าเสร็จสิ้น ไม่ใช่การหยุดก่อนกำหนด)

## "การรันถูกปฏิเสธก่อนที่จะเริ่มต้นจริง"

**สิ่งที่เกิดขึ้น:** มี gate ตัวใดตัวหนึ่งทำงานสกัดไว้ — ซึ่งช่วยประหยัดทรัพยากรได้มากกว่าการปล่อยให้รันล้มเหลว
หลังจากผ่านไปหลายชั่วโมง สาเหตุที่พบบ่อย ได้แก่:

- **ไม่มี training extra** — `nmt-forge preflight run --config
  config.json` shows `✗ backend-installed` พร้อมวิธีแก้ปัญหา
  `python3 -m pip install 'nmt-forge[hf]'`
- **ไม่มี dev set หรือใช้ dev set ไม่ถูกต้อง** — dev-fence จะปฏิเสธการรันที่
  `data.dev` ไม่ใช่ชุดข้อมูลที่ลงทะเบียนไว้ด้วยบทบาท `dev` แบ่งข้อมูลออกมาด้วย
  `nmt-forge split … --register project`
- **ข้อมูลรั่วไหล (Leakage)** — ไฟล์เทรนมี prompt หรือคำตอบซ้ำกับชุดทดสอบ
  ที่ลงทะเบียนไว้หรือ sealed set ให้ทำความสะอาดไฟล์ด้วย `nmt-forge leak-audit <file> --clean-to
  <file.clean.jsonl>` แล้วกำหนดค่า config ให้ชี้ไปยังไฟล์ที่ทำความสะอาดแล้ว
- **เวลาตามนาฬิกาจริง (Wall-clock)** — ในช่วงนาทีแรก forge จะวัดความเร็วในการเทรนและ
  ปฏิเสธการรันที่มีการคาดการณ์ว่าจะใช้เวลาเกิน `model.time_budget_hours` หากใช้ CPU ปัญหานี้
  มักหมายถึงพรีเซ็ตจำเป็นต้องใช้ GPU (`nllb-600m`) หรือชุดข้อมูลที่ผสมมีขนาดใหญ่กว่า
  ที่คุณตั้งใจไว้มาก ข้อความจะระบุแนวทางปรับปรุง: ลดขนาดข้อมูลที่ผสม, ใช้ลำดับข้อความที่สั้นลง
  หรือเพิ่มงบประมาณเวลาหากคุณยินยอมที่จะรอได้จริง

**วิธีแก้ไข:** รัน `nmt-forge preflight run --config config.json` ก่อนการรันทุกครั้ง
คำสั่งนี้จะแสดงรายการ gate ทั้งหมดพร้อมเครื่องหมาย ✓/✗ และวิธีแก้ไขสำหรับแต่ละ ✗

## "Metric ที่ต้องการหายไปจากรายงาน"

รายงานซื่อสัตย์แต่ว่างเปล่าในแกนหนึ่ง (COMET, การตรวจสอบ FST validity)

**สิ่งที่ forge พบ:** `R6-referee-unavailable` — lane ถูกระบุว่าไม่พร้อมใช้งานพร้อมเหตุผล
**Lever: REFEREE**

**วิธีแก้ไข:** ติดตั้ง/กำหนดค่า referee ที่ระบุแล้วประเมินคะแนนใหม่อีกครั้ง เมื่อ language
card มีการประกาศใช้ referee ข้อความของ forge จะระบุคำสั่งในการติดตั้ง
(`mt-eval setup --lang <code>`) คะแนนที่คุณมีอยู่ยังคงเชื่อถือได้ — เพียงแต่
ยังขาดการประเมินในมิตินั้นจนกว่าจะติดตั้ง referee ครบถ้วน

## "โมเดล emit `<unk>` หรืออักขระที่ผิดเพี้ยน"

โดยเฉพาะกับ script แบบ syllabic หรือ extended-Latin

**ขึ้นอยู่กับพรีเซ็ตที่ใช้**

- **`cpu-tiny`** จะเรียนรู้คำศัพท์ของตัวเองจากแถวข้อมูลเทรนของคุณ ดังนั้นทุก
  อักขระที่ปรากฏในชุดเทรนจะได้รับการครอบคลุม `<unk>` ในที่นี้หมายความว่าอินพุต
  มีอักขระที่ไม่เคยปรากฏในการเทรนเลย — เช่น ตัวอักษรหรือเครื่องหมายกำกับเสียงที่หายาก หรือรูปแบบ Unicode ที่ต่างกัน (ข้อความ
  จะถูกแปลงให้อยู่ในรูป NFC ดังนั้นเครื่องหมายกำกับเสียงแบบผสมและแบบแยกจะถือว่าเหมือนกัน) ตรวจสอบให้แน่ใจว่าข้อมูลเทรน
  และข้อมูลทดสอบของคุณใช้อักขรวิธีเดียวกัน
- **`cpu-finetune` และ `nllb-600m`** จะใช้ tokenizer ของโมเดลฐานที่เป็น pretrained

⚠ **สิ่งที่ต้องระวัง — ยังไม่ได้เป็นแบบอัตโนมัติ (โมเดลฐานที่เป็น pretrained)** **tokenizer** ของโมเดลฐาน
**อาจไม่รองรับชุดตัวเขียนเป้าหมายของคุณ** forge ยังไม่มีการตรวจสอบ
ความครอบคลุมของ tokenizer ก่อนเริ่มการเทรน โปรดตรวจสอบ tokenizer ของโมเดลฐานกับ
ตัวอย่างชุดตัวเขียนเป้าหมายของคุณ ควรเลือกโมเดลฐานที่มีคำศัพท์ครอบคลุมชุดตัวเขียนนั้น
(ภาษาที่มีทรัพยากรน้อยจำนวนมากได้รับการครอบคลุมโดยโมเดลฐานตระกูล NLLB) หรือขยาย
tokenizer เพิ่มเติมก่อนทำการเทรน

## เมื่อ forge ปฏิเสธและคุณไม่เข้าใจว่าทำไม

การปฏิเสธจะระบุเสมอว่า **เกิดอะไรขึ้น** **ทำไมมันจึงทำให้ผลลัพธ์เสียหาย** และ **วิธีแก้ไข**
หากยังไม่ชัดเจน:

- `nmt-forge status` — ตำแหน่งที่คุณอยู่และคำสั่งถัดไปเพียงคำสั่งเดียว
- `nmt-forge preflight <command>` — ทุก gate ที่คำสั่งนั้นจะต้องพบ พร้อมสัญลักษณ์ ✓/✗ และ
  วิธีแก้ไขสำหรับแต่ละ ✗ เพื่อให้คุณแก้ไขทั้งหมดได้ในคราวเดียวแทนที่จะแก้ทีละจุด
  (สำหรับ `run`, `evaluate` และ `export` ให้เพิ่ม `--config config.json`)
- เพิ่ม `--json` ในคำสั่งใดก็ได้เมื่อให้ agent เป็นผู้อ่านผลลัพธ์ การปฏิเสธ
  จะส่งกลับมาเป็นออบเจกต์ JSON เพียงรายการเดียว — `{"error": {"type", "guard", "message",
  "why", "fix", …}}` — พร้อมรหัสออกจากระบบ 2

การปฏิเสธไม่ใช่ข้อผิดพลาดในการตั้งค่าของคุณ — มันคือเครื่องมือที่จับความผิดพลาด
ก่อนที่จะส่งผลต่อผลลัพธ์ของคุณ นั่นคือการออกแบบทั้งหมด
