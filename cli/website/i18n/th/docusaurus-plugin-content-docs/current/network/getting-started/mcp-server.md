# เซิร์ฟเวอร์ MCP — ประตูสู่ระบบสำหรับเอเจนต์

`champollion-mcp-server` เปิดให้เอเจนต์ AI เข้าถึง Champollion ผ่าน [Model
Context Protocol](https://modelcontextprotocol.io) ทาง stdio โดยมีโปรไฟล์สองแบบ:

| โปรไฟล์ | เริ่มต้นด้วย | สิ่งที่ให้บริการ | สร้างมาเพื่อ |
|---|---|---|---|
| **rails** (ค่าเริ่มต้น) | `npx -y champollion-mcp-server` | เครื่องมือหกรายการ: `start_project`, `project_status`, `run_next_step`, `add_data`, `try_translation`, `explain` | นำพาโปรเจกต์ภาษาหนึ่งโปรเจกต์จากโฟลเดอร์ว่างเปล่าไปสู่โมเดลที่ผ่านการวัดผลบนคอมพิวเตอร์ของผู้ใช้เอง ทีละขั้นตอน |
| **full** | `npx -y champollion-mcp-server --profile full` (หรือ `CHAMPOLLION_MCP_PROFILE=full`) | 34 เครื่องมือ, 3 รีซอร์ส และ 4 พรอมต์ | การค้นหาข้อมูล การเบนช์มาร์ก การฝึกฝนทีละขั้นตอน การแปล และเครือข่าย |

หากคุณกำลังช่วยเหลือผู้อื่นสร้างระบบแปลสำหรับภาษาของพวกเขา ให้ใช้โปรไฟล์
rails; วิธีการสั่งการอยู่ใน [การขับเคลื่อน rails ผ่าน
MCP](/docs/agents/mcp) และกฎเกณฑ์ที่คุณต้องปฏิบัติตามอยู่ใน [สัญญาการดำเนินงาน](/docs/agents/contract)

ทุกสิ่งในที่นี้สามารถเข้าถึงได้ผ่าน HTTP ธรรมดาเช่นกัน — ดู [เอนด์พอยต์ที่เครื่องอ่านได้](#machine-readable-endpoints) — แต่เซิร์ฟเวอร์ MCP เป็นส่วนติดต่อเดียวที่อนุญาตให้เอเจนต์ *ดำเนินการ* (แปลผล ดำเนินการเบนช์มาร์ก ฝึกฝนโมเดล) แทนที่จะแค่อ่านเพียงอย่างเดียว

## การติดตั้ง

```bash
npx -y champollion-mcp-server
```

จากนั้นลงทะเบียนกับไคลเอนต์ของคุณ สำหรับ Claude Code:

```bash
claude mcp add champollion -- npx -y champollion-mcp-server
```

สำหรับไคลเอนต์ที่กำหนดค่าผ่านไฟล์ (Claude Desktop, Cursor, Antigravity) ให้เพิ่ม:

```json
{
  "mcpServers": {
    "champollion": {
      "command": "npx",
      "args": ["-y", "champollion-mcp-server"]
    }
  }
}
```

สำหรับโปรไฟล์ full ให้เพิ่ม `"--profile", "full"` หลังชื่อแพ็กเกจใน
`args` หรือลงท้ายคำสั่ง `claude mcp add` ด้วย `--profile full`

## โปรไฟล์ rails (ค่าเริ่มต้น)

เครื่องมือทั้งหกรายการจะนำพาโปรเจกต์ภาษาหนึ่งโปรเจกต์ตั้งแต่โฟลเดอร์ว่างเปล่าไปจนถึงโมเดล
ที่ผ่านการวัดผลบนคอมพิวเตอร์ของผู้ใช้เอง แต่ละขั้นตอนจะระบุไว้อย่างชัดเจนว่าต้องเรียกใช้เครื่องมือใด
และทุกคำถามที่มีเพียงผู้ใช้เท่านั้นที่ตอบได้ (ใครเป็นผู้ครอบครองไฟล์ โมเดลสามารถเรียนรู้จากไฟล์นั้นได้หรือไม่
ข้อความในไฟล์สามารถส่งออกจากคอมพิวเตอร์ได้หรือไม่ พวกเขาคาดหวังอะไร ผลลัพธ์ดีเพียงพอหรือไม่) จะถูกส่งกลับไปให้พวกเขาตอบ เครื่องมือจะรายงานจำนวนนับและคอลัมน์ โดยไม่ส่งข้อความประโยคกลับมาเด็ดขาด เครื่องมือทุกตัวขับเคลื่อนบรรทัดคำสั่ง `champollion`
ในฐานะโพรเซสที่แยกส่วนและถูกจำกัดขอบเขต — คำสั่งเดียวกับที่ผู้ใช้พิมพ์
โปรไฟล์นี้สร้างขึ้นสำหรับเอเจนต์ขนาดเล็กที่มีคำสั่งสั้นๆ

| เครื่องมือ | อาร์กิวเมนต์ | การทำงาน |
|---|---|---|
| `start_project` | `folder`, `from`, `to`, `target_name?`, `source_name?`, `purpose?`, `parent_dir?`, `confirmed?` | สร้างโปรเจกต์ (`champollion new`) การเรียกครั้งแรกจะไม่สร้างสิ่งใดและส่งคืน `ask_first`: ให้แจ้งทิศทางภาษากลับไปยังผู้ใช้ จากนั้นทำการเรียกตามที่ระบุไว้สำหรับคำตอบของพวกเขา |
| `project_status` | `project_dir`, `wait_seconds?` (สูงสุด 120) | ขั้นตอนถัดไป โดยอ่านจากไฟล์ (`champollion next --json`): โหมดของขั้นตอน สิ่งที่ต้องแจ้ง เหตุผล และการเรียกที่แน่นอนเพื่อดำเนินการขั้นตอนนี้ |
| `run_next_step` | `project_dir`, `step_id`, `answers?`, `confirmed?` | ดำเนินการขั้นตอนที่ `project_status` เพิ่งระบุ ขั้นตอน `confirm` จำเป็นต้องมี `confirmed: true` หลังจากผู้ใช้ตอบตกลง ขั้นตอน `ask_user` จำเป็นต้องมีคำตอบของผู้ใช้เอง ส่วนขั้นตอน `human_only` และ `wait` จะถูกปฏิเสธพร้อมแจ้งสิ่งที่ต้องทำแทน |
| `add_data` | `project_dir`, `path`, `into?` (`parallel`, `test` หรือ `lexicon`), `source_col?`, `target_col?`, `sheet?`, `header?`, `usfm_source?`, `replace?` | นำเข้าไฟล์จากตำแหน่งของมัน — สเปรดชีต ตาราง Word พจนานุกรม Toolbox หรือ LIFT ไฟล์ ELAN หรือพระคัมภีร์ USFM (`champollion data add`) — และรายงานจำนวนนับและคอลัมน์ โดยไม่รายงานประโยคเด็ดขาด |
| `try_translation` | `project_dir`, `text` (สูงสุด 10 บรรทัด) | แปลประโยคของผู้ใช้สองสามประโยคด้วยโมเดลที่โปรเจกต์ให้บริการ สำหรับโมเดลที่เรียนรู้จากประโยคที่อยู่เฉพาะในเครื่อง จะส่งคืนที่อยู่หน้าเพจของโมเดลนั้นเอง โดยไม่ส่งข้อความประโยคกลับมาเด็ดขาด |
| `explain` | `topic`: `rails`, `privacy`, `quality`, `modes`, `improve` หรือ `off_rails` | คำอธิบายด้วยภาษาที่เข้าใจง่ายเพื่อส่งต่อให้ผู้ใช้ |

## โปรไฟล์ full

เนื้อหาทั้งหมดด้านล่างนี้อธิบายถึง **โปรไฟล์ full** — เครื่องมือครบทุกตัว สำหรับการค้นหาข้อมูล
การเบนช์มาร์ก และเครือข่าย:

```bash
npx -y champollion-mcp-server --profile full
```

## โปรดอ่านข้อความนี้ก่อนเริ่มใช้งานจริง

**ในโปรไฟล์ full มีเครื่องมือ 14 ตัวจากทั้งหมด 34 ตัวที่ทำงานได้ทันทีจากการติดตั้ง `npx` เปล่าๆ และ `translate` จะทำงานได้
เมื่อมีเอนจิน ส่วนอีก 19 ตัวที่เหลือจำเป็นต้องใช้แพ็กเกจ Python ซึ่งแพ็กเกจ npm
ไม่ได้จัดส่งมาด้วยและไม่สามารถจัดส่งมาให้ได้** เครื่องมือเหล่านี้จะไม่ล้มเหลวเงียบๆ — แต่ละตัวจะส่งคืนข้อผิดพลาดที่ระบุสิ่งที่ขาดหายไปพร้อมวิธีแก้ไข — แต่คุณควรทราบโครงสร้างนี้ไว้ก่อนวางแผนการทำงาน

| เครื่องมือ | ทำงานได้ทันทีหลัง `npx` หรือไม่? | สิ่งที่ต้องใช้เพิ่มเติม |
|---|---|---|
| `search_languages`, `get_language`, `language_overview`, `list_corpora`, `get_results`, `get_run_card`, `get_metric_reliability`, `list_contests`, `get_contest`, `get_project_info`, `list_queue`, `get_queue_item`, `estimate_cost`, `get_training_guardrails` | **ได้** — แบบอ่านอย่างเดียว ให้บริการจากเอนด์พอยต์สาธารณะ | ไม่ต้องใช้อะไรเพิ่มเติม |
| `translate` | **ได้** เมื่อมีเอนจิน | คีย์ API สำหรับเอนจินที่คุณเลือก — หรือไม่ต้องใช้ หากใช้วิธี `local` ร่วมกับเซิร์ฟเวอร์โมเดลบนเครื่องของคุณเอง |
| `run_benchmark`, `get_run_status`, `preview_publish`, `publish_report` | ไม่ได้ | evaluation harness — `pipx install mt-eval-harness` |
| เครื่องมือ `forge_*` ทั้ง 15 รายการ | ไม่ได้ | NMT Forge 0.2.0 หรือใหม่กว่า — `python3 -m pip install nmt-forge` (เพิ่ม `'nmt-forge[hf]'` เพื่อฝึกฝนและให้บริการ) ซึ่งจะรวม evaluation harness มาด้วยในตัวและค้นหาการ์ดภาษาได้เอง ไม่จำเป็นต้อง clone |

ไม่จำเป็นต้อง clone เรโพซิทอรีสำหรับขั้นตอนใดๆ เลย

## การทำงานของเครื่องมือ

**เรียกดูและประเมินค่าใช้จ่ายของงาน** `list_queue` และ `get_queue_item` ท่องดูคิวเบนช์มาร์กที่เปิดอยู่ — ซึ่งเป็นรายการการวัดผลที่จัดลำดับไว้ที่จะช่วยปรับปรุงแผนที่ได้มากที่สุด `estimate_cost` ประเมินราคาของชุดการรันก่อนที่คุณจะเสียค่าใช้จ่ายจริง

**ค้นหาข้อมูล** `search_languages` ค้นหาการ์ดภาษาตามชื่อ รหัส ตระกูลภาษา หรือภูมิภาค และรองรับการสะกดผิด แต่ละผลลัพธ์ยังระบุว่าภาษานั้นมีผู้พูดที่ใด (ประเทศ พิกัดบนแผนที่ มหาภูมิภาค) และชื่อเรียกอื่นๆ — เฉพาะข้อเท็จจริงที่การ์ดนั้นระบุแหล่งที่มา พร้อมแหล่งอ้างอิงแต่ละรายการ เพื่อให้สามารถแยกแยะภาษาที่มีชื่อคล้ายกันได้ ตำแหน่งที่ไม่มีแหล่งอ้างอิงจะไม่แสดงเด็ดขาด โดยบรรทัดนั้นจะแจ้งให้ทราบและให้ลิงก์ไปยังบันทึก Glottolog ของภาษานั้นแทน การ์ดที่ดึงข้อมูลมาจากตารางการ์ดที่เผยแพร่ของ champollion.dev (ในการติดตั้งผ่าน npm คือทุกภาษาที่อยู่นอกเหนือชุดหลักที่รวมมาด้วย) จะยังไม่มีแหล่งที่มารายฟิลด์ — ซึ่งจะมาพร้อมกับการอัปโหลดตารางในรอบถัดไป — ดังนั้นบรรทัดเหล่านั้นจึงมีลิงก์ Glottolog แทนที่จะเป็นตำแหน่งที่ตั้ง `language_overview` คือจุดเริ่มต้นหน้าเดียวสำหรับการสร้างโมเดลสำหรับภาษาใดภาษาหนึ่ง: สิ่งที่มีอยู่ สิ่งที่สามารถรันได้ และขั้นตอนถัดไป `get_language` ส่งคืนการ์ดฉบับเต็มพร้อมแหล่งอ้างอิง `list_corpora` แสดงรายการคลังข้อมูลการประเมินผลที่ลงทะเบียนไว้สำหรับคู่ภาษาหรือตระกูลเบนช์มาร์ก — แสดงเฉพาะข้อมูลกำกับ (เมทาดาตา: ขนาด สัญญาอนุญาต ระดับการปนเปื้อน และระบุว่า harness สามารถดึงข้อมูลได้ จำเป็นต้องใช้โทเค็นการเข้าถึง หรือถูกกักกันไว้); เนื้อหาคลังข้อมูลจะไม่ถูกส่งกลับมาเด็ดขาด และคู่ภาษาที่คลังข้อมูลทั้งหมดถูกกักกันจะแจ้งให้ทราบอย่างชัดเจนแทนที่จะดูเหมือนไม่รองรับ `get_results` และ `get_run_card` อ่านผลการรันที่ให้คะแนนแล้วจากลีดเดอร์บอร์ดสาธารณะ `get_metric_reliability` ตอบคำถามที่เอเจนต์ส่วนใหญ่ตอบผิด — *ฉันควรเชื่อถือเมตริกใดสำหรับภาษาเป้าหมายนี้* — จากความสัมพันธ์กับการตัดสินของมนุษย์แยกตามตระกูลภาษา `list_contests` และ `get_contest` แสดงการแข่งขันและเงื่อนไขที่ประกาศไว้ การเข้าร่วมการแข่งขันเป็นขั้นตอน CLI ที่ต้องได้รับการอนุญาตจากมนุษย์ ไม่ใช่ผ่านเครื่องมือ

**ลงมือปฏิบัติ** `translate` ส่งข้อความผ่านไปป์ไลน์ที่ทดสอบแล้ว พร้อม Translation
Memory (ข้อความซ้ำไม่มีค่าใช้จ่าย) และเกตคุณภาพแบบกำหนดได้ล่วงหน้า (deterministic quality gate) ทุกคำตอบ
จะระบุชื่อเอนจินที่รันจริง พร้อมโมเดลและเอนด์พอยต์หากมี
`run_benchmark` เริ่มต้นการประเมินผลและส่งคืน **รหัสงาน (job id) ในทันที**
เนื่องจากการรันจริงใช้เวลานานเกินกว่าการหมดเวลาของไคลเอนต์ คุณสามารถตรวจสอบสถานะด้วย `get_run_status` โดยใช้รหัสนั้น งานจะยังคงอยู่แม้เซิร์ฟเวอร์จะรีสตาร์ท: การรันจะดำเนินต่อไป และการตรวจสอบด้วยรหัสเดิมหลังจากนั้นจะยังคงได้สถานะและผลลัพธ์ ข้อมูลจะไม่ถูกเผยแพร่เว้นแต่คุณจะส่ง `publish: true`; จากนั้นแผนงานจะระบุสิ่งที่จะเปิดเผยต่อสาธารณะ — ทุกแถวพร้อมข้อความประโยค หรือคะแนนเพียงอย่างเดียว; พรอมต์ หรือเฉพาะค่าแฮชของพรอมต์; และเผยแพร่ที่ใด — และการเผยแพร่จริงจำเป็นต้องระบุ `publish_ack` ตามข้อความตรงตัวที่แผนงานให้ไว้ เพื่อให้แน่ใจว่าผู้ใช้ได้เห็นข้อความนั้นก่อน การรันที่ทำโดยไม่มีพารามิเตอร์นี้สามารถเผยแพร่ในภายหลังได้ภายใต้เกตเดียวกัน `preview_publish` เป็นแบบอ่านอย่างเดียว:
จะแสดงตัวอย่างการเผยแพร่ของ harness เอง ข้อความตรงตัว และการเรียก `publish_report` ตรงตัวที่จะทำการเผยแพร่ โดยตัวมันเองไม่สามารถเผยแพร่ได้ มีแอนโนเทชัน MCP `readOnlyHint: true` กำกับไว้ ดังนั้นโฮสต์ของเอเจนต์ที่ถามยืนยันก่อนการเขียนทุกครั้งจึงสามารถอนุญาตได้โดยอัตโนมัติ `publish_report` ทำหน้าที่เขียนข้อมูล
(กำกับด้วย `destructiveHint` และ `openWorldHint`) และ `scores_only`
จะระงับการส่งข้อความประโยค ทุกแผนงานจะเปิดด้วยสถานะ `EVAL PACK:` ของภาษาเป้าหมาย — `missing` (พร้อมคำสั่งสำหรับติดตั้ง) `ready` หรือ `none needed` — และระบุสัญญาอนุญาตของคลังข้อมูลพร้อมข้อกำหนด `do_not_train` เนื่องจากเป็นการรันที่ส่ง `--yes` การขาด FST (ตัววิเคราะห์หรือรันไทม์ pyhfst) จะไม่ทำให้การรันหยุดลง: การรันจะดำเนินต่อไป และการ์ดการรันจะทำเครื่องหมายว่าการยอมรับของ FST ไม่ได้ถูกคำนวณ ส่วนประกอบอื่นๆ ที่ขาดหายไปจะหยุดการรันก่อนที่จะเริ่มแปล `skip_fst` และ `skip_eval_standard` จะให้คะแนนโดยไม่มีส่วนประกอบเหล่านั้น และการ์ดการรันจะทำเครื่องหมายสิ่งที่ละเว้นไว้ แผนงานยังระบุด้วยว่าจะมีการคำนวณ COMET หรือไม่ (harness จะคำนวณเมื่อใดก็ตามที่ติดตั้ง `unbabel-comet` ไว้; `comet: true` กำหนดให้การรันต้องใช้ค่านี้) และ `metricx` กับ `fuse`
จะร้องขอ MetricX-24 แบบเลือกเปิดใช้ของ harness และตัวเปรียบเทียบรูปแบบ FUSE สำหรับแต่ละรายการ แผนงานจะแจ้งจาก harness ว่าได้ติดตั้งไว้แล้วหรือไม่ ต้องติดตั้งอะไร และจะดาวน์โหลดอะไรบ้าง การรันที่ยืนยันแล้วซึ่งร้องขอเมตริกที่ harness ไม่สามารถคำนวณได้จะถูกปฏิเสธ แทนที่จะรันต่อโดยไม่มีเมตริกนั้น บรรทัด `Results:`
และ `Cache:` ของแผนงานจะระบุตำแหน่งที่บันทึกการรัน รายงาน และแคชการแปลถูกบันทึกไว้
ไฟล์ทดสอบที่อยู่ในโฟลเดอร์ซึ่ง `mt-eval contest prepare` ระบุว่าสามารถเผยแพร่ได้
(`public/` ของการแข่งขัน) จะรันไปยังโฟลเดอร์ `runs/` ของการแข่งขันแทน เพื่อไม่ให้สิ่งใดที่การรันเขียนขึ้นถูกเผยแพร่ไปพร้อมกัน โมเดลบนเครื่องของคุณเอง (เซิร์ฟเวอร์ในเครื่อง หรือ `method: "local-model"` ซึ่ง harness จะรันภายในโพรเซสและไม่ต้องการการรับรอง) จะรายงานเป็น `$0 API cost (runs on this machine)`

**ฝึกฝนโมเดลโดยไม่หลอกตัวเอง** `get_training_guardrails` ส่งคืนกฎเกณฑ์
ที่สกัดมาจากความล้มเหลวที่วัดผลได้จริง เครื่องมือ `forge_*` ทั้ง 15 รายการจะรัน
[NMT Forge](/docs/agents/training) ทีละขั้นตอนโดยมีระบบป้องกัน
— `forge_status` ในขั้นตอนแรกและหลังจบทุกขั้นตอน (จะระบุคำสั่งถัดไปและเครื่องมือที่ใช้รันคำสั่งนั้น), `forge_preflight` เพื่อตรวจสอบว่าคำสั่งจะติดเกตใดก่อนที่จะถูกปฏิเสธ, `forge_prereg_template` และ `forge_prereg`
เพื่อบันทึกการคาดการณ์ล่วงหน้าก่อนที่จะมีคะแนนการทดสอบใดๆ (และก่อนที่จะทำการเบนช์มาร์กบนชุดทดสอบ: การอ่านคะแนนจะบล็อกการลงทะเบียนล่วงหน้าในภายหลัง), `forge_export` เพื่อให้คะแนนชุดทดสอบหนึ่งครั้งและรวมแพ็กเกจโมเดลที่ฝึกฝนแล้ว, `forge_compare` เพื่อเปรียบเทียบ A/B ระหว่างสองโมเดลพร้อมข้อควรระวังเรื่องคู่เหมือน (near-twin) ของแต่ละโมเดลกำกับไว้ข้างผู้ชนะ และ
`forge_prereg_verdict` เพื่อบันทึกคำตัดสินของผู้ใช้เองเกี่ยวกับการคาดการณ์ที่ forge ไม่สามารถตัดสินได้ (ช่วงข้อความอิสระ) — ซึ่งจะแสดงเป็นคำตัดสินของมนุษย์ ไม่ใช่ผลจากการคำนวณเด็ดขาด `forge_status` แสดงรายการการรันที่ฝึกฝนแล้วทุกรายการพร้อมคะแนน dev และแจ้งเตือนเมื่อชุด dev อิ่มตัว (คะแนน dev สมบูรณ์แบบจนไม่มีเกณฑ์ให้การเลือกเช็กพอยต์ตัดสินใจได้) เมื่อ eval harness ใส่ข้อควรระวังไว้กับคะแนนทดสอบ (เช่น ผลลัพธ์แทบจะคงที่: ข้อความผลลัพธ์เพียงหยิบมือเดียวถูกส่งออกมาสำหรับทุกประโยคต้นทาง) `forge_export`, `forge_status`,
`forge_compare` และ `forge_lint` จะนำข้อความเตือนของ harness เองมาแสดงอย่างตรงตัว และข้อควรระวังสำคัญจะปรากฏขึ้นก่อนในขั้นตอนถัดไป: คะแนนจะไม่ถูกอ้างอิงโดยปราศจากข้อควรระวังเด็ดขาด เมื่อมีข้อปฏิเสธ ระบบจะส่งกลับพร้อมรายละเอียดว่าเกิดอะไรผิดพลาด เหตุใดจึงสำคัญ และวิธีแก้ไข มีสองขั้นตอนที่ใช้เวลานานเกินกว่าการเรียกใช้เครื่องมือใดๆ และต้องรันในเทอร์มินัลแทน: การฝึกฝน (`nmt-forge run`) และการให้บริการโมเดลที่ส่งออก (`nmt-forge serve` ซึ่งจะนำโมเดลไปอยู่เบื้องหลังเอนด์พอยต์ในเครื่องที่ `translate` และ CLI สามารถใช้งานได้)

`get_metric_reliability { "target": "crk" }` เป็นการถามคำถามเดียวกัน

### การแปลด้วยโมเดลที่คุณนำไปใช้งาน (deploy)

`nmt-forge serve` จะพิมพ์ที่อยู่สองรายการสำหรับโมเดลที่ให้บริการอยู่ คุณสามารถชี้
`translate` ไปยังที่อยู่ใดที่หนึ่งได้:

| อาร์กิวเมนต์ | ใช้ร่วมกับ | ตัวอย่าง |
|---|---|---|
| `base_url` | `method: "local"` — เซิร์ฟเวอร์ที่เข้ากันได้กับ OpenAI (รวมถึง `"openai"`) | `http://127.0.0.1:8378/v1` |
| `endpoint` | `method: "api"` — สัญญา API ของ Champollion | `http://127.0.0.1:8378/translate` |
| `model` | เอนจิน LLM เท่านั้น; จะถูกปฏิเสธสำหรับ API การแปลภาษาด้วยเครื่อง ซึ่งไม่มีพารามิเตอร์นี้ | `llama3.1` |
| `project_dir` | เมธอดใดก็ได้ — ใช้ Translation Memory ของโปรเจกต์นั้น | `~/my-app` |

เซิร์ฟเวอร์บนเครื่องของคุณเองไม่จำเป็นต้องใช้คีย์ ส่วนเอนด์พอยต์ `api` ทางไกลจะอ่านคีย์จาก
`CHAMPOLLION_API_KEY` ในสภาพแวดล้อมของเซิร์ฟเวอร์ เครื่องมือจะปฏิเสธอาร์กิวเมนต์ที่ไม่รู้จักโดยระบุชื่อ
แทนที่จะเพิกเฉย เพื่อป้องกันไม่ให้อาร์กิวเมนต์ที่สะกดผิดส่งข้อความของคุณไปยังโมเดลอื่นโดยไม่รู้ตัว

### ตำแหน่งที่เซิร์ฟเวอร์เก็บสถานะ

ทุกสิ่งจะถูกจัดเก็บไว้ใน `~/.champollion-mcp/` (กำหนดค่า `CHAMPOLLION_MCP_HOME` เพื่อย้าย
ตำแหน่ง):

- **Translation Memory ของ `translate`** เป็นไฟล์ของมันเอง
  คือ `.champollion/tm.json` ในโฟลเดอร์นั้น ซึ่งแยกจาก `.champollion/tm.json` ของโปรเจกต์ใดๆ
  ให้ส่ง `project_dir` เพื่อใช้ไฟล์ของโปรเจกต์แทน ซึ่งเป็นไฟล์เดียวกับที่ `champollion sync` ใช้งานที่นั่น
- **งานของ `run_benchmark`** จะถูกบันทึกไว้ใน `jobs.json` ซึ่งจะเก็บงาน
  ล่าสุด 50 รายการ แต่ละงานจะมีโฟลเดอร์ใน `jobs/` พร้อมผลลัพธ์ของงาน และสำหรับรายการในคิวหรือคลังข้อมูลที่ลงทะเบียนไว้ จะมีผลลัพธ์ของ harness รวมอยู่ด้วย การรันบนไฟล์ทดสอบที่คุณครอบครองจะเขียนผลลัพธ์และแคชไว้ข้างๆ ไฟล์นั้น ใน
  `results/` — ยกเว้นไฟล์ในโฟลเดอร์ที่ `mt-eval contest prepare`
  ทำเครื่องหมายว่าเผยแพร่ได้ ซึ่งการรันจะเขียนไปยังโฟลเดอร์ `runs/` ของการแข่งขันแทน การรันแต่ละครั้งดังกล่าวจะได้โฟลเดอร์ `mcp-run-<id>/` ของตัวเองที่นั่น และ `get_run_status`
  จะพิมพ์คำสั่ง `mt-eval compare` ครอบคลุมการรันทั้งหมดเหล่านั้น
  (`results/mcp-run-*/*_report.json`)
  การรันคิวจะเขียนรายงานไปยัง `eval/logs/harness/queue/` ภายใต้โฟลเดอร์การทำงานของเซิร์ฟเวอร์ เช่นเดียวกับที่ harness ทำเสมอ

:::note[การจำกัดค่าใช้จ่ายถูกออกแบบไว้โดยเฉพาะ]
`run_benchmark` **ปฏิเสธการรันคิวที่ไม่มีการกำหนดขอบเขต** คุณต้องส่งขอบเขตเพียงหนึ่งรายการอย่างแน่นอน — `budget`, `top` หรือ `item_id` ที่ระบุเจาะจง ไม่มีการเรียกใช้งานแบบ "รันคิวไปเรื่อยๆ" เพราะมิฉะนั้นเอเจนต์ที่เข้าใจคิวผิดอาจก่อให้เกิดค่าใช้จ่ายโดยไม่มีขีดจำกัด
:::

## เวอร์ชันของโพรโทคอล

การรับส่งข้อมูลเป็นแบบ **stdio เท่านั้น** — หนึ่งโพรเซสเซิร์ฟเวอร์ต่อหนึ่งเอเจนต์

[การปรับปรุงแก้ไขเมื่อ 2026-07-28](https://blog.modelcontextprotocol.io/posts/2026-07-28/) ของ MCP
ได้เปลี่ยนให้โพรโทคอลเป็นแบบไร้สถานะ (stateless) โดยค่าเริ่มต้น โดยยกเลิกการแฮนด์เชก `initialize` และ
เฮดเดอร์ `Mcp-Session-Id` เซิร์ฟเวอร์นี้ไม่ได้รับผลกระทบในเชิงการออกแบบ: เนื่องจากไม่ได้ใช้ความสามารถใดๆ ที่ถูกเลิกใช้ไปแล้ว (Roots, Sampling, Logging), ไม่เคยใช้การรับส่งข้อมูลแบบเดิมอย่าง HTTP+SSE และได้ปฏิบัติตามแนวทางใหม่สำหรับสถานะระหว่างการเรียกใช้ (cross-call state) อยู่แล้ว —
`run_benchmark` จะสร้างแฮนเดิลงาน (job handle) ขึ้นมาอย่างชัดเจนเพื่อให้โมเดลส่งกลับมา แทนที่จะพึ่งพาเซสชันของการรับส่งข้อมูล

เซิร์ฟเวอร์นี้ยัง **ไม่ได้** อัปเกรดเป็นรุ่นแก้ไขใหม่ เนื่องจากยังไม่มี TypeScript SDK ที่เผยแพร่ออกมารองรับรุ่นดังกล่าว โปรดดู [README ของเซิร์ฟเวอร์](https://github.com/gamedaysuits/Champollion/tree/main/mcp-server) สำหรับคำชี้แจงฉบับเต็ม
