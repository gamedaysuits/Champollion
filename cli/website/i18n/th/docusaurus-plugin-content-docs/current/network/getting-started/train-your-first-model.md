# ฝึกโมเดลแรกของคุณ (ด้วย agent ของคุณ)

คุณไม่จำเป็นต้องรู้วิธีฝึกโมเดลการแปลด้วยเครือข่ายประสาทเทียม สิ่งที่คุณต้องทำคือ **บอก coding agent ว่าคุณต้องการอะไร** — Claude, หรือโมเดลระดับ Sonnet/Flash, หรือ agent ใดก็ตามที่สามารถรันคำสั่ง shell ได้ **nmt-forge** ถูกออกแบบมาให้ agent ขับเคลื่อนได้ *อย่างเป็นระบบ*: ในทุกขั้นตอน เครื่องมือจะบอก agent อย่างชัดเจนว่าต้องทำอะไรต่อไป และจะปฏิเสธ — อย่างชัดเจน พร้อมวิธีแก้ไข — เมื่อขั้นตอนใดจะทำให้ผลลัพธ์ของคุณเสียหาย

หน้านี้ครอบคลุมกระบวนการทั้งหมด ตั้งแต่ `pip install` ไปจนถึงโมเดลที่ champollion CLI สามารถเรียกใช้งานได้ แต่ละขั้นตอนเขียนขึ้นในรูปแบบ **สิ่งที่คุณบอกเอเจนต์ของคุณ**, **สิ่งที่ forge ทำ**, **ลักษณะของการปฏิเสธ (refusal)** (เพื่อให้ทั้งคุณและเอเจนต์ไม่ตื่นตระหนกเมื่อเกิดการปฏิเสธขึ้น — เพราะการปฏิเสธแสดงว่าเครื่องมือกำลังทำงานได้อย่างถูกต้อง) และท้ายที่สุดคือ **วิธีอ่านรายงานสรุป** เนื้อหานี้เป็นส่วนของ forge ในขั้นตอนที่ 2 และ 4 ของ [สร้าง MT สำหรับภาษาของคุณ](/docs/build-mt-for-your-language) ซึ่งครอบคลุมสิ่งที่เกิดขึ้นก่อนหน้า (การค้นหาสิ่งที่มีอยู่แล้ว), ช่วงระหว่างกลาง (การวัดผลตัวเลือกที่มีอยู่) และหลังจากนั้น (การเผยแพร่, การรวมวิธีการต่าง ๆ)

**ลำดับขั้นตอนมีความสำคัญอย่างยิ่ง** ให้ลงทะเบียนชุดทดสอบ (test set) ของคุณ, ตรวจกรองข้อมูลการฝึกฝน (training data) เทียบกับชุดทดสอบนั้น และบันทึกการคาดการณ์ (predictions) ของคุณไว้ (ขั้นตอนที่ 1–3) **ก่อนที่จะมีการให้คะแนนใด ๆ บนชุดทดสอบ** — รวมถึงค่าเกณฑ์มาตรฐาน (baselines) ในขั้นตอนที่ 3 ของคู่มือที่วัดด้วย `mt-eval run` เพราะการเบঞ্চมาร์กถือเป็นการอ่านเพื่อคิดคะแนน (scoring read): forge จะนับจำนวนครั้งไว้ และจะปฏิเสธการคาดการณ์ที่บันทึกหลังจากนั้น จากนั้นจึงทำการแบ่งชุดข้อมูลและเริ่มฝึกฝน (ขั้นตอนที่ 4)

:::tip กฎข้อเดียวสำหรับเอเจนต์ของคุณ
บอกเอเจนต์ว่า: *"ให้รัน `nmt-forge status --json` ก่อนเสมอ และรันหลังจบทุกขั้นตอน ปฏิบัติตามสิ่งที่ `next_command` ของคำสั่งระบุไว้"* นิสัยเพียงข้อเดียวนี้จะเปลี่ยน forge ให้กลายเป็นรางนำทาง ทุกคำสั่งของ forge รองรับ `--json`: ส่งออกเอกสาร JSON หนึ่งชุดทาง stdout พอดี และการปฏิเสธจะถูกส่งกลับมาเป็น `{"error": {…, "why", "fix"}}` พร้อม exit code 2 หากเอเจนต์ของคุณเชื่อมต่อผ่าน MCP กระบวนการลูปเดียวกันนี้คือเครื่องมือ `forge_status` (`{ "project_dir": "<dir>" }`) — ดูที่ [คู่มือสำหรับเอเจนต์](/docs/network/getting-started/agent-guide)
:::

## ขั้นตอนที่ 0 — ติดตั้ง และกำหนดภาษาเป้าหมายให้เอเจนต์ของคุณ

**คุณบอกว่า:** *"ติดตั้ง nmt-forge พร้อม training extra ฉันต้องการฝึกฝนโมเดลภาษาอังกฤษ→[ภาษาของคุณ] เริ่มต้นด้วยการค้นหาว่า forge รู้อะไรเกี่ยวกับภาษานี้บ้าง รหัส ISO 639-3 คือ `crk`"* (ใช้รหัสภาษาของคุณ)

```bash
python3 -m pip install 'nmt-forge[hf]'      # Python 3.11+; brings mt-eval-harness (the scorer)
```

แพ็กเกจเสริม `[hf]` จะเพิ่มไลบรารีสำหรับการฝึกฝน (torch, transformers, accelerate, tokenizers, sentencepiece, peft) ซึ่ง wheel เวอร์ชัน CPU-only ก็เพียงพอสำหรับโมเดลเริ่มต้นแล้ว ส่วน `python3 -m pip install nmt-forge` แบบปกติจะให้ระบบป้องกัน (guards), การแบ่งชุดข้อมูล (splits), การตรวจสอบ (audits) และการให้คะแนน (scoring) โดยไม่มีส่วนการฝึกฝน

**สิ่งที่ forge ทำ:** `nmt-forge discover crk` จะอ่านการ์ดข้อมูลของภาษา — ระบบการเขียน, พจนานุกรม, ตัววิเคราะห์ทางสัณฐานวิทยา (morphological analyzers), คลังข้อมูล (corpora) และชุดประเมินผลที่มีอยู่ (พร้อมแฟล็ก `do_not_train` / กักกัน หากมี) รวมถึงเมทริกซ์อ้างอิงเฉพาะภาษา (referee metrics) คุณไม่จำเป็นต้องมีสำเนาของ Champollion repository: การ์ดจะถูกค้นหาจากไดเรกทอรีที่คุณระบุ (`--cards-dir`), เช็กเอาต์ในเครื่องหรือ `node_modules/champollion` หรือดัชนีการ์ดสาธารณะ (ซึ่งมีการแคชไว้ จึงใช้งานแบบออฟไลน์ได้หลังจากนั้น) จากนั้น forge จะจัดวางภาษาของคุณลงบน **ลำดับขั้นของสินทรัพย์ (asset ladder)**: (1) ข้อความคู่ขนาน (parallel text) → การฝึกฝนที่มีระบบป้องกัน; (2) + ข้อความภาษาเดียว (monolingual) → การแปลย้อนกลับแบบติดแท็ก (tagged backtranslation); (3) + พจนานุกรม/ไวยากรณ์ → ข้อมูลสังเคราะห์ที่มีการอ้างอิง; (4) + ตัววิเคราะห์ → การสังเคราะห์ที่ยืนยันแบบไป-กลับ (round-trip-verified synthesis); (5) + เมทริกซ์อ้างอิง → เมทริกซ์เฉพาะของภาษานั้นในการให้คะแนนและคัดเลือกเช็กพอยต์

**ช่องว่างหมายถึง UNKNOWN ไม่ใช่ศูนย์** การ์ดที่มีข้อมูลน้อยไม่ได้หมายความว่า "ภาษานี้ไม่มีทรัพยากร" — อาจเป็นเพราะยังไม่ได้บันทึกทรัพยากรนั้นไว้ คุณสามารถนำคลังข้อมูลคู่ขนานของคุณเองมาใช้ได้เสมอ

จากนั้น: *"สร้างโครงสร้างโปรเจกต์ (Scaffold)"*

```bash
nmt-forge init crk --dir school-mt && cd school-mt
```

ขั้นตอนนี้จะสร้างพื้นที่ทำงาน (`.forge/`), ไฟล์เริ่มต้น `config.json` และบรีฟ `NEXT_STEPS.md` พร้อมลำดับคำสั่งที่แน่นอน **โปรดรันทุกคำสั่งหลังจากนี้จากภายในไดเรกทอรีของโปรเจกต์** — เนื่องจากพาธในไฟล์คอนฟิกจะเป็นแบบสัมพัทธ์ (relative) กับไดเรกทอรีดังกล่าว

คอนฟิกเริ่มต้นจะใช้พรีเซ็ตโมเดล **`cpu-tiny`** เว้นแต่คุณจะเลือกแบบอื่น:

| `--model` | คืออะไร | สิ่งที่ต้องใช้ | สิ่งที่คาดหวังได้ |
|---|---|---|---|
| `cpu-tiny` (ค่าเริ่มต้น) | โมเดล transformer ขนาดเล็ก (~6M พารามิเตอร์) ที่ฝึกฝนตั้งแต่เริ่มต้น (from scratch) บนคู่ประโยคของคุณ; คลังคำศัพท์จะเรียนรู้จากแถวข้อมูลการฝึกฝนของคุณเท่านั้น | CPU, ไม่ต้องดาวน์โหลด | ค่อนข้างต่ำ: สำหรับคู่ประโยค 1–2 พันคู่ ค่า chrF++ จะอยู่ที่ประมาณ 5–30 (แตะระดับบนเฉพาะข้อมูลที่เป็นเทมเพลตซ้ำ ๆ สูง) โมเดลจะเรียนรู้วลีและรูปแบบของข้อมูลที่คุณมี ไม่ใช่ภาษาโดยรวม |
| `cpu-finetune --base <hf-id>` | ไฟน์จูนโมเดล Marian/opus-mt ขนาดเล็กที่ผ่านการพรีเทรนแล้วตามที่คุณระบุ (เลือกโมเดลสำหรับคู่ภาษาที่ *มีความเกี่ยวข้องกัน*) | CPU, ดาวน์โหลด ~300 MB | มักจะดีกว่า `cpu-tiny` เมื่อมีคู่ภาษาที่เกี่ยวข้องกันอยู่ — ให้วัดผลบนชุด dev ของคุณ อย่าด่วนสรุปเอง |
| `nllb-600m` | NLLB-200 distilled 600M พร้อม LoRA | GPU, ดาวน์โหลด ~2.5 GB | จุดเริ่มต้นที่ทรงพลังที่สุด; การตรวจสอบ wall-clock ของ forge จะปฏิเสธการรันบน CPU ภายในไม่กี่นาที |

พรีเซ็ตจะถูกเขียนเป็นตัวเลขอย่างชัดเจนใน `config.json` → `model` จึงไม่มีอะไรถูกซ่อนไว้ และการเปลี่ยนตัวเลขจะทำให้เกิดการรันใหม่ที่มีค่าแฮชแยกต่างหาก

**ไม่มีการ์ดสำหรับภาษาของคุณใช่ไหม?** `nmt-forge init <code> --no-card --name "<name>"` ยังคงสร้างโครงสร้างโปรเจกต์ได้ ทุกสิ่งที่การ์ดควรระบุจะถูกบันทึกเป็น unknown (ไม่ระบุ) และไม่มีการแต่งเติมข้อมูลใด ๆ ขึ้นเอง

## ขั้นตอนที่ 1 — แยกชุดทดสอบออกมา และลงทะเบียน {#step-1--set-your-test-set-aside-then-split}

**คุณบอกว่า:** *"นี่คือคลังข้อมูลคู่ขนานของฉัน และแยกต่างหากคือชุดทดสอบที่ผ่านการตรวจสอบโดยครูผู้สอนแล้ว อย่าให้ชุดทดสอบนี้เข้าไปอยู่ในการฝึกฝน และลงทะเบียนก่อนที่จะมีการให้คะแนนใด ๆ บนชุดนี้"*

ไฟล์สามารถเป็นรูปแบบ `.tsv` (ข้อความต้นทาง, แท็บ (TAB), ตามด้วยคำแปล หนึ่งคู่ต่อหนึ่งบรรทัด; บรรทัดที่ขึ้นต้นด้วย `# ` คือความคิดเห็น) หรือ `.jsonl` (`{"source": …, "target": …}` ต่อหนึ่งบรรทัด) หากชุดทดสอบเป็นแบบส่วนตัว (private) ให้ทำเครื่องหมายเป็น local-only **ก่อนที่** จะมีสิ่งใดอ่านไฟล์นั้น — รวมถึงเอเจนต์ของคุณด้วย: `echo '{"transmission": "local-only"}' > ~/teacher-test.tsv.champollion.json` จากนั้น forge จะไม่พิมพ์ประโยคในชุดทดสอบออกมาเลย

**สิ่งที่ forge ทำ — หากคุณมีชุดทดสอบของตนเองอยู่แล้ว** (กรณีทั่วไปสำหรับโรงเรียนหรือคลินิก):

```bash
nmt-forge registry add project-test ~/teacher-test.tsv --role test
```

การลงทะเบียนจะเริ่มต้น **บันทึกการอ่าน (read log)** ของไฟล์ (`<file>.reads.jsonl`): นับจากนี้เป็นต้นไป ทุกการคิดคะแนนบนไฟล์นี้ — ไม่ว่าจะโดย forge หรือโดย `mt-eval run` / `mt-eval compare` — จะถูกนับจำนวนครั้งไว้ นี่คือเหตุผลว่าทำไมการลงทะเบียนจึงต้องมาก่อน: เพราะการรันเบঞ্চมาร์กที่ทำขึ้นก่อนการลงทะเบียนจะถูกระบุไว้ตอนลงทะเบียน แต่จะไม่ถูกนับรวม

**หากคุณไม่มีชุดทดสอบแยกต่างหาก** ให้ตัดแบ่งออกมาจากคลังข้อมูลแทน — `nmt-forge split pairs.tsv --test 150 --dev 100 --seed 42 --out data/split --register project` registers `project-test` and `project-dev` ได้ในขั้นตอนเดียว (ขั้นตอนที่ 4 จะอธิบายการแบ่งชุดข้อมูล) — แล้วข้ามไปยังขั้นตอนที่ 3 ได้เลย

ตอนนี้ `nmt-forge status` จะระบุขั้นตอนถัดไป: การคาดการณ์ (ขั้นตอนที่ 3) ก่อนการเบঞ্চมาร์กใด ๆ — ให้ตรวจกรองคลังข้อมูลของคุณก่อน (ขั้นตอนที่ 2)

## ขั้นตอนที่ 2 — ตรวจสอบการรั่วไหลของข้อมูล

**คุณบอกว่า:** *"ก่อนที่เราจะเริ่มฝึกฝน ให้ตรวจสอบคลังข้อมูลเทียบกับชุดทดสอบ และบอกฉันว่าคุณจะตัดอะไรออกบ้างและเพราะเหตุใด"*

```bash
nmt-forge leak-audit ~/pairs.tsv --clean-to pairs.clean.jsonl
```

**สิ่งที่ forge ทำ:** ระบบจะตรวจกรองทุกแถวเทียบกับชุด dev/test/sealed ที่ลงทะเบียนไว้ทั้งหมด คลังข้อมูลเดียวกันและชุดข้อมูลที่ลงทะเบียนเดียวกันจะให้ผลลัพธ์เดิมเสมอ และระบบจะอธิบายสิ่งที่จะ **ตัดออก (drop)**:

- **พรอมต์ตรงกันทุกประการ (Identical prompt)** — ประโยคต้นทางของแถวนั้นตรงกับประโยคต้นทางของแถวในชุดทดสอบ (หลังละเว้นตัวพิมพ์เล็ก-ใหญ่ เครื่องหมายวรรคตอน และช่องว่างแล้ว) จะถูกตัดออก **แม้คำแปลของแถวนั้นจะแตกต่างกันก็ตาม**: เนื่องจากโมเดลจะได้ฝึกฝนกับพรอมต์ทดสอบที่ตรงกันเป๊ะ
- **คำตอบตรงกันทุกประการ (Identical answer)** — ข้อความปลายทางของแถวนั้นตรงกับเฉลยอ้างอิงในชุดทดสอบ
- **คำตอบเกือบซ้ำกัน (Near-duplicate answer)** — ข้อความปลายทางของแถวนั้นมีคำที่ตรงกับคำตอบทดสอบอย่างน้อย 60% (ละเว้นเครื่องหมายกำกับเสียง เพื่อให้นับรวมรูปแบบการสะกดที่ต่างกัน) **และ** ครอบคลุมคำตอบทั้งหมด เป็นส่วนหนึ่งของคำตอบ หรือมีความเหมือนกันอย่างน้อย 90% เพราะจะถือว่าโมเดลได้เห็นคำตอบเกือบทั้งหมดแล้ว

…และสิ่งที่ระบบ **ตั้งใจเก็บไว้ (keeps on purpose)** ซึ่งจะรายงานให้ทราบแต่จะไม่ถูกลบออก:

- **คู่ต่างตามเทมเพลต (Template siblings)** — แถวข้อมูลใช้โครงสร้างประโยคร่วมกับคำตอบในชุดทดสอบ แต่มีการสลับคำในแต่ละด้าน (*"I see the dog"* / *"I see the cat"*) โมเดลยังคงต้องสร้างคำที่ไม่เคยเห็นในโครงสร้างประโยคนั้น คลังข้อมูลจากหนังสือเรียนและโรงเรียนที่เป็นเทมเพลตมักเต็มไปด้วยรูปแบบเหล่านี้ forge จะแสดงรายการแถวทดสอบที่มีคู่ต่างในการฝึกฝน และเนื่องจากคอนฟิกเริ่มต้นได้ตั้งค่า `eval.near_dupe_corpus` ไว้ รายงานสรุปสุดท้ายจึงแสดงคะแนน **"(strict)"** บนแถวข้อมูลที่ไม่มีคู่ต่างเทียบเคียงควบคู่ไปกับคะแนนเต็ม
- **พรอมต์คล้ายกัน แต่คำตอบต่างกัน (Similar prompt, different answer)** — ต้นทางเกือบจะซ้ำกัน (ไม่ใช่สำเนาที่เหมือนกันทุกประการ) กับต้นทางในชุดทดสอบ แต่คำแปลแตกต่างกัน ซึ่งถือเป็นความเปรียบต่างขั้นต่ำที่ถูกต้องตามหลัก (minimal contrast) ไม่ใช่การรั่วไหลของข้อมูล

นี่คือตัวอย่างรายงานสำหรับคลังข้อมูลจำลองขนาด 12 แถว ที่ผ่านการตรวจกรองเทียบกับชุดทดสอบขนาด 3 แถว (ตัดทอนข้อความ; ประโยคจำลองเป็นภาษาอังกฤษโดยมีปลายทางคล้ายภาษาฝรั่งเศส):

```
leak-audit: pairs.tsv — 12 rows screened against project-test [test, 3 rows]

DROPPED by --clean-to: 4 row(s) — the model would see an eval answer (or prompt)
  • identical PROMPT: the row's source equals an eval row's source ...
      project-test (test): 2
      e.g. line 2 "The library opens at nine." → project-test row 2
      e.g. line 3 "The library opens at nine!" → project-test row 2
  • identical ANSWER: the row's target equals an eval row's reference ...
      project-test (test): 1
  • near-duplicate ANSWER: the row's target overlaps an eval answer and only adds/removes words ...
      project-test (test): 1
      e.g. line 6 "ou est la grande grange rouge maintenant?" → project-test row 3 (contains the whole answer; overlap 0.86)

KEPT on purpose (reported, never removed): 1 row(s)
  • template sibling: shares a sentence frame with an eval answer but swaps a word each way ...
      e.g. line 1 "je vois le chat dans la maison." → project-test row 1 (swaps word(s); overlap 0.75)

Cleaned: 8 row(s) kept → pairs.clean.jsonl (audit manifest: pairs.clean.audit.json)
```

บรรทัดที่ 3 มีคำแปลที่ *แตกต่าง* จากแถวในชุดทดสอบ แต่ก็ยังคงถูกตัดออก: เนื่องจากพรอมต์ของบรรทัดนี้คือพรอมต์ทดสอบ

ตัวอย่างจะอ้างอิงแถวจาก **คลังข้อมูลของคุณ** ตามหมายเลขบรรทัด โดยจะไม่มีการพิมพ์ข้อความของไฟล์ทดสอบออกมาเลย และแถวที่ตรงกับชุดข้อมูล **แบบปิดผนึก (sealed)** จะแสดงเฉพาะหมายเลขบรรทัดเท่านั้น (ในกรณีที่แถวคลังข้อมูลเหมือนกับแถวทดสอบทุกประการ หรือมีแถวทดสอบรวมอยู่ การอ้างอิงแถวคลังข้อมูลก็จะแสดงประโยคทดสอบนั้นไปด้วย — ให้ส่ง `--no-examples` หากจะมีการแชร์ผลลัพธ์นี้)

`--clean-to pairs.clean.jsonl` จะเขียนเฉพาะแถวที่ผ่านการคัดกรอง พร้อมทั้งบันทึกการตรวจสอบที่ไม่มีเนื้อหาข้อความ (content-free audit record) ไว้ข้างกัน (`pairs.clean.audit.json`) ให้ตรวจกรองคลังข้อมูล **ก่อนที่** คุณจะทำการแบ่งชุดข้อมูล (ขั้นตอนที่ 4 จะแบ่งไฟล์ที่ทำความสะอาดแล้ว) อย่าตรวจกรองคลังข้อมูลทั้งหมดซ้ำหลังจากตัดแบ่งชุด dev ออกมาแล้ว — เพราะแถวของชุด dev จะตรงกับตัวเองและถูกตัดทิ้ง ตรวจกรองข้อมูล *เพิ่มเติม* ใด ๆ (ข้อมูลที่ดึงจากเว็บ, ข้อความภาษาเดียว) ด้วยวิธีเดียวกันนี้ก่อนจะนำไปเพิ่มในการฝึกฝน

**การตรวจกรองไม่ได้ทำให้ชุดทดสอบถูกใช้ไป** leak-audit จะอ่านชุดทดสอบเพื่อเปรียบเทียบแถวข้อมูล และ forge จะบันทึกการอ่านนั้นเป็นการอ่านเพื่อการ *ตรวจสอบ (audit)* ไม่ใช่การอ่านเพื่อการคิดคะแนน: จึงไม่เป็นอุปสรรคต่อการคาดการณ์ที่คุณจะเขียนในขั้นตอนที่ 3

**อ่านคำวินิจฉัย (verdict) เป็นอันดับแรก** (บรรทัด `VERDICT:`; หรือเมื่อใช้ `--json` คือคีย์ `verdict`) หากผลระบุว่าแถวทดสอบส่วนใหญ่มีประโยคคู่แฝด (near-twin) อยู่ในคลังข้อมูล โมเดลที่ฝึกฝนด้วยข้อมูลทั้งหมดจะทำคะแนนได้จากการจดจำวลีที่ฝึกฝนมากกว่าความสามารถในการแปลจริง เมื่อใช้ชุดทดสอบคงที่ (ที่ผ่านการตรวจสอบโดยครูหรือพยาบาล) โดยทั่วไปคุณจะต้องฝึกฝน **สองโมเดล**: โมเดลหนึ่งฝึกด้วยข้อมูลทั้งหมด — ซึ่งมักจะมีประโยชน์มากกว่าในการนำไปใช้งานจริง — และอีกโมเดลหนึ่งที่ปลอดคู่แฝด (twin-free) ซึ่งคะแนนของโมเดลนี้จะบ่งบอกว่าแนวทางนี้จัดการกับประโยคใหม่ ๆ ได้อย่างไร คลังข้อมูลปลอดคู่แฝดจะได้มาจาก `--drop-test-twins`:

```bash
nmt-forge leak-audit ~/pairs.tsv --clean-to pairs.notwins.jsonl --drop-test-twins
```

คำสั่งนี้จะลบแถวการฝึกฝนที่เป็นคู่แฝดกับแถวทดสอบ รายงานสับเซตแบบเข้มงวด (strict subset) ก่อนและหลัง ปฏิเสธหากการตัดออกทำให้ไม่เหลือข้อมูลสำหรับการฝึกฝน — และเขียนคอนฟิกของโมเดลปลอดคู่แฝดไว้ข้าง ๆ คอนฟิกของคุณ คือ **`config-notwins.json`**: ซึ่งเป็นคอนฟิกเดียวกันแต่มี `run_name` ของตัวเอง และตั้งค่า `data.gold` / `eval.near_dupe_corpus` ชี้ไปยังไฟล์ปลอดคู่แฝด (`--companion-config <file>` ใช้ระบุชื่อไฟล์อื่น; จะไม่มีการเขียนทับไฟล์เดิมที่มีอยู่แล้ว) พร้อมทั้งพิมพ์คำสั่งสำหรับฝึกฝนโมเดลนั้น จนกว่าจะมีการลงทะเบียนชุด dev (ขั้นตอนที่ 4) ระบบจะแจ้งให้ตัดแบ่งชุด dev ออกมาก่อนแล้วรันการตรวจสอบนี้อีกครั้ง เพื่อให้แถวของชุด dev ถูกนำออกจากไฟล์ปลอดคู่แฝดด้วยเช่นกัน `nmt-forge status` จะเก็บคำวินิจฉัย — และโมเดลปลอดคู่แฝดที่ยังไม่ได้ฝึกฝน — ไว้ในการแจ้งเตือนจนกว่าคุณจะดำเนินการ

**ลักษณะของการปฏิเสธ:** คุณไม่จำเป็นต้องจำว่าต้องรันคำสั่งนี้ — เพราะ `nmt-forge run` จะตรวจสอบไฟล์การฝึกฝนทุกไฟล์เทียบกับชุด test และชุด sealed ของคุณ และจะปฏิเสธหากพบการรั่วไหล: *"[leak-audit] corpus leaks into 1 test/sealed set(s) — project-test: 0 identical prompt(s), 3 identical answer(s), 1 near-duplicate answer(s) — plus 12 template sibling(s) … which are KEPT"* วิธีแก้ไข: `nmt-forge leak-audit <file> --clean-to <file.clean.jsonl>` แล้วฝึกฝนด้วยไฟล์ที่ทำความสะอาดแล้ว

## ขั้นตอนที่ 3 — ทำนายก่อนดูผล

**คุณบอกว่า:** *"บันทึกสิ่งที่เราคาดหวังว่าแต่ละโมเดลจะได้คะแนนเท่าใดบนชุดทดสอบ — ก่อนที่เราจะทำการวัดผลใด ๆ กับชุดทดสอบนั้น"*

**สิ่งที่ forge ทำ:** สร้างการลงทะเบียนล่วงหน้า (preregistration) หนึ่งรายการต่อหนึ่งโมเดลที่คุณวางแผนจะฝึกฝน โดยตั้งชื่อตามโมเดล:

```bash
nmt-forge prereg template --out predictions.json    # then EDIT it
nmt-forge prereg new all-data --eval-set project-test --predictions predictions.json
nmt-forge prereg new notwins --eval-set project-test --predictions predictions-notwins.json   # only with a twin-free model
```

ไฟล์การคาดการณ์ (predictions file) คือ JSON array ของการคาดการณ์ แต่ละรายการจะระบุชื่อเมทริกซ์และเหตุผลประกอบความยาวหนึ่งประโยค บวกด้วยทิศทางเมื่อเทียบกับเกณฑ์มาตรฐาน (`"direction": "increase", "baseline_score": 0, "margin": 5`) — ซึ่งจะได้รับการตรวจสอบโดยอัตโนมัติในภายหลัง — หรือความคาดหวังในรูปแบบข้อความอิสระ (`"expect": "between 10 and 30"`) ให้มนุษย์เป็นผู้ตรวจสอบ คุณ (หรือเอเจนต์ของคุณที่ระบุออกมาอย่างชัดเจน) จะต้องคอมมิตสิ่งเหล่านี้ **ก่อนที่** จะมีคะแนนการทดสอบใด ๆ — **และก่อนการเบঞ্চมาร์กโมเดลที่มีอยู่บนชุดทดสอบ**: ค่าเกณฑ์มาตรฐานในขั้นตอนที่ 3 ของ [สร้าง MT สำหรับภาษาของคุณ](/docs/build-mt-for-your-language#3-measure-the-options) จะเกิดขึ้น *หลังจาก* ขั้นตอนนี้ เมื่อคุณเอ็กซ์พอร์ต `--prereg <id>` จะระบุว่าการคาดการณ์ใดใช้ตัดสินโมเดลใด หรือคุณสามารถตรึง (pin) การคาดการณ์ไว้กับคอนฟิกของโมเดลได้ทันที: `--config-hash <hash>` บน `prereg new` พร้อมค่าแฮชเต็มรูปแบบที่ `nmt-forge preflight run --config config-notwins.json` พิมพ์ออกมา การแก้ไขคอนฟิกนั้นในภายหลัง (เช่น งบประมาณเวลา) จะเปลี่ยนค่าแฮชและยกเลิกการตรึง ดังนั้นการระบุ prereg ตอนเอ็กซ์พอร์ตจึงเป็นวิธีที่ง่ายกว่า

**ลักษณะของการปฏิเสธ:** สี่กรณีที่คุณอาจพบในขั้นตอนนี้

- เทมเพลตที่ไม่ได้แก้ไขจะถูกปฏิเสธ: ตัวแทนที่ (placeholders) `REPLACE` ไม่ได้คาดการณ์อะไรเลย ให้เขียนความคาดหวังและเหตุผลประกอบของคุณเอง
- ไฟล์ Markdown หรือข้อความร้อยแก้วจะถูกปฏิเสธ พร้อมแจ้งรูปแบบที่ถูกต้องและคำสั่งเทมเพลต โดยมีรูปแบบเดียวที่รองรับคือ: JSON array
- การลงทะเบียนล่วงหน้าที่เขียนขึ้นหลังจากชุดทดสอบถูกให้คะแนนไปแล้วจะถูกปฏิเสธ: *"[preregister] eval set 'project-test' was already read for scoring … before this preregistration"* การเบঞ্চมาร์กถือว่านับด้วย ตัวเลือก `--allow-after-reads` มีไว้สำหรับกรณีที่มีการบันทึกการคาดการณ์ไว้ก่อนการอ่านเหล่านั้นจริง ๆ เท่านั้น (เช่น เขียนบนกระดาษ); สิ่งนี้จะถูกบันทึกไว้ และทุกรายงาน, การเอ็กซ์พอร์ต, `DEPLOY.md` และ `nmt-forge status` จะระบุว่าการคาดการณ์เกิดขึ้นหลังจากมีการอ่านเพื่อคิดคะแนนไปแล้ว N ครั้ง
- การให้คะแนนชุดทดสอบโดยไม่มีการลงทะเบียนล่วงหน้าจะถูกปฏิเสธ: *"[preregister] no preregistration for eval set 'project-test' … why: results looked at without written-down expectations become post-hoc stories"* สิ่งนี้คือสิ่งที่แยกผลลัพธ์ที่แท้จริงออกจากการแต่งเรื่องราวย้อนหลังตามผลลัพธ์ที่ได้

:::info เหตุใดสิ่งนี้จึงรู้สึกเหมือนงานพิเศษ
มันคืองานที่ต้องทำ การป้องกันทุกอย่างที่นี่คือความผิดพลาดที่เคยหลอกนักวิจัยจริงๆ เครื่องมือทำให้เส้นทางที่ซื่อสัตย์เป็นเส้นทางที่ง่าย และเส้นทางที่ไม่ซื่อสัตย์เป็นเส้นทางที่หยุดคุณ
:::

ตอนนี้ให้วัดผลตัวเลือกที่มีอยู่เดิมบนชุดทดสอบ — ขั้นตอนที่ 3 ของ [สร้าง MT สำหรับภาษาของคุณ](/docs/build-mt-for-your-language#3-measure-the-options) — แล้วค่อยกลับมาทำการฝึกฝน

## ขั้นตอนที่ 4 — แบ่งชุดข้อมูล ตรวจสอบเกต แล้วเริ่มฝึกฝน {#step-4--check-the-gates-then-train}

**คุณบอกว่า:** *"แบ่งคลังข้อมูลที่ทำความสะอาดแล้วออกเป็น train และ dev การรันการฝึกฝนจะผ่านการตรวจสอบทั้งหมดหรือไม่? หากผ่าน ให้เริ่มฝึกฝน"*

**สิ่งที่ forge ทำ — การแบ่งชุดข้อมูล:**

```bash
nmt-forge split pairs.clean.jsonl --test 0 --dev 100 --seed 42 \
    --out data/split --register project
```

`--test 0` จะตัดแบ่งเฉพาะ train และ dev เนื่องจากชุดทดสอบของคุณมีอยู่แล้วในฐานะไฟล์ที่ลงทะเบียนแยกต่างหาก (หากตัดแบ่งชุดทดสอบ ขั้นตอนที่ 1 จะทำการแบ่งไว้แล้ว) `--register project` จะบันทึก `project-dev` ไว้ในพื้นที่ทำงาน — ซึ่งเป็นชื่อที่คอนฟิกเริ่มต้นชี้ไปอยู่แล้ว

การแบ่งชุดข้อมูลเป็นแบบ **ไม่ทับซ้อนกันระดับกลุ่ม (group-disjoint)**: คู่ประโยคสองคู่ใด ๆ ที่ใช้ต้นทาง *หรือ* ปลายทางร่วมกัน จะต้องไปอยู่ฝั่ง **เดียวกัน** เสมอ นี่คือสาเหตุที่พบบ่อยที่สุดที่ทำให้คะแนนของภาษาที่มีทรัพยากรน้อยพุ่งสูงเกินจริง — เช่น หนังสือเรียนจับคู่แบบฝึกหัดภาษาอังกฤษหลายข้อกับคำแปลปลายทางคำเดียว การสุ่มแบ่งแบบไม่ระวังจะทำให้สำเนาหนึ่งหลุดไปอยู่ใน train และคู่แฝดของมันไปอยู่ใน test ทำให้โมเดล "แปล" คำตอบที่ตนเองจำได้ออกมา ผลลัพธ์จะแจ้งให้ทราบว่าเกิดอะไรขึ้นบ้าง:

```
split pairs.clean.jsonl: 1580 rows in 1544 share-groups (largest 4)
  train 1480 · dev 100 · test 0  → data/split/
  verified: 0 shared canonical source/target keys across sides
  test side: none (--test 0) — your test set is a separate file; ...
  registered project-dev (role=dev)
```

เมื่อมีการลงทะเบียนชุดทดสอบไว้แล้ว `split` จะตรวจกรองไฟล์ train และ dev ใหม่เทียบกับชุดทดสอบทันที และแจ้งเตือนหากมีแถวใดที่จะถูกปฏิเสธในภายหลัง

**คลังข้อมูลที่เป็นเทมเพลต (หนังสือรวมวลี, แบบฝึกหัด)** `--near-dupe 0.6` จะเก็บประโยคที่ *เกือบ* ซ้ำกัน — ประโยคที่สร้างบนโครงสร้างเดียวกัน — ไว้ฝั่งเดียวกันด้วย เพื่อไม่ให้แถวใน dev หรือ test มีคู่แฝดตามเทมเพลตอยู่ในการฝึกฝน ในคลังข้อมูลที่มีเทมเพลตสูงมาก โครงสร้างประโยคอาจเชื่อมโยงเป็นลูกโซ่จนกลายเป็นกลุ่มขนาดยักษ์กลุ่มเดียว (*"Does your arm hurt?"* ~ *"Does your leg hurt?"* ~ *"Your leg looks swollen"* …) และกลุ่มข้อมูลจะต้องถูกจัดไปอยู่ฝั่งใดฝั่งหนึ่งทั้งกลุ่มเท่านั้น เมื่อเกิดกรณีที่ทำให้ฝั่งหนึ่งมีจำนวนแถวมากกว่าที่คุณขอไว้มาก — มากกว่า **1.5 เท่า** ของคำขอ — หรือทำให้ชุดฝึกฝนเหลือข้อมูลน้อยกว่าครึ่งหนึ่งของที่คำขอควรจะเหลือไว้ `split` จะปฏิเสธและไม่เขียนไฟล์ใด ๆ: *"[split-guard] split refused — nothing was written: the carve does not match the request (dev: asked for 100 rows, the carve put 663 there (6.63×); training keeps 210 of the 773 rows the request leaves it)"* ตามด้วยเหตุผล (การเชื่อมโยงลูกโซ่ พร้อมขนาดของกลุ่มที่ใหญ่ที่สุด) และแนวทางแก้ไขที่ใช้ได้: การตั้งค่าเกณฑ์ให้สูงขึ้น, การจำกัดขนาดกลุ่มสูงสุด (`--near-dupe 0.6 --max-group 51` — ลิงก์ที่เกือบซ้ำกันซึ่งเกินขีดจำกัดจะไม่ถูกตัด และการแบ่งข้อมูลจะนับรวมไว้), การตัดคู่แฝดของชุดทดสอบคงที่ออกด้วย `leak-audit --drop-test-twins` หรือการเขียนประโยค dev/test แยกต่างหากจากสื่อการฝึกฝน forge จะตรวจสอบการเชื่อมโยงลูกโซ่นี้ด้วยตนเอง: สำหรับคลังข้อมูลประเภทนี้ คำแนะนำเรื่องคู่แฝดของ forge (ที่นี่, ใน preflight และใน DEPLOY.md ของการเอ็กซ์พอร์ต) จะไม่แนะนำให้ใช้ `--near-dupe 0.6`

**ลักษณะของการปฏิเสธ:** หากคุณส่งชุดข้อมูลที่แบ่งเองให้ forge ตรวจสอบ `nmt-forge verify-split train.jsonl dev.jsonl test.jsonl` จะปฏิเสธเมื่อพบว่าแต่ละฝั่งมีข้อมูลทับซ้อนกัน — *"[split-guard] 3 shared canonical source keys and 1 shared target keys between 'train' and 'test'"* — พร้อมวิธีแก้ไข: ให้ตัดแบ่งใหม่ด้วย `split` แทนที่จะลบแถวที่มีปัญหาด้วยตนเอง

**ต้องการสองโมเดลหรือไม่?** เมื่อชุด dev ได้รับการลงทะเบียนแล้ว ให้รันการตรวจสอบแบบปลอดคู่แฝดจากขั้นตอนที่ 2 อีกครั้ง (แถวของชุด dev จะถูกนำออกจากไฟล์ปลอดคู่แฝดด้วย); จากนั้นใช้ `config-notwins.json` เพื่อฝึกฝนโมเดลที่สองตามรายละเอียดด้านล่าง

**สิ่งที่ forge ทำ — การตรวจสอบเกต:** `nmt-forge preflight run --config config.json` จะแสดงรายการเกตทุกด่านที่การรันจะต้องผ่าน พร้อมเครื่องหมาย ✓ หรือ ✗ โดยแต่ละจุดที่เป็น ✗ จะระบุวิธีแก้ไข — รวมถึงการตรวจสอบว่าได้ติดตั้ง training extra แล้วหรือไม่:

```
preflight: nmt-forge run

  ✓ config: config.json parses (config hash 9a85524275ff)
  ✓ dev-fence: config data.dev = 'project-dev': registered, role=dev
  ✓ training-data: 1 gold + 0 synthetic file(s) present
  ✗ backend-installed: backend 'hf-scratch' needs accelerate — not installed (the run would refuse)
      fix: python3 -m pip install 'nmt-forge[hf]'
  ✓ leak-audit: every gold and synthetic lane in the config will be audited ...
  ✓ schedule-sanity: regime, early-stop floor and eval cadence are derived from the config's data mix ...
  ✓ generation-headroom: decode cap is checked against dev reference lengths BEFORE training compute is spent

1 gate(s) would refuse — fix them first
```

เมื่อทุกอย่างผ่านเป็นสีเขียว: `nmt-forge run config.json` (และสำหรับโมเดลปลอดคู่แฝด ให้ใช้ `nmt-forge preflight run --config config-notwins.json && nmt-forge run config-notwins.json`)

เมื่อใช้พรีเซ็ตเริ่มต้น `cpu-tiny` การรันจะทำงานบน CPU แล็ปท็อปทั่วไปได้ — โดยไม่ต้องใช้ GPU และไม่ต้องดาวน์โหลด การฝึกฝนยังคงเป็นขั้นตอนเดียวที่ **ไม่ได้** เสร็จสิ้นในทันทีผ่าน tool call ดังนั้นเอเจนต์ของคุณควรรันไว้ในเบื้องหลังโดยส่งเอาต์พุตไปยังไฟล์ล็อก และคอยจับตาดูเฉพาะบรรทัดที่สำคัญ (`refused`, `Error`, `wall-clock`, `RUN EXIT`) แทนที่จะคอยส่งคำสั่งเช็กเรื่อย ๆ แผงควบคุมสดพร้อมกราฟแสดงค่า loss และปุ่มหยุดจะเปิดขึ้นสำหรับ **คุณ** (ที่ `http://127.0.0.1:8377` เมื่อพอร์ตว่าง) — ซึ่งเป็นของคุณ ไม่ใช่ของเอเจนต์ ในช่วงต้นของการรัน forge จะวัดความเร็วและจะปฏิเสธ — ภายในไม่กี่นาที ไม่ใช่หลายวัน — หากการรันไม่สามารถเสร็จสิ้นได้ภายใน `model.time_budget_hours` ที่กำหนดไว้ในคอนฟิก

บรรทัด `[schedule-sanity]` จะแสดง **ขีดจำกัดขั้นต่ำ (floor)** สำหรับ early-stopping ที่ forge คำนวณจากสัดส่วนข้อมูลของคุณ เพื่อให้การรันที่เน้นข้อมูลสังเคราะห์ไม่หยุดกลางคันที่ครึ่ง epoch เมื่อค่า loss ของ real-dev เกิดความผันผวน (ซึ่งเป็นรูปแบบความล้มเหลวที่เกิดขึ้นจริง — ดูที่ [การวินิจฉัยการรันการฝึกฝน](/docs/network/getting-started/diagnosing-training))

เมื่อเสร็จสิ้น forge จะ **คัดเลือกเช็กพอยต์บนชุด dev ที่ล้อมรั้วป้องกันไว้** (ไม่มีวันเลือกบนชุดทดสอบ), เขียนไฟล์ `run-manifest.json` และพิมพ์คะแนน dev ออกมา — โดยระบุช่วงความเชื่อมั่น 95% เสมอ — ตามด้วยคำสั่งถัดไป

## ขั้นตอนที่ 5 — ให้คะแนนเพียงครั้งเดียว แล้วแพ็กเกจโมเดล

**คุณบอกว่า:** *"ให้คะแนนโมเดลบนชุดทดสอบและแพ็กเกจโมเดลเพื่อให้เราสามารถนำไปใช้งานได้"*

**สิ่งที่ forge ทำ:**

```bash
nmt-forge export .forge/runs/<run>/run-manifest.json --prereg all-data --out export/
```

คำสั่งเดียวจะทำหน้าที่:

- ถอดรหัสชุดทดสอบของคุณด้วยเช็กพอยต์ที่การรันคัดเลือกไว้และให้คะแนน — จะถูกปฏิเสธหากไม่มีการลงทะเบียนล่วงหน้า บันทึกไว้ในบัญชีแยกประเภท (ledger) ของพื้นที่ทำงาน มีช่วงความเชื่อมั่น 95% สำหรับทุกตัวเลข พร้อมหมวด **การวินิจฉัยและข้อเสนอแนะ (Diagnosis & Recommendations)** ที่อธิบายด้วยภาษาที่เข้าใจง่าย
- เขียนผลลัพธ์เป็น **รายงาน mt-eval** ใน `export/evaluation/` เพื่อให้ `mt-eval compare` นำโมเดลนี้ไปวางเปรียบเทียบควบคู่กับสิ่งอื่นที่คุณเคยวัดผลด้วยชุดเครื่องมือ harness (เช่น โมเดลที่โฮสต์ไว้ในขั้นตอนที่ 3 ของ [สร้าง MT สำหรับภาษาของคุณ](/docs/build-mt-for-your-language#3-measure-the-options))
- แพ็กเกจ **โมเดลที่สมบูรณ์ในตัวเอง (self-contained model)** ไว้ใน `export/model/` (ค่าน้ำหนักและ tokenizer โดยไม่มี training state), `forge-model.json` (ระบุว่าเป็นโมเดลอะไรและวัดผลอย่างไร), manifest ของปลั๊กอิน champollion และ `DEPLOY.md` พร้อมคำสั่งที่แน่นอน โดย `export/model/` จะไม่มีประโยคทดสอบใด ๆ อยู่เลย และเป็นโฟลเดอร์เดียวที่คุณนำไปดีพลอย

**คะแนน** คือพาดหัวหลักของ harness: ค่า corpus chrF++ พร้อมช่วงความเชื่อมั่น 95% ซึ่งจะเขียนในรูปแบบเดียวกันทุกที่ที่ forge แสดงผล — ตัวอย่างเช่น `chrF++ 31.2 [28.4, 34.0]` — พร้อมลายเซ็น sacreBLEU ในบันทึกแบบเต็ม (`forge-model.json`, สรุปการเอ็กซ์พอร์ต, `DEPLOY.md`) ส่วนค่า BLEU, spBLEU และ TER จะแสดงอยู่ข้างกัน โดยไม่นำมาผสมรวมกัน; exact match และชุดการทดสอบอื่น ๆ ถือเป็นข้อมูลการวินิจฉัย ไม่มีการแสดงผลใดใน forge ที่พิมพ์คะแนนรวมสังเคราะห์ (composite) หรือป้ายกำกับคุณภาพ (quality label) ออกมา: เพราะคุณค่าของผลลัพธ์นั้นขึ้นอยู่กับผู้พูดภาษานั้นเป็นผู้ตัดสิน

**ข้อจำกัดของคะแนนจะติดตามคะแนนไปด้วยเสมอ** รายงาน mt-eval จะบันทึกทุกสิ่งที่เป็นข้อจำกัดของความหมายของคะแนน — เช่น *เอาต์พุตที่เกือบจะคงที่ (near-constant output)* (โมเดลส่งประโยคเดิมซ้ำ ๆ จากประโยคไม่กี่แบบให้กับอินพุตที่ต่างกันจำนวนมาก ทำให้เอาต์พุตไม่สอดคล้องกับอินพุต), เอาต์พุตที่ยาวหรือสั้นกว่าเฉลยอ้างอิงมาก หรือการคัดลอกข้อความต้นทางมาตรง ๆ `export` จะส่งต่อข้อจำกัดเหล่านี้ทั้งหมดตามถ้อยคำของ harness เอง: ทั้งในบทสรุป (`score_caveats`), ใน `forge-model.json` และใน `DEPLOY.md` ที่อยู่ใต้คะแนนทันที `status`, `report`, `compare` และ `lint` ก็ระบุเช่นเดียวกัน คะแนนที่มีข้อแม้ติดอยู่จะไม่ถูกนำเสนอเป็น "ตัวเลขสำหรับใช้อ้างอิง" โดยปราศจากข้อแม้เหล่านั้นอย่างเด็ดขาด

หากเกิดข้อผิดพลาดใด ๆ จะไม่มีการทิ้งไฟล์เอ็กซ์พอร์ตที่เขียนค้างไว้ครึ่ง ๆ กลาง ๆ ข้อควรระวังสองประการ: `export/evaluation/` มีประโยคทดสอบของคุณอยู่ — อย่าคัดลอกไฟล์นี้ไปพร้อมกับโมเดล ให้เก็บไว้กับชุดทดสอบ (เมื่อชุดทดสอบถูกทำเครื่องหมายเป็น private ทุกไฟล์ในนั้นจะได้รับเครื่องหมายเดียวกัน) และชุดทดสอบ **แบบปิดผนึก (sealed)** จะใช้งานได้เพียงครั้งเดียวเท่านั้น: การเอ็กซ์พอร์ตจะถือว่าใช้ชุดทดสอบนั้นไปแล้ว และการเอ็กซ์พอร์ตครั้งที่สองจะถูกปฏิเสธ เว้นแต่คุณจะระบุ `--no-eval` (เพื่อแพ็กเกจโมเดลโดยไม่ต้องคิดคะแนนซ้ำ)

`nmt-forge evaluate <run-manifest>` คือส่วนการให้คะแนนอย่างเดียวของ `export` หากคุณต้องการแค่ตัวเลขโดยไม่ต้องการแพ็กเกจโมเดล (`--harness-out DIR` จะเขียนรายงาน mt-eval)

**กรณีมีสองโมเดลบนชุดทดสอบเดียว** (เช่น โมเดลหนึ่งฝึกด้วยข้อมูลทั้งหมด และอีกโมเดลหนึ่งใช้ `--drop-test-twins`): เมื่อพื้นที่ทำงานมีการรันครั้งที่สอง บรรทัด `NEXT` และ `nmt-forge status` ของการรันจะตั้งชื่อโฟลเดอร์แยกตามการรัน (`--out export-<run>/`) ลำดับการดำเนินการไม่มีผล: ไม่ว่าโมเดลใดจะถูกเอ็กซ์พอร์ตเป็นอันดับสอง ไฟล์ `DEPLOY.md` ของโมเดลที่ใช้ข้อมูลทั้งหมดจะลงเอยด้วยการอ้างอิงคะแนนของโมเดลปลอดคู่แฝดเสมอ หากมีการลงทะเบียนล่วงหน้าสองรายการบนชุดทดสอบเดียว `nmt-forge status` และ `nmt-forge report` จะระบุว่ารายการใดใช้กับการรันใด (หรือให้ `--prereg <id>` เป็นผู้ตัดสิน — export the twin-free model with `--prereg notwins`). `nmt-forge compare` จะทำการทดสอบ A/B ทั้งสองโมเดลบนชุดทดสอบ และระบุจำนวนแถวทดสอบที่มีประโยคคู่แฝดในข้อมูลฝึกฝนของแต่ละโมเดล: การชนะเพราะการจดจำข้อความเดิมจะถูกรายงานตามจริง เครื่องมือนี้จะนำสมมติฐานการแปล (hypotheses) ของแต่ละโมเดล — `<export>/evaluation/battery-hyps.jsonl` ซึ่งมีชื่อว่า `hypotheses` ในสรุปการเอ็กซ์พอร์ต — และส่งต่อข้อแม้ของคะแนนที่ mt-eval บันทึกไว้สำหรับการเอ็กซ์พอร์ตนั้น คะแนนของโมเดลปลอดคู่แฝดคือตัวเลขที่ใช้อ้างอิงสำหรับประโยคใหม่ ๆ ได้ โดยต้องระบุควบคู่กับข้อแม้ใด ๆ ที่มีเสมอ: หากเอาต์พุตของโมเดลปลอดคู่แฝดมีลักษณะเกือบจะคงที่ คะแนนของโมเดลนั้นก็ไม่ใช่หลักฐานยืนยันว่าโมเดลแปลประโยคใหม่ ๆ ได้ และ `DEPLOY.md` จะระบุเรื่องนี้ไว้ข้างตัวเลข

**การอ่านโดย harness จะถูกนับรวมทั้งหมด** เมื่อ forge ลงทะเบียนชุดทดสอบ ระบบจะเริ่มต้นไฟล์บันทึกการอ่านขนาดเล็กไว้ข้างไฟล์นั้น (`<file>.reads.jsonl`) และ `mt-eval run` / `mt-eval compare` จะต่อท้ายหนึ่งบรรทัดที่ไม่มีเนื้อหาข้อความ (run id, วัตถุประสงค์, sha256 ของไฟล์, การประทับเวลา) ทุกครั้งที่มีการคิดคะแนนบนไฟล์นั้น forge จะอ่านบันทึกนี้: การลงทะเบียนล่วงหน้าที่เขียนขึ้นหลังจากการอ่านดังกล่าวจะถูกปฏิเสธเนื่องจากเป็นการทำนายย้อนหลัง (postdiction) (เว้นแต่จะระบุ `--allow-after-reads` ซึ่งทุกรายงานจะเปิดเผยข้อมูลนี้ให้ทราบ) — นี่คือเหตุผลที่ขั้นตอนที่ 3 ต้องมาก่อนการวัดเกณฑ์มาตรฐาน — ชุดข้อมูลแบบปิดผนึกที่ถูกอ่านโดย `mt-eval` จะถือว่าถูกใช้ไปแล้ว `status` และ `ledger show --set` จะนับจำนวนครั้งที่อ่าน และ `DEPLOY.md` จะแจ้งให้ทราบหากคะแนนที่เอ็กซ์พอร์ตไม่ได้มาจากการประเมินครั้งแรก

### วิธีอ่านรายงาน battery-lint

รายงานจะแสดงตารางคะแนน **ตามระดับภาษาหรือประเภทการใช้งาน (register)** (หนังสือเรียน, ทางการ/ราชการ, นิทานมุขปาฐะ, …) — หรือกลุ่มเดียวคือ `all` หากแถวทดสอบของคุณไม่ได้ระบุ register — แต่ละกลุ่มจะมีช่วงความเชื่อมั่นกำกับไว้ ตามด้วยการวินิจฉัย การวินิจฉัยจะระบุ **register ที่อ่อนที่สุด** ของคุณ และสำหรับแต่ละ register จะบอกสาเหตุที่เป็นไปได้มากที่สุดพร้อม **คันโยก (lever)** สำหรับใช้แก้ไขในลำดับถัดไป:

| หากผลการวินิจฉัยระบุว่า… | ความหมายคือ… | คันโยกสำหรับแก้ไข |
|---|---|---|
| `R1-vocabulary-gap` | register นั้นได้คะแนนต่ำ **และ** เอาต์พุตแปลไม่เสร็จสมบูรณ์; โมเดลขาดคำศัพท์ | **VOCABULARY** — เพิ่มคลังคำศัพท์ แล้วตรวจสอบ funnel อีกครั้ง |
| `R2-structure-gap` | โมเดลรู้จักคำศัพท์แต่ไม่รู้จัก *โครงสร้าง* ประโยค | **STRUCTURE** — เพิ่มโครงสร้างไวยากรณ์ที่ขาดหายไป (templates/compositor) |
| `R3-mixed-convention` | เอาต์พุตมีการสะกดคำปะปนกันหลายระบบ | **ORTHOGRAPHY** — ปรับคลังข้อมูลให้เป็นมาตรฐานเดียวกัน แล้วฝึกฝนใหม่ |
| `R4-optimism-bound` | คะแนน "เต็ม" สูงเกินจริงเนื่องจากแถวทดสอบมีคู่แฝด | **MEASUREMENT** — ใช้อ้างอิงคะแนนแบบ strict สำหรับการทดสอบความสามารถทั่วไป (generalization) |
| `R5-low-power` | ช่วงความเชื่อมั่นกว้างเกินไป | **MEASUREMENT** — อย่าตัดสินใจจากส่วนต่างคะแนน (delta) ที่น้อยกว่าช่วงความเชื่อมั่น (CI); ให้ขยายชุดทดสอบ |
| `R7-transfer-plateau` | ทำได้ดีมากบนข้อมูลสังเคราะห์ แต่ชะงักกับข้อความจริง | **REAL-DATA** — แปลย้อนกลับ (backtranslate) ข้อมูลภาษาเดียว หรือหาประโยคคู่ขนานจริงเพิ่ม |
| `R9-harness-score-caveat` | รายงาน mt-eval มีข้อจำกัดต่อคะแนน (เช่น เอาต์พุตเกือบจะคงที่); `high` เมื่อ mt-eval ระบุว่าเป็นประเด็นหลัก | **MEASUREMENT** — อ้างอิงคะแนนพร้อมข้อจำกัดเสมอ และอ่านตัวอย่างเอาต์พุตบางส่วนก่อนจะสรุปว่าเป็นคุณภาพการแปล |

ทุกข้อค้นพบจะมีหลักฐานประกอบที่ทำให้ตรวจพบเสมอ สำหรับข้อค้นพบประเภท `--json` เอเจนต์ของคุณสามารถดำเนินการแก้ไขผ่านโปรแกรมได้: `nmt-forge lint export/evaluation/battery-hyps-battery.json --json`.

## ขั้นตอนที่ 6 — ให้บริการโมเดลแก่ champollion CLI

**คุณบอกว่า:** *"เปิดให้บริการโมเดลที่เอ็กซ์พอร์ตแล้ว และใช้โมเดลนี้แปลข้อความสตริงของแอปเรา"*

**สิ่งที่ forge ทำ:**

```bash
nmt-forge serve export/model                               # http://127.0.0.1:8378
LOCAL_API_BASE=http://127.0.0.1:8378/v1 champollion sync --method local
```

`serve` ตอบสนองสองรูปแบบ: สัญญาข้อตกลง **api method** ของ champollion (`POST /translate`) และ `/v1/chat/completions` **ที่เข้ากันได้กับ OpenAI** ซึ่งเป็นรูปแบบที่ `champollion sync --method local` ใช้สื่อสาร `export/model/DEPLOY.md` มีโค้ดตัวอย่าง `champollion.config.json` สำหรับวิธี `api` (ซึ่งเป็นวิธีที่แนะนำ) และสำหรับ manifest ของปลั๊กอิน เซิร์ฟเวอร์จะรับการเชื่อมต่อที่ `127.0.0.1` เท่านั้น; หากต้องการเปิดให้บริการผ่านเครือข่าย คุณต้องกำหนดโทเค็น (`--token` หรือ `NMT_FORGE_SERVE_TOKEN`) เนื่องจากใครก็ตามที่เข้าถึงพอร์ตนี้ได้จะสามารถใช้งานโมเดลของคุณได้ CLI ไม่จำเป็นต้องใช้คีย์สำหรับการเชื่อมต่อแบบ loopback แต่เซิร์ฟเวอร์ที่เริ่มต้นด้วยโทเค็นจะต้องระบุค่าเดียวกันใน `CHAMPOLLION_API_KEY`

หากมีโมเดลที่เอ็กซ์พอร์ตสองโมเดล การเลือกว่าจะดีพลอยโมเดลใดขึ้นอยู่กับการตัดสินใจของคุณ: `nmt-forge choose export-<run>/model` จะบันทึกการเลือกนี้ และจากนั้น `nmt-forge status` จะระบุชื่อโมเดลนั้น การเปิดเซิร์ฟเวอร์เพื่อทดลองใช้งานจะถูกบันทึกเป็น served (เปิดให้บริการ) ไม่ใช่ choice (การเลือกใช้งาน) หากต้องการส่งโมเดลเข้าประกวดในการแข่งขัน sovereign แทน `DEPLOY.md` §6 จะแสดงรายการไฟล์ที่ประกอบเป็นรายการส่งเข้าประกวดแบบ declarative (Lane A) พร้อมคำสั่ง `mt-eval contest submit-model` ที่แน่นอน

ทำความเข้าใจสิ่งที่คุณกำลังดีพลอย: โมเดล NMT ทำหน้าที่แปลข้อความ โมเดลนี้ **ไม่** ปฏิบัติตามคำสั่ง (instructions) ดังนั้นคำแนะนำเรื่องระดับภาษา (tone guidance), ไฟล์แนะแนว (coaching files) และคลังคำศัพท์เฉพาะ (glossaries) ที่ CLI ส่งไปยังวิธีของ LLM จะถูกเพิกเฉย และการแปลภาษาด้วยเครื่องสำหรับภาษาที่มีทรัพยากรน้อยจำเป็นต้องได้รับการตรวจสอบโดยผู้ที่พูดภาษานั้นได้อย่างคล่องแคล่วก่อนที่ข้อความจะเผยแพร่ไปถึงผู้อ่าน

## สิ่งที่คุณเพิ่งทำ

คุณได้ฝึกฝนโมเดลที่มีคะแนนที่เชื่อถือได้จริง: ไม่มีการรั่วไหลของคำตอบ, เช็กพอยต์ได้รับการคัดเลือกโดยไม่แอบดูชุดทดสอบ, มีแถบแสดงความคลาดเคลื่อน (error bars) ในทุกตัวเลข, บันทึกการคาดการณ์ไว้ล่วงหน้าก่อนทราบผลลัพธ์, มีการวินิจฉัยที่ระบุคันโยกถัดไปที่ต้องทำแทนที่จะปล่อยให้คุณคาดเดาเอง — และได้โมเดลที่แพ็กเกจเรียบร้อยซึ่ง CLI สามารถเรียกใช้ได้ รวมถึงนำไปเปรียบเทียบได้โดยตรงกับทุกวิธีอื่นที่คุณเคยวัดผล นั่นคือหัวใจสำคัญทั้งหมด — **ผลลัพธ์ที่ซื่อสัตย์คือค่าเริ่มต้น และไม่จำเป็นต้องมีความเชี่ยวชาญด้าน MT (หรือ GPU) เพื่อให้ได้ผลลัพธ์นี้**

เมื่อตัวเลขคะแนนไม่เป็นไปตามหวัง (ซึ่งมักจะเป็นเช่นนั้นในครั้งแรก — เพราะโมเดลเริ่มต้นถูกออกแบบมาให้มีขนาดเล็กและประสิทธิภาพจำกัด) ให้ไปที่ [การวินิจฉัยการรันการฝึกฝน](/docs/network/getting-started/diagnosing-training) — ซึ่งเรียบเรียงตามอาการที่พบเป็นหลัก และเขียนขึ้นเพื่อสถานการณ์นั้นโดยเฉพาะ
