# คำถามที่พบบ่อย

> **สรุปสำหรับผู้บริหาร** คำตอบสำหรับคำถามทั่วไปเกี่ยวกับ Champollion Network — วิธีการคำนวณคะแนน สิ่งที่ทำให้ถูกตัดสิทธิ์ วิธีจัดการกับภาษาที่ไม่มี FST คำแนะนำเกี่ยวกับโมเดลและพารามิเตอร์ และกระบวนการส่งผลงาน

---

## การให้คะแนนและเมตริก

### harness คำนวณเมตริกอะไรบ้าง?

ระบบทดสอบคำนวณเมตริกทั้งหมดห้าตัว โดยสามตัวไม่ขึ้นกับภาษาและใช้งานได้กับคู่ภาษาใดก็ได้ ส่วนอีกสองตัวในปัจจุบันอาศัยปลั๊กอินเฉพาะสำหรับ CRK และจะถูกพัฒนาให้รองรับภาษาอื่นเพิ่มเติมในอนาคต คลังข้อมูลอ้างอิงที่ใช้งานได้ในปัจจุบันเป็นชุดข้อมูลสาธารณะที่มีสัญญาอนุญาตแบบเปิด ได้แก่ Global Voices, Tatoeba, TICO-19, IN22, SMOL และอื่นๆ (ดู [Datasets](/docs/network/leaderboard/datasets)) และ leaderboard เปิดรับการส่งผลงานสำหรับทุกคู่ภาษาที่ลงทะเบียนไว้ Plains Cree เป็นเพียงภาษาแรกที่นำเมตริกเฉพาะภาษาทั้งสองตัว (ที่ใช้ FST) มาใช้งาน

| เมตริก | สเกล | สิ่งที่วัด | สถานะ |
|--------|-------|-----------------|--------|
| **chrF++** | 0–100 | ความทับซ้อนของ character n-gram ระหว่างการแปลที่ทำนายและการแปลอ้างอิง เป็นเมตริกระดับพื้นผิวที่ดีที่สุดสำหรับภาษาที่มีสัณฐานวิทยาซับซ้อน ใช้การให้คะแนนแบบ native ของ sacrebleu | ✅ ทุกภาษา |
| **Exact match** | 0.0–1.0 | สัดส่วนของรายการที่การทำนายตรงกับข้อมูลอ้างอิงทุกประการหลังการทำให้เป็นมาตรฐาน | ✅ ทุกภาษา |
| **FST acceptance** | 0.0–1.0 | สัดส่วนของคำในผลลัพธ์ที่ได้รับการยอมรับจาก finite-state transducer (ตัววิเคราะห์สัณฐานวิทยา) คำนวณเฉพาะเมื่อมีการระบุไฟล์ไบนารี FST | ✅ ทุกภาษาที่มี FST |
| **Equivalent match** | 0.0–1.0 | สัดส่วนของรายการที่ตรงกับข้อมูลอ้างอิงหรือรูปแบบที่ยอมรับได้ โดยคำนึงถึงลำดับคำ ข้อตกลงการสะกด และความแตกต่างทางภาษาถิ่น | ⚡ CRK (กำลังขยาย) |
| **Semantic score** | 0.0–1.0 | คะแนนการรักษาความหมาย — การแปลถ่ายทอดความหมายที่ตั้งใจได้ดีเพียงใดโดยไม่คำนึงถึงรูปแบบพื้นผิว | ⚡ CRK (กำลังขยาย) |

มีแผนเพิ่มเมตริกเพิ่มเติม ได้แก่ **ความถูกต้องทางสัณฐานวิทยา**, **การตรวจจับการสลับรหัสภาษา**, **การปฏิบัติตามคำศัพท์เฉพาะ** และ **การตรวจจับการสร้างข้อมูลเท็จ** ดู [Scoring Specification §2](/docs/network/specifications/scoring#2-metric-inventory) สำหรับรายการเมตริกทั้งหมด (หกหมวดหมู่)

### คะแนนรวมคำนวณอย่างไร?

คะแนนรวมคือค่าเฉลี่ยถ่วงน้ำหนักของเมตริกที่มีอยู่ ทำให้เป็นมาตรฐานในสเกล 0.0–1.0 น้ำหนักถูกกำหนดไว้ในสองโปรไฟล์:

- **โปรไฟล์ A** (ภาษาที่มี FST): 9 เมตริก เมตริกเชิงโครงสร้าง (FST + ความถูกต้องทางสัณฐานวิทยา) มีน้ำหนัก 40% ของคะแนนรวม
- **โปรไฟล์ B** (ภาษาที่ไม่มี FST): 8 เมตริก semantic และ chrF++ มีน้ำหนักสูงสุดเท่ากัน

เมื่อเมตริกใดไม่พร้อมใช้งาน น้ำหนักของเมตริกนั้นจะถูกกระจายตามสัดส่วนไปยังเมตริกที่เหลือ ซึ่งหมายความว่า benchmark ในระยะเริ่มต้น (ที่มีเพียง chrF++ และ exact match) ยังคงให้คะแนนรวมที่ถูกต้อง — เพียงแต่น้ำหนักที่มีผลจะสะท้อนสิ่งที่มีอยู่เท่านั้น

**ตารางน้ำหนักทั้งหมด กฎการทำให้เป็นมาตรฐาน และเหตุผลการยกเว้นอยู่ใน [Scoring Specification §4](/docs/network/specifications/scoring#4-composite-score)** โค้ด harness สะท้อนตารางเหล่านี้ใน `mt_eval_harness/scoring.py` chrF++ ถูกทำให้เป็นมาตรฐานโดยหารด้วย 100 ก่อนถ่วงน้ำหนัก อัตราการสลับรหัสภาษาและการสร้างข้อมูลเท็จถูกกลับค่า (ยิ่งต่ำยิ่งดี)

### ระดับคุณภาพคืออะไร?

ระดับคุณภาพคือป้ายกำกับแบบ heuristic ที่แมปกับช่วงคะแนนรวม ช่วยสื่อสารว่าคะแนนหนึ่งๆ *หมายความว่าอะไร* ในทางปฏิบัติ:

| ระดับ | ช่วงคะแนนรวม | การตีความ |
|------|----------------|----------------|
| **Baseline** | 0.00 – 0.30 | ต่ำกว่าคุณภาพที่เป็นประโยชน์ วิธีการต้องการการปรับปรุงอย่างมีนัยสำคัญ |
| **Emerging** | 0.30 – 0.50 | แสดงให้เห็นศักยภาพ การแปลบางส่วนถูกต้องแต่ยังไม่สม่ำเสมอ |
| **Functional** | 0.50 – 0.70 | ใช้งานได้สำหรับการอ้างอิงโดยมีการตรวจสอบโดยมนุษย์ ไม่เหมาะสำหรับการใช้งานโดยไม่มีการตรวจสอบ |
| **Deployable** | 0.70 – 0.85 | พร้อมสำหรับการใช้งานจริงโดยมีการตรวจสอบเป็นระยะ เป็นตัวกระตุ้นสิทธิ์การโอนความเป็นเจ้าของ |
| **Fluent** | 0.85 – 1.00 | คุณภาพใกล้เคียงเจ้าของภาษา เหมาะสำหรับการใช้งานโดยไม่ต้องมีการดูแล |

### ความแตกต่างระหว่างระดับคุณภาพและระดับการยืนยันคืออะไร?

**ระดับคุณภาพ** อธิบาย *ความหมายของคะแนนอัตโนมัติ* (Baseline → Fluent) **ระดับการยืนยัน** อธิบาย *ว่าใครเป็นผู้ตรวจสอบผลลัพธ์*:

| ระดับการตรวจสอบยืนยัน | ความหมาย |
|-------------------|---------------|
| **ประเมินด้วยตนเอง (Self-benchmarked)** | ผู้ส่งผลงานรันชุดทดสอบ (harness) ด้วยตนเอง คะแนนมีความเป็นไปได้แต่ยังไม่ได้รับการตรวจสอบยืนยัน |
| **ตรวจสอบยืนยันโดย Champollion (Champollion Verified)** | ผู้ดูแลระบบจำลองผลลัพธ์ได้โดยใช้การกำหนดค่าวิธีการที่ส่งมา |
| **ตรวจสอบความถูกต้องโดยชุมชน (Community Validated)** | ผู้พูดสองภาษาของภาษาเป้าหมาย ซึ่งมีคุณสมบัติตามโปรโตคอลของชุมชน ได้ตรวจสอบกลุ่มตัวอย่างแบบแบ่งชั้นของผลลัพธ์ (≥30 รายการ, ผู้ตรวจสอบ ≥2 คน) และ ≥70% ผ่านเกณฑ์ของชุมชน ระดับนี้จะมอบให้ผ่านการทดสอบของชุมชนเองเท่านั้น การลดระดับจากการสุ่มตรวจสอบจะดำเนินการในลักษณะเดียวกันและเปิดเผยต่อสาธารณะอย่างเท่าเทียมกัน |

วิธีการหนึ่งอาจมีคุณภาพระดับ "Deployable" แต่มีการยืนยันเพียงระดับ "Self-benchmarked" — หมายความว่าคะแนนดูดีแต่ยังไม่มีใครยืนยันอย่างอิสระ

## การส่งผลงานและการตัดสิทธิ์

### อะไรทำให้การส่งผลงานของฉันถูกตัดสิทธิ์?

การส่งผลงานของคุณจะถูกปฏิเสธหรือถูกตั้งค่าสถานะหากมีสิ่งต่อไปนี้:

1. **วิธีการของคุณถูกเปิดเผยต่อข้อมูลการประเมิน** หากคุณฝึก fine-tune few-shot-prompt หรือใช้รายการใดๆ จากชุดข้อมูลการประเมินในทางใดทางหนึ่ง คะแนนของคุณจะถูกเพิ่มขึ้นอย่างไม่เป็นธรรม ซึ่งรวมถึงการใช้การแปลอ้างอิงใน prompt ของคุณด้วย
2. **run card ของคุณไม่ผ่านการตรวจสอบความสมบูรณ์** fingerprint ต้องตรงกับการกำหนดค่า run card ที่ถูกแก้ไขจะถูกปฏิเสธ
3. **วิธีการของคุณไม่ได้ implement โปรโตคอล TranslationMethod** harness คาดหวัง `translate(entries, config) → results` การ integration แบบกำหนดเองที่ข้าม harness จะไม่ได้รับการยอมรับ

### ฉันสามารถส่งผลงานได้หลายครั้งหรือไม่?

ได้ leaderboard ติดตามการส่งผลงานทั้งหมด คุณสามารถทำซ้ำได้ — รันการทดลองหลายสิบครั้ง แล้วส่งเฉพาะผลที่ดีที่สุด การส่งผลงานแต่ละครั้งบันทึก fingerprint ที่ไม่ซ้ำกัน จึงไม่มีความคลุมเครือว่า run ใดให้คะแนนใด

### ฉันจะให้คะแนนของฉันได้รับการยืนยันได้อย่างไร?

1. **ประเมินด้วยตนเอง (Self-benchmarked) (อัตโนมัติ):** ทุกการส่งผลงานจะเริ่มต้นที่นี่
2. **ตรวจสอบยืนยันโดย Champollion (Champollion Verified) (อัตโนมัติ):** เซิร์ฟเวอร์จะให้คะแนนผลลัพธ์ที่คุณส่งมาใหม่อีกครั้ง โดยเทียบกับคลังข้อมูลอ้างอิงที่ถูกตรึงด้วย SHA ด้วยตัวชี้วัดของชุดทดสอบ เมื่อคะแนนของคุณสามารถจำลองซ้ำได้ การรันนั้นจะถูกเลื่อนระดับเป็น ตรวจสอบยืนยันโดย Champollion ซึ่งเป็นระดับเดียวที่กระดานจัดอันดับนำมาแสดง หากไม่สามารถจำลองซ้ำได้ หรือข้อมูลอ้างอิงที่จัดเก็บไว้ถูกแก้ไข การรันนั้นจะถูกตัดสิทธิ์
3. **ตรวจสอบความถูกต้องโดยชุมชน (Community Validated):** ผู้พูดสองภาษาของภาษาเป้าหมาย ซึ่งมีคุณสมบัติตามโปรโตคอลของชุมชน จะตรวจสอบกลุ่มตัวอย่างแบบแบ่งชั้นของผลลัพธ์จากวิธีการของคุณ — อย่างน้อย 30 รายการ, ผู้ตรวจสอบอย่างน้อย 2 คน — และอย่างน้อย 70% ต้องผ่านเกณฑ์ของชุมชน ระดับนี้จะมอบให้ผ่านการทดสอบที่ชุมชนดำเนินการเองตามดุลยพินิจของชุมชนเท่านั้น และสามารถถูกเพิกถอนได้ด้วยวิธีเดียวกัน: การสุ่มตรวจสอบที่ไม่ผ่านเกณฑ์จะลดระดับวิธีการนั้นอย่างเปิดเผยต่อสาธารณะเช่นเดียวกัน กระบวนการนี้ไม่สามารถทำแบบอัตโนมัติได้ — จำเป็นต้องอาศัยการมีส่วนร่วมของชุมชน

### ทำไมคุณถึงไม่รันวิธีการของทุกคนใหม่อีกครั้งเพื่อตรวจสอบยืนยัน?

เพราะเราไม่มีทรัพยากรเพียงพอและไม่มีความจำเป็นต้องทำเช่นนั้น เซิร์ฟเวอร์จะให้คะแนนผลลัพธ์ที่ส่งมาของ *ทุกคน* ใหม่อีกครั้งโดยไม่มีค่าใช้จ่าย (ซึ่งช่วยจับผิดคะแนนที่ถูกพิมพ์เข้ามาเองหรือถูกแก้ไข) การรันโมเดลใหม่อีกครั้งจริงๆ นั้นมีค่าใช้จ่ายด้านการประมวลผล (compute) เราจึงทำเฉพาะกับ **กลุ่มตัวอย่าง** ที่เลือกโดย **การตรวจสอบแบบถ่วงน้ำหนักตามชื่อเสียง (reputation-weighted auditing)**: การรันจะถูกรันใหม่อีกครั้งเสมอหากมีความสำคัญสูง (เช่น เป็นการสร้างสะพานเชื่อมแรกไปยังตระกูลภาษาใหม่ทั้งตระกูล) หรือมีความผิดปกติ (เช่น คะแนนก้าวกระโดดจากสถิติที่ดีที่สุดก่อนหน้าจนดูดีเกินจริง) และสำหรับผู้ร่วมสมทบที่ได้รับการพิสูจน์แล้ว จะมีการสุ่มตรวจสอบเพียงนานๆ ครั้ง ชื่อเสียงจะได้รับจากการผ่านการตรวจสอบเหล่านี้เท่านั้น (หรือจากการที่ผู้ร่วมสมทบอิสระยืนยันผลลัพธ์ของคุณ) — ไม่ใช่จากปริมาณการส่ง — ดังนั้นบัญชีที่เพิ่งสร้างใหม่เพื่อใช้ทิ้งขว้างจะไม่ได้ประโยชน์อะไรเลย การจับได้ว่ามีการปลอมแปลงเพียงครั้งเดียวจะทำให้ชื่อเสียงของผู้ร่วมสมทบกลายเป็นศูนย์ ประวัติที่ได้รับการตรวจสอบยืนยันแล้วทั้งหมดจะถูกตรวจสอบใหม่อีกครั้ง และจะถูกบันทึกไว้ต่อสาธารณะ คล้ายกับการเพิกถอนผลงาน (retraction) เรา **ไม่** อ้างว่าการรันของคุณ "ผ่านชุดทดสอบ (harness)" — สำหรับการประมวลผลแบบโฮสต์เอง (self-hosted) ที่เซิร์ฟเวอร์ไม่สามารถตรวจสอบยืนยันได้ — ดังนั้นความถูกต้องจึงขึ้นอยู่กับ *ความสามารถในการทำซ้ำได้ (reproducibility) + เดิมพันด้านชื่อเสียง (reputation stake) + การยืนยันจากผู้อื่น (corroboration)* ไม่ใช่การรับรอง (attestation) ดู [กฎการประเมิน MT](/docs/network/leaderboard/rules#how-verification-scales-reputation-weighted-auditing) สำหรับโมเดลฉบับเต็ม

### API การส่งผลงานพร้อมใช้งานแล้วหรือยัง?

ยังไม่รองรับในขณะนี้ endpoint `https://champollion.dev/api/leaderboard/submit` เป็นเป้าหมายที่วางแผนไว้ในอนาคต เส้นทางการส่งผลงานในปัจจุบันคือ `mt-eval publish` — ซึ่งอัปโหลด run card จากไดเรกทอรีผลลัพธ์ของระบบทดสอบ (`eval/logs/harness/`) ไปยัง leaderboard โดยตรงในสถานะ *self-benchmarked (unverified)*

## โมเดลและพารามิเตอร์

### ฉันควรใช้โมเดลใด?

ไม่มีโมเดลที่ดีที่สุดเพียงตัวเดียว — ขึ้นอยู่กับคู่ภาษา งบประมาณ และแนวทางของคุณ คำแนะนำทั่วไป:

| ประเภทภาษา | จุดเริ่มต้นที่แนะนำ | เหตุผล |
|---------------|---------------------------|-----|
| **ทรัพยากรสูง** (ฝรั่งเศส สเปน ญี่ปุ่น) | `google/gemini-2.5-flash` หรือ `gpt-4o-mini` | รวดเร็ว ราคาถูก baseline ที่แข็งแกร่ง |
| **ทรัพยากรต่ำที่มีการครอบคลุม LLM บ้าง** (Quechua, Yoruba) | `google/gemini-2.5-pro` หรือ `anthropic/claude-sonnet-4` | โมเดลขนาดใหญ่มีความรู้แฝงที่ดีกว่า |
| **Polysynthetic / ทรัพยากรต่ำมาก** (Plains Cree, Inuktitut) | `google/gemini-2.5-pro` พร้อม coaching | ข้อมูล coaching สำคัญกว่าการเลือกโมเดล OMT-1600 รวมภาษา polysynthetic บางภาษา (เช่น CRK ที่ระดับ R1) แต่ใช้ tokenization แบบ BPE มาตรฐาน — ทำ benchmark เป็น baseline ใน Network |

ระบบทดสอบการประเมินใช้ OpenRouter ดังนั้นโมเดลใดก็ตามที่มีให้บริการบน OpenRouter สามารถนำมาทดสอบประสิทธิภาพได้ ดูรายการโมเดลที่มีได้ที่ [openrouter.ai/models](https://openrouter.ai/models)

### ฉันควรใช้ temperature เท่าไหร่?

โดยทั่วไปค่าที่ต่ำกว่าจะดีกว่าสำหรับการแปล:

| Temperature | ผล | แนะนำสำหรับ |
|-------------|--------|-----------------|
| **0.0 – 0.2** | ผลลัพธ์ที่กำหนดได้สูง สม่ำเสมอ | วิธีการสำหรับ production, benchmark ขั้นสุดท้าย |
| **0.3 – 0.5** | มีความหลากหลายบ้าง บางครั้งสร้างสรรค์มากขึ้น | การสำรวจ การทำซ้ำในระยะเริ่มต้น |
| **0.6+** | ความหลากหลายสูง คาดเดาไม่ได้ | ไม่แนะนำสำหรับการทำ MT benchmark |

Temperature ถูกบันทึกใน run card ดังนั้น temperature ที่แตกต่างกันจะให้ fingerprint ที่แตกต่างกัน — ถือเป็นการทดลองที่แตกต่างกัน

### ข้อมูล coaching ช่วยได้หรือไม่?

ช่วยได้อย่างมีนัยสำคัญ — โดยเฉพาะสำหรับภาษาที่มีทรัพยากรต่ำ ข้อมูล coaching (กฎไวยากรณ์ รายการพจนานุกรม หมายเหตุสไตล์) ถูกแทรกเข้าไปใน system prompt ของ LLM สำหรับ Plains Cree วิธีการที่ใช้ coaching มีประสิทธิภาพเหนือกว่าวิธีการ LLM ดิบสำหรับภาษา polysynthetic อย่างสม่ำเสมอ เนื่องจาก LLM ทั่วไปมีการเรียนรู้ภาษา polysynthetic จำกัดและไม่มีความตระหนักทางสัณฐานวิทยา แม้แต่ OMT-1600 ที่ได้รับการฝึกเฉพาะสำหรับ CRK ก็ยังใช้ tokenization แบบ BPE มาตรฐานที่ไม่สามารถแสดงสัณฐานวิทยา polysynthetic ในเชิงโครงสร้างได้ ข้อมูล coaching ให้บริบทเชิงภาษาศาสตร์ที่โมเดลขาดอยู่

สำหรับภาษาที่มีทรัพยากรสูง (ฝรั่งเศส สเปน) coaching มีผลกระทบน้อยกว่า เนื่องจากโมเดลมีความรู้พื้นฐานที่แข็งแกร่งอยู่แล้ว

ดู [Coaching Data](https://champollion.dev/docs/concepts/coaching-data) สำหรับข้อกำหนดฉบับสมบูรณ์

## FST และการตรวจสอบสัณฐานวิทยา

### จะทำอย่างไรถ้าไม่มี FST สำหรับภาษาของฉัน?

หลายภาษาไม่มี finite-state transducer ซึ่งไม่เป็นปัญหา — harness ทำงานได้โดยไม่ต้องมี FST คะแนนรวมใช้น้ำหนักโปรไฟล์ B (ดู [Scoring Specification §4.3](/docs/network/specifications/scoring#43-weight-tables)) ซึ่งเปลี่ยนน้ำหนักไปยังเมตริก semantic และ surface FST acceptance จะถูกทำเครื่องหมายเป็น `null` ใน run card

registry หลักสำหรับ FST ที่มีอยู่:

| ทะเบียน | ความครอบคลุม | URL |
|----------|----------|-----|
| **GiellaLT** | กว่า 100 ภาษา — ภาษา Sámi, Cree, Inuktitut และภาษาในตระกูล Uralic รวมถึงภาษาชนกลุ่มน้อยอื่นๆ อีกมากมาย | [giellalt.uit.no](https://giellalt.uit.no/) |
| **ALTLab** | Plains Cree, Tsuut'ina, Odawa | [altlab.ualberta.ca](https://altlab.ualberta.ca/) |
| **Apertium** | คู่ภาษาประมาณ 60 คู่ ส่วนใหญ่เป็นภาษายุโรป | [apertium.org](https://apertium.org/) |
| **UniMorph** | กระบวนทัศน์ทางสัณฐานวิทยา (Morphological paradigms) สำหรับกว่า 150 ภาษา | [unimorph.github.io](https://unimorph.github.io/) |

### ฉันสามารถสร้าง FST ได้หรือไม่?

ได้ แต่ไม่ใช่เรื่องง่าย FST เข้ารหัสกฎสัณฐานวิทยาของภาษา — รูปแบบคำที่ถูกต้องทั้งหมด การสร้าง FST ต้องการความรู้เชิงภาษาศาสตร์เชิงลึกเกี่ยวกับภาษานั้น หากคุณมีไวยากรณ์สัณฐานวิทยา (เช่น จากภาควิชาภาษาศาสตร์) สามารถคอมไพล์เป็น FST ได้โดยใช้เครื่องมืออย่าง [HFST](https://hfst.github.io/) หรือ [Foma](https://fomafst.github.io/)

### FST gating ทำงานอย่างไรในทางปฏิบัติ?

pipeline ที่ใช้ FST gating ทำงานดังนี้:

1. LLM สร้างการแปล
2. แต่ละคำในผลลัพธ์ถูกตรวจสอบกับ FST
3. คำที่ FST ปฏิเสธจะถูกตั้งค่าสถานะว่าไม่ถูกต้องทางสัณฐานวิทยา
4. วิธีการสามารถลองใหม่พร้อม feedback ("คำ X ไม่ถูกต้อง ลองอีกครั้ง")
5. หลังจากลองใหม่แล้ว คำที่ยังไม่ถูกต้องจะถูกบันทึกไว้

อัตรา FST acceptance วัดว่ามีคำกี่คำที่ผ่านการตรวจสอบ ดู [FST-Gated Pipeline Tutorial](/docs/network/tutorials/fst-gated-pipeline) สำหรับตัวอย่างที่สมบูรณ์

## ข้อมูลและชุดข้อมูล

### ฉันสามารถมีส่วนร่วมในการสร้างชุดข้อมูลสำหรับภาษาใหม่ได้หรือไม่?

ได้ ข้อกำหนดขั้นต่ำจาก [Benchmark Specification §11](/docs/network/specifications/benchmark#11-extending-to-new-languages):

- **50 รายการมาตรฐานทอง** (ต้นฉบับ + การแปลอ้างอิงที่ผ่านการยืนยัน)
- **30 รายการสำหรับพัฒนา** (สามารถทับซ้อนกับมาตรฐานทองได้สำหรับคลังข้อมูลขนาดเล็ก)
- **ความยินยอมของชุมชน** (สำหรับภาษาของชนพื้นเมือง ต้องได้รับการอนุญาตอย่างชัดเจนจากองค์กรกำกับดูแล)
- **เอกสารแหล่งที่มา** (ข้อมูลมาจากไหน มีสัญญาอนุญาตอะไรบ้าง)

ชุดข้อมูลใหม่จะเปิด track leaderboard ใหม่โดยอัตโนมัติ ดู [For Language Communities](/docs/network/community/for-language-communities) สำหรับคู่มือผู้มีส่วนร่วม

### ชุดข้อมูลของฉันควรอยู่ในรูปแบบใด?

JSON พร้อมชื่อฟิลด์มาตรฐาน:

```json
{
  "name": "my-language-dev-v1",
  "language_pair": "en-xxx",
  "segment": "development",
  "version": "1.0",
  "entries": [
    {
      "id": 1,
      "source": "Hello",
      "reference": "[translation in target language]",
      "difficulty": 1,
      "domain": "general"
    }
  ]
}
```

ดู [Datasets](/docs/network/leaderboard/datasets) สำหรับ schema ฉบับสมบูรณ์และคำจำกัดความของระดับความยาก

## อธิปไตยและความเป็นเจ้าของ

### ใครเป็นเจ้าของวิธีการที่สร้างขึ้นสำหรับภาษาของชนพื้นเมือง?

สำหรับภาษาของชนพื้นเมือง วิธีการที่บรรลุระดับ Deployable (คะแนนรวม ≥ 0.70) และผ่านการตรวจสอบโดยชุมชนจะกระตุ้นกระบวนการ [โอนความเป็นเจ้าของ](/docs/network/sovereignty/ownership-transfer) ความเป็นเจ้าของโค้ดจะโอนจากนักวิจัยไปยังองค์กรกำกับดูแลของชุมชนภาษา

นักวิจัยยังคงมีสิทธิ์:
- สิทธิ์การเผยแพร่ (บทความวิชาการเกี่ยวกับวิธีการ)
- เครดิตบน leaderboard
- สิทธิ์ในการนำ *เทคนิค* เดียวกันไปใช้กับภาษาอื่น

องค์กรกำกับดูแลได้รับ:
- ความเป็นเจ้าของเต็มรูปแบบของโค้ดวิธีการและข้อมูล coaching
- การควบคุมการใช้งาน (เมื่อไหร่ ที่ไหน อย่างไร) — และทุกสิ่งที่การใช้งานนั้นสร้างรายได้ Champollion ไม่แสวงหากำไรและไม่รับส่วนแบ่งใดๆ

### ฉันสามารถใช้ champollion สำหรับภาษาที่ไม่ใช่ภาษาของชนพื้นเมืองโดยไม่มีข้อกังวลด้านอธิปไตยได้หรือไม่?

ได้ สำหรับภาษามาตรฐาน (ฝรั่งเศส ญี่ปุ่น สเปน ฯลฯ) ไม่มีข้อพิจารณาด้านอธิปไตย ใช้ champollion ตามปกติ — แปล ซิงค์ เผยแพร่ตามต้องการ กรอบงานอธิปไตยใช้กับภาษาของชนพื้นเมืองและภาษาที่ชุมชนกำกับดูแลโดยเฉพาะ ซึ่งหลักการกำกับดูแลข้อมูล (หลักการอธิปไตยทางข้อมูลของ First Nations, CARE, Te Mana Raraunga) ต้องการการพิจารณาเป็นพิเศษ
