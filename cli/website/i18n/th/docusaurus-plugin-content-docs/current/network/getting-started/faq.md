# คำถามที่พบบ่อย

> **สรุปสำหรับผู้บริหาร** คำตอบสำหรับคำถามทั่วไปเกี่ยวกับ Champollion Network — วิธีการคำนวณคะแนน สิ่งที่ทำให้ถูกตัดสิทธิ์ วิธีจัดการกับภาษาที่ไม่มี FST คำแนะนำเกี่ยวกับโมเดลและพารามิเตอร์ และกระบวนการส่งผลงาน

---

## การให้คะแนนและเมตริก

### harness คำนวณเมตริกอะไรบ้าง?

ค่าหลัก (Headline) และเป็นตัวเลขเพียงค่าเดียวที่ใช้จัดอันดับการรัน คือ **corpus chrF++** พร้อมด้วยช่วงความเชื่อมั่น 95% นอกจากนี้ ตัวชุดทดสอบ (Harness) จะรายงานเมตริกมาตรฐานอื่นๆ ควบคู่ไปด้วย ได้แก่ **BLEU, spBLEU และ TER** รวมถึง **COMET** เมื่อมีการติดตั้งไว้ โดยแต่ละค่าจะแสดงแยกกัน ไม่มีการนำมาคำนวณผสมกัน ส่วนค่าอื่นๆ ทั้งหมดถือเป็น**ค่าการวินิจฉัย (Diagnostic)** ซึ่งจะรายงานแยกต่างหากเพื่อใช้อธิบายคะแนน แต่จะไม่ถูกนับรวมเป็นส่วนหนึ่งของคะแนน ตารางด้านล่างแสดงรายละเอียดของ chrF++ และค่าการวินิจฉัยหลักๆ โดยสามค่าแรกไม่ขึ้นกับภาษาใดภาษาหนึ่ง (Language-agnostic) ส่วนอีกสองค่าในปัจจุบันยังต้องพึ่งพาปลั๊กอินเฉพาะของภาษา CRK และจะถูกปรับให้รองรับภาษาทั่วไปเมื่อเราขยายไปยังภาษาอื่นๆ เพิ่มเติม คลังข้อมูลอ้างอิงที่สามารถรันได้ในปัจจุบันเป็นชุดข้อมูลสาธารณะที่ใช้สัญญาอนุญาตแบบเปิด ได้แก่ Global Voices, Tatoeba, TICO-19, IN22, SMOL และอื่นๆ (ดูที่ [ชุดข้อมูล](/docs/network/leaderboard/datasets)) และกระดานผู้นำ (Leaderboard) ก็เปิดรับการส่งผลงานสำหรับทุกคู่ภาษาที่ลงทะเบียนไว้ ภาษา Plains Cree เป็นเพียงภาษาแรกที่มีการนำเมตริกเฉพาะภาษาทั้งสองตัว (ที่ทำงานเบื้องหลังด้วย FST) มาใช้งาน

| เมตริก | สเกล | สิ่งที่วัดผล | สถานะ |
|--------|-------|-----------------|--------|
| **chrF++** (ค่าหลัก) | 0–100 | ความทับซ้อนของ Character n-gram ระหว่างคำแปลที่คาดการณ์กับคำแปลอ้างอิง โดยคำนวณจากทั้งคลังข้อมูลด้วย sacreBLEU (มีการบันทึก Signature ไว้) เป็นเมตริกระดับพื้นผิวที่เป็นมาตรฐานสำหรับภาษาที่มีการเปลี่ยนแปลงรูปคำสูง | ✅ ทุกภาษา |
| **Exact match** (การวินิจฉัย) | 0.0–1.0 | สัดส่วนของรายการที่ผลการคาดการณ์ตรงกับคำแปลอ้างอิงทุกประการหลังผ่านกระบวนการ Normalization | ✅ ทุกภาษา |
| **FST acceptance** (การวินิจฉัย) | 0.0–1.0 | สัดส่วนของคำในผลลัพธ์ที่ได้รับการยอมรับโดย Finite-state transducer (เครื่องมือวิเคราะห์ทางสัณฐานวิทยา) จะคำนวณเฉพาะเมื่อมีการระบุไบนารี FST เท่านั้น | ✅ ทุกภาษาที่มี FST |
| **Equivalent match** (การวินิจฉัย) | 0.0–1.0 | สัดส่วนของรายการที่ตรงกับคำแปลอ้างอิงหรือรูปแบบอื่นที่ยอมรับได้ โดยพิจารณาถึงลำดับคำ หลักเกณฑ์การสะกดคำ และความแตกต่างทางภาษาถิ่น | ⚡ CRK (กำลังขยายการรองรับ) |
| **Semantic score** (การวินิจฉัย) | 0.0–1.0 | คะแนนการรักษาความหมาย — ผลการแปลสามารถสื่อความหมายที่แท้จริงได้ดีเพียงใด โดยไม่ขึ้นกับรูปแบบการเขียนระดับพื้นผิว | ⚡ CRK (กำลังขยายการรองรับ) |

การวินิจฉัยเพิ่มเติม — **ความแม่นยำทางสัณฐานวิทยา (Morphological accuracy)**, **การสลับรหัสภาษา (Code-switching)**, **การยึดตามคำศัพท์เฉพาะ (Terminology adherence)**, **อาการประสาทหลอน (Hallucination)** และ**รูปแบบการเขียน (Writing style)** — รวมถึงสถานะการนำไปใช้งานของแต่ละเมตริก สามารถดูได้ใน [ข้อกำหนดการให้คะแนน §2](/docs/network/specifications/scoring#2-metric-inventory) ซึ่งเป็นรายการเมตริกฉบับเต็ม

### การให้คะแนนการรันทำอย่างไร?

ทุกการรันใหม่จะได้รับการให้คะแนนภายใต้มาตรฐานการให้คะแนน `standard/1` ตามแนวทางที่แวดวงการประเมินผลการแปลด้วยเครื่อง (MT evaluation) รายงานกัน (เช่น WMT, FLORES-200, AmericasNLP):

- **ค่าหลัก (Headline):** corpus chrF++ ระบุพร้อมกับค่า Bootstrap CI ที่ 95% และ sacreBLEU Signature — ตัวอย่างเช่น `chrF++ 47.5 [45.9, 49.0]`
- **ควบคู่กัน:** BLEU, spBLEU, TER และ COMET เมื่อมีการคำนวณ โดยไม่มีการนำมารวมผสมกัน
- **การวินิจฉัย:** Exact match, FST acceptance, ความแม่นยำทางสัณฐานวิทยา, การสลับรหัสภาษา, อาการประสาทหลอน, คำศัพท์เฉพาะ, รูปแบบการเขียน รายงานแยกต่างหากและไม่นำมาใช้จัดอันดับการรัน
- **ข้อควรระวังของคะแนน (Score caveats)** จะพิมพ์แสดงไว้ข้างๆ ค่าหลักทันทีเมื่อชุดทดสอบตรวจพบรูปแบบที่ทำให้ตัวเลขดังกล่าวชวนให้เข้าใจผิด

การตัดสินว่าการรันหนึ่ง**ดีกว่า**อีกการรันหนึ่งหรือไม่ จะตัดสินด้วยการทดสอบนัยสำคัญแบบจับคู่ (Paired significance test) บน chrF++ (`mt-eval compare --significance`) ไม่ใช่การเปรียบเทียบตัวเลขสองตัวโดยตรง กฎเกณฑ์ฉบับเต็ม: [วิธีการให้คะแนนการรัน](/docs/network/specifications/scoring#how-runs-are-scored) และ [ข้อกำหนดการทดสอบนัยสำคัญ](/docs/network/specifications/significance)

### เกิดอะไรขึ้นกับคะแนนรวม (Composite score) และระดับคุณภาพ (Quality tiers)?

ทั้งสองอย่างได้**ยกเลิกการใช้งานแล้ว**สำหรับการรันใหม่ คะแนนรวมเดิมเกิดจากการนำ chrF++, Exact match, FST acceptance และสัญญาณอื่นๆ มาถ่วงน้ำหนักผสมกัน และระดับคุณภาพ (Baseline → Fluent) ก็เป็นป้ายกำกับที่อ่านค่ามาจากคะแนนดังกล่าว ข้อมูลนำเข้าหลายตัวไม่ได้เปรียบเทียบผลลัพธ์กับข้อความต้นทางหรือข้อความอ้างอิงเลย ทำให้ระบบสามารถได้คะแนนส่วนใหญ่ไปโดยไม่ได้แปลจริง ตัวอย่างเช่น โมเดลภาษาอังกฤษ→นอร์เทิร์นซามีที่ยังไม่ได้ผ่านการเทรน ซึ่งพิมพ์ประโยคที่ถูกต้องประโยคเดิมซ้ำๆ สำหรับทุกอินพุต ได้คะแนน 0.6244 — พร้อมติดป้ายกำกับว่า "functional" — ทั้งที่มีค่า chrF++ เพียง 5.5 การ์ดแสดงผลการรันใหม่จึงเปลี่ยนมาแสดง `composite: null` และ `quality_tier: null` แทน

การ์ดที่เผยแพร่ก่อนที่จะมีมาตรฐานนี้จะยังคงเก็บคะแนนรวมเดิมไว้และสามารถตรวจสอบได้ โดยเมื่อใดก็ตามที่มีการแสดงผล จะถูกระบุป้ายกำกับว่า **คะแนนรวมแบบเดิม (ยกเลิกแล้ว)** ดูรายละเอียดที่ [เหตุผลที่ยกเลิกการใช้คะแนนรวม](/docs/network/specifications/scoring#why-the-composite-was-retired)

คะแนนจากการประเมินอัตโนมัติไม่ใช่ข้อตัดสินด้านคุณภาพ มีเพียงการประเมินโดยมนุษย์ซึ่งเป็นผู้พูดภาษานั้นเท่านั้นที่จะรับรองคุณภาพได้

### ระดับการตรวจสอบยืนยัน (Verification tiers) คืออะไร?

**ระดับการตรวจสอบยืนยัน** เป็นตัวอธิบายว่า *ใครเป็นผู้ตรวจสอบผลลัพธ์* ไม่ใช่การบอกว่าผลลัพธ์นั้นดีเพียงใด:

| ระดับการตรวจสอบ | ความหมาย |
|-------------------|---------------|
| **ทดสอบด้วยตนเอง (Self-benchmarked)** | ผู้ส่งรันชุดเครื่องมือทดสอบด้วยตนเอง คะแนนดูสมเหตุสมผลแต่ยังไม่ได้รับการตรวจสอบ |
| **ยืนยันโดย Champollion (Champollion Verified)** | โครงการได้คำนวณคะแนนของผลลัพธ์ที่ส่งมาใหม่เทียบกับคลังข้อมูลอ้างอิงที่ระบุ sha แน่นอน และได้คะแนนตรงกัน การคำนวณคะแนนใหม่เป็นคำสั่งของผู้ดูแลที่รันด้วยตนเอง ดังนั้นในปัจจุบันจึงยังไม่มีแถวข้อมูลใดที่ได้รับการเลื่อนระดับทันทีเมื่อส่งเข้ามา |
| **รับรองโดยชุมชน (Community Validated)** | ผู้พูดสองภาษาของภาษาเป้าหมาย ซึ่งมีคุณสมบัติตามเกณฑ์วิธีของชุมชนเอง ได้ตรวจสอบกลุ่มตัวอย่างแบบแบ่งชั้นของผลลัพธ์ (≥30 รายการ, ผู้ตรวจ ≥2 คน) และมีผลลัพธ์ ≥70% ที่ผ่านเกณฑ์ของชุมชน การรับรองนี้มอบให้ผ่านการทดสอบของชุมชนเองเท่านั้น และการลดระดับโดยการสุ่มตรวจสอบก็ใช้หลักการเดียวกันและเปิดเผยต่อสาธารณะเช่นกัน |

การรันอาจได้คะแนน chrF++ ที่สูงมาก แต่ยังคงอยู่ในระดับ "Self-benchmarked" เท่านั้น — ซึ่งหมายความว่ายังไม่มีใครตรวจสอบยืนยันคะแนนดังกล่าวอย่างเป็นอิสระ และยังไม่มีผู้พูดภาษานั้นมาตัดสินผลลัพธ์

## การส่งผลงานและการตัดสิทธิ์

### อะไรทำให้การส่งผลงานของฉันถูกตัดสิทธิ์?

การส่งผลงานของคุณจะถูกปฏิเสธหรือถูกตั้งค่าสถานะหากมีสิ่งต่อไปนี้:

1. **วิธีการของคุณถูกเปิดเผยต่อข้อมูลการประเมิน** หากคุณฝึก fine-tune few-shot-prompt หรือใช้รายการใดๆ จากชุดข้อมูลการประเมินในทางใดทางหนึ่ง คะแนนของคุณจะถูกเพิ่มขึ้นอย่างไม่เป็นธรรม ซึ่งรวมถึงการใช้การแปลอ้างอิงใน prompt ของคุณด้วย
2. **run card ของคุณไม่ผ่านการตรวจสอบความสมบูรณ์** fingerprint ต้องตรงกับการกำหนดค่า run card ที่ถูกแก้ไขจะถูกปฏิเสธ
3. **วิธีการของคุณไม่ได้ implement โปรโตคอล TranslationMethod** harness คาดหวัง `translate(entries, config) → results` การ integration แบบกำหนดเองที่ข้าม harness จะไม่ได้รับการยอมรับ

### ฉันสามารถส่งผลงานได้หลายครั้งหรือไม่?

ได้ leaderboard ติดตามการส่งผลงานทั้งหมด คุณสามารถทำซ้ำได้ — รันการทดลองหลายสิบครั้ง แล้วส่งเฉพาะผลที่ดีที่สุด การส่งผลงานแต่ละครั้งบันทึก fingerprint ที่ไม่ซ้ำกัน จึงไม่มีความคลุมเครือว่า run ใดให้คะแนนใด

### ฉันจะให้คะแนนของฉันได้รับการยืนยันได้อย่างไร?

1. **Self-benchmarked:** ทุกการส่งผลงานจะเริ่มต้นที่ระดับนี้ และในปัจจุบันทุกแถวบนกระดานก็ยังคงอยู่ที่ระดับนี้
2. **Champollion Verified:** โครงการจะนำผลลัพธ์ที่คุณส่งมาไปคำนวณคะแนนใหม่เทียบกับคลังข้อมูลอ้างอิงที่ระบุ SHA ไว้อย่างชัดเจนโดยใช้เมตริกของชุดทดสอบ เมื่อคะแนนของคุณสามารถทำซ้ำได้ การรันนั้นจะเลื่อนระดับขึ้นเป็น Champollion Verified — ซึ่งเป็นระดับเริ่มต้นที่การจัดอันดับการแข่งขันใช้ และเป็นระดับเดียวที่มีสิทธิ์รับรางวัล สำหรับกระดานสาธารณะจะแสดงแถวที่เป็น Self-benchmarked ด้วยเช่นกันโดยระบุป้ายกำกับไว้อย่างชัดเจน หากผลลัพธ์ไม่สามารถทำซ้ำได้ หรือข้อความอ้างอิงที่จัดเก็บไว้ถูกดัดแปลง การรันนั้นจะถูกตัดสิทธิ์ การคำนวณคะแนนใหม่เป็นงานแบบแบทช์ของผู้ดูแลโครงการที่ดำเนินการด้วยตนเอง ไม่มีระบบอัตโนมัติรันเมื่อมีการส่งผลงาน และไม่มีการตั้งเวลาล่วงหน้า
3. **Community Validated:** ผู้พูดภาษาเป้าหมายที่สื่อสารได้สองภาษาและผ่านเกณฑ์คุณสมบัติตามเกณฑ์วิธีของชุมชนเอง จะทำการตรวจสอบกลุ่มตัวอย่างแบบแบ่งชั้นจากผลลัพธ์ของวิธีที่คุณใช้ — อย่างน้อย 30 รายการ โดยมีผู้ประเมินอย่างน้อย 2 คน — และต้องผ่านเกณฑ์ของชุมชนอย่างน้อย 70% ระดับนี้มอบให้ผ่านการทดสอบที่ชุมชนดำเนินการเองตามดุลยพินิจเท่านั้น และสามารถเพิกถอนได้ด้วยวิธีเดียวกัน นั่นคือ หากการสุ่มตรวจไม่ผ่านก็จะถูกปรับลดระดับอย่างเปิดเผยต่อสาธารณะเช่นกัน กระบวนการนี้ไม่สามารถทำแบบอัตโนมัติได้ — จำเป็นต้องอาศัยการมีส่วนร่วมของชุมชน

### ทำไมคุณถึงไม่รันวิธีของทุกคนซ้ำทั้งหมดเพื่อตรวจสอบยืนยัน?

เนื่องจากเราไม่สามารถแบกรับค่าใช้จ่ายได้และไม่มีความจำเป็นต้องทำเช่นนั้น การนำผลลัพธ์ที่*ทุกคน*ส่งมาไปคำนวณคะแนนใหม่นั้นไม่มีค่าใช้จ่าย (ซึ่งช่วยดักจับคะแนนที่พิมพ์ขึ้นมาเองหรือผ่านการแก้ไขมาได้) แต่การรันโมเดลซ้ำจริงๆ นั้นต้องใช้ทรัพยากรประมวลผลสูง ดังนั้นกระบวนการนี้จึงจะเกิดขึ้นกับ**กลุ่มตัวอย่าง**ที่คัดเลือกผ่าน**การตรวจสอบแบบถ่วงน้ำหนักด้วยชื่อเสียง (Reputation-weighted auditing)** — นโยบายการสุ่มตัวอย่างถูกสร้างและทดสอบเรียบร้อยแล้ว แต่ตัวระบบรันซ้ำที่จะขับเคลื่อนนโยบายนี้ยังสร้างไม่เสร็จ จึงยังไม่มีการสุ่มรันซ้ำเกิดขึ้นจริงในตอนนี้ และการรันที่ถูกเลือกจะถูกบันทึกสถานะไว้เป็น *L2-pending* ภายใต้นโยบายดังกล่าว การรันจะถูกเลือกเสมอหากมีความสำคัญสูงมาก (เช่น เป็นการบุกเบิกสะพานเชื่อมภาษาแรกไปยังตระกูลภาษาทั้งหมด) หรือมีความผิดปกติ (คะแนนก้าวกระโดดแซงหน้าสถิติเดิมที่ดีที่สุดจนดูเกินจริง) ในขณะที่ผลงานจากผู้ร่วมสมทบที่ได้รับการพิสูจน์แล้วจะถูกสุ่มตรวจเพียงนานๆ ครั้ง ชื่อเสียงจะได้รับก็ต่อเมื่อผ่านการตรวจสอบเหล่านี้เท่านั้น (หรือมีผู้ร่วมสมทบอิสระมายืนยันผลลัพธ์ของคุณซ้ำ) — ไม่ได้ขึ้นอยู่กับปริมาณงานที่ส่ง — ดังนั้นการสร้างตัวตนใหม่ชั่วคราวเพื่อส่งผลงานจึงไม่ได้ประโยชน์อะไร หากตรวจพบการปลอมแปลงข้อมูลแม้แต่ครั้งเดียว ชื่อเสียงของผู้ร่วมสมทบรายนั้นจะกลายเป็นศูนย์ทันที ประวัติการตรวจสอบที่ผ่านมาทั้งหมดจะถูกนำกลับมาตรวจใหม่ และจะมีการบันทึกไว้ต่อสาธารณะในลักษณะเดียวกับการเพิกถอนผลงาน เรา**ไม่**อ้างว่าการรันของคุณ "ผ่านชุดทดสอบมาแล้ว" — เพราะการประมวลผลบนเครื่องส่วนตัว (Self-hosted) ไม่สามารถตรวจสอบผ่านเซิร์ฟเวอร์ได้ — ความถูกต้องสมบูรณ์จึงขึ้นอยู่กับ *ความสามารถในการทำซ้ำ + การเอาชื่อเสียงเป็นเดิมพัน + การยืนยันความถูกต้อง* ไม่ใช่การรับรองด้วยวาจา ดูรายละเอียดโมเดลฉบับเต็มได้ที่ [กฎการประเมินผล MT](/docs/network/leaderboard/rules#how-verification-scales-reputation-weighted-auditing)

### API การส่งผลงานพร้อมใช้งานแล้วหรือยัง?

ยังไม่รองรับในขณะนี้ endpoint `https://champollion.dev/api/leaderboard/submit` เป็นเป้าหมายที่วางแผนไว้ในอนาคต เส้นทางการส่งผลงานในปัจจุบันคือ `mt-eval publish` — ซึ่งอัปโหลด run card จากไดเรกทอรีผลลัพธ์ของระบบทดสอบ (`eval/logs/harness/`) ไปยัง leaderboard โดยตรงในสถานะ *self-benchmarked (unverified)*

## โมเดลและพารามิเตอร์

### ฉันควรใช้โมเดลใด?

ไม่มีโมเดลที่ดีที่สุดเพียงตัวเดียว — ขึ้นอยู่กับคู่ภาษา งบประมาณ และแนวทางของคุณ คำแนะนำทั่วไป:

| ประเภทภาษา | จุดเริ่มต้นที่แนะนำ | เหตุผล |
|---------------|---------------------------|-----|
| **ทรัพยากรสูง** (ฝรั่งเศส, สเปน, ญี่ปุ่น) | โมเดลระดับ "flash" ที่เร็วและประหยัด | รวดเร็ว ประหยัด เป็นเกณฑ์มาตรฐานที่แข็งแกร่ง |
| **ทรัพยากรต่ำที่มีข้อมูลใน LLM อยู่บ้าง** (เกชัว, โยรูบา) | โมเดลระดับ "pro" ที่ใหญ่ขึ้น | โมเดลขนาดใหญ่กว่ามีความรู้แฝงที่ดีกว่า |
| **ภาษาหลายหน่วยคำ / ทรัพยากรต่ำมาก** (ครีแถบที่ราบ, อินุกติตุต) | โมเดลขนาดใหญ่ขึ้นพร้อมการชี้แนะ (coaching) | ข้อมูลการชี้แนะมีความสำคัญมากกว่าการเลือกโมเดล OMT-1600 มีภาษาหลายหน่วยคำรวมอยู่บ้าง (เช่น CRK ที่ระดับ R1) แต่ใช้การแบ่งโทเคนแบบ BPE มาตรฐาน — ให้ทดสอบเทียบเป็นเกณฑ์มาตรฐานในเครือข่าย |

ระบุชื่อโมเดลด้วย slug ที่ตรงกันทุกประการ (`provider/model` บน OpenRouter) โดยระบบจะไม่ยอมรับชื่อแทนแบบย่อและ id ที่ไม่ระบุเวอร์ชันแน่ชัด (`…-latest`) ค่าเริ่มต้นที่ CLI และชุดเครื่องมือทดสอบใช้จะอยู่ใน `shared/model-defaults.json` ชุดเครื่องมือทดสอบจะใช้ OpenRouter เป็นค่าเริ่มต้น ดังนั้นโมเดลใดก็ตามที่มีให้บริการที่นั่นจึงสามารถนำมาทดสอบเทียบมาตรฐานได้ ([openrouter.ai/models](https://openrouter.ai/models)) ทั้งนี้ คุณสามารถใช้คีย์จากผู้ให้บริการโดยตรงหรือโมเดลบนเครื่องของคุณเองได้เช่นกัน

### ฉันควรใช้ temperature เท่าไหร่?

ค่าเริ่มต้นคือ **0** (กำหนดผลลัพธ์แน่นอน) สำหรับทั้ง CLI และชุดเครื่องมือทดสอบ — เป็นค่าเดียว เพื่อให้สิ่งที่วัดได้คือสิ่งที่จะถูกนำไปใช้งานจริง โดยทั่วไปแล้วค่ายิ่งต่ำยิ่งส่งผลดีต่อการแปล:

| Temperature | ผล | แนะนำสำหรับ |
|-------------|--------|-----------------|
| **0.0 – 0.2** | ผลลัพธ์ที่กำหนดได้สูง สม่ำเสมอ | วิธีการสำหรับ production, benchmark ขั้นสุดท้าย |
| **0.3 – 0.5** | มีความหลากหลายบ้าง บางครั้งสร้างสรรค์มากขึ้น | การสำรวจ การทำซ้ำในระยะเริ่มต้น |
| **0.6+** | ความหลากหลายสูง คาดเดาไม่ได้ | ไม่แนะนำสำหรับการทำ MT benchmark |

Temperature ถูกบันทึกใน run card ดังนั้น temperature ที่แตกต่างกันจะให้ fingerprint ที่แตกต่างกัน — ถือเป็นการทดลองที่แตกต่างกัน

### ข้อมูล coaching ช่วยได้หรือไม่?

ช่วยได้อย่างมีนัยสำคัญ — โดยเฉพาะสำหรับภาษาที่มีทรัพยากรต่ำ ข้อมูล coaching (กฎไวยากรณ์ รายการพจนานุกรม หมายเหตุสไตล์) ถูกแทรกเข้าไปใน system prompt ของ LLM สำหรับ Plains Cree วิธีการที่ใช้ coaching มีประสิทธิภาพเหนือกว่าวิธีการ LLM ดิบสำหรับภาษา polysynthetic อย่างสม่ำเสมอ เนื่องจาก LLM ทั่วไปมีการเรียนรู้ภาษา polysynthetic จำกัดและไม่มีความตระหนักทางสัณฐานวิทยา แม้แต่ OMT-1600 ที่ได้รับการฝึกเฉพาะสำหรับ CRK ก็ยังใช้ tokenization แบบ BPE มาตรฐานที่ไม่สามารถแสดงสัณฐานวิทยา polysynthetic ในเชิงโครงสร้างได้ ข้อมูล coaching ให้บริบทเชิงภาษาศาสตร์ที่โมเดลขาดอยู่

สำหรับภาษาที่มีทรัพยากรสูง (ฝรั่งเศส สเปน) coaching มีผลกระทบน้อยกว่า เนื่องจากโมเดลมีความรู้พื้นฐานที่แข็งแกร่งอยู่แล้ว

ดู [Coaching Data](https://champollion.dev/docs/concepts/coaching-data) สำหรับข้อกำหนดฉบับสมบูรณ์

## FST และการตรวจสอบสัณฐานวิทยา

### จะทำอย่างไรถ้าไม่มี FST สำหรับภาษาของฉัน?

หลายภาษายังไม่มี Finite-state transducer ซึ่งไม่เป็นไร — ชุดทดสอบสามารถทำงานได้แม้ไม่มี FST เนื่องจากค่าหลักคือ chrF++ ไม่ว่าจะกรณีใดก็ตาม การรันที่มีหรือไม่มี FST จึงได้รับการให้คะแนนในลักษณะเดียวกัน FST acceptance เป็นเพียงค่าการวินิจฉัย และจะถูกทำเครื่องหมายเป็น `null` ในการ์ดแสดงผลการรันเมื่อไม่ได้ใช้งาน FST

registry หลักสำหรับ FST ที่มีอยู่:

| ทะเบียนข้อมูล (Registry) | ภาษาที่ครอบคลุม | URL |
|----------|----------|-----|
| **GiellaLT** | มากกว่า 100 ภาษา — กลุ่มภาษาซามี, ครี, อินุกติตุต และกลุ่มภาษาฟินโน-อูกริก รวมถึงภาษาชนกลุ่มน้อยอื่นๆ อีกมากมาย | [giellalt.uit.no](https://giellalt.uit.no/) |
| **ALTLab** | Plains Cree, Tsuut'ina, Odawa | [altlab.ualberta.ca](https://altlab.ualberta.ca/) |
| **Apertium** | ~60 คู่ภาษา โดยส่วนใหญ่เป็นภาษาในยุโรป | [apertium.org](https://apertium.org/) |
| **UniMorph** | แบบจำลองกระบวนทัศน์ทางสัณฐานวิทยา (Morphological paradigms) สำหรับมากกว่า 150 ภาษา | [unimorph.github.io](https://unimorph.github.io/) |

### ฉันสามารถสร้าง FST ได้หรือไม่?

ได้ แต่ไม่ใช่เรื่องง่าย FST เข้ารหัสกฎสัณฐานวิทยาของภาษา — รูปแบบคำที่ถูกต้องทั้งหมด การสร้าง FST ต้องการความรู้เชิงภาษาศาสตร์เชิงลึกเกี่ยวกับภาษานั้น หากคุณมีไวยากรณ์สัณฐานวิทยา (เช่น จากภาควิชาภาษาศาสตร์) สามารถคอมไพล์เป็น FST ได้โดยใช้เครื่องมืออย่าง [HFST](https://hfst.github.io/) หรือ [Foma](https://fomafst.github.io/)

### FST gating ทำงานอย่างไรในทางปฏิบัติ?

pipeline ที่ใช้ FST gating ทำงานดังนี้:

1. LLM สร้างการแปล
2. แต่ละคำในผลลัพธ์ถูกตรวจสอบกับ FST
3. คำที่ FST ปฏิเสธจะถูกตั้งค่าสถานะว่าไม่ถูกต้องทางสัณฐานวิทยา
4. วิธีการสามารถลองใหม่พร้อม feedback ("คำ X ไม่ถูกต้อง ลองอีกครั้ง")
5. หลังจากลองใหม่แล้ว คำที่ยังไม่ถูกต้องจะถูกบันทึกไว้

อัตราการยอมรับของ FST จะวัดว่ามีคำจำนวนเท่าใดที่ผ่านการตรวจสอบความถูกต้อง ดูตัวอย่างการทำงานฉบับสมบูรณ์ได้ที่ [บทเรียนกระบวนการทำงานที่มี FST ควบคุม](/docs/agents/methods)

## ข้อมูลและชุดข้อมูล

### ฉันสามารถมีส่วนร่วมในการสร้างชุดข้อมูลสำหรับภาษาใหม่ได้หรือไม่?

ได้ ข้อกำหนดขั้นต่ำจาก [Benchmark Specification §11](/docs/network/specifications/benchmark#11-extending-to-new-languages):

- **50 รายการมาตรฐานทอง** (ต้นฉบับ + การแปลอ้างอิงที่ผ่านการยืนยัน)
- **30 รายการสำหรับพัฒนา** (สามารถทับซ้อนกับมาตรฐานทองได้สำหรับคลังข้อมูลขนาดเล็ก)
- **ความยินยอมของชุมชน** (สำหรับภาษาของชนพื้นเมือง ต้องได้รับการอนุญาตอย่างชัดเจนจากองค์กรกำกับดูแล)
- **เอกสารแหล่งที่มา** (ข้อมูลมาจากไหน มีสัญญาอนุญาตอะไรบ้าง)

ชุดข้อมูลใหม่จะเปิดหมวดการแข่งขันใหม่บนลีดเดอร์บอร์ดโดยอัตโนมัติ ดูคู่มือสำหรับผู้ร่วมสมทบได้ที่ [คำของคุณ กฎของคุณ](/docs/your-words-your-rules)

### ชุดข้อมูลของฉันควรอยู่ในรูปแบบใด?

JSON พร้อมชื่อฟิลด์มาตรฐาน:

```json
{
  "name": "my-language-dev-v1",
  "language_pair": "en-xxx",
  "segment": "development",
  "version": "1.0",
  "entries": [
    {
      "id": 1,
      "source": "Hello",
      "reference": "[translation in target language]",
      "difficulty": 1,
      "domain": "general"
    }
  ]
}
```

ดู [Datasets](/docs/network/leaderboard/datasets) สำหรับ schema ฉบับสมบูรณ์และคำจำกัดความของระดับความยาก

## อธิปไตยและความเป็นเจ้าของ

### ใครเป็นเจ้าของวิธีการที่สร้างขึ้นสำหรับภาษาของชนพื้นเมือง?

สิทธิ์เป็นของคุณ เว้นแต่คุณจะตกลงเป็นอย่างอื่น ตำแหน่งบนลีดเดอร์บอร์ดสาธารณะไม่มีการโอนสิทธิ์ใดๆ สิทธิ์จะโอนก็ต่อเมื่อคุณเข้าร่วมการประกวดแบบปิด (sealed contest) ภายใต้ข้อกำหนดของรางวัลที่ผู้จัดประกาศไว้ล่วงหน้าก่อนที่จะมีใครเข้าร่วม — ซึ่งมีหนึ่งในสามข้อกำหนดต่อไปนี้ ([ข้อกำหนดของรางวัล §1.3](/docs/network/specifications/prizes#1-3-declared-terms)):

- `pass_to_holders` — กรรมวิธีจะตกเป็นของผู้ดูแลการทดสอบเทียบมาตรฐานที่เป็นเจ้าของสิทธิ์ (ดูรายละเอียดใน [เทมเพลตการโอนสิทธิ์ให้ชุมชน](/docs/network/sovereignty/ownership-transfer))
- `retain_ip` — คุณยังคงเป็นเจ้าของ ผู้จัดจะเก็บสำเนาที่ปิดผนึกไว้สำหรับการตรวจสอบความถูกต้องเท่านั้น
- `release_open` — คุณยังคงเป็นเจ้าของ แต่ต้องเผยแพร่กรรมวิธีภายใต้สัญญาอนุญาตแบบเปิด

ภายใต้ `pass_to_holders` นักวิจัยยังคงมีสิทธิ์ต่อไปนี้:
- สิทธิ์ในการตีพิมพ์ (ผลงานวิชาการเกี่ยวกับกรรมวิธีดังกล่าว)
- การให้เครดิตบนลีดเดอร์บอร์ด
- สิทธิ์ในการนำ*เทคนิค*เดียวกันนี้ไปใช้กับภาษาอื่น

และผู้ถือสิทธิ์จะได้รับ:
- กรรมสิทธิ์โดยสมบูรณ์ในโค้ดของกรรมวิธีและข้อมูลการชี้แนะ (coaching data)
- การควบคุมการนำไปใช้งาน (เมื่อใด ที่ไหน อย่างไร) — รวมถึงรายได้ทั้งหมดที่เกิดจากการนำไปใช้งาน Champollion ไม่มีส่วนแบ่งใดๆ

### ฉันสามารถใช้ champollion สำหรับภาษาที่ไม่ใช่ภาษาของชนพื้นเมืองโดยไม่มีข้อกังวลด้านอธิปไตยได้หรือไม่?

ได้ สำหรับภาษามาตรฐานทั่วไป (เช่น ภาษาฝรั่งเศส ภาษาสเปน ภาษาญี่ปุ่น ฯลฯ) จะไม่มีข้อพิจารณาเรื่องอำนาจอธิปไตยเหนือข้อมูล คุณสามารถใช้ champollion ได้ตามปกติ — แปลข้อมูล ซิงค์ และเผยแพร่ได้ตามที่คุณต้องการ ทั้งนี้ กรอบการทำงานด้านอำนาจอธิปไตยถูกนำมาใช้โดยเฉพาะกับภาษาของชนพื้นเมืองและภาษาที่มีชุมชนเป็นผู้กำกับดูแล ซึ่งหลักการกำกับดูแลข้อมูล — ความเป็นเจ้าของและการควบคุมข้อมูลภาษาของชุมชน, CARE, Te Mana Raraunga — จำเป็นต้องได้รับการพิจารณาเป็นพิเศษ
