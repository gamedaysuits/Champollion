# 정직한 한계

> 이것들은 우리가 **넘지 않을** 주장들이에요. 이 사이트의 다른 곳에서
> 여기에 적힌 것보다 더 많은 것을 암시하는 내용이 있다면, 버그로 간주하고
> [알려주세요](/docs/network/perspectives/reporting-errors-and-owning-corrections).

평가 인프라는 그 경계에 대해 정직할 때에만 신뢰를 얻어요. 여기
우리의 한계들이 확인할 수 있을 만큼 명확하게 기술되어 있어요.

## 1. 심층 형태론적 검증은 FST*와* 순위 산정이 가능한 테스트 세트에 의존해요

FST 기반 형태론적 검증(모든 출력 단어가 타깃 언어에서 올바른 형태의 단어인지 확인하는 작업)을 언어 쌍에 적용하려면 두 가지가 필요해요. 하네스가 고정한 FST와 해당 언어 쌍에 대해 순위를 매길 수 있는 평가 세트예요. `GiellaLTFSTMetric` 자체는 **범용적**이에요. GiellaLT FST가 고정된 언어(플레인스 크리어, 사미어군, 핀란드어, 노르웨이어 보크몰, 이누크티투트어 등)라면 어떤 언어든 점수를 매겨요. 이들 언어 중 일부는 공개 평가 세트(Tatoeba, WMT, WMT24++)를 보유하고 있어요. [데이터셋 페이지](/docs/network/leaderboard/datasets)에 카탈로그가 정리되어 있고, `mt-eval corpora --source eng --target <code>`에는 언어 쌍별로 실행 가능한 항목이, `mt-eval corpora --with-fst`에는 타깃 언어에 고정 FST가 있는 언어 쌍과 로컬 머신 설치 여부만 정리되어 있어요.
FST 작업이 처음 시작된 언어인 플레인스 크리어는 예외예요. 두 개의 평가 세트(EdTeKLA)가 격리 라벨로 분류되어 있어서, 데이터베이스는 이들을 대상으로 제출된 점수를 거부해요.

여기에 두 가지 제한이 더 적용돼요. 고정된 FST가 맞춤법 검사용 **수용기(acceptor)**에 불과한 경우(북부 사미어, 암하라어, 바스크어), 단어의 존재 여부만 알 수 있을 뿐 올바르게 굴절되었는지는 알 수 없어서 `morphological_accuracy`가 계산되지 않아요. 또한 수용기는 일부 영어 및 대문자로 시작하는 단어도 수용하므로, FST 수용이 번역되지 않은 출력을 인정해 버릴 수 있어요(이 경우 실행 카드에 원문 복사 주의 문구가 표시돼요. [점수 관련 주의사항](/docs/network/specifications/scoring#2-8-score-caveats)을 참고하세요). FST 수용은 진단용 지표일 뿐이에요. chrF++ 대표 점수에 반영되지 않으며 실행 순위 산정에도 사용되지 않아요.
또한 모든 입력에 대해 유효한 문장 하나를 반복해서 내놓는 경우에도 점수를 인정하므로, 실행 카드에 유사 상수 출력 주의 문구가 표시돼요.
그리고 FST가 없는 모든 언어 쌍은 표면적 지표(chrF++, BLEU) 및 동작 검사를 통해 점수가 매겨져요. 이는 유용한 신호이지만 형태론적 타당성을 **보장하지는 않아요**. FST와 순위 산정이 가능한 평가 세트를 둘 다 갖추지 않은 언어에 대해서는 형태론적 검증을 주장하지 않아요.

## 2. 신뢰 등급은 출시 시점에 자체 보고돼요

대부분의 점수는 기여자가 직접 하네스를 실행하고 그 결과를
게시하여 계산돼요. 서버 측 **검증** — SHA로 고정된 표준 코퍼스에 대해
제출물을 다시 채점하는 것 — 이 존재하고 확대되고 있지만,
"검증됨"이 아직 보편적이지는 않아요. 각 행의 신뢰 배지를 확인하세요: **"자체 보고됨"은
말 그대로의 의미이며**, 이것이 기본값이에요.

## 3. 커뮤니티 화자 검증은 아직 이루어지지 않았어요

저희 상금 요건은 **이중언어 화자로부터 ≥ 70%의 수용도**를 얻는 것이에요. 해당 관문은 명세화되어 있고 이를 실행하기 위한 도구가 개발 중이지만, **커뮤니티 화자 평가는 아직 진행되지 않았으며**, **본 사이트의 어떤 점수도 화자 관문을 통과하지 못했어요**. chrF++를 비롯한 모든 자동 산출 수치는 기계적 신호일 뿐 커뮤니티의 판정이 아니며, 그렇기 때문에 이곳의 어떤 점수에도 품질 라벨이 붙어 있지 않아요.

## 4. 평가 샌드박스와 키 세리머니는 존재하지만, 어떤 관리자도 아직 사용하지 않았어요

저희는 말뭉치를 출처로부터 가져와 SHA로 고정하며, 격리된 분할 데이터는 봉인돼요. 커뮤니티가 비밀 테스트 세트를 보유하고 있을 때, 해당 세트가 커뮤니티의 손을 전혀 벗어나지 않고도 특정 방식에 대한 평가 점수를 산출할 수 있어요. 그리고 이 평가에는 이제 **두 가지 경로**가 있어요.
표준 신경망 모델에 선호되는 경로는 **선언적 방식**이에요. 참가자는 데이터(safetensors 가중치 + 선언적 토크나이저 + 설정)만 제출하고, 주최자는 신뢰할 수 있는 자체 추론 엔진(`trust_remote_code=False`, 오프라인 방식. 안전성은 아키텍처 이름이 아니라 코드가 없는 포맷 자체에서 나오므로 아키텍처에 대해서는 관대함)에서 이를 실행해요. 참가자의 코드가 전혀 실행되지 않으므로 샌드박스를 적용할 대상 자체가 없어요. 이때의 안전성 검사는 임의의 코드가 안전한지 증명하려는 시도가 아니라, 결정 가능한 포맷 검증(pickle이 아닌 safetensors인가? `trust_remote_code`이 없는가?)이에요. 본질적으로 코드 형태인 방식(파이프라인, LLM 코칭 하이브리드)의 경우 대체 경로는 네트워크가 차단된 **샌드박스**(정적 검사, `--network=none` 컨테이너, 점수만 외부로 전송, 선택적 완전 격리 파일 전송)예요. 샌드박스에는 네트워크가 없으므로, 해당 방식은 호출하는 모든 모델을 번들 내에 포함해야만 실행돼요. 호스팅된 LLM API에는 연결할 수 없으므로, LLM 코칭 하이브리드는 LLM을 오픈 가중치로 함께 제공해야 해요. 샌드박스는 신뢰할 수 없는 코드를 실행 거부하는 대신 격리 수용하므로 솔직히 더 취약한 경로예요. 샌드박스의 핵심 보장은 `--network=none`이며(휴리스틱 정적 스캔으로는 바이너리 모델을 검증할 수 없음), 더 깊은 수준의 보안 강화(seccomp, microVM)는 추후로 미뤄두었어요. 현재 실제로 적용된 부분과 그렇지 않은 부분에 대한 자세한 내용은 [소버린 경연 운영하기](/docs/network/sovereignty/run-a-sovereign-contest)를 참고하세요. 오프라인 노드의 **키 세리머니는 구축되어 있어요**. 세트 키를 M-of-N으로 분할하고 쿼럼이 승인한 실행 중에만 메모리에서 재조합하는 방식이지만, 실제 관리자와 함께 사용된 적은 없으며 초기 버전에서는 공유 키가 일반 파일 형태예요. 아직 구축되지 **않은** 항목은 임계값 서명(점수는 단일 노드 키로 서명됨)과 하드웨어 증명(점수 매니페스트는 소프트웨어로만 서명됨)이에요. 아직 관리자가 지정되지 않았으므로, 관리자와 커뮤니티의 동의가 마련될 때까지 골드 표준 **상금** 평가는 비공개 상태로 유지돼요.

## 5. 키 보관 구조는 설계되었지만, 관리자가 아직 지정되지 않았어요

보관 *메커니즘*은 설계되어 있어요. **Champollion이 키 조각을 전혀 보유하지 않도록 설계된** 임계값 방식이에요. 아직 실제 관리자와 함께 운영된 적은 없어요. 관리자는 커뮤니티가 직접 선정하지만 아직 아무도 지정되지 않았기 때문에, 저희는 **"커뮤니티 키 관리자 — 아직 지정되지 않음"**이라고 표기하고 있어요. 보관이 곧 동의를 의미하지는 않아요. 관계 중심의 커뮤니티 동의 프로세스는 이와 별개로 진행되는, 더 느리지만 더 중요한 과정이에요.

## 6. 벤치마크를 기반으로 방식을 측정하며, 개별 번역의 점수를 매기지는 않아요 {#system-vs-output}

서로 다른 두 가지 개념이 모두 "신뢰할 수 있는 기계 번역"이라는 이름으로 불려요. 저희는 그중 하나만 수행해요.

**시스템 수준 — 저희가 하는 일.** 주어진 언어 쌍, 테스트 세트, 방식에 대해: 해당 방식이 어떤 지표에서, 어떤 도메인에서, 어떤 오염 경로에서, 어떤 신뢰 등급으로 점수를 얻는가? 이것은 *벤치마크 기반의 방식*에 대한 주장이며, 기준을 누가 정했는지에 대한 주장이기도 해요. 점수 산정 규칙은 공개되어 있고, 말뭉치는 고정되어 있으며, 소버린 벤치마크의 경우 테스트 세트를 소유한 커뮤니티가 통과 기준을 결정해요. 리더보드, 지도, 실행 카드, `mt-eval`은 모두 이것만을 다루며, 다른 것은 다루지 않아요.

**출력 수준 — 저희가 하지 않는 일.** 주어진 하나의 원문 문장과 그 번역문에 대해: *그* 번역이 맞을 확률은 얼마나 되는가? 기계 번역과 자연어 처리 분야에서는 이를 품질 추정(QE) 및 불확실성 정량화라고 부르며, 이는 독자적인 연구 분야예요. 저희는 **어떤 번역에 대해서도 세그먼트별 신뢰도를 게시하지 않으며**, 이곳의 어떤 내용도 특정 출력이 맞을 확률을 보정해 둔 것이 아니에요. 높은 점수를 받은 행이 해당 방식이 생성할 다음 문장을 보증해 주는 것은 아니에요.

그 반대의 경우에서 실수하기가 더 쉬우며, 이 점은 저희에게도 동일하게 적용돼요. 이곳의 페이지에서 [휴먼 번역 서비스](/human-services)처럼 특정 언어 쌍에 배포할 만큼 충분한 점수를 얻은 방식이 없다고 안내할 때, 이는 측정된 테스트 세트에서 측정된 방식들에 대한 진술이에요. 이는 해당 언어 쌍에 대해 기계 번역 출력을 배포하지 말아야 할 타당한 이유가 되지만, 특정 문장 하나하나에 대한 판정은 아니에요.

**품질 추정(QE)은 비어 있는 슬롯이지 숨겨진 결함이 아니에요.** 하네스는 골드 참조 데이터가 없는 실행에 대한 적절성 신호로서 무참조 신경망 점수인 AfriCOMET-QE(`qe_score`)를 이미 계산하고 있어요. 이는 별도의 신경망 경로에서 **말뭉치 수준** 수치로 보고되고, 검증기에 의해 다시 유도되며, chrF++ 대표 점수에는 결코 포함되지 않아요([점수 산정 명세](/docs/network/specifications/scoring#how-runs-are-scored) 참고). 지표는 플러그인 형태이므로([플러그인 명세](/docs/reference/plugin-spec) 참고), 세그먼트 수준의 QE 지표도 이 하네스가 수용할 수 있는 항목이에요. 참조 기반 지표처럼 언어별로 연결되고, 공개되고, 메타 평가를 거치기 전까지는([지표 신뢰도](/docs/network/specifications/metric-reliability) 참고), 저희는 개별 출력에 대해 어떤 판단도 내리지 않아요.

---

이 한계들은 작업이 진행됨에 따라 변할 거예요. 그중 하나가 변경되면, 이 페이지도
그에 따라 변경돼요 — 그리고 그 변경은 조용히 사라지는 것이 아니라 페이지 기록에서
확인할 수 있어야 해요.
