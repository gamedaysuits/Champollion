# 코퍼스 파트너십 전략: 학술 언어학과를 통한 평가 코퍼스 구축

자원이 부족한 언어를 위한 *학습용* 코퍼스를 구축하려면 수십만 개의
문장 쌍이 필요해요. 이는 일일이 확인하기에는 너무 많은 양이라서, 이를 바탕으로
학습된 모델이 실패하기 전까지는 아무도 모르게 품질이 들쭉날쭉해지기 마련이에요. 반면 *평가용*
코퍼스는 수백 개의 쌍만 있으면 되고, 해당 언어를 아는 사람이 모든 문장을
검토하며, 결코 쓸모없어지지 않아요. 새로운 모델이나 방법론이 등장할 때마다
이를 기준으로 측정되니까요. 이 문서는 비용이 훨씬 적게 드는 이 두 번째
결과물, 즉 부서의 전문성이 모든 단일 문장에 닿을 수 있는 유일한 결과물을
구축하기 위한 워크플로우를 설명해요. 그리고 그 이후에 일어나는 일에 대해서도 다뤄요.
평가 기준이 마련되면, [게시된 상금](/docs/network/specifications/prizes)을 통해
여러분의 언어는 전 세계의 모든 방법론 개발자가 목표로 삼을 수 있는 대상이 되며,
공개 리더보드에서 모든 시도를 측정하게 돼요.

> **목적.** 언어학과 파트너십을 통해 기계 번역 평가용 코퍼스를 구축하기 위한 전체 워크플로우예요. 부서에서 제공하는 결과물, 코퍼스의 필수 형태, 암호화 봉인 방법, 샌드박스 평가 작동 방식, 그리고 부서가 그 대가로 얻는 것이 무엇인지 다뤄요. 잠재적인 학술 파트너와의 회의에 지참하기 좋은 문서예요.
>
> **대상 독자.** 활발한 언어 기록화 또는 NLP 프로그램을 운영하는 대학의 학과장, 책임 연구원(PI), 연구 코디네이터, 그리고 원주민 언어 프로그램 디렉터.
>
> **참고 문서:**
> - [코퍼스 설계 프레임워크](/docs/network/specifications/corpus-design) — 타당하고 신뢰할 수 있는 평가용 코퍼스를 구축하는 방법론
> - [상금 명세서](/docs/network/specifications/prizes) — 인센티브 부분: 봉인된 데이터 세트에 상금을 거는 방법
> - [코퍼스 등록](/docs/network/sovereignty/registering-corpora) — 데이터 통제권을 유지하면서 코퍼스를 네트워크에 합류시키는 방법
> - [화자 검증 프로토콜](/docs/network/specifications/speaker-validation) — 이중 언어 구사자에게 기존 번역을 *채점*하도록 요청하는 방법 (품질 평가, 린터 검증, FST 검토)
> - [벤치마크 명세서](/docs/network/specifications/benchmark) — 코퍼스, 실행 카드(run card), 평가 프로토콜에 대한 전체 기술 명세서
> - [데이터 주권](/docs/network/sovereignty/data-sovereignty) — 원주민 데이터 주권 원칙, CARE, 그리고 소유권 이전이 중요한 이유

## 1. 이 파트너십이 만들어내는 것

**봉인된 평가 코퍼스**: 기계 번역 품질을 측정하기 위한 정답(ground truth)이 되는 큐레이션된 병렬 텍스트 쌍(원본 언어 → 대상 언어)의 집합이에요. 방법론은 이 코퍼스에 대해 샌드박스에서 테스트되며, 개발자는 테스트 데이터를 절대 볼 수 없어요.

이 파트너십은 세 가지 산출물을 만들어내요:

| 산출물 | 무엇인가 | 누가 통제하는가 |
|----------|-----------|-----------------|
| **개발 코퍼스** | 방법론 개발을 위한 100~200개 이상의 공개 병렬 텍스트 쌍 | 공개 게시(CC BY-NC-SA 4.0 또는 이에 준하는 라이선스) |
| **골드 스탠더드 테스트 세트** | 공식 평가를 위한 50~150개의 비공개 병렬 텍스트 쌍 | 커뮤니티 거버넌스 조직(암호학적으로 봉인됨) |
| **진단 테스트 스위트** | 특정 언어 현상을 테스트하는 10~50개의 표적 대조 쌍 | 공개 게시 |

이를 모두 합치면 160~400개의 쌍이 돼요. 학습용 코퍼스에 필요한 수십만 개와
달리, 단일 연구 그룹이 실제로 전문가 수준으로 큐레이션할 수 있는 규모의
코퍼스죠. 개발용 코퍼스를 통해 누구나 번역 방법론을 구축할 수 있어요.
골드 스탠다드(gold-standard) 세트는 이러한 방법론이 정직하게 테스트되도록
보장해요. 진단 스위트는 특정 실패 유형(예: "이 시스템이 주변격(obviation)을
처리할 수 있는가?")을 잡아내요.

## 2. 학과가 해야 할 일

### 1단계: 코퍼스 설계 (2~4주, 연구자 시간)

**주도:** 대상 언어에 전문성을 가진 PI 또는 박사후연구원.

1. **원본 자료 도메인 선택.** 언어 커뮤니티가 실제로 번역이 필요한 4~6개의 실제 도메인을 선택해요. 우리의 분류 체계는 16개 도메인을 지원해요(벤치마크 명세 §2.7 참조):

   | 우선순위 | 도메인 | 이유 |
   |----------|--------|-----|
   | 🔴 높음 | `edu` — 교육 | 교과서, 커리큘럼 — 커뮤니티의 직접적 필요 |
   | 🔴 높음 | `gov` — 정부 | 밴드 의회 문서, 정책 — 실질적인 일상 필요 |
   | 🔴 높음 | `medical` — 보건 | 진료소 접수 양식, 건강 정보 — 안전 필수 |
   | 🟡 중간 | `conv` — 대화 | 일상 대화 — 기본 유창성 기준선 확립 |
   | 🟡 중간 | `legal` — 법률 | 권리 문서, 조약 — 커뮤니티 중요성 |
   | 🟢 낮음 | `literary` — 문학/문화 | 이야기, 구술 역사 — 문화 보존 |

2. **다음을 명시한 코퍼스 설계 문서를 작성해요:**
   - 세그먼트별 목표 크기(development, gold_standard, diagnostic)
   - 난이도 등급 분포(아래 §3.3 참조)
   - 레지스터 및 도메인 커버리지
   - 원본 문장 선택 기준(합성 텍스트 없음, 성경 전용 없음)
   - 화자 모집 계획

3. **설계안을 검토를 위해 우리에게 제출해요.** 우리는 코퍼스 스키마(벤치마크 명세 §2)에 대해 이를 검증하고 1주 이내에 피드백을 드려요.

### 2단계: 원본 문장 생성 (4~8주, 화자 시간)

**주도:** 이중 언어 화자와 함께 작업하는 연구 코디네이터.

1. **계획된 도메인과 난이도 등급에 걸쳐 원본 문장을 생성하거나 선택해요.** 출처는 다음이 될 수 있어요:
   - 기존에 출판된 이중 언어 자료(교과서, 정부 문서)
   - 특정 언어 현상을 다루도록 설계되어 새로 이끌어낸 문장
   - 실제 문서에서 각색한 것(밴드 의회 안건, 진료소 양식, 교육 자료)

2. **각 원본 문장은 다음을 갖춰야 해요:**
   - 도메인 태그(16코드 분류 체계에서)
   - 레지스터 태그(대화, 격식, 기술, 의례, 교육)
   - 문맥 태그(인사, 선언, 질문, 지시, 서사, 라벨, 오류)
   - 추정 난이도 등급(1~5, §3.3 참조)
   - 출처 태그(textbook, elicited, corpus, gold_standard)

3. **각 원본 문장을 대상 언어로 번역해요.** 이중 언어 화자가 수행해요. 항목당 여러 개의 참조 번역이 있으면 유용하지만 필수는 아니에요.

4. **선택적으로, 각 참조 번역에 형태론적 분석을 추가해요:**
   - 행간 주석(형태소별 분해)
   - FST 태그 문자열(해당 언어에 FST가 존재하는 경우)
   - 방언 변이형, 모호성, 문화적 맥락에 대한 번역자 노트

### 3단계: 품질 보증 (2~4주)

**주도:** 대상 언어 전문성을 가진 언어학자.

1. **교차 검토.** 각 번역은 원본 번역을 수행하지 않은 최소 한 명 이상의 이중 언어 화자에게 검토받아야 해요. 검토자는 다음을 확인해요:
   - 번역이 정확한가?
   - 자연스럽게 들리는가?
   - 난이도 등급이 올바른가?
   - 기록해야 할 허용 가능한 변이형이 있는가?

2. **우리의 스키마 검증기로 실행해요.** 우리는 코퍼스를 항목 스키마(벤치마크 명세 §2.2)에 대해 검증하는 스크립트를 제공해요. 이는 다음을 확인해요:
   - 필수 필드 존재 여부
   - 도메인 코드 유효성
   - 난이도 등급이 1~5의 정수인지
   - 중복 ID 없음
   - 문자 인코딩(UTF-8 NFC 정규화)

3. **해당 언어에 FST가 존재하면,** 참조 번역을 이를 통해 실행해요. 참조의 모든 단어는 FST 유효해야 해요. 그렇지 않은 단어(외래어, 신조어, 고유명사)는 허용 목록(allowlist)에 문서화해야 해요.

### 4단계: 세그먼트 분할 및 봉인 (1주, 우리 엔지니어링)

**주도:** Champollion 팀, 학과 검토 포함.

1. **층화 분할.** 우리는 결정론적 무작위 샘플링(시드 문서화, 재현 가능)을 사용하여 코퍼스를 세그먼트로 분할해요:

   | 세그먼트 | 목표 크기 | 접근 |
   |---------|------------|--------|
   | `development` | 항목의 60%(최소 100개) | 공개 |
   | `gold_standard` | 항목의 30%(최소 50개) | 비공개, 봉인 |
   | `held_out` | 항목의 10%(최소 10개) | 비공개, 봉인, 활성화 전까지 미사용 |

   이 분할은 난이도 등급 분포를 보존하므로(층화 샘플링) 각 세그먼트가 등급 전반에 걸쳐 비례적으로 대표돼요.

2. gold_standard 및 held_out 세그먼트의 **암호학적 봉인**:

   ```
   1. SHA-256 hash of each entry (source + reference + metadata)
   2. SHA-256 hash of the complete segment file
   3. Segment file encrypted with AES-256-GCM
   4. Encryption key split using Shamir Secret Sharing (2-of-3 threshold)
   5. Key shares distributed to:
        - Share 1: Community governance organization
        - Share 2: Academic department partner
        - Share 3: Champollion project (escrow)
   6. Hash manifest published to a public commit (proves the corpus existed
      at a specific time without revealing its contents)
   ```

3. **개발 세그먼트**는 공개 저장소에 커밋되어 전체 라이선스와 함께 게시돼요.

4. **진단 세그먼트** 역시 공개돼요 — 이는 특정 언어 현상을 테스트해요(§3.4 참조).

### 5단계: 통합 및 출시 (1~2주, 우리 엔지니어링)

1. **하니스 구성.** 우리는 해당 언어를 평가 하니스에 추가해요:
   - 언어 카드 생성 또는 검증
   - 데이터셋 레지스트리에 코퍼스 등록
   - LYSS 메트릭 구성(FST 사용 가능 시 LYSS-fst, 린터 규칙 존재 시 LYSS-eq)
   - 기본 스코어링 프로파일 선택(FST 사용 가능 시 Profile A, 그 외에는 Profile B)

2. **베이스라인 벤치마크.** 우리는 개발 세그먼트에 대해 12개 모델 스윕을 실행하여 리더보드에 초기 점수를 채워요.

3. **공개 발표.** 해당 언어는 실시간 개발 세그먼트 벤치마크와 함께 Network 리더보드에 나타나요. 학과는 코퍼스 파트너로 인정돼요.

## 3. 코퍼스가 어떤 형태여야 하는가

### 3.1 형식

모든 코퍼스 파일은 벤치마크 명세 §2.1~§2.2의 스키마를 따르는 JSON 문서예요:

```json
{
  "dataset": {
    "id": "crk-ualberta-v1",
    "version": "1.0",
    "language_pair": "EN→CRK",
    "source_language": "en",
    "target_language": "crk",
    "created": "2026-09-15",
    "license": "CC-BY-NC-SA-4.0",
    "provenance": ["textbook", "elicited", "gold_standard"]
  },
  "entries": [
    {
      "id": 1,
      "source": "I see the dog",
      "reference": "niwâpamâw atim",
      "segment": "development",
      "difficulty": 2,
      "provenance": "textbook",
      "register": "conversational",
      "context": "declaration",
      "domain": "edu",
      "morphological_analysis": "ni-wâpam-âw atim | 1sg-see.TA-3sg.DIR dog.AN",
      "notes": "Animate noun (atim); direct form because speaker is proximate"
    }
  ]
}
```

### 3.2 최소 크기 요건

| 세그먼트 | 최소 항목 수 | 권장 |
|---------|----------------|-------------|
| `development` | 100 | 200~300 |
| `gold_standard` | 50 | 100~150 |
| `diagnostic` | 10 | 30~50 |
| `held_out` | 10 | 20~30 |
| **합계** | **170** | **350~530** |

### 3.3 난이도 분포

코퍼스는 다섯 개 난이도 등급 전반에 걸친 항목을 포함하되, 2~4등급에 가중치를 두어야 해요:

| 등급 | 설명 | 목표 분포 |
|------|-------------|-------------------|
| 1 — 기본 어휘 | 단어, 흔한 인사, 숫자 | 10~15% |
| 2 — 단순 문장 | SVO, 현재 시제 | 25~30% |
| 3 — 중간 복잡도 | 과거/미래 시제, 소유격, 유정성 | 30~35% |
| 4 — 복잡한 형태론 | 근칭/원칭, 수동, 접속형 어순, 관계절 | 15~20% |
| 5 — 고급 | 다중 절, 격식 레지스터, 의례, 관용 표현 | 5~10% |

### 3.4 진단 테스트 스위트

진단 세그먼트는 **대조 쌍**을 사용하여 특정 언어 현상을 테스트해요: 하나는 올바른 번역, 다른 하나는 최소한으로 다른 잘못된 번역이에요. 시스템의 메트릭이 올바른 쪽에 더 높은 점수를 주면 테스트를 통과한 것이에요.

포합어(polysynthetic languages)의 경우, 진단 스위트는 다음을 표적으로 삼아야 해요:

| 현상 | 예시(Cree) | 무엇을 테스트하는가 |
|-----------|----------------|--------------|
| **유정성 일치** | atim(유정) 대 maskisin(무정) — 다른 동사 형태 | 시스템이 어떤 명사가 유정인지 아는가? |
| **근칭/원칭** | 근칭 대 원칭 3인칭 | 3인칭 위계를 추적하는가? |
| **역방향 표시** | 순방향 대 역방향 동사 형태 | 피동주가 행위주보다 상위인 경우를 처리하는가? |
| **접속형/독립형** | 주절 대 종속절 동사 어순 | 올바른 동사 패러다임을 사용하는가? |
| **포함/배제** | "우리(당신 포함)" 대 "우리(당신 제외)" | 1인칭 복수형을 구분하는가? |

다른 어족의 경우, 유능한 번역과 무능한 번역을 구분하는 가장 진단적인 3~5개 현상을 식별해요. 여기서 학과의 언어학 전문성이 필수적이에요 — 이것들은 전문가만이 작성할 줄 아는 테스트예요.

### 3.5 우리가 원하지 않는 것

| 안티패턴 | 이유 |
|-------------|-----|
| **성경 전용 텍스트** | 고어체 레지스터, 전례 어휘, 정형화된 구조. OMT-1600은 1,560개 언어를 이런 방식으로 평가했어요 — 우리는 의도적으로 이를 피해요. |

## 4. 암호학적 봉인 및 샌드박스 테스트 {#4-cryptographic-sealing-and-sandbox-testing}

### 4.1 왜 테스트 세트를 봉인하는가?

통상적인 ML 벤치마크는 테스트 세트를 공개해요. 일단 공개되면 프론티어 LLM이 결국 그것으로 학습하게 되며(의도적이든 웹 스크래핑을 통해서든), 점수를 신뢰할 수 없게 만들어요. 원주민 언어 데이터의 경우 추가적인 우려가 있어요: 공개된 언어 데이터는 커뮤니티 동의 없이 사용될 수 있어요.

봉인은 다음을 보장해요:
- **테스트 세트 무결성:** 방법론이 한 번도 본 적 없는 데이터에 과적합할 수 없어요
- **데이터 주권:** 커뮤니티가 자신의 데이터에 대해 누가 평가할지를 통제해요
- **영구적 신선도:** 테스트 세트가 결코 오염되지 않아요

### 4.2 샌드박스 테스트 작동 방식

```
Developer workflow:
  1. Developer builds a translation method using the PUBLIC development corpus
  2. Developer tests locally against the development segment (unlimited, self-serve)
  3. When ready, developer submits their complete method (code + config + coaching data)
  4. Governance org installs the method in the evaluation sandbox
  5. Sandbox runs the method against the SEALED gold-standard test set
  6. Only scores are returned to the developer
  7. Developer never sees the source sentences or reference translations

The sandbox:
  - Runs on governance-controlled infrastructure
  - Has selective network access (LLM APIs only, no exfiltration)
  - Produces a tamper-proof run card (SHA-256 hash of all inputs and outputs)
  - Logs all execution for audit purposes
  - Can be inspected by the governance org at any time
```

### 4.3 키 관리

봉인된 테스트 세트의 암호화 키는 2-of-3 임계값의 Shamir Secret Sharing을 사용하여 분할돼요:

| 지분 보유자 | 역할 | 취소 권한 |
|-------------|------|-----------------|
| **커뮤니티 거버넌스 조직** | 주 관리인 | 평가 접근을 단독으로 취소할 수 있음 |
| **학술 학과 파트너** | 공동 관리인 | 키 재구성에 참여할 수 있음 |
| **Champollion 프로젝트** | 에스크로 | 단독으로 데이터에 접근할 수 없음; 다른 당사자들이 불가용 상태가 되면 연속성을 보장함 |

3개 중 어느 2개 지분이든 키를 재구성해요. 이는 다음을 의미해요:
- 커뮤니티 + 학과는 Champollion 없이 데이터에 접근할 수 있어요
- 커뮤니티 + Champollion은 학과 없이 데이터에 접근할 수 있어요
- Champollion 단독으로는 데이터에 절대 접근할 수 없어요

### 4.4 해시 매니페스트

코퍼스가 봉인되면, **해시 매니페스트**가 공개 Git 커밋에 게시돼요:

```json
{
  "corpus_id": "crk-ualberta-v1",
  "seal_date": "2026-09-15T00:00:00Z",
  "segments": {
    "development": {
      "entry_count": 200,
      "sha256": "a3f7c...",
      "access": "public"
    },
    "gold_standard": {
      "entry_count": 100,
      "sha256": "b8d2e...",
      "access": "sealed",
      "key_scheme": "shamir-2-of-3"
    },
    "held_out": {
      "entry_count": 20,
      "sha256": "c9e4f...",
      "access": "sealed",
      "key_scheme": "shamir-2-of-3"
    },
    "diagnostic": {
      "entry_count": 30,
```

이는 다음을 증명해요:
- 코퍼스가 특정 날짜에 존재했음

- 봉인된 세그먼트에 대한 어떤 수정도 해시 체인을 깨뜨림
- 커뮤니티가 자신의 데이터가 변조되지 않았음을 검증할 수 있음

이 파트너십은 연구비 제안서를 위한 구체적인 산출물을 제공해요:

- "[언어] MT를 위한 오픈소스 평가 인프라" — 입증 가능한 산출물
- "원주민 언어 데이터를 위한 암호학적 데이터 주권" — 확립된 주권 프레임워크(원주민 데이터 주권 원칙/CARE, Kaitiakitanga, TK Labels)를 MT 평가에 적용; 게시 가능
- "실시간 리더보드를 갖춘 커뮤니티 거버넌스 벤치마크" — 지속적인 임팩트 지표
- "[언어]에 대한 OMT-1600 / Google Translate의 독립적 평가" — 시의적절하고 주목도 높음

### 5.4 커뮤니티 임팩트

- 언어 커뮤니티는 **독립적인 평가 역량**을 얻어요 — 어떤 MT 시스템(Google, Meta, 또는 커스텀)이든 자신의 언어에 실제로 작동하는지 평가할 수 있어요
- 커뮤니티는 암호화 키 보관을 통해 **테스트 데이터를 통제**해요
- 벤치마크를 통해 입증된 모든 방법론은 커뮤니티로 **소유권이 이전**되며(벤치마크 명세 §8.3 참조), 배포로 벌어들이는 모든 것을 커뮤니티가 갖게 돼요 — Champollion은 비영리이며 어떤 지분도 취하지 않아요

   - 이 문서
   - 코퍼스 스키마 및 검증 도구
   - 기존 Cree(CRK) 코퍼스의 예시
   - 코퍼스 설계 템플릿 초안

5. **작업 시작.** 우리는 매주 체크인해요. 학과는 언어학적 결정에 대해 완전한 자율성을 가지며, 우리가 모든 엔지니어링을 처리해요.

## 8. 자주 묻는 질문

### "우리는 이미 병렬 코퍼스가 있어요. 사용할 수 있나요?"

네 — 코퍼스가 명확한 출처를 갖고, 사람이 작성했으며, 라이선스가 평가에서의 사용을 허용하는 경우에요. 우리는 그것을 우리 스키마에 맞게 포맷하고, 누락된 메타데이터를 추가하고, 통합하는 것을 도와드려요. 기존 코퍼스는 타임라인을 극적으로 앞당길 수 있어요(2단계를 건너뛰거나 공백을 채우는 작업으로 축소).

### "우리 언어에는 FST가 없어요."

괜찮아요. LYSS-fst(형태론적 유효성)는 FST가 필요하지만, 하니스는 Profile B 가중치(chrF++, BLEU, COMET, 행동 메트릭)를 사용하여 FST 없이도 작동해요. 관련 언어에 GiellaLT FST가 존재하면, 우리가 그것을 각색할 수 있을지도 몰라요. 그렇지 않더라도, 코퍼스는 여전히 가치 있는 평가를 가능하게 해요 — 다만 형태론적 유효성 게이트가 없을 뿐이에요.

### "우리 화자는 비라틴 문자를 사용해요."

완전히 지원돼요. 코퍼스 스키마는 어떤 유니코드 문자든 처리해요. 우리는 Cree를 위한 SRO(Standard Roman Orthography)와 음절 문자를 위해 설계했지만, 동일한 인프라가 데바나가리, 아랍 문자, CJK, 에티오피아 문자, 또는 다른 어떤 문자 체계에도 작동해요.

### "방언 변이는 어떻게 하나요?"

태그를 달아요. 코퍼스 항목 스키마는 방언 정보를 위한 `notes` 필드를 포함해요. 여러 방언이 표현된 경우, 그것들을 문서화해요. 린터의 등가 클래스(LYSS-eq)는 방언 변이형을 등가로 받아들이도록 구성할 수 있어요. 진단 테스트 스위트는 방언별 대조를 포함할 수 있어요.

### "코퍼스는 누가 소유하나요?"

거버넌스 조직을 통해 언어 커뮤니티가 소유해요. 학과는 연구 파트너로 인정돼요. Champollion은 운영 연속성을 위해 에스크로 키 지분을 보유하지만 단독으로는 봉인된 데이터에 접근할 수 없어요. 개발 세그먼트는 커뮤니티가 지정한 Creative Commons 라이선스 하에 게시돼요.

### "중단하고 싶으면 어떻게 되나요?"

커뮤니티는 암호화 키 재구성을 거부함으로써 언제든지 평가 접근을 취소할 수 있어요. 봉인된 데이터는 절대 노출되지 않아요. 이미 게시된 개발 세그먼트는 해당 라이선스 하에 공개된 채로 남아요. 학과의 연구 산출물(출판물, 발표)은 무엇이든 학과의 것으로 유지돼요.

### "거버넌스 조직이 아직 존재하지 않으면 어떻게 되나요?"

우리는 거버넌스 조직 없이 1~3단계(코퍼스 설계, 생성, QA)를 시작할 수 있어요. 봉인(4단계)에는 키 관리인을 식별하는 것이 필요해요. 그 사이에, 학과가 Champollion 프로젝트와 함께 공동 관리인 역할을 할 수 있으며, 커뮤니티 거버넌스 조직이 설립되면 관리권이 그곳으로 이전된다는 양해 하에서요.

## 부록: 태깅 대 코퍼스 구축

이 문서는 **코퍼스 구축** — 평가 정답을 형성하는 병렬 텍스트 쌍을 만드는 것 — 을 다뤄요. 태깅(형태론적 주석, 행간 주석, FST 태그 문자열)은 코퍼스를 풍부하게 만드는 별도의 활동이지만 기본 평가에는 필요하지 않아요.

| 활동 | 필수 여부 | 무엇을 가능하게 하는가 |
|----------|-----------|-----------------|
| **코퍼스 구축**(이 문서) | ✅ 필수 | 기본 평가: chrF++, 정확 일치, COMET, 행동 메트릭 |
| **FST 커버리지 검사** | 🟡 선택 | LYSS-fst 형태론적 유효성 메트릭 **및** FST 유래 `morphological_accuracy`(표제어 일치 — 주석 불필요; 스코어링 명세 §2.2) |
| **형태론적 주석** | 🟡 선택 | 향후 `morphological_accuracy`의 *골드 검증* 업그레이드를 가능하게 함; FST 유래 버전(위)은 아무것도 필요하지 않음 |
| **린터 등가 규칙** | 🟡 선택 | LYSS-eq 등가 일치 메트릭 |
| **의미 검증기 규칙** | 🟡 선택 | LYSS-sem 의미 검증 메트릭 |
| **화자 품질 평가** | 별도 활동 | 메트릭 검증(참조: [화자 검증 프로토콜](/docs/network/specifications/speaker-validation)) |

태깅과 화자 검증은 별도 문서에서 다루며 코퍼스 구축과 병행하거나 그 이후에 진행할 수 있어요.
