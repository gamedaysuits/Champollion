# 평가 코퍼스 설계 프레임워크

FLORES+에서 프런티어 모델을 평가하여 85 chrF++ 점수를 받았을 때, "모델이 번역을 잘한다"는 것과 "모델이 이 특정 문장 쌍을 암기했다"는 것을 구별할 수 없어요. 이 프레임워크가 존재하는 이유는 바로 그 단 하나의 모호함 때문이에요. 평가 코퍼스는 그 점수가 주장하는 바를 정확히 의미할 때만 구축할 가치가 있으며, 이를 위해서는 새로운 문장 쌍, 추적된 출처, 계층화된 도메인, 단계별 난이도 등 의도적인 설계가 필요해요. 이 페이지는 Champollion 평가 데이터셋이 어떻게 설계, 구축 및 유지 관리되는지에 대한 기준 문서예요.

> **버전:** 1.0 · **상태:** 초안 · 참고: [Corpus Partnership](/docs/network/specifications/corpus-partnership) 워크플로우는 연구 부서와 함께 이 방법론을 실무에 적용해요.

## 1. 설계 원칙

### 1.1 — 공개 벤치마크를 사용하지 않는 이유

공개 병렬 코퍼스(FLORES+, Tatoeba, WMT 테스트 세트, OPUS)는 개발과 디버깅에 사용할 수 있지만 **공식 리더보드 평가에서는 제외됩니다**. 이유는 간단합니다:

**오염.** 프런티어 LLM은 방대한 웹 스크래핑 데이터를 바탕으로 훈련돼요. 공개적으로 존재했던 모든 병렬 텍스트, 특히 큐레이션되고 널리 인용되는 벤치마크 데이터셋은 훈련 데이터에 포함되어 있을 가능성이 높아요. 이는 이론적인 우려가 아니에요. [연구에 따르면](https://arxiv.org/abs/2311.04850) 기계 번역(MT) 벤치마크에서 측정 가능한 오염 효과가 입증되었어요. (공개 벤치마크도 여전히 여기에서 실행되지만, 절대적인 품질 기준이 아니라 방법론 간의 순위를 매길 수 있는 *상대적 비교* 레인에서만 사용돼요.)

Champollion에게 이는 매우 중요한 문제예요. 그 이유는 다음과 같아요:
- 리더보드는 LLM 방법론, 기존 MT 서비스, 특수 목적 시스템을 나란히 비교해요.
- 우리의 가치 제안은 *정직하고 엄격한 평가*예요.
- 우리의 대상 사용자(언어 커뮤니티)는 이 점수를 바탕으로 배포 결정을 내려요.

### 1.2 — 핵심 요건

모든 Champollion 평가 코퍼스는 다음을 충족해야 합니다:

| 요건 | 근거 |
|-------------|-----------|
| **사람이 작성** | 합성 데이터 불가. 모든 원문과 참조 번역은 사람이 작성해야 합니다. LLM은 정렬과 형식 지정을 도울 수 있지만 콘텐츠를 생성해서는 안 됩니다. |
| **병렬 형태로 공개되지 않음** | 원문은 공개되어 있을 수 있고, 참조 번역도 공개되어 있을 수 있지만, 그 특정한 *쌍*은 다운로드 가능한 병렬 코퍼스로 존재해서는 안 됩니다. |
| **출처 추적** | 모든 항목에는 출처가 문서화되어 있어야 합니다: 원본 문서, 번역자, 라이선스, 날짜. |
| **언어학적 정보 기반** | 커버리지는 무작위 샘플링이 아니라 유형론적 특징을 기반으로 결정되어야 합니다. |
| **도메인 계층화** | 항목은 정의된 텍스트 도메인을 아우르며 통제된 대표성을 가져야 합니다. |
| **난이도 등급화** | 항목은 구조적 복잡성에 따라 난이도 등급(1–5)이 부여되어야 합니다. |
| **버전 관리** | 코퍼스 버전은 콘텐츠 해시로 식별됩니다. 점수는 동일한 버전 내에서만 비교 가능합니다. |
| **커뮤니티 검토 가능** | 참조 번역은 언어 커뮤니티 구성원이 검토할 수 있어야 합니다. |

### 1.3 — 코퍼스 유형, 길이, 스타일 중립성

Champollion은 **번역 단위가 무엇인지에 대해 중립적인** 오픈 번역 평가 허브입니다. 코퍼스 항목은 임의 길이의 텍스트입니다 — 짧은 단일 문장, 여러 절로 이루어진 긴 문장, 단락, 또는 문서 전체일 수 있으며 — 플랫폼은 이 모두를 동일하게 평가합니다. **짧거나 쉬운 텍스트로 제한되지 않습니다.** 하니스는 길이 제한을 두지 않으며(긴 번역이 잘리는 것을 방지하기 위해 의도적으로 넉넉한 출력 토큰 여유를 설정합니다), 난이도 등급(§3)과 도메인(§2.1)은 어렵거나 긴 자료를 배제하는 게이트가 아니라 *구성 가능한 축*입니다.

이 허브는 다음 전반에 걸쳐 중립적이고 구성 가능합니다:

| 축 | 범위 |
|------|-------|
| **세분성** | 문장 · 장문 문장 · 단락 · 문서 (`sizeUnit: entries \| sentences \| segments \| documents`) |
| **길이 및 복잡성** | 짧음 → 김; 단순 → 매우 복잡함 (난이도 등급 1–5) |
| **스타일 및 격식** | 격식체, 비격식체, 기술적, 문학적, 대화체, 행정적 (도메인 분류 체계, §2.1) |
| **방법** | 모든 `TranslationMethod` — LLM, 신경망 NMT, 규칙 기반, 하이브리드, 사람 |
| **언어 및 쌍** | 모든 방향성 쌍; 고자원 편향이 내재되어 있지 않음 |

코퍼스는 자신의 유형, 세분성, 격식, 난이도를 카드에 선언하며, 하니스는 카드가 선언한 내용을 그대로 따릅니다. 기본 Tatoeba 출처 **개발** 코퍼스가 짧은 문장으로 구성된 것은 Tatoeba가 그렇기 때문입니다 — 이는 해당 원본 코퍼스의 속성이지 **플랫폼의 제한이 아닙니다**. 문서 수준 및 장문 평가 세트는 1급 시민(first-class)입니다; 동일한 방식으로 등록하세요(예를 들어, 매우 긴 항목의 경우 더 작은 요청 배치를 구성하세요).

## 2. 원문 선정

### 2.1 — 도메인 분류 체계

Champollion은 학술적 연습이 아니라 **실제 배포 맥락**을 위한 번역을 평가합니다. 모든 코퍼스 항목에는 **표준 16코드 도메인 분류 체계**의 도메인이 태그되며, 이는 구축 시점에 검증됩니다.

분류 체계는 단일 신뢰 출처인 [벤치마크 명세 §2.7](/docs/network/specifications/benchmark#27-domain)에서 한 번만 정의되며, 불일치를 방지하기 위해 여기에서는 다시 기술하지 않습니다. 코드는 다음과 같습니다: `conv`, `ecommerce`, `edu`, `financial`, `gov`, `legal`, `literary`, `marketing`, `medical`, `news`, `religious`, `scientific`, `subtitles`, `support`, `tech`, `ui`. 각 코드의 설명과 일반적인 사용 대상은 §2.7을 참조하세요. 해당 집합 외의 도메인 코드를 도입하지 마세요.

### 2.2 — 도메인 분포

표준 평가 코퍼스는 대상 커뮤니티에 가장 관련성이 높은 도메인 전반에 걸친 분포를 목표로 해야 합니다. 정확한 코드와 비율은 언어 쌍마다 다릅니다; 아래 표는 §2.1의 표준 코드를 사용한 하나의 *예시* 목표 분포입니다:

| 도메인 | 코드 | 목표 % | 근거 |
|--------|------|----------|-----------|
| 소프트웨어 UI | `ui` | 25% | champollion CLI 사용자의 주요 배포 맥락 |
| 정부 / 행정 | `gov` | 15% | 법적 의미가 있는 고위험 번역 |
| 교육 | `edu` | 15% | 언어 부흥의 핵심 사용 사례 |
| 문학 / 서사 | `literary` | 10% | 문화적 뉘앙스와 문학적 격식을 테스트 |
| 대화 | `conv` | 10% | 비격식 격식과 자연스러운 화법 패턴을 테스트 |
| 기술 | `tech` | 10% | 정확성과 용어 일관성을 테스트 |
| 의료 / 건강 | `medical` | 10% | 고위험, 도메인 특화 어휘를 테스트 |
| 뉴스 / 저널리즘 | `news` | 5% | 현대 어휘와 중립적 격식을 테스트 |

### 2.3 — 원문 선정 기준

새 코퍼스를 위한 원문을 선정할 때:

1. **라이선스 호환성.** 원문은 평가 코퍼스에서의 사용을 허용하는 라이선스 하에 있어야 합니다. CC BY, CC BY-SA 또는 퍼블릭 도메인을 선호하세요. 라이선스를 문서화하세요.

2. **최신성.** 지난 10년 이내에 발행된 텍스트를 선호하세요. 언어는 진화합니다 — 특히 기술, 거버넌스, 의료 관련 어휘가 그렇습니다.

3. **격식 다양성.** 각 도메인 내에서 서로 다른 격식 수준의 텍스트를 찾으세요. 정부 보도 자료(격식체)와 정부 소셜 미디어 게시물(비격식체)은 둘 다 `admin` 도메인이지만 격식이 다릅니다.

4. **문화적 관련성.** 원주민 및 소수 언어의 경우, 단지 병렬로 존재한다는 이유의 텍스트보다 커뮤니티에 중요한 텍스트 — 토지 관리 문서, 해당 언어로 된 교육 자료, 문화 보존 텍스트 — 를 우선하세요.

5. **기계 번역 원문 금지.** "병렬" 문서가 원본을 Google Translate에 돌린 후 후편집하여 만들어진 것이라면, 참조 번역으로 허용되지 않습니다. 참조는 독립적인 사람 번역이어야 합니다.

## 3. 난이도 등급 체계

### 3.1 — 등급 정의

모든 항목에는 *원문*의 구조적 복잡성을 기준으로 난이도 등급(1–5)이 부여되며, 이는 (방법에 따라 달라지는) 번역 난이도가 아닙니다.

| 등급 | 라벨 | 구조적 특성 |
|------|-------|---------------------------|
| 1 | **초급** | 단순 문장. 단일 절. 현재 시제. 일반 어휘. 관용구 없음. 내포 구조 없음. |
| 2 | **중급** | 복문(compound). 접속사로 연결된 두 개의 절. 과거/미래 시제. 일부 도메인 어휘. |
| 3 | **고급** | 복잡한 문장. 종속절, 관계절. 혼합 시제. 도메인 특화 용어. 수동태. |
| 4 | **전문가** | 다수의 내포절. 법률/기술 격식. 조건 구조. 추상 개념. 문화적 참조. |
| 5 | **극상** | 여러 도전 과제가 동시에 등장하는 밀도 높은 산문: 중첩된 종속절, 모호한 대명사 참조, 문화적 관용구, 혼합 격식, 희귀 어휘. |

### 3.2 — 언어학적 정보 기반 난이도 요인

구조적 복잡성을 넘어, 난이도는 원천 언어와 대상 언어 간 **유형론적 거리**에 의해 조절됩니다. 이 요인들은 WALS 유형론적 특징과 언어 카드의 분류 데이터에서 도출됩니다:

| 요인 | 낮은 난이도 | 높은 난이도 |
|--------|---------------|-----------------|
| **어순** | 동일한 기본 어순 (예: SVO→SVO) | 다른 기본 어순 (예: SVO→SOV) |
| **형태론적 유형** | 유사한 유형 (예: 분석어→분석어) | 다른 유형 (예: 분석어→포합어) |
| **문법적 성** | 동일한 체계 또는 성 없음 | 원천 언어에 성이 없고, 대상 언어에 복잡한 성 체계가 있음 |
| **경어/격식** | 격식 표지 없음 | 대상 언어에 복잡한 격식 체계가 있음 (예: 일본어, 한국어) |
| **문자** | 동일한 문자 | 다른 문자 (음역 필요) |
| **유정성(Animacy)** | 유정성 구분 없음 | 대상 언어에 유정성 기반 일치가 있음 (예: Cree) |
| **증거성(Evidentiality)** | 증거성 없음 | 대상 언어가 정보 출처를 문법적으로 표시함 |

### 3.3 — 등급 분포

표준 코퍼스는 대략 다음을 갖춰야 합니다:

| 등급 | 목표 % | 근거 |
|------|----------|-----------|
| 1 | 15% | 기준선 확립 — 나쁜 방법조차도 이를 처리할 수 있어야 함 |
| 2 | 25% | 실용 번역의 기본 |
| 3 | 30% | 방법 간 품질 차이가 드러나는 지점 |
| 4 | 20% | 좋은 방법과 훌륭한 방법을 구분 |
| 5 | 10% | 상한 테스트 — 이를 잘 처리할 수 있는 방법은 극소수 |

## 4. 참조 번역 품질

### 4.1 — 번역자 요건

참조 번역은 다음 조건을 갖춘 사람이 작성해야 합니다:

1. 대상 언어의 **유창한 화자** (L1 또는 그에 준하는 수준)
2. 원천 언어와 대상 언어 모두에 **문해력**이 있음
3. 해당 텍스트 도메인에 대한 **도메인 지식**이 있음 (건강 텍스트의 경우 의료 번역자 등)
4. **독립성** — 번역자는 번역 중 동일 텍스트에 대한 어떠한 MT 출력에도 접근할 수 없어야 함

### 4.2 — 번역 브리프

모든 번역자는 다음을 포함하는 브리프를 받습니다:

- 사용할 **격식** (격식체, 대화체 등)
- **대상 독자** (일반 대중, 전문가, 어린이 등)
- 언어 커뮤니티에 특화된 모든 **용어 규칙**
- 명시적 지침: "단어가 아닌 의미를 번역하세요. 직역보다 자연스럽게 들리는 번역이 더 가치 있습니다."

### 4.3 — 품질 보증

1. **이중 번역.** 이상적으로는 각 항목에 서로 다른 번역자가 작성한 두 개의 독립적인 참조 번역이 있어야 합니다. 이것이 실현 불가능한 경우, 등급 4–5에 대해 이중 번역을 우선하세요.

2. **커뮤니티 검토.** 참조 번역은 해당 번역을 작성하지 않은 최소 한 명의 추가 화자가 검토해야 합니다.

3. **허용 가능한 변이형.** 각 참조에 대해 알려진 허용 가능한 변이형(어순, 정서법 규칙, 방언형)을 문서화하세요. 이는 `equivalent_match_rate` 지표에 반영됩니다.

### 4.4 — 나쁜 참조의 조건

| 문제 | 평가를 무효화하는 이유 |
|---------|------------------------------|
| 기계 번역 후 후편집 | 후편집은 MT 구조를 유지하므로, 더 자연스러운 번역을 산출하는 방법에 불이익을 줌 |
| 유창한 화자가 아닌 학습자가 번역 | 참조에 오류가 포함되어 올바른 MT 출력에 불이익을 줄 수 있음 |
| 지나치게 직역적 | 자연스러운 번역이 직역적 참조에 대해 낮은 점수를 받음 |
| 모호한 원문에 대한 단일 유효 해석 | 유효한 대안 해석에 불이익을 줌 |

## 5. 오염 방지

### 5.1 — 오염 위협 모델

| 위협 | 설명 | 완화책 |
|--------|-------------|------------|
| **학습 데이터 중복** | LLM이 병렬 코퍼스로 학습됨 | 병렬 코퍼스를 공개적으로 게시하지 않음 |
| **퓨샷 누출** | 방법 작성자가 평가 항목을 퓨샷 예제로 사용함 | 지문 확인: 프롬프트에 포함된 항목이 감지되어 플래그됨 |
| **간접 오염** | 원문이 LLM 학습 데이터에 존재함 (단일 언어) | 허용됨 — 단일 언어 원문은 예상되는 일임. 그 *쌍*은 새로운 것이어야 함. |
| **크라우드 오염** | 커뮤니티 검토자가 항목을 공개적으로 공유함 | 라이선스 조건이 병렬 코퍼스의 재배포를 금지함 |

### 5.2 — 코퍼스 비밀 등급

| 등급 | 가시성 | 용도 |
|------|-----------|-----|
| **공개 개발 세트** | 완전 공개 | 방법 개발, 디버깅, 회귀 테스트. 점수는 리더보드에 게시되지 않음. |
| **홀드아웃 평가 세트** | 원문은 가시적, 참조는 비밀 | 공식 리더보드 평가. 방법은 원문을 받고 번역을 반환하며, 채점은 서버 측에서 이루어짐. 참조는 절대 방법에 노출되지 않음. |
| **골드 스탠더드 세트** | 완전 비밀, 커뮤니티 통제 | 커뮤니티 검증 평가. 거버넌스 조직이 관리함. "커뮤니티 검증(Community Validated)" 인증 등급에 사용됨. |

### 5.3 — 순환 정책

평가 코퍼스는 주기적으로 **순환**되어야 합니다:

1. 코퍼스가 12개월 동안 사용된 후, 대체 코퍼스 구축을 시작
2. 기존 코퍼스를 "개발 세트" 상태로 은퇴(공개)
3. 새 코퍼스를 "홀드아웃 평가 세트"로 승격
4. 이는 고정된 대상에 대한 반복적 최적화를 통한 점진적 오염을 방지함

## 6. 코퍼스 구축 워크플로

### 6.1 — 단계별 프로세스

```
Step 1: Language Pair Selection
    └─ Identify target language, read language card
    └─ Review typological features (WALS), contact influences, scripts
    └─ Identify which difficulty factors apply

Step 2: Source Text Curation
    └─ Identify candidate source documents per domain
    └─ Verify licenses
    └─ Extract candidate sentences/segments
    └─ Classify by domain and preliminary difficulty tier

Step 3: Segment Selection
    └─ Sample segments to match domain distribution (§2.2)
    └─ Sample segments to match difficulty distribution (§3.3)
    └─ Ensure linguistic phenomenon coverage (§6.2)
    └─ Target minimum corpus size (§6.3)

Step 4: Reference Translation
    └─ Assign segments to qualified translators
    └─ Provide translation brief
    └─ Collect translations
    └─ Dual-translate Tier 4–5 entries

Step 5: Quality Assurance
    └─ Community review of references
    └─ Document acceptable variants
    └─ Flag and resolve disagreements

Step 6: Metadata & Packaging
    └─ Assign final difficulty tiers
    └─ Add provenance metadata per entry
    └─ Content-hash the corpus for versioning
    └─ Package as corpus JSON per harness spec

Step 7: Registration
    └─ Register in Supabase datasets table
    └─ Add to ATTRIBUTION.md if new sources used
    └─ Document in arena website
```

### 6.2 — 언어 현상 커버리지

모든 코퍼스는 언어 쌍과 관련된 특정 언어 현상을 테스트하는 항목을 포함해야 합니다. 이는 언어 카드의 `linguisticChallenges` 및 `contactInfluences` 필드에서 도출됩니다:

**보편적 현상 (모든 언어 쌍):**
- 대명사 해소 (모호한 선행사)
- 부정 (단일, 이중, 범위)
- 양화사 (모두, 일부, 없음, 대부분)
- 시간 표현 (상대적 날짜, 기간)
- 고유명사 (인물, 장소, 조직)
- 숫자와 측정값
- 목록과 열거

**쌍 특화 현상 (언어 카드에서):**
- 포합어 대상: 복잡한 동사 형태론, 포합(incorporation)
- 성을 가진 대상: 성 일치, 중립/포괄 참조
- SOV 대상: 절말 동사, 후치사
- 성조 언어: 성조 의존적 의미 구분
- 경어 언어: 격식 표지, 사회적 맥락
- 접촉 언어: 코드 스위칭 경계, 차용어 통합

### 6.3 — 최소 코퍼스 크기

통계적 신뢰성을 위해서는 최소 항목 수가 필요합니다. 이는 짝지은 부트스트랩 신뢰 구간 요건(`significance.py`)을 기반으로 합니다:

| 목적 | 최소 항목 수 | 권장 |
|---------|-----------------|-------------|
| 개발 세트 | 50 | 100–200 |
| 홀드아웃 평가 세트 | 100 | 200–500 |
| 골드 스탠더드 세트 | 200 | 500+ |
| 도메인당 최소 | 10 | 25+ |
| 등급당 최소 | 10 | 20+ |

**평가에 최소 100개가 필요한 이유는?** 약 100개 미만의 항목으로는 짝지은 부트스트랩 유의성 검정(1,000회 재표본)이 약 5 chrF++ 점 미만의 차이를 신뢰성 있게 감지할 수 없습니다. 200개 이상의 항목으로는 p<0.05에서 약 2점 차이를 감지할 수 있습니다.

## 8. 부정행위 방지 조치

### 8.1 — 코퍼스 무결성

| 조치 | 구현 |
|---------|----------------|
| **콘텐츠 해싱** | 코퍼스 버전 = 정렬된 항목 ID + 참조의 SHA-256. 어떤 수정이든 새 버전을 생성함. |
| **항목 지문화** | 각 항목은 콘텐츠에서 도출된 ID를 가짐. 누군가 수정된 코퍼스에 대해 결과를 제출하면, 지문이 일치하지 않음. |
| **홀드아웃 강제** | 공식 평가의 경우, 방법은 원문만 받음. 참조는 절대 노출되지 않음. 채점은 서버 측에서 이루어짐. |
| **순환 일정** | 코퍼스는 고정된 대상에 대한 장기 최적화를 방지하기 위해 매년 순환함. |

### 8.2 — 제출 무결성

| 조치 | 구현 |
|---------|----------------|
| **결정적 지문** | 실행 구성(모델, 온도, 프롬프트, 코퍼스 버전)이 해시됨. 동일한 구성은 동일한 지문을 생성함. |
| **선별 제출(cherry-pick) 감지** | 제출자는 최선의 결과만이 아니라 모든 실행을 공개해야 함. 동일한 지문을 가진 다수의 제출은 플래그됨. |
| **오염 확인** | 평가 항목이 방법의 프롬프트나 코칭 데이터에 그대로 나타나면, 제출이 자격 박탈됨. |

## 10. 언어 카드 통합

코퍼스 프레임워크는 언어 카드 시스템과 통합됩니다:

1. **도메인 선정**은 카드의 `linguisticChallenges`에 의해 결정됩니다 — 언어에 고유한 도전 과제(포합성, 성조, 유정성)가 있는 경우, 코퍼스는 이를 테스트하는 항목을 포함해야 합니다.

2. **난이도 보정**은 카드의 `classification`를 사용합니다 — 원천과 대상 어족 간의 유형론적 거리가 무엇이 "어려운지"를 결정합니다.

3. **격식 커버리지**는 카드의 `registers`를 사용합니다 — 언어에 정의된 격식(formal-filipino, taglish-professional, taglish-casual)이 있는 경우, 코퍼스는 각 격식 수준의 항목을 포함해야 합니다.

4. **접촉 영향 테스트**는 카드의 `contactInfluences`를 사용합니다 — 차용층이 두꺼운 언어(Filipino: 스페인어 + 영어 + 아랍어)의 경우, 방법이 차용어를 올바르게 처리하는지 아니면 과도하게 번역하는지를 테스트하는 항목을 포함하세요.

5. **문자 처리**는 카드의 `scripts[]`를 사용합니다 — 다중 문자 언어(Serbian: 키릴 문자 + 라틴 문자)의 경우, 올바른 문자 선택을 테스트하는 항목을 포함하세요.
