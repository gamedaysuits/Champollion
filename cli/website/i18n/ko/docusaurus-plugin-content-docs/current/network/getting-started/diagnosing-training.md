# 학습 실행 진단하기

모델 학습을 마쳤지만, 수치가 기대했던 것과 다를 수 있어요. 이 페이지는 **현재 나타나는 현상**에서 출발하여 유력한 원인과 이를 해결하는 forge 도구를 안내해요. 대부분의 작업은 자동화되어 있어요. `nmt-forge export`(및 점수만 산출하는 `nmt-forge evaluate`)는 발견된 문제와 조정 수단을 명시하는 **Diagnosis & Recommendations** 섹션을 추가해요. 이 가이드는 이를 쉬운 언어로 풀어쓴 버전이며, forge가 *경고*만 표시할 수 있는 몇 가지 사항(⚠ **주의 사항**으로 표시)도 함께 다뤄요.

에이전트에게 다음과 같이 지시하세요. *"`nmt-forge lint <battery-manifest.json> --json` 명령을 실행하고 가장 심각도가 높은 발견 사항을 조치해 줘."* 내보내기(export) 후의 배터리 매니페스트는 `export/evaluation/battery-hyps-battery.json`이에요. 그런 다음 리포트된 내용을 아래 섹션들과 대조해 보세요.

---

## "기본 모델의 점수가 낮아요"

기본 `cpu-tiny` 프리셋으로 학습을 진행했는데 테스트 점수가 5~30 chrF++ 사이에 머무르는 경우예요.

**원인:** 이 프리셋의 원래 동작 특성이 그래요. 사용자가 제공한 쌍(pair) 데이터만으로 처음부터(from scratch) 학습되는 소형 트랜스포머이므로, 1~2천 개 정도의 쌍으로는 언어 전반이 아니라 해당 데이터의 구문과 문장 패턴만을 학습해요. 점수 범위의 상단은 데이터가 고도로 템플릿화되어 있을 때만 나타나요. 이 프리셋의 역할은 배포용 모델이 되는 것이 아니라, 전체 파이프라인(격리된 dev, 감사된 데이터, 사전 등록된 test, CLI가 호출할 수 있는 모델)을 실질적으로 검증하는 것이에요.

**해결 방법:** 한 번에 한 가지씩 변경하고 dev 세트에서 측정해 보세요. 효과가 큰 순서대로 정리하면 다음과 같아요.

1. **실제 데이터 쌍 늘리기.** 이 규모에서는 데이터가 그 어떤 설정보다 중요해요.
2. **사전 학습된 모델로 시작하기.** `nmt-forge init <code> --model cpu-finetune --base <hf-id>` 명령은 사전 학습된 소형 Marian/opus-mt 모델을 CPU에서 파인튜닝해요. *관련* 언어 쌍에 해당하는 모델을 선택하고, 무조건 성능이 더 좋을 것이라 가정하기보다 dev 세트에서 `cpu-tiny`와 비교해 보세요. `--model nllb-600m`는 가장 강력한 시작점이지만 GPU가 필요해요.
3. **보유한 데이터에서 더 많은 데이터 확보하기** — 단일 언어 텍스트의 역번역(backtranslation), 또는 분석기(analyzer)가 있는 언어라면 검증된 합성 데이터 생성하기([직접 모델을 훈련하고 싶으신가요?](/docs/network/tutorials/train-your-own-model) 참고).

⚠ **주의 사항:** `cpu-tiny`에서 나온 높은 점수는 기뻐하기 전에 먼저 의심해 보아야 해요. ["점수가 너무 좋아 보이는 경우"](#the-score-looks-too-good)를 참고하세요.

## "교과서 예문에서는 훌륭한데, 실제 문장에서는 형편없어요"

**저자원 환경에서 가장 흔한 함정이에요.** 합성/템플릿 데이터에서는
점수가 아름답게 나오는데, 실제 텍스트에서는 무너져요.

**무슨 일이 일어나고 있는가:** **전이 정체(transfer plateau)** 현상이에요. 학습 중에
실제 dev set의 손실은 일찍 바닥을 찍은 다음 다시 올라간 반면, 학습 손실은 계속
떨어졌어요 — 모델이 번역을 배우는 게 아니라 합성 데이터의 *덩어리*를 숙달하고 있었던
거예요. 합성 데이터를 더 넣어도 도움이 **되지 않아요**.

**forge 발견 사항:** `R7-transfer-plateau` (실행 매니페스트의 스케줄 스토리에서). **레버: REAL-DATA.**

**해결법:** 실제 텍스트를 추가하세요. 단일 언어 대상 데이터를 역번역하거나
(`nmt_forge.training.backtranslation`), 실제 병렬 문장을 확보하세요.
합성 데이터의 양은 레버가 아니에요 — *실제* 데이터의 다양성이 레버예요.

⚠ **이 점을 주의하세요:** 작은 실제 dev set에 대비해 혼합 비율이 약 99% 합성 데이터라면,
점수에서 확인하기 *전에* 이미 이 위험에 처해 있는 거예요. 병적인 비율에 대한
사전 점검 린트는 아직 없으니, 혼합 매니페스트의 gold/합성 데이터 개수를
확인하세요.

## "한 어체가 다른 것들보다 훨씬 나빠요"

어체별 표를 보세요. 특정 어체(예: 행정 또는 법률)가 나머지보다 훨씬 아래에
있어요.

**서로 다른 두 가지 원인이 있는데 — 진단은 *커버리지*와 출력이 *미완성*인지를 살펴
이 둘을 구분해요:**

- **모델이 단어를 모르는 경우** (`R1-vocabulary-gap`: 낮은 커버리지 **그리고** 높은
  미완성 비율). **레버: VOCABULARY.** 어휘집을 늘리고(사전 / 용례
  수집), 그런 다음 `nmt-forge` 퍼널 회계를 실행해서 새 항목들이
  실제로 코퍼스에 도달하는지 확인하세요 — 한 글자짜리 표기법 불일치가
  이전에 수천 개의 단어를 소리 없이 삭제한 적이 있어요.
- **모델이 단어는 알지만 문장 형태를 모르는 경우** (`R2-structure-gap`:
  커버리지는 괜찮은데, 여전히 미완성). **레버: STRUCTURE.** 커버리지 맵을
  문법 체크리스트와 대조해 실행하고 누락된 구문을 추가하세요
  (명령문, 의문사 의문문, 소유, 역태 — 여러분의 템플릿이 한 번도
  요청하지 않은 무엇이든).

## "출력이 한 문장 안에서 표기법을 섞어요"

모델이 같은 소리를 두 가지 방식으로 쓰는데, 때로는 한 문장 안에서 그래요.

**무슨 일이 일어나고 있는가:** 학습 대상 데이터가 모델에게 표기 관례가
서로 바꿔 쓸 수 있는 것이라고 가르친 거예요 — 코퍼스에 동일한 내용이
여러 표기법으로 담겨 있었던 거죠.

**forge 발견 사항:** `R3-mixed-convention`. **레버: ORTHOGRAPHY.**

**해결법:** 코퍼스를 `convention-lint`하고, 데이터 경계에서 **하나의**
정규 관례로 정규화한 다음 다시 학습하세요. 배터리에 혼합 관례 비율을 유지해서
그것이 떨어지는 걸 확인할 수 있도록 하세요.

## "모델 B가 모델 A를 이기긴 하는데 — 아주 조금 앞서요"

두 모델을 비교했더니 하나가 소수점 몇 자리 차이로 앞서 있어요.

**무슨 일이 일어나고 있는가:** 그 차이가 노이즈보다 작을 수 있어요. 80개
문장에서 0.4 chrF++ 격차는 동전 던지기예요.

**forge 발견 사항:** `R5-low-power` (신뢰 구간이 델타보다
넓어요). **레버: MEASUREMENT.**

**해결법:** CI보다 작은 델타에는 조치하지 마세요. 해당 어체의 eval set을
늘리거나, 두 개의 겹치는 구간 대신 *짝지은* 유의성 검정을 보고하는
`nmt-forge compare`을 사용하세요. forge는 결코 벌거벗은 점수를 렌더링하지 않아요 —
구간이 항상 함께 있는 건 바로 여러분이 이 점을 볼 수 있도록 하기 위해서예요.

⚠ **이 점을 주의하세요:** **단일 시드**에서 나온 결과는 시드 간 분산 대역을
포함하지 않아요. 재시딩에서 살아남지 못하는 이득은 실제가 아니에요.
결정이 중요하다면 2~3개의 시드로 다시 실행하세요.

## "점수가 너무 좋아 보여요"

의심스러울 정도로 높다면, 특히 초기이거나 데이터가 적을 때 그렇다면요. 그 의심을 믿으세요.

**다음 순서로 확인하세요:**

1. **데이터 누출(Leakage).** `nmt-forge leak-audit <corpus>` — 테스트 문장이 학습 데이터에 포함되었나요? 이 명령은 테스트 프롬프트와 동일한 프롬프트를 가진 행(번역이 다르더라도), 테스트 정답과 동일한 정답을 가진 행, 그리고 테스트 정답을 포함하거나 그 일부이거나 90% 이상 일치하는 행을 제거해요. `nmt-forge run`는 등록된 테스트 세트나 봉인된(sealed) 세트로 누출되는 학습 행을 거부하므로, 이 문제는 주로 forge 외부의 데이터나 파이프라인, 또는 등록하지 않은 테스트 세트에서 발생해요.
2. **체크포인트 선택.** 체크포인트가 테스트 세트가 아닌 **격리된 dev 세트**를 기준으로 선택되었나요? forge는 정확히 이러한 상황을 방지하기 위해 dev 세트 없이는 학습을 거부하지만, 직접 구축한 파이프라인은 그렇지 않을 수 있어요.
3. **유사 쌍(Near-twins)으로 인한 낙관적 평가.** `R4-optimism-bound`: "전체(full)" 배터리 점수가 "엄격(strict)" 점수보다 몇 점 더 높다면, 그 격차는 반복 훈련 유사 쌍(drill-sibling)으로 인한 낙관적 왜곡이에요. `leak-audit`는 템플릿 유사 쌍(학습 데이터의 *"I see the dog"*, 테스트 세트의 *"I see the cat"*)을 의도적으로 *유지*하며 유사 쌍이 있는 테스트 행 목록을 보여줘요. `eval.near_dupe_corpus`를 학습 파일로 설정하면(초기 구성이 이렇게 설정됨) 리포트에서 유사 쌍이 *없는* 테스트 행만 따로 채점하여 "(strict)"로 표시해요. 일반화 성능을 주장할 때는 **반드시 strict 수치를 인용하세요**. *모든* 테스트 행에 유사 쌍이 있어(`R4-recall-not-translation`: strict 하위 집합이 비어 있으므로, 점수가 학습 문구의 암기율을 측정하게 됨) 테스트 세트가 고정되어 있다면, `nmt-forge leak-audit <train> --clean-to <train>.notwins.jsonl --drop-test-twins` 명령으로 유사 쌍이 제거된 말뭉치를 별도 파일로 작성하고 이를 사용해 유사 쌍 없는 두 번째 모델을 학습시키세요(leak-audit는 첫 번째 모델이 학습 중인 파일을 덮어쓰지 않아요). 아니면 학습 템플릿과 독립적으로 작성된 테스트 문장을 확보하세요.
4. **출력이 입력을 따르지 않음.** `R9-harness-score-caveat`: mt-eval 리포트에서 점수에 단서 조건(qualified)이 붙었다고 표시돼요. 가장 흔한 경우는 **거의 일정한 출력(near-constant output)**이에요. 서로 다른 수많은 테스트 문장에 대해 동일한 몇 개의 출력만 나오는 현상입니다(어느 병원 모델은 150개의 서로 다른 문장에 대해 9개의 출력만 생성했지만, 자주 쓰이는 문구가 여러 참조 문장과 많은 문자를 공유했기 때문에 chrF++ 48점을 기록했어요). 유사 쌍을 제거한 모델에서 이런 현상이 자주 발생해요. 학습 템플릿이 제거되면 소형 모델은 가장 빈번하게 등장하는 문장으로 후퇴(fallback)할 수 있거든요. forge는 하네스의 표현 그대로 주의 사항을 전달하며(내보내기 요약에서 `DEPLOY.md`, `status`, `report`, `compare`, `lint`), 이러한 단서 없이 해당 점수를 "인용할 수 있는 수치"로 표시하지 않아요. 점수를 번역 품질로 보고하기 전에 테스트 세트가 있는 머신에서 출력 결과 몇 개를 직접 확인해 보세요(`<export>/evaluation/battery-hyps.jsonl`). 해결 방법은 더 다양하고 실제적인 학습 쌍을 확보하는 것이에요.

## "학습이 거의 즉시 멈췄어요"

실행이 몇백 스텝 만에 끝났고, 모델이 데이터를 거의 보지 못했어요.

**무슨 일이 일어나고 있는가:** 조기 종료가 합성 데이터가 많은 dev의 예상된
흔들림을 수렴으로 오인한 거예요.

**forge 동작 방식:** 이 문제는 기본적으로 *방지*되어 있어요. `nmt-forge run`는 데이터 구성(mix)에서 조기 종료 **최저 기준선(floor)**을 도출하여 그 이하에서의 조기 종료를 억제하고, 그 이유를 `[schedule-sanity]` 라인에 기록해요. dev 세트의 평가 빈도 역시 실행 규모에 따라 도출되므로, 작은 규모의 실행이라도 평가 없이 끝나지 않아요. 예상치 못한 조기 종료가 발생했다면 해당 라인을 읽어 보세요. 실행 매니페스트에 어떤 일이 왜 일어났는지 정확히 기록되어 있어요. (마지막 계획된 스텝에 단순히 도달한 실행은 조기 종료가 아니라 완료로 보고돼요.)

## "학습이 본격적으로 시작되기도 전에 거부되었어요"

**원인:** 게이트(검사 조건)가 작동했어요. 몇 시간 동안 학습하다 실패하는 것보다 훨씬 비용이 적게 들죠. 흔히 발생하는 원인은 다음과 같아요.

- **학습용 추가 패키지(training extra)가 누락됨** — `nmt-forge preflight run --config config.json` shows `✗ backend-installed` 메시지와 함께 해결 방법(`python3 -m pip install 'nmt-forge[hf]'`)이 표시돼요.
- **dev 세트가 없거나 잘못됨** — dev 격리(dev-fence) 기능이 `data.dev`가 `dev` 역할을 가진 등록된 세트가 아닐 경우 실행을 거부해요. `nmt-forge split … --register project`로 분할해 생성하세요.
- **데이터 누출(Leakage)** — 학습 파일이 등록된 테스트 세트나 봉인된 세트와 프롬프트 또는 정답을 공유하고 있어요. `nmt-forge leak-audit <file> --clean-to <file.clean.jsonl>`로 정제하고 설정이 정제된 파일을 가리키도록 지정하세요.
- **소요 시간(Wall-clock)** — forge는 시작 후 몇 분 동안 학습 속도를 측정하여 `model.time_budget_hours`를 초과할 것으로 예상되는 실행을 거부해요. CPU 환경이라면 보통 프리셋에 GPU가 필요하거나(`nllb-600m`), 데이터 구성이 의도했던 것보다 훨씬 크다는 의미예요. 메시지에는 조정할 수 있는 방법(데이터 규모 줄이기, 시퀀스 길이 단축, 대기 시간을 감수할 경우 예산 시간 늘리기)이 안내돼요.

**해결 방법:** 매 학습을 실행하기 전에 `nmt-forge preflight run --config config.json`를 실행하세요. 모든 게이트의 상태를 ✓/✗로 표시하며, 각 ✗에 대한 해결 방법도 함께 보여줘요.

## "원했던 지표가 그냥… 보고서에서 빠져 있어요"

보고서는 정직하지만 한 축(COMET, FST 유효성 검사)에서 비어 있어요.

**forge 발견 사항:** `R6-referee-unavailable` — 해당 레인이 사용 불가로 명명되고
그 이유가 함께 표시돼요. **레버: REFEREE.**

**해결 방법:** 안내된 판정기(referee)를 설치하거나 구성한 뒤 다시 채점하세요. 언어 카드(language card)에 판정기가 선언되어 있다면, forge 메시지에 설치 명령(`mt-eval setup --lang <code>`)이 표시돼요. 현재 점수가 거짓인 것은 아니에요. 다만 판정기가 준비되기 전까지는 해당 축에 대한 평가가 빠져 있을 뿐이에요.

## "모델이 `<unk>` 또는 깨진 문자를 내보내요"

특히 음절 문자나 확장 라틴 문자에서요.

**프리셋에 따라 달라져요.**

- **`cpu-tiny`**은 학습 행으로부터 자체 어휘집(vocabulary)을 학습하므로, 학습 데이터에 등장한 모든 문자가 포함돼요. 여기서 `<unk>`가 나타난다면 입력에 학습 데이터에 한 번도 나오지 않은 문자(희귀한 글자나 발음 구별 부호(diacritic), 또는 다른 유니코드 형식)가 포함되어 있다는 의미예요(텍스트는 NFC로 정규화되므로 완성형과 조합형 악센트는 동일하게 취급돼요). 학습 데이터와 테스트 데이터가 동일한 맞춤법/철자법(orthography)을 사용하는지 확인하세요.
- **`cpu-finetune` 및 `nllb-600m`**은 사전 학습된 기본 모델의 토크나이저를 사용해요.

⚠ **주의 사항 — 아직 자동화되지 않음 (사전 학습된 베이스).** 기본 모델의 **토크나이저가 대상 언어의 문자 체계(script)를 제대로 표현하지 못할 수 있어요**. forge는 아직 학습 전에 토크나이저 커버리지를 자동으로 검사하지 않아요. 대상 언어의 문자 체계 샘플을 바탕으로 기본 모델의 토크나이저를 확인해 보세요. 해당 문자 체계를 어휘집에 포함하고 있는 기본 모델(많은 저자원 언어가 NLLB 제품군 베이스에서 지원됨)을 선택하거나, 학습 전에 토크나이저를 확장하세요.

## forge가 거부했는데 이유를 모를 때

거부는 항상 **무엇이** 일어났는지, **왜** 그것이 결과를 오염시키는지, 그리고
**해결법**을 명시해요. 그래도 여전히 불분명하다면:

- `nmt-forge status` — 현재 위치와 다음에 실행해야 할 단일 명령을 보여줘요.
- `nmt-forge preflight <command>` — 해당 명령이 거치게 될 모든 게이트를 ✓/✗로 표시하고 각 ✗에 대한 해결 방법을 제공하므로, 하나씩 해결하지 않고 한 번에 모두 처리할 수 있어요(`run`, `evaluate`, `export`의 경우 `--config config.json`를 추가하세요).
- 에이전트가 결과를 읽을 때는 어떤 명령에든 `--json`를 추가하세요. 그러면 거부 사유가 종료 코드 2와 함께 단일 JSON 객체(`{"error": {"type", "guard", "message", "why", "fix", …}}`)로 반환돼요.

거부는 여러분의 설정 오류가 아니에요 — 실수가 결과에 도달하기 전에 도구가
잡아내는 거예요. 그것이 바로 전체 설계 의도예요.
