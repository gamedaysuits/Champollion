# MT 평가

> **핵심 요약.** 이 페이지는 리더보드 제출 기준, 채점 지표(chrF++, FST 수용, 정확 일치, 동등 일치, 의미 점수), 부정행위 방지 정책, 검증 등급, 제출 워크플로를 정의해요. 평가 데이터에 노출된 방법은 실격 처리돼요.

champollion에는 번역 방법의 **재현 가능한 벤치마킹**을 위해 설계된 기계 번역 평가 프레임워크가 포함되어 있어요 — 특히 표준 MT 벤치마크가 존재하지 않고 품질 주장을 검증하기 어려운 저자원 및 원주민 언어를 위한 것이에요.

---

## 리더보드

핵심은 **[Method Leaderboard](https://champollion.dev/leaderboard)**입니다. 이는 실시간으로 운영되며 **제출이 열려 있는** 공개 점수판으로, 연구자와 커뮤니티 구성원이 핑거프린트가 적용되고 재현 가능한 평가를 통해 번역 메서드를 제출하고 비교하는 곳이에요.

모든 제출에는 다음이 포함돼요:

- **Fingerprinted pipeline** — 특정 Git 커밋 및 config 해시에 연결되어, 결과를 생성한 정확한 코드로 추적할 수 있어요.
- **Versioned dataset** — 콘텐츠 해시가 적용되고 버전이 관리됩니다. 점수는 동일한 데이터셋 버전 내에서만 비교할 수 있어요.
- **Standardised metrics** — 모든 점수 계산은 공유된 evaluation harness에 의해 수행되어 구현상의 차이를 제거해요.
- **Trust tiers** — self-benchmarked, Champollion Verified, 또는 Community Validated로 나뉩니다.
- **Cost tracking** — 제출당 API 비용을 추적하여 비용과 품질 간의 트레이드오프를 투명하게 보여줘요.

리더보드는 다섯 가지 지표를 채점해요. 세 가지는 모든 언어에서 작동하고, 두 가지는 Plains Cree에서 사용 가능하며 확장하면서 일반화될 예정이에요:

| 지표 | 유형 | 측정 대상 |
|--------|------|------------------|
| **chrF++** | 문자 n-gram F-점수 | 주요 품질 지표 — 특히 형태론적으로 풍부한 언어에서 인간의 판단과 잘 상관돼요 |
| **정확 일치** | 완벽 일치 비율 | 엄격한 정확도 — 번역이 골드 스탠다드와 정확히 얼마나 자주 일치하는가? |
| **FST 수용** | 형태론 게이트 통과율 | 유한 상태 변환기 검증이 있는 방법의 경우 — 출력 중 형태론적으로 유효한 비율은 얼마인가? |
| **동등 일치** | 허용 가능한 변형 비율 | 참조 또는 허용 가능한 변형(어순, 정서법 관례)과 일치하는 비율. 현재 CRK; 일반화 중. |
| **의미 점수** | 의미 충실도 | 의미 보존 — 표면 형태와 관계없이 번역이 의도된 의미를 담아내는가? 현재 CRK; 일반화 중. |

:::info[전체 메트릭 세트]
[Scoring Specification](/docs/network/specifications/scoring)에서 전체 메트릭 목록(surface, structural, semantic, behavioral, compliance, reported comparators의 여섯 개 범주), 종합 점수 공식, 가중치 표, 품질 등급 임계값을 정의해요.
:::

| **Language pair** | EN → CRK (Plains Cree, SRO orthography) |
| **Entry count** | 436개 항목의 dev split (`textbook_dev.json`). 전체 내역은 [Evaluation Datasets 페이지](/docs/network/leaderboard/datasets#edtekla-development-set-v1)에 한 번 명시되어 있어요. |
| **License** | [EdTeKLA's modified CC BY-NC-SA](https://github.com/EdTeKLA/IndigenousLanguages_Corpora) (`LicenseRef-EdTeKLA-Modified-CC-BY-NC-SA-4.0`, sovereignty-scoped) — 비상업적 용도. 리더보드, 상금 및 상업용/API 레인에서 제외됩니다. |
| **Provenance** | `gold_standard` (화자 검증 완료), `textbook` (출판된 교육 자료) |

### FLORES+ Devtest — 개발 용도 전용

> [!WARNING]
> **FLORES+는 개발 및 디버깅용으로 사용 가능하지만 공식 리더보드 평가에는 사용되지 않아요.** FLORES+(원래 Meta FLORES-200)는 최전선 LLM이 거의 확실히 학습했을 널리 공개된 벤치마크 데이터셋이에요. FLORES+에 대한 점수는 LLM 기반 방법의 실제 번역 품질을 신뢰성 있게 반영하지 못해요. 비-LLM 방법(FST, 규칙 기반, 미세 조정된 NMT)은 영향을 덜 받지만, FLORES+ 점수는 여전히 리더보드에 게시되지 않아요.

FLORES+ 픽스처는 파이프라인 스모크 테스트, 교차 언어 검증, 개발 용도로 `test/benchmark/fixtures/`에 계속 제공돼요. 공식 평가는 병렬 형태로 공개되지 않은 사람이 작성한 텍스트로 구축된 맞춤형 코퍼스를 사용해요.

전체 데이터셋 스키마, 난이도 등급, 직접 만드는 방법은 [평가 데이터셋](/docs/network/leaderboard/datasets)을 참고하세요.

:::danger[평가 데이터로 학습하지 마세요]

**이 데이터셋은 평가 전용이에요.** 평가 데이터로 학습, 미세 조정, few-shot 프롬프트, 또는 그 외 방식으로 노출된 방법은 인위적으로 부풀려진 점수를 만들며 **리더보드에서 실격 처리돼요.**

이것은 제안이 아니에요 — 평가 무결성의 가장 중요한 단일 규칙이에요. 학습에는 별도의 코퍼스를 사용하세요. 평가 세트는 개발 중 모델에 노출되지 않은 상태로 유지되어야 해요.

코칭 데이터나 few-shot 예제를 사용하는 경우, 그것들은 **완전히 별개의 출처**에서 나와야 해요. 확신이 없다면 포함하지 마세요.
:::

:::warning[LLM 비결정성]

LLM 출력은 비결정적이에요. 점수는 특정 모델 버전과 API 구성 하에서의 특정 시점 측정치를 나타내요. 모델 제공자는 언제든지 가중치, 디코딩 전략, 안전 필터를 업데이트할 수 있으며, 이는 실행 간 점수 편차를 유발할 수 있어요. 리더보드는 모든 제출에 대해 정확한 모델 slug와 타임스탬프를 기록해요.
:::

## 좋은 방법을 만드는 요소

모든 방법이 동등하게 만들어지는 것은 아니에요. 엄밀한 작업과 부풀려진 점수를 구분하는 것이 여기 있어요.

### 강력한 방법의 특성

- **학습 데이터와 평가 데이터의 명확한 분리** — 개발, 튜닝, 프롬프트 엔지니어링, few-shot 예제 선택 중에 방법이 평가 세트를 한 번도 본 적이 없어요
- **재현 가능** — 다른 사람이 저장소를 복제하고 하네스를 실행해 동일한 점수를 얻을 수 있어요 (LLM 비결정성 범위 내에서)
- **문서화** — [방법 카드](/docs/network/specifications/methods)가 방법이 무엇을 하고, 어떤 도구를 사용하며, 어떤 한계가 있는지 설명해요
- **범위에 대한 정직성** — 방법이 한 언어 쌍에만 작동한다면 그렇게 말하세요; 특정 형태론 패턴에서 성능이 저하된다면 그것을 문서화하세요
- **커뮤니티 인식** — 원주민 언어의 경우, 방법이 데이터 주권을 존중해요. 언어 커뮤니티와 상의했거나 공개 라이선스 데이터만 사용했어요

### 위험 신호 (실격되는 것들)

| 위험 신호 | 왜 문제인가 |
|----------|--------------------|
| 평가 데이터로 학습 | 평가의 목적을 완전히 무너뜨려요. 부풀려진 점수는 모두를 오도해요. |
| 결과 체리피킹 | 10번 실행하고 나머지를 공개하지 않은 채 최고 실행만 제출 |
| 공개되지 않은 후처리 | 채점 전에 출력을 수동으로 수정 |
| 오염된 코칭 데이터 | 평가 세트 예제를 few-shot 프롬프트나 사전 항목으로 사용 |
| 출처 없이 상업적 준비 완료 주장 | 방법이 CC BY-NC-SA 데이터를 사용한다면 상업적으로 준비되지 않은 것이에요 |

### 검증 등급

검증 등급은 **누가 결과를 검증했는지**를 설명해요 — 자동 복합 점수가 무엇을 의미하는지를 설명하는 [채점 명세, §5](/docs/network/specifications/scoring#5-quality-tiers)에 정의된 품질 등급(Baseline → Fluent)과는 별개예요.

| Tier | Meaning | How to Get It |
|------|---------|--------------|
| **Self-benchmarked** | 직접 harness를 실행하고 결과를 제출했어요. | `mt-eval publish` 명령어로 run card를 게시하세요. |
| **Champollion Verified** | 서버가 sha-pinned reference corpus를 기준으로 제출된 출력물을 독립적으로 다시 채점하여 점수를 재현했어요. | 자동 — 모든 제출물은 다시 채점됩니다(아래 참조). |
| **Community Validated** | 커뮤니티 자체 프로토콜에 따라 자격을 갖춘 대상 언어의 이중 언어 화자가 출력물의 층화 표본(≥30개 항목, ≥2명의 리뷰어)을 검토했으며, ≥70%가 커뮤니티 기준을 충족했어요. 커뮤니티 자체 테스트를 통해서만 부여되며, spot-audit에 의한 강등도 대칭적으로 적용돼요. | 거버넌스 조직에 메서드 코드를 제출하세요. 조직에서 gold-standard 세트를 기준으로 코드를 실행하고 출력물을 커뮤니티 리뷰에 회부해요. |

### 검증 확장 방식: 평판 가중치 기반 감사(reputation-weighted auditing)

**우리는 출처(provenance)를 주장하지 않아요.** 리더보드의 행은 기여자가
*자신의* 머신에서 *오픈소스* harness를 실행하여 생성됩니다. "이 실행이 정말로
harness를 통해 이루어졌다"는 것은 self-hosted 컴퓨팅 환경에서 서버가 검증할 수
있는 것이 아니에요. harness의 서명 키는 기여자의 손에 있으므로, 서명은 *정직성이
아닌 머신*을 인증할 뿐입니다. 그렇지 않은 척하는 대신, **여기서 유효성은 획득되고
스스로 교정됩니다**. 행이 신뢰할 수 있는 이유는 점수가 **재현 가능**하기 때문이며,
그 이면의 기여자가 **조작이 발각될 경우 파괴될 평판을 걸었기 때문**이에요. 검증은
4개의 계층으로 실행되므로, 철저해야 할 곳에서는 철저하고 저렴할 수 있는 곳에서는
저렴하게 진행돼요. 프로젝트가 모든 사람의 작업을 다시 실행할 필요는 없습니다.

- **L0 — 모든 항목 다시 채점 (무료, 100%).** 서버는 harness가 사용하는 것과
  동일한 메트릭을 사용하여, (기여자가 저장한 사본이 아닌) **sha-pinned reference corpus**를
  기준으로 *제출된 출력물*에서 점수를 다시 도출해요. 출력물에서 점수가 재현되지
  않거나 저장된 reference가 변경된 경우, 해당 실행은 **실격(disqualified)** 처리됩니다.
  이것만으로도 직접 입력하거나 편집한 점수를 걸러낼 수 있어요. 재현에 성공한 실행은
  보드에서 순위를 매기는 유일한 티어인 **Champollion Verified**로 승격돼요.
  이는 모든 제출물에 대해 실행되며 수 밀리초밖에 걸리지 않습니다.
- **L1 — 기여자 평판 사다리.** 각 기여자(로그인으로 식별됨)는 아래의 더 깊은
  검증을 통과해야만 평판을 얻을 수 있어요. 단순히 제출량만으로는 평판을 얻을 수
  없으므로, 새로운 계정을 무수히 생성해도 아무 소용이 없습니다. 평판은 **공개**되며,
  비용이 많이 드는 검증이 얼마나 자주 실행될지를 결정해요.
- **L2 — *표본* 다시 실행 (비용이 많이 드는 검증).** *공개된* development 세트의 경우,
  단순히 reference를 복사하여 "번역"으로 제출하는 기여자를 L0 단계에서는 잡아낼 수
  없어요. 이를 잡아내려면 실제로 모델을 다시 실행하는 실제 컴퓨팅 작업이 필요하므로,
  모든 사람이 아닌 **표본(sample)**에 대해서만 수행해요. L2 다시 실행을 위해 표본으로
  추출될 확률은 **중요도(stakes)**가 높을수록(전체 어족으로 가는 첫 번째 다리를 놓는
  실행은 *항상* 다시 실행됨), **이상 징후(anomaly)**가 클수록(이전 최고 기록을
  믿기 힘들 정도로 뛰어넘는 경우 *항상* 다시 실행됨) 높아지며, **평판(reputation)**이
  높을수록 낮아져요(많은 감사를 통과한 기여자는 드물게 spot-check를 받지만,
  신규 기여자나 익명 제출자는 신뢰를 얻을 때까지 매 실행마다 검증을 받습니다).
  L2 감사를 통과하면 평판이 올라가요.
- **L3 — 교차 검증 (무료 검증).** 두 명의 *독립적인* 기여자가 동일한 corpus에서
  동일한 모델을 실행하고 다시 채점된 출력물이 **일치(agree)**하는 경우, 그 일치 자체가
  검증이 되며 두 사람 모두의 평판을 높여줘요. 진정한 **불일치(disagreement)**가
  발생하면 두 실행 모두 L2 감사 대상으로 지정됩니다. 재현(Replication)은 중복으로
  취급되지 않고 보상을 받아요.

**한 번의 조작 발각은 치명적입니다 — 논문 철회와 같아요.** 조작이 입증되면
기여자의 평판은 0이 되고, **검증된 전체 기록을 다시 감사**하며(검증된 모든 실행이
다시 검증 단계를 거침), 감사 로그에 **공개적으로** 기록돼요. 이것이 바로 가벼운
표본 추출(light sampling)을 안전하게 만드는 이유입니다. 공개된 dev 세트를 속이는
것이 한 번의 실행에서는 넘어갈 수 있지만, 얻은 모든 신뢰를 잃고 전체 기록을 다시
조사받는 예상 비용을 고려하면 이는 매우 나쁜 도박이 되기 때문이에요. 이 규칙은
유지보수 담당자의 자체 실행에도 대칭적으로 적용됩니다.

**그럼에도 기여할 가치가 있는 이유.** 비용이 많이 드는 부분(메서드 실행)은
항상 여러분이 부담하지만, 프로젝트는 모든 사람에 대한 무료 L0 다시 채점과
*점점 줄어드는 표본*에 대한 L2 다시 실행 비용만 부담해요. 이 표본은 신규 기전자와
중요도가 높은 실행에는 높게, 검증된 기여자에게는 낮게 적용됩니다. 검증 비용은
매번 전액을 다시 지불하는 것이 아니라, *평판에 의해 상각되고 교차 검증에 의해 공유*돼요.

## 제출 방법

1. **메서드 구축** — 메서드 인터페이스는 [Building a Method](/docs/network/specifications/methods)를 참조하세요.
2. **harness 실행** — 설정 및 사용법은 [Eval Harness](/docs/network/specifications/harness)를 참조하세요.
3. **run card 생성** — harness는 점수, 핑거프린트 및 메타데이터가 포함된 JSON run card를 생성해요.
4. **게시** — `mt-eval publish eval/logs/harness/<your-run-card>.json` 명령어로 run card를 리더보드에 업로드해요.
5. **리더보드에 표시** — 실행 결과는 *self-benchmarked (unverified)* 상태로 준비된 후, 서버가 sha-pinned corpus를 기준으로 출력물을 자동으로 다시 채점(L0)해요. 재현에 성공하면 실행 결과는 [Method Leaderboard](https://champollion.dev/leaderboard)에서 순위를 매기는 유일한 티어인 *Champollion Verified*로 승격됩니다. 더 깊은 평판 가중치 기반 감사는 위의 trust tiers를 따라요.

## 무결성 정책: 철회, 다시 실행, 목록 제외, 분쟁

집행이 감정적인 문제가 아닌 절차가 되도록 사전에 작성되었어요. 이 규칙은
유지보수 담당자의 자체 실행을 포함하여 모든 사람에게 대칭적으로 적용됩니다.

**철회 불가.** 게시된 실행은 영구적인 기록이에요. 부끄럽다는 이유로 점수를
삭제할 수 있는 메커니즘은 누구에게도 제공되지 않습니다.
모든 실행 행에는 서버가 찍은 `submitted_at` 타임스탬프와
변경할 수 없는 감사 추적이 포함되며, 조정(moderation) 작업 자체도 로그로 남아요.

**다시 실행은 추가될 뿐, 대체되지 않음.** 메서드를 개선했다면 새로운 실행을
게시하세요. 이전 실행은 그대로 유지됩니다. 비공개로 여러 변형을 테스트하고
승자만 게시하는 선택적 공개(Selective disclosure)는 다른 리더보드를
악용 가능하게 만든 원인이에요. 추가만 가능한(append-only) 기록이 이에 대한
구조적 해답입니다. 핑거프린트 중복 제거는 바이트 단위로 동일한 재제출 스팸을
차단할 뿐, 결코 기록을 덮어쓰지 않아요.

**목록 제외는 규칙 실행이며, 규칙 이름이 명시됨.** 실행이 목록에서 제외되는
(조용히 제거되는 것이 아니라 `disqualified`로 명확히 표시됨) 경우는
명시된 원인에 한정돼요. 격리되거나 부적절한 하위 집합 데이터셋(모든 클라이언트
아래의 데이터베이스 트리거에 의해 강제됨), corpus 체크섬 불일치, 조작되거나
범위를 벗어난 점수, 콘텐츠 보호 위반, 또는 관리자의 기본 데이터 등록 철회가
이에 해당합니다. 목록 제외 시에는 규칙과 증거가 명시돼요. 새로운 원인은
적용되기 전에 날짜가 기입된 편집을 통해 여기에 추가되며, 특정 사례를 위해
소급하여 만들어지지 않습니다.

**Trust tiers는 라벨일 뿐, 편집이 아님.** `self-benchmarked` 행은 주장(claims)입니다.
`Champollion Verified` 행은 sha-pinned corpus를 기준으로 제출자의 출력물에서
독립적으로 다시 채점된 것이며, `Community Validated`는 커뮤니티 자체 테스트를
통해서만 부여돼요. 검증은 행의 티어를 변경할 뿐, 행의 점수를 변경하지는 않습니다.

**평판은 공개되며 스스로 교정됨.** 기여자의 평판과 모든 다시 채점, 표본 다시 실행,
교차 검증, 조작으로 인한 평판 소멸을 기록하는 감사 로그는 공개돼요. 평판은 점수
승수가 아니며 실행의 수치에 전혀 영향을 주지 않습니다. 단지 기여자의 실행이
얼마나 자주 다시 감사될지 결정할 뿐이에요(위의 *평판 가중치 기반 감사* 참조).
조작이 입증되면 논문 철회만큼이나 공개적으로 기록되며 기여자의 검증된 전체 기록을
다시 감사해요. 동일한 규칙이 유지보수 담당자의 자체 실행에도 적용됩니다.

**분쟁.** run id와 구체적인 주장(잘못된 점수, 잘못된 데이터셋, 규칙 오적용)을
포함하여 이슈를 여세요. 유지보수 담당자는 결정론적(deterministic) 검사를
공개적으로 다시 실행하며, 결과와 증거는 해당 이슈에 남겨집니다. 분쟁이 커뮤니티의
데이터나 검증에 관한 것이라면 커뮤니티 자체 권한으로 결정하고 보드는 그 결정을
이행해요. 상금 콘테스트의 경우 동일한 규칙에 콘테스트의 사전 게시된 예선 및
감사 단계가 추가로 적용됩니다. 우승자는 상금 지급 **전에** 감사를 받으며,
실격 시 다른 목록 제외와 마찬가지로 규칙을 정확히 인용해요.

## 향후 방향

- **포괄적인 모델 비교 실행** — 맞춤형 평가 코퍼스(공개 벤치마크가 아님)를 사용하여 champollion 언어 전반에서 최전선 모델(GPT-4o, Claude, Gemini 등)의 체계적 평가
- **더 많은 언어 쌍** — 커뮤니티 검증 데이터셋이 사용 가능해지면 Quechua, Inuktitut, 기타 저자원 언어
- **데이터셋 임포트** — 외부 평가 데이터셋(WMT, Tatoeba 등)을 champollion 평가 형식으로 변환하는 도구
- **자동 재실행** — 모델 버전 변경을 감지하고 벤치마크를 재실행하여 점수 편차 추적
