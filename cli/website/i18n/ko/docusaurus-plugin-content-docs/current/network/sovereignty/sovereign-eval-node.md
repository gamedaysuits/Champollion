# Sovereign Eval Node — 하드웨어 및 에어갭 운영

Sovereign Eval Node는 **여러분**이 직접 제어하는 머신으로, 비밀 테스트 세트를 보관하고 이를 기준으로 번역 방식을 평가해요. 방식(Method)이 데이터가 있는 곳으로 이동할 뿐, 데이터는 절대 외부로 이동하지 않아요. 오직 점수만이 밖으로 나옵니다.

이 페이지는 실용적인 사양을 다뤄요. 어떤 하드웨어를 구매(또는 재사용)해야 하는지, 어떻게 설정하는지, 그리고 "테스트 세트가 머신을 절대 벗어나지 않았다"는 것을 단순히 믿어야 하는 약속이 아니라 방어할 수 있는 사실로 만드는 운영 원칙을 설명해요.

:::info[오늘 출시된 기능 vs. 진행 중으로 표시된 기능]
주최자 노드 소프트웨어는 `mt-eval`에 **오늘 출시되었어요** — [자주적 대회 가이드](/docs/network/sovereignty/run-a-sovereign-contest)를 참고하세요:
대회 준비 및 봉인(sealing), 관리자(custodian)에게 승인을 요청하기 전에
**노드 자체가 모든 출품작에 대해 재실행하는** 공개 예선(public-qualifier) 게이트,
임계값 기반 채점, 그리고 임포트 검사 기능이 포함된 네트워크 격리 방식의
메서드 실행기가 포함되어 있어요. 노드가 허용하는 것은 노드가 실행할 수 있는
아티팩트인 **모델 또는 메서드**예요. 소스 공개 블라인드 세트의 번역본을
업로드하는 방식은 2026-09-06에 대회 출품 경로에서 폐기되었고 해당 동사(명령어)도
삭제되었어요. 소스 공개 라운드는 주최자의 선택적 진단용으로만 유지되며,
자체 보고된 점수는 대회가 아닌 말뭉치와 언어 쌍 방향별로 색인된 공개 게시판인
오픈 리더보드에 속해요.
**§4의 임계값 키 세레머니 및 유휴 상태 봉인(sealed-at-rest) 워크플로 역시 오늘 출시되었어요**: `mt-eval node ceremony init|share|verify|restore`, `mt-eval node
seal`, 실행 시점에 제시되는 정족수 샤드(quorum shares)(`node run-method --offline --share …`),
해시 체인 기반 로컬 권한 부여 원장(`node ledger verify|head`),
서명된 점수 매니페스트(`node sign-manifest` / `node verify-manifest`),
그리고 §2–§3 에어갭 툴링(`node bundle`, `node manifest`, `node egress-check`)이 포함돼요.
점수 번들은 Node.js 런타임 없이도 오프라인 번들이 동작하도록 **노드에서 Python으로** 서명되며,
동일한 분리 서명(detached-signature) 포맷은 두 구현체 모두에서 검증할 수 있어요.
주최자 측의 **요청 스테이징(request staging)도 출시되었어요**:
`mt-eval node stage-request`은 온라인 릴레이가 작성할 교환 요청을 번들 파일로부터 데이터베이스 없이
(리허설 또는 절대 연결되지 않는 배포 환경용) 그대로 작성하며,
임포트 검증 방식대로 사전 검증되어 노드 ID에 바인딩돼요. 반환되는 점수는
매니페스트를 통해 검증 가능하지만, 발행 기준으로 삼을 권한 부여 기록이
존재하지 않으므로 릴레이에 게시되지는 않아요.
단일 키쌍 대행 방식은 주최자가 참조 기준(references)을 전적으로 보유하는
대회에만 유지되며, 모든 인터페이스에 현재 사용 중인 레인이 명시돼요.
분명히 말씀드리면, v1에 **포함되지 않는** 사항은 다음과 같아요: 하드웨어
원격 증명(TEE)은 제공되지 않으며(§5), 플랫폼 측 임계값 *서명*(호스팅된
인프라에 대한 관리자 폰 승인)은 향후 과제예요. 자주적 노드에서 보관 권한은
머신에 직접 N개 중 M개의 샤드를 물리적으로 제시함으로써 행사돼요(§4).
그리고 암호화에 대해 정확히 짚고 넘어가자면, 이는 승인된 실행 중에
**노드의 잠긴 메모리에서 복원된 후**(이후 0으로 초기화됨) 사용되는 Shamir의 N개 중 M개
비밀 공유 방식이에요. 이는 다자간 연산(MPC)이 *아니며*, 오프라인 머신에 키가
완전히 조합된 상태로 잠시 존재해요. 마지막으로, 커뮤니티 동의 게이트가
열릴 때까지 이 레인은 **합성 데이터로만** 실행돼요. 실제 말뭉치는 해당 동의를 기다려야 해요.
:::

## 1. 레퍼런스 하드웨어

실행기는 로컬 NMT 디코딩, FST/형태론 검증, 메트릭 계산과 같은 독립적인 방식을 실행해요. 에어갭 내부에서는 클라우드 호출이 발생하지 않아요(LLM-API 방식은 에어갭 노드가 거부하는 정확한 클래스예요. [벤치마크 사양](/docs/network/specifications/benchmark)의 방식 클래스를 참조하세요).

| 티어 | 사양 | 적합성 | 대략적인 비용 (2026년 기준) |
|---|---|---|---|
| **최소** (작동 가능) | 4코어 x86_64 또는 Apple/ARM, 16GB RAM, 500GB SSD | 메트릭 + FST 평가, 소형 NMT 모델의 CPU 디코딩 (느리지만 정확함) | US$0 (여분 노트북) – $400 (중고) |
| **권장** | 8코어, 32GB RAM, 1TB NVMe, NVIDIA GPU ≥ 12GB VRAM (예: RTX 4070급) | 전체 테스트 배터리를 위한 원활한 NMT 디코딩, 병렬 방식 평가 | ~US$900–1,600 (소형 워크스테이션) |
| **기관용** | 16코어, 64–128GB RAM, 2TB NVMe, 24GB+ VRAM | 다수 방식 경연, 대규모 배터리, 보관용 암호문 저장소 | ~US$2,500–4,000 |

모든 티어의 필수 요구 사항:

- **무선 통신 장치가 없거나, 꺼져 있음을 증명할 수 있어야 해요.** 가장 좋은 방법: Wi-Fi/Bluetooth 카드가 없는 데스크톱. 허용되는 방법: 무선 카드가 물리적으로 제거되었거나 펌웨어에서 비활성화된 노트북. "비행기 모드"는 에어갭이 아니에요.
- **플러그를 뽑아둘 수 있는 유선 NIC.** 케이블이 없는 것은 가장 감사하기 쉬운 네트워크 제어 방법이에요.
- **두 개의 전용 USB 드라이브**(IN 및 OUT으로 라벨링 — §3 참조)가 필요하며, 이상적으로는 펌웨어에서 다른 포트를 비활성화한 머신이 좋아요.
- **전체 디스크 암호화**(Linux의 경우 LUKS)를 통해 도난당한 노드를 무용지물로 만들고, 전원 공급이 불안정하다면 UPS를 구비하세요. 배터리 도중 중단된 평가는 복구할 수 있지만, 굳이 그런 상황을 겪을 필요는 없으니까요.

## 2. 소프트웨어 설정 (1회, 약 1시간 소요)

1. **네트워크 케이블을 분리한 상태에서** USB 설치 미디어를 통해 최신 Linux LTS(Ubuntu/Debian)를
   설치하세요. 설치 시 전체 디스크 암호화(full-disk encryption)를 활성화하세요.
2. 하네스가 설치된 별도의 온라인 머신(`python3 -m pip install mt-eval-harness`, 0.2.0 이상)에서 오프라인 번들을 빌드하세요.
   `mt-eval node bundle --out <dir>` 명령은 다음 네 가지 작업을 수행해요:
   - 설치된 하네스와 종속성을 휠(wheel) 파일로 패키징합니다(또는 `--wheel <file>` 옵션으로 특정 휠 지정).
   - 하네스 내부에 포함된 해시 고정 목록에 따라 암호화 라이브러리를 가져옵니다.
   - 모든 `--include` 아티팩트를 복사합니다.
   - 모든 파일에 대한 sha256 매니페스트를 작성합니다.

   노드가 채점할 모든 언어에 대한 **언어 카드**를 포함하세요
   (`--include <cards-dir>`). 노드는 로컬 카드 색인에서 실행의 언어 쌍 이름을
   가져오며 원격에서 절대 가져오지 않아요. 설치된 두 패키지 모두 언어별
   카드 디렉터리를 기본 제공하지 않으므로, 여기에서 `champollion`
   CLI를 사용해 언어당 하나의 `<code>.json`을 작성하고(`champollion network card eng --json >
   node-cards/eng.json` 실행 후 다른 언어에도 동일하게 수행),
   `--include node-cards` 옵션을 전달하세요. 노드에서는
   `<dir>/artifacts/node-cards`에 위치하므로 `cards_dir`이 그 위치를 가리키도록 설정하세요. 노드에 필요한 모든 것은
   IN 드라이브를 통해 한 번만 전달돼요. 노드가 실행하는 동일한 Python 버전(3.11 또는 3.12)에서
   빌드하세요. 고정된 목록은 다른 버전을 거부해요.
3. IN 드라이브에 번들을 전송하세요. 설치하기 전에 **노드에서** 매니페스트를
   기준으로 모든 아티팩트의 sha256을 검증하세요
   (`mt-eval node bundle --verify <dir>`). 그런 다음 번들로 제공된 휠에서만 설치하세요:
   `python3 -m pip install --no-index --find-links <dir>/wheels 'mt-eval-harness[node]'`.
   `[node]` 엑스트라는 `mt-eval node
   keygen` and the custody ceremony need; a plain `mt-eval-harness` 설치본에
   빠져 있는 `cryptography` 라이브러리예요.
4. 노드의 서명 키쌍을 생성하고(`mt-eval node keygen`) 공개 키 부분을 기록하세요 — 누구나 점수 매니페스트를 검증할 수 있도록 이를 공개해야 해요(§5).
   노드에는 네트워크가 차단된 컨테이너에서 각 제출된 메서드를 실행하는 **Docker**(또는 Podman)도 필요해요. `PATH`에 둘 다 없으면,
   `mt-eval node run-method`은 둘 모두를 언급하는 한 줄 메시지와 함께 실행을 거부하며,
   요청은 계속 실행 가능한 상태로 유지돼요. 또한 `~/.mt-eval/node.json` 경로에 노드 설정 파일이 필요해요.
   이 파일에는 노드 이름, 카드 디렉터리(`cards_dir` 또는 `MT_EVAL_CARDS_DIR`), 노드가 서비스하는 대회가 지정돼요.
   `mt-eval node init` 명령은 공개 예선 게이트(노드가 봉인된 세트를 열기 전에 모든 메서드에 대해 재실행하는 `qualifier` + `dev_corpus`) 및
   봉인된 홀드아웃 슬롯(`holdout_set_id` + `holdout_corpus`, 홀드아웃이 없는 대회의 경우 삭제 가능)을 포함하여 채점 노드가 읽는 모든 키가 들어 있는 시작용 설정을 작성해요.
   `mt-eval node init --from-contest <out>` 명령은 `contest prepare`이 작성한 매니페스트로부터 대회의 값을 채웁니다(매핑 정보는
   [자주적 대회 가이드](/docs/network/sovereignty/run-a-sovereign-contest#organizer-prerequisites)에 나와 있어요).
   `sandbox` 블록은 노드의 리소스 정책(RAM 4GB, 스크래치 공간 4GB, 실행당 30분, GPU 없음)이며, `contest submit-method`은 기본적으로
   이 값들을 정확히 선언하므로 설정을 변경했다면 대회와 함께 제한 값을 공개하세요.
   해당 게이트의 절반만 선언된 노드 설정은 시작 시 거부돼요.
   `mt-eval node ledger verify`은 채워진 파일을 확인해요. 남아 있는 첫 번째 `<...>` 값이나 노드에 존재하지 않는 선언된 파일을 감지하면 거부하고,
   확인한 내용을 출력한 뒤 로컬 원장의 해시 체인을 재생해요. 노드로 요청을 릴레이하는 연결된 머신에는
   데이터베이스의 **service-role 키**(`MT_EVAL_SUPABASE_SERVICE_KEY`)도 필요해요. 이 키는 에어갭 노드 자체에는 전혀 필요하지 않아요.
5. 이때부터 머신은 네트워크와 절대 연결되지 않으며, 봉인된 실행을 통해 이를 사전에 입증할 수 있어요:
   `mt-eval node egress-check`(노드 설정에서 `assert_airgap`로도 자동 적용됨)은 라우트, 프로브, 또는 DNS를 통해 외부로 나가는 경로가 발견되면 실행을 거부해요. OS 업데이트는 백그라운드 서비스가 아니라
   신중하게 번들링되고 해시가 검증된 이벤트로 진행돼요.

## 3. 전송 원칙 (모든 경연, 양방향)

에어갭은 제품이 아니라 *절차*예요. 절차는 다음과 같아요.

- **IN 드라이브**가 담는 항목: 제출된 메서드 또는 모델 번들과 해당 매니페스트.
  실행하기 전에 노드는 매니페스트를 기준으로 각 패키지의 해시를 검증하고
  임포트 검사를 실행해요(네트워크 라이브러리를 임포트하는 메서드는 거부되며, 이 기능은 오늘 출시되었어요).
- **OUT 드라이브**가 담는 항목: 서명된 점수 매니페스트(집계 점수,
  해당 점수가 속한 메서드/설정 해시, 감사 로그 헤드)와 *그 외에는 아무것도 담지 않아요*.
  세그먼트별 결과물은 주최자의 통제하에 노드에 유지되며, 이를 공개할지 여부는
  커뮤니티의 별도적이고 신중한 결정에 달려 있어요.
- 드라이브당 하나의 방향만 항상 유지해요. 노드에 연결되었던 드라이브는 온라인 머신에서
  절대 자동으로 마운트되지 않아야 해요 — `noexec,nodev`으로 마운트하고 매니페스트를 수동으로 복사하세요.
- 이동하기 전에 `mt-eval node manifest write <drive> --direction in|out`이 드라이브의 모든 파일을 해싱하며,
  수신 측의 `mt-eval node manifest verify`은 추가되거나 변경되거나 누락된 항목이 있으면 작업을 거부해요.
- 모든 이동 내역(날짜, 드라이브, 매니페스트 해시)을 노드의 서면 로그나
  노드 내부 로그에 기록하세요. 단순하고 엄격한 관리가 핵심이에요. "다른 데이터가
  외부로 유출된 적이 있는가?"라는 질문에 증거를 가지고 답할 수 있게 해 주는 것이 바로 이 로그예요.

## 4. 키 보관 (M-of-N, 커뮤니티 보유)

봉인된 테스트 세트는 유휴 상태에서 암호화돼요. 복호화하려면 장로회(Elders' council),
언어 당국, 교육 기관 등 **커뮤니티가 선정한** 관리자(custodians)가 보유한
키 샤드의 정족수가 필요해요. 이 설계에서 플랫폼은 단 하나의 샤드도 갖지 않으므로,
Champollion은 봉인된 세트를 복호화할 수 없으며 단일 관리자 혼자서도 복호화할 수 없어요.
아래의 세레머니는 아직 실제 관리자들과 함께 진행되지는 않았어요.

세리머니(오프라인에서 한 번 진행되며, 제공되는 도구가 이를 자동화함): `mt-eval node ceremony init`은 노드에서 세트 키를 생성하고 이를 N개의 셰어로 분할한 뒤(M개가 모이면 재구성되며, 그보다 적으면 아무것도 드러나지 않는 정보 이론적 공유 방식), 즉시 키를 0으로 초기화해요. `ceremony share`는 각 관리자의 셰어를 토큰용 파일과 인쇄 가능한 종이 백업으로 출력해요. `ceremony verify`은 분산된 복사본이 재구성됨을 증명하며, 이 과정에서 아무것도 영구 저장하지 않아요. `ceremony share --wipe-originals` then destroys the node's own copies. `mt-eval node seal`은 말뭉치를 세리머니의 공개 키로 암호화해요. 노드는 암호문과 내용이 없는 메타데이터 카드만 저장하며, 그 외에는 아무것도 저장하지 않아요. 그 이후로 평가를 실행하려면 관리자가 N개의 셰어 중 M개를 물리적으로 제시해야 해요(`node run-method --offline --share …`). 키는 **실행기의 잠긴 메모리에서만** 재구성되어 해당 권한이 부여된 단일 실행에 사용된 후 0으로 초기화되며, 디스크에 다시는 닿지 않아요. 모든 요청, 투표, 권한 부여 및 사용은 해시 체인 기반 로컬 원장(`node ledger verify`)에 추가되며, 쿼럼 없는 시도는 거부되는 *동시에* 기록돼요.

이 메커니즘에 대해 솔직하게 한 문장으로 설명하자면, 이는 다자간 컴퓨팅이 아니라 커뮤니티가 보유한 오프라인 머신의 메모리에서 재구성되는 Shamir 비밀 공유 방식이에요. 승인된 실행 중에 키는 커뮤니티가 물리적으로 제어하는 하드웨어에 조립된 상태로 잠시 존재해요. 이 방식이 방어하는 속성은 *디스크에 상주하는 키가 없고*, *쿼럼 없이는 실행되지 않으며*, *모든 사용 내역이 검사 가능한 원장에 체인으로 연결된다*는 점이에요. 키가 어디에서도 조립되지 않는 플랫폼 측 임계값 서명은 향후 작업으로 남아 있으며, 언급되는 모든 곳에 그렇게 표시되어 있어요.

교체 및 관리자 변경 시에는 세리머니를 다시 실행해요. N−M개 이상의 셰어를 분실하면 커뮤니티의 원본 복사본에서 세트를 다시 밀봉해야 해요. [소유권](/docs/network/sovereignty/data-sovereignty)은 애초에 우리가 가질 수 있는 것이 아니었기 때문에, 커뮤니티는 항상 자체 평문 원본을 유지해요.

## 5. 여기서 "증명됨(attested)"의 의미와 그렇지 않은 것

모든 평가는 **서명된 점수 매니페스트**를 생성해요. 여기에는 점수, 방식 패키지 해시, 말뭉치 체크섬, 추가 전용 감사 로그의 헤드에 대한 노드의 서명이 포함돼요. 노드의 게시된 공개 키를 가진 사람이라면 누구나 `mt-eval node verify-manifest <manifest> --pubkey <published .pub.json>` 명령을 통해 *이 노드*가 *정확히 이 입력*에 대해 *이 점수*를 생성했음을 검증할 수 있으며, 해시 체인 로그를 통해 몰래 이루어진 기록 수정도 감지할 수 있어요.

이것이 바로 **소프트웨어 증명**이에요. 기록의 무결성을 증명하며, v1에서 제공하는 기능이에요. 하지만 어떤 실리콘(하드웨어)이 실행을 수행했는지는 증명하지 **않아요**. 하드웨어 원격 증명(TEE)은 향후 작업이며 의도적으로 지원을 주장하지 않아요. v1에 대한 솔직한 보안 선언은 다음과 같아요. 주최자의 원칙(§3), 서명된 매니페스트, 그리고 커뮤니티의 물리적 머신 보관이 신뢰의 앵커(trust anchor)가 되며, 이는 주권 우선(sovereignty-first) 설계가 신뢰를 두고자 하는 바로 그 지점이에요.

## 6. 운영 루프

1. 대회를 공지하고, 노드의 공개 키와 개발 세트(dev-set) 임계값을 공개하세요.
2. 일반 온라인 머신에서 제출물을 수신하고 IN 매니페스트를 구성하세요(`mt-eval node manifest write <drive> --direction in`).
3. IN 드라이브를 노드로 가져간 뒤 해시를 검증하세요(`node manifest verify`).
   import-scan (`node import-bundle`); queue methods. An entrant's offline
   제안(proposal)은 *보류 중(pending)* 상태로 도착해요. 노드가 먼저 이를 확인해요(`node run-method
   <id> --offline` 명령은 공개 개발 세트에서 참가자의 예선을 재실행하고 코드 출품작에 대한
   컨테이너 런타임을 확인하며, 봉인된 데이터는 일절 열지 않고 로컬 원장에 통과 기록을 남김).
   그런 다음 관리자가 노드에 결정을 기록해요(해당 확인을 통과하기 전까지 거부되는 `node approve <id> --offline --actor <custodian>`
   또는 `node deny … --offline --reason …`: 로컬 원장에 투표 + 권한 부여를 기록하고 노드 키로 서명된 기록을 생성하며,
   `node list --offline`은 대기 중인 항목을 표시함). 봉인된 실행(다시 `node run-method
   --offline`)은 해당 승인이 기록되고 검증될 때까지 보류 중인 제안을 거부해요.
4. 관리자는 정족수의 샤드를 제시하여 실행을 승인해요(§4 — `node run-method <id> --offline --share … --share …`).
   봉인된 세트는 실행기(executor) 내부로만 복호화돼요. 정족수가 충족되지 않으면 실행되지 않으며,
   해당 시도는 원장에 기록돼요.
5. 실행 후 점수가 계산되며, 세그먼트별 결과물은 노드 측에 유지돼요.
6. 정리(Teardown): 작업 평문이 삭제되고, 감사 로그가 추가되며, 매니페스트가 서명돼요.
7. OUT 드라이브를 다시 가져와 점수와 매니페스트를 공개하세요. 누구나 검증할 수 있어요(`node verify-manifest`).
8. 이동 내역을 기록하세요. 드라이브는 전용으로 유지되며, 노드는 오프라인(dark) 상태를 유지해요.
