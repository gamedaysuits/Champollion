# Sovereign Eval Node — 하드웨어 및 에어갭 운영

Sovereign Eval Node는 **여러분**이 직접 제어하는 머신으로, 비밀 테스트 세트를 보관하고 이를 기준으로 번역 방식을 평가해요. 방식(Method)이 데이터가 있는 곳으로 이동할 뿐, 데이터는 절대 외부로 이동하지 않아요. 오직 점수만이 밖으로 나옵니다.

이 페이지는 실용적인 사양을 다뤄요. 어떤 하드웨어를 구매(또는 재사용)해야 하는지, 어떻게 설정하는지, 그리고 "테스트 세트가 머신을 절대 벗어나지 않았다"는 것을 단순히 믿어야 하는 약속이 아니라 방어할 수 있는 사실로 만드는 운영 원칙을 설명해요.

:::info[현재 제공되는 기능 vs. 진행 중으로 표시된 기능]
주최자 노드 소프트웨어(경연 준비, 가설 수집, 임계값 기반 채점, import scan) **ships today** in `mt-eval` — see the을 갖춘 네트워크 격리 방식 실행기)는 [Sovereign 경연 가이드](/docs/network/sovereignty/run-a-sovereign-contest)에 설명된 대로 제공돼요. **§4의 임계값 키 세리머니(threshold key ceremony) 및 유휴 상태 밀봉(sealed-at-rest) 워크플로우도 오늘 함께 제공돼요**: `mt-eval node ceremony init|share|verify|restore`, `mt-eval node seal`, 실행 시 제시되는 쿼럼 셰어(`node run-method --offline --share …`), 해시 체인 기반 로컬 권한 부여 원장(`node ledger verify|head`), 서명된 점수 매니페스트(`node sign-manifest` / `node verify-manifest`), 그리고 §2–§3의 에어갭 도구(`node bundle`, `node manifest`, `node egress-check`)가 포함돼요. 단일 키페어 대체재는 주최자가 참조 데이터를 완전히 소유한 경연에만 남아 있으며, 모든 표면에는 어떤 레인이 사용 중인지 표시돼요. 분명히 말씀드리자면, v1에 **포함되지 않는** 것은 다음과 같아요. 하드웨어 원격 증명(TEE)은 지원하지 않으며(§5), 플랫폼 측 임계값 *서명*(호스팅된 인프라에 대한 관리자의 전화 승인)은 향후 작업으로 남겨두었어요. Sovereign Node에서 보관은 머신에 N개의 셰어 중 M개를 물리적으로 제시함으로써 행사돼요(§4). 암호화에 대해 정확히 설명하자면, 이는 **승인된 실행 중에 노드의 잠긴 메모리에서 키가 재구성되는**(이후 0으로 초기화됨) Shamir M-of-N 비밀 공유 방식이에요. 다자간 컴퓨팅(multi-party computation)이 *아니며*, 오프라인 머신에 조립된 상태의 키가 잠시 존재하게 돼요. 마지막으로, 커뮤니티 동의 게이트가 열릴 때까지 이 레인은 **합성 데이터에 대해서만** 실행돼요. 실제 말뭉치는 해당 동의를 기다려야 해요.
:::

## 1. 레퍼런스 하드웨어

실행기는 로컬 NMT 디코딩, FST/형태론 검증, 메트릭 계산과 같은 독립적인 방식을 실행해요. 에어갭 내부에서는 클라우드 호출이 발생하지 않아요(LLM-API 방식은 에어갭 노드가 거부하는 정확한 클래스예요. [벤치마크 사양](/docs/network/specifications/benchmark)의 방식 클래스를 참조하세요).

| 티어 | 사양 | 적합성 | 대략적인 비용 (2026년 기준) |
|---|---|---|---|
| **최소** (작동 가능) | 4코어 x86_64 또는 Apple/ARM, 16GB RAM, 500GB SSD | 메트릭 + FST 평가, 소형 NMT 모델의 CPU 디코딩 (느리지만 정확함) | US$0 (여분 노트북) – $400 (중고) |
| **권장** | 8코어, 32GB RAM, 1TB NVMe, NVIDIA GPU ≥ 12GB VRAM (예: RTX 4070급) | 전체 테스트 배터리를 위한 원활한 NMT 디코딩, 병렬 방식 평가 | ~US$900–1,600 (소형 워크스테이션) |
| **기관용** | 16코어, 64–128GB RAM, 2TB NVMe, 24GB+ VRAM | 다수 방식 경연, 대규모 배터리, 보관용 암호문 저장소 | ~US$2,500–4,000 |

모든 티어의 필수 요구 사항:

- **무선 통신 장치가 없거나, 꺼져 있음을 증명할 수 있어야 해요.** 가장 좋은 방법: Wi-Fi/Bluetooth 카드가 없는 데스크톱. 허용되는 방법: 무선 카드가 물리적으로 제거되었거나 펌웨어에서 비활성화된 노트북. "비행기 모드"는 에어갭이 아니에요.
- **플러그를 뽑아둘 수 있는 유선 NIC.** 케이블이 없는 것은 가장 감사하기 쉬운 네트워크 제어 방법이에요.
- **두 개의 전용 USB 드라이브**(IN 및 OUT으로 라벨링 — §3 참조)가 필요하며, 이상적으로는 펌웨어에서 다른 포트를 비활성화한 머신이 좋아요.
- **전체 디스크 암호화**(Linux의 경우 LUKS)를 통해 도난당한 노드를 무용지물로 만들고, 전원 공급이 불안정하다면 UPS를 구비하세요. 배터리 도중 중단된 평가는 복구할 수 있지만, 굳이 그런 상황을 겪을 필요는 없으니까요.

## 2. 소프트웨어 설정 (1회, 약 1시간 소요)

1. **네트워크 케이블을 뽑은 상태에서** USB 설치 프로그램으로 최신 Linux LTS(Ubuntu/Debian)를 설치하고, 설치 시 전체 디스크 암호화를 활성화해요.
2. 온라인 상태의 별도 머신에서 오프라인 번들을 빌드해요. `mt-eval node bundle --out <dir>`은 `mt-eval[node]` 및 해당 종속성의 휠(wheel)을 가져오고, `--include` 아티팩트를 복사하며, 모든 파일에 대해 sha256 매니페스트를 작성해요. 노드에 필요한 모든 것은 IN 드라이브를 통해 한 번만 전달돼요.
3. IN 드라이브로 번들을 전송해요. 설치하기 전에 **노드에서** 매니페스트를 기준으로 모든 아티팩트의 sha256을 검증해요(`mt-eval node bundle --verify <dir>`).
4. 노드의 서명 키페어를 생성하고(`mt-eval node keygen`) 공개 키 부분을 기록해요. 누구나 점수 매니페스트를 검증할 수 있도록 이를 게시하게 될 거예요(§5).
5. 그 이후로 머신은 절대 네트워크에 연결되지 않아요. 이를 먼저 증명하기 위해 밀봉된 실행을 수행할 수 있어요. `mt-eval node egress-check`(노드 구성의 `assert_airgap`을 통해 자동으로 강제 적용됨)는 라우팅, 프로브 또는 DNS가 외부로 나가는 경로를 표시할 경우 실행을 거부해요. OS 업데이트는 백그라운드 서비스가 아니라 의도적이고 번들로 제공되며 해시 검증을 거치는 이벤트예요.

## 3. 전송 원칙 (모든 경연, 양방향)

에어갭은 제품이 아니라 *절차*예요. 절차는 다음과 같아요.

- **IN 드라이브**에는 제출된 방식 패키지, 가설 파일 및 해당 매니페스트가 포함돼요. 어떤 것이든 실행되기 전에 노드는 매니페스트를 기준으로 각 패키지의 해시를 검증하고 임포트 스캔을 실행해요(네트워크 라이브러리를 임포트하는 방식은 거부하며, 이 기능은 현재 제공돼요).
- **OUT 드라이브**에는 서명된 점수 매니페스트(집계된 점수, 해당 점수가 속한 방식/구성 해시, 감사 로그 헤드)만 포함되며, *그 외에는 아무것도 포함되지 않아요*. 세그먼트별 출력은 주최자의 통제하에 노드에 유지돼요. 이를 게시하는 것은 별도의 신중한 커뮤니티 결정 사항이에요.
- 드라이브당 항상 한 방향으로만 사용해요. 노드에 연결했던 드라이브는 온라인 머신에 절대 자동 마운트되지 않아야 해요. `noexec,nodev`로 마운트하고 매니페스트를 수동으로 복사하세요.
- `mt-eval node manifest write <drive> --direction in|out`은 교차 전송 전에 드라이브의 모든 파일을 해시 처리해요. 수신 측의 `mt-eval node manifest verify`는 추가, 변경 또는 누락된 모든 것을 거부해요.
- 노드의 종이 문서나 노드 내 로그에 모든 교차 전송(날짜, 드라이브, 매니페스트 해시)을 기록해요. 지루해 보이는 것이 핵심이에요. 로그는 "다른 것이 유출된 적이 있는가?"라는 질문에 증거를 들어 대답할 수 있게 해줘요.

## 4. 키 보관 (M-of-N, 커뮤니티 보유)

밀봉된 테스트 세트는 유휴 상태에서 암호화돼요. 복호화하려면 원로 위원회, 언어 기관, 교육 기관 등 **커뮤니티가 선택한** 관리자가 보유한 키 셰어의 쿼럼(정족수)이 필요해요. 플랫폼은 셰어를 전혀 보유하지 않아요. Champollion은 밀봉된 세트를 복호화할 수 없으며, 단일 관리자 혼자서도 복호화할 수 없어요.

세리머니(오프라인에서 한 번 진행되며, 제공되는 도구가 이를 자동화함): `mt-eval node ceremony init`은 노드에서 세트 키를 생성하고 이를 N개의 셰어로 분할한 뒤(M개가 모이면 재구성되며, 그보다 적으면 아무것도 드러나지 않는 정보 이론적 공유 방식), 즉시 키를 0으로 초기화해요. `ceremony share`는 각 관리자의 셰어를 토큰용 파일과 인쇄 가능한 종이 백업으로 출력해요. `ceremony verify`은 분산된 복사본이 재구성됨을 증명하며, 이 과정에서 아무것도 영구 저장하지 않아요. `ceremony share --wipe-originals` then destroys the node's own copies. `mt-eval node seal`은 말뭉치를 세리머니의 공개 키로 암호화해요. 노드는 암호문과 내용이 없는 메타데이터 카드만 저장하며, 그 외에는 아무것도 저장하지 않아요. 그 이후로 평가를 실행하려면 관리자가 N개의 셰어 중 M개를 물리적으로 제시해야 해요(`node run-method --offline --share …`). 키는 **실행기의 잠긴 메모리에서만** 재구성되어 해당 권한이 부여된 단일 실행에 사용된 후 0으로 초기화되며, 디스크에 다시는 닿지 않아요. 모든 요청, 투표, 권한 부여 및 사용은 해시 체인 기반 로컬 원장(`node ledger verify`)에 추가되며, 쿼럼 없는 시도는 거부되는 *동시에* 기록돼요.

이 메커니즘에 대해 솔직하게 한 문장으로 설명하자면, 이는 다자간 컴퓨팅이 아니라 커뮤니티가 보유한 오프라인 머신의 메모리에서 재구성되는 Shamir 비밀 공유 방식이에요. 승인된 실행 중에 키는 커뮤니티가 물리적으로 제어하는 하드웨어에 조립된 상태로 잠시 존재해요. 이 방식이 방어하는 속성은 *디스크에 상주하는 키가 없고*, *쿼럼 없이는 실행되지 않으며*, *모든 사용 내역이 검사 가능한 원장에 체인으로 연결된다*는 점이에요. 키가 어디에서도 조립되지 않는 플랫폼 측 임계값 서명은 향후 작업으로 남아 있으며, 언급되는 모든 곳에 그렇게 표시되어 있어요.

교체 및 관리자 변경 시에는 세리머니를 다시 실행해요. N−M개 이상의 셰어를 분실하면 커뮤니티의 원본 복사본에서 세트를 다시 밀봉해야 해요. [소유권](/docs/network/sovereignty/data-sovereignty)은 애초에 우리가 가질 수 있는 것이 아니었기 때문에, 커뮤니티는 항상 자체 평문 원본을 유지해요.

## 5. 여기서 "증명됨(attested)"의 의미와 그렇지 않은 것

모든 평가는 **서명된 점수 매니페스트**를 생성해요. 여기에는 점수, 방식 패키지 해시, 말뭉치 체크섬, 추가 전용 감사 로그의 헤드에 대한 노드의 서명이 포함돼요. 노드의 게시된 공개 키를 가진 사람이라면 누구나 `mt-eval node verify-manifest <manifest> --pubkey <published .pub.json>` 명령을 통해 *이 노드*가 *정확히 이 입력*에 대해 *이 점수*를 생성했음을 검증할 수 있으며, 해시 체인 로그를 통해 몰래 이루어진 기록 수정도 감지할 수 있어요.

이것이 바로 **소프트웨어 증명**이에요. 기록의 무결성을 증명하며, v1에서 제공하는 기능이에요. 하지만 어떤 실리콘(하드웨어)이 실행을 수행했는지는 증명하지 **않아요**. 하드웨어 원격 증명(TEE)은 향후 작업이며 의도적으로 지원을 주장하지 않아요. v1에 대한 솔직한 보안 선언은 다음과 같아요. 주최자의 원칙(§3), 서명된 매니페스트, 그리고 커뮤니티의 물리적 머신 보관이 신뢰의 앵커(trust anchor)가 되며, 이는 주권 우선(sovereignty-first) 설계가 신뢰를 두고자 하는 바로 그 지점이에요.

## 6. 운영 루프

1. 경연을 발표하고, 노드의 공개 키와 개발 세트 임계값을 게시해요.
2. 온라인(일반 머신)으로 제출물을 접수하고, IN 매니페스트를 구성해요(`mt-eval node manifest write <drive> --direction in`).
3. IN 드라이브를 노드로 가져가서 해시를 검증해요(`node manifest verify`).
   import-scan (`node import-bundle`); queue methods.
4. 관리자가 셰어의 쿼럼을 제시하여 실행을 승인해요(§4 — `node run-method <id> --offline --share … --share …`). 밀봉된 세트는 실행기 내에서만 복호화돼요. 쿼럼이 없으면 실행되지 않으며, 시도 내역은 원장에 기록돼요.
5. 실행을 진행하고 점수를 계산하며, 세그먼트별 출력은 노드 측에 유지돼요.
6. 해체(Teardown): 작업 중인 평문을 삭제하고, 감사 로그를 추가하며, 매니페스트에 서명해요.
7. OUT 드라이브를 다시 가져와서 점수와 매니페스트를 게시해요. 누구나 이를 검증할 수 있어요(`node verify-manifest`).
8. 교차 전송을 기록해요. 드라이브는 전용으로 유지되고, 노드는 오프라인 상태를 유지해요.
