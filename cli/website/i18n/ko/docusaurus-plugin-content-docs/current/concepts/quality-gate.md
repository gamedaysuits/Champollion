# 품질 게이트

모든 번역은 디스크에 기록되기 전에 결정론적 검증 게이트를 통과해요. 품질 게이트는 일반적인 기계 번역 실패 모드를 잡아내요 — 조용한 폴백도 없고, 로케일 파일에 쓰레기 데이터가 기록되는 일도 없어요.

## 검증 검사

| 검사 | 감지 대상 | 게이트 라벨 |
|-------|----------------|-----------|
| **비어 있음/공백** | 모델이 빈 문자열 또는 공백을 반환함 | `[GATE] empty` |
| **원문 그대로 출력** | 모델이 원래의 영어 입력을 그대로 반환함 — 있는 그대로이거나 변형된 형태(악센트, 대소문자, 전각 문자)로, 전체 값 또는 하나의 복수형 형태로 | `[GATE] source-echo` |
| **ICU / 플레이스홀더 구조** | 번역된 변수, 복수형 키워드 또는 선택자, 누락된 `#` 또는 `%s` | `[GATE] icu` |
| **마크업** | 태그 열림, 닫힘 또는 중첩이 원문과 다름 | `[GATE] markup` |
| **플레이스홀더 옆 문장 분리** | 원문에는 없는 위치에서 플레이스홀더 바로 앞이나 뒤에 번역 결과가 문장 끝마침을 넣은 경우: `Take this medicine at {time}.` → `… sina. {time}.` | `sentence break beside a placeholder` |
| **환각 루프** | 반복되는 트라이그램(trigram) 패턴 (예: `"Qo' Qo' Qo'"`) | `[GATE] hallucination` |
| **길이 과도 팽창** | 출력이 원문보다 훨씬 김 | `[GATE] length` |
| **콘텐츠 삭제** | 출력이 원문에서 글자만 제거된 형태임 | `[GATE] content` |
| **문자 체계 준수** | 타깃 로캘에 맞지 않는 문자 체계 | `[GATE] script` |
| **서로 다른 입력에 동일한 출력** | 서로 다른 여러 원문 문자열에 대해 하나의 텍스트만 반환됨 (암기된 문장) | `[GATE] shared-output` |
| **ICU 복수형 범주** | 로캘에 필요한 복수형이 누락됨 | `[GATE] icu-plural` |

[`noTranslate`](/docs/getting-started/configuration#no-translate)로 선언된 키는 게이트에 도달하지 않아요. 원문에서 그대로 복사되므로 검증할 내용이 없기 때문이에요.

**Markdown 페이지도 블록 단위로 동일한 검사를 받아요.** 콘텐츠 폴더(`contentDir`, Docusaurus 문서)에서는 각 제목, 문단, 목록 항목, 표 셀이 개별적으로 검사되며, 각 front-matter 필드도 마찬가지예요. 검사항목은 위와 같아요: 비어 있음, 원문 그대로 출력, 환각 루프, 길이 과도 팽창, 콘텐츠 삭제, 문자 체계, 서로 다른 입력에 동일한 출력 등이에요. `## Feast` 같은 짧은 제목이 전체 문장으로 반환되면 동일한 텍스트의 앱 키와 마찬가지로 거부돼요.

거부된 블록은 **이유와 함께 한 번 더 요청돼요**. 모델에 무엇이 잘못되었는지, 그리고 작성된 그대로가 맞는 텍스트는 변경 없이 반환되어도 된다는 점을 알려줘요. 어떤 거부는 고정된 규칙만으로 판단할 수 없어요. 고유명사인 제목(`### BLEURT (Sellam et al., 2020)`), 참고문헌 목록 항목, 코드 표, 용어 설명 등은 작성된 그대로가 맞을 수도 있고, 번역을 빠뜨린 것일 수도 있어요. 블록이 변경 없이 반환되었거나 비라틴어 언어에서 라틴 문자로 유지되었을 때, 모델이 동일한 답변을 다시 제공하면 그 답변은 의도된 것으로 받아들여져요. 그 외의 모든 거부는 두 번째 답변에서 게이트를 확실히 통과해야 해요. 지침을 따르지 않는다고 선언된 엔드포인트(`"acceptsInstructions": false`)에는 다시 묻지 않으며, 첫 번째 답변이 두 번째 답변인 것처럼 평가돼요.

여전히 거부된 항목은 해당 페어의 `fallback` 메서드로 넘어가요. 이 메서드가 없다면, **해당 블록은 페이지에 마커가 추가되지 않은 채 원문 텍스트를 유지하고**, 캐시되지 않으며, 페이지의 lock 항목에 `pending:<hash>`으로 기록돼요. `status` 및 `verify` 명령은 이러한 페이지 목록을 보여주며, sync는 각 블록의 이름을 지정해요. 거부 내역은 저장되어 다음 일반 sync 실행 시 해당 블록을 동일한 모델에 다시 전송하지 않아요([거부된 Markdown 블록 및 front-matter 필드](#refused-markdown-blocks-and-front-matter-fields) 참조). 블록 내의 코드, 링크, 마크업은 별도로 보호되며, HTML 주석은 절대 전송되지 않아요. 다음과 같은 텍스트는 다시 묻지 않고 작성된 그대로 유지돼요:
- 짧은 이름(`## GitHub`, 인라인 코드, 따옴표, 괄호, `{#anchor}`을 제외하고 측정됨);
- 참고문헌 목록 항목 또는 하나의 블록에 들어 있는 전체 참고문헌 목록;
- 원문 자체에 포함되어 있는 전각 문자.

표는 파이프나 구분 기호 행이 아닌 각 셀 단위로 측정돼요. `verify`은 이미 디스크에 있는 블록을 동일한 방식으로 검사해요(단, sync가 원문에 대해 이미 수락하고 캐시한 내용과 정확히 일치하는 블록은 예외예요). 검사에 실패한 블록은 경고로 처리되어 `verify --strict` 실패로 이어지며, 복구 명령인 `champollion sync --pair en:fr --redo files:<page>`과 함께 표시돼요. sync도 동일한 파일에 대해 동일한 명령을 출력해요.

### 빈 값/공백

빈 문자열, 공백만 있는 값, 또는 `null`인 번역을 거부해요. 어려운 키에 대해 아무것도 반환하지 않는 모델을 잡아내요.

### 원문 그대로 반환

모델이 번역 대신 영어 원문 텍스트를 그대로 반환하는 경우를 감지해요. 짧은 문자열이나 프롬프트 지침이 부족할 때 자주 발생해요. 서로 다른 대상을 측정하는 두 가지 규칙이 적용돼요:

1. **정확한 복사본**(원문과 바이트 단위로 동일)은 거부돼요. 단, **길이가 짧고 대부분 ASCII인 값**(30자 이하, 80% 이상 일반 ASCII)은 예외예요. `"Blog"`, `"GitHub"`, `"npm"`은 영어로 유지되는 것이 정상이므로, 라틴 문자 타깃에서는 이러한 복사본이 허용돼요(`verify`에 원문 그대로 출력으로 표시됨). 비라틴 문자 타깃에서는 모델에 고유명사인지 한 번 확인 질문을 하며, 동일한 답변이 두 번 나오면 고유명사로 인정돼요. **이 예외는 길이에 관한 것이며, 정확한 복사본에만 적용돼요.**
2. **변형된 복사본** — 대소문자, 악센트, 띄어쓰기, 보이지 않는 문자 또는 호환용 형태(전각 문자, 합자)만 변경된 원문 — 은 아무리 짧더라도 원문에 문자를 포함하는 단어가 **3개 이상** 있는 경우 거부돼요(`{count}` 또는 `%s` 같은 플레이스홀더 및 마크업 태그는 단어로 계산되지 않음). `"Book an appointment"`(19자, 3단어) → `"Bóok án appóintment"`은 거부돼요. 반면 `"cafe"` → `"café"`(1단어)는 실제 번역이 영어와 악센트만 다를 수도 있으므로 허용돼요. 악센트가 정당하게 추가되는 더 긴 이름(`"Universite de Montreal"`)은 악센트가 들어간 표기를 보호된 용어로 선언하면 허용돼요.

두 규칙 모두 **각 복수형 형태**에도 동일하게 적용돼요. gettext의 `msgstr[n]` 복수형, ICU의 `{n, plural, …}` 분기, i18next의 `_one`/`_other` 키도 단수형 값과 동일한 규칙을 따라요. 예를 들어 러시아어 복수형에서 `few` 형태가 악센트가 붙은 영어로 반환되면 단수형과 마찬가지로 거부돼요.

변경 없이 유지되는 것이 맞는 더 긴 값(URL, 저장소 경로, 제품 식별자 등)은 게이트의 문제가 아니며 게이트를 조정한다고 해결할 수도 없어요. 올바른 답 자체가 원문 그대로이기 때문에 모델의 다른 어떤 출력도 잘못된 것이 돼요. 이러한 키는 [`noTranslate`](/docs/getting-started/configuration#no-translate)로 선언하면 파이프라인을 완전히 건너뛰어요. URL 형식의 값을 가진 키는 기본적으로 그렇게 처리돼요.

### 환각 루프

출력의 trigram(3자) 패턴을 분석해요. 어떤 trigram이 출력 길이 대비 임계값을 초과하여 반복되면 번역이 거부돼요. 이는 `"Qo' Qo' Qo' Qo' Qo'"`와 같은 비정상적인 출력을 잡아내요.

### 길이 팽창

출력 길이가 `maxLengthRatio × source length`(기본값: 4배)를 초과하는 번역을 거부해요(정확히 초과하는 경우에 해당하며, 정확히 4배인 번역은 통과함). 이는 짧은 입력에 대해 방대한 텍스트 덩어리를 생성하는 모델 환각을 잡아내요.

설정 파일의 `maxLengthRatio`를 통해 구성할 수 있어요.

### 콘텐츠 삭제

길이 과도 팽창의 반대 경우예요. 문자열에 대한 어휘를 모르는 모델은 번역할 수 없는 모든 글자를 삭제하고 원문의 구두점과 공백만 그대로 남겨둘 수 있어요:

```
"low-resource nmt · tokenizers · nêhiyawêwin"  →  "   ·   · êhiêi"
"the simple-builder approach"                  →  "  "
```

다른 검사로는 이를 잡아낼 수 없어요. 비어 있지도 않고, 원문 그대로도 아니며, 반복적이지도 않고, 원문 *길이*의 33%이므로 `minLengthRatio`도 무난히 통과해요.

이 검사는 구두점, 공백, 보이지 않는 서식을 제외한 원문과 출력 간의 **콘텐츠 문자**(문자와 숫자)를 비교해요. 하지만 밀도만으로는 규칙을 세울 수 없는데, 원래 압축적인 문자 체계도 정확히 같은 위치에 해당할 수 있기 때문이에요:

| 원문 | 출력 | 유지된 콘텐츠 | 판정 |
|--------|--------|------------------|---------|
| `low-resource nmt · tokenizers · nêhiyawêwin` | `   ·   · êhiêi` | 14% | **거부됨** |
| `Getting started` | `入门` | 14% | 수락됨 |
| `Frequently asked questions` | `常见问题` | 17% | 수락됨 |

첫 번째 사례를 잡는 임계값을 그대로 쓰면 중국어, 일본어, 한국어가 무조건 거부돼요. 둘을 구분하는 기준은 얼마나 많이 살아남았는가가 아니라 *그 문자가 어디서 왔는가*예요. 속이 빈 출력은 원문에서 문자를 삭제하여 만들어낼 수 있는 원문의 **부분수열(subsequence)**인 반면, 실제 번역은 원문과 본질적으로 문자를 거의 공유하지 않아요. 감지 플래그가 동작하려면 **두 신호가 모두** 필요하므로, 이 검사는 반복 감지기와 마찬가지로 필요조건이지만 충분조건은 아니에요.

`minContentRetention`(기본값 `0.35`)를 통해 페어별 또는 언어별로 설정할 수 있어요. 값을 높이면 검사가 더 엄격해지지만, 항상 부분수열 신호와 함께 나타날 때만 트리거돼요.

:::note[이는 어휘 신호이며, 품질 조절 다이얼이 아니에요]
특정 타깃 언어에서 이 검사가 반복해서 트리거된다면, 모델이 해당 텍스트에 대한 어휘를 모른다는 뜻이에요. 대개 폐쇄적인 어휘 체계를 가진 언어에서 전문 용어가 밀집된 짧은 문자열일 때 발생해요. 임계값을 완화하면 조용한 데이터 훼손이 복원될 뿐이며, 번역이 생성되는 것은 아니에요. 프롬프트나 코칭 데이터, 또는 페어를 수정해야 해요.
:::

### 스크립트 준수

언어 카드에 비라틴 문자로 기록된 로캘(아랍어, CJK, 키릴 문자 등)의 경우, 출력이 라틴 문자 전용이 아닌지 검증해요. 문자는 바이트가 아니라 **유니코드 문자 체계(Unicode script)** 기준으로 분류돼요. 악센트가 붙은 라틴 문자(`"Bóók"`)와 전각 라틴 문자(`"Ｂｏｏｋ"`)는 모두 라틴 문자이므로 러시아어로 통과할 수 없어요. 전각 라틴 문자는 CJK 타이포그래피(`"ＯＫ"`가 일상적인 일본어 표기인 경우)를 제외한 모든 타깃에서 거부돼요. 이는 변형된 영어에 불과하기 때문이에요. 기존 예외 규정은 그대로 적용돼요. 작성된 그대로 유지된 짧은 이름(앞서 언급한 이름 또는 라벨 질문), 선언된 보호된 용어, `noTranslate` 키(URL 포함)는 절대 이 검사에 걸리지 않아요.

이 검사가 *아닌 것*에 대한 두 가지 명확한 사항:

- 이 검사는 **`script:` 설정 필드에 의해 동작하지 않아요.** 해당 필드는 [문자 체계 변환](/docs/getting-started/configuration#script-conversion)을 위한 출력 정서법을 선택하는 용도이며, 게이트의 기대 기준은 언어 카드에서 가져와요.
- 이 검사는 항상 문자 체계 변환 *이전에* **모델이 출력하는 작업 문자 체계(working script)**를 검증해요. 문자 변환기를 사용하는 로캘(crk, sr, tlh 등)은 정상적으로 라틴 작업 문자 체계 출력을 생성하므로 이 검사에서 제외돼요. 변환(설정에서 선택한 경우)은 게이트 통과 이후에 이루어져요.

### 마크업

태그는 코드예요. 태그 이름별로 번역본은 원문과 동일한 개수의 태그를 열고 닫고 자체 종료해야 하며, 동일한 방식으로 중첩해야 해요(`<a>` 안의 `<b>`은 `<a>` 안에 그대로 유지됨). 형제 요소의 순서는 단어 순서에 따라 달라질 수 있어요. `"Please <strong>book</strong> now"` → `"Veuillez <strong>réserver maintenant"`는 거부돼요. 닫는 태그가 누락되면 페이지가 깨지기 때문이에요. 복수형 메시지에서는 각 형태를 번역 대상인 원문 형태와 비교해요. `verify`은 파일에 대해 동일한 검사를 실행해요.

### 플레이스홀더 옆 문장 분리

플레이스홀더는 런타임에 채워지므로, 번역에서 그 바로 옆에 문장 끝마침을 두면 독자가 보게 되는 내용이 달라져요. `"Take this medicine at {time}."` → `"… sina. {time}."`는 시간을 독립된 문장처럼 보여주게 돼요. 게이트는 원문에는 해당 위치에 기호가 없고 번역문의 문장 끝마침 개수가 원문보다 많을 때, 플레이스홀더 바로 **앞**에 문장 끝마침(`.`, `!`, `?`, 또는 다른 문자 체계의 기호: `。`, `？`, `।`, `؟`, `።`, `᙮` 등)을 두거나 플레이스홀더 바로 **뒤**에 텍스트가 더 이어지는데도 끝마침을 두는 번역을 거부해요. 문장의 끝으로 이동하기만 한 플레이스홀더(`"Shipped by {carrier} on {date}."` → `"Expédié le {date} par {carrier}."`)는 통과해요. 말줄임표, 소수점이나 파일명(`{host}.com`), 한 글자 약어(`"M. {name}"`)도 통과해요. 플레이스홀더 앞의 더 긴 약어(`"ca. {count}"`)는 문장 끝마침과 구별할 수 없으므로 마찬가지로 거부되며, 페어의 폴백이나 다시 표현된 답변이 이를 대신 처리해요. `verify`은 디스크의 동일한 값을 플래그로 지정하며, 다시 질문하는 `--redo` 명령을 함께 안내해요. ICU 복수형 및 select 메시지는 ICU 검사에 맡겨져요.

### 서로 다른 입력에 동일한 출력

학습용 문장을 암기한 모델은 모르는 문자열이 나왔을 때 해당 문장을 반환할 수 있어요. 예를 들어 앱 제목, "Contact the school", 뉴스레터 제목 및 그 헤딩에 모두 동일한 문장을 반환하는 식이며, 개별적으로는 위의 모든 검사를 통과할 수 있어요. 한 로캘의 실행 내에서 단일 번역이 **3개 이상의 서로 다른 원문 문자열**에 대한 답변으로 사용되고, 그 번역이 4단어 이상이거나 각 원문이 공통점이 거의 없는 2단어 이상인 경우, 해당 키들은 거부돼요(따라서 재시도 후 폴백이 이를 인계받음). 증거가 확실한 경우에는 **2개**의 서로 다른 원문 문자열로도 충분해요. 둘 다 2단어 이상이고, 단어의 절반 미만을 공유하며, 공유된 번역문이 4단어 이상인 경우예요(`"Thank you for coming!"` 및 `"Please bring the forms."`가 단 하나의 문장으로 답변된 경우). 이렇게 잡힌 문장은 해당 로캘에 대해 기억돼요. 이후의 sync에서 단 하나의 문자열에 대해서라도 이 문장이 다시 반환되면 거부되고, 이미 이를 제공했던 캐시 항목도 삭제되어 redo 시 캐시에서 가져오는 대신 모델에 다시 요청하게 돼요. 짧은 번역 하나로 수렴되는 동의어(`"OK"`/`"Okay"`/`"Sure"` → `"D'accord"`, `"Close"`/`"Dismiss"` → `"Fermer"`)는 허용되며, 여러 키에 동일한 원문 텍스트가 사용된 경우도 허용돼요. 해당 실행의 콘텐츠 파일에 포함된 Markdown 블록과 front-matter 필드도 포함되며, ICU 복수형이나 select 메시지의 각 분기도 마찬가지예요(복수형 메시지의 각 분기는 하나의 원문으로 취급돼요 — 수 굴절이 없는 언어는 각 분기에 동일한 텍스트를 작성하기 때문임). 출력 비교 시 대소문자, 구두점, Markdown 블록 마커는 제외되므로 `"S?"`, `"S."`, 제목 `# S`는 모두 동일한 출력으로 취급돼요. 계산에는 해당 로캘이 이미 디스크에 가지고 있는 내용과 캐시가 제공할 내용도 포함되므로(다른 도구에 의해 한 번에 하나씩 캐시된 문장은 캐시 단계에서 거부되어 작성되지 않음), sync마다 하나씩 추가되는 키도 잡아낼 수 있어요. `verify`은 디스크의 동일한 패턴에 대해 실패하며, MCP `translate` 도구는 호출 내에서 이를 거부해요.

### 물음표가 누락된 의문문

원문이 `?` 또는 `!`로 끝나는데 번역문이 그것으로도 끝나지 않고 해당 문자 체계에서 사용하는 해당 기호(`？`, `؟`, 그리스어 `;`, `¿…?`, `！` 등)로도 끝나지 않는 경우, `sync` 및 `verify`에서 경고를 표시해요. `"Where does it hurt?"`를 평서문으로 작성하면 평서문으로 읽히기 때문이에요. 어떤 언어들은 문장 부호 대신 단어나 불변화사(조사)로 의문문을 나타내므로 거부가 아닌 경고로 처리돼요. 이 경고에는 키 이름과 다시 요청하는 `--redo keys:<key> --fresh` 명령(캐시에 답변이 남아 있으므로 `--fresh` 옵션 포함)이 표시돼요.

## 실패 시 동작

1. 실패한 번역은 `[GATE]` 접두사, 키 이름, 이유, 값 미리보기와 함께 stderr에 기록돼요
2. 해당 키는 로캘 파일에 작성되지 **않아요**
3. 재시도 연쇄(retry cascade)가 동작해요(아래 참조)
4. 여전히 실패하는 경우 거부 내역이 **저장돼요**([거부된 키는 보류됨](#refused-keys-are-held-back) 참조)

```
[GATE] hero.title: source-echo — "Welcome to our platform"
[GATE] nav.about: hallucination — "À À À À À À À À"
```

## 피드백 재시도 및 재시도 연쇄

게이트에서 거부된 키는 **한 번의 피드백 재시도**를 거쳐요. 거부 이유가 프롬프트에 키별 컨텍스트로 주입돼요(낮은 temperature에서의 무작위 단순 재시도는 바이트 단위로 동일한 출력을 반환하기 때문이에요). 재시도가 통과하면 키가 작성되고 sync는 **성공(green)** 상태가 돼요 — 자체 치유된 게이트 거부는 실패가 아니며, 이것이 의도된 동작이에요. 재시도 후에도 여전히 실패하는 키는 건너뛰고 보고돼요(sync는 `2`로 종료됨).

재시도는 LLM, Google Translate, DeepL, 직접 연동 제공업체 등 페어 자체의 번역 메서드를 통해 실행돼요. LLM 메서드만 피드백을 읽으며, 실행 줄에 이 점이 명시돼요(`retrying with feedback` 또는 `asking once more (deepl takes no instructions…)`). `api` 엔드포인트는 (페어 또는 플러그인 매니페스트에서) `"acceptsInstructions": true`를 선언한 경우에만 피드백을 받아요. `false`을 선언한 엔드포인트(어차피 동일하게 답변할 `nmt-forge serve`과 같은 학습된 NMT 모델)에는 아예 다시 요청하지 않아요. 첫 번째 답변이 두 번째 답변인 것처럼 평가되며, 여기서 거부된 항목은 페어의 폴백으로 넘어가요. 재시도는 번역 메모리(Translation Memory) 히트 항목에도 적용돼요. 게이트가 거부한 캐시 값은 제거되고 동일한 실행 내에서 다시 번역되므로 오염된 캐시가 자체적으로 치유돼요.

### 거부된 키는 보류됨

거부 내역은 키의 **현재 원문 텍스트**와 거부된 답변을 생성한 **메서드 및 모델**에 대해 `.champollion.lock`에 키별로 저장돼요. Docusaurus UI 문자열(`i18n/<locale>/code.json` 및 플러그인의 JSON 파일)도 파일 및 id별로 동일한 규칙을 따라요. 다음 일반 `sync` 실행 시 해당 키를 동일한 모델에 다시 보내지 않으며(동일한 답변에 요금만 부과될 뿐임), 몇 개가 보류되었는지와 진행 방법을 알려줘요:

- 다시 요청하기: `champollion sync --redo keys:<key>` (또는 `--redo all`, `--fresh`) — 키 이름을 지정하는 것은 명시적 재시도를 의미해요;
- 다른 방법으로 채우기: 페어에 `"fallback"` 메서드를 추가하거나(페어 자체 메서드가 거부한 키에 대해 요청됨), 작성된 그대로 유지되는 경우 `noTranslate`에 키를 등록하거나, 파일에 직접 번역을 수동으로 작성해요.

보류된 키는 번역되지 않은 상태이므로, 채워질 때까지 sync가 `2`로 종료돼요. 원문 텍스트, 모델 또는 메서드를 변경하면 보류 상태가 해제돼요(거부는 해당 모델의 해당 텍스트에 대한 것이었기 때문임). 캐시는 여전히 읽혀요 — 보류 처리는 무료 조회가 아닌 유료 호출을 중단시키는 것이 목적이기 때문이에요. redo가 완료하지 못한 키가 유일한 예외이며, 아래에서 설명해요.

### 거부된 Markdown 블록 및 front-matter 필드

콘텐츠 파일(`contentDir`, Docusaurus 문서)에도 동일한 규칙이 적용돼요. 게이트가 거부한 블록이나 front-matter 필드는 블록의 **현재 원문 텍스트**와 거부된 답변을 생성한 **메서드 및 모델**에 대해 `.champollion-content.lock`에 페이지, 블록, 로캘별로 저장돼요. 블록은 원문 텍스트로 식별되므로 해당 문단을 수정하면 보류 상태가 해제돼요. 다음 일반 `sync` 실행 시 동일한 모델에 다시 전송하지 않으며, 어떤 페이지에서 몇 개의 블록과 필드가 보류되었는지 알려줘요:

- 보류된 블록은 채워질 때까지 마커 없이 페이지의 원문 텍스트를 유지하며, 페이지의 나머지 부분은 정상 작성돼요;
- 보류된 front-matter 필드도 같은 방식으로 원문 텍스트를 유지하며, 페이지의 나머지 부분은 정상 작성돼요;
- 전체 페이지 단위로 번역된 페이지(`contentSegmentation: "page"`)는 답변이 보호된 블록을 손상시키거나 페이지를 비워버리는 경우 페이지 전체가 거부돼요. 본문 텍스트를 기준으로 저장되며 전체가 보류돼요. 채워질 때까지 작성되지 않고 아무것도 전송되지 않아요. 본문을 수정하거나 블록 분할 세그먼테이션으로 전환하면 보류가 해제돼요.

이전 버전의 게이트에서 발생한 거부는 자동으로 해제돼요. 검사가 완화되면 이전에 거부되었던 항목은 redo 없이도 다음 sync에서 다시 요청돼요.

우선순위는 키의 우선순위와 동일해요:

1. redo 대상으로 지정된 페이지는 항상 전송돼요: `champollion sync --redo files:<page>`, `--redo content`(모든 페이지), `--retranslate`, 또는 `--fresh` 아래의 모든 항목.
2. 그렇지 않은 경우 거부된 블록이나 필드는 보류돼요. 페어에 해당 항목을 거부한 적이 없는 `fallback` 메서드가 있다면, 페어 자체 메서드 대신 폴백에 요청돼요.
3. 모델이나 메서드를 변경하면 보류가 해제되며, 블록의 원문 텍스트를 수정해도 해제돼요.

캐시를 항상 먼저 읽으므로 보류 처리는 무료 조회가 아닌 유료 호출을 방지해요. 다른 방법으로 채워진 블록은 기록에서 삭제돼요. 폴백, 캐시 또는 번역본에 사용자가 직접 작성한 문단(콘텐츠 폴더는 수동으로 작성된 문단을 유지함)으로 채워지는 경우예요. 보류된 블록이나 필드는 번역되지 않은 상태이므로, 채워질 때까지 sync가 `2`로 종료돼요. 이번 실행 중에 게이트에서 거부된 블록도 마찬가지예요. 드라이 런(dry run)을 실행하면 실제 실행에서 보류될 항목 목록을 보여줘요.

### 완료되지 못한 redo

`--redo all`, `--redo keys:` 또는 모델 전환(`--redo all --fresh-on-model-change`)으로 인해 키-값 파일의 키가 번역되지 않은 채로 남으면, `.champollion.lock`에 **대기 중(pending)**으로 기록돼요. 그리고 다음 일반 `sync` 실행 시 모델에 이를 다시 한 번 요청해요 — 캐시가 아닌 모델에서 가져와요(redo의 목적이 새 모델의 텍스트를 얻는 것이었기 때문이에요). `champollion status` 명령이 이 목록을 보여줘요. 이 재시도마저 거부되면 키는 대기 상태로 유지되고(status에 표시됨) 다른 거부된 키와 마찬가지로 보류돼요. 우선순위 순서는 다음과 같아요: `--redo`/`--fresh`로 지정된 키는 항상 전송됨; 대기 중인 키는 한 번의 재시도를 거침; 거부된 키는 보류됨. Docusaurus UI 문자열에는 대기 재시도가 없어요. redo 시 거부되면 콘텐츠 블록과 마찬가지로 다음 일반 sync에서 보류돼요.

이와 별도로, 전체 배치가 실패하는 경우(JSON 파싱 오류 등) Champollion은 배치 크기를 점진적으로 줄이면서 재시도해요:

```
Full batch (80 keys) → parse error
  └→ Half batch (40 keys) → 2 failures
      └→ Individual keys (1 each) → isolates the 2 problem keys
```

재시도 예산은 `maxRetries`(기본값: 3, 언어별 구성 가능)로 제한돼요. 이는 지속적으로 실패하는 키에 대한 토큰 비용 폭주를 방지해요.

재시도를 모두 소진하면 문제 키들이 기록되고 건너뛰어져요. 사용할 수 있는 답변을 받지 못한 키(응답에서 누락됨)는 다음 `sync` 실행 시 다시 요청돼요. 게이트가 거부한 키는 위와 같이 보류돼요.

## 프롬프트 캐싱

시스템 메시지(레지스터, 문법 규칙, 스타일 노트)는 사용자 메시지(번역할 키)와 분리돼요. 이 분리는 의도적이에요:

- 시스템 메시지는 주어진 로케일에 대해 **배치 전반에 걸쳐 동일해요**
- Anthropic과 Google 같은 제공업체는 반복되는 시스템 메시지를 캐싱해요
- 결과적으로 첫 번째 배치는 전체 토큰 비용을 지불하지만, 이후 배치는 사용자 메시지에 대해서만 비용을 지불해요

이는 배치가 많은 프로젝트의 토큰 비용을 크게 줄일 수 있어요.

## ICU MessageFormat 검증

`integrity` 명령은 ICU MessageFormat 복수형 패턴을 CLDR 복수형 규칙과 대조하여 검증해요. 원본 파일이 다음과 같은 ICU 구문을 사용하는 경우:

```json
"items": "{count, plural, one {# item} other {# items}}"
```

Champollion은 번역된 버전이 대상 로케일에 필요한 모든 복수형 카테고리를 포함하는지 확인해요. 예를 들어, 아랍어는 `one`과 `other`만이 아니라 여섯 개의 카테고리(`zero`, `one`, `two`, `few`, `many`, `other`)가 필요해요.

### 번역에서 제공되지 않은 복수형 형태

프롬프트에는 타깃 언어의 CLDR 범주가 명시돼요. 일반적인 개수(0부터 1000까지의 개수 — 러시아어의 경우 2, 3, 4에 해당하는 `few` 및 0, 5, 6에 해당하는 `many`)에 언어가 사용하는 복수형 형태가 누락되어 반환되면, 게이트는 누락된 형태와 해당 형태가 적용되는 개수를 명시하여 모델에 한 번 더 요청해요. 두 번째 답변에서도 누락되어 있으면 그대로 수락되며, 세 번째로 묻지 않고 도구가 임의로 채워 넣지도 않아요. 이후 sync는 다음과 같이 동작해요:

- 각 키와 누락된 형태, 그리고 다시 요청하는 명령(더 강력한 `--model`가 도움이 되는 `sync --redo keys:… --fresh`)을 안내하며 경고해요;
- `msgfmt`이 모든 `msgstr[n]`을 필요로 하는 gettext 카탈로그에서는 누락된 형태를 `other`의 복사본으로 작성하고 해당 항목에 `# champollion:` 번역가 주석을 표시해요(Poedit 및 Weblate에 표시되며, `verify`도 캐시 없는 CI 환경에서 이를 읽음);
- ICU 파일(next-intl, ARB)에서는 메시지를 받은 그대로 작성해요. 앱은 해당 개수에 대해 `other` 형태를 표시해요.

이러한 메시지는 번역 완료된 것으로 처리되지 않아요. 이후 다른 메서드나 모델(예: 로컬 모델 실행 후 CI의 호스팅 모델처럼 아직 해당 메시지를 처리하지 않은 모델)로 sync를 실행하면 캐시(불완전한 답변이 들어 있음)가 아닌 모델에 다시 요청하며, 비용 예측에도 반영돼요. `sync --redo gaps`은 누가 남겼든 관계없이 이러한 모든 메시지에 대해 다시 요청해요. 새 답변에서도 해당 형태가 누락된 경우 메시지는 그대로 유지되며(카탈로그에 주석 표시됨), `.champollion.lock`에 어떤 환경 설정이 해당 형태 없이 답변했는지 기록하여 동일한 텍스트에 대해 다시 묻지 않도록 해요([CI 가이드](/docs/guides/ci-cd#plural-gaps)).

`verify`은 두 경우 모두 복구 명령과 함께 보고해요. 1000을 초과하거나 분수에서만 사용되는 형태(1,000,000에 사용되는 프랑스어 및 스페인어 `many`)는 경고가 아닌 안내(info) 행으로 표시돼요. 기계 번역 엔진(DeepL, Google 등)에는 어떤 형태를 작성할지 지시할 수 없으므로 해당 답변은 재시도되지 않고 보고만 돼요. i18next 파일의 경우 원문에 없는 각 형태(영어에서 프랑스어로 번역 시 `count_many`)는 별도의 키가 되며, `_other` 텍스트로부터 번역돼요. LLM에는 해당 형태가 요청되고 sync에 그렇게 표시되며, 기계 번역 엔진의 경우 해당 값이 `other` 형태를 담고 있다고 표시돼요.

`champollion integrity`를 실행하여 모든 로케일에서 복수형 완전성을 확인하세요.

## 용어 강제

사전이 있는 코칭된 쌍의 경우, champollion은 번역 후 용어 검사를 실행해요. 품질 게이트를 통과한 후, LLM이 실제로 필요한 사전 용어를 사용했는지 검증해요.

```
[TERM] en→fr: 2 term violation(s)
  • hero.title: "dashboard" → expected "tableau de bord" but got "panneau de contrôle"
```

용어 위반은 **차단 오류가 아니라 경고예요**. 번역은 여전히 디스크에 기록돼요. 이는 의도적이에요 — LLM이 대안을 선택한 정당한 이유(맥락, 문법)가 있을 수 있고, 용어 불일치로 차단하는 것이 도움보다 해가 될 수 있기 때문이에요.

위반을 수정하려면 코칭 사전을 업데이트하거나 로케일 파일을 수동으로 편집하세요.
