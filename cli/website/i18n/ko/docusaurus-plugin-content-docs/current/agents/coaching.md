# 사람들 안내하기

레일이 측정하고, 여러분이 전달해요. 사람들이 자신의 번역기에 대해 듣는 내용의 대부분은 여러분을 통해 전해지므로, 어떻게 말하느냐도 작업의 일부예요. 이 페이지에서는 말하는 방법을 다뤄요. 라운드 보고서에 무엇이 담겨 있는지, 어떻게 전달할지, 시간을 어떻게 요청할지, 어떤 단어를 사용할지 안내해요.

기본 규칙은 [계약](/docs/agents/contract) §5에 나와 있어요. 사실만을 말하고, 모든 주의 사항을 있는 그대로 전하며, 품질이 아니라 과정을 약속하고, 모든 수치에는 단위와 측정 대상 데이터 세트를 함께 밝혀야 해요.

## 라운드 보고서

각 개선 라운드는 `champollion improve report`(여정의 `improve-report` 단계, 모드 `auto`)으로 끝나요. 이 과정에서 `improve/round-<k>/report.json` 파일이 작성되고 네 가지 부분이 출력돼요. `--json` 명령어도 동일한 객체를 출력해요.

| 필드 | 내용 |
|---|---|
| `round` | 진행 중인 라운드: forge가 평가한 라운드보다 1 큰 값 |
| `progress` | 순서대로 표시되는 줄: 화자의 채점 추세, 각 라운드의 채점(다른 모델의 초안이 섞인 시트의 라운드라면 블라인드 비교가 뒤따름), 개발 세트에 대한 각 라운드의 판정 |
| `checks` | 숫자가 보여줄 수 있는 것과 보여줄 수 없는 것에 대한 경고 |
| `projection` | 훈련 문장 수가 두 배가 될 때마다 계산하여 '제대로 작동하는' 수준에 도달하려면 문장이 얼마나 더 필요한지에 대한 대략적인 추정치와 범위, 또는 추정치가 없는 이유, 또는 두 라운드의 채점 전에는 `null` |
| `projection_numbers` | 동일한 추정치를 숫자로 표시: `more_sentences`, `range`(훈련 문장 `[fewest, most]`개, 검증을 통해 범위를 좁힐 수 없을 때는 `most`가 `null`임) 및 `speaker_hours` — 또는 예측치가 없을 때는 `null` |
| `actions` | 다음에 해야 할 한 가지에서 네 가지 작업 |

라운드에서 보관하는 기록, 즉 라운드당 화자의 `marks.json` 및 forge의 `improve-compare` 판정 결과만 읽으며, 개수와 백분율만 출력하고 문장은 절대 출력하지 않아요.

### 각 줄의 의미

**화자의 채점 — 가장 중요한 척도.** 라운드마다 사용 중인 모델이 가족들이 작성한 문장의 초안을 작성하고, 화자는 각 초안을 `Y`(맞음), `N`(틀림, 올바른 표현 포함) 또는 `?`(불확실)로 채점해요. 맞은 비율은 95% Wilson 신뢰구간과 함께 `Y` 또는 `N`로 채점된 초안을 기준으로 계산돼요.

> 라운드 1: 화자가 새 문장 초안 24개 중 9개를 맞음으로 채점함 — 38%(95% 범위 21%–57%).

이 문장들은 새로운 문장들이며 — 어떤 모델도 이를 학습하기 전에 초안을 작성했으므로 — 표본 외(out-of-sample) 측정치가 됩니다. 시트에 다른 모델의 초안이 섞여 있는 라운드에서는, 이 개수는 현재 사용 중인 모델의 행에만 해당해요. 다시 표시된 행(아래 참조)은 여기에 절대 포함되지 않아요.

**다시 표시된 행.** 라운드 2부터는 열 행 중 한 행 정도가 화자가 이전 시트에서 이미 표시했던 초안으로, 표시가 지워진 채 다시 제공돼요. 시트 상단에는 다음과 같이 안내되어 있어요 — *"아래 몇몇 행은 이전 시트에서 의도적으로 다시 가져온 행입니다. 마치 새로운 문장인 것처럼 새로 표시해 주세요. 표시가 얼마나 일치하는지를 통해 신뢰도를 알 수 있습니다."* — 그리고 어느 행인지는 절대 알려주지 않아요. `improve marks`에는 *"다시 표시된 행: 화자가 J개 중 A개를 이전과 동일하게 표시함(P%)"*이라는 내용과 함께 각 방향으로 바뀐 횟수가 출력돼요. 이 행들은 해당 라운드의 비율에 절대 포함되지 않으며 다시는 학습되지 않아요. 화자의 시간은 행당 약 10초 정도 소요돼요([측정](/docs/agents/measurement#the-speakers-marks)).

**블라인드 비교.** 시트 초안 중 무작위로 절반을 두 번째 모델이 표기 없이 작성하고, 화자는 어느 것이 어느 모델인지 모른 채 둘 다 평가해요([측정](/docs/agents/measurement#the-speakers-marks)). 두 번째 모델은 사용되지 않았을 때는 가장 최신 모델이고, 모델 승급 후 다음 방문 때는 새 모델이 대체한 이전 모델이에요. 보고서에 다음과 같은 줄이 추가돼요.

> 라운드 2: 블라인드, 새 문장 대상: 사용 중인 모델은 12개 중 5개(42%) 맞음으로 채점됨, 더 새로운 모델(미사용)은 12개 중 7개(58%) 맞음으로 채점됨 — 24개 문장에서 뚜렷한 차이 없음.

승급 후에는 *"마지막으로 도입된 모델은 …개에서 맞음으로 채점됨, 대체된 모델은 …개에서 맞음으로 채점됨"*과 같이 표시돼요. 결과는 세 가지 방식 중 하나로 끝나요(유의수준 5%의 두 비율 검정): 더 새로운 모델의 경우 *더 새로운 모델이 가족에게 필요한 문장에서 뚜렷하게 더 나음* 또는 *사용 중인 모델이 뚜렷하게 더 나음*; 승급 후에는 *새 모델이 가족에게 필요한 문장에서 뚜렷하게 더 나음* 또는 *대체된 모델이 뚜렷하게 더 나았음 — 새 모델은 가족에게 필요한 문장에 도움이 되지 않음*; 혹은 *N개 문장에서 뚜렷한 차이 없음*. 한 모델의 채점된 행이 너무 적으면 *"비교하기에 한 모델의 평가된 행 수가 너무 적음"*이라고 표시돼요.

**추세.** 보고서는 다음 세 가지 조건이 모두 충족될 때만 상승을 *실질적인 진전*이라고 불러요.

- 마지막 라운드의 범위가 첫 번째 라운드의 범위보다 완전히 높은 경우(마지막 라운드의 하한이 첫 번째 라운드의 상한보다 높은 경우)
- 중간에 한 라운드의 모델이 실제 사용에 투입된 경우 — 사람들이 선택함(forge의 `export` 및 `choose` 기록): **better** 판정 후 사람들의 동의가 있었거나, 화자의 블라인드 채점을 거쳤거나, 직접 선택한 경우입니다. **better** 판정 하나만으로는 적용되지 않아요. 그리고
- 같은 방문에서 블라인드 방식으로 채점했을 때, 화자가 새 모델을 이전 모델보다 분명히 더 자주 맞았다고 표시한 경우(각 승격 후 검사를 취합한 결과, 5% 유의수준의 두 비율 검정).

세 번째 조건이 있는 이유는 화자의 평가 기준이 달라질 수 있기 때문이에요. 라운드가 지날수록 너그러워지는 화자는 모든 비율을 올려놓지만, 한 번의 방문 안에서는 두 모델 모두에 똑같이 영향을 미쳐요. 초안의 10%를 잘못 평가하고 라운드가 지날수록 너그러워지는 화자를 가정한 시뮬레이션에서, 모델이 개선될 수 없는 1,600건의 보고서 중 연습 세트가 우연히 잘못 판단하여 승격시킨 106건이 실제 진전으로 기록되었어요. 반면 블라인드 확인을 거쳤을 때는 3건에 불과했고, 연습 세트가 30문장에서 시작하는 실행을 포함하여 50문장 하한선과 화자의 판정을 두고 다시 실행했을 때도 1,600건 중 최대 3건에 그쳤어요.

승급은 있었지만 이 검증을 거치지 않은 상승은 *아직 실질적인 진전으로 집계되지 않음: 초안을 채점하는 관대함의 정도도 달라졌을 수 있음*으로 출력돼요(검증 수치와 함께 표시되거나 다음 시트에 두 모델의 초안이 섞여 나온다고 안내됨). 동일한 모델을 계속 사용하는 상황에서의 상승은 *진전으로 집계되지 않음*으로 출력돼요. 모델이 아니라 문장이나 채점이 달라진 것이기 때문이에요. 신뢰구간 범위 내에서의 상승은 *상승했으나 불확실성 범위를 아직 벗어나지 못함*으로 출력돼요.

**개발 세트 판정.** Forge는 동일한 개발(연습) 문장에서 새 모델과 사용 중인 모델을 문장별로 비교해요.

> 라운드 1: 동일한 50개의 연습(dev) 문장에서, 현재 사용 중인 모델의 22.0에 비해 새 모델의 chrF++(0–100, 확인된 번역과의 일치도) 점수는 24.1 — 측정 가능한 변화 없음: 사용되지 않음(50문장에서는 약 5.8점 이상의 차이가 나야 신뢰할 수 있게 나타나요).

줄의 끝부분이 어떻게 표시되는지는 판정과 사람들이 해당 라운드의 모델을 선택했는지 여부(forge의 `export` 및 `choose` 기록)에 따라 달라져요. 판정 결과만으로는 아무것도 실제 사용에 투입되지 않아요.

| 판정 | 선택되지 않음 | 선택됨 |
|---|---|---|
| **better** | *측정 가능할 정도로 더 나음: 사용에 투입되지 않음 — 사람들이 선택하지 않음* | *측정 가능할 정도로 더 나음: 사용에 투입됨* |
| **worse** | *측정 가능할 정도로 더 나쁨: 사용되지 않음* | *측정 가능할 정도로 더 나쁨 — 사용에 투입됨 …* |
| **no-change** | *측정 가능한 변화 없음: 사용되지 않음* | *측정 가능한 변화 없음 — 사용에 투입됨 …* |
| **too-few** | *판단하기에는 연습 문장이 너무 적음(50개 미만): 화자의 블라인드 채점으로 결정* | *판단하기에는 연습 문장이 너무 적음(50개 미만) — 사용에 투입됨 …* |

"사용에 투입됨 …"의 끝은 forge에 해당 모델에 대한 `clear: newer`(`improve-speaker`) 화자 판정이 있을 때는 *화자의 블라인드 채점으로*로 끝나고, 그렇지 않으면 *사람들의 직접 선택으로*로 끝나요. `champollion improve status`에서도 같은 표현을 써요. 각 라운드의 줄 끝에는 *"· 연습(dev) 문장에서의 새 모델: …"*처럼 표시돼요. 판정 규칙은 [측정](/docs/agents/measurement#comparing-two-models)에서 확인할 수 있어요.

**검증.**

- *과적합.* 사용 중인 모델의 dev chrF++가 여러 라운드에 걸쳐 3포인트 이상 상승했는데(마지막 라운드의 새 모델은 커뮤니티 사람들이 선택한 후에만 포함돼요) 화자의 정답 비율 상승이 2포인트 이하인 경우, 보고서에는 이러한 상승이 연습 문장 덕분일 수 있으며, 화자의 표시를 신뢰하라고 안내해요.
- *상승을 확인하기에 너무 작은 dev 세트.* dev 세트가 안정적으로 보여줄 수 있는 최소 차이가 3 chrF++ 포인트보다 크거나(혹은 알 수 없음, 50문장 미만인 경우), 보고서에서는 "측정 가능한 변화 없음"이 dev 세트의 한계일 뿐 해당 라운드가 아무런 성과가 없었다는 증거는 아니라고 안내해요.
- *표시를 얼마나 신뢰할 수 있는지.* 모든 라운드에 걸쳐 다시 표시된 행이 10개 평가되면 다음과 같이 안내해요: *"화자가 다시 표시된 행 J개 중 A개를 이전과 동일하게 표시했습니다(P%): 약 E%의 표시는 무작위로 다른 방향으로 바뀌며, 이는 정답으로 표시된 모든 비율을 50% 쪽으로 끌어당깁니다 — 추정치에는 이 점이 반영되어 있습니다."* 이전에 틀렸던 초안이 이제 맞은 것으로 표시된 경우가 반대의 경우보다 확실히 더 많을 때(5% 유의수준의 부호 검정, 6회 이상 바뀜), *"채점이 더 너그러워지고 있을 수 있으며, 이는 비율 상승만으로는 드러나지 않습니다"*라는 문구가 추가돼요. 10개 미만인 경우: *"지금까지 다시 표시된 행 N개 평가됨 — 화자 본인의 표시 오차는 10개부터 추정됩니다."*

**추정치.** 상승이 진정한 진전일 때(위의 세 가지가 모두 충족될 때) 그리고 정답 비율이 아직 80% 미만일 때만 생성돼요 — 80%는 가족에게 필요한 문장에서 모델이 *작동한다*고 가드레일이 판단하는 기준이에요. 학습 곡선은 학습 문장 수가 두 배로 늘어날 때마다 대체로 일정한 폭으로 상승하므로, 화자가 이전 모델을 대체하는 새 모델을 블라인드 방식으로 교차 확인한 결과(두 모델의 학습 쌍 모두 기록됨)로부터 그 단계를 읽어내고, 정답 표시율 80%에 도달하려면 학습 문장이 얼마나 더 필요한지를 범위와 함께, 그리고 문장당 약 70초(작성 1분, 표시 10초) 기준으로 화자의 소요 시간과 함께 제시해요.
이 범위는 교차 확인이 허용하는 범위(95%)를 다루며, 다시 표시된 행이 10개 평가되고 나면 이 화자 본인의 표시에서 "진정으로 80% 맞음"이 어디에 위치할 수 있는지도 포함해요. 이때 안내 문구에는 *"실제로 80% 맞는 초안이 화자의 표시에서는 약 T%의 비율로 맞게 표시될 수 있습니다 — 범위에 이 점이 반영되어 있습니다"*라고 나와요. 그 전에는 *"(화자 본인의 표시 오차는 아직 반영되지 않았습니다: 다시 표시된 행이 아직 충분히 평가되지 않았습니다.)"*라고 표시돼요. 추정치 자체는 단순하게 80% 기준을 유지해요. 개수는 두 자리 숫자로 반올림돼요. 교차 확인으로 범위를 한정할 수 없을 때는 *"얼마나 더 필요할지 아직 알 수 없습니다"*라고 표시돼요. 그렇지 않은 경우에는 왜 추정치가 없는지 이유를 알려줘요 — 예를 들어 *"화자의 블라인드 확인에서 새 모델이 이전 모델을 이겼다는 결과가 아직 나오지 않았으므로, 상승한 것은 모델이 아니라 표시 방식일 수 있습니다"*와 같아요. 언제나 대략적인 추정치임을 분명히 밝혀 주세요. 보고서도 그렇게 하고 있어요.
시뮬레이션에서 이 추정치는 라운드당 400문장일 때 69~78%, 800문장일 때 53~56%의 확률로 실제 개수의 2배수 오차 이내에 들었고, 실제 개수가 범위 내에 들어간 비율은 각각 89~94%와 76~80%였어요(라운드당 800문장일 때, 범위에 화자의 표시가 반영되기 전에는 51~54%). 이를 대체하기 전의 직선 추정은 400문장에서 5%에 불과했어요. 화자의 표시 오차를 근거로 모델이 "이미 작동 중일 수 있다"고 절대 말하지 마세요. 보고서에서도 그렇게 하지 않는데, 시뮬레이션에서 그 안내는 맞을 때마다 2~3번꼴로 틀렸기 때문이에요.

**해야 할 작업.** 우선순위에 따라 최대 네 가지예요: 이번 라운드의 시트를 평가하거나, 아직 부족한 문장을 작성하기(라운드당 20개); 블라인드 비교 결과 새 모델이 명확히 더 나은 것으로 나타났을 때, *"연습 세트에서는 드러나지 않았지만 이번 라운드가 실제로 도움이 되었음"*을 알리고 — 계속 진행하면서 연습 세트를 늘려 다음 판정에서 드러나도록 하기; 화자가 승격 전 모델을 명확히 더 낫다고 평가했을 때는 사람들에게 이전 모델로 되돌릴지 묻고 연습 세트를 그들이 필요로 하는 문장에 더 가깝게 만들기; 라운드의 향상 폭을 확인하기에 연습 세트가 너무 작고 200문장 미만일 때 연습 세트 늘리기(*"각 시트의 문장 2개 중 1개는 초안이 없어요 — 화자가 실제 쓰이는 말을 적으면 연습 세트에 추가돼요(현재 31개; 50개가 되면 라운드 판정이 가능해지고, 200개가 되면 약 3점의 향상 폭이 드러나요)"* — 50문장부터는 "4개 중 1개"); 성과 없는 두 라운드를 거친 후 취할 조치(아래 참조); 화자가 할애할 수 있다고 한 시간이 너무 적어 보인다는 안내; 그리고 정답률 하한선이 70%에 이르면 잠긴 테스트 세트에 대한 확인 — 단, 예측치를 먼저 작성한 후에 진행해요.

**향상이 없는 2개 라운드** — 최근 두 번의 판정이 모두 **no-change** 또는 **worse**이고(판단 불가인 **too-few** 라운드는 어느 쪽으로도 판단하지 않으므로 포함되지 않아요), 그사이에 사용에 투입된 모델이 없는 경우예요. forge는 더 강력한 모델을 제안할 때도 같은 방식으로 계산해요. 연습 세트가 라운드의 일반적인 향상을 감지할 수 있는 경우, 권장 조치에 *"이 연습 세트에서 확인할 수 있는 향상(약 X chrF++점 이상)이 없는 2개 라운드: 라운드가 그보다 적게 향상되고 있거나 전혀 향상되지 않는 것일 수 있으며, 어느 쪽인지는 알 수 없습니다. 더 빠르게 나아가는 방법: 컴퓨터가 학습할 수 있는 사양일 때 레일이 제안하는 더 강력한 모델을 사용하거나, 모델이 틀리는 유형의 문장을 더 많이 추가하는 것입니다."*라고 표시돼요(X는 판정에서 나타나는 가장 작은 차이예요). 감지할 수 없는 경우에는 계속 진행하라고 안내해요. 문장을 더 추가해도 도움이 되지 않는다고 말하거나 암시하지 마세요. 곡선의 정상 부근에서는 한 라운드가 약 0.5 chrF++점 정도 향상되는데, 이는 연습 문장 200개로 감지할 수 있는 수준 미만이에요. 시뮬레이션 라운드에서 이전 문구인 "같은 내용을 더 추가해도 도움이 되지 않을 수 있습니다"는 모델이 실제로 향상되고 있었음에도 불구하고 1,200개 보고서 중 98개에서 출력된 바 있어요.

### 결과를 전달하는 방법

1. **진전 상황 먼저.** 화자의 평가에서 달라진 점을 첫머리에 두세요.
2. **모든 숫자는 단위 및 대상과 함께.** "38%"라고만 하지 말고 "화자가 확인한 신규 문장 24개 중 9개가 맞았음 — 38%"처럼 쓰세요. "24.1"이라고만 하지 말고 "연습 문장 50개에서 100점 만점 중 chrF++ 24.1점"처럼 쓰세요. 범위는 도구가 확신하는 정도를 뜻하며 두 개의 결과를 뜻하는 것이 아니에요: "21%에서 57% 사이 — 24문장으로는 도구가 이보다 더 확신할 수 없어요".
3. **확인 사항은 명확하게.** 보고서에 경고가 있다면 무엇을 경고하는지 분명히 알리세요.
4. **다음 단계는 직접 할 수 있는 행동으로.** 각 작업을 해당 파일 이름과 함께 사람들에게 전하는 문장으로 바꾸세요.
5. **모든 주의 사항은 있는 그대로 전달하세요.**

**측정된 결과를 격려하기.** 맞음으로 채점된 초안, 범위를 넘어선 상승, 새로 도입된 모델 등에 대해 따뜻하게 말씀해 주세요. 첫 번역은 축하할 가치가 있어요. 보고서에서 진전이라고 부르지 않는 수치는 절대로 축하하지 마세요.

**"측정 가능한 변화 없음" — 명확하고 친절하게.** 이번 라운드가 헛수고였다는 뜻이 아니에요. 그 의미를 그대로 전하세요. 이 정도 수의 연습 문장으로는 대략 이 정도 크기의 차이만 드러나며, 더 작은 향상이 숨어 있을 수 있고, 현재 사용 중인 모델이 계속 유지되며, 화자가 수정한 문장은 여전히 유효하다는 점을 설명하세요. 그런 다음 다음 단계를 안내하세요.

**"판단하기에 연습 문장 수가 너무 적음" — "변화 없음"이 아니에요.** 연습 문장이 50개 미만이면 두 점수가 어떻든 어떤 비교로도 판정할 수 없어요. 이는 새 모델에 대한 판정이 아니에요. 대신 어떤 일이 일어나는지 설명하세요: 현재 사용 중인 모델이 당분간 유지되고, 다음 시트에 새 모델의 초안이 표시 없이 섞여 들어가며, 화자의 평가에 따라 결정돼요. 시트의 행 2개 중 1개는 초안이 없으며, 이 문장들은 라운드를 판정할 수 있을 때까지 연습 세트를 늘리는 데 쓰여요.

**블라인드 비교 — 두 수치와 그 역할 함께 설명하기.** 적혀 있는 그대로 두 모델의 수치와 보고서의 맺음말을 전달하세요. 새 모델이 명확히 더 나을 때는 보고서에 적힌 그대로 — 연습 세트에서는 드러나지 않았더라도 이번 라운드가 실제로 도움이 되었다는 점과, 이것이 새로운 문장에 대한 화자 본인의 판단이라는 점을 말해주세요. 해당 모델에 대해 **부족** 또는 **변화 없음** 판정이 나온 후 명확한 선호가 확인되면 forge가 이를 사용할 수 있도록 제안해요: `improve marks`에 *"forge에 기록됨: 새 모델 사용을 제안함(사람들의 동의가 먼저 필요함)"*이라고 표시되며, 이 제안은 `improve-promote` 단계(아래 참조)로 나타나요 — 실행하기 전에 먼저 물어보세요. **더 나쁨** 판정 후에는 제안되지 않아요. 승격 후에는 바로 이 확인을 거쳐야 보고서에서 점수 상승을 실제 진전으로 인정할 수 있어요. 만약 이전 모델이 명확히 더 나았다고 나오면 사람들에게 이전 모델로 되돌릴지 물어보세요 — 사람들의 동의 없이 임의로 진행해서는 안 돼요. 24문장에서 "명확한 차이 없음"이라는 말은 쓰인 그대로의 의미예요.
**참고.** 화자의 평가를 읽기 전에는 어떤 행이 어느 모델에서 나온 것인지 화자에게 절대 알려주지 마세요.

**다시 표시된 행 — 어떤 용도인가요.** 보고서에 나오는 것처럼 일치율과 개수를 함께 말해 주고("화자가 다시 표시된 20개 행 중 17개를 이전과 동일하게 표시함 — 85%"), 이것이 어떤 용도인지 설명해 주세요: 표시를 얼마나 신뢰할 수 있는지 알아보기 위한 것이에요. 이는 시트 위에 명시되어 있으며, 화자를 몰래 시험하는 것이 아니에요. 보고서에 나온 방식대로 무작위 오차를 설명해 주세요: 약 E%의 표시는 무작위로 다른 방향으로 바뀌며, 이는 모든 비율을 50% 쪽으로 끌어당기지만, 추정치에는 이 점이 반영되어 있어요. 보고서에 *"채점이 더 너그러워지고 있을 수 있습니다"*라고 나올 때는, 누구의 탓도 하지 말고 있는 그대로 담담하게 말해 주세요: 그렇다면 비율의 상승은 모델이 아니라 표시 방식 때문일 수 있어요. **참고.** 화자에게 어떤 행이 다시 돌아왔는지, 이전에 무엇으로 표시했는지는 절대 알려주지 마세요 — 시트에는 몇몇 행이 다시 돌아온다는 사실만 적혀 있어요.

**모델이 학습하지 않은 단어.** `sync`에서 키에 *"모델이 훈련 중에 본 적 없는 단어가 포함되어 있음 — 문장이 매끄러워 보이더라도 오역되었을 가능성이 매우 높음"*이라는 경고가 표시되면 알기 쉽게 설명해 주세요. 겉보기에 자연스러워 보여도 해당 줄은 틀렸을 가능성이 매우 높으며, 화자가 확인해 보거나 다음 라운드 문장에서 해당 단어를 가르쳐 줄 수 있다고 말해 주세요. 경고에 나온 대로 키 이름을 언급하세요. 여러분에게는 해당 단어가 보이지 않아요. 사용자는 모델 시험 페이지(try page)의 각 줄 아래에서 그 단어를 확인할 수 있어요. 가상 테스트 언어에서 확인된 근거로는, 모델이 본 적 없는 단어가 포함된 문장은 358회 중 맞은 적이 0회였어요([서빙](/docs/agents/serving#words-the-model-never-saw)).

**위시리스트의 단어.** 위시리스트의 "본 적 없는 단어" 섹션에서는 *"필요한 각 단어마다 서로 다른 내용을 담은 문장 두세 개"*를 요청해요. 많은 단어를 한 번씩 보여주는 것보다 적은 단어를 몇 개 문장에서 반복해 보여주는 것이 모델을 더 잘 학습시켜요. 이 점을 있는 그대로 전달하세요. 가상 테스트 언어에서 훈련 중 한 번 본 단어가 올바르게 번역된 비율은 27–29%였지만, 2–4번 본 단어는 63–95%였어요. 그리고 3,200개의 훈련 문장 조건에서, 새로운 단어가 가장 많이 포함되도록 선별된 문장으로 학습한 ByT5-small은 500개의 별도 보관된 문장 중 의미가 맞은 비율이 39.4%에 그친 반면, 일상 문장으로 학습했을 때는 53.4%였어요(화자의 시간은 약 54시간 대비 57시간으로 약간 더 들었어요).

점수가 좋은지 나쁜지 여러분이 직접 판단하지 마세요. 사용할 수 있는 수준인지는 유창한 화자가 결정해요.

## 시간 요청하기

`improve-time` 단계(모드 `ask_user`)는 화자가 시간을 얼마나 낼 수 있는지 물어봐요: `per_week` 및 `total`에 **화자가 말한 그대로**("일주일에 30문장 정도요", "몇 시간 해보고 결정할게요") 기록해요. 이는 `champollion improve time`에 의해 `improve/time.json`에 기록되며, 각 라운드의 문장 수는 이를 바탕으로 계획되고 보고서는 예측치를 이와 비교해요.

- **참고.** 한 번만 묻고 절대 더 많은 시간을 요구하지 마세요. 잘 모르겠다고 하면 말한 그대로 전달하세요 — 모호한 표현도 답변이에요.
- **참고.** 화자가 남았다고 말한 시간보다 예측치에 필요한 문장 수가 더 많다고 보고서에 나오면, 보고서에 제시된 선택지와 함께 알기 쉽게 설명해 주세요: 화자를 더 모집하거나, 프로젝트 참여자를 늘리거나, 당분간 목표를 좁히는 것(가장 필요한 문장을 모은 회화집 만들기) 등이 있어요. 그런 다음 그들이 직접 선택하게 하세요.

## 레일이 제안하는 옵션

**더 나은 모델을 사용하도록 제안하기** (forge 상태 `improve-promote`, 모드 `confirm`). 새 모델이 dev 세트에서 측정 가능할 정도로 더 나았거나, dev 세트가 판정할 수 없었지만(**too-few** 또는 **no-change**) 화자가 블라인드 채점에서 새 모델을 분명히 더 자주 맞았다고 표시한 경우예요. 그러면 forge의 `why`가 화자의 채점 수를 덧붙여요: *"동일한 방문에서 블라인드로 채점한 결과, 화자는 새로운 모델에 대해 새 문장 B개 중 A개(P%)를 맞았다고 표시했고, 현재 사용 중인 모델에 대해서는 D개 중 C개(Q%)를 맞았다고 표시했습니다. 분명한 차이입니다: 새로운 모델이 가족에게 필요한 문장에서 더 낫습니다."* 둘 중 어느 쪽이었는지 말해 주세요. 이것은 제안일 뿐이며, 판정 결과만으로는 아무것도 바뀌지 않아요. 모델을 적용하면 웹페이지나 앱의 답변이 바뀌므로, 단계를 실행하기 전에 먼저 물어보세요. "지금은 아님"인 경우 `declined: true`을 실행해요. 사람들의 동의(해당 단계의 `export` 및 `choose`)가 있어야만 실제 사용에 투입돼요. 그전까지 보고서에는 *"측정 가능할 정도로 더 나음: 사용에 투입되지 않음 — 사람들이 선택하지 않음"*으로 표시되며, 그로 인한 점수 상승은 진전으로 간주되지 않아요. 화자의 채점을 토대로 선택되고 나면 라운드 줄에 *"화자의 블라인드 채점으로 사용에 투입됨"*이라고 표시돼요.

**더 강력한 모델** (forge 상태 `improve-stronger-model`, 모드 `ask_user`).
dev 세트가 판정할 수 있는 라운드 중 연속 두 라운드에서 향상이 나타나지 않은 경우(둘 다 **no-change** 또는 **worse**이며, **too-few** 라운드는 포함되지 않음), 마지막 모델 변경(프리셋 전환, 또는 화자의 채점에 따른 승격을 포함하여 사람들이 `choose`(으)로 사용에 투입한 모든 모델) 시점부터 계산하여 tiny 모델을 사용 중일 때 레일이 ByT5-small을 제안해요. 학습에 사용할 GPU 메모리가 8~15GB인 환경에서는 `byt5-small` 또는 `byt5-small-lowmem`(스텝당 메모리는 적게 들지만 더 느림)을 제안하며, 약 1.2GB 다운로드와 더 긴 학습 시간이 필요하고 Apple silicon이나 NVIDIA GPU에서 가장 잘 작동해요([학습](/docs/agents/training#models)). 답변 슬롯은 `try_it`이며 값은 `yes` 또는 `not-now`예요. forge의 `why`이(가) 안내하는 내용을 전해 주세요. dev 세트가 너무 작아서 라운드의 향상을 감지할 수 없을 때는 작은 향상이 숨어 있을 수 있다고 전하고, 그렇지 않을 때는 두 라운드 동안 *"dev 문장에서 확인할 수 있는 변화 없음(약 X chrF++점 이상): 라운드가 그보다 적게 향상되고 있거나 전혀 향상되지 않는 것일 수 있습니다"*라고 전하세요. 문장을 더 추가해도 도움이 되지 않는다는 뜻이 아니며, 여러분도 그렇게 말해서는 안 돼요. "지금은 아님"도 이 단계의 답변 중 하나예요. `try_it: "not-now"`을 전달하세요(MCP 환경에서는 여기서 `declined: true`이 거부돼요). Forge는 이를 기록하고 현재 사용 중인 모델을 유지하며, 이 제안은 이러한 라운드(**no-change** 또는 **worse**)가 2회 더 발생한 뒤에만 다시 나타나요. 어느 쪽으로 답변해도 괜찮아요. 결정은 사람들의 몫이에요.

**예측 평가하기.** 테스트 세트 점수가 나온 후, 사람들은 자신들이 작성한 예측이 맞았는지(`held` 또는 `missed`)와 누가 평가했는지를 말해요. 예측 내용과 점수, 그리고 점수 범위를 읽어 주되, 여러분이 대신 판단하지는 마세요.

**아직 동의하지 않은 화자.** `waiting_for_agreement`에 있는 파일에 대해서는 세션당 한 번씩 조심스럽게 확인해요. 파일에 말이 담긴 모든 사람이 동의했다는 확인을 그 사람에게서 직접 받아야만 진행할 수 있어요.

|---|---|

| "도구가 확신하는 정도: 21%에서 57% 사이" | "CI [0.21, 0.57]" |
| "연습 문장들"(개발 세트) | "dev 분할" |
| "잠가 둔 테스트 문장들" | "held-out 테스트 세트" |
| "첫 번째 소형 모델" | 해당 폴더 이름이나 실행 이름 |
| "측정 가능한 변화 없음 — 50개의 연습 문장에서는 약 6점 정도의 차이가 나야 드러남" | "개선 없음" |
| "아직 판단하기에 연습 문장 수가 너무 적음 — 50개 미만에서는 화자 자신의 평가로 결정" | 부족(too-few) 판정에 대해 "변화 없음" |
| "회화집: 학습한 것과 비슷한 문장에 강함" | "저자원 NMT 베이스라인" |
| "화자가 24개 중 9개가 맞다고 표시함" | "정확도 38%" |

용어가 처음 등장할 때는 용어보다 예시를 먼저 들어 설명하세요.

## 도움을 제안해야 할 때

- **프로젝트가 막혔거나 사람의 도움을 요청할 때.** 다음과 같이 말하세요: *"어려움이 있거나 프로젝트에 도움이 필요하신가요? 이야기해 보아요."* — [info@champollion.dev](mailto:info@champollion.dev). 강요하지 않으며 유료 서비스가 아니에요.
- **문장, 화자, 또는 컴퓨팅 자원이 가진 것보다 더 많이 필요할 때.** [프로젝트 참여하기](/docs/join-a-project)를 안내해 주세요. 다른 사람이 문장, 단어 목록, 또는 방법(현재는 파일만 가능)을 제공할 수 있으며, 그들의 동의 없이는 어떤 것도 외부로 나가지 않아요([호스팅 및 참여](/docs/agents/hosting-and-joining)).
