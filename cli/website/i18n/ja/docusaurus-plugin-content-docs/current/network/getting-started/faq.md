# よくある質問

> **要約。** Champollion Network に関するよくある質問への回答です。スコアリングの仕組み、失格となる条件、FST がない言語の扱い方、モデルとパラメータの推奨事項、提出プロセスについて説明します。

---

## スコアリングと指標

### ハーネスはどのような指標を計算しますか？

ハーネスは5つの指標を計算します。そのうち3つは言語に依存せず、任意の言語ペアで機能します。残りの2つは現在CRK固有のプラグインに依存しており、対応言語を拡大するにつれて汎用化される予定です。現在実行可能なリファレンスコーパスは、オープンライセンスの公開データセット（Global Voices、Tatoeba、TICO-19、IN22、SMOLなど）です（[データセット](/docs/network/leaderboard/datasets)を参照）。リーダーボードは登録済みのすべての言語ペアへの投稿を受け付けています。Plains Creeは、言語固有の2つの指標（FSTベース）が最初に実装された言語にすぎません。

| 指標 | スケール | 測定内容 | ステータス |
|--------|-------|-----------------|--------|
| **chrF++** | 0–100 | 予測訳と参照訳の間の文字 n-gram の重複。形態的に豊かな言語に最適な表層指標。sacrebleu のネイティブスコアリングを使用。 | ✅ 全言語 |
| **完全一致** | 0.0–1.0 | 正規化後に予測が参照と完全に一致するエントリの割合。 | ✅ 全言語 |
| **FST 受理率** | 0.0–1.0 | 有限状態トランスデューサー（形態素解析器）に受理された出力単語の割合。FST バイナリが提供されている場合のみ計算されます。 | ✅ FST がある全言語 |
| **等価一致** | 0.0–1.0 | 語順・正書法の慣習・方言の違いを考慮した上で、参照訳または許容可能なバリアントと一致するエントリの割合。 | ⚡ CRK（汎用化中） |
| **意味スコア** | 0.0–1.0 | 意味保持スコア — 表層形式に関わらず、翻訳が意図された意味をどれだけ捉えているかを示します。 | ⚡ CRK（汎用化中） |

追加指標も計画されています：**形態的正確性**、**コードスイッチング検出**、**用語遵守**、**幻覚検出**。指標の全一覧（6カテゴリ）については [スコアリング仕様 §2](/docs/network/specifications/scoring#2-metric-inventory) を参照してください。

### 総合スコアはどのように計算されますか？

総合スコアは、利用可能な指標の加重平均であり、0.0–1.0 のスケールに正規化されます。重みは2つのプロファイルで定義されています：

- **プロファイル A**（FST がある言語）：9指標、構造的指標（FST + 形態的正確性）が総合重みの 40% を占める
- **プロファイル B**（FST がない言語）：8指標、意味スコアと chrF++ が同等の最高重みを持つ

指標が利用できない場合、その重みは残りの指標に比例して再配分されます。つまり、chrF++ と完全一致のみが利用可能な初期段階のベンチマークでも有効な総合スコアが算出されます — 実効重みは利用可能な指標を反映したものになります。

**重みの全テーブル、正規化ルール、除外の根拠は [スコアリング仕様 §4](/docs/network/specifications/scoring#4-composite-score) に記載されています。** ハーネスのコードはこれらのテーブルを `mt_eval_harness/scoring.py` に反映しています。chrF++ は重み付け前に 100 で割って正規化されます。コードスイッチング率と幻覚率は反転されます（低いほど良い）。

### 品質ティアとは何ですか？

品質ティアは、総合スコアの範囲に対応するヒューリスティックなラベルです。スコアが実際に何を意味するかを伝えるために使用されます：

| ティア | 総合スコア範囲 | 解釈 |
|------|----------------|----------------|
| **Baseline** | 0.00 – 0.30 | 実用的な品質に達していません。手法の大幅な改善が必要です。 |
| **Emerging** | 0.30 – 0.50 | 可能性を示しています。一部の翻訳は正確ですが、一貫性がありません。 |
| **Functional** | 0.50 – 0.70 | 人間によるレビューを前提とした参照用途に使用可能。未レビューでの展開には適しません。 |
| **Deployable** | 0.70 – 0.85 | 定期的なレビューを伴う本番環境での使用に対応。所有権移転の資格要件を満たします。 |
| **Fluent** | 0.85 – 1.00 | ネイティブに近い品質。監視なしでの展開に適しています。 |

### 品質ティアと検証ティアの違いは何ですか？

**品質ティア**は*自動スコアが何を意味するか*を表します（Baseline → Fluent）。**検証ティア**は*誰が結果を検証したか*を表します：

| 検証ティア | 意味 |
|-------------------|---------------|
| **Self-benchmarked** | 提出者が自身でハーネスを実行しました。スコアは妥当ですが、未検証です。 |
| **Champollion Verified** | メンテナーが、提出されたメソッド構成を使用して結果を再現しました。 |
| **Community Validated** | コミュニティ独自のプロトコルに基づいて資格を得た対象言語のバイリンガル話者が、出力の層化抽出サンプル（30エントリ以上、2名以上のレビュアー）をレビューし、70%以上がコミュニティの基準を満たしました。コミュニティ自身のテストによってのみ付与されます。スポット監査による降格も同様に行われ、等しく公開されます。 |

手法が「Deployable」品質でありながら「Self-benchmarked」検証にとどまる場合があります — スコアは優れているように見えますが、誰も独立して確認していないことを意味します。

## 提出と失格

### どのような場合に提出が失格になりますか？

以下の場合、提出は却下またはフラグが立てられます：

1. **評価データに手法が露出していた場合。** 評価データセットのエントリを使ってトレーニング、ファインチューニング、few-shot プロンプト、またはその他の方法で使用した場合、スコアは人為的に高くなります。プロンプトに参照訳を使用することも含まれます。
2. **ランカードが整合性チェックに失敗した場合。** フィンガープリントは設定と一致している必要があります。改ざんされたランカードは却下されます。
3. **手法が TranslationMethod プロトコルを実装していない場合。** ハーネスは `translate(entries, config) → results` を期待しています。ハーネスをバイパスするカスタム統合は受け付けられません。

### 複数回提出できますか？

はい。リーダーボードはすべての提出を記録します。何度でも繰り返すことができます — 数十の実験を行い、最良の結果のみを提出することも可能です。各提出には固有のフィンガープリントが記録されるため、どの実行がどのスコアを生成したかについて曖昧さはありません。

### スコアを検証してもらうにはどうすればよいですか？

1. **Self-benchmarked（自動）:** すべての提出はここから始まります。
2. **Champollion Verified（自動）:** サーバーは、ハーネスのメトリクスを使用して、shaで固定された参照コーパスに対して提出された出力を再スコアリングします。スコアが再現されると、実行はChampollion Verifiedに昇格します。これはボードがランク付けする唯一のティアです。再現されない場合、または保存された参照が変更された場合、その実行は失格となります。
3. **Community Validated:** コミュニティ独自のプロトコルに基づいて資格を得た対象言語のバイリンガル話者が、メソッドの出力の層化抽出サンプル（30エントリ以上、2名以上のレビュアー）をレビューし、70%以上がコミュニティの基準を満たす必要があります。このティアは、コミュニティ自身の裁量によるテストの実行によってのみ付与され、同じ方法で取り消される可能性があります。スポット監査に不合格となった場合も、同様に公開された形でメソッドが降格されます。これは自動化できず、コミュニティの参加が必要です。

### なぜ全員のメソッドを再実行して検証しないのですか？

そのコストを負担できず、またその必要もないからです。サーバーは、提出された*全員*の出力を無料で再スコアリングします（これにより、手入力や編集されたスコアを検出します）。実際にモデルを再実行するには実際の計算リソースのコストがかかるため、**レピュテーションで重み付けされた監査（reputation-weighted auditing）**によって選ばれた**サンプル**に対してのみ実行します。影響が大きい場合（言語グループ全体への最初の架け橋となる場合など）や、異常な場合（過去の最高記録を不自然なほど上回る場合など）は常に再実行されますが、実績のあるコントリビューターからの提出はまれにスポットチェックされる程度です。レピュテーションは、これらの監査に合格すること（または独立したコントリビューターが結果を裏付けること）によってのみ獲得され、提出量によって獲得されることは決してありません。そのため、新規の使い捨てアカウントは何も得られません。捏造が一度でも発覚すると、そのコントリビューターのレピュテーションはゼロになり、検証済みの履歴全体が再監査され、論文の撤回のように公に記録されます。サーバーで検証できないセルフホストの計算リソースについて、私たちはあなたの実行が「ハーネスを通過した」とは**主張しません**。したがって、有効性は証明（attestation）ではなく、*再現性 + レピュテーションの担保 + 裏付け（reproducibility + reputation stake + corroboration）*に依存します。完全なモデルについては、[MT評価ルール](/docs/network/leaderboard/rules#how-verification-scales-reputation-weighted-auditing)を参照してください。

### 提出 API は稼働していますか？

まだです。`https://champollion.dev/api/leaderboard/submit` エンドポイントは将来的な目標です。現在の投稿パスは `mt-eval publish` です。これはハーネスの出力ディレクトリ（`eval/logs/harness/`）からランカードを*self-benchmarked（未検証）*としてリーダーボードに直接アップロードします。

## モデルとパラメータ

### どのモデルを使用すればよいですか？

最適なモデルは一つではありません — 言語ペア、予算、アプローチによって異なります。一般的なガイダンス：

| 言語タイプ | 推奨される出発点 | 理由 |
|---------------|---------------------------|-----|
| **高リソース**（フランス語、スペイン語、日本語） | `google/gemini-2.5-flash` または `gpt-4o-mini` | 高速、低コスト、強力なベースライン |
| **LLM カバレッジがある程度ある低リソース**（ケチュア語、ヨルバ語） | `google/gemini-2.5-pro` または `anthropic/claude-sonnet-4` | 大規模モデルはより優れた潜在知識を持つ |
| **多合成語 / 非常に低リソース**（Plains Cree、イヌクティトゥット語） | コーチングありの `google/gemini-2.5-pro` | モデルの選択よりコーチングデータが重要。OMT-1600 は一部の多合成語言語（例：R1 ティアの CRK）を含みますが、標準的な BPE トークナイゼーションを使用しています — Network でベースラインとしてベンチマークしてください。 |

評価ハーネスはOpenRouterを使用しているため、OpenRouterで利用可能なモデルであればベンチマークを実行できます。利用可能なモデルの一覧については、[openrouter.ai/models](https://openrouter.ai/models)を参照してください。

### どの温度（temperature）を使用すればよいですか？

翻訳には一般的に低い値が適しています：

| 温度 | 効果 | 推奨用途 |
|-------------|--------|-----------------|
| **0.0 – 0.2** | 高度に決定論的で一貫した出力 | 本番手法、最終ベンチマーク |
| **0.3 – 0.5** | 若干のバリエーションがあり、時により創造的 | 探索、初期の反復 |
| **0.6+** | 高いバリエーション、予測不可能 | MT ベンチマークには推奨しません |

温度はランカードに記録されるため、異なる温度は異なるフィンガープリントを生成します — それぞれ別の実験として扱われます。

### コーチングデータは効果がありますか？

はい、低リソース言語では大きな効果があります。コーチングデータ（文法規則、辞書エントリ、スタイルノート）は LLM のシステムプロンプトに注入されます。Plains Cree の場合、コーチングありの手法は多合成語言語において生の LLM 手法を一貫して上回ります。これは汎用 LLM が多合成語への露出が限られており、形態的な認識を持たないためです。CRK 向けに特別にトレーニングされた OMT-1600 でさえ、多合成語の形態論を構造的に表現できない標準的な BPE トークナイゼーションを使用しています。コーチングデータは、モデルが欠いている言語的コンテキストを提供します。

高リソース言語（フランス語、スペイン語）では、モデルがすでに強力なベースライン知識を持っているため、コーチングの効果は小さくなります。

詳細な仕様については [コーチングデータ](https://champollion.dev/docs/concepts/coaching-data) を参照してください。

## FST と形態的検証

### 対象言語に FST がない場合はどうすればよいですか？

多くの言語には有限状態トランスデューサーがありません。それでも問題ありません — ハーネスは FST なしでも動作します。総合スコアはプロファイル B の重みを使用します（[スコアリング仕様 §4.3](/docs/network/specifications/scoring#43-weight-tables) を参照）。これにより重みが意味スコアと表層指標にシフトします。FST 受理率はランカードで `null` としてマークされます。

既存の FST の主なレジストリ：

| レジストリ | 対象範囲 | URL |
|----------|----------|-----|
| **GiellaLT** | 100以上の言語 — サーミ語、クリー語、イヌクティトゥット語、およびその他の多くのウラル語族や少数言語 | [giellalt.uit.no](https://giellalt.uit.no/) |
| **ALTLab** | 平原クリー語、ツゥーティナ語、オダワ語 | [altlab.ualberta.ca](https://altlab.ualberta.ca/) |
| **Apertium** | 約60の言語ペア、主にヨーロッパ言語 | [apertium.org](https://apertium.org/) |
| **UniMorph** | 150以上の言語の形態論的パラダイム | [unimorph.github.io](https://unimorph.github.io/) |

### FST を自分で構築できますか？

はい、ただし簡単ではありません。FST は言語の形態規則 — すべての有効な語形 — をエンコードします。構築には言語の深い言語学的知識が必要です。形態論的文法（例：言語学部門のもの）にアクセスできる場合、[HFST](https://hfst.github.io/) や [Foma](https://fomafst.github.io/) などのツールを使って FST にコンパイルできます。

### FST ゲーティングは実際にどのように機能しますか？

FST ゲーティングパイプラインは次のように動作します：

1. LLM が翻訳を生成する
2. 出力の各単語が FST に対してチェックされる
3. FST が拒否した単語は形態的に無効としてフラグが立てられる
4. 手法はフィードバックとともに再試行できる（「単語 X は有効ではありません、もう一度試してください」）
5. 再試行後も残った無効な単語はログに記録される

FST 受理率は、検証を通過した単語の割合を測定します。完全な実例については [FST ゲーティングパイプラインチュートリアル](/docs/network/tutorials/fst-gated-pipeline) を参照してください。

## データとデータセット

### 新しい言語のデータセットを提供できますか？

はい。[ベンチマーク仕様 §11](/docs/network/specifications/benchmark#11-extending-to-new-languages) に基づく最低要件：

- **50件のゴールドスタンダードエントリ**（ソース + 検証済み参照訳）
- **30件の開発エントリ**（小規模コーパスの場合はゴールドスタンダードと重複可）
- **コミュニティの同意**（先住民族の言語の場合、ガバナンス機関からの明示的な承認が必要）
- **出所の文書化**（データの出典、適用されるライセンス）

新しいデータセットを追加すると、新しいリーダーボードトラックが自動的に開設されます。貢献者ガイドについては [言語コミュニティの方へ](/docs/network/community/for-language-communities) を参照してください。

### データセットはどのような形式にすればよいですか？

標準的なフィールド名を使用した JSON 形式：

```json
{
  "name": "my-language-dev-v1",
  "language_pair": "en-xxx",
  "segment": "development",
  "version": "1.0",
  "entries": [
    {
      "id": 1,
      "source": "Hello",
      "reference": "[translation in target language]",
      "difficulty": 1,
      "domain": "general"
    }
  ]
}
```

完全なスキーマと難易度ティアの定義については [データセット](/docs/network/leaderboard/datasets) を参照してください。

## 主権と所有権

### 先住民族の言語向けに構築された手法の所有権は誰にありますか？

先住民族の言語の場合、Deployable ティア（総合スコア ≥ 0.70）に達し、かつコミュニティ検証に合格した手法は、[所有権移転](/docs/network/sovereignty/ownership-transfer) プロセスを開始します。コードの所有権は研究者から言語コミュニティのガバナンス組織に移転されます。

研究者が保持するもの：
- 出版権（手法に関する学術論文）
- リーダーボード上のクレジット
- 同じ*技術*を他の言語に適用する権利

ガバナンス組織が得るもの：
- 手法コードとコーチングデータの完全な所有権
- 展開に関する管理権（いつ、どこで、どのように）— および展開から得られるすべての収益。Champollion は非商業的であり、いかなる取り分も受け取りません

### 先住民族の言語以外に champollion を使用する場合、主権に関する懸念はありますか？

ありません。標準的な言語（フランス語、日本語、スペイン語など）については、主権に関する考慮事項はありません。champollion を通常通り使用してください — 翻訳、同期、公開を自由に行えます。主権フレームワークは、データガバナンス原則 — 言語データのコミュニティによる所有と管理、CARE、Te Mana Raraunga — が特別な配慮を必要とする先住民族およびコミュニティ管理の言語に特化して適用されます。
