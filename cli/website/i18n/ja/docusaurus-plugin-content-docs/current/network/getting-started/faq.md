# よくある質問

> **要約。** Champollion Network に関するよくある質問への回答です。スコアリングの仕組み、失格となる条件、FST がない言語の扱い方、モデルとパラメータの推奨事項、提出プロセスについて説明します。

---

## スコアリングと指標

### ハーネスはどのような指標を計算しますか？

ヘッドラインであり、実行結果のランキングを決定する唯一の数値は、95%信頼区間を伴う**コーパス chrF++** です。その横に、ハーネスは他の標準メトリクス（**BLEU、spBLEU、TER**、およびインストールされている場合は **COMET**）を報告します。これらはそれぞれ単独で扱われ、混合されることは決してありません。それ以外のすべては**診断情報**です。スコアを説明するために個別に報告されるものであり、スコアの一部になることはありません。以下の表は、chrF++ と主な診断メトリクスをまとめたものです。3つは言語非依存であり、2つは現在 CRK 固有のプラグインに依存していますが、対応言語の拡大に合わせて一般化される予定です。現在実行可能な参照コーパスは、オープンライセンスの公開データセット（Global Voices、Tatoeba、TICO-19、IN22、SMOL など。[データセット](/docs/network/leaderboard/datasets)を参照）であり、リーダーボードは登録されたすべての言語ペアからの提出を受け付けています。Plains Cree（平原クリー語）は、単に2つの言語固有（FST 連携）メトリクスが最初に実装された言語にすぎません。

| メトリクス | スケール | 測定対象 | ステータス |
|--------|-------|-----------------|--------|
| **chrF++**（ヘッドライン） | 0–100 | 予測翻訳と参照訳との間の文字 n-gram オーバーラップ。sacreBLEU を使用してコーパス全体で算出（シグネチャも記録されます）。形態論的に豊かな言語向けの標準的な表層メトリクス。 | ✅ すべての言語 |
| **完全一致**（診断情報） | 0.0–1.0 | 正規化後に予測が参照訳と完全に一致したエントリの割合。 | ✅ すべての言語 |
| **FST 受理率**（診断情報） | 0.0–1.0 | 有限状態トランスデューサ（形態素解析器）によって受理された出力単語の割合。FST バイナリが提供されている場合にのみ算出。 | ✅ FST を持つすべての言語 |
| **等価一致**（診断情報） | 0.0–1.0 | 語順、正書法上の慣例、方言差を考慮した上で、参照訳または許容される異形態と一致したエントリの割合。 | ⚡ CRK（一般化対応中） |
| **セマンティックスコア**（診断情報） | 0.0–1.0 | 意味の保持スコア。表層的な形式にかかわらず、翻訳が意図された意味をどれだけ捉えているかを測定。 | ⚡ CRK（一般化対応中） |

その他の診断メトリクス（**形態論的正確さ**、**コードスイッチング**、**用語の遵守**、**ハルシネーション**、**文体**）および各メトリクスの実装状況については、メトリクスの全一覧である[スコアリング仕様 §2](/docs/network/specifications/scoring#2-metric-inventory)に記載されています。

### 実行結果はどのようにスコア付けされますか？

すべての新しい実行結果は、機械翻訳評価の分野標準（WMT、FLORES-200、AmericasNLP など）の報告方法に準拠したスコアリング標準 `standard/1` に従ってスコア付けされます。

- **ヘッドライン:** コーパス chrF++。95% ブートストラップ CI と sacreBLEU シグネチャを併記して表示されます（例: `chrF++ 47.5 [45.9, 49.0]`）。
- **併記メトリクス:** BLEU、spBLEU、TER、および算出された場合は COMET。混合されることはありません。
- **診断情報:** 完全一致、FST 受理率、形態論的正確さ、コードスイッチング、ハルシネーション、用語、文体。個別に報告され、実行結果の順位付けには一切使用されません。
- **スコアの注意事項:** 数値が誤解を招く恐れのあるパターンをハーネスが検出した場合、ヘッドラインのすぐ横に出力されます。

ある実行結果が別の実行結果よりも**優れている**かどうかは、2つの数値を比較するのではなく、chrF++ の対応のある有意差検定（`mt-eval compare --significance`）によって判断されます。詳細なルールについては、[実行結果のスコアリング方法](/docs/network/specifications/scoring#how-runs-are-scored)および[有意性仕様](/docs/network/specifications/significance)を参照してください。

### 複合スコアと品質ティアはどうなりましたか？

どちらも新規の実行結果に対しては**廃止**されました。複合スコアは chrF++、完全一致、FST 受理率などのシグナルを加重平均したものであり、ティア（Baseline → Fluent）はそこから読み取られるラベルでした。その入力のいくつかでは出力を原文や参照訳と一切比較しないため、システムは翻訳を行わなくてもスコアの大半を獲得できてしまう問題がありました。たとえば、未学習の英語→北サーミ語モデルがすべての入力に対して単一の文法的に正しい文を繰り返した場合、chrF++ は 5.5 であるにもかかわらず 0.6244 のスコアを獲得し、「functional（機能的）」とラベル付けされていました。新しい実行カードでは `composite: null` および `quality_tier: null` が公開されます。

この標準より前に公開されたカードは、保存された複合スコアを維持し、検証可能な状態が保たれます。表示される場所ではすべて**レガシー複合スコア（廃止済み）**と表記されます。[複合スコアが廃止された理由](/docs/network/specifications/scoring#why-the-composite-was-retired)を参照してください。

自動スコアは品質の最終判断ではありません。その言語の話者による人的評価のみが品質を証明します。

### 検証ティアとは何ですか？

**検証ティア**は、結果の良し悪しではなく、*誰がその結果を検証したか*を示すものです。

| 検証ティア | 意味 |
|-------------------|---------------|
| **自己ベンチマーク（Self-benchmarked）** | 提出者自身がハーネスを実行した場合。スコアは妥当と見なされますが、未検証です。 |
| **Champollion 検証済み（Champollion Verified）** | メンテナーが、提出された手法の設定を用いて結果を再現した場合。 |
| **コミュニティ検証済み（Community Validated）** | 対象言語のバイリンガル話者（コミュニティ独自のプロトコルで認定）が、出力の層化サンプル（30エントリ以上、査読者2名以上）をレビューし、70%以上がコミュニティの基準を満たした場合。コミュニティ自身のテストによってのみ付与され、抜き打ち監査による格下げも同様に対称的かつ公開で行われます。 |

実行結果の chrF++ が高くても、「自己ベンチマーク」にとどまることがあります。これは、誰もそのスコアを独自に確認しておらず、話者もその出力を評価していないことを意味します。

## 提出と失格

### どのような場合に提出が失格になりますか？

以下の場合、提出は却下またはフラグが立てられます：

1. **評価データに手法が露出していた場合。** 評価データセットのエントリを使ってトレーニング、ファインチューニング、few-shot プロンプト、またはその他の方法で使用した場合、スコアは人為的に高くなります。プロンプトに参照訳を使用することも含まれます。
2. **ランカードが整合性チェックに失敗した場合。** フィンガープリントは設定と一致している必要があります。改ざんされたランカードは却下されます。
3. **手法が TranslationMethod プロトコルを実装していない場合。** ハーネスは `translate(entries, config) → results` を期待しています。ハーネスをバイパスするカスタム統合は受け付けられません。

### 複数回提出できますか？

はい。リーダーボードはすべての提出を記録します。何度でも繰り返すことができます — 数十の実験を行い、最良の結果のみを提出することも可能です。各提出には固有のフィンガープリントが記録されるため、どの実行がどのスコアを生成したかについて曖昧さはありません。

### スコアを検証してもらうにはどうすればよいですか？

1. **自己ベンチマーク（Self-benchmarked）:** すべての提出はここから始まり、現在リーダーボード上のすべての行もこの状態です。
2. **Champollion 検証済み（Champollion Verified）:** プロジェクト側が、提出された出力を sha 固定された参照コーパスに対してハーネスのメトリクスを用いて再スコア付けします。スコアが再現された場合、その実行結果は Champollion 検証済みに昇格します。これはコンテストのランキングでデフォルトで使用されるティアであり、賞金の対象となる唯一のティアです（公開ボードには自己ベンチマークの行もその旨を明記して掲載されます）。再現されない場合や保存された参照訳が改ざんされていた場合、その実行結果は失格となります。再スコア付けはメンテナーによる手動のバッチ処理であり、提出時に自動実行されたりスケジュールされたりすることはありません。
3. **コミュニティ検証済み（Community Validated）:** コミュニティ独自のプロトコルに基づいて認定された対象言語のバイリンガル話者が、その手法の出力の層化サンプル（最低30エントリ、最低2名の査読者）をレビューし、最低70%がコミュニティの基準を満たす必要があります。このティアは、コミュニティが自身の裁量で実施するテストによってのみ付与され、同様に取り消されることもあります。抜き打ち監査に不合格となった場合、その手法は同様に公に格下げされます。これを自動化することはできず、コミュニティの関与が不可欠です。

### なぜ全員の手法を再実行して検証しないのですか？

費用的に不可能であり、その必要もないためです。*全員*の提出された出力に対する再スコア付けは無償で行えます（これにより、入力ミスや改ざんされたスコアを検出できます）。しかし、実際にモデルを再実行するには実質的な計算コストがかかるため、**レピュテーション加重監査**によって選ばれた**サンプル**に対して実施されます。サンプリングポリシーは構築・テスト済みですが、それを駆動する再実行エンジンはまだ稼働していないため、サンプルによる再実行はまだ実行されておらず、選定された実行結果は *L2-pending* として記録されます。このポリシーでは、重大な意味を持つ場合（言語ファミリー全体への最初の架け橋となる場合など）や異常値を示す場合（従来最高値を信じがたいほど大きく上回る場合など）は常に再実行対象として選ばれ、実績のあるコントリビューターからのものは稀にしか抜き打ちチェックされません。レピュテーションはこれらの監査に合格すること（または独立したコントリビューターによって結果が裏付けられること）によってのみ獲得され、提出量によって得られることは決してないため、使い捨ての新規アカウントには何のメリットもありません。捏造が1度でも発覚した場合、そのコントリビューターのレピュテーションはゼロになり、過去のすべての検証済み履歴が再監査され、論文撤回のように公に記録されます。私たちは実行結果が「ハーネスを通じて生成された」とは**主張しません**（セルフホストの計算リソースではサーバー側で検証不能なためです）。したがって、妥当性は証明書ではなく、*再現性 + レピュテーションの担保 + 第三者による裏付け*に基づいています。モデルの詳細については、[MT 評価ルール](/docs/network/leaderboard/rules#how-verification-scales-reputation-weighted-auditing)を参照してください。

### 提出 API は稼働していますか？

まだです。`https://champollion.dev/api/leaderboard/submit` エンドポイントは将来的な目標です。現在の投稿パスは `mt-eval publish` です。これはハーネスの出力ディレクトリ（`eval/logs/harness/`）からランカードを*self-benchmarked（未検証）*としてリーダーボードに直接アップロードします。

## モデルとパラメータ

### どのモデルを使用すればよいですか？

最適なモデルは一つではありません — 言語ペア、予算、アプローチによって異なります。一般的なガイダンス：

| 言語タイプ | 推奨される出発点 | 理由 |
|---------------|---------------------------|-----|
| **高リソース**（フランス語、スペイン語、日本語） | `google/gemini-2.5-flash` または `gpt-4o-mini` | 高速、低コスト、強力なベースライン |
| **LLM カバレッジがある程度ある低リソース**（ケチュア語、ヨルバ語） | `google/gemini-2.5-pro` または `anthropic/claude-sonnet-4` | 大規模モデルはより優れた潜在知識を持つ |
| **多合成語 / 非常に低リソース**（Plains Cree、イヌクティトゥット語） | コーチングありの `google/gemini-2.5-pro` | モデルの選択よりコーチングデータが重要。OMT-1600 は一部の多合成語言語（例：R1 ティアの CRK）を含みますが、標準的な BPE トークナイゼーションを使用しています — Network でベースラインとしてベンチマークしてください。 |

評価ハーネスはOpenRouterを使用しているため、OpenRouterで利用可能なモデルであればベンチマークを実行できます。利用可能なモデルの一覧については、[openrouter.ai/models](https://openrouter.ai/models)を参照してください。

### どの温度（temperature）を使用すればよいですか？

翻訳には一般的に低い値が適しています：

| 温度 | 効果 | 推奨用途 |
|-------------|--------|-----------------|
| **0.0 – 0.2** | 高度に決定論的で一貫した出力 | 本番手法、最終ベンチマーク |
| **0.3 – 0.5** | 若干のバリエーションがあり、時により創造的 | 探索、初期の反復 |
| **0.6+** | 高いバリエーション、予測不可能 | MT ベンチマークには推奨しません |

温度はランカードに記録されるため、異なる温度は異なるフィンガープリントを生成します — それぞれ別の実験として扱われます。

### コーチングデータは効果がありますか？

はい、低リソース言語では大きな効果があります。コーチングデータ（文法規則、辞書エントリ、スタイルノート）は LLM のシステムプロンプトに注入されます。Plains Cree の場合、コーチングありの手法は多合成語言語において生の LLM 手法を一貫して上回ります。これは汎用 LLM が多合成語への露出が限られており、形態的な認識を持たないためです。CRK 向けに特別にトレーニングされた OMT-1600 でさえ、多合成語の形態論を構造的に表現できない標準的な BPE トークナイゼーションを使用しています。コーチングデータは、モデルが欠いている言語的コンテキストを提供します。

高リソース言語（フランス語、スペイン語）では、モデルがすでに強力なベースライン知識を持っているため、コーチングの効果は小さくなります。

詳細な仕様については [コーチングデータ](https://champollion.dev/docs/concepts/coaching-data) を参照してください。

## FST と形態的検証

### 対象言語に FST がない場合はどうすればよいですか？

有限状態トランスデューサ（FST）が存在しない言語も数多くあります。それでも問題ありません。ハーネスは FST がなくても動作します。いずれにしてもヘッドラインは chrF++ であるため、FST の有無にかかわらず実行結果は同じようにスコア付けされます。FST 受理率は診断情報であり、FST が使用されなかった場合は実行カードに `null` とマークされます。

既存の FST の主なレジストリ：

| レジストリ | カバレッジ | URL |
|----------|----------|-----|
| **GiellaLT** | 100以上の言語 — サーミ諸語、クリー語、イヌクティトゥット語、その他多数のウラル語族および少数言語 | [giellalt.uit.no](https://giellalt.uit.no/) |
| **ALTLab** | 平原クリー語（Plains Cree）、ツースティーナ語（Tsuut'ina）、オダワ語（Odawa） | [altlab.ualberta.ca](https://altlab.ualberta.ca/) |
| **Apertium** | 約60言語ペア（主にヨーロッパ言語） | [apertium.org](https://apertium.org/) |
| **UniMorph** | 150以上の言語の形態論パラダイム | [unimorph.github.io](https://unimorph.github.io/) |

### FST を自分で構築できますか？

はい、ただし簡単ではありません。FST は言語の形態規則 — すべての有効な語形 — をエンコードします。構築には言語の深い言語学的知識が必要です。形態論的文法（例：言語学部門のもの）にアクセスできる場合、[HFST](https://hfst.github.io/) や [Foma](https://fomafst.github.io/) などのツールを使って FST にコンパイルできます。

### FST ゲーティングは実際にどのように機能しますか？

FST ゲーティングパイプラインは次のように動作します：

1. LLM が翻訳を生成する
2. 出力の各単語が FST に対してチェックされる
3. FST が拒否した単語は形態的に無効としてフラグが立てられる
4. 手法はフィードバックとともに再試行できる（「単語 X は有効ではありません、もう一度試してください」）
5. 再試行後も残った無効な単語はログに記録される

FST 受理率は、検証を通過した単語の割合を測定します。完全な実例については [FST ゲーティングパイプラインチュートリアル](/docs/network/tutorials/fst-gated-pipeline) を参照してください。

## データとデータセット

### 新しい言語のデータセットを提供できますか？

はい。[ベンチマーク仕様 §11](/docs/network/specifications/benchmark#11-extending-to-new-languages) に基づく最低要件：

- **50件のゴールドスタンダードエントリ**（ソース + 検証済み参照訳）
- **30件の開発エントリ**（小規模コーパスの場合はゴールドスタンダードと重複可）
- **コミュニティの同意**（先住民族の言語の場合、ガバナンス機関からの明示的な承認が必要）
- **出所の文書化**（データの出典、適用されるライセンス）

新しいデータセットを追加すると、新しいリーダーボードトラックが自動的に開設されます。貢献者ガイドについては [言語コミュニティの方へ](/docs/network/community/for-language-communities) を参照してください。

### データセットはどのような形式にすればよいですか？

標準的なフィールド名を使用した JSON 形式：

```json
{
  "name": "my-language-dev-v1",
  "language_pair": "en-xxx",
  "segment": "development",
  "version": "1.0",
  "entries": [
    {
      "id": 1,
      "source": "Hello",
      "reference": "[translation in target language]",
      "difficulty": 1,
      "domain": "general"
    }
  ]
}
```

完全なスキーマと難易度ティアの定義については [データセット](/docs/network/leaderboard/datasets) を参照してください。

## 主権と所有権

### 先住民族の言語向けに構築された手法の所有権は誰にありますか？

先住民族の言語において、賞の基準（自動スコアの閾値および話者によるコミュニティ検証）を満たした手法は、デフォルトのテンプレートに基づき[所有権移転](/docs/network/sovereignty/ownership-transfer)プロセスを開始します。コードの所有権は、研究者からその言語コミュニティの統治組織へと移転されます。

研究者が保持するもの：
- 出版権（手法に関する学術論文）
- リーダーボード上のクレジット
- 同じ*技術*を他の言語に適用する権利

ガバナンス組織が得るもの：
- 手法コードとコーチングデータの完全な所有権
- 展開に関する管理権（いつ、どこで、どのように）— および展開から得られるすべての収益。Champollion は非商業的であり、いかなる取り分も受け取りません

### 先住民族の言語以外に champollion を使用する場合、主権に関する懸念はありますか？

はい。標準的な言語（フランス語、日本語、スペイン語など）については、主権に関する考慮事項はありません。Champollion を通常どおり使用し、希望に応じて翻訳、同期、公開を行ってください。主権フレームワークは、言語データのコミュニティによる所有と管理、CARE、Te Mana Raraunga などのデータガバナンス原則において特別な配慮が必要とされる、先住民族の言語およびコミュニティが管理する言語に特化して適用されます。
