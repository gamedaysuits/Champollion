# 主権コンテストを開催する

> **エグゼクティブサマリー。** コミュニティや組織は、**自組織のインフラから外に出ることのない**非公開テストコーパスを対象に、スポンサー賞金付きの評価コンテストを開催できます。コーパスの構築、暗号化、ホスティング、鍵の管理はすべてあなたが行います。ネットワークに登録されるのは、内容を含まないメタデータカードと暗号文のダイジェストのみです。手法はまず公開コーパスで資格審査を通過する必要があり、封印済みセットへの評価実行はすべてカストディアンの承認を必要とします。外部に出るのは**スコアのみ**です。賞金は**スポンサーが保管**します — あなたの組織または指定する信託機関が管理し、**Champollion は資金にもデータにも一切関与しません。** このページは、エンドツーエンドのセルフサービス運用手順書です。

:::warning[現在利用可能な機能と開発中の機能]
始める前に、現実を正確に把握してください — これは進化中の非商用研究プロジェクトです。私たちを盲目的に信頼するより、ご自身で確認されることをお勧めします：

- ✅ **稼働中:** コーパス登録（メタデータカード、ハッシュ固定、公開レーン）、封印セットレジストリ（ダイジェスト + 保管者グループ + 予選ゲート、コンテンツなし）、封印レーンを備えたコンテスト機構、認可リクエスト/付与/監査データレイヤー（保留中 → M-of-N 決定 → 単一使用・時間制限付き付与、追記のみのハッシュチェーン監査ログ）、およびデータベースレイヤーで強制されるスコアのみの出力。
- ✅ **稼働中: 主催者スコアリングノード。** 1つのコマンドでコーパスを公開開発セット（参加者が自己スコアリングを行う予選用）と封印された秘密セット（ノードがエントリーを実行対象とするもの）に分割し、秘密側の半分をユーザー自身のマシン上で保管時に封印します（`mt-eval contest prepare`）。封印セット、予選ゲート、コンテストの登録は、**ご自身のサインインからセルフサービスで行えます** — `contest prepare --self-serve`、または以前に準備したコンテスト用の `mt-eval contest register --manifest` — すべての行がデータベースレイヤーでIDバインドされます。キュレーターの介入や特権キーは不要です（現実的な制限についてはステップ4を参照）。
- ✅ **稼働中: エントリーは「手法（METHOD）」であり、翻訳結果ではありません。** コンテストへの参加は、ノードが「実行」できるものを渡すことによって行われます。参加者は公開開発セットを自己スコアリング（`mt-eval contest qualify`）してレシートを取得し、モデルまたは手法を提出します。保管者に承認を求める前に、ノードはそのレシートのスコアをご自身の開発セットのコピーで再実行し、不一致の場合は拒否します。ノードは提出物からレーンを選択します:
  - **レーンA — 宣言的モデル（推奨）。** 標準的なニューラルモデルは「データ」です: `mt-eval contest submit-model` は safetensors の重み + 宣言的トークナイザー + 設定を送信します — **コードなし、Dockerfile なし。** ノードはそれがコードフリーであること（pickle ではなく safetensors、`trust_remote_code`/`auto_map` なし、データ専用ファイル）を検証し、自身の信頼できるエンジン（`transformers`、`trust_remote_code=False`、オフライン）で重みを実行します。アーキテクチャはデフォルトで寛容です（エンジンがネイティブに読み込めるものはすべて許可）。慎重なホストは許可リストを固定できます。信頼できないものは一切実行されないため、サンドボックス化の必要がありません。`declarative-model` として公開され、手法の識別情報は**構造的にコードフリー**となります。
  - **レーンB — 実行可能バンドル（サンドボックスフォールバック）。** 実際にコードである手法向け: `mt-eval contest submit-method` は Dockerfile + エントリポイントを送信します。保管者が承認した後、**ご自身の**ノードがネットワークから隔離されたコンテナ（`--network=none` — 内部にはネットワークスタックが存在しません。読み取り専用ルート、ドロップされたケーパビリティ、サニタイズされた環境）内で実行します。事前に自動静的チェックが行われ、参照訳がコンテナ内に入ることは決してありません。**実行検証済み**の識別情報とともに `method-execution` として公開されます。
  どちらのレーンでも、バンドルのハッシュは認可リクエストに固定され（実行されるものは提案されたものであることが証明可能）、スコアは同じ集計専用パスを通じて公開されます。最大限の隔離を行うため、スコアリングマシンを完全なエアギャップにすることも可能です: 認可されたリクエストと Ed25519 署名済みのスコア専用バンドルはリムーバブルメディア（`mt-eval node relay` / `import-bundle` / `export-scores`）経由でやり取りされ、秘密テキストが接続されたマシンにさえ届くことはありません。これらのレーンに「まだ」含まれていないもの: ノードのハードウェア認証（IDは自己申告）、正式な紛争解決メカニズム、そして（レーンB特有として）削除されたネットワークスタックを超えるコンテナの強化（seccompプロファイル、マイクロVM。これがレーンAを推奨する理由です）。[現実的な制限事項](/docs/network/honest-limitations) を参照してください。
- ✅ **コミットメントレイヤーが稼働中（2026-09-07）。** エントリーの宣言（主要/対照的、トラック）、提出フェーズ、非公開結果（`hidden_until_close`）、およびエントリーが存在すると宣言されたコミットメントが編集不可能になる凍結は、ネットワークホスト型エンドポイント上のデータベースで強制されます。フェデレーションホストも、ハーネスに同梱されているマイグレーションを適用することで同じルールを取得します。古いエンドポイントに対しては、ハーネスは見せかけの動作をせず、基本セットにフォールバックしてその旨を通知します（`declarations_available: false`）。以下のステップで「*データベースが凍結 / 保留する*」と記述されている箇所は、文字通りその通りに機能します。
- 🔲 **開発中: しきい値署名。** `champollion seal-corpus` で封印されたセットの場合、保管者による M-of-N の承認は認可テーブルおよび監査テーブルに「記録」され、封印キーにはラベル付けされた単一キーペアのプレースホルダー（`champollion seal-corpus keygen`）が使用されます。オフラインノード（`mt-eval node seal`）で封印されたセットは、ノードに組み込まれた**キーセレモニー**（`mt-eval node ceremony`）を使用します: セットのキーは M-of-N に分割され、定足数によって認可された実行中にのみメモリ内で再組み立てされます。このセレモニーは実際の保管者と使用された実績がまだなく、そのシェアは v1 ではプレーンファイルです。どちらのパスにもしきい値「署名」はありません: エアギャップのスコアバンドル署名は単一のノードキー（`seal-corpus sign-keygen`）です。
- ❌ **設計上、存在しないもの:** Champollion がコーパスをホストすること、キーを保持すること、賞金基金を保持すること。参加者のバンドル（自身のモデルまたはコード）はノードへ向かう途中で当方のストレージを通過しますが、コーパスのコンテンツが通過することは決してありません。
- ❌ **罠として残さず削除された機能。** `contest submit-hypotheses`（2026-09-06廃止）はソース公開ブラインドセットの翻訳をアップロードしていました。`contest submit`（2026-09-06廃止）はご自身で公開したスコアをリンクしていました。どちらも現在はコンテストのエントリーパスではありません。ソース公開ブラインドラウンドは主催者用のオプションの診断としてのみ残り、自己申告スコアは引き続きオープンリーダーボード（コンテストではなく、コーパスと言語ペア方向でインデックス化された公開ボード）に属します。

以下のステップが 🔲 リストの項目に依存する場合、そのステップに明記されています。

## 取り決めの概要

| 誰が | 保持するもの | 保持しないもの |
|-----|-------|-------------|
| **あなた（コミュニティ／組織）** | コーパス、暗号化鍵（カストディアン経由）、賞金、授賞の決定 | — |
| **Champollion ／ネットワーク** | メタデータカード、暗号文ダイジェスト、承認・監査レコード、公開スコア | あなたのコーパスの内容、鍵、資金 |
| **手法開発者** | 自分の手法 | あなたのテストデータ — 彼らが見るのはスコアのみで、文章は見えません |

## 主催者の前提条件

ステップ1の前に、ノード側の実行に実際に何が必要かを把握してください：

- **node extra を含むハーネス:**
  `python3 -m pip install 'mt-eval-harness[node]'`（0.2.0以降。ハーネスが実行される任意の環境で動作する `python3 -m pip` を使用してください — 単体の `pip` はすべての仮想環境の `PATH` にあるとは限りません）。`[node]` extra は、`mt-eval node keygen`、保管者セレモニー、スコアマニフェストの署名が使用する `cryptography` ライブラリを追加します。通常の `python3 -m pip install mt-eval-harness` にはこれが含まれておらず、これらのコマンドは停止してこのインストールの必要性を提示します。
- **docker または podman** — 手法実行レーンに必要です。ノードは docker、次いで podman を自動検出します（`node.json` 内の `sandbox.runtime` はデフォルトで `null` です。固定したい場合はそこに明記してください）。どちらも `PATH` にない場合、`mt-eval node run-method` は何も実行する前に両方を挙げた1行のメッセージで拒否し、ランタイムがインストールされた後に実行できるようリクエストはそのまま保持されます。**フォールバックはありません**。`--network=none` によるコンテナの隔離が根幹となる保証であるため、コンテナランタイムなしでは何も実行されません。
- **Node.js 20.11+ および `champollion` npm CLI** — ハーネスは封印用暗号を再実装していません。`champollion seal-corpus`（動詞: `keygen`、`seal`、`open`、`sign-keygen`、`sign`、`verify`）が唯一の暗号実装（X25519-ECDH → HKDF-SHA256 → AES-256-GCM）であり、主催者ノードはこれを外部呼び出しします。
- **`~/.mt-eval/node.json` にあるノード設定。** すべての `mt-eval node` コマンドは、これがないと開始を拒否します。`mt-eval node init` はそこにスターター設定を書き込みます（`--print` は代わりにそれを表示します）。これには自己申告の `node_id`（すべてのリクエストフィンガープリントにバインドされます）と、開発セット、封印セット（`secret_set_id` + `secret_artifact`）、準備した場合は封印ホールドアウト（`holdout_set_id` + `holdout_corpus`。用意しなかった場合は両方のキーを削除）、および公開予選ゲート（`qualifier` + `dev_corpus`、0〜100の予選スケールでのしきい値）を指す `contests` マップが保持されます。`contest prepare`（ステップ1）を実行すると、`mt-eval node init --from-contest ./mytask` は `./mytask/local/manifest.json` からコンテストの値があらかじめ入力されたスターター設定を書き込み、残りの設定項目をリストアップします。適用されるマッピングは以下の通りです（手動で入力しても構いません）:

  | `local/manifest.json` | `node.json`（`contests.<contest-id>` 配下） |
  |---|---|
  | `contest.language_pair` | `language_pair` |
  | `secret.sealed_set_id` | `secret_set_id` |
  | `secret.corpus_sealed_artifact` | `secret_artifact` |
  | `holdout.sealed_set_id` / `holdout.corpus_sealed_artifact` | `holdout_set_id` / `holdout_corpus`（ホールドアウトがない場合は両方削除） |
  | `qualifier.corpus_file` | `dev_corpus` |
  | `qualifier.qualifier_id`、`corpus_card_id`、`threshold`、`metric`、`year` | `qualifier.*`（同名） |
  | `test_suites[].suite_id` / `sha256`、`test_suite_local_copies` | `test_suites[].suite_id` / `corpus_sha256` / `corpus_path`: `contest prepare` が読み取ったコピー（`--test-suite <id>=<path>`、または検出されたもの。固定バイトとともにこのマシン上にある場合）。それ以外の場合は `corpus_path` を設定 |
  | `secret.sealed_block.keyScheme` | `custody`: 単一キーペアに封印されたセットの場合は `single-key`（その後 `secret_privkey` を設定）、セレモニーの場合は `threshold-quorum` |
  | `registration.prize_terms`（`contest prepare` および `contest register` によって記録） | `prize_terms_sha256`: 規約の SHA-256、参加者が `--accept-terms` に渡すハッシュ（コンテストで賞金が宣言されていない場合は省略） |

  コンテストIDは、`contest prepare` に指定した `--slug` です（以下の例では `mytask`）。prepare はこれをマニフェストに記録し、登録によってそのIDの下にコンテストが作成されます。これは参加者が `contest qualify` や `submit-method` に渡すIDとなるため、開発版のリリース時に告知してください。`--contest-id` でオーバーライドできます。（IDが記録される前に作成されたマニフェストは、そのコンテスト、レシート、ノード設定ですでに使用されているため、名前に由来するID `"My Task 2026"` → `my-task-2026` を維持します。）どのマニフェストも `node_id`、`cards_dir`、`signing_key`、または秘密鍵ファイルを把握していないため、これらは手動で入力できるように `<...>` のまま残されます。
  その後、`mt-eval node ledger verify` は設定をチェックし、何をチェックしたかを報告します: 設定（保管情報、予選ゲート全体、ホールドアウトペア、ローカルカードインデックス）を読み込み、依然として `<...>` プレースホルダーのままになっている最初の値や、このマシン上に存在しない宣言されたファイルがあれば拒否し、各コンテストのセットとファイルを出力し、その後初めて認可台帳のハッシュチェーンを再生します（新しいノードではゼロ件）。
- **ノードが保持するローカル言語カードインデックス。** スコアリングでは実行対象の言語ペアが指定されますが、ノードがネットワーク経由で言語を検索することは決してありません。`node.json` の `cards_dir` を、ノードがスコアリングするすべての言語のカードを保持するディレクトリに向けてください（または `MT_EVAL_CARDS_DIR` を設定）。ローカルインデックスを持たないノードは、外部から取得するのではなく起動時に拒否します。どちらのインストール済みパッケージにも言語ごとのカードディレクトリは同梱されていないため、接続されたマシン上で `champollion` CLI を使用して、対象ペアの言語ごとに1つの `<code>.json` ファイルを作成してください:

  ```bash
  mkdir -p node-cards
  champollion network card eng --json > node-cards/eng.json
  champollion network card crk --json > node-cards/crk.json
  ```

  その後、`"cards_dir"` をそのディレクトリの絶対パスに設定します。エアギャップされたノードの場合は、オフラインバンドル（`mt-eval node bundle --out <dir> --include node-cards`）に入れて持ち込みます。これは `<dir>/artifacts/node-cards` に配置され、ノード上の `cards_dir` がそこを指すようになります。
- **サインイン。** 別途アカウント作成を行う手順はありません。IDを必要とする最初のコマンド（例: `mt-eval contest prepare --self-serve` や `mt-eval publish`）を実行すると、ブラウザで **GitHub または Google**（Supabase Auth）による OAuth サインインが開きます。そのアカウントのメールアドレスが、すべてのレジストリ行がバインドされるIDとなります — ご自身の組織が管理するアカウントを使用してください。
- **取り込み制限（スロットリング）。** 参加者の提出は、提出者ごとに**デフォルトで24時間あたり5件**にレート制限されています（探索的プロービング対策。コンテストごとに prepare 時に `--intake-daily-limit` で設定、または共有タスク版のデフォルトとして設定）。これを考慮してコンテストのタイムラインを計画してください。

**セルフサービス登録に関する現実的な注意点。** **デフォルトのネットワークホスト型エンドポイント**では、セルフサービス登録（`contest prepare --self-serve` / `contest register`）は現在、本番エンドポイントのガードにより停止します。その扉を開放するかどうかのポリシー決定が保留中であるため、CLI は本番プロジェクトへの書き込みを行わず、明示的なメッセージを表示して拒否します。フェデレーションホスト（独自の Supabase プロジェクト）には影響しません。デフォルトのホストでこのガードに遭遇した場合、それは現状の仕様であり、設定ミスではありません — [issue を作成](https://github.com/gamedaysuits/Champollion/issues)していただければ、登録手順をご案内します。

## ステップ 1 — 非公開テストコーパスを構築する

測定に使用するコーパスを設計し、最初から非公開に保ちます。コーパスの内容は、これまでに公開、投稿、またはモデルプロバイダーと共有されたことがないものにしてください。

- エントリ構造、難易度ティア、レジスターカバレッジについては [Corpus Design Framework](/docs/network/specifications/corpus-design) を、ツールについては [Corpus Creation cookbook](/docs/network/tutorials/corpus-creation) を参照してください。
- 封印前に流暢な話者によるエントリの確認を行ってください — [Speaker Validation Protocol](/docs/network/specifications/speaker-validation) は、手法レビューだけでなくコーパス QA にも再利用できるレビュー構造を説明しています。
- コーパスの**バージョン**ラベルを今決めてください（例: `v1`）。承認付与は特定のバージョンにバインドされるため、バージョン管理は単なる記録管理ではなくセキュリティモデルの一部です。

### コーパスの分割方法

1つのコマンドで、選択して記録したシード値から決定論的に、マスターコーパスからすべてのティアを生成します:

```bash
mt-eval contest prepare --corpus master.json --slug mytask --name "My Task 2026" \
    --pair 'eng>crk' --seed 20260906 --qualifier-threshold 35 \
    --dev-size 400 --secret-size 500 --sealed-holdout-size 250 \
    --test-suite <a public corpus card id> \
    --license <the licence the rights-holder grants> \
    --custodian-group <opaque id> --threshold-pubkey ./contest.pub.json \
    --out ./mytask
```

`--qualifier-threshold` は、ノードが封印セットおよび封印ホールドアウトで手法を実行する前に、その手法が公開開発セット上で到達しなければならないスコアです。これは **0〜100の予選スケール**に基づいています: 予選スコアは、公開された開発参照訳に対する開発出力の **コーパス chrF++**（sacreBLEU chrF、`word_order=2`）です — これはスコアリング基準の主要指標であり、同じ出力に対して `mt-eval run` カードがトップに掲げる数値と同じです。他の要素が合成されることはありません。完全一致（Exact Match）は診断用として横に並べて表示されますが、ゲート条件になることはありません。ノードが手法を再実行する際にも同じ数値が計算されるため、参加者のレシートとノードの測定結果は比較可能です。

このしきい値は、他の評価セットのスコアからではなく、この開発セット上で測定した chrF++ スコア（ベースラインの開発出力に対して `contest qualify` を実行）に基づいて設定してください。chrF++ の水準は言語やコーパスによって大きく異なります。
[スコアリング基準](/docs/network/specifications/scoring#how-runs-are-scored) 以前に廃止された複合指標を用いて登録された予選ゲートも引き続き機能します: そのしきい値は chrF++ スケールで読み取られ、qualify の実行時に毎回その旨が表示されるため、数値を確認するか新しい予選ゲートへローテーションしてください。

`--license` は必須です。これは公開される開発セットが提供されるライセンスを指定するもので、mt-eval が自動で選択することは決してありません。公開されたファイルには `dataset.license` としてこれが付与され、`mt-eval run`、`contest qualify`、`publish` がこれを読み取るため、参加者の実行は指定したライセンスによって制御されます。権利保有者の許諾内容を SPDX ID として使用してください。`CC-BY-4.0` の場合、参加者は任意のモデルサービスを使用して評価を行えます。`CC-BY-NC-4.0` などの非商用ライセンスの場合、リモートモデルは学習なしチャンネル経由でのみ実行されます。独自の規約（`LicenseRef-<name>`）の場合、権利保有者の許可が記録されるまでリモート評価は拒否されるため、参加者はローカルモデルを使用することになります。

公開されたファイルには、マスター自体のカード（`champollion network register-corpus` が `<file>.champollion.json` サイドカーを通じて作成したコーパスカード）およびそのエンベロープから読み取られた、マスターのその他の条件も記載されます: `dataset.do_not_train`、およびマスターがローカル限定としてマークされている場合は `dataset.transmission: "local-only"`（この場合、参加者は自身のマシン上のモデルでのみ開発セットを実行できます）。これらにはそれぞれどこから取得されたかを示す `dataset.terms_from` が付与されます。マスターのカードにトレーニング条件が記載されていない場合は、`--do-not-train true` または `false` を渡してください。このフラグはマスターの条件を厳しくすることはできますが、緩めることはできません（`doNotTrain: true` のマスターに対して `--do-not-train false` を指定すると拒否されます）。prepare はこれらの条件を出力し、マスターのカードで再配布が禁止されている場合は警告します: `public/` の公開は再配布にあたるため、権利保有者の同意が得られるまで公開しないでください。

| 分割 | 閲覧可能な対象 | 用途 |
|---|---|---|
| **公開開発セット**（`--dev-size`） | 全員 — ソース*および*参照訳が公開される | **予選ゲート**: 参加者は提出を行う前に、まずこのセットで自己スコアリングを行う必要があります（ステップ8） |
| **封印セット**（`--secret-size`） | ノードのみ — ソース*および*参照訳は暗号化されたまま | エントリーが実際にスコアリングされる対象 |
| **封印ホールドアウト**（`--sealed-holdout-size`、オプション） | ノードのみ | **第2の**封印分割。同じ実行内でスコアリングされ、コンテストを終了するまでスコアは非公開に保持されます |
| *ブラインドセット*（`--blind-size`、デフォルト0） | ソースは公開、参照訳は非公開 | 主催者自身によるオプションの診断ラウンド。エントリーパスでは**ありません**: コンテストへの参加は手法を提出することによって行われ、翻訳をアップロードすることは決してありません |

分割は互いに素であり、再現可能です: 同じコーパス、同じシード値であれば、常に同一の分割になります。そのレシピは主催者のローカルマニフェストに保持され、マシンから外に出ることはありません。

**重複する文は同一の分割に留まります。** 分割はグループ単位で互いに素（group-disjoint）です（`group-disjoint/1`、マニフェストの `split` ブロックに記録）。大文字小文字、句読点、空白を正規化した後も含め、ソースまたは参照訳を共有する行は1つのグループを形成し、グループ全体が丸ごと1つの分割に収まります。そのため、封印された行が公開開発セットの行を繰り返すことはありません。グループはシード値に従ってシャッフルされ、dev、blind、secret、holdout の順に配置されます。重複する文がないマスターの場合は、行ごとにシャッフルした場合とまったく同じ分割になります。グループ全体で要求されたサイズを満たせない場合、prepare は拒否し、重複行の数と対処法（重複を削除して各グループから1行を残すか、一部のグループを除外できるようにマスターのサイズを下回る合計サイズを要求する）を提示します。

**`public/` は公開可能、実行ログは `runs/` へ。** prepare はマーカーファイル `.champollion-releasable.json` を `public/` に書き込みます。実行ログ、レポート、翻訳キャッシュがそこに書き込まれることは決してありません: `mt-eval run` はその内部にある `--output-dir` や `--cache-dir` を拒否し、代わりに隣接する `runs/`（`<out>/runs/`）を指定します。また、MCP サーバーの `run_benchmark` は公開開発セット上での実行（しきい値設定のために実行するベースライン）を自動的に `runs/` に配置し、その旨を表示します。マーカーが存在する前に準備されたコンテストは、そのレイアウト（`local/manifest.json` の隣にある `public/`）によって識別されます。

**なぜホールドアウトを用意するのか。** 長期間のコンテストでは、単一の封印セットに対してもチューニングが行われてしまう可能性があります — すべての提出はある種のプロービングであり、十分な回数のプロービングがあればわずかな情報漏洩が生じます。同じ認可された実行内でスコアリングされ、終了時まで誰も数値を見ることができない第2の分割を用意することで、最後にクリーンな検証結果が得られます: 両者の間でシステムの順位に変動があれば、どれだけがチューニングによるもので、どれだけが真の翻訳性能によるものだったのかを把握できます。両方のセットは**単一の**認可でカバーされるため、保管者に追加のセレモニーの手間は発生しません。

**サードパーティ製テストスイート。** `--test-suite` は、すべてのエントリーが同様に実行される公開診断コーパス（他者が作成し、SHA固定され、公にダウンロード可能なもの）を指定します。これらの数値は**レポートされるのみで、ランキングには使用されません**: 主催者が設計していないセットに対しても、強力な封印セットスコアが維持されているかどうかを読者が確認できるようにするためのものです。Champollion は、隔離中、固定されていない、対象言語ペア用ではない、あるいは自身の分割のいずれかであるテストスイートを拒否します。

**すでに公開されている封印行は封印されていません。** `contest prepare` は、封印セットおよび封印ホールドアウトを、公開されているすべてのデータと比較します: 公開する開発セット（上記のグループ分割により重複はゼロに保たれます）、ブラインドソースの公開（存在する場合）、および宣言されたすべてのテストスイート。完全一致および大文字小文字、句読点、空白の正規化後の一致（分割時にグループ化するのと同じ比較）を検証し、重複を件数とともに表示して（例: 「30件中30行がテストスイート … にも含まれています」）、その件数を `local/manifest.json` に記録します。サードパーティ製スイートの場合、拒否するのではなく警告を発します: そのスイートは他者の公開テキストであるため、マスターからそれらの行を削除するかスイートを除外して再度 prepare するかは主催者の判断に委ねられます。スイートをチェックするために、prepare はその文を必要とします。準備作業中にダウンロードを行うことはなく、マシン上に既にあるコピーを使用します。`--test-suite <id>=<path>` でそのコピーを指定してください。その sha256 はレジストリの固定値と一致している必要があります。コピーが見つからない場合、警告には問題がなかったということではなく、スイートが**チェックされなかった**という旨が表示されます。マニフェストには prepare が読み取った各コピーのパスが記録されるため、`node init --from-contest` でノードにそれを指定できます。

宣言されたホールドアウトとテストスイートは「約束（コミットメント）」となります: 最初のエントリーが届いた時点でコンテストはそれらを凍結するため、コンテストの途中でテストスイートを追加したり削除したりすることはできません。

## ステップ 2 — 暗号化して YOUR インフラにホストする

コーパスを保存時に暗号化し（任意の現代的な AEAD スキーム — 例: `age`/x25519 または AES-256-GCM）、**暗号文**をあなたが管理する場所にホストします。Champollion は平文も暗号文も受け取りません。

公開するのは 1 つのアーティファクトのみです: **暗号文 blob の SHA-256 ダイジェスト**。

```bash
shasum -a 256 sealed-corpus-v1.age
# → 3b5f0c…e91a  sealed-corpus-v1.age
```

ダイジェストは公開されますが、データは公開されません。誰でも後から、評価に使用された blob が封印した blob とバイト単位で同一であることを検証できます — 所有なしの完全性保証です。これは[通常のコーパス登録](/docs/network/sovereignty/registering-corpora#1-registration-is-metadata-not-content)と同じ「コピーではなくハッシュ」の規律です。

## ステップ 3 — メタデータカードを登録する

標準のフェイルプライベート[登録レーン](/docs/network/sovereignty/registering-corpora)を通じてコーパスを登録します: `language_pair`、`license`、`attribution`、`do_not_train` を含むカードを作成します — **文章は含みません**。**private** 公開レーンを選択してください。次のステップの封印済みセット登録によって、コンテスト対象として有効になります。

## ステップ 4 — 封印済みセットとして登録する

封印済みセットとは、3 つの事項を公的記録に残す、内容を含まないレジストリエントリです:

| フィールド | コミットする内容 |
|-------|------------------------|
| `ciphertext_digest` | 「コーパス」として扱われる正確なバイト列 |
| `custodian_group_id` | アクセスを管理するグループの不透明な ID（同意なしに組織名や国名を公開しない） |
| `current_qualifier_id` | 封印済み実行を提案する前に手法がクリアしなければならない公開ラウンド |

登録は**自分のサインインからセルフサービスで行えます** — キュレーターの介在も特権鍵も不要です:

```bash
# Register a contest you prepared with `mt-eval contest prepare --no-register`
mt-eval contest register --manifest local/manifest.json

# Or do it in one shot at prepare time
mt-eval contest prepare … --self-serve
```

マニフェストはご自身のマシン上に留まります — 登録時に送信されるのは、コンテンツを含まないID、ダイジェスト、しきい値のみです。データが送信される前に、何が送信されるかを正確に確認できます: `contest prepare --no-register` は登録プランを出力し、`contest register` が書き込むすべての行を順番に表示します — 各封印セットのIDと暗号文の SHA-256（マシン上に封印されたまま残る行数を含む）、保管者グループ、予選ゲートのIDとしきい値、記録されたコミットメントを含むコンテスト行、ポリシー列、およびコンテストのメタデータにマージされたホールドアウト、テストスイート、賞金規約。このプランは行を送信するコードと同じコードによって構築されるため、送信される内容と異なるものが記述されることはあり得ません。すべてのレジストリ行は**IDにバインド**されます: データベースはそれを登録したサインイン済みアカウントを記録し、その後の編集に対してそのバインディングを凍結します。また、予選ゲートは**同一の**IDが登録した封印セットのみを制御できます。封印セットは隔離された状態で生成され（通常のコンテストのバックエンドとして使用されたり、公開リーダーボードにランク付けされたりすることは決してありません）、予選ゲートは安全な状態で生成され、登録にはレート制限が適用されます — これらはすべて、当方のクライアントを含むすべてのクライアントの下位にあるデータベーストリガーによって強制されます。レジストリ自体は公開読み取り可能であるため、エントリーが封印した内容と正確に一致しており、それ以外のものは含まれていないことを検証できます。

**現実的な制限事項。** セルフサービスの扉は登録のみに限定されています（データベースレイヤーでの挿入専用）。**予選ゲートのローテーションと封印セットの廃止は、引き続きキュレーターの介在が必要です** — [GitHub](https://github.com/gamedaysuits/Champollion/issues) から issue を作成するかプロジェクトにお問い合わせください。また、以降のステップで主催者スコアリングノードを実行すること（ライフサイクルの進行、認可の付与、監査操作）は、ご自身のノード上の別個のサービスクレデンシャル付きレーンで行われます — セルフサービスは公開レコードの作成までとなります。

## ステップ 5 — カストディアンと M-of-N ルールを選択する

あなたのコーパスへのすべての評価を共同で承認しなければならない人物または機関、および閾値（例: **5 人中 3 人**）を選択します。カストディアンは Champollion ではなくあなたのコミュニティに対して責任を負うべきです — コミュニティごとの条件の設定方法については [Data Stewardship](/docs/network/sovereignty/data-sovereignty) および [Ownership & Terms](/docs/network/sovereignty/ownership-transfer) を参照してください。

**率直な補足:** しきい値「署名」（M個の署名なしには文字通り発行できない付与）は**開発中**です。オフラインノードのキーセレモニー（`mt-eval node ceremony`、Shamir の M-of-N）は構築済みですが、実際の保管者との運用実績はまだありません。それ以外の点では、M-of-N ルールは記録されたプロセスとして強制されます: すべてのアクセスリクエストは**保留中（pending）**キューに入り、保管者の決定が記録され、認可されたリクエストに対してのみ付与が発行されます。各付与は**単一使用、時間制限付き、かつ特定の（手法、コーパスバージョン、評価ノード）フィンガープリントにバインド**され、ブロックされた試行を含むすべてのイベントは、**追記のみ、ハッシュチェーン化された、公開読み取り可能な監査ログ**に記録されます。データベースは、すべてのクライアントおよびキーの下位で不正な状態遷移を拒否します。現時点で防ぐことができないのは、プラットフォームオペレーター自体の侵害です — これを解決するのがしきい値署名であり、それがリリースされるまでは、「Champollion がキーシェアを一切保持しない」という点は現在検証可能な特性ではなく、目指して構築中の設計目標として捉えていただく必要があります。

## ステップ 6 — 賞金の設定と規約の宣言

賞金は任意です。**宣言された賞金規約がないコンテストには、単に賞金が存在しません** — これがデフォルトであり、劣ったコンテストというわけではありません。

賞金を提供する場合は、以下の項目を決定し、コンテストとともに公開してください:

- **金額と通貨。**
- **スポンサー** — 資金を提供する主体。
- **資金の保管場所** — 貴組織の口座、または指定されたコミュニティトラスト。**Champollion が賞金基金を保持、エスクロー、または送金することは決してありません。** 保管者の身元を事前に公開することが賞金の信頼性につながります。規約テンプレートの [スポンサー不履行リスクに関する注記](/docs/network/sovereignty/terms-templates#trojan-horse-risks) を参照してください。
- **しきい値条件** — [賞金仕様](/docs/network/specifications/prizes) に従って記述された、手法がクリアしなければならないスコア基準: chrF++ しきい値、必要な診断ゲート（最小 FST 受理率など — エントリーが通過すべきゲートであり、スコアではありません）、話者による検証要件、再現性。公開されたスコアから授与条件を検証できるようにし、基準がクリアされたかどうかについて貴組織（または当方）の言葉を鵜呑みにする必要がないようにしてください。
- **賞金規約** — エントリーそのものがどのように扱われるか。

### 賞金規約の選択

実行方法は決まっています: 主権的コンテストでは、参加者がモデルまたは手法を提示し、ご自身のノードがそれを実行します。その「後」にそれがどう扱われるかは主催者が選択でき、以下の3つのいずれかになります:

| 規約 | 参加者への提示内容 |
|---|---|
| `pass_to_holders` — *保持者へ譲渡* | 手法は主権的ベンチマークの保持者である貴組織に譲渡されます。勝敗に関係なく、貴組織がそれをスコアリングして保持します。 |
| `retain_ip` — *知的所有権（IP）を保持* | 参加者が所有権を保持します。貴組織はエントリーをスコアリングし、監査用に最大でも封印されたコピーを1部保持するのみです。 |
| `release_open` — *オープン公開* | 参加者は所有権を保持しますが、オープンライセンスの下で手法を公開する必要があります。その公開が賞金授与の条件となります。 |

詳細は規約から自動的に決まるため、複雑な表を埋める必要はありません: 主催者が保持するもの（`retention`）、権利の移転の有無（`rights`）、利用可能な用途（`host_use`）、参加者に公開義務があるかどうか（`release`）は、すべて選択したオプションから**導き出されます**。2つのオプションでは、1つのフィールドを絞り込むことができます:

- `retain_ip` の下では、`--prize-retention delete_after_scoring` を指定するとスコアリング完了後にアーティファクトが破棄されます（デフォルトでは封印された監査用コピーが保持されます）。
- `release_open` の下では、`--prize-release-timing` によって公開先を `required_before_scores` または `required_after_prize` に変更できます（デフォルトは `required_before_prize`）。また、`--prize-release-license` により、任意の OSI 承認ライセンス（`any_osi`）を受け入れる代わりにライセンスを指定できます。

完全な導出表、および支払い前に各オプションを検証する方法については、[賞金仕様 §2.1、条件7](/docs/network/specifications/prizes#condition-7-in-detail-the-term-is-one-choice-of-three) を参照してください。

```bash
# The term…
mt-eval contest prepare … --prize-disposition retain_ip

# …with the one narrowing that option offers
mt-eval contest prepare … --prize-disposition retain_ip \
  --prize-retention delete_after_scoring

# …or the same declaration from a JSON file
mt-eval contest prepare … --prize-terms my-terms.json
```

どちらを選択した場合でも、データが書き込まれる前に、規約はわかりやすい平易な言葉と **SHA-256** とともに出力されます。そのハッシュが承諾トークンとなります: 参加者が `--accept-terms <hash>` を渡し、その承諾がバンドル内にパックされ、コンテンツハッシュでカバーされます。ノードはそれ以外のものを承諾したバンドルを拒否します。規約はコンテストに最初のエントリーがあった瞬間に凍結されるため、読んだことのない規約に縛られる人はいません。

賞金額は意図的に規約の対象外となっています: 金額、通貨、スポンサーはコンテストの情報であり、手法を誰が所有するかに関する規約は、いくら支払われるかに関する規約とは性質が異なるためです。

## ステップ 7 — コンテストを作成する

封印済みセットを対象とするコンテストは、明示的な**封印レーン**を使用します。資格審査はフェイルクローズドです: 封印済みセットの登録が存在してアクティブでない限り、コンテストは拒否されます — また、コンテストを作成しても**誰にも**コーパスへのアクセスは付与されません。

```bash
mt-eval contest create \
  --name "EN→CRK Community Challenge 2026" \
  --corpus sealed-eng-crk-v1 \
  --language-pair "en>crk" \
  --visibility public \
  --use-context non-commercial \
  --prize-disposition retain_ip \
  --results-visibility hidden_until_close \
  --anonymize-until-close \
  --description "Community-custodied held-out set; scores-only; prize held by <your org/trust>."
```

これらのフラグのうち2つは、その後に何をしようとデータベースによって固定または凍結されます。さらに3つが**コミットメント**となります:

- `--use-context` はコンテストのIDの一部です: コンテストが登録された瞬間に固定され、変更することはできません（変更する場合は新しいコンテストを作成してください）。デフォルトは `non-commercial` です。
- 順位付けに使用されるメトリクスである `--primary-metric`（デフォルト: `chrf_plus_plus`）は、コンテストに最初のエントリーがあった時点で凍結されます。廃止された `composite` を指定する新しいコンテストは理由とともに拒否されます。[スコアリング基準](/docs/network/specifications/scoring#how-runs-are-scored) 以前に登録されたコンテストは引き続き動作します。
- `--visibility`（デフォルト: `public`）、`--description`、および受付がオープンしているかどうかは凍結されません。

以下の3つのコミットメントは、コンテストに最初のエントリーがあった瞬間に凍結されます:

- `--prize-disposition` / `--prize-terms` — ステップ6の規約。両方を省略した場合、コンテストには賞金がありません。
- `--results-visibility hidden_until_close` — ノードが測定したすべてのスコアは、コンテストを終了するまで**保留（非公開）**されます。これにより、自身の測定結果から封印セットに対するチューニングを行うことを防ぎます。これがデフォルトです。自身の記録においてコミットメントが明確になるよう、例ではこれを明示しています。ノードが完了するたびに各カードが公開されるライブリーダーボードを希望する場合は、`--results-visibility immediate` を渡してください。
- `--anonymize-until-close` — コンテスト開催中、参加者は順位表内で固定の仮名で表示されます。（これは主催者の順位ビュー向けです。オープンボードにカードが公開された後にカードが匿名化されるわけではありません。）

同じ3つのフラグは `contest prepare` および `contest register` でも利用可能であり、これらのインターフェースがコンテストを作成するため、ほとんどの主催者はここで設定することになります。`contest prepare --no-register` を使用すると、指定した登録フラグ（`--results-visibility`、`--anonymize-until-close`、`--primary-metric`、賞金フラグ、`--visibility`、`--use-context`、`--closed-intake`）が `local/manifest.json` に記録され、`contest register --manifest` 独自のフラグを渡さない限りそれらが適用されます（記録された値が置き換えられる場合はその旨が表示されます）。prepare は、登録を行う前に、指定した値かデフォルト値か、およびいつ変更不可になるかを含め、これらの規約をすべて出力します。その `--help` に各デフォルト値が記載されています。

*（`--corpus` の値は登録済みの `sealed_set_id` です。封印レーンは封印済みセット登録から**自動的に**選択されます — 追加フラグは不要です。封印済みセットは通常のコンテストを支援することは決してできず、通常の隔離済みデータセットはいかなるコンテストも支援できません。両方のルールはデータベースで、すべてのクライアントの下で強制されます。ステップ 4 で `contest register` または `prepare --self-serve` を使用して登録した場合、コンテスト行は**すでに存在します** — このステップをスキップしてください。`contest create` を手動で実行するのは、既に登録済みの封印済みセットからコンテストを組み立てる場合のみです。）*

## ステップ 8 — 手法はまず公開環境で資格審査を通過する

開発者は、ステップ1で公開した**公開開発セット**上で手法を構築し、スコアリングを行います。封印セットの `current_qualifier_id` はそのラウンドを指定し、手法はそのしきい値をクリアしなければ封印環境での実行をリクエストすることさえできません。これによりコーパスに対するプロービング圧力を排除できます: 公の場で真のパフォーマンスを示さない限り、封印セットを標的にすることはできません。

参加者は、1つのコマンドでこれをオフラインかつ自身で実行します:

```bash
mt-eval contest qualify <contest-id> --dev my-dev-output.txt \
    --dev-corpus <the dev corpus you released> \
    --system "acme-nmt" --method-class pipeline \
    --offline-qualifier-id <qualifier id> --offline-threshold <threshold>
```

予選IDとしきい値は、スコアリングが主催者から必要とする2つの情報ですので、開発版のリリース時に両方を公開してください。`contest prepare` で作成されたコンテストの場合、予選IDは開発コーパス自身のID（その `dataset.corpus_id`）となり、prepare は開発コーパスの説明にしきい値を書き込みます。2つの `--offline-…` フラグがない場合、qualify は代わりにコンテストデータベースからそれらを読み取ります。これは、参加者が接続しているエンドポイントに対象コンテストが登録されている場合にのみ機能します。コンテストが存在しない場合、またはデータベースに到達できない場合、qualify は停止し、参加者自身の引数が入力された上記のオフラインコマンドを出力します。

`--dev` は、参加者による開発セットの翻訳を、コーパス順の1行に1文の形式、エントリーIDをキーとするJSON形式、または `mt-eval run --corpus <the dev corpus>` wrote (or its `_report.json` による実行ログとして受け取ります。実行ログはエントリーIDごとに読み取られ、同一の開発コーパス上での実行であることがチェックされます。すべてのエントリーがスコアリングされる必要があるため、エラーとなったエントリーを含む実行ログは拒否されます。その後、サマリーには出力がその実行においてハーネスによって生成され、そのファイルから再スコアリングされた旨（およびその実行のコスト）が記載されます。ハーネスの外部で生成されたという扱いにはならず、プレーンな推論結果（hypotheses）ファイルのみがそのように記述されます。

**合格はまだ提出ではありません。** 判定が出た後、qualify は提出に関して現時点で判明している事項を伝えます。マシン上にフォルダが存在する手法プラグインの実行の場合、`submit-method` およびノードが実行するのと同じ静的スキャン（ネットワークライブラリ、シェルのネットワークツール、禁止されたファイルシステムパス）を実行し、モデルサーバーを呼び出すために `urllib` をインポートするプラグインなど、拒否される原因となるものを表示します。ハーネス独自の LLM パス（プロバイダー経由でアクセスするモデル）の実行の場合、現状のままでは提出できる手法が存在しない旨を伝えます: ノードはネットワークなしでエントリーを実行するため、モデルがバンドルの内部に含まれている必要があります（以下の「*手法が呼び出すモデルはすべてバンドルする*」を参照）。それ以外の場合、合格行には提出時に待ち受けているチェック項目が表示されます。これらによって判定やレシートが変更されることはありません。

予選スコア（ゲートとなる値）としきい値が、ともに 0〜100 の chrF++ 予選スケールで並べて出力され、そのスコアの内訳が表示されます: sacreBLEU シグネチャ付きのコーパス chrF++、その横に並ぶ他の標準メトリクス（混合されることはありません）、ゲート条件にはならない診断用の完全一致、およびスコアに関する注意事項。qualify は何も公開しません。開発出力の大部分がソーステキストの単なるコピーであるシステムは、スコアに関係なく拒否されます: 半数以上がソースと同一である場合（大文字小文字、アクセント、句読点を無視し、人名など参照訳自体がソースと同一である行を除外した上で判定）、参加者は翻訳を行っていないとみなされます。ノードが再実行する際にも、同じルールによって再度拒否されます。これにより参加者のマシン上に**予選レシート**が書き込まれ、`submit-model` および `submit-method` はこれがない提出物のビルドを拒否します。レシートはコンテストごと、およびシステムごと（`--system`）に保持されるため、2つのシステムを予選通過させた参加者は両方を保持できます。同じシステムを再度予選通過させた場合、以前のレシートも併せて保持されます。`submit-method` および `submit-model` は `--system` のレシートを使用し（デフォルト: `--name` のレシート、それ以外の場合はコンテスト唯一のレシート）、曖昧な場合は一覧を表示して拒否します。レシートは構造上自己申告であるため、これ自体がゲートとなるわけではありません。認可が付与される前に、**ご自身のノードが同一の開発セット上で提出された手法を再実行**し、自己申告内容と自身の測定結果を比較します。手法を過大申告したレシートはそこで却下され、却下理由には申告値と実測値が記載されます。

**レシートには元の実行が明記されます。** `--dev` が実行ログ（またはその `_report.json`）である場合、レシートにはその実行と実行されたモデルが記録されます: `mt-eval run --method local-model -m <model>` の場合、Hugging Face ID とリビジョン、またはファイル群の SHA-256 を含むモデルディレクトリが記録されます。モデルを指定していない `local-model` 実行ログは拒否されます — 初期の 0.2.0 ビルドではそのエンジンに `-m` が渡されず、代わりにフォールバックの英語→スペイン語モデルが実行されていました。その後、`submit-model` はパックする重みがレシートに記載されたファイルの中に存在することをチェックし、存在しない場合は両方のハッシュを挙げて拒否します。プレーンな推論結果ファイルからスコアリングされたレシートにはモデル名が記載されません。この場合はノードの再実行がそのチェックとなります。

**レシートとノード間の乖離はフラグが立てられます。** 両方の数値は同じ方法で計算されるため（同一のスコアラー、同一の開発セット、モデルの場合は同一のデコード長ルール）、同じ重みであれば誤差は1ポイント未満に収まります。ノードの数値とレシートの数値が、0〜100の予選スケールで **2.0 ポイント** を超えて異なる場合、ノードは再実行後にその旨を通知します。エアギャップされたノードもローカル台帳のチェック結果とともにその乖離を記録し、`node approve --offline` 時に保管者に向けて再度出力します。これはフラグであり、拒否ではありません: ゲートとなるのはノード自身の数値です。（2.0 という境界値は、敏感にフラグを立てるよう意図的に保守的に設定された選択です。これは主催者が再検討できるポリシー値です。）

### 参加者は提出前にすべてをリハーサルできます

バンドルが不正な形式であったことを、数日後の却下によって知るべきではありません。`mt-eval contest validate` は参加者のマシン上で、ネットワークを使用せずに、ノードが最初に実行する処理とまったく同じものを実行します:

```bash
# the static checks your node runs on a bundle
mt-eval contest validate ./my-bundle.tar.gz

# …and the qualifier: does my dev output line up, and does it clear the bar?
mt-eval contest validate ./my-bundle.tar.gz --contest <contest-id> \
    --dev my-dev-output.txt --dev-corpus <released dev corpus>
```

検出結果の表を出力し、拒否される項目がある場合はゼロ以外のステータスで終了します（ツール連携用の `--json`）。参加募集（Call for Participation）でこれを案内してください: 参加者にとってはコマンド1回の手間であり、主催者側にとっては却下対応の手間を省くことができます。

`validate` は何も書き込みません。レシートを書き込まずに開発出力を再スコアリングし、その後レシートをチェックします:

- **パックされたバンドル**（submit コマンドが書き込んだ `.tar.gz`）にはパッケージング時のレシートが含まれており、ノードが読み取るのはそのコピーです。したがって、validate はそのコピーに対してリハーサルの検証を行います。また、バンドルの手法名が何であれ、そのコピーの元となった参加者マシン上のレシートを検索し、そのシステム名を表示します。`--system` が別のレシートを指定している場合や、パッケージング以降に参加者がそのシステムを再度予選通過させた場合（バンドルには古いレシートが残ったままになります）には警告を発します。`--offline-…` フラグがない場合、予選IDとしきい値もそのコピーから取得されます。つまり、参加者が `contest qualify` に渡した値となります。検出結果にはその旨が表示されます。
- **チェック用に `--manifest` でパックされたソースディレクトリ:** validate は `submit-method` および `submit-model` が埋め込む予定のレシートを使用します。検索方法はそれらと同じです: `--system`、なければバンドルの手法名と同じ名前のレシート、それもなければコンテスト唯一のレシートです。

そのレシートが別の開発出力、別の開発ファイル、または別の予選ゲートを対象としている場合は警告します。レシートが存在しない場合も警告します。レシートは `contest qualify` からのみ生成されます。

これはあくまでリハーサルであり、出力にもそのように明記されます。ノード側でも依然としてネットワークなしでイメージをビルドし、コンテナを実行し、予選ゲート自体を再実行します。validate で問題が検出されなかったということは、「問題があることが*事前に判明しているわけではない*」ことを意味するのであり、本番の実行でスコアが出ることを保証するものではありません。

:::note[参加者の方へ: コンテストはどのエンドポイントにありますか？]
**ネットワークホスト型**のコンテストでは、エンドポイントのセットアップは不要です — ハーネスに同梱されているデフォルトのエンドポイントにコンテスト機構（予選ゲート、手法の提案、認可）が含まれており、`mt-eval contest submit-model` / `submit-method` はそれと直接通信します。ハーネス **0.2.0 以降**（`mt-eval --version`）が必要です。以前のリリースには `qualify`、`validate`、`rank`、`close` が含まれていません。ネットワークホスト型のコンテストは、主催者が上記の注意書きにある手順で登録された場合にのみ開設されるため、現在ほとんどのコンテストは**フェデレーション型**となっています。

**フェデレーテッド型**コンテスト — オーガナイザーが自身の Supabase プロジェクト上で機構を運用するため、提出物が私たちのストレージを経由しない — は、コンテスト資料とともにエンドポイントを公開します。提出前にエクスポートしてください:

```bash
export MT_EVAL_SUPABASE_URL=https://<contest-host>.supabase.co
export MT_EVAL_SUPABASE_ANON_KEY=<contest-anon-key>
```

ハーネスがコンテスト機構を持たないエンドポイント（例: マイグレーションが不足しているフェデレーテッドホスト）を指している場合、コマンドは *「このSupabaseエンドポイントではコンテストレーンがまだ利用できません」* というメッセージとともに停止し、どのエンドポイントと通信していたかを表示します。（フェデレーテッドオーガナイザーの方へ: コーパスリリースの隣にこれら2つの値を公開してください。`--node-id` および `--corpus-version`。）
:::

## ステップ 9 — 封印済み実行: リクエスト、承認、実行、スコア出力

各エントリーの流れ:

1. 封印セットに対して**リクエスト**が提出されます — `pending` に入り、（バンドルハッシュ、コーパスID、コーパスバージョン、`scores-only`、評価ノードの測定結果）の不変のフィンガープリントが付与されます。
2. ノードはバンドルに対して**独自の静的チェック**を実行します。コードエントリー（レーンB）の場合、実行可能かどうかの確認が行われます: コンテナランタイムが存在し、バンドルが宣言しているRAM、スクラッチディスク、実行時間が `sandbox` の上限内に収まっているかをチェックします。ここで不一致があっても、手法に対する不合格判定ではありません。拒否メッセージにはすべての不一致点（例: 「8 GB の RAM が要求されましたが、このノードの上限は 4 GB です (sandbox.max_ram_gb)」）が明記され、何も実行も却下もされず、リクエストはそのまま保持されます。`node.json` で上限を引き上げ、再提出なしで `mt-eval node run-method <id>` を再実行できます。または、参加者が拒否時に表示されたフラグ（例: `--ram-gb 4`）を用いて再パッケージ化することもできます。リソース要件はバンドルのハッシュに含まれるため、これは新しいリクエストとなります。その後、ノードは公開開発セットの自身のコピー上で、**参加者の予選申告を再実行**します。提出されたレシートは申告にすぎず、こちらが実測値となります。ここで不一致があれば却下されます — 保管者に承認を求める前、かつ封印セットを開く前の段階であり、却下理由には申告値、実測値、基準値が記載されます。コンテストが宣言した賞金規約と異なる規約を承諾したバンドルも、同じ時点で拒否されます。
3. **保管者が決定を下します**（M-of-N）。承認されると**認可（グラント）**が発行されます: 単一使用、有効期限付き、かつその正確なフィンガープリントに対してのみ有効です。
4. 評価は**貴組織の**ノード上のネットワーク隔離されたサンドボックス内で実行されます（`mt-eval node run-method`）: ネットワークスタックのないコンテナであり、参照訳はコンテナの外部に保持されます — または、最大限の隔離のために、署名されたスコア専用バンドルをリムーバブルメディアで持ち運ぶ完全エアギャップマシン上で実行されます（何がカバーされ、何がカバーされないかについては上記のステータスボックスを参照）。ダークノード（完全オフラインノード）は何もアップロードしません: 署名されたスコアバンドルを外部へ持ち出し、接続されたマシンから実行カードを公開します（`mt-eval node relay`）。封印ホールドアウトおよび宣言されたサードパーティテストスイートは**同一の**認可された実行内で実行されるため、保管者に追加のセレモニーの手間はかかりません。
5. **スコアのみが外部に出力されます。** `scores-only` の出力ルールはデータベースレイヤーで固定されており、コーパスの各エントリーごとのテキストが公開されることは決してありません。
6. コンテストが `hidden_until_close` を約束している場合、スコアはすぐには公開されません: 主催者のみが閲覧できる保留中の結果として**非公開（withheld）**にされ、`contest close` は順位付けを凍結する前に、保留されていたすべてのカードを公開します。保留された結果が失われることは決してありません。
7. すべてのステップ — リクエスト、投票、認可、使用、およびブロックされた試行 — は、主催者（および誰でも）が再生可能な公開ハッシュチェーン監査ログに追記されます。

## 手法の提出（参加者向け）— 2つのレーン

ほとんどの NMT エントリーは特殊なものではなく、標準的なファインチューニング済み Transformer とその重みです。これらに対しては、**推奨されるコードフリーのレーン**が用意されています — そして、真にコードである手法のためにサンドボックスへのフォールバックが用意されています。

### レーンA — 宣言的モデル（標準的な NMT 向け推奨）

手法が標準的なニューラルモデルである場合、**データ**（重み、トークナイザー、設定）として提出し、主催者は信頼できる独自の推論エンジンでそれを実行します。**Dockerfile なし、コードなし、サンドボックスなし。** 提出されたものは一切実行されないため、主催者の安全確認は任意のコードが安全であることを証明しようとするのではなく、判定可能なフォーマット検証となります — これは参加者にとってもコーパスにとっても、極めて強固な保証となります。

```bash
mt-eval contest submit-model <contest-id> \
  --model-dir ./my-model \          # config.json + model.safetensors + tokenizer.* at the ROOT
  --name "My NMT" --version 2.0 \
  --architecture MarianMTModel \    # must be on the organizer's trusted whitelist
  --method-class pipeline --paradigm neural-nmt \
  --track constrained --training-data-file ./training-data.txt \
  --parameter-count 92487 \
  --weights-license Apache-2.0 --weights-public \
  --developer "Your Name" --node-id <organizer-advertised-node-id> --agree
```

**NMT Forge でトレーニングされたモデル。** `nmt-forge export` はデプロイ可能なフォルダ `export/model/` を出力します。重み、設定、トークナイザーのほかに、`forge-model.json`（プライベートテストセットでのそのモデルのスコア、およびローカルパス）、`DEPLOY.md`、`champollion-plugin/` が含まれますが、これらはエントリーの一部ではありません。`submit-model` は transformers が読み取るファイル（重み、`config.json`、`generation_config.json`、トークナイザーファイル）のみをパックし、除外したすべてのファイルを出力するため、それら3つは自動的に除外されます。その `DEPLOY.md` のセクション6には、エントリーを構成するファイル群、`config.json` からのアーキテクチャ、重みファイルのヘッダーから読み取られたパラメータ数が正確なコマンドとともに出力されます。確認したファイルのみを正確に送信するには、それらを専用のフォルダにコピーし、`--model-dir` として渡してください:

```bash
mkdir -p lane-a
cp export/model/config.json export/model/generation_config.json \
   export/model/model.safetensors export/model/tokenizer.json \
   export/model/tokenizer_config.json lane-a/      # the files DEPLOY.md §6 lists
mt-eval contest submit-model <contest-id> --model-dir lane-a \
  --architecture MarianMTModel --paradigm neural-nmt …
```

**パラメータ数のカウント方法。** レーンAは `--parameter-count` を重みファイルと照合してチェックします。`safetensors` ヘッダー内のテンソルサイズを合算し、申告値との差が1%を超える場合は拒否します。これはファイルに保存されている値であり、torch 内でカウントされた値とは異なる場合があります。共有（tied）ウェイトは1回のみ保存されます。正弦波位置エンコーディングなど、モデルのロード時に再構築されるテーブルはまったく保存されない場合があります。拒否メッセージにはファイル側のカウントが表示されますので、その数値を申告してください。

バンドルが満たさなければならないルール（アップロード前にローカルで検証され、主催者ノードによって再度検証されます）:

- **重みは `safetensors` であり、pickle は不可。** PyTorch の `.bin`/`.pt`/`.ckpt` は pickle（ロード時に任意のコードを実行可能）であるため拒否されます。`model.safetensors` にエクスポートしてください（`safetensors` / `transformers` はこれを標準でサポートしています）。
- **主催者のエンジンがネイティブに読み込めるアーキテクチャ。** `config.json` の `architectures` は、ホストの `transformers` が実装している任意のアーキテクチャ（Marian、NLLB/M2M100、mBART、T5、Pegasus など多数）を使用できます — `trust_remote_code=False` では安全性がアーキテクチャ名ではなくコードフリーな形式によって担保されるため、ホストは**デフォルトで寛容**です（サポートされていないアーキテクチャは単純にロードに失敗し、何も実行されません）。慎重なホストは許可リストを公開する場合があります。`auto_map` や `trust_remote_code` は不可です — これらはカスタムコードを再混入させるものであり、常に拒否されます。
- **宣言的トークナイザー**（`tokenizer.json`、または `sentencepiece` `.model` + 語彙ファイル）、および**データファイルのみ** — バンドル内に `.py`、スクリプト、バイナリを含めることはできません。

**`submit-model` がパックするもの。** `--model-dir` のルートにあるデータファイル（`.safetensors`、`.json`、`.model`、`.txt`、`.spm`、`.vocab`、`.merges`）: 重み、設定、トークナイザー、生成設定です。それ以外のもの — `README.md` や `DEPLOY.md`、サブフォルダ、safetensors の横にある pickle チェックポイント — は除外され、コマンドは何を除外したかを一覧表示します。したがって、`nmt-forge export` が書き出した `model/` フォルダはそのままで提出可能です: その `DEPLOY.md` と `champollion-plugin/` は自動的に取り残されます。`contest validate` も同様にパックし、除外されたファイルを INFO 検出項目として報告します。ノード側のチェックは変わらず、データ以外のファイルを含むバンドルはノード側でも拒否されます。

**出力の最大長。** ノードは常に明示的な長さでデコードを行います: モデルが宣言している `max_new_tokens` または `max_length`（その `generation_config.json`）、それ以外の場合は1文あたり最大 `max(64, 4 × source tokens)` 個の新規トークン（デコーダーの位置数上限まで）。`mt-eval run --method local-model` も同じルールでデコードするため、参加者のレシートとノードの再実行結果が一致します。`submit-model` は適用される長さを表示してマニフェスト（`model.decodeLength`）に書き込み、ノードは適用した長さを実行ファクト（`execution.generation`）に記録します。明示的な長さがない場合、transformers ライブラリは約20トークンで停止してしまい、すべてのエントリーが途切れた出力でスコアリングされてしまいます。

主催者はこれを `trust_remote_code=False` でオフライン実行し、スコアのみが出力されます — `declarative-model` として公開され、手法の識別情報は**構造的にコードフリー**となります。（数GBの重みの場合: 下記と同様にスニーカーネットレーン用の `--bundle-out` を使用してください。）

### レーンB — 実行可能バンドル（コード手法向けサンドボックス）

手法が真にコードである場合 — パイプライン、LLM 指導型ハイブリッド、カスタムデコーダーなど — 宣言的に実行することはできないため、代わりにネットワークから隔離されたサンドボックスを経由します。これは（信頼できないコードの実行を拒絶するのではなく封じ込めるため）レーンAより明らかに脆弱なレーンですので、手法が標準的なモデルである場合は常にレーンAを使用してください。

**手法が呼び出すモデルはすべてバンドルしてください。** ノードはネットワークが一切ない状態でエントリーを実行するため、ホストされたモデル API を呼び出す手法（クラウド LLM に問い合わせる LLM 指導型ハイブリッド、MT サービスなど）は応答を得られず、スコアはゼロになります。LLM 指導型ハイブリッドが予選を通過できるのは、バンドル内に LLM が含まれている場合のみです: `/method` 配下のオープンウェイトであり、プロセス内またはエントリポイントが起動するローカルサーバーによって実行される必要があります。手法が実行時に読み取る辞書、FST、その他のデータについても同様です。（[手法仕様](/docs/network/specifications/methods#method-validity-and-dependency-classes) では、ホスト型 LLM を必要とする手法を依存関係クラス A1 と呼んでいます。これをサンドボックス内で実行できるようにするためのゲートウェイは構築されていません。）

**実行可能バンドルの規約は stdin/stdout です。** コンテナ内で、主催者のノードは正確に以下を実行します:

```
cat /eval/source.txt | <your entrypoint> > /output/translations.txt
```

ソース文が1行に1文ずつ stdin に渡され、1行に1つの翻訳結果を stdout に出力します。コンテナにはネットワークスタックがなく（`--network=none`）、ルートは読み取り専用で、書き込み可能な `/tmp` が提供されます。

**ファイルの配置場所。** `--method-dir` として渡したフォルダ内のすべてのものは、バンドル内の `method/` 配下にパックされ、実行時に重みを含めて **`/method` に読み取り専用でマウント** されるため、イメージ内に何もコピーする必要はありません。次のように配置してください:

```text
my-method/              ← --method-dir ./my-method
  translate.py          ← --entrypoint translate.py   (runs as /method/translate.py)
  weights/              ← read at /method/weights
  wheels/               ← vendored dependencies (see the Dockerfile below)
Dockerfile              ← --dockerfile ./Dockerfile
training-data.txt       ← --training-data-file ./training-data.txt
```

`--entrypoint` は `--method-dir` 内のスクリプトのパスです。バンドル内のパスである `method/translate.py` も受け付けられます。名前が2つの異なるファイルを指す可能性がある場合、コマンドは拒否して両方の名前を表示します。ファイルが見つからない場合は、検索したすべてのパスを表示します。

**最小限の Hugging Face transformers ラッパー：**

```python title="my-method/translate.py"
#!/usr/bin/env python3
import sys
from transformers import AutoModelForSeq2SeqLM, AutoTokenizer

tok = AutoTokenizer.from_pretrained("/method/weights")
model = AutoModelForSeq2SeqLM.from_pretrained("/method/weights")

for line in sys.stdin:
    inputs = tok(line.strip(), return_tensors="pt", truncation=True)
    out = model.generate(**inputs, max_new_tokens=256)
    print(tok.decode(out[0], skip_special_tokens=True), flush=True)
```

**Dockerfile はネットワークなしでビルドできなければなりません。** 主催者は `--network=none` を使用してイメージをビルドします — エアギャップビルドテスト*がそのまま*ビルドとなります — そのため、すべての依存関係は**バンドルにベンダリング**する必要があります（PyPI にアクセスする `pip install` はビルドに失敗し、プリフライト静的スキャンが送信前にネットワーク呼び出しを検出します）。メソッドディレクトリ内に wheel ファイルを同梱し、そこからインストールしてください：

```dockerfile title="Dockerfile"
FROM python:3.11-slim
# The build context is the bundle root: Dockerfile + method/
COPY method/wheels/ /wheels/
RUN python3 -m pip install --no-index --find-links=/wheels torch transformers sentencepiece
# Weights are NOT copied — /method is mounted read-only at run time.
```

**すべての提出物に必須の項目。** これらは必須であり、不足している場合はネットワーク処理に進む前にコマンドが停止します:

- `--method-dir`、`--dockerfile`、`--entrypoint`、`--name`、`--version`、`--method-class`、`--developer`、`--node-id`、および `--agree`。
- このコンテストおよびこのシステムに対する**合格した `mt-eval contest qualify` レシート**（ステップ8。複数予選通過している場合は `--system` で指定）。
- 申告として記録される2つの宣言: `--track constrained` または `--track unconstrained`（デフォルトはありません）、および `--parameter-count`。
- トレーニングされた重みを持つ手法の場合（`--parameter-count` が0より大きい場合）: `--weights-license <SPDX id or LicenseRef-…>`、および `--weights-public` または `--weights-private` のいずれかも必要。
- **トレーニングされた重みを持たない**手法の場合（ルールベース、辞書、FST）: `--parameter-count 0` を指定し、重み関連フラグは指定しません。提出物には、架空のライセンスを作成させるのではなく、重みライセンスおよびオープン性が「該当なし（not applicable）」として記録されます。
- **LLM にプロンプトを与える**手法の場合（何もトレーニングせず、プロンプトの作成のみを行う場合）: パラメータ数は、自身でトレーニングしたかどうかにかかわらず、バンドルが実行するすべてのモデル（LLM を含む）の合計パラメータ数となります。LLM のモデルカードまたは重みヘッダーから取得し、重みが公にダウンロード可能な場合は LLM のライセンスを `--weights-license` として `--weights-public` とともに渡してください。`--parameter-count 0` を指定するとシステムの実態を偽ることになります: 0 は手法がモデルを一切実行しないことを意味します。ホストされた LLM を呼び出す手法は、封印コンテストには一切参加できません: ノードにはネットワークがなく、そのような呼び出しを中継するゲートウェイは構築されていないためです（上記の「*手法が呼び出すモデルはすべてバンドルする*」を参照）。スコアリング対象の出力がプロバイダー経由であった場合、`contest qualify` はすでにその旨を警告しています。
- `--track constrained` を指定する場合: トレーニングに使用したデータのプレーンテキストリストである `--training-data-file`（何もトレーニングしていない手法の場合はファイル内にその旨を記述）。
- コンテストが賞金規約を宣言している場合: `--accept-terms <hash>`（これを指定せずに一度実行すると、規約が返信用のハッシュとともに出力されます）。説明が必須とされている場合: `--description-file`。

**手法が宣言するリソース。** バンドルには必要な RAM、スクラッチディスク、実行時間が記載され、主催者ノードはその `sandbox` の上限を超える要求を拒否します。デフォルトは、`mt-eval node init` が書き出すノードテンプレートの上限値です: `--ram-gb 4`、`--disk-gb 4`、`--max-runtime-minutes 30`、GPU なし。したがって、デフォルト設定でパッケージ化されたバンドルは、テンプレートのデフォルトで設定されたノード上で実行できます。手法がそれ以上のリソースを必要とする場合は、それらのフラグ（および `--gpu`）で明記し、主催者のノードがそれを許可していることを確認してください。上限を変更した主催者は、コンテスト情報とともにそれを公開する必要があります。ノードが拒否した場合、拒否理由には各値とノード側の許容値が表示されます。

次のコマンドで提出します：

```bash
mt-eval contest submit-method <contest-id> \
  --method-dir ./my-method --dockerfile ./Dockerfile \
  --name "My NMT" --version 1.0 \
  --entrypoint translate.py \
  --method-class pipeline --paradigm neural-nmt \
  --developer "Your Name" --node-id <organizer-advertised-node-id> \
  --track constrained --parameter-count 78000000 \
  --weights-license Apache-2.0 --weights-public \
  --training-data-file ./training-data.txt \
  --primary \
  --agree
```

主催者のノードは、保管者に実行の承認を求める前に、公開開発セットのコピー上でご自身の手法を再実行します。`--agree` は手法提出規約を承諾するものです。

**数GBの重み、または接続がない場合: スニーカーネットレーンを使用してください。** ホスト型の受付パスは、コンテストホストのストレージへの**単一の POST** として tarball をアップロードするため、そのホストのストレージアップロード制限を受けます — コードや小規模モデルには問題ありませんが、数GBのチェックポイントには適していません。バンドル規約自体ははるかに大きなアーティファクトを許容しています（最大 100 GB の tarball、最大 150 GB のビルド済みイメージ）。`--offline` はネットワークを一切使わずにバンドルをパッケージ化し、交換用ディレクトリを書き出します。接続がない状態では読み取るべきコンテスト行が存在しないため、主催者が公開した値も必要となります: `--bundle-out`、`--secret-set`、`--pair`、`--developer-email`、`--offline-qualifier-id`、および `--offline-threshold`（0〜100の予選スケールでのしきい値）。重みのないルールベースの手法をオフラインでパッケージ化する例:

```bash
mt-eval contest submit-method <contest-id> \
  --method-dir ./my-method --dockerfile ./Dockerfile \
  --name "My Rules" --version 1.0 \
  --entrypoint translate.py \
  --method-class pipeline --paradigm rule-based \
  --developer "Your Name" --developer-email you@example.org \
  --node-id <organizer-advertised-node-id> \
  --track constrained --parameter-count 0 \
  --training-data-file ./training-data.txt \
  --agree \
  --offline --bundle-out ./exchange \
  --secret-set <sealed-set-id> --pair 'eng>crk' \
  --offline-qualifier-id <published-qualifier-id> --offline-threshold 35
```

交換ディレクトリはリムーバブルメディア（または双方が信頼するチャネル）で主催者に届けられます。主催者は `mt-eval node import-bundle` でそれを取り込みます。バンドルの SHA-256 はいずれの方法でも認可リクエストに固定されるため、実行されるものは提案したものと証明可能な形で一致します。

**主催者の方へ: オフラインの提案は、オンラインの場合と同様に保管者の承認を待ちます — そしてノードはステップ9の順序で最初にそれをチェックします。** これは「保留中（pending）」のリクエストとして到着し、エアギャップされたノードはデータベースもサービスキーも使用せずに、ノード自身のチェック結果と保管者の決定の両方を記録します:

```bash
mt-eval node import-bundle ./exchange               # stages it: PENDING custodian approval
mt-eval node run-method <request-id> --offline      # the node's checks: re-runs the entrant's qualifier, checks the container runtime
mt-eval node list --offline                         # what is staged, checked, approved or waiting, and the next command
mt-eval node approve <request-id> --offline --actor <custodian>
#   or: mt-eval node deny <request-id> --offline --actor <custodian> --reason "…"
mt-eval node run-method <request-id> --offline      # the sealed run: refuses until the approval is recorded
mt-eval node export-scores ./exchange               # signed scores, or the signed refusal
```

保留中の提案に対する最初の `node run-method --offline` は、封印されたものを何も開きません。公開開発セット（ご自身の `node.json` が宣言している `qualifier` + `dev_corpus`。`node init --from-contest` が両方を入力します）上で参加者の予選を再実行し、コードエントリーの場合はコンテナランタイムが存在すること、およびバンドルが宣言した RAM、スクラッチディスク、実行時間が `sandbox` の上限内に収まっていることをチェックします。合格すると、ノードのハッシュチェーン化されたローカル台帳に記録されます。予選基準を満たさなかった場合はそこで拒否され、ノードの却下として記録され、署名された拒否通知として返送されます。保管者への問い合わせは行われません。エントリーを実行できないノード（ランタイムがない、上限が小さすぎる）はノードの問題として拒否し、何も記録しません。リクエストはそのまま保持されます。

`node approve --offline` は、このリクエストの正確なフィンガープリントおよびバンドルに対する合格チェックが台帳に記録されるまで拒否し、そのエラーメッセージには最初に実行すべきコマンドが示されます。その後、同じ台帳（保管者シェアのセレモニーが使用するもの）に投票と認可を書き込み、承認の根拠となったチェック内容を明記したノードの `signing_key` で署名された決定レコードを書き込みます。2回目の `node run-method --offline` は、封印されたものが実行される前にこれら3点すべてをチェックするため（台帳が検証され、インポートされたフィンガープリントの下でこのリクエストが認可されていることが示され、署名されたレコードが検証されてこのリクエストを指定していること）、保留中の提案がオペレーターの独断だけで実行されることは決してありません。その後、封印セットが開かれる前に、ランタイムチェックと予選の再実行が行われます。却下も同様に記録され、署名された拒否通知として参加者に返送されます。保管者はチェックの成否にかかわらず、どの時点でも却下することができます。
すでに認可された状態で届いたリクエスト — リレーエクスポート（コンテストデータベースで認可済み）または `node stage-request`（ステージング主催者が認可を兼ねる）— は、2回目の決定を必要としません。

**主催者の方へ：エアギャップマシンにベースイメージをプリロードしてください。** イメージビルドは `--network=none` で実行されるため、Dockerfile の `FROM` ベースイメージはマシンのローカルイメージストアに既に存在している必要があります。接続済みのマシンでは `docker pull python:3.11-slim && docker save -o base.tar python:3.11-slim` を実行し、`base.tar` をバンドルと一緒に持ち込んでください。エアギャップマシンでは、`mt-eval node run-method` を実行する前に `docker load -i base.tar` を実行してください。使用するベースイメージについては、公開するコンテスト資料で参加者と事前に合意してください。

## ステップ 10 — 順位付け、終了、エクスポート

スコアのみの結果は、他の実行と同様に封印セット評価としてマークされ、[リーダーボード](/docs/network/leaderboard/rules) に公開されます。コンテスト独自の順位付けは、主催者自身が構築、凍結、公開を行います:

```bash
mt-eval contest open-intake <contest-id>     # entry intake on — submit-model / submit-method admitted (owner only)
mt-eval contest close-intake <contest-id>    # intake off — work already received still scores
mt-eval contest rank <contest-id> --json     # provisional ranking, any time
mt-eval contest close <contest-id>           # one-way: freezes the ranking, shuts intake
mt-eval contest export <contest-id> --format csv --out results.csv
```

`rank` の動作（ルールに記載できるように説明します）: エントリーは、コンテストに**記録された主要メトリクス**（作成時は `--primary-metric`、デフォルトは chrF++）で順位付けされ、次いで chrF++ → BLEU → COMET → 提出日時が早い順となります。**デフォルトでは検証済みのみ**（ノードが公開した実行カード）を対象とし、非表示にした自己申告カードがあればそれもカウントします。隣接するすべてのペアには、ラベル付きの同着（タイ）判定が付与されます: セグメントごとの行が存在する場合はセグメントごとの対応のある有意差検定、そうでない場合は **95% 信頼区間の重複**、それ以外はスコアの一致。**封印コンテストがセグメントごとの行を公開することは決してない**ため（設計上、集計値のみ）、対応のある検定は代わりにご自身のノード上で実行されます。コンテストを終了する前に、ノード上で `mt-eval node verdicts --contest <id> --out verdicts.json` を実行してください。署名された判定のみ（ペアごとの p値、スコア差、信頼区間、セグメント数 — テキストは含まれません）が書き出されます。その後、`--node-verdicts verdicts.json --verify-key <the node's .pub.json>` を指定して終了処理を行います。判定データがない場合、同着は信頼区間の重複から判定されます。どちらの場合も、出力には使用された根拠が明記され、同着となったシステムは同じ順位を共有します（`1, 1, 3`）。

`close` は元に戻せない不可逆な操作です。記録されたメトリクスで順位付けを行い、提出物のスコアリングがまだ進行中の間は拒否し（強制終了フラグを指定しない限り）、表を表示して確認を求めた上で、順位付けをコンテストレコードに凍結します。`export` は、Findings（調査報告）や結果ページ向けに、その凍結された結果を JSON または CSV としてそのまま返します。他のセット（完全秘密の T2 セット、迷い込んだ開発セットカードなど）でスコアリングされたカードは個別にリストされ、メインの順位付けに混ざることは決してありません。

### 結果の公開タイミングの決定

作成時に行う2つの約束（コミットメント）は、後から密かに変更することはできません — コンテストにエントリーがあった瞬間に、データベースが両方を凍結します:

```bash
mt-eval contest create … \
  --results-visibility hidden_until_close \   # no score is visible while the contest runs
  --anonymize-until-close                     # pseudonyms in YOUR ranking artifacts
```

**実際にスコアを非表示にするのは `--results-visibility hidden_until_close` です。** この設定の下では、ノードがスコアリングしたすべてのカードは公開されずに保留されます: 手法は実行され、認可は消費され、カードはそのまま構築、検証、保存されます — 単にボード上に表示されないだけです。`contest close` は、保留されていたすべてのカードを**まず**公開し、その後に順位付けを構築して凍結するため、何も失われることはなく、凍結された結果には保持しているすべてのものがランク付けされます。これは強制終了（force close）の場合でも同様に行われます: 強制とは処理中の順位付け作業を打ち切るためのものであり、コンテストが開示すべきスコアを非公開のままにすることではありません。凍結されたスナップショットには、終了処理によって公開された結果が正確にリストされます。

保留中（withheld）は**記録された状態であり、失われた実行ではありません**: 保留されたカードを編集することはできず、どこに公開されたかを示すポインタは一度書き込まれると二度と変更されません — これらはすべて、あらゆるクライアントの下位にあるデータベース内で強制されます。コンテストの開催中、`rank` は保留されている結果の数を通知するため、暫定的な順位付けが不完全であるにもかかわらず完全なものであると誤認されることはありません。

**`--anonymize-until-close` の役割はより限定的であり、その内容を正確に把握しておく価値があります。** これはコンテスト開催中、*主催者側の* 順位付けアーティファクト（`rank` の表、その JSON、CSV）において、参加者名を決定論的な仮名に置き換えるものであり、`close` によってそれらが開示されます。公開リーダーボードを匿名化するものでは**ありません**: すでに公開されたカードには、エントリーが宣言した署名が表示されます。終了前に参加者同士が互いの結果を見られないようにしたい場合は、`--results-visibility hidden_until_close` を使用してください。このフラグはその代わりにはなりません。

手法がステップ6で公開したしきい値条件（自動化されたゲートではなく、貴コミュニティのゲートである [話者による検証](/docs/network/specifications/speaker-validation) を含む）をクリアした場合、主催者自身の公開規約に従って、**主催者**（または貴組織のトラスト）が賞金を授与します。Champollion の役割は測定の完了をもって終了します。
