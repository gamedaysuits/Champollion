# Sovereign Eval Node — ハードウェアとエアギャップ運用

Sovereign Eval Node（ソブリン評価ノード）は、**あなた**が管理するマシンであり、機密のテストセットを保持し、それに対して翻訳メソッドを評価します。メソッドがデータの場所に移動し、データ自体は決して移動しません。スコア、そしてスコアのみが出力されます。

このページは実践的な仕様書です。購入（または再利用）すべきハードウェア、そのセットアップ方法、そして「テストセットがマシンから決して離れていない」ということを、単なる信頼に基づく約束ではなく、証明可能な事実にするための運用規律について説明します。

:::info[現在提供されている機能と進行中とマークされている機能]
主催者ノードソフトウェアは`mt-eval`で**現在提供されています**。[ソブリンコンテストガイド](/docs/network/sovereignty/run-a-sovereign-contest)を参照してください。コンテストの準備と封印、**管理者が承認を求められる前にノード自身がすべてのエントリーに対して再実行する**公開予選ゲート、しきい値制御によるスコアリング、およびインポートスキャンを備えたネットワーク隔離されたメソッド実行環境が含まれます。ノードが受け付けるのは**モデルまたはメソッド**であり、ノードが実行可能な成果物です。公開ソースのブラインドセットの翻訳をアップロードする形式は、2026年9月6日にコンテストのエントリーパスとしては廃止され、該当する操作コマンドも削除されました。公開ソースのラウンドは、オプションの主催者用診断ツールとしてのみ残されており、自己申告によるスコアはオープンリーダーボード（コンテストではなく、コーパスと言語ペアの方向によってインデックス付けされた公開掲示板）に掲載されます。
**§4 のしきい値キーセレモニーと保存時封印（sealed-at-rest）ワークフローも現在提供されています**: `mt-eval node ceremony init|share|verify|restore`、`mt-eval node
seal`、実行時に提示されるクォーラムシェア
（`node run-method --offline --share …`）、ハッシュチェーン化されたローカル承認台帳（`node ledger verify|head`）、署名済みスコアマニフェスト
（`node sign-manifest` / `node verify-manifest`）、および §2–§3 のエアギャップツール（`node bundle`、`node manifest`、`node egress-check`）。スコアバンドルは**ノード上で Python によって**署名されます（オフラインバンドルには Node.js ランタイムは不要です）。分離署名（detached-signature）の同一フォーマットはどちらの実装でも検証できます。主催者側の**リクエストステージングも提供されています**:
`mt-eval node stage-request` は、バンドルファイルからデータベースを一切使わずに（リハーサルや、ネットワークに一切接続しないデプロイメント用）、オンラインリレーが生成するものとまったく同じ交換リクエストを書き出します。これはインポート時と同様に事前検証され、ノードの ID に紐付けられます。返されるスコアはマニフェストによって検証可能ですが、公開の根拠となる認可レコードが存在しないため、リレーによる公開は行われません。単一キーペアの代用機能は、主催者がリファレンスを完全に保持しているコンテストにのみ残されています。どのレーンが使用されているかは、すべての画面に明示されます。率直に言えば、v1 に**含まれない**ものは以下のとおりです。ハードウェアリモート構成証明（TEE）は謳っておらず（§5）、プラットフォーム側のしきい値*署名*（ホストされたインフラに対するカストディアンのスマートフォンによる承認）は将来の作業です。ソブリンノードでは、マシン上で M of N 個のシェアを物理的に提示することによって保管・管理権限が行使されます（§4）。暗号技術について正確を期すならば、これは Shamir の M-of-N 秘密分散法であり、**承認された実行中にノードのロックされたメモリ内でキーが再構成され**（その後ゼロクリアされます）、マルチパーティ計算（MPC）*ではありません*。キーはオフラインマシン上に一時的に復元された状態で存在します。最後に、コミュニティの同意ゲートが開かれるまで、このレーンは**合成データのみ**に対して実行されます。実際のコーパスはその同意を待つことになります。
:::

## 1. リファレンスハードウェア

エグゼキューターは、ローカルNMTデコード、FST/形態素解析の検証、メトリクス計算など、自己完結型のメソッドを実行します。エアギャップ内ではクラウド呼び出しは一切発生しません（LLM-APIメソッドは、まさにエアギャップノードが拒否するクラスです。[ベンチマーク仕様](/docs/network/specifications/benchmark)のメソッドクラスを参照してください）。

| 階層 | 仕様 | 適合 | 概算費用 (2026年) |
|---|---|---|---|
| **最小** (動作可能) | 4コア x86_64 または Apple/ARM、16 GB RAM、500 GB SSD | メトリクス + FST評価、小規模NMTモデルのCPUデコード (低速だが正確) | US$0 (予備のノートPC) – $400 (中古) |
| **推奨** | 8コア、32 GB RAM、1 TB NVMe、NVIDIA GPU ≥ 12 GB VRAM (例: RTX 4070クラス) | 完全なテストバッテリーの快適なNMTデコード、並列メソッド評価 | 約US$900–1,600 (小型ワークステーション) |
| **機関向け** | 16コア、64–128 GB RAM、2 TB NVMe、24 GB+ VRAM | 多数のメソッドのコンテスト、大規模バッテリー、アーカイブされた暗号文ストア | 約US$2,500–4,000 |

すべての階層における必須要件：

- **無線通信機能がないこと、またはオフになっていることを証明できること。** 最適：Wi-Fi/Bluetoothカードが搭載されていないデスクトップPC。許容範囲：ワイヤレスカードが物理的に取り外されている、またはファームウェアで無効化されているノートPC。「機内モード」はエアギャップではありません。
- **ケーブルを抜いたままにできる有線NIC。** ケーブルがないことは、最も監査しやすいネットワーク制御です。
- **2つの専用USBドライブ**（INおよびOUTのラベル付き — §3を参照）。理想的には、ファームウェアで他のポートを無効化したマシン。
- **フルディスク暗号化**（Linuxの場合はLUKS）。これにより、盗難されたノードはただの文鎮になります。また、電源が不安定な場合はUPS（無停電電源装置）を使用してください。バッテリーの途中で中断された評価は回復可能ですが、わざわざ試す必要はありません。

## 2. ソフトウェアのセットアップ（1回のみ、約1時間）

1. **LAN ケーブルを抜いた状態で**、USB インストーラーから現行の Linux LTS（Ubuntu/Debian）をインストールします。インストール時にフルディスク暗号化を有効にしてください。
2. ハーネスがインストールされている（`python3 -m pip install mt-eval-harness`、0.2.0 以降）別のオンラインマシンで、オフラインバンドルをビルドします。
   `mt-eval node bundle --out <dir>` は以下の 4 つの処理を実行します:
   - インストールされているハーネスとその依存関係を wheel 化する（または `--wheel <file>` を指定して特定の wheel を対象とする）。
   - ハーネス内に同梱されているハッシュ固定リストに基づいて暗号化ライブラリを取得する。
   - すべての `--include` 成果物をコピーする。
   - すべてのファイルに対する sha256 マニフェストを書き出す。

   ノードがスコアリングするすべての言語の**言語カード**を含めます（`--include <cards-dir>`）。ノードはローカルのカードインデックスから実行対象の言語ペアを指定し、外部から取得することはありません。インストールされたどちらのパッケージにも言語ごとのカードディレクトリは同梱されていないため、ここで `champollion` CLI を使用して言語ごとに 1 つの `<code>.json` を書き出し（`champollion network card eng --json >
   node-cards/eng.json`、続いてもう一方の言語についても同様に実行）、`--include node-cards` を渡します。ノード上では `<dir>/artifacts/node-cards` に配置されるため、`cards_dir` でその場所を指定します。ノードに必要なものはすべて、IN ドライブを経由して一度だけ転送されます。ノードが実行するのと同じ Python バージョン（3.11 または 3.12）でビルドしてください。固定リストはそれ以外のバージョンを拒否します。
3. バンドルを IN ドライブで転送します。インストールする前に、**ノード上で**すべての成果物の sha256 をマニフェストと照合して検証します（`mt-eval node bundle --verify <dir>`）。その後、同梱の wheel からのみインストールします:
   `python3 -m pip install --no-index --find-links <dir>/wheels 'mt-eval-harness[node]'`。
   `[node]` エクストラは、`mt-eval node
   keygen` and the custody ceremony need; a plain `mt-eval-harness` インストールには含まれていない `cryptography` ライブラリです。
4. ノードの署名用キーペアを作成し（`mt-eval node keygen`）、その公開鍵側を記録します。誰でもスコアマニフェストを検証できるように、これを公開することになります（§5）。
   ノードには、ネットワークなしのコンテナ内で提出された各メソッドを実行するための **Docker**（または Podman）も必要です。`PATH` にどちらも存在しない場合、`mt-eval node run-method` は両方の名前を挙げた 1 行のエラーで拒否し、リクエストは実行可能な状態のまま維持されます。また、`~/.mt-eval/node.json` にノード設定が必要です。このファイルには、ノード名、カードディレクトリ（`cards_dir` または `MT_EVAL_CARDS_DIR`）、および対象とするコンテストが指定されます。
   `mt-eval node init` は、スコアリングノードが読み取るすべてのキーを含むスターター設定を書き出します。これには、公開予選ゲート（ノードが封印されたセットを開く前にすべてのメソッドに対して再実行する `qualifier` + `dev_corpus`）や、封印されたホールドアウトのスロット（`holdout_set_id` + `holdout_corpus`。ホールドアウトのないコンテストの場合は削除してください）が含まれます。
   `mt-eval node init --from-contest <out>` は、`contest prepare` が書き出したマニフェストからコンテストの値を入力します（マッピングについては[ソブリンコンテストガイド](/docs/network/sovereignty/run-a-sovereign-contest#organizer-prerequisites)に記載されています）。
   その `sandbox` ブロックはノードのリソースポリシー（4 GB RAM、4 GB スクラッチ領域、1 回の実行あたり 30 分、GPU なし）であり、`contest submit-method` はデフォルトでまさにこれらの値を宣言するため、変更する場合はその上限値をコンテスト情報とともに公開してください。
   そのゲートの半分しか宣言していないノード設定は、起動時に拒否されます。
   `mt-eval node ledger verify` は記入済みのファイルをチェックします。未記入のまま残っている `<...>` の値や、ノード上に存在しない宣言されたファイルが最初に見つかった時点で拒否し、チェックした内容を出力して、ローカル台帳のハッシュチェーンを再生・検証します。リクエストをノードに中継する接続マシンには、データベースの **service-role キー**（`MT_EVAL_SUPABASE_SERVICE_KEY`）も必要です。このキーは、エアギャップ環境のノード自体には一切必要ありません。
5. それ以降、マシンがネットワークに接続されることは決してありません。また、封印された実行を行うことで、事前にそれを証明できます: `mt-eval node egress-check`（ノード設定内の `assert_airgap` でも自動的に強制されます）は、ルーティング、プローブ、または DNS によって外部への経路が検知された場合に実行を拒否します。OS のアップデートは、バックグラウンドサービスではなく、バンドル化されハッシュ検証された計画的なイベントとして実施します。

## 3. 転送の規律（各コンテスト、双方向）

エアギャップは製品ではなく、*手順*です。その手順は以下の通りです：

- **IN ドライブ**の携行内容: 提出されたメソッドまたはモデルのバンドル、およびそのマニフェスト。何かが実行される前に、ノードは各パッケージのハッシュをマニフェストと照合して検証し、インポートスキャンを実行します（ネットワークライブラリをインポートするメソッドは拒否されます — この機能は現在提供されています）。
- **OUT ドライブ**の携行内容: 署名済みスコアマニフェスト（集計スコア、それらが属するメソッド/設定のハッシュ、監査ログの先頭）のみであり、*それ以外は一切含みません*。セグメントごとの出力は主催者の管理下でノード上に保持されます。それらを公開するかどうかは、コミュニティによる個別の慎重な決定事項です。
- 1 つのドライブは常に単一方向のみに使用します。ノードに接続されたドライブをオンラインマシンで自動マウントしてはなりません。`noexec,nodev` でマウントし、手動でマニフェストをコピーしてください。
- `mt-eval node manifest write <drive> --direction in|out` は、受け渡し前にドライブ上のすべてのファイルをハッシュ化します。受け取り側の `mt-eval node manifest verify` は、追加、変更、または欠落しているものがあればすべて拒否します。
- すべての受け渡し（日時、ドライブ、マニフェストハッシュ）をノードの紙の記録簿またはノード上のログに記録します。退屈であることこそが重要です。ログこそが、「それ以外の何かが持ち出されたことはないか？」という問いに対して証拠をもって答えるための手段となります。

## 4. キーの管理（M-of-N、コミュニティ保持）

封印されたテストセットは保存時に暗号化されています。復号には、長老評議会、言語統括機関、教育機関など、**コミュニティが選定した**カストディアンが保持するキーシェアのクォーラム（定足数）が必要です。この設計ではプラットフォームにシェアが一切割り当てられないため、Champollion も、いかなる単一のカストディアン単独でも、封印されたセットを復号することはできません。なお、以下のセレモニーは実際のカストディアンを交えて実施された実績はまだありません。

セレモニー（1回のオフラインセッション。提供されているツールで自動化されます）：`mt-eval node ceremony init` はノード上でセットキーを生成し、それをN個のシェアに分割し（任意のM個で再構築可能。それ未満では何も明らかになりません。この分散は情報理論的なものです）、同時にキーをゼロクリアします。`ceremony share` は、各管理者のシェアをトークン用のファイルと印刷可能な紙のバックアップとして出力します。`ceremony verify` は、配布されたコピーが再構築可能であることを証明します（何も永続化しません）。`ceremony share --wipe-originals` then destroys the node's own copies. `mt-eval node seal` は、コーパスをセレモニーの公開鍵で暗号化します。ノードは暗号文とコンテンツを含まないメタデータカードのみを保存し、それ以外は何も保存しません。それ以降、評価を実行するには、管理者がN個中M個のシェアを物理的に提示する必要があります（`node run-method --offline --share …`）。キーは**エグゼキューターのロックされたメモリ内でのみ**再構築され、その1回の許可された実行に使用された後、ゼロクリアされます。二度とディスクに触れることはありません。すべてのリクエスト、投票、許可、および使用は、ハッシュチェーン化されたローカル台帳（`node ledger verify`）に追記され、クォーラムなしでの試行は拒否され、*かつ*記録されます。

このメカニズムについて正直に一言で言えば、これはコミュニティが保持するオフラインマシンのメモリ内での再構築を伴うシャミアの秘密分散法であり、マルチパーティ計算ではありません。承認された実行中、キーはコミュニティが物理的に管理するハードウェア上で一時的に組み立てられた状態で存在します。これが守る特性は、*ディスク上に常駐するキーがないこと*、*クォーラムが存在しない状態での実行がないこと*、そして*すべての使用が検査可能な台帳にチェーンされること*です。キーがどこにも組み立てられないプラットフォーム側のしきい値署名は、将来の課題として残されており、言及される箇所にはそのように明記されています。

ローテーションや管理者の交代を行う場合は、セレモニーを再実行します。N−M個を超えるシェアが失われた場合は、コミュニティのソースコピーからセットが再封印されることを意味します。コミュニティは常に独自のプレーンテキストのオリジナルを保持します。なぜなら、[所有権](/docs/network/sovereignty/data-sovereignty)は決して私たちが保持するものではないからです。

## 5. ここでの「構成証明（attested）」が意味するもの — そして意味しないもの

すべての評価は、**署名付きスコアマニフェスト**を生成します。これには、スコア、メソッドパッケージのハッシュ、コーパスのチェックサム、および追記専用の監査ログのヘッドに対するノードの署名が含まれます。ノードの公開鍵を保持している人なら誰でも、`mt-eval node verify-manifest <manifest> --pubkey <published .pub.json>` を使用して、*このノード*が*これらの正確な入力*に対して*これらのスコア*を生成したことを検証できます。また、ハッシュチェーン化されたログにより、履歴の密かな改ざんを検出できます。

これが**ソフトウェア構成証明**です。これは記録の整合性を証明するものであり、v1が提供するものです。どのシリコンが実行を行ったかを証明するものでは**ありません**。ハードウェアリモート構成証明（TEE）は将来の課題であり、意図的に要件から外されています。v1の正直なセキュリティステートメントは次の通りです。オーガナイザーの規律（§3）、署名付きマニフェスト、およびコミュニティによるマシンの物理的な管理がトラストアンカー（信頼の基点）となります。これはまさに、主権を第一に考える設計において、信頼を置くべき場所そのものです。

## 6. 運用ループ

1. コンテストを告知し、ノードの公開鍵としきい値（dev-set threshold）を公開します。
2. オンライン（通常のマシン）で提出物を受け取り、IN マニフェストを組み立てます（`mt-eval node manifest write <drive> --direction in`）。
3. IN ドライブをノードへ運搬し、ハッシュを検証します（`node manifest verify`）。
   import-scan (`node import-bundle`); queue methods. An entrant's offline
   プロポーザルは *pending*（保留中）として到着します。ノードが最初にそれをチェックします（`node run-method
   <id> --offline` は、提出者の予選コードを公開開発セットに対して再実行し、コードエントリー用のコンテナランタイムをチェックしますが、封印されたものは一切開かず、ローカル台帳に合格を記録します）。その後、カストディアンがノード上で決定を記録します（`node approve <id> --offline --actor <custodian>` はチェックに合格するまで拒否されます。または `node deny … --offline --reason …`: ローカル台帳への投票と承認、およびノードキーで署名された記録。`node list --offline` は待機中の項目を表示します）。封印実行（再度 `node run-method
   --offline` を実行）は、その承認が記録されて検証されるまで、保留中のプロポーザルを拒否します。
4. カストディアンがシェアのクォーラムを提示して実行を承認します（§4 — `node run-method <id> --offline --share … --share …`）。封印されたセットは実行環境内のみに復号されます。クォーラムが揃わなければ実行されず、その試行は台帳に記録されます。
5. 実行が行われ、スコアが計算され、セグメントごとの出力はノード側に保持されます。
6. 終了処理: 作業用平文の消去、監査ログの追記、マニフェストへの署名を行います。
7. OUT ドライブを持ち帰り、スコアとマニフェストを公開します。誰でも検証可能です（`node verify-manifest`）。
8. 受け渡しをログに記録します。ドライブは専用のまま維持され、ノードはネットワークから遮断された状態（ダーク）を保ちます。
