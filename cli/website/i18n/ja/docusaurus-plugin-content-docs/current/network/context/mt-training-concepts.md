# MT トレーニング用語をわかりやすく解説

機械翻訳（MT）モデルのトレーニングには独自の用語体系があり、その大半は初心者に説明されることなく、知っているものとして扱われます。このページでは何も前提としません。以下のすべての用語は平易な言葉で定義され、具体的な例に紐づけられています。[トレーニングのウォークスルー](/docs/network/tutorials/train-your-own-model)を読んだり、コーディングエージェントがコマンドを実行するのを見たりするときに、言葉の意味を理解できるように、そして何より**静かに結果を台無しにする間違いがどの用語に潜んでいるかを把握できるように**するためのページです。

:::info[対象読者]
Python を書く必要はありません。現在この作業を行う想定される方法は、**コーディングエージェント**（Claude Code、OpenAI Codex、Cursor、OpenCode、Google Antigravity など）にツールを実行させながら指示を出すことです。あなたの役割は、適切な指示を出し、結果を正直に読み取れる程度にコンセプトを理解することです。このページはまさにそのためにあります。ツールに言及する場合は、これらのアイデアが組み込まれたトレーニングスイートである [**nmt-forge**](/docs/network/getting-started/training-honestly) を指します。ただし、ここで使う用語はこの分野全体のものであり、私たちだけのものではありません。
:::

ページ全体を通じて、一つの実例が説明をつなぎます。**英語 → 低リソース言語**（ここでは*ターゲット言語*と呼びます）の翻訳モデルを構築したいとします。その言語には翻訳済みテキストがほとんど存在しません。以下の内容はすべて、そのプロジェクトの一部です。

---

## 1. 二つのデータの山：トレーニングデータと評価データ

**対訳データ（Parallel data）**とは、翻訳とペアになったテキストのことです。二つの言語で同じ意味を持つ文が、文ごとに対応して並んでいます。

> `The children are playing.` → `awâsisak mêtawêwak.`

モデルは何千ものペアを学習することで習得します。ただし、ペアは**決して混ざり合わない二つの山**に分けておく必要があります。

- **トレーニングデータ** — モデルが*学習を許可された*ペアです。モデルはこれらを繰り返し読み込み、再現できるよう自身を調整します。
- **評価データ**（または**eval データ**）— モデルが*トレーニング中に一切見ることを許可されない*ペアです。翻訳を隠した状態でモデルにソース側を翻訳させ、その答えを隠された正解と比較します。これが、モデルが*暗記*ではなく*翻訳*を学習したかどうかを測る唯一の正直な指標です。

:::tip[このページの内容を一文で表すと]
テストが意味を持つのは、モデルが答えを一度も見ていない場合だけです。以下に挙げるほぼすべての間違いは、誰も気づかないうちに eval の山からトレーニングの山へ答えが漏れ出す、さまざまなパターンです。
:::

### 実データと合成対訳データ

- **実データ（または*ゴールド*対訳データ）**は人間が作成したものです。バイリンガルの教科書、人が翻訳した政府の記録、コミュニティがアーカイブした物語などが該当します。信頼性は高いですが、ほとんどの言語では痛ましいほど少なく、数百の文ペアしかないことも珍しくありません。
- **合成対訳データ**は、人が書くのではなくプログラムによって*生成*されたものです。実データが 400 ペアしかない場合、使えるモデルをトレーニングすることはできません。そのため、ルールに基づいて何十万もの追加ペアを生成します（方法の詳細は [§7](#7-manufacturing-data-when-you-dont-have-enough) を参照）。

この関係は非常に重要です。

> **実例。** あるプロジェクトでは、435 ペアの実英語→クリー語データがあり、約 1,000,000 ペアの合成データを生成しました。モデルは大量の合成データと数百の実データを合わせてトレーニングします。合成データは網羅性をもたらし、実データはモデルを実際の言語使用に根付かせます。この作業の核心は、(a) 合成データの山が言語をできる限り広くカバーすること、(b) モデルが一度も触れていない実テキストのみで評価することです。

:::danger[合成データでテストしない]
評価セットは**実データのみ**でなければなりません。生成された文でテストすると、モデルが翻訳できるかどうかではなく、*ジェネレーター*に合致するかどうかを測ることになります。適切なトレーニングスイートは、合成データの行をテストセットとして登録することを拒否します。
:::

## 2. 分割：train、dev、test

まず実データのペアが一つの山にあり、それを三つの役割に**分割**します。

| 分割 | 別名 | 用途 | トレーニング中にモデルが見るか |
|---|---|---|---|
| **train** | トレーニングセット | モデルが学習するペア | はい |
| **dev** | 検証セット、held-in | *いつ停止するか*と*どのバージョンが最良か*を決定する | いいえ（*スコアリングのみ*、学習には使わない） |
| **test** | held-out、評価セット | 最終的な正直な評価 | **絶対に見せない** |

この表には二つの重要な考え方が含まれています。

- **Held-out** とは単に「トレーニングから切り離して保管する」という意味です。テストセットは意図的に held-out にされます。
- **dev セット**は巧みな中間的存在です。モデルは dev セットを*学習*しませんが、トレーニング中にモデルの dev セットに対するパフォーマンスを*確認*して意思決定を行います。本番試験ではないが、勉強を続けるべきかどうかを教えてくれる模擬試験のようなものです。dev セットをこのように使うのは正当ですが、*テスト*セットをこのように使うのは不正行為です（[§4](#4-contamination-and-leakage-the-mistake-that-eats-results) を参照）。

### シールドセットと再分割

- **シールドセット（Sealed set）**とは、**厳密に一度だけ**スコアリングできるテストセットです。スコアを確認した瞬間に「使用済み」になります。その数値を知った後は、以降のすべての判断がそれに微妙に影響されるからです。シールドセットは、コンペティションやコミュニティが最終評価を本当に最終的なものとして保つための仕組みです。
- **再分割（Re-split）**とは、train/dev/test の分割をゼロから再構築することです。通常、古い分割が汚染されていることが判明した場合に行います。漏れのある分割は数行を削除しても修正できません。すべてを再グループ化して切り直す必要があります（理由は [§4](#4-contamination-and-leakage-the-mistake-that-eats-results) で説明します）。

## 3. 「トレーニング」が実際に行うこと：損失とその二つの顔

トレーニングはループです。モデルが予測を行い、どれだけ間違っていたかを確認し、次回に少し間違いを減らすよう内部の数値を微調整します。これを何百万回も繰り返します。

**損失（Loss）**は「どれだけ間違っているか」を測る単一の数値です。低いほど良いです。ただし、損失には*二種類*あり、混同することは典型的な落とし穴です。

- **トレーニング損失** — モデルが実際に学習中のペアに対してどれだけ間違っているかです。モデルはトレーニングペアを単純に*暗記*できるため、これはほぼ常に下がり続けます。
- **dev 損失**（検証損失）— モデルが学習していない held-back の dev セットに対してどれだけ間違っているかです。これが正直なシグナルです。トレーニング損失が下がり続ける一方で dev 損失の改善が止まった場合、モデルは*言語を学習する*ことをやめて*トレーニングセットを暗記し始めた*ことを意味します。

> **実例。** しばらくすると、トレーニング損失が 0.8 で下降中なのに、dev 損失が 1.9 で止まり、むしろ*上昇*しているのが見えます。このギャップがサインです。モデルはトレーニングペアの暗唱が上手くなっているだけで、新しい文の翻訳は改善されていない、むしろ悪化しています。

### 損失は代理指標です。デコーディングが本質です。

ほぼ全員がつまずく微妙な点があります。損失は、*正解がすでに目の前にある状態で*モデルが次の正しい単語に高い確率を割り当てるかどうかを測ります。これはモデルが実際に良い翻訳を自力で生成することとは**同じではありません**。

- **デコーディング**（*生成*または*推論*とも呼ばれます）は、モデルが**実際に翻訳する**ことです。ソース文だけを与えられた状態で、何も頼るものなく単語ごとにターゲット文を出力します。
- **損失**はトレーニング中に計算される安価な*代理指標*です。品質と相関しますが、完全ではありません。

> **実例。** 二つのチェックポイントの dev 損失はほぼ同じですが、dev 文を*デコード*して実際の翻訳をスコアリングすると、一方が明らかに流暢です。損失ではその差が見えませんでしたが、デコーディングでは見えました。これが、真剣なチェックポイント選択では損失だけを信頼するのではなく、dev セットをデコードして実際の出力をスコアリングする理由です。

:::note[「dev 損失は品質を追跡するか」は未解決の問いであり、通説ではない]
「eval 損失は嘘をつく」という自信満々な主張を耳にするでしょう。それは**未確定**として扱ってください。証明されたことではありません。その通説の多くは汚染された実験から生まれたものです。正直な立場はこうです。dev 損失は有用で安価なシグナルであり、dev **生成メトリクス**（デコードしてスコアリング）はより直接的なシグナルです。最終的な判断には直接的なものを優先し、「損失は嘘をつく」を事実として繰り返さないでください。
:::

## 4. 汚染と漏洩：結果を台無しにする間違い

**汚染**（または**漏洩**）とは、eval の答えが密かにトレーニングの山に混入することです。モデルは記憶によってテストを「完璧にこなし」、スコアは素晴らしく見えますが、結果は無価値です。これは低リソース MT の結果が偽物になる最も一般的な原因であり、このページ全体が警告している最も重要な事項です。

典型的で巧妙な形は**共有ターゲット最小対（shared-target minimal pair）**です。

> **実例 — "Feed him" / "Feed her"。** ある言語の教科書では、多くの異なる英語の練習文が**一つの**ターゲット語に対応しています。*"Feed him"* と *"Feed her"* はどちらも同じ形 `asam` に翻訳されます。単純なランダム分割では、*"Feed him"* → `asam` が**トレーニング**に、*"Feed her"* → `asam` が**テストセット**に入ります。ターゲットの答え `asam` は両方の山に存在することになります。モデルはトレーニングから `asam` を暗記し、テストで「正解」しますが、何も学習していません。ある実際のプロジェクトでは、54 の「テスト」行のうち 17 行がこの方法で漏洩し、それらの行の品質メトリクスのスコアは **83** だったのに対し、クリーンな行は **44** でした。その数値に基づいて構築されたすべての知見は破棄しなければなりませんでした。

漏洩にはいくつかの形があり、適切な**漏洩監査（leak audit）**ではすべてを確認します。

- **完全一致の重複** — 同じソース*または*同じターゲットが両側に存在する（上記の例）。
- **ほぼ重複した重複** — 同一ではないが、テスト文の*言い換え版*がトレーニングに含まれている。同じドメインの文書は言い換えを共有しており、完全一致では見逃すため、監査では単語重複の類似度も測定します。
- **ファイル全体の重複** — 誰かが誤ってテストファイルのコピーでトレーニングしてしまった。（これは実際に起きます。「トレーニング」用に収集したデータがゴールドの教科書そのものであり、489 行中 489 行が一致していたケースがありました。）

### グループ非重複分割（Group-disjoint splitting）— 解決策

漏洩は問題のある行を一つずつ削除しても修正できません。パターンが再び現れるだけです。解決策は**グループ非重複分割**です。分割前に、ソース*または*ターゲットを共有するすべてのペアを**グループ**としてまとめ、各*グループ全体*をどちらか一方の側にのみ送ります。これにより `asam` とそれを共有するすべてのペアは、train *または* test のどちらか一方にのみ存在し、両方には存在しません。分割後は**ゼロ重複を検証**し、残っている場合は処理を拒否します。

:::tip[「スプリットガード」がこれを自動で行います]
エージェントがスプリッターを実行すると、デフォルトでグループ非重複分割が行われ、ゼロ重複が自動的に検証されます。"Feed him / Feed her" の落とし穴を覚えておく必要はありません。ツールがその間違いを犯しにくくし、回避しようとすると修正方法を示すメッセージとともに拒否します。
:::

## 5. 過学習、早期停止、プラトー

**過学習（Overfitting）**とは、モデルが学習の限界を超えて学習を続け、*暗記*し始めることです。トレーニング損失は素晴らしく見えますが、実際の翻訳品質は悪化します。[§3](#3-what-training-actually-does-loss-and-its-two-faces) の損失ギャップがその兆候です。

**早期停止（Early stopping）**はその対策です。dev シグナルを監視し、設定した回数のチェック（**patience**）の間改善が見られなくなったら、トレーニングを停止して最良の以前のバージョン、つまり最良の**チェックポイント**（トレーニング途中のモデルの保存済みスナップショット）を保持します。早期停止は無駄な計算と過学習を同時に防ぎます。

ただし、主に合成データでトレーニングする場合、早期停止には有名な失敗パターンがあります。**合成→実データ転移プラトー**です。

> **実例 — ハーフエポック停止。** あるモデルが 97.5% 合成データの混合でトレーニングされ、42 文の*実*dev セットで評価されます。序盤、モデルは大量の合成データに素早く適応するため、実文に対する dev 損失が急速に低下し、ステップ 8,000 付近で底を打ち、その後*上昇*に転じます。単純な早期停止は「dev 損失が 6 回連続で上昇した」と判断し、計画されたトレーニングの 20 分の 1 にあたるエポック 0.52 で終了を宣言します。しかしモデルはまだ完了していませんでした。*簡単な*合成学習を終えただけで、実言語品質への遅い**転移**をまだ始めていなかったのです。プラトーの段階で、成果が出る前に停止されてしまいました。

教訓：合成データが多い混合では、dev 損失の*早期の*下降と上昇は**予想される**ことであり、収束ではありません。停止ルールは、プラトーを乗り越えてトレーニングを続けられるほど賢くなければなりません。それは、あなたが知っているべき魔法の数字ではなく、混合のサイズから導き出されるフロア値です。

:::note[正直なセットアップは本物のバグを表面化させる]
そのプラトーのバグは何ヶ月も見えませんでした。以前の実行では（不正に）*テスト*セットを dev セットとして使用していたため、バグが隠れていたからです。最初の*クリーンな*実行がそれを露わにしました。これが繰り返されるテーマです。正直に行うことは、真実を保つだけでなく、本物の問題を可視化します。
:::

## 6. 品質の測定：メトリクス、バッテリー、レジスター

モデルがテスト文を*デコード*したとき、その答えを参照翻訳と比較してどのようにスコアリングしますか？

### 部分点メトリクス：chrF++ と BLEU

翻訳が参照と一語一句一致することはほとんどありませんが、それでも完全に正しい場合があります。そのため MT では、完全一致を要求するのではなく*重複*に対して報酬を与える**部分点**メトリクスを使用します。

- **chrF++** はモデルの出力と参照の間の**文字シーケンス**（および一部の単語シーケンス）の重複をスコアリングします。文字レベルで機能するため、単語が*ほぼ*正しい場合（正しい語幹に誤った語尾）でも部分点が与えられます。これにより、一つの語根が多くの形を取る形態論的に豊かな言語に適しています。高いほど良く、通常 0〜100 のスケールで報告されます。
- **BLEU** は古くからある標準です。**単語全体**のチャンク（n-gram）の重複をスコアリングします。今でも広く報告されていますが、語尾の惜しい間違いが完全な不正解として扱われるため、単語が多くの活用形を持つ言語には厳しいです。

> **実例。** 参照：`awâsisak mêtawêwak`。モデル出力：`awâsisak mêtawêw`（正しい語根、誤った最終音節）。BLEU は 2 番目の単語を単純に不正解と見なします。chrF++ はほとんどの文字が一致していることを認識し、部分点を与えます。同じ出力でも、スコアは大きく異なります。これが、選択するメトリクスによって結果の解釈が変わる理由です。

:::tip[どのメトリクスを信頼するかは測定によって決まる問いです]
すべてのメトリクスがすべての言語で人間の判断と同等に相関するわけではありません。言語ファミリーによっては BLEU が人間の評価とほとんど相関しないこともあり、別のファミリーでは高度なニューラルメトリクスが信頼できないこともあります。*どの*メトリクスに向けて最適化する前に、あなたの言語ファミリーの [メトリクス信頼性](/docs/network/specifications/metric-reliability) のエビデンスを確認してください。正直な答えが「未測定」であれば、数値を信頼するのではなくそう述べてください。
:::

### ニューラルメトリクス：COMET、MetricX

文字・単語の重複を超えて、**ニューラルメトリクス**（COMET、COMET-QE、MetricX）はトレーニング済みモデルを使って人間に近い形で翻訳を*評価*します。はるかに信頼性が高い場合がありますが、それはそれらが評価するようにトレーニングされた言語に限られており、ほとんどの低リソース言語は除外されます。また方向依存性があります。**MetricX** は**低いほど良い**という評価方向で、chrF++ とは逆です。数値を比較する前に知っておく価値のある詳細です。

### 誤差範囲：一つの数値を信頼しない

不確実性のない単一のスコアは罠です。小さなテストセットでは、差異はしばしば単なるノイズです。

> **実例。** 「モデルは口述物語セットで 16.7 から 18.1 に改善した」と聞けば進歩のように聞こえます。しかし、そのセットが 37 文しかないことに気づくまでは。そのデータ量では、±3 ポイントの変動は純粋な偶然です。正直な報告は `17.4 [15.1, 19.8] 95% CI` です。数値に加えて**信頼区間（CI）**、つまり真の値が妥当に収まる範囲を示します。二つのモデルの区間が大きく重なっている場合、どちらが優れているとは言えません。

適切なツールは CI なしでスコアを出力することを拒否し、A が B に勝つと宣言する前に[有意性検定](/docs/network/specifications/significance)を使用します。

### バッテリーとレジスター

実際の言語は一様ではありません。**レジスター**（または**ドメイン**）とは言語の*種類*です。日常会話、教科書の練習問題、ニュース記事、口述物語、公式な政府文書などが該当します。モデルはあるレジスターでは優れていても、別のレジスターでは劣ることがあります。

**バッテリー**とは、複数のレジスターに意図的に分割され、**個別に**スコアリングされる評価セットです。単一の平均値が弱点を隠せないようにします。

> **実例。** あるモデルの総合スコアは 46 で、まずまずです。しかしバッテリーの内訳を見ると、教科書の練習問題では 58、口述物語では 22 でした。平均値が自然な発話に対するほぼ完全な失敗を隠していたのです。レジスターごとのバッテリーだけがそれを明らかにしました。

## 7. データが不足しているときの合成データ生成

実データのペアが少ない場合、合成データを生成します。二つの手法が主流であり、どちらも一つの言葉にかかっています。**検証（verification）**です。

### FST と形態素解析器

**形態素解析器（Morphological analyzer）**は言語の語形成を知るツールです。語根が接頭辞や接尾辞とどのように組み合わさって有効な単語を作るかを理解しています。多くは**FST**（有限状態トランスデューサー）として構築されています。これはニューラルネットワークではなく、精密なルールベースの技術で、二方向に動作します。

- **解析（analyze）**：単語を受け取り、語根と文法タグに分解します（`nipâw` → 「sleep、三人称単数」）。
- **生成（generate）**：語根とタグを受け取り、正しい語形を綴ります（`sleep + 3sg` → `nipâw`）。

多合成語言語（英語では文全体が必要な意味を一つの単語で表せる言語）にとって、FST は非常に価値があります。既知の語根の*あらゆる*有効な形を綴ることができ、それがトレーニングデータを生成するための原材料となります。

### ラウンドトリップ検証 — 合成データを信頼できるものにするルール

データの生成は危険です。ジェネレーターが静かに無意味なデータを出力することがあります。それを防ぐ規律が**ラウンドトリップの法則**です。生成されたすべての単語は *generate → analyze → 開始時と同じ解析結果* を通過しなければなりません。FST に語形を綴らせ、その綴りを再度入力してタグが返ってこない場合、その単語は破棄されます。ラウンドトリップに失敗したものはトレーニングデータに一切含めません。

> **実例 — 一文字の漏洩。** ある辞書では音を文字 `ý` で綴っていましたが、解析器は通常の `y` を期待していました。二つの綴りが接続部分で統一されていなかったため、*1,375 の動詞*が静かに「未知」と判定され、生成から除外されました。何週間も、誰にも気づかれずに。解決策は**正規化器（canonicalizer）**です。二つのコンポーネントが接続するすべての場所で綴りを単一の規則に正規化する関数と、パイプラインの各ステージを通過するアイテム数をカウントする**ファネル監査**を組み合わせることで、1,375 件の静かな脱落が二度と隠れられないようにします。

### 量ではなく網羅性

100 万の生成文は包括的に聞こえます。しかし、同じ少数のパターンの 100 万通りのバリエーションであれば、そうではありません。

> **実例。** 1,000,000 ペアの合成コーパスに、**命令形**（「Vote!」）、**wh 疑問文**（「who/where/when」）、**所有格**（「my dog」）、**逆形**（「she sees *me*」— 多くの言語で核心的な文法）が**一切含まれていない**ことが判明しました。解析器はそれらすべてを生成できましたが、テンプレートが一度も要求しなかったのです。量が構造的な穴を隠していました。

対策は、公開された文法書から書き起こした**網羅性チェックリスト**です。必要な文法現象をそれぞれ引用付きで記載し、必要な現象の例がゼロの場合はビルドが失敗するようにします。また、**種類ごとの上限（per-kind cap）**により、一つのテンプレートパターンが支配的になるのを防ぎます。あるコーパスでは、二つのパターンがデータの 54% を占めており、モデルの「経験」の半分が二つの文パターンだったことになります。

### バックトランスレーション

**バックトランスレーション（Backtranslation）**はもう一つの主要な合成手法で、巧みな方法です。ターゲット言語の翻訳されていない平文テキスト（**モノリンガル**コーパス — 対訳テキストよりはるかに見つけやすい）がある場合、次のことができます。

1. *逆方向*モデル（ターゲット → 英語）を用意し、
2. モノリンガルのターゲットテキストを機械翻訳で*英語に*翻訳し、
3. 各機械翻訳英語文と、元の**実際の**ターゲット文をペアにして、
4. そのペアで順方向（英語 → ターゲット）モデルをトレーニングします。

ターゲット側は本物の言語であり、英語側だけが合成です。通常、これは良いトレードオフです。

> **実例。** ターゲット言語の実文が 50,000 文あるが、対訳ペアは 400 しかないとします。50,000 文をバックトランスレーションで粗い英語に変換すると、*ターゲット*側が本物の 50,000 トレーニングペアが得られます。

:::danger[モノリンガルテキストも漏洩監査する]
バックトランスレーションは「モノリンガルテキストだから」安全に感じられますが、そのテキストが実は eval データそのものである可能性があります。あるプロジェクトでは、漏洩監査によってモノリンガルとして収集したデータがゴールドテストセットと完全に一致していることが発覚しました。合成データとモノリンガルデータを含む**すべての**入力を**すべての** eval セットと照合して監査してください。明らかな対訳コーパスだけではありません。
:::

### 合成データへのタグ付け

最後の実践として、合成ソースにマーカー（`<synth>` や `<bt>` など）で**タグ付け**し、実（ゴールド）データはタグなしのままにします。これにより、モデルは「練習素材」と「本物」を区別できるようになり、本物のデータが出力スタイルの基準となります。翻訳時にはタグを付けないため、モデルはゴールドデータから学んだことを活用します。（この手法の詳細は [バックトランスレーションのクックブック](/docs/network/tutorials/back-translation) を参照してください。）

## 8. 各要素のつながり

上から下に読むと、これが一つのワークフローになります。

1. **実対訳データ**を収集します（[§1](#1-the-two-piles-training-data-and-evaluation-data)）— 通常は不足しています。
2. グループ非重複で train / dev / test に**分割**します（[§2](#2-splitting-train-dev-and-test)、[§4](#4-contamination-and-leakage-the-mistake-that-eats-results)）。
3. ギャップを埋めるために合成データを**生成**します — ラウンドトリップ検証済み、網羅性確認済み、漏洩監査済み（[§7](#7-manufacturing-data-when-you-dont-have-enough)）。
4. 混合データで**トレーニング**し、**dev 損失 / dev 生成**を監視して**過学習**を避け、**プラトー**を乗り越えます（[§3](#3-what-training-actually-does-loss-and-its-two-faces)、[§5](#5-overfitting-early-stopping-and-the-plateau)）。
5. held-out の**テストバッテリー**を**デコード**し、**レジスター**ごとに**部分点メトリクス + 信頼区間**でスコアリングします（[§6](#6-measuring-quality-metrics-batteries-registers)）。
6. eval の答えがトレーニングに触れないよう、すべてを通じて徹底します（[§4](#4-contamination-and-leakage-the-mistake-that-eats-results)）— 他の五つのルールが従うべき原則です。

ここに挙げたすべてのルールは、実際のプロジェクトが犯し、記録した実際の測定済みの間違いに対応しています。暗記する必要はありません。トレーニングスイートがそれぞれを機械化しているため、正直な道がデフォルトとなり、不正直な道は説明付きで拒否されます。それが次のページのテーマです。

## この用語でエージェントに指示する

コーディングエージェントを通じて作業するため、このページの実践的な成果は、次のような指示を出し、確認できるようになることです。

- *「コーパスをグループ非重複で分割し、トレーニング前にゼロ重複を検証してください。」*
- *「トレーニング側から dev セットを切り出してください。テストセットでチェックポイントを選択しないでください。」*
- *「合成データとモノリンガルデータを含む、すべての入力をすべての eval セットと照合して漏洩監査してください。」*
- *「chrF++ を 95% 信頼区間付きで、レジスターごとに分けて報告してください。」*
- *「どのスコアに向けて最適化する前に、この言語ファミリーのメトリクス信頼性を確認してください。」*

エージェントが Champollion MCP サーバーを利用できる場合、`get_training_guardrails` を呼び出してこれらのルールと各ルールが防ぐ間違いをコマンドを一つ書く前にコンテキストに直接取り込むことができます。
