# 正直な制限事項

> これらは、私たちが**超えると主張しない**内容です。このサイトの他の箇所にここに記載された内容以上のことが示唆されている場合は、バグとして扱い、[お知らせください](/docs/network/perspectives/reporting-errors-and-owning-corrections)。

評価インフラは、その限界について正直であることによってのみ信頼を得られます。以下に、確認できる形で率直に述べます。

## 1. 深い形態論的検証は現在1つの言語ペアのみに対応

FST（有限状態トランスデューサー）ベースの形態論的検証 — すべての出力単語が対象言語において正しく形成された単語であるかを確認する処理 — は、実際には**英語 → Plains Cree のみ**に対応しています。`GiellaLTFSTMetric` 自体は**汎用的**です：GiellaLT の `.hfstol` アナライザーが公開されている言語（Plains Cree、サーミ語、フィンランド語、ノルウェー語ブークモール、イヌクティトゥット語など）であればスコアリングが可能であり、機能としての適用範囲は広いです。しかし、**評価コーパスは現時点で Plains Cree のみ**存在するため、FST スコアリングが実際に行われているのは crk のペアだけです。リーダーボード上の他のすべての言語ペアは、表層的な指標（chrF++、BLEU）と動作チェックによってスコアリングされています。これらは有用なシグナルですが、形態論的な正確さを**保証するものではありません**。FST と評価コーパスの両方が存在しない言語については、形態論的検証を主張しません。

## 2. 信頼ティアはローンチ時点では自己申告

ほとんどのスコアは、コントリビューターが自らハーネスを実行して結果を公開することで算出されています。SHA ピン留めされた正規コーパスに対して提出物を再スコアリングするサーバーサイドの**検証**は存在し、拡張中ですが、「verified（検証済み）」はまだ全件には適用されていません。各行の信頼バッジをご確認ください：**「self-reported（自己申告）」はまさにその意味であり**、これがデフォルトです。

## 3. コミュニティ話者による検証はまだ実施されていない

私たちの賞の要件は、**バイリンガル話者による承認率 ≥ 70%** です。この基準は定められており、実施するためのツールも構築中ですが、**コミュニティ話者によるレビューはまだ一度も実施されておらず**、**このサイト上のいかなるスコアも話者ゲートを通過していません**。Composite スコアや chrF++ の数値は機械的なシグナルであり、コミュニティの判断ではありません。

## 4. 評価サンドボックスは存在するが、カストディセレモニーはまだ

コーパスをソースから取得してSHAでピン留めし、ホールドアウト（検証用）データ分割は封印されます。コミュニティが非公開のテストセットを保持している場合、そのデータセットがコミュニティの手を離れることなく、手法のスコアリングを行うことができます。現在、この評価には**2つのレーン**が用意されています。標準的なニューラルモデルにおいて推奨されるのは**宣言型（declarative）**のレーンです。参加者はデータ（safetensorsの重み + 宣言型トークナイザー + 設定ファイル）のみを提出し、主催者は自身が管理する信頼できる推論エンジンでそれを実行します（`trust_remote_code=False`、オフライン。安全性の根拠はアーキテクチャ名ではなくコードを含まないフォーマット自体にあるため、アーキテクチャの制約は緩やかです）。参加者のコードは一切実行されないため、サンドボックス化する必要はありません。ここでの安全性チェックは、任意のコードが安全であることを証明しようとするものではなく、決定可能なフォーマット検証（pickleではなくsafetensorsであるか？ `trust_remote_code`が含まれていないか？）となります。純粋にコードとして実装される手法（パイプライン、LLMを活用したハイブリッドなど）に対するフォールバックは、ネットワークから隔離された**サンドボックス**です（静的チェック、`--network=none`コンテナ、スコアのみの外部出力、オプションの完全なエアギャップによるファイル転送）。サンドボックスは、信頼できないコードの実行を拒否するのではなく封じ込めるアプローチをとるため、率直に言ってセキュリティの弱いレーンとなります。その中核となる保証は`--network=none`であり（ヒューリスティックな静的スキャンではバイナリモデルを検証できないため）、より高度な堅牢化（seccomp、microVMなど）は今後の課題として見送られています。現在何が稼働しており、何が稼働していないかの詳細については、[run a sovereign contest](/docs/network/sovereignty/run-a-sovereign-contest)を参照してください。どちらのレーンでも構築されて**いない**のは、コミュニティによる鍵管理の仕組み（しきい値署名、鍵生成セレモニー、ノードの構成証明）です。現在の承認は記録されたプロセス（単一の管理者、単一の鍵、誠実なラベル付け）に留まっているため、鍵管理の仕組みとコミュニティの合意形成が追いつくまでは、ゴールドスタンダードとなる**賞（prize）**の評価は非公開のままとなります。

## 5. キーカストディは決定済み；コミュニティカストディアンは確認中

カストディの*仕組み*は決定されています：**Champollion がキーシェアをゼロ保有する**閾値/マルチシグスキームです。カストディアン自身はコミュニティによって選ばれ、その協議は進行中です — そのため、**「コミュニティキーカストディアン（確認中）」**と表現しています。カストディは同意ではありません：関係的なコミュニティ同意のプロセスは独自のものであり、より時間がかかり、より重要なトラックです。
