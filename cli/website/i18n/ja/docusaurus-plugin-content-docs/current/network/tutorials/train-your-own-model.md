# 独自モデルのトレーニングを始めるには

これは、低リソース言語向けの機械翻訳モデルをトレーニングするための完全なチュートリアルです。「この言語を話せるが、データがほとんどない」という状態から、信頼して報告でき、champollion CLI 経由で自身のアプリに提供でき、そして [Network](/docs/network/) に提出できるモデルに至るまでの手順を解説します。トレーニングは長い道程（既存のものを探し、選択肢を測定し、より優れたものを構築し、それを証明し、デプロイする）の 1 ステップにすぎません。その全容については [お使いの言語向けの機械翻訳を構築する](/docs/build-mt-for-your-language) をご覧ください。
このガイドは初心者向けに書かれており、現代的な開発アプローチを前提としています。つまり、**あなたがコーディングエージェント**（Claude Code、OpenAI Codex、Cursor、OpenCode、Google Antigravity など）**に指示を出し**、エージェントがツールを実行します。

そのため、以下の各ステップは同じ構成になっています。

- 🗣️ **エージェントへの指示** — 平易な言葉で何を依頼するか。
- 🛠️ **ツールの動作** — [nmt-forge](/docs/network/getting-started/training-honestly) が代わりに実行する内容と、よくあるミスを事前に防ぐ**ガードレール**。
- 👀 **結果の読み方** — 「良い状態」とはどのようなものか、何に注意すべきか。

:::info[まず用語を確認しましょう]
*dev set*、*decoding*、*chrF++*、*leakage*、*round-trip verification* といった用語がまだ馴染みのない方は、先に [**MT Training in Plain Language**](/docs/network/context/mt-training-concepts) をお読みください。このページで使われるすべての用語が、具体例とともに定義されています。このページはそれらの用語をすべて前提としています。
:::

:::note[誠実さは機能であり、障壁ではありません]
このツールは意図的に主張を持った設計になっています。ガードレールは、実際のプロジェクトで実際に起きた、測定済みのミスを機械的に防ぐものです。そのため、誠実なパスがデフォルトであり、不誠実なショートカットは**修正方法を明示したメッセージとともに拒否されます**。このガイドで拒否が発生した場合、それはツールが正しく機能している証拠です。そうあるべきなのです。
:::

## 始める前に必要なもの

- ターミナルとファイルシステムへのアクセス権を持つ**コーディングエージェント**。これが作業の実行役となります。
- お使いの言語ペアの**実際の翻訳文** — 人手で作成された数組でも、有効なスタート地点となります。二言語併記の教科書、コミュニティのアーカイブ、翻訳された公的記録、教育教材など。量より質が重要です。
- **必須ではないが強力な要素:** ターゲット言語の単一言語テキスト、二言語辞書、出版された参照文法書、形態素解析器（FST）。これらすべてが最初から揃っている**必要はありません** — ツールが何が存在し、どれがどの機能を解放するかを正確に教えてくれます。
- **コンピュートリソース:** ノート PC で十分です。ガードレール、データ分割、データ合成、監査、スコアリングはすべて CPU 上で動作し、デフォルトのモデル（スクラッチからトレーニングする小型 Transformer）のトレーニングも同様です。GPU が必要になるのは、最大のプリセット（`nllb-600m`）を選択する場合のみです — [ステップ 5](#step-5--train) を参照してください。

> 🗣️ **エージェントへの指示:** *"nmt-forge をトレーニング用の extra
> (`python3 -m pip install 'nmt-forge[hf]'`) とともにインストールし、`nmt-forge` コマンドが動作することを確認してください。
> これから英語 → <your language\> の翻訳モデルを、
> 誠実な手順でトレーニングします。"*

```bash
python3 -m pip install 'nmt-forge[hf]'     # Python 3.11+; brings mt-eval-harness, the scorer
```

`[hf]` extra はトレーニング用スタック（torch、transformers、accelerate、tokenizers、sentencepiece、peft）であり、CPU 専用の wheel で問題ありません。他には何も必要ありません — Champollion リポジトリのクローンも不要です。すべてのコマンドは `--json` を受け入れます（標準出力に 1 つの JSON ドキュメントを出力し、拒否された場合は `{"error": {…, "why", "fix"}}` with exit code 2), and `nmt-forge status` として返されます）。任意の時点で次のコマンドを確認できます。

エージェントは、コマンドを実行する前に、Champollion MCP サーバーの `get_training_guardrails` ツール（引数なし、オプションで `topic`）を呼び出して、完全なルールブック（10 個のガードレールと、それぞれが防ぐ過ち）を自身のコンテキストに読み込むことができます。エージェントを指示して作業を進める場合は、まずこれを実行するよう求めてください。

## ステップ 1 — 言語を選び、実際に何が存在するかを確認する

すべてのプロジェクトは、インデックスにその言語が*何を持っているか*を正直に問い合わせることから始まります。

> 🗣️ **エージェントへの指示:** *「対象言語の ISO 639-3 コードで `nmt-forge discover` を実行し、どのようなデータが存在し、何が不足しているかをまとめてください。」*

```bash
nmt-forge discover nav        # Navajo, as an example
```

🛠️ **ツールの機能:** その言語の Champollion **カード**（その言語に関して判明している情報の唯一の情報源）を読み取り、記録されている文字体系、形態素解析器、辞書、コーパス、評価データセットを報告した上で、その言語を**アセットラダー**に配置します。（カードは、`--cards-dir` で指定されたディレクトリ、ローカルのチェックアウトまたは `node_modules/champollion`、あるいは公開カードインデックスから取得されます。キャッシュされるため、初回の取得後はオフラインで動作します。キャッシュなしでオフラインで使用する場合は、`champollion network card <code> --json` を使ってカードをディレクトリにエクスポートし、`--cards-dir` を渡してください。）

```
THE ASSET LADDER — what this language can do TODAY:
  ✓ rung 1: parallel text → train with every guard (no pack needed)
  ? rung 2: monolingual text → the tagged backtranslation lane
  ? rung 3: dictionary (+ grammar) → a cited template pack is worth building
  ? rung 4: morphological analyzer → round-trip-VERIFIED synthesis
  ? rung 5: LYSS referee → the language's own metric in selection
```

👀 **結果の読み方:** `✓` マークは現在実行可能な項目を示し、`?` マークはアセットの到着を待っている段階を示します。重要な点として、**カード上に記載がないことは「未確認」を意味し、「その言語には何も存在しない」という意味では決してありません**。情報が少ないカードは、知っている情報を追加するための招待状であり、行き止まりではありません — そして、最低限のカードであっても、ラダーの 1 段階目にある完全なガードレール付きトレーニングループを利用できます。充実したカード（平原クリー語など）では、上位の段階が自動的に連携されます。その評価セットには **NEVER TRAIN ON THIS**（トレーニングに絶対使用禁止）のフラグが付けられて届き、言語固有のレフェリーもすぐに接続できる状態で提供されます。5 段階目にチェックが入るのは、そのレフェリーのパッケージがここにインストールされている場合のみです。それ以外の場合は ✗ *UNAVAILABLE* とインストールコマンドが表示されます。また、レフェリーは外部サービスで単語を検索する可能性があるため、ローカル限定または封印されたテストセットに対して読み込まれることは決してありません。

次に、プロジェクトをスキャフォールドします。

> 🗣️ **エージェントへの指示:** *「この言語ペアに対して `nmt-forge init` でプロジェクトをスキャフォールドし、生成される `NEXT_STEPS.md` を読み上げてください。」*

```bash
nmt-forge init nav --dir my-nav-mt --pair eng-nav
cd my-nav-mt                     # run every later command from here
```

🛠️ これにより、ワークスペース（すべてのガードレールが参照する `.forge/` ディレクトリ）、**スターター設定ファイル**、そして*あなたとエージェント向け*に書かれた `NEXT_STEPS.md` ブリーフ（コマンドの実行順序、言語のアセットラダー、厳守すべきルール）が作成されます。これ以降のすべての作業のロードマップとなります。設定ファイルのパスは相対パスであるため、forge はプロジェクトディレクトリ内から実行してください。

`init` はトレーニングする**モデル**も選択します（`--model`、`config.json` 内に明示的な数値として書き出されます）。デフォルトは `cpu-tiny` で、`cpu-finetune --base <hf-id>`, or `nllb-600m` も選べます。選択肢の詳細は [ステップ 5](#step-5--train) で説明します。対象言語のカードがまだ存在しない場合でも、`nmt-forge init <code> --no-card --name "<name>"` はプロジェクトの雛形を作成します — カードの各項目は未知として記録され、捏造されることはありません。

## ステップ 2 — 解析器と辞書を指定する（存在する場合）

このステップはラダーの**ランク 3〜4** に関するものです。言語に解析器がない場合は、[ステップ 4](#step-4--split-your-real-data-safely) にスキップしてください。実データ（およびバック翻訳データ）のみでトレーニングするのは、完全に正当なパスです。

解析器と辞書が*存在する*場合、検証済みのトレーニングデータを*生成*する能力が解放されます。これは、並列テキストが少ない言語にとって最大のレバーです。

> 🗣️ **エージェントへの指示:** *「カードにはこの言語の形態素解析器と辞書が記載されています。カードのインストール手順に従ってそれらを取得し、ドキュメントに記載された環境変数を通じて言語パックに指定し、解析器がいくつかの既知の単語をラウンドトリップできることを確認してください。」*

🛠️ **ツールの動作 — 越えない境界線。** 解析器（FST）と辞書は、**独自のライセンスを持つ、ユーザーが個別に取得する別ツール**です。このスイートはそれらを**バンドルしたり再配布したりしません** — 入手先とライセンスを案内し、ユーザーが取得します。これは官僚主義ではありません。多くの言語リソースには実際の許可条件と主権に関する制約があり、ツールはその設計によってそれらを尊重しています。

接続部分は**言語パック**です。これは、*あなたの*解析器、辞書、正書法ルール、文法に基づく文テンプレートをエンジンに適合させる小さなプラグインです。このスイート自体はパックを**一切**同梱しません — パックはそれぞれの言語とともに存在します（たとえば Plains Cree パックは独自のプロジェクトに存在し、モジュールパスで接続します）。

👀 **結果の読み方。** 解析器が**ラウンドトリップ**できることを確認してください。つまり、ある形を入力し、その表記を解析器に戻したとき、同じ文法タグが得られることです。そうならない場合、パックの**正規化器** — 2つのコンポーネントが接触するすべての場所で表記を正規化する関数 — におそらくルールの追加が必要です。これを正しく設定することは重要です。1つの未解決の文字（`ý` と `y`）が、生成パイプラインから1,375個の動詞を何週間も静かに削除し続けたことがありました。ツールの**ファネル監査**は各ステージでの生存数を正確にカウントするため、このような静かな脱落を隠すことができません。

## ステップ 3 — 文法ルールからトレーニングデータを合成する

解析器 + 辞書 + 文法に基づくテンプレートのパックがあれば、数十万の検証済みペアを生成できます。

> 🗣️ **エージェントへの指示:** *「`nmt-forge synth` を使って言語パックで合成トレーニングデータを生成し、カバレッジレポートを表示してください。」*

```bash
nmt-forge synth my_pack.module:get_pack --out data/synth.jsonl
```

🛠️ **ツールの動作 — 出力の法則。** 出力に到達するすべての行は、どのパックも回避できないルールを満たす必要があります。

- **ラウンドトリップ検証済み** — 生成されたすべての単語が *生成 → 解析 → 同じ解析結果* を通過するか、その行は破棄されます。未検証の形は一切出力されません。
- **文法引用済み** — すべてのテンプレート種別は、それが転写した出版済み文法書を引用します。引用のないテンプレートは存在しません。コードはそれらの読み込みを拒否します。
- **カバレッジチェック済み** — テンプレートは必要な文法現象のチェックリスト（命令形、疑問文、所有、逆形など）に対して照合されます。*必須*の現象に例が0件の場合、ビルドは失敗します。これは「百万文あっても、すべて同じ少数のパターン」という罠 — 構造的な穴を隠す量 — に対するガードです。
- **出所スタンプ済み** — すべての合成行には `synthetic: true` のマークが付きます。このスタンプは重要な意味を持ちます。レジストリは合成行をテストセットとして登録することを**拒否します**。テストは実データのみです。

👀 **結果の読み方。** カバレッジレポートで**カバレッジがゼロの必須項目**（テンプレートが一度も生成しなかった文法現象）と**種別分布**を確認してください。2つのテンプレート形が支配的な場合、サンプラーの種別ごとの上限（デフォルト15%）がそれらを再バランスし、単一のパターンがモデルの経験の半分を占めないようにします。

:::tip[解析器がない場合: 代わりに逆翻訳を使用]
ルールベースでの合成ができないものの、ターゲット言語の**単一言語**テキストがある場合は、エージェントに**逆翻訳**レーンの使用を依頼してください。指定した逆方向モデルを使用して単一言語テキストを英語に機械翻訳し、各結果を**本物の**ターゲット文とペアにします。ターゲット側の真正性は保たれます。
これは CLI のサブコマンドではなく、Python ライブラリの呼び出し（`nmt_forge.training.backtranslation.backtranslate`）です。エージェントはこれを取り入れた短いスクリプトを記述し、タグ付けされた出力ファイルを設定ファイルの `data.synthetic` レーンに追加します。この呼び出しは**まず単一言語テキストのリーク監査を行います** — そのテキストが評価データそのものである可能性があるためです。
詳細は [逆翻訳クックブック](/docs/network/tutorials/back-translation) を参照してください。
:::

## ステップ 4 — 実データを安全に分割する

次に、**本物の**対訳ペアを用意し、すべての判断基準となる文を取り置きます。ここには、低リソース機械翻訳において最も結果を損ないがちな過ちが潜んでおり、ガードレールが真価を発揮する場面でもあります。

ファイル形式は `.tsv`（ソース、タブ、翻訳の順で 1 行に 1 ペア。`# ` で始まる行はコメント）または `.jsonl`（1 行あたり `{"source": …, "target": …}`）が使用できます。

**すでにテストセットがある場合**（教師による確認済み、看護師による確認済み、非公開のものなど）は、別ファイルとして保持し、登録した上で、コーパスをそれと照合してスクリーニングし、train と dev のみを切り出します。

> 🗣️ **エージェントへの指示:** *"テストセットを登録し、それに対してコーパスのリーク監査を行ってください。その後、クリーンアップされたコーパスを `nmt-forge split` を使って固定シードのグループ素（group-disjoint）分割で train と dev に分割してください。"*

```bash
nmt-forge registry add project-test ~/teacher-test.tsv --role test
nmt-forge leak-audit ~/corpus.tsv --clean-to corpus.clean.jsonl
nmt-forge split corpus.clean.jsonl --test 0 --dev 100 --seed 42 \
    --out data/split --register project
```

**テストセットがない場合**は、同じステップでコーパスからテストセットを切り出します。

```bash
nmt-forge split corpus.tsv --test 150 --dev 100 --seed 42 \
    --out data/split --register project
```

🛠️ **ツールの機能 — 分割ガード:** **グループ素（group-disjoint）分割**を行います。ソース*または*ターゲットを共有するすべてのペアは 1 つのグループにまとめられ、グループ全体がいずれか一方の側に完全に配置されます。その後、**重複がゼロであることを検証**し、重複が存在する場合は処理の続行を拒否します。

```
split corpus.clean.jsonl: 1580 rows in 1544 share-groups (largest 4)
  train 1480 · dev 100 · test 0  → data/split/
  verified: 0 shared canonical source/target keys across sides
  registered project-dev (role=dev)
```

これにより、**「Feed him」/「Feed her」のリーク**を防ぎます。教科書で英語の異なる練習文が 1 つのターゲット単語（`asam`）に対応している場合、単純なランダム分割を行うと、一方の複製が train に、もう一方が test に入り、モデルが暗記によって「合格」してしまいます。ある実際のプロジェクトでは、54 行のテストデータのうち 17 行がこのようにリークし、クリーンな行のスコアが 44 であったのに対し、83 という数値を記録しました — その結果、その数値に基づいて構築されたすべての知見が無効になりました。`--register project` は dev セット（および切り出された場合は test セット）を `project-dev` / `project-test` として記録します。これらはスターター設定ファイルがすでに参照している名前であるため、以降のすべてのコマンドはそれらが*決してトレーニングに使用してはならない評価セット*であることを認識します。テストセットがすでに登録されている場合、`split` はその場で新しい train および dev ファイルをテストセットと照合してスクリーニングも行います。

🛠️ **リーク監査:** `leak-audit` は登録されたすべての評価セットに対して行をスクリーニングし、自身のコーパスからの例を挙げながら、何を**除外**するかを報告します — ソースがテストプロンプトと同一の行（翻訳が異なっていても該当）、ターゲットがテストの正答と同一の行、およびターゲットがテストの正答のほぼ重複である行（正答を含んでいる、正答の断片である、またはアクセントを無視した状態で 90% 以上同一である行など）。そして、意図的に**保持**するものも報告します。文の骨組みを共有しながら 1 単語だけを入れ替えた*テンプレート兄弟*（「犬が見える」/「猫が見える」）や、正答が異なる類似プロンプトなどです。トレーニング内にテンプレート兄弟を持つテスト行がリスト化されます。スターター設定では `eval.near_dupe_corpus` がトレーニングファイルに設定されているため、最終レポートでは兄弟を持たないテスト行を「(strict)」スコアとして個別に採点し、兄弟が存在することによる楽観的なバイアスを可視化します。大半のテスト行に兄弟が存在し、テストセットが固定されている場合、`--clean-to <file> --drop-test-twins` はそれらのトレーニング側の兄弟も削除します（除外前後の strict サブセットを報告し、トレーニングデータが空になる処理は拒否します）。これには専用のファイル（`corpus.notwins.jsonl`）を指定してください。これは全データを含むコーパスの横に置かれる、兄弟を含まないモデル用コーパスとなります。リーク監査は、設定ファイル、実行、または分割によってすでに読み込まれているファイルを上書きすることを拒否します。結果は決定論的であり、テストファイル自体のテキストが出力されることは決してありません。

👀 **結果の読み方。** **verified: 0 shared** という行が表示されることを確認してください。代わりに `SplitLeakageError` が表示された場合、行を手動で削除しないでください — それは問題を再配置するだけです。グループ非重複分割を再実行してください。それが修正方法であり、エラーメッセージにもそう書かれています。

:::danger[ベンチマークでトレーニングしないこと]
共有レジストリから評価データセットを取得した場合（`nmt-forge registry add-harness`）、ツールはそれにスタンプを押し、トレーニングに使用できないものとして扱います — レジストリの**すべての**ベンチマークは *do-not-train* フラグが付きます。正当に使用できるデータでファインチューニングしてください。ただし、テストセットは絶対に使用しないでください。これは Network 全体の[唯一のルール](/docs/network/leaderboard/rules)です。
:::

## ステップ 5 — トレーニングする

1 つの設定ファイルが実行全体を定義し、1 つのコマンドがそれを再現可能に実行します。`nmt-forge init` がすでにそれを書き出しています。

> 🗣️ **エージェントへの指示:** *"`config.json` を読み込み、合成レーンを作成した場合はそれを追加し、`nmt-forge preflight run --config config.json` を実行して警告があれば修正した上で、`nmt-forge run config.json` を実行してスケジュールの診断状況を監視してください。"*

デフォルトの `cpu-tiny` モデルを使用し、合成レーンを追加したスターター設定ファイルの抜粋:

```jsonc
{
  "run_name": "nav-baseline",
  "workspace": ".forge",
  "data": {
    "gold": ["data/split/train.jsonl"],
    "synthetic": [{"path": "data/synth.jsonl", "tag": "<synth>"}],
    "dev": "project-dev"              // registry name, role=dev — the fence
  },
  "mix": {"gold_upweight": 20, "kind_cap": 0.15, "seed": 42},
  "regime": "auto",
  "model": {"backend": "hf-scratch", "device": "cpu", "d_model": 256,
            "layers": 3, "epochs": 60, ...},   // no time_budget_hours: init writes none
  "selection": {"metric": "generation:chrf++", "top_k": 3},
  "decode": {"max_new_tokens": 384, "headroom_factor": 1.5},
  "eval": {"battery": "project-test", "metrics": ["chrf++"],
           "near_dupe_corpus": "data/split/train.jsonl"}
}
```

**どのモデルを選ぶべきか？** `init`（`--model`）の実行時に選択します。すべての数値は `config.json` に記録されます。

| プリセット | 内容 | 必要な環境 | 正直な期待値 |
|---|---|---|---|
| `cpu-tiny`（デフォルト） | スクラッチからトレーニングする小型 Transformer（パラメータ数約 6M）。語彙は**トレーニング**行のみから学習されます | ノート PC の CPU、ダウンロード不要 | 控えめ: 1〜2 千ペアの場合、chrF++ はおよそ 5〜30（上限は高度に定型化されたデータの場合のみ）— 一般的な翻訳ではなく、データのフレーズやパターンを学習します |
| `cpu-finetune --base <hf-id>` | 指定した事前学習済みの小型 Marian/opus-mt モデルをファインチューニングします — *関連する*言語ペアのものを選択してください | CPU、約 300 MB のダウンロード | 関連するペアが存在する場合、通常は `cpu-tiny` より優れています — 推測せず dev セットで測定してください |
| `nllb-600m` | LoRA を適用した NLLB-200 distilled 600M | GPU、約 2.5 GB のダウンロード | 最も強力なスタート地点。CPU では実時間チェックにより数分以内に実行が拒否されます |

`cpu-tiny` の要点はスコアの高さではありません。ガードレール、監査、事前登録されたテスト、CLI から呼び出し可能なモデルといった**ループ全体**を実際に機能させることで、後からより優れたモデルを同じプロジェクトに投入し、同一の基準で測定できるようにすることにあります。

`preflight` は、実行時に通過するすべての関門を ✓ または ✗ で一覧表示し、各 ✗ に対する解決策を示します — トレーニング用の extra がインストールされているかどうか（`✗ backend-installed: … fix: python3 -m pip install 'nmt-forge[hf]'`）も含まれます。

```bash
nmt-forge preflight run --config config.json
nmt-forge run config.json
```

🛠️ **ツールの動作 — 4つのガードレールが同時に機能します。**

- **トレーニング前のリーク監査:** 本物データ、合成データ、逆翻訳テキストを含む*すべての*レーンが、登録済みの*すべての*テストセットおよび封印セットと照合してスクリーニングされます。正答のリーク（同一のプロンプトまたは正答、ほぼ重複する正答）およびファイル全体の完全一致は致命的エラーとなります。テンプレート兄弟は保持され、報告されます（`--drop-test-twins` は固定テストセットに対してこれらを削除します）。混合データがクリーンになるまで、トレーニングは開始されません。
- **Dev セットの保護フェンス:** トレーニングは**登録された dev セットがないと開始を拒否**し、チェックポイントの選択は常にその dev セットのみに基づいて行われ、テストセットが使われることは決してありません。（`cp test.jsonl dev.jsonl` のような不正を防ぐため、dev 行とテストセットの内容照合チェックまで行われます。）チェックポイントの選択には、dev の**損失**または dev の**生成メトリクス**（dev セットをデコードして実際の出力を採点する、より誠実なシグナル。スターター設定ではデコードされた dev 出力に対して chrF++ を使用）を利用できます。
- **スケジュールの健全性チェック:** 混合データにおいて合成データの割合が大きい場合、ツールはデータの規模からトレーニング停止の基準値を*算出し*、**プラトー（停滞期）**（モデルが単純な合成データの学習を終え、実データの品質への汎化がまだ始まっていない段階）を通じてトレーニングを維持します。これにより、単純な早期終了が計画の 20 分の 1 の段階で停止してしまう「半エポックでの終了」を防ぎます。dev セットの評価頻度も実行規模から算出されるため、小規模な実行であっても適切に評価されます。介入が行われるたびに、dev 損失の推移とその理由がわかりやすい言葉で出力されます。
- **露出量の計算 + タグ付き合成データ:** わずかな実データが埋もれてしまわないよう、本物データの重み付け（複製）が行われます。A/B テストの公平性を保つため、マニフェストには**一意の文あたりの有効露出量**が記録されます。合成データソースにはタグが付与され、出力スタイルの基準となるよう本物データはタグなしのまま維持されます。

トレーニングは唯一、ある程度の時間を要するステップです。エージェントはポーリングを行うのではなく、ログファイルに出力しながらバックグラウンドで実行し、重要な行（`refused`、`Error`、`wall-clock`、`RUN EXIT`）を監視する必要があります。損失曲線と停止ボタンを備えたリアルタイムパネルが**あなた向け**に開きます（ポートが空いている場合は `http://127.0.0.1:8377` にて）。開始直後の数分間で、forge はトレーニング速度を測定し、実時間の予測を出力します（最初は初期推定値、続いて安定状態の推定値）。`init` は制限時間を設定しません。制限時間はツールが勝手に決めるものではなく、あなた自身が設定する数値だからです。予測を確認し、許容できる時間を決定した上で、`"time_budget_hours": <hours>` を `config.json` の `model` の下に追加してください。それ以降、forge はその時間内に完了できない実行を拒否するため、規模の設定を誤った実行を早期に失敗させることができます。制限時間を設定するまでは forge の安全上限のみが適用されます。これは数日かかるような実行を停止させるものであり、予測には誰かが選んだ制限時間としてではなく、「no budget set; … ceiling（制限時間未設定、安全上限を適用）」として出力されます。

👀 **結果の読み方:** 実行が完了すると、**信頼区間付きの dev レポート**（数値だけのスコア出力はありません）と、次のコマンドが出力されます（以下の数値は説明のための例です）。

```
dev report (95% CIs — there is no bare-score rendering):
n=100 · set=project-dev
  chrf++       21.40  [18.95, 23.90] 95% CI

NEXT: nmt-forge export .forge/runs/nav-baseline-…/run-manifest.json --out export/
```

早期停止を*保留*してトレーニングを継続したことを説明する `schedule-sanity` メッセージが表示された場合、それはプラトーガードが機能している証拠です — 良い兆候です。ランは**マニフェスト**も書き出します。設定ハッシュ、データファイルハッシュ、シード、導出されたスケジュールが含まれており、ラン全体が再現可能です。

## ステップ 6 — 誠実に評価する

モデルができました。テストセットでスコアリングする前に、まず期待値を書き留めます — *最初に*。

> 🗣️ **エージェントへの指示:** *"テストセットの採点に向けた事前登録（予測するメトリクス、方向性、マージン、および 1 行の理由）を作成し、その後実行をエクスポートしてテストセットを 1 回採点してください。"*

```bash
# 1. Predict BEFORE you peek — the one format is a JSON array; edit the template
nmt-forge prereg template --out predictions.json
nmt-forge prereg new run1 --eval-set project-test --predictions predictions.json

# 2. Score the test set once against that prediction, and package the model
nmt-forge export .forge/runs/<run>/run-manifest.json --prereg run1 --out export/
```

`--prereg` は、このモデルを評価するための事前登録を指定します。テストセットに対する事前登録が 1 つだけ存在する場合、export はそれを自動的に検出します。同じテストセットに対して 2 つ目のモデルとその独自の事前登録が存在する場合、export は推測を行わないため、それぞれを明示的に指定してください。

（事前登録は最初のテスト採点の前であればいつでも行えます — `nmt-forge status` はトレーニング前に登録を求めます。）

🛠️ **ツールの動作 — 後付けストーリー防止ガード。**

- **事前登録:** 登録された**テスト**セットの採点には、データを見る*前*に作成された事前登録が必要です。予測ファイルは JSON 配列です。各予測にはメトリクスと根拠、およびベースラインに対する方向性（`nmt-forge prereg check` によって自動検証）または人間が確認する自由記述の期待値のいずれかを記述します。未編集のテンプレート、Markdown、散文は拒否され、フォーマットと修正方法が提示されます。事前登録がない場合、採点は単純に**拒否**されます:

  ```
  [preregister] no preregistration for eval set 'project-test' at its current content hash
    why: results looked at without written-down expectations become
         post-hoc stories; ...
    fix: write one FIRST: ... — then score
  ```

  これは、事後的なこじつけ（「口承物語で改善したのは当然だ」など）を事前予測であるかのように見せかける行為を防ぐためのガードレールです。*失敗した*予測を記録しておくことこそが、成功した予測の信頼性を担保します。
- **常に信頼区間を表示:** すべてのスコアは 95% ブートストラップ信頼区間（CI）とともに出力されます。信頼区間のないスコア出力は存在しません。信頼区間が重複している `+0.5` の向上は、改善とは見なされません。
- **評価台帳（eval-ledger）:** すべての評価セットの読み取り履歴がログに記録されます（追記専用、改ざん検知機能付き）。データセットがどれだけ「消費」されたかは `nmt-forge ledger show --set project-test` で確認できます。**封印（sealed）**セットは 1 回限りのものです — 1 度採点されるとクローズされます（2 回目の `export` は拒否され、`--no-eval` は再採点なしでパッケージングを行います）。

`export` は、dev セットで選ばれたチェックポイントを使用してテストセットをデコードし、採点を行った上で、わかりやすい言葉で書かれた **診断と推奨事項（Diagnosis & Recommendations）** セクションを末尾に追加します。また、結果を **mt-eval レポート**（`export/evaluation/`）として書き出すため、`mt-eval compare` を使用して、同じテストセットで本ハーネスを用いて測定された他の手法とモデルを並べて比較できます。さらに、モデル自体を `export/model/` にパッケージングします（ステップ 8）。ここにはテスト文は一切含まれません。`export/evaluation/` にはテスト文が含まれているため、モデルと一緒にコピーすることは絶対に避け、テストセット元に保管してください。パッケージが不要でスコアのみが必要な場合は、`nmt-forge evaluate <run-manifest>` を使用します。

👀 **結果の読み方:** 数値を**信頼区間およびレジスター（文体・位相）ごとに**確認し、トレーニングデータがテストセットと文テンプレートを共有している場合は「(strict)」スコアを確認し、喜ぶ前に**どのメトリクスを信頼すべきか**を検証してください。同じ登録済みセットに対して、別のシステムの出力ファイルをより多くのメトリクスで採点するには、以下のようにします。

```bash
nmt-forge score --eval-set project-test --hyps decoded.txt \
    --metric chrf++ --metric comet --target-lang nav
```

`nmt-forge discover` は、あなたの言語ファミリーに対する各メトリックの**測定済み信頼性**を示します（WMT メタ評価から）。ファミリーによっては、BLEU のようなメトリックが人間の判断をほとんど反映しない一方で COMET が有効な場合があります。多くの低リソース言語ファミリーでは、正直な答えは*未測定*です — その場合、自動的な数値ではなく、ネイティブスピーカーの判断が真のシグナルです。[Metric Reliability](/docs/network/specifications/metric-reliability) をご覧ください。

:::tip[言語固有のレフェリー]
言語に LYSS 評価標準がある場合（たとえば、2つの表記が文書化された長母音の慣例のみで異なることを知っているリンター）、`--plugin` で接続すると chrF++ と並んでスコアリングされます — チェックポイントの*選択*にも使用できるため、勝つモデルはその言語固有のレフェリーが好むモデルになります。プラグインの数値にも信頼区間が付きます。
:::

## ステップ 7 — 反復する

次は改善です — そしてすべての改善は同じ誠実な方法で測定されます。

> 🗣️ **エージェントへの指示:** *"1 点だけ変更してください（テンプレートの種類を追加する / 逆翻訳データを増やす / 別のモデルプリセットを試すなど）。再トレーニングを行い、有意性検定を含めて dev セット上で前回の実行と A/B テストを行ってください。"*

各実行では、すでに信頼区間付きの dev スコアが出力されています。対応のある検定（paired test）を行うには、各実行で dev セットをデコードします — `nmt-forge evaluate <run-manifest> --config dev-eval.json --out-hyps run1-dev.jsonl`, where `dev-eval.json` は、`eval.battery` が `project-dev` になっている設定ファイルのコピーです — その後、以下を実行します:

```bash
nmt-forge compare --eval-set project-dev \
    --hyps-a run1-dev.jsonl --hyps-b run2-dev.jsonl --metric chrf++
```

🛠️ **ツールの動作。** `compare` は単純な差分ではなく**ペア有意差検定**を実行するため、「B が A を上回る」という主張は統計的に裏付けられたものになります — ノイズではありません。**dev** セットで反復してください（それがその目的です）。**テスト**セットは頻度を抑えた事前登録済みのチェックに使用し、**シールド済み**セットは最後のために取っておいてください。

👀 **結果の読み方。** 真の改善は信頼区間*と*有意差検定の両方をクリアします。クリアしない場合でも、何かを学べます — そのレバーは期待より弱かったということであり、それを知ることには価値があります。プラトー / カバレッジ / リークガードにより、比較している数値は信頼できるものになっているため、自分の反復ループを実際に信頼できます。

データが乏しい言語に対して、効果の高い順に並べた一般的な次のレバーは以下の通りです。

1. **本物の対訳ペアを増やす** — 数千文規模では、どのような設定変更よりも、実際のペアを 1 つ追加することの方が効果的です。
2. 合成データの**カバレッジを広げる** — カバレッジレポートで指摘された不足している文法現象を追加します。
3. **逆翻訳** — ターゲット言語の単一言語テキストをより多くのトレーニングペアに変換します。
4. **より強力なスタート地点を採用する** — 関連ペア向けのベースモデルを用いた `cpu-finetune`、または GPU 上での `nllb-600m` を検討し、同じ dev セット上で `cpu-tiny` と比較測定します。
5. **カリキュラム学習** — 合成データで事前学習を行い、その後に本物のペアでファインチューニングします。

## ステップ 8 — 実用化と Network への展開

誠実にトレーニングされたモデルは、今すぐに利用できる価値ある成果物であり、まさに [Champollion Network](/docs/network/) が受け入れるために構築された対象そのものです。

**自身で利用する:** `export` によってモデルはすでにパッケージ化されています。自己完結型のモデルディレクトリ、`forge-model.json`（モデルの概要と測定方法の記録）、champollion プラグインマニフェスト（`method.json`）、および正確な実行コマンドが記載された `DEPLOY.md` が含まれます。

> 🗣️ **エージェントへの指示:** *"エクスポートしたモデルを配信し、champollion CLI を使ってアプリの文字列を翻訳してください。"*

```bash
nmt-forge serve export/model                               # http://127.0.0.1:8378
LOCAL_API_BASE=http://127.0.0.1:8378/v1 champollion sync --method local
```

`serve` は champollion の **api method** 規約（`POST /translate`）および **OpenAI 互換**の `/v1/chat/completions` をサポートしています — 後者は `--method local` が使用するもので、`DEPLOY.md` には前者向けの `champollion.config.json` スニペットが含まれています。これは `127.0.0.1` のみをリッスンします。ネットワーク上に公開するにはトークン（`--token` または `NMT_FORGE_SERVE_TOKEN`）が必要です。NMT モデルはテキストを翻訳するのみで指示は無視するため、CLI が LLM メソッドに送信するトーンプロンプト、コーチングファイル、用語集は効果を持ちません — また、その出力は読者に届く前に流暢な話者によるレビューが必要です。

**Network への展開:**

> 🗣️ **エージェントへの指示:** *「このモデルをメソッドとしてパッケージ化し、この言語ペアのリーダーボードに提出してください。」*

- **[Submit a Method](/docs/network/getting-started/submit-a-method)** は、あなたのモデルを Network エントリーに変換し、公開参照コーパスでスコアリングされ、あなたに帰属します。
- 評価がクリーンだったため — グループ非重複、dev フェンス、リーク監査済み、CI 付き、事前登録済み — あなたの提出は、ほとんどの低リソース MT の主張を沈める精査に耐えられます。アンチゲーミングアーキテクチャ（コミュニティが所有する秘密のテストセット、再現性チェック、ネイティブスピーカーによる検証）は、この方法で構築されたモデルにとって障壁ではなく、信頼性のスタンプです。
- あなたの言語に**賞**が設けられている場合、誠実に構築されたベースラインを上回る安定したメソッドは、まさにスポンサー付きプールが報いるものです。そして、先住民族の言語に対してメソッドが機能する場合、**所有権をコミュニティに移転できます** — ここで構築し、彼らが自分たちの条件でデプロイします。[Prize Specification](/docs/network/specifications/prizes) と [Ownership Transfer](/docs/network/sovereignty/ownership-transfer) をご覧ください。

## 全体の流れを一息で

1. 対象言語に何が存在するかを**発見する**（`discover`、`init`） — 記載がないことはゼロではなく未確認を意味します。
2. 解析器や辞書が存在する場合、ライセンスを尊重しつつそれらを**指定する**（ラダーの 3〜4 段階目）。
3. 検証・引用・カバレッジ確認済みのトレーニングデータを**合成する**（`synth`） — または単一言語テキストを**逆翻訳する**。
4. 実データをグループ素（group-disjoint）で**分割し**、テストセットと照合してスクリーニングし、評価セットを登録する（`registry add`、`leak-audit`、`split`）。
5. 1 つの設定ファイルを**トレーニングする**（デフォルトは CPU） — dev セット保護、リーク監査、プラトー検知を適用（`preflight`、`run`）。
6. 事前登録、信頼区間、適切なメトリクスを用いて**評価する**（`prereg`、`export`）。
7. 有意性検定を伴う A/B テストで**反復改善する**（`compare`）。
8. CLI 経由でモデルを**活用し**（`serve`）、Network に**提出する** — そこでは誠実な取り組みこそが最も重視されます。

低リソース MT の結果が間違う10通りの方法を暗記する必要はありませんでした。ツールが誠実なパスをデフォルトにし、ショートカットを説明付きで拒否しました。それがすべてのアイデアです。**ガードレールが初歩的なミスを防ぐので、あなたは言語に集中できます。**
