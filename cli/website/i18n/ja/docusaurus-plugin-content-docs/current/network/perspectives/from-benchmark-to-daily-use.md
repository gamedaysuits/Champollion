# ベンチマークから日常利用へ：ポストエディットという道筋

> **要約。** リーダーボードのスコアは製品ではありません。「この手法のchrF++スコアが47.5である」という状態から「バンドオフィスが毎週その言語で文書を発行している」という状態に至る道筋は、ただ1つのワークフローを経由します。それは、機械が下書きを生成し、流暢な話者がそれを修正し、修正されたテキストのみが公開されるというものです。私たちの仕様におけるすべての品質閾値は、このワークフローに合わせて調整されています。機械による監視のない出力は対象外であり、私たちは本プラットフォーム上のいかなる言語に対してもそれを推奨していません。

「いつになったら翻訳手法が『そのまま使えるほど良くなる』のか」と聞かれることがあります。このネットワークが対象とする言語において、その問いには落とし穴があります。正直に答えるなら、目指すべき基準は「レビューなしで公開できるほど良い」ではありません。**「下書きをレビューする方が、ゼロから翻訳するより速い、と言えるほど良い」**ことです。この基準ははるかに低く、測定可能であり、それを超えることでコミュニティの翻訳オフィスが一週間に生み出せる成果が変わります。

## ワークフロー：全体像

```
 English source document
        │
        ▼
 Machine draft  ←  a benchmarked, community-owned method
        │
        ▼
 Fluent-speaker post-edit  ←  the human gate; nothing skips it
        │
        ▼
 Published text  ←  carries human approval, not a machine score
        │
        ▼
 (Optional, community-controlled) corrections become
 data that improves the next version of the method
```

注目すべき点が三つあります。

1. **機械は公開しない。** 出力の単位は下書きです。話者による修正作業は、最後に付け足す品質保証ではありません。それ自体がワークフローです。
2. **最適化すべきリソースは話者の時間です。** ある手法が別の手法より優れているのは、話者が修正する量を減らせる限りにおいてです。リソースが豊富な言語のポストエディットに関する研究では、中程度のMT品質であれば、ゼロから翻訳するより一貫して速いという結果が出ています（Plitt & Masselot 2010; Green, Heer & Manning 2013、いずれもリンク付きで[翻訳は言語復興ではない](/docs/network/perspectives/translation-is-not-revitalization)に引用）。これが多合成語言語にも当てはまるかどうかを検証するために、まさにベンチマークが存在します。私たちはこれを言語ごとに検証すべき仮説として扱っており、前提とはしていません。
3. **フィードバックループはコミュニティが所有する。** 修正済みの文書はすべて、トレーニングやコーチングのデータになり得ます。そしてそれはコミュニティに帰属し、[データ主権](/docs/network/sovereignty/data-sovereignty)のルールのもと、コミュニティ自身の判断でフィードバックするかどうかを決めます。フィードバックの仕組みはプラットフォームの設計目標ですが、まだ実装されていません。修正と出所がどのように機能する予定かについては、[エラーの報告と修正の所有](/docs/network/perspectives/reporting-errors-and-owning-corrections)をご覧ください。

## リーダーボードのスコアが示せること・示せないこと

リーダーボードは機械翻訳（MT）分野の慣例に従って手法をランク付けします。具体的には、95%信頼区間およびsacreBLEUシグネチャを伴うコーパスレベルの**chrF++**（0〜100）を主指標とし、併せてBLEU、spBLEU、TER、COMETを表示し、FST受容性などの診断結果を個別に報告します（[スコアリング仕様](/docs/network/specifications/scoring#how-runs-are-scored)）。同一の評価セットにおいてある手法が別の手法よりも優れているかどうかは、2つの数値を大まかに見比べるのではなく、対応のある有意差検定によって判断されます（[有意差検定](/docs/network/specifications/significance)）。

これがコミュニティに伝えるのは、どの手法が信頼できる参照訳に近い出力を生成するか、そして2つの手法の差が有意（本物）であるかということです。一方、伝えることができないのは、その下書きが話者の時間を割くに値するものかどうかです。同じchrF++の数値であっても、言語や評価セットが異なればその意味合いは変わるため、ここではいかなる自動スコアにも品質ラベルを付与していません。以前のNetworkでは、加重複合スコアを名前付きの階層（「実用的（functional）」、「展開可能（deployable）」など）にマッピングしていましたが、入力に対して有効な同一文を繰り返すだけのシステムが「実用的」と判定されてしまったことなどを理由に、これらのラベルは廃止されました（[複合スコアが廃止された理由](/docs/network/specifications/scoring#why-the-composite-was-retired)）。

[ベンチマーク仕様 §7](/docs/network/specifications/benchmark#7-human-validation)から、構造的誠実性に関する2つのルールが導かれます。

- **スコアは人間によるレビューへの推薦であり、決定ではありません。** 高いchrF++スコアはその手法を話者と共にパイロット運用する価値があることを示すだけであり、実用に耐える準備ができたことを意味するわけではありません。
- **手法がポストエディットワークフローに対応できる準備が整ったと判断できるのは、コミュニティレビューのみです。** 出力の層化サンプルがバイリンガル話者に送られ、各翻訳を*拒否（reject）/ 大意把握可能（gist）/ 許容可能（acceptable）/ 優秀（excellent）*として評価します。その手法を次の段階に進めるかどうかを決定するのは、リーダーボードではなくガバナンス組織です。

比較として、[Founder's Prize](/docs/network/specifications/prizes)（創設者賞）の条件（chrF++の下限、ゲート条件としての形態素的に有効な単語率99%以上、話者による「許容可能」以上の評価70%以上）は、残された誤りが捏造された単語ではなく、語形変化の誤りなどの*実際の言語としての誤り*にとどまる手法を定義しています。これが数値として表された「話者の時間を割くに値する下書き」の姿であり、それを確定させる決定打となるのが話者による判定です。

## 優勝手法から機能するオフィスへ

ある手法がそれらの関門を通過したとします。残りのステップは組織的なものであり、即興ではなく仕様として定められています。

1. **所有権が移転する。** 手法のコードはコミュニティのガバナンス組織の所有物になります。開発者は帰属表示と公開の権利を保持します（[所有権の移転](/docs/network/sovereignty/ownership-transfer)）。
2. **手法はサービスになる——コミュニティのサービスとして。** ガバナンス組織が自身のインフラで実行し、アクセスと許可された用途を管理できるプラグインとしてパッケージ化されます（[本番環境へのデプロイ](/docs/network/getting-started/deploy-to-production)）。コミュニティが商業的に提供することを選択した場合、それはあらゆる意味でコミュニティのビジネスです。Champollionは収益を受け取りません（[活動の資金調達について](/docs/network/sovereignty/economic-model)）。
3. **翻訳者が日常業務に組み込む。** 翻訳オフィスは既存の文書ワークフローを手法のAPIに向けます。原文を入力し、下書きを受け取り、ポストエディットして公開します。公開されたテキストには翻訳者の名前と権威が付きます。機械は辞書と同じく、翻訳者の机の上にあるツールです。

## 現状について

率直に言えば、全体の道筋はエンドツーエンドで仕様化されており、部分的に構築されています。評価ハーネス、メトリクス、実行カード、公開リーダーボードは存在しています。評価サンドボックスは構築済みですが、トイモデルでのリハーサルにとどまっています。アップストリームにはPlains Creeの開発コーパスが存在します。賞の提案は行われていますが、まだ募集は開始されていません。デプロイプラットフォームは存在しています。コミュニティレビューのインターフェースおよび修正済みテキストのフィードバックループは仕様化されているものの、まだ稼働していません — 仕様上も計画中と記載されており、私たちの見解も同様です。ベンチマークからコミュニティでの日常的な利用に至る全工程を完了した手法はまだ存在しません。その全工程を成し遂げることこそがこのプロジェクトにおける「成功」の定義であり、だからこそ私たちは時期尚早な成功を主張しないのです。

## これがあなたにとって意味すること

:::info[コミュニティメンバーの方へ]
リーダーボードのハイスコアは、機械が監視なしにあなたの言語でコンテンツを公開することを意味するものでは決してありません。それは、下書き生成ツールがあなたの翻訳者に向けて、あなた方の条件のもとで、あなた方の話者を審査員（有償の審査員 — [話者への報酬支払いについて](/docs/network/perspectives/how-speakers-get-paid)を参照）として*オーディション*を受ける準備ができた可能性があることを意味します。コミュニティで翻訳オフィスを運営されている場合、私たちにお尋ねいただきたい論点は「パイロット運用はどのような形になり、誰が出力をレビューするのか？」ということです。
:::

:::info[研究者の方へ]
ポストエディットという枠組みは、測定すべき価値のある対象を変えます。それは単なるchrF++ではなく、話者がプロセスに関与した状態（speaker-in-the-loop）で「許容可能なテキストになるまでの時間」です。Networkのメトリクスはその代替指標であり（[スコアリング仕様 §1](/docs/network/specifications/scoring)）、形態素的に複雑な言語を対象とした言語ごとのポストエディット研究は、本インフラストラクチャが支援することを目的とした未開拓の研究課題です。
:::

:::info[開発者の方へ]
メトリクスではなく、編集者のために最適化してください。実在する単語を生成しつつ、ときどき活用形を誤るような手法は、スピーカーが数秒で修正できます。一方、もっともらしく見える形式を幻覚するような手法はワークフロー全体を汚染します。これが、形態論的妥当性がここで厳しくゲートされている理由です。まず [Submit a Method](/docs/network/getting-started/submit-a-method) から始め、勝利した場合に最終的に引き渡すものについては [Method Interface](/docs/network/specifications/methods) をお読みください。
:::
