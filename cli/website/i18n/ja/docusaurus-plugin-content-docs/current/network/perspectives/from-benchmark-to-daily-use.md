# ベンチマークから日常利用へ：ポストエディットという道筋

> **要約。** リーダーボードのスコアは製品ではありません。「この手法のスコアは0.78だ」から「バンドオフィスが毎週その言語で文書を公開している」に至る道筋は、ただ一つのワークフローを通ります。機械が下書きを生成し、流暢な話者がそれを修正し、修正済みのテキストだけが公開される、というものです。私たちの仕様書にあるすべての品質基準は、このワークフローに合わせて調整されています。監督なしの機械出力を基準にしているのではありません。本プラットフォームのいかなる言語においても、監督なしの機械出力は推奨しません。

「いつになったら翻訳手法が『そのまま使えるほど良くなる』のか」と聞かれることがあります。このネットワークが対象とする言語において、その問いには落とし穴があります。正直に答えるなら、目指すべき基準は「レビューなしで公開できるほど良い」ではありません。**「下書きをレビューする方が、ゼロから翻訳するより速い、と言えるほど良い」**ことです。この基準ははるかに低く、測定可能であり、それを超えることでコミュニティの翻訳オフィスが一週間に生み出せる成果が変わります。

## ワークフロー：全体像

```
 English source document
        │
        ▼
 Machine draft  ←  a benchmarked, community-owned method
        │
        ▼
 Fluent-speaker post-edit  ←  the human gate; nothing skips it
        │
        ▼
 Published text  ←  carries human approval, not a machine score
        │
        ▼
 (Optional, community-controlled) corrections become
 data that improves the next version of the method
```

注目すべき点が三つあります。

1. **機械は公開しない。** 出力の単位は下書きです。話者による修正作業は、最後に付け足す品質保証ではありません。それ自体がワークフローです。
2. **最適化すべきリソースは話者の時間です。** ある手法が別の手法より優れているのは、話者が修正する量を減らせる限りにおいてです。リソースが豊富な言語のポストエディットに関する研究では、中程度のMT品質であれば、ゼロから翻訳するより一貫して速いという結果が出ています（Plitt & Masselot 2010; Green, Heer & Manning 2013、いずれもリンク付きで[翻訳は言語復興ではない](/docs/network/perspectives/translation-is-not-revitalization)に引用）。これが多合成語言語にも当てはまるかどうかを検証するために、まさにベンチマークが存在します。私たちはこれを言語ごとに検証すべき仮説として扱っており、前提とはしていません。
3. **フィードバックループはコミュニティが所有する。** 修正済みの文書はすべて、トレーニングやコーチングのデータになり得ます。そしてそれはコミュニティに帰属し、[データ主権](/docs/network/sovereignty/data-sovereignty)のルールのもと、コミュニティ自身の判断でフィードバックするかどうかを決めます。フィードバックの仕組みはプラットフォームの設計目標ですが、まだ実装されていません。修正と出所がどのように機能する予定かについては、[エラーの報告と修正の所有](/docs/network/perspectives/reporting-errors-and-owning-corrections)をご覧ください。

## 品質ティアが実際の利用においてどう意味するか

リーダーボードは自動化されたメトリクスの複合スコアで手法を評価し（[スコアリング仕様](/docs/network/specifications/scoring)）、スコアは名前付きのティアに対応します。以下は、それらのティアを日常利用の観点から正直に翻訳したものです。

| ティア（複合スコア） | ポストエディットの観点での意味 |
|---|---|
| **Baseline**（0.00〜0.30） | いかなる用途にも使えない。出力の大部分がターゲット言語ではない。研究上の下限としてのみ有用。 |
| **Emerging**（0.30〜0.50） | まだ下書きツールとしては使えない。正しい断片は現れるが、話者はゼロから書くより修正に時間がかかる。 |
| **Functional**（0.50〜0.70） | 簡単なテキストについて、ポストエディットがゼロからの翻訳を*上回る可能性がある*最初のティア。話者と試験運用する価値はあるが、依存するには早い。形態論的なエラーが頻繁に残る。 |
| **Deployable**（0.70〜0.85） | 上記ワークフローの目標ティア。形態論の大部分が正しく、流暢な話者が再翻訳より意味のある速さで修正できる下書き。**「Deployable」とは、ポストエディットワークフロー*への*展開が可能という意味であり、「レビューなしで公開可能」という意味では決してない。** |
| **Fluent**（0.85〜1.00） | 有能な人間の翻訳に近い。エラーはまれで軽微。レビュー作業は残るが、速くなる。 |

この表の上に、[ベンチマーク仕様 §5 および §7](/docs/network/specifications/benchmark#5-quality-tiers) から直接引用した、構造的な誠実さに関する二つのルールがあります。

- **自動化されたティアは暫定的なラベルであり、判定ではない。** 人間によるレビューへの推薦です。閾値は話者による検証データが蓄積されるにつれて再調整され、言語によって異なる結果になる可能性があります。
- **コミュニティレビューなしに、いかなる手法もDeployable以上を主張できない。** 出力の層化サンプルがバイリンガルの話者に送られ、各翻訳を*reject / gist / acceptable / excellent*で評価します。手法が昇格するかどうかを決めるのは、リーダーボードではなくガバナンス組織です。

比較のために、[創設者賞](/docs/network/specifications/prizes)の閾値（複合スコア ≥ 0.80、形態論的に有効な語 ≥ 99%、話者評価でacceptable以上 ≥ 70%）は、残存するミスが*実際の言語エラー*（作り上げられた語ではなく、誤った活用）である手法を表しています。「話者の時間に値する下書き」を数値で表すとこうなります。

## 優勝手法から機能するオフィスへ

ある手法がそれらの関門を通過したとします。残りのステップは組織的なものであり、即興ではなく仕様として定められています。

1. **所有権が移転する。** 手法のコードはコミュニティのガバナンス組織の所有物になります。開発者は帰属表示と公開の権利を保持します（[所有権の移転](/docs/network/sovereignty/ownership-transfer)）。
2. **手法はサービスになる——コミュニティのサービスとして。** ガバナンス組織が自身のインフラで実行し、アクセスと許可された用途を管理できるプラグインとしてパッケージ化されます（[本番環境へのデプロイ](/docs/network/getting-started/deploy-to-production)）。コミュニティが商業的に提供することを選択した場合、それはあらゆる意味でコミュニティのビジネスです。Champollionは収益を受け取りません（[活動の資金調達について](/docs/network/sovereignty/economic-model)）。
3. **翻訳者が日常業務に組み込む。** 翻訳オフィスは既存の文書ワークフローを手法のAPIに向けます。原文を入力し、下書きを受け取り、ポストエディットして公開します。公開されたテキストには翻訳者の名前と権威が付きます。機械は辞書と同じく、翻訳者の机の上にあるツールです。

## 現状について

率直に言えば、全体の道筋は仕様として端から端まで定められており、部分的に構築されています。評価ハーネス、メトリクス、実行カード、公開リーダーボードは存在します。Plains Creeの開発コーパスとアクティブな賞も存在します。デプロイメントプラットフォームも存在します。コミュニティレビューインターフェース、評価サンドボックス、修正済みテキストのフィードバックループは仕様として定められていますが、まだ稼働していません。仕様書ではそれらを計画中と記しており、私たちも同様に記します。ベンチマークから日常的なコミュニティ利用まで、全行程を完了した手法はまだありません。その旅こそがこのプロジェクトの成功の定義です。だからこそ、早まって達成を主張することはしません。

## これがあなたにとって意味すること

:::info[コミュニティメンバーの方へ]
リーダーボードの「Deployable」バッジは、機械があなたの言語で監督なしに公開するという意味では決してありません。これは、ドラフト生成ツールがあなたの翻訳者のために*オーディション*を受ける準備ができているかもしれないということを意味します。あなたの条件で、あなたのスピーカーを審査員として（有償で — [スピーカーへの報酬について](/docs/network/perspectives/how-speakers-get-paid)をご覧ください）。コミュニティが翻訳オフィスを運営している場合、私たちに持ちかけるべき質問はこうです：「パイロットはどのような形になるか、そして誰が出力をレビューするか？」
:::

:::info[研究者の方へ]
ポストエディットという枠組みは、何を測定する価値があるかを変えます。複合スコアだけでなく、スピーカーがループに入った状態での「許容できるテキストに到達するまでの時間」が重要です。Network のメトリクスはその代理指標です（[スコアリング仕様 §1](/docs/network/specifications/scoring)）。形態論的に複雑な言語に対する言語別ポストエディット研究は未開拓の研究領域であり、このインフラはそれを支援するために設計されています。
:::

:::info[開発者の方へ]
メトリクスではなく、編集者のために最適化してください。実在する単語を生成しつつ、ときどき活用形を誤るような手法は、スピーカーが数秒で修正できます。一方、もっともらしく見える形式を幻覚するような手法はワークフロー全体を汚染します。これが、形態論的妥当性がここで厳しくゲートされている理由です。まず [Submit a Method](/docs/network/getting-started/submit-a-method) から始め、勝利した場合に最終的に引き渡すものについては [Method Interface](/docs/network/specifications/methods) をお読みください。
:::
