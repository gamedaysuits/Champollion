# 翻訳は言語復興ではない

> **立場。** 機械翻訳はテキストを言語間で変換します。言語復興は新たな話者を生み出します。これらは異なる活動であり、成功の基準も異なります。リーダーボードのスコアがそれを変えることはありません。私たちは機械翻訳をコミュニティの目標に奉仕するインフラとして構築しています――世代間の言語継承の代替としてではなく。子どもは機械からではなく、人から言語を学びます。

2026年、ソフトウェアが話者を失いつつある言語を含め、あらゆる問題を解決できると信じることは容易です。私たちはその信念がなぜ誤りなのか、そして翻訳技術が*正直に*何に貢献できるのかを明確にしたいと思います。

このページが存在するのは、このプロジェクトを批評するよう招いた言語学者が、ある論点を強く主張したからです。完璧な英語→クリー語翻訳システムがあっても、継承の問題（子どもが家庭で言語を学ばないこと）、威信の問題（英語が経済的権力の言語であること）、教育の問題（イマージョンスクールと訓練された教師の不足）は解決されないという主張です。むしろ事態を悪化させる可能性すらあります。「コンピューターがクリー語を話せる」という幻想を生み出し、人による継承の緊急性を薄めてしまうかもしれません。私たちはその批評の大部分を受け入れ、それを埋もれさせるのではなく、ここに回答を公開します。

---

## 言語復興が実際に必要とするもの

言語復興に関する研究文献は一点において一致しています。言語は世代間で受け継がれるときに生き残る――親や祖父母やコミュニティが子どもに話しかけ、子どもが話し返しながら育つとき（Fishman 1991; Hinton & Hale 2001）。それ以外のすべて――学校、メディア、辞書、アプリ――はその継承を支援するか、さもなければ何も支援しないかのどちらかです。

いかなる翻訳システムもその交換には参加しません。英語の文書をプレーンズ・クリー語に変換するモデルは、話者を生み出しません。イマージョン教室に人員を配置することも、教師を育成することも、台所のテーブルで子どもと向き合うこともしません。私たちの取り組みが「言語を救っている」と表現されることがあれば、その表現は誤りであり、私たちはそう言います。

## 機械翻訳にできないこと

後で曖昧さが生じないよう、明確に述べます。

- **話者の代替はできません。** 流暢な話者がレビューしていない出力は草稿であり、テキストではありません。私たち自身の[スコアリングルール](/docs/network/specifications/scoring)では、すべての自動スコアを代理指標として扱います。使用可能かどうかを確認できるのは人によるレビューだけです。
- **第一言語を教えることはできません。** 子どもは関係性とイマージョンを通じて言語を習得します。翻訳された文書を通じてではありません。
- **有害な幻想を生み出す可能性があります。** ある言語を「話す」デモは、その言語が安全な状態にあるという印象を与えかねません。この威信に関するリスクは現実のものであり、私たちはそれをコミュニティと*ともに*検討すべき未解決の問題として扱います――管理すべき話題としてではなく。
- **何も決定することはできません。** ある言語に翻訳システムを存在させるべきかどうか、またどこで使用してよいかは、コミュニティが判断することです――まったく導入しないという判断も含めて。そのコントロールは[所有権の移転](/docs/network/sovereignty/ownership-transfer)と[データ主権](/docs/network/sovereignty/data-sovereignty)のアーキテクチャに組み込まれており、文脈も含まれます。コミュニティは公式文書には機械翻訳を受け入れ、教室教材には拒否するという選択もできます。

## 機械翻訳が正直にできること

以上を踏まえた上で、翻訳インフラが貢献できる具体的で限定的なことがあります――それぞれが、すでに本当の仕事をしている人々に奉仕するものです。

**1. 過負荷の翻訳者のためのスループット向上。** コミュニティの翻訳部門は、その言語で*存在すべき*文書を、人間の翻訳者がゼロから作成できる量よりも多く抱えています。機械による草稿は、仕事を「すべてを翻訳する」から「レビューして修正する」へと変えます。そして管理された研究では、ポストエディットはゼロからの翻訳よりも大幅に速く、品質は維持または向上することが示されています（Plitt & Masselot 2010; Green, Heer & Manning 2013）。このワークフローについては[ベンチマークから日常利用へ](/docs/network/perspectives/from-benchmark-to-daily-use)で詳しく説明しています。留保事項として、これらの研究は高リソース言語ペアを対象としており、多合成語言語に関する同等のエビデンスはまだありません。それを測定するためにこのプロジェクトが設立された理由の一つです。

**2. 言語権のための実践的なレバレッジ。** 先住民族の言語による行政サービスを受ける権利は、いくつかの法域で法律に存在します。しばしば欠けているのは、官僚主義が要求するスピードで翻訳を生産する実践的な能力です。50ページの政策文書を数ヶ月ではなく数日でレビュー済みの翻訳に変えられるコミュニティは、より強い交渉力を持ちます。技術が権利を生み出すのではありません。技術は権利を無視しにくくするのです。

**3. 再利用可能な言語インフラ。** 翻訳出力に実在する単語が含まれているか――幻覚された単語ではなく――を検証するために使用する形態素解析器（FST）は、各語形がなぜ有効なのかをエンコードしています。その同じ仕組みが学習ツールの基盤となります。活用トレーナー、誤り訂正ライティング支援、形態素エクスプローラーなどです。検証エンジンと教育エンジンは同じ成果物です。これは約束ではなく、可能性の道筋です――学習ツールは構築が必要であり、構築されるかどうかはコミュニティの決定です。

**4. 第二言語学習者への支援。** 言語復興は、子どもが第一言語を習得することだけではありません。大人が第二言語として学ぶことでもあります――長老レベルの流暢さには達しないかもしれないが、コミュニティの文書を読み、理解しながら参加し、言語を使うことでその公的な存在感を高められる人々です。この層にとって、翻訳支援は辞書が道具であるのと同様に、本物の道具です。

**5. 仕事が地元で資金調達され所有される理由。** 私たちのモデルでは、実証された手法は[コミュニティの所有権に移転](/docs/network/sovereignty/ownership-transfer)され、コミュニティが所有する資産から得た収益はすべてそのコミュニティのものです（[仕事の資金調達方法](/docs/network/sovereignty/economic-model)）。話者は専門知識に対して[報酬を受け取ります](/docs/network/perspectives/how-speakers-get-paid)――ボランティアを求められるのではなく。これらのいずれも言語復興ではありません――しかし、言語復興を行っている人々に向けてリソースを向けます。彼らから遠ざけるのではなく。

## 正直なフレーミング

この分野には、救済の物語とともに現れ、論文を残して去っていくテクノロジープロジェクトの長い記録があります（Bird 2020）。私たちはより限定的な主張を保持しようとしています。**機械翻訳はインフラです。** インフラは他者が設定した目標に奉仕します。道路はあなたがどこへ旅するかを決めません。この技術は言語が生き残るかどうかを決めません。話者、家族、コミュニティが決めます――そして[ユネスコ先住民族言語の国際の十年](https://idil2022-2032.org/)のフレーミングは、ツールではなく先住民族を中心に置くことで正しいと言えます。

コミュニティが翻訳技術が自分たちの目標に役立つと結論づけるなら、私たちはそれを可能な限り最良で最も説明責任のあるバージョンにしたいと思います――コミュニティが所有し、話者によって検証され、コミュニティの条件で展開される。コミュニティが役立たないと結論づけるなら、その結論はこのプロジェクトの失敗ではなく、有効な成果です。その文の両半分がコミットメントです。

## これがあなたにとって意味すること

:::info[コミュニティメンバーの方へ]
このプロジェクトは、アプリがあなたの言語を救えるとは主張しません――実際、そうはなりません。提供できるものには限りがあります：流暢な話者によるレビューのもとでの文書翻訳の効率化、コミュニティが完全に所有できるインフラ、そして話者の専門知識への報酬です。それらをどのように、またはそもそも使用するかどうかは、使用しないという選択も含め、コミュニティ自身が決めることです。[言語コミュニティの方へ](/docs/network/community/for-language-communities)および[エラーの報告と修正の所有](/docs/network/perspectives/reporting-errors-and-owning-corrections)をご覧ください。
:::

:::info[研究者の方へ]
「危機言語に対する機械翻訳」を、言語復興の主張としてではなく、インフラに関する主張として捉えると、評価の問いが変わります：「BLEUスコアは高いか？」ではなく、「実際の作業を担う人々の負担を、彼らの条件のもとで測定可能な形で軽減できているか？」という問いになります。[ベンチマーク仕様](/docs/network/specifications/benchmark)および[仕組み §8（緊張関係と限界）](/docs/network/how-it-works#8-tensions-and-limitations)において、私たちはその基準に基づいて自らを律しています。
:::

:::info[開発者の方へ]
デモではなく、ポストエディットのワークフローを念頭に置いて構築してください。あなたの手法を使うのは、下書きを修正する流暢な話者です。最悪の失敗パターンは、非話者には自然に見えてしまう幻覚的な語の生成です――だからこそ、ここではすべてに形態論的な検証ゲートを設けています。まずは[手法の提出](/docs/network/getting-started/submit-a-method)および[ベンチマークから日常利用へ](/docs/network/perspectives/from-benchmark-to-daily-use)をご覧ください。
:::
