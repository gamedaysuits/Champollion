# 翻訳は言語復興ではない

> **立場。** 機械翻訳はテキストを言語間で変換します。言語復興は新たな話者を生み出します。これらは異なる活動であり、成功の基準も異なります。リーダーボードのスコアがそれを変えることはありません。私たちは機械翻訳をコミュニティの目標に奉仕するインフラとして構築しています――世代間の言語継承の代替としてではなく。子どもは機械からではなく、人から言語を学びます。

2026年、ソフトウェアが話者を失いつつある言語を含め、あらゆる問題を解決できると信じることは容易です。私たちはその信念がなぜ誤りなのか、そして翻訳技術が*正直に*何に貢献できるのかを明確にしたいと思います。

本稿が存在するのは、ある言語学者の視点から書かれた本プロジェクトへの批評において、次のような力強い主張がなされたためです。すなわち、完璧な英語→クリー語の翻訳システムがあったとしても、継承の問題（子どもたちが家庭で言語を学ばないこと）、威信の問題（経済的力を持つ言語としての英語）、あるいは教育上の問題（イマージョンスクールや訓練を受けた教員の不足）は解決されないということです。それどころか、「コンピューターがクリー語を話せる」という幻想を生み出し、人間による継承の切迫感を薄れさせることで、事態をさらに悪化させる可能性すらあります。私たちはその批判の大部分を受け入れ、それを覆い隠すのではなく、ここに私たちの回答を公開します。

---

## 言語復興が実際に必要とするもの

言語復興に関する研究文献は一点において一致しています。言語は世代間で受け継がれるときに生き残る――親や祖父母やコミュニティが子どもに話しかけ、子どもが話し返しながら育つとき（Fishman 1991; Hinton & Hale 2001）。それ以外のすべて――学校、メディア、辞書、アプリ――はその継承を支援するか、さもなければ何も支援しないかのどちらかです。

いかなる翻訳システムもその交換には参加しません。英語の文書をプレーンズ・クリー語に変換するモデルは、話者を生み出しません。イマージョン教室に人員を配置することも、教師を育成することも、台所のテーブルで子どもと向き合うこともしません。私たちの取り組みが「言語を救っている」と表現されることがあれば、その表現は誤りであり、私たちはそう言います。

## 機械翻訳にできないこと

後で曖昧さが生じないよう、明確に述べます。

- **話者の代わりにはなれません。** 流暢な話者による確認を経ていない出力は、テキストではなく下書き（ドラフト）にすぎません。私たちの[スコアリング規則](/docs/network/specifications/scoring)でも、すべての自動スコアを代用指標として扱っており、実用性を確認できるのは人間のレビューだけです。
- **第一言語（母語）を教えることはできません。** 子どもは翻訳された文書を通じてではなく、人との関係やイマージョン（言語浸漬）を通じて言語を習得します。
- **有害な錯覚を生み出す恐れがあります。** ある言語を「話す」デモは、実際には危機に瀕しているにもかかわらず、その言語が安全であるかのような印象を与えることがあります。このプレステージリスクは実在するものであり、私たちはこれをごまかすための想定問答ではなく、コミュニティ*とともに*検討すべき未解決の問いとして捉えています。
- **何も決定することはできません。** ある言語のための翻訳システムが存在すべきかどうか、またどこで使用されるべきかは、コミュニティ自身の判断です。まったく配備しないという判断も含みます。この管理権限は、[所有権の移転](/docs/network/sovereignty/ownership-transfer)や[データ主権](/docs/your-words-your-rules)の設計に組み込まれており、文脈による使い分けも含まれます。たとえば、公式文書には機械翻訳を受け入れる一方、教室の教材には拒否するといった判断が可能です。

## 機械翻訳が正直にできること

以上を踏まえた上で、翻訳インフラが貢献できる具体的で限定的なことがあります――それぞれが、すでに本当の仕事をしている人々に奉仕するものです。

**1. 負担の大きい翻訳者の処理能力向上。** コミュニティの翻訳部署は、人間の翻訳者が一から作成できる量を超える、その言語で存在する*べき*文書を抱えています。機械による下書きは、業務を「すべてを一から翻訳する」ことから「見直して修正する」ことへと変えます。そして対照実験研究では、品質を維持または向上させながら、ポストエディットが一から翻訳するよりも有意に速いことが示されています（Plitt & Masselot 2010; Green, Heer & Manning 2013）。このワークフローについては、[現場での活用](/docs/put-it-to-work)で詳しく説明しています。ただし留意点として、それらの研究は高リソース言語ペアを対象としたものでした。複統合語（抱合語）について同等の証拠はまだ得られておらず、それを測定することも本プロジェクトの目的の一部です。

**2. 言語権のための実践的なレバレッジ。** 先住民族の言語による行政サービスを受ける権利は、いくつかの法域で法律に存在します。しばしば欠けているのは、官僚主義が要求するスピードで翻訳を生産する実践的な能力です。50ページの政策文書を数ヶ月ではなく数日でレビュー済みの翻訳に変えられるコミュニティは、より強い交渉力を持ちます。技術が権利を生み出すのではありません。技術は権利を無視しにくくするのです。

**3. 再利用可能な言語インフラ。** 翻訳出力に実在する単語が含まれているか――幻覚された単語ではなく――を検証するために使用する形態素解析器（FST）は、各語形がなぜ有効なのかをエンコードしています。その同じ仕組みが学習ツールの基盤となります。活用トレーナー、誤り訂正ライティング支援、形態素エクスプローラーなどです。検証エンジンと教育エンジンは同じ成果物です。これは約束ではなく、可能性の道筋です――学習ツールは構築が必要であり、構築されるかどうかはコミュニティの決定です。

**4. 第二言語学習者への支援。** 言語復興は、子どもが第一言語を習得することだけではありません。大人が第二言語として学ぶことでもあります――長老レベルの流暢さには達しないかもしれないが、コミュニティの文書を読み、理解しながら参加し、言語を使うことでその公的な存在感を高められる人々です。この層にとって、翻訳支援は辞書が道具であるのと同様に、本物の道具です。

**5. 活動資金が地元で調達され、成果が地元に帰属するための理由。** 私たちのモデルでは、有効性が実証された手法は完全に[コミュニティ所有へと移転](/docs/network/sovereignty/ownership-transfer)され、所有する資産からコミュニティが得た利益はすべてそのコミュニティのものとなります（[誰が利用でき、費用はいくらか](/docs/getting-started/who-may-use-this)）。話者は専門知識に対して[対価を受け取り](/docs/working-with-speakers)、ボランティアとしての提供を求められることはありません。これらもまた復興そのものではありませんが、リソースを復興活動を行う人々から奪うのではなく、その人々へと届けることにつながります。

## 正直なフレーミング

この分野には、救済の物語とともに現れ、論文を残して去っていくテクノロジープロジェクトの長い記録があります（Bird 2020）。私たちはより限定的な主張を保持しようとしています。**機械翻訳はインフラです。** インフラは他者が設定した目標に奉仕します。道路はあなたがどこへ旅するかを決めません。この技術は言語が生き残るかどうかを決めません。話者、家族、コミュニティが決めます――そして[ユネスコ先住民族言語の国際の十年](https://idil2022-2032.org/)のフレーミングは、ツールではなく先住民族を中心に置くことで正しいと言えます。

コミュニティが翻訳技術が自分たちの目標に役立つと結論づけるなら、私たちはそれを可能な限り最良で最も説明責任のあるバージョンにしたいと思います――コミュニティが所有し、話者によって検証され、コミュニティの条件で展開される。コミュニティが役立たないと結論づけるなら、その結論はこのプロジェクトの失敗ではなく、有効な成果です。その文の両半分がコミットメントです。

## これがあなたにとって意味すること

:::info[コミュニティの方へ]
このプロジェクトは、アプリが言語を救えるなどとは言いません――そんなことはできないからです。提供できることは限定されています。流暢な話者のレビューのもとで文書の翻訳を迅速化すること、コミュニティが完全に所有できるインフラ、そして話者の専門知識に対する対価です。それらのいずれかを、どのように使用するか（あるいはまったく使用しないか）は、コミュニティの決定事項です。[あなたの言葉、あなたのルール](/docs/your-words-your-rules)および[エラーの報告と修正の所有権](/docs/network/perspectives/reporting-errors-and-owning-corrections)をご覧ください。
:::

:::info[研究者の方へ]
「危機言語のための機械翻訳」を言語復興の主張ではなく、インフラに関する主張として捉えると、評価における問いが変わります。「BLEUスコアは高いか？」ではなく、「実際の活動を行っている人々の負担を、彼ら自身の基準に沿って測定可能な形で軽減できているか？」です。[ベンチマーク仕様](/docs/network/specifications/benchmark)および[リーダーボードと公開](/docs/reference/leaderboard)は、私たちが自らにその基準を課している場所です。
:::

:::info[開発者の方へ]
デモのためではなく、ポストエディットのワークフローのために構築してください。あなたの手法の利用者は、下書きを修正する流暢な話者です。そして最悪の失敗パターンは、非話者にはもっともらしく見える、ハルシネーションによって生成された単語です。だからこそ、ここでは形態論的検証がすべての関門となっています。まずは[手法の提出](/docs/network/getting-started/submit-a-method)と[現場での活用](/docs/put-it-to-work)から始めてください。
:::
