# 賞仕様

賞金は、評価優先の取り決めのインセンティブ側の要素です。コミュニティまたは研究グループが、小規模で非公開の評価セットを厳選します — 数百組のペアであり、すべてがチェックされています（このワークフローが[コーパスパートナーシップ](/docs/network/specifications/corpus-partnership)です）。スポンサーは、その評価セットに対する目標スコアに対して賞金を掲示します。その瞬間から、その言語は常設のチャレンジとなります。世界中のあらゆる手法開発者がこれを目指すことができ、リーダーボードはすべての試行を公開で測定し、合否基準は最も声の大きい者ではなくコミュニティ自身の正解基準によって決定されます。本文書では、このような賞金がどのように機能するか — 閾値条件、請求プロセス、依存関係クラス、およびルール — を規定し、賞金が開始されたときに基準が一義的かつ手法に依存しないものとなるようにします。

賞金は**スポンサーから拠出され、スポンサーによって保持されます**。資金はスポンサー組織、またはスポンサーが指定するコミュニティトラストに保管されます — **Champollionが賞金資金を保持、エスクロー、または送金することは決してありません。** あらゆるコミュニティや組織は、[主権コンテストの実施](/docs/network/sovereignty/run-a-sovereign-contest)にあるセルフサービスの手順に従って独自のコンテストを実施し、独自のコーパスと独自の資金を保持できます。

> **ステータス: 提案中（PROPOSED） — 現在開かれている賞金はなく、請求可能なものもまだありません。**
> 賞金の*開始*を左右するのは測定側です。すなわち、コミュニティの合意を得たゴールドスタンダードコーパスと、話者レビューの関門です。どちらもまだ存在していません。エアギャップ（物理隔離）環境の評価サンドボックスはすでに提供されています — [ベンチマーク仕様 §8.6](/docs/network/specifications/benchmark#86-dependency-classes-and-the-sandbox-network-policy)を参照してください。このサイト上のどのスコアも、賞金の基準をクリアしていません。[率直な制限事項](/docs/network/honest-limitations)を参照してください。メトリクスに関するリファレンス: [スコアリング仕様](/docs/network/specifications/scoring)、プロトコル: [ベンチマーク仕様](/docs/network/specifications/benchmark)。

> **約束レイヤーは稼働しています。** エントリーが存在するようになった後に宣言された賞金条件を編集不可にする凍結、および非公開（`hidden_until_close`）の結果は、2026-09-07時点でネットワークホスト型エンドポイント上のデータベースで強制されています。フェデレーションホストは、テストハーネスに同梱されているマイグレーションを適用することで同じルールを取得できます。より古いエンドポイントに対しては、ハーネスは偽ることなくベースセットにフォールバックし、その旨を通知します。§3.2の集計値のみのエグレスルールは、以前から常にすべての場所で適用されています。

## 言語をネットワークに加えるためにご協力いただけますか？

賞を待つ必要はありません。今日できる最も効果的なことは以下のとおりです:

- **MT達成賞のスポンサーになる。** 具体的な目標に資金を提供します — たとえば、信頼性の高い英語 → Plains Cree の手法など。Champollionが測定を調整します。資金は**あなた**（あなたの組織、またはあなたが指定するコミュニティトラスト）のもとに置かれ、コミュニティの条件に基づいて授与されます（[Data Sovereignty](/docs/network/sovereignty/data-sovereignty)および[Economic Model](/docs/network/sovereignty/economic-model)を参照）。エンドツーエンドのセルフサービスパスは[Run a Sovereign Contest](/docs/network/sovereignty/run-a-sovereign-contest)に記載されています。新しい言語ペアの追加は[corpus partnership](/docs/network/specifications/corpus-partnership)から始まります。
- **コンピュートの寄付を調整する。** APIクレジット/トークンをプールして、公開キューがより多くのペアをマッピングし、翻訳が信頼できる箇所とそうでない箇所を明らかにできるようにします。
- **私たちが基盤とするオープンソースイニシアチブを*直接*支援する。** Champollionは他者のオープンな成果をつなぎ合わせる配管です。*彼ら*を支援することがこのマップを支援することになります（私たちは彼らの成果の功績を横取りするよりも、上流を案内したいと考えています）:
  - [Tatoeba](https://tatoeba.org) — コミュニティが提供する対訳文
  - [Endangered Languages Catalog (ELCat)](https://www.endangeredlanguages.com) — 危機言語データ
  - [Glottolog](https://glottolog.org) · [WALS](https://wals.info) · [Grambank](https://grambank.clld.org) · [PHOIBLE](https://phoible.org) — 言語カタログ・類型論
  - [GiellaLT](https://giellalt.uit.no) / ALTLab — 形態論的トランスデューサー（FST）
  - [Masakhane](https://www.masakhane.io) — アフリカ言語MTコミュニティ
  - [OPUS](https://opus.nlpl.eu) — オープン対訳コーパス

> 賞金のスポンサーになる、計算リソースの寄付を企画する、またはパートナーシップについて相談する場合は、[GitHub](https://github.com/gamedaysuits)経由でプロジェクトにご連絡ください。コミュニティの鍵管理者はまだ任命されておらず、同意を得る前にパートナーとして指名されているネイションや組織はありません。

## 1. 理念

> **一言で言えば: 言語を攻略し、勝利し、ホストが宣言した条件に従う。**
> Champollionは意図的にMLベンチマーキング事業として運用されています — 競争こそが困難な言語ペアを解決する手段だからです。私たちはML研究者や有能な開発者を歓迎し、特定の困難な言語ペアに対する最高の手法を構築して賞金を獲得することを推奨します。その後、手法がどのように扱われるかは**ホスト**が公開した選択であり、私たちの選択でもデフォルトの決定でもありません。勝利した手法の引き渡しを望むコミュニティはその条件で宣言し、測定して削除することだけを望むコミュニティは代わりにその旨を宣言します（§1.3）。競争のエネルギーは本物であり、それは単にリーダーボードを登るためではなく、その言語の人々が定めた条件の下で、あらゆる言語を翻訳可能にするという使命に向けられています。

### 1.1 賞は突破口に報いるものであり、参加に報いるものではない

賞金は、手法が定義された能力閾値を明確に達成した場合にのみ支払われます。参加賞、準優勝賞、慰労金はありません。誰も基準を超えなければ、誰も支払いを受けません。これは意図的な設計です — スポンサーは実際に機能する結果に対してのみ支払うことを意味します。

### 1.2 コミュニティによる検証は交渉の余地がない

自動化されたメトリクスは代理指標です（SCORING_SPEC §1.1）。手法はchrF++とFST受理率で高いスコアを出しながら、話者が受け入れられない出力を生成することがあります。**すべての賞の請求にはコミュニティによる検証が必要です** — バイリンガルの話者が出力が使用可能であることを確認しなければなりません。これが人間による検証ゲートです（BENCHMARK_SPEC §7）。

### 1.3 勝利した手法の扱いは想定されるものではなく、宣言されるものである {#1-3-declared-terms}

1つだけ確定している点があります。それは、主権コンテストの*本質*そのものです。すなわち、エントリーはホスト自身のエアギャップノードに渡され、ホストのマシン上で非公開セットに対して実行されます。その*後*にどう扱われるかはホストが宣言する選択肢であり、コンテストごとに決定され、コンテストとともに公開されます — そしてそれは**3つの選択肢のうちの1つ**です。

| 条件 | 参加者にとっての意味 |
|---|---|
| `pass_to_holders` — *保持者への譲渡* | 手法は主権ベンチマーク保持者に譲渡されます。誰が勝利したかに関わらず、保持者がスコアリングを行い、それを保持します。 |
| `retain_ip` — *知的財産（IP）の保持* | あなた自身の手法の所有権はあなたが保持します。ホストはスコアリングを行い、監査のためにせいぜい封印されたコピーを保持するにとどまります。 |
| `release_open` — *オープンライセンスでの公開* | あなたは所有権を保持しますが、オープンライセンスの下で手法を公開する必要があります。その公開が賞金の獲得条件となります。 |

条件から派生する他のすべての事項 — 成果物が保持されるかどうか、権利が移転するかどうか、ホストがどのような目的で使用できるか、公開期限がいつになるか — は、ホストが選択したオプションから**導出**され（§2.1、条件7）、ホストがチェックを入れる個別の項目ではありません。ホストが条件を選び、詳細がそれに続きます。

明確に述べておくべき2つの結果:

- **賞金条件が宣言されていないコンテストには賞金がありません。** これがデフォルトです。劣ったコンテストというわけではなく、エントリーに関する権利などは一切移転しません。
- **暗黙的に決まるものは何もありません。** 宣言された条件はハッシュ化され、平易な言葉で参加者に提示され、そのハッシュによって承諾されます。承諾情報はエントリー内に含まれ、そのコンテンツハッシュによってカバーされます。ホストのノードは、それ以外のものを承諾したエントリーを拒否します。その後、コンテストに最初のエントリーがあった瞬間に条件は凍結されるため、読むことができなかった条件に縛られる人はいません。

ホストが`pass_to_holders`を選択した場合でも、開発者は帰属表示（クレジット表記）および公開の権利を保持し、この取り決めの目的は、賞金が言語コミュニティで実際に使用できるテクノロジーに資金を提供することにあります。これは、コミュニティホストがその条件を選択する十分な理由となります。これは選択肢であり、強制的なルールではありません。

### 1.4 ゲーミング対策

賞の閾値は**ゴールドスタンダード評価**（秘密のテストセット、ガバナンス組織がサンドボックスで実行）に対して定義されます。開発者はテストデータを見ることができません。これはアーキテクチャ上強制されるものであり、名誉に依存するポリシーではありません。BENCHMARK_SPEC §8.2を参照してください。

### 1.5 コーパスライセンス: 非商用コーパスは賞のレーンから除外される

手法の開発中に使用される一部のコーパスには、非商用ライセンスが適用されています — 例えば、EdTeKLA Cree Language Textbook コーパスには、**EdTeKLAの修正版CC BY-NC-SA**が適用されています（主権が及ぶ範囲限定、非商用。元の教科書はCC BY-NC-ND 4.0です）。これらのコーパスは**研究・開発レーン専用**です:

1. **賞のゴールドスタンダードコーパスにNCライセンスのコーパスコンテンツを含めてはなりません。** ゴールドスタンダードのテストセグメントはコミュニティが委託したオリジナル（コーパスパートナーシップ戦略を参照）です — 賞のために人間が作成し、評価および商用展開のための権利が最初から確保されています。
2. **賞を請求する手法にNCライセンスのコーパスコンテンツを含めてはなりません**（例: コーチングデータ、埋め込み例、ルックアップテーブルとして）。移転された手法は、コミュニティが選択するいかなる条件でもガバナンス組織が展開できるものでなければなりません — コミュニティがそう決定した場合は商用利用も含めて（BENCHMARK_SPEC §8.3）。その中にNCライセンスのコンテンツが含まれていると、その自由が損なわれます。
3. **開発者はNCライセンスのコーパスを開発と自己評価に自由に使用できます** — それが開発レーンの目的です。制限は提出されるものと展開されるものに適用され、開発者がどのように学ぶかには適用されません。

### 1.6 依存関係クラスが賞の適格性を決定する

すべての賞の評価はサンドボックスで行われ（§1.4）、賞を獲得した手法はガバナンス組織に移転されます（§1.3）。どちらの事実も同じ制約を課します: **手法が依存するすべてのものは、開発者がサンドボックスに入れ、コミュニティに提供する権利を持つものでなければなりません。** すべての提出物は依存関係クラスを宣言します — [Method Interface spec](/docs/network/specifications/methods#method-validity-and-dependency-classes)で定義されています — そして適格性はクラスに従います:

| 依存関係クラス | 賞の適格性 | 条件 |
|------------------|----------------|------------|
| **S** — 自己完結型 | ✅ あり | §2の閾値条件以外なし |
| **O** — オープン外部（例: 提出時にミラーされたAGPL FST） | ✅ あり | アーティファクトが固定され提出物にベンダリングされている; ライセンスがコミュニティへの移転を許可している; コピーレフト条項が保持されている（コミュニティはライセンスが全員に付与するのと同じ権利を受け取る） |
| **A1** — 代替可能なLLM推論 | ⚠️ 条件付き | モデルが宣言、固定され、代替可能（コミュニティがホストするオープンウェイトモデルに対して実行できなければならない）; 評価はサンドボックスLLMゲートウェイを通じてルーティングされる（🔲 計画中 — ゲートウェイが運用されるまでA1手法はゴールドスタンダードスコアを生成できない）; 移転はモデルではなく完全なレシピ（プロンプト、コーチング、コード）を提供する |
| **A2** — 代替不可能な外部データ/サービスAPI | ❌ 未対応 | 権利保有者がサンドボックスへの組み込みと移転の許可を付与するまで不適格。オープンリーダーボードでは「外部依存関係」フラグ付きで許可 |
| **X** — 権利のないバンドルコンテンツ | ❌ 永久に不可 | すべてのレーンで受理不可 |

手法のクラスは、宣言された依存関係の中で最も制限の厳しいクラスになります。いかなるクラスの未宣言の依存関係も失格事由となります（§5）。

#### 条件7の詳細: 条件は3つの選択肢のうちの1つ

すべての主権コンテストは、実行時に同じように機能します。参加者は自身の手法（重みまたはコード）をホストのエアギャップノードに渡し、ノードが非公開セット上でそれをスコアリングします。これこそが「ホストが測定した」ということが意味するすべてであり、調整することはできません。

その*後*に何が起こるかはホストの選択であり、コンテストごとに宣言され、3つのオプションのうちの1つとなります。ホストはエントリーが開始される前にそれを公開します。コンテストに最初のエントリーがあった瞬間に**凍結**されるため、あなたが読んだ条件が、あなたが従うべき条件となります。

| 条件 | 参加者にとっての意味 |
|---|---|
| `pass_to_holders` — *保持者への譲渡* | 手法は主権ベンチマーク保持者に譲渡されます。誰が勝利したかに関わらず、保持者がスコアリングを行い、それを保持します。 |
| `retain_ip` — *知的財産（IP）の保持* | あなた自身の手法の所有権はあなたが保持します。ホストはスコアリングを行い、監査のためにせいぜい封印されたコピーを保持するにとどまります。 |
| `release_open` — *オープンライセンスでの公開* | あなたは所有権を保持しますが、オープンライセンスの下で手法を公開する必要があります。その公開が賞金の獲得条件となります。 |

**各オプションの詳細な意味。** これら4つの次元 — および必須の公開に付随するライセンス — は、オプションから*導出*されます。ホストが手動で`rights`や`host_use`を記述することはなく、どのコンテストもこれらを勝手に組み合わせることはできません:

| フィールド | `pass_to_holders` | `retain_ip` | `release_open` |
|---|---|---|---|
| `retention` — スコアリング後も成果物は残るか？ | `retain` | `retain_sealed_audit` | `retain` |
| `rights` — 所有権は移転するか？ | `assignment_to_host` | `participant_retains_all` | `participant_retains_all` |
| `host_use` — ホストはそれを何に使用できるか？ | `any` | `evaluation_only` | `any`（あなたが公開したオープンライセンスの下で） |
| `release` — **あなた**がそれを公開する必要があるか、いつ公開するか？ | `not_required` | `not_required` | `required_before_prize` |
| `release_license` — どのライセンスの下で公開するか | — | — | `any_osi`、または指定されたSPDX識別子 |

2つのオプションでは、ホストが1つのフィールドを限定することができます。変更できるのはそれだけです:

- `retain_ip`では、ホストは`retention`を`delete_after_scoring`に設定できます — あなたの手法はスコアリングされた後に破棄されます。
- `release_open`では、ホストは公開のタイミングを`required_before_scores`（自身のスコアが公開される前に公開）または`required_after_prize`（支払い後に公開）に変更でき、OSI承認ライセンスを任意で認める代わりに特定のライセンスを指定できます。

3つのオプションのいずれにも、`community_terms_url` — ホスト独自の書面による利用規約への`https://`リンク — を付随させることができます。コンテスト自体では、選択されたオプションはその`disposition`として記録され、上記の内容はすべてその単一の値から読み取られます。

それ以外の設定はコンテスト作成時に拒否されます。あるオプションで提供されていないフィールドを指定することはできず、導出すべき箇所に手動でフィールドが記述された場合は、暗黙的に信用されるのではなく名前を挙げて拒否されます。

**賞金が支払われる前にチェックされる項目。** 必要な検証は条件から導き出されます。ホストが個別に設定することはありません:

- **引き渡し（Handover）** — 常に実施。ホストはスコアリングした正確な成果物（ノードによって記録された手法ダイジェスト）を保持します。これは測定されます。
- **公開（Release）** — `release_open`において、スコア公開前または賞金支払い前に公開期限が到来する場合。ホストは公開URLと公開された成果物のSHA-256を記録します。この記録が検証され、URL自体へのアクセス取得は行われないため、確定した結果が他者の稼働状況に依存することはありません。賞金支払い*後*に義務付けられる公開は支払い後に到来する義務であるため、支払い時のチェック項目には含まれません。
- **譲渡（Assignment）** — 所有権が移転する`pass_to_holders`において実施。譲渡はこのプラットフォームの外部で署名された証書です。ホストはその証書と日付を記録し、プラットフォームは記録が存在することを検証します。**プラットフォームが法的な効力を検証することはありません。**

**賞金条件が宣言されていないコンテストには賞金がありません。** デフォルトの条件は存在せず、誰かのために暗黙のうちに想定されることもありません。条件を宣言しているコンテストに参加することは、提出時にそのハッシュによって明示的にその条件を承諾することを意味します — その承諾はバンドルに同梱され、ホストのノードがチェックする検証項目の一部となります。

> **なぜ99%以上のFSTなのか？** 複統合的言語の機械翻訳における中心的な問題はハルシネーションです — LLMは目的の言語のように*見える*ものの、形態論的には無効な文字列を生成します。95%の有効な出力を生成する手法であっても、依然として5%の捏造された単語が含まれており、本番での利用には許容できないノイズです。99%以上の閾値は、稀なエッジケース（FSTが知らない固有名詞、正当な新語）を許容しつつ、ハルシネーションのほぼ完全な排除を求めます。手法が99%以上のFST受容率を達成できない場合、その問題は解決されていません。
>
> **なぜchrF++とFSTを組み合わせるのか、そしてなぜどちらか一方だけでは不十分なのか。** FST受容率は各単語が存在することを示すだけであり、あらゆる入力に対して1つの有効な文を繰り返すようなシステムでも完全に通過してしまいます。chrF++は各出力を参照訳と比較するため、そのようなケースを検知します。どちらの自動測定数値も単独では品質を証明できません。コミュニティ検証ゲート（条件4）こそが、話者が出力を使用可能と判断したことを確認するものです。

#### この閾値が実際に意味すること

これらの条件が総合的に確立すること:

- **実質的にすべての**出力単語が本物のクリー語の単語であること（FSTが99%以上を検証 — 捏造された語形がほぼゼロ）
- 非公開セットにおいて、出力が参照訳に近いこと（chrF++ ≥ 55）
- コミュニティ独自のプロトコルに基づき、バイリンガル話者が層化サンプルの少なくとも70%を「許容可能」以上と評価したこと — 品質を直接証明する唯一の条件
- 残存するエラーは本物の言語的エラー（誤った屈折、不正確なオビエーション（相手辞）、生物性の一致の誤りなど）であり、捏造された単語ではないこと

これは**言語を損なわない**システムです。完璧ではないかもしれませんが、生成するすべての単語は本物の単語です。それが多合成語言語の敬意ある機械翻訳の最低基準です。

## 3. 賞の請求プロセス

### 3.1 参加資格取得、そして提出

1. **公開環境で予選を通過する。** 開発者は、自身のシステムでコンテストの公開開発セットをスコアリングし、その受領書（`mt-eval contest qualify`）を保持します。この受領書は設計上自己申告によるものです — あくまで主張（クレーム）であり、ホストはステップ4でそれをチェックします。

2. **エントリーを引き渡す。** コンテストへのエントリーは、次の2つのレーンのいずれかで、ホストのノードが実行可能なものを渡すことによって行われます:
   - **モデル** — safetensorsの重み、宣言的トークナイザー、および設定ファイルで構成され、コードを一切含まないもの（`mt-eval contest submit-model`）。または
   - **手法** — Dockerfileとエントリーポイントで構成され、ネットワークなしでビルドおよび実行できるように依存関係が同梱（ベンダー化）されているもの（`mt-eval contest submit-method`）。

   公開テストセットの翻訳をアップロードすること、および開発者自身が公開したスコアをリンクすることは、**2026-09-06にコンテストのエントリー経路として廃止**され、該当するコマンドは削除されました。自己申告によるスコアは引き続きオープンリーダーボード（コーパスと言語ペアの方向によってインデックス付けされた公開掲示板）の対象となりますが、これはコンテストではなく、賞金レーンでもありません。

3. **エントリー自体に以下を宣言する:** トラック（`constrained` — ホストが許可したデータのみでトレーニングされたもの — または `unconstrained`）、パラメータ数、重みのライセンスおよびそれらが公開されているかどうか、制約トラックの主張に関連するトレーニングデータ、これがチームの主要エントリーか対照エントリーか、および — コンテストで要求されている場合は — システムの説明。開発者はまた、手法提出規約に対する`--agree`を渡し、コンテストで賞金条件が宣言されている場合は、それらに対する`--accept-terms <hash>`も渡します。

### 3.2 評価

1. ホストのノードはバンドルに対して**静的チェック**を実行し、ネットワークを必要とするものを拒否し、このコンテストが宣言しているもの以外の賞金条件を受け入れているエントリーを拒否します。
2. ノードは、同じレーン実行エンジンと同じスコアラーを使用して、公開開発セットの独自のコピー上で**予選の実行自体をやり直します**。開発者の受領書は主張に過ぎず、これが実際の測定となります。基準未達の場合はここで拒否されます — 管理者に承認を求める前、かつ非公開セットが開かれる前です — 何が主張され、何が測定され、基準は何であったかが示されます。
3. **管理者が非公開セットでの実行を承認します**（M-of-N、コンテストの承認モデルに準拠）。この付与は1回限り、有効期限付きであり、正確な（バンドルハッシュ、コーパス、コーパスバージョン、ノード）のフィンガープリントにバインドされます。
4. エントリーは、ホスト自身のマシン上のネットワークから隔離されたサンドボックス内で`gold_standard`非公開コーパスに対して実行され、自動メトリクス（CIおよびシグネチャ付きのchrF++、その他の標準メトリクス、およびFST受容率などの診断情報）が計算されます。宣言された非公開ホールドアウトおよびサードパーティのテストスイートは、**同一の**承認された実行内で実行されます。
5. **集計スコアのみが外部に出力されます** — これは慣習ではなく、データベースレイヤーで強制されます。コンテストが`hidden_until_close`を約束していた場合、終了時に公開されるまでカードは非公開（保留）とされます。
6. 自動化された閾値（条件2〜3）が満たされた場合、ホストはコミュニティレビューに進みます。満たされなかった場合、開発者はスコアを受け取りますが、コミュニティレビューはトリガーされません。

### 3.3 コミュニティレビュー

1. 出力の層別サンプル（30件以上のエントリ、難易度ティア2〜5をカバー）がバイリンガル話者に提示されます
2. 最低2名の独立したレビュアーが各エントリを評価します
3. 評価スケール: **reject** / **gist** / **acceptable** / **excellent**
4. 両方のレビュアーから70%以上のエントリが「acceptable」または「excellent」を受け取った場合、コミュニティ検証は合格です

### 3.4 支払い

順序は固定されています: **宣言されたゲートステップの検証 → コンテストの終了 → 賞金の支払い。** それらのステップが具体的に何であるかは、*この*コンテストが宣言した条件によって決まります（§2.1、条件7） — しかし、どれであっても終了前に検証され、まだ変動しているランキングから支払われることはありません。

主催者は、満たされていないゲートを越えて`close --force`を実行できます。その場合、終了処理は進み、凍結されたランキングには、そのエントリーの賞金獲得資格が計算どおりに正確に記録されます — 不適格であり、不合格となったステップ名が記載されます。強制終了はあくまでコンテストの終了であり、ゲートを通過したことには決してなりません。

1. 7つの条件がすべて満たされていること
2. **コンテストで宣言された賞金条件が要求するすべてのゲートステップが検証されていること** — スコアリングされた成果物の引き渡しは常に必須であり、それらの条件で求められている場合は、記録された公開および/または記録された譲渡も含まれます
3. コンテストが**終了**し、そのランキングが凍結されていること
4. ガバナンス組織が、凍結されたランキングに対して結果を確認すること
5. 確認から30日以内に賞金が支払われること
6. 宣言された条件における所有権に関する規定が、その条件の指定通りに発効すること — `rights`が`participant_retains_all`であるコンテストの場合、権利の移転は一切発生しません
7. 結果が「Community Validated（コミュニティ検証済み）」の検証ティアでリーダーボードに公開されること

### 3.5 複数回の提出

- 同じ開発者/チームが複数回提出できます
- 各提出は独立して評価されます
- 手法が改善されて再提出された場合、最新のランカードのみが有効です
- 賞はすべての閾値を超えた**最初の**手法に授与されます — 分割されません

### 3.6 チームによる提出

- チームおよびElderと若者のペアが適格です
- チーム内の賞の分配はチームの責任です
- すべてのチームメンバーが参加条件に署名しなければなりません
- リーダーボードの帰属にはすべてのチームメンバーが記載されます

## 4. 将来の賞プール {#4-future-prize-pools}

ファウンダーズ賞は種です。追加の賞プールはスポンサーによって資金提供されます。各新しい賞プールは§2の新しいサブセクションとして以下とともに文書化されます:

- 賞の金額と通貨
- 言語ペア
- スポンサーの帰属
- 閾値条件（ファウンダーズ賞と異なる場合がある）
- 有効期限（ある場合）
- 特別条件

### 4.1 スポンサー賞テンプレート

スポンサーは任意の金額で賞プールに資金を提供します。推奨ティア:

| ティア | 金額 | 推奨閾値 |
|------|--------|---------------------|
| **シード** | $5,000–$15,000 | コンテスト開始前に公開された、非公開セットでのchrF++基準 + コミュニティ検証 |
| **ブレークスルー** | $25,000–$50,000 | より高いchrF++基準 + コミュニティ検証 |
| **最優秀賞（Grand Prize）** | $100,000+ | ブレークスルーの条件 + 複数の言語レジスターの網羅 + デプロイメント統合 |

基準は常にchrF++です（再現性を担保するためシグネチャを伴います）。FST受容率などの診断用ゲートは、関門として追加できます。複合スコアや品質ティアを賞金の閾値にすることはできません。

スポンサーは以下の資金を提供することもできます:
- **改善報奨金（Improvement bounties）** — 現在の最高値からchrF++が5ポイント向上するごとの固定支払い
- **レジスター賞（Register prizes）** — 特定のレジスター（公式、儀礼、教育用）に対する個別の賞
- **コスト賞（Cost prizes）** — chrF++の基準をクリアした手法のうち、エントリあたりのコストが最も低いもの（コストはスコアと合算されることはなく、スコアの横に報告されます）

### 4.2 賞金の保持場所

賞金は**スポンサーが保持します**: スポンサー組織、またはスポンサーが指定するコミュニティトラストに置かれます — 測定を調整し資金に一切触れない**Champollionには置かれません**。信頼できる賞は開設前に以下を公開します: **誰が資金を保持するか**、どのような取り決めで（組織のアカウント、トラスト、またはスポンサーが選択するサードパーティエスクロー）、および授与閾値 — これにより、基準を超えることが公開スコアとコミュニティのスピーカー検証の判定から検証可能となり、支払いのデフォルトは公に可視化されます。現時点では賞金はどこにも保持されていません。賞が未請求のまま期限切れになった場合、資金は常にあった場所 — スポンサーのもと — に留まり、スポンサーの裁量でリダイレクトまたは引き出されます。スポンサーのデフォルトリスクとその軽減策を含むセルフサービスの仕組みは、[Run a Sovereign Contest](/docs/network/sovereignty/run-a-sovereign-contest)および[Terms Templates](/docs/network/sovereignty/terms-templates)に文書化されています。

## 5. 失格

提出物は以下の場合に失格となります:

1. **評価データでのトレーニング。** 手法が`gold_standard`または`held_out`コーパスのエントリにさらされていた場合。（サンドボックスでの実行により構造的に防止されていますが、汚染の証拠が見つかった場合、結果は無効になります。）
2. **再現不能。** ガバナンス組織が±2%以内でスコアを再現できない場合。
3. **未宣言または不適格な依存関係。** 手法が依存関係マニフェストで宣言されている範囲を超えて外部サービスへのランタイムアクセスを必要とする場合、またはその実質的な依存関係クラスがA2またはXである場合（§1.6）。評価ゲートウェイを経由してルーティングされる、宣言済みのクラスA1 LLM推論は許可されます。それ以外のランタイムネットワーク依存関係 — およびクラスを問わず未宣言の依存関係 — はすべて失格の対象となります。
4. **参加規約への未署名。** すべてのチームメンバーは、手法提出規約に同意する必要があり、コンテストで賞金条件が宣言されている場合（§1.3）は、ハッシュによってその条件にも同意する必要があります。
5. **不正行為（ゲーミング）の検出。** 出力が翻訳品質ではなくメトリクスに過剰適合されている場合（BENCHMARK_SPEC §9.3に基づくコミュニティレビューおよび/または不正防止チェックによって検出されます）。

## 7. コードと仕様の同期

### 7.1 正規ソース

本文書（`cli/website/docs/network/specifications/prize-spec.md`）は以下の正規ソースです:
- 賞プールの定義（§2）
- 閾値条件（§2.x）
- 請求プロセス（§3）
- 失格ルール（§5）

### 7.2 実装要件

賞金プールがアクティブ化された場合:
1. リーダーボードUIに、アクティブな賞金とその閾値条件が表示される必要があります
2. 自動化された閾値（条件2〜3）を満たすランカードには、コミュニティレビューのフラグが付けられる必要があります
3. 品質ティアは使用されません。すべての新しいランカードで`quality_tier`フィールドはnullになります（スコアリング標準/1）
4. 賞金**条件**レイヤーはすでに提供されており（`contest_prize_terms` — 宣言、ハッシュ、承諾、および支払いゲート）、スコアリング自体に変更はありません。新しい賞金プールによって追加されるのは、§2の閾値ポリシーおよび上記項目1〜2のリーダーボードへの表示です
