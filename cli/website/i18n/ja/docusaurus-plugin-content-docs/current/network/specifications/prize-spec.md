# 賞仕様

賞は、評価優先（eval-first）の取り決めにおけるインセンティブの側面を担うものです。コミュニティや
研究グループは、小規模で非公開の評価セット（すべてがチェックされた数百のペア）をキュレーションします
（[コーパスパートナーシップ](/docs/network/specifications/corpus-partnership)
がそのワークフローです）。スポンサーは、そのセットの目標スコアに対して賞を提示します。
その瞬間から、その言語は常設の課題となります。世界中のあらゆるメソッド
構築者がそれを目指すことができ、リーダーボードはすべての試みを公開で測定し、
基準は声の大きい者ではなく、コミュニティ自身の解答キーによって決定されます。
本ドキュメントでは、賞が開始された際に基準が明確であり、かつメソッドに依存しないように、
そのような賞がどのように機能するか（しきい値の条件、請求プロセス、依存関係のクラス、およびルール）を規定します。

賞は**スポンサーが資金を提供し、スポンサーが管理します**。資金は
スポンサー組織、またはスポンサーが指定するコミュニティトラストに保管されます。
**Champollionが賞金を保持、エスクロー、またはルーティングすることは決してありません。**
どのコミュニティや組織も、[主権コンテストの運営](/docs/network/sovereignty/run-a-sovereign-contest)
のセルフサーブ方式で、独自のコーパスと独自の資金を保持して賞を運営することができます。

> **ステータス: 提案段階（PROPOSED） — 現在公開されている賞はなく、ここで請求できるものはまだありません。**
> 賞の*開始*のゲートとなるのは測定側です。つまり、
> コミュニティが同意したゴールドスタンダードのコーパス、エアギャップされた評価
> サンドボックス（仕様は策定済み、未構築）、および話者レビューのゲートです。このサイトのどのスコアも
> 賞の基準をクリアしていません。詳細については、
> [誠実な制限事項](/docs/network/honest-limitations)を参照してください。指標の参照先:
> [スコアリング仕様](/docs/network/specifications/scoring)、プロトコル:
> [ベンチマーク仕様](/docs/network/specifications/benchmark)。

## 言語をネットワークに加えるためにご協力いただけますか？

賞を待つ必要はありません。今日できる最も効果的なことは以下のとおりです:

- **MT達成賞のスポンサーになる。** 具体的な目標に資金を提供します — たとえば、信頼性の高い英語 → Plains Cree の手法など。Champollionが測定を調整します。資金は**あなた**（あなたの組織、またはあなたが指定するコミュニティトラスト）のもとに置かれ、コミュニティの条件に基づいて授与されます（[Data Sovereignty](/docs/network/sovereignty/data-sovereignty)および[Economic Model](/docs/network/sovereignty/economic-model)を参照）。エンドツーエンドのセルフサービスパスは[Run a Sovereign Contest](/docs/network/sovereignty/run-a-sovereign-contest)に記載されています。新しい言語ペアの追加は[corpus partnership](/docs/network/specifications/corpus-partnership)から始まります。
- **コンピュートの寄付を調整する。** APIクレジット/トークンをプールして、公開キューがより多くのペアをマッピングし、翻訳が信頼できる箇所とそうでない箇所を明らかにできるようにします。
- **私たちが基盤とするオープンソースイニシアチブを*直接*支援する。** Champollionは他者のオープンな成果をつなぎ合わせる配管です。*彼ら*を支援することがこのマップを支援することになります（私たちは彼らの成果の功績を横取りするよりも、上流を案内したいと考えています）:
  - [Tatoeba](https://tatoeba.org) — コミュニティが提供する対訳文
  - [Endangered Languages Catalog (ELCat)](https://www.endangeredlanguages.com) — 危機言語データ
  - [Glottolog](https://glottolog.org) · [WALS](https://wals.info) · [Grambank](https://grambank.clld.org) · [PHOIBLE](https://phoible.org) — 言語カタログ・類型論
  - [GiellaLT](https://giellalt.uit.no) / ALTLab — 形態論的トランスデューサー（FST）
  - [Masakhane](https://www.masakhane.io) — アフリカ言語MTコミュニティ
  - [OPUS](https://opus.nlpl.eu) — オープン対訳コーパス

> 賞のスポンサー、コンピュート寄付の調整、またはパートナーシップについては、[GitHub](https://github.com/gamedaysuits)からプロジェクトにご連絡ください。コミュニティキーの管理者は確認中です。同意を得る前に、いかなる国家や組織もパートナーとして記載されません。

## 1. 理念

> **一言で言えば: 言語を解読し、賞を獲得し、それを返す。** Champollionは意図的にMLベンチマーキングの取り組みです — 競争こそが困難なペアを解決する方法です。私たちはML研究者およびあらゆる有能なビルダーを招待し、特定の困難な言語ペアに対して最良の手法を構築し、賞を獲得し、**そして**その手法をその言語を所有する主権組織に引き渡すことを求めます（§1.3）。競争のエネルギーは本物であり、それはミッション — すべての言語を、その人々が定める条件のもとで翻訳すること — に向けられています。リーダーボードを登るためだけのものではありません。

### 1.1 賞は突破口に報いるものであり、参加に報いるものではない

賞金は、手法が定義された能力閾値を明確に達成した場合にのみ支払われます。参加賞、準優勝賞、慰労金はありません。誰も基準を超えなければ、誰も支払いを受けません。これは意図的な設計です — スポンサーは実際に機能する結果に対してのみ支払うことを意味します。

### 1.2 コミュニティによる検証は交渉の余地がない

自動化されたメトリクスは代理指標です（SCORING_SPEC §1.1）。手法はchrF++とFST受理率で高いスコアを出しながら、話者が受け入れられない出力を生成することがあります。**すべての賞の請求にはコミュニティによる検証が必要です** — バイリンガルの話者が出力が使用可能であることを確認しなければなりません。これが人間による検証ゲートです（BENCHMARK_SPEC §7）。

### 1.3 所有権の移転は取引の一部である

賞を請求した手法は、所有権移転条項の対象となります（BENCHMARK_SPEC §8.3）。開発者は帰属権と出版権を保持します。ガバナンス組織は、その言語のために手法を使用、修正、配布、および収益化する権利を得ます。これはペナルティではありません — これが目的です。賞金は言語コミュニティに属する技術の創出に資金を提供します。

### 1.4 ゲーミング対策

賞の閾値は**ゴールドスタンダード評価**（秘密のテストセット、ガバナンス組織がサンドボックスで実行）に対して定義されます。開発者はテストデータを見ることができません。これはアーキテクチャ上強制されるものであり、名誉に依存するポリシーではありません。BENCHMARK_SPEC §8.2を参照してください。

### 1.5 コーパスライセンス: 非商用コーパスは賞のレーンから除外される

メソッド開発中に使用される一部のコーパスには、非営利ライセンスが適用されています。たとえば、EdTeKLA Cree Language Textbookコーパスには、**EdTeKLAの改変版CC BY-NC-SA**（主権スコープ、非営利。元の教科書はCC BY-NC-ND 4.0）が適用されています。これらのコーパスは**研究/開発レーン専用**です。

1. **賞のゴールドスタンダードコーパスにNCライセンスのコーパスコンテンツを含めてはなりません。** ゴールドスタンダードのテストセグメントはコミュニティが委託したオリジナル（コーパスパートナーシップ戦略を参照）です — 賞のために人間が作成し、評価および商用展開のための権利が最初から確保されています。
2. **賞を請求する手法にNCライセンスのコーパスコンテンツを含めてはなりません**（例: コーチングデータ、埋め込み例、ルックアップテーブルとして）。移転された手法は、コミュニティが選択するいかなる条件でもガバナンス組織が展開できるものでなければなりません — コミュニティがそう決定した場合は商用利用も含めて（BENCHMARK_SPEC §8.3）。その中にNCライセンスのコンテンツが含まれていると、その自由が損なわれます。
3. **開発者はNCライセンスのコーパスを開発と自己評価に自由に使用できます** — それが開発レーンの目的です。制限は提出されるものと展開されるものに適用され、開発者がどのように学ぶかには適用されません。

### 1.6 依存関係クラスが賞の適格性を決定する

すべての賞の評価はサンドボックスで行われ（§1.4）、賞を獲得した手法はガバナンス組織に移転されます（§1.3）。どちらの事実も同じ制約を課します: **手法が依存するすべてのものは、開発者がサンドボックスに入れ、コミュニティに提供する権利を持つものでなければなりません。** すべての提出物は依存関係クラスを宣言します — [Method Interface spec](/docs/network/specifications/methods#method-validity-and-dependency-classes)で定義されています — そして適格性はクラスに従います:

| 依存関係クラス | 賞の適格性 | 条件 |
|------------------|----------------|------------|
| **S** — 自己完結型 | ✅ あり | §2の閾値条件以外なし |
| **O** — オープン外部（例: 提出時にミラーされたAGPL FST） | ✅ あり | アーティファクトが固定され提出物にベンダリングされている; ライセンスがコミュニティへの移転を許可している; コピーレフト条項が保持されている（コミュニティはライセンスが全員に付与するのと同じ権利を受け取る） |
| **A1** — 代替可能なLLM推論 | ⚠️ 条件付き | モデルが宣言、固定され、代替可能（コミュニティがホストするオープンウェイトモデルに対して実行できなければならない）; 評価はサンドボックスLLMゲートウェイを通じてルーティングされる（🔲 計画中 — ゲートウェイが運用されるまでA1手法はゴールドスタンダードスコアを生成できない）; 移転はモデルではなく完全なレシピ（プロンプト、コーチング、コード）を提供する |
| **A2** — 代替不可能な外部データ/サービスAPI | ❌ 未対応 | 権利保有者がサンドボックスへの組み込みと移転の許可を付与するまで不適格。オープンリーダーボードでは「外部依存関係」フラグ付きで許可 |
| **X** — 権利のないバンドルコンテンツ | ❌ 永久に不可 | すべてのレーンで受理不可 |

手法のクラスは、宣言された依存関係の中で最も制限の厳しいクラスになります。いかなるクラスの未宣言の依存関係も失格事由となります（§5）。

### 2.1 ファウンダーズ賞 — EN→Plains Cree (nêhiyawêwin)

| フィールド | 値 |
|-------|-------|
| **賞プール** | **10,000 CADドル**（提案） |
| **言語ペア** | 英語 → Plains Cree (EN→CRK) |
| **想定スポンサー** | Champollionプロジェクト創設者 — 意図されたコミットメントであり、**現時点では資金はどこにも保持されていません。** コミットされた場合、資金はスポンサーまたは指定されたコミュニティトラストに置かれます — Champollionには置かれません。 |
| **ステータス** | **提案中 — 開設されていません。** 提出を受け付けていません。 |
| **開設条件** | ゴールドスタンダードコーパス、評価サンドボックス、およびスピーカーレビューゲートがすべて存在し（現時点ではいずれも存在しない）、スポンサーの資金が§4.2に従って検証可能な形で保持されている場合のみ。 |
| **有効期限** | 開設後は有効期限なし。 |

#### 閾値条件

手法がファウンダーズ賞を請求するには、以下の**すべて**の条件を同時に満たす必要があります:

| # | 条件 | メトリクス | 閾値 | 根拠 |
|---|-----------|--------|-----------|-----------|
| 1 | **複合スコア** | `composite` (SCORING_SPEC §4) | **≥ 0.80** | Deployable（0.70）とFluent（0.85）の間。すべてのメトリクス次元で高品質が必要 — 形態論的妥当性だけでなく。 |
| 2 | **FST受理率** | `fst_acceptance_rate` (SCORING_SPEC §2.2) | **≥ 0.99（99%以上）** | 実質的にすべての出力単語が、GiellaLT FSTによって認識される形態論的に有効な形式でなければなりません。1%の許容範囲は、FSTが正当にカバーしない可能性のあるエッジケース（固有名詞、新語、借用語）を考慮しています。これは多合成語MT の決定的な品質ゲートです — FSTが1%を超える単語を拒否する場合、その手法は言語に存在しない形式を生成しています。この賞の目的は、言語を損なわないシステムを生み出すことです。 |
| 3 | **chrF++** | `chrf_plus_plus` (SCORING_SPEC §2.1) | **≥ 55.0** | 文字n-gramの重複が0〜100スケールで55を超える必要があります。形態論的妥当性だけでなく、参照翻訳との表面的な類似性を確保します。 |
| 4 | **コミュニティ検証** | 人間によるレビュー（BENCHMARK_SPEC §7） | **「acceptable」または「excellent」が70%以上** | 出力の層別サンプル（難易度ティア2〜5にわたる30件以上のエントリ）が、2名以上のバイリンガルCRK話者によってレビューされます。レビューされたエントリの少なくとも70%が「acceptable」または「excellent」の評価を受ける必要があります。 |
| 5 | **ゴールドスタンダード評価** | サンドボックス実行（BENCHMARK_SPEC §8.2） | **必須** | すべての自動化メトリクスは、ガバナンス組織がサンドボックス環境で実行した`gold_standard`コーパスセグメントに対して計算される必要があります。開発セットのスコアは無効です。 |
| 6 | **再現性** | フィンガープリント一致（BENCHMARK_SPEC §3.8） | **±2%** | ガバナンス組織が手法を再実行し、提出されたランカードの±2%以内のスコアを達成できなければなりません。 |

> **なぜFST 99%以上なのか？** 多合成語言語における機械翻訳の中心的な問題はハルシネーションです — LLMはターゲット言語のように*見える*が形態論的に無効な文字列を生成します。95%の有効な出力を生成する手法でも、5%は作り上げられた単語です — これはいかなる本番利用においても許容できないノイズです。99%以上の閾値は、FSTが知らない固有名詞や正当な新語などのまれなエッジケースを許容しながら、ほぼゼロのハルシネーションを要求します。手法が99%以上のFST受理率を達成できない場合、問題を解決していません。
>
> **なぜ複合スコア0.80なのか？** これはDeployable（0.70）とFluent（0.85）の間に位置します。FST 99%以上で複合スコア0.80の手法は、実質的にすべての単語が本物のCree語であり、かつ表面、構造、意味の各次元で全体的な翻訳品質が高い出力を生成します。コミュニティ検証ゲート（条件#4）により、これが単なるメトリクスのゲーミングでないことが保証されます — 話者が出力が本当に使用可能であることを確認しなければなりません。

#### この閾値が実際に意味すること

複合スコア ≥ 0.80、FST ≥ 0.99、chrF++ ≥ 55 の場合、バイリンガル話者は通常以下を目にします:

- **実質的にすべての**出力単語が本物のCree語（FSTが99%以上を検証 — ハルシネーションされた形式はほぼゼロ）
- 主要な文法カテゴリ（人称、数、時制）がほとんどのエントリで正確
- 語順が概ね自然
- 意味が確実に保持されている
- 残りのエラーは実際の言語エラー（誤った活用、不正確なobviation、生物性の不一致）であり、作り上げられた単語ではない
- 流暢な話者は出力を高品質な下書きとして使用し、ゼロから翻訳するよりも大幅に速く修正できる

これは**言語を損なわない**システムです。完璧ではないかもしれませんが、生成するすべての単語は本物の単語です。それが多合成語言語の敬意ある機械翻訳の最低基準です。

## 3. 賞の請求プロセス

### 3.1 提出

1. 開発者はガバナンス組織に完全で実行可能な手法を提出します:
   - すべてのソースコード
   - すべての依存関係（コーチングデータ、辞書、FST設定、プロンプト）
   - インストールおよび実行手順
   - 手法のアプローチを説明するREADME
   - おおよそのスコアを示す開発セットのランカード（事前スクリーニング用）

2. 開発者は参加条件に署名します。以下を含みます:
   - 所有権移転条項（BENCHMARK_SPEC §8.3）
   - 評価データでのトレーニングなし宣言
   - 再現性のコミットメント

### 3.2 評価

1. ガバナンス組織は`gold_standard`コーパスに対してサンドボックスハーネスで手法をインストールして実行します
2. 自動化メトリクスが計算されます（複合スコア、FST、chrF++など）
3. 自動化閾値が満たされた場合（条件1〜3）、ガバナンス組織はコミュニティレビューに進みます
4. 自動化閾値が満たされない場合、開発者はスコアとフィードバックを受け取ります。コミュニティレビューは開始されません。

### 3.3 コミュニティレビュー

1. 出力の層別サンプル（30件以上のエントリ、難易度ティア2〜5をカバー）がバイリンガル話者に提示されます
2. 最低2名の独立したレビュアーが各エントリを評価します
3. 評価スケール: **reject** / **gist** / **acceptable** / **excellent**
4. 両方のレビュアーから70%以上のエントリが「acceptable」または「excellent」を受け取った場合、コミュニティ検証は合格です

### 3.4 支払い

1. 6つの条件がすべて満たされる
2. ガバナンス組織が結果を確認する
3. 確認から30日以内に賞が支払われる
4. 手法の所有権がBENCHMARK_SPEC §8.3に従って移転される
5. 結果が「Community Validated」検証ティアとともにリーダーボードに公開される

### 3.5 複数回の提出

- 同じ開発者/チームが複数回提出できます
- 各提出は独立して評価されます
- 手法が改善されて再提出された場合、最新のランカードのみが有効です
- 賞はすべての閾値を超えた**最初の**手法に授与されます — 分割されません

### 3.6 チームによる提出

- チームおよびElderと若者のペアが適格です
- チーム内の賞の分配はチームの責任です
- すべてのチームメンバーが参加条件に署名しなければなりません
- リーダーボードの帰属にはすべてのチームメンバーが記載されます

## 4. 将来の賞プール {#4-future-prize-pools}

ファウンダーズ賞は種です。追加の賞プールはスポンサーによって資金提供されます。各新しい賞プールは§2の新しいサブセクションとして以下とともに文書化されます:

- 賞の金額と通貨
- 言語ペア
- スポンサーの帰属
- 閾値条件（ファウンダーズ賞と異なる場合がある）
- 有効期限（ある場合）
- 特別条件

### 4.1 スポンサー賞テンプレート

スポンサーは任意の金額で賞プールに資金を提供します。推奨ティア:

| ティア | 金額 | 推奨閾値 |
|------|--------|---------------------|
| **Seed** | 5,000〜15,000ドル | Deployable（複合スコア ≥ 0.70）+ コミュニティ検証 |
| **Breakthrough** | 25,000〜50,000ドル | Fluent（複合スコア ≥ 0.85）+ コミュニティ検証 |
| **Grand Prize** | 100,000ドル以上 | Fluent + マルチレジスターカバレッジ + デプロイメント統合 |

スポンサーは以下にも資金を提供できます:
- **改善バウンティ** — 現在の最高chrF++から5ポイント改善するごとの固定支払い
- **レジスター賞** — 特定のレジスター（フォーマル、儀式的、教育的）に対する個別の賞
- **スピード賞** — コスト調整済みの最高スコア（SCORING_SPEC §6.3）

### 4.2 賞金の保持場所

賞金は**スポンサーが保持します**: スポンサー組織、またはスポンサーが指定するコミュニティトラストに置かれます — 測定を調整し資金に一切触れない**Champollionには置かれません**。信頼できる賞は開設前に以下を公開します: **誰が資金を保持するか**、どのような取り決めで（組織のアカウント、トラスト、またはスポンサーが選択するサードパーティエスクロー）、および授与閾値 — これにより、基準を超えることが公開スコアとコミュニティのスピーカー検証の判定から検証可能となり、支払いのデフォルトは公に可視化されます。現時点では賞金はどこにも保持されていません。賞が未請求のまま期限切れになった場合、資金は常にあった場所 — スポンサーのもと — に留まり、スポンサーの裁量でリダイレクトまたは引き出されます。スポンサーのデフォルトリスクとその軽減策を含むセルフサービスの仕組みは、[Run a Sovereign Contest](/docs/network/sovereignty/run-a-sovereign-contest)および[Terms Templates](/docs/network/sovereignty/terms-templates)に文書化されています。

## 5. 失格

提出物は以下の場合に失格となります:

1. **評価データでのトレーニング。** 手法が`gold_standard`または`held_out`コーパスエントリにさらされていた場合。（サンドボックス実行によりアーキテクチャ上防止されていますが、汚染の証拠が見つかった場合、結果は無効となります。）
2. **再現不可能。** ガバナンス組織がスコアを±2%以内で再現できない場合。
3. **未宣言または不適格な依存関係。** 手法が依存関係マニフェストで宣言した範囲を超えた外部サービスへのランタイムアクセスを必要とする場合、または実効的な依存関係クラスがA2またはX（§1.6）の場合。評価ゲートウェイを通じてルーティングされた宣言済みクラスA1 LLM推論は許可されます。その他のランタイムネットワーク依存関係、およびいかなるクラスの未宣言依存関係も失格事由となります。
4. **参加条件への未署名。** すべてのチームメンバーが所有権移転に同意しなければなりません。
5. **ゲーミングの検出。** 出力が翻訳品質ではなくメトリクスに最適化されている場合（コミュニティレビューおよび/またはBENCHMARK_SPEC §9.3のアンチゲーミングチェックによって検出）。

## 7. コードと仕様の同期

### 7.1 正規ソース

本文書（`cli/website/docs/network/specifications/prize-spec.md`）は以下の正規ソースです:
- 賞プールの定義（§2）
- 閾値条件（§2.x）
- 請求プロセス（§3）
- 失格ルール（§5）

### 7.2 実装要件

賞プールが有効化された場合:
1. リーダーボードUIはアクティブな賞とその閾値条件を表示しなければなりません
2. 自動化閾値を満たすランカード（条件1〜3）はコミュニティレビューのためにフラグが立てられなければなりません
3. ランカードスキーマの`quality_tier`フィールドはすでにティア（「deployable」、「fluent」）を取得しています
4. ハーネスへの新しいコード変更は不要です — 賞の仕様は既存のスコアリングの上にあるポリシーレイヤーです

---

*賞の構造は所有権移転条件と互換性がなければなりません。受賞者は賞を請求できますが、手法がDeployableティアに達した場合、その手法はガバナンス組織の財産となります。これは意図的な設計です — 賞金は言語コミュニティに属する技術の創出に資金を提供します。*
