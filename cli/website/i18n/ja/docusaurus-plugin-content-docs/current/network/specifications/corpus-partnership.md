# コーパスパートナーシップ戦略：大学言語学部との連携による評価コーパスの構築

リソースの少ない言語の*トレーニング*コーパスを構築するには、何十万もの文のペアが必要になります。これはすべてをチェックするにはあまりにも膨大な量であるため、それらでトレーニングされたモデルが失敗するまで、誰にも気づかれない形で品質にばらつきが生じます。一方、*評価用*コーパスに必要なのは数百のペアであり、そのすべてがその言語を熟知している人によってレビューされます。そして、それが陳腐化することはありません。登場する新しいモデルや手法はすべて、このコーパスを基準に測定されるからです。本書は、この2つ目の、劇的に低コストなもの（学科の専門知識がすべての文に行き届く唯一の成果物）を構築するためのワークフローと、その後の展開について説明するものです。評価基準が確立されることで、[提示された懸賞金](/docs/network/specifications/prizes)は、あなたの言語を世界中のあらゆる手法開発者が目指すターゲットへと変え、公開リーダーボードがすべての試行を測定します。

> **目的.** 言語学科とのパートナーシップを通じて機械翻訳の評価用コーパスを確立するための完全なワークフロー。学科が提供するもの、コーパスの要件、暗号学的に封印される仕組み、サンドボックス評価の機能、そして学科が得られる見返りについて説明します。これは、学術機関のパートナー候補との会議に持参するドキュメントです。
>
> **対象読者.** 活発な言語記録またはNLPプログラムを持つ大学の学科長、主任研究員（PI）、リサーチコーディネーター、および先住民言語プログラムのディレクター。
>
> **関連ドキュメント:**
> - [コーパス設計フレームワーク](/docs/network/specifications/corpus-design) — 妥当で信頼性の高い評価用コーパスの背後にある方法論
> - [懸賞金仕様](/docs/network/specifications/prizes) — インセンティブ部分：封印されたデータセットに対する懸賞金の提示
> - [コーパスの登録](/docs/network/sovereignty/registering-corpora) — 手元からデータを手放すことなくコーパスをネットワークに参加させる方法
> - [話者検証プロトコル](/docs/network/specifications/speaker-validation) — バイリンガル話者に既存の翻訳を*採点（マーク）*してもらうための依頼（品質評価、リンター検証、FSTレビュー）
> - [ベンチマーク仕様](/docs/network/specifications/benchmark) — コーパス、ランカード、評価プロトコルの完全な技術仕様
> - [データ主権](/docs/network/sovereignty/data-sovereignty) — 先住民族のデータ主権の原則、CARE、そして所有権の移転が重要である理由

## 1. このパートナーシップが生み出すもの

**シールされた評価コーパス**：機械翻訳品質を測定するためのグラウンドトゥルースとなる、厳選された並列テキストペア（ソース言語 → ターゲット言語）のセットです。手法はサンドボックス内でこのコーパスに対してテストされ、開発者がテストデータを見ることはありません。

このパートナーシップは3つの成果物を生み出します：

| 成果物 | 内容 | 管理者 |
|----------|-----------|-----------------|
| **開発コーパス** | 手法開発用の100〜200件以上の公開並列テキストペア | 公開（CC BY-NC-SA 4.0 または同等のライセンス） |
| **ゴールドスタンダードテストセット** | 公式評価用の50〜150件の非公開並列テキストペア | コミュニティガバナンス組織（暗号化シール済み） |
| **診断テストスイート** | 特定の言語現象をテストする10〜50件の対照ペア | 公開 |

これらを合わせると160〜400のペアになります。これは、トレーニングコーパスが要求する何十万ものペアとは対照的に、1つの研究グループが実際にプロフェッショナルな基準でキュレーションできる規模のコーパスです。開発用コーパスにより、誰でも翻訳手法を構築できるようになります。ゴールドスタンダード・セットは、それらの手法が公正にテストされることを保証します。診断スイートは、特定の失敗パターン（例：「このシステムはオビビエーションを処理できるか？」など）を捕捉します。

## 2. 学部に行ってもらうこと

### フェーズ1：コーパス設計（2〜4週間、研究者の作業時間）

**リード：** ターゲット言語の専門知識を持つ PI またはポスドク。

1. **ソース素材のドメインを選択する。** 言語コミュニティが実際に翻訳を必要としている4〜6つの実世界のドメインを選択します。私たちのタクソノミーは16のドメインをサポートしています（ベンチマーク仕様 §2.7 参照）：

   | 優先度 | ドメイン | 理由 |
   |----------|--------|-----|
   | 🔴 高 | `edu` — 教育 | 教科書、カリキュラム — コミュニティの直接的なニーズ |
   | 🔴 高 | `gov` — 行政 | バンド評議会の文書、政策 — 日常的な実用的ニーズ |
   | 🔴 高 | `medical` — 医療 | クリニックの受付フォーム、健康情報 — 安全上重要 |
   | 🟡 中 | `conv` — 会話 | 日常会話 — 基本的な流暢さの基準を確立 |
   | 🟡 中 | `legal` — 法律 | 権利文書、条約 — コミュニティにとって重要な意義 |
   | 🟢 低 | `literary` — 文学・文化 | 物語、口承の歴史 — 文化の保存 |

2. **コーパス設計文書を作成する。** 以下を明記します：
   - セグメントごとの目標サイズ（development、gold_standard、diagnostic）
   - 難易度ティアの分布（以下の §3.3 参照）
   - レジスターとドメインのカバレッジ
   - ソース文の選択基準（合成テキスト不可、聖書のみ不可）
   - 話者の採用計画

3. **設計をレビューのために提出する。** コーパススキーマ（ベンチマーク仕様 §2）に対して検証し、1週間以内にフィードバックを返します。

### フェーズ2：ソース文の作成（4〜8週間、話者の作業時間）

**リード：** バイリンガル話者と協力する研究コーディネーター。

1. **計画されたドメインと難易度ティアにわたってソース文を生成または選択する。** ソースとして使用できるもの：
   - 既存の公開バイリンガル資料（教科書、政府文書）
   - 特定の言語現象をカバーするために新たに引き出した文
   - 実際の文書から適用したもの（バンド評議会の議題、クリニックのフォーム、教育資料）

2. **各ソース文には以下が必要です：**
   - ドメインタグ（16コードのタクソノミーから）
   - レジスタータグ（会話、フォーマル、技術的、儀礼的、教育的）
   - コンテキストタグ（挨拶、宣言、質問、指示、物語、ラベル、エラー）
   - 推定難易度ティア（1〜5、§3.3 参照）
   - 出典タグ（教科書、引き出し、コーパス、gold_standard）

3. **各ソース文をターゲット言語に翻訳する。** バイリンガル話者が行います。エントリごとに複数の参照翻訳があると有益ですが、必須ではありません。

4. **オプションとして、各参照翻訳に形態素解析を追加する：**
   - インターリニアグロス（形態素ごとの分解）
   - FST タグ文字列（言語の FST が存在する場合）
   - 方言変異、曖昧性、または文化的文脈に関する翻訳者のメモ

### フェーズ3：品質保証（2〜4週間）

**リード：** ターゲット言語の専門知識を持つ言語学者。

1. **相互レビュー。** 各翻訳は、元の翻訳を作成していない少なくとも1人の追加のバイリンガル話者によってレビューされる必要があります。レビュアーは以下を確認します：
   - 翻訳は正確か？
   - 自然に聞こえるか？
   - 難易度評価は正しいか？
   - 注記すべき許容可能な変異形はあるか？

2. **スキーマバリデーターを実行する。** コーパスをエントリスキーマ（ベンチマーク仕様 §2.2）に対して検証するスクリプトを提供します。以下を確認します：
   - 必須フィールドの存在
   - ドメインコードの有効性
   - 難易度ティアが整数 1〜5 であること
   - 重複 ID がないこと
   - 文字エンコーディング（UTF-8 NFC 正規化）

3. **言語の FST が存在する場合、** 参照翻訳をそれに通します。参照内のすべての単語は FST 有効でなければなりません。そうでない単語（借用語、新語、固有名詞）は許可リストに記録する必要があります。

### フェーズ4：セグメント分割とシーリング（1週間、エンジニアリング作業）

**リード：** Champollion チーム（学部のレビューを伴う）。

1. **層化分割。** 決定論的ランダムサンプリング（シードを記録し、再現可能）を使用してコーパスをセグメントに分割します：

   | セグメント | 目標サイズ | アクセス |
   |---------|------------|--------|
   | `development` | エントリの60%（最低100件） | 公開 |
   | `gold_standard` | エントリの30%（最低50件） | 非公開、シール済み |
   | `held_out` | エントリの10%（最低10件） | 非公開、シール済み、有効化されるまで未使用 |

   分割は難易度ティアの分布を維持します（層化サンプリング）。これにより、各セグメントがティア全体にわたって比例した代表性を持ちます。

2. **gold_standard および held_out セグメントの暗号化シーリング：**

   ```
   1. SHA-256 hash of each entry (source + reference + metadata)
   2. SHA-256 hash of the complete segment file
   3. Segment file encrypted with AES-256-GCM
   4. Encryption key split using Shamir Secret Sharing (2-of-3 threshold)
   5. Key shares distributed to:
        - Share 1: Community governance organization
        - Share 2: Academic department partner
        - Share 3: Champollion project (escrow)
   6. Hash manifest published to a public commit (proves the corpus existed
      at a specific time without revealing its contents)
   ```

3. **development セグメント**は公開リポジトリにコミットされ、完全なライセンスとともに公開されます。

4. **diagnostic セグメント**も公開されます — 特定の言語現象をテストします（§3.4 参照）。

### フェーズ5：統合とローンチ（1〜2週間、エンジニアリング作業）

1. **ハーネス設定。** 評価ハーネスに言語を追加します：
   - 言語カードの作成または確認
   - データセットレジストリへのコーパス登録
   - LYSS メトリクスの設定（FST が利用可能な場合は LYSS-fst、リンタールールが存在する場合は LYSS-eq）
   - デフォルトスコアリングプロファイルの選択（FST が利用可能な場合はプロファイル A、そうでない場合はプロファイル B）

2. **ベースラインベンチマーク。** 12モデルのスイープを development セグメントに対して実行し、リーダーボードに初期スコアを登録します。

3. **公開アナウンス。** 言語がライブの development セグメントベンチマークとともに Network リーダーボードに表示されます。学部はコーパスパートナーとしてクレジットされます。

## 3. コーパスの形式要件

### 3.1 フォーマット

すべてのコーパスファイルは、ベンチマーク仕様 §2.1〜§2.2 のスキーマに従った JSON ドキュメントです：

```json
{
  "dataset": {
    "id": "crk-ualberta-v1",
    "version": "1.0",
    "language_pair": "EN→CRK",
    "source_language": "en",
    "target_language": "crk",
    "created": "2026-09-15",
    "license": "CC-BY-NC-SA-4.0",
    "provenance": ["textbook", "elicited", "gold_standard"]
  },
  "entries": [
    {
      "id": 1,
      "source": "I see the dog",
      "reference": "niwâpamâw atim",
      "segment": "development",
      "difficulty": 2,
      "provenance": "textbook",
      "register": "conversational",
      "context": "declaration",
      "domain": "edu",
      "morphological_analysis": "ni-wâpam-âw atim | 1sg-see.TA-3sg.DIR dog.AN",
      "notes": "Animate noun (atim); direct form because speaker is proximate"
    }
  ]
}
```

### 3.2 最小サイズ要件

| セグメント | 最小エントリ数 | 推奨 |
|---------|----------------|-------------|
| `development` | 100 | 200〜300 |
| `gold_standard` | 50 | 100〜150 |
| `diagnostic` | 10 | 30〜50 |
| `held_out` | 10 | 20〜30 |
| **合計** | **170** | **350〜530** |

### 3.3 難易度の分布

コーパスには5つの難易度ティア全体にわたるエントリが含まれている必要があり、ティア2〜4に重点を置きます：

| ティア | 説明 | 目標分布 |
|------|-------------|-------------------|
| 1 — 基本語彙 | 単語、一般的な挨拶、数字 | 10〜15% |
| 2 — 単純な文 | SVO、現在時制 | 25〜30% |
| 3 — 中程度の複雑さ | 過去・未来時制、所有格、生物性 | 30〜35% |
| 4 — 複雑な形態論 | Obviation、受動態、接続法語順、関係節 | 15〜20% |
| 5 — 上級 | 複文、フォーマルレジスター、儀礼的、慣用的 | 5〜10% |

### 3.4 診断テストスイート

診断セグメントは、**対照ペア**を使用して特定の言語現象をテストします：1つの正しい翻訳と、最小限の差異を持つ1つの誤った翻訳です。システムのメトリクスが正しいものをより高くスコアリングすれば、テストは合格です。

多合成語言語の場合、診断スイートは以下を対象とする必要があります：

| 現象 | 例（Cree） | テスト内容 |
|-----------|----------------|--------------|
| **生物性一致** | atim（AN）vs. maskisin（IN）— 異なる動詞形 | システムはどの名詞が生物的かを知っているか？ |
| **Obviation** | 近称 vs. 遠称の三人称 | 三人称の階層を追跡しているか？ |
| **逆形マーキング** | 直接形 vs. 逆形の動詞形 | 患者が行為者を上回る場合を処理できるか？ |
| **接続法・独立法** | 主節 vs. 従属節の動詞語順 | 正しい動詞パラダイムを使用しているか？ |
| **包括・排他** | 「私たち（あなたを含む）」vs.「私たち（あなたを除く）」 | 一人称複数形を区別しているか？ |

他の語族の場合、有能な翻訳と無能な翻訳を区別する最も診断的な3〜5つの現象を特定してください。ここでは学部の言語学的専門知識が不可欠です — これらは専門家だけが書き方を知っているテストです。

### 3.5 望ましくないもの

| アンチパターン | 理由 |
|-------------|-----|
| **聖書のみのテキスト** | 古風なレジスター、典礼的語彙、定型的な構造。OMT-1600 はこの方法で1,560言語を評価しました — 私たちは意図的にこれを避けます。 |
| **合成評価ペア** | LLM が生成した参照は評価の目的を損ないます。参照は人間が作成したものでなければなりません。 |
| **単一レジスターのコーパス** | すべてフォーマル、またはすべて会話的。実世界の翻訳は複数のレジスターにまたがります。 |
| **難易度1のみ** | 単語と挨拶は翻訳をテストしません — 語彙検索をテストするだけです。 |
| **機械翻訳された参照** | Google 翻訳の出力を「参照」として使用することは循環的です。 |
| **コンテキストタグのない文** | 診断分析のためにコミュニケーション機能を知る必要があります。 |

## 4. 暗号化シーリングとサンドボックステスト {#4-cryptographic-sealing-and-sandbox-testing}

### 4.1 テストセットをシールする理由

従来の ML ベンチマークはテストセットを公開します。一度公開されると、フロンティア LLM は最終的にそれらを（意図的に、またはウェブスクレイピングを通じて）学習データとして使用し、スコアの信頼性が低下します。先住民言語データについては、さらなる懸念があります：公開された言語データはコミュニティの同意なしに使用される可能性があります。

シーリングにより以下が保証されます：
- **テストセットの完全性：** 手法は一度も見たことのないデータに過学習できない
- **データ主権：** コミュニティが自分たちのデータに対する評価を誰が行うかを管理する
- **永続的な新鮮さ：** テストセットが汚染されることがない

### 4.2 サンドボックステストの仕組み

```
Developer workflow:
  1. Developer builds a translation method using the PUBLIC development corpus
  2. Developer tests locally against the development segment (unlimited, self-serve)
  3. When ready, developer submits their complete method (code + config + coaching data)
  4. Governance org installs the method in the evaluation sandbox
  5. Sandbox runs the method against the SEALED gold-standard test set
  6. Only scores are returned to the developer
  7. Developer never sees the source sentences or reference translations

The sandbox:
  - Runs on governance-controlled infrastructure
  - Has selective network access (LLM APIs only, no exfiltration)
  - Produces a tamper-proof run card (SHA-256 hash of all inputs and outputs)
  - Logs all execution for audit purposes
  - Can be inspected by the governance org at any time
```

### 4.3 鍵管理

シールされたテストセットの暗号化鍵は、2-of-3 閾値の Shamir Secret Sharing を使用して分割されます：

| 鍵保有者 | 役割 | 失効権限 |
|-------------|------|-----------------|
| **コミュニティガバナンス組織** | 主要な管理者 | 評価アクセスを単独で失効できる |
| **アカデミック学部パートナー** | 共同管理者 | 鍵の再構築に参加できる |
| **Champollion プロジェクト** | エスクロー | 単独ではデータにアクセスできない；他の当事者が利用不能になった場合の継続性を確保 |

3つのシェアのうち任意の2つで鍵を再構築できます。つまり：
- コミュニティ + 学部は Champollion なしでデータにアクセスできる
- コミュニティ + Champollion は学部なしでデータにアクセスできる
- Champollion 単独では絶対にデータにアクセスできない

### 4.4 ハッシュマニフェスト

コーパスがシールされると、**ハッシュマニフェスト**が公開 Git コミットに公開されます：

```json
{
  "corpus_id": "crk-ualberta-v1",
  "seal_date": "2026-09-15T00:00:00Z",
  "segments": {
    "development": {
      "entry_count": 200,
      "sha256": "a3f7c...",
      "access": "public"
    },
    "gold_standard": {
      "entry_count": 100,
      "sha256": "b8d2e...",
      "access": "sealed",
      "key_scheme": "shamir-2-of-3"
    },
    "held_out": {
      "entry_count": 20,
      "sha256": "c9e4f...",
      "access": "sealed",
      "key_scheme": "shamir-2-of-3"
    },
    "diagnostic": {
      "entry_count": 30,
      "sha256": "d1a3b...",
      "access": "public"
    }
  },
  "total_entries": 350,
  "manifest_sha256": "e2b5c..."
}
```

これにより以下が証明されます：
- コーパスが特定の日付に存在していたこと
- 既知のサイズと構造を持つこと
- シールされたセグメントへの変更はハッシュチェーンを壊すこと
- コミュニティは自分たちのデータが改ざんされていないことを確認できること

## 5. 学部が得られるもの

### 5.1 研究インフラ

| 資産 | 説明 |
|-------|------------|
| **評価ハーネス** | 言語のための動作確認済みの評価フレームワーク — ツール構築の数ヶ月を節約 |
| **LYSS メトリクス** | 言語固有の評価メトリクス（LYSS-fst、LYSS-eq、LYSS-sem）を言語向けに設定 — FST と辞書リソースが存在する場合 |

### 5.4 コミュニティへの影響

- 言語コミュニティは**独立した評価能力**を得ます — 任意の MT システム（Google、Meta、またはカスタム）が自分たちの言語に対して実際に機能するかどうかを評価できます
- コミュニティは暗号化鍵の管理を通じて**テストデータを管理します**
- ベンチマークを通じて証明された手法は**所有権をコミュニティに移転します**（ベンチマーク仕様 §8.3 参照）。デプロイメントが得たものはすべてコミュニティのものとなります — Champollion は非営利であり、取り分はありません

## 8. よくある質問

### 「すでに並列コーパスがあります。使用できますか？」

はい — コーパスに明確な出典があり、人間が作成したものであり、ライセンスが評価での使用を許可している場合は可能です。スキーマへのフォーマット、不足しているメタデータの追加、統合をお手伝いします。既存のコーパスはタイムラインを大幅に短縮できます（フェーズ2をスキップするか、ギャップ補完作業に縮小できます）。

### 「言語の FST がありません。」

問題ありません。LYSS-fst（形態論的有効性）は FST を必要としますが、ハーネスはプロファイル B の重み（chrF++、BLEU、COMET、行動メトリクス）を使用して FST なしでも動作します。関連言語の GiellaLT FST が存在する場合、適用できる可能性があります。そうでない場合でも、コーパスは価値ある評価を可能にします — 形態論的有効性ゲートがないだけです。

### 「話者がラテン文字以外の文字を使用しています。」

完全にサポートされています。コーパススキーマはあらゆる Unicode スクリプトを処理します。Cree の SRO（標準ローマ字正書法）と音節文字向けに設計しましたが、同じインフラがデーヴァナーガリー、アラビア文字、CJK、エチオピア文字、またはその他の書記体系でも動作します。

### 「方言の変異についてはどうですか？」

タグ付けしてください。コーパスエントリスキーマには方言情報のための `notes` フィールドが含まれています。複数の方言が表現されている場合は、それらを記録してください。リンターの等価クラス（LYSS-eq）は方言変異を等価として受け入れるように設定できます。診断テストスイートには方言固有の対照を含めることができます。

### 「コーパスは誰のものですか？」

ガバナンス組織を通じて言語コミュニティのものです。学部は研究パートナーとしてクレジットされます。Champollion は運用継続性のためにエスクロー鍵シェアを保持しますが、シールされたデータに単独でアクセスすることはできません。development セグメントはコミュニティが指定した Creative Commons ライセンスの下で公開されます。

### 「中止したい場合はどうなりますか？」

コミュニティはいつでも暗号化鍵の再構築を拒否することで評価アクセスを失効させることができます。シールされたデータが公開されることはありません。すでに公開されている development セグメントはそのライセンスの下で公開されたままです。学部の研究成果（論文、発表）は、いかなる場合でも学部のものとして保持されます。

### 「ガバナンス組織がまだ存在しない場合はどうなりますか？」

ガバナンス組織なしでフェーズ1〜3（コーパス設計、作成、品質保証）を開始できます。シーリング（フェーズ4）には鍵の管理者を特定する必要があります。暫定的に、学部が Champollion プロジェクトとともに共同管理者として機能することができます。コミュニティガバナンス組織が設立された時点で管理権が移転されることを前提とします。

## 付録：タグ付けとコーパス構築

本文書は**コーパス構築** — 評価のグラウンドトゥルースを形成する並列テキストペアの作成 — を対象としています。タグ付け（形態論的注釈、インターリニアグロス、FST タグ文字列）はコーパスを豊かにする別の活動ですが、基本的な評価には必須ではありません。

| 活動 | 必須？ | 有効にするもの |
|----------|-----------|-----------------|
| **コーパス構築**（本文書） | ✅ 必須 | 基本評価：chrF++、完全一致、COMET、行動メトリクス |
| **FST カバレッジチェック** | 🟡 オプション | LYSS-fst 形態論的有効性メトリクス **および** FST 由来の `morphological_accuracy`（レンママッチ — 注釈不要；スコアリング仕様 §2.2） |
| **形態論的注釈** | 🟡 オプション | `morphological_accuracy` の将来の*ゴールド検証済み*アップグレードを可能にする；FST 由来バージョン（上記）は不要 |
| **リンター等価ルール** | 🟡 オプション | LYSS-eq 等価マッチメトリクス |
| **セマンティックバリデータールール** | 🟡 オプション | LYSS-sem セマンティック検証メトリクス |
| **話者品質評価** | 別の活動 | メトリクス検証（[話者検証プロトコル](/docs/network/specifications/speaker-validation)参照） |

タグ付けと話者検証は別の文書で説明されており、コーパス構築と並行して、またはその後に進めることができます。
