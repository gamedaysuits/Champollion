# 評価コーパス設計フレームワーク

FLORES+でフロンティアモデルを評価し、85 chrF++のスコアが出たとしても、「モデルの翻訳能力が高い」のか、「モデルがこれらの特定の文ペアを暗記している」のかを区別することはできません。このフレームワークが存在する理由は、まさにこの単一の曖昧さにあります。評価コーパスは、そのスコアが主張通りの意味を持つ場合にのみ構築する価値があり、そのためには、新しい文ペア、追跡された出所、階層化されたドメイン、段階的な難易度といった、意図的な設計が必要です。このページは、Champollionの評価データセットがどのように設計、構築、維持されているかを示す信頼できる唯一の情報源（source of truth）です。

> **バージョン:** 1.0 · **ステータス:** ドラフト · 関連資料: [Corpus Partnership](/docs/network/specifications/corpus-partnership)ワークフローは、この方法論を研究部門と共同で実践するためのものです。

---

## 1. 設計原則

### 1.1 — 公開ベンチマークを使用しない理由

公開並列コーパス（FLORES+、Tatoeba、WMT テストセット、OPUS）は開発およびデバッグ目的では利用可能ですが、**公式リーダーボード評価からは除外されています**。理由は明確です。

**データ汚染。** フロンティアLLMは、膨大なウェブスクレイピングデータでトレーニングされています。公開されているパラレルテキスト（特によく整理され、広く引用されているベンチマークデータセット）は、そのトレーニングデータに含まれている可能性が高いです。これは理論上の懸念ではありません。[研究により](https://arxiv.org/abs/2311.04850)、機械翻訳（MT）ベンチマークにおいて測定可能な汚染の影響が実証されています。（ここでも公開ベンチマークは引き続き実行されますが、それは手法同士をランク付けする*相対比較*レーンにおいてのみであり、絶対的な品質として扱われることは決してありません。）

Champollionにとって、これは非常に重要な問題です。その理由は以下の通りです。
- リーダーボードでは、LLMの手法、従来のMTサービス、および専用システムを並べて比較するため
- 私たちの価値提案は、*誠実で厳密な評価*であるため
- ターゲットユーザー（言語コミュニティ）が、これらのスコアに基づいて導入の意思決定を行うため

### 1.2 — 基本要件

すべての Champollion 評価コーパスは以下を満たす必要があります。

| 要件 | 根拠 |
|-------------|-----------|
| **人間が作成したもの** | 合成データは不可。すべてのソーステキストと参照翻訳は人間が執筆したものでなければなりません。LLM はアライメントやフォーマットの補助には使用できますが、コンテンツの生成には使用できません。 |
| **並列形式で公開されていないもの** | ソーステキストは公開されていてもよく、参照翻訳も公開されていてもよいですが、特定の*ペアリング*はダウンロード可能な並列コーパスとして存在してはなりません。 |
| **出所が追跡されているもの** | すべてのエントリには、ソース文書・翻訳者・ライセンス・日付という記録された出所が必要です。 |
| **言語学的知見に基づくもの** | カバレッジはランダムサンプリングではなく、類型論的特徴によって導かれなければなりません。 |
| **ドメインが層別化されているもの** | エントリは定義されたテキストドメインにわたって、制御された代表性をもって分布していなければなりません。 |
| **難易度が段階分けされているもの** | エントリは構造的複雑さに基づいて難易度ティア（1〜5）を割り当てられなければなりません。 |
| **バージョン管理されているもの** | コーパスのバージョンはコンテンツハッシュで管理されます。スコアは同一バージョン内でのみ比較可能です。 |
| **コミュニティがレビュー可能なもの** | 参照翻訳は言語コミュニティのメンバーがレビューできなければなりません。 |

### 1.3 — コーパスタイプ・長さ・スタイルの中立性

Champollion は、**翻訳単位が何であるかについて中立な**オープン翻訳評価ハブです。コーパスエントリは任意の長さのテキスト——短い一文、長い複文、段落、または文書全体——であり、プラットフォームはすべてを同じ方法で評価します。**短いテキストや簡単なテキストのみに制限はありません。** ハーネスは長さの上限を設けておらず（長い翻訳が切り捨てられないよう、意図的に出力トークンに十分な余裕を持たせています）、難易度ティア（§3）とドメイン（§2.1）は*設定可能な軸*であり、難しいテキストや長いテキストを除外するゲートではありません。

ハブは以下の軸にわたって中立かつ設定可能です。

| 軸 | 範囲 |
|------|-------|
| **粒度** | 文・長文・段落・文書（`sizeUnit: entries \| sentences \| segments \| documents`） |
| **長さと複雑さ** | 短い → 長い；単純 → 非常に複雑（難易度ティア 1〜5） |
| **スタイルとレジスター** | フォーマル、インフォーマル、技術的、文学的、会話的、行政的（ドメイン分類、§2.1） |
| **手法** | 任意の `TranslationMethod` — LLM、ニューラル NMT、ルールベース、ハイブリッド、人間 |
| **言語とペア** | 任意の有向ペア；高リソース言語バイアスは組み込まれていない |

コーパスはそのカードで独自のタイプ・粒度・レジスター・難易度を宣言し、ハーネスはカードが宣言した内容を尊重します。Tatoeba をソースとするデフォルトの**開発用**コーパスが短文であるのは、Tatoeba がそういうものだからです——これはそれらのソースコーパスの特性であり、**プラットフォームの制限ではありません**。文書レベルおよび長文の評価セットはファーストクラスです。同じ方法で登録してください（例えば、非常に長いエントリの場合はリクエストバッチを小さく設定するなど）。

## 2. ソーステキストの選択

### 2.1 — ドメイン分類体系

Champollion は、学術的な演習ではなく**実際のデプロイコンテキスト**における翻訳を評価します。すべてのコーパスエントリは、**正規の 16 コードドメイン分類体系**からのドメインでタグ付けされており、構築時に検証されます。

この分類体系は一度だけ定義されています——唯一の信頼できる情報源である [Benchmark Specification §2.7](/docs/network/specifications/benchmark#27-domain) に記載されており、ドリフトを避けるためここでは再掲しません。コードは：`conv`、`ecommerce`、`edu`、`financial`、`gov`、`legal`、`literary`、`marketing`、`medical`、`news`、`religious`、`scientific`、`subtitles`、`support`、`tech`、および `ui` です。各コードの説明と典型的な利用者については §2.7 を参照してください。このセット外のドメインコードを導入しないでください。

### 2.2 — ドメイン分布

標準的な評価コーパスは、対象コミュニティに最も関連するドメインにわたって分布することを目指すべきです。正確なコードとパーセンテージは言語ペアによって異なります。以下の表は §2.1 の正規コードを使用した*例示的な*目標分布の一例です。

| ドメイン | コード | 目標 % | 根拠 |
|--------|------|----------|-----------|
| ソフトウェア UI | `ui` | 25% | Champollion CLI ユーザーの主要なデプロイコンテキスト |
| 政府・行政 | `gov` | 15% | 法的影響を伴う重要度の高い翻訳 |
| 教育 | `edu` | 15% | 言語復興の中核的なユースケース |
| 文学・物語 | `literary` | 10% | 文化的ニュアンスと文学的レジスターをテスト |
| 会話 | `conv` | 10% | インフォーマルなレジスターと自然な話し言葉パターンをテスト |
| 技術 | `tech` | 10% | 精度と用語の一貫性をテスト |
| 医療・健康 | `medical` | 10% | 重要度が高く、ドメイン固有の語彙をテスト |
| ニュース・ジャーナリズム | `news` | 5% | 現代的な語彙とニュートラルなレジスターをテスト |

### 2.3 — ソース選択基準

新しいコーパスのソーステキストを選択する際：

1. **ライセンスの互換性。** ソーステキストは評価コーパスでの使用を許可するライセンスのもとにある必要があります。CC BY、CC BY-SA、またはパブリックドメインを優先してください。ライセンスを記録してください。

2. **新しさ。** 過去 10 年以内に公開されたテキストを優先してください。言語は進化します——特にテクノロジー、ガバナンス、医療に関する語彙は。

3. **レジスターの多様性。** 各ドメイン内で、異なるフォーマリティレベルのテキストを求めてください。政府のプレスリリース（フォーマル）と政府のソーシャルメディア投稿（インフォーマル）はどちらも `admin` ドメインですが、レジスターは異なります。

4. **文化的関連性。** 先住民族言語および少数言語については、たまたま並列で存在するテキストよりも、コミュニティにとって重要なテキスト——土地管理文書、その言語での教育資料、文化保存テキスト——を優先してください。

5. **機械翻訳されたソースは不可。** 「並列」文書が元のテキストを Google 翻訳にかけてポストエディットすることで作成されたものである場合、参照翻訳として受け入れられません。参照翻訳は独立した人間による翻訳でなければなりません。

## 3. 難易度ティアシステム

### 3.1 — ティア定義

すべてのエントリは、翻訳難易度（手法によって異なる）ではなく、*ソーステキスト*の構造的複雑さに基づいて難易度ティア（1〜5）が割り当てられます。

| ティア | ラベル | 構造的特徴 |
|------|-------|---------------------------|
| 1 | **初級** | 単純な文。単一節。現在時制。一般的な語彙。慣用句なし。埋め込み構造なし。 |
| 2 | **中級** | 重文。接続詞で結ばれた 2 つの節。過去・未来時制。一部のドメイン語彙。 |
| 3 | **上級** | 複文。従属節、関係節。混合時制。ドメイン固有の専門用語。受動態。 |
| 4 | **専門家** | 複数の埋め込み節。法律・技術的レジスター。条件構造。抽象的概念。文化的参照。 |
| 5 | **極限** | 複数の課題が同時に存在する密度の高い文章：入れ子になった従属構造、代名詞参照の曖昧さ、文化的慣用句、混合レジスター、希少語彙。 |

### 3.2 — 言語学的知見に基づく難易度要因

構造的複雑さに加えて、難易度はソース言語とターゲット言語の**類型論的距離**によって調整されます。これらの要因は WALS の類型論的特徴と言語カードの分類データから導かれます。

| 要因 | 低難易度 | 高難易度 |
|--------|---------------|-----------------|
| **語順** | 同じ基本語順（例：SVO→SVO） | 異なる基本語順（例：SVO→SOV） |
| **形態論的タイプ** | 類似したタイプ（例：分析的→分析的） | 異なるタイプ（例：分析的→多合成的） |
| **文法的性** | 同じシステムまたは性なし | ソースに性がなく、ターゲットに複雑な性がある |
| **敬語・レジスター** | レジスターマーキングなし | ターゲットに複雑なレジスターシステムがある（例：日本語、韓国語） |
| **文字** | 同じ文字 | 異なる文字（音訳が必要） |
| **有生性** | 有生性の区別なし | ターゲットに有生性に基づく一致がある（例：クリー語） |
| **証拠性** | 証拠性なし | ターゲットが情報源を文法的にマークする |

### 3.3 — ティア分布

標準的なコーパスはおおよそ以下の分布を持つべきです。

| ティア | 目標 % | 根拠 |
|------|----------|-----------|
| 1 | 15% | ベースラインを確立——質の低い手法でもこれらは処理できるはず |
| 2 | 25% | 実用的な翻訳の主力 |
| 3 | 30% | 手法の品質差が見えてくる領域 |
| 4 | 20% | 良い手法と優れた手法を区別する |
| 5 | 10% | 上限テスト——これらをうまく処理できる手法はほとんどない |

## 4. 参照翻訳の品質

### 4.1 — 翻訳者の要件

参照翻訳は以下の条件を満たす人間が作成しなければなりません。

1. ターゲット言語の**流暢な話者**（母語話者または同等レベル）
2. ソース言語とターゲット言語の両方で**読み書きができる**
3. テキストのドメインに**精通している**（医療テキストには医療翻訳者など）
4. **独立している**——翻訳者は翻訳中に同じテキストの MT 出力にアクセスしてはならない

### 4.2 — 翻訳ブリーフ

すべての翻訳者は以下を含むブリーフを受け取ります。

- 使用する**レジスター**（フォーマル、会話的など）
- **対象読者**（一般市民、専門家、子供など）
- 言語コミュニティ固有の**用語規則**
- 明示的な指示：「言葉ではなく意味を翻訳してください。自然に聞こえる翻訳は逐語訳よりも価値があります。」

### 4.3 — 品質保証

1. **二重翻訳。** 理想的には、各エントリは異なる翻訳者による 2 つの独立した参照翻訳を持ちます。これが実現できない場合は、ティア 4〜5 の二重翻訳を優先してください。

2. **コミュニティレビュー。** 参照翻訳は、翻訳を作成していない少なくとも 1 人の追加の話者によってレビューされるべきです。

3. **許容可能なバリアント。** 各参照について、既知の許容可能なバリアント（語順、正書法の慣習、方言形式）を記録してください。これらは `equivalent_match_rate` メトリクスに反映されます。

### 4.4 — 不良な参照とは何か

| 問題 | 評価を無効にする理由 |
|---------|------------------------------|
| 機械翻訳後にポストエディットされたもの | ポストエディットは MT の構造を保持するため、より自然な翻訳を生成する手法にペナルティを与える |
| 流暢な話者ではなく学習者が翻訳したもの | 参照にエラーが含まれる可能性があり、正しい MT 出力にペナルティを与える |
| 過度に逐語的なもの | 自然な翻訳は逐語的な参照に対して低いスコアになる |
| 曖昧なソースに対して単一の有効な解釈しかないもの | 有効な代替解釈にペナルティを与える |

## 5. 汚染防止

### 5.1 — 汚染の脅威モデル

| 脅威 | 説明 | 軽減策 |
|--------|-------------|------------|
| **学習データの重複** | LLM が並列コーパスで学習されている | 並列コーパスを公開しない |
| **Few-shot リーケージ** | 手法の作者が評価エントリを few-shot の例として使用する | フィンガープリントチェック：プロンプト内のエントリが検出されフラグが立てられる |
| **間接的な汚染** | ソーステキストが LLM の学習データに存在する（単言語） | 許容可能——単言語のソーステキストは想定内。*ペアリング*が新規でなければならない。 |
| **クラウド汚染** | コミュニティレビュアーがエントリを公開共有する | ライセンス条件が並列コーパスの再配布を禁止する |

### 5.2 — コーパス秘密保持ティア

| ティア | 可視性 | 用途 |
|------|-----------|-----|
| **公開開発セット** | 完全公開 | 手法の開発、デバッグ、回帰テスト。スコアはリーダーボードに公開されない。 |
| **ホールドアウト評価セット** | ソーステキストは可視、参照は秘密 | 公式リーダーボード評価。手法はソーステキストを受け取り翻訳を返す；スコアリングはサーバーサイドで行われる。参照は手法に公開されない。 |
| **ゴールドスタンダードセット** | 完全秘密、コミュニティ管理 | コミュニティ検証済み評価。ガバナンス組織が管理。「Community Validated」検証ティアに使用。 |

### 5.3 — ローテーションポリシー

評価コーパスは定期的に**ローテーション**されるべきです。

1. コーパスが 12 ヶ月使用された後、代替コーパスの構築を開始する
2. 古いコーパスを「開発セット」ステータス（公開）に移行する
3. 新しいコーパスを「ホールドアウト評価セット」に昇格させる
4. これにより、固定されたターゲットに対する反復的な最適化による段階的な汚染を防ぐ

## 6. コーパス構築ワークフロー

### 6.1 — ステップバイステッププロセス

```
Step 1: Language Pair Selection
    └─ Identify target language, read language card
    └─ Review typological features (WALS), contact influences, scripts
    └─ Identify which difficulty factors apply

Step 2: Source Text Curation
    └─ Identify candidate source documents per domain
    └─ Verify licenses
    └─ Extract candidate sentences/segments
    └─ Classify by domain and preliminary difficulty tier

Step 3: Segment Selection
    └─ Sample segments to match domain distribution (§2.2)
    └─ Sample segments to match difficulty distribution (§3.3)
    └─ Ensure linguistic phenomenon coverage (§6.2)
    └─ Target minimum corpus size (§6.3)

Step 4: Reference Translation
    └─ Assign segments to qualified translators
    └─ Provide translation brief
    └─ Collect translations
    └─ Dual-translate Tier 4–5 entries

Step 5: Quality Assurance
    └─ Community review of references
    └─ Document acceptable variants
    └─ Flag and resolve disagreements

Step 6: Metadata & Packaging
    └─ Assign final difficulty tiers
    └─ Add provenance metadata per entry
    └─ Content-hash the corpus for versioning
    └─ Package as corpus JSON per harness spec

Step 7: Registration
    └─ Register in Supabase datasets table
    └─ Add to ATTRIBUTION.md if new sources used
    └─ Document in arena website
```

### 6.2 — 言語現象のカバレッジ

すべてのコーパスには、言語ペアに関連する特定の言語現象をテストするエントリを含める必要があります。これらは言語カードの `linguisticChallenges` および `contactInfluences` フィールドから導かれます。

**普遍的な現象（すべての言語ペア）：**
- 代名詞解決（曖昧な先行詞）
- 否定（単一、二重、スコープ）
- 量化詞（all、some、none、most）
- 時間表現（相対的な日付、期間）
- 固有表現（人名、地名、組織名）
- 数字と単位
- リストと列挙

**ペア固有の現象（言語カードより）：**
- 多合成的なターゲットの場合：複雑な動詞形態論、組み込み
- 性を持つターゲットの場合：性の一致、中立・包括的な参照
- SOV ターゲットの場合：節末動詞、後置詞
- 声調言語の場合：声調に依存する意味の区別
- 敬語言語の場合：レジスターマーカー、社会的文脈
- 接触言語の場合：コードスイッチングの境界、借用語の統合

### 6.3 — 最小コーパスサイズ

統計的信頼性には最小エントリ数が必要です。これらはペアードブートストラップ信頼区間の要件（`significance.py` より）に基づいています。

| 目的 | 最小エントリ数 | 推奨 |
|---------|-----------------|-------------|
| 開発セット | 50 | 100〜200 |
| ホールドアウト評価セット | 100 | 200〜500 |
| ゴールドスタンダードセット | 200 | 500+ |
| ドメインごとの最小 | 10 | 25+ |
| ティアごとの最小 | 10 | 20+ |

**評価に最低 100 エントリが必要な理由は？** 約 100 エントリ未満では、ペアードブートストラップ有意性検定（1,000 リサンプル）は chrF++ で約 5 ポイント未満の差を確実に検出できません。200 以上のエントリがあれば、p<0.05 で約 2 ポイントの差を検出できます。

## 8. ゲーミング対策

### 8.1 — コーパスの整合性

| 対策 | 実装 |
|---------|----------------|
| **コンテンツハッシュ** | コーパスバージョン = ソートされたエントリ ID + 参照の SHA-256。変更があれば新しいバージョンが生成される。 |
| **エントリフィンガープリント** | 各エントリはコンテンツ由来の ID を持つ。変更されたコーパスに対して結果を提出した場合、フィンガープリントが一致しない。 |
| **ホールドアウトの強制** | 公式評価では、手法はソーステキスト**のみ**を受け取る。参照は公開されない。スコアリングはサーバーサイドで行われる。 |
| **ローテーションスケジュール** | コーパスは固定されたターゲットに対する長期的な最適化を防ぐため、年次でローテーションされる。 |

### 8.2 — 提出の整合性

| 対策 | 実装 |
|---------|----------------|
| **決定論的フィンガープリント** | 実行設定（モデル、温度、プロンプト、コーパスバージョン）がハッシュ化される。同一の設定は同一のフィンガープリントを生成する。 |
| **チェリーピック検出** | 提出者は最良のものだけでなく、すべての実行を開示しなければならない。同じフィンガープリントを持つ複数の提出はフラグが立てられる。 |
| **汚染チェック** | 評価エントリが手法のプロンプトやコーチングデータにそのまま含まれている場合、提出は失格となる。 |

## 10. 言語カードとの統合

コーパスフレームワークは言語カードシステムと統合されています。

1. **ドメイン選択**はカードの `linguisticChallenges` によって導かれます——言語に固有の課題（多合成性、声調、有生性）がある場合、コーパスにはそれらをテストするエントリを含める必要があります。

2. **難易度の調整**はカードの `classification` を使用します——ソース言語とターゲット言語のファミリー間の類型論的距離が、何が「難しい」かに影響します。

3. **レジスターのカバレッジ**はカードの `registers` を使用します——言語に定義されたレジスターがある場合（formal-filipino、taglish-professional、taglish-casual など）、コーパスには各レジストレベルのエントリを含めるべきです。

4. **接触影響のテスト**はカードの `contactInfluences` を使用します——重い借用層を持つ言語（フィリピン語：スペイン語 + 英語 + アラビア語）については、手法が借用語を正しく処理するか、過剰翻訳するかをテストするエントリを含めてください。

5. **文字処理**はカードの `scripts[]` を使用します——複数文字の言語（セルビア語：キリル文字 + ラテン文字）については、正しい文字選択をテストするエントリを含めてください。
