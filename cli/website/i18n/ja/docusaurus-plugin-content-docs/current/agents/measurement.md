# 測定ルール

レールの約束は、人々が自分たちの文に対してモデルがどれほど優れているかを**知る**ことができるということであり、モデルが優れていること自体を約束するものではありません。その約束はいくつかのルールに基づいており、その大半はツールによって強制されます。このページではそれらのルールを正確に示し、最後に数値の伝え方について説明します。

## スコアリング標準（standard/1）

すべての新しい実行は同じ方法でスコア付けされます（`arena/mt_eval_harness/scoring.py`）：

- **主要指標：** コーパス全体の **chrF++**（単語順序2のsacreBLEU chrF）、0〜100（高いほど参照訳に近いことを意味します）。**95%ブートストラップ区間**とsacreBLEUシグネチャを伴います。表記は `chrF++ 47.5 [45.9, 49.0]`。
- **どのセグメントを数えるか：** 主要指標、その信頼区間、およびすべての比較に対して1つのルールを適用します。翻訳に失敗したセグメントは空の出力としてカウントされ、除外されることも、プレースホルダーとしてスコア付けされることもありません。参照訳のないセグメントはすべてにおいて除外されます。
- **区間：** 主要指標自身の区間 — それらのセグメントに対するパーセンタイル・ブートストラップ、再サンプリング1,000回、シード値12345、α 0.05。セグメント数が30未満の場合、ツールは区間のカバレッジが低い可能性があると警告します。2未満の場合は区間が算出されません。
- **並列表示（混用禁止）：** BLEU、spBLEU、TER、および算出された場合のCOMET。それぞれにシグネチャまたはモデルIDが付きます。
- **診断（別枠）：** 完全一致、等価一致、FST受理、形態素精度、意味バリデータ、コードスイッチング、ハルシネーション、用語準拠、文章スタイル。これらが主要指標に入り込むことはなく、順位付けに使われることもありません。
- **「より優れている」とはchrF++の対応あり有意差検定**を指し、2つの数値を視覚的に比較することではありません。
- **品質ラベルなし。** 人手による評価のみが品質を保証します。

**廃止済み：** 重み付け複合スコアと品質ティアのラベル。standard/1の実行カードには `composite: null` および `quality_tier: null` が記載されます。
**注意：** 過去のカードのものであっても、複合スコアやティアを提示、計算、引用してはなりません。

**スコアの注意書き（caveat）**はスコアの横に書かれる診断情報であり、スコア自体を変更するものではありません：`source_copy`（出力の半分以上がソースをそのままコピー）、`length_inflation` および `length_deflation`（出力が参照訳の長さの2倍超、または半分未満 — 平均して、またはセグメントの4分の1以上で発生）、`near_constant_output`（1つの出力が多くのソースにわたって繰り返されている）、`train_test_near_twin`（訓練データにそっくりな行があるテスト行 — 半分以上の場合は重大）。**注意：** 注意書きはすべて、一言一句そのままスコアと一緒に伝えてください。

## ゲート付き測定

実行にゲートチェーンがある場合（[メソッドとゲート](/docs/agents/methods#gate-chains)）、**測定されるものは実際に出力されるもの**です：

- 主要指標のchrF++は、ゲートを通った出力をスコア付けします。
- ゲートなしのchrF++とその信頼区間は、その横に並びます（`overall.gates.ungated`）。
- **拒絶率（refusal rate）** — ゲートが拒絶したセグメント数 ÷ 判定されたセグメント数 — は独立した数値であり、ゲート別および実際に出力された内容（`shipped_from`：メソッド、ソース、フォールバック、何もなし）ごとの件数を伴います。
- チェーンの**フィンガープリント**（正規化JSONのsha256）は、レポートおよび公開されるすべての実行に付随します。

**ロック：** 測定におけるフォールバックの禁止：`mt-eval run` および `mt-eval test` は、翻訳やコストが発生する前に、拒絶されたセグメントをフォールバックに渡すゲートを持つチェーンを拒否します。

**注意：** ゲート付きスコアを報告する際は、ゲートなしのスコアと拒絶率も併せて報告してください。ゲート付きスコア単体では、ゲートが何を破棄したのかが隠れてしまいます。

## 各セットとその用途

| 役割 | 用途 | 読み出し |
|---|---|---|
| `train` | 学習 | 決して結果としてスコア化されない |
| `dev`（練習用） | チェックポイントの選択、改善ラウンドの判定（50文以上）、辞書フロア | 自由に |
| `test` | マイルストーン：人々の予測と照らし合わせたモデルのテスト | スコア測定のための読み出しには事前登録（forge）が必要。すべての読み出しがログに記録される |
| `sealed` | 保持者以外には誰にも見られないテスト | 1回のみ |

**nmt-forge内**（レジストリ、`.forge/eval-registry.json`、台帳）：

- **ロック：** 登録されたセットのすべての読み取りは、その目的（`score`、`dev-selection`、`audit`、`inspect`）とともにハッシュチェーンされた台帳に書き込まれます。
- **ロック：** テストセットのスコア付けには、その現在の内容に対する有効な事前登録が必要です。
- **ロック：** 封印（sealed）セットは1回だけスコア付けされます。2回目のスコア付けは拒否されます（`sealed set '<name>' has already been spent`); a single `mt-eval` による封印ファイルの読み取りも、それを消費します。`--override-respend '<reason>'`（`nmt-forge score` および `nmt-forge compare` 上）が台帳に記録されます。`export` は再消費を拒否し、`--no-eval` を指定します。
- **ロック：** devフェンス：訓練には登録された `dev` セットが必要です。dev行は、テストセットや封印セットとまったく同じソースまたはターゲットを共有してはなりません。訓練行がdev行であってはなりません。

**mt-eval内：**

- **注意：** `mt-eval run` および `mt-eval compare` は、事前登録なしでテストファイルまたは封印ファイルをスコア付けし、読み取り回数によって拒絶することはありません。`mt-eval run` は、forgeが読み取りログを作成した場合にのみ、ファイルの読み取りログ（`<file>.reads.jsonl`）に1行追加します。`compare` および `test` は何もログに記録しません。人々の予測が書き込まれる前に、mt-evalでテストセットをスコア付けしてはなりません。

## 予測

```bash
nmt-forge prereg new first-model --eval-set project-test --expect "<their words>" --rationale "<their reason>"
nmt-forge prereg new round-2 --eval-set project-test --predictions predictions.json
nmt-forge prereg template --out predictions.json
```

- `--expect` および `--rationale`：chrF++に関する、人々の自由な言葉による1つのテキスト予測。その判定は人々の手によるものです：`nmt-forge prereg verdict <id> --prediction <n> --held` (or `--missed`) `--by "<who>"`。
- `--predictions <file>`：JSON配列。各予測は `metric` と `rationale` を指定し、ツールによって判定される `direction`（`increase`、`decrease`、`no_change`）と `baseline_score`（および任意の `margin`）、または自由記述の `expect` のいずれかを持ちます。
- **ロック：** （forgeまたは `mt-eval run` による）セットのスコア付け読み取りが行われた後に書き込まれた予測は拒否されます：*"eval set '…' was already read for scoring (N time(s): …) before this preregistration"*。`--allow-after-reads` はこれを通しますが、すべてのレポート、エクスポート、ステータスにその旨が表示されます。
- **注意：** 予測は人々のものであり、スコアが存在する前に書かれ、あなたが言い換えたり絞り込んだりしてはなりません。レールの質問は数値を提示しません（*「当て推量にとどめるため、ここでは数値を提示しません」*）。あなたからも数値を提案しないでください。

## ほぼ同一のコピー

`nmt-forge leak-audit` は、すべての訓練ペアを、登録されたすべてのdev、テスト、および封印セットと比較します：

| 検出内容 | ルール | 処理 |
|---|---|---|
| 同一ファイル | sha256 | 除外 |
| 完全コピー | 正規化後にソースまたはターゲットが同一 | 除外 |
| ほぼ同一のコピー | ターゲット単語セットの重複（Jaccard）が一方が他方を含む場合に ≥ 0.6、または ≥ 0.9 | 除外 |
| テンプレートの兄弟 | 同じ文の枠組みで、答えが異なる | 学習のために**保持**し、それらのテスト行を含めたスコアと除外したスコアの両方を読めるようにカウント |
| ソースのみ一致 | 同じプロンプトで、答えが異なる | 保持し、レポートに記載 |

短い文は文字トライグラムで比較され、ごく短い文は完全一致のみで比較されます。訓練行がテスト行と同一、またはどちらかの側で重複が ≥ 0.6 の場合、そのテスト行は**ニアツイン（ほぼ双子）**とみなされます。テスト行の半分以上にツインがある場合、スコアは翻訳ではなく主に記憶の再生（リコール）となり、重大な注意書きが付きます。`--clean-to` はスクリーニング済みのファイルを書き出します。`--drop-test-twins` はツインのないスコアを出すために、テスト行とツインになっている訓練行も除外します。

レールの最初のdev分割でも同じしきい値が適用されます：`nmt-forge split` 上の `--near-dupe 0.6` は、単語の重複が ≥ 0.6 の行をdevと訓練の境界の一方の側に留めるため、最初のdevスコアに、のちのラウンドのスクリーニングで拒絶されるようなニアコピーの記憶が含まれることはありません。`--max-group` は、テンプレートから書かれたファイルでも分割できるよう、ニアコピーのグループをdevサイズの半分+1に制限します。

**注意：** 「リーク監査で…が見つかりました」と述べるのは、`true_now` または監査自身の出力からのみにしてください。独断で「テストセットはクリーンです」などと言ってはなりません。

## 辞書フロア

`nmt-forge floor <word lists>` は、devセットを辞書を用いて逐語訳（最長フレーズ優先）し、実行のdevスコアと同じコード（chrF++と95%信頼区間）でスコア付けします。これはローカルのコンピュータで実行され、テストセットを読み取ることは決してなく、辞書の名前、ハッシュ、エントリ数、到達したソース単語数、およびスコアのみを記録します。実行が**フロアを上回る（beats the floor）**のは、そのdev信頼区間の下限がフロアの上限を上回っている場合のみです。`nmt-forge status` は、これを満たさない実行について警告します。

## 2つのモデルの比較

**改善ラウンド**（`nmt-forge compare-runs <in-use> <new>`）：両方のモデルによる**同じdev文**の翻訳を、行ごとに対にして比較します。対になった近似ランダム化検定（1,000試行）と、差に対する95%ブートストラップ区間を用います。

| 判定 | ルール |
|---|---|
| **too-few** | スコアに関係なく開発用の文が50文未満 — 使用中のモデルが維持され、話者のブラインド評価（下記）によって決定されます |
| **better** | 50文以上、p < 0.05 **かつ** 区間の下限が0を上回る — 新しいモデルの使用が提案されます。実際に使われるのは人々の同意があった場合のみです |
| **worse** | 50文以上、p < 0.05 かつ 区間の上限が0を下回る |
| **no-change** | それ以外 — 使用中のモデルが維持されます |

**なぜ50文なのか。** 考案されたテスト言語のByT5-smallの出力において、サイズごとに100組のランダムな練習セットを用意し、このルールで測定しました。開発文が23文の場合、ほぼ同等（500文で0.7 chrF++差）の2つのモデルを異なると判定したのが100回中9回、実際の+5.9 chrF++の向上を**better**と判定したのが100回中わずか21回でした。これが50文になると、それぞれ100回中4回と96回になりました。10回中8回検出された最小の差は、23文で8.1 chrF++ポイント、50文で5.8、100文で4.0、200文で2.8でした。そのため、railsの最初の分割では、200ペア以上ある場合に少なくとも50文の開発文を確保します（選別されたペアの10分の1、最大500文。200ペア未満の場合は4分の1で、これは50文未満になります）。そしてレビューシートでは練習行によってセットを増やしていきます。50行未満の間は2行に1行、200行に達するまでは4行に1行の割合で追加されます。

各判定は、そのdevセットが確実に（10回中8回）示す最小の差も示します：区間の幅 × (1.96 + 0.84) ÷ (2 × 1.96)。これが3 chrF++ポイントを超える場合、「no-change」はdevセットの検出限界であり、そのラウンドが無駄だった証拠ではありません。また、devセットによって新しい実行のチェックポイントが選ばれているため、新しいモデルにわずかに有利になります — 判定を伝える際は**その旨を述べてください**。

話者がブラインド評価で新しいモデルを選んだ場合（下記）、forgeがそれを使用対象として提案するのは、判定が**too-few**または**no-change**であった後のみです（**worse**の後は絶対にありません）。そして、まず人々が同意する必要があります（`improve-promote`、モード `confirm`）。昇格によって置き換えられた以前のモデルを話者がブラインド評価で好んだとしても、自動的に元に戻ることはありません。ラウンドレポートのアクションが人々に確認します。

**任意の2つの実行**（`mt-eval compare <report> <report> --significance`）：
デフォルトでは近似ランダム化（もう一方は `--method paired_bootstrap`）、1,000試行（`--n-bootstrap`）、α 0.05、シード値12345を使用し、レポート間でIDが共通するエントリに対して実施されます（10件未満の場合は警告）。chrF++が最初で、その後に二次的な評価指標が続きます。すべての実行ペアがテストされます。多重検定の補正は行われず、出力にもその旨が表示されます。

## ウィッシュリストが基準とするもの

`nmt-forge analyze` は、実行のdev chrF++を文の種類ごとに分解します（その種類のdev文が少なくとも5文ある場合）。ある種類が**最弱**であり、ウィッシュリストの重み付け対象となるのは、その種類の文のスコアが他の文をどれだけ下回っているかを示す95%信頼区間が、完全にゼロを上回っている場合のみです（文レベルchrF++に対するウェルチの信頼区間）。偶然の可能性がある低スコアは、そのように報告され（*「…は偶然の可能性があります — ウィッシュリストの基準にはなりません」*）、シートの重み付けには決して使われません。

「見たことのない単語」セクションでは、各単語について1文ではなく、それぞれ異なる内容を表す2〜3文を要求します。架空のテスト言語では、訓練で1回現れた単語が正しく出力された割合は27〜29%でしたが、2〜4回現れた単語では63〜95%でした。また、3,200の訓練文において、最も多くの未知語を含むように選ばれた文で訓練されたByT5-smallは、500のホールドアウト文のうち意味が正しかった割合が39.4%にとどまり、日常的な文での53.4%に対して劣り、話者の時間もわずかに多くかかりました（約54時間に対して約57時間）。

## 話者による採点

各改善ラウンドで、話者は新しい文に対するモデルの下訳に
`Y`、`N`、または`?`の印を付けます。正解率は`Y ÷ (Y + N)`（`?`、無印、練習用の
行、および再表示された行は除外）であり、95%のウィルソン区間が付きます。ラウンド間の上昇が
**進捗**とみなされるのは、最新ラウンドの区間が最初のラウンドの区間を完全に
上回っており、その間にいずれかのラウンドのモデルが実用化され — 人々によって選ばれた
場合（forgeの`export`および`choose`レコード）、それが**より良い**という判定の後であれ、
話者によるブラインド評価によるものであれ、自分たちの選択によるものであっても構いません。**より良い**という判定
単独では進捗とみなされません — **かつ**、その間のラウンド全体で合算した各昇格時の話者によるブラインド確認（下記）において、
新しいモデルが置き換え前のモデルよりも明らかに高い頻度で正解と判定された
場合（|z| > 1.96）に限られます。
これらはどのモデルも見たことのない文です。最も重要であり、
最初に取り組むべき測定指標です（[指導](/docs/agents/coaching)）。

**2つのモデルによるブラインド評価。** `champollion improve sheet`では、下訳された行のシード付きランダムな半分（`nmt-forge draft-newer`）を、印を付けずに
2つ目のモデルに下訳させます。
使用中でない場合は直近に訓練されたモデル（判定が少なすぎる、変化なし、または悪化だったラウンドの後など）、または昇格直後の訪問では、
現在使用中のモデルが置き換えた以前のモデルが担当します。どの行がどちらのモデルによるものかは、
シートとは別に`improve/round-<k>/sheet-key.json`に保持されます（`in_use`、`other`、
`relation` `newer`または`replaced`、各モデルの訓練ペア数`in_use_pairs`
および`other_pairs`、`other_rows`、ならびに下記の`repeat_rows`）。
その後、`champollion improve marks`が2つのモデルを別々に集計し、
再表示された行はすべて除外されます。

- 上記の正解率（進捗の測定基準）は、現在使用中のモデルの行のみをカウントします。
- どちらのモデルが下訳したかにかかわらず、正解と判定されたすべての下訳およびすべての修正が訓練ペアになります。
- 2比率の差の検定（併合、両側5%：|z| > 1.96）により、話者がどちらのモデルをより多く正解と判定したか（もし差があれば）を示します。`clear`は`newer`または`replaced`（もう一方のモデル）、`in-use`または`neither`となり、両方のカウント（`in_use_right`、`in_use_judged`、`other_right`、`other_judged`、`in_use_share`、`other_share`）、`other`、`relation`、および両モデルの訓練ペア数とともに`marks.json`（`blind`）に記録されます。新しいモデルとの比較では、`newer`、`newer_right`、`newer_judged`、`newer_share`も保持されます。いずれかのモデルで`Y`または`N`とマークされた行がない場合、`clear`は`null`となり、テキストには*「比較するには一方のモデルで判定された行が少なすぎます」*と表示されます。
- 新しいモデルとの比較において、それぞれ少なくとも1つの下訳が判定されている場合、カウントはforge（`nmt-forge speaker-verdict`）に送られ、forgeは同じ検定を実行して元帳（`improve-speaker`）に`clear`（`newer`、`in-use`、または`neither`）を記録します。その実行で**too-few**または**no-change**の判定が出た後、`clear: newer`によってforgeは新しいモデルを使用対象として提案します。その後、`champollion improve marks`に*「forgeに記録されました。新しいモデルの使用を提案します（まず人々が同意する必要があります）」*と表示されます（[トレーニング](/docs/agents/training#the-improve-rounds)）。

行は1つのシート上でランダムに割り当てられ、同じ話者によって、家族自身の新しい文を使って判定されます。そのため、明確な差があれば、devセットが小さすぎて示せないような事実を表しており、話者の採点の甘さ・厳しさの変化は両方のモデルに等しく影響します。**注意：** 話者の採点が読み取られる前に、どの行がどのモデルのものかを話者に教えてはなりません。

**再表示された行。** ラウンド2以降、`champollion improve sheet`はシート上の新しい文10件ごとに
1行を戻します（`REPEAT_EVERY`。端数切り捨て、条件を満たすものが少ない場合はそれ以下）。
以前のシートで話者が`Y`または`N`と付けた下訳を、以前の下訳とともに、印のない状態で、シード付きランダムな位置に配置します —
練習用の行、それ自体が重複である行、すでに再表示された行、
またはこのシート上の文は決して選ばれません。シートの先頭行、ヘッダーの上には
次のように記載されています。*「以下の数行は、意図的に過去のシートから再表示されています。
初めて見る文のように新しく印を付けてください。評価がどれだけ一致するかによって、
どの程度信頼できるかがわかります。」* どの行であるかは示されません。`sheet-key.json`はそれらを
`repeat_rows`として保持します（`row`、`from_round`、`from_row`、および以前の評価である`mark`）。
これにかかる話者の時間は1行あたり約10秒です。

`improve marks`は、各行を話者自身の過去の評価とのみ照合して判定します。
重複行はそのラウンドの正解率にカウントされることはなく、再び訓練ペアになることも、
ブラインド比較に含まれることもありません。`marks.json`には`repeats`が追加されます：`shown`、
`judged`（今回`Y`または`N`と付けられたもの。`?`または空欄は表示されますが判定されません）、
`agreed`、`agreement`（一致 ÷ 判定数）、`wrong_to_right`、
`right_to_wrong`、`wrong_before`（かつて`N`と付けられた判定対象行）、および
`rounds_apart_wrong_before`。次のように出力されます：*「再表示された行：話者はJ行中A行を以前と同じように評価しました（P%）— かつて不正解だったW行が正解に、かつて正解だったR行が不正解になりました。このラウンドの正解率には含まれず、再訓練にも使用されません。」*

ラウンド全体で合算し、10行以上が判定されると（`MIN_REPEATS`）、
ラウンドレポートはそこから2つの要素を読み取ります。

- **ランダム誤差** `e`：両方向に均等に起こる判定の反転から算出されます。ひとつの
  下訳に対する2回の評価が偶然不一致になる確率は2e(1 − e)であり、半分ずつ各方向に生じます。
  d = 2 × min(`wrong_to_right`, `right_to_wrong`) ÷ `judged`とすると、
  e = (1 − √(1 − 2d)) ÷ 2となります。誤差はあらゆる割合を50%へと引き寄せます。真の
  正解率がpである下訳は、e + p(1 − 2e)の割合で正解と付けられるため、
  e = 10%の場合、「真に80%正解」は約74%と表示されます。
- **ドリフト**：均等な反転を超えて一方の方向に偏った反転です。「かつて不正解で現在正解」の反転が
  もう一方の方向を明らかに上回っている場合、レポートは評価基準が甘くなっている可能性があると警告します。
  反転が6回以上あり、かつ符号検定で
  (`wrong_to_right` − 反転数 ÷ 2) ÷ √(反転数 ÷ 4) > 1.96となる場合です。

その確認行：*「話者は再表示されたJ行中A行を以前と同じように評価しました（P%）：約E%の評価がランダムにもう一方に反転し、これにより正解と付けられた割合全体が50%に引き寄せられます — 予測ではこれを考慮しています。」* — そしてドリフトについて：*「また、かつて不正解と付けられたW件の下訳が現在は正解と付けられており、逆方向のR件を上回っています：評価基準が甘くなっている可能性があり、正解率の上昇には現れないことがあります。」* 判定が10行未満の場合：*「これまでに判定された再表示行はN行です — 話者自身の評価誤差は10行から推計されます。」*

**ラウンドが示す見通し。** ラウンドレポートの予測は、正解率が80%未満である間、
実際の進捗（上記）からのみ作成されます。学習曲線は訓練データが倍増するごとに
対数オッズでほぼ均等な幅で上昇するため、昇格後の同じブラインド確認からその幅を読み取ります。
`logit(in_use_share) − logit(other_share)`の合計を
`log2(in_use_pairs ÷ other_pairs)`の合計で割った値（正解率は1〜99%に制限）であり、各正解率の分散（判定された下訳n件に対して約1 ÷ (n・p・(1 − p))）から
95%の範囲を求めます。使用中モデルの訓練ペア数から、正解と評価される割合が80%に達するまでに
さらに必要な文数（推計値）と、1文あたり70秒とした場合の話者の作業時間を提示します。
この範囲はステップ幅の区間をカバーし（さらに6回倍増した先の上限はありません）、再表示された行が10行判定された後は、
この話者の評価において「真に80%正解」がどこに位置するかを考慮します：e + 0.8(1 − 2e) + 0.2 × K（最大97%）。ここでKは1ラウンドあたりのドリフト（均等な反転を超えた反転数を、かつて不正解だった行の2回の評価が何ラウンド離れていたかで割った値）に、最初と最後の評価の間のラウンド数を掛けたもので、±30%を上限とします。最小値はステップ幅の上限における2つの目標値のうち小さい方、最大値はその下限における大きい方です。最小値が0の場合は「なし」と表示されます。テキストには続けて次のように追加されます：*「話者自身の評価：再表示されたJ行中A行を以前と同じように評価したため（P%）、約E%の評価がランダムにもう一方に反転します … 真に80%正解の下訳は、この話者の評価では約T%の頻度で正解と付けられる可能性があります — 推計範囲にはこれが織り込まれています。」*（Kがどちらかの方向に1%以上ある場合は、かつて不正解と付けられた下訳が現在どれだけ多く、あるいは少なく正解と付けられているかも記載）。それまでは、*「（話者自身の評価誤差はまだ考慮されていません：判定された再表示行が少なすぎます。）」*となります。`report.json`は
これらの数値を`projection_numbers`（`more_sentences`、`range`、
`speaker_hours`）として保持します。

シミュレーション — ノイズのある話者、rails独自の開発用分割、およびこれらの判定ルールを用い、2組のシードでシナリオごとに200回の試行を実施 — では、推計値は1ラウンドあたり400文の新しい文で69〜78%、800文で53〜56%の頻度で真の値の2倍以内の範囲に収まり、真の値は89〜94%および76〜80%の頻度で範囲内に収まりました（重複なしの場合は91〜93%および51〜54%）。
推計値自体を話者の評価基準に合わせて調整すると、1ラウンド800文では改善したものの400文では悪化したため（2倍以内の割合：64%および19%）、単純な80%の基準のまま維持されています。モデルが「すでに機能している可能性がある」という注記は試行された後に削除されました。正しかった回数に対して2〜3倍誤っていたためです。大まかな予測であり、その旨が明記されています。

## 数値が語らないこと

- スコアはそのセットにおけるシステム全体のものであり、個々の文に対するものではありません。文ごとの確信度（信頼度）はありません。
- chrF++は参照訳との重複を測定します。異なる言い回しの良い翻訳でもスコアが低くなることがあり、流暢な誤訳でもかなり高いスコアになることがあります。
- FST受理は単語が存在することを示すだけであり、文が正しい意味であることを示すわけではありません。
- 公開リーダーボードの行はデフォルトで自己報告によるものです。検証ツールは提出された出力をハッシュで固定されたコーパスに対して再スコア付けするのみで（1.0 chrF++以内）、メソッドを再実行することはありません。

## 数値の報告方法

すべての数値には、**その単位、何を測定したものか、どのセットで測定されたか**を付記します — セットのサイズ、および範囲がある場合はその範囲も併記します。

| 使う表現 | 使ってはいけない表現 |
|---|---|
| 「50文の練習用（dev）文で100点中chrF++ 24.1、範囲20.6〜27.6」 | 「24.1」・「精度24%」 |
| 「話者は24件の新しい下訳のうち9件を正解と判定 — 38%（21%〜57%）」 | 「精度38%」 |
| 「測定可能な変化なし：50の開発文では約5.8ポイントの差しか現れません」 | 「わずかに改善した」 |
| 「練習文が少なすぎてまだ判断できません：50文未満では比較による決定は行われず、話者のブラインド評価で決定されます」 | **too-few**の判定に対する「変化なし」 |
| 「ロックされた50文のテスト文において1回のみ、あなたが書いた予測と照らし合わせて：『…』」（相手の言葉をそのまま読み返す） | セットや予測が示されていないテストスコア |
| 「ブラインドで新しい文を評価した結果、話者は新しいモデルを12件中7件正解、使用中のモデルを12件中5件正解と判定 — 24文では明確な差はありません」 | 判定結果のみから「新しいモデルのほうが優れている」とすること |
| 「chrF++ 31.0（ゲートあり・出荷版）、33.5（ゲートなし）、12%がゲートにより拒否」 | ゲート適用後のスコア単独 |

- 範囲はツールがどれだけ確信を持っているかを示すものであり、2つの結果ではありません。
- 異なるセットでの2つのスコアは比較できません。同じセットでの2つのスコアは、対応あり検定で有意差が認められた場合にのみ差があるとみなせます。
- 注意書きや警告は、一言一句そのまま引用してください。
- スコアを「良い」「悪い」と呼んだり、品質を表す言葉を付けたりしてはなりません。何が実用に適しているかを決めるのは、流暢な話者です。
