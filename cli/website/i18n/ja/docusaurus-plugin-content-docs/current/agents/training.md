# nmt-forge による学習

`nmt-forge` は、コミュニティのペアデータをもとに、ガードレールの中でモデルを学習させます。結果を損なうような処理は拒絶され、拒絶のたびに「何が問題か」「なぜか」「どう修正するか」が示されます。独自の評価指標は実装しておらず、すべてのスコアは評価エンジン（`mt-eval`）から取得されます。これは他のすべてをスコア付けするのと同じコードです。

rails 上では、これらのコマンドを手動で入力することはほとんどありません。`champollion next` がコマンドを指定し、`forge` ステップ以降は forge 自身のアドバイザー（`nmt-forge status`）を中継します。このページでは、それらのステップで何が行われるかを説明します。

## モデル

`nmt-forge init --model <preset>` は、プリセットを明示的な数値として `config.json` に書き込みます（各実行の同一性にハッシュ化されるため、将来の forge リリースによって既存プロジェクトの実行が変更されることはありません）。`nmt-forge use-model <preset>` はプロジェクトを切り替えます。

| プリセット | 概要 | 必要要件 | forge による期待値の記述 |
|---|---|---|---|
| `cpu-tiny` | ペアデータからゼロから学習する小型 Transformer。学習行から学習した 4,000 トークンの語彙を使用 | CPU のみ · ダウンロード不要 | 「約 1,000〜2,000 ペアにおいて：chrF++ はおよそ 5〜30（上限は高度に定型化されたデータのみ）— 記憶されたフレーズやデータのテンプレートであり、一般的な翻訳ではありません」 |
| `byt5-small` | Google の ByT5-small（3 億パラメータ、バイト列を読み取るため語彙の適合が不要）をファインチューニング | 約 1.2 GB のダウンロード · Apple silicon または CUDA GPU を推奨 | 「forge 自体の試験では、同じペアデータから cpu-tiny よりもはるかに多くを学習しました — それでも dev セット上で運用中モデルと比較測定してください」 |
| `byt5-small-lowmem` | 同じモデル、学習率、長さ制限を、8〜15 GB のメモリを搭載したコンピュータ向けに設定：Adafactor、勾配チェックポインティング、4 ペアのバッチを 4 回蓄積（1 ステップあたり同じ 16 ペア）— ステップあたりのメモリは少なく、時間は長く。8 GB コンピュータでは未計測 | `byt5-small` と同じ | `byt5-small` と同じ |
| `cpu-finetune` | CPU 上でファインチューニングされる、学習済みの小型 Marian/opus-mt モデル。ベースモデルは明示的に指定します（`--base`）。推測されることはありません | CPU のみ · 約 300 MB のダウンロード | 「ベースのターゲット言語がどれほど関連しているかに依存します — dev セット上で cpu-tiny と比較測定してください」 |
| `nllb-600m` | LoRA を適用した NLLB-200 distilled 600M | CUDA GPU（8 GB 以上）· 約 2.5 GB のダウンロード | 「NLLB が関連言語をカバーしている場合、3 つの中で最も強力です。それでも測定してください — 決して推測で済ませないでください」 |

すべてのプリセットは、forge の学習用 extra（`nmt-forge[hf]`）とシード値 42 で学習を行います。
タイムバジェット（時間制限）を設定するプリセットはありません。その値はコミュニティが決めるものです。

- **`--model` を指定しない場合**、`init` は `cpu-tiny` を書き込みます。
- **`--model auto`**（rails が渡すもの）は、forge が学習に使用できる GPU のメモリを読み取ります。Apple silicon 搭載の Mac ではコンピュータのメモリ（GPU と共有）、`PATH` 上の `nvidia-smi` では最大の NVIDIA カードのメモリです。16 GB 以上（またはメモリが読み取れない場合）は `byt5-small`、8〜15 GB は `byt5-small-lowmem`、8 GB 未満は `cpu-tiny` となります。どちらの GPU もない場合は `cpu-tiny` です。検出されたメモリと判定理由が出力され（`chosen: …`）、`--json` 内で `model_choice` として返されます。なお、GPU が実際に動作するかどうかはテストしません。`NMT_FORGE_AUTO_PRESET` で上書きできます（プリセット名を指定する必要があります）。
- **ラウンドで提案されるより強力なモデル**は、現在運用中のモデルが `cpu-tiny` であるプロジェクトにのみ提供されます。`--model auto` がそれを選択する環境では `byt5-small-lowmem`、それ以外では `byt5-small` となり、`auto` が `cpu-tiny` を選択するコンピュータでも同様です。提案の `why` に必要な要件が示されます。

**注意：** プリセットの期待値を約束として説明しないでください。必ず dev セットで測定してください。

## ガードされたループ

各コマンドは `--json` を受け取ります。`--workspace <dir>`（デフォルトは `.forge`）はサブコマンドの前に指定します。Forge は省略形のフラグを拒絶します。

| ステップ | コマンド | 処理内容 | 拒否されるケース |
|---|---|---|---|
| ワークショップ | `nmt-forge init <code> --dir . --pair <src>-<tgt> --model auto` | `.forge/`、`config.json`、`NEXT_STEPS.md` を書き出します | 読み取り不可能な `--pair`、`--base` のない `cpu-finetune` |
| テストセット | `nmt-forge registry add project-test <file> --role test` | ファイルの sha256 を固定し、読み取りログを開始します | テストセットまたは封印セット内の合成行、既に別の内容で登録されている名前（`--allow-rotate` を指定した場合を除く） |
| スクリーニング | `nmt-forge leak-audit <corpus> --clean-to <clean.jsonl>` | 登録済みのすべての開発セット、テストセット、封印セットに対してすべてのペアをスクリーニングし、クリーンなコピーを書き出します | 使用中のファイルの上書き（`--overwrite` を指定した場合を除く）、学習データが残らない結果 |
| 予測 | `nmt-forge prereg new <id> --eval-set <set> --expect "…" --rationale "…"` | スコアリング前にコミュニティによる予測を書き出します | 既存の id、forge または `mt-eval` によるセットのスコアリング読み取り後の書き出し（`--allow-after-reads` が指定され台帳に記録された場合を除く） |
| 開発セット | `nmt-forge split <clean.jsonl> --test 0 --dev <n> --seed 42 --near-dupe 0.6 --max-group <m> --out data/split --register project` | グループ単位で重複のない開発セットの切り出しを行い、`project-dev` として登録します。ガードレール（rails）の `<n>`：スクリーニング済みペアの10分の1（最低50、最大500、ペア数が200未満の場合はその4分の1）([shell](/docs/agents/shell#build-and-test-a-model))。`--near-dupe 0.6` はニアコピー（単語の重複度 ≥ 0.6）を片側に保持します（これは以降のすべてのラウンドのスクリーニングで適用される閾値です）。ガードレールは `--max-group` を開発セットサイズの半分プラス1に設定するため、テンプレートから作成されたファイルでも分割できます | 要求の1.5倍を超えるサイズ、または学習データが元の行の半分未満しか残らない場合 |
| フロア | `nmt-forge floor <word lists>` | 開発セットを辞書から逐語訳し、実行の開発スコアと同じ方法でスコアリングします | 開発セットが登録されていない場合 |
| チェック | `nmt-forge preflight run --config config.json` | 実行時に適用されるすべてのゲートを修正策とともに実行します。いずれかが失敗した場合は終了コード2を返します | — |
| 学習 | `nmt-forge run config.json --detach` | 学習を行い、開発セット上でチェックポイントを選定し、その実行の他のチェックポイントを削除して（[ディスク容量](#disk-space)）、`run-manifest.json`、`run-report.md`、`dev-outputs.jsonl` を含む `.forge/runs/<run name>-<8 hex>/` を書き出します | 既存の実行（同じ設定、学習ファイル、開発セット）、空き容量のないディスク（何かを書き込む前の `disk-room`。`--skip-disk-check` でオーバーライド可能）、実行中のプロセス、テストセットまたは封印セットに漏洩した学習行、学習データに含まれる開発行、do-not-train（学習不可）または隔離対象としてマークされたデータ、`terms.training: not-allowed`、上限を超えた合成データ、参照文に対して短すぎるデコード上限、未知の設定キー |
| テストスコア | `nmt-forge export <run-manifest.json> --prereg <id> --out export/` | 予測に対してテストセットを1回スコアリングします。モデルをパッケージ化し、そのフォルダーの横に `input-words.json`（学習に使用された単語群。サーバーが未見の単語を特定できるようにするため）を配置します ([配信](/docs/agents/serving#what-an-export-holds)) | 事前登録がない場合、または複数あって `--prereg` が指定されていない場合、使用済みの封印セット、`--force` のない空でない `--out` |
| 選択 | `nmt-forge choose <export>/model` | コミュニティによるモデルの選択を記録します | モデルを含む記録済みエクスポートではないフォルダー |
| 配信 | `nmt-forge serve <export>/model --detach` | このコンピューター上でモデルを配信します ([配信](/docs/agents/serving#nmt-forge-serve)) | トークンなしでのループバック外からのアクセス、または `--holders-agreed-by` のないローカル限定モデル |

重要な情報はすべて、ハッシュチェーンされた台帳（`.forge/ledger.jsonl`）に記録されます。登録、目的付きの読み取り、予測、スコア、sealed セットの消費、オーバーライド、監査判定、ベースライン、エクスポート、選択、配信、ジョブの開始と終了が記録されます。実行マニフェストは、各実行の記録となります。

**事前確認ゲート（Preflight gates）：** config（完全な設定ハッシュを出力）、ワークスペースの一致、進行中の実行なし、dev フェンス、学習データ、バックエンドのインストール状況、選択プラグイン、テストのほぼ重複（警告）および dev のほぼ重複（警告）、漏洩監査、学習データ配合（training mix）、生成ヘッドルーム、スケジュールの健全性。

**デコード：** 最終 dev デコード、テスト読み取り（`export`）、運用中モデルによる dev セットの再翻訳、および配信モデルでは、`decode.num_beams` を使用したビームサーチが行われます（`config.json` で別段の指定がない限り 4）。多数のチェックポイントを順位付けするチェックポイント選択では、貪欲法（greedy）でデコードします。エクスポートには `beams_applied` が記録され、`nmt-forge serve` はモデルが測定された方法でデコードします（これを含まない古いエクスポートは貪欲法で配信されます）。

**長さ制限：** モデルは原文の最大 `model.max_src` トークン、その訳文の最大 `model.max_tgt` トークンから学習し、翻訳時には最大 `model.max_src` を読み取り、最大 `decode.max_new_tokens` を出力します（`byt5-small`：それぞれ 320 バイト — ラテン文字で約 320 文字、音節文字で約 100 文字。`cpu-tiny`：入力 256 トークン、出力 384 トークン）。
黙って切り捨てられることはありません。学習ではいずれかの制限を超えたペアをカットする前にカウントし、最終 dev デコードでは入力時に切り捨てられた文と上限で停止した訳文をカウントします。どちらも実行マニフェスト（`length_limits`）に記録され、`status` が修正方法とともに警告します。長い文を分割するか、`config.json` 内で `model.max_src` と `model.max_tgt`（および `decode.max_new_tokens`）を引き上げてください（その分、学習時間は長くなります）。

**注意：** `nmt-forge run` 自体は予測を必須としませんが、rails では先に予測を求めます。予測ステップが完了する前に学習を実行しないでください。

**注意：** `export` はテストセットを読み取るステップです。その実行は、コミュニティの予測がすでに記録された状態で行う重要な節目（マイルストーン）であり、決して日常的な確認のために実行するものではありません。

## バックグラウンドジョブ

`run --detach` および `serve --detach` は、監視付きジョブを開始して制御を戻します。

```bash
nmt-forge jobs                          # every job: state, stage, step, time left, last sign of life
nmt-forge jobs stop <name> --wait 120   # stop it, and wait up to 120 s (at most 180) for it to exit
```

- 状態：`running`、`finished`、`refused`、`crashed`、`stalled`、`deadline`、`interrupted`、`lost`。`lost` は、監視プロセスが記録を残さずに終了したジョブです（再起動後にプロセス番号が別のプロセスに割り当てられた場合など）。
- **このコンピュータ上での学習は一度に 1 つのみ：** 学習ジョブはすべてのプロジェクトにわたり、マシン全体で先着順（`~/.nmt-forge/machine/train-queue`）でキューに入ります。キューに入ったジョブは `running` のまま維持され、`nmt-forge jobs --json` に `queued_behind`（待機対象のジョブ）が記録されます。`status` は `training` で、どのジョブの背後で待機しているかを示し、自動的に開始されます。待機中に停止されると未開始のまま終了し（`interrupted`）、24 時間待機すると終了します（`deadline`）。
- **制限範囲（Bounds）**（学習ジョブ）：起動時に 15 分間応答がない場合（`--startup-minutes`）；10 分またはステップ所要時間の中央値の 30 倍のいずれか長い方の時間進捗がない場合（`--stall-minutes`）；期限は `--deadline-hours`、なければ設定のタイムバジェット × 1.25、それもなければ 24 時間。制限を超えたジョブは停止され、記録されます。
- **停止：** 実行は次のステップで停止します。監視プロセスは 60 秒後に terminate、さらに 10 秒後に kill へとエスカレーションします。
- **経過時間ゲート（The wall-clock gate）**（Hugging Face バックエンド）：ウォームアップ後、forge はステップ時間を計測して実行時間を予測し、予算に収まらない実行を拒絶します（`wall-clock budget exceeded: …`）。予算が設定されていない場合の上限は 24 時間です。
- 学習ジョブの実行中、`status` は `training` となり、rails のステップは `wait` となります。失敗したジョブは、その後のすべてのステータスで警告として表示されます。
- **再開（Resuming）：** 前回の学習ジョブがチェックポイントを保存した後に `lost`、`crashed`、`stalled`、または `deadline` で終了した場合、`status` は `nmt-forge preflight run --config config.json && nmt-forge run config.json --resume --detach` を提示します。これは中断された実行の最新チェックポイント（その重み、新しいオプティマイザ、残りのエポック）から開始される新しい実行であり、マニフェストにはどこから再開されたか（`resumed_from`）が記録されます。手動で停止した後に提示されることはありません。
- デタッチされたジョブは POSIX（macOS、Linux）のみ対応です。

## ディスク容量

学習ではチェックポイントが書き出されます。一度に最大 `model.save_total_limit` 個（`config.json` の指定がない限り4個）で、ByT5-small の場合は1個あたり約 1.4 GB です。これらのルールが導入される前は、ByT5-small プロジェクトの改善ラウンドごとに約 5.6 GB が保持され、過去のラウンドのモデルは自動で削除されず、保存時にディスクが満杯になって実行が異常終了していました。forge の GB は 1024³ バイトです。

- **完了した実行は、選択されたチェックポイントのみを保持します。** チェックポイントが選ばれると、その実行の他のすべての`checkpoint-*`フォルダーは削除されます。それらが再び読み取られることはありません（`export`は選択されたものをコピーし、次のラウンドは使用中のモデルから開始されます）。マニフェストには`checkpoints_pruned`（`removed`、`bytes`、`kept`）が記録されます。`config.json`の`model`ブロック内の`"keep_checkpoints": "all"`は、それらすべてを保持します。それ以外の値は、学習が始まる前、設定が読み込まれた時点で拒否されます（`ConfigError`。ここでは値`x`の場合）:
  `config.model.keep_checkpoints is "selected" (the default: only the checkpoint the run picks stays) or "all", not 'x'`。
- **ロック。** ディスクの空き容量が不足している実行は、何かが書き込まれる前に拒否されます（ガード`disk-room`）。デタッチされた実行は、ジョブが開始される前に即座に拒否されます。見積もり値は、1つのチェックポイントのサイズ（このワークスペースにおける同じベースモデルの以前の実行で保持されているチェックポイント、またはベース自体の重みファイル〈ローカルフォルダーまたはHugging Faceキャッシュ〉）の`model.save_total_limit`倍に、完了用の1 GBを加えたもので、2 GBを下回ることはありません。拒否メッセージには次のように表示されます:
  `[disk-room] this computer has <free> free; training this model needs about <need> (<n> checkpoints of about <size> each while it trains, and room to finish)`
  — または、サイズが不明な場合は *「（モデルにかかわらず、少なくともこれだけの空き容量を維持する必要があります）」* — 続いて
  `why: a disk that fills mid-training loses the run as it saves, and slows the whole computer`、
  そして`nmt-forge tidy`がここで解放できるもの（解放できるものがある場合）、ディスクから他のファイルを移動すること、および`--skip-disk-check`を提示する`fix`が表示されます。
- `nmt-forge run … --skip-disk-check`（`--detach`の有無にかかわらず）は、それでも開始します。マニフェストの`disk_room`には、チェック内容（`free_bytes`、`checkpoint_bytes`〈不明な場合は`null`〉、`checkpoints_at_once`、`need_bytes`）または`{"skipped": "--skip-disk-check"}`が記録されます。**注意。** 見積もりは外れることがあります。チェックをスキップするかどうかは利用者の判断です。
- **`nmt-forge tidy`** は、何にも使われていない以前のラウンドのモデル重みを一覧表示し（各実行のサイズ、合計、空き容量を表示）、何も削除しません。`nmt-forge tidy --yes`はそれらを削除します。使用中のモデル、最新の実行、または使用中のモデルによって置き換えられたモデル（ブラインドレビューシートの下書きに使用されます）が削除されることは決してありません。出力の`Kept:`行には、それぞれが理由とともに示されます。整理（tidy）された実行はその記録（マニフェスト、開発用翻訳、レポート）を保持し、マニフェストには`model_removed`（`at`、`by`、`bytes`、`why`）が追加されます。台帳には`tidy`エントリ（`runs`、`bytes`）が記録されます。整理された実行に翻訳が求められた場合（`compare-runs`がそれで開発セットを再翻訳する場合）、拒否されます:
  `run <name>'s model was removed by nmt-forge tidy on <time> to free disk space — its record stays, its weights do not`。
  **注意。** `--yes`はファイルを削除します。利用者に一覧を示し、同意を得た場合のみ実行してください。
- **`status`の警告** — ワークスペースを保持しているディスクの空き容量が10 GB未満の場合、またはtidyによって5 GB以上解放できる場合に、`warnings`の1行としてレールによって中継されます: *「このコンピューターにはX GBの空き容量があります。何にも使われていない過去N回のラウンドのモデルがY GBを占有しています — `nmt-forge tidy`で一覧を表示し、`nmt-forge tidy --yes`で容量を解放できます（使用中のモデル、最新のモデル、および置き換えられたモデルは保持されます）」*（セミコロン以降はtidyで解放できるものがある場合のみ）。

## 改善ラウンド

モデルの運用が始まると、各ラウンドでは同じ dev セットを使い、より多くのデータで新しい実行を学習させます。

**ラウンドの学習方法：** `champollion improve prepare` は、次の 2 つの方法のいずれかで `nmt-forge round-plan --config config.json`, which rewrites `config.json` を実行し、計画を台帳に書き込みます（`round-plan`）。

- **運用中モデルから継続**（モデルフォルダを `init_from`）：これまでの全センテンスに対して、忘却を防ぐために古い文も含めて学習率を半分にして 4 パス（エポック）行います。最初から学習するよりもはるかに短時間で済みます。完全な設定は `config.json` の `model_full` の下に保持されます。
- **最初から学習**：完全な設定を復元して学習します。まだ運用中のモデルがない場合、モデルが変更された場合（`use-model`。これは `model_full` も削除します）、学習センテンスから語彙を構築する `cpu-tiny` の場合（数分で学習が完了します）、アダプタ（LoRA）モデルの場合、および短い継続学習の繰り返しによるドリフトを防ぐための 4 ラウンドごとに行われます。

`prepare` は計画とその理由を表示し、`improve/round-<k>/prepared.json` に `training`（`mode`、`epochs`）を記録します。いずれにせよ、新しい実行は同じ開発文において使用中のモデルと比較評価されます。その後、以下のようになります（1、3、4 は forge のアドバイザーが指定する状態であり、2 はガードレールによって記録されます）：

1. **`improve-compare`** (`auto`): `nmt-forge compare-runs <in-use
   run-manifest.json> <new run-manifest.json>` — 開発セット上で文ごとにペアリングされた2つのモデル。開発文が50文未満の場合、スコアにかかわらず判定は **too-few** となります: *「開発文が少なすぎて判断できません: 50文未満では、差の大きさにかかわらず、偶然によるものと確実に区別できません」*。50文以上の場合: 対応のある検定の p < 0.05 **かつ** 差の95%信頼区間がゼロを上回る場合にのみ **better**、p < 0.05 かつゼロを下回る場合は **worse**、それ以外は **no-change** となります。すべての判定は、その開発セットが確実に示せる最小の差を伝えます。テストセットが読み取られることは決してありません。異なる開発セットでの実行、保存された開発用翻訳がない実行、または新規実行以降に変更された開発セットの場合は拒否されます（`improve-loop`）。
2. **話者の判定**（開発セットで判断できなかった場合）。採用されなかったラウンドのモデルは、次のレビューシートの下書き行の半分をブラインドで作成し（下記の`draft-newer`）、`champollion improve marks` が話者の集計結果をforgeに記録します:
   `nmt-forge speaker-verdict --newer <run> --in-use <run> --newer-right <n> --newer-judged <n> --in-use-right <n> --in-use-judged <n> --json`。
   Forgeは、判定が **too-few** または **no-change** の場合にのみこれに基づいて動作します。プールされた2比率の検定（両側5%、|z| > 1.96）によって`clear`が算出されます:
   `newer`、`in-use`、または`neither`。台帳の`improve-speaker`エントリには、2つの実行名、4つのカウント、`z`、および`clear`が保持されます（カウントのみ）。0未満のカウント、判定数を超える正解数、および判定された下書きのないモデルは拒否されます。そのメッセージテキストは次の通りです: *「同じ訪問時にブラインドで採点した結果、話者は新しいモデルについてB文の新しい文のうちA文（P%）を正解とし、使用中のモデルについてD文のうちC文（Q%）を正解としました」*、続いて *「これらの文において新しいモデルのほうが明らかに優れています — forgeはこれを採用することを提案します」*、*「これらの文において使用中のモデルのほうが明らかに優れています — 現行のまま維持されます」*、または *「これらの文において明確な差は見られません — 使用中のモデルが維持されます」*。
3. **`improve-promote`** (`confirm`): **better** の場合、またはその実行における最新の`speaker-verdict`が`clear: newer`を示している場合の **too-few** や **no-change** の際に実行されます（**worse** では決して実行されません）。これは提案であり、判定だけで勝手に採用されることはありません。人々の同意（yes）が得られると、テストセットを読み取ることなく新しい実行をエクスポートし（`--no-eval`）、選択されたものとして記録し（`choose`）、実行中のサーバーを停止して同じポートで新しいモデルを提供（serve）します。その`export`と`choose`のみが、モデルを採用したとみなされます。それまでは、ラウンドレポートに *「測定可能な改善: 採用されていません — 人々によって選択されていません」* と表示され、その進捗、予測、および過学習チェックからモデルは除外されます。話者の採点がある場合、その`why`には集計カウントと *「明確な差: 家族が必要としている文において、新しいモデルのほうが優れています」* が追記されます。次のシートでは、下書き行の半分が置き換えられた旧モデルから生成されるため、話者は昇格の妥当性をブラインドで確認できます（下記参照）。
4. それ以外の場合は使用中のモデルが維持され、次のラウンドが始まります — ただし、モデルの前回の変更以降の直近2回のラウンド判定がいずれも **no-change** または **worse** であり、かつ`cpu-tiny`が使用されている場合を除きます。モデルの前回の変更とは、台帳内の最新の`model-change`（プリセットの切り替えまたは`not-now`）または`choose`エントリ（話者の採点による昇格を含め、人々が採用した任意のモデル）を指します。**too-few** のラウンドは判定されたラウンドとはみなされません。直近2回のうちいずれかがtoo-fewである場合、提案は行われません。
   その場合、**`improve-stronger-model`** (`ask_user`) が行われます:
   `nmt-forge use-model <preset> --config config.json --answer yes`（または`not-now`）、プリセット`byt5-small`または`byt5-small-lowmem`（[モデル](#models)）。回答スロットは`try_it`です。`yes`は設定のモデルを書き換え（人々の時間枠の予算を維持）、次のステップでそれを学習します。`not-now`は何の変更も行いません。どちらも台帳に記録され（`model-change`）、提案はこのようなラウンドがさらに2回行われた後にのみ再度行われます。
   MCP経由では、ここでの「not now」は回答`try_it: "not-now"`となります。このステップでは`declined: true`は拒否されます（[MCP](/docs/agents/mcp#not-now)）。その`why`が、文を増やしても役に立たないと述べることは決してありません。ラウンドの向上が見られないほど開発セットが小さすぎる場合は *「小さな向上が隠れている可能性があります」* となり、それ以外の場合はラウンドによって *「開発文で確認できる変化（約X chrF++ポイント以上）はありませんでした: ラウンドによる増加分がそれ未満であるか、または変化がない可能性があります」* となります — 曲線の頂点付近では、1ラウンドあたりの向上は約0.5 chrF++ポイントであり、200の開発文で確認できる範囲を下回ります。
   **注意。** `--answer`のデフォルトは`yes`です。常に人々の回答を明示的に渡してください。

ラウンドの残りの部分はガードレールが進行を管理します（`champollion improve …`）：`nmt-forge wishlist` は最も役立つ内容のシートを書き出します（デフォルトで40個のプロンプト、少なくとも4分の1は自由記入用に空けておきます。モデルが一度も見たことがない単語については、それぞれ異なる内容を表現する文を2〜3文求めます — 学習で1回しか見られなかった単語はほとんど習得されません ([測定](/docs/agents/measurement#what-the-wishlist-steers-on))）。`nmt-forge analyze` は開発セットの chrF++ を文の種類ごとに内訳を表示し、`nmt-forge grow-dev` は話者の練習文を同じ名前で開発セットに追加します（すでに開発セットにある行や、テストセットまたは封印セットに原文がある行は決して追加されません）。文の種類がウィッシュリストの方向性を決定するのは、そのスコアが他より明らかに低い場合のみです ([測定](/docs/agents/measurement#what-the-wishlist-steers-on))。
`nmt-forge draft-newer`（`champollion improve sheet` によって実行）は、次回のレビューシートの行のランダムな半分をもう一方のモデルで印を付けずに下訳し、話者が両方のモデルをブラインドで判定できるようにします ([測定](/docs/agents/measurement#the-speakers-marks))。使用中でない最新の学習済みモデル（そのラウンドが本番採用されなかった場合）、または昇格後は、使用中のモデルによって置き換えられたモデルが対象となります。その `--json` にはどちらであるかが示され（`relation`: `newer` または `replaced`。他のモデルがなくすべての行が使用中のモデルによるものである場合は `null`）、`other`、`in_use`、それぞれの背後にある学習ペア数（`other_pairs`、`in_use_pairs`）、および `n` が含まれます。台帳の `draft-newer` エントリにも同様に記録されます。ラウンドをどのように中継・伝達するかについては、[コーチング](/docs/agents/coaching) を参照してください。

## 合成データと逆翻訳

- `nmt-forge synth <pack> --out <file>` は言語パックのジェネレーターを実行します。Forge にはパックが同梱されていません。各行は検証され、`synthetic: true` のスタンプが付与されます。
- 合成ファイルは、`config.json` 内でタグ付きレーンとして学習されます（`data.synthetic`、`{"path", "tag": "<synth>"}`）。同一種類が 15% を超える場合、設定で `mix.synthetic_sample` が指定されていない限り実行は拒絶されます。`nmt-forge sample --cap 0.15 --key kind` は上限付きサンプルを抽出します。
- **逆翻訳には専用のコマンドがありません。** ライブラリ関数（`nmt_forge.training.backtranslation.backtranslate`）として提供されています。ユーザーが逆方向モデルを用意すると、まず登録されたすべてのセットに対して単一言語テキストをスクリーニングし、出力を `<bt>` としてタグ付けします。その後、その出力は合成レーンとして学習されます。品質フィルターは適用されません。`config.data.monolingual` は拒絶されます。
- **注意：** 単一言語テキストも他のデータと同様にコミュニティのデータです。そのサイドカー利用規約が適用され、逆方向モデルがホスト型 LLM である場合はプロバイダーにデータが送信されます（[データ規則](/docs/agents/data-rules)）。

## 症状 → 原因 → 対処法

| 症状 | 考えられる原因 | 解決策 |
|---|---|---|
| `cpu-tiny` の開発セットでのスコアが 5〜30 chrF++ の間である | 設計上性能が控えめであるため: 学習データに似た定型句向けのフレーズ集として動作します | 実際のペアを増やす。Apple silicon または GPU 環境では `byt5-small`（`nmt-forge use-model byt5-small`。GPU が 8〜15 GB の場合は `byt5-small-lowmem`） |
| 「テンプレートでは良いが、実際のテキストでは悪い」 | ルール R7（転移プラトー）: 開発セットの損失（dev loss）が最後のチェックポイントの前に底を打ち、5%以上上昇した。開発セットの chrF++ の動きにかかわらず、このような上昇があれば発動します — 開発スコアと併せて確認してください | 実際のペアを増やす。エクスポート時ではなく `nmt-forge lint <run-manifest.json>` によって示されます |
| スコアが良すぎるように見える | 学習データ内にテストのコピーまたはニアコピーが存在する。またはテスト行の大部分に学習データの「双子（twin）」が存在する（R4-recall-not-translation、半分以上） | `leak-audit --drop-test-twins` で双子行のないファイルを作成する。双子行がある場合とない場合の両方のスコアを報告する |
| 2つのモデル間の差が小さい | 信頼区間が広い（R5-low-power、信頼区間が8ポイントより広い） | `nmt-forge compare`（対応のある検定）。ラウンドの場合は `compare-runs`。開発セットを拡充する |
| ラウンドで「too few dev sentences to tell（判定するには開発文が少なすぎます）」と表示される（`too-few`） | 開発セットが50文未満: この規模では比較による判定ができません | 修正の必要はありません: 次のシートで両方のモデルの下訳がブラインドで混ざり、話者の判定によって決定されます。開発セットが50文になるまで、シートの2行に1行が練習行になります |
| ラウンドで「no measurable change（測定可能な変化なし）」と表示される | 開発セットが小さすぎてラウンドの向上が見えない | 話者の練習文から開発セットを拡充する（`champollion improve prepare` によって駆動される `grow-dev`） |
| 学習が拒否される: `[disk-room] this computer has … free` | ディスクに実行のチェックポイントを保存する空き容量がない | `nmt-forge tidy` で過去のラウンドのモデルが解放できる容量を一覧表示し、利用者の承諾を得て `nmt-forge tidy --yes` を実行する。または他の場所で空き容量を確保する。利用者が「見積もりが誤っている」と判断した場合にのみ `--skip-disk-check` を使用する |
| 実行が辞書フロアを超えない | 学習によって単語リスト以上の内容が何も学習されなかった | ペア数を増やす。フロアのカバレッジを確認する。コミュニティの人々にその旨を伝える |
| 開発セットが飽和している | 信頼区間の下限が上限値の99%に達している | より難度の高い開発セットを用意する。スコアはこれ以上向上しません |
| 学習前に拒否される | 上記の「学習」行を参照。`preflight run` が失敗した各ゲートとその修正案を表示します | 修正案に従う。学習用の追加機能（extra）が不足している場合: `uv tool install --reinstall --python 3.12 'nmt-forge[hf]'`（または forge 自身の Python に `pip`） |
| 実時間（ウォールクロック）の制限で停止した | 予測される実行時間が予算（未設定の場合は24時間）を超過している | より小さいモデルにするかエポック数を減らす、またはコミュニティが設定した予算にする（`model.time_budget_hours`） |
| バックグラウンドジョブが失敗した | `nmt-forge jobs` に `crashed`、`stalled`、`deadline`、`lost`、または `refused` と表示されている | `.forge/jobs/<name>/` 内の `stderr.log` を確認して修正し、再度学習するか、`status` が `--resume` を指定している場合は最後のチェックポイントから再開する |
| 学習が待機状態のまま開始されない | このコンピューターで別の学習が実行中であり、このジョブはその背後にキューイングされている（`queued_behind`） | 待機してください: 自動的に開始されます。別の学習を開始しないでください |
| 長い文の途中で途切れて出力される | 長さの上限: `status` が件数とともに警告を表示する（学習で切り捨てられたペア数、入力時に切り捨てられた開発文数、上限で停止した翻訳数） | 長い文を分割する。または `model.max_src`、`model.max_tgt`、`decode.max_new_tokens` を増やす（学習時間を延ばす） |
| 単語が未知の断片（`cpu-tiny`）として出力される | 語彙が学習行からのみ学習されているため | それらの単語を使用するペアを増やす。またはバイト単位で読み取る `byt5-small` を使用する |

## 失敗の分類体系

Forge は、学習プロジェクトが自らを欺いてしまうパターンのカタログをもとに構築されました。要約すると以下のとおりです（「強制」はツールが操作を拒絶することを意味します）：

| 分類 | 失敗例 | コードでの対応 |
|---|---|---|
| 漏洩（Leakage） | 学習セットに正解が含まれている、ほぼ同一のコピー、分割をまたぐ言い換え、連鎖テンプレート | 強制（漏洩監査、分割ガード）。テンプレートの同類文（Template siblings）は保持されカウントされます |
| dev/テスト汚染 | テストセットでのチェックポイント選択、sealed セットの 2 重消費、予測のないテストスコア測定、読み取り後の予測 | 強制（dev フェンス、評価台帳、事前登録） |
| トークナイザーと正書法 | 表記文字を出力できないトークナイザー、混在した綴り表記法 | トークナイザーについては未チェック。混在表記法は設定で指定されている場合のみ lint で検出 |
| 合成データ | 合成配合の過剰適応、合成データ過多の実行を早期終了（early stopping）が打ち切る、崩壊、自らの誤りを取り込む逆翻訳 | 早期終了の最低基準は強制。その他は lint またはタグ |
| 網羅率 | 特定のレジスター（位相・待遇表現）の単語の不足 | プラグインが網羅率を報告する場合に lint で検出 |
| 測定 | 信頼区間よりも小さい差、単一の不透明な数値、エンジン外での評価指標計算 | 強制：すべてのスコアは信頼区間を伴い、エンジンから取得されます |
| デコード | 切り捨てられた出力、出力ではなく loss に基づくチェックポイント選択 | 強制：デコードヘッドルーム、生成指標に基づく選択、長さによる切り捨てのカウントと警告 |
| プロセス | 未知の設定キー、do-not-train データ、暴走した実行 | 強制 |

現時点でコード化されていない既知の課題：トークナイザーの網羅率、逆翻訳の品質、レジスターによる切り捨て、正解データ（gold）と合成データの比率、シード間のばらつき。

## プログラム向け出力

`--json` は、標準出力に正確に 1 つの JSON ドキュメントを出力します。拒絶時は `{"error": {"type", "guard", "message", "why", "fix", "how_to_get", "text"}}`
となり exit 2 で終了します（分割および dev フェンスによる拒絶の場合は `details` が追加されます）。exit 1 は予期せぬクラッシュです。`nmt-forge run` は `RUN EXIT <code>`（0、1、2、または 130）で終了します。`run --detach` はジョブドキュメントとともに 0 を返します。`nmt-forge status --json` is `{"snapshot", "advice": {"state", "next_command", "why", "ready", "blockers", "warnings", "answers"}}`。
