# 人々へのコーチング

レールが測定し、あなたが伝えます。人々が自分たちの翻訳機について耳にする情報の多くはあなたを通じて届くため、その伝え方自体も仕事の一部です。このページでは、その伝え方について説明します。ラウンドレポートの内容、その伝え方、協力できる時間の尋ね方、そして使うべき言葉についてです。

その基礎となる規則は[コントラクト](/docs/agents/contract) §5に記載されています。真実のみを伝えること、すべての注意書きを一言一句漏らさず伝えること、プロセスを約束し品質は決して約束しないこと、すべての数値に単位と測定対象のセットを明記すること。

## ラウンドレポート

各改善ラウンドは`champollion improve report`（ジャーニーの`improve-report`ステップ、モード`auto`）で終了します。これは`improve/round-<k>/report.json`を書き込み、4つの部分を出力します。`--json`も同じオブジェクトを出力します。

| フィールド | 内容 |
|---|---|
| `round` | 進行中のラウンド：forgeが判定したラウンドの次のラウンド |
| `progress` | 順番に並んだ行：話者の判定結果の傾向、次に各ラウンドの判定結果（シートに別のモデルのドラフトが混ざっていたラウンドでは、その後にブラインド比較が続く）、そして開発セットに対する各ラウンドの判定 |
| `checks` | 数値が示せることと示せないことに関する警告 |
| `projection` | 「実用レベル」に達するまでに必要な追加の学習文のおおよその見積もり（倍増ごとにカウント、範囲付き）— または見積もりが存在しない理由 — あるいは判定が2ラウンド分揃う前の`null` |
| `projection_numbers` | 数値としての同じ見積もり：`more_sentences`、`range`（学習文`[fewest, most]`文。検証によって上限を特定できない場合は`most`が`null`）および`speaker_hours` — または予測がない場合は`null` |
| `actions` | 次に行うべき1〜4つのこと |

これはラウンドで保持される記録（各ラウンドでの話者の`marks.json`およびforgeの`improve-compare`判定）のみを読み取り、件数とパーセンテージを出力します。文を出力することは決してありません。

### 各行の意味

**話者による判定 — 最も重要な指標。** 各ラウンドで、使用中のモデルが家族の書いた文のドラフト（下書き）を作成し、話者が各ドラフトを`Y`（正解）、`N`（不正解、正しい言い方を添える）、または`?`（不確か）と判定します。正解率は、`Y`または`N`と判定されたドラフト全体に対して集計され、95%のウィルソン信頼区間が付きます。

> ラウンド1: 話者は新しい文のドラフト24件中9件を正解と判定しました — 38%（95%の範囲: 21%〜57%）。

これらは、どのモデルも学習していない段階で作成された新しい文であるため、標本外の測定値となります。シートに別のモデルの下訳が混ざっていたラウンドでは、これらの件数は現在使用中のモデルの行のみのものです。再表示された行（後述）がここに含まれることはありません。

**再表示された行。** ラウンド2以降、約10行に1行は、話者が以前のシートですでに判定した下訳が未判定の状態で再度表示されます。シートの冒頭には、「*以下の数行は、意図的に以前のシートから再度掲載されています。初めて見る文として、新たに判定してください。判定の一致度は、判定結果の信頼性を測る目安となります。*」と記載されており、どの行であるかは示されません。`improve marks`には、「*再表示された行：話者はJ行中A行を以前と同じように判定しました（P%）*」と、判定が反転したそれぞれの内訳とともに出力されます。これらの行がラウンドの正解率に加算されることはなく、再学習に用いられることもありません。話者にかかる負担は1行あたり約10秒です（[測定](/docs/agents/measurement#the-speakers-marks)）。

**ブラインド比較。** シートのドラフトのランダムな半分を、印を付けずに2つ目のモデルが作成し、話者はどちらがどちらかを知らずに両方を判定します（[測定](/docs/agents/measurement#the-speakers-marks)）。2つ目のモデルは、まだ使用されていない最新のモデルです。昇格後の訪問では、新しいモデルに置き換えられた元のモデルになります。レポートには次のような行が追加されます。

> ラウンド2: ブラインド比較（新しい文）: 使用中のモデルは12件中5件（42%）が正解と判定され、より新しいモデル（未使用）は12件中7件（58%）が正解と判定されました — 24文において明確な差はありません。

昇格後は、*「直近で使用開始されたモデルは…で正解と判定され、置き換えられたモデルは…」*と表示されます。末尾は次の3つのいずれかになります（有意水準5%の2標本比率の検定）：より新しいモデルの場合は、*「新しいモデルのほうが、家族が必要とする文において明らかに優れています」*または*「使用中のモデルのほうが明らかに優れています」*。昇格後の場合は、*「新しいモデルのほうが、家族が必要とする文において明らかに優れています」*または*「置き換えられたモデルのほうが明らかに優れていました — 新しいモデルは家族が必要とする文で役に立っていません」*。あるいは*「N文において明確な差はありません」*。一方のモデルの判定行数が少なすぎる場合は、*「比較するには一方のモデルの判定行数が少なすぎます」*と表示されます。

**傾向。** レポートでは、次の3つがすべて満たされた場合にのみ、上昇を*真の進歩*と呼びます。

- 最後のラウンドの範囲が、最初のラウンドの範囲より完全に上にあること（最後のラウンドの下限が、最初のラウンドの上限より上にあること）。
- その間にいずれかのラウンドのモデルが実用化されたこと — 人々によって選ばれたもの（forgeの`export`および`choose`の記録）。**better**（改善）の判定と人々の承認、話者のブラインド評価、または人々の独自の選択によるものです。**better**の判定だけではカウントされません。そして
- 同じ訪問時のブラインド評価において、話者が新しいモデルを正解とした頻度が、置き換えられたモデルよりも明らかに高かったこと（各昇格後のチェックをプールしたもの。有意水準5%の2比率検定）。

3つ目の条件があるのは、話者の採点基準がブレる（ドリフトする）可能性があるためです。ラウンドを重ねるごとに採点が甘くなる話者は全体の割合を押し上げますが、1回の訪問の中であれば両方のモデルに同じように影響します。下訳の 10% を誤って採点し、ラウンドごとに甘くなる話者を想定したシミュレーションでは、モデルが改善し得ない 1,600 件のレポート中、練習セットが偶然誤って昇格させた 106 件が「真の進展」として読み取られてしまいました。ブラインド確認を含めるとこれは 3 件に減り、50 文の基準と話者の判定を取り入れて再実行した場合も（練習セットが 30 文から始まる実行を含め）、1,600 件中最大で 3 件に抑えられました。

昇格はあったもののその検証がない状態での上昇は、*「まだ真の進歩とは見なされません: ドラフトの判定基準が甘くなった可能性もあります」*と出力され、検証の件数が付記されるか、次のシートに2つのモデルのドラフトが混ざることが伝えられます。同じモデルを使用し続けた状態での上昇は、*「進歩とは見なされません」*と出力されます。モデルではなく、文または判定基準が変わったためです。範囲内での上昇は、*「上昇していますが、まだ不確実性の範囲内です」*と出力されます。

**開発セットの判定。** Forgeは、同じ開発（練習）用の文を用いて、新しいモデルと使用中のモデルを文ごとに比較します。

> ラウンド 1: 同じ 50 文の練習（dev）文において、chrF++（0〜100、確認済み翻訳との一致度）は使用中モデルの 22.0 に対し新モデルは 24.1 — 測定可能な変化なし: 不採用（50 文では約 5.8 ポイント以上の差しか確実に現れません）。

行末の表示は、判定結果および人々がそのラウンドのモデルを選んだかどうか（forgeの`export`および`choose`の記録）によって決まります — 判定だけでは何も実用化されません。

| 判定 | 未選択 | 選択済み |
|---|---|---|
| **better** | *測定可能な改善：実用化されていません — 人々が選択していません* | *測定可能な改善：実用化済み* |
| **worse** | *測定可能な悪化：未使用* | *測定可能な悪化 — 実用化済み …* |
| **no-change** | *測定可能な変化なし：未使用* | *測定可能な変化なし — 実用化済み …* |
| **too-few** | *練習文が少なすぎて判断不可（50文未満）：話者のブラインド評価で決定* | *練習文が少なすぎて判断不可（50文未満） — 実用化済み …* |

「実用化済み …」の続きは、forgeにそのモデルの話者判定として`clear: newer`（`improve-speaker`）がある場合は*「話者のブラインド評価に基づく」*となり、それ以外の場合は*「人々の独自の選択による」*となります。`champollion improve status`も同じ文言を使用します。各ラウンドの行は*「· 練習（dev）文での新モデル：…」*で終わります。判定ルールは[測定](/docs/agents/measurement#comparing-two-models)に記載されています。

**検証。**

- *過学習。* 使用中のモデルの開発セットchrF++がラウンド間で3ポイント以上上昇したにもかかわらず（直前ラウンドの新しいモデルは、コミュニティの人々がそれを選択した時点で初めてカウントされます）、話者による正解判定の割合の上昇が2ポイント以下であった場合、レポートには、その伸びは練習用の文だけに特化したものである可能性があり、話者の判定を信頼すべきであると記載されます。
- *向上を捉えるには開発セットが小さすぎる場合。* 開発セットが確実に示せる最小の差がchrF++で3ポイント超（または不明な場合で50文未満）である場合、レポートには「測定可能な変化なし」は開発セットの限界であり、そのラウンドで何も成果がなかったことの証明ではないと記載されます。
- *判定の信頼性。* 全ラウンドを通じて、再表示された行が10行判定されると、次のように表示されます。「*話者は再表示されたJ行中A行を以前と同じように判定しました（P%）：約E%の判定がランダムに逆へと振れており、正解判定の割合全体が50%に向かって引き寄せられます — 予測ではこれを考慮しています。*」以前は誤りだった下訳が今回は正解と判定された件数が、その逆を明らかに上回る場合（有意水準5%の符号検定、6回以上の反転）、レポートには「*判定が寛容になってきている可能性があり、正解率の上昇にはそれが表れていない場合があります*」と追加されます。10行未満の場合：「*これまでに判定された再表示行はN行です — 話者自身の判定誤差は10行から推定されます。*」

**予測。** 上昇が真の進展であり（上記の3つすべてを満たす）、正解と判定された割合がまだ80%未満の場合にのみ行われます。80%とは、家族が必要とする文に対してモデルが*機能している*ことを示すrails上の基準です。学習曲線は学習用の文が2倍になるごとにおよそ一定の幅で上昇するため、新しいモデルとそれが置き換えた旧モデルとの比較についての話者のブラインドチェック（両モデルの学習ペア数が記録されています）からそのステップ幅を読み取ります。そして、正解判定率80%に達するまでにあと何文の学習文が必要かを範囲とともに示し、1文あたり約70秒（執筆に1分、判定に10秒）として話者の所要時間も算出します。この範囲はチェック結果が許容する範囲（95%）をカバーしており、再表示された行が10行判定された後は、この話者自身の判定において「真に80%正しい」がどの位置に来るかも考慮されます。その場合、本文には「*真に80%正しい下訳は、この話者の判定では約T%の確率で正解と判定される可能性があります — 範囲にはこれが考慮されています*」と表示されます。それ以前は、「*（話者自身の判定誤差はまだ考慮されていません：判定済みの再表示行が少なすぎます）*」と表示されます。推定値そのものは通常の80%のまま維持されます。件数は有効数字2桁に丸められます。チェック結果から範囲を絞り込めない場合、レポートには「*あと何文必要になるかはまだ判断できません*」と表示されます。それ以外の場合は、予測が出せない理由が記載されます。例えば、「*話者のブラインドチェックでは、新しいモデルが旧モデルを上回っていることがまだ示されていないため、上昇はモデルではなく判定によるものである可能性があります*」などです。レポートと同様に、これは大まかな目安であることを必ず伝えてください。シミュレーションでは、真の件数の2倍以内の範囲に収まった割合は、1ラウンド400文で69〜78%、800文で53〜56%であり、真の件数が推定範囲内に収まった割合は89〜94%および76〜80%でした（1ラウンド800文の場合、話者の判定を範囲に考慮する前は51〜54%でした）。これ以前の直線補間では、400文で5%でした。話者の判定誤差をもとに、モデルが「すでに機能している可能性がある」とは絶対に言わないでください。レポートもそう言っていません。シミュレーションにおいて、その指摘は正しかった回数1回に対して2〜3回誤っていたためです。

**アクション。** 優先度順に最大4つ提示されます。今ラウンドのシートを採点するか、まだ不足している文を書く（1ラウンドあたり20文）。ブラインド比較で新モデルが明らかに優れていると判明した場合、*「練習セットでは示せなかったものの、このラウンドは確実に効果がありました」*と伝え、そのまま作業を続け、練習セットを増やすことで次の判定で差を確認できるようにする。昇格によって置き換えられた以前のモデルの方が明らかに良いと話者が採点した場合は、以前のモデルに戻すかどうかを人々に尋ね、練習セットを自分たちが必要とする文により近づける。練習セットが小さすぎてラウンドの成果が確認できず、かつ200文未満の場合は練習セットを増やす（*「各シートの2文に1文は下訳がありません — 話者がその言い方を書き、練習セットに追加されます（現在は31文。50文でラウンドの判定が可能になり、200文で約3ポイントの伸びが確認できるようになります）」* — 50文以降は「4文に1文」）。成果のないラウンドが2回続いた後の対処（下記参照）。話者が確保できると回答した時間が少なすぎるように見えること。そして、正解率の下限が 70% に達した時点で、ロックされたテストセットでの確認（事前の予測を記入した上で行う）。

**向上が見られないラウンドが2回続いた場合** — 直近の2回の判定がともに**no-change**または**worse**であり（**too-few**のラウンドはどちらとも言えないためカウントされません）、その間にモデルが実用化されていない場合です。forgeは、より強力なモデルの提案に対しても同じようにカウントします。練習セットでそのラウンドの通常の向上を確認できる場合、アクションには次のように表示されます。*「この練習セットで確認できる向上（約X chrF++ポイント以上）のないラウンドが2回続きました。各ラウンドによる向上幅がそれより小さいか、あるいは変化がないかのどちらかですが、どちらであるかは判断できません。より迅速に進める方法：コンピューターでトレーニングできる場合はレールが提案するより強力なモデルに切り替えるか、モデルが間違えた種類の文をさらに追加してください。」*（Xは判定で確認可能な最小差です）。確認できない場合は、作業を継続するよう指示されます。文を増やしても効果がないと言ったり、それをほのめかしたりしては絶対にいけません。曲線の頂点付近では、1回のラウンドでの向上は約0.5 chrF++ポイントとなり、これは200の練習文で示せる範囲を下回ります。模擬ラウンドでは、モデルが実際に改善している最中にもかかわらず、以前の文言「同じような文を増やしても効果がない可能性があります」が1,200件のレポート中98件で表示されてしまっていました。

### どのように伝えるか

1. **まず進展から伝える。** 話者の採点において、何が向上したかを真っ先に伝えます。
2. **すべての数値に単位と対象セットを添える。** 単に「38%」ではなく、「話者が確認した新しい24文のうち9文が正解でした — 38%」と伝えます。単に「24.1」ではなく、「50文の練習文で100点満点中 chrF++ 24.1」と伝えます。範囲はツールの確信度を表すものであり、2つの結果ではありません。「21%から57%の間 — 24文では、ツールがこれ以上確信を持つことはできません」。
3. **確認結果をわかりやすく伝える。** レポートに警告がある場合は、その警告内容を伝えます。
4. **次のステップを実行可能な行動として示す。** 各アクションを、指定されたファイル名とともに、コミュニティの人々に向けた文に書き換えます。
5. **すべての注意事項を一言一句そのまま伝える。**

**測定された成果を励ます。** 正解と判定されたドラフト、範囲を超えた上昇、新しいモデルの使用開始：これらは温かく伝えてください。最初の翻訳は祝福に値します。レポートが進歩と呼んでいない数値を決して祝わないでください。

**「測定可能な変化なし」— 率直かつ親切に伝える。** そのラウンドが無駄だったという意味ではありません。その意味を伝えてください。この文数の練習文では、おおよそこの程度の差しか現れないこと、より小さな改善が隠れている可能性があること、使用中のモデルは引き続き使用されること、話者が修正した文は今後も無駄にならないこと。その上で、次のステップを伝えます。

**「練習文が少なすぎて判定不能」であり、「変化なし」ではない。** 練習文が 50 文未満の場合、2つのスコアがどうであれ比較による決定は下されません。これは新モデルについての評価ではありません。代わりに何が起きるかを説明してください。使用中のモデルが当面維持されること、次のシートには新モデルの下訳がラベルなしで混ぜられ、話者の採点によって決定されること、シートの2行に1行は下訳がなく、それらの文が練習セットに追加されていき、やがてラウンドの判定ができるようになること、を伝えます。

**ブラインド比較 — 両方の件数と、それが意味すること。** 両方のモデルの件数と、レポートの結びの文言をそのまま伝えます。新モデルが明らかに優れている場合は、レポートの記述どおりに伝えてください（練習セットでは示せなかったものの、このラウンドは確実に効果があったこと、そしてそれが新しい文に対する話者自身の判定であること）。そのモデルに対する判定が **too-few**（データ不足）または **no-change**（変化なし）であった後、明確な好みが示された場合、forge はそれを実戦投入候補として提示します。`improve marks` には *「forge が記録しました: 新しいモデルの実戦投入を提案します（まずコミュニティの人々の同意が必要です）」* と表示され、その提案は `improve-promote` ステップ（下記参照）として現れます — 実行する前に必ず確認してください。**worse**（悪化）判定の後は提示されません。昇格の後、レポートが上昇を真の進展としてカウントできるのはこの確認があるためです。置き換えられたモデルの方が明らかに優れていたと示された場合は、以前のモデルに戻すかどうかを人々に尋ねてください — 同意なしに戻してはなりません。24 文での「明確な差なし」は、言葉通りの意味です。
**注意。** 採点を読み取る前に、どの行がどちらのモデルによるものかを話者に決して伝えてはなりません。

**再表示された行 — その目的。** レポートに記載されている通り、一致度をその件数とともに伝えてください（「話者は再表示された20行中17行を以前と同じように判定しました — 85%」）。そしてそれが何のためのものか、つまり判定結果の信頼性を測るためのものであることを伝えてください。これはシート上で予告されており、話者を隠れて試すものではありません。レポートにある通り、ランダムな誤差についても伝えてください。すなわち、約E%の判定がランダムに逆へと振れ、正解判定の割合全体が50%に引き寄せられること、そして予測ではそれが考慮されていることです。レポートに「*判定が寛容になってきている可能性があります*」とある場合は、責めることなく率直に伝えてください。その場合、割合の上昇はモデルの成果ではなく、判定によるものかもしれません。**注意。** どの行が再表示されているか、あるいは以前どう判定したかを話者に伝えてはいけません — シートには、数行が再表示されることだけが記載されています。

**モデルが一度も見たことのない単語。** `sync`が、キーに*「モデルが学習で一度も見たことのない単語が含まれています — どれほど流暢に見えても誤訳されている可能性が極めて高いです」*と警告している場合は、率直に伝えてください。それらの行は、どれほど自然に読めても間違っている可能性が極めて高いこと、話者が確認すべきであること、あるいは次のラウンドの文でそれらの単語を学習させることができることを伝えます。警告に記載されているとおりにキーの名前を挙げてください。あなた自身がその単語を目にすることはありません。利用者はモデルの試用ページで各行の下にそれらの単語を確認できます。人工のテスト言語による根拠として、モデルが見たことのない単語を含む文が正しかった回数は358回中0回でした（[サービング](/docs/agents/serving#words-the-model-never-saw)）。

**ウィッシュリストの単語。** 「一度も見たことのない単語」セクションでは、*「必要な単語ごとに、それぞれ異なる内容を表す2〜3文」*を求めています。多くの単語を1度だけ学習させるよりも、少ない単語をそれぞれ数文の中で学習させるほうがモデルの学習効率が高まります。そのように伝えてください。人工のテスト言語では、学習で1度だけ見られた単語が正しく翻訳された割合は27〜29%でしたが、2〜4回見られた単語では63〜95%でした。また、学習文3,200文において、最も多くの新しい単語が含まれるように選ばれた文で学習したByT5-smallは、500件のホールドアウト文のうち意味が正しかった割合が39.4%にとどまり、日常的な文での53.4%を下回りました — 話者の所要時間はわずかに長かったにもかかわらずです（約54時間に対して約57時間）。

スコアを自分自身で良い、あるいは悪いと評価してはなりません。実際に使用に適しているかどうかを判断するのは、流暢な話者です。

## 協力できる時間を尋ねる

`improve-time`ステップ（モード`ask_user`）では、話者がどれくらいの時間を割けるかを尋ねます：`per_week`と`total`であり、それぞれ**話者が言ったとおりの言葉**で記録します（「週にたぶん30文くらい」「数時間やってみて、それから考える」など）。これは`champollion improve time`によって`improve/time.json`に記録されます。各ラウンドの文数はこれに基づいて計画され、レポートはこの時間と予測を比較します。

- **注意。** 尋ねるのは1回だけにしてください。それ以上無理に聞き出そうとしてはいけません。分からないと言われたら、その発言をそのまま受け取ってください — 曖昧な言葉も立派な答えです。
- **注意。** 残り時間として話者が伝えてくれた量よりも多くの文が予測で必要とされる場合、その旨を率直に伝え、レポートに挙げられている選択肢（話者を増やす、プロジェクトの協力者を募る、あるいは現時点での目標を絞り込んで最も必要な文のフレーズ集を目指すなど）を提示してください。その上で、人々に選んでもらいます。

## レールが提示する提案

**より良いモデルの実用化を提案する**（forgeステート`improve-promote`、モード`confirm`）。新モデルが開発セットで測定可能なほど優れていた場合、または開発セットでは判断できず（**too-few**または**no-change**）、ブラインド評価を行った話者が新モデルを明らかに高い頻度で正解とした場合です。その際、forgeの`why`に話者の集計値が追加されます。*「同じ訪問時のブラインド評価において、話者は新しい文B件中A件（P%）で新モデルを正解とし、D件中C件（Q%）で使用中のモデルを正解としました — 明らかな差があります：家族が必要としている文において、新モデルの方が優れています。」* どちらの理由であったかを伝えてください。これはあくまで提案であり、判定だけでは何も変わりません。実用化するとページやアプリの応答内容が変わるため、ステップを実行する前に確認してください。「今はしない」の場合は`declined: true`とします。人々の承認（ステップの`export`および`choose`）があって初めて実用化されます。それまでは、レポートに*「測定可能な改善：実用化されていません — 人々が選択していません」*と表示され、そこからの数値上昇は進捗としてカウントされません。話者の評価に基づいて選択されると、ラウンドの行には*「話者のブラインド評価に基づいて実用化済み」*と表示されます。

**より強力なモデル**（forgeステート`improve-stronger-model`、モード`ask_user`）。
開発セットで判定可能なラウンドが2回連続で向上が見られなかった後 — ともに**no-change**または**worse**（**too-few**のラウンドはカウントされません）—、前回のモデル変更（プリセットの切り替え、または人々が`choose`で実用化したモデル。話者の評価による昇格も含みます）からカウントして、極小モデル（tiny）が使用されている場合、レールはByT5-small — `byt5-small`、またはGPUのトレーニング用メモリが8〜15 GBの場合は`byt5-small-lowmem`（ステップあたりのメモリ消費が少なく、処理は遅くなります）— を提案します。約1.2 GBのダウンロードと長時間のトレーニングが必要で、AppleシリコンまたはNVIDIA GPUでの実行が最適です（[トレーニング](/docs/agents/training#models)）。回答スロットは`try_it`（`yes`または`not-now`）です。forgeの`why`の内容をそのまま伝えてください — 開発セットが小さすぎてラウンドの向上を確認できない場合は、わずかな向上が隠れている可能性があることを伝え、そうでない場合は、その2回のラウンドで*「開発文で確認できる変化がありませんでした（約X chrF++ポイント以上）：各ラウンドによる向上幅がそれより小さいか、あるいは変化がないかのどちらかです」*と伝えます。文を増やしても役に立たないとは書かれていませんし、あなた自身もそう言ってはなりません。「今はしない」もこのステップの回答の1つです：`try_it: "not-now"`を渡します（MCP経由では、ここでは`declined: true`は拒否されます）。forgeはそれを記録し、使用中のモデルを維持します。この提案は、同様のラウンド（**no-change**または**worse**）がさらに2回続いた後にのみ再度表示されます。どちらの回答でも構いません。決めるのは人々です。

**予測の判定。** テストセットのスコアが出た後、事前に書いた予測が的中したかどうか（`held`または`missed`）および誰が判定したかを人々が伝えます。予測とスコア（範囲付き）を読み上げてください。人々に代わって判定してはなりません。

**まだ同意していない話者。** `waiting_for_agreement`内のファイルについては、セッションごとに1回、穏やかに尋ねられます。そのファイルに含まれる言葉の主全員が同意したという、その人からの「はい（yes）」という回答のみがこれに応答できます。
