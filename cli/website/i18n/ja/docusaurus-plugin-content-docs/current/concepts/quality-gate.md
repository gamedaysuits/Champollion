# クオリティゲート

すべての翻訳は、ディスクに書き込まれる前に決定論的な検証ゲートを通過します。クオリティゲートは、機械翻訳によくある失敗パターンを検出します — サイレントフォールバックなし、ロケールファイルへのゴミデータの書き込みなし。

## 検証チェック

| チェック | 検出内容 | ゲートラベル |
|-------|----------------|-----------|
| **空/空白** | モデルが空の文字列または空白を返した | `[GATE] empty` |
| **ソースのエコー** | モデルが元の英語の入力をそのまま返した | `[GATE] source-echo` |
| **ハルシネーションループ** | 繰り返されるトライグラムパターン (例: `"Qo' Qo' Qo'"`) | `[GATE] hallucination` |
| **長さの膨張** | 出力がソースよりも大幅に長い | `[GATE] length` |
| **コンテンツの削除** | 出力がソースから文字を削除したものである | `[GATE] content` |
| **文字体系の準拠** | ターゲットロケールに対して間違った文字体系 (スクリプト) | `[GATE] script` |
| **ICU複数形カテゴリ** | ロケールに必要な複数形が欠落している | `[GATE] icu-plural` |

[`noTranslate`](/docs/getting-started/configuration#no-translate) で宣言されたキーはゲートに到達しません。これらはソースからそのままコピーされるため、検証する内容がありません。

### 空白/ブランク

空文字列、空白のみ、または`null`の翻訳を拒否します。難しいキーに対してモデルが何も返さないケースを検出します。

### ソースエコー

モデルが翻訳せずに英語のソーステキストをそのまま返した場合を検出します。短い文字列や指定が不十分なプロンプトでよく発生します。

短い、ほぼASCIIのみの文字列（30文字以下）は免除されます。`"Blog"`、`"GitHub"`、`"npm"` はどこでも英語のままであるのが正当であり、これらを拒否すると無限ループに陥るためです。

URL、リポジトリパス、製品識別子など、変更しなくても正しい長い値は、ゲートの問題ではなく、ゲートを調整しても修正できません。正解はエコー*そのもの*であるため、モデルの出力はすべて間違いになります。これらのキーを [`noTranslate`](/docs/getting-started/configuration#no-translate) で宣言すると、パイプラインを完全にバイパスします。URLを値に持つキーは、デフォルトでそのように処理されます。

### ハルシネーションループ

出力内のトライグラム（3文字）パターンを分析します。出力の長さに対して特定のトライグラムが閾値を超えて繰り返される場合、翻訳は拒否されます。`"Qo' Qo' Qo' Qo' Qo'"`のような異常な出力を検出します。

### 長さの膨張

出力の長さが`maxLengthRatio × source length`（デフォルト：4倍）を超える翻訳を拒否します。短い入力に対して大量のテキストを生成するモデルのハルシネーションを検出します。

設定ファイルの`maxLengthRatio`で変更できます。

### コンテンツの削除

長さの膨張の逆です。文字列に対する語彙を持たないモデルは、翻訳できないすべての文字を削除し、ソースの句読点と空白だけを残すことがあります。

```
"low-resource nmt · tokenizers · nêhiyawêwin"  →  "   ·   · êhiêi"
"the simple-builder approach"                  →  "  "
```

他のチェックではこれを検出できません。空でもなく、エコーでもなく、反復でもなく、ソースの*長さ*の33%であるため、`minLengthRatio` を余裕でクリアしてしまいます。

このチェックでは、ソースと出力の間で**コンテンツ文字**（句読点、空白、不可視のフォーマットを無視した文字と数字）を比較します。しかし、密度だけをルールにすることはできません。なぜなら、正当で密度の高い文字体系（スクリプト）もまったく同じ位置に存在するからです。

| ソース | 出力 | 保持されたコンテンツ | 判定 |
|--------|--------|------------------|---------|
| `low-resource nmt · tokenizers · nêhiyawêwin` | `   ·   · êhiêi` | 14% | **拒否** |
| `Getting started` | `入门` | 14% | 承認 |
| `Frequently asked questions` | `常见问题` | 17% | 承認 |

最初の例を検出するようなしきい値を設定すると、中国語、日本語、韓国語が完全に拒否されてしまいます。これらを区別するのは、どれだけ残ったかではなく、*それがどこから来たか*です。中身が空っぽになった出力は、それ自身のソースの**部分列 (subsequence)**（ソースから文字を削除することで生成可能）ですが、実際の翻訳はソースと本質的に何も共有しません。フラグを立てるには**両方**のシグナルが必要であるため、このチェックは反復検出器と同様に、必要条件ではありますが十分条件ではありません。

ペアごと、または言語ごとに `minContentRetention`（デフォルトは `0.35`）で設定可能です。この値を上げるとチェックがより厳格になります。このチェックは常に部分列シグナルと同時にのみ発動します。

:::note[これは語彙のシグナルであり、品質のダイヤルではありません]
あるターゲット言語でこれが繰り返し発動する場合、モデルはそのテキストに対する語彙を持っていません。これは通常、閉じた語彙を持つ言語における、短くて専門用語が密集した文字列で発生します。しきい値を緩めると、静かな破損が復活するだけで、翻訳が生成されるわけではありません。プロンプト、コーチングデータ、またはペアを修正してください。
:::

### スクリプト準拠

言語カードに非ラテン文字体系（アラビア文字、CJK、キリル文字など）が記録されているロケールの場合、出力に実際に非ASCII文字が含まれているかを検証します。これらのロケールに対するラテン文字のみの出力は、間違った文字体系として拒否されます。

このチェックが*該当しない*2つの点について明確にしておきます。

- **`script:` 設定フィールドによって駆動されるわけではありません。** このフィールドは、[文字体系の変換](/docs/getting-started/configuration#script-conversion) のための出力正書法を選択します。ゲートの期待値は言語カードから取得されます。
- 常に、文字体系の変換が行われる*前*に、**モデルが出力する作業用文字体系 (working script)** を検証します。文字体系コンバーターを持つロケール (crk、sr、tlh など) は、正しくラテン文字の作業用文字体系を出力するため、このチェックは免除されます。設定で有効になっている場合、変換はゲートの後に実行されます。

## 失敗時の動作

1. 失敗した翻訳は`[GATE]`プレフィックス、キー名、理由、および値のプレビューとともにstderrに記録されます
2. そのキーはロケールファイルに**書き込まれません**
3. リトライカスケードが開始されます（以下を参照）

```
[GATE] hero.title: source-echo — "Welcome to our platform"
[GATE] nav.about: hallucination — "À À À À À À À À"
```

## フィードバックの再試行と再試行カスケード

ゲートによって拒否されたキーは、**1回のフィードバック再試行**を受けます。拒否の理由は、キーごとのコンテキストとしてプロンプトに注入されます（低い温度パラメータでの盲目的な再試行では、バイト単位で同一の出力が返されるためです）。再試行に合格した場合、キーは書き込まれ、同期は**グリーン（成功）**になります。自己修復するゲートの拒否は失敗ではなく、これが意図されたセマンティクスです。再試行後も失敗し続けるキーのみがスキップされ、報告され（同期はゼロ以外の値で終了します）、次回の同期で再試行されます。

再試行は、LLM、Google Translate、DeepL、または直接のプロバイダーなど、ペア自身の翻訳メソッドを通じて実行されます。これは翻訳メモリ (Translation Memory) のヒットにも適用されます。ゲートが拒否したキャッシュ値は破棄され、同じ実行内で再翻訳されるため、汚染されたキャッシュは自己修復されます。

これとは別に、バッチ全体が失敗した場合（JSON解析エラーなど）、Champollionはバッチサイズを段階的に小さくして再試行します。

```
Full batch (80 keys) → parse error
  └→ Half batch (40 keys) → 2 failures
      └→ Individual keys (1 each) → isolates the 2 problem keys
```

リトライの上限は`maxRetries`（デフォルト：3、言語ごとに設定可能）によって制限されます。これにより、継続的に失敗するキーに対するトークンの過剰消費を防ぎます。

リトライを使い果たした後、問題のあるキーはログに記録されてスキップされます。次回の`sync`実行時に再試行されます。

## プロンプトキャッシング

システムメッセージ（レジスター、文法ルール、スタイルノート）はユーザーメッセージ（翻訳するキー）から分離されています。この分離には意図があります：

- システムメッセージは特定のロケールに対して**バッチ間で同一**です
- AnthropicやGoogleなどのプロバイダーは繰り返されるシステムメッセージをキャッシュします
- 結果：最初のバッチはフルトークンコストを支払い、以降のバッチはユーザーメッセージ分のみを支払います

これにより、多くのバッチを持つプロジェクトのトークンコストを大幅に削減できます。

## ICU MessageFormat検証

`integrity`コマンドは、ICU MessageFormatの複数形パターンをCLDR複数形ルールに対して検証します。ソースファイルが以下のようなICU構文を使用している場合：

```json
"items": "{count, plural, one {# item} other {# items}}"
```

Champollionは、翻訳済みバージョンにターゲットロケールで必要なすべての複数形カテゴリが含まれているかを検証します。たとえばアラビア語では、`one`と`other`だけでなく、6つのカテゴリ（`zero`、`one`、`two`、`few`、`many`、`other`）が必要です。

`champollion integrity`を実行して、すべてのロケールの複数形の完全性を確認してください。

## 用語の適用

辞書を持つコーチングペアに対して、champollionは翻訳後に用語チェックを実行します。クオリティゲートを通過した後、LLMが必要な辞書用語を実際に使用したかどうかを検証します。

```
[TERM] en→fr: 2 term violation(s)
  • hero.title: "dashboard" → expected "tableau de bord" but got "panneau de contrôle"
```

用語の違反は**警告であり、ブロッキングエラーではありません**。翻訳は引き続きディスクに書き込まれます。これは意図的な設計です — LLMが代替表現を選択する正当な理由（文脈、文法）がある場合もあり、用語の不一致でブロックすると利益よりも害が大きくなります。

違反を修正するには、コーチング辞書を更新するか、ロケールファイルを手動で編集してください。
