# クオリティゲート

すべての翻訳は、ディスクに書き込まれる前に決定論的な検証ゲートを通過します。クオリティゲートは、機械翻訳によくある失敗パターンを検出します — サイレントフォールバックなし、ロケールファイルへのゴミデータの書き込みなし。

## 検証チェック

| チェック | 検出対象 | ゲートラベル |
|-------|----------------|-----------|
| **空 / 空白** | モデルが空文字列または空白文字を返した | `[GATE] empty` |
| **原文のエコー** | モデルが元の英語の入力をそのまま返した、あるいは偽装して（アクセント、大文字・小文字、全角文字など）、値全体または一部の複数形において返した | `[GATE] source-echo` |
| **ICU / プレースホルダーの構造** | 翻訳されてしまった変数、複数形のキーワードやセレクター、欠落した `#` や `%s` | `[GATE] icu` |
| **マークアップ** | 原文と異なる開きタグ、閉じタグ、またはネスト構造 | `[GATE] markup` |
| **プレースホルダー前後の文末区切り** | 原文にはない場所で、翻訳がプレースホルダーの直前または直後に置いた文末記号: `Take this medicine at {time}.` → `… sina. {time}.` | `sentence break beside a placeholder` |
| **ハルシネーションのループ** | 繰り返されるトリグラムパターン（例: `"Qo' Qo' Qo'"`） | `[GATE] hallucination` |
| **極端な文字数増加** | 出力が原文より著しく長い | `[GATE] length` |
| **内容の削除** | 原文から文字が削除されたような出力 | `[GATE] content` |
| **文字体系の準拠** | ターゲットロケールに不適切な文字体系 | `[GATE] script` |
| **異なる入力に対する同一出力** | 複数の異なる原文文字列に対して1つのテキストが返された（暗記された文） | `[GATE] shared-output` |
| **ICU複数形カテゴリ** | ロケールに必要な複数形が欠落している | `[GATE] icu-plural` |

[`noTranslate`](/docs/getting-started/configuration#no-translate) と宣言されたキーはゲートに到達しません。原文からそのまま逐語的にコピーされるため、検証するものがないからです。

**Markdownページもブロック単位で同様のチェックを受けます。** コンテンツフォルダー（`contentDir`、Docusaurusのdocs）では、見出し、段落、リスト項目、表の各セルがそれぞれ個別にチェックされ、front-matterの各フィールドも同様にチェックされます。チェック内容は上記と同じです。空、原文のエコー、ハルシネーションのループ、極端な文字数増加、内容の削除、文字体系、異なる入力に対する同一出力などです。`## Feast` のような短い見出しが完全な1文として返ってきた場合は、同じテキストを持つアプリのキーと同様に拒否されます。

拒否されたブロックは、**理由を添えてもう一度モデルに要求されます**。モデルには何に問題があったのかが伝えられ、記述どおりで正しいテキストは変更せずに返してもよいことが示されます。拒否の中には、固定されたルールでは判断できないものもあります。名前である見出し（`### BLEURT (Sellam et al., 2020)`）、参考文献リストのエントリ、コード表、用語解説などは、記述されたままで正しい場合もあれば、翻訳漏れの可能性もあります。ブロックが変更されずに返された場合、あるいは非ラテン文字言語でラテン文字のまま保持され、モデルが再度同じ回答を返した場合、その回答は意図的なものとして受け入れられます。それ以外の拒否はすべて、2回目の回答で完全にゲートを通過しなければなりません。指示に従わないことを宣言しているエンドポイント（`"acceptsInstructions": false`）には再問い合わせを行わず、その初回の回答が2回目の回答と同様に判定されます。

それでも拒否されたものは、そのペアの `fallback` メソッドに渡されます。フォールバックがない場合、**ブロックはページにマーカーを追加することなく原文テキストを保持し**、キャッシュされることはなく、ページのロックエントリには `pending:<hash>` と記録されます。`status` や `verify` はそのようなページを一覧表示し、sync は各ブロックの名前を出力します。この拒否は記憶されるため、次回の通常の sync ではそのブロックを同じモデルに再度送信しません（[拒否されたMarkdownブロックとfront-matterフィールド](#refused-markdown-blocks-and-front-matter-fields) を参照）。ブロック内のコード、リンク、マークアップは個別に保護され、HTMLコメントは一切送信されません。一部のテキストは、問い合わせを受けることなくそのまま保持されます:
- 短い名前（`## GitHub`）。インラインコード、引用符、括弧、`{#anchor}` を除いて判定されます。
- 参考文献リストのエントリ、または1つのブロック内の参考文献リスト全体。
- 原文自体に含まれている全角文字。

表はパイプや区切り行ではなく、各セル単位で判定されます。`verify` は、すでにディスク上にあるブロックを同様にチェックします（ただし、sync が受け入れて原文用としてキャッシュしたものと完全に一致するブロックを除きます）。不合格となったブロックは警告となり、`verify --strict` でエラーとなります。また、修復コマンド `champollion sync --pair en:fr --redo files:<page>` が提示されます。sync も同じファイルに対して同じコマンドを出力します。

### 空白/ブランク

空文字列、空白のみ、または`null`の翻訳を拒否します。難しいキーに対してモデルが何も返さないケースを検出します。

### ソースエコー

モデルが翻訳せずに英語の原文テキストを返したケースを検出します。短い文字列や、指示が不十分なプロンプトでよく発生します。2つのルールが適用され、それぞれ異なる観点を測定します:

1. **完全なコピー**（原文とバイト単位で一致するもの）は拒否されます。ただし、**短く、大半がASCII**の値（30文字以下で80%以上がプレーンASCII）は除外されます。`"Blog"`、`"GitHub"`、`"npm"` は英語のままであることが妥当なため、ラテン文字のターゲット言語ではこのようなコピーが受け入れられます（`verify` はこれを原文のエコーとして一覧表示します）。非ラテン文字のターゲット言語では、それが名前であるかどうかモデルに1回確認され、同じ回答が2度返された場合は名前として受け入れられます。**この例外は長さに基づくものであり、完全なコピーのみに適用されます。**
2. **偽装されたコピー**（大文字・小文字、アクセント、空白、不可視文字、互換形式（全角文字、合字）のみが変更された原文）は、原文に文字を含む単語が**3語以上**ある場合（`{count}` や `%s` などのプレースホルダーやマークアップタグは含みません）、**どれほど短くても**拒否されます。`"Book an appointment"`（19文字、3語）→ `"Bóok án appóintment"` は拒否されますが、`"cafe"` → `"café"`（1語）は受け入れられます。本物の翻訳であっても英語との違いがアクセントのみという場合があるためです。妥当にアクセントが付加される長い名前（`"Universite de Montreal"`）は、アクセント付きの綴りを保護対象用語として宣言すれば受け入れられます。

両方のルールは**各複数形**にも同様に適用されます。gettext の `msgstr[n]` 複数形、ICU の `{n, plural, …}` 分岐、i18next の `_one`/`_other` キーは、単数形の値と同じルールが適用されます。例えば、ロシア語の複数形で `few` 形式がアクセント付きの英語として返された場合、単数形と同様に拒否されます。

変更しないことが正しい長めの値（URL、リポジトリのパス、製品識別子など）は、ゲートの問題ではなく、ゲートの調整で解決できるものでもありません。正しい答えがエコーそのものであるため、モデルのあらゆる出力が不正とみなされてしまいます。これらのキーは [`noTranslate`](/docs/getting-started/configuration#no-translate) で宣言してください。パイプライン全体をバイパスするようになります。URL値を持つキーはデフォルトでそのように処理されます。

### ハルシネーションループ

出力内のトライグラム（3文字）パターンを分析します。出力の長さに対して特定のトライグラムが閾値を超えて繰り返される場合、翻訳は拒否されます。`"Qo' Qo' Qo' Qo' Qo'"`のような異常な出力を検出します。

### 長さの膨張

出力の長さが `maxLengthRatio × source length`（デフォルト: 4倍）を超える翻訳を拒否します。厳密に「超える」場合であり、ちょうど4倍の翻訳は合格します。これにより、短い入力に対して大量のテキストを出力してしまうモデルのハルシネーションを検出します。

設定ファイルの`maxLengthRatio`で変更できます。

### 内容の削除

極端な文字数増加の裏返しです。文字列に対する語彙を持たないモデルは、翻訳できない文字をすべて削除し、原文の句読点や空白だけを残してしまうことがあります:

```
"low-resource nmt · tokenizers · nêhiyawêwin"  →  "   ·   · êhiêi"
"the simple-builder approach"                  →  "  "
```

これを検出できるチェックは他にありません。空ではなく、エコーでもなく、反復的でもなく、原文の「長さ」の33%であるため `minLengthRatio` も余裕でクリアしてしまいます。

このチェックでは、原文と出力の間で**内容文字**（句読点、空白、不可視の書式設定を無視した文字や数字）を比較します。しかし、正当な文字密度の高い文字体系もまったく同じ数値帯になるため、密度だけをルールにすることはできません:

| 原文 | 出力 | 保持された内容 | 判定 |
|--------|--------|------------------|---------|
| `low-resource nmt · tokenizers · nêhiyawêwin` | `   ·   · êhiêi` | 14% | **拒否** |
| `Getting started` | `入门` | 14% | 合格 |
| `Frequently asked questions` | `常见问题` | 17% | 合格 |

最初の例を検出するようないかなるしきい値も、中国語、日本語、韓国語をことごとく拒否してしまいます。両者を分けるのは、どれだけの文字が残ったかではなく、それらが「どこから来たか」です。骨抜きにされた出力は自身の原文の**部分列（subsequence）**（原文から文字を削除することで生成可能）であるのに対し、本物の翻訳は原文と基本的に共通点がありません。警告のフラグを立てるには**両方**のシグナルが必要となるため、このチェックは反復検出機能と同様に必要条件であっても十分条件ではありません。

`minContentRetention`（デフォルト: `0.35`）を介して、ペア単位または言語単位で設定可能です。値を引き上げるとチェックがより厳格になりますが、部分列シグナルと同時に検知された場合にのみ発動します。

:::note[これは品質の調整つまみではなく、語彙に関するシグナルです]
特定のターゲット言語でこれが繰り返し発生する場合、モデルはそのテキストに対する語彙を持っていません。語彙体系の閉じた言語における、専門用語が密集した短い文字列などで典型的に起こります。しきい値を緩めても、無音の破損が元に戻るだけであり、翻訳が生成されるわけではありません。プロンプト、コーチングデータ、またはペアを修正してください。
:::

### スクリプト準拠

言語カードに非ラテン文字体系（アラビア文字、CJK、キリル文字など）が記録されているロケールに対して、出力がラテン文字のみになっていないかを検証します。文字はバイト単位ではなく、**Unicodeスクリプト**によって分類されます。アクセント付きラテン文字（`"Bóók"`）や全角ラテン文字（`"Ｂｏｏｋ"`）はラテン文字であるため、どちらもロシア語としては合格しません。全角ラテン文字は、CJKタイポグラフィ（日本語で `"ＯＫ"` のような日常的な用法がある環境）以外のターゲットでは拒否されます。これらは英語の偽装にすぎないためです。通常の許容事項は適用されます。記述どおりに保持された短い名前（上記の「名前かラベルか」の確認）、宣言された保護対象用語、および `noTranslate` キー（URLなど）がこのチェックで不合格になることはありません。

このチェックが「対象としていないもの」についての2つの明確化:

- **`script:` 設定フィールドによって制御されるわけではありません。** そのフィールドは[文字体系の変換（script conversion）](/docs/getting-started/configuration#script-conversion)のための出力正書法を選択するものであり、ゲートの判定基準は言語カードから得られます。
- 常に、いかなる文字体系の変換よりも**前**に、**モデルが出力する作業用スクリプト（working script）**を検証します。スクリプトコンバーターを持つロケール（crk、sr、tlh など）は正しくラテン文字の作業用スクリプト出力を生成するため、このチェックから除外されます。設定で有効にされている場合、変換処理はゲート通過後に行われます。

### マークアップ

タグはコードです。タグ名ごとに、翻訳は原文と同じ数のタグを開き、閉じ、自己終了させ、同じようにネストしなければなりません（`<a>` 内の `<b>` は `<a>` 内にとどまります）。語順に伴って兄弟要素の順序が変わることは問題ありません。`"Please <strong>book</strong> now"` → `"Veuillez <strong>réserver maintenant"` は拒否されます。閉じタグの欠落はページを破損させるためです。複数形メッセージでは、各フォームが翻訳元の原文フォームと比較されます。`verify` はファイルに対して同様のチェックを実行します。

### プレースホルダー前後の文末区切り

プレースホルダーは実行時に値が挿入されるため、翻訳によってその直前直後に文末記号が置かれると、読者に見える内容が変わってしまいます。例えば `"Take this medicine at {time}."` → `"… sina. {time}."` では、時刻が独立した1つの文として表示されてしまいます。ゲートは、原文に記号がないにもかかわらず、プレースホルダーの直**前**、あるいは後ろにテキストが続くプレースホルダーの直**後**に文末記号（`.`、`!`、`?`、または他の文字体系の記号: `。`、`？`、`।`、`؟`、`።`、`᙮` など）を置き、翻訳全体の文末記号の数が原文より多くなっている翻訳を拒否します。プレースホルダーが文末に移動しただけの場合（`"Shipped by {carrier} on {date}."` → `"Expédié le {date} par {carrier}."`）は合格します。省略記号、小数点、ファイル名（`{host}.com`）、および1文字の略語（`"M. {name}"`）も同様に合格します。プレースホルダーの前にある長めの略語（`"ca. {count}"`）は文末記号と区別がつかないため拒否され、ペアのフォールバックか、言い換えられた回答が処理を引き継ぎます。`verify` はディスク上の同様の値を検出し、再問い合わせを行う `--redo` コマンドを表示します。ICUの複数形および select メッセージはICUチェックに委ねられます。

### 異なる入力に対する同一出力

訓練文を丸暗記したモデルは、未知の文字列に対してその暗記した文を返してしまうことがあります。アプリのタイトル、「Contact the school」、ニュースレターのタイトルとその見出しに対して同一の文が返され、それぞれ単体では上記のチェックをすべて通過してしまうようなケースです。あるロケールの実行において、1つの翻訳が**3つ以上の異なる原文文字列**に対して返され、それが4単語以上であるか、あるいは各原文が2単語以上で共通点がほとんどない場合、それらのキーは拒否されます（これによりリトライが行われ、その後フォールバックが処理します）。証拠が強力な場合は、**2つ**の異なる原文文字列でも十分です。両方が2単語以上で、共通の単語が半分未満であり、共通の翻訳が4単語以上ある場合です（`"Thank you for coming!"` と `"Please bring the forms."` が1つの文で返された場合など）。このようにして検出された文はそのロケール用に記憶されます。以降の sync で1つの文字列に対してであってもその文が返された場合は拒否され、すでにその文を提供していたキャッシュエントリは削除されるため、再実行（redo）時はキャッシュから書き込むのではなくモデルに再度問い合わせます。類義語が1つの短い翻訳に集約される場合（`"OK"`/`"Okay"`/`"Sure"` → `"D'accord"`、`"Close"`/`"Dismiss"` → `"Fermer"`）や、複数のキーで同じ原文テキストが使われている場合は合格します。その実行に含まれるコンテンツファイルのMarkdownブロックやfront-matterフィールドも対象としてカウントされ、ICUの複数形や select メッセージの各分岐も同様です（1つの複数形の各分岐は1つの原文としてカウントされます。数の屈折を持たない言語では各分岐に同じテキストが書かれるためです）。出力の比較では大文字・小文字、句読点、Markdownのブロックマーカーは除外されるため、`"S?"`、`"S."`、および見出しの `# S` は同一の出力とみなされます。このカウントにはロケールがすでにディスク上に保持している内容やキャッシュが提供し得る内容も含まれるため（別のツールによって1テキストずつキャッシュされた文は、キャッシュの時点で拒否され、書き込まれません）、1回の sync ごとに1キーずつ追加された場合でも検出されます。`verify` はディスク上の同様のパターンで失敗し、MCP の `translate` ツールは呼び出し内でこれを拒否します。

### 疑問符が失われた疑問文

原文が `?` や `!` で終わっているにもかかわらず、翻訳がその記号でもその言語体系で使用される同等の記号（`？`、`؟`、ギリシャ語の `;`、`¿…?`、`！` など）でも終わっていない場合、`sync` と `verify` は警告を発します。`"Where does it hurt?"` が平叙文として書かれると、平叙文として読まれてしまうためです。一部の言語では記号の代わりに単語や助詞で疑問文を表すため、これは拒否ではなく警告となります。警告にはキーの名前と、再度問い合わせるための `--redo keys:<key> --fresh` コマンドが示されます（キャッシュに回答が保持されているため、`--fresh` が使用されます）。

## 失敗時の動作

1. 不合格となった翻訳は、`[GATE]` プレフィックス、キー名、理由、および値のプレビューとともに stderr にログ出力されます
2. そのキーはロケールファイルに書き込ま**れません**
3. リトライカスケードが作動します（下記参照）
4. それでも失敗した場合、その拒否は**記憶されます**（[拒否されたキーの保留](#refused-keys-are-held-back) を参照）

```
[GATE] hero.title: source-echo — "Welcome to our platform"
[GATE] nav.about: hallucination — "À À À À À À À À"
```

## フィードバックリトライとリトライカスケード

ゲートによって拒否されたキーには、**1回のフィードバックリトライ**が行われます。拒否理由がキーごとのコンテキストとしてプロンプトに注入されます（低い temperature でフィードバックなしに再試行しても、バイト単位で同一の出力が返されるためです）。リトライが合格した場合、キーは書き込まれ、sync は**成功（green）**となります。自動修復されたゲートの拒否は失敗とはみなされず、これが意図されたセマンティクスです。リトライ後も不合格のままのキーはスキップされて報告されます（sync は `2` で終了します）。

リトライは、そのペア自身の翻訳方法（LLM、Google Translate、DeepL、または直接プロバイダーなど、何であれ）を通じて実行されます。フィードバックを読み取るのはLLMメソッドのみです。実行時の行にその旨が表示されます（`retrying with feedback` または `asking once more (deepl takes no instructions…)`）。`api` エンドポイントは、`"acceptsInstructions": true` を宣言している場合（ペア上またはプラグインマニフェスト内）にのみフィードバックを受け取ります。`false` を宣言しているエンドポイント（`nmt-forge serve` などの訓練済みNMTモデル。再問い合わせしても同じ回答を返すため）には一切再問い合わせを行いません。その回答は2回目の回答と同様に判定され、拒否されたものはペアのフォールバックに送られます。リトライは翻訳メモリ（Translation Memory）のヒットにも適用されます。ゲートが拒否したキャッシュ値は破棄され、同じ実行内で再翻訳されるため、破損したキャッシュは自動的に修復されます。

### 拒否されたキーの保留

拒否は、キーの**現在の原文テキスト**、および拒否された回答を生成した**メソッドとモデル**に対して、キー単位で `.champollion.lock` に記憶されます。DocusaurusのUI文字列（`i18n/<locale>/code.json` およびプラグインのJSONファイル）も、ファイルおよびID単位で同じルールに従います。次回の通常の `sync` では、そのキーを同じモデルに再送信しません（同じ回答に対して課金されてしまうためです）。また、保留されたキーの数と対処方法が表示されます:

- 再度問い合わせる: `champollion sync --redo keys:<key>`（または `--redo all`、`--fresh`）— キー名を指定することは明示的なリトライとなります。
- 別の方法で補完する: ペアに `"fallback"` メソッドを追加する（ペア自身のメソッドが拒否したキーに対して問い合わせが行われます）、記述どおりに維持する場合はキーを `noTranslate` にリストする、または手作業でファイルに翻訳を記述する。

保留されたキーは未翻訳扱いとなるため、それが埋められるまで sync は `2` で終了します。原文テキスト、モデル、またはメソッドを変更すると、保留は解除されます（拒否はそのモデルからのそのテキストに対するものであったためです）。キャッシュからの読み取りは引き続き行われます。保留は有料の呼び出しを止めるものであり、無料のキャッシュ読み取りを止めるものではありません。やり直し（redo）で完了できなかったキーのみが例外となり、後述します。

### 拒否されたMarkdownブロックとfront-matterフィールド

コンテンツファイル（`contentDir`、Docusaurus docs）についても同じルールが適用されます。ゲートが拒否したブロックやfront-matterフィールドは、そのブロックの**現在の原文テキスト**、および拒否された回答を生成した**メソッドとモデル**に対して、ページ、ブロック、ロケール単位で `.champollion-content.lock` に記憶されます。ブロックはその原文テキストによって識別されるため、段落を編集すると保留が解除されます。次回の通常の `sync` では同じモデルに再送信されず、どのページでいくつのブロックとフィールドが保留されたかが表示されます:

- 保留されたブロックは、補完されるまでマーカーなしでページ上に原文テキストを保持します。ページの残りの部分は書き込まれます。
- 保留されたfront-matterフィールドも同様に原文テキストを保持し、ページの残りの部分は書き込まれます。
- ページ全体を一括翻訳する場合（`contentSegmentation: "page"`）、その回答が保護されたブロックを破損させたりページを骨抜きにしたりしたときは、ページ全体が拒否されます。本文テキストによって記憶され、ページ全体が保留されます。補完されるまで書き込まれず、何も送信されません。本文を編集するか、ブロック分割に切り替えることで保留が解除されます。

以前のバージョンのゲートによる拒否は自動的に解除されます。チェックが緩和された場合、拒否されていた項目は redo なしで次回の sync 時に再度問い合わせが行われます。

優先順位はキーの優先順位と同様です:

1. redo の対象として指定されたページは常に送信されます: `champollion sync --redo files:<page>`、`--redo content`（全ページ）、`--retranslate`、または `--fresh` 以下のすべて。
2. それ以外の場合、拒否されたブロックやフィールドは保留されます。ペアにそれを拒否していない `fallback` メソッドがある場合、フォールバックに問い合わせが行われ、ペア自身のメソッドには問い合わせされません。
3. モデルまたはメソッドの変更によって保留が解除されます。ブロックの原文テキストの変更でも同様です。

キャッシュは引き続き最初に読み取られるため、保留は有料の呼び出しを止めるものであり、無料のキャッシュを止めるものではありません。別の方法（フォールバック、キャッシュ、または翻訳内に自分で記述した段落など。コンテンツフォルダーは手書きされた段落を保持します）で補完されたブロックは、その記録が削除されます。保留されたブロックやフィールドは未翻訳扱いとなるため、それが補完されるまで sync は `2` で終了します。今回の実行中にゲートが拒否したブロックについても同様です。ドライラン（dry run）を実行すると、実際の実行で何が保留されるかが一覧表示されます。

### 完了できなかった redo（再実行）

`--redo all`、`--redo keys:`、またはモデルの切り替え（`--redo all --fresh-on-model-change`）によってキーバリューファイルのキーが未翻訳のまま残った場合、それらは `.champollion.lock` に**保留中（pending）**として記録され、次回の通常の `sync` でモデルにもう一度問い合わせが行われます（キャッシュからではなくモデルから取得します。redo の目的は新しいモデルのテキストを得ることだからです）。`champollion status` はそれらを一覧表示します。そのリトライも拒否された場合、キーは保留中のままとなり（status に表示されます）、通常の拒否されたキーと同様に保留（hold back）されます。優先順位としては、`--redo`/`--fresh` で指定されたキーが常に送信され、保留中のキーはその1回のリトライを受け、拒否されたキーは保留されます。DocusaurusのUI文字列には保留中のリトライはありません。redo で拒否された場合、コンテンツブロックと同様に次回の通常の sync で保留されます。

これとは別に、バッチ全体が失敗した場合（JSONパースエラーなど）、Champollion はバッチサイズを段階的に小さくしながらリトライします:

```
Full batch (80 keys) → parse error
  └→ Half batch (40 keys) → 2 failures
      └→ Individual keys (1 each) → isolates the 2 problem keys
```

リトライの上限は`maxRetries`（デフォルト：3、言語ごとに設定可能）によって制限されます。これにより、継続的に失敗するキーに対するトークンの過剰消費を防ぎます。

リトライを使い果たした後、問題のキーはログに記録されてスキップされます。使用可能な回答が得られなかったキー（レスポンスから欠落していたキー）は、次回の `sync` で再度問い合わせが行われます。ゲートが拒否したキーは、上記のとおり保留されます。

## プロンプトキャッシング

システムメッセージ（レジスター、文法ルール、スタイルノート）はユーザーメッセージ（翻訳するキー）から分離されています。この分離には意図があります：

- システムメッセージは特定のロケールに対して**バッチ間で同一**です
- AnthropicやGoogleなどのプロバイダーは繰り返されるシステムメッセージをキャッシュします
- 結果：最初のバッチはフルトークンコストを支払い、以降のバッチはユーザーメッセージ分のみを支払います

これにより、多くのバッチを持つプロジェクトのトークンコストを大幅に削減できます。

## ICU MessageFormat検証

`integrity`コマンドは、ICU MessageFormatの複数形パターンをCLDR複数形ルールに対して検証します。ソースファイルが以下のようなICU構文を使用している場合：

```json
"items": "{count, plural, one {# item} other {# items}}"
```

Champollionは、翻訳済みバージョンにターゲットロケールで必要なすべての複数形カテゴリが含まれているかを検証します。たとえばアラビア語では、`one`と`other`だけでなく、6つのカテゴリ（`zero`、`one`、`two`、`few`、`many`、`other`）が必要です。

### 翻訳で提供されなかった複数形

プロンプトにはターゲット言語のCLDRカテゴリが指定されます。通常のカウント（0から1000までの任意のカウント。例えばロシア語で 2, 3, 4 に対する `few` や 0, 5, 6 に対する `many`）で使用される複数形が欠落した状態で複数形メッセージが返された場合、ゲートは欠落しているフォームとそれがカバーする数値を指定して、モデルにもう一度問い合わせます。それらが含まれない2回目の回答は受け入れられ、3回目の問い合わせが行われることはなく、ツールによって自動補完されることもありません。その場合、sync は次の処理を行います:

- 各キーと欠落しているフォーム、および再度問い合わせるためのコマンド（`sync --redo keys:… --fresh`。より強力な `--model` が有効です）を明記して警告を出力します。
- `msgfmt` がすべての `msgstr[n]` を必要とする gettext カタログでは、欠落したフォームを `other` のコピーとして書き込み、エントリに `# champollion:` 翻訳者コメントを付与します（Poedit や Weblate で表示され、キャッシュのない CI 環境でも `verify` がこれを読み取ります）。
- ICUファイル（next-intl、ARB）では、届いたメッセージをそのまま書き込みます。アプリ側ではそれらの数値に対して `other` フォームが表示されます。

このようなメッセージは翻訳済みとして扱われません。別のメソッドやモデル（ローカルモデルの後にCIのホスト型モデルを実行する場合など、まだそのメッセージに回答していない構成）を実行する後続の sync では、キャッシュ（不完全な回答が保持されています）からではなくモデルから再度問い合わせを行います。見積もり（estimate）にもそのコストが計上されます。`sync --redo gaps` は、誰が残したかにかかわらず、そのようなすべてのメッセージに対して再問い合わせを行います。新しい回答でもフォームが不足している場合、メッセージはそのまま（カタログ内ではマークされた状態）維持され、`.champollion.lock` はどの設定がそれらのフォームなしで回答したかを記録するため、同じテキストについてそれらの設定に再度問い合わせることはありません（[CIガイド](/docs/guides/ci-cd#plural-gaps) を参照）。

`verify` は、修復コマンドとともに両方のケースを報告します。1000を超える数値や端数（分数・小数）でのみ到達するフォーム（フランス語やスペイン語の `many`、1 000 000 などで使用）には、警告ではなく情報（info）行が出力されます。機械翻訳エンジン（DeepL、Google など）にはどのフォームを出力すべきかを指示できないため、その回答に対してリトライは行われず、報告のみが行われます。i18next ファイルの場合、原文に存在しない各フォーム（英語からフランス語への翻訳における `count_many` など）は独自のキーとなり、`_other` テキストから翻訳されます。LLMにはそのフォームが要求され、sync にその旨が表示されます。機械翻訳エンジンの場合は、その値が `other` フォームを保持している旨が表示されます。

`champollion integrity`を実行して、すべてのロケールの複数形の完全性を確認してください。

## 用語の適用

辞書を持つコーチングペアに対して、champollionは翻訳後に用語チェックを実行します。クオリティゲートを通過した後、LLMが必要な辞書用語を実際に使用したかどうかを検証します。

```
[TERM] en→fr: 2 term violation(s)
  • hero.title: "dashboard" → expected "tableau de bord" but got "panneau de contrôle"
```

用語の違反は**警告であり、ブロッキングエラーではありません**。翻訳は引き続きディスクに書き込まれます。これは意図的な設計です — LLMが代替表現を選択する正当な理由（文脈、文法）がある場合もあり、用語の不一致でブロックすると利益よりも害が大きくなります。

違反を修正するには、コーチング辞書を更新するか、ロケールファイルを手動で編集してください。
